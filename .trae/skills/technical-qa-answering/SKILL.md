# Technical QA Answering

## 核心原则

这是一个面向通用问答与学习的“一轮一题”问答 skill。问题可以属于任何主题，可以由用户直接提出，也可以由助手主动生成。默认每轮只处理一个问题，并给出回答大纲和完整专业回答；只有用户明确要求测验模式时，才只提问并等待用户作答。

回答必须建立在资料检索之上：同时查询本地学习资料和外部资料，交叉验证关键结论，发现本地资料明显错误、过时或互相矛盾时，必须提示用户修正。

## 触发场景

使用本 skill：

- 用户直接提出一个需要详细、专业、完整回答的问题；
- 用户要求“提一题”“出一题”“问我一个问题”“讲一个问题并回答”；
- 用户要求记录、保存、写入某个问答；
- 用户说某次回答可作为“正面模版”或“反面模版”；
- 用户要求更新本地资料索引；
- 用户要求围绕任意主题做结构化问答，包括技术、学习、工作、生活、写作、决策、常识、项目、面试、AI、工程或其他问题。

普通闲聊或极简单问题可以简短回答；当用户需要详细、专业、完整、可追溯、可记录，或明确要求按“一轮一题 + 资料检索 + 专业回答”的方式处理时，执行本 skill 的完整流程。

## 场景分流

- 用户直接提问：将用户问题作为本轮唯一问题，执行“标准问答流程”，必须查 QA 历史、本地资料和外部资料。
- 助手主动出题：根据 QA 历史和资料缺口生成一个新问题，执行“标准问答流程”。
- 记录已有问答：执行“记录问题规则”，不要重新生成问题，不要改写原回答。
- 收录正反面模版：执行“正反面模版规则”，不要把收录动作扩展成新问答。
- 更新本地资料索引：执行“更新本地资料索引”，只更新本地索引，不把外部网页写成本地资料。

质量自检中的“同时查本地资料和外部资料”只强制适用于生成正式问答；记录、模版收录和索引更新按对应章节检查。

## 标准问答流程

### 1. 先查历史问题，避免重复或脱节

正式回答前必须读取：

1. `cx-learn-notes/QA/问题目录.md`；
2. 与当前主题相关的 QA 分类文档；
3. 必要时用 `rg` 在 `cx-learn-notes/QA` 中搜索关键词。

规则：

- 助手主动出题时，不能重复提出已经记录过的同一问题；
- 用户直接提问时，即使问题曾被记录，也要回答用户当前问题；但应提示已有相关记录，并在必要时复用或扩展历史内容；
- 可以在旧问题上继续深入，但必须换成更窄、更深或更工程化的角度；
- 如果旧问题是“浏览器渲染流程包含哪些阶段”，新问题可以是“为什么合成线程能降低部分动画的主线程压力”，但不能只是改写成“浏览器渲染流程是什么”。

### 2. 判断基础是否充足

正式回答或主动出题前，必须根据 `QA/问题目录.md`、相关分类文档和当前问题判断学习者是否具备必要基础。

规则：

- 如果基础问题记录不足，不要盲目深入到高阶问题；优先补齐概念定义、边界、最小流程、典型误区和基础对比。
- 如果用户直接提出高阶问题，但历史记录显示基础薄弱，仍要回答用户问题；但应先补一段必要前置知识，再进入高阶内容。
- 主动出题时按“基础 → 机制 → 工程实践 → 高阶权衡”的顺序推进，不能因为资料中有深度内容就直接出难题。
- 深度回答必须能被当前学习状态承接。若无法承接，应拆成更基础的一题，而不是输出大量高阶细节。

### 3. 每轮只给一题

默认每轮只处理一个问题，并立即给出完整回答。不要同时列多个候选题。

如果用户直接提出一个问题，就以用户的问题为本轮问题，不再额外生成新题。

如果用户一次提出多个独立问题，优先拆分并说明本轮先回答第一个；只有用户明确要求批量回答时，才可以一次处理多个问题。

如果用户要求“多给几题”，仍先给一题，并说明本 skill 按一轮一题推进。只有用户明确取消该约束时，才可批量输出。

### 4. 同时查本地资料和外部资料

本地资料检索：

- 先读 `references/local-source-index.md`，确定资料入口；
- 根据问题主题选择对应资料分类，例如前端基础、JavaScript、React、Vue、工程化、性能、网络、Node.js、项目复盘、算法、AI、Agent、MCP、音视频等；
- 用 `rg` 查找关键词，再读取具体文件，不要只依赖文件名。
- 如果本地目录没有找到相关资料，也必须说明“已检索本地资料但未找到直接相关内容”，并把它作为本地资料缺口记录在资料可靠性或完善建议中。

外部资料检索：

- 必须查询外部资料，优先使用官方文档、论文和权威工程文章；
- 优先级：官方文档 > 论文/标准 > 官方工程博客 > 框架仓库文档 > 普通博客；
- 常用权威来源包括标准组织、官方文档、论文、官方工程博客和主流框架文档。例如 MDN、WHATWG、W3C、TC39、Node.js、React、Vue、Vite、Webpack、Python、PostgreSQL、Git、GitHub、Anthropic、OpenAI、LangChain/LangGraph、Model Context Protocol、arXiv 等；
- 对框架 API、协议能力、产品特性和年份相关内容，要检查资料日期或当前文档，不要凭记忆回答。

最低证据要求：

- 每次正式回答至少使用本地资料和外部资料各一组；
- 对核心判断，尽量使用 2 个以上互相独立的资料来源交叉验证；
- 如果外部查询失败，必须明确说明“未能完成外部资料核验”，并降低结论确定性，不得伪造来源。

### 5. 甄别资料准确性

回答时区分三类内容：

| 类型 | 写法要求 |
| --- | --- |
| 事实 | 由论文、官方文档、标准或本地原文直接支持 |
| 分析 | 基于多个事实作出的解释，要说明推理链 |
| 推论 | 工程建议或抽象模型，要标注不是官方唯一定义 |

当本地资料与外部权威资料冲突时：

1. 优先采用外部官方资料或论文支持的事实；
2. 在回答中增加“本地资料修正提醒”；
3. 写清具体本地路径、冲突点、建议修正方向；
4. 不要静默改写本地资料，除非用户明确要求更新或修正。

## 回答结构

正式回答必须按下面顺序输出。

### 问题

只写一个问题。问题要具体，避免“大而泛”的题目。

- 用户直接提问时，可保留用户原问题；必要时可以轻微规范化标题，但不能改变问题含义；
- 助手主动出题时，需要基于 QA 历史和资料缺口提出新问题。

### 回答大纲

回答大纲必须出现在正式回答前，用来说明本次问题考察内容和核心思路。大纲不是摘要，不能替代详细回答。

至少包含：

- 本题考察什么；
- 核心判断；
- 回答思路；

### 正式回答

要求：

- 详细、专业、完整、清晰；
- 有条理，不写成零散摘要；
- 对关键概念给出定义、边界、对比和工程意义；
- 使用表格、分层列表、流程图文本或案例来解释复杂关系；
- 涉及框架用法、框架原理或手写代码相关知识点时，优先用代码或伪代码辅助讲解；除非用户指定其他语言，代码默认使用 TypeScript 实现。
- 不要用“简单来说”后只给一段短答收尾。
- 最后必须用 `专业回答总结：` 对本轮问题给出最终回答。

推荐展开方式：

1. 先给核心结论；
2. 再解释背景和概念边界；
3. 然后拆解机制、流程或架构；
4. 接着给工程例子或反例；
5. 最后总结判断标准和常见误区。

### 资料依据与可靠性

资料必须充足，不要新增资料依据与可靠性一节去列出资料，只在正文中引用即可。

### 本地资料修正或完善建议

如果本地资料有明显错误、缺口、过时或表述容易误导，必须写出修正建议。

如果没有发现明显问题，无需回复。

### 专业回答总结：

正式回答最后必须有这个小节，标题使用 `专业回答总结：`。

要求：

- 对本轮问题给出最终、可复述的专业回答，而不是复述大纲或只做摘要；
- 用一到三段收束核心定义、判断标准、工程结论和风险边界；
- 不引入新的未解释概念、新资料；

### 下一题建议

可选。只能给一个下一题建议，且不得替代本轮问题， 放在专业回答总结之后。

## 记录问题规则

默认禁止记录。只有用户明确说“记录问题”“保存这题”“写入 QA”“把刚才的问题记录下来”等，才允许写入 `cx-learn-notes/QA`。

记录步骤：

1. 读取 `QA/问题目录.md`，确认分类、已有编号和是否重复；
2. 选择或创建对应分类文档。相同知识点可放入同一个文档；
3. 追加完整问题和回答，必须保留原回答主体，不得摘要、改写或重构；
4. 更新 `问题目录.md`：
   - 增加问题编号、问题标题、状态、记录文档；
   - 更新“当前学习状态”中的已完成问题、已学习概念、易混淆概念；

如果当前对话里已经看不到原始完整回答，不要凭记忆重写成“原回答”。应先说明无法逐字复原，请用户重发，或只记录可追溯内容。

## 正反面模版规则

默认不写入模版。只有用户明确说“作为正面模版”或“作为反面模版”时才写入。

如果当前对话里已经看不到完整原回答，不要凭记忆重写或补全。应先说明无法保真收录，请用户重发原回答，或只收录用户明确提供的可追溯内容。

写入正面模版时：

- 目标文件是 `references/positive-answer-templates.md`；
- 记录问题、原回答、选入原因、可复用优点；
- 强调这是参考，不是机械模板；
- 提炼优点，例如内容详细、回答全面、表达清晰、逻辑严密、证据充足、问题新颖。

写入反面模版时：

- 目标文件是 `references/negative-answer-templates.md`；
- 记录问题、原回答、选入原因、主要问题、改进方向；
- 可标注问题类型，例如内容太少、回答片面、过于摘要、证据不足、晦涩难懂、结构混乱。

## 更新本地资料索引

当用户要求“更新本地资料”“刷新资料索引”“资料目录更新了”时，更新 `references/local-source-index.md`。

流程：

1. 扫描 `cx-learn-notes` 的目录和 Markdown 文件；
2. 识别新增、移动、删除或内容变化的本地资料，覆盖所有知识类型，不限定任何主题；
3. 保持现有索引结构：总览、按知识类型定位、快速定位清单、推荐使用方式；
4. 新增或修正条目时写清“用途、对应目录或文档、可定位内容”；
5. 不把外部网页写成本地资料索引，除非它已经被保存到本地目录；
6. 如果发现旧索引指向不存在路径，标注并修正。

## 质量自检

发送最终回答前检查：

- 是否只给出一个问题；
- 是否先查了 `QA` 历史记录；
- 是否判断基础知识是否足以承接本题深度；
- 是否同时查了本地资料和外部资料；
- 是否先给回答大纲，再给正式回答；
- 是否以 `专业回答总结：` 作为整次回答最后内容；
- 是否避免了摘要式短答；
- 涉及框架用法、框架原理或手写代码时，是否用代码或伪代码辅助讲解，且默认使用 TypeScript；
- 是否没有在用户未明确要求时写入 QA 或模版文档；
- 如果写文件，是否保持了既有目录和文档格式。

## 常见错误

| 错误 | 正确做法 |
| --- | --- |
| 只凭记忆回答问题 | 先查本地资料，再查外部权威资料 |
| 直接列多个问题 | 每轮只给一题 |
| 基础问题不足却直接深入 | 先补概念、边界、最小流程和典型误区，再逐步进入高阶内容 |
| 问题已在 QA 中记录仍重复提出 | 先查 `QA/问题目录.md` 和相关分类文档 |
| 只给摘要，没有完整回答 | 大纲后必须给专业、完整、可追溯的回答 |
| 框架用法、框架原理或手写代码只做抽象描述 | 用代码或伪代码辅助解释；未指定语言时默认 TypeScript |
| 回答结束没有最终收束 | 最后用 `专业回答总结：` 对本轮问题给出最终回答 |
| 默认把问答写入 QA | 只有用户明确要求记录才写 |
| 发现本地资料错误但不提示 | 明确写“本地资料修正提醒” |
| 把本地归纳说成官方定义 | 标注为本地框架或工程推论 |
| 把正反面模版当成唯一标准 | 只提炼可复用优点或问题，不机械套用 |
