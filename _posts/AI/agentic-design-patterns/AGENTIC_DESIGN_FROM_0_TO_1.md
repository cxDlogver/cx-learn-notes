## 1. 什么是 Agent Design

Agent Design，本质上是在设计一种能够围绕目标持续感知、思考、行动、纠偏并交付结果的系统。

它不是单次问答，也不是简单的提示词包装，而是把以下能力编排成一个整体：

- **目标定义**
- 任务分解
- 路由决策
- 工具调用
- 状态与记忆
- 反思与自我修正
- 安全约束
- 评估与监控
- 人类协同
- 多智能体协作

如果把传统 LLM 应用理解为“输入一个问题，返回一个答案”，那么 Agent 系统更像是“输入一个目标，系统自己组织过程，最后交付一个结果”。

## 2. 智能体和普通 AI 应用的区别

一个系统通常在满足下面几个条件时，才值得被视为“智能体系统”：

### 2.1 它有明确目标，而不只是回答问题

普通问答系统只负责响应输入。智能体系统需要围绕目标持续推进，例如：

- 完成一份市场调研报告这个过程通常能够称之为上下文工程
- 诊断一段代码中的问题并修复
- 帮用户规划旅行并执行预订流程
- 在知识库中完成多轮检索、比对和总结

### 2.2 它会管理过程，而不只是生成文本

真正的 Agent 不只“写答案”，而是会决定：

- 先做什么
- 后做什么
- 是否需要调用工具
- 是否需要重新规划
- 是否需要请求人工确认
- 当前是否已经完成目标

### 2.3 它会与环境交互

智能体的能力必须超出参数内知识，通常需要连接外部世界，例如：

- 搜索引擎
- 数据库
- 企业 API
- 文件系统
- 浏览器
- 代码执行环境

### 2.4 它会维护状态并处理不确定性

智能体执行的是过程型任务，因此要处理：

- 上下文偏离（Contextual Drift）
- 指令忽略（Instruction Neglect）
- 错误传播（Error Propagation）
- 幻觉（Hallucination）
- 工具失败
- 外部环境变化

所以 Agent Design 的重点从来不是“让模型更聪明一点”，而是“让系统在不确定条件下仍然可靠地完成任务”。

## 3. 先回答一个关键问题：什么时候应该做 Agent

不是所有问题都应该做成智能体。

### 3.1 适合做 Agent 的场景

- 任务是多步骤的
- 任务路径不是完全固定的
- 需要调用外部工具或外部知识
- 需要跨轮次保存上下文
- 需要根据中间结果动态调整策略
- 需要对结果做自检、评审或重试
- 需要人工审批或高风险控制

### 3.2 不适合做 Agent 的场景

- 规则完全固定
- 结果强确定性，适合传统程序直接实现
- 没有外部环境交互需求
- 不需要多步规划
- 成本、延迟要求极严，且任务逻辑简单

一个很实用的判断标准是：

如果“工作流”足够解决问题，就不要急着上“自主智能体”。

## 5. 从 0 到 1 的整体路线

如果你要从零开始做一个 Agent 系统，最合理的顺序不是把所有模式一次性堆上去，而是分阶段演进。

### 阶段 0：定义目标、边界和成功标准

先回答 4 个问题：

1. 这个智能体的目标到底是什么？
2. 它可以做什么，不能做什么？
3. 成功的结果如何衡量？
4. 失败时应该如何处理？

这一阶段要输出：

- 目标定义
- 输入输出契约
- 风险边界
- 是否需要人工审批
- 成本和延迟预算

### 阶段 1：把提示词打磨到足够稳定

附录 A 说明了提示设计是 Agent 的起点。最初阶段至少要做好：

- 角色定义
- 任务说明
- 结构化输出约束
- 示例输入输出
- 分隔符与上下文隔离
- 失败时的默认行为

这个阶段的目标不是“做出智能体”，而是把任务说清楚。

### 阶段 2：建立最小可用闭环

最小 Agent 闭环通常包含：

- 一个任务入口
- 一个执行器
- 一组工具
- 一套状态对象
- 一个最终输出

这一阶段最常用的模式是：

- 提示词链（Chapter 1）
- 工具使用（Chapter 5）
- 规划（Chapter 6）

如果任务路径简单，做成单智能体即可。

### 阶段 3：让流程具备动态决策能力

当任务不再是固定流水线时，需要引入：

- 路由（Chapter 2）
- 并行化（Chapter 3）
- 反思（Chapter 4）

这时系统开始从“顺序执行器”变成“能根据任务情况调度流程的智能体”。

### 阶段 4：加入状态、记忆和目标跟踪

如果任务跨轮次、跨步骤或长时间运行，就必须引入：

- 记忆管理（Chapter 8）
- 目标设定与监控（Chapter 11）
- 学习与适应（Chapter 9）

这一步决定系统是不是“只会做一轮”，还是能“持续推进任务”。

### 阶段 5：连接外部知识和标准化环境

当智能体要进入真实生产环境时，常见扩展是：

- RAG（Chapter 14）
- MCP（Chapter 10）
- 更稳定的工具协议

这一步本质上是在解决“模型如何安全、标准化地接入现实世界”。

### 阶段 6：把失败和风险纳入设计得到一个新的状态，然后用户根据这个新的状态能够做出反馈，是否进入下一个闭环的循环，以及agent在这个过程中，他可以自己根据新的状态的反馈来进行下一个循环

只要进入真实业务，就不能只考虑成功路径。必须设计：

- 异常处理与恢复（Chapter 12）
- 人机协同（Chapter 13）
- Guardrails / 安全模式（Chapter 18）

这是系统可靠性和治理能力的起点。

### 阶段 7：做评估、监控和资源优化

一个能上线的 Agent 系统，必须回答：

- 它做得好不好？
- 成本是否可控？
- 延迟是否可接受？
- 失败是否可观测？

对应的关键模式是：

- 资源感知优化（Chapter 16）
- 评估与监控（Chapter 19）
- 优先级排序（Chapter 20）

### 阶段 8：进入复杂系统形态

当单智能体能力到顶，才考虑：

- 多智能体协作（Chapter 7）
- A2A（Chapter 15）
- 探索与发现（Chapter 21）
- 更高级的推理技术（Chapter 17）

多智能体不是第一步，而是后期扩展能力边界的选择。

## 6. 21 个核心模式的系统讲解

下面按照全书分层，对每个模式回答 4 个问题：

- 它解决什么问题
- 什么时候用
- 设计重点是什么
- 最容易犯什么错

## 6.1 基础执行层

### 6.1.1 提示词链（Prompt Chaining）

- 解决的问题：把复杂任务拆成多个可控步骤，降低单次大提示词的复杂度。
- 适用场景：信息提取、格式转换、逐步分析、生成后处理。
- 设计重点：每一步只做一件事；前一步输出要结构化；链路尽量短。
- 常见错误：把每一步拆得过碎，导致链条过长、延迟变高、错误传播加剧。

### 6.1.2 路由（Routing）

- 解决的问题：根据输入类型、任务类型或上下文，把请求送到合适的处理路径。
- 适用场景：多任务助手、客服分流、模型选择、专家子智能体分派。
- 设计重点：分类规则清晰；每条路由路径职责单一；路由失败要有默认回退。
- 常见错误：路由标签设计模糊，导致分类不稳定，后续链路全错。

### 6.1.3 并行化（Parallelization）

- 解决的问题：把可以同时执行的子任务并发处理，缩短总耗时。
- 适用场景：多源检索、多角度分析、多专家独立研究。
- 设计重点：只并行独立任务；结果合并要有统一结构；并行上限要可控。
- 常见错误：并行执行带来重复工作、状态冲突或工具资源争抢。

### 6.1.4 反思（Reflection）

- 解决的问题：让智能体在输出前检查自身结果，提升质量。
- 适用场景：写作、代码生成、复杂问答、策略建议、长文本总结。
- 设计重点：反思标准必须明确，例如事实性、逻辑性、完整性；最好和执行器分离。
- 常见错误：只是让模型“再想一遍”，却没有明确批判标准，结果只是改写而不是改进。

### 6.1.5 工具使用（Tool Use）

- 解决的问题：把 LLM 从“会说”扩展成“会做”，让它能获取实时信息并执行动作。
- 适用场景：搜索、数据库查询、日历邮件、文件处理、代码执行。
- 设计重点：工具描述清晰；参数模式明确；工具结果统一；错误可返回。
- 常见错误：把业务逻辑都塞进工具说明里，或让模型直接拼自由文本调用，导致不可控。

### 6.1.6 规划（Planning）

- 解决的问题：面对复杂目标时，先拆任务，再分步执行。
- 适用场景：研究任务、复杂工单处理、软件交付、长流程自动化。
- 设计重点：计划要能被执行，不只是漂亮；计划应可重规划；步骤要可观测。
- 常见错误：计划过于宏观，执行器根本落不了地；或者每次都重新规划，造成抖动。

### 6.1.7 多智能体协作（Multi-Agent Collaboration）

- 解决的问题：将复杂任务按角色拆分给多个专门化智能体。
- 适用场景：研究、创作、代码审查、复杂业务编排。
- 设计重点：角色边界明确；协调者职责清晰；共享状态或通信协议要统一。
- 常见错误：在任务还很简单时就过早多智能体化，结果系统复杂度远超收益。

## 6.2 认知与状态层

### 6.2.1 记忆管理（Memory Management）

- 解决的问题：让智能体能够保存和复用历史信息，而不是每轮都从零开始。
- 适用场景：长期对话、个性化助手、持续任务执行、跨会话服务。
- 设计重点：区分短期状态、会话记忆和长期记忆；记忆写入要有策略；检索要可控。
- 常见错误：把所有内容无差别写入记忆，最后记忆变成噪声堆。

### 6.2.2 学习与适应（Learning and Adaptation）

- 解决的问题：让系统根据反馈和经验迭代改进，而不是永远停在初始版本。
- 适用场景：重复性任务优化、智能体自我改进、提示或策略演化。
- 设计重点：学习必须有反馈信号；更新机制要可回滚；线上学习要谨慎。
- 常见错误：没有评估基线就直接自学习，导致系统越改越偏。

### 6.2.3 模型上下文协议（MCP）

- 解决的问题：用标准协议连接模型、工具和数据源。
- 适用场景：工具生态复杂、需要标准化接入、希望模型可迁移时。
- 设计重点：把工具发现、调用、上下文传输做成标准化接口。
- 常见错误：把 MCP 当成“更多工具”而不是“统一协议层”，导致价值发挥不出来。

### 6.2.4 目标设定与监控（Goal Setting and Monitoring）

- 解决的问题：让智能体知道自己在追什么目标，以及当前推进到了哪里。
- 适用场景：长任务、项目式任务、持续执行型 Agent。
- 设计重点：目标可分解、可观测、可判断完成度；监控要和执行状态绑定。
- 常见错误：目标写得过于抽象，最后只能输出很多过程，无法证明是否完成。

## 6.3 稳定性与边界层

### 6.3.1 异常处理与恢复（Exception Handling and Recovery）

- 解决的问题：当工具失败、网络失败、输出格式错误时，系统怎么继续工作。
- 适用场景：所有生产环境。
- 设计重点：区分可重试错误、可回退错误、需要人工介入错误；恢复策略前置设计。
- 常见错误：只记录异常，不做恢复；或者无脑重试，结果放大成本和故障。

### 6.3.2 人机协同（Human-in-the-Loop）

- 解决的问题：在关键节点引入人类判断，降低高风险决策的不确定性。
- 适用场景：审批、金融、医疗、法务、高价值内容发布、关键代码修改。
- 设计重点：明确哪些步骤需要人工确认；把人工输入设计成可消费信号，而不是自由噪声。
- 常见错误：要么完全不设审批，要么每一步都卡人工，最终系统失去自动化价值。

### 6.3.3 知识检索（RAG）

- 解决的问题：把模型生成建立在外部知识基础之上，降低幻觉。
- 适用场景：企业知识库问答、政策检索、文档分析、研究助手。
- 设计重点：数据清洗、切分、索引、召回、重排序、引用链路都要设计。
- 常见错误：以为有了向量库就等于做好了 RAG，忽略了检索质量和答案约束。

## 6.4 高级架构层

### 6.4.1 智能体间通信（A2A）

- 解决的问题：让不同智能体之间建立稳定的任务和消息交换机制。
- 适用场景：跨团队智能体、跨系统协作、平台化多 Agent 生态。
- 设计重点：消息格式、任务状态、同步与流式交互、身份和权限要标准化。
- 常见错误：多个智能体之间只靠自然语言随意对话，导致协议不可控。

### 6.4.2 资源感知优化（Resource-Aware Optimization）

- 解决的问题：在成本、时延、模型能力之间做动态平衡。
- 适用场景：生产部署、混合模型架构、高并发系统。
- 设计重点：按任务难度选择模型；设置预算；把高成本步骤集中在关键节点。
- 常见错误：所有请求都上最强模型，导致成本失控；或者全部降级，导致质量崩塌。

### 6.4.3 推理技术（Reasoning Techniques）

- 解决的问题：提升复杂任务中的分析、分解、搜索和决策能力。
- 适用场景：研究、复杂决策、数学与代码、多步策略推演。
- 设计重点：选择合适推理框架，如 CoT、ToT、ReAct、反思循环；推理成本要可控。
- 常见错误：盲目增加“思考”长度，以为越长越好，却没有任何评估收益。

### 6.4.4 Guardrails / 安全模式（Guardrails / Safety Patterns）

- 解决的问题：控制输入风险、输出风险和行为风险。
- 适用场景：面向用户的公开系统、企业内部高风险流程、工具型智能体。
- 设计重点：输入过滤、输出校验、权限控制、策略执行、敏感操作拦截。
- 常见错误：只做敏感词过滤，却没有行为层面的权限控制和结果验证。

### 6.4.5 评估与监控（Evaluation and Monitoring）

- 解决的问题：持续判断系统质量，并在运行中发现异常。
- 适用场景：所有需要长期维护的 Agent 系统。
- 设计重点：同时看结果质量、过程轨迹、成本、延迟、失败率和用户反馈。
- 常见错误：只看最终回答像不像，而不看任务是否完成、工具是否用对、成本是否失控。

### 6.4.6 优先级排序（Prioritization）

- 解决的问题：当任务很多、资源有限时，系统如何决定先做什么。
- 适用场景：任务队列、项目管理、运营工单、自动调度。
- 设计重点：优先级规则要显式；高价值、高紧急、高依赖任务优先。
- 常见错误：没有统一优先级策略，智能体总在“看起来有趣”的任务上浪费资源。

### 6.4.7 探索与发现（Exploration and Discovery）

- 解决的问题：让智能体在开放问题中主动寻找信息、提出假设并发现新方向。
- 适用场景：科研助手、情报分析、创新探索、深度研究。
- 设计重点：探索需要阶段性目标和评估节点；要能控制发散范围。
- 常见错误：把探索做成无边界发散，系统持续搜索却始终不收敛。

## 7. 支撑附录对 Agent Design 的价值

附录不是补充材料，而是帮助你把 21 个模式真正落地的工具箱。

### 附录 A：高级提示技术

它回答的是“怎么让模型更稳定地理解任务”。核心包括：

- 零样本、单样本、少样本提示
- 系统提示和角色提示
- 分隔符
- 结构化输出
- CoT、ToT、ReAct
- 元提示和迭代提示优化

没有这一层，后面很多模式都只能停留在概念上。

### 附录 B：AI 智能体交互形态

它提醒你：智能体不一定只活在聊天框里。Agent 可能工作在：

- GUI
- 浏览器
- 桌面系统
- 真实物理环境

这会直接影响工具设计、观测方式和权限模型。

### 附录 C：框架概览

这里给出的是实现层的选择参考：

- LangChain / LangGraph 更适合流程和图编排
- Google ADK 更强调智能体原生能力、会话、记忆和工具体系
- CrewAI 更适合角色化多智能体协作

框架不是设计的起点，而是设计落地后的实现容器。

### 附录 D：AgentSpace

这部分体现的是一种“快速搭建和配置智能体”的路径，适合：

- 低代码原型
- 平台化试验
- 快速验证交互流程

### 附录 E：CLI 智能体

命令行智能体非常重要，因为它们天然适合：

- 开发者工作流
- 文件系统操作
- 自动化脚本
- 本地工程任务

这也是今天编码智能体快速成熟的重要土壤。

### 附录 F：推理引擎内部机制

这部分的价值在于让你理解一个现实：

智能体设计再好，也仍然建立在模型能力边界之上。

所以做 Agent Design 时，必须同时理解：

- 模型能做什么
- 模型容易错在哪里
- 推理成本如何影响系统设计

### 附录 G：编码智能体

编码智能体几乎是 Agent Design 的高密度实战样板，因为它天然需要：

- 长流程规划
- 工具调用
- 文件读写
- 代码执行
- 测试反馈
- 反思修复
- 人机协同

如果你想验证 Agent Design 是否真正落地，编码智能体是很好的练兵场。

## 8. 一个标准 Agent 系统应该长什么样

下面是一个面向生产的标准化 Agent 架构草图：

```text
用户请求
  ->
输入校验 / 安全过滤
  ->
目标识别与任务分类
  ->
路由器
  ->
规划器
  ->
执行器
  -> 工具调用
  -> RAG 检索
  -> MCP 服务
  -> 外部系统
  ->
状态与记忆层
  ->
反思 / 质量检查
  ->
异常处理 / 回退 / 重试
  ->
人工审批（如需要）
  ->
最终输出
  ->
评估、日志、监控、成本统计
```

这个结构反映了 Agent Design 的一个核心原则：

不要把所有能力塞进一个提示词，而是把系统拆成可观察、可替换、可评估的部件。

## 9. 以“研究助手”场景为例，看系统如何从 0 到 1 演化

为了更容易理解，可以把全书模式映射到一个具体案例：构建“AI 研究助手”。

### 版本 0：普通问答机器人

只有一个系统提示和一个聊天模型。

特点：

- 开发快
- 成本低
- 无法处理复杂目标
- 无法追踪过程质量

### 版本 1：加入提示词链和结构化输出

系统开始具备基本分工：

- 先拆问题
- 再抽取信息
- 最后生成报告

此时已经开始具备“工作流”特征，但还不是完整智能体。

### 版本 2：加入工具、规划和检索

这时系统可以：

- 搜索论文或网页
- 调知识库
- 生成研究计划
- 按步骤推进

这才进入真正的 Agent 阶段。

### 版本 3：加入反思、记忆和监控

系统可以：

- 对草稿做自检
- 记录历史结论
- 跟踪研究进展
- 根据失败情况重新规划

这时系统已经从“会做任务”进化到“会管理任务”。

### 版本 4：加入多智能体和 A2A

研究助手被拆成多个角色：

- 研究员智能体
- 检索智能体
- 写作智能体
- 审稿智能体
- 协调者智能体

这时系统能力大幅增强，但复杂度也明显提高。

### 版本 5：加入 Guardrails、评估和资源优化

最终生产级系统需要：

- 内容风险控制
- 轨迹记录
- 人工审批
- 成本治理
- 质量评分
- 回归测试

这才是一个真正可以在业务中长期运行的 Agent 系统。

## 10. 框架该怎么选

基于附录 C、D、E、G，可以把框架选择简化成下面这张表。

| 场景 | 更适合的方向 |
|------|------|
| 想快速做单智能体流程 | LangChain |
| 想做复杂图式编排 | LangGraph |
| 想强调智能体原生能力、会话和记忆 | Google ADK |
| 想做角色化多智能体团队 | CrewAI |
| 想快速平台化搭建 | AgentSpace |
| 想把智能体放进开发者终端 | CLI Agent |
| 想验证复杂工程任务闭环 | Coding Agent |

正确顺序应该是：

先确定架构，再选框架；不要先选框架，再被框架反向决定系统形态。

## 11. Agent Design 的核心设计原则

把全书内容压缩成方法论，可以归纳为下面 10 条原则。

1. 先定义目标，再设计智能体。
2. 先做最小闭环，再加复杂能力。
3. 先工作流，后自治；先单智能体，后多智能体。
4. 思考、行动、记忆、评估要解耦。
5. 工具、状态和输出都要结构化。
6. 所有失败路径都要提前设计。
7. 高风险行为必须受控，必要时引入人工审批。
8. 记忆不是越多越好，关键在于可检索、可更新、可清理。
9. 评估和监控不是上线后补的，而是设计时就要进入架构。
10. 资源优化不是“降成本附加项”，而是系统工程的一部分。

## 12. 最容易踩的坑

### 12.1 一个超级大提示词试图解决一切

这是最常见误区。结果通常是：

- 指令互相干扰
- 输出不稳定
- 无法调试
- 无法评估

### 12.2 过早引入多智能体

很多团队在单智能体都没跑通时，就开始拆角色。常见结果是：

- 通信复杂
- 状态混乱
- 故障定位困难
- 成本迅速升高

### 12.3 把记忆当日志仓库

记忆不是“把所有内容都存起来”，而是“只保留未来有价值的信息”。

### 12.4 没有恢复机制

工具失败、检索失败、格式错误、模型超时都是常态。没有恢复机制，系统上线后一定脆弱。

### 12.5 只有模型质量，没有系统质量

很多团队只比较模型回答是否“像样”，却忽略：

- 任务是否完成
- 路径是否合理
- 工具是否用对
- 成本是否可控
- 风险是否拦住

### 12.6 把安全等同于敏感词过滤

真正的安全包括：

- 输入安全
- 输出安全
- 工具权限
- 数据边界
- 人工审批
- 行为约束

## 13. 上线前检查清单

如果你准备把 Agent 系统投入真实环境，至少要检查下面这些问题。

### 13.1 目标与范围

- 目标是否清晰
- 完成条件是否可判断
- 失败处理是否定义
- 不该做的事情是否明示

### 13.2 工具与外部环境

- 每个工具是否有清晰描述和参数模式
- 工具失败是否有可观测错误
- 是否限制了危险操作
- 是否定义了超时和重试策略

### 13.3 状态与记忆

- 会话状态和长期记忆是否分离
- 记忆写入规则是否明确
- 是否支持删除、过期和更新
- 是否避免敏感数据无控制入库

### 13.4 质量与安全

- 是否有反思或审查环节
- 是否有输出校验
- 是否有 Guardrails
- 是否定义人工审批点

### 13.5 评估与监控

- 是否有离线评测集
- 是否记录智能体轨迹
- 是否监控成本、延迟和失败率
- 是否能快速回放问题请求

## 15. 最终总结

如果只用一句话概括整本书的价值，那就是：

Agent Design 不是在“提示词上多写几句”，而是在设计一个可以围绕目标持续运行的系统。

这套系统的关键，不是某个单点技巧，而是以下能力的协同：

- 把复杂任务拆开
- 在正确节点做正确决策
- 连接外部世界
- 保存有价值的状态
- 在失败时恢复
- 在高风险处收紧边界
- 用评估和监控持续优化

从 0 到 1 的正确路线也不是“一步到位做全能智能体”，而是：

先把任务说清楚，先把最小闭环跑通，再逐步加入规划、工具、记忆、检索、安全、评估和协作能力。

当你把这些模式看成一套可以组合的系统积木，而不是零散技巧时，Agent Design 才真正开始变成一门工程实践。
