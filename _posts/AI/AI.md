# 一、完整的软件开发生命周期总览

我一般会把它拆成 9 个阶段：

1. 需求提出与业务目标确认
2. 需求分析与范围界定
3. 系统设计与技术方案设计
4. 任务拆解与排期
5. 开发实现
6. 测试与质量保障
7. 发布上线
8. 运维监控与问题处理
9. 复盘与持续迭代

它不是单纯“程序员写代码”的流程，而是一个**跨产品、设计、开发、测试、运维协作的完整闭环**。



**如果让我设计一个软件开发生命周期，我会把它设计成一个从需求到上线再到沉淀复用的闭环流程，而不是单纯的编码流程。整体上我会分成需求澄清、范围定义、方案设计、Spec 沉淀、测试设计、编码联调、Review 发布、复盘沉淀八个阶段，并设置需求、设计、实现、交付四个质量闸口。**

**在 AI 使用上，我不会把 AI 只当代码生成器，而是让它参与整个工程链路：在需求阶段帮助做结构化分析，在方案阶段辅助做技术对比和风险识别，在 Spec 阶段把需求和设计沉淀成规则，在测试阶段先生成测试用例，在编码阶段按模块受控生成代码，在 Review 阶段做第一轮自动审查，在复盘阶段沉淀知识和 Skill。**

**如果再进一步工程化，我会把 Spec、Skill、MCP、RAG 分层使用：Spec 负责约束，Skill 负责动作执行，MCP 负责连接外部系统，RAG 负责补充知识。这样 AI 才不是一个临时问答工具，而是进入了可复用、可控制、可沉淀的软件工程体系。**

### 如果让我真的落地，我会怎么用 AI 工具

这部分你可以回答得更“像做过”。

------

#### 1. 在需求阶段

我会用 AI 做：

- 需求整理
- 会议纪要结构化
- 用户故事拆解
- 范围边界补全
- 风险点识别

但不会让 AI 决定业务价值。

------

#### 2. 在方案阶段

我会用 AI 做：

- 技术选型对比
- 模块划分初稿
- 数据流建议
- 接口契约草稿
- 风险清单

但最终方案由工程师拍板。

------

#### 3. 在 spec 阶段

我会用 AI 做：

- 把需求文档转成 spec
- 把方案转成开发任务
- 生成验收标准
- 生成 checklist
- 检查 spec 漏项

这是 AI 最能提升稳定性的阶段。

------

#### 4. 在测试阶段

我会用 AI 做：

- 根据 spec 生成测试用例
- 生成 mock 数据
- 生成边界测试场景
- 生成 E2E 测试路径

这样代码实现会更稳。

------

#### 5. 在编码阶段

我会让 AI：

- 只按模块实现
- 先读 spec 再编码
- 同步生成测试
- 遵守项目风格
- 输出改动说明

而不是一次性生成整个项目。

------

#### 6. 在 Review 阶段

我会让 AI 做：

- 第一轮自动审查
- 重复逻辑扫描
- 潜在风险提醒
- 测试不足提醒
- 文档遗漏提醒

------

#### 7. 在沉淀阶段

我会让 AI 做：

- 总结本次开发经验
- 归纳 bug 模式
- 更新规范
- 更新 skill
- 更新知识库

## 问题二

我理解，AI 这一块之所以现在变化这么快，核心原因是它还没有像前端那样，形成一套被行业广泛接受、足够成熟稳定的标准范式。

前端早期其实也经历过类似阶段。更早的时候，前后端职责边界没有现在这么清晰，社区里也出现过很多不同的框架和方案。后面经过一段时间的发展，才逐渐沉淀出像 React、Vue、Angular 这样相对主流的技术路线，行业的开发模式才慢慢稳定下来。

AI 现在也处在一个类似的阶段。尤其是在 coding 这块，虽然已经出现了很多工具、工作流和新概念，比如 prompt engineering、context engineering、spec coding、skill、MCP、RAG 等，但本质上，行业里还没有形成一套所有团队都普遍认可、同时又足够完整的“标准开发范式”或者“全栈解决方案”。所以这段时间新概念会很多，变化也会很快。

但我觉得这种状态不会一直持续下去。随着实践越来越多，后面一定会逐渐沉淀出更标准化的流程。就像现在大家已经开始慢慢形成一个共识：AI 不是简单替代编码，而是要嵌入到整个软件开发生命周期里，去提升每一个环节的效率和质量。

所以如果把 AI 放到实际开发里看，我更倾向于把它理解成对标准开发流程的增强，而不是完全推翻原来的流程。一个比较完整的过程，依然是：

先理解需求，明确目标和边界；
 然后做方案设计，确定技术路线和实现方式；
 再往下分析方案里的重点、难点和风险点；
 在真正开始编码前，把这些内容沉淀成比较清晰的 spec 或规则；
 如果希望结果更稳定，还可以先让 AI 生成测试用例，包括单元测试和集成测试；
 然后再进入编码实现；
 代码完成后，再让 AI 协助跑测试、做 review、补文档、整理发布说明；
 最后进入发布和后续迭代。

也就是说，即使没有 AI，这本身也是一个标准的软件开发生命周期；而 AI 的价值，是把需求分析、方案设计、测试生成、编码实现、代码审查、文档沉淀这些环节串起来，形成更高效的工程流程。

如果是我个人在平时写代码，我会尽量培养一种更接近企业开发的习惯，而不是上来就直接让 AI 生成代码。更好的做法是：

先把需求讲清楚，
 再把方案想清楚，
 然后把规范、边界、模块拆分、测试要求整理出来，
 必要时先进入 plan 模式和 AI 讨论，
 让它先输出 spec 或开发计划，
 把这些内容沉淀到代码库里，
 最后再开始正式开发。

这样做的好处是，AI 输出会更稳定，代码结构也更像团队开发，而不是一次性的“vibe coding”。

所以我觉得，现阶段面对 AI 最重要的不是去死记很多新概念，而是要理解这些概念为什么会出现。它们本质上都在解决同一个问题：**怎么让 AI 从一个会回答问题、会写片段代码的工具，逐步变成一个真正能参与工程流程的协作系统。**

### 1. prompt engineer 怎么理解

**Prompt engineer** 本质上是在研究：

> 怎样设计输入，让模型更稳定地产出我想要的结果。

OpenAI 把 prompt engineering / prompting 描述为：设计和优化输入提示，以更有效地引导模型输出。常见手段包括明确任务、给格式要求、给示例、分步骤说明、用结构化分隔符标清上下文。

#### 它更像什么

更像“**把话说清楚**”。

#### 它主要解决什么

解决的是：

- 模型答非所问
- 输出格式不稳定
- 指令理解不一致
- 简单任务结果不够可控

#### 它属于哪一类

这更偏 **AI 提效**。

因为你不一定在“开发 AI 产品”，你也可能只是：

- 用 AI 帮你写代码
- 帮你改文档
- 帮你出方案
- 帮你做总结

这时你本质上是在提升个人或团队使用 AI 的效率，还没有真正进入“搭建 AI 系统”的层面。

------

### 2. context engineer 怎么理解

**Context engineer** 比 prompt engineer 更进一步。

Anthropic 把 context engineering 定义为：在 LLM 推理过程中，策划和维护“最优 token 集合”的一组策略；OpenAI Cookbook 里也把 context engineering 描述为“管理模型当下知道什么”，包括存什么、取什么、注入什么。

换句话说，它关注的不再只是“这句话怎么写”，而是：

> **模型这次工作时，应该看到哪些信息，不该看到哪些信息，信息以什么顺序和结构进入上下文。**

#### 它更像什么

更像“**给模型准备工作台**”。

#### 它主要关心什么

例如：

- 系统提示词怎么组织
- 项目规则怎么注入
- 历史对话保留多少
- 哪些代码文件要给模型读
- 哪些知识从 RAG 动态检索
- 哪些记忆需要长期保存
- 长上下文怎么压缩和裁剪

#### 它解决的问题

它解决的是 prompt engineer 解决不了的那部分：

- 单条 prompt 已经写得不错，但模型还是容易忘
- 多轮任务里上下文越来越乱
- 项目越来越大，模型拿不到关键背景
- agent 虽然能调用工具，但经常因为上下文不完整而跑偏

### harness engineer

要让 agent 在多上下文窗口、长时间任务、真实软件工程场景里稳定推进，就需要设计外部“支架”。这些支架包括任务循环、工具、状态、计划、权限、验证、记忆、隔离执行和反馈机制。

更像“**给 AI 搭整个施工现场和控制系统**”。

#### 它会涉及什么

通常包括：

- agent loop 怎么跑
- 工具系统怎么接
- 权限怎么控制
- 文件改动如何审查
- 计划如何拆分和追踪
- 失败后如何恢复
- 输出如何验证
- 长任务如何跨上下文继续
- memory / logs / eval / sandbox 怎么设计





### 1. Anthropic

更关注：

- 支架系统
- 长任务
- 多上下文接力
- artifacts 交接
- planner / generator / evaluator 协作
- agent harness 和 evaluation harness 的区分

一句话概括：

**Anthropic 更像在研究“怎样把 agent 长时间、稳定地跑下去”。** 

------

### 2. OpenAI

更关注：

- core agent loop
- execution logic
- tool orchestration
- client-side harness
- environments / feedback loops / control systems
- agent-first software engineering

一句话概括：

**OpenAI 更像在研究“怎样把 agent loop 变成可靠的软件工程基础设施”。**
