## Webpack开发构建优化

### 开发模式基础配置

#### 配置mode: 'development'

在开发环境中，配置`mode: 'development'`是基础优化步骤，其核心作用是启用Webpack内置的开发模式优化，具体优势包括：加快构建速度、输出未压缩的源码（便于调试）、保留代码中的注释和原始变量名，同时禁用生产环境特有的代码压缩、Tree-Shaking等优化（避免开发阶段构建耗时过长）。需注意，Webpack默认的`mode`值为`'production'`，开发环境需手动指定为`'development'`。

```javascript
module.exports = {
  mode: 'development',
  // 其他配置...
};
```

**知识点对应问题**：开发环境中如何启用Webpack内置优化，提升调试效率并加快构建速度？

#### 配置devtool: 'eval-cheap-module-source-map'

`devtool`配置项用于控制是否生成`source map`及生成的类型，`source map`的核心作用是建立构建后代码与构建前源码的映射关系，可在浏览器开发者工具中直接定位到原始源码的错误位置，大幅提升调试效率。

开发模式下推荐使用`eval-cheap-module-source-map`，该配置在构建速度和调试体验之间实现了良好平衡：相比其他类型（如`source-map`），构建速度更快，同时能精准定位原始源码（而非构建后的代码），且仅映射行信息（忽略列信息），兼顾速度与实用性。

```javascript
module.exports = {
  mode: 'development',
  devtool: 'eval-cheap-module-source-map',
  // 其他配置...
};
```

**知识点对应问题**：开发模式下如何配置`source map`，既能保证构建速度，又能精准定位原始源码以便调试？

#### 启用HMR（Hot Module Replacement）

HMR（热模块替换）是开发模式下的核心优化之一，其作用是在不刷新整个页面的前提下，替换、添加或删除项目中的模块，减少页面刷新耗时，保留页面当前状态（如表单输入、页面滚动位置），大幅提升开发效率。

启用HMR需通过`webpack-dev-server`的`hot: true`配置，同时引入`webpack.HotModuleReplacementPlugin`插件（Webpack 5中，当`hot: true`时会自动引入该插件，可省略手动配置，但手动引入更稳妥），此外需安装`webpack-dev-server`依赖，通过命令行`webpack dev-server`启动开发服务器。

```javascript
const webpack = require('webpack');
const WebpackDevServer = require('webpack-dev-server');

module.exports = {
  mode: 'development',
  devtool: 'eval-cheap-module-source-map',
  devServer: {
    contentBase: './dist', // 指定静态资源目录
    hot: true, // 启用HMR
  },
  plugins: [
    new webpack.HotModuleReplacementPlugin(), // 手动引入HMR插件（可选，建议添加）
  ],
  // 其他配置...
};
```

### 模块解析优化

#### 使用resolve.alias设置路径别名

Webpack在解析模块时，会从当前目录开始递归查找模块路径，若项目目录较深，会增加路径解析时间。通过`resolve.alias`为常用模块（如组件、工具函数）设置路径别名，可直接指定模块的绝对路径，减少解析耗时，同时简化代码中的导入路径（如用`@components`替代`../src/components`）。

```javascript
const path = require('path');

module.exports = {
  mode: 'development',
  resolve: {
    alias: {
      '@components': path.resolve(__dirname, 'src/components/'), // 组件目录别名
      '@utils': path.resolve(__dirname, 'src/utils/'), // 工具函数目录别名
    },
  },
  // 其他配置...
};
```

**知识点对应问题**：如何优化Webpack模块解析速度，同时简化代码中的导入路径？

#### 配置resolve.extensions优化扩展名解析

`resolve.extensions`用于指定Webpack解析模块时默认尝试的文件扩展名，若不配置或配置过多无关扩展名，Webpack会逐一尝试解析，增加解析次数，降低构建速度。

开发模式下，应仅包含项目中实际使用的扩展名（如`.js`、`.jsx`、`.json`），避免冗余配置，同时可省略导入时的扩展名（如`import utils from '@utils/index'`，无需写`.js`）。

```javascript
module.exports = {
  mode: 'development',
  resolve: {
    extensions: ['.js', '.jsx', '.json'], // 仅包含项目所需扩展名
  },
  // 其他配置...
};
```

**知识点对应问题**：如何减少Webpack解析模块时的尝试次数，提升解析速度？

#### 使用resolve.modules明确模块路径

`resolve.modules`用于指定Webpack查找模块的目录，默认情况下，Webpack会从`node_modules`目录开始递归查找，若项目中自定义模块较多（如`src`目录下的模块），可将其添加到`resolve.modules`中，明确模块查找路径，避免不必要的递归查找，加速模块解析。

需注意，若导入模块时未指定扩展名（如`import "@/utils/index"`），需配合`resolve.extensions`配置，否则可能出现模块找不到的报错。

```javascript
const path = require('path');

module.exports = {
  mode: 'development',
  resolve: {
    modules: [path.resolve(__dirname, 'src'), 'node_modules'], // 优先查找src目录，再查找node_modules
  },
  // 其他配置...
};
```

### 缓存优化

#### 持久化缓存：启用文件系统缓存

Webpack 5引入了文件系统缓存（filesystem cache）机制，通过配置`cache: { type: 'filesystem' }`，可将构建过程中的中间结果（如模块解析结果、编译结果）缓存到本地文件系统中，二次构建时，若文件未发生改变，Webpack会直接复用缓存，无需重新构建，显著减少二次构建时间。

Webpack支持两种缓存类型：`filesystem`（文件系统缓存，可持久化，重启项目后仍有效）和`memory`（内存缓存，仅在当前项目运行期间有效，重启后失效），开发模式下优先使用`filesystem`缓存。

```javascript
module.exports = {
  mode: 'development',
  cache: {
    type: 'filesystem', // 启用文件系统缓存
  },
  // 其他配置...
};
```

#### 使用babel-loader的cacheDirectory选项

项目中使用`babel-loader`转换ES6+代码时，每次构建都会重新转换所有JS文件，耗时较长。通过启用`babel-loader`的`cacheDirectory`选项，可将Babel的转换结果缓存到本地目录（默认是`node_modules/.cache/babel-loader`），二次构建时，仅重新转换修改过的文件，大幅提升构建速度。

```javascript
module.exports = {
  mode: 'development',
  module: {
    rules: [
      {
        test: /\.js$/, // 匹配JS文件
        exclude: /node_modules/, // 排除node_modules目录（无需转换第三方依赖）
        use: {
          loader: 'babel-loader',
          options: {
            cacheDirectory: true, // 启用babel-loader缓存
          },
        },
      },
    ],
  },
  // 其他配置...
};
```

### 其他构建优化

#### 减少监听文件

开发模式下，Webpack默认会监听所有项目文件的变化，当文件修改时自动触发重新构建。若项目中存在大量无需监听的文件或目录（如`node_modules`、`dist`），可通过`watchOptions.ignored`配置排除这些目录，减少文件监听数量，降低系统资源消耗，同时避免无关文件修改触发不必要的构建。

```javascript
module.exports = {
  mode: 'development',
  watchOptions: {
    ignored: /node_modules/, // 排除node_modules目录，不监听其变化
  },
  // 其他配置...
};
```

**知识点对应问题**：如何减少Webpack开发模式下的文件监听数量，降低系统资源消耗？

#### 使用多进程并行构建

Webpack默认是单进程构建，当项目体积较大、文件较多时，构建速度会明显变慢。通过使用`thread-loader`（推荐）或`webpack-parallel-uglify-plugin`等插件，可利用多核CPU的优势，将构建任务拆分到多个进程中并行执行，大幅提升构建速度。

`thread-loader`需配置在其他loader之前（如`babel-loader`），通过`workers`选项指定进程数量（通常设置为CPU核心数减1，避免占用过多系统资源）。

```javascript
const ThreadLoader = require('thread-loader');

module.exports = {
  mode: 'development',
  module: {
    rules: [
      {
        test: /\.js$/,
        use: [
          {
            loader: 'thread-loader',
            options: {
              workers: 2, // 指定2个进程并行构建（根据CPU核心数调整）
            },
          },
          'babel-loader', // 后续loader会在thread-loader启动的进程中执行
        ],
      },
    ],
  },
  // 其他配置...
};
```

## Webpack生产构建优化

### 生产模式基础配置

#### 配置mode: 'production'

Webpack 5 的`mode: 'production'`是生产环境构建的基础配置，该模式会自动启用多种内置优化，无需手动配置，核心目标是减少输出文件体积、提升应用运行时性能，降低线上部署成本和加载耗时。

启用`mode: 'production'`后，Webpack 会自动激活以下核心优化功能，无需额外引入插件：

1. 代码压缩：通过`TerserPlugin`压缩 JavaScript 代码，移除冗余空格、注释、未使用变量，混淆变量名，大幅减小文件体积；
2. Tree Shaking：删除项目中未被使用的模块和代码，仅保留实际被引用的内容，减少无效代码加载；
3. 作用域提升（Scope Hoisting）：将多个模块合并到一个函数中，减少闭包数量，降低运行时内存消耗，提升代码执行效率；
4. 自动代码分割：分析模块依赖关系，自动将重复依赖或第三方依赖拆分，优化缓存效果和加载速度。

```javascript
module.exports = {
  mode: 'production',
  // 其他配置...
};
```

**知识点对应问题**：生产环境中如何启用Webpack内置的核心优化，减少输出文件体积并提升运行时性能？

### 生产模式核心优化：代码分割

#### splitChunks 核心解析（定义与作用）

`optimization.splitChunks`是Webpack生产环境中代码分割的核心配置，用于将打包产物按规则拆分为多个chunk（文件），解决单文件体积过大、缓存命中率低、首屏加载慢等问题，其核心作用的包括：

1. 抽离公共代码：多个入口或路由复用的模块仅打包一次，避免重复打包，减少总体积；
2. 抽离第三方依赖（vendor）：将`node_modules`中的第三方依赖拆分为独立chunk，此类依赖更新频率低，利于浏览器长缓存；
3. 提升缓存命中：业务代码频繁更新，而vendor、commons等chunk相对稳定，浏览器可复用旧缓存，减少重复下载；
4. 降低首包体积：拆分非首屏所需代码，配合动态导入，减少首屏加载的文件大小，提升首屏加载速度；
5. 支持并行加载：多个chunk可通过HTTP/2/3并行下载，提升整体加载效率（受浏览器并发策略限制）。

其本质是解决两个核心问题：哪些模块应该被抽离到新chunk，以及抽离后的chunk如何命名、何时抽离、抽离的粒度如何控制。

**知识点对应问题**：Webpack中`optimization.splitChunks`的核心作用是什么，能解决生产构建中的哪些痛点？

#### splitChunks 核心工作机制

Webpack会扫描整个项目的模块依赖图，对每个模块进行分析，计算其被引用的chunk数量和来源，再根据配置规则决定是否抽离为独立chunk，具体机制如下：

1. 筛选条件：模块需满足“被多处复用”“来自`node_modules`”“体积达到指定阈值”“命中更高优先级的cacheGroup规则”中的一种或多种，才会被抽离为共享chunk；
2. 规则优先级：当多个配置规则同时命中某个模块时，按`cacheGroups`的`priority`（优先级）排序，数值越大，优先级越高，优先按该规则抽离；
3. 运行时关联：拆分后，入口chunk会通过Webpack的runtime manifest（运行时代码）记录拆分chunk的依赖关系，确保运行时能正确加载所需chunk。

**知识点对应问题**：Webpack的`splitChunks`是如何判断模块是否需要抽离，以及如何处理多规则冲突的？

#### splitChunks 核心配置项详解

以下是生产环境中常用的`splitChunks`配置项，涵盖开关、粒度控制、命名策略等，需结合业务场景灵活调整：

##### 1. chunks：对哪些chunk生效（核心开关）

控制代码分割的作用范围，决定哪些类型的chunk会参与拆分，是最基础的配置项：

- `chunks: "async"`（默认值）：仅对异步chunk生效，即通过动态`import()`导入的模块；

- `chunks: "initial"`：仅对入口初始chunk生效，即首屏加载的核心chunk；

- `chunks: "all"`：对初始chunk和异步chunk均生效，是生产环境中最常用的配置，可全面拆分公共依赖和第三方依赖。

结论：多数SPA、后台系统等项目，需拆分vendor和业务公共模块，通常选择`chunks: "all"`。

##### 2. minSize / maxSize：控制拆分粒度

用于控制chunk的大小，避免拆分过细或过粗，平衡文件体积和请求数：

- `minSize`：chunk的最小体积（单位：字节），只有当chunk体积大于等于该值时，才会被拆分，过小的chunk不拆分，减少HTTP请求数；

- `maxSize`：chunk的最大体积（单位：字节），当chunk体积超过该值时，Webpack会尝试将其拆分为更小的chunk，实现更均匀的体积分配，但会增加请求数，需结合HTTP/2性能权衡。

常见策略：追求少文件则提高`minSize`、不设置`maxSize`；追求均匀体积则合理配置`maxSize`，同时关注浏览器并发请求限制。

##### 3. minChunks：复用阈值

指定模块被引用的最小次数，只有当模块被至少`minChunks`个chunk引用时，才会被抽离为公共chunk，直接决定“公共包”的形成概率：

常用配置为`minChunks: 2`，表示被2个及以上chunk引用的模块，会被抽离为公共chunk；值越大，生成的公共包越少，反之则越多。

##### 4. maxAsyncRequests / maxInitialRequests：限制并发请求数

用于避免代码拆分过细导致的HTTP请求爆炸，控制不同类型chunk的最大并行请求数：

- `maxInitialRequests`：首屏加载时，最多允许的并行chunk请求数；

- `maxAsyncRequests`：异步加载（动态`import()`）时，最多允许的并行chunk请求数。

默认值可满足多数项目需求，若拆分过细导致请求数超标，可适当降低该值。

##### 5. automaticNameDelimiter / name：命名策略

控制拆分后chunk的名称，影响缓存稳定性和可读性：

- `automaticNameDelimiter`：自动生成chunk名称时的分隔符，默认值为`~`，例如`chunk-vendors~app.js`；

- `name`：可自定义chunk名称，可在`cacheGroups`中为不同规则配置单独名称，命名需兼顾可读性、缓存稳定性，避免频繁变名（变名会导致浏览器缓存失效）。

##### 6. cacheGroups：拆分规则核心（最重要配置）

`cacheGroups`是一组拆分规则的集合，每组规则定义了“哪些模块需要拆分”“如何拆分”，是`splitChunks`的核心配置，每个缓存组包含以下关键属性：

- `test`：匹配模块的规则，可使用正则表达式或函数，例如匹配`node_modules`中的模块；

- `priority`：规则优先级，数值越大，优先级越高，多个规则同时命中时，优先按高优先级规则拆分；

- `reuseExistingChunk`：是否复用已存在的chunk，若当前模块已被抽离为某个chunk，不再重复创建新chunk，提升构建效率；

- `enforce`：是否强制执行拆分，即使不满足`minSize`等全局配置，也会按该规则拆分；

- `name`：该缓存组拆分后chunk的名称；

- `minChunks/minSize`：可覆盖全局配置，为当前缓存组单独设置复用阈值和体积阈值。

生产环境中最常用的缓存组的是`vendors`（抽离第三方依赖）和`commons`（抽离业务公共模块）。

#### splitChunks 常用配置范式（生产实战）

以下是生产环境中最常用的两种配置范式，覆盖多数项目场景，可直接复用并根据业务调整：

##### 1. 通用范式：vendor + commons（多数SPA/后台系统适用）

核心目标：抽离第三方依赖和业务公共模块，优化缓存和首屏加载，是最基础、最常用的配置：

```javascript
// webpack.config.js
module.exports = {
  mode: 'production',
  optimization: {
    splitChunks: {
      chunks: 'all', // 对所有chunk生效
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/, // 匹配node_modules中的第三方依赖
          name: 'chunk-vendors', // 拆分后chunk名称
          priority: 10, // 优先级，高于commons
        },
        commons: {
          name: 'chunk-commons', // 业务公共模块chunk名称
          minChunks: 2, // 被至少2个chunk引用才抽离
          priority: 0, // 优先级低于vendors
          reuseExistingChunk: true, // 复用已存在的chunk
        },
      },
    },
  },
};
```

配置效果：`node_modules`中的第三方依赖被抽离为`chunk-vendors`，被2个及以上chunk引用的业务模块被抽离为`chunk-commons`，入口chunk仅保留自身独有代码。

##### 2. 进阶范式：拆分大依赖（提升缓存稳定性）

核心目标：将体积大、更新频率低的第三方依赖（如`react/vue`、`echarts`、`lodash`）单独拆分，进一步提升缓存稳定性，避免因小依赖更新导致整个vendor chunk缓存失效：

```javascript
module.exports = {
  mode: 'production',
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        framework: { // 单独拆分框架类依赖
          test: /[\\/]node_modules[\\/](vue|vue-router|pinia)[\\/]/,
          name: 'chunk-framework',
          priority: 30, // 最高优先级，优先拆分
        },
        echarts: { // 单独拆分大型图表依赖
          test: /[\\/]node_modules[\\/]echarts[\\/]/,
          name: 'chunk-echarts',
          priority: 25, // 优先级低于framework，高于vendors
        },
        vendors: { // 拆分剩余第三方依赖
          test: /[\\/]node_modules[\\/]/,
          name: 'chunk-vendors',
          priority: 10,
        },
      },
    },
  },
};
```

配置意义：framework、echarts等大依赖更新频率极低，单独拆分后可实现长缓存；业务代码或其他小依赖更新时，不会影响这些chunk的hash值，缓存收益最大化。

**知识点对应问题**：生产环境中，如何配置`splitChunks`实现第三方依赖和业务公共模块的拆分，如何进一步优化大依赖的缓存稳定性？

#### splitChunks 的收益与代价（实战权衡）

代码分割并非越多越好，需结合业务场景权衡收益与代价，避免过度拆分：

##### 1. 核心收益

- 减少重复打包：多入口、多页面项目中，共享依赖不会被每个入口重复打包，降低总体积；

- 提升缓存效率：稳定的vendor、commons chunk可被浏览器长期缓存，业务代码更新时，仅需下载变化的chunk；

- 加快首屏加载：拆分非首屏代码，配合动态导入，减少首屏加载的文件大小，提升加载速度（需结合HTTP/2）。

##### 2. 潜在代价

- 请求数上升：拆分过细会导致HTTP请求数增加，若未启用HTTP/2，可能因请求排队降低加载效率；

- 运行时复杂度提升：chunk间的依赖关系更复杂，调试难度增加，若配置不当可能出现加载错误；

- 缓存失效风险：若chunk命名、hash策略不稳定，或未分离runtime，可能出现“改一行代码，多个chunk hash变化”的情况，降低缓存收益。

**知识点对应问题**：代码分割（splitChunks）的收益和代价分别是什么，如何避免过度拆分带来的问题？

#### splitChunks 关键注意点（易忽略细节）

以下细节直接影响代码分割效果和缓存稳定性，生产配置中需重点关注：

1. splitChunks ≠ 懒加载：splitChunks的核心是“抽离重复/第三方模块”，而懒加载依赖`import()`动态导入语法，两者常配合使用（懒加载的模块会被splitChunks拆分），但作用不同；
2. runtimeChunk 影响缓存稳定性：Webpack的runtime（引导代码，负责chunk加载和依赖管理）若不分离，当chunk id或依赖关系变化时，会导致多个chunk的hash值变化，缓存失效。多入口项目建议配置`optimization.runtimeChunk: 'single'`，将runtime抽离为独立chunk；
3. 避免过度拆分：需结合业务路由结构、HTTP/2支持情况、首屏关键路径，平衡“文件体积”和“请求数”，不可盲目拆分；
4. cacheGroups priority 需合理：优先级设置需可解释，避免出现“模块未按预期拆分”的情况（如第三方依赖被误拆到commons），通常第三方依赖优先级高于业务公共模块；
5. maxSize 是建议性配置：Webpack会尝试按`maxSize`拆分chunk，但受模块依赖图限制，无法保证完全按预期边界拆分，无需过度纠结精确值。

**知识点对应问题**：配置`splitChunks`时，有哪些易忽略的细节，如何避免这些细节导致的缓存失效或拆分异常？

#### 动态导入实现代码懒加载

代码懒加载是生产环境中降低首屏体积的核心手段，通过`import()`动态导入语法，可实现“需要时才加载模块”，动态导入的模块会被Webpack自动拆分为独立chunk，配合`splitChunks`可进一步优化加载效率。

`import()`语法返回一个Promise，可通过`.then()`方法获取模块，也可配合`async/await`使用，适用于路由懒加载、组件懒加载等场景。

```javascript
// 动态导入示例（基础用法）
function loadComponent() {
  // 动态导入component模块，会被拆分为独立chunk
  return import('./component').then(module => {
    const component = module.default;
    // 使用导入的组件
    return component;
  });
}

// 配合async/await使用（更简洁）
async function loadComponent() {
  const module = await import('./component');
  return module.default;
}
```

注意：动态导入的模块会被Webpack自动拆分，无需额外配置`splitChunks`（但`splitChunks`可优化其拆分规则），懒加载的核心是“延迟加载”，减少首屏加载的模块数量。

### 代码压缩优化

#### 启用optimization.minimize 及自定义压缩

生产模式下，`mode: 'production'`会自动启用`optimization.minimize: true`，默认使用`TerserPlugin`压缩JavaScript代码，实现代码体积精简。

若需自定义压缩行为（如移除控制台打印、自定义压缩规则），可手动配置`minimizer`选项，指定`TerserPlugin`并设置相关参数。

```javascript
const TerserPlugin = require('terser-webpack-plugin');

module.exports = {
  mode: 'production',
  optimization: {
    minimize: true, // 启用代码压缩（生产模式默认开启，可省略）
    minimizer: [
      new TerserPlugin({
        terserOptions: {
          compress: {
            drop_console: true, // 移除所有console打印（生产环境常用）
            drop_debugger: true, // 移除debugger语句
            pure_funcs: ['console.log'], // 仅移除console.log，保留其他console方法
          },
        },
      }),
    ],
  },
  // 其他配置...
};
```

说明：`drop_console: true`会移除所有`console`相关语句，若需保留部分console方法（如`console.error`），可使用`pure_funcs`指定需移除的方法。

### 无用代码清除（Tree Shaking）

Tree Shaking的核心作用是移除项目中未被使用的代码（死代码），减少文件体积，其依赖ES6模块语法（`import`/`export`），生产模式下默认启用，但需满足特定条件才能生效。

#### 前提：确保使用ES6模块

Tree Shaking仅对ES6模块（静态模块）生效，CommonJS模块（`require`/`module.exports`）是动态模块，Webpack无法提前分析其依赖关系，无法进行Tree Shaking。

需确保项目中所有模块均使用ES6模块语法，避免混合使用CommonJS和ES6模块。

```javascript
// 正确：ES6模块（支持Tree Shaking）
import { foo } from './module';

export function bar() {
  return foo();
}

// 错误：CommonJS模块（不支持Tree Shaking）
const { foo } = require('./module');
module.exports = { bar: () => foo() };
```

#### 配置sideEffects：告知Webpack无副作用模块

`sideEffects`选项用于告知Webpack哪些模块具有“副作用”（即模块执行时会影响全局状态，如修改全局变量、引入CSS文件），Webpack会对无副作用的模块进行Tree Shaking，移除未使用的代码；对有副作用的模块，即使未被使用，也不会移除。

配置方式分两种，根据项目实际情况选择：

```javascript
module.exports = {
  mode: 'production',
  optimization: {
    // 方式1：整个项目无副作用（无全局修改、无单独引入的CSS等）
    sideEffects: false,
    // 方式2：部分文件有副作用，指定具体文件（如CSS、全局初始化文件）
    // sideEffects: ['*.css', '*.scss', './src/global.js'],
  },
  // 其他配置...
};
```

注意：CSS文件属于有副作用的文件（引入后会影响页面样式），若项目中使用CSS Modules或单独引入CSS，需将`*.css`等后缀加入`sideEffects`数组，避免被Tree Shaking误删。

**知识点对应问题**：Tree Shaking的生效条件是什么，如何配置`sideEffects`避免无副作用模块被误删或有副作用模块被误移除？

### 图片与资源优化

生产环境中，图片等静态资源是导致打包体积过大的重要原因，核心优化思路是“压缩资源体积”“合理处理资源引入方式”，常用工具包括`image-webpack-loader`、`url-loader`、`file-loader`。

#### 使用image-webpack-loader压缩图片

`image-webpack-loader`是Webpack的图片压缩 loader，可在打包过程中自动压缩PNG、JPG、GIF、SVG等图片资源，减少图片体积，且不影响图片清晰度（可配置压缩质量）。

使用前需安装相关依赖，配置时需放在`file-loader`或`url-loader`之后（先处理图片路径，再压缩）。

```javascript
const ImageMinimizerPlugin = require('image-minimizer-webpack-plugin');

module.exports = {
  mode: 'production',
  module: {
    rules: [
      {
        test: /\.(png|jpe?g|gif|svg)$/i, // 匹配图片文件
        use: [
          {
            loader: 'file-loader', // 处理图片路径，输出到指定目录
            options: {
              name: '[name].[hash:8].[ext]', // 图片输出名称（带hash，利于缓存）
              outputPath: 'images/', // 图片输出目录
            },
          },
          {
            loader: 'image-webpack-loader', // 压缩图片
            options: {
              mozjpeg: { // 压缩JPG
                progressive: true, // 渐进式JPG（提升加载体验）
                quality: 75, // 压缩质量（0-100，越高越清晰，体积越大）
              },
              optipng: { // 压缩PNG
                enabled: true, // 启用压缩
              },
              pngquant: { // 压缩PNG（更高效）
                quality: [0.65, 0.90], // 质量范围
                speed: 4, // 压缩速度（1-10，越快质量越差）
              },
              gifsicle: { // 压缩GIF
                interlaced: false, // 禁用交错扫描
              },
              webp: { // 将图片转为WebP格式（体积更小）
                quality: 75,
              },
            },
          },
        ],
      },
    ],
  },
  // 其他配置...
};
```

#### 使用url-loader和file-loader处理图片引入

`url-loader`和`file-loader`配合使用，可根据图片大小决定“内联到代码中”还是“输出为单独文件”，减少HTTP请求数，同时优化加载体验。

核心逻辑：小于指定大小（`limit`）的图片，会被转换为base64编码，内联到JS/CSS中，无需额外请求；大于该大小的图片，由`file-loader`输出为单独文件，利于缓存。

```javascript
module.exports = {
  mode: 'production',
  module: {
    rules: [
      {
        test: /\.(png|jpe?g|gif|svg)$/i,
        use: [
          {
            loader: 'url-loader',
            options: {
              limit: 8192, // 小于8KB的图片转为base64内联（单位：字节）
              fallback: 'file-loader', // 大于8KB的图片，使用file-loader处理
              name: '[name].[hash:8].[ext]', // 输出图片名称
              outputPath: 'images/', // 输出目录
            },
          },
        ],
      },
    ],
  },
  // 其他配置...
};
```

说明：`limit`值需根据项目实际调整，过小会导致内联代码过多、JS体积增大，过大会导致请求数增加，通常设置为8KB或10KB。

**知识点对应问题**：生产环境中如何优化图片资源，`image-webpack-loader`、`url-loader`、`file-loader`的作用分别是什么，如何配合使用？

### 输出产物分析（生产优化关键步骤）

生产构建后，需对输出产物进行分析，定位体积过大的资源、不合理的chunk拆分等问题，才能针对性优化，核心分析要点：是否有体积过大的资源、是否按需拆分chunk、模块依赖是否合理。

常用分析方式有两种：通过命令行生成stats.json文件分析，或使用`webpack-bundle-analyzer`插件可视化分析（推荐）。

#### 方式1：通过命令行生成stats.json文件

Webpack支持通过`--profile`和`--json`参数，生成包含所有构建信息的JSON文件，再通过在线工具分析产物结构。

步骤1：执行构建命令，生成stats.json文件：

```bash
webpack --profile --json > stats.json
```

说明：`--profile`记录构建过程中的耗时信息，`--json`以JSON格式输出构建结果，`>`将输出内容写入stats.json文件。

步骤2：使用在线工具分析stats.json文件，常用工具：webpack-stats viewer（在线网站），可上传文件查看产物结构、模块占比等信息。

#### 方式2：使用webpack-bundle-analyzer插件（可视化分析）

`webpack-bundle-analyzer`是一款强大的可视化分析插件，可直观展示打包产物的结构、每个模块的体积占比、模块依赖关系，以及Gzip后的大小，是生产优化的首选工具。

##### 1. 安装插件

```bash
npm install --save-dev webpack-bundle-analyzer
```

##### 2. 配置插件（Webpack配置文件中）

```javascript
const BundleAnalyzerPlugin = require('webpack-bundle-analyzer').BundleAnalyzerPlugin;

module.exports = {
  mode: 'production',
  // 其他配置...
  plugins: [
    new BundleAnalyzerPlugin({
      analyzerMode: 'server', // 报告输出方式：启动HTTP服务器展示
      analyzerHost: '127.0.0.1', // 服务器主机地址
      analyzerPort: 8888, // 服务器端口（默认8888）
      reportFilename: 'report.html', // 静态报告文件名（analyzerMode为static时生效）
      defaultSizes: 'parsed', // 显示文件大小方式：parsed（解析后大小）、gzip（压缩后大小）
      openAnalyzer: true, // 构建完成后自动打开浏览器展示报告
      generateStatsFile: false, // 是否生成stats.json文件
      statsFilename: 'stats.json', // stats.json文件名
      logLevel: 'info', // 日志级别：info、warn、error、silent
    })
  ]
};
```

##### 3. 插件参数说明

- `analyzerMode`：报告输出模式，`server`（启动服务器）、`static`（生成静态HTML）、`json`（生成JSON报告）、`disabled`（禁用）；

- `defaultSizes`：默认显示的文件大小，`parsed`为Webpack解析后的实际大小，`gzip`为Gzip压缩后的大小（更贴近线上实际加载体积）；

- `openAnalyzer`：自动打开浏览器，方便快速查看报告，开发和生产环境均可启用。

##### 4. 分析报告的核心用途

通过插件生成的可视化报告，可快速定位以下问题：

1. 识别体积过大的模块（如第三方依赖、大型组件），针对性拆分或替换；
2. 查看模块依赖关系，发现冗余依赖或重复打包的模块；
3. 验证代码分割效果，确认chunk拆分是否合理；
4. 查看每个文件的Gzip大小，评估线上加载体积。

## Vite开发构建优化

### Vite开发模式核心优势

Vite 与传统构建工具（如Webpack）相比，其核心优势集中在开发模式，无需额外复杂配置，即可实现极快的开发体验。核心原因在于Vite采用“按需编译”机制，开发时不进行全量打包，而是直接启动服务器，对请求的模块实时编译，配合内置的优化功能，大幅提升开发启动速度和热更新效率，降低开发过程中的等待成本。

Vite开发模式的核心优势体现在：启动速度快、热更新即时、配置简洁，无需手动配置过多优化项，即可满足绝大多数项目的开发需求，尤其适合大型项目和前端框架（Vue、React等）开发。

**知识点对应问题**：Vite开发模式的核心优势是什么，与传统构建工具相比，其开发体验更优的关键原因是什么？

### 模块热替换（HMR）

#### HMR 核心概述

模块热替换（HMR, Hot Module Replacement）是Vite开发服务器的核心功能，默认自动启用，无需手动配置。其核心作用是：在不完全刷新整个页面的前提下，实时更新修改后的模块内容，保留页面当前运行状态，避免因页面刷新导致的状态丢失，大幅提升开发调试效率。

与传统的“全量页面刷新”相比，HMR仅更新变化的模块，无需重新加载整个页面资源，尤其在大型项目中，能显著减少更新等待时间，提升开发流畅度。

#### HMR 机制原理

Vite的HMR通过“服务器-浏览器”双向通信实现，核心流程如下：

1. 开发启动时，Vite服务器与浏览器建立WebSocket连接，用于实时传递模块更新信息；
2. 当开发者修改某个模块文件（如组件、JS文件、CSS文件）时，Vite服务器监听并检测到文件变化；
3. 服务器仅重新编译该变化的模块，而非全量打包所有模块，生成更新后的模块代码；
4. 服务器通过WebSocket向浏览器发送模块更新通知，告知浏览器需替换的模块及更新后的代码；
5. 浏览器接收通知后，在不刷新页面的情况下，替换当前页面中的旧模块，保留页面原有运行状态，完成热更新。

关键优势：仅更新变化模块，减少编译和加载开销，实现“即时更新”，尤其适合频繁修改代码的开发场景。

#### HMR 使用示例

Vite的HMR默认启用，无需额外配置，以下以React应用为例，展示HMR的实际效果：

假设项目中存在一个`HelloWorld`组件，初始代码如下：

```javascript
// src/components/HelloWorld.jsx
import React from 'react';

export default function HelloWorld() {
  return <h1>Hello, Vite!</h1>;
}
```

开发过程中，修改组件内容为`<h1>Hello, Vite HMR!</h1>`，保存文件后，Vite会通过HMR自动更新浏览器中的组件实例，页面不会刷新，组件的状态（若有）保持不变，无需重新操作页面即可看到修改效果。

### 环境变量配置

Vite支持通过`.env`系列文件配置环境变量，无需复杂配置，即可在代码和HTML中访问环境变量，同时支持多环境区分，满足开发、测试、生产等不同环境的配置需求，提升开发灵活性。

#### 基础环境变量配置（.env文件）

在项目根目录创建`.env`文件，即可定义全局环境变量，Vite会自动加载该文件中的变量，并注入到项目中，供代码和HTML使用。

注意：Vite中定义的环境变量，需以`VITE_`为前缀，否则无法被Vite识别和注入（除`NODE_ENV`等内置变量外）。

```plain
# .env 文件（全局环境变量）

```

示例2：在代码中访问环境变量：

```javascript
// src/main.js
console.log(import.meta.env.VITE_APP_TITLE); // 输出：Vite开发示例
console.log(import.meta.env.VITE_APP_BASE_URL); // 输出：http://localhost:5173
```

```html
<!DOCTYPE html>
<html lang="en">
  <head>
```

#### 多环境支持（.env.{mode}文件）

Vite支持为不同环境创建对应的`.env`文件，通过`--mode`参数指定当前环境，Vite会自动加载对应环境的配置文件，实现多环境隔离。

常见环境文件命名规范：

\- `.env.development`：开发环境配置（默认环境，启动时无需指定mode）；

\- `.env.production`：生产环境配置；

\- `.env.test`：测试环境配置。

示例：创建开发环境和生产环境的环境变量文件：

```plain
# .env.development（开发环境）
VITE_APP_TITLE=Vite开发环境
VITE_APP_BASE_URL=http://localhost:5173

# .env.production（生产环境）
VITE_APP_TITLE=Vite生产环境
VITE_APP_BASE_URL=https://example.com
```

启动命令指定环境：

```bash
# 启动开发环境（默认，可省略 --mode development）
npm run dev

# 启动生产环境（构建时使用）
npm run build --mode production

# 启动测试环境
npm run dev --mode test
```

说明：不同环境的变量会自动覆盖，当前环境的变量优先级最高，例如启动生产环境时，`.env.production`的变量会覆盖`.env`中的同名变量。

#### 通过define选项注入全局变量

除了`.env`文件，Vite还提供`define`选项，用于在构建过程中注入全局变量，类似于Webpack的`DefinePlugin`。该选项允许将指定的字符串替换为具体的值，适用于需要全局注入非环境变量的场景。

### 文件监听优化

#### 文件监听核心说明

Vite在开发模式下会自动监听项目中所有文件的变化，当文件修改时，触发HMR或页面更新。但在部分场景下，项目中可能存在大量无需监听的文件或目录（如大型静态资源目录、日志目录等），过多的监听文件会增加系统资源消耗，降低Vite的响应速度，此时需要通过配置调整文件监听行为。

#### 调整server.watch选项

Vite提供`server.watch`选项，用于配置文件监听的行为，可通过`ignored`属性指定需要忽略的文件或目录，减少监听负担，提升开发响应速度。

示例：忽略大型静态资源目录，减少文件监听：

```javascript
import { defineConfig } from 'vite';

export default defineConfig({
  server: {
    watch: {
      // 忽略指定目录下的文件变化，支持glob模式
      ignored: ['**/large-static-files/**', '**/logs/**'],
    },
  },
});
```

说明：`ignored`属性支持glob模式，`**/large-static-files/**`表示忽略项目中所有名为`large-static-files`的目录及其子目录下的所有文件，Vite不会监听这些文件的变化，从而减少系统资源消耗，提升开发体验。

补充：除了`ignored`，`server.watch`还支持其他配置（如`usePolling`用于解决某些系统下监听失效的问题），可根据项目实际环境调整。

### 关键点

结合Vite的开发特性，以下两个关键点可进一步优化开发体验，减少不必要的消耗，提升开发效率：

#### 1. 减少不必要的监听

通过合理配置`server.watch.ignored`，忽略项目中无需监听的文件和目录（如大型静态资源、日志、第三方依赖的源码目录等），减少Vite的文件监听工作量，降低CPU和内存消耗，避免因监听文件过多导致的Vite响应缓慢。

核心原则：只监听开发过程中会频繁修改的文件（如src目录下的业务代码、组件、样式文件），忽略静态资源、构建产物、日志等不会频繁变化的内容。

#### 2. 适当的预构建

Vite 默认使用 esbuild 进行依赖预构建，esbuild 是用 Go 语言编写的构建工具，专为速度优化设计，相比传统的 JavaScript 构建工具（如 Babel 或 Terser），其解析和编译速度极快。通过高效的依赖解析和并行化编译，esbuild 能够在极短的时间内完成对模块的预构建，显著减少开发服务器的启动时间。

默认情况下，Vite 会自动扫描项目中的第三方依赖，自动进行预构建，将其转换为 ES 模块，并存入`node_modules/.vite`目录，后续开发时直接复用预构建结果，减少启动时间和实时编译负担。同时，你可以通过`optimizeDeps`选项更细粒度地控制预构建行为，进一步提升开发启动速度，核心配置项如下：

\- `optimizeDeps.include`：指定要提前预构建的依赖包，这些依赖在首次启动时会被 Vite 优化为较小的模块，以减少后续加载时间，适用于需要强制预构建的常用依赖；

\- `optimizeDeps.exclude`：指定不需要预构建的依赖包，这可以减少无用的预构建操作，避免不必要的资源消耗，提升预构建和启动性能，适用于一些轻量依赖或无需预构建的模块。

可通过`optimizeDeps`选项调整预构建行为，优化预构建效果，示例如下：

```javascript
import { defineConfig } from 'vite';

export default defineConfig({
  optimizeDeps: {
    // 强制预构建指定依赖（如react、react-dom）
    include: ['react', 'react-dom'],
    // 排除不需要预构建的依赖（如某些轻量依赖）
    exclude: ['some-large-lib'],
  },
});
import { defineConfig } from 'vite';

export default defineConfig({
  optimizeDeps: {
    // 强制预构建指定依赖
    include: ['vue', 'vue-router', 'lodash-es'],
    // 排除不需要预构建的依赖
    exclude: ['some-lightweight-dependency'],
  },
});
```

优化意义：合理配置`optimizeDeps`，可确保常用的第三方依赖被预先优化，减少开发启动时间和实时编译的开销，尤其适合第三方依赖较多的大型项目；同时排除无用依赖，避免预构建资源浪费，进一步提升开发启动效率。

## Vite生产构建优化

Vite 生产模式构建的核心目标是生成体积小、性能优、加载快的构建产物，适配线上部署场景，降低服务器带宽消耗和用户加载等待时间。与开发模式不同，生产模式会进行全量打包、代码压缩、资源优化等操作，Vite 基于 Rollup 实现生产构建，可通过灵活配置进一步优化产物质量和构建效率，兼顾“体积小”和“构建快”的双重需求。

生产构建优化的核心方向的包括：代码压缩、代码分割、资源优化、产物分析，通过合理配置这些选项，可显著提升线上应用的加载性能和运行效率。

### 代码压缩优化（build.minify）

#### 压缩工具选择与配置

Vite 生产构建默认启用代码压缩，通过`build.minify`选项可选择具体的压缩工具，核心支持两种压缩工具，需根据项目需求（体积优先/速度优先）灵活选择：

1. Terser：压缩效果更优，能最大程度减小产物体积，支持更多自定义压缩规则（如移除控制台打印、调试语句），但构建速度相对较慢，适用于对产物体积要求较高、不追求极致构建速度的项目（如线上正式部署的生产环境）；
2. esbuild：基于 Go 语言开发，压缩速度极快，能大幅提升生产构建效率，但压缩率略低于 Terser，适用于需要快速构建、对体积要求不极致的场景（如测试环境、临时部署）。

注意：Vite 生产模式默认使用`esbuild`作为压缩工具，若需追求更优的压缩效果，可手动配置为`terser`。

#### 配置示例与自定义压缩规则

通过`build.minify`指定压缩工具，同时可通过`terserOptions`（仅 Terser 生效）配置自定义压缩规则，如移除控制台打印、调试语句等，进一步减小产物体积。

```javascript
// vite.config.js
export default {
  build: {
    minify: 'terser', // 选择terser作为压缩工具，也可设置为'esbuild'
    terserOptions: { // 自定义terser压缩规则（仅minify为'terser'时生效）
      compress: {
        drop_console: true, // 移除所有console语句（生产环境常用）
        drop_debugger: true, // 移除debugger调试语句
        pure_funcs: ['console.log'], // 仅移除console.log，保留其他console方法（如console.error）
      },
    },
  },
}
```

说明：若选择`minify: 'esbuild'`，无需配置`terserOptions`，esbuild 会使用默认压缩规则，若需自定义 esbuild 压缩，可通过`build.esbuildOptions`配置。

### Rollup配置优化（build.rollupOptions）

Vite 生产构建的底层基于 Rollup 实现，因此可通过`build.rollupOptions`选项直接配置 Rollup 的相关参数，进一步优化代码输出，核心优化方向包括代码分割、手动拆分模块、输出配置等，实现更灵活的产物优化。

#### 核心配置方向：代码分割与模块拆分

代码分割是生产构建优化的核心手段之一，通过拆分代码模块，减少单个产物文件的体积，实现按需加载，提升首屏加载速度。Vite 支持自动代码分割和手动代码分割，可通过`rollupOptions.output.manualChunks`实现手动拆分，灵活控制模块拆分规则。

1. 自动代码分割：Vite 默认会对第三方依赖、公共模块进行自动拆分，无需额外配置，将重复依赖或大型依赖拆分为独立 chunk，利于浏览器缓存；
2. 手动代码分割：通过`manualChunks`配置，可手动将特定模块（如大型第三方库、独立业务模块）拆分到单独的文件中，实现更精细的代码分割，适配复杂项目的需求。

#### 配置示例：手动拆分模块

以下示例通过`manualChunks`将`node_modules`中的第三方依赖按包名拆分，每个第三方包对应一个独立 chunk，便于浏览器缓存，同时可手动拆分特定业务模块。

```javascript
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        // 手动代码分割配置，接收一个函数，返回chunk名称
        manualChunks(id) {
          // 拆分node_modules中的第三方依赖，按包名拆分
          if (id.includes('node_modules')) {
            // 将node_modules下的每个包拆分为独立chunk，如vue、react等
            return id.toString().split('node_modules/')[1].split('/')[0].toString();
          }
          // 可额外添加自定义拆分规则，如拆分大型业务模块
          if (id.includes('src/components/largeModule')) {
            return 'chunk-large-module'; // 将大型业务模块拆分为独立chunk
          }
        }
      }
    }
  }
}
```

配置效果：`node_modules`中的每个第三方包（如`vue`、`react`、`lodash`）会被拆分为独立的 chunk 文件，大型业务模块会被拆分为`chunk-large-module`，减少单个文件体积，提升缓存效率。

### 代码分割与懒加载

代码分割与懒加载相辅相成，代码分割是“拆分模块”，懒加载是“按需加载拆分后的模块”，核心目标是减少首屏加载的资源体积，提升首屏加载速度，尤其适用于大型项目和多路由应用。

#### 手动代码分割（manualChunks 进阶）

除了拆分第三方依赖，`manualChunks`还可用于拆分业务模块，根据业务场景灵活控制拆分粒度，例如将路由组件、大型组件拆分为独立 chunk，配合懒加载实现按需加载。

```javascript
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          // 拆分第三方依赖
          if (id.includes('node_modules')) {
            return `chunk-vendor-${id.toString().split('node_modules/')[1].split('/')[0]}`;
          }
          // 拆分路由组件（假设路由组件在src/views目录下）
          if (id.includes('src/views/')) {
            const viewName = id.split('src/views/')[1].split('.')[0];
            return `chunk-view-${viewName}`; // 每个路由组件对应一个独立chunk
          }
        }
      }
    }
  }
}
```

优势：手动拆分路由组件后，每个路由对应的 chunk 可单独加载，用户访问不同路由时，仅加载该路由所需的代码，减少首屏加载压力。

#### 动态导入实现懒加载

动态导入（`import()`）是实现懒加载的核心技术，Vite 原生支持动态导入语法，动态导入的模块会被自动拆分为独立 chunk，在需要时才加载，无需手动配置代码分割（但可通过`manualChunks`优化拆分规则）。

懒加载适用于路由组件、大型组件、非首屏必需的模块，核心作用是延迟加载非首屏资源，减少首屏加载时间。

##### 代码示例1：路由组件懒加载（Vue为例）

```javascript
// src/router/index.js
import { createRouter, createWebHistory } from 'vue-router';

// 动态导入路由组件，实现懒加载
const Home = () => import('./views/Home.vue');
const About = () => import('./views/About.vue');
const User = () => import('./views/User.vue');

const routes = [
  { path: '/', component: Home },
  { path: '/about', component: About },
  { path: '/user', component: User },
];

const router = createRouter({
  history: createWebHistory(),
  routes,
});

export default router;
```

效果：启动应用时，仅加载核心路由配置和首屏（Home）组件，访问`/about`或`/user`路由时，才加载对应的组件 chunk，减少首屏加载体积。

##### 代码示例2：组件懒加载（通用）

```javascript
// 假设有一个大型组件 MyComponent.vue，非首屏必需
// 动态导入实现懒加载
const MyComponent = () => import('./components/MyComponent.vue');

// 在父组件中使用
export default {
  components: {
    MyComponent // 组件被使用时才会加载对应的chunk
  },
  // ...其他选项
}
```

注意：动态导入返回一个 Promise，可配合`async/await`使用，也可通过加载状态提示优化用户体验（如加载中动画）。

### 资源优化

生产构建中，静态资源（图片、字体、音频等）是产物体积的重要组成部分，资源优化的核心目标是减小资源体积、优化加载方式，减少HTTP请求数，提升加载速度，核心优化手段包括图片压缩、资源内联控制等。

#### 图片与字体资源优化

图片和字体资源通常体积较大，可通过`vite-plugin-imagemin`插件进行压缩，减小资源体积，同时可根据需求将图片转为WebP格式（体积更小），**推荐使用cwebp工具处理WebP转换（避免使用已停止维护的旧库）**。

##### 1. 插件安装

```bash
npm install --save-dev vite-plugin-imagemin
```

##### 2. 配置示例（图片压缩）

```javascript
// vite.config.js
import viteImagemin from 'vite-plugin-imagemin';

export default {
  plugins: [
    viteImagemin({
      // 压缩GIF
      gifsicle: {
        optimizationLevel: 7, // 优化级别（1-7），级别越高压缩效果越好
        interlaced: false, // 禁用交错扫描
      },
      // 压缩PNG
      optipng: {
        optimizationLevel: 7, // 优化级别（0-7）
      },
      // 压缩JPG/JPEG
      mozjpeg: {
        quality: 75, // 压缩质量（0-100），越高越清晰，体积越大
      },
      // 压缩SVG
      svgo: {
        plugins: [
          { name: 'removeViewBox' }, // 移除viewBox属性
          { name: 'removeEmptyAttrs', active: false }, // 禁用移除空属性（根据需求调整）
        ],
      },
      // 转为WebP格式（推荐，体积更小）
      webp: {
        quality: 75, // WebP压缩质量
      },
    }),
  ],
}
```

说明：该插件支持自动压缩PNG、JPG、GIF、SVG等图片格式，并可自动将图片转为WebP格式（需确保项目支持WebP），大幅减小图片体积；若无需转为WebP，可删除`webp`配置项。

##### 3. 字体资源优化补充

字体资源可通过以下方式优化：1. 压缩字体文件（删除无用字形）；2. 按需引入字体（仅引入项目中使用的字体权重和格式）；3. 使用`font-display: swap`优化字体加载体验，避免页面闪烁。

#### 控制资源内联（build.assetsInlineLimit）

Vite 提供`build.assetsInlineLimit`选项，用于设置资源内联的阈值（单位：字节），小于该阈值的静态资源（图片、字体等）会被直接内联到JavaScript文件中，无需生成独立的资源文件，减少HTTP请求数；大于该阈值的资源会以独立文件形式输出，利于浏览器缓存。

```javascript
// vite.config.js
export default {
  build: {
    assetsInlineLimit: 4096, // 默认4KB（4096字节）
    // 说明：小于4KB的资源会内联到JS中，大于4KB的资源会输出为独立文件（如images/xxx.png）
  }
}
```

优化建议：根据项目实际情况调整阈值，若项目中存在大量小图片，可适当提高阈值，减少HTTP请求；若小图片较多导致JS体积过大，可降低阈值，将部分小图片转为独立文件。

## 打包工具默认配置

### 核心说明

Webpack 和 Vite 作为主流前端打包工具，在不进行任何额外配置的情况下，均默认具备代码分割、Tree-shaking（未用代码消除）、资源优化等核心能力，但两者的默认表现、生效前提、优化强度存在差异，且容易存在认知误解。本笔记重点梳理两者在默认配置下，三大核心能力的具体表现、生效条件及易混淆点，帮助明确“默认配置能做到什么、做不到什么”。

核心前提：以下所有默认表现，均基于“未手动修改任何配置”的基础上，区分开发模式与生产模式（两者优化策略差异较大）。

**知识点对应问题**：Webpack和Vite在不额外配置时，默认是否具备代码分割、Tree-shaking、资源优化能力？两者的默认表现核心差异是什么？

### 代码分割/代码拆分（Code Splitting）

代码分割的核心目的是拆分代码模块，减少单个产物文件体积，实现按需加载，提升加载性能。Webpack和Vite默认均支持代码分割，但默认拆分范围、拆分逻辑、生效场景存在明显差异，且均未达到“工程化最佳实践”的拆分效果。

#### Webpack：默认仅具备有限拆分能力

Webpack的默认代码分割的核心聚焦于“入口拆分”和“动态导入拆分”，对公共依赖的抽离需依赖默认策略或手动配置，具体表现如下：

1. 多入口拆分：当项目配置多入口（multiple entry）时，Webpack会天然为每个入口生成独立的entry chunk，实现“按入口拆分”，但这种拆分仅区分不同入口的代码，不涉及公共依赖的抽离。

示例：多入口默认拆分效果（无需额外配置）

```javascript
// webpack.config.js（默认多入口配置，无需额外代码分割配置）
module.exports = {
  entry: {
    page1: './src/page1.js',
    page2: './src/page2.js'
  },
  output: {
    filename: '[name].js', // 默认输出page1.js、page2.js两个独立chunk
    path: __dirname + '/dist'
  }
}
```

2. 动态导入拆分：动态导入（`import()`）是Webpack默认支持的核心拆分能力，使用动态导入的模块，会被自动拆分为独立的异步chunk，在需要时才加载，无需手动配置。
3. 公共包抽离：默认不主动进行精细化的公共依赖抽离（如vendors、commons）。生产模式下，Webpack会有简单的默认拆分策略（如抽离部分重复依赖），但该策略未必符合工程化的缓存目标（如稳定的vendor chunk），若需实现公共包的精准抽离，需手动配置`optimization.splitChunks`。

#### Vite：默认拆分，分开发/生产模式差异显著

Vite的代码拆分逻辑与Webpack不同，核心取决于开发模式与生产模式的构建机制，默认拆分表现如下：

1. 开发模式（vite dev）：本质是原生ESM按需加载，每个模块均为独立请求，不存在“bundle意义上的代码拆分”，看似“无限分包”，但这只是开发时的模块加载方式，并非最终生产产物的拆分结构。
2. 生产构建（vite build）：底层基于Rollup实现，默认具备以下拆分能力：

   \- 动态导入拆分：与Webpack一致，使用`import()`的模块会被默认拆分为独立异步chunk；

   \- 共享依赖分组：Rollup会对项目中的共享依赖进行一定程度的chunk分组，实现简单的公共依赖拆分，但不会默认按“vendor（第三方依赖）/commons（公共业务代码）”的结构拆分，若需实现该结构，需手动配置`build.rollupOptions.output.manualChunks`（或依赖框架封装的默认策略）。

#### 核心结论

Webpack和Vite默认均支持“动态导入拆分”，多入口项目均支持“按入口拆分”；但两者对“公共包（vendors/commons）的精细化抽离”均未默认实现，需手动配置才能达到工程化的缓存和体积优化目标。

**知识点对应问题**：Webpack默认的代码分割能力有哪些限制？Vite开发模式与生产模式的代码拆分有什么本质区别？两者默认均能实现公共包抽离吗？

### Tree-shaking（未用代码消除）

Tree-shaking的核心是消除项目中未被使用的代码（死代码），减小产物体积。Webpack和Vite默认均具备Tree-shaking能力，但该能力的生效依赖严格前提，并非“默认就能摇干净所有无用代码”。

#### Webpack：默认能做，但生效前提严格

Webpack默认支持Tree-shaking，但效果受模块格式、包的副作用标记、代码引入方式等因素影响，具体表现如下：

1. 生效前提：必须满足两个核心条件——一是项目代码及依赖均采用ESM模块格式（使用`import/export`）；二是依赖包本身是“可摇树”的（如package.json中配置`sideEffects: false`，标记无副作用，或明确标记有副作用的文件）。
2. 优化强度：生产模式下，Webpack会结合内置压缩器（如Terser）和自身的DCE（死代码消除）机制，实现更彻底的Tree-shaking；开发模式下，为了调试便捷和构建速度，Tree-shaking效果较弱，不会彻底消除未使用代码。
3. 失效场景：若项目中大量使用CommonJS模块（`require/module.exports`）、依赖包无副作用标记或存在大量副作用、代码引入方式导致全量引入（如`import _ from 'lodash'`，而非按需引入`import { debounce } from 'lodash-es'`），Tree-shaking会显著失效，无法消除未使用代码。

#### Vite：默认更容易触发，但同样依赖前提

Vite的Tree-shaking能力基于生产构建的Rollup实现，Rollup对ESM模块的Tree-shaking支持比Webpack更原生、更高效，默认表现如下：

1. 生效前提：与Webpack一致，需依赖ESM模块格式和依赖包的副作用标记，若依赖为CommonJS格式、存在大量副作用，Tree-shaking同样会失效。
2. 优化强度：生产构建时，Rollup会先进行Tree-shaking消除未使用代码，再配合esbuild或Terser进行压缩和DCE，整体摇树效果比Webpack默认表现更优，但同样受代码引入方式和副作用影响。
3. 开发模式：与Webpack类似，Vite开发模式不进行彻底的Tree-shaking，仅聚焦于快速启动和HMR，未使用代码不会被消除，方便开发者调试。

#### 核心结论

Webpack和Vite默认均具备Tree-shaking能力，Vite生产模式下的默认摇树效果更优；但两者的Tree-shaking效果均不取决于工具本身，主要由模块格式（ESM）、依赖包的副作用标记、代码引入方式决定，若不满足前提，摇树会大幅失效。

**知识点对应问题**：Webpack和Vite的Tree-shaking生效前提是什么？两者默认的Tree-shaking效果有什么差异？哪些场景会导致Tree-shaking失效？

### 资源优化（压缩、哈希、缓存、图片等）

资源优化的核心是减小静态资源（JS、CSS、图片、字体等）体积、优化加载方式、提升缓存效率，Webpack和Vite默认均具备基础的资源优化能力，但优化强度和覆盖范围有限，且严格区分开发模式与生产模式。

#### Webpack：默认优化聚焦生产模式，深度不足

Webpack的资源优化默认仅在生产模式下开启，开发模式为了调试和构建速度，几乎不进行生产级优化，具体表现如下：

1. 开发模式：不进行代码压缩、资源深度优化，仅实现基础的模块打包，保留代码格式和注释，方便开发者调试，也不涉及复杂的缓存策略。
2. 生产模式：默认开启一系列基础优化，核心包括：

   \- JS代码压缩：默认使用Terser进行JS压缩，减小JS体积；

   \- Scope Hoisting（作用域提升）：合并模块作用域，减少代码冗余，提升运行效率；

   \- Chunk IDs优化：生成稳定的chunk标识，配合文件名哈希，实现基础的缓存优化；

3. 优化局限：图片压缩、CSS深度抽离与压缩、静态资源的精细化处理（如图片格式转换）、分包策略的精细化配置等，均不默认支持，需额外引入loader（如file-loader、url-loader）或插件（如mini-css-extract-plugin、image-webpack-loader）才能实现。

#### Vite：默认优化更全面，仍需插件实现深度优化

Vite的资源优化同样区分开发模式与生产模式，生产构建的默认优化比Webpack更全面，但深度优化仍需插件支持，具体表现如下：

1. 开发模式：不进行生产级压缩，重点聚焦于快速启动和HMR，静态资源仅做基础处理，不优化体积和加载方式。
2. 生产模式：默认开启的基础优化包括：

   \- JS/CSS打包与压缩：默认使用esbuild进行JS/CSS压缩（可手动切换为Terser），实现基础体积优化；

   \- 文件名哈希：为产物文件添加哈希后缀（如`app.[hash].js`），便于浏览器长缓存，模块更新时仅更新对应文件的哈希；

   \- 静态资源处理：默认设置小资源内联阈值（4KB），小于该阈值的静态资源（图片、字体等）会内联到JS文件中，减少HTTP请求；大于阈值的资源会输出到assets目录，实现基础的资源分类。

3. 优化局限：图片深度压缩（如PNG/JPG压缩、WebP格式转换）、按业务场景定制的资源策略（如字体精细化处理）等，均不默认支持，需额外引入插件（如vite-plugin-imagemin）才能实现。

#### 核心结论

Webpack和Vite默认均仅在生产模式下开启基础资源优化，开发模式不做深度优化；两者的默认优化均覆盖JS/CSS压缩、基础缓存配置，但静态资源的深度优化（如图片压缩、格式转换）均不默认实现，需额外配置插件或loader。

### 最容易误解的核心要点

在理解打包工具默认配置时，容易出现三个核心误解，需明确区分，避免混淆：

#### 误解1：开发模式的“拆分”就是生产模式的“分包”

两者的“拆分”本质不同，不可混淆：

1. Vite开发模式：采用原生ESM按需加载，每个模块都是独立请求，看似“无限分包”，但这只是开发时的模块加载方式，不涉及最终产物的chunk结构，生产构建时会重新按Rollup的规则进行分包；
2. Webpack开发模式：通常会生成内存中的bundle文件，与生产模式的chunk结构、体积均不同，开发时的拆分仅为了调试便捷，并非最终线上产物的分包效果。

#### 误解2：Tree-shaking默认就能把所有没用的代码都删掉

Tree-shaking的效果并非“万能”，默认情况下，只要满足以下任一条件，就会出现“摇不动”的情况：

1. 依赖模块为CommonJS格式（而非ESM）；
2. 依赖包未配置`sideEffects`标记，或存在大量无法识别的副作用；
3. 代码引入方式错误（如全量引入第三方库，而非按需引入）。

#### 误解3：默认分包就是“最佳缓存结构”

Webpack和Vite的默认分包策略，仅能满足基础的体积优化需求，无法实现工程化所需的“稳定缓存结构”：

1. 工程化最佳实践中，通常需要将框架（如Vue、React）、第三方依赖（如lodash）、公共业务代码、页面代码分别拆分为独立chunk（如framework、vendor、commons、page），确保依赖更新时仅更新对应chunk，最大化利用浏览器缓存；
2. 要实现该结构，Webpack需手动配置`optimization.splitChunks`和`optimization.runtimeChunk`，Vite需手动配置`build.rollupOptions.output.manualChunks`，或依赖框架封装的默认优化策略。

**知识点对应问题**：关于打包工具默认配置，最容易出现的三个误解是什么？如何区分开发模式与生产模式的“拆分”差异？如何实现工程化的最佳缓存结构？

### 总结

Webpack和Vite在不额外配置时，均默认具备代码分割、Tree-shaking、资源优化三大核心能力，但存在以下共性特点：

1. 能力有限：默认优化仅能满足基础需求，精细化、工程化的优化（如公共包精准抽离、资源深度压缩、最佳缓存结构）均需手动配置；
2. 模式差异：开发模式优先保证速度和调试便捷，几乎不做深度优化；生产模式优先保证体积和性能，默认开启基础优化；
3. 前提依赖：Tree-shaking、代码分割的效果，均依赖模块格式、代码引入方式、依赖包配置等前提，并非“零配置即最优”。

核心建议：默认配置仅适用于简单项目或快速开发场景，对于中大型项目，需结合项目需求，在默认配置的基础上，手动优化代码分割、Tree-shaking、资源处理策略，才能达到最优的线上性能。
