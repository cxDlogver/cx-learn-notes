### 实现瓦片地图加载（核心亮点：瓦片化+鉴权）

全球能源数据是大规模栅格数据（如热力图），若采用整图加载，会导致网络开销大、渲染卡顿，因此项目采用TileWMS瓦片加载方式，同时通过自定义tileLoadFunction实现Token鉴权，保障私有数据安全，这是本任务的核心亮点，本人全程负责该模块的开发与调试。

#### 瓦片加载的类型：TileWMS

TileWMS是OpenLayers中用于加载WMS瓦片服务的数据源，适用于大规模栅格数据加载，其工作原理是：地图视图每变化一次（缩放、平移），OpenLayers会根据TileGrid自动计算当前视窗所需的瓦片索引，为每个瓦片发起一次HTTP请求，通过tileLoadFunction控制加载逻辑。

```javascript
const qgjMapSource = new TileWMS({
  url: `${baseURL}/map/getmap`, // 后端瓦片服务地址
  params: { // 瓦片请求参数，与后端服务端配置一致
    SERVICE: "WMS",
    VERSION: "1.1.0",
    REQUEST: "GetMap",
    Map: props.qgsMapPath, // QGS工程路径，后端用于定位地图数据
    LAYERS: props.tifMapPath, // TIF地图路径，对应能源热力数据
    FORMAT: "image/png", // 瓦片图片格式
    CRS: "EPSG:4326", // 坐标系，与地图视图一致
    language: locale.value, // 语言参数，适配国际化
  },
  serverType: "geoserver", // 服务端类型，告知OpenLayers解析响应格式
  tileLoadFunction: function (imageTile, src) { // 自定义加载函数，核心鉴权逻辑
    // 自定义加载逻辑，携带Token鉴权
  }
});
```

#### 自定义tileLoadFunction，实现Token鉴权

默认情况下，OpenLayers的瓦片加载是浏览器直接请求瓦片URL，无法携带自定义请求头，无法实现鉴权，因此需要重写tileLoadFunction，通过fetch请求携带Token，实现私有数据的安全访问，这是保障数据安全的核心逻辑。

```javascript
tileLoadFunction: function (imageTile, src) {
  // 获取Token（从本地存储中获取，由登录模块统一管理）
  const token = JSON.parse(localStorage.getItem("leiyangUser"))?.token;
  fetch(src, {
    headers: { Token: `${token}` }, // 携带Token，后端校验权限
  })
  .then(r => {
    if (!r.ok) {
      throw new Error("瓦片加载失败，权限不足或Token过期");
    }
    return r.blob(); // 将响应转为二进制Blob对象
  })
  .then(blob => {
    const objectUrl = URL.createObjectURL(blob); // 生成临时资源地址
    imageTile.getImage().src = objectUrl; // 将临时地址赋值给瓦片，完成加载
  })
  .catch(err => {
    console.error("Tile loading error:", err);
    // 加载失败处理，显示默认占位图
    imageTile.getImage().src = "/assets/images/tile-error.png";
  })
}
```

实战参与细节：本人负责tileLoadFunction的重写，核心实现了Token携带、响应校验、失败处理三个逻辑：一是确保Token正确获取，与登录模块联动，处理Token过期的场景；二是对响应状态进行校验，若权限不足或Token过期，提示用户重新登录；三是添加失败重试和占位图显示，提升用户体验，解决了瓦片加载失败导致的地图空白问题。同时采用双Token策略（access token放内存，refresh token放HttpOnly Cookie），进一步提升鉴权安全性。

#### 为什么必须用Blob？

`Blob`（Binary Large Object）是浏览器中用于表示不可变二进制数据的对象，瓦片图片属于二进制数据（PNG/JPEG格式），既不是JSON格式，也不是文本格式，因此必须使用Blob处理，否则会导致数据破坏或解析失败。

错误解析方式（会报错或破坏数据）：

```javascript
r.json()  // 错误，无法解析二进制图片数据
r.text()  // 错误，会破坏图片二进制结构，导致图片无法显示
```

正确解析方式：

```javascript
r.blob() // 正确，获取原始二进制图片数据
```

#### URL.createObjectURL(blob)的作用

`URL.createObjectURL(blob)` 用于生成一个临时的资源地址，该地址指向Blob对象，浏览器可以通过该地址识别并显示图片。由于瓦片图片是二进制数据，无法直接赋值给image元素的src属性，因此需要通过该方法转换为浏览器可识别的URL。

```javascript
const objectUrl = URL.createObjectURL(blob);
```

实战参与细节：本人在开发中发现，临时URL会占用浏览器内存，因此在瓦片卸载时，通过`URL.revokeObjectURL(objectUrl)`释放内存，避免内存泄漏，优化了长期使用后的性能。

#### OpenLayers默认tileLoadFunction

OpenLayers默认的瓦片加载函数仅实现基础的图片地址赋值，完全依赖浏览器原生加载机制，无法注入自定义请求头，因此无法满足项目的鉴权需求，这也是我们重写该函数的原因。

```javascript
function defaultTileLoadFunction(imageTile, src) {
  imageTile.getImage().src = src; // 直接赋值URL，无法携带鉴权信息
}
```

### 核心问题解析（项目实战高频问题）

#### Q1 项目里为什么要用瓦片地图加载？

核心原因是项目面对的是全球尺度的能源分布热力图，属于大规模栅格数据，数据覆盖范围大、分辨率高，若采用整图或大范围一次性加载，会带来三大问题：一是网络开销极大，单次加载可能达到几十MB，导致首屏加载缓慢；二是内存压力大，浏览器无法快速处理大规模图片数据，容易出现卡顿甚至崩溃；三是交互流畅性差，缩放、平移时需要重新加载整图，出现明显卡顿。

瓦片加载的优势的是：仅加载当前视图范围内的瓦片，每次请求仅产生几十个小图片请求，网络开销小；缩放、平移时仅加载新增瓦片，复用已有瓦片，交互流畅；后端提前按层级切分瓦片，前端按需加载，显著降低内存压力和渲染开销。

#### Q2 为什么不用前端切片，而要采用后端瓦片服务？

项目不采用前端切片，核心原因是全球尺度的高分辨率能源热力数据，前端切片在工程上不可行、不可控，具体原因如下：

- 数据规模与性能问题：前端切片需要将整张全球热力图一次性传输到浏览器，再由前端进行裁剪分块，这会带来极大的网络开销和内存压力，尤其是高分辨率、多时间尺度的数据场景下，浏览器容易卡顿、崩溃；而后端瓦片是服务端提前按层级和规则切分，仅向前端下发当前视图所需瓦片，效率更高。
- 计算职责划分：切片、重采样、坐标映射属于GIS服务层的核心职责，更适合由后端成熟的地理服务组件（如GeoServer）完成，后端可结合投影、缩放级别、数据范围精确生成瓦片，前端仅负责渲染和交互，架构更清晰，符合WebGIS分层设计思想。
- 数据安全：前端切片需要将完整的能源数据传输到浏览器，无法保障私有数据安全；而后端瓦片服务可通过Token鉴权，仅向授权用户下发瓦片数据，避免数据泄露。

#### Q3 如何实现的私有数据安全？

项目通过“前端鉴权+后端校验”的双重机制，实现私有能源数据的安全访问，核心实现如下：

- 前端层面：重写OpenLayers的tileLoadFunction，使用fetch手动请求每个瓦片，在请求头中携带Token，确保每个瓦片请求都有鉴权信息；采用双Token策略，access token放内存（短期有效），refresh token放HttpOnly Cookie（长期有效），避免Token被前端JS读取，降低XSS攻击风险。
- 后端层面：后端接收瓦片请求后，首先校验Token的签名与有效期，再根据用户权限判断是否允许访问该业务地图与图层，校验通过后才返回瓦片图片数据；即使用户拿到瓦片URL，没有合法Token也无法加载，避免公开链接被盗链或批量爬取。

实战参与细节：本人负责前端鉴权逻辑的实现，与后端配合完成Token校验流程，解决了Token过期、权限不足等异常场景的处理，确保数据安全的同时，不影响用户体验。

#### Q4 Token放在请求头中有没有可能会被截获？

从原理上讲，Token在网络中传输时，确实存在被截获的可能性，但项目中通过多层手段控制风险，将风险降到可控范围，具体措施如下：

- 采用HTTPS传输：所有地图与瓦片接口统一使用HTTPS协议，Token会被加密传输，避免在网络中明文暴露，防止被中间人截获。
- 优化Token存储：采用双Token策略，access token（短期有效，如2小时）放内存，避免被本地存储泄露；refresh token放HttpOnly、Secure、SameSite=Lax属性的Cookie中，避免被前端JS读取，降低XSS攻击导致Token泄露的风险。
- Token有效期控制：access token设置较短的有效期，即使被窃取，泄露风险也仅限于有效期内；refresh token通过HttpOnly Cookie存储，无法被前端获取，进一步提升安全性。

实战参与细节：本人负责Token的存储与传输优化，配合后端完成双Token刷新机制，确保Token过期后用户无需重新登录，同时保障数据安全。

#### Q5 SameSite是如何防止CSRF攻击的？

CSRF攻击的本质是：浏览器在用户不知情的情况下，自动携带Cookie向目标站点发起跨站请求，从而利用用户的登录态执行恶意操作。SameSite的作用是限制Cookie在跨站请求中是否会被自动携带，从浏览器层面切断CSRF的攻击条件，项目中采用SameSite=Lax（主流默认值）策略。

SameSite的三种策略及作用：

- SameSite=Strict：严格模式，Cookie仅在同站请求中发送，任何跨站跳转、表单提交、资源请求都不会携带Cookie，能从根本上防止CSRF，但会影响跨站跳转后的登录态体验，不适用于本项目。
- SameSite=Lax：宽松模式，Cookie不会在大多数跨站请求中携带（如POST表单、图片、iframe请求），但在用户主动发起的顶级导航GET请求中仍会携带Cookie，既保证了用户体验，又能防御绝大多数CSRF攻击，是本项目的首选。
- SameSite=None：无限制，Cookie会在所有跨站请求中携带，需要配合Secure属性使用（仅HTTPS传输），适用于跨站交互场景，本项目不适用。

## 任务二：全球尺度能源数据性能优化体系实现

本任务核心是针对全球尺度能源数据量大、加载压力大的问题，通过资源缓存、请求优化与分层渲染，构建性能优化体系，提升地图加载速度与交互流畅性。本人主要负责性能优化方案的设计与实现，重点解决瓦片加载慢、请求堆积、渲染卡顿等问题。

### 资源优化

资源优化的核心目标是：让每个瓦片更小、更易解码、更易缓存，从而提升吞吐率与首屏加载速度，结合项目特点，重点实现了LOD分级和缓存策略。

#### LOD分级（低zoom只提供低分辨率数据）

LOD（Level of Detail）分级是指根据地图缩放级别，提供不同分辨率的瓦片数据，低缩放级别（显示大范围，如全球）时，加载低分辨率瓦片，减少数据量；高缩放级别（显示局部，如区域）时，加载高分辨率瓦片，保证显示精度，从而平衡加载速度与显示效果。

实战中，瓦片大小选择1024x1024，该尺寸在性能和加载速度之间达到较好平衡，既避免了瓦片太小导致的请求过多、并发排队问题，也避免了瓦片太大导致的单请求耗时长、解码慢、内存压力大的问题。

```javascript

      0.17578125, // 缩放级别2（低分辨率，可根据实际扩展）

  });
  const token = JSON.parse(localStorage.getItem("leiyangUser"))?.token;

      VERSION: "1.1.0",
```

#### 三层缓存区分

工程实践中，OpenLayers Tile 相关的缓存需明确区分三层，避免混淆不同缓存的职责与作用范围，其中“默认缓存策略”的核心的是第一层（OpenLayers内部瓦片缓存）。OpenLayers 的 Tile 默认缓存策略，本质上是“内存级的瓦片对象缓存 + 浏览器层的资源缓存配合”。它并非显式配置 Redis/CDN 那样的“持久缓存系统”，核心逻辑是地图库内部缓存已请求、已创建的瓦片对象，同时借助浏览器HTTP缓存复用同URL瓦片资源，视图变化时优先复用已有瓦片，缓存压力过大时淘汰旧瓦片，而非无限保留。以下从缓存分层、核心细节、命中与失效场景等方面，详细梳理相关知识点，并附上对应问题以便巩固。

##### OpenLayers内部瓦片缓存

这是地图库自身维护的缓存，也是默认缓存策略的核心，完全由OpenLayers内部管理，与后端缓存、浏览器缓存相互独立但协同工作。

缓存内容（核心是瓦片实例及其资源，而非整屏快照）：

- tile 对象：已创建的瓦片实例，包含瓦片的完整信息
- tile 状态：标识瓦片当前所处状态（idle/loading/loaded/error），避免重复发起加载请求
- tile 对应的图像资源引用：瓦片关联的image/canvas资源，复用资源减少重复渲染
- 已请求过的某级某行某列瓦片实例：通过投影、缩放级别、行列号等维度唯一标识

缓存核心目的：

- 拖动地图时快速复用附近瓦片，提升视图切换的流畅度
- 回到已浏览过的区域时，无需重新创建和请求瓦片，减少重复计算与网络请求
- 降低前端渲染开销，避免频繁创建销毁瓦片导致的性能损耗

存储位置：仅存在于前端运行时内存中，属于临时缓存，页面刷新后会被清空，无法跨页面持久化。

知识点对应问题：OpenLayers内部瓦片缓存的核心内容是什么？为什么它不能实现跨页面持久化？

##### 浏览器HTTP缓存

该层缓存不由OpenLayers控制，由浏览器根据HTTP响应头自主管理，是默认缓存策略的重要补充，常被误认为是OpenLayers内部缓存的效果。

缓存内容：同URL的瓦片图片，具体缓存形式分为两种：

- memory cache：内存中的图片缓存，读取速度快，页面关闭后失效
- disk cache：磁盘中的图片缓存，读取速度略慢，但可跨页面、跨会话保留（取决于缓存策略）

缓存判断依据：浏览器通过后端返回的HTTP响应头决定是否缓存及缓存时长，核心响应头包括：

- `Cache-Control`：指定缓存策略（如max-age指定缓存有效期）
- `Expires`：指定缓存过期的具体时间
- `ETag`：资源唯一标识，用于验证资源是否更新
- `Last-Modified`：资源最后修改时间，用于对比资源是否有更新

注意点：当看到“瓦片未重新下载”时，可能是浏览器HTTP缓存命中，而非OpenLayers内部缓存命中，二者无直接关联但可协同提升性能。

知识点对应问题：浏览器HTTP缓存的判断依据有哪些？如何区分“OpenLayers内部缓存命中”与“浏览器HTTP缓存命中”？

##### 服务端或代理缓存

该层属于后端侧优化，OpenLayers 本身无法感知其存在，但能直接受益于该层缓存带来的加载速度提升，不属于默认缓存策略的范畴，但在工程实践中不可或缺。

常见实现方式：

- GeoWebCache：专门用于GIS瓦片的缓存组件，支持预切片和动态切片缓存
- WMTS预切片：后端提前按固定缩放级别、行列号切分瓦片，前端直接请求预生成瓦片
- CDN缓存：通过CDN节点分发瓦片资源，缩短请求链路，提升加载速度
- Nginx缓存：通过Nginx服务器缓存瓦片请求结果，减少后端服务压力
- GeoServer瓦片缓存：GeoServer服务自带的瓦片缓存功能，优化WMS/WMTS瓦片响应速度

知识点对应问题：服务端或代理缓存的常见实现方式有哪些？OpenLayers为何能受益于该层缓存？

##### OpenLayers内部瓦片缓存核心细节

默认缓存策略的核心是OpenLayers内部对Tile的管理机制，需重点掌握缓存的复用逻辑、存储特征、淘汰规则等细节。

###### 缓存复用逻辑：按“瓦片键”复用

OpenLayers 并非按“屏幕位置”缓存，而是按 `tile key`（瓦片键）或 tile coordinate（瓦片坐标）复用，核心逻辑是“同一标识的瓦片优先复用”。

瓦片唯一标识维度（需同时满足以下条件，才会判定为同一瓦片）：

- 投影（projection）：如EPSG:4326、EPSG:3857，投影不同则瓦片网格体系不同
- 缩放级别（z）：不同缩放级别的瓦片分辨率不同，无法复用
- 行列号（x/y）：瓦片在对应缩放级别下的唯一位置标识
- URL：瓦片请求的地址，包括请求参数（如LAYERS、STYLE等）
- 图层源（source）配置上下文：source的核心参数未发生变化

复用场景：当用户回到同一缩放级别、同一区域，且上述标识维度未变化，若瓦片仍在缓存中，会直接复用已有tile实例，无需重新创建、重新发起HTTP请求，这也是拖动地图时邻近区域补图速度快的核心原因。

知识点对应问题：OpenLayers内部瓦片缓存的复用逻辑是什么？判定为“同一瓦片”的核心标识维度有哪些？

###### 缓存存储特征：内存级临时缓存

OpenLayers内部瓦片缓存的核心特征是“内存级、临时化”，与持久化缓存有本质区别：

- 存储载体：仅存在于前端运行时内存，不涉及磁盘存储
- 生命周期：与当前页面绑定，页面刷新、组件销毁后，缓存会被清空
- 非持久化：无法跨页面、跨会话保留，再次打开页面需重新加载瓦片并重建缓存

常见误区：很多开发者误以为OpenLayers默认会将瓦片持久化到磁盘，实际上默认缓存仅为内存级临时缓存，持久化需依赖浏览器HTTP缓存或后端缓存。

知识点对应问题：OpenLayers内部瓦片缓存的存储特征是什么？为什么说它不是持久化缓存？

###### 缓存淘汰规则：有限容量 + 偏LRU思路

OpenLayers内部瓦片缓存为有限容量缓存，不会无限增长（避免内存溢出），其淘汰规则近似LRU（最近使用优先）思路，核心逻辑是“保留常用瓦片，淘汰不常用瓦片”。

具体淘汰逻辑：

- 优先保留当前视口及邻近区域的瓦片，确保当前视图渲染流畅
- 保留近期使用过的相近缩放级别瓦片，方便用户快速切换缩放级别时复用
- 淘汰规则：久未使用、距离当前视图较远、超出缓存容量上限的瓦片会被逐步清理

注意点：OpenLayers内部并未严格实现标准LRU算法，但其缓存行为与LRU思路一致，重点是“复用最近使用的瓦片，释放无用瓦片占用的内存”。

知识点对应问题：OpenLayers内部瓦片缓存的淘汰规则是什么？为什么要采用有限容量缓存？

###### 缓存命中场景

明确缓存命中场景，可帮助开发者判断缓存是否生效，进而优化性能，常见命中场景如下：

###### 拖动地图到已浏览的邻近区域

若之前浏览过的邻近区域瓦片仍在缓存中，会直接复用，表现为补图速度快、无额外HTTP请求，部分区域几乎瞬时显示。

###### 缩放后回到原缩放级别

若原缩放级别的瓦片未被淘汰，会直接复用缓存中的瓦片，无需重新请求；注意：不同缩放级别的瓦片是独立集合，无法相互复用（如zoom=1的瓦片不能复用给zoom=2）。

###### 图层暂时隐藏后重新显示

若图层仅做隐藏操作，未修改source配置、URL等核心参数，缓存中的瓦片可直接复用，无需重新加载。

###### 同URL瓦片再次请求

即使OpenLayers内部缓存中无对应tile实例，若浏览器HTTP缓存命中（同URL、未过期），也会直接复用浏览器缓存的瓦片图片，减少网络请求。

##### 缓存失效或被淘汰的场景

掌握缓存失效场景，可避免因缓存导致的数据不一致、加载异常等问题，常见失效/淘汰场景如下：

###### 缓存容量不足，旧瓦片被淘汰

最常见场景：用户持续拖动地图、切换缩放级别，缓存中积累的瓦片数量超出上限，此时离当前视图较远、久未使用的瓦片，以及旧缩放级别的大量瓦片会被逐步清理，释放内存。

###### source参数变化

source的核心参数变化后，瓦片的唯一标识（URL或配置上下文）会发生改变，原有缓存的瓦片无法复用，需重新请求，常见参数变化包括：

- `LAYERS`：切换瓦片对应的图层
- `STYLE`：修改瓦片渲染样式
- `CQL_FILTER`：添加或修改瓦片数据过滤条件
- `TIME`：切换瓦片对应的时间维度数据
- `language`：切换瓦片注记的语言
- URL中与鉴权相关的参数（如token）变化
- 其他影响瓦片资源的query params变化

注意点：在WMS服务中，即使仅修改一个参数（如`language=zh`改为`language=en`），也会被判定为不同瓦片，原有缓存失效。

###### 投影变化

当地图的projection（如从EPSG:4326改为EPSG:3857）发生变化时，瓦片网格体系会完全改变，原有缓存的瓦片无法适配新的投影，会直接失效。

###### 页面刷新或组件销毁

OpenLayers内部缓存为内存级缓存，页面刷新、浏览器标签关闭或地图组件销毁后，缓存会被彻底清空；此时若再次加载地图，能否快速显示瓦片，取决于浏览器HTTP缓存是否命中。

### 请求优化（控制请求风暴、消除无效请求）

针对用户交互过程中可能出现的重复请求、请求堆积、无效请求等问题，实现了请求缓存、请求去重、请求取消三大优化方案，本人负责所有请求优化逻辑的开发与调试。

#### 请求缓存机制

问题：用户可能重复点击相同位置，或相同请求参数的API调用重复发送，浪费带宽和服务器资源，导致响应延迟。

优化方案：创建请求缓存管理器，对相同请求进行缓存，设定缓存过期时间，避免重复请求，提升响应速度。

```javascript
// 1. 创建缓存管理器（Map存储，key为缓存标识，value为缓存数据和时间戳）
const requestCache = new Map(); // { cacheKey: { data, timestamp } }
const CACHE_EXPIRE_TIME = 5 * 60 * 1000; // 缓存过期时间：5分钟

// 2. 实现缓存请求函数
const cachedRequest = async (cacheKey, requestFn) => {
  // 检查缓存是否存在且未过期
  const cached = requestCache.get(cacheKey);
  if (cached && Date.now() - cached.timestamp < CACHE_EXPIRE_TIME) {
    return cached.data; // 直接返回缓存数据，响应时间从~200ms降至<1ms
  }

  // 发起新请求
  const data = await requestFn();

  // 存入缓存，更新时间戳
  requestCache.set(cacheKey, {
    data,
    timestamp: Date.now(),
  });

  return data;
};

// 3. 实战使用：点击地图获取能源数据时使用缓存
const handleMapClick = async (event) => {
  const { lon, lat } = event.coordinate;
  const params = {
    MAP: props.qgsMapPath,
    LAYERS: props.tifMapPath,
    lon,
    lat,
    lang: locale.value
  };
  // 生成唯一缓存键（精确到小数点后3位坐标，避免重复）
  const cacheKey = `getpoint_${params.MAP}_${params.LAYERS}_${lon.toFixed(3)}_${lat.toFixed(3)}_${params.lang}`;
  // 调用缓存请求函数
  const data = await cachedRequest(cacheKey, () =>
    request.get("/map/getpoint", { params }),
  );
  // 展示能源数据弹窗
  showEnergyData(data);
};
```

实战参与细节：本人负责缓存请求函数的封装，重点设计了缓存键的生成规则，精确到小数点后3位坐标，既避免了因坐标精度问题导致的缓存失效，又确保了相同位置的请求能命中缓存；同时在组件卸载时，自动清空缓存，避免内存泄漏；根据业务需求，将缓存过期时间设置为5分钟，平衡数据新鲜度和缓存效果。

优化效果：相同请求直接从缓存读取，响应速度大幅提升；减少40%以上的重复请求，节省带宽和服务器资源；用户点击交互体验显著提升，几乎瞬时响应。

#### 请求去重（防止重复请求）

问题：用户快速连续点击多个位置时，会同时发起多个相同请求，网络较慢时会出现请求堆积，浪费服务器资源，甚至出现响应顺序错乱的问题。

优化方案：创建进行中请求跟踪器，对相同请求进行去重，同一时间相同请求仅发起一次，后续请求复用同一个Promise。

```javascript
// 1. 创建进行中请求的跟踪器（Map存储，key为缓存键，value为请求Promise）
const pendingRequests = new Map();

// 2. 在cachedRequest中集成请求去重逻辑
const cachedRequest = async (cacheKey, requestFn) => {
  // 检查是否有相同请求正在进行，有则复用Promise
  if (pendingRequests.has(cacheKey)) {
    return pendingRequests.get(cacheKey);
  }

  // 发起新请求，将Promise存入跟踪器
  const requestPromise = requestFn();
  pendingRequests.set(cacheKey, requestPromise);

  try {
    const data = await requestPromise;
    // 存入缓存
    requestCache.set(cacheKey, {
      data,
      timestamp: Date.now(),
    });
    return data;
  } finally {
    // 请求完成（成功/失败）后，从跟踪器中移除
    pendingRequests.delete(cacheKey);
  }
};
```

#### 请求取消机制（AbortController）

问题：用户快速点击多个不同位置时，旧请求还未完成，旧请求返回后可能覆盖新请求的结果，同时浪费计算资源处理已过期的响应。

优化方案：使用AbortController创建请求取消控制器，在发起新请求前取消旧请求，组件卸载时取消所有未完成请求，确保只处理最新请求的结果。

```javascript
// 1. 创建AbortController管理器（Map存储，key为请求标识，value为控制器）
const abortControllers = new Map();

// 2. 实现带取消机制的请求函数（以点击获取能源数据为例）
const identifyNum = async (longitude, latitude) => {
  // 定义请求标识，用于区分不同类型的请求
  const abortKey = "identifyNum";
  // 取消之前的同类型请求
  if (abortControllers.has(abortKey)) {
    abortControllers.get(abortKey).abort();
  }

  // 创建新的AbortController
  const abortController = new AbortController();
  abortControllers.set(abortKey, abortController);

  try {
    // 发起请求，携带signal参数，用于取消请求
    const data = await request.get("/map/getpoint", {
      params: {
        lon: longitude,
        lat: latitude,
        MAP: props.qgsMapPath,
        LAYERS: props.tifMapPath
      },
      signal: abortController.signal // 绑定取消信号
    });
    // 处理请求结果
    showEnergyData(data);
  } catch (error) {
    // 忽略取消请求导致的错误
    if (error.name !== "AbortError") {
      console.error("请求失败：", error);
      ElMessage.error("获取能源数据失败，请重试");
    }
  } finally {
    // 请求完成后，移除控制器
    abortControllers.delete(abortKey);
  }
};

// 3. 组件卸载时取消所有未完成请求
onBeforeUnmount(() => {
  abortControllers.forEach((controller) => controller.abort());
  abortControllers.clear();
});
```

实战参与细节：本人负责请求取消机制的实现，重点处理了请求取消后的错误忽略逻辑，避免用户看到不必要的错误提示；同时在组件卸载时，取消所有未完成请求，避免组件销毁后请求仍在进行，导致内存泄漏和数据错乱。

优化效果：确保只处理最新请求的结果，避免过期数据覆盖新数据；减少不必要的数据处理和网络开销；组件卸载时无残留请求，提升系统稳定性。

#### 防抖优化（Debounce）

问题：地图平移、缩放时，moveend事件会频繁触发（每秒可达数十次），每次触发都会执行坐标计算、弹窗位置更新、世界副本坐标计算等操作，造成不必要的CPU开销，导致界面卡顿。

优化方案：使用防抖函数（Debounce）控制事件触发频率，仅在事件停止触发并静默一段时间后，才执行回调函数，减少计算开销。

Debounce（防抖限频）是一种**控制高频事件触发频率的机制**，其核心思想是：在事件被连续触发时，只在**最后一次触发结束并静默一段时间后**才执行回调函数。也就是说，连续触发过程中会不断重置计时器，只有当事件停止触发超过设定时间，逻辑才真正执行一次。

在地图交互场景中，缩放和平移会在短时间内触发大量视图变化事件，如果每一次都执行坐标计算、可见性判断和 DOM 更新，会造成性能浪费甚至界面抖动。通过 debounce 对事件处理函数进行限频，可以将高频触发压缩为一次有效执行，既保证交互结果正确，又显著降低计算和渲染开销，提升整体交互的稳定性。

```javascript
// 引入lodash的debounce函数，也可自定义实现
import _ from "lodash";

// 防抖优化：150ms内连续触发，只执行最后一次
const handleViewChange = _.debounce(() => {
  // 视图变化后需要执行的逻辑：弹窗位置更新、标记点可见性判断等
  updatePopoverPosition();
  checkMarkerVisibility();
}, 150); // 延迟150ms，平衡响应速度和性能

// 绑定视图变化事件（已防抖）
map.value.on("moveend", handleViewChange);
```

实战参与细节：本人负责防抖函数的配置和使用，测试了不同延迟时间（100ms、150ms、200ms）的效果，最终选择150ms，既保证了交互响应的及时性，又显著减少了事件触发次数，降低了CPU开销；同时在防抖函数中，优化了执行逻辑，优先处理核心操作（如弹窗定位），非核心操作（如日志打印）延迟执行，进一步提升性能。

知识点对应问题：什么是Debounce限频？项目中为什么要对moveend事件进行防抖优化？如何选择合适的防抖延迟时间？

#### Q1 什么是跨世界坐标问题

跨世界坐标问题是指在全球地图场景中，由于地图在水平方向允许无限平铺，同一个地理位置会在多个“世界副本”中重复出现，导致同一经纬度点在不同视图状态下对应不同的坐标表示。当用户进行大范围平移或多次跨越 ±180° 经线时，地图事件返回的经度可能超出常规的 [-180°, 180°] 范围，从而引发标记点错位、弹窗定位异常或交互跳变等问题，这类现象统称为跨世界坐标问题。

解决思路是**坐标规范化 + 副本选择 + 视图感知校正**。在工程实现中，首先对用户点击或交互得到的经度进行标准化处理，将其统一映射到 [−180°,180°)范围内，确保标记与业务计算基于稳定坐标；其次在地图缩放或平移过程中，根据当前视图范围计算该点可能出现的多个世界副本坐标，并从中选择位于当前视窗且距离视图中心最近的副本作为交互参考；

#### Q2 经纬度坐标和窗口像素是如何转换的？

在 WebGIS 中，经纬度坐标与窗口像素之间的转换本质上是**“地理坐标 → 地图视图坐标 → 屏幕像素坐标”**的两级映射过程。

首先，地图引擎（如 OpenLayers）基于当前 `View` 的投影方式、中心点、分辨率和缩放级别，将经纬度坐标转换为**相对于地图容器左上角的像素坐标**，例如 `getPixelFromCoordinate`。

其次，由于弹窗等 UI 元素通常是普通 DOM（如 `position: fixed` 或 `absolute`），需要将地图容器内的像素坐标进一步叠加地图容器在页面中的偏移量（`getBoundingClientRect`），从而换算为**浏览器窗口中的绝对像素位置**。

通过这种方式，可以在地图缩放和平移时，持续使用“坐标 → 像素”的实时映射结果，对弹窗或交互元素的位置进行校正，保证其始终与对应的地理位置保持一致。
