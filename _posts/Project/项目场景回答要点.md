# 走航车



## 项目难点：面试回答版

> 在这个项目里，我觉得最大的难点是实时数据的不稳定性。理论上走航车应该每秒采集一次气体数据，再由后台通过 WebSocket 推给前端，但真实场景里会出现一秒多条、几秒一条、消息延迟、批量到达、短时断流、WebSocket 假活或者断连等问题。这样前端收到的数据节奏就不是稳定的 1 秒 1 条，而是有波动的。
>
> 这个问题会带来三个直接挑战。
>  第一，数据断流时，图表不能伪装成连续曲线，所以我把时间窗口固定为五分钟，对断流区间的起点和恢复点做锚点处理，让图表能真实表达“这里断过流，后面又恢复了”。
>  第二，如果短时间来了很多条数据，不能每条都立刻渲染，否则会造成主线程压力过大、页面掉帧，所以我把 WebSocket 收到的数据先放进缓冲区，再通过 requestAnimationFrame 按节奏批量消费，把数据接收和页面渲染解耦。
>  第三，WebSocket 本身也不稳定，所以我设计了完整的连接机制，包括 token 过期后的刷新、心跳检测假活、断线原因判断和按策略重连，避免无意义重连和异常状态无法恢复。
>
> 所以这个项目的核心难点，不是单纯把实时数据展示出来，而是把一个不稳定的实时链路，处理成一个相对稳定、可恢复、可解释的前端展示系统。

这个项目里我觉得最大的难点，是**实时数据链路本身不稳定**，而前端又必须把这种不稳定的数据，尽可能稳定、准确地展示出来。

具体来说，理论上走航车应该是每秒采集一次气体数据，后台收到后再通过 WebSocket 实时推送给前端。但是在真实场景里，这个过程并不会严格按照“每秒一条”来发生，主要会有几类问题。

第一类是不稳定采样。
 走航车端本身可能因为设备计算、环境干扰或者采样耗时波动，出现一秒多次采样，或者几秒才采样一次的情况。

第二类是不稳定传输。
 即使后端已经拿到了数据，在服务端通过 WebSocket 推送到客户端时，也会受到网络波动影响，可能出现某条消息延迟到达、几条消息同时到达，甚至短时间断流的情况。这样前端收到的数据节奏就不是均匀的，而是会出现**抖动、堆积、断流**。

第三类是连接层的不稳定。
 WebSocket 在真实环境里还会有假活问题，也就是前端看起来连接还在，但实际上链路已经不可用了；另外还会遇到网络中断、token 过期、权限失效这些情况。一旦处理不好，就会导致页面数据停住、重复重连，或者恢复后瞬间收到大量积压数据，进一步放大渲染压力。

所以这个难点本质上不是“怎么把数据画出来”，而是要解决三个层面的稳定性问题：

### 1. 数据断流时，页面怎么正确表达

如果某段时间没有收到数据，前端不能简单把图表连成一条连续曲线，否则会误导用户，像是这段时间数据正常存在一样。
 所以我们对数据做了时间规划处理：把图表的展示时间窗口固定为五分钟，如果窗口内出现断点，就只在断流的起点和恢复点打锚点，用这种方式让图表能真实表达“这里断过流、后面又恢复了”，而不是伪造连续数据。

同时在地图展示上，也要考虑车辆在数据缺失时的表现。比如如果只是短暂断流，车辆是否保持上一位置静止；如果恢复后拿到新点，再继续推进。这些都要根据业务语义来设计，而不是单纯看有没有新数据就立即刷新。

### 2. 多条数据同时到达时，怎么避免页面卡顿

如果一秒钟内同时到达多条数据，而前端对每条数据都立刻触发一次图表或地图渲染，就会导致渲染频率瞬间过高，主线程压力变大，容易出现掉帧和卡顿。

针对这个问题，我做的是把“数据接收”和“页面渲染”解耦。
 也就是说，WebSocket 的 onmessage 收到数据后，不会直接进入渲染，而是先放进一个缓冲区。然后再通过统一的渲染调度机制去消费这批数据。

这里可以用 `requestAnimationFrame` 来控制渲染节奏，因为它会在浏览器下一帧绘制前执行回调，更适合做和视觉刷新同步的更新。这样可以避免消息一到就频繁改 DOM 或频繁调用图表更新，而是改成按帧、按批次去处理。
 实际策略上，可以根据页面压力控制成“每帧渲染一个点”或者“隔帧渲染一个点”，本质是把突发数据拉平，让用户看到的是连续、平滑的变化，而不是瞬间卡一下再跳很多点。

### 3. WebSocket 异常时，怎么做连接恢复和状态判断

实时项目里，WebSocket 不是建立一次就结束了，而是要考虑完整生命周期。
 这里最关键的是区分几种不同情况：

- token 过期导致的鉴权失败
- 网络抖动导致的暂时断开
- 假活连接
- 服务端主动关闭连接

如果不做区分，前端可能在 token 已经失效时还一直无意义重连，或者连接其实已经假活但页面还以为自己在线。

所以这里我会把 WebSocket 设计成一整套机制：

- 通过 token 做连接鉴权
- token 过期时优先刷新 token，而不是盲目重连
- 通过心跳机制检测假活
- 断线后判断原因，再决定是刷新 token 还是执行重连
- 重连时控制恢复节奏，避免恢复后瞬间把积压数据一次性全部推给前端，导致二次卡顿

这部分的关键不是“重连成功”本身，而是**区分断开的原因，并根据原因走不同恢复策略**。

------

## 一句总结版

所以这个项目最大的难点，其实是：
 **后端推过来的实时数据本身是不稳定的，但前端要把它处理成用户可理解、页面可承受、状态可恢复的稳定展示链路。**

我最后主要从三个方向解决这个问题：

- 在连接层，通过 token 刷新、心跳检测、断线重连保证 WebSocket 可用性
- 在数据层，通过固定时间窗口和断点锚点处理断流
- 在渲染层，通过缓冲区 + `requestAnimationFrame` 调度，把突发数据平滑消费，避免页面卡顿

## 项目优秀点

我觉得这个项目的优秀点，主要体现在三个方面。

第一是**实时链路更稳定**。
 通过 WebSocket + JWT + 心跳 + 指数退避重连，我把原来“连上了但不一定可用”的实时连接，做成了能探测、能区分、能恢复的链路。它的价值在于：网络短暂异常时可以自动恢复，权限失效时不会无意义重连，用户能更明确感知当前状态。

第二是**图表展示更准确、性能更稳**。
 通过只补边界 null、不补中间缺失点，我把“无数据、断流、恢复”的语义表达清楚了；通过增量更新和限频渲染，降低了 setOption 调用频率，减轻了 burst 数据对主线程的冲击，让图表在实时刷新时更流畅。

第三是**架构更可扩展**。
 图表层通过 getChart 收敛差异，地图层通过点、线、车分层解耦，实时与历史又复用了同一套时间推进模型，所以后面无论是新增图表类型、增加新的气体指标，还是扩展历史回放能力，改动范围都比较可控。

从结果上来说，我觉得至少取得了三类成绩：

一类是**用户体验结果**：页面不会因为短时断流就“看起来卡死”，异常状态也更容易解释。
 一类是**性能结果**：高频数据下的图表刷新更稳定，主线程压力更可控。
 一类是**工程结果**：组件复用度更高，后续需求扩展成本更低。

## 讨论点：网络断开恢复后，断开期间的数据怎么处理

在这个项目里，一个讨论比较多的点是：**如果网络断开一段时间后恢复，断开期间的数据到底要怎么展示。**

这个问题看起来像是一个简单的数据补发问题，但实际上会同时影响**图表真实性、地图展示效果和前端渲染压力**。

因为网络断开以后，会有几种处理思路：

第一种是把断开期间的所有数据一次性补发到前端，然后完整绘制出来。
 这种方式的优点是数据最完整，但问题也很明显。如果断开时间比较长，恢复后瞬间回推大量数据，会让前端短时间内收到很多点，图表和地图都可能出现明显的渲染压力。

第二种是完全保留断点，不补这段时间的数据。
 这样前端处理最简单，也能明确表达“这里发生过断流”，但缺点是如果断开时间其实很短，比如几秒钟，用户看到一个明显断点，会觉得页面不够平滑，也会损失一部分短时数据连续性。

第三种是把断开前最后一个点和恢复后的第一个点直接连起来。
 这种做法在图表上看起来可能比较连续，但在地图上会有明显问题。因为车辆实际行驶路径不一定是两点之间的直线，如果直接相连，就可能出现视觉上的“穿墙”或者“跨障碍直线穿越”问题，和真实轨迹不符。

所以这个问题最后不能只从“数据能不能补”来考虑，而要从**业务合理性和展示合理性**一起判断。

### 最终方案

我们最后做了一个**基于时间窗口的折中方案**：

- 以 **5 分钟** 作为前端展示和补数的统一时间窗口
- 如果断开恢复时，缺失的数据还在这 5 分钟窗口内，就按窗口内的数据去补齐展示
- 如果断开时间已经超过 5 分钟，就不追求把更久之前的数据全部补回来，而是**最多只返回最近 5 分钟的数据**
- 同时页面仍然保留断流语义，不会把特别长时间的断点伪装成连续轨迹

# 能源平台

## （1）你在项目中遇到的哪些难题，你是如何解决的

这个项目最值得讲的难题有 3 个。

### 难题一：全球尺度地图数据量太大，整图加载根本不可行

这个系统面对的是全球范围的能源热力图，属于大规模栅格数据。如果用整图或者大范围一次性加载，会直接带来几个问题：首屏加载慢、浏览器内存压力大、缩放和平移时明显卡顿。项目材料里也明确提到，整图加载会带来很大的网络和渲染压力，因此最终选择了 **TileWMS 瓦片化方案**，按当前视图范围按需加载瓦片，而不是一次把整张图传给前端。

我在实现上主要做了两层工作：

一层是 **瓦片化加载本身**。
 基于 OpenLayers 的 `TileWMS` 去接后端瓦片服务，让地图每次缩放、平移时只请求当前窗口需要的瓦片，而不是请求整图。这样把“大图问题”拆成了很多小瓦片问题，首屏和交互都稳定很多。

另一层是 **LOD 分级**。
 我根据 zoom 级别配置不同分辨率的瓦片网格，低缩放时只给低分辨率瓦片，高缩放时再给高分辨率瓦片，同时把瓦片尺寸控制在 1024×1024，在“请求数”和“单次解码开销”之间做平衡。这样解决的不是单点卡顿，而是全球尺度下整体吞吐率的问题。

------

### 难题二：瓦片数据是私有数据，默认加载方式无法做安全鉴权

OpenLayers 默认的瓦片加载方式，本质上就是把 URL 直接赋给图片 `src`，这种方式带不了自定义请求头，也就没法对私有数据做 Token 鉴权。项目里明确写到，这也是必须重写 `tileLoadFunction` 的原因。

我当时的解决方式是：

- 重写 `tileLoadFunction`
- 用 `fetch` 主动请求每个瓦片
- 在请求头里携带 Token
- 把响应转成 `Blob`
- 再通过 `URL.createObjectURL(blob)` 转成浏览器能识别的临时地址赋给瓦片

这样就把“地图图片直接加载”改造成了“受控的带鉴权资源加载流程”。同时我还处理了几个异常场景：
 比如 Token 过期、权限不足时做响应校验；加载失败时展示占位图；临时 URL 在不再使用时及时 `revokeObjectURL` 释放内存。项目中也强调了双 Token 策略、HTTPS 传输和 SameSite 等安全措施，说明这个模块不只是“能加载”，而是把安全问题一并考虑进去了。

------

### 难题三：全球地图支持横向无限平铺，弹窗和标记点很容易错位

这个项目里最有技术含量、也最容易让面试官眼前一亮的难点，其实是 **跨世界坐标问题**。
 因为全球地图水平方向允许无限平铺，同一个地理位置会出现在多个“世界副本”里。这样一来，用户点击地图后，标记点、弹窗位置、视图变化后的跟随，都可能出现错位、瞬移或者跳到错误副本的问题。项目材料里把这个问题讲得很清楚：经度可能会变成 190、370、-200 这种非常规值，从而导致坐标异常和弹窗定位错乱。

我最后是按三步来解决的：

第一步是 **坐标规范化**。
 点击后先把经度折回到 `[-180, 180)` 区间，让 marker 的几何坐标保持稳定。

第二步是 **像素链路校正**。
 因为弹窗不是 OpenLayers overlay，而是普通 DOM，所以必须走“地图坐标 → 容器像素 → 屏幕像素”的转换链路，再叠加地图容器在页面中的偏移量，才能让弹窗真正贴在点击点上。

第三步是 **世界副本选择**。
 视图平移后，不是简单沿用原坐标，而是先计算所有可能的副本坐标，再从里面选“当前视图中可见且离视图中心最近”的那个副本来定位弹窗。这样就避免了用户跨越 180° 经线后，弹窗突然跳到另一边或者出现“瞬移”。

### 一段可直接背的“难点题”回答

这个项目里我觉得最大的难点主要有三个。
 第一个是全球尺度的数据量太大，如果整图加载会导致首屏慢、缩放卡、内存压力大，所以我采用了 TileWMS 做瓦片化加载，并结合 LOD 分级，在低缩放时加载低分辨率瓦片，高缩放时再加载高分辨率瓦片，解决了全球地图的性能问题。

第二个是私有能源数据的安全访问问题。因为 OpenLayers 默认瓦片加载方式无法携带自定义请求头，所以我重写了 tileLoadFunction，用 fetch 手动请求瓦片，在请求头中携带 Token，再把响应转成 Blob 和临时 URL 给瓦片显示，同时处理了 Token 过期、权限不足、加载失败和临时 URL 内存释放等问题。

第三个是全球地图的跨世界坐标问题。因为地图支持横向无限平铺，同一个点会在多个世界副本中重复出现，所以我做了坐标标准化、坐标到像素的链路校正，以及副本坐标选择逻辑，确保点击后的 marker 和弹窗在缩放、平移后仍然能定位到当前视图里正确的副本，解决了弹窗错位和瞬移的问题。

# 官网开发

## （1）你在项目中遇到的哪些难题，你是如何解决的

这个项目最适合讲 3 个难点。

### 难点一：官网为什么不能只做成普通 SPA，而要做 SSR + SEO 工程化

官网和后台不一样，它核心诉求不是“登录后高频操作”，而是 **首屏可见、可收录、可长期获客**。
 如果只是普通 CSR，初始 HTML 内容少，页面内容要依赖客户端 JS 执行后才出来，这会让首屏更慢，也会让搜索引擎抓取和索引更不稳定。你这个项目之所以选 Nuxt 4，本质上就是为了解决这个问题：通过现代 SSR 让服务端直接返回有内容的 HTML，客户端再做 hydration 接管交互，兼顾首屏速度、SEO 和后续交互体验。

所以我在项目里的一个难点，其实是 **把“为什么做 SSR”落到工程实现上**。
 最后的做法是：基于 Nuxt 4 做 SSR 官网架构，同时把 SEO 配置从“手写零散 meta”升级成工程化方案，封装元信息生成器自动产出 TDK/OG，尽量减少页面层重复配置和漏配问题。

------

### 难点二：首屏体验和 SEO 不能只靠“开了 SSR”就自动变好

很多人会觉得用了 SSR 就结束了，但实际上官网性能和 SEO 还有很多工程细节。
 你项目里明确写了两件事：一是首屏渲染优化，二是 SEO 工程化；并且配了模块按需加载，降低主线程压力。

这里真正的难点是：
 **既要让搜索引擎更容易理解页面，又要让用户真的更快看到页面。**

所以我的处理思路是两层：

第一层是 SEO 信息标准化。
 把页面标题、描述、OG 信息做成统一生成逻辑，而不是每个页面手写一套，降低内容重复、字段漏配和不一致的问题。官网场景里，搜索引擎主要依赖 HTML 源码来理解页面内容，因此页面的标题、描述和结构化信息质量直接影响收录和自然流量效果。

第二层是首屏资源控制。
 对于非首屏关键模块做按需加载，避免一开始把所有 JS 都压到主线程上，减少首屏阻塞，让 SSR 返回的内容更快进入“可见 + 可交互”的状态。现代 SSR 本身就是“服务端先出内容，客户端再注水接管”，所以如果客户端包过重，还是会拖慢真实体验。

------

### 难点三：官网动效既要高级感，也不能引入白屏、抖动和卡顿

你这个项目里第三个任务很有价值：
 不是简单写几个 CSS animation，而是专门设计了 **可复用关键帧动效库**，并通过 `requestAnimationFrame` 精细控制复杂动画节奏，目标是保障高帧率体验，消除切换白屏和布局抖动。

这里真正的难点在于：
 官网往往既要品牌感，又要稳定性。如果动画处理不好，就会出现：

- 首次进入动画不触发
- 页面切换时白屏
- 列表重排时抖动
- 高度展开收起不流畅
- 主线程忙时动画掉帧

你材料里已经把核心原理讲出来了：
 在 Vue 过渡钩子里，`requestAnimationFrame` 的作用不是“为了炫技”，而是把初始状态和目标状态拆到不同渲染时机，让浏览器真正识别到变化，从而稳定触发动画。

所以我的解决方式是：

- 把动效抽成可复用库，而不是写成零散页面样式
- 基于 `<Transition>` / `<TransitionGroup>` 统一页面切换、元素进入离开、列表重排的动画方式
- 对复杂过渡用 rAF 做时序控制，避免浏览器把状态合并渲染导致动画失效
- 尽量优先用 `transform`、`opacity` 这些更稳定的动画属性，降低布局抖动风险。

### 讨论点一：官网到底做成普通 CSR 就够了，还是要上 SSR

这是最经典、也最适合讲的。

#### 回答思路

一开始比较容易有一种想法：
 官网页面不复杂，直接做成普通前端 SPA 也能上线，开发路径更熟。

但我更倾向于 SSR，原因不是为了“技术更高级”，而是因为官网的核心诉求不是后台那种强交互，而是首屏展示和 SEO。
 如果用普通 CSR，搜索引擎拿到的初始 HTML 内容少，首屏也更依赖 JS 下载和执行；而现代 SSR 能让服务端先返回完整 HTML，再由客户端注水接管，业务上更匹配官网场景。

最终结果是采用 Nuxt 4 做 SSR 官网架构，兼顾了可收录性、首屏速度和后续交互体验。

### 讨论点二：动画到底是“简单点能跑就行”，还是值得做成可复用库

第二个很适合讲动效库。

#### 回答思路

团队里对官网动画通常会有两种思路：
 一种是页面级临时写，哪里要动画就在哪里补；
 另一种是从一开始就抽成统一方案。

我更倾向于后者。
 因为官网里动画不只是装饰，它会影响首屏进入、组件切换、列表重排、折叠展开这些很多场景。如果全部写成零散代码，后面很容易出现风格不统一、时序不稳定、页面切换白屏和布局抖动的问题。

所以后来我更倾向于把常用过渡和关键帧模式做成可复用动效库，并在复杂过渡里用 rAF 控制状态切换时机，让浏览器能稳定识别动画起止状态。最终结果是动画效果更统一，页面切换和组件过渡也更稳定。

### 这题可以直接背的版本

这个项目里没有特别激烈的团队冲突，但有两个方案上讨论比较多的点。
 第一个是官网到底做成普通 CSR 就够了，还是要做 SSR。表面上看 CSR 开发更直接，但我认为官网的核心诉求是首屏展示和 SEO，而不是后台那种强交互，所以最终采用了 Nuxt 4 的现代 SSR 方案，让服务端先输出完整 HTML，客户端再做 hydration 接管，这样更符合官网场景。

第二个是动效到底是页面里零散写就行，还是应该抽成统一能力。我更倾向于后者，因为官网很多地方都涉及进入、离开、切换、重排，如果都写成临时动画，后面很容易出现风格不统一和稳定性问题。所以最后我把常见过渡和关键帧模式沉淀成可复用动效库，并通过 requestAnimationFrame 去控制复杂过渡时序，最终页面切换更平滑，也减少了白屏和布局抖动。
