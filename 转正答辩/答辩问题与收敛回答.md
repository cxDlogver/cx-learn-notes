# 答辩问题与回答

## 一、头部达人数据分级管控

### 1. 为什么要做头部达人数据分级管控？

- 头部达人数据敏感，原有权限体系存在管控不足、非必要查看、传播和数据泄露风险。
- 通过分级管控落实 **<u>最小权限原则</u>**，运营只能访问 **<u>职责范围内真正需要的数据</u>**。

### 2. 敏感数据的范围是如何定义的？

- 敏感数据范围由 **<u>产品、运营和风控共同确定</u>**，研发负责实现，不自行判断业务敏感性。
- 当前主要包括经营和经济指标、风险处罚等隐私数据，以及 **<u>L4 和 L4+</u>** 达人相关数据。

### 3. 权限改造上线后，如何证明机制有效？

- 上线后没有出现已知的越权访问或敏感数据异常暴露。
- 数据查看、权限申请和协助人申请均有审批留痕，截至材料记录时间累计 **<u>4000 多条审批记录</u>**。
- 审批记录持续产生，说明权限链路在真实业务中被触发并实际执行。

### 4. 头达权限项目中最大的工程挑战和能力提升是什么？

- 最大挑战是在 **<u>尽量不破坏存量代码</u>** 的前提下接入统一权限管控，兼顾现有功能兼容和已有能力复用。
- 开发前先梳理存量实现、依赖关系和已有全局能力，再通过抽象、封装和最小改动接入新能力，减少大范围重构带来的回归风险。
- 这次项目让我形成了在存量系统约束下进行 **<u>兼容式演进</u>** 的工程思路。

### 5. 你如何判断权限需求已经可以上线？

- 所有敏感数据相关的权限行为都要满足需求并完成验收，保证 **<u>功能正确性</u>**。
- 不能出现明显越权或敏感信息暴露，保证 **<u>安全边界</u>**。
- 公共能力要完成模块化封装，并通过前端代码覆盖率和相关测试检查，保证工程质量。

## 二、AI Coding 与研发工作流

### 6. 你如何理解 AI Coding 的完整工程闭环？

- 完整链路是 **<u>需求澄清 → 任务规划 → 代码实现 → 自动化验证 → 交付</u>**。
- AI 承担分析、规划、编码和验证等执行工作，人工在高风险节点和质量门禁进行审查。
- 目标是在提高研发自动化程度的同时，保证结果可验证、质量可控。

### 7. AI Coding 中最容易被低估但风险最大的环节是什么？

- 最容易被低估、风险最大的环节是 **<u>Test Case 的构建与验收</u>**。一些通用方案能够提供需求规范，但没有产出可执行、结构化的 Test Case，后续自动审查和验收就缺少统一标准。
- Test Case 的准确性和完整性可以暴露需求分析、任务规划中的理解偏差，避免偏差进入代码实现后造成大量返工。
- Test Case 是最终验收标准。每个验收项都要与需求、执行结果和证据对应，才能证明需求覆盖完整、验收结论可信。
- 根据内部统计，代码生成只占开发时间的 **<u>百分之十几</u>**，需求澄清和 Test Case 构建约占 **<u>57%</u>**，其余三成多用于执行 Test Case 和验收。代码生成不是耗时最多的部分，前置理解和验收标准才决定交付质量。

### 8. 如果需求理解偏差导致代码和测试形式上都通过，第一责任门禁在哪里？

- 第一责任门禁是 **<u>需求澄清</u>**。产品和研发要共同明确目标、冲突和不清晰项，不能让 AI 根据主观判断直接进入实现。
- 如果需求已经人工澄清但仍有理解偏差，问题可能来自模型对 PRD 的分析能力，此时需要通过下一道门禁继续发现。
- 第二道关键门禁是 **<u>Test Case 验收</u>**。Test Case 建立需求点和验收项的映射，其完整性和准确性能够检查 AI 的需求分析、任务规划是否符合产品和研发预期。

### 9. 为什么 Test Case 要在代码生成之前形成？

- Test Case 前置可以避免测试标准受到已经生成代码的影响，防止按照现有实现反向编写测试并掩盖需求偏差。
- Test Case 应直接基于需求规范建立 **<u>需求点与测试项的映射</u>**，把需求转换成可执行、可验收的测试矩阵。
- 测试矩阵要尽可能覆盖全部需求点、功能点和重要场景，明确后续代码实现的验收边界。

### 10. Test Case 为什么是 AI Coding 中的重要门禁？

- Test Case 把需求转化为 **<u>可执行、可验收的标准</u>**，AI 后续按照这些标准逐条执行和验收。
- Test Case 的准确性和完整性直接影响验收质量，也能检查前期需求分析和任务规划有没有跑偏。
- 因此，Test Case 既是自动化验收依据，也是需要人工审查的关键质量门禁。

### 11. 如何判断 Test Case 是否合格？

- 前置条件、操作行为和预期结果要与需求严格对应，保证 **<u>准确性</u>**。
- 测试项要尽可能覆盖全部功能点和重要边界，保证 **<u>完整性</u>**。
- 可以使用 **<u>BDD / Given-When-Then</u>** 组织测试行为，并明确每条 Test Case 对应的需求点，保证需求与验收可追溯。

### 12. Test Case 中为什么要设计正向、视觉和反向三类断言？

- 正向断言验证需求要求的功能是否真正实现。
- 视觉断言验证页面样式和交互效果是否符合设计。
- 反向断言验证不应该发生的行为没有出现，覆盖回归风险。
- 三类断言共同覆盖 **<u>功能、视觉和回归风险</u>**，避免只验证正常路径。

### 13. 为什么 Test Case 还需要 Assertion-Evidence 闭环？

- Assertion-Evidence 闭环的目标是保证 **<u>验收结论可信</u>**。AI 依据 Test Case 逐项验收，每个 Case 都要有明确的预期结果和验收清单。
- 验收需要覆盖功能、视觉和回归风险，每个维度都要记录实际观察结果，并判断是否与预期一致。
- 截图、Network 日志和操作步骤日志等证据要与断言、观察结果一一对应，不能只给出“通过”结论。
- 人工复核时也基于同一批证据判断观察结果能否支撑验收结论，因此 AI 自动验收和人工验收共用一套 **<u>断言—观察—证据—结论</u>** 链路。

### 14. AI 完成代码生成后，如何设计测试和验收保证代码真正可用？

- 编码前已经完成 Test Case，并建立测试标准与需求点的对应关系。
- 代码生成后逐条执行 Test Case，收集实际观察结果以及截图、日志等证据。
- 每条断言都要与执行结果和证据对齐，保证验收覆盖和结论可追溯。
- 人工重点复核关键页面、交互效果和证据可信度。
- 最终要证明 **<u>“需求实现了”</u>**，不只是“代码生成了”。

### 15. Human-in-the-loop 的人工门禁应该放在哪些节点？

- 人工门禁应放在 **<u>错误会被后续流程持续放大的节点</u>**。例如需求澄清发生偏差，会让任务规划、代码实现和验收一起偏离，因此需求目标、冲突和不清晰项必须由产品和研发确认。
- 人工门禁也应放在 **<u>最终质量判断节点</u>**。Test Case、验收结果和证据可信度需要复核，上线前的测试联调和质量检查需要人工放行。
- 人工审查只覆盖高风险和高不确定性环节，目的是在保留自动化效率的同时保证交付质量和验收结论可信。

### 16. 为什么不能每一步都让人工审核？

- 人工审查的作用是在自动化过程中控制高风险，而不是替代自动化；审核过多会直接降低 AI 工作流的效率价值。
- 低风险、结果确定的环节可以通过脚本自动验收，没有必要引入人工。
- 只有高风险、低置信度或自动验收结论不够可信的节点，才需要 **<u>人工介入</u>**。

### 17. AI Coding 中的长任务为什么要拆成多个子任务？

- 长任务拆分可以提高执行过程的 **<u>稳定性和可恢复性</u>**。任务规划时，每个子任务都要有独立目标和验收标准。
- 每个子任务完成后要输出关键产物并持久化，避免结果只保留在临时上下文中。
- 结构化状态要记录任务进度、输入输出和检查结果，保证执行过程可追溯、可审查。
- 发生失败或中断时，可以根据状态和持久化产物从中断位置恢复，不需要重新执行整个长任务。

### 18. 长任务应该按照什么标准拆分子任务？

- 核心判断标准是 **<u>子任务目标是否一致</u>**。目标决定需要哪些能力、工具和 Skill，也决定验收标准，必要时还会决定是否使用不同 Agent。
- Code 阶段的目标是实现高质量代码，验收可能包括代码审查、静态类型检查和安全检查；Review 阶段的目标是依据 Test Case 完成验收，并生成能够支撑结论的验收文档和证据。
- 两个阶段需要的能力不同。Code 阶段侧重编码和读取设计结构化数据，Review 阶段侧重稳定执行测试、操控浏览器和收集证据。
- 如果一个通用 Agent 无法稳定完成不同目标的复杂任务，可以分别构建专用 Agent，让它们按照各自的目标和评测标准独立演进。

### 19. 某个子任务执行失败时，如何保证系统可恢复？

- 系统通过 **<u>状态管理和持久化产物</u>** 判断当前子任务执行到了哪一步、哪些步骤已经完成。
- 恢复时重新读取已沉淀的需求、计划、代码、测试结果等产物，从最近的有效状态继续执行。
- Gate 检查应记录失败原因，并把原因作为后续 Agent 的输入上下文，帮助定位和修复问题。
- 状态、记忆和关键产物不能只存在于单次模型上下文中，否则任务中断后无法可靠恢复。

### 20. 业务方临时新增需求时，AI Coding 工作流如何快速响应又保证质量？

- 新需求和测试联调发现的问题都视为对现有需求、产物和代码的增量修复。
- 通常不打断当前正在执行的阶段，而是在当前子任务结束后保存 **<u>工作区快照</u>**，再基于已有产物做增量修改。
- 工作区通过矩阵维护需求、计划、测试项和代码之间的映射。需求变化后先定位受影响区域，修订需求，再同步调整计划和 Test Case。
- Test Case 需要检查哪些断言和预期结果要修改、哪些场景要新增；仍然坚持 **<u>测试标准先于代码修改</u>**。
- 代码修复完成后重新执行受影响的 Test Case 和必要回归测试，验收通过后把结论写回原问题。
- 整个过程保持规范驱动测试和规范驱动开发，不因临时需求跳过质量门禁。

### 21. 如何判断一个系统到底是单 Agent 还是多 Agent？

- 判断标准是系统中有几个 **<u>独立决策单位</u>**，而不是 Workflow 中有多少阶段或 Tool。
- 如果不同阶段都由同一个 Agent 推理决策，只是动态加载不同工具和 Skill，它仍然是单 Agent。
- 如果每个阶段分别由独立 Agent 负责，并且可以互不影响、并行执行或独立演进，就是多 Agent。

### 22. 多 Agent 相比单 Agent，最大的性能和工程开销在哪里？

- 多个 Agent 会增加独立模型调用次数，也可能重复读取和理解相同信息。
- Agent 之间需要同步上下文、任务状态和关键产物，处理传递丢失或版本不一致的问题。
- 系统需要额外调度，决定由哪个 Agent 执行、何时切换以及失败后怎样恢复。
- 不同 Agent 的输出可能冲突，需要做结果对齐、一致性维护和异常定位。
- 只有这些成本能换来明显的能力边界、隔离性或并行收益时，才值得采用 **<u>多 Agent</u>**。

### 23. 对严格串行的 AI Coding 工作流，有必要使用多 Agent 吗？

- 严格串行不等于一定要使用多 Agent，关键仍是阶段之间是否存在明确的职责边界和独立演进需求。
- 如果一个通用 Agent 通过动态组合不同工具和 Skill 就能稳定完成全部阶段，没有必要增加多个决策单位。
- 如果不同阶段存在明显能力边界，一个 Agent 无法同时做好，才需要为各阶段配置专用 Agent，并按各自目标独立优化。

### 24. 什么时候才真正需要使用多 Agent？

- 单 Agent Workflow 是同一个 Agent 在不同阶段加载不同工具或 Skill；多 Agent Workflow 是每个阶段有独立 Agent，即使它们可以复用相同 Harness，也能分别运行。
- 是否拆成多 Agent 主要看 **<u>是否需要独立运行或并行协作</u>**，以及 **<u>是否需要独立演进</u>**。
- 当通用 Agent 出现能力边界，某个阶段需要专门的工具组合、提示、状态或评测体系时，才适合构建专用 Agent。

### 25. 什么叫多 Agent 的“独立演进”？

- 独立演进是每个 Agent 围绕自己负责的阶段任务单独优化和迭代，最终形成解决该阶段问题的专用 Agent。
- 因为各 Agent 的目标、能力边界和验收标准不同，所以需要使用 **<u>不同的评测方法、指标和优化目标</u>**。
- 一个 Agent 的升级不应强迫其他 Agent 同步改造，各阶段可以按照自身问题和数据持续迭代。

### 26. 多个子任务之间如何保证正确衔接，避免上下文丢失或实现冲突？

- 子任务之间通过 **<u>输入输出契约</u>** 和 **<u>持久化产物</u>** 传递信息，避免只依赖临时对话上下文。
- Gate 根据契约检查上游输出，阻止错误或不完整结果继续向后传播。
- Orchestrator 根据结构化状态完成阶段调度和 Workflow 编排，明确每个子任务当前使用的产物版本和执行状态。

## 三、运营 Agent 与业务设计

### 27. 运营 Agent 主要想解决哪两个业务问题？

- 通过 **<u>批量个性化运营</u>**，在规模化覆盖下为不同达人提供不同诊断和策略。
- 通过 **<u>优秀经验沉淀</u>**，把经过业务效果验证的运营方法保存下来，供后续运营和 Agent 复用。
- 最终同时提高运营效率和策略针对性，让有效经验可以长期积累。

### 28. 运营 Agent 要解决“规模化”和“个性化”之间的什么矛盾？

- 传统规模化运营通过圈选相似人群和标准动作实现批量覆盖，效率高，但容易忽略同一表象背后的不同原因。
- 例如同样是“近七天未直播”，可能因为缺少合适商品，也可能因为经营活跃度下降，不能使用同一套策略。
- Agent 先对每个达人分别诊断，再生成针对性策略，最后调用已有平台和触达能力批量执行，实现 **<u>规模化覆盖与个性化决策</u>**。

### 29. 运营 Agent 的完整业务闭环是什么？

- 先圈选目标达人并获取经营数据，为后续诊断准备输入。
- 根据数据识别每个达人的核心问题，形成可追溯的 **<u>诊断结果</u>**。
- 围绕诊断问题生成个性化运营策略，而不是直接套用统一话术。
- 调用已有运营平台、BPO 或 RPA 能力完成批量触达和任务执行。
- 回收策略采纳、任务完成和后续经营数据，判断策略是否生效。
- 只把经过效果验证的优秀策略沉淀下来，形成 **<u>圈选—诊断—策略—执行—反馈—沉淀</u>** 的闭环。

### 30. 运营 Agent 落地的前提是什么？

- 原有业务链路要先打通，圈选、诊断、策略、触达和后续追踪本身能够正常运行。
- Agent 是接入已有运营工作流，不是重新建设运营平台。
- 数据、触达和业务系统要提供可调用接口，让 Agent 能够读取信息并执行动作。
- 必须有明确指标衡量运营提效和业务改善，保证 **<u>效果可验证</u>**。

### 31. 运营 Agent 为什么不能替代原有运营平台、BPO 和 RPA？

- 运营 Agent 替代的是运营人员的一部分重复性工作，目标是释放人力并提高效率，不是替换已有业务基础设施。
- 运营平台继续提供达人经营数据、任务管理和触达等基础能力，Agent 通过 API 读取和调用。
- BPO、RPA 等能力继续承担批量触达和确定性执行，Agent 负责诊断、决策和策略生成。
- 三者的分工是 **<u>Agent 做智能判断，平台和自动化系统提供数据与执行能力</u>**。

### 32. 为什么运营 Agent 在生成策略之前一定要先做诊断？

- 诊断先明确达人当前的问题和原因，再生成对应策略，避免模型在缺少事实依据时直接给出泛化建议。
- 诊断结果是显式的中间产物，可以检查策略是否基于正确问题，提高结果的准确性和可信度。
- 如果策略没有生效，可以沿着 **<u>诊断 → 策略 → 执行结果</u>** 追溯，判断问题来自诊断偏差还是策略生成偏差，再针对具体能力优化。

### 33. 为什么要单独设置“经验沉淀”阶段？

- 通用模型能够完成复杂任务，但缺少业务领域的专业知识和经过验证的运营经验。
- 经验沉淀阶段把有效策略、适用条件和效果结果保存到知识库，供后续运营和 Agent 复用。
- 复用经过验证的经验可以减少无依据生成，提升策略的专业性，让通用 Agent 逐步形成解决达人规模化运营问题的 **<u>专业 Agent</u>**。

### 34. 经验沉淀做不好会带来什么问题？

- 偶然有效或实际无效的策略可能被当成最佳实践，形成无效经验。
- 不同策略之间可能冲突，低质量内容持续积累后会造成知识污染。
- 后续 Agent 或运营基于错误经验生成更差的建议，错误会被不断复用和放大。
- 因此，经验入库前必须设置明确的 **<u>效果门槛</u>**，并保留适用条件和验证结果。

### 35. 为什么不能只把历史话术和策略放到知识库里检索？

- 历史话术只记录过去做过什么，通常没有说明为什么有效、适用于谁以及效果如何。
- 缺少执行反馈和经营结果，就无法判断策略是真正有效还是偶然相关。
- 需要打通诊断、策略、执行、反馈和业务结果，只将 **<u>被数据证明有效且具有复用价值</u>** 的策略沉淀到知识库。

### 36. 如何证明某个运营策略真的有效，而不是巧合？

- 是否成功生成策略只能证明系统可用，不能证明策略有效。
- 先看作者是否采纳策略、任务是否完成，再观察交易表现、活跃度等经营数据是否改善。
- 高采纳率和经营数据提升可以提供初步效果信号，但不能单独排除其他因素。
- 进一步通过 **<u>对照实验</u>** 比较相似达人：一组使用 Agent 策略，另一组使用传统规模化运营方式，在可比条件下观察经营结果差异，判断 Agent 策略是否带来增量效果。

### 37. 运营 Agent 应该重点看哪些效果指标？

- 运营提效看单个运营服务作者数、有效运营作者数和相关 KPI。
- 策略使用看作者采纳率和任务完成率，判断建议是否真正被执行。
- 业务结果看经营数据、交易表现、活跃度和等级跃迁等变化。
- 评价时既要证明 **<u>更省人</u>**，也要证明 **<u>效果更好</u>**。

### 38. 如果未来新增“风险识别”或“策略审核”能力，Agent 架构如何扩展？

- 把风险识别或策略审核作为新的阶段节点，明确它在现有 Workflow 中的位置。
- 为节点定义输入、输出、职责和 Gate 条件，再调整阶段完成后的调度和流转配置。
- 新能力通过插件方式接入，异常时可以移除或绕过，避免侵入其他节点。
- 工作流配置需要版本化，保留原版本，支持 **<u>向后兼容和平滑回退</u>**。

## 四、综合工程能力与答辩成长

### 39. 代码生成后，如何保证后续可维护，而不是成为一次性代码？

- 把多个页面或模块真正共用的逻辑抽象到公共层，避免相同能力重复实现。
- 共享能力统一管理，后续修改只调整公共实现，降低漏改和不一致风险。
- 不为形式上的复用过度抽象，公共层只承载稳定、通用的逻辑。
- 通过 **<u>合理抽象、统一管理和控制抽象边界</u>** 降低修改成本与回归风险。

### 40. 除了抽象和封装，还有哪些工程思想有利于后续维护？

- 将容易变化的业务规则做 **<u>配置化管理</u>**，减少散落在代码中的写死判断。
- 建立必要日志，保留关键执行信息，方便定位线上问题。
- 补充自动化测试和回归验证，降低修改已有能力时的风险。
- 保持清晰的模块边界和依赖关系，让问题能够快速定位、改动范围可控。
