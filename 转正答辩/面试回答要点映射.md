# 转正答辩面试回答要点映射

## AI coding 工作流

> 来源：`AI_Agent_答辩问题记录.md`。实际包含 20 道题；以下已按当前文档顺序连续编号。

### 问题一：Verify 阶段如何避免 Agent 只验证部分断言就直接 PASS？

> **题目：**
>
> 在 Verify 阶段，不是简单让 Agent 操作页面然后给出 PASS，而是要求：
>
> **Test Case → Assertion → Observed Result → Evidence → Conclusion**
>
> 逐层闭合。
>
> 假设实际运行时出现这样一个问题：
>
> > Agent 执行某个 Test Case，页面看起来符合预期，也保存了一张截图，于是直接把 Case 标记成 PASS。  
> > 但这个 Test Case 实际有三个断言：页面展示正确、接口请求参数正确、Mock 规则正确命中。Agent 只验证了第一个。
>
> 如果这是实际工作流里发生的问题，你会怎么定位它为什么会发生？又会怎么解决？

**一句话结论：** Verify 不能以“操作过页面”作为完成标准，必须让每个 Assertion 都形成 Observed Result、Evidence 和 Conclusion 的闭环。

**30秒回答：** 我先检查 Agent 为什么把局部证据当成整条 Case 的结论，通常是因为 Skill 只有自然语言要求，Agent 看到页面符合预期就提前结束。当前做法是在执行前初始化结构化验收记录，把所有 Assertion 列出来；执行中逐项写入结果和证据；结束前用脚本 Gate 检查是否还有未完成项、证据类型是否匹配。Gate 失败就返回具体 Assertion 补验。后续如果要做到不可绕过，还需要把 Gate 提升到 Hook 或 Workflow Runtime。

**1分钟展开：**

- 先明确目标：Verify 要证明结论可信，而不是证明 Agent 打开过页面。
- 再定位原因：自然语言 Skill 是软约束，长任务中可能漏步骤或根据局部结果提前结束。
- 当前机制：预先列出 Assertion；页面结果看 Screenshot / DOM，接口行为看 Network，Mock 命中看 Rule Hit 日志；每完成一项就增量落盘。
- 结束条件：Validation Script 检查未完成项、必填结果、证据存在性和失败状态；失败时精准回到对应 Assertion。
- 工程边界：现在主要靠 Skill、模板和脚本降低漏验概率；真正的硬 Gate 需要由外部 Runtime 自动触发。

**高频关键词：** Assertion 闭环、Evidence 类型、结构化验收、增量持久化、Validation Script、硬 Gate。

**易追问：**

- 不同 Assertion 应分别采集什么证据？
- Gate 返回哪些错误，Agent 才能局部补验？
- 怎样防止 Agent 跳过 Validation Script？

**回答雷区：**

- 把一张截图等同于整条 Case 已通过。
- 只说“把 Prompt 写得更严格”，不说明结构化状态和 Gate。
- 把尚未实现的 Runtime 硬约束说成当前已经落地。

### 问题二：AI Gate 的结论应该直接决定下一阶段吗？

> **题目：**
>
> 假设 Verify 的确定性检查已经确认每个 Assertion 都有 Observed Result，证据文件也存在。
>
> 但是进一步通过模型检查这些证据时，模型认为：
>
> > 证据虽然存在，但不足以证明这个断言成立。
>
> 那么：
>
> **AI Gate 的结论应该直接决定 Workflow 是 PASS 还是 FAIL、以及下一阶段去哪吗？如果不是，AI Gate、Orchestrator 和人工 Review 的关系应该怎么设计？**

**一句话结论：** AI Gate 有判断权，但没有业务流程控制权；下一阶段由 Orchestrator 根据结构化结果和预定义规则决定。

**30秒回答：** AI Gate 不应该只给 PASS 或 FAIL，而要返回原因、关联 Assertion 和证据，例如证据不足、实现错误或无法确定。证据不足时可以在 Verify 内有限次数重新取证；仍不收敛再转人工。AI Gate 只输出判断，Orchestrator 根据规则决定 reverify、repair、next stage 或 human review。否则模型一边判断、一边调用下一个 Agent，控制方式就已经变成 Supervisor。

**1分钟展开：**

- AI Gate 先输出结构化诊断，而不是只有二值结论，让后续知道具体补什么。
- 对 `INSUFFICIENT_EVIDENCE` 先局部重取证，避免一处证据缺失导致整条 Workflow 重跑。
- Gate 负责语义判断；Orchestrator 持有路由表，例如 `PASS → next`、`CODE_ERROR → repair`、`UNCERTAIN → human_review`。
- 如果模型持续选择下一阶段和下一执行者，它就不再只是 Gate，而更接近 Supervisor。
- 当前独立 AI Gate 和 Orchestrator 属于后续工程化设计；现有实践主要是 Verify 内的结构化检查和人工复核。

**高频关键词：** 判断权、控制权、结构化结果、规则路由、有限重试、Human Review、Supervisor。

**易追问：**

- AI Gate 的结果结构应该包含哪些字段？
- 什么情况在阶段内重试，什么情况进入 Repair？
- AI Gate 和 Supervisor 的分界点是什么？

**回答雷区：**

- 让模型直接决定并调用下一业务 Stage。
- Gate 只返回 PASS / FAIL，没有原因和证据关联。
- 不区分当前实践与未来 Workflow Engine 设计。

### 问题三：如何判断一个 Agent 的边界？不同 Stage 应复用还是拆分 Agent？

> **题目：**
>
> 假设一个 Workflow 中存在多个 Stage，例如代码实现、代码修复、浏览器验收等。
>
> 这些 Stage 底层可能使用同一个模型、同一个 Agent SDK 或同一套 Agent Harness，只是在不同阶段加载不同的 Skill、Tool 或 MCP。
>
> 那么：
>
> **应该怎样判断一个 Agent 的边界？什么时候多个 Stage 可以复用同一个 Agent，什么时候应该拆成不同 Agent？**

**一句话结论：** Agent 的边界首先是稳定的目标和职责边界，再用上下文、能力、权限、配置和评测边界判断是否需要独立。

**30秒回答：** 我不会按模型、SDK 或 Stage 数量拆 Agent，而是先看这些任务是否长期承担同一类目标。代码实现和代码修复目标、工具和评测相近，可以复用 Coding Agent，在不同 Stage 加载不同 Skill；Coding 和 Browser Verification 的目标、权限、工具和评测完全不同，更适合拆开。Stage 表示流程走到哪里，Skill 表示这一类任务怎么做，Agent 表示谁长期承担这类职责。

**1分钟展开：**

- 第一层看目标和职责：是否解决同一类问题、是否能形成稳定角色。
- 第二层看工程边界：上下文和能力组合、权限与运行环境、版本配置、评测方式是否接近。
- Coding 与 Repair 都围绕代码修改，能力和质量指标接近，可以复用同一 Agent，通过不同 Skill 区分阶段要求。
- Coding 与 Browser Verification 一个负责产出代码，一个负责按 Test Case 采证和验收，职责和评测不同，应考虑拆分。
- 共享同一个模型或 Harness 不代表是同一个 Agent；Agent 是职责配置，不等于底层模型实例。

**高频关键词：** 目标职责、工程边界、Agent / Stage / Skill、能力组合、权限、评测。

**易追问：**

- 同一个 Agent 如何在不同 Stage 切换 Skill 和权限？
- 多 Agent 会增加哪些运维和上下文传递成本？
- Browser Verification 为什么不能只是 Coding Agent 的一个 Tool？

**回答雷区：**

- 按“一个 Stage 一个 Agent”机械拆分。
- 把模型、Agent、SDK 和 Harness 混为一谈。
- 只谈工具不同，不谈目标和评测边界。

### 问题四：AI Coding 主流程为什么更适合 Orchestrator，而不是 Supervisor？

> **题目：**
>
> 你现在这套 AI Coding 流程本身已经有比较明确的 SOP：
>
> **Requirement → Task → Test Case → Coding → Verify → Repair / 交付**
>
> 假设后续要把它真正做成自动化的 Agent Workflow，有两种方案：
>
> - 用 **Business Orchestrator** 按预定义 Stage 和规则推进；
> - 用 **Supervisor Agent** 根据当前任务状态动态决定下一步调用哪个 Agent。
>
> 那么：
>
> **你会怎么选择？为什么这套 AI Coding 主流程更适合 Orchestrator 还是 Supervisor？哪些局部环节反而适合使用 Supervisor？**

**一句话结论：** 下一步可以提前定义的稳定 SOP 应由 Orchestrator 控制；只有局部开放任务才适合让 Supervisor 根据运行时证据动态路由。

**30秒回答：** Requirement、Task、Test Case、Coding、Verify、Repair 这些主阶段及其转移条件大多可以提前写成规则，所以外层业务主干更适合 Orchestrator：Stage 执行、Gate 判断、Orchestrator 查规则推进。Supervisor 适合复杂根因分析这类路径不能预先穷举的任务，它根据新证据动态选择专业 Agent。两者可以组合：外层稳定 SOP 用 Orchestrator，某个开放 Stage 内部再使用 Supervisor。

**1分钟展开：**

- 判断标准不是“是否用了模型”，而是下一步能否提前定义。
- 主流程的 Stage、Gate 结果和状态映射稳定，例如 `PASS → next`、`IMPLEMENTATION_ERROR → repair`。
- Gate 可以包含确定性检查和 AI 判断，但业务转移仍由 Orchestrator 执行。
- 复杂排障可能先查 Network，再根据结果查服务端或数据库，路径随证据变化，更适合 Supervisor。
- 组合方式：Supervisor 在局部 Stage 内完成开放分析，输出统一结果，再交回外层 Gate 和 Orchestrator。

**高频关键词：** 稳定 SOP、规则路由、模型路由、Orchestrator、Supervisor、局部组合。

**易追问：**

- 哪些状态应该预先写入路由表？
- Supervisor 如何避免无限调用 Agent？
- Orchestrator 与 Main Agent 调度 Sub-agent 有什么区别？

**回答雷区：**

- 把 Orchestrator 和 Supervisor 当作两个产品名比较。
- 因为“Supervisor 更智能”就把主流程控制权交给模型。
- 只说二选一，不说明外层与局部可以组合。

### 问题五：为什么 Mock 要和 Test Case 绑定？扩展到全栈后如何继续发挥作用？

> **题目：**
>
> 当前工作流没有按照接口提前批量生成 Mock，而是把 Mock 作为 Verify 中按需进入的辅助环节，并建立：
>
> **Test Case → Rule ID → Request Condition → Mock Response**
>
> 之间的映射。
>
> 那么：
>
> **为什么 Mock 不能简单按照接口提前批量生成，而要和 Test Case 绑定？这套设计是怎么从人工 Mock 的 SOP 演进成 Agent 自动化验收流程的？如果后续工作流扩展到全栈，这套思想还能如何继续发挥作用？**

**一句话结论：** Mock 应围绕 Test Case 和真实 Request 按需建立；扩展到全栈后，核心能力应升级为“Test Case 驱动测试状态准备”。

**30秒回答：** 同一个接口可能服务正常、空态、异常等多个 Case，所以接口名称不能决定 Mock Response，真正区分场景的是页面实际发出的 Request Condition。当前流程把人工 Mock SOP 自动化：先执行 Case，数据不足时捕获真实 Request，建立 Rule，重新执行并用 Rule Hit 日志和页面结果形成证据。全栈以后，正常状态优先由真实 Backend 和测试数据库准备，难构造的异常继续用 Mock，但仍然由 Test Case 驱动并通过真实执行校验。

**1分钟展开：**

- 先解释粒度：一个接口对应多个业务场景，必须由当前 Case 和真实请求条件共同确定 Rule。
- 人工 SOP 是先操作页面、看 Request、配规则、重跑并确认命中；当前 Workflow 把这条链交给 Agent 自动完成。
- 映射关系是 `Test Case → Rule ID → Request Condition → Mock Response`，Rule Hit 日志进入 Verify Evidence。
- 核心价值不是生成 Mock 文件，而是在后端或目标数据未就绪时让前端验收继续闭环。
- 全栈演进后，正常状态用测试数据库或 API 准备；真实请求未命中预期状态时定位并补齐；第三方异常等难构造场景保留 Mock。

**高频关键词：** Test Case 驱动、真实 Request、Rule ID、Rule Hit、按需 Mock、测试状态准备。

**易追问：**

- 如何选择稳定的 Request Condition？
- 怎样防止 Agent 为了通过测试随意修改测试数据？
- 全栈场景中 Mock 和真实测试数据库如何分工？

**回答雷区：**

- 简化为“按接口提前生成一批假数据”。
- 只讲 Mock 文件生成，不讲真实请求、重跑和证据闭环。
- 把全栈演进理解成完全取消 Mock。

### 问题六：为什么要单独设计 Repair？它如何保持代码和工作流产物一致？

> **题目：**
>
> 在当前 AI Coding Workflow 里，测试联调以后如果发现问题，并不是让 Coding Agent 只修改代码，而是进入 Repair，对问题相关的工作流产物和代码一起做修复。
>
> 那么：
>
> **为什么要单独设计 Repair，而不是发现问题以后直接修改代码？Repair 怎么定位当前问题影响了哪些 Requirement、Task、Test Case 和 Verify 记录？又怎么保证修复以后整个工作区仍然能够反映当前代码的最新状态？**

**一句话结论：** Repair 不只是改 Bug，而是沿产物映射做局部修复和局部复验，保证 Requirement、Task、Test Case、Verify 记录与当前代码同步演进。

**30秒回答：** 如果测试发现需求理解偏差，只改代码会留下旧 Task、旧 Test Case 和旧验收结论，后续人工或 Agent 还会根据错误产物继续工作。Repair 先定位问题对应的原子需求，再沿 Requirement、Task、代码范围、Test Case、Verify Evidence 的映射找到受影响部分，只更新必要产物和代码，重新执行相关 Case，并把新证据和结论写回原问题。

**1分钟展开：**

- 先说明双重目标：解决问题，同时维持代码与工作流产物的一致性。
- 前序阶段已经建立 `原子需求 → Task → 代码范围 → Test Case → Verify` 映射，Repair 用它反向定位影响范围。
- 修复链路是：发现问题、定位需求、更新受影响产物、修改代码、局部复验、更新证据与结论。
- Repair 不默认重跑整个 Workflow；实现细节问题只改代码和相关验收，需求理解偏差才向前修正 Requirement、Task 和 Test Case。
- 最终价值是让工作区始终描述当前代码，而不是积累过期中间文档。

**高频关键词：** 产物一致性、反向映射、局部修复、局部复验、增量更新、Source of State。

**易追问：**

- 如何判断问题需要回溯到哪一层产物？
- Repair 和 Orchestrator 的错误分支有什么区别？
- 多个问题同时修改同一产物时如何处理冲突？

**回答雷区：**

- 把 Repair 说成普通的“再次 Coding”。
- 每次出错都重跑整个 Workflow。
- 只修改代码，不更新受影响的测试和验收记录。

### 问题七：BITS 为什么不是“让 AI 再 Review 一遍代码”？

> **题目：**
>
> 在当前 AI Coding Workflow 里，BITS 被放在交付前，负责处理代码评审中的 Review Comment，并保留人工最终审查。
>
> 那么：
>
> **为什么 BITS 不能简单理解成“让 AI 再 Review 一遍代码”？它真正想解决的是什么问题？哪些工作适合交给 AI 自动处理，为什么最后仍然必须保留人工 Review？**

**一句话结论：** BITS 自动化的是 Review Comment 的分析、修复、验证和回写流程，而不是再生成一轮泛化代码审查；人工仍保留最终质量判断权。

**30秒回答：** Review Comment 不一定都成立，不能看到评论就机械改代码。BITS 先拉取评论、定位代码，再结合 Requirement、Task、Test Case、Verify 和当前源码判断评论是否有效。有效问题复用 Repair，更新代码和受影响产物、重新验证；无效评论说明不修改理由。AI 负责批量执行，人工最终确认判断和修复是否正确，再完成提交、回复和关闭。

**1分钟展开：**

- BITS 要减少的是研发逐条“找代码、看评论、判断、修改、验证、回复”的重复成本。
- 第一步不是修改，而是结合需求范围和现有验收判断评论是否成立，避免过度防御或需求外改动。
- 有效评论进入 Repair，保持代码、Task、Test Case 和 Verify 记录一致，并重新执行相关 Case。
- 无需修改的评论也要形成清晰依据，供人工快速复核。
- 人工保留最终 Gate，避免 AI 自己判断问题、自己修改、再自己宣布正确。

**高频关键词：** Review Comment、有效性判断、Repair 复用、结果回写、人工 Gate、质量独立性。

**易追问：**

- AI 如何判断评论属于过度防御或需求外建议？
- BITS 和普通 Code Review Agent 有什么不同？
- 人工最终主要审查哪些内容？

**回答雷区：**

- 把所有 Review Comment 都当成必须修复的问题。
- 把 BITS 描述成单纯增加一次 AI Code Review。
- 让 AI 独立关闭全部评论，不保留人工质量门禁。

### 问题八：为什么 Test Case 必须放在 Coding 之前？

> **题目：**
>
> 在当前 AI Coding Workflow 里，流程不是 Requirement → Coding → Test，而是先经过 Requirement、Task Planning 和 Test Case，再进入 Coding。
>
> 那么：
>
> **为什么要在 Coding 之前先生成 Test Case？它和传统“代码写完以后再补测试”有什么本质区别？如果 Requirement 已经拆成原子需求，Task 也已经告诉 Agent 要修改哪些代码，Test Case 在整个 Workflow 里到底承担了什么不可替代的职责？**

**一句话结论：** Test Case 要先于实现确定验收标准，既校验前序需求理解，也避免测试反向迎合已经生成的代码。

**30秒回答：** Requirement 和 Task Planning 完成后，不能直接假设 AI 已经理解正确。我会先按原子需求生成 Test Case，并由人工检查需求覆盖、场景和断言。这样验收标准来自需求，而不是来自代码。如果先 Coding 再补 Case，AI 可能只测试自己已经实现的 A、B，继续漏掉需求中的 C。后续 Mock、Verify 和 Repair 都以这批预先确定的 Case 为统一基准。

**1分钟展开：**

- 第一层作用是校验 Requirement 和 Task：每条原子需求是否有 Case，场景、操作和结果是否准确。
- Case 需要覆盖正向行为、反向或回归约束，以及必要的视觉结果。
- 第二层是保持测试标准独立：`Requirement → Test Case → Coding → Verify`，避免用实现定义验收。
- 第三层是形成任务契约：Mock 为 Case 准备数据，Verify 按 Assertion 采证，Repair 后重新执行受影响 Case。
- 因此 Test Case 不是 Coding 后的附属文档，而是贯穿需求、实现和验收的统一基准。

**高频关键词：** 验收前置、实现独立性、原子需求、统一验收契约、正反向断言、人工 Review。

**易追问：**

- 为什么 Task Plan 不能替代 Test Case？
- Test Case 应细化到操作步骤还是只定义目标？
- 如何防止生成 Case 的 Agent 与 Coding Agent 形成同源偏差？

**回答雷区：**

- 把 Test Case 仅仅理解为开发完成后的测试记录。
- 让代码实现反向决定应该验证哪些需求。
- 只关注正向功能，不考虑约束、回归和视觉结果。

### 问题九：人工如何审查 Test Case 是否覆盖 PRD 的全部需求点？

> **题目：**
>
> 在当前 AI Coding Workflow 里，Test Case 会在 Coding 前生成，并作为后续 Mock、Verify、Repair 的统一验收基准。
>
> 那么：
>
> **人工在审查 Test Case 时，怎么判断它是否真正覆盖了 PRD 中的全部需求？如何避免 AI 在“PRD → 原子需求”或者“原子需求 → Test Case”两个阶段发生遗漏？**

**一句话结论：** 人工应沿 `PRD 需求点 → 原子需求 → Test Case → Assertion` 双向审查，分别解决“有没有漏”和“有没有测错”。

**30秒回答：** 覆盖检查分两层。先按 PRD 功能模块检查所有需求点是否都拆成原子需求；页面、交互、业务状态、预期结果或约束不同且需要独立实现或验收时继续拆分。再把每条原子需求按 Given、When、Then 转成可执行 Case，不同前置条件、操作路径和结果要分开。最后检查每个 Case 的正向、反向或回归、视觉 Assertion 是否准确。

**1分钟展开：**

- 第一阶段检查 `PRD → 原子需求`：每个模块和明确需求点至少有映射，不能遗漏“不能发生什么”这类约束。
- 拆分标准不是句子长短，而是是否需要独立开发或独立验收；页面、交互、状态、结果不同通常应拆开。
- 第二阶段检查 `原子需求 → Test Case`：按前置条件、操作、预期结果组织，一个 Case 必须能独立执行和判断。
- 每个 Case 再检查正向功能、反向或回归约束、视觉结果三类断言。
- 人工先顺向看覆盖，再反向从 Case 回到 PRD 核对语义，确保既不漏测也不测偏。

**高频关键词：** 覆盖链、原子需求、Given / When / Then、正向断言、反向回归、视觉断言。

**易追问：**

- 什么粒度才算“原子需求”？
- 一条原子需求能否对应多个 Test Case？
- 如何量化覆盖完整度？

**回答雷区：**

- 认为“每条 Requirement 至少一个 Case”就一定完整。
- 只审查 Case 文案，不回到 PRD 和原子需求映射。
- 忽略业务状态、约束条件和视觉要求。

### 问题十：如何根据原子需求确定代码修改范围？Planning 不完整怎么办？

> **题目：**
>
> 在 Task Planning 阶段，需要把前面已经拆分好的原子需求进一步映射到具体的代码修改范围。
>
> 那么：
>
> **你是怎么根据一条原子需求判断它应该修改哪些代码、哪些模块和哪些文件的？这个过程具体怎么做？如果 Task Planning 一开始没有找全所有需要修改的文件，Coding 过程中发现必须修改计划范围之外的代码，应该怎么处理？**

**一句话结论：** Task Planning 应沿真实代码调用链找到“最小完整实现范围”，但这个范围是可校正的预期边界，不是禁止扩展的硬边界。

**30秒回答：** 我不会根据需求关键词猜文件，而是先定位页面、功能模块、数据和业务状态，再沿页面组件、状态或 Hook、接口和公共逻辑追踪真实调用链，判断需求应该在哪一层实现，形成最小但完整的预计范围。Coding 发现新的真实依赖时，可以扩展范围，但必须说明为什么与当前需求相关，先更新 Task Plan，再继续修改。

**1分钟展开：**

- 原子需求先提供业务入口：发生在哪个页面、模块、数据链路和状态下。
- 从入口沿真实调用链分析，而不是简单搜索同名文件。
- 在相关代码中继续判断正确实现层，避免页面各自重复逻辑，也避免只改 UI 而漏掉状态或接口。
- “最小”控制无关改动，“完整”保证实现链路不缺环，最终记录为预计文件、接口和模块范围。
- Planning 不可能一次绝对准确；Coding 发现新依赖时要给出代码依据、更新计划并保留追踪关系。

**高频关键词：** 业务入口、真实调用链、最小完整范围、预计边界、影响分析、计划回写。

**易追问：**

- 如何识别公共组件修改会影响哪些页面？
- 范围外修改由谁批准？
- Task Plan 更新后是否需要补 Test Case？

**回答雷区：**

- 根据 PRD 关键词直接猜几个文件。
- 把 Planning 范围当作绝对不可突破的边界。
- 允许 Agent 无依据扩大修改范围且不回写 Task。

### 问题十一：PRD、Figma 和现有代码发生冲突时怎么处理？

> **题目：**
>
> 在 Requirement 阶段，AI 不只是读取 PRD，还会结合 Figma 设计稿和现有代码理解当前需求。
>
> 那么：
>
> **如果 PRD、Figma 和现有代码之间的信息并不一致，AI 应该以谁为准？Requirement 阶段应该怎么识别和处理这种冲突，避免 AI 自己做需求判断后继续进入 Task Planning 和 Coding？**
>
> 例如：
>
> > PRD 说按钮只在 A 状态展示；  
> > Figma 中 A、B 两种状态都有这个按钮；  
> > 当前代码又只有 B 状态存在。
>
> 这种情况下应该怎么处理？

**一句话结论：** 冲突意味着需求输入还不可靠，AI 应整理差异并暂停后续流程，由拥有业务决策权的人确认后再继续。

**30秒回答：** 我不会设置“PRD 永远优先”或“代码现状优先”的固定权重。Requirement 阶段要把 PRD、Figma 和代码的具体差异列成 Requirement Ambiguity，说明各自表达和冲突位置，然后暂停 Task Planning 和 Coding，向产品或研发确认。结论回写 Requirement 后再放行。否则 AI 的一次猜测会被后续 Task、Case、Coding 和 Verify 稳定放大。

**1分钟展开：**

- 先判断输入是否明确到足以开发，而不是急着在三个来源中选一个“权威答案”。
- Requirement 阶段识别 PRD / Figma 冲突、前后表述不一致、业务状态缺失、代码现状与新需求关系不明等问题。
- AI 可以整理三方事实和差异，但不能根据时间、新旧或现状替产品做业务决策。
- 关键冲突进入人工确认，确认结论写回 Requirement，再继续 Task、Test Case 和 Coding。
- 这构成 Requirement Gate：检查的是需求是否可靠，不是文档是否已经生成。

**高频关键词：** Requirement Ambiguity、Source of Truth、需求决策权、暂停恢复、Requirement Gate、结论回写。

**易追问：**

- 哪些冲突必须阻塞，哪些可以记录假设后继续？
- 如果产品短期无法确认怎么办？
- 如何记录确认人和确认依据？

**回答雷区：**

- 机械规定 PRD、Figma、代码的固定优先级。
- 让 AI 自己选择最合理解释并继续开发。
- 只记录冲突但不阻断后续流程。

### 问题十二：Browser Verification 和 E2E Test 是什么关系？

> **题目：**
>
> 在 Coding 阶段，可以通过静态检查、Unit Test 和 Integration Test 分别验证工程质量、局部逻辑以及多个模块之间的协作。
>
> 那么：
>
> **如果要验证完整业务链路，为什么还需要进入 E2E 层？当前 Workflow 里的 Browser Verification 和传统通过固定 Playwright Script 执行的 E2E Test 有什么区别？为什么这里更希望把验收过程交给 Agent，而不是提前把所有测试输入和执行步骤固化成脚本？**

**一句话结论：** Browser Verification 不是新的测试层级，而是一种 Agentic E2E 验收：固定目标和断言，把具体操作路径交给 Agent 在真实页面中动态完成。

**30秒回答：** 静态检查验证工程合法性，Unit Test 验证局部逻辑，Integration Test 验证模块协作；要证明用户从页面入口走完整业务链仍然需要 E2E。当前 Browser Verification 本质上属于 E2E，区别在执行方式：传统脚本提前固定账号、数据和步骤，Agentic Browser Verification 固定 Test Case 和 Assertion，由 Agent 根据真实页面状态选择操作、测试数据和 Evidence，数据不足时再进入 Mock 或测试状态准备。

**1分钟展开：**

- 先区分维度：Unit / Integration / E2E 描述覆盖范围，Browser Verification 描述验收的执行方式。
- 完整业务链需要真实浏览器贯穿页面、前端逻辑、请求和最终结果，所以仍处在 E2E 层。
- 固定脚本把输入和路径预先确定，适合稳定回归；新需求阶段的页面状态和可用数据可能尚不稳定。
- Agentic 方式固定场景和 Assertion，让 Agent运行时选择页面路径、对象和 Screenshot / DOM / Network 等证据。
- 边界是目标和判断标准不能动态漂移；Agent 只自主决定“怎么验”，不能修改“验什么”。

**高频关键词：** Agentic E2E、测试范围、动态路径、固定 Assertion、真实页面、Evidence。

**易追问：**

- Agentic Browser Verification 能否替代固定 E2E 回归脚本？
- 如何保证每次动态路径仍然验证同一业务语义？
- 什么时候应把稳定 Agent 路径沉淀成固定脚本？

**回答雷区：**

- 把 Browser Verification 与 E2E 说成并列层级。
- 认为 Screenshot、DOM、Network 是 Agentic 方式独有。
- 允许 Agent 同时改变测试步骤和验收目标。

### 问题十三：当前 SOP 如何产品化为真正的 Business Workflow？

> **题目：**
>
> 当前这套 AI Coding Workflow 主要还是通过 SOP、Skill / Command 和工作区产物来串联 Requirement、Task、Test Case、Coding、Verify、Repair、BITS 等阶段。
>
> 那么：
>
> **如果未来要把它产品化成一个真正可长期运行的 Business Workflow，如何解决中断恢复、状态推进和阶段编排？Skill、Workflow、Orchestrator 和 Runtime 之间应该分别承担什么职责？**

**一句话结论：** 产品化要把 Stage、Gate 和状态转移显式建模，并由 Runtime 持久化执行状态；Skill 继续只负责单个 Stage 内“怎么做”。

**30秒回答：** 当前方案仍是 SOP、Command、Skill 和工作区产物，但已经通过 Stage 状态和子任务增量写入支持轻量恢复。产品化后，我会把 Requirement、Task、Test Case、Coding、Verify、Repair、BITS 建成显式 Workflow：Stage 执行，Gate 输出结构化状态，Orchestrator 按规则推进；Runtime 负责 Checkpoint、Pause / Resume、Retry、失败恢复和幂等。业务产物与运行状态分开保存。

**1分钟展开：**

- 当前恢复方式：Stage 完成或阻塞时记录状态；长 Stage 按 Test Case 等子任务增量持久化，恢复后从未完成项继续。
- 产品化不能把所有 Skill 再塞进一个大 Prompt，而要显式定义 Stage 输入、输出、Gate 状态和转移关系。
- 职责划分：Skill 决定当前任务怎么做；Workflow 定义阶段和分支；Orchestrator 根据 Gate Result 推进；Runtime 保证一次 Run 可靠执行。
- Requirement、Task、Test Case、Evidence 属于业务产物；当前 Stage、Checkpoint、重试次数和阻塞原因属于 Runtime State。
- 当前已落地的是轻量 SOP 与增量产物；独立 Workflow Engine 和 Runtime 是后续架构方向。

**高频关键词：** Business Workflow、Stage、Gate、Orchestrator、Runtime State、Checkpoint、幂等。

**易追问：**

- 哪些状态属于业务产物，哪些属于 Runtime？
- Retry 是由 Stage、Orchestrator 还是 Runtime 决定？
- 如何恢复一个被人工暂停的 Workflow？

**回答雷区：**

- 把 Skill、Workflow、Orchestrator 和 Runtime 混成同一层。
- 把当前 SOP 描述成已经上线的 Workflow Engine。
- 只谈流程图，不说明状态、恢复和幂等。

### 问题十四：为什么选择代码级 BAM Mock？未来如何避免技术强绑定？

> **题目：**
>
> 当前 AI Coding Workflow 里，Mock 最终选择了代码级 BAM Mock，而不是把 Mock 放到独立网络代理层。
>
> 那么：
>
> **为什么当前场景下选择代码级 Mock？这个选择解决了什么现实问题，又有哪些局限？如果未来这套 Workflow 要扩展到更多项目，应该继续绑定 BAM，还是把底层 Mock 能力抽象成统一接口？**

**一句话结论：** BAM 是当前项目链路最短、证据最容易闭合的实现方式；长期资产应是统一 Mock 能力和 Test Case 驱动的规则模型，而不是 BAM 本身。

**30秒回答：** 当前要建立的是 `Test Case → Rule ID → Request Condition → Mock Response`，并在 Browser Verify 中证明真实请求命中规则。代码级 BAM 能直接获取真实 Request / Response、基于真实 Response 做最小改动，并输出 Rule Hit 日志，因此当前接入成本最低。它的局限是项目和技术栈耦合。跨项目时上层 Workflow 应依赖 Mock Adapter，由 BAM、Proxy、MSW 等实现 capture、apply、verify 和 cleanup。

**1分钟展开：**

- 先解释当前目标：不只是替换 Response，而是让规则与 Test Case、真实请求和 Evidence 对应。
- BAM 在业务请求链路中，便于读取真实结构、提取匹配条件，并尽量基于真实 Response 修改少量字段。
- Rule Hit 日志可以和页面结果在同一次 Verify 中采集，证据链更短。
- 局限是侵入当前项目并依赖 BAM 接入方式，换技术栈后无法直接复用。
- 未来抽象 Mock Adapter，上层只关心捕获请求、加载规则、验证命中和清理，不关心底层是代码 Mock 还是代理层 Mock。

**高频关键词：** BAM、代码级 Mock、Rule Hit、真实 Response、Mock Adapter、跨项目复用。

**易追问：**

- Mock Adapter 的统一输入输出是什么？
- 网络代理层相比 BAM 有什么优势？
- 如何确保规则清理和 Case 隔离？

**回答雷区：**

- 说成“BAM 能做、网络层做不到”。
- 把当前技术选型包装成长期唯一方案。
- 只抽象接口名，不说明上层稳定的规则模型。

### 问题十六：Design Verification 如何判断页面与 Figma 真正对齐？

> **题目：**
>
> 在当前 AI Coding Workflow 里，Design Verification 不只是让 AI 把页面截图和 Figma 设计稿做一次主观对比。
>
> 那么：
>
> **AI 在做视觉验收时，具体怎么判断页面是否真正和 Figma 对齐？如何避免只依赖截图导致判断不稳定？哪些部分适合做结构化检查，哪些部分仍然更适合人工做最终视觉 Review？**

**一句话结论：** 视觉验收应同时检查 Figma 到 Code、Figma 到 Browser DOM / CSS、以及设计稿到 Screenshot，分别解决实现参数、运行结果和整体观感。

**30秒回答：** 只比较两张截图能发现“看起来不一样”，但不容易定位具体节点和属性。我会先从 Figma 获取布局、尺寸、间距、字体和颜色等结构化数据，在 Coding 阶段检查实现；页面运行后再把这些设计数据与真实 DOM 和 computed CSS 对比；最后保留 Figma 与 Browser Screenshot 给人工做整体视觉 Review。这样前两层可定位，最后一层保留人的整体审美判断。

**1分钟展开：**

- 第一层 `Figma 数据 → Code`：在实现阶段检查设计参数是否正确写入源码。
- 第二层 `Figma 数据 → Browser DOM / CSS`：页面运行后检查父子布局、继承、响应式和状态影响下的最终生效样式。
- 前两层应输出具体节点和属性差异，避免只给主观相似度。
- 第三层 `Figma 设计稿 → Browser Screenshot`：人工检查整体层级、空间关系、视觉平衡和难以结构化的观感。
- 三层证据互补，不能用结构化属性完全替代人工，也不能只靠截图完成全部定位。

**高频关键词：** Figma MCP、结构化设计数据、computed CSS、DOM、Screenshot、人工视觉 Review。

**易追问：**

- Figma 节点如何映射到 Browser DOM？
- 响应式页面的视觉容差怎么定义？

**回答雷区：**

- 把视觉验收简化成截图相似度。

### 问题十七：Human-in-the-loop 应该放在哪些节点？

> **题目：**
>
> 当前 AI Coding Workflow 并不是完全无人化，而是在 Requirement、Test Case、Verify / Design、最终 Review 等关键位置保留人工参与，同时尽量让 Coding、Mock、Repair 等执行过程由 AI 自动完成。
>
> 那么：
>
> **Human-in-the-loop 应该放在哪些节点？判断一个 Stage 是否需要人工介入的标准是什么？如果人工 Gate 太多，会不会让 Workflow 又退化成人工流程？你是怎么在自动化程度和最终交付可信度之间做平衡的？**

**一句话结论：** 人工应放在业务语义不明确、错误会显著向后传播或需要独立质量确认的节点，其余可确定性验证的执行环节尽量自动化。

**30秒回答：** 我不会每个 Stage 都加人工 Gate。判断标准是：这个决策错了是否会大范围影响后续，以及 AI 能否通过明确事实可靠完成。Requirement 冲突、Test Case 覆盖、Verify / Design 证据和最终 Review 属于高风险节点，需要人工确认；Coding、Mock、Repair、静态检查和结构化校验在输入明确时尽量自动完成。这样人的角色是关键决策者和最终审核者，而不是每一步的操作员。

**1分钟展开：**

- 人工过多会让 Workflow 退化成人工驱动；完全无人又会让业务歧义和同源自证失去控制。
- Requirement 冲突涉及业务决策权，必须暂停并由产品或研发确认。
- Test Case 决定后续 Coding 和 Verify 的验收标准，错误会形成“错误但自洽”的链路，因此需要人审。
- Verify / Design 和最终 Review 保留独立质量判断，避免 AI 自己执行、自己判断、自己宣布正确。
- Coding、Mock、Repair 等在输入明确、结果可验证时自动运行，人工只处理例外和高风险结果。

**高频关键词：** Human-in-the-loop、高风险节点、错误传播、独立质量 Gate、暂停恢复、自动化边界。

**易追问：**

- 如何量化“高风险节点”？
- 人工长时间不响应时 Workflow 怎么处理？
- 是否可以对低风险需求减少人工 Gate？

**回答雷区：**

- 每个 Stage 都要求人工确认。
- 为追求无人化取消所有独立质量门禁。
- 因为任务“复杂”就加人工，而不分析决策风险和可验证性。

### 问题十八：跨 Stage 的 Context Engineering 应该怎么设计？

> **题目：**
>
> 在 Requirement、Task、Test Case、Coding、Verify 等阶段之间，会不断产生新的工作区产物。
>
> 那么：
>
> **后一个 Stage 到底应该读取多少前序上下文？原始 PRD、Figma 截图、技术文档和仓库代码，与 Requirement、Task Plan、Test Case 等中间产物之间应该是什么关系？如何避免 Context 越来越大，同时又避免多轮摘要导致信息不断丢失、最终让 AI 实现跑偏？**

**一句话结论：** 原始资料始终是 Source of Truth，中间产物负责结构化、索引和阶段契约，每个 Stage 再按任务动态组装最小充分 Context。

**30秒回答：** PRD、Figma、技术文档和 Codebase 不能被 Requirement、Task Plan 或 Test Case 替代，因为中间产物经过 AI 压缩，连续摘要会放大遗漏。中间产物主要负责告诉下一 Stage 当前处理什么、回到原始资料哪里读，以及提供明确任务契约。Task Planning 和 Test Case 要回读原始需求；Coding 主要消费 Task Plan 并按需读取原文和代码；Verify 主要消费 Test Case，再补充 Figma、Mock Rule 和运行证据。

**1分钟展开：**

- 第一层区分：原始资料保存完整事实，是 Source of Truth；中间产物是 AI 的结构化理解，不能替代原文。
- 中间产物有两个作用：收敛检索范围，以及作为 Stage 之间的输入输出契约。
- Task Plan 是 Coding 的 Primary Context，Test Case 是 Verify 的 Primary Context，但两者都能按需回到原始 Source。
- Context 按 Stage 目标动态组装，不默认塞入整份 PRD、全部 Case 和所有历史记录。
- 发现信息不足时动态读取对应 Source，而不是继续对摘要做摘要，从而同时控制体积和错误传播。

**高频关键词：** Source of Truth、Primary Context、动态组装、索引、阶段契约、最小充分上下文。

**易追问：**

- 如何判断 Context 已经“充分”？
- 中间产物如何保存对原文的引用位置？
- Context 压缩后怎样恢复关键细节？

**回答雷区：**

- 把所有 Workspace 内容一次性塞给每个 Agent。
- 让中间摘要完全替代 PRD、Figma 和代码。
- 所有 Stage 使用同一套固定 Context。

### 问题十九：如何判断 Agent 既实现新需求，又没有破坏存量功能？

> **题目：**
>
> Agent 完成 Coding 以后，需要同时回答两个问题：
>
> **第一，当前需求要求的功能有没有真正实现；第二，这次代码修改有没有破坏已有功能。**
>
> 那么：
>
> **你会怎么从 Task Planning、Git Diff、Verify 和 Regression 几个阶段共同控制这个问题？当前 Workflow 已经做到哪一步，哪些能力还没有真正实现？**

**一句话结论：** Planning 和 Git Diff 控制修改边界，Verify 证明新功能正确，Regression 证明受影响存量能力没有被破坏。

**30秒回答：** Coding 前，Task Plan 建立原子需求、预计代码范围和 Test Case 的映射；Coding 后以真实 Git Diff 为准，检查每处修改是否能被需求或真实依赖解释。Verify 按预先确定的 Case 和 Evidence 证明新增功能正确。回归则覆盖 Diff 直接影响的存量能力和核心业务链路。当前主要通过反向或约束 Assertion 做局部回归，还没有完整的存量 Regression Suite，这一点要明确。

**1分钟展开：**

- Planning 定义预计边界，降低需求外修改风险，但不是绝对文件白名单。
- Git Diff 检查真实边界：范围外修改有真实依赖就更新 Task；无法对应需求或依赖的改动要检查甚至回退。
- Verify 回答“该做的功能是否做出来”，通过 Test Case、Assertion、执行、Evidence 和 Conclusion 闭环。
- Regression 回答“原来正确的功能是否被改坏”，应覆盖受影响存量能力和固定核心链路。
- 当前只通过与本需求相关的反向约束覆盖部分风险；未来要结合依赖分析沉淀存量 Case 库并自动选择回归范围。

**高频关键词：** 预计边界、真实 Git Diff、需求追踪、Browser Verify、Regression Suite、反向断言。

**易追问：**

- 如何从 Diff 自动识别受影响的存量功能？
- 公共组件修改的回归范围怎么确定？
- 什么时候应该回退范围外修改？

**回答雷区：**

- 只验证新增功能，不讨论存量回归。
- 把 Task Plan 当作真实修改结果，不检查 Git Diff。
- 把尚未建立的完整回归测试库说成当前已落地。

### 问题二十：如何设计让 Agent 稳定执行的 Skill？

> **题目：**
>
> 在业务需求交付和 AI Coding Workflow 建设过程中，会沉淀大量 Skill。
>
> 那么：
>
> **Skill 主要依赖自然语言描述，本质上属于软约束。Agent 在执行长任务时可能遗漏规范、跳过检查步骤，甚至在任务没有真正完成时提前结束。你认为设计一个能够让 Agent 稳定执行的 Skill，最大的难题是什么？你是怎么提高 Skill 执行稳定性的？**

**一句话结论：** 稳定 Skill 的关键不是继续加长 Prompt，而是用 Gate 定义完成条件、把确定性规则下沉到结构和脚本，并对长任务增量持久化。

**30秒回答：** 最大难题是 Skill 的主体仍是自然语言，Agent 可能在长任务中漏规范、跳检查或提前结束。我会先建立结构化验收合同，执行中逐项更新 Assertion、Observed Result、Evidence 和 Status；把字段、格式、文件存在性等确定性规则交给模板和 Validation Script；结束前由 Gate 返回具体失败项。当前这能显著降低漏执行，但如果脚本是否运行仍由 Agent 决定，就还是软约束，真正的硬约束需要接入 Hook 或 Workflow Runtime。

**1分钟展开：**

- 先承认根因：自然语言只能告诉 Agent 应该怎么做，不能保证每一步一定执行。
- 第一层是 Gate：完成不能由 Agent 主观宣布，失败时要返回验收项、缺失信息和原因。
- 第二层是确定性下沉：必填字段、格式、Evidence 文件和未完成状态由结构化字段、模板和脚本检查；语义判断仍交给模型。
- 第三层是增量持久化：任务开始初始化验收合同，每完成一项立即写入，避免上下文压缩或中断后丢状态。
- 当前 Skill + Script 仍可能被跳过；产品化后由 Hook 或 Runtime 自动触发 Gate，未通过就不能进入下一 Stage。
- 实践中，拜访 Skill 加入验收合同、模板和 Validation Script 后，输出格式稳定性明显提升。

**高频关键词：** 软约束、验收合同、Gate、Validation Script、增量持久化、Hook、Workflow Runtime。

**易追问：**

- 哪些规则适合脚本，哪些必须由模型判断？
- Gate 如何支持局部修复而不是整条任务重跑？
- Skill 的稳定性应该如何做 Eval？

**回答雷区：**

- 认为 Prompt 写得足够详细就能保证稳定执行。
- Gate 只返回 PASS / FAIL，无法指导补救。
- 把 Skill 内“记得执行脚本”说成系统级硬约束。

### 问题六：为什么把字段权限编码进原字段值，而不是新增独立权限字段？

>
> **你们当时为什么要这样设计？这个方案主要是在解决什么实际工程问题？**

**一句话结论：** “特殊前缀 + 权限标识”主要用于缩小存量改造范围，并让业务值和权限信息在多层组件链路中始终一起传递。

**30秒回答：** 敏感字段已经经过接口类型、Store、列表 Column、`renderValue` 和业务组件等多层链路。如果新增独立 `hasPermission` 或 `front_key`，前后端结构和每层传参都要调整，任一层漏传都会让底层组件失去权限上下文。把权限标识编码在原字段值中，可以复用原链路，由公共解析方法统一处理，减少改造和回归风险。但它是协议取舍，不代表这种编码在所有系统中都最优。

**1分钟展开：**

- 第二层考虑是信息绑定：敏感值经过多层组件传递，值和权限标识拆开后容易漏传、错传或不同步。
- 当前方案由后端返回脱敏特殊值，前端公共方法解析字段标识和权限状态，业务页面尽量维持原用法。
- 代价是协议可读性下降并形成前后端约定，因此必须集中解析、做好类型和异常兜底，不能让业务页面各自判断前缀。

**高频关键词：** 特殊前缀、最小改造、信息绑定、多层传参、统一解析、协议约定。

**1分钟展开：**

### 问题八：权限确认后为什么局部刷新，而不是统一整页刷新？

> **题目：**
>
> 在头达数据分级管控里，用户完成“待确认查看”以后，需要重新获取真实业务数据。
>
> 最简单的方式其实是直接执行：
>
> ```js
> window.location.reload()
> ```
>
> 但实际实现中，列表页和详情页采用了不同的局部刷新方式：列表页重新请求当前列表，详情页重新挂载当前 Tab，并尽量保留用户当前的页面状态。
>
> **为什么当时没有统一使用整页刷新？你是怎么考虑“数据重新获取”和“用户当前页面状态保持”之间关系的？**

**一句话结论：** 权限变化只影响局部业务数据，公共层应统一发出刷新通知，具体刷新和页面状态保持由列表、详情等页面自行决定。

**30秒回答：** `window.location.reload()` 简单但范围过大，会重新请求无关数据，还可能丢失筛选、分页、排序、Tab 和滚动位置。列表页可以复用 `getList(false)` 按当前查询条件重取数据；详情页通过更新当前 Tab 的 React `key` 重新挂载并恢复状态。因为两种页面结构不同，公共权限组件只负责通知“权限已变化”，页面注册自己的刷新 Handler，整页刷新只做兜底。

**1分钟展开：**

- 先说明目标：确认查看成功后要重新获取真实敏感数据，不是重新初始化整个应用。
- 整页刷新会扩大请求范围并破坏运营平台已经建立的查询和浏览状态。
- 列表复用现有请求入口，保留筛选、排序和页码；详情只重挂当前 Tab，并考虑滚动位置恢复。
- 公共层不知道页面内部 Store 和 Tab 结构，因此只提供统一通知入口，由页面注册刷新方法。
- 当前列表与详情是独立窗口；若以后改为共享 Runtime 的 SPA，需要管理 Handler 注册、卸载和多页面隔离。

**高频关键词：** 局部刷新、状态保持、getList、React key、刷新 Handler、整页兜底。

**易追问：**

- 用 React `key` 重挂载有什么副作用？
- 多个页面共享 Runtime 时 Handler 如何隔离？
- 局部刷新失败后如何兜底？

**回答雷区：**

- 只说“局部刷新体验更好”。
- 让公共权限组件直接依赖列表 Store 或详情 Tab。
- 忽略刷新 Handler 的生命周期和覆盖问题。

### 问题九：为什么前端依赖稳定 `front_key`，把权限 code 映射放到 TCC？

>
> 你们通过 TCC 的 `indicator_auth_config` 来维护 `front_key` 和具体权限 code 之间的映射关系。
>
> **为什么当时要通过 TCC 配置来维护这层映射？什么情况下只需要改配置，什么情况下才真正需要修改前端业务代码？**

**一句话结论：** `front_key` 是稳定业务标识，易变化的 `auth_code`、`permission_code` 应收敛到配置；只有管控对象或交互语义变化时才改前端代码。

**30秒回答：** 页面和前后端协议使用稳定的 `front_key`，申请数据权限或查询模块权限时再通过 TCC 的 `indicator_auth_config` 映射到平台 code。这样平台 code 调整只改配置，不需要重新修改和发布业务代码。真正需要前端改动的，是新增敏感字段或指标，或者出现现有公共状态机无法表达的新权限状态和操作流程；如果新等级最终仍落到已有无权限状态，则未必需要改组件。

**1分钟展开：**

- 先区分稳定标识和易变配置：业务字段标识应长期稳定，平台权限 code 可能随配置调整。
- TCC 维护 `front_key → auth_code / permission_code`，把 code 变化从业务发布流程中解耦。
- 仅 code 值变化时改配置；新增管控数据时要把字段接入解析、展示和权限操作链路。
- 新权限等级如果引入新的页面状态、审批或确认方式，需要扩展公共状态和组件；语义未变则复用现有状态。

- 配置与前端版本不兼容怎么办？

**回答雷区：**

- 认为所有权限变化都可以只改配置。
- 不区分 code 数值变化与业务状态变化。
- 忽略配置校验、缓存和异常兜底。

### 问题十：TCC 或权限接口异常时，为什么默认不放行？

> **题目：**
>
> 在头达数据分级管控里，前端需要依赖 TCC 配置和 `employee_permission` 等权限接口判断当前状态。
>
> 实际实现中还考虑了异常情况，例如：
>
> - 根据 `front_key` 没找到 TCC 配置；
> - TCC 配置请求失败；
> - 权限接口请求异常。
>
> **为什么这些异常情况下要优先按照“无权限”处理，而不是为了保证页面可用性先展示数据？你们又是怎么避免因为配置刚更新、缓存没刷新而把正常用户误判成无权限的？**

**一句话结论：** 敏感权限判断必须 fail closed：未明确授权时不展示真实数据，同时通过刷新配置和重试降低正常用户被误判的概率。

**30秒回答：** 配置或权限接口异常时，如果默认放行，就会把系统故障变成敏感数据泄露。字段级安全底线由后端脱敏保证，前端即使解析异常也拿不到无权限用户真实值；模块级在权限结果不明确时保持关闭，不挂载敏感内容。但 fail closed 不等于永久判无权限，`front_key` 第一次查不到时会强制刷新一次 TCC，排除缓存未更新，再根据最终结果处理。

**1分钟展开：**

- 原则是权限状态未明确通过前不能展示真实敏感数据，安全优先于异常时的可用性。
- 字段级由后端返回真实值或脱敏特殊值，真实数据是否下发不依赖前端展示判断。
- 模块级依赖权限接口，异常时不能进入 `viewable`，也不应提前请求或挂载敏感内容。
- 为减少误判，首次配置缺失时刷新 TCC 缓存并重查；仍失败才保持关闭，同时记录可观测错误。
- 还要区分 `loading`、明确无权限和系统异常，不能把所有关闭状态都展示成同一种业务原因。

**高频关键词：** fail closed、后端脱敏、模块关闭、TCC 缓存刷新、安全兜底、异常可观测。

**易追问：**

**回答雷区：**

- 为保证页面可用性在异常时默认展示敏感数据。
- 把安全性完全归功于前端遮罩。
- 一查不到配置就永久判无权限，不做缓存刷新和错误区分。

### 问题十一：为什么用 `ResizeObserver` 让无权限组件按容器尺寸自适应？

> **题目：**
>
> 模块级无权限组件 `SensitiveNoPermission` 会被复用在不同大小的业务区域里：有的模块空间比较大，可以展示插图、提示文案和按钮；有的卡片或图表区域高度很小，只能展示紧凑版提示。
>
> 实际实现中，组件会根据自身容器尺寸调整展示：
>
> - 高度较小时切换成紧凑布局；
> - 空间足够时展示正常按钮；
> - 宽高都达到一定条件后再展示插图。
>
> **为什么这里选择使用 `ResizeObserver` 监听组件所在容器，而不是简单监听 `window.resize`，或者只通过页面宽度做响应式判断？**

**一句话结论：** 公共组件真正可用的空间由自身容器决定，`ResizeObserver` 能感知窗口不变时的内部布局变化，比监听 `window.resize` 更符合组件级响应式需求。

**30秒回答：** `SensitiveNoPermission` 会放在完整模块、卡片和图表遮罩等不同区域，同一窗口下容器高度也可能差很多。组件根据容器宽高切换紧凑文案、正常按钮和插图，例如高度小于 80px 用紧凑版，宽度至少 350px 且高度至少 200px 才展示插图。Tab 切换、父布局和内容变化都可能改变容器而不触发窗口 resize，因此直接观察容器更可靠。

**1分钟展开：**

- 先说明复用场景：同一权限组件可能处在大模块，也可能处在很小的卡片或图表区域。
- 展示策略按真实空间分级：小高度保留核心提示和文字入口，空间增加后显示按钮，再满足宽高条件才显示插图。
- `window.resize` 只能反映视口变化，无法覆盖 Tab、父容器、折叠展开和内部比例调整。
- `ResizeObserver` 直接监听组件容器，使布局决策与真实可用空间绑定，页面无需分别实现无权限样式。

**高频关键词：** SensitiveNoPermission、ResizeObserver、容器查询、紧凑布局、组件复用、window.resize。

**易追问：**

- 如何避免 ResizeObserver 高频回调或循环警告？
- 阈值 80、350、200 如何确定？
- 是否可以用 CSS Container Queries 替代？

**回答雷区：**

- 只回答“为了响应式”。
- 把窗口大小等同于组件容器大小。
- 忽略监听清理和布局抖动问题。

### 问题十二：为什么数据权限申请公共化，而协作人申请继续复用页面存量实现？

> **题目：**
>
> 在头达数据分级管控里，三类权限操作依赖的存量能力并不一样：
>
> - 数据权限申请依赖宿主平台提供的统一权限申请弹窗；
> - 协作人申请复用作者列表、作者详情页原本各自已有的申请弹窗；
> - 公共权限组件在识别到“缺少协作人”时，只通过 `onApply` 通知当前页面打开自己的弹窗。
>
> **既然已经在做公共权限能力，为什么不把“协作人申请”也像“数据权限申请”一样彻底封装成一个全局公共方法？当时是怎么判断哪些能力应该收进公共层，哪些能力应该继续留在页面里的？**

**一句话结论：** 数据权限申请依赖统一宿主能力，适合全局收口；协作人申请强依赖页面既有弹窗和状态，只统一触发入口更符合最小改造原则。

**30秒回答：** 数据权限申请只需根据权限标识调用宿主的 `GarfishBridge` 打开统一弹窗，与具体页面状态关系很弱，所以可以封装成公共方法。协作人申请在列表和详情中已经各自有弹窗、状态和提交链路，如果为这次需求强行重构成全局能力，范围大且容易破坏存量功能。因此公共组件在无协作人状态下只调用页面传入的 `onApply`，统一“何时触发”，不统一“页面内部怎么实现”。

**1分钟展开：**

- 先比较依赖：数据权限申请由宿主平台统一提供，输入稳定，页面只需传权限 code。
- 协作人申请已有列表和详情两套存量实现，依赖各自弹窗、状态和提交逻辑。
- 当前方案选择最小改造：公共层识别状态并触发 `onApply`，页面负责具体申请流程。
- 抽象原则是通用稳定且不依赖页面状态的能力进入公共层；强依赖存量页面实现的能力保留在页面。
- 如果未来协作人申请本身完成统一，再重新收口会比当前提前重构更合理。

**高频关键词：** GarfishBridge、onApply、宿主能力、存量复用、最小改造、统一触发入口。

**易追问：**

- 页面忘记传 `onApply` 时如何处理？
- 数据权限申请为何不也使用页面回调？
- 未来统一协作人申请需要什么前提？

**回答雷区：**

- 认为公共能力抽得越多越好。
- 忽略列表和详情已有弹窗及状态管理。
- 把统一触发入口误说成已经统一了整个申请实现。

### 问题十三：为什么把多接口、多字段的权限 Mock 沉淀成 Skill，而不是固定脚本？

> **题目：**
>
> 在头达数据分级管控的联调过程中，同一种权限状态往往需要同时修改多个接口中的字段级和模块级返回。人工 Mock 时，需要逐个找到接口响应、修改对应字段，再检查是否遗漏；每次切换状态都要重新处理。
>
> 因此，最终将这套重复操作沉淀成了权限 Mock Skill。
>
> **为什么这里选择沉淀成 Skill，而不是只写一个普通脚本？你认为这种能力沉淀在 AI / Agent 研发过程中有什么价值？**

**一句话结论：** Script 负责确定性执行，Skill 进一步封装权限状态、接口范围和使用规则，让 AI 能从自然语言目标完成整套 Mock 切换。

**30秒回答：** 权限联调一次状态切换要同时修改多个接口、字段级和模块级返回，人工重复操作容易漏。底层脚本适合做确定性的文件修改，但只提供脚本，开发者仍要判断目标状态、涉及接口和改写规则。Skill 把这些任务知识一起沉淀下来，用户只说“切到无数据权限”，AI 就能选择规则、调用脚本、统一修改并提示刷新验证。因此 Skill 不是替代 Script，而是把 Script 变成 Agent 可直接复用的任务能力。

**1分钟展开：**

- 先说明问题：权限状态多、接口多，字段级和模块级还要保持一致，人工切换重复且容易遗漏。
- Script 适合稳定的数据转换和文件修改，但不知道何时使用、目标状态是什么、哪些接口需要一起处理。
- Skill 增加任务语义：支持的权限状态、各状态规则、接口和字段清单、执行顺序及验证方式。
- 使用时由自然语言目标触发，AI 读取 Skill，再调用底层脚本完成确定性修改。
- 更大的价值是把研发中稳定、重复的操作持续沉淀为 Skill、Tool、CLI 或 SDK，供后续 Agent 组合复用。

**高频关键词：** Mock Skill、Script、任务语义、自然语言调用、权限状态一致性、能力沉淀。

**易追问：**

- 哪些逻辑放 Skill，哪些放脚本？
- 新增接口后如何保证 Skill 不漏更新？
- 怎样验证一次状态切换真的完整？

**回答雷区：**

- 把 Skill 和 Script 说成互相替代。
- 只讲“自然语言更方便”，不讲规则和上下文封装。
- 把一次性业务操作包装成 Skill，却没有复用边界。

### 问题十五：为什么增量覆盖率达到 90% 仍不能代表测试完成？

> **题目：**
>
> 在头达数据分级管控的交付阶段，前端增量覆盖率 Skill 会先获取变更文件覆盖率，再定位具体未覆盖代码，并通过页面操作去触发对应分支。
>
> 既然最终设置了 90% 的覆盖率目标，**为什么不能单纯把覆盖率刷到 90% 就认为测试完成？为什么还必须结合需求验收项来判断是否需要继续测试？你认为代码覆盖率能够证明什么，又不能证明什么？**

**一句话结论：** 覆盖率证明新增代码被执行过，Test Case 和浏览器验收才证明需求行为正确；90% 是辅助目标，不是交付结论。

**30秒回答：** 增量覆盖率能定位无协作人、无数据权限、待确认查看等新增分支是否真正跑到，未覆盖代码可能意味着漏测、实现路径有问题或冗余逻辑。但一行代码执行过，不代表页面展示、访问记录、权限更新、数据刷新和存量功能都正确。因此 Skill 要把未覆盖代码映射回业务场景，通过页面操作和 Test Case 验证。即使达到 90%，核心验收项未完成也不能结束；剩余代码无业务价值时也不应为了数字机械刷覆盖。

**1分钟展开：**

- 覆盖率先回答“新增代码和分支是否执行”，用于发现测试缺口和可疑死路径。
- 对未覆盖分支要判断是缺少业务场景、实现不可达，还是当前需求不需要的冗余代码。
- 功能验收回答“需求是否做对”，还要检查页面结果、访问日志、权限变化、重新请求和回归。
- Skill 不以执行某行代码为最终目标，而是根据代码位置找到对应业务 Test Case 并真实操作页面。
- 90% 只是阈值信号；核心 Case 未闭环就继续测，无关生成或防御代码也不为数字强行触发。

**高频关键词：** 增量覆盖率、分支覆盖、业务验收、Test Case、未覆盖代码、90% 阈值。

**易追问：**

- 低于 90% 是否一定不能交付？
- 如何识别无法触发的冗余代码？
- 覆盖率数据怎样映射到浏览器操作？

**回答雷区：**

- 把覆盖率等同于功能正确率。
- 为达到数字执行无意义路径或编造场景。
- 只看总覆盖率，不定位新增分支和业务验收项。

### 问题十六：已有数据权限后为什么仍需要“小眼睛”和访问审计？

> **题目：**
>
> 在头达数据分级管控中，用户即使已经拥有对应的数据权限，也不一定会直接看到真实数据。
>
> 如果七天内没有确认查看，页面仍然会默认隐藏敏感数据，并通过“小眼睛”让用户主动确认查看；确认以后再记录访问行为并展示真实数据。
>
> **既然已经有数据权限，为什么还需要增加确认查看和小眼睛？这层能力具体解决什么安全问题？为什么不能只做权限控制？**

**一句话结论：** 权限控制解决“谁有资格看”，确认查看和审计解决“谁实际看过什么”，从而支持事后追溯和异常访问监控。

**30秒回答：** 有权限不代表每次访问行为都无需记录。“小眼睛”不是再次做授权，而是让用户明确触发一次敏感数据查看，并记录谁、何时、查看了哪个作者。发生泄露时，可以从实际访问者而不是所有有权限者中排查；平时还可以统计短时间内查看作者数量和频率，对合法权限下的异常集中访问预警。

**1分钟展开：**

- 数据权限先判断访问资格，解决无权限用户不能查看的问题。
- 小眼睛把一次查看变成明确的用户确认事件，并在确认后记录实际访问。
- 审计记录包含访问者、时间和对象，敏感数据泄露后能够缩小追溯范围。
- 单次请求都合法不代表行为正常；聚合访问次数、对象数量和时间窗口后，可以识别异常集中查看。
- 因此完整链路是授权、确认查看、访问记录、事后追溯与异常监控，各自职责不同。

**高频关键词：** 小眼睛、访问确认、访问审计、事后追溯、异常访问、最小暴露。

**易追问：**

- 为什么确认有效期是七天？
- 审计记录需要保存哪些字段、保存多久？
- 如何避免“小眼睛”给用户带来过多操作成本？

**回答雷区：**

- 把小眼睛说成重复的权限校验。
- 只讲留日志，不讲追溯和异常行为分析。
- 认为有合法权限的所有访问天然安全。

### 问题十七：为什么查询保持真实，而写操作使用网络层 Mock？

> **题目：**
>
> 在头达数据分级管控的前端增量覆盖率 Skill 中，查询接口保持真实请求；涉及数据写入时，则在浏览器网络层返回 Mock 响应，避免产生真实业务数据。
>
> **为什么要这样区分？既然都是为了触发页面代码分支，为什么不把所有接口都 Mock 掉，或者全部直接请求真实环境？你是怎么权衡测试真实性和测试安全性的？**

**一句话结论：** 查询链路尽量真实以保留业务状态和联动，写请求在网络边界隔离以避免副作用，从而兼顾真实性、安全性和可重复执行。

**30秒回答：** 增量覆盖率不是单纯让代码跑一次，而是让 AI 在真实页面和真实业务状态中进入对应分支，所以查询接口尽量保持真实。如果所有查询都 Mock，页面只是在人工构造数据链路中运行。写操作会创建记录、修改状态或写数据库，自动化反复执行会污染环境。因此保留真实页面操作和前端请求触发，但在浏览器网络层拦截写请求并返回 Mock Response。

**1分钟展开：**

- 查询保持真实，能够保留真实数据结构、权限状态、接口联动和页面表现。
- 把所有接口 Mock 会降低测试与用户实际使用环境的一致性。
- 写操作具有业务副作用，自动化反复执行可能制造测试数据、改变状态并干扰他人。
- 解决方式是页面点击和前端逻辑真实执行，在请求离开浏览器前拦截写操作并返回可控响应。
- 总原则是“能安全真实执行的尽量真实，有副作用的链路在边界处隔离”。

**高频关键词：** 真实查询、写操作、副作用、网络层 Mock、环境隔离、可重复执行。

**易追问：**

- 如何区分查询和实际有副作用的接口？
- Mock Response 与真实返回不一致怎么办？
- 哪些写操作应该在专用测试环境真实执行？

**回答雷区：**

- 为方便把所有接口都 Mock，忽略测试真实性。
- 让自动化直接反复写真实业务环境。
- 只拦请求却不验证前端是否真的发起了正确写操作。

### 问题十九：权限接口未返回时为什么需要独立 `loading` 状态？

> **题目：**
>
> 在头达数据分级管控中，模块级权限需要通过权限接口获取状态。
>
> 当权限接口还没有返回时，前端不会直接把用户当成“无数据权限”“非协作人”或者“待确认查看”，而是先进入一个独立的 `loading` 状态。
>
> **为什么这里要单独设计 `loading`？既然权限结果未知时本来就不能展示真实数据，为什么不能直接默认成某一种无权限状态？这个中间态具体解决了什么问题？**

**一句话结论：** `loading` 表示“权限未知”，必须同时阻止真实数据展示和具体权限操作，直到接口返回后才能映射为确定业务状态。

**30秒回答：** 权限请求中只能确定当前不能展示敏感数据，不能确定用户是无协作人、无数据权限、待确认查看还是可查看。如果提前默认成某一种无权限状态，就会展示错误操作，例如用户其实有权限却先看到“申请数据权限”，甚至产生重复申请。`loading` 期间只显示 Loading 或 Skeleton，不挂载敏感内容，也不开放申请和确认入口；结果返回后再根据 `hasPermission`、`needEyes`、`isCoo` 进入真实状态。

**1分钟展开：**

- 先区分未知与无权限：接口未返回是信息不足，不是已经得到某个否定结论。
- 最终可能是 `viewable`、`view_permission_required`、`no_data_permission` 或 `no_cooperation`，对应完全不同的展示和操作。
- 提前映射会让用户误入申请协作人、申请数据权限或确认查看链路。
- `loading` 阶段不展示真实数据、不做具体业务判断、不给权限操作，只表达“仍在获取权限”。
- 结果返回后再进入确定状态；异常则进入单独的安全关闭和错误处理，而不是永久停留在 loading。

**高频关键词：** loading、权限未知、状态机、Skeleton、操作门禁、hasPermission / needEyes / isCoo。

**易追问：**

- loading、error 和 no_permission 如何区分？
- 如何防止 Loading 闪烁？
- 请求超时后页面应该展示什么？

**回答雷区：**

- 把 loading 直接当成无权限。
- 只隐藏数据，却提前展示具体申请入口。
- 权限异常后无限 loading，没有错误状态和重试机制。

### 问题二十：为什么把多页面共用的权限判断和操作提取到公共层？

> **题目：**
>
> 头达数据分级管控涉及多个页面，而无协作人、无数据权限、待确认查看等权限状态，会在不同页面中反复出现。
>
> 如果每个页面都自己判断权限状态、自己决定展示内容、自己处理申请或确认查看链路，也能完成需求。
>
> **为什么还要把这些通用的权限判断、状态映射和后续操作提取到公共层统一管理？这种公共层设计具体解决了什么问题？它对后续维护和扩展有什么价值？**

**一句话结论：** 公共层的核心价值是统一跨页面的权限语义和操作规则，避免各页面判断不一致，并把后续规则变化收敛为一次修改。

**30秒回答：** 无协作人、无数据权限、待确认查看会在多个页面重复出现。如果每个页面各自解析、展示和触发操作，容易漏分支或产生不同规则。公共层统一状态解析、映射、提示和操作触发，页面只提供业务数据与少量特有回调。以后规则或文案变化只改公共层即可。边界上，协作人弹窗等强依赖页面存量状态的实现仍留在页面，公共层只通过 `onApply` 统一触发时机。

**1分钟展开：**

- 多页面都要完成状态识别、提示展示和申请或确认操作，规则散落会产生重复和不一致。
- 公共方法统一解析权限状态，公共组件统一状态映射、文案和基础操作入口。
- 页面消费同一套规则，降低漏掉权限分支和跨页面表现不一致的风险。
- 后续规则、文案或操作链变化集中修改，减少逐页查找、修改和回归成本。
- 公共层只收稳定通用语义；协作人弹窗、图表表现等页面依赖逻辑通过回调或页面实现保留边界。

**高频关键词：** 权限公共层、状态映射、跨页面一致性、统一操作、onApply、维护成本。

**易追问：**

- 公共层修改后如何保证所有页面兼容？
- 公共组件与权限状态机如何测试？
- 哪些页面差异应该通过配置，哪些通过回调？

**回答雷区：**

- 只强调减少重复代码，不讲规则一致性。
- 把页面所有弹窗、状态和特殊展示都收进公共层。
- 认为改公共层后不需要做跨页面回归。

### 问题二：如何理解作者运营和内容运营，两者为什么都由团队重点支撑？

> **题目：**
>
> 当前团队围绕运营平台建设，重点支撑**作者运营和内容运营**。
>
> 请分别说明作者运营和内容运营各自在解决什么业务问题、核心业务链路是什么，以及两者之间是什么关系。并结合一个具体场景说明：如果一个达人保持正常开播和投稿，但是优质内容占比较低、内容转化效果也不好，作者运营和内容运营分别应该发挥什么作用？

**一句话结论：** 作者运营解决“达人应该怎样经营”，内容运营解决“达人怎样生产更好的内容”，两者分别提升经营能力和内容能力，最终共同服务达人成长、生态健康和交易结果。

**30秒回答：** 作者运营围绕达人经营，链路是数据分析、问题诊断、制定策略、触达和持续跟进；头部和高潜达人偏精细化运营，中腰部和长尾达人偏规模化运营。内容运营围绕内容生态，通过定标准、做激励、抓治理和帮诊断增加优质内容。比如达人正常开播投稿但优质内容占比低，作者运营先判断整体问题是否在内容，确认后由内容运营进一步定位表达、商品呈现或内容结构问题并给出改进方法。

**1分钟展开：**

- 作者运营先看经营数据，完成“分析—诊断—策略—触达—跟进”，目标是改善经营状态并推动等级跃迁。
- 根据达人价值分层：KA、高潜达人适合一对一精细化运营；中腰部和长尾达人通过人群、任务、BPO、RPA 扩大覆盖。
- 内容运营按照“定标准—做激励—抓治理—帮诊断”提升优质内容供给、分发和转化。
- 两者的衔接是先由作者运营判断达人整体问题，再由内容运营解决其中与内容质量和创作有关的具体问题。

**高频关键词：** 作者运营、内容运营、精细化运营、规模化运营、内容标准、经营诊断、等级跃迁。

**易追问：**

- 如何判断达人问题来自内容而不是选品或流量？
- 两类运营分别看哪些指标？

**回答雷区：**

- 把作者运营简化成发消息，把内容运营简化成审核内容。

### 问题三：运营平台在联盟业务中扮演什么角色，未来如何向 Agent 辅助运营演进？

> **题目：**
>
> 整个联盟有达人、商家、撮合、内容、基建与生态、运营平台六个业务方向。
>

> 5. 未来引入 Agent 之后，你认为运营平台的角色会发生什么变化？

**一句话结论：** 运营平台负责把运营方法变成可线上执行、可复用、可规模化的系统能力；Agent 会在平台已有数据和执行能力上补充复杂分析与个性化判断。

**30秒回答：** 作者、内容等方向定义要解决的业务问题，运营平台负责让这些方法真正在线上执行。作者运营可以在平台完成达人筛选、诊断、任务、触达和跟进；内容运营可以完成活动、筛选、评选、分发、发奖和复盘。平台价值应看线上化率、使用率、触达率、数据覆盖和单运营服务规模，再看达人跃迁、优质内容和交易结果。未来不是 Agent 取代平台，而是平台负责稳定执行，Agent 辅助复杂分析和个性化建议。

**1分钟展开：**

- 核心定位：把作者运营、内容运营等工作从人工和线下工具迁移为线上化、标准化、规模化流程。
- 独立存在的原因：它解决的不是单个达人或单条内容，而是大量运营工作如何稳定执行和持续复用。

- 价值指标先看平台效率，再看作者成长、优质内容和交易结果；Agent 则在原有能力上补充人群内部的个体判断。

**高频关键词：** 线上化、标准化、规模化、运营闭环、平台指标、稳定执行、Agent 判断。

**易追问：**

**回答雷区：**

- 只讲内部提效，不说明对达人和内容业务的最终影响。

### 问题四：如何理解作者运营指标？覆盖提升但达人没有成长时怎样定位？

> **题目：**
>
> 作者运营的目标不是单纯“触达更多达人”，而是帮助达人改善经营状态、提升交易表现，并最终实现成长和等级跃迁。
>
> 假设现在出现这样一种情况：
>
> > **有效运营作者数和触达率都明显提升了，但是一个月以后，达人等级跃迁率、活跃度和交易表现并没有明显改善。**
>
> 请说明作者运营最核心的指标应该怎么看、各个指标之间是什么关系，以及为什么“覆盖提高”不一定代表运营真正有效。

**一句话结论：** 作者运营要沿“有效覆盖—实际行动—经营改善—等级跃迁—规模与留存”看完整链路；覆盖变高只是前置条件，不能直接等同于运营有效。

**30秒回答：** 我会同时看作者规模、成长、有效运营覆盖和活跃留存。出现触达率和有效运营作者数上升但跃迁、活跃、交易没有改善时，先检查互动是否转成实际行动，再看行动后经营指标是否改善；如果行动无效，可能是问题诊断或策略本身不对；如果经营已改善但等级没变化，还要考虑统计周期和成长滞后。

**1分钟展开：**

- 作者规模看优质、高质量作者数，反映长期供给结果。
- 作者成长看等级跃迁人数和跃迁率，判断运营是否真正改善经营状态。
- 有效覆盖不能只看消息发送，要看回复、任务领取和实际交互；活跃留存看月活、留存和流失召回。
- 结果不增长时按链路拆解：覆盖是否真实、建议是否采纳、是否产生行动、策略是否有效、结果是否存在时间滞后。

**高频关键词：** 有效运营、作者行动、经营改善、等级跃迁、优质作者、留存、指标链路。

**易追问：**

- 什么样的互动才算有效运营？
- 如何区分策略无效和结果滞后？
- 作者规模和等级跃迁哪个更重要？

**回答雷区：**

- 把消息发送量当成有效覆盖。
- 看到跃迁没增长就直接判断运营策略无效。
- 罗列指标但说不清各指标对应运营链路的哪一段。

### 问题五：为什么现有规模化运营还需要引入运营 Agent？

> **题目：**
>
> 当前规模化运营已经具备人群圈选、任务下发、BPO、RPA 批量触达等能力，理论上已经可以用有限的人力覆盖大量达人。
>
> 那么为什么团队还要继续建设运营 Agent？
>
> 请从现有规模化运营模式的业务瓶颈出发说明：
>
> 1. 传统规模化运营已经解决了什么问题？
> 2. 还有哪些问题没有解决？
> 3. 运营 Agent 相比现有 BPO、RPA 和规则化运营，真正新增的业务价值是什么？
> 4. 为什么运营 Agent 还需要承担运营经验沉淀和复用的作用？
>
> 可以结合“最近 7 天没有开播”的达人场景说明：同样属于一类人群，但不同达人背后的真实原因可能并不一样。

**一句话结论：** 传统规模化运营解决“覆盖更多达人”，运营 Agent 要进一步解决“在大规模覆盖下逐个诊断并给出个性化策略”，同时把有效运营经验沉淀下来。

**30秒回答：** 人群圈选、任务、BPO 和 RPA 已经能让有限人力覆盖大量达人，但通常还是对一类人使用同一策略。比如同样七天没开播，有人缺商品，有人意愿低，有人是直播转化差，统一话术很难有效。Agent 的增量不是再做一次批量发送，而是逐个读取经营数据、判断原因、生成不同建议，再调用现有执行能力，并通过回复、行动和经营结果验证策略，沉淀真正有效的方法。

**1分钟展开：**

- 现有模式先按人群特征制定标准策略，再通过任务、BPO、RPA 扩大覆盖，已经解决规模问题。
- 瓶颈是同一标签下的真实原因不同，人工又无法对大规模人群逐个诊断。
- Agent 将流程升级为“批量圈人—个体分析—个性化诊断—个性化建议—批量执行”。
- 触达后回收回复、采纳、行动和经营结果，判断诊断是否有效；验证过的方法再沉淀为知识或 Skill。

**高频关键词：** 规模化运营、批量个性化、达人级诊断、RPA、BPO、反馈闭环、经验沉淀。

**易追问：**

- Agent 与规则化人群策略的分界是什么？
- 如何避免个性化建议不可执行？
- 什么样的运营经验值得沉淀为 Skill？

**回答雷区：**

- 把 Agent 价值说成生成更多消息或更好看的话术。
- 忽略现有人群、任务和触达能力的复用。
- 未经业务结果验证就把模型输出当成优秀经验。

### 问题六：运营 Agent 上线后，怎样证明它比传统规模化运营更有价值？

> **题目：**
>
> 前面已经明确，运营 Agent 希望把传统的“批量统一运营”升级成“批量个性化运营”。
>
> 但从业务角度来看，用了 Agent 本身并不代表产生了价值。
>
> 假设团队已经上线第一版运营 Agent：
>
> > 同样圈选 1 万个目标达人，一部分继续使用传统规则 + RPA/BPO 运营，另一部分使用 Agent 做个性化诊断和建议。
>
> 请说明：
>
> 1. 应该通过哪些指标判断运营 Agent 有没有价值？
> 2. 怎么区分“Agent 生成得很好”和“真正产生业务效果”？
> 3. 为什么一定需要和传统规模化运营建立基线或对照？
> 4. 运营经验沉淀这一部分应该如何评估？

**一句话结论：** 运营 Agent 要沿“效率—采纳—行动—结果—经验复用”评估，并通过实验组和传统运营对照，证明同等成本下结果更好或同等结果下成本更低。

**30秒回答：** 我不会看 Agent 生成了多少建议，而会先看单运营服务人数、有效运营作者数和人工诊断耗时，再看建议采纳率、任务领取和完成率，最后看活跃、跃迁、留存和 GMV。业务结果受活动、人群质量和大盘影响，因此必须与传统规则加 RPA/BPO 建立基线或对照。经验沉淀也不能只看案例或 Skill 数量，而要看同一方法在相似达人上复用时是否仍然有效。

**1分钟展开：**

- 效率与覆盖：同样人力能服务多少达人，诊断和建议生成节省多少人工时间。
- 策略采纳与行动：建议是否被运营或达人接受，并转成任务领取、完成和真实经营动作。
- 作者经营结果：活跃、跃迁、优质作者、留存和 GMV 是否改善，但不能直接把变化都归因给 Agent。
- 建立实验组和对照组，比较相同成本下的结果或相同结果下的成本；经验则看完整记录和跨样本复用稳定性。

**高频关键词：** 运营效率、采纳率、行动率、经营结果、实验对照、成本收益、经验复用。

**易追问：**

- 怎样设计特征相近的实验组和对照组？
- GMV 提升如何排除大盘和活动影响？
- 运营经验复用的稳定性怎样衡量？

**回答雷区：**

- 用生成量、调用量证明 Agent 有价值。
- 只看最终 GMV，不看建议到行动的过程。
- 没有基线就宣称效果全部来自 Agent。

### 问题七：运营 Agent 第一期应该如何选择落地场景？

> **题目：**
>
> 运营 Agent 的方向已经比较明确，但真正落地时不可能一开始就把作者运营全链路都 Agent 化。
>
> 假设现在有几个候选方向：
>
> - 达人经营诊断
> - 个性化运营建议生成
> - 达人触达话术生成
> - 达人回复自动处理
> - 运营经验沉淀
> - 任务自动创建和执行
>
> 如果让你负责第一期建设，你会怎么判断：
>
> 1. 哪个场景应该优先做？
> 2. 你会用什么标准判断一个业务场景适不适合 Agent，而不是继续用规则、RPA 或人工？
> 3. 为什么第一期不能直接追求端到端全自动运营？

**一句话结论：** 第一期应选择业务痛点明确、结果可衡量、规则难以解决且数据执行链路已经具备的场景，从人机协同开始，而不是直接追求端到端自动化。

**30秒回答：** 我会优先做批量个性化诊断和建议，因为它直接对应现有规模化运营个性化不足的问题，而且可以通过有效运营作者数、采纳率、任务完成率和经营结果验证。固定人群、固定话术、批量发送这类确定性任务继续用规则或 RPA。第一期还要确保数据读取、诊断、建议、触达、反馈和结果链路打通，并采用 Agent 生成、运营审核、小范围执行的方式验证。

**1分钟展开：**

- 先看业务价值，不按“哪个功能最容易接模型”选择。
- 再看结果是否可衡量，必须能从 Agent 输出追到采纳、行动和经营结果。
- 判断是否真的需要 Agent：确定性流程继续用规则、Workflow、RPA；多源上下文和难穷举判断才交给 Agent。
- 检查数据与执行链路是否完整；第一期由人工审核和小范围试跑控制风险，稳定后再逐步提高自动化。

**高频关键词：** 场景选择、业务价值、可衡量、Agent 必要性、完整链路、人机协同、小范围试跑。

**易追问：**

- 为什么不先做最容易展示的触达话术生成？
- 哪些指标达到后可以降低人工审核比例？
- 数据链路不完整时能否先做 PoC？

**回答雷区：**

- 按模型能力或演示效果选择首个场景。
- 把所有步骤都交给 Agent，忽略已有确定性能力。
- 第一版未经验证就直接批量触达达人。

### 问题八：运营 Agent 和现有运营平台是什么关系，为什么不能只是聊天机器人？

> **题目：**
>
> 未来团队希望从传统运营工具平台逐步向 Agent 辅助运营演进。
>
> 如果已经有了大模型能力，为什么不能直接给运营做一个 ChatBot：
>
> > 运营把达人 UID 或问题输进去，Agent 给出诊断和建议，运营自己再去其他系统执行。
>
> 请说明：
>
> 1. 一个真正能够落地的运营 Agent，应该和现有运营平台形成什么关系？
> 2. 如果只是“聊天 + 给建议”，它还缺少什么？
> 3. 为什么运营 Agent 需要和现有达人库、人群、任务、RPA/BPO、触达、经营数据等平台能力深度结合？
> 4. 运营 Agent 和普通 ChatBot 的本质区别是什么？

**一句话结论：** ChatBot 停在问答和建议，运营 Agent 必须嵌入“读数据—做判断—调工具—执行—收结果”的业务闭环；平台提供数据和稳定执行，Agent 补充复杂分析。

**30秒回答：** 独立聊天机器人可以查询达人 GMV、开播等信息并给建议，但运营还要切到其他系统执行，也无法知道建议是否被采纳。真正的运营 Agent 要读取达人库和经营数据，结合上下文完成诊断，再调用人群、任务、RPA/BPO 和触达能力执行，并回收达人回复、行动和后续经营结果。它不重新建设运营平台，而是使用平台已有能力，并让运营根据结果持续优化和发布诊断 Skill。

**1分钟展开：**

- ChatBot 解决信息获取，通常在“给出答案或建议”处结束。
- 运营 Agent 参与完整链路：圈人、读数据、诊断、建议、执行、反馈和经营结果。
- 达人库、人群、任务、BPO、RPA 和触达是 Agent 的数据与执行基础，无需由模型重做。
- 平台负责稳定确定性能力，Agent 负责多数据综合判断；结果回流后由运营评测和优化方法，而不是 Agent 无约束自改 Skill。

**高频关键词：** ChatBot、业务闭环、平台能力、Tool/API、复杂判断、反馈回流、Skill 评测。

**易追问：**

- 一个只生成建议的系统能否称为 Agent？
- Agent 调用现有平台能力时如何做权限控制？
- 为什么不允许 Agent 自动修改并上线 Skill？

**回答雷区：**

- 用是否有聊天界面区分 ChatBot 和 Agent。
- 让 Agent 重新实现已有任务、触达和数据系统。
- 只有输出，没有执行和结果反馈闭环。

### 问题九：除了规模化运营，还有哪些业务方向适合接入 Agent？

> **题目：**
>
> 当前运营 Agent 主要服务规模化运营，目标是帮助运营实现批量个性化运营，并沉淀经过验证的优秀运营经验。
>
> 那么从整个运营平台来看：
>
> 1. 除了规模化运营以外，还有哪些业务方向适合进一步接入 Agent 能力？
> 2. `alliance-operation-rd` 在整个运营平台里是什么定位？
> 3. Agent 能力应该怎样和 daren、content、scale、mobile 等现有业务模块结合？
> 4. 未来“运营平台 Agent 化”应该怎么理解？

**一句话结论：** 运营平台 Agent 化不是给每个模块加聊天框，而是由 RD 提供横向 AI 能力，Agent 按业务目标嵌入作者、内容、BPO、撮合和达人经营链路。

**30秒回答：** `alliance-operation-rd` 是研发与 AI 工具的横向支撑应用，不直接承载所有运营业务，也不等于 Agent Runtime。作者运营可用 Agent 做 KA 诊断、拜访前准备和会后待办；内容运营可做内容诊断和优秀案例提炼；BPO 可获得达人背景、沟通建议和结果总结；撮合可综合达人和商品特征；达人 Agent 则直接给达人经营建议。业务模块继续承载真实链路，RD 提供横向能力。

**1分钟展开：**

- 先明确 RD 定位：提供 Agent、AIGC、实验和案例分析等横向能力，不替代 daren、content、scale 等业务 App。
- 作者运营接入诊断、拜访准备和跟进总结，提升精细化运营效率。
- 内容运营接入内容质量诊断和优秀方法提炼；BPO 接入服务前准备、沟通辅助和会后总结。
- 还可探索商达撮合和直接面向达人的经营 Agent；共性原则是嵌入真实业务链，而不是新增孤立聊天入口。

**高频关键词：** RD、横向 AI 能力、作者 Agent、内容诊断、BPO 助手、撮合 Agent、达人 Agent。

**易追问：**

- RD 与业务 App、AIME 分别是什么关系？
- 哪个方向最适合作为规模化运营后的下一场景？
- 横向能力和业务专属 Skill 如何划分？

**回答雷区：**

- 把所有 AI 功能都放进 RD 并让其承载业务链路。
- 把 Agent 化理解成每个页面增加聊天框。
- 只列场景，不说明现有业务能力如何承接执行。

### 问题十：内容运营第一期最值得接入哪个 Agent 场景？

> **题目：**
>
> 当前内容运营已经有比较完整的链路：
>
> > **内容活动 → 视频/直播/图文管理 → 好内容/好作者评选 → 内容分发 → 激励结算 → 数据复盘。**
>
> 如果团队希望下一步把 Agent 能力进一步接入内容运营，但第一期只能选择一个核心场景，请回答：
>
> 1. 你会优先选择哪个内容运营场景接入 Agent？
> 2. 它当前解决的业务问题是什么？
> 3. 为什么这个问题适合 Agent，而不是继续用规则、算法筛选或者人工？
> 4. 最后通过什么指标证明它有价值？

**一句话结论：** 第一阶段优先做内容质量诊断 Agent：规则和算法继续负责确定性筛选，Agent 重点解释内容为什么好或不好、应该怎样改，并用后续内容结果验证价值。

**30秒回答：** 现有视频、直播、图文管理和好内容评选已经能按播放、成交、评级等条件筛选，Agent 再判断一次“是不是优质内容”增量不大。我会让 Agent 综合内容表达、商品卖点、达人历史数据和同赛道案例，定位问题环节并生成优化建议；由运营审核后反馈达人，再观察优质内容率、播放、互动和转化是否改善。

**1分钟展开：**

- 先复用成熟能力：明确阈值和质量评级继续由规则、算法筛选。
- Agent 负责开放诊断，综合内容、商品、达人和经营数据解释“为什么”及“怎么改”。
- 业务闭环是“读取数据—诊断—建议—运营审核—达人调整—回收表现”，第一阶段不自动进入好内容评选。
- 评估看三层：诊断效率、运营或达人采纳与执行、后续内容质量和交易结果。

**高频关键词：** 内容质量诊断、规则筛选、上下文分析、运营审核、建议采纳、内容结果。

**易追问：**

- 为什么不先做优质内容自动评选？
- 内容诊断需要哪些输入数据？
- 如何证明内容改善来自建议而不是自然波动？

**回答雷区：**

- 让 Agent 重复已有规则和算法的筛选工作。
- 只看诊断文案质量，不看达人是否执行和结果是否改善。
- 第一版未经验证就自动决定优质内容和资源分配。

### 问题十一：如何判断现有业务是否适合升级为 Agent，并完成业务和技术设计？

> **题目：**
>
> 假设现在有一个已经稳定运行的传统业务，原有链路主要通过人工、规则、Workflow、RPA 或普通系统能力完成。
>
> 现在希望引入 AI / Agent。
>
> 如果由你负责这个方向，你会如何判断：
>
> > **这个业务到底适不适合升级成 Agent？如果适合，应该从哪些方面完成业务规划和技术落地？**

**一句话结论：** 先判断业务增量价值、问题是否真的需要智能判断、效果是否可衡量和闭环是否具备；适合后再让固定流程控主干、Agent 做复杂节点、Tool/API 复用现有能力。

**30秒回答：** 我不会先问模型能不能做，而会先看业务痛点和增量价值。如果规则明确、输入输出固定，继续用规则、Workflow 或 RPA；只有需要多源数据理解、上下文分析和难穷举的个性化判断才交给 Agent。建设前定义效率、审核通过或采纳、最终业务结果的指标链，再梳理原 SOP，让 Agent 嵌入关键判断节点，通过 Tool/API 调用数据、任务、触达等系统，并对高风险动作保留人工审核和回退。

**1分钟展开：**

- 业务价值：Agent 是降低人工成本，还是新增传统方案难以提供的个性化能力。
- Agent 必要性：确定性执行留给规则和系统，复杂理解、判断和策略生成交给 Agent。
- 可衡量性：提前建立“输出—采纳—行动—结果”指标链，而不是上线后只看调用量。
- 落地设计：先读清现有 SOP，再用固定 Workflow 控主流程、Agent 处理复杂节点、Tool/API 复用成熟能力，并补齐数据、执行、反馈和风险控制。

**高频关键词：** 业务增量、Agent 必要性、可衡量、SOP、Workflow、Tool/API、人机审核、闭环。

**易追问：**

- 规则难以穷举的判断如何识别？
- 外层固定 Workflow 会不会限制 Agent？
- 高风险业务动作怎样逐步提高自动化？

**回答雷区：**

- 因为模型能实现就决定 Agent 化。
- 把所有业务节点都交给 Agent。
- 只做诊断建议，不打通执行和结果反馈。

### 问题十二：Monorepo 新模块应该放在 App、libs、packages 还是 RD？

> **题目：**
>
> 当前运营平台是一个 Monorepo，既有 `daren`、`content`、`scale`、`rd` 等业务应用，也有 `libs` 和 `packages` 两种共享能力。
>
> 如果现在需要新增一个业务模块或者公共能力，你会如何判断：
>
> > **它应该直接放在某个业务 App 中，还是抽到 `libs`、`packages`，或者放到 `rd`？**
>
> 同时，在已有存量代码的情况下，你会如何控制改造范围，避免为了复用而过度设计，或者影响原有业务功能？

**一句话结论：** 先按业务归属最小范围落地，再按真实复用半径逐层上收：单业务放 App，仓库内多业务稳定复用放 `libs`，需要独立构建、版本或跨项目复用放 `packages`；RD 是业务应用而不是公共代码层。

**30秒回答：** `apps` 承载纵向业务，`libs` 做当前 Monorepo 内源码共享，`packages` 提供独立构建、稳定 API 和版本管理，`rd` 则是研发与 AI 工具入口型 App。新增功能先判断属于哪条业务链，第一版优先在原 App 最小改动；真实出现多个业务稳定复用后再抽 `libs`；需要跨项目或独立发布再放 `packages`。不能因为使用 AI 就默认放 RD，运营 Agent 实际可能运行在 AIME。

**1分钟展开：**

- 先识别业务归属和存量链路：达人拜访属于 `daren`，内容诊断属于 `content`，先把单业务功能做对。
- 多个内部业务确实复用同一逻辑时上收到 `libs`，例如统一的敏感权限展示。
- 需要稳定 API、独立构建和版本管理时再沉淀到 `packages`，例如 `operation-request`。
- RD 仍是独立 App，聚合研发和 AI 入口；Agent Runtime 在哪里运行，要看真实平台架构，不能与公共代码目录混淆。

**高频关键词：** Monorepo、App、libs、packages、RD、复用半径、最小改造、AIME。

**易追问：**

- 第二个调用方出现时是否一定要抽 `libs`？
- `libs` 和 `packages` 的发布与依赖方式有什么区别？
- RD 提供 Agent 入口时业务能力应该放在哪里？

**回答雷区：**

- 为未来可能复用提前做大范围公共抽象。
- 把 `libs`、`packages` 和 RD 当成同一种共享层。
- 因为功能与 AI 有关就默认开发或运行在 RD。

### 问题十三：什么是作者运营？

> **题目：**
>
> 什么是作者运营？作者运营主要围绕哪些对象、做哪些事情，最终希望达成什么业务目标？

**一句话结论：** 作者运营围绕联盟达人，通过经营数据分析、问题诊断、运营建议和持续跟进，帮助达人改善经营表现、实现等级跃迁并扩大优质作者规模。

**30秒回答：** 作者运营服务的是通过电商内容帮助商家带货赚佣金的联盟达人。运营先查看开播、投稿、成交、选品等数据，判断问题并给出流量、选品或经营方向建议；建议发出后还要继续观察达人是否行动、数据是否改善。最终不是完成一次触达，而是帮助作者成长、提升经营表现和等级。

**1分钟展开：**

- 运营对象是联盟达人，不是所有平台用户。
- 核心动作是读取经营数据、定位问题并给出有针对性的运营建议。
- 建议之后持续跟进开播、投稿、选品、成交等行动和数据变化。
- 最终用作者成长、等级跃迁和优质作者规模判断运营是否有效。

**高频关键词：** 联盟达人、经营数据、问题诊断、运营建议、持续跟进、等级跃迁。

**易追问：**

- 作者运营与用户运营有什么区别？
- 一条完整作者运营链路包含哪些环节？
- 怎样判断一次触达是否真正有效？

**回答雷区：**

- 把作者运营定义成消息触达或任务下发。
- 建议发出后不追踪行动和结果。
- 只讲 GMV，不讲作者成长和长期经营。

### 问题十四：达人库在作者运营中有什么作用？

> **题目：**
>
> 达人库在作者运营中承担什么作用？为什么它是后续作者诊断和运营策略制定的重要基础？

**一句话结论：** 达人库统一管理达人信息和运营归属，为后续经营诊断、分层策略、责任人跟进和差异化运营提供基础。

**30秒回答：** 达人库不只是资料列表，它集中管理达人基本信息、经营数据、违规处罚、团队和赛道，并明确由哪个团队、哪个运营负责。运营有了这套基础，才能判断达人当前状态和适用的运营方式。比如规模化达人适合通过 BPO、RPA、任务覆盖，KA 达人则需要一对一深度诊断和持续跟进。

**1分钟展开：**

- 统一达人基本信息、经营表现、违规记录、团队和赛道，避免数据分散。
- 建立运营归属关系，明确责任团队和跟进人员。
- 这些信息共同构成诊断基础，决定后续看什么问题、采取什么策略。
- 按达人价值和运营类型承接差异化流程：规模化批量执行，KA 精细化服务。

**高频关键词：** 达人库、信息管理、运营归属、经营诊断、达人分层、差异化运营。

**易追问：**

- 达人库需要沉淀哪些核心数据？
- 运营归属变更如何影响历史跟进记录？
- 达人库和人群圈选能力是什么关系？

**回答雷区：**

- 把达人库说成简单的查询列表。
- 只讲数据展示，不讲责任关系和后续运营执行。
- 所有达人使用同一套诊断和触达方式。

### 问题十五：作者和达人有什么区别？

> **题目：**
>
> 在联盟业务里，“作者”和“达人”分别指什么？为什么作者运营最终重点服务的是联盟达人？

**一句话结论：** 作者是通过电商内容带货的更大范围概念，达人是其中能够帮助其他商家带货赚佣金的非商家型作者；联盟作者运营重点服务后者。

**30秒回答：** 电商作者包括商家型作者和达人型作者。商家型作者主要销售自己授权店铺的商品；达人型作者除了可能卖自己的商品，也能从联盟选品，帮助其他商家带货并赚佣金。联盟平台连接商家与达人，因此我们说的联盟作者或联盟达人，核心就是这类为其他商家带货的达人。

**1分钟展开：**

- 作者是上位概念，只要通过电商内容带货都可以纳入。
- 商家型作者主要服务自己的店铺，达人型作者可以帮助其他商家推广商品并赚佣金。
- 联盟业务中的作者通常指联盟达人，也就是进入商达撮合和佣金结算链路的人群。
- 因此作者运营的核心服务对象不是所有作者，而是联盟达人。

**高频关键词：** 电商作者、商家型作者、达人型作者、联盟达人、商达撮合、佣金。

**易追问：**

- 达人销售自己店铺商品时是否仍属于联盟业务？
- 联盟平台在商家和达人之间提供哪些能力？
- 为什么业务中有时混用作者和达人？

**回答雷区：**

- 认为作者和达人完全是两个互斥群体。
- 忽略“是否帮助其他商家带货赚佣金”这一联盟边界。
- 把所有平台作者都当成联盟作者运营对象。

### 问题十六：作者运营有哪些核心指标？

> **题目：**
>
> 你会从哪些指标判断作者运营做得好不好？这些指标分别反映了什么？

**一句话结论：** 作者运营指标要同时覆盖规模、成长、有效运营和留存，并沿“覆盖—行动—成长—长期结果”判断，而不能只看触达量。

**30秒回答：** 我会看四类指标：优质和高质量作者数反映作者规模；等级跃迁人数和跃迁率反映成长；有效运营作者数和有效运营率反映是否产生真实互动；月活、留存和流失召回反映长期经营。最终要把这些指标串起来，判断运营是否让达人从被覆盖走向行动、成长和持续活跃。

**1分钟展开：**

- 作者规模：优质作者、高质量作者数量，反映长期高质量供给。
- 作者成长：等级跃迁人数和比例，反映运营是否帮助作者改善经营。
- 有效运营：回复、任务领取和后续行动，而不是单向消息发送。
- 活跃留存：月活、留存和召回；最终再观察这些变化是否服务交易增长和生态健康。

**高频关键词：** 优质作者、等级跃迁、有效运营率、作者月活、留存、流失召回。

**易追问：**

- 有效运营作者的口径怎样定义？
- 作者跃迁存在周期时怎样评价短期运营？
- 规模、成长和留存指标冲突时如何取舍？

**回答雷区：**

- 只看触达人数或消息发送量。
- 把一次回复直接等同于经营改善。
- 只列最终指标，不建立过程指标。

### 问题十七：什么是内容运营？

> **题目：**
>
> 你怎么理解内容运营？它主要通过哪些方式提升内容生态质量，最终服务什么业务目标？

**一句话结论：** 内容运营通过定标准、做治理、给激励和做诊断，持续扩大优质内容供给、维护内容生态，并让好内容获得更多分发和交易价值。

**30秒回答：** 内容运营的核心是提升内容生态健康度和优质内容供给。平台先把真实、专业、可信、有趣等主张转成质量标准；对虚假宣传和违规营销做治理；通过流量、权益和活动激励优质内容；再把问题和改进建议反馈给作者。最终不是管理内容数量，而是让更多好内容被看到，并提高内容消费和交易转化。

**1分钟展开：**

- 定标准：把内容主张拆成可判断的质量维度，为评价和资源分配提供依据。
- 做治理：识别低质、违规、虚假宣传和内容商品不匹配，守住生态底线。
- 给激励：用流量、权益、评选和活动奖励扩大优质内容供给。
- 做诊断：告诉作者问题在哪里、怎样改，并用创作工具降低门槛；最终服务分发和交易。

**高频关键词：** 内容标准、生态治理、内容激励、内容诊断、优质内容供给、分发、交易转化。

**易追问：**

- 内容标准怎样避免过于主观？
- 治理和激励如何共同作用？
- AI 可以在哪些内容运营节点发挥作用？

**回答雷区：**

- 把内容运营等同于内容审核。
- 只强调曝光和成交，忽略生态健康。
- 定了标准却没有激励、诊断和结果反馈。

### 问题十八：内容运营有哪些核心指标？

> **题目：**
>
> 内容运营应该看哪些核心指标？这些指标之间是什么关系？

**一句话结论：** 内容运营指标形成“质量—分发—转化”递进链路：先有优质内容，再让好内容被看到，最后衡量它是否产生交易价值。

**30秒回答：** 第一层看优质内容数和优质内容 VV 占比，分别反映供给规模和好内容是否获得更多播放；第二层看内容 Load，判断整体曝光和消费规模；第三层看全域成交价值和 GPM，衡量内容带来的直接、间接成交以及单位播放效率。质量是基础，分发是桥梁，转化是最终结果。

**1分钟展开：**

- 质量层：优质内容数看供给，优质内容 VV 占比看优质内容是否获得有效分发。
- 分发层：内容 Load 反映内容曝光和消费盘子是否扩大。
- 转化层：全域成交价值覆盖直接挂车和搜索、商城等间接成交，GPM 看每千次播放的成交效率。
- 三层要结合分析：质量好但 Load 低是分发问题，分发高但 GPM 低则要继续看内容与商品转化。

**高频关键词：** 优质内容数、VV 占比、内容 Load、全域成交价值、GPM、质量分发转化。

**易追问：**

- 优质内容 VV 占比和内容 Load 有什么区别？
- 为什么要看全域成交而不只看挂车 GMV？
- 高播放低转化时怎样定位问题？

**回答雷区：**

- 把播放量直接等同于内容价值。
- 只看 GMV，不看内容质量和分发过程。
- 罗列指标却说不清三层之间的递进关系。

### 问题十九：什么是规模化运营，为什么还需要运营 Agent？

> **题目：**
>
> 规模化运营解决的是什么问题？既然已经有 BPO、RPA、任务等批量能力，为什么还需要运营 Agent？

**一句话结论：** 规模化运营用标准化人群策略和批量执行扩大覆盖，运营 Agent 则在这一基础上补充达人级个性化诊断，并通过结果回收沉淀有效经验。

**30秒回答：** 面对大量中腰部和长尾作者，运营无法逐个分析，所以会按等级、经营状态或问题类型划分人群，再用 BPO、RPA、任务批量执行。但同样七天没开播，真实原因可能是缺商品、意愿下降或直播效果差，统一策略不够准确。Agent 可以对圈选后的每个作者读取数据、分别诊断和生成建议，再回收回复、行动和 T+N 经营结果。

**1分钟展开：**

- 规模化运营解决有限人力如何覆盖大量作者，核心是人群划分、标准策略和批量执行。
- 精细化运营诊断更深，但高度依赖人工，难以复制到长尾人群。
- Agent 希望兼顾两者：保留规模覆盖，同时对每个作者做个性化分析和建议。
- 触达后继续看采纳、行为和经营结果，用来验证策略并沉淀“什么作者—什么问题—什么策略—什么结果”。

**高频关键词：** 规模化运营、精细化运营、人群策略、BPO、RPA、个性化诊断、结果回收。

**易追问：**

- 规模化运营和精细化运营如何划分人群？
- Agent 怎样批量处理又保持个性化？
- 结果回收应该观察多长时间？

**回答雷区：**

- 把规模化运营理解成单纯群发消息。
- 认为同一人群一定适用同一策略。
- 只生成建议，不回收达人行动和经营结果。

### 问题二十：产品和运营有什么区别，怎样协作？

> **题目：**
>
> 产品和运营的目标往往都指向业务增长，它们之间最大的区别是什么？又是如何协作的？

**一句话结论：** 产品和运营可以共同服务业务增长，但运营主要制定和执行增长策略，产品把需要系统承接的部分转化为稳定、可持续的产品能力。

**30秒回答：** 两者目标可能都指向 GMV，但手段不同。产品通过功能、流程和体验设计解决问题，需要完成设计、研发、测试和发布；运营通过内容、活动、用户和策略动作推动增长。两者不是割裂的，例如运营提出优惠券拉新，产品还要设计用户在哪里看到、怎么领取、怎么使用和核销，再由研发落地。

**1分钟展开：**

- 共同点是最终业务目标可能一致，例如增长、GMV 或留存。
- 产品以系统功能和用户体验为主要手段，强调长期、稳定、可复用的能力。
- 运营通过内容、活动、触达和人群策略推动业务，手段更灵活、更贴近执行。
- 协作时运营提出策略和业务需求，产品将需要系统化的环节设计成完整流程，并与研发、测试共同落地。

**高频关键词：** 产品能力、运营策略、业务增长、用户体验、系统承接、协作落地。

**易追问：**

- 运营策略什么时候值得产品化？
- 产品和运营意见冲突时怎样决策？
- 怎样判断一个运营功能上线后是否有效？

**回答雷区：**

- 把产品理解成写需求、运营理解成做活动。
- 认为产品和运营目标天然不同。
- 只讲分工，不说明策略如何转化为系统能力。

### 问题二十一：怎样证明指标提升来自 Agent 策略，而不是达人自身成长或平台波动？

> **题目：**
>
> 如果 Agent 触达后达人 GMV 提升了，你怎么证明这是 Agent 策略带来的，而不是达人自身变化或者平台整体波动？

**一句话结论：** 归因不能只看最终 GMV，要先串联“建议—触达—采纳—行动—结果”，再通过相似人群、基线或对照组排除个体和大盘波动。

**30秒回答：** Agent 触达后 GMV 上升，只能说明相关，不能直接证明因果。我会先确认建议是否触达、达人是否回复和采纳、是否产生与建议一致的开播、投稿或选品动作，再看经营结果。还要观察一批相似达人是否出现一致改善，并与未使用 Agent 的对照组或历史基线比较，尽量剔除活动、大盘和达人自然成长影响。

**1分钟展开：**

- 先看过程链路：建议是否成功触达、被理解、被采纳。
- 再看行为变化是否与策略一致，例如重新开播、增加投稿或调整选品。
- 行为之后再看活跃、跃迁、留存和 GMV，避免跳过中间环节直接归因。
- 单个案例容易受自然波动影响，需要相似达人群体、历史基线或实验对照增强可信度。

**高频关键词：** 因果归因、过程指标、策略采纳、行为变化、相似人群、实验对照、大盘波动。

**易追问：**

- 对照组怎样避免人群质量差异？
- 无法做严格实验时如何提高归因可信度？
- 观察窗口应该怎样确定？

**回答雷区：**

- 达人 GMV 上升就直接归因于 Agent。
- 只看一两个成功案例。
- 有对照组但没有控制人群和活动差异。

### 问题二十二：如何验证和发布新 Skill 版本，避免直接影响线上达人？

> **题目：**
>
> 如果运营通过自然语言修改 Skill，如何保证新版本不会未经验证就直接影响线上达人？你会如何设计验证、发布和回退流程？

**一句话结论：** Skill 修改必须经过版本隔离、PPE 仿真、固定样本新旧对比、小流量只生成不触达、人工审核和可回退发布，不能让自然语言修改直接覆盖线上版本。

**30秒回答：** 我会从稳定 online 版本创建草稿和评测版本，在运营专属 PPE 中用正常、优秀、历史 badcase 和边界样本做新旧对比。固定样本通过后，再选择少量达人试跑，但只生成诊断和建议，由运营审核，不直接触达。发布 online、绑定人群和真实触达要拆成三个动作，并记录 Skill 版本、人群和执行结果；异常时可以暂停并回退上一版本。

**1分钟展开：**

- 版本隔离：修改发生在草稿和评测版本，不覆盖当前稳定 online。
- PPE 与固定样本：在隔离环境覆盖正常、优秀、badcase 和边界样本，对比新旧能力与退化。
- 小范围试跑：少量真实目标只生成结果，由运营人工审核，未通过不触达。
- 发布、绑定、触达分离，并记录版本、人群和日志，支持暂停、定位影响范围和快速回退。

**高频关键词：** Skill 版本、PPE、固定样本、badcase、新旧对比、小流量、人工审核、回退。

**易追问：**

- 固定评测样本如何持续更新？
- 新版本通过率达到多少才能上线？
- 线上问题发生后如何确定受影响达人？

**回答雷区：**

- 运营修改 Skill 后直接覆盖 online。
- 只测成功案例，不做旧能力回归。
- 把发布、绑定人群和真实触达合成一次不可逆操作。

### 问题二十三：为什么要提升全栈交付能力？

> **题目：**
>

**一句话结论：** 团队正在向“全栈 + AI”交付演进，而真实 Agent 业务依赖前端、服务端、数据和工具调用闭环，因此需要补齐服务端能力，形成端到端交付能力。

### 问题二十四：为什么运营 Agent 需要知识库？

> **题目：**
>
> 为什么运营 Agent 需要知识库？你准备重点学习哪些知识库形式，它们分别解决什么问题？

**一句话结论：** Wiki 负责以人可维护的方式沉淀业务规则、案例和运营经验，RAG 负责让 Agent 按语义检索和使用这些知识，两者是知识源与检索机制的关系。

**30秒回答：** 模型本身不了解企业内部规则和运营经验，而运营 Agent 的诊断高度依赖这些垂直知识。经过验证的“什么达人、什么问题、怎样判断、什么策略有效”需要先沉淀。LLM Wiki 适合人编写、阅读和维护，是原始知识载体；向量 RAG 将文档切分和索引，让 Agent 根据当前问题检索相关内容，它不适合作为人直接维护的最终载体。

**1分钟展开：**

- 必要性：模型通用知识不能替代企业规则、业务口径和资深运营经验。
- 沉淀内容：业务规则、诊断方法、优秀案例以及经过结果验证的运营策略。
- LLM Wiki 面向人，便于编写、审阅、更新和学习，是可治理的原始知识源。
- 向量 RAG 面向模型，负责语义检索；实际架构可以由 Wiki 提供内容，再构建索引供 Agent 使用。

**高频关键词：** 企业知识、运营经验、LLM Wiki、向量 RAG、原始知识源、语义检索、知识治理。

**易追问：**

- 哪些运营记录值得进入知识库？
- Wiki 更新后怎样同步 RAG 索引？
- 如何避免检索到过期或错误知识？

**回答雷区：**

- 把 Wiki 和 RAG 当成互相替代的两套知识库。
- 将所有聊天记录未经验证直接入库。
- 只讲检索技术，不讲知识维护、审核和版本。

### 问题 二十七 如果总结这段实习经历，你的工程思维发生了什么变化？

这段实习对我最大的改变，是让我逐渐从学生思维转变为工程师思维。

以前以学生思维做项目时，我更关注功能能不能实现，但对业务目标、协作方式和交付结果考虑得不够完整。经过这段实习，我主要有三个方面的转变。

第一，从只关注功能实现，转变为从业务背景出发思考需求。

拿到一个需求后，我不会再直接思考代码应该怎么写，而是先理解它要解决什么业务问题、希望达到什么目标，以及这个目标决定了哪些实现重点。在具体设计中，除了保证功能可用，我还会考虑安全性、可维护性、可扩展性，以及改动对存量功能的影响。

第二，从被动接受需求，转变为带着问题和方案主动沟通。

以前遇到不清楚的问题时，我可能只是向产品经理或服务端研发提问，希望对方直接给出答案。现在我会先分析问题，形成自己的判断或初步方案，再带着方案与对方沟通。例如，我会说明自己对需求的理解、当前可选的实现方式，以及不同方案的成本和风险。这样沟通不只是获取答案，也是共同完成方案决策。

第三，从模糊汇报进度，转变为对交付结果负责。

在汇报工作时，不能只说“正在做”或者“应该快完成了”，而要给出明确的信息，包括当前进度、预计交付时间、存在的问题和风险，以及下一步的处理计划。同时，说明正常情况下的交付目标、最晚交付时间和对应的应对方案，让项目进度保持透明、可预期。

一句话总结：这段实习让我意识到，工程师不仅要把功能做出来，还要理解业务价值，主动推动协作，并对最终交付结果负责。
