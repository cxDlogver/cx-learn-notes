## 问题二：AI Gate 的结论应该直接决定下一阶段吗？

 这道题我理解的是，Agent 的验收结论是否可信，也就是门禁检查的结论是否可信，能否通过门禁检查去决定下一阶段应该进入到哪一步，或者说去执行哪一个任务？

我的结论是，要根据门禁的类型来判断。门禁通常分为以下几个类型：

1. 确定性门禁
   这类文件通常通过脚本来验收，具有明确的通过或者不通过的标准。

2. 自然语言模型验收
   这一类通常没有明确的通过标准，它的规范通常是自然语言来表述的。需要通过模型的自主推理决策，判断当前的输出状态是否满足自然语言的不确定性的规范来判断能否通过门禁。所以这类问题本身是依赖于模型的主观判断，不确定性比较强，不能保证是一定可信的。因此，通常来说，对于第二类门禁是不能直接决定下一阶段，不能去根据门禁结论来决定下一阶段的。

3. 人工审查
   如果一个任务必须要通过模型来进行验收和门禁检查的话，最后对于一些高风险的节点就要通过人工审查来放行。人工审查通常是用于高风险、低置信度的环节。因为人工审查的成本高，要消耗大量的人力成本和时间成本，所以并不是每一个阶段、每一个不确定性的模型验收都需要引入人工审查。

## 问题六：为什么要单独设计 Repair？它怎么保证代码和工作流产物始终保持一致？

  为什么要提前？为什么要单独设计 repair？

Repair 是指返修流程，它的目的和目标是：

1. 保存原有工作流：当我们在测试期间发现问题，或者需求发生变更时，要能够保存原来的工作流。
2. 基础上进行返修：在原来的工作流基础上进行返修，重新执行一轮新的工作流。而这轮新的工作流不需要从头开始，而是在原来的工作流基础上进行修复和验证。

在 review 阶段进行修复时，不能只改代码，而是要按照以下步骤进行：

1. 修改需求：先修改需求，澄清需求。
2. 调整 test case 和计划文档。
3. 代码修复与必要重新验证：最后进行代码的修复，并进行必要的重新验证。

这样做的目的是为了保证代码和工作区的产物始终保持一致，工作区能够始终代表当前代码的最新状态。后续在进行人工审查或迭代优化时，能够基于当前的工作区产物迅速定位需要修改的计划和 test case。

这是因为我们在工作流阶段已经建立了原始需求、计划文档、test case 以及代码验收之间的映射关系。它通过矩阵的方式，将整个流程中每一个需求对应的 test case、对应的验收结果、对应的代码修改范围建立起了验收关系。因此，在后续迭代时可以快速找到需要修改哪些代码范围、需要调整哪些 test case、需要重新验证哪些验收项，而不需要再重新建立整个工作区的产物。

## 问题七：BITS 为什么不是“让 AI 再 Review 一遍代码”？它真正解决的是什么问题？

  历史阶段，它真正解决的问题其实是把评审评论的问题解决，即让评审评论从人工逐个解决变成让 AI 去进行自动化的处理，从而减少验证的时间周期和人工参与的成本。

它的整个流程如下：

1. AI 自动去拉取 Bug 上的评审评论。
2. 对它们进行分析：
   (a) 有效评论会保留。
   (b) 无效评论会直接回复：“这是一个无效评论，它和当前的需求设计没有关系”。
   (c) 有效评论才会去进行分析。
3. 分析后同步修改产物、同步修改测试项任务计划，然后修复代码再进行重新验证。
4. 验证完以后，会把最后的回复写回到评审评论上。
5. 最后由人工来审查。人工要审查评审评论和 AI 给出的回复来做把控，来判断是否放行。因为 AI 解决问题具有不确定性，而当前的评审评论又是整个代码交付或质量门禁检查的关键环节，所以这一轮的人工审查是必要的，必须由人工去放行，否则质量不可控。

所以，如果最后人工审查通过了，那么代码提交评审消除评审评论，最后就可以进入到上线阶段的代码上线上线环节。

因此，它真正解决的问题其实是实现自动化地解决评审评论，从而达到提效、缩短时间周期和减少人力成本的目的。

## 问题八：为什么 Test Case 必须放在 Coding 之前？它在整个 Workflow 里承担什么职责？

  Test case 放在 code 之前，目的是为了避免我们在构建 test case 的时候，由于受到生成代码的影响，导致 test case 避免迎合生成的代码，从而引起 test case 的偏差。将构建 test case 前置到代码生成之前，是满足现在主流规范（即 SDT，规范驱动测试）的要求。

SDT 的含义是：
1. Test case 构建要基于需求规范，建立需求与 test case 之间的映射关系。
2. 目的是将需求拆解成一组可执行、可验收的测试项，从而作为后续 AI 做自动化验收时的标准。
3. 建立需求与验收结论之间的映射关系。

在我看来，test case 是整个研发工作流中最核心、最重要的产物。它的准确性和完整性能够反映出 AI 或研发人员在做需求分析和任务规划时是否存在理解偏差。

为了确保这一点，test case 必须满足以下要求：
1. 准确性：每一个 test case 的预期、前置条件和预期结论，都必须和需求相对应。
2. 覆盖全面性：尽可能覆盖所有的需求场景和边界条件。

因此，在这个阶段我们需要引入人工审查，最好是由产品研发甚至测试同学共同去审查同一份 test case，认可同一份 test case 来作为后续验证的标准。后续 AI 在做自动化验收的时候，会按照这个 test case 矩阵来逐条进行验收，从而反映整个代码交付的质量。

## 问题十九：怎么判断 Agent 既实现了新需求，又没有破坏存量功能？

  简单来说，就是要去做回测和代码审查。在 AI 工作流里面，我做的工作主要包括以下几个方面：

1. 代码审查
   在代码提交之前，会通过 Git diff 判断当前修改的代码。AI 会对修改的代码进行审查，判断修改的内容是否有不可解释的修改，或者是否符合当前需求范围内的修改。

2. 测试验收
   在做测试验收的时候，每个 test case 除了有功能验收和视觉验收，还有回归风险的测试。也就是说，会验证当前的需求点需要实现什么功能、实现什么样的视觉效果，同时还要保证它没有出现什么样的结果和结论。这通常属于反向断言，目的是为了避免出现一些预期以外的修改。

目前这两类工作都是由 AI 根据自己的主观判断去进行验收的，没有明确的、确定性的验收标准。

如果更进一步，可能要做回归测试。回归测试主要包括以下两个方面：

1. 代码上线之前，会对核心的一些链路进行回归测试。
2. 对于当前代码修改可能造成直接影响的功能点，需要去单独建立一个测试库或者测试文件来进行回归测试。

  那最后为了消除A I的不确定性，还是需要人工审查，人工在做测试的时候，测试联调的时候，除了判断当前的功能能否功能点是否实现，还，还需要判断当前功能点相关的一些已有的功能是否还出现，是否出现了能回退

## 问题七：头达权限管控中，如何判断哪些逻辑应该抽到公共层、哪些必须留在业务页面？公共组件抽象过度会有什么问题？

   在投达权限管控中，抽象层、控制层和公共层的能力主要包括：

1. 权限解析：即权限中的解析方法。
2. 页面渲染遮盖和操作生成入口的公共组件：不管是字段级还是模块级，都是这两个全局方法，也就是这两个公共层能力。

针对如何将这样的能力封装成公共层，通常根据工程化思想和模块化设计，我们可以采取以下两种方式：

1. 抽象公共方法：
   将通用且会被多个页面复用的功能逻辑抽象成公共能力。例如，像需求里提到的权限状态解析，所有页面的权限状态解析链路是一样的，都可以复用权限状态解析的方法，最后提取成公共方法统一接入即可。

2. 组件化：
   提取多个页面可以复用的组件。各个页面只需通过统一接入公共组件，就可以实现统一的页面渲染组件。后续的修改只需要修改公共方法和公共组件，就可以实现所有页面的统一更新。

这就是提取公共层或者实施模块化带来的优势，能够提高代码的可维护性和可测试性。

但需要注意的是，公共组件不能抽象过度。不能为了兼容所有页面的情况，把整个公共组件变得过于冗余。要遵循高内聚、低耦合的设计思想，如果抽象过度，反而不利于后续的规模扩展和功能拓展。

## 问题八：头达权限确认成功后，为什么列表页和详情页要采用局部刷新，而不是统一使用 `window.location.reload()`？

 首先，图达权限管控里面没有统一用 06 年的 location reload，是因为它是一个标签页的刷新。我们觉得它带来的用户体验不好，比如我们想查看某一行作者列表的数据，希望查看它的真实数据，但是点击以后却把整个页面中所有的数据都进行了刷新，甚至还有菜单栏这些数据都重新刷新了一遍，它带来的缓冲时间和视觉用户体验效果都不好。

所以需求希望我们在列表详情页中只重新刷新列表，在详情页中只重新刷新当前的 tab。这样的局部刷新能够带来更好的用户体验。

1. 列表页：它刷新列表、重新加载数据是通过一个 get list 的方法。
2. 刷新 tab：我们修改 tab 的标签，让它能够让它的响应式能够监听到数据变化，然后重新去更新当前的 tab 页面。

所以每个页面都注册自己的刷新方法，注册到全局刷新函数里面，然后通过全局刷新方法的统一调用来实现我们在公共组件中来实现不同页面的刷新。

## 问题十：TCC 配置或权限接口异常时，为什么敏感数据默认按“无权限”处理，而不是直接放行？

  当 TCC 配置或者权限接口硬编码时，敏感数据默认既不是按照无权限处理，也不是直接放行。

1. 字段级权限异常情况：
   如果接口异常，没有返回业务数据或响应，页面会持续处于加载状态。因为此时既拿不到脱敏字段，也拿不到真实值。

2. 模块权限异常情况：
   在调用“查看权限”接口时，如果拿不到全返回的权限状态字段，代码逻辑中会判定为当前处于 loading 状态（即表示正在加载中）。此时页面通常也会显示 loading。

3. 数据返回与重新请求：
   只有当数据返回时，模块才会重新更新状态，并重新去请求正式的业务数据。因为查询模块权限接口本质上是一个异步调用的数据请求，所以当接口返回以后，它会更新状态并去请求这些业务数据。

## 问题十一：`SensitiveNoPermission` 为什么根据组件容器尺寸使用 `ResizeObserver` 自适应，而不是只监听浏览器窗口大小？

  我们通过自适应和监听的方法，去监听容器的尺寸，根据容器的尺寸来响应式地进行页面渲染。

因为当前的模块组件是对整个业务模块进行遮盖，而整个业务模块的容器尺寸不一致、不统一。它可能高度很小，但也作为一个业务模块存在，这时候没有办法放下一张无权限的插图，所以需要根据当前容器的高度，来自适应渲染样式。

在代码逻辑里面：
1. 如果高度小于 80，它会直接渲染“无权限文案”加上文字形式的链接去提供申请入口；
2. 如果在 280 到 200 之间，它会呈现出“文案加按钮”的顺序入口；
3. 如果超过 200，它才会显示无权限插图。

这里它不监听浏览器窗口，因为它不是根据浏览器窗口去渲染的，而是根据容器的尺寸去渲染的。

## 问题十二：为什么数据权限申请可以收口成全局公共能力，而协作人申请仍复用列表页和详情页各自的存量实现？

  因为申请数据权限是直接去复用一个数组平台的接口调用函数，接口调用通过调用一个接口就可以去渲染数据权限申请弹窗。

而协助人申请弹窗，它不是通过数组能力的调用，而是当前页面在列表和详情页中已经实现了一套申请协助人弹窗的方法，并且已经在各自组件中渲染了申请协助人弹窗，只是它默认就是不显示。

如果说我们想要申请协助人弹窗，其实其实就是把组件的属性从不可见变为可见。

所以在考虑不对存量代码功能造成破坏、不修改存量代码的前提下，尽量不修改全量代码的前提下，我们是通过去设计一个打开弹窗的公共方法，把它通过回调函数作为回调函数传递给公共组件，把它作为打开、把它作为申请协助人弹窗的方法入口。

## 问题十三：为什么把多接口、多字段的权限 Mock 重复操作沉淀成 Skill，而不是只写一个固定脚本？

  固定脚本与 Skill 的对比：

1. 固定脚本：
   * 目标：希望直接通过给 AI 输入一句话（例如“我要切换成某一种权限状态”），就能实现页面的统一切换。
   * 特点：它是确定性的，必须根据当前的权限状态以及脚本的参数，手动去判断并调用相应的脚本参数，然后再去复用脚本。

2. Skill：
   * 实质：本质上还是通过调用脚本去实现。
   * 优势：能够通过 AI 分析当前的数据 mark 状态，然后自主推理、调整并调用脚本。

## 问题十四：在复杂存量需求中，为什么方案设计前必须先读清页面入口、接口、状态来源和刷新方式等完整调用链？

  方案设计前要先读清页面入口接口状态来源和优化方案的完整调用链，目的是为了梳理当前的需求跟需求功能点的更新会修改哪些原文件和模块。这些原文件和模块会作为当前任务的代码修改范围清单。

在 AI 进行 coding 阶段，它会严格按照清单范围去进行代码的修改、调整以及更新。对于清单外的文件，默认是不允许去改动的，这是一个支持机制，用来作为门禁。这样可以保证不对需求范围外的存量代码造成再多的修改，从而避免对已有功能造成破坏。

所以，我们在任务规划阶段通常会根据需求分析来确定当前页面的需求入口，找到它的完整调用链，然后判断。在他所构建的需求文档和计划文档里面，每一个任务都会绑定一个需求范围修改清单，后续代码实现会基于这份计划文档去实现。

## 问题十五：前端增量覆盖率为什么不能只把代码覆盖率刷到 90%，还必须结合需求验收项判断测试是否完成？

  因为他们测试的目标不一样：

1. 验收项的测试是为了验证功能点、需求点和功能需求点的所有边界条件，它是质量交付的保障。只有所有的验收项都能够通过验收，才能够保证当前代码的质量，能够实现所有的需求。但是，每一个功能的实现可能过于冗余，它不是最优的。例如，一个功能的实现为了考虑所有的异常情况，导致过于冗余；或者为了考虑各种接口返回，甚至会根据接口返回的类型去编写大量的分支去抛出不一样的异常错误。同时，前端代码可能会像 AI 一样，既希望有 message 提示，又有 console log，又有 console error 这种一大串的报错提示。

2. 前端增量覆盖率测试是为了去优化代码：
   (a) 把一些永远不可能进入的分支的冗余代码找出来并删除、去除掉。
   (b) 优化简化一下代码。例如像刚才提到的安全防护，其实可能只需要通过一两行代码，即如果接口返回错误直接抛出异常，或者网络失败、上游服务器网络报错就可以，不需要有大量的代码去做维护，从而避免代码过于冗余。

这是前端增量覆盖率想解决的问题。但是前端增量覆盖率又不能实现功能的验收，所以两者需要结合起来。

## 问题十六：用户已经有数据权限后，为什么还要通过“小眼睛”进行确认查看和访问审计？它具体解决什么安全问题？

  两个安全解决两个问题：

1. 保证数据查看可追溯、可回溯、可审计。通过“小眼睛”来记录哪些运营看到了哪些数据，做了哪些操作。当隐私数据发生泄露时，可以追溯到在泄露期间、泄露之前的一段时间内，有哪些运营或者用户查看了当前作者的敏感数据，从而追溯定位原因和问题。
2. 防止异常访问。例如，一个用户频繁查看大量作者的隐私数据，当查看的频率达到某一个超出正常范围的阈值时，系统的审计就会记录并触发监听提示。虽然这个功能目前好像还没有实现，但它应该可以采取一些安全措施。

## 问题十七：前端增量覆盖率 Skill 为什么让查询请求保持真实，而对会写入后端的操作使用网络层 Mock？

 前端增量覆盖就是 skill，它是验证所有验证代码的逻辑链路是否能够走通。所以它必须基于真实页面在 PP 环境上去进行页面的操作和验收，它的所有点击或者接口请求都应该是真实的接口，并且拿到返回值。

对于一些不安全的接口请求，比如说写接口，它可能会修改服务端的状态。如果对于非幂等的新接口频繁地调用，企业接口还会频繁地去修改服务端的状态。

所以在 skill 里面，会统一对写接口、对不安全的接口使用网络层 mock。也就是说，接口不会真正地打到服务端，它会在网络层就被拦截，然后返回一个像 mock 响应。

## 问题十九：模块权限接口尚未返回时，为什么要单独使用 `loading` 状态，而不能提前按某一种无权限状态处理？

 因为无权限状态，每一种无权限状态都有自己的整个业务链路。

如果在接口未返回的时候显示一种无权限状态，比如说数据权限，用户就可以点击申请数据权限。但如果用户本身是有权限的，重新申请数据权限会导致整个链路存在冗余的请求，  对导也会导致他这个后续统计存在一些偏差。

## 问题二十：为什么要把多页面共用的权限判断和后续操作提取到公共层统一管理？

 按照工程化设计思想，通过把多个页面共用的通用公共逻辑统一到公共组件管理，能够实现模块化，从而提升系统的可维护性、可扩展性和可测试性。

后续如果规则发生变化，只需要对公共组件或公共方法进行修改，就能够统一更新所有的页面，而不需要单独对每个页面进行处理，从而避免一些页面漏改的问题。

   当前团队的业务定位依然是运营平台的建设，其目的是服务于作者运营和内容运营。核心目标是帮助达人成长和实现等级跃迁，从而提高优质作者的数量，最终提升整个联盟平台的 GMV 增长、生态建设和整个联盟生态的健康。

1. 作者运营：通过运营平台的达人库管理所有达人的数据。运营通过对达人库中获取的数据进行分析，给出运营策略。
2. 达人触达：通过运营平台中的达人触达模块，利用 BPO 或 RPA 的方式，系统直接将策略和任务下发给达人。

3. 运营 Agent 的作用：通过接入运营 Agent 来解决这个问题。由 Agent 直接收集达人的数据并对其进行个性化诊断，为每一个达人生成个性化的诊断策略。
4. 运营效果追踪：Agent 通过达人触达的方式触达给作者，并能够自动进行后续数据的追踪。它能够收集达人的反馈，包括任务领取情况、任务完成度、采纳改进措施后的经济指标是否提升、交易表现是否提升等。通过数据回收来判断运营策略是否有效，并进一步优化运营 Agent。

而对于一些有价值的、能够帮助达人成长的运营……

有有效的运营策略，能够沉淀到知识库里供后续运营或者 Agent 去复用。

所以团队未来的业务方向，就是希望把 Agent 的能力接入到运营平台的各个方面，能够实现运营辅助、Agent 辅助运营，来进一步实现团队绩效和运营绩效，解决业务痛点。

最终的目标是能够帮助更多达人成长和等级跃迁，从而提升优质作者数量，提升联盟的交易表现和联盟生态健康。这是团队未来的发展方向。

## 问题三：运营平台在整个联盟六个业务方向里扮演什么角色？未来会如何向 Agent 辅助运营演进？

 联盟的定位是商家与达人撮合的平台。商家将商品放在联盟中设置佣金，达人通过选择商品进行带货来赚取佣金，联盟则负责提供平台并进行撮合。

根据这一定位，联盟的业务可以分为以下几个方向：

1. 达人方向的业务
   简单来说就是作者运营。帮助作者诊断分析他们的经营数据，下达任务，提供运营策略，帮助他们成长并实现等级跃迁，成为优质作者。

2. 商家方向的业务
   吸引更多的商家将他们的商品放到联盟上，帮助商家找到达人带货，通过联盟的成交金额来提升商家的整体表现。

3. 撮合业务
   提供平台和方法，让商家能够找到达人，让达人能够找到合适的商品，从而促成商家与达人之间的合作。

4. 内容业务
   尤其是维护整个内容生态的健康，提升优质内容的数量。对于低质量内容要进行诊断，对于违规内容要进行治理。

5. 基建业务
   要保证整个电商交易平台或者联盟平台交易过程中的安全性、稳定性和数据交易过程的安全性。确保数据交易过程中不会出现问题，作者和达人的隐私数据不会泄露。这是整个电商平台的基础能力，也是最基本的保障。

6. 运营平台
   运营平台是服务于运营的，最终还是要服务于各个具体的业务，包括作者运营和内容运营。其目标是提升作者的经营表现，帮助他们成长和实现跃迁。

未来联盟平台会逐渐向 Agent 辅助型平台演进。也就是说，把联盟平台的各个链路通过接入 Agent 的能力，来解决一些运营的复杂任务，从而进一步为运营提效，并解决一些业务痛点的问题。比如利用“运营 Agent”来解决规模化运营中的业务痛点问题，即无法实现个性化运营。

## 问题四：你怎么理解作者运营的核心指标？如果“运营覆盖变高了，但达人没有成长”，你会怎么判断问题？

  作者运营的核心指标，我想从以下几个方面来看：

1. 作者规模
   主要是优质作者数和优质作者占比。因为优质作者是作者运营的最终目标，即能够提升优质作者数量，它能够直接反映整个联盟平台的交易表现和生态健康。

2. 成长维度
   包括：
   (a) 作者活跃度：如作者月签数、作者月签率。
   (b) 达人跃迁情况：在一定周期内，低质量作者跃迁到高质量作者的人数和占比。
   这些指标能够衡量在这个周期内，我们运营采取的一系列策略和手段是否有效果。相比于之前阶段的运营月签数进行对比，可以看到这一个周期的工作或方法能否达到很好的效果，从而为后续的工作重心转移提供参考建议。

3. 有效运营作者数
   这主要是针对规模化运营而言。有效运营是指运营通过生成策略触达给达人以后，达人领取了任务或者采纳了运营策略，去改进、改变自己的经营方法。

4. 作者留存
   包括月活作者数、作者留存数、流失作者的召回数等相关指标。这反映了运营能不能留住作者，能不能让作者始终在联盟中保持高质量的活跃度，使其保持在一个较高的值上，以及能否把流失的作者召回，让他们继续在联盟中进行带货和赚钱。

所以，我们要从这几个维度去衡量作者运营。

目前存在的问题是：如果作者运营覆盖数变高了，但达人没有成长。当前的主要问题在于：
1. 作者的供给量很高，并且活跃度也很高。
2. 交易表现比较低。
3. 达人没有实现成长和等级跃迁。

这是后续需要解决的重点。其中一方面可能是运营策略有问题。像规模化运营，它通过生成一个比较标准化的运营策略，这个策略被达人采纳并完成了任务以后，并没有产生好的效果，说明运营策略本身可能是有问题的。

引入 Agent 以后，就希望能够为每一个达人进行诊断分析，然后生成一个个性化的经营策略来考虑。我们需要评估：
1. 能否解决这个问题？
2. 能否在一定程度上解决这个问题？
3. 是否能够提升经营策略的价值和质量，帮助他们成长？

## 问题五：为什么现有规模化运营还需要引入运营 Agent？它真正要解决的业务问题是什么？

    规模化运营引入运营AI，它真正想要解决的业务问题是实现批量个性化运营，批量生成个性化的诊断策略，并且能够沉淀优秀的经营策略。

当前团队在端前作者运营的问题是，作者的贡献量很高，作者的经营活跃度也很好，但是他们的交易成交金额和效果成交金额不高，并且他们的成长和等级跃迁的效果很差，特别是对于S0到S3的这种长尾作者，他们的成长过于缓慢。整个作者生态呈现的是一个钉子状态，为底部的作者人数过多，而这一部分作者的运营是通过规则的运营策略，也就是规模化运营。因为人数过多，运营策略没有办法做到一对一的进行诊断分析，帮助他们去成长，而是通过规模化运营，也就是通过圈选一部分具有相似问题的作者进行批量诊断，生成一个相对标准化的经营策略，然后通过BPO的方式和系统触达给这一批作者达人。

而对于一些高质量的作者、高潜作者，可以通过BPO的方式去外包，通过BPO外包的方式去持续跟进，来判断应用场景是否生效。而更多通过RPA方式直接触达给达人的，后续可能就没有下文了，也没有回收数据，比如作者有没有提升，就没有去做针对性的分析。这可能是导致底部尾部作者难以成长的一个关键问题。

一方面是这个运营策略，它是一个标准化的，针对这一圈选的达人去批量生成的，没有针对每一个达人的问题进行个性化诊断和生成个性化的策略。第二，他没有对每一个作者的经营数据进行回收，去判断他们的反馈，去收集他们的反馈和后续的交易表现进行分析。

而运营agent的引入就是希望能够解决这个问题，它通过用agent去自动获取所有圈选的作者达人的数据，为每一个作者达人进行诊断和生成专门针对当前达人的个性化经营策略，然后触达给作者。后续会自动去收集作者的反馈和他们的交易表现、经营指标来判断策略是否生效。如果策略没有生效，要分析问题，优化运营agent。如果运营策略达到了很好的效果，需要去沉淀这些优秀的经营策略来供后续运营和agent进行分析和生成策略时提供参考和复用。

所以当前运营agent想要解决的业务问题是实现进化的运营和实现批量个性化运营，沉淀优秀的经营策略，最终是希望能够帮助S0到S3这一部分作者实现成长和等级跃迁，帮助他们成为S4加的高质量作者。

## 问题八：你认为运营 Agent 和现有运营平台是什么关系？为什么不能只做成一个独立的聊天机器人？

  运营平台依然要提供工具，它依然是一个提供工具的平台。运营 Agent 只是在现有的运营平台上接入 Agent 的能力。

它的作用是代替运营人员完成一部分复杂的工作，实现运营的提效，并解决一些业务重点问题。但它依然要依赖于运营平台的各项能力，例如：

1. 需要读取达人库的数据；
2. 需要通过系统模块和触达模块，把任务下发给达人；
3. 通过设立内容活动来激励作者产生更加优质的内容。

因此，运营平台的工具依然要提供各种工具来实现线上化和规模化。运营 Agent 只是接入运营平台，它们之间是调用的关系，即运营 Agent 会调用运营平台的各项工具，而不是替代的关系。

## 问题九：除了规模化运营 Agent，运营平台还有哪些业务方向可以接入 Agent 能力？

   应该有很多，包括任何复杂任务，其实都可以考虑交由 Agent 能力接入。

1. 内容诊断
   内容诊断需要根据当前内容进行，需要对当前内容的数据进行分析，比如播放率、交易表现、浏览量等指标，来判断当前内容的质量、当前内容的问题在哪里，以及怎么去做改进。
   * 案例：比如浏览量很高，但是交易表现很低，那么如何考虑诊断并进行优化和调整？是由于内容没有太大价值，还是说它在哪些质量维度方面还需要跟进？
   * 方案：这可以通过多维数据诊断分析和推理的工作，由 Agent 基于模型推理来帮助诊断。因此，运营 Agent 也可以借助 Agent 的能力来进行精细化运营。

2. 线下拜访提案
   比如我们做线下拜访，需要生成拜访提案。之前也设计过拜访提案的 skill，即为每一个达人作者，根据他们的历史经营表现、历史数据，以及和同类型作者进行比对，生成一份拜访提案。
   * 提案内容：包括他的数据总结、几个核心问题、拜访提案的主要流程以及应该关注哪些问题的交流。
   * 性质：这是运营精细化的一个 case。

总的来说，如果一个业务方向是不确定性和复杂性的任务，就可以考虑通过接入 Agent 的能力来解决一些业务痛点，并帮助运营提效。

## 问题十：如果把 Agent 能力接入内容运营，你认为最值得优先做哪个场景？为什么？

1. **第一期优先做内容质量诊断 Agent**
   - 不把第一期目标定义成“让 Agent 自动筛选所有优质内容”。
   - 重点解决“为什么这个内容好/不好，以及应该怎么优化”。

2. **规则和算法继续负责确定性筛选**
   - 播放量、成交金额、质量评级、阈值等明确指标继续通过规则和算法处理。
   - Agent 不需要重复建设已经成熟的筛选能力。

3. **Agent 负责复杂内容理解和诊断**
   - 综合内容表达、商品卖点、达人特征、播放互动转化数据、同赛道优秀案例等上下文。
   - 判断问题发生在哪个环节，并生成针对性的优化建议。

4. **形成完整业务闭环**
   - “读取内容和经营数据 → Agent 诊断 → 给出建议 → 运营审核 → 达人调整内容 → 回收后续内容表现”。
   - 第一阶段保持人工审核，不直接自动进入好内容周或好作者选。

5. **后续沉淀优秀内容经验**
   - 把经过真实结果验证的优秀案例沉淀成“内容特征 → 判断依据 → 优化建议 → 实际结果”。
   - 后续可以供运营、达人和其他 Agent 复用。

6. **通过三层指标评估**
   - 运营效率：单条内容诊断耗时、可覆盖内容量。
   - 建议质量：运营/达人采纳率、建议执行率。
   - 业务结果：优质内容率、播放、互动、转化和成交表现是否改善。

## 问题十一：如何判断一个现有业务是否适合升级为 Agent？如果适合，应该如何完成业务和技术设计？

### 【题目】

假设现在有一个已经稳定运行的传统业务，原有链路主要通过人工、规则、Workflow、RPA 或普通系统能力完成。

现在希望引入 AI / Agent。

如果由你负责这个方向，你会如何判断：

> **这个业务到底适不适合升级成 Agent？如果适合，应该从哪些方面完成业务规划和技术落地？**

### 【回答要点】

1. **先看业务价值**
   - 当前业务到底存在什么痛点？
   - 引入 Agent 是为了提效，还是解决传统方案难以解决的业务问题？
   - Agent 应该带来明确的增量价值，而不是单纯替换原有技术实现。

2. **判断这个问题是不是真的需要 Agent**
   - 明确区分确定性问题和复杂判断问题。
   - 规则明确、输入输出固定的问题继续用规则、Workflow、RPA 或普通服务。
   - 多源数据理解、上下文分析、规则难以穷举、需要个性化判断的问题更适合 Agent。

3. **建设之前定义清楚效果指标**
   - 效率指标：人工耗时、单人服务规模、任务处理时间等。
   - Agent 输出质量：人工审核通过率、建议采纳率、策略执行率等。
   - 最终业务结果：用户行动、经营改善、跃迁、交易结果等。
   - 最终要形成“Agent 输出 → 采纳 → 行动 → 业务结果”的指标链。

4. **判断现有业务链路是否完整，并设计 Agent 如何嵌入原有系统**
   - 先梳理现有业务 SOP，再判断哪些节点需要 Agent。
   - 可以采用“外层固定 Workflow / SOP + 内部关键节点使用 Agent”的方式。
   - Agent 负责复杂理解、判断和个性化策略生成；确定性能力继续复用原有系统。
   - 通过 API / Tool 复用数据查询、人群管理、任务、RPA/BPO、触达、权限等已有能力。
   - 同时检查“数据 → 判断 → 执行 → 反馈”链路是否完整。
   - 对高风险业务动作加入人工审核、权限、日志、监控和回退机制。

## 问题十三：什么是作者运营？

作者运营围绕电商作者，特指联盟作者的日常经营展开。

运营首先会通过作者的经营数据了解他当前的经营状态，比如开播、投稿、成交、选品等情况，然后分析作者目前存在的问题，并给出一些个性化的诊断意见，比如流量扶持、商品选品、经营方向调整等，帮助作者提升经营活跃度和交易表现。

但作者运营并不是把建议发出去就结束了，还需要持续跟踪作者后续有没有采取行动，比如有没有重新开播、投稿、调整选品，以及这些动作之后经营数据有没有改善。

所以作者运营最终关注的是：这些运营策略是否真正帮助作者成长，是否能够推动作者实现等级跃迁，并逐步成为高质量、优质的联盟作者。

## 问题十四：达人库的作用是什么？

达人库的核心作用是管理达人的基本信息和运营关系，包括经营数据、违规处罚数据、所属团队和所属赛道等。

除了信息本身，更重要的是通过达人库建立运营归属关系，也就是明确每个达人属于哪个运营团队、由哪个运营人员负责跟进。这样后续做作者诊断时，运营就能知道这个达人当前是什么经营状态、属于什么类型，以及应该采用什么样的运营方式。

比如，一个达人属于规模化运营还是 KA 运营，对应的运营策略是不一样的。规模化运营可能通过 BPO、RPA、任务等方式批量触达；而 KA 运营则更偏向精细化运营，需要运营人员深入分析单个达人的问题，给出更有针对性的建议，并持续追踪后续结果。

所以达人库解决的核心问题，就是统一管理达人的信息和运营归属，为后续诊断、策略制定和运营执行提供基础。

## 问题十五：作者和达人的区别是什么？

我理解作者和达人最大的区别在于范围不同。

作者是一个更大的概念，指通过电商内容实现带货的人。按照经营方式，可以进一步分成商家型作者和达人型作者。

商家型作者主要销售自己授权店铺中的商品，而达人型作者除了可能给自己的店铺带货以外，还可以帮助其他商家销售商品并赚取佣金。

在联盟业务中，我们重点关注的是联盟达人，也可以理解为联盟作者，也就是帮助其他商家带货赚取佣金的这部分达人。如果只是销售自己店铺的商品，就不属于联盟作者运营的核心范围。

所以作者运营最终重点服务的是联盟达人。

## 问题十六：作者运营的核心指标有哪些？

1. **作者规模**：优质作者、高质量作者数量。
2. **作者成长**：作者从低等级向高等级跃迁的数量或占比。
3. **运营覆盖**：有效运营作者数、有效运营率，强调真实互动而不是单向发送。
4. **作者留存**：月活作者数、留存、流失召回率。
5. **最终结果**：作者成长、活跃和优质作者规模扩大，最终服务 GMV 和生态健康。

---

## 问题十七：什么是内容运营？

我理解内容运营的核心，是管理内容生态的健康度，持续扩大优质内容供给。

具体来说，我会把内容运营拆成四条主线。

第一是定标准。平台会有“真实、专业、可信、有趣”等内容主张，需要进一步拆成可以衡量的质量维度，比如信息量、画风、商品价值等，并形成内容质量判断标准，作为后续分发和权益分配的依据。

第二是做治理。这是内容生态的底线，通过机审和人审识别虚假宣传、违规营销、内容和商品不匹配等问题，该治理的治理，保证生态健康。

第三是给激励。对于优质内容，通过流量倾斜、权益加成、周选月选、活动发奖等方式，让作者做好内容以后能够真正获得收益，形成正向循环。

第四是做诊断。把内容质量问题、违规点和改进建议反馈给作者，让作者知道内容差在哪里、应该怎么改，同时通过 AI 脚本、混剪工具等方式降低创作门槛。

所以内容运营最终不是单纯管理内容，而是持续提升优质内容供给，让好内容获得更多流量，并进一步带动内容消费和交易增长。

---

## 问题十八：内容运营的核心指标有哪些？

第一层是内容质量。核心看优质内容数和优质内容 VV 占比。优质内容数反映平台到底生产了多少好内容，优质内容 VV 占比则反映这些好内容有没有真正拿到更多播放和流量。这两个指标合起来既看供给规模，也看优质内容是否被有效分发。

第二层是内容分发。核心可以看内容 Load，也就是整体内容曝光和播放规模。它反映内容策略、活动和热点运营有没有真正把内容消费盘子做大。如果内容质量很好但 Load 上不去，说明好内容没有被有效分发出去。

第三层是内容转化。核心看内容 GMV，更准确地说是全域成交价值，以及 GPM。全域成交价值不仅包括视频挂车带来的直接 GMV，还应该包括看完内容以后去搜索、商城下单等间接成交，以及内容种草带来的相关成交。GPM 则衡量每一千次播放能够产生多少成交金额。

所以这三层指标的关系是：质量是基础，分发是桥梁，转化是最终结果。内容运营的本质就是让好内容被更多人看到，并且最终产生更高的交易价值。

## 问题二十：产品和运营到底有什么区别？

我理解产品和运营很多时候目标是一致的，比如在电商业务中都可能希望提升 GMV，但两者实现目标的手段不同。

产品主要通过产品功能来实现目标。一个产品功能从设计到上线，需要考虑用户体验、业务流程和技术落地可行性，并经过设计、研发、测试和发布。

运营实现目标的手段更加丰富，比如内容运营通过内容影响用户决策，活动运营通过活动促进购买，用户运营通过拉新、召回和留存扩大用户生命周期价值。

所以虽然目标可能一样，但产品更多是通过“产品能力”解决问题，运营则更多通过“运营策略和动作”推动业务增长。

但两者也需要紧密协作，因为很多运营方案最终需要产品能力承接。

比如运营希望通过优惠券拉新，就不仅是提出“发优惠券”，还需要进一步设计用户在哪里看到优惠券、怎么领取、怎么使用、怎么核销。这些具体的系统能力就需要产品和研发共同落地。

所以可以理解为：

> **运营更多决定“用什么策略推动业务”，产品负责把需要系统承接的策略转化成可落地、可持续的产品能力。**

## 问题二十一：怎么证明指标提升来自 Agent 的策略，而不是达人自身成长或平台波动？

判断 Agent 策略是否有效，不能只看 GMV 等最终业务指标，而应该看策略从触达到执行的完整过程。

首先要确认运营建议有没有成功触达达人；其次看达人有没有回复、有没有采纳；再进一步看达人采纳以后有没有产生和建议对应的实际行为，比如重新开播、投稿、调整选品等。

只有当“建议—采纳—行动—经营结果”能够串起来，才有更充分的依据说明后面的指标变化可能和这次运营策略有关。

同时还要看一批相似达人是不是出现相对一致的效果。如果只有一两个达人 GMV 提升，而大部分达人没有变化，那么这更可能是个体自然波动，不能说明策略有效。相反，如果一批相似达人在采纳建议后都出现了对应行为变化，并且经营指标整体改善，那么这套策略的有效性会更可信。

如果需要进一步做严格归因，还应该引入基线、对照组或者相似人群对比，尽量把平台大盘波动和达人自身成长因素剔除。

所以我会把归因链路理解成：

> **Agent 建议 → 成功触达 → 达人采纳 → 行为发生变化 → 经营结果改善 → 对照验证。**

---

## 问题二十二：你准备如何验证和发布新版本，避免修改后直接影响线上达人？

1. **版本隔离**：基于稳定 online 版本创建草稿和评测版本。
2. **PPE 仿真**：先在与真实触达隔离的环境测试。
3. **固定样本评测**：覆盖正常、优秀、历史 badcase 和边界样本，新旧版本对比。
4. **少量达人试跑**：只生成结果，不直接真实触达。
5. **人工审核**：未通过评测和审核不能上线。
6. **发布、绑定、触达分离**：避免一次动作直接影响大范围达人。
7. **日志和回退**：保留 Skill 版本、人群范围和执行记录，支持快速回退。

## 问题二十三：为什么要提升全栈交付能力？

我把全栈交付能力作为后续重点提升方向，主要有两个原因。

第一，团队整体正在向“全栈 + AI”的研发模式转型。现在很多业务需求已经不是单纯的前端页面开发，而是会同时涉及前端、服务端接口、数据链路以及 Agent 能力。

第二，后续运营 Agent 要真正完成业务闭环，也需要依赖后端能力。比如 Agent 要读取达人经营数据、查询内容信息、创建任务或者调用其他业务服务，这些都离不开服务端接口和数据能力。

我目前的能力主要集中在前端，所以后续需要补齐 Go、内部服务端框架以及服务端开发流程。

具体学习方式上，我希望从一个基础的真实服务端需求入手，完整经历接口设计、代码开发、前后端联调、测试和上线，先真正跑通一次全栈交付闭环，而不是只停留在看文档或者理解概念。

## 问题二十四：为什么要掌握知识库能力？

Agent 仅靠模型本身无法了解企业内部业务知识，而运营 Agent 又需要大量垂直领域信息，比如业务规则、诊断方法和经过验证的优秀运营经验，所以知识库是很重要的一部分。

比如某类达人出现经营下降以后，资深运营可能已经总结出一套有效判断方法。如果这些经验只停留在个人脑子里或者聊天记录中，其他运营和 Agent 都很难直接复用。把这些经验沉淀到知识库以后，就可以成为后续诊断的重要参考。

我目前重点关注两类知识库形式。

第一类是 LLM Wiki。它以文档形式组织知识，更适合人编写、阅读和维护。运营经验可以先沉淀到 Wiki 中，既方便新运营学习，也可以作为 Agent 的原始知识来源。

第二类是向量 RAG。它会把文档拆分并转成向量，让 Agent 可以根据当前问题的语义检索到相关知识。向量索引本身不适合人直接阅读和编辑，所以它更像模型侧的检索机制，而不是知识的最终维护载体。

所以我理解二者不是替代关系，而是：

> **Wiki 负责沉淀和维护知识，RAG 负责帮助 Agent 按需找到和使用知识。**

## 问题二十五：你实习期间最大的成长是什么？

我觉得实习期间最大的成长，是逐渐形成了一套比较稳定的解决问题的方法：

> **先分析问题，再调研解决方案，最后把有效方法沉淀下来。**

比如在解决代码覆盖率问题时，原来的方式需要人工点击页面去触发不同代码分支，不仅耗时，而且很多分支很难进入。

后来我先和负责华佗覆盖率的同学沟通，了解如何通过 API 获取覆盖率报告，再把这个能力和浏览器自动化结合起来，让 AI 自动获取覆盖率、定位未覆盖分支并操作页面完成验证，最后把整个过程沉淀成增量覆盖率 Skill。

处理评审评论也是类似的。人工逐条查看评论和处理比较耗时，所以我先调研了相关工具，了解 bytecli 怎么拉取评审评论，再把这套流程沉淀成 Skill，让 AI 自动读取和处理评论，人工主要做最终审核。

所以我最大的收获，不只是学会了某一个工具，而是形成了一套方法：先理解问题和底层原理，再通过调研以及和有经验的同学沟通找到解决方式，最后把可以复用的方法沉淀下来。这样下一次遇到同类问题时，就不需要再从头解决。

## 问题二十六：和正式员工相比，你有什么不足，如何解决？

### 【题目】

你认为自己和正式员工相比，目前最大的不足是什么？你准备如何持续改善？

### 【回答要点】

1. **技术不足**：对内部工具更多停留在使用层，对底层原理和能力边界理解不深。
2. **具体案例**：浏览器自动化中因不了解 vmok 原理，前期在工具选型上走了弯路。
3. **业务不足**：需求分析更多关注实现，对业务目标和团队阶段性重点理解还不够。
4. **改进方式**：阅读内部文档、主动向产品运营和技术同学学习、结合真实实践沉淀经验。

### 【标准回答】

我认为自己目前主要有两方面不足。

第一，对内部工具的学习还比较偏使用层，对背后的原理和能力边界理解得不够深入。这会影响我对工具适用场景的判断，也会增加选型的试错成本。

比如在浏览器自动化验收时，我最初希望使用内置浏览器，但当时需要解决登录态复用以及如何在真实平台环境中运行本地代码的问题。因为我不了解 vmok 的工作原理，也没有深入理解代理和资源加载机制，所以误以为内置浏览器不能解决这个问题。

因此我又尝试了 Playwright 和 Chrome DevTools MCP，希望通过接管本地 Chrome 来复用登录态和本地开发环境，但这些方案不够稳定，经常出现连接中断。

后来团队进一步调研后发现，vmok 可以把页面中的线上业务代码替换成本地正在开发的代码，这样就可以直接使用更稳定的内置浏览器完成自动化验收。

这件事让我意识到，如果只知道一个工具“怎么用”，但不了解它为什么能用、边界在哪里，就容易在工具选型和问题分析上产生盲区。

第二，对团队业务背景的理解还不够深入。

目前我做需求分析时，更多关注怎么实现需求、怎么解决技术问题，但对需求背后的业务目标、团队当前阶段性重点理解得还不够。所以在判断需求价值、参与业务讨论或者理解团队后续规划时，我的判断还不够成熟。

这两方面都需要长期积累。

一方面，我会继续阅读团队内部业务文档和技术经验沉淀，建立更系统的认识；另一方面，我会加强和团队的交流，业务方面主动向产品和运营了解需求背后的目标，技术方面多和有经验的同学讨论工具原理和选型依据，吸收已有实践，避免只依靠自己反复试错。

同时我也会继续把学习和实践中的经验沉淀下来，逐步提升自己的业务判断能力和技术深度。

## 问题 二十七 如果总结这段实习经历，你的工程思维发生了什么变化？

这段实习对我最大的改变，是让我逐渐从学生思维转变为工程师思维。

以前以学生思维做项目时，我更关注功能能不能实现，但对业务目标、协作方式和交付结果考虑得不够完整。经过这段实习，我主要有三个方面的转变。

第一，从只关心需求时的功能实现，转变为要考虑代码交付质量。

一方面是在拿到需求以后，不能直接思考代码的设计，而是要根据当前业务问题和想实现目标，来决定实现重点。要从功能可用性、安全性、维护性以及对存量功能的影响等多个维度，去考虑代码的交付质量。

另一方面是要按照严格需求交付流程，确保整个需求交付过程是可验收、可回溯、可审查的，从而保证交付质量。具体的开发流程包括：
1. 需求分析评审
2. 技术方案设计
3. 任务规划
4. 代码实现
5. 验收和通过门禁检查

第二，从被动接受需求，转变为带着问题和方案主动沟通。

以前遇到不清楚的问题时，我可能只是向产品经理或服务端研发提问，希望对方直接给出答案。现在我会先分析问题，形成自己的判断或初步方案，再带着方案与对方沟通。例如，我会说明自己对需求的理解、当前可选的实现方式，以及不同方案的成本和风险。这样沟通不只是获取答案，也是共同完成方案决策。

第三，从模糊汇报进度，转变为对交付结果负责。

在汇报工作时，不能只说“正在做”或者“应该快完成了”，而要给出明确的信息，包括当前进度、预计交付时间、存在的问题和风险，以及下一步的处理计划。同时，说明正常情况下的交付目标、最晚交付时间和对应的应对方案，让项目进度保持透明、可预期。

一句话总结：这段实习让我意识到，工程师不仅要把功能做出来，还要理解业务价值，主动推动协作，并对最终交付结果负责。
