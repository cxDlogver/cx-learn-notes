## 1. 自我介绍

大家好，我是陈相，目前是中国地质大学的硕士研究生。从今年 4 月 20 日开始，我加入了**<u>电商内容运营大前端团队</u>**。实习期间，我的重点工作主要有两部分：第一是独立完成头达敏感数据权限管控需求，第二是参与 AI Coding 研发工作流的设计和业务实践。

### 【重点工作】

**<u>第一项重点工作，是头达敏感数据权限管控。</u>**

这个需求主要针对头部达人的敏感数据存在被非授权查看以及数据泄露的风险。这次需求希望针对头达敏感数据建立一套更加完整的权限管控机制。

整个权限链路可以分成几个层次。对于L4+的数据，用户首先需要满足协作关系，也就是成为对应作者的协作人；在此基础上，还需要进一步申请数据权限；数据权限申请通过之后，对于更高敏感等级的数据，还需要经过一次“确认查看”，才能最终展示真实数据。通过这样的多层权限控制，来降低敏感数据被非必要访问的风险。

**<u>这个项目的主要难点，是需要在大量存量代码和已有业务能力的基础上，接入一套统一的权限管控能力。</u>**

所以在方案设计上，我重点考虑了两个方向，第一个是安全性，第二个是工程上的可复用性和可维护性。

**<u>首先是安全性。</u>**

整个真实数据的权限校验和脱敏都放在服务端完成。没有通过权限校验的真实数据不能下发到浏览器，这样可以避免真实数据可以通过抓包或者调试工具获取的问题。也就是说，前端负责权限状态的展示和交互，真正的数据安全边界放在后端。

**<u>第二个方面是工程设计。</u>**

因为这次需求是基于全量存量代码对多个页面的组件和代码逻辑进行统一的改造。我在实现过程中会先梳理现有代码和调用链，尽可能复用已有能力，在此基础上把通用的权限状态解析、展示逻辑以及申请和确认查看流程进一步抽象成公共方法和公共组件。

这样做的目的，是尽量减少对存量代码的侵入，实现不同页面的权限统一管控。

上线以后，确认查看链路和权限申请链路也产生了真实的访问和审批记录，确认查看产生了近 5000 条访问记录。整个需求运行期间，没有发现敏感数据误展示或者越权访问的问题，所以这套方案已经在真实生产环境中发挥了敏感数据权限管控的价值。

**<u>第二项重点工作，是 AI Coding 研发工作流的设计和业务验证。</u>**

这项工作的目标，是希望面向电商前端交付场景，构建一套更适合团队内部业务的 AI Coding 工作流。

团队之前已经在使用各种 AI Coding 工具，但实际使用下来，我们发现通用工具本身并不能直接解决企业内部研发流程的问题。一方面，他没有办法使用内部的一些工具，也没有针对后端未实现的一套 mock 流程，也没有通过操纵浏览器实现自动化验收，所以它并不能解决真实电商前端需求交付的问题。

所以我们希望把团队在需求交付过程中沉淀的经验和内部工具集成到 AI 空降工作流中，形成一套面向电商前端交付的端到端 AI Coding 工作流。

**<u>在整个工作流的设计中，我主要关注四个原则。</u>**

第一个是规范驱动。

也就是SDD规范， 在代码实现之前，先进行需求澄清、技术分析以及任务规划，明确整体任务计划。目的就是先把**“要做什么、为什么这么做、做到什么程度**”定义清楚，再进入代码实现，而不是直接让 AI 根据一份模糊需求开始写代码。

**<u>第二个是验收先行。</u>**

这里主要参考 ADTT 验收测试驱动开发的思想，把 Test Case 前置到代码开发之前。

测试项不能根据最终代码实现反向生成，而应该直接来源于需求规范，并且建立需求和测试之间的映射关系。

也就是说，在真正开始编码之前，就应该先明确这个需求应该如何被验收、每一个功能点对应什么样的验收标准。这样后续 AI 在完成代码之后，验收的标准是相对稳定的，不会出现“代码怎么实现，就按照代码怎么测试”的问题。

**<u>第三个是过程可追溯。</u>**

AI Coding 本质上是在执行一个比较长的研发任务，所以我们会把整个任务拆分成多个阶段和子任务，每个阶段都有明确的输入、输出以及结构化产物。

通过这些产物，可以建立需求、Task、代码和 Test Case 之间的映射关系。

这样一方面，每一个需求都可以追溯到它具体修改了哪些代码、对应什么验收标准，以及最终验收结论是什么；另一方面，每一处代码修改也能够反向找到它对应的需求点，从而判断这个修改是不是合理、是不是必要，以及有没有对其他功能产生影响。

所以，可追溯性的核心，就是通过阶段性的结构化产物，把整个研发过程连接起来，同时把这些产物作为后续 AI 继续开发和迭代时的上下文资料。

**<u>第四个是安全机制，也就是人工门禁。</u>**

因为 AI 当前还不能完全可靠地独立完成企业级研发交付，根据AI-DLC 在自动化开发过程中，人工仍然需要对关键节点进行审查，尤其是高风险或者低置信度的结果。

例如需求澄清、Task 和 Test Case、验收证据、验收结论以及最终代码审查，都需要人工进行确认。最后在代码真正交付之前，还需要通过门禁检查和人工放行，保证整个研发过程是可控的，同时保证最终交付代码的质量。



在工作流设计之外，第二个重点是通过真实业务需求验证它是否真正有效。

因为如果只设计一套流程，但没有经过业务实践，很难说明它是否真的能够帮助团队提升研发效率。

所以我们选择真实业务需求进行了完整验证，例如内容激励管控需求，通过真实需求去观察这套工作流能不能完成从需求分析、任务拆解、代码实现、自动验收到问题修复的完整过程。

我们希望最终能够从几个维度来评估它的价值：第一是能不能减少人工投入，第二是能不能缩短整体交付周期，第三是能不能在提升效率的同时保证交付质量。

### 【业务方向】

目前这两部分，是我在实习期间投入比较多的重点工作。

**<u>从业务方向来看，当前团队主要还是围绕运营平台进行建设，服务于作者运营和内容运营。</u>**

整个业务的核心目标，是希望通过运营手段帮助作者成长，实现等级跃迁，从而提升优质作者数量，并最终改善联盟整体的 GMV 和生态健康。

而团队后续比较重要的方向，是进一步把 AI 和 Agent 能力接入运营平台，让 AI 去解决传统系统难以处理的一些复杂任务，从而帮助运营进一步提效，同时解决现有业务中的一些痛点。

比如在作者运营中，目前作者生态存在比较明显的分层问题，大量作者集中在中腰部和长尾等级。部分作者虽然保持较高活跃度，但是交易表现和等级跃迁效果并不好。这也说明，在规模化运营过程中，当前的一些经营策略和运营方式还有进一步优化的空间。

所以，未来运营平台在继续完善基础工具能力的同时，也希望引入运营 Agent。

比如让 Agent 在规模化处理大量作者的同时，还能够针对每一个作者的数据进行个性化诊断，分析作者当前存在的经营问题，再生成更加有针对性的经营策略。这样就可以在保持规模化运营效率的同时，进一步提升经营策略的个性化和质量，解决传统批量策略比较标准化、无法充分覆盖个体差异的问题。

未来团队希望能够逐步把 AI 能力连接到运营平台的不同业务环节中，一方面提升团队和运营同学的效率，另一方面真正改善作者成长和内容经营中的业务痛点。最终希望通过帮助更多作者成长、实现等级跃迁，进一步提升优质作者数量以及联盟整体的 GMV 和生态健康。

从更长期来看，**<u>我认为团队的研发和业务形态也会逐渐向 AI Native 的方向发展</u>**。AI 不再只是一个单点的编码工具或者辅助工具，而会逐步参与到研发流程和业务运营流程中。

### 【个人成长】

#### <u>1. 你实习期间最大的成长是什么？</u>

- 最大成长是形成了 **<u>发现问题—调研分析—解决问题—沉淀方法</u>** 的工作习惯，不再只满足于完成需求。
- 前端增量覆盖率测试原来需要约 3 PD，通过覆盖率数据、浏览器自动化和网络 Mock 组合成 Skill 后，材料记录中一次需求可在约 4 小时内完成。
- 处理评审评论和 Agent 执行不稳定问题时，也沿用同样方法，把一次性解决方案沉淀成可复用的流程和规范。
- 这套习惯也延伸到业务理解：发现技术痛点之外，还要识别业务链路中真正值得解决的问题。

#### <u>2. 和正式员工相比，你有哪些不足，如何改进？</u>

- 对内部工具的理解仍偏使用层，对原理和能力边界掌握不深，容易在工具选型时增加试错。
- 浏览器自动化方案选型中，最初没有理解 vmok 的资源替换能力，尝试了稳定性较差的其他方案，后来才发现内置浏览器可以复用真实环境和本地代码。
- 对团队业务目标和阶段重点理解还不够深入，需求分析时容易更关注技术实现而忽略业务价值。
- 改进方式是系统阅读内部资料，并主动向产品、运营和有经验的研发了解 **<u>业务目标、工具原理和选型依据</u>**，再通过真实项目验证。

#### <u>3. 这段实习经历让你的工程思维发生了什么变化？</u>

- 从“功能做完”转向 **<u>高质量交付</u>**，同时考虑业务价值、安全性、可维护性和存量影响。
- 从零散实现转向流程化交付，按照需求分析、评审、规划、编码、验收和 CI/CD 管理质量。
- 从被动提问转向带着分析和方案参与讨论，提高沟通效率和决策质量。
- 对结果负责，主动管理进度、风险、依赖、预计交付时间和异常情况下的备选方案。

#### <u>4. 如果让你负责一项工作，你会如何推进？</u>

- 先明确业务背景、问题范围、目标和成功指标，确认这项工作值得推进。
- 拉齐相关角色对目标、优先级和责任边界的理解。
- 设计能够验证价值的最小方案，拆出任务、Owner、时间节点和依赖关系。
- 执行过程中持续跟踪进度、阻塞和风险，必要时调整方案并及时同步。
- 完成后用既定指标复盘结果，判断问题是否真正解决，并沉淀可以复用的经验。

#### <u>5. 线上出现 Bug 时应该怎么处理？</u>

- 第一目标是 **<u>控制影响</u>**。影响范围大或仍在扩散时，先回退稳定版本、关闭开关或隔离问题链路。
- 保存用户操作、前端报错、请求响应、服务端日志、数据状态、版本和配置等现场证据。
- 明确影响用户、功能和时间范围，再安排定位、修复、验证和对外同步。
- 修复上线后继续观察监控和错误率，并补充 Test Case、告警或回归测试，形成闭环。

#### <u>6. 如何定位线上 Bug 的根因？</u>

- 按时间顺序串起 **<u>用户操作 → 前端状态 → 请求 → 服务端处理 → 响应 → 页面结果</u>**，找到实际行为第一次偏离预期的位置。
- 根据第一个异常点提出假设：可能来自用户路径、前端状态、请求参数、网络、服务负载、数据、配置或浏览器环境。
- 用正常与异常用户、PPE 与线上、低负载与高负载等对照缩小范围，每次尽量只改变一个变量。
- 网络问题关注 502、503、504、Timeout 和 Connection Reset；并发问题要验证 QPS、资源使用率、P99、超时和错误率是否同步变化。
- 通过最小复现或对照实验验证假设，形成 **<u>现象—异常点—假设—证据—根因</u>** 的完整链路。

## 2. 当前业务方向和未来规划

### 【业务方向】

当前团队的业务方向是**<u>运营平台的建设</u>**，主要服务于作者运营和内容运营。**<u>核心目标</u>**是希望通过运营工具帮助作者成长、实现等级跃迁，从而提升优质作者的数量，最终改善整个联盟的GMV和生态健康。

运营平台主要面向运营同学，它的核心作用，是把运营动作沉淀为线上的平台工具。运营同学可以直接通过平台，将原本大量依赖人工执行的工作线上化、规模化，让运营动作变得可配置、可追踪，从而提升整体运营效率，扩大运营服务的范围和规模。

比如，运营平台中的作者达人库，可以帮助运营查询每一个作者的经营数据，并基于这些数据进行整体分析，是作者运营的基础能力。达人触达模块，则可以把运营制定的经营策略和任务，通过系统批量触达给作者达人。除此之外，还包括视频查询、内容活动分发、达人拜访等不同模块。这些模块的目的，本质上都是帮助运营同学提升效率，并辅助业务运营。

而**<u>团队未来的规划</u>**，是希望进一步把 AI 能力接入运营平台。对于运营流程中一些比较复杂、存在较强不确定性的任务节点，希望能够由 AI 结合上下文、综合多元数据进行理解、分析和决策，从而解决传统系统难以处理的一些业务痛点，同时进一步提升运营效率。

### 【当前业务的痛点是什么？】

**<u>首先是作者运营。</u>**

作者运营主要是希望通过对作者的经营数据进行分析和诊断，给出相应的经营策略，再通过系统把任务和策略触达给达人。达人领取任务以后，根据这些策略调整自己的经营方式，从而改善经营和交易表现，实现进一步成长和等级跃迁。

作者运营目前主要分为两种模式。第一种是针对 KA 作者采取精细化运营，也就是一对一的运营方式；第二种是针对 S0 到 S3 这类中腰部和长尾作者进行规模化运营，通过人群分层、BPO、RPA 等方式，实现批量管理、触达以及经营策略的下发。

当前作者运营面临的一个明显问题，是**<u>整个作者生态呈现比较明显的钉子结构</u>**，也就是 S0 到 S3 这部分中腰部和长尾作者规模非常大。尤其是 S0、S2、S3 这几个等级，S0 想要实现等级跃迁十分困难。而 S4、S5 等高等级作者的数量又在不断下降，最终导致大量作者集中在 S0，S2，S3这几个等级。

另一方面，从当前的经营数据来看，S0 到 S3 这部分作者的达人供给量其实是比较充足的，也就是说，他们的活跃度并不低，但是交易表现却比较差。这意味着这些作者虽然在持续经营，但最终并没有获得很好的交易表现和转化效果。简单来说，就是作者投入了很多精力，但是没有获得相应的经营回报。

这也说明，我们当前给出的经营策略可能还存在一定的问题。

**<u>第二个方向是内容运营。</u>**

内容运营主要负责维护整个内容生态的健康。它的核心目标，是增加优质内容的供给，减少低质和违规内容，同时让真正优质的内容能够获得更多曝光和交易价值。

整个内容运营过程，内容运营通常可以归纳为四项工作。

**第一是制定标准**。需要明确什么样的内容属于优质内容，通过一系列内容标准去引导作者，让作者按照平台所希望的方向产出更加优质的内容。

**第二是做激励**。通过流量、佣金以及活动奖励等方式，对能够持续产出优质内容的作者进行激励，让他们有动力继续生产更高质量的内容。

**第三是做治理**。对于低劣、违规、庸俗、虚假宣传等问题内容，需要能够及时识别、处理和封禁，避免这部分内容对平台生态造成影响。

**第四是做诊断**。需要判断一条内容为什么表现不好，以及应该从哪些方向进行改进，进而帮助作者提升内容创作质量。

所以，内容运营最终希望解决的问题，就是让平台能够持续产生更多优质内容。从最终目标来看，内容运营和作者运营其实是一致的，都是希望通过改善作者的经营和内容表现，从而帮助作者成长并实现等级跃迁。

**<u>但是当前内容运营同样存在几个明显的痛点。</u>**

第一个问题是，什么才是真正的优质内容，这个标准本身需要持续调整和校准。有些内容从现有标准来看属于优质内容，但是最终的交易表现可能并不好。这说明单一规则很难覆盖所有内容形态，也很难用一套标准适配所有行业，所以优质内容标准本身需要持续迭代。

第二个问题是，内容治理不一定能够做到足够及时。一些低质量内容可能通过一定的包装方式伪装成正常作品，从而绕过系统现有的检查机制，并获得流量分发，最终导致低质量内容被大量传播。

### 【接入Agent能力】

所以，我们希望通过接入 Agent 能力，来解决当前业务中的部分痛点。

Agent 的价值在于，它可以基于多元数据进行综合理解和推理，处理一些存在不确定性的复杂任务，从而突破传统规则系统的一些局限。

**<u>其中一个比较重要的业务方向，就是运营 Agent。</u>**我们希望通过接入 Agent 能力，提高经营策略的质量。

当前规模化运营的业务模式，因为运营不可能对大规模作者全部进行一对一诊断，所以通常只能圈选一批具有相似问题的达人，对他们进行统一分析，形成一套相对标准化的经营策略，再通过 BPO 等方式批量触达给作者。

但前面也提到，目前规模化运营中的部分作者即使领取并执行了任务，最终交易表现仍然比较低，这说明当前**<u>经营策略本身也存在质量不够高的问题</u>**。

而这种基于一类人群生成一套相对标准化经营策略的方式，本身就可能是导致策略质量不高的原因之一。因为同一类作者虽然表面问题相似，但每个作者实际的经营情况可能都不一样。

所以运营 Agent 希望解决的问题，就是让 Agent 自主获取每个作者的经营数据，对作者进行更加个性化的诊断分析，并**<u>针对这个作者生成个性化的经营策略</u>**，再把策略触达给作者达人。

在策略执行之后，运营 Agent 还能够自主回收作者反馈以及后续交易表现数据，进一步判断当前策略是否真正生效。

对于效果比较好的经营策略，可以**<u>进一步沉淀到知识库中</u>**，供后续运营人员以及 Agent 继续复用；而对于效果比较差的策略，则可以作为 bad case 沉淀下来，作为后续优化 Agent 能力的重要依据。

这样就能够逐渐形成从诊断、策略生成、任务触达，到结果回收、效果评估，再到经验沉淀的一套闭环。

在**<u>内容运营上，同样可以应用类似的 Agent 能力。</u>**

比如内容诊断，可以综合内容本身的表现、作者特征等多方面数据，对一条内容进行分析，回答为什么这条内容质量或者表现不够好，并进一步给出具体的内容改进策略。

这样就可以帮助作者更加明确地知道，下一步应该从哪些方向调整自己的内容创作方式和思路，从而持续产出更加优质的内容。

所以，在实际业务中，我们**<u>判断一个业务节点是否应该接入 Agent 能力</u>**，我认为需要从三个方面考虑。

**<u>第一个方面是业务价值。</u>**

接入 Agent 之后，首先要判断它是否真的能够产生业务价值。这个价值通常体现在两个方向。**一种是提效**，比如降低人工成本、扩大运营覆盖范围，让原本只能服务少量作者的能力可以规模化覆盖更多作者。**另一种是解决传统方案无法解决的问题**。比如传统规则系统只能处理相对确定的问题，而 Agent 可以通过多元信息理解和推理，处理一些更加复杂、更加动态的问题，从而解决现有方案的业务痛点。

**<u>第二个方面是 Agent 的必要性。</u>**

也就是说，这个问题是不是真的需要 Agent。

如果一个问题本身规则非常明确，流程也是固定的，通过普通系统、工作流或者确定性脚本就能够完成，那就没有必要为了使用 Agent 而引入 Agent。

比如任务触达，本身就是一个非常确定性的流程。运营配置任务以后，通过现有任务触达模块直接批量下发给作者，就能够很好地解决这个问题。这类能力并不需要 Agent，同样能够达到提效的目的。

所以只有当一个任务真正需要综合多元信息进行理解，需要模型进行推理，并且需要根据不同上下文进行动态决策时，才更适合接入 Agent。

**<u>第三个方面是指标能不能形成闭环。</u>**

也就是说，在建设 Agent 之前，就要明确有没有相应的数据指标，能够证明 Agent 到底有没有提升效率，或者有没有真正改善业务结果。

这里可以分成两类指标。

第一类是 Agent 自身能力的指标，也就是 Agent 能不能把任务做好。比如任务完成度、安全性、稳定性，以及整体的成本和效率。

第二类是最终业务结果指标，也就是 Agent 介入以后，业务结果是不是真的有所改善。

比如作者跃迁率、跃迁人数、优质作者数量、有效运营作者数有没有提升；进一步来看，还可以关注作者对经营任务的采纳率、任务领取率以及任务完成率有没有改善。

这些指标共同帮助我们判断，Agent 的介入究竟只是完成了一个技术能力的建设，还是确实对最终业务产生了实际价值。

### 【核心指标】

最后再看作者运营和内容运营本身的核心指标。

对于作者运营，第一个维度是**<u>作者规模</u>**。

这里最核心的指标是**优质作者数量**。因为优质作者规模会直接影响后续联盟平台的交易表现，同时也会影响整个联盟作者生态的健康程度。

第二个维度是**<u>作者成长</u>**。

这里比较核心的指标是**作者跃迁数和作者跃迁率**，也就是在一个周期内，有多少作者能够从低等级跃迁到更高等级，以及它在整体作者中的占比。

这个指标能够比较直接地反映，在当前周期内我们采取的运营手段，是否真正帮助作者实现了成长。同时，通过和上一个周期的跃迁率进行比较，也可以判断这一周期内运营方案的调整有没有取得更好的效果。

第三个维度是**<u>规模化运营效果</u>**。

这里主要关注**有效运营作者数**。因为有效运营作者数能够衡量规模化运营到底覆盖了多少作者，以及这些运营动作能不能真正帮助一批作者实现成长和等级跃迁。

第四个维度是**<u>作者活跃度和留存</u>**。

比如**月活作者数、有效运营月活作者数、作者留存率等指标**，可以帮助我们判断当前的运营策略，能否让作者持续保持比较高的经营活跃度。

对于内容运营，第一个维度是**<u>内容质量</u>**。

主要包**括优质内容数量、优质内容占比，以及优质内容的视频播放表现**等指标，用来判断平台能不能持续产生更多优质内容，同时减少低质量内容的供给。

第二个维度是**<u>内容分发</u>**。

这里主要关注**内容的曝光和播放情况**，用来判断真正优质的内容能不能被用户看到，能不能获得足够的真实曝光和消费。

第三个维度是**<u>内容转化</u>**。

主要关注内容 GMV、内容 GPM 等指标，用来判断一条内容最终能不能真正产生交易价值。

所以无论是作者运营还是内容运营，最终的目标其实都是一致的通过作者和内容经营质量的提升，最终提升整个联盟平台的全域成交价值，同时保证整个联盟生态能够长期、健康地发展。

### 【相关问题】

#### <u>1. 运营平台在联盟业务中扮演什么角色？</u>

- 联盟连接商家和达人，业务涉及作者、商家、撮合、内容、基础设施和运营平台等方向。
- 运营平台不是独立业务终点，而是为作者运营、内容运营等具体业务提供数据、任务、触达和管理工具。
- 平台把运营动作线上化、规模化，Agent 再调用这些能力处理诊断、策略生成等复杂任务。
- 演进方向是 **<u>平台提供数据与执行，Agent 提供理解与决策</u>**。

#### <u>2. 产品和运营有什么区别？</u>

- 产品主要通过系统功能解决问题，需要把业务目标转成可持续的产品流程和能力。
- 运营通过内容、活动、用户触达和策略动作推动业务指标。
- 两者目标可能一致，但手段不同；运营提出策略后，涉及系统承接的部分仍需要产品和研发落地。
- 可以概括为：**<u>运营决定用什么策略推动业务，产品把策略转成可复用的系统能力</u>**。

## 3. 头达数据权限分级管控

如果让我理解当前的软件工程化设计，我会认为它的核心目的，是**<u>把一个最开始比较模糊的业务需求，通过一套稳定的工程流程，逐步转换成明确的需求、技术方案、可执行任务、经过验证，最后能够安全、完整地交付到生产环境</u>**。

传统软件工程中的 SDLC（Software Development Life Cycle，软件开发生命周期）体现的就是这种思想。软件开发并不是一次简单的“需求到编码”的活动，而是由多个相互衔接的阶段共同完成。每一个阶段都有自己的目标和交付物，同时又为下一个阶段提供输入。

这样做的价值，是让产品、研发、测试等不同角色能够围绕同一个目标、同一套规范和同一套阶段产物协作完成复杂任务，而不是依赖个人理解和临时沟通。

到了 AI Native 环境以后，这套工程体系并没有消失，反而变得更加重要。

现在 AI 已经逐渐从 Coding Assistant（编码辅助工具）变成整个研发流程中的执行者，可以参与需求分析、技术规划、代码实现、测试、Review 和交付。因此，工程化设计需要解决的问题，也从单纯的“人和人如何协作”，进一步变成：

> **如何让人和 AI / Agent 在同一套工程规则下共同完成复杂任务，并且在 AI 高速执行的情况下，仍然保证需求不跑偏、任务可追踪、结果可验证、风险可控制。**

AWS 在 AI-DLC（AI-Driven Development Life Cycle，AI 驱动开发生命周期）中把这种关系概括成“AI 执行、人工监督”。也就是说，大量分析和执行工作可以交给 AI，但是关键判断、高风险节点和最终放行仍然由人负责。

### 【四条主线】

基于这个目标，我认为 AI Native 下的软件工程化可以通过四条主线来贯穿整个研发流程：规范、验证、可追溯和风险控制。

#### **<u>第一，规范驱动</u>**

第一条原则是规范先行。

AI 要稳定执行任务，前提是我们要先把过去依赖产品、研发个人理解的隐式信息，转换成明确的工程规范。

这和 SDD（Spec-Driven Development，规范驱动开发）的思想是一致的：在真正开始编码之前，先形成明确的 Spec（规范），然后再形成 Plan（计划）、Tasks（任务），最后进入 Implementation（实现）。

因此，在需求分析和技术分析阶段，需要提前沉淀需求规范、技术方案、接口协议、Test Case、代码规范和实现计划等结构化产物。

这些产物不只是留档，它们本身就是后续 AI 执行任务的依据。

也就是说，要尽量形成：

> **业务目标 → 需求规范 → 验收标准 → 技术方案 → 实现计划 → Task → Code**

这样可以减少 AI 在每一个阶段重新理解需求、自由猜测或者扩大修改范围的问题。

#### **<u>第二，验证前置</u>**

第二条原则是验证前置。

不能等代码已经生成以后，才重新讨论“这个需求应该怎么测试”。

因为如果测试项根据已经生成的代码反向设计，就可能出现一种风险：AI 一开始对需求理解错了，按照错误理解写了代码，又根据错误代码生成测试，最后测试仍然全部通过。

所以测试标准应该来源于需求规范，而不是来源于代码实现。

这和 ATDD（Acceptance Test-Driven Development，验收测试驱动开发）的思想一致：在功能实现之前，产品、研发、测试就应该共同明确什么情况下可以认为需求已经完成。

在我们的工程体系中，可以进一步采用“规范驱动测试”的思路，把 Requirement（需求）逐渐转换成 Scenario（场景）和 Test Case（测试用例），建立需求与测试项之间的映射关系，并覆盖正常场景、异常场景和重要边界条件。

因此，在技术评审阶段需要形成一套完整的 Test Case Matrix（测试用例矩阵），并由产品、研发和测试共同确认。

在整个 AI Coding 工作流中，我认为 Test Case 是最重要的质量产物之一。

一方面，它是后续 AI 自动验收的标准，它的完整性和准确性直接决定最终验收质量；另一方面，它也是检查前面需求分析和技术规划是否存在理解偏差的重要手段。

如果一个 Test Case 的预期结果说不清楚，或者不同角色对同一个 Case 的预期存在分歧，就说明前面的需求本身还没有真正对齐。

#### **<u>第三，可追溯</u>**

第三条原则是可追溯。

一个完整需求实际上可以看成一个 Long-running Task（长任务），它会跨多个阶段，也可能跨多个 Agent 和多个 Session 执行。

因此不能只保存最后的代码，而需要持续沉淀结构化工程产物，把整个过程连接起来。

例如建立：

> **Requirement → Scenario → Test Case → Technical Plan → Task → Code Change → Test Result → Release**

这样的关系。

它首先解决的是人工审查问题。人工不可能重新执行 Agent 完成的所有工作，而是需要根据需求、技术方案、代码 Diff、测试结果和验收证据判断当前结论是否可信。

**同时，它也是 Agent 执行长任务的重要基础。**

一个大需求应该提前拆成多个相对独立、具有明确目标和完成标准的任务。每个任务执行完成以后，都应该留下任务状态、代码修改、测试结果等结构化产物。

这样即使 Agent 因为上下文限制、工具异常或者环境问题中断，也能够根据已有产物快速恢复到之前的稳定状态，从未完成的位置继续执行，而不是重新执行整个需求。

因此，可追溯真正解决的是：

> **任务能够持续推进，中断以后能够恢复，结果能够审查，需求变化以后能够继续演进。**

**<u>第四，风险控制</u>**

第四条原则是风险控制。

AI Native 并不意味着所有研发节点都应该完全自动化。

AI 本身仍然具有不确定性，因此自动化程度不能只看“AI 能不能做”，还要看当前任务的风险、确定性和结果是否容易验证。

规则明确、风险较低、结果容易判断的任务，可以更多交给 AI 自动执行。

但对于需求歧义、安全权限、全局状态、公共能力、核心业务链路、大范围架构变化以及最终生产发布等高风险节点，需要引入 Human-in-the-Loop（人在回路），也就是由人工进行判断、确认或者放行。

### 【五个阶段】

所以在 AI Native 的工程体系中，人的角色会逐渐从大量执行工作，转变成规范制定、关键判断、风险审查和最终质量负责。

#### **<u>第一阶段：需求分析</u>**

需求分析主要解决三个问题：

> **为什么做、做什么、什么算完成。**

首先需要根据当前的业务目标和业务问题来设计需求。

要先判断当前真正存在的问题是什么、这个问题影响谁、为什么值得解决，以及解决以后能够带来什么业务价值。

然后再把问题拆解成具体需求点，明确系统需要支持哪些能力、有哪些业务规则、哪些边界场景需要考虑，以及本次需求的范围和非范围。

如果需求涉及页面，还需要进一步完成 UI / UX 设计。

在当前 AI Coding 环境下，设计稿已经不只是给人看的交互参考，也逐渐成为 AI 的结构化输入。像 Figma 这样的设计工具可以让 Agent 直接读取布局、组件、设计变量等结构化信息，相比单纯依赖截图和自然语言，更容易保持页面结构和设计意图的一致性。

因此，对于前端需求来说，结构化设计稿是后续代码实现和视觉验收的重要依据。

完成需求设计以后，还需要进行需求评审。

需求评审主要解决三个问题：第一，当前需求方案是否真的能够解决最开始定义的问题；第二，根据现有系统、代码、接口和资源条件，这个需求是否能够落地，如果范围过大是否需要划分优先级或者一期、二期；第三，当前需求是否已经能够转换成明确的验收标准和测试场景。

需求分析最终不是简单产生一份 PRD，而是要让产品、研发、测试以及必要的安全、风控角色对：

> **为什么做、最终做什么、什么情况下算完成**

形成共同理解。

#### **<u>第二阶段：技术分析</u>**

如果需求分析解决的是“做什么”，那么技术分析解决的是：

> **怎么做，以及后续怎么证明实现正确。**

如果是一个从零开始的新项目，首先需要进行项目初始化和规范设计。

包括技术框架和工具链选型、项目目录结构，以及 ESLint、Prettier、Git Hooks、commitlint、Type Check、CI 等工程规则。

这些规范的作用，是让后面无论代码由人还是 AI 生成，都必须遵循同一套工程质量要求。

之后进入技术设计。

对于已有项目，需要先分析存量系统，明确当前模块在哪里、数据从哪里来、涉及哪些接口、公共组件和页面，哪些能力能够复用，以及本次需求真正需要修改哪些代码。

在此基础上形成技术方案，包括接口协议、数据流、状态管理、公共能力设计以及安全、性能和兼容性等约束。

技术设计完成以后，需要进一步形成两个非常关键的产物。

第一个是 Implementation Plan（实现计划）。

把整个需求拆成多个可以独立执行和验证的 Task，并为每个 Task 明确目标、修改范围、输入、输出和完成标准。后续 AI Coding 就按照这个计划逐项执行，而不是一次性完成整个需求。

第二个是 Test Case。

Test Case 是后续测试验收的直接标准，同时也用来反向验证前面的需求分析和技术设计是否正确。

因此，在技术评审阶段，一方面需要前后端和相关研发角色对技术方案、接口和影响范围形成共识；另一方面需要产品、研发、测试共同检查 Test Case 的完整性和准确性。

只有当大家既统一“怎么实现”，又统一“怎么证明实现正确”，才能进入代码开发阶段。

#### **<u>第三阶段：代码开发</u>**

进入代码开发以后，主要执行者可以逐渐变成 AI。

这里不建议让 AI 一次完成整个需求，而是按照前面已经拆好的 Task 小批量推进：

> **Task → Implement → Test → Review → 下一个 Task**

每完成一个 Task，就应该立即执行对应的静态检查、类型检查、Unit Test（单元测试）和 Integration Test（集成测试），而不是整个需求全部完成以后才统一测试。

同时 AI 需要主动执行第一轮 Code Review。

首先通过 Git Diff 判断代码修改是否都有需求依据，是否出现需求范围之外的改动，避免为了实现局部功能破坏存量逻辑。

然后进一步检查是否存在重复代码、无用参数、无用函数、不必要的依赖、过度设计，以及安全、性能和公共能力方面的潜在风险。

对于明确的问题，AI 可以自动修改并重新测试。

人工在代码阶段主要关注高风险变更，例如全局状态、核心业务逻辑、权限、安全、公共组件、公共方法以及大范围重构，因为这些修改可能影响多个页面或者已有功能。

所以这一阶段的核心不是“AI 能不能把代码写出来”，而是：

> **AI 是否能够按照已经确定的规范和 Task 小批量实现，并持续证明每一步修改都是必要、正确和可控的。**

#### **<u>第四阶段：测试验收</u>**

测试验收阶段解决的核心问题是：

> **如何证明当前代码真的满足前面已经确定的需求。**

首先是功能验收。

按照技术分析阶段已经确定的 Test Case，基于前置条件和预期结果逐项验证功能。

传统自动化测试通常提前写死测试步骤和输入；现在也可以通过 Browser Agent（浏览器智能体），只提供 Test Case 的前置条件和预期结果，由 AI 根据页面当前状态自主判断下一步如何操作。

也就是说：

> **AI 可以自主决定“怎么验”，但是不能自己决定“什么算正确”。**

验收标准仍然必须来自前面已经确定的 Test Case。

第二部分是覆盖率检查。

一方面检查 Requirement Coverage（需求覆盖率），确认所有重要需求场景和边界条件都有对应 Test Case。

另一方面检查 Code Coverage（代码覆盖率），判断重要的代码行、函数和分支是否真正被执行过。

如果某些代码分支在正常、异常和测试场景中始终无法进入，就需要进一步判断到底是测试遗漏，还是代码本身已经不可达或者属于冗余逻辑。

第三部分是代码质量检查。

AI 可以基于团队沉淀的代码规范、安全规范、架构规范和知识库，对当前代码从安全性、可维护性、可扩展性、兼容性等角度进行 Review，并自动修复明确的问题。

最后是 Quality Gate（质量门禁）。

AI 自动化验收最关键的问题，不是 AI 能不能把页面操作完，而是：

> **怎么证明 AI 给出的验收结论可信。**

所以每一个 Test Case 都不能只留下 PASS，而应该建立：

> **Test Case → Expected Result → Actual Result → Evidence → Pass / Fail**

Evidence 可以包括截图、接口请求、日志、DOM 状态、Mock 命中记录以及操作轨迹。

最终需要检查 Test Case 是否全部执行、实际结果是否符合预期、证据是否充分、执行过程和最终结论是否一致。

对于高风险需求，最终质量门禁仍然需要人工审查和放行。

所以整个测试验收阶段最关键的一句话是：

> **AI 可以负责执行验收，但验收是否可信，必须由预先确定的 Test Case、完整证据链和独立质量门禁共同证明。**

#### **<u>第五阶段：交付上线</u>**

测试验收通过以后，最后进入交付上线阶段。

首先通过 CI/CD 的自动化门禁执行 Build、Test、安全检查、Review 等流程，保证只有满足要求的代码才能进入正式发布。

之后形成明确的 Release（发布版本），再经过回归测试、发布前验证以及必要的小流量或灰度验证。

对于高风险需求，可以先发布给少量用户，观察错误率、接口异常、核心业务指标等情况，再逐步扩大流量；出现异常时及时停止或者回滚。

最终上线以后，还要回到需求分析阶段最开始定义的业务目标和成功指标。

因为：

> **代码成功上线，只能证明 Delivery Success（交付成功），并不能证明 Business Success（业务成功）。**

最终还要通过线上数据判断：

> 最开始定义的问题是不是真的被解决了。

因此整个研发过程最终形成一个闭环：

> **业务问题 → 需求分析 → 技术分析 → 代码开发 → 测试验收 → 交付上线 → 数据反馈 → 下一轮需求。**

------

整体来看，我理解的 AI Native 软件工程化，不是简单地把原来的研发流程全部交给 AI，而是：

> 通过规范、验证、可追溯和风险控制四条主线，重新设计人和 Agent 的协作方式。AI 承担越来越多分析、开发、测试和修复工作，人则重点负责目标定义、规范确认、风险判断和最终质量放行，再通过需求分析、技术分析、代码开发、测试验收和交付上线五个阶段，把一个业务问题稳定地转换成可以安全交付的软件。

### 【相关问题】

#### <u>1. 已有数据权限后，为什么还要通过“小眼睛”确认查看？</u>

- “小眼睛”把查看敏感数据变成一次明确操作，并记录谁在什么时间查看了哪些数据，实现 **<u>访问可追溯、可回溯、可审计</u>**。
- 数据泄露或异常访问发生后，可以利用审计记录缩小排查范围。
- 访问频率等审计数据也可以作为后续异常检测依据，但材料中未说明该自动预警能力已经上线。

#### <u>2. 头达权限项目中最大的工程挑战和能力提升是什么？</u>

- 最大挑战是在 **<u>尽量不破坏存量代码</u>** 的前提下接入统一权限管控，同时兼容现有功能并复用已有能力。
- 开发前先梳理存量实现、依赖关系和全局能力，再通过抽象、封装和最小改动接入新能力，减少大范围重构带来的回归风险。
- 这次项目让我形成了在存量系统约束下进行 **<u>兼容式演进</u>** 的工程思路。

## 4. AI Coding 工作流

### 【相关问题】

#### <u>1. AI Coding 中最容易被低估但风险最大的环节是什么？</u>

- 最容易被低估的环节是 **<u>Test Case 的构建与验收</u>**。没有可执行、结构化的 Test Case，后续自动审查和验收就缺少统一标准。
- Test Case 的准确性和完整性可以暴露需求分析、任务规划中的理解偏差，避免问题进入代码实现后造成大量返工。
- 每个验收项都要与需求、执行结果和证据对应，才能证明需求覆盖完整、验收结论可信。
- 根据内部统计，代码生成只占开发时间的 **<u>百分之十几</u>**，需求澄清和 Test Case 构建约占 **<u>57%</u>**，其余三成多用于执行 Test Case 和验收。

#### <u>2. 某个子任务执行失败时，如何保证系统可恢复？</u>

- 系统通过 **<u>状态管理和持久化产物</u>** 判断当前子任务执行到哪一步、哪些步骤已经完成。
- 恢复时重新读取需求、计划、代码和测试结果等产物，从最近的有效状态继续，考虑**<u>幂等性</u>**。
- 先用有限重试处理网络、环境或 Tool 临时异常；重试无效后再根据日志和产物定位当前阶段或前置阶段的问题。
- Gate 记录失败原因并作为后续输入；回溯修复仍失败或风险较高时，再引入人工。

#### <u>3.  如何判断一个系统到底是单 Agent 还是多 Agent？</u>

- 判断标准是系统中有几个 **<u>独立决策单位</u>**，而不是 Workflow 中有多少阶段或 Tool。
- 如果不同阶段都由同一个 Agent 推理决策，只是动态加载不同工具和 Skill，它仍然是单 Agent。
- 如果每个阶段分别由独立 Agent 负责，并能互不影响地运行或独立演进，就是多 Agent。

#### <u>4. 什么时候才真正需要使用多 Agent？</u>

- 需要执行和审查并行、上下文相互隔离时，适合拆成不同 Agent。
- 某些阶段需要专门的工具组合、提示、状态或评测体系，并且要长期独立优化时，适合构建专用 Agent。
- 判断重点是 **<u>独立运行、职责隔离和独立演进</u>**，不是阶段数量。

#### <u>5. 多个子任务之间如何保证正确衔接？</u>

- 子任务之间通过 **<u>输入输出契约</u>** 和 **<u>持久化产物</u>** 传递信息，避免只依赖临时对话上下文。
- Gate 根据契约检查上游输出，阻止错误或不完整结果继续传播。
- Orchestrator 根据结构化状态完成阶段调度，明确每个子任务使用的产物版本和执行状态。

#### **<u>6. Agent、Workflow 和传统自动化系统如何划分边界？</u>**

- 传统脚本、API 和规则适合输入输出明确、动作确定的单点任务。
- Workflow 适合阶段稳定、状态转移可以提前定义的业务流程，负责流程编排和任务调度。
- Agent 适合输入复杂、环境变化、路径难以枚举且需要动态理解和判断的任务。
- 三者通常组合使用：**<u>传统系统执行确定动作，Workflow 管理确定流程，Agent 处理不确定决策</u>**。

#### <u>7. 如何设计 Agent 的记忆系统？</u>

- 短期记忆服务当前任务，保存执行状态、已完成步骤和近期 Tool 结果，用于保持连续性和恢复任务。
- 长期记忆跨任务、跨会话保存仍有复用价值的信息，例如用户偏好、稳定经验和历史解决方案。
- Context 是一次模型调用的输入集合，除 Memory 外还包括 Prompt、知识库、当前状态和 Tool 结果；Memory 只是 Context 的来源之一。
- 记忆不能无限积累，需要筛选高价值内容、清理过期信息、处理冲突并记录来源。
- 记忆访问同样受权限控制，避免跨用户或跨职责泄露信息。
