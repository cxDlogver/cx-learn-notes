.trae Delivery Harness

Trae AI 工作流架构

一套面向真实需求交付的 AI 协作流水线：自动收集 Meego、PRD、Figma、BAM、业务仓库和浏览器运行态证据，再通过主 Agent 编排多个 Subagent 完成规划、实现、功能验证、视觉验证、设计对齐和交付验收；后续可由开发机 WebServer 和飞书机器人包装成产研测协作入口。

一句话理解：它把“AI 写代码”升级成“AI 交付需求”，用状态机管理阶段，用产物记录事实，用 Subagent 分工处理复杂上下文，再用 Gate 和互审机制防止跑偏。

Why

解决什么问题

避免一个大 Agent 靠聊天记忆硬推完整需求，导致需求事实丢失、实现越界、验证缺口和设计返工无法追踪。

How

怎么完成交付

从需求入口开始，按 PRD、BAM、Plan、Task、Code、Verify、Design、Accept 串行推进；也可由飞书机器人触发 init、走查修复、CR 修复和 PPE 部署。

Guardrail

如何防止偏移

写代码、跑命令、做设计检查和最终放行分属不同角色；主 Agent 汇总证据，独立审查 diff 与合同。

使用场景：飞书机器人驱动交付

这套流程会部署在开发机上，由常驻 WebServer 统一调用 CoCo CLI；ByteClow 上的飞书机器人作为产研测入口，与 WebServer 通讯，把群聊里的需求、走查问题、CR 问题和流程问题调试转成可审计的 `.trae` 阶段动作。

参与方主链路

飞书需求群 产研测发起需求、走查问题、CR 修复和回归请求。
消息事件@机器人 / 指令 / 附件
ByteClow Bot 接收消息、鉴权、解析意图，并把上下文转发给 WebServer。
HTTP 回调user + group + command
开发机 WebServer 维护任务队列、workspace 锁、执行状态和回调通道。
本机调度queue + lock + env
CoCo CLI 在开发机执行 `.trae` command，并把过程写入 artifacts。
阶段写入artifacts + code + PPE

状态回调summary + links + blockers
飞书回写 阶段摘要、阻塞问题、PPE 链接、MR 状态和下一步确认。
顺序规则 同一需求按 workspace 串行执行；新的飞书指令先进入队列，不能抢占未关闭的阶段 Gate。
锁定规则 WebServer 对 repo、branch、workspace 加锁，避免两个群消息同时改同一套代码或产物。
回调规则 长任务先回 ACK，再按 phase_start、gate_result、blocked、done 回写阶段摘要和链接。
安全规则 飞书只传指令和摘要；token、cookie、storage state、原始请求响应不进入群消息。

需求启动：从群聊拉起 `/delivery:init`

目标是把 PRD、Meego、设计资料和目标仓库上下文落成可恢复的 `.trae` workspace。

  1. 01
    用户把机器人拉入需求群，并发送 PRD / Meego / 需求描述 机器人只收集启动所需上下文，不直接进入实现。
    飞书群→ByteClow Bot
  2. 02
    Bot 解析意图为 init 请求，并携带用户、群、文档、仓库候选 权限、任务唯一性和参数完整性在 WebServer 侧统一校验。
    ByteClow Bot→WebServer
  3. 03
    WebServer 加锁 workspace，调用 CoCo CLI 执行 `/delivery:init` CoCo CLI 按 `.trae` 规则创建 artifacts workspace，并写入 `00-inputs.md`、`01-intake.md` 和状态指针。
    WebServer→CoCo CLI→.trae workspace
  4. 04
    执行摘要回写飞书，提示下一阶段和阻塞问题 输出 workspace、当前阶段、已拉取资料、缺失输入和建议下一步。
    CoCo CLI→WebServer→飞书群

产品走查修正：从 PPE 问题到自动修复部署

目标是让产品在飞书里描述走查差异后，系统完成受限修复、验证和 PPE 回写。

  1. 01
    产品在飞书发起走查问题 输入可以是 PPE 链接、截图、文案差异、交互问题或期望行为。
    产品→ByteClow Bot
  2. 02
    WebServer 绑定 active workspace 和问题上下文 问题被转成 design / verify / code fix 的受限请求，保留用户原话和证据链接。
    Bot→WebServer→CoCo CLI
  3. 03
    CoCo CLI 执行受限修复和验证 按当前阶段 Gate 选择 `/delivery:design` auto-fix、code handoff 或 verify 复验，不允许绕过 artifacts 与证据闭环。
    CoCo CLI→代码修改→浏览器验证
  4. 04
    验证通过后触发 PPE 部署并回写复查入口 飞书消息包含修复摘要、验证证据、PPE 地址和仍需产品确认的点。
    WebServer→PPE→飞书群

CR 修复闭环：从评审评论到 MR 回写

目标是研发把 CR 评论交给机器人后，系统判断范围、修复、验证，并可按权限回写评审状态。

  1. 01
    研发发送 MR 链接、评论线程或 CodeGuard 报告 机器人解析为 `/delivery:bits --cr` 或受限 code fix 请求。
    研发→ByteClow Bot
  2. 02
    WebServer 拉取评审来源并建立问题池 合并 Codebase Assistant、Aime、CodeGuard 等来源，区分采纳、拒绝、待确认。
    WebServer→Codebase / BITS→CoCo CLI
  3. 03
    CoCo CLI 修复当前需求范围内的问题 每个 accepted issue 都要有需求映射、修改范围、验证命令和 closure 记录。
    CoCo CLI→代码 / 测试→bits-flow
  4. 04
    通过后提交、推送并逐条回写评论 未传 submit 时只生成本地修复和回写草稿；传 submit 后才执行远端回写。
    WebServer→Git / MR→飞书群

测试回归协作：从 case 复验到风险回写

目标是测试通过机器人指定 case 或问题，系统复跑证据链并把结果沉淀回交付 workspace。

  1. 01
    测试在飞书指定 case、页面状态或回归问题 输入会映射到 `09-test-case-matrix.md` 的 case queue 或新增问题记录。
    测试→ByteClow Bot
  2. 02
    WebServer 恢复对应 workspace、PPE / vmok 入口和浏览器状态 必要时要求用户补登录态或 P0 决策，不伪造验证通过。
    WebServer→Execution State→Browser Runtime
  3. 03
    CoCo CLI 复跑 verify / design 或生成受限修复 复验只关闭当前 case；代码问题必须走 handoff，设计问题走 design auto-fix。
    CoCo CLI→Verify / Design→Artifacts
  4. 04
    结果回写飞书并更新风险/执行记录 回写 PASS / BLOCKED / NEEDS_TARGETED_REVIEW、证据路径、截图摘要和下一步责任人。
    Artifacts→WebServer→飞书群

流程问题调试：人工介入后修改流程完成修复

目标是在工作流遇到无法自动判断的问题时，先暂停请求人工确认，再把确认结果沉淀成流程规则、回归用例和验证报告。

  1. 01
    CoCo CLI 在阶段 Gate 中遇到 P0 / 低置信 / 规则冲突 例如接口边界不清、设计证据缺失、自动修复越界、mock 策略不明确或子 Agent 输出自相矛盾。
    CoCo CLI→WebServer→飞书群
  2. 02
    机器人按 Pause and Ask 格式请求人工介入 产研测在飞书里确认业务规则、授权边界、默认处理或是否修改流程；回答会写回 decision-log / uncertainty-register。
    飞书群→ByteClow Bot→WebServer
  3. 03
    若确认是流程问题，进入流程维护路径 主 Agent 使用 trae-flow-maintainer 判断应修改 command、skill、agent、Gate 还是 handoff 合同，并只改权威落点。
    WebServer→CoCo CLI→流程文件
  4. 04
    捕获回归并用最新流程重跑目标阶段 执行 /delivery:capture-regression 记录问题，再按需执行 /delivery:regress；通过后从原 resume point 继续业务需求。
    流程修复→Regression→飞书回写
WebServer 职责 统一处理飞书事件、用户权限、任务排队、workspace 锁、CoCo CLI 调用、PPE 部署触发和执行状态查询。
机器人职责 把自然语言对话转成明确动作，回写阶段摘要、阻塞问题、验证链接、PPE 地址和需要人工确认的 P0。
安全边界 飞书消息只承载指令与摘要；token、cookie、storage state、原始请求响应和敏感日志仍留在开发机或受控产物中。

Execution Bootstrap

/delivery:bam、code、verify、design、accept 进入前先复用执行工作区和项目命令协议，禁止在 main/master 写仓库。

Pause and Ask

任一阶段遇到 P0_BLOCKER 时暂停，更新 Pause State，用户确认后从 resume_command 恢复。

Mock Detour

MOCK_PREVIEW 下 Code 只更新 BAM 矩阵的“补充说明”；delivery-mock.md 仅由 /delivery:mock 写入。

Sample Coverage

非 Mock Preview 仅在 verify / design 的 SAMPLE_COVERAGE_GAP 内允许临时补 mock；case 关闭后必须立即清理。

Auto-fix / Rewind

验证阶段定位为代码问题时生成 handoff 并回到受限 code；阶段产物需回退时使用 /delivery:rewind 保留快照。

新增辅助入口：不替代主线 Gate

这些命令围绕主流程提供任务平台、执行履历、流程回归、阶段回退和日志分析能力。它们可以插入当前 workspace，但不会跳过 PRD、Plan、Task、Verify、Design、Accept 的门禁判断。

/delivery:bits

需求级 BITS 辅助入口，支持 --init 创建或复用开发任务、--cr 处理评审闭环、--coverage 做覆盖率优化；产物统一写入 bits-flow/。

/delivery:record

只读汇总当前需求执行履历，生成 delivery-execution-record.md，串联阶段时间线、关键产物、问题、解决记录和遗留风险。

/delivery:analyze-flow

读取 flow-logs/*.ndjson 做阶段、agent、Gate 和阻塞分布统计，只给出观察和下一步建议，不修改状态或阶段产物。

/delivery:rewind

把当前 workspace 回退到指定阶段前，保留允许继续消费的上游产物，把旧阶段输出移入 _rewind-snapshots，再建议重跑目标阶段。

/delivery:capture-regression

当流程规则被修复时，把原问题、预期行为、影响文件和 replay 成本写入 flow-regression-cases/，默认只捕获不立即重跑。

/delivery:regress

在 shadow replay workspace 中重跑指定阶段或 daily suite，验证流程修复是否真正生效；禁止只检查旧产物后宣称通过。

/delivery:mock

BAM runtime mock 唯一入口。Mock Preview 服务正式预览，Sample Coverage 只服务 verify / design 单 case 补样本，且必须 cleanup。

Flow Log Hook

phase_start、gate_result、detour_start、runtime_event 等事件只观察不决策，敏感信息必须脱敏。

Mock Preview Mode 允许用 BAM runtime mock 推进前端效果预览，但不得写业务代码 mock，也不得标记为真实联调完成。
Sample Coverage Gap 真实 contract 已闭合但样本不足时，verify / design 可临时补充 mock 取证；case 关闭后立即清理。
Browser Runtime Mode 桌面优先 Trae 内置浏览器；CLI / 无桌面使用无头浏览器和 storage state，报告必须记录工具、登录态和 Network 能力。

AI 工作流核心机制

读完主流程、关键闭环和系统分层后，可以把整套系统收敛成下面五个机制：状态恢复、证据落盘、角色边界、互相审核，以及流程自身迭代。

状态机驱动

每个阶段从 DELIVERY_STATE.md 和 workspace 产物恢复上下文，阶段推进由 command / Gate 控制，不依赖聊天上下文里的临时记忆。

证据落盘

PRD、Plan、Task、Code、Verify、Design 和 Accept 的结论都写入 artifacts。后续阶段消费上游产物，而不是重新猜测需求事实。

角色分层

Command 管入口，Skill 管阶段规则，Agent 做受限执行，Script 做确定性检查，主 Agent 做编排和最终 Gate 判断。

Plan / Task 物化 tech-planner 和 task-planner 把需求转成技术合同、Task 和测试矩阵；发现事实漂移时回到上游，不自行改写真相。
Code 受限实现 code-writer 只写当前 Task 或 hotfix 切片，不接管阶段，不处理后续 Task，不自己宣布通过。
运行时辅助 runtime-runner 只做 dev server、health check、HMR、命令和日志摘要；视觉、DOM、截图和 case 判断由主 Agent / design-checker 闭合。
独立审查 普通 code Task 完成后必须只读审查 diff、scope、contract、UI evidence、mock boundary 和 verification freshness。
Main Agent Gate 主 Agent 汇总子 Agent 证据、独立审查、浏览器复核和风险，收敛为 PASS / BLOCKED / NEEDS_TARGETED_REVIEW。
防需求偏移 Task / test 发现 plan 偏移时返回 /delivery:plan，不得把未确认事实直接写成执行任务。
防执行偏移 写代码的人不最终验收；跑命令的人不判业务通过；看设计的人不随手扩大实现范围。
效率来源 通过 Agent Gate Summary、Task Review Packet 和 targeted diff 压缩证据，标准不降级。
浏览器功能验证 通过真实页面点击、输入、Network、DOM 和错误日志确认功能路径闭合。
浏览器视觉验证 通过截图、computed style、区域顺序、直接子元素和关键控件状态验证运行态视觉。
Figma 对齐 Design 阶段用 Figma screenshot / node data 对比浏览器运行态，视觉差异不能只靠 build 或 typecheck 放行。
Execution Bootstrap 执行型阶段统一读取 PROJECT_CONTEXT.md，创建或复用 execution workspace 后再安装、启动、BAM 或写代码。
Browser Runtime Mode TRAE_DESKTOP 和 COCO_CLI_HEADLESS 都必须记录浏览器工具、登录态边界、Network 能力和 vmok URL。
BITS 不抢 Gate /delivery:bits 只维护 bits-flow/ 和评审/覆盖率闭环，不能替代 code、verify、design 或 accept 的放行。

流程自身迭代机制

这套工作流本身也按“观察问题 → 定位规则 → 修改流程 → 捕获回归 → 定期复盘”的方式持续演进。业务需求执行过程中暴露出的偏移、慢点、误判或过严规则，会被沉淀为可追踪的流程改进，而不是只靠一次性的人工记忆修补。

Hook 日志观察 flow-logs/*.ndjson 记录 phase、agent、gate、detour、runtime_event 和 workflow_version，用低成本日志发现耗时、阻塞和反复返工点。
执行记录复盘 /delivery:record 汇总阶段产物、截图、发现的问题、解决动作和遗留风险，形成单个需求的执行档案。
日志分析入口 /delivery:analyze-flow 统计 flow logs 的阶段、agent、Gate 和阻塞分布，只观察流程瓶颈，不改变阶段结论。
规则维护入口 发现流程错误时，用 trae-flow-maintainer 判断应改 command、skill、agent 还是全局 contract，并记录影响范围。
回归用例沉淀 /delivery:capture-regression 把已修流程问题写入 flow-regression-cases/，daily 或 targeted suite 再集中验证。

附录：组件职责

组件 职责 核心输入 / 输出
commands/ 作为用户命令入口，执行前置检查并路由到对应阶段规则。 读取 DELIVERY_STATE.md，输出阶段执行请求。
skills/ 定义每个阶段的输入、步骤、产物、Gate 和回退策略。 消费上游产物，约束 agents / scripts 的执行边界。
agents/ 承担高上下文专业任务，但最终阶段放行由主 Agent 决定。 输出 Agent Gate Summary 与阶段报告。
scripts/ 承接确定性操作：导入、检查、BAM 同步、回退、变更扫描。 输出校验报告、同步结果、workspace 状态。
artifacts/<task>/ 作为跨会话事实中心，所有阶段结论必须落盘。 沉淀 PRD、Plan、Task、Verify、Design、Accept 全链路证据。

附录：架构要点

状态机 DELIVERY_STATE.md 记录当前阶段、workspace、执行分支和暂停恢复点。
门禁 每阶段必须收敛为 PASS、AUTO_FIX_REQUIRED、BLOCKED 或 NEEDS_TARGETED_REVIEW。
浏览器验证 既验证功能路径，也验证运行态视觉；截图、DOM、computed style、Network 和 Figma 对齐证据都属于 Gate 输入。
Mock Preview 运行时 mock 只能由 /delivery:mock 与 BAM runtime 管理，禁止业务代码造数。
执行隔离 写代码、BAM 生成、自动修复等执行型阶段必须复用 Execution State 指定仓库和分支。
辅助流程 /delivery:bits、/delivery:record、/delivery:analyze-flow、/delivery:rewind、/delivery:capture-regression 和 /delivery:regress 只补充治理能力，不替代主线阶段。
可追溯 需求、方案、任务、用例、验证、设计、验收全部通过 artifacts 串联。
