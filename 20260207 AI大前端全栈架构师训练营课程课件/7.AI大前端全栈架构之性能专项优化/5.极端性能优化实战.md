## 相关面试真题


### 在处理计算密集型任务（如大文件加密或复杂数据转换）时，如何避免主线程卡死？请简述基于 Worker 的“零拷贝”通信方案。


**考察点：**

- 事件循环与主线程阻塞机制。
- Web Worker 的基本使用与数据通信开销。
- `Transferable Objects` 与 `SharedArrayBuffer` 的区别与应用场景。
- 多线程同步机制（Atomics）。

**参考解答思路：**

1. **问题分析**：首先说明 JS 单线程特性，计算密集型任务在主线程执行会占用 CPU 时间片，导致渲染流水线（Render Pipeline）中断，产生“掉帧”或“未响应”。解决方案是将计算移至 Web Worker。
2. **通信瓶颈**：指出普通的 `postMessage` 传输大数据（如 100MB 的 ArrayBuffer）默认使用“结构化克隆算法”（Structured Clone），会产生内存拷贝和序列化开销，导致通信延迟。
3. **优化方案 A（转移所有权）**：使用 `Transferable Objects`（如 `postMessage(buffer, [buffer])`）。这会瞬间转移内存所有权，主线程不再能访问该数据，也就是“剪切粘贴”而非“复制粘贴”，速度极快。
4. **优化方案 B（共享内存 - 进阶）**：对于需要频繁读写的场景，使用 `SharedArrayBuffer`。主线程和 Worker 共享同一块内存地址，完全消除拷贝开销。
5. **同步机制**：强调在使用 `SharedArrayBuffer` 时，必须配合 `Atomics` 操作（如 `Atomics.wait` / `Atomics.notify` / `Atomics.add`）来解决多线程并发竞争（Race Condition）和锁的问题。


### 如何设计一个支持“不定高度”且包含图片的虚拟滚动组件？


**考察点：**

- 虚拟列表的基本原理（可视区计算）。
- DOM 渲染策略（回收复用 vs 销毁重建）。
- 高度动态变化的修正算法。
- 滚动抖动（Scroll Jank）的处理。


**参考解答思路：**

1. **基础原理**：简述只渲染视口（Viewport）+ 缓冲区（Buffer）内的数据，利用 `padding` 或 `transform` 撑开容器高度。
2. **不定高难点**：传统的虚拟列表依赖固定高度计算偏移量（Offset）。在高度未知时，需要维护一个“位置元数据表”（Offset Map），存储每一项的 `index`、`height`（初始为预估值）、`top`、`bottom`。
3. **动态修正流程**：

   - **渲染前**：使用预估高度（Estimated Height）计算布局。
   - **渲染后**：使用 `ResizeObserver` 监听列表项的真实高度。
   - **修正**：当真实高度与预估不符时，更新元数据表，并计算高度差（Delta）。
   - **防抖动**：如果高度变化发生在滚动视口上方，需要手动调整 `scrollTop`（`scrollTop += Delta`）以保持用户的阅读位置不跳变（Scroll Anchoring）。
4. **图片处理**：图片加载会导致高度二次变化。需要结合 `IntersectionObserver` 进行懒加载，且图片容器必须预设占位高度（Skeleton），或者在图片加载完成后再次触发高度修正逻辑。


### 面对千万级数据的前端表格，如果要求支持实时排序和筛选，你将如何从架构层面进行性能优化？


**考察点：**

- 渲染性能极限（DOM vs Canvas）。
- 计算性能极限（Main Thread vs Worker）。
- 调度策略（Time Slicing）。
- 交互体验优化（异步反馈）。


**参考解答思路：**

1. **渲染层架构：放弃 DOM，拥抱 Canvas**。

   - DOM 节点过多（如 > 10万）会导致巨大的内存开销和 Style Recalculation 耗时。
   - 应采用 Canvas 绘制表格，使用“双缓存”（Double Buffering）避免闪烁，仅重绘脏矩形区域（Dirty Rect）。
   - 如果是极度复杂的渲染，考虑 `OffscreenCanvas` 将渲染逻辑也移入 Worker。
2. **计算层架构：Web Worker + WASM**。

   - 千万级数据的排序和筛选是 CPU 密集型操作。不能在主线程进行（会卡死 UI）。
   - 将数据和算法下放至 Worker。对于纯数值计算或字符串匹配，可引入 Rust 编写的 WASM 模块来进一步提升遍历性能（利用 SIMD 指令集）。
3. **交互与调度：时间分片（Time Slicing）**。

   - 如果必须在主线程处理（或 Worker 返回大量结果时），不能一次性处理所有数据。
   - 采用 Generator 或 `requestIdleCallback` 拆分任务，每帧只处理一小部分数据（如 50ms 内），优先保证 UI 响应（Loading 状态），逐步展示结果（增量渲染）。
4. **事件处理**：Canvas 内部无法利用 DOM 事件冒泡。需要自行设计“空间索引”（Spatial Indexing），根据点击坐标 \$(x, y)\$ 快速映射到对应的行与列数据，实现 \$O(1)\$ 的点击响应。


## 极端性能优化业务场景梳理与度量体系


在前面几节，我们关注的是“页面加载速度（FCP/LCP）”、打包构建优化、缓存优化等等；而在前端专家视野里，我们还需要更关注**运行时（Runtime）的性能表现**。本节将从底层原理出发，解构极端场景下的性能瓶颈，并构建一套可量化的监控体系。


### 界定极端场景


#### 高频交互类


- **特征**：用户操作频率接近或超过显示器刷新率（60Hz/144Hz），每一帧的渲染预算极低（<16.6ms）。
- **典型案例**：

  - **在线协作白板**：多用户同时绘图，数千个矢量图形（SVG/Canvas Path）实时重绘。
  - **实时 K 线图**：WebSocket 每秒推送数十次数据，导致图表连续重绘。
  - **高频拖拽与缩放**：在低端机上拖拽复杂的 DOM 树或 WebGL 场景。


#### 海量数据类


- **特征**：DOM 节点数量突破浏览器舒适区（通常 > 3000 节点开始劣化，> 10000 节点显著卡顿），内存占用极高。
- **典型案例**：

  - **日志分析平台**：需要在一个页面内加载并搜索百万条日志记录。
  - **基因测序/科研数据**：超长、超宽的表格数据展示。
  - **大型 ERP 报表**：复杂的嵌套表格，伴随大量的条件渲染逻辑。


#### 计算密集类


- **特征**：主线程被长时间占用（Long Task），导致 UI 失去响应（Unresponsive），也就是俗称的“假死”。
- **典型案例**：

  - **端侧音视频编解码**：纯 JS 进行 H.264 解码或 ffmpeg 转换。
  - **复杂加密/解密**：上传大文件前的 MD5/SHA 计算、非对称加密运算。
  - **3D 模型实时解析**：解析数模（CAD）文件的大型 OBJ/STL 数据。


### 性能瓶颈的本质


为什么代码会慢？透过现象看本质，主要源于浏览器的物理限制。


#### 浏览器渲染流水线（Pixel Pipeline）的阻塞


浏览器生成一帧图像需要经历：`JavaScript -> Style -> Layout -> Paint -> Composite`。

- **致命伤**：**强制同步布局（Forced Synchronous Layout）**。
- **场景**：在循环中先写入 DOM（导致布局失效），紧接着读取布局属性（如 `offsetHeight`），迫使浏览器为了返回正确数值而立即重排。这会打断流水线的批处理优化。


#### V8 垃圾回收（GC）的 "Stop The World"


JavaScript 的自动内存管理是有代价的。当堆内存（Heap）占用过高时，V8 必须暂停 JS 执行来回收垃圾。

- **全量回收（Mark-Sweep）**：如果在动画执行过程中触发了一次 Major GC，可能会造成几十毫秒甚至上百毫秒的停顿，用户感知就是“明显掉帧”。


#### JavaScript 单线程模型的物理限制


GUI 渲染线程与 JS 引擎线程是互斥的。

- **根本矛盾**：当 JS 脚本执行时间超过 **50ms**（Long Task 定义标准），渲染线程就无法更新界面，用户的点击、滚动事件也无法及时响应（Input Delay）。


### 高级性能度量体系


无法度量就无法优化。除了常规的 Chrome DevTools，以及我们前面介绍给大家的所有性能分析工具外，我们还需要在**生产环境**建立代码级极端性能相关的监控。


#### 利用 PerformanceObserver 监控 Long Tasks（长任务检测）

长任务会贯穿我们后面多个场景，我这里定义一个耗时任务，供后面所用

```JavaScript
// 1. 定义并启动监控
const observer = new PerformanceObserver((list) => {
    list.getEntries().forEach((entry) => {
        console.warn(`🚨 抓到了！检测到长任务！`);
        console.table({
            "耗时": Math.round(entry.duration) + 'ms',
            "开始时间": Math.round(entry.startTime) + 'ms',
            "来源": entry.name
        });
    });
});
// 开始监听
observer.observe({ entryTypes: ['longtask'] });
console.log("✅ 监控已启动，准备制造卡顿...");

// 2. 立即制造卡顿
// 延迟 100ms 执行，确保监控已经就位
setTimeout(() => {
    console.log("🔥 开始阻塞主线程 2秒...");
    const start = Date.now();
    while (Date.now() - start < 2000) {
        // 死循环，霸占主线程
    }
    console.log("✨ 阻塞结束，请看上方是否有 🚨 警报");
}, 100);
```


这是最直接判断主线程是否繁忙的 API。

#### 自定义 FPS 监控与卡顿（Jank）检测


不依赖 DevTools，通过代码感知当前的流畅度。

```JavaScript
let lastTime = performance.now();
let frame = 0;
let lastFameTime = performance.now();

const loop = () => {
    const now = performance.now();
    const fs = (now - lastFameTime); // 两帧间隔时间
    lastFameTime = now;
    
    // 如果两帧间隔超过 33ms (约 30FPS)，视为一次轻微卡顿
    // 如果超过 100ms，视为严重冻结
    if (fs > 33) {
        console.log('检测到掉帧:', fs);
    }

    frame++;
    if (now > lastTime + 1000) {
        const fps = Math.round((frame * 1000) / (now - lastTime));
        // console.log('当前 FPS:', fps);
        frame = 0;
        lastTime = now;
    }
    requestAnimationFrame(loop);
}
loop();
```


#### 内存泄漏排查（Detached DOM Trees）


**分离的 DOM 树**是 SPA 应用中最常见的内存泄漏源。节点已从页面删除，但 JS 变量仍持有引用，导致无法 GC。

- **排查思路**：在 Chrome Memory 面板搜索 "Detached"，如果在生产环境，可以通过 `performance.memory`（非标准，Chrome 独有）监控 `usedJSHeapSize` 的增长趋势。如果路由切换后内存不回落，大概率存在泄漏。


### 优化实战


#### 基于 requestIdleCallback 的任务调度器


业务场景：

在数据大屏或复杂编辑器中，用户正在进行高频拖拽（高优先级），后台同时需要解析新的 WebSocket 数据并计算图表坐标（低优先级，计算量大）。直接计算会卡死拖拽。

解决策略：

实现一个时间分片（Time Slicing）调度器。

**核心代码架构**：

```JavaScript
class TaskScheduler {
  constructor() {
    this.tasks = []; // 任务队列
    this.isRuning = false;
  }

  // 添加任务，支持优先级
  addTask(callback, priority = 'low') {
    this.tasks.push({ callback, priority });
    if (!this.isRuning) {
      this.isRuning = true;
      requestIdleCallback(this.run.bind(this));
    }
  }

  run(deadline) {
    // 当任务队列不为空，且当前帧还有剩余闲置时间（或者任务已超时）
    while (this.tasks.length > 0 && deadline.timeRemaining() > 1) {
      const task = this.tasks.shift();
      task.callback(); // 执行微任务片段
    }

    if (this.tasks.length > 0) {
      // 本帧没空了，申请下一帧的闲置时间
      requestIdleCallback(this.run.bind(this));
    } else {
      this.isRuning = false;
    }
  }
}

// 使用示例：将大数组的处理拆分为小块
const scheduler = new TaskScheduler();
const bigArray = new Array(10000).fill(0);

// 拆解任务
bigArray.forEach(item => {
  scheduler.addTask(() => {
    heavyCalculation(item); // 单个耗时较短的计算
  });
});
```

**设计关键点**：

1. **输入响应优先**：`requestIdleCallback` 只有在浏览器“空闲”时才执行，确保不影响用户的交互（Input Latency < 50ms）。
2. **任务原子化**：必须将大循环拆解为小的 Function，否则一旦开始执行一个 500ms 的函数，调度器也无法暂停它。


#### 自动化卡顿“录制”埋点 SDK


业务场景：

VIP 用户反馈操作表格时“偶尔卡顿”，但在开发者的电脑上无法复现。需要保留“案发现场”。

解决策略：

开发一个自动触发式采样器（Sampler）。

**架构设计**：

1. **触发器 (Trigger)**：

   - 监听 FPS 循环。
   - **判定条件**：当连续 3 帧的渲染间隔 > 50ms（即 FPS < 20），触发报警。
2. **采样 (Snapshot)**：

   - 一旦触发，立即记录当前时刻的上下文信息。
   - **采集内容**：
   
     - `performance.now()` 时间戳。
     - 当前 URL 与路由参数。
     - `performance.memory` 快照（JS 堆内存使用量）。
     - 过去 3 秒内的 `Long Task` 列表（通过 PerformanceObserver 缓冲获取）。
     - 用户最近 10 次的行为栈（点击了哪个按钮、输入了什么，通过全局事件代理捕获）。
3. **上报 (Report)**：

   - 使用 `requestIdleCallback` 或 `Navigator.sendBeacon` 在后台静默上传数据，避免为了上报数据导致更严重的卡顿。

**SDK 伪代码逻辑**：

```JavaScript
class LagMonitor {
    constructor() {
        this.frameTimestamps = [];
        this.longTasksBuffer = [];
        this.initLongTaskObserver();
        // 这个是针对掉帧情况的捕获
        this.startFPSLoop();
    }

    initLongTaskObserver() {
        // 持续收集长任务，只保留最近 50 条
        new PerformanceObserver((list) => {
            this.longTasksBuffer.push(...list.getEntries());
            if(this.longTasksBuffer.length > 50) this.longTasksBuffer.shift();
        }).observe({ entryTypes: ['longtask'] });
    }

    checkJank(fps) {
        if (fps < 20) {
            this.captureSnapshot();
        }
    }

    captureSnapshot() {
        const report = {
            reason: 'Low FPS',
            memory: performance.memory?.usedJSHeapSize,
            recentLongTasks: this.longTasksBuffer, // 罪魁祸首通常在这里
            url: window.location.href
        };
        // 避免重复上报（节流）
        this.sendReport(report); 
    }
}
```


## 虚拟列表与虚拟滚动原理详解


在处理成千上万条数据时，直接渲染所有 DOM 节点是影响前端性能的最大原因。虚拟滚动（Virtual Scrolling）通过“只渲染可视区域”的策略，将页面节点维持在恒定数量（如 20-50 个），从而实现 O(1) 级别的渲染性能。

本节我们将深入底层，拆解从定高到不定高、从简单渲染到复杂交互的完整技术链路。


### 核心原理拆解


#### 可视区渲染模型


虚拟滚动的本质是数学映射。我们需要根据滚动位置实时计算出数据源中哪些项需要被渲染。

假设列表各项高度固定为 `itemHeight`，容器高度为 `containerHeight`，滚动偏移量为 `scrollTop`：

- 起始索引 (StartIndex)：

  - $StartIndex = \lfloor \frac{scrollTop}{itemHeight} \rfloor$
- 结束索引 (EndIndex)：

  - $EndIndex = StartIndex + \lceil \frac{containerHeight}{itemHeight} \rceil$
- 列表总高度 (Phantom Height)：用于撑开滚动条，模拟真实列表长度。

  - $TotalHeight = data.length \times itemHeight$


#### DOM 复用机制：销毁重建 vs. 节点池


当用户滚动时，旧节点离开视口，新节点进入视口。有两种处理流派：

| **策略** | **机制描述** | **优点** | **缺点** | **适用库** |
|-|-|-|-|-|
| **销毁与重建** | 每次滚动计算出新的 Slice 数据，React/Vue Diff 算法自动卸载旧组件、挂载新组件。 | 实现简单，完全利用框架生命周期，不易出错。 | GC 压力大，组件初始化开销大（尤其是有复杂 hooks 时）。 | react-window, vue-virtual-scroller |
| **节点池复用 (Recycling)** | 维护一个固定数量的 DOM 池（如 20 个）。滚动时只改变 DOM 的内容和位置，不销毁节点。 | 极致性能，内存波动极小，无 GC 抖动。 | 状态管理极其困难（脏数据残留），难以与现代框架声明式风格结合。 | 原生 JS 实现, recyclerlistview |


#### 布局策略：绝对定位 vs. Transform


为了让这一小撮 DOM 节点出现在正确的位置，我们需要对它们进行定位。

- **绝对定位 (Absolute + Top)**：

  - 改变 `top` 属性会触发 **Reflow (重排)**。
  - 虽然现代浏览器优化较好，但在低端机上高频触发仍有性能瓶颈。
- **3D 变换 (Transform: translate3d)**：✅

  - 改变 `transform` 只触发 **Composite (合成)**。
  - 能够开启 GPU 加速，是高性能滚动的首选方案。
  - *注意*：层数过多可能导致显存占用上升。


### 复杂场景进阶


#### 不定高度的挑战


现实业务中，聊天气泡、Feeds 流的高度往往由内容决定，无法预知。

- **悖论**：不知道高度 \$\rightarrow\$ 无法计算 `TotalHeight` \$\rightarrow\$ 滚动条乱跳 \$\rightarrow\$ 无法精准计算 `StartIndex`。
- **解法**：**“预估 + 修正”策略**。先给一个默认值（如 50px），渲染后获取真实高度并缓存。


###  实战：构建高性能不定高虚拟列表引擎


**目标**：实现一个支持图文混排、高度未知、滚动不抖动的虚拟列表组件。


#### 核心架构设计


我们需要维护一个核心数据结构：**位置元数据表 (Position Manager)**。


##### 步骤 1：初始化与预估


在数据加载初期，我们无法获取真实高度。

- **策略**：使用 `estimatedHeight`（如 50px）初始化元数据表。
- **数据结构**：

```JavaScript
// cachedPositions: 维护所有列表项的几何信息
[
  { index: 0, height: 50, top: 0, bottom: 50, dValue: 0 }, // dValue: 预估与真实的差值
  { index: 1, height: 50, top: 50, bottom: 100, dValue: 0 },
  // ...
]
```


##### 步骤 2：基于二分查找的渲染计算


由于不定高，列表项的 `top` 值不是线性的，无法用简单的除法计算 `startIndex`。

- **策略**：因为 `top` 值是单调递增的，使用 **二分查找 (Binary Search)** 寻找第一个 `bottom > scrollTop` 的项作为 `startIndex`。
- **复杂度**：将查找耗时从 \$O(N)\$ 降至 \$O(\log N)\$。


##### 步骤 3：缓冲区 (Buffer Zone) 设计


为了避免快速滚动时出现“白屏”或闪烁，我们不能只渲染视口内的元素。

- **策略**：上下各多渲染 1-2 屏的数据（Overscan）。

```JavaScript
const visibleStart = binarySearch(scrollTop);
const renderStart = Math.max(0, visibleStart - bufferSize);
const renderEnd = Math.min(totalCount, visibleEnd + bufferSize);
```


##### 步骤 4：真实高度监听与动态修正 (核心难点)


这是不定高方案的灵魂。我们需要在 DOM 渲染后立即获取真实高度，并修正元数据。

- **工具**：使用 `ResizeObserver` 监听列表项容器。
- 修正逻辑：
- 当第 i 项的高度从 50px 变为 120px（差值 delta = 70）时：

  1. 更新 `cachedPositions[i].height = 120`。
  2. **关键点**：不仅要更新第 `i` 项，还需要将 `i` 之后**所有**项的 `top` 和 `bottom` 都加上 `delta`。
  3. 更新总高度 `TotalHeight`，使滚动条长度匹配真实内容。


##### 步骤 5：滚动锚定 (Scroll Anchoring) —— 防止抖动


如果用户正在看第 50 条，而第 10 条（在视口上方）的图片加载完成，高度突然变大 100px。

- **后果**：整个列表会被“顶”下来，用户看到的第 50 条会瞬间下移 100px，产生严重的视觉跳动。
- 解决方案：
- 在修正高度时，判断变更节点是否在 scrollTop 之上。如果是，则同步调整 scrollTop。

```JavaScript
// 伪代码：修正逻辑
if (nodeIndex < startIndex) {
    // 变更发生在视口上方，为了保持当前视口内容不动，需要把滚动条也往下顶
    container.scrollTop += delta;
}
```

## 千万行数据表格渲染优化方案


当数据量级从“千”跃升至“千万”级别时，前端架构面临的挑战就不再是简单的“渲染快慢”，而是“程序存亡”。传统的 DOM 架构在内存占用和重排耗时上会呈指数级崩溃。

本节我们将抛弃 DOM，转向图形编程（Graphics Programming），构建一套基于 **Canvas + Web Worker + SharedArrayBuffer** 的高性能表格引擎。


### DOM 的极限与 Canvas 的引入


#### 为什么 DOM 会崩溃？


- **内存膨胀**：每个 `<div>` 或 `<td>` 在浏览器内部都是一个复杂的 C++ 对象（`HTMLDivElement`）。渲染 10 万个单元格，内存占用可能高达 100MB+。千万级数据完全无法实例化。
- **流水线阻塞**：表格列宽调整引发的 `Recalculate Style` 和 `Layout` 是全局性的。在巨大 DOM 树上执行一次 Reflow，耗时可能是秒级的。


#### Canvas 渲染方案


Canvas 的渲染，屏幕上只有像素，没有对象，内存占用恒定（只与画布尺寸有关，与数据量无关）。

- 双缓存 (Double Buffering) 与 OffscreenCanvas：
- 直接在屏幕 Canvas 上频繁绘制会导致闪烁。

  - **策略**：在内存中创建一个 `OffscreenCanvas` 作为“后缓冲区”，所有绘制操作都在这里完成，最后通过 `ctx.drawImage` 一次性将渲染好的 Bitmap 复制到屏幕。
- 脏矩形渲染 (Dirty Rect Optimization)：
- 当光标悬停导致单元格背景变色时，不要重绘整个表格。

  - **策略**：计算出变化的区域 `(x, y, width, height)`，仅调用 `ctx.clearRect` 和重绘该区域。这能将 GPU 负载降低 90% 以上。


### 数据层与渲染层分离架构


在千万级数据下，**主线程（UI 线程）严禁触碰数据处理逻辑**。


#### Web Worker 数据治理


排序、筛选、聚合（Pivot）等操作是典型的 CPU 密集型任务。

- **架构**：主线程仅负责接收用户的 UI 交互指令（如“点击表头排序”），将指令转发给 Worker。Worker 计算完毕后，不返回全量数据，而是返回“可视区域的渲染数据”或“索引视图”。


#### SharedArrayBuffer：零拷贝架构


传统 `postMessage` 通信存在\*\*结构化克隆（Structured Clone）\*\*开销。发送 100MB 的 JSON 数据，浏览器需要序列化再反序列化，耗时可能长达 500ms+。

- 解决方案：SharedArrayBuffer (SAB)。
- SAB 允许主线程和 Worker 线程共享同一块内存地址。

  - **数据结构**：使用 `Int32Array` 或 `Float64Array` 视图直接操作二进制数据。
  - **同步机制**：使用 `Atomics` 也就是原子操作（如 `Atomics.store`, `Atomics.load`, `Atomics.wait`）来管理锁，防止多线程同时写入导致的数据竞争（Race Condition）。


### 交互体验优化


#### 惯性滚动模拟 (Inertia Scroll)


Canvas 也就是一张画板，没有自带的滚动条和滚动行为。我们需要手写物理引擎。

- 算法：基于动量（Momentum）的物理模型。

  - $Velocity_{next} = Velocity_{current} \times Friction$
- 通常摩擦系数 $Friction$ 设为 0.95 左右。当用户手指离开屏幕时，继续按当前速度滚动并逐渐减速，直到速度小于阈值。


#### Canvas 内部的事件系统


Canvas 上的像素无法响应 `click` 事件。我们需要自己实现**点击检测 (Hit Testing)**。

- **传统方案**：`ctx.isPointInPath(x, y)` —— 性能较差，需要遍历图形。
- **高性能方案**：**数学映射**（见下文设计思路 3）。


### 实战


#### 基于 Canvas 的分块渲染（Tile Rendering）系统


场景：

类似于 **飞书表格**或地图应用，用户快速拖拽巨型表格，视口内容不断变化。

策略：

将表格单元格作为瓦片 (Tile)。

**尺寸分离 (`COL_WIDTH`, `ROW_HEIGHT`)**：

- 表格最显著的特征是“扁长”，所以我将原来的正方形 `TILE_SIZE` 拆分为 `120px` 宽和 `30px` 高的矩形，这立刻让界面看起来像数据列表。

**固定表头 (Fixed Headers)**：

- **难点**：Canvas 是位图，无法像 DOM 元素那样用 `position: sticky`。
- **解法**：在 `render()` 函数中分两步绘制。

  1. 先 `translate` 偏移，绘制所有数据单元格。
  2. `restore` 坐标系，然后在最上层单独绘制“行号栏”和“列标栏”。这样无论怎么滚动，表头都会重新绘制在视口的边缘，模拟出固定的效果。

**样式细化 (`THEME` 对象)**：

- 使用了 Excel 风格的配色：`#f8f9fa` 作为表头背景，`#e0e0e0` 作为网格线。
- 增加了 `ctx.clip()` 裁剪，防止文字太长溢出单元格。
- 支持高分屏（Retina屏），通过 `devicePixelRatio` 缩放，使文字在手机或 Mac 上不模糊。

**交互逻辑**：

- 监听 `mousemove`。注意这里需要反向计算：`鼠标位置 + 滚动距离 - 表头偏移量 = 实际数据坐标`。

            ctx.fillStyle = THEME.headerBg;

        ctx.stroke();

        const startRow = Math.floor(contentScrollTop / ROW_HEIGHT);

        ctx.font = '12px sans-serif';
        ctx.textAlign = 'center';
        ctx.textBaseline = 'middle';

        // A. 绘制顶部列标头 (A, B, C...)
        ctx.save();
        ctx.translate(HEADER_COL_WIDTH, 0); // 让出左上角
        for (let c = startCol; c < endCol; c++) {
            const x = (c * COL_WIDTH) - scrollLeft;

            ctx.fillStyle = THEME.headerBg;
            ctx.fillRect(x, 0, COL_WIDTH, HEADER_ROW_HEIGHT);

            ctx.strokeStyle = THEME.headerBorder;
            ctx.strokeRect(x, 0, COL_WIDTH, HEADER_ROW_HEIGHT);
            
            // 绘制文字
            ctx.fillStyle = THEME.headerText;
            if (c === state.selected.c) { // 高亮选中的列头
                ctx.fillStyle = THEME.selectBorder;
                ctx.font = 'bold 12px sans-serif';
            } else {
                 ctx.font = '12px sans-serif';
            }
            ctx.fillText(getColLabel(c), x + COL_WIDTH / 2, HEADER_ROW_HEIGHT / 2);
        }
        ctx.restore();

        // B. 绘制左侧行号头 (1, 2, 3...)
        ctx.save();
        ctx.translate(0, HEADER_ROW_HEIGHT); // 让出左上角
        for (let r = startRow; r < endRow; r++) {
            const y = (r * ROW_HEIGHT) - scrollTop;
            
            ctx.fillStyle = THEME.headerBg;
            ctx.fillRect(0, y, HEADER_COL_WIDTH, ROW_HEIGHT);
            
            ctx.strokeStyle = THEME.headerBorder;
            ctx.strokeRect(0, y, HEADER_COL_WIDTH, ROW_HEIGHT);

                ctx.font = 'bold 12px sans-serif';
            } else {
                 ctx.font = '12px sans-serif';
            }
            ctx.fillText(r + 1, HEADER_COL_WIDTH / 2, y + ROW_HEIGHT / 2);
        }
        ctx.restore();

        // C. 绘制左上角的全选块
        ctx.fillStyle = THEME.headerBg;
        ctx.fillRect(0, 0, HEADER_COL_WIDTH, HEADER_ROW_HEIGHT);
        ctx.strokeStyle = THEME.headerBorder;

             state.selected = { ...state.hover };
             requestAnimationFrame(render);
         }
    });

    // 启动
    resize();

</script>

    function* gridSearchGenerator(targetText) {
        // 遍历假设的大数据集
        for (let r = 0; r < MAX_SEARCH_ROWS; r++) {
            for (let c = 0; c < MAX_SEARCH_COLS; c++) {

                // 不，这样开销太大。我们在调度器里控制何时暂停。
                // 这里我们仅仅是产出状态。
                yield { found: false, progress: { r, c } };

        // 16ms 是一帧，留给渲染和浏览器内核约 6-8ms，剩下 8-10ms 给 JS 运算
        const TIME_BUDGET = 8;

            if (!isSearching) return; // 被取消

            const start = performance.now();

            // --- 关键循环 ---
            // 只要当前帧还有剩余时间，就一直执行 next()
            while (performance.now() - start < TIME_BUDGET) {
                const result = searchIterator.next();

                if (result.done) {
                    finishSearch(null); // 遍历完也没找到
                    return;
                }

                if (result.value.found) {
                    finishSearch(result.value); // 找到了
                    return;

                // 可选：更新进度条（不要太频繁，会影响性能，这里简单显示行号）
                // document.getElementById('status').innerText = `正在搜索第 ${result.value.progress.r} 行...`;
            }

            // 时间片用完了，通过 RAF 申请在下一帧继续执行
            searchJobId = requestAnimationFrame(runSlice);
        }

        // 启动任务
        runSlice();
    }

        document.getElementById('btnSearch').disabled = false;
        document.getElementById('btnCancel').disabled = true;

            behavior: 'smooth' // 平滑滚动
        });

        // 触发一次重绘以显示高亮
        render();
    }

#### 自定义 Hit Detection (O(1) 点击检测)


场景：

用户点击 Canvas 上的某一点 \$(x, y)\$，需要立即知道点中了第几行、第几列，以便显示编辑框。

**策略**：**空间索引 (Spatial Indexing) 与 数学映射**

不遍历图形，而是利用表格布局的规则性进行反向计算。

1. 固定行高场景：

   1. $RowIndex = \lfloor \frac{ClickY + ScrollTop}{RowHeight} \rfloor$
   2. $ColIndex = \lfloor \frac{ClickX + ScrollLeft}{ColWidth} \rfloor$

时间复杂度为 \$O(1)\$。

1. **不定行高场景**（难点）：

   - 维护一个 **二分查找树 (BST)** 或 **前缀和数组 (Prefix Sum Array)** 记录每行的高度累加值。
   - 数组结构：`[0, 50, 120, 180, ...]` (表示第 0 行起止 0-50，第 1 行 50-120...)。
   - 当点击 \$Y = 150\$ 时，对数组进行二分查找，快速定位到对应的索引。
   - 时间复杂度为 \$O(\log N)\$。

    // ==========================================
    // 1. 核心算法：前缀和与二分查找 (GridMetrics)
    // ==========================================
    class GridMetrics {
        constructor(rowCount, defaultHeight) {
            this.rowCount = rowCount;
            this.heights = []; // 存储每一行的高度
            this.offsets = [0]; // 前缀和数组：offsets[i] = 第 i 行的起始 Y 坐标
            
            // 模拟：生成不定行高 (随机高度 30px - 60px)
            let currentOffset = 0;
            for (let i = 0; i < rowCount; i++) {
                // 演示技巧：偶数行高一些，奇数行矮一些
                const h = (i % 5 === 0) ? 60 : 30; 
                this.heights.push(h);
                currentOffset += h;
                this.offsets.push(currentOffset);
            }
            
            this.totalHeight = currentOffset;
        }

        // 获取第 index 行的起始位置 (O(1))
        getRowOffset(index) {
            if (index < 0) return 0;
            if (index >= this.offsets.length) return this.offsets[this.offsets.length - 1];
            return this.offsets[index];
        }

        // 获取第 index 行的高度 (O(1))
        getRowHeight(index) {
            if (index < 0 || index >= this.heights.length) return 0;
            return this.heights[index];
        }

        // 核心难点：给定 Y 坐标，找到对应的行索引 (O(log N))
        // 使用二分查找 (Binary Search)
        getRowIndexAt(y) {
            let low = 0;
            let high = this.rowCount - 1;
            
            while (low <= high) {
                const mid = (low + high) >> 1;
                const start = this.offsets[mid];
                const end = this.offsets[mid + 1];

                if (y >= start && y < end) {
                    return mid; // 命中
                } else if (y < start) {
                    high = mid - 1;
                } else {
                    low = mid + 1;
                }
            }
            return -1; // 超出范围
        }
    }

            if (this.changes[key] !== undefined) return this.changes[key];

        ctx.fillRect(0, 0, canvas.width, canvas.height);

            endRow++;

        const endCol = Math.floor((scrollLeft + window.innerWidth) / CONFIG.colWidth) + 1;

        ctx.translate(CONFIG.headerWidth, CONFIG.headerHeight);

        ctx.fillRect(0, 0, CONFIG.headerWidth, canvas.height);

        editor.style.left = screenX + 'px';
        editor.style.top = screenY + 'px';

        editor.style.lineHeight = (rowH - 4) + 'px'; 

        // 3. 填充值并聚焦
        editor.value = dataModel.getValue(r, c);
        editor.focus();

        debug.innerHTML = `点击命中: Row ${r} (H:${rowH}px), Col ${c} <br> 算法: 二分查找定位`;
    }

    function closeEditor(save) {
        if (!state.editing) return;
        const { r, c } = state.editing;

        if (save) {
            dataModel.setValue(r, c, editor.value);
            render(); // 重绘显示新值
        }

        editor.style.display = 'none';
        state.editing = null;
    }

    editor.addEventListener('blur', () => closeEditor(true)); // 失去焦点保存
    editor.addEventListener('keydown', (e) => {

            // 这里还可以做：按 Enter 自动跳到下一行
        }
    });

    window.addEventListener('resize', resize);
    resize();

##### 应对“不定行高”的数据结构 (`GridMetrics` 类)


这是本实现的精华。为了支持不定行高，我们不能简单使用 `y / height`。

- **Prefix Sum (前缀和)**: `offsets` 数组存储了每一行的**绝对 Y 坐标**。例如，如果第0行高30，第1行高50，那么 `offsets` 就是 `[0, 30, 80, ...] `。

  - 第 `i` 行的区间是 `[offsets[i], offsets[i+1])`。
- **Binary Search (二分查找)**: 当用户点击屏幕上的 `Y=150` 时，我们需要在有序数组 `offsets` 中找到一个索引 `i`，使得 `offsets[i] <= 150 < offsets[i+1]`。

  - 这就是标准的 `getRowIndexAt` 函数实现。
  - 即使有 100万行，查找次数也仅为 `log2(1000000) ≈ 20` 次，极其高效。


##### 点击检测流程


1. **事件捕获**: 监听 `viewport` 的 `click` 事件。
2. 坐标转换:

   1. $WorldY = ClientY - HeaderOffset + ScrollTop$
3. **索引计算**: 调用 `metrics.getRowIndexAt(WorldY)` 得到行号。
4. **UI 响应**:

   - 计算出该行在屏幕上的确切矩形区域。
   - 将 `position: fixed` 的 `<input>` 元素移动到该区域覆盖 Canvas。
   - 这种“真假替换”是 Canvas 应用（如 Google Sheets, Excel Online）通用的编辑实现方式。


## Webassembly (WASM) 基础进阶与实战


在视频解码、图像处理、复杂算法运算等 CPU 密集型场景下，JS 的动态类型和垃圾回收机制成为了性能的掣肘。WebAssembly (WASM) 的出现，为浏览器引入了接近原生代码（Native Code）的执行效率，它是前端架构师必学高阶优化手段。


### 核心内容：WASM 基础与工具链


#### WASM 的内存模型：线性内存（Linear Memory）


WASM 与 JS 并不直接共享变量。它们唯一的交集是一块**线性内存（Linear Memory）**。

- **本质**：在 JS 侧，它就是一个可读写的 `WebAssembly.Memory` 对象（本质是 `ArrayBuffer`）。
- **交互方式**：

  - JS 无法直接把一个 Object 传给 WASM。
  - JS 必须将数据（如字符串、图片像素）序列化为二进制，写入 `ArrayBuffer` 的特定偏移量（Offset）。
  - 然后将“指针（Pointer）”和“长度（Length）”传递给 WASM 函数。
  - WASM 读取内存，处理后，再将结果写入内存，JS 依据返回的新指针去读取。


#### 开发流派：Rust vs C++


- **Rust + wasm-pack（现代前端首选）**：

  - Rust 拥有零成本抽象和内存安全特性，且拥有极其完善的 WASM 生态（`wasm-bindgen`）。
  - **开发流**：编写 `.rs` 代码 \$\rightarrow\$ `wasm-pack build` \$\rightarrow\$ 自动生成 `.wasm` 文件和封装好的 JS 胶水代码（Glue Code），可以直接 npm install。
- **Emscripten (C/C++ 迁移流)**：

  - 主要用于将现有的 C/C++ 库（如 FFmpeg, OpenCV）编译到 Web 端。
  - 工具链较重，生成的胶水代码体积较大，但生态积淀深厚。


#### 通信开销与胶水代码


- **昂贵的边界**：JS 调用 WASM 函数是有开销的（Trampoline）。虽然现在浏览器优化得很好，但高频调用（如在循环里调用 100 万次 WASM 加法）依然会比纯 JS 慢。
- **原则**：**"Chunky, not Chatty"**（大块交互，而非频繁闲聊）。将整个循环或整个计算任务下沉到 WASM，而不是让 JS 当指挥官频繁发令。


### WASM 性能调优


#### 减少 JS <-> WASM 边界穿越


- **反例**：JS 遍历数组，每次循环调用一次 WASM 的 `add(a, b)`。
- **正解**：JS 直接把整个数组的内存指针传给 WASM，WASM 内部循环处理完，返回结果。


#### SIMD（单指令多数据）加速


现代 CPU 支持 SIMD 指令集（如 SSE, AVX），能一条指令处理多个数据（如同时计算 4 个 float 乘法）。

- WASM 目前已支持 128-bit SIMD。
- **应用**：在图像滤镜、矩阵运算中，开启 SIMD 往往能带来 2-4 倍的性能提升。


### 实战


#### 端侧图片极速压缩与滤镜处理

**💡 提示**

几个问题：
1. 如果wasm-pack 卡死，可能是包缓存问题，`rm -rf ~/.cargo/.package-cache`
2. 一定要确保网络状态良好


业务场景：

电商卖家后台，用户上传 4K/8K 原始图片（20MB+）。需要在前端立即进行压缩（Compress）、裁剪（Crop）和添加水印，且不能卡死浏览器。纯 Canvas 处理大图在低端机容易导致 OOM（内存溢出）或 UI 冻结。

**技术策略 (Rust + WASM)**：

1. **架构设计**：

   - 使用 Rust 的 `image` crate（社区成熟库）编写图像处理算法。
   - 暴露一个 `process_image(ptr, len, quality)` 函数给 JS。
2. **内存交互流程**：

   - **JS 侧**：用户上传 `File` \$\rightarrow\$ `FileReader` 读取为 `Uint8Array`。
   - **分配内存**：JS 调用 WASM 的 `alloc(size)` 申请内存空间，拿到指针 `ptr`。
   - **写入数据**：JS 将 `Uint8Array` 写入 WASM 堆内存（`HEAPU8.set`）。
   - **执行**：调用 `process_image(ptr, len)`。WASM 内部解码图片、重采样、编码为 JPEG/WebP。
   - **读取结果**：WASM 返回结果图片的 `result_ptr` 和 `result_len`。JS 通过 `new Uint8Array(memory.buffer, result_ptr, result_len)` 构造视图。
   - **生成文件**：JS 将数据转为 `Blob` 上传，并调用 `dealloc` 释放 WASM 内存。

**优势**：相比 Canvas API，WASM 方案能精确控制内存分配与回收，且处理速度通常快 30%-50%（开启 SIMD 后）。

#### MD5/SHA 大文件秒传计算


业务场景：

网盘或视频网站，上传 2GB 视频前，需要计算文件的 MD5/SHA-256 指纹（Hash），用于实现“秒传”（服务端检测文件已存在则跳过上传）。

- **痛点**：纯 JS 计算 2GB 文件的 Hash 非常慢，且容易阻塞 UI。

**技术策略 (Web Worker + WASM + Stream)**：

1. **架构设计**：

   - **主线程**：负责 UI 交互，读取文件切片（Chunk）。
   - **Web Worker**：加载 WASM 实例，负责计算。
   - **WASM**：使用 Rust 的 `md-5` 或 `sha2` crate，暴露 `update(chunk)` 和 `digest()` 接口。
2. **增量计算流程**：

   - **分块读取**：使用 `FileReader` 或 `File.stream()` 每次读取 10MB 数据。
   - **零拷贝传输**：主线程使用 `postMessage(chunk, [chunk.buffer])` 将数据的所有权转移（Transfer）给 Worker。**注意：这是零拷贝，速度极快。**
   - **WASM 计算**：Worker 接收数据，写入 WASM 内存，调用 `context.update(ptr, len)` 更新 Hash 状态。
   - **循环**：重复上述步骤直到文件结束。
   - **输出**：调用 `context.digest()` 获取最终 Hash 字符串。

**性能对比**：

- **JS (CryptoJS)**: 约 10-20 MB/s。
- **JS (WebCrypto API)**: 极快（Native 实现），但部分旧浏览器不支持增量更新（Incremental Update），只能一次性读入内存，无法处理 2GB 大文件。
- **WASM (Rust)**: 约 150-300 MB/s，且支持流式计算，完美解决大文件问题。


##### 最终实现完整代码（基于 rust + 原生html）

完整实战步骤

1. 初始化 wasm 构建工程：`cargo init`
2. 指定相关依赖：

   ```TOML
   [package]
   name = "wasm-hash-pro"
   version = "0.1.0"
   edition = "2021"
   
   [lib]
   crate-type = ["cdylib"]
   
   [dependencies]
   wasm-bindgen = "0.2"
   # 纯 Rust 实现的加密哈希库，性能极高且容易编译为 WASM
   md-5 = "0.10"
   sha2 = "0.10"
   # 用于将二进制摘要转为 Hex 字符串
   hex = "0.4"
   ```
3. 编写核心加密代码，`src/lib.rs`
4. 构建 wasm，`wasm-pack build --target web`
5. 在 worker.js 中通过 WebWorker 引入 wasm 进行处理，结果逐步返回至 html
6. html 文件中接收 WebWorker 更新


##### wasm 主要优势总结


| **方案** | **速度 (MB/s)** | **2.4GB 总耗时** | **备注** |
|-|-|-|-|
| **纯 JS (spark-md5)** | \~35 MB/s | \~70 秒 | 如果不在 Worker 中运行，UI 会严重卡顿。依赖 V8 JIT 优化。 |
| **Rust + WASM + Worker** | **\~280 MB/s** | **\~8.5 秒** | **比纯 JS 快约 8 倍**。CPU 占用率更低。 |
| **Native (命令行 md5)** | \~600 MB/s | \~4 秒 | 本地原生 C 代码，无浏览器沙箱开销。 |
