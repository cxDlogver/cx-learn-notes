## 相关面试真题


### DeepAgents.js 与 LangChain `createAgent`、原生 LangGraph 的核心区别是什么？请分别说明它们的适用场景。


**参考答案要点**：

1. **定位差异**：DeepAgents 是**Agent Harness（智能体执行环境）**，提供开箱即用的生产级运行时；`createAgent` 是简单工具调用循环；LangGraph 是底层工作流编排引擎
2. **能力差异**：DeepAgents 内置规划、虚拟文件系统、子代理、技能系统；`createAgent` 仅支持基础工具调用；LangGraph 需要手动实现所有能力
3. **适用场景**：

   - DeepAgents：复杂多步骤任务（代码开发、研究分析）
   - `createAgent`：单轮工具调用、简单问答
   - LangGraph：需要高度定制的特殊业务流程


### DeepAgents 的子代理（Subagents）机制解决了什么核心问题？它与普通工具调用的本质区别是什么？


**参考答案要点**：

1. **解决的问题**：**上下文污染与膨胀问题**。传统工具调用的所有中间结果都会进入主代理上下文，导致窗口溢出和注意力分散
2. **本质区别**：

   - 子代理拥有**独立的上下文、系统提示词和工具集**，执行过程完全隔离
   - 主代理只接收子代理的最终结果，不关心中间过程
   - 子代理可以使用不同的模型和权限，实现专业分工
3. **额外优势**：子任务失败不影响主流程、支持并行执行、便于权限控制


## DeepAgents核心认知与快速上手


### 什么是DeepAgents.js

#### 官方定义

> DeepAgents是一个基于LangGraph构建的独立智能体库，专为**复杂多步骤任务**设计。它受到Claude Code、Deep Research和Manus等前沿智能体应用的启发，内置了规划能力、文件系统上下文管理和子代理生成能力。


#### 解决的三大核心痛点

传统Agent开发中，你会遇到这些无法回避的问题：

1. **上下文窗口溢出**：工具返回大量结果，很快填满上下文窗口
2. **长任务不可靠**：执行多步任务时，Agent容易迷失方向、忘记目标
3. **多角色协作复杂**：需要手动实现子代理的创建、通信和结果整合

DeepAgents把这些问题都变成了可配置的能力，你不需要自己从零开始实现。


#### 与其他技术的对比

| 技术 | 核心定位 | 适用场景 | 局限性 |
|-|-|-|-|
| LangChain `createAgent` | 简单工具调用循环 | 单轮工具调用、简单问答 | 不支持复杂控制流、上下文管理差 |
| 原生LangGraph | 自定义工作流编排 | 需要高度定制的业务流程 | 所有能力都需要自己实现，开发成本高 |
| DeepAgents.js | 开箱即用的通用智能体运行时 | 复杂多步骤任务、代码开发、研究分析 | 不适合需要极致定制的特殊场景 |


#### 核心设计思想：Agent Harness

Harness的字面意思是"马具"，它的作用是把马（模型）套住，让它按照你的方向前进。


**Harness架构的核心思想**：

- 模型只负责**推理决策**这一件事
- Harness负责所有**工程化问题**：环境、权限、存储、隔离、观测
- 把智能体放进一个**可控、安全、可观测**的工作台中

你可以把它想象成一个智能体的"操作系统"：模型是CPU，Harness提供了内存管理、文件系统、进程管理、安全机制等所有操作系统能力。

## DeepAgents 四大核心能力详解


### 规划与任务分解


传统Agent处理长任务时，就像一个没有计划的人，走一步看一步，很容易在执行过程中迷失方向，忘记最初的目标。


#### DeepAgents的解决方案：内置规划系统

DeepAgents内置了`write_todos`工具和自适应规划引擎，让Agent能够：

1. 将复杂目标自动拆解为可执行的离散步骤
2. 实时跟踪每个步骤的执行状态
3. 根据新信息动态调整计划


#### 核心概念

- **待办事项（Todo）**：一个可执行的最小任务单元
- **任务树**：复杂任务可以嵌套多层待办事项
- **进度跟踪**：自动更新待办事项的状态（未开始/进行中/已完成/已失败）
- **动态调整**：当遇到意外情况时，自动修改或重新生成计划

#### 关键用法

你不需要手动实现任何规划逻辑，只需要在系统提示词中简单引导：

```TypeScript
const agent = createDeepAgent({
  model,
  systemPrompt: `
    你是一个专业的项目助理。
    1. 收到任务后，首先使用write_todos工具将任务拆解为3-5个步骤
    2. 每完成一个步骤，更新待办事项的状态
    3. 如果遇到问题，调整计划并说明原因
    4. 所有步骤完成后，输出最终结果
  `,
});
```


#### 执行流程演示

当你请求"生成一个DeepAgents课程大纲"时，Agent会自动执行以下步骤：

```Plain Text
1. 调用write_todos生成计划：
   - [ ] 分析DeepAgents的核心能力
   - [ ] 设计课程结构和时间分配
   - [ ] 编写每个模块的详细内容
   - [ ] 添加实战项目和最佳实践
   - [ ] 审核并完善课程大纲

2. 逐个执行步骤，自动更新状态：
   - [x] 分析DeepAgents的核心能力
   - [x] 设计课程结构和时间分配
   - [ ] 编写每个模块的详细内容
   ...

3. 遇到新信息时自动调整计划：
   - 发现需要添加生产部署内容，新增步骤：
   - [ ] 添加生产部署和安全最佳实践
```


#### 最佳实践

1. **不要硬编码任务步骤**：让Agent自己决定如何分解任务，它比你更擅长
2. **控制计划粒度**：每个步骤应该能在1-3轮工具调用内完成
3. **允许动态调整**：不要要求Agent严格按照初始计划执行，要给它调整的空间
4. **复杂任务使用嵌套计划**：对于特别复杂的任务，可以让Agent生成多层嵌套的待办事项


### 虚拟文件系统


大模型的上下文窗口是有限的，当工具返回大量结果（比如读取一个上千行的代码文件）时，很快就会填满上下文窗口，导致后续执行失败。


#### DeepAgents的解决方案：文件系统优先的上下文管理

DeepAgents的核心设计理念之一是：**所有大文本、工具输出都应该写入文件，上下文只保留文件路径和摘要**。


当工具返回超过一定大小的结果时，DeepAgents会自动将其写入文件，然后在上下文中只保留文件路径。需要时，Agent再读取文件的具体内容。


这种设计彻底解决了上下文溢出问题，让Agent能够处理任意大小的文本和数据。


#### 四大内置Backend

Backend是虚拟文件系统的底层实现，决定了文件实际存储在哪里。DeepAgents提供了四种内置Backend：


| Backend类型 | 存储位置 | 生命周期 | 适用场景 |
|-|-|-|-|
| **StateBackend**（默认） | LangGraph状态 | 单线程 | 临时文件、中间结果 |
| **FilesystemBackend** | 本地磁盘 | 持久化 | 任务产物、本地项目 |
| **StoreBackend** | LangGraph Store | 跨线程 | 长期记忆、共享数据 |
| **CompositeBackend** | 路由到其他Backend | 取决于子Backend | 混合场景 |


#### 关键用法：CompositeBackend路由

最常用的是`CompositeBackend`，它允许你将不同的虚拟路径映射到不同的Backend：

```TypeScript
import { 
  CompositeBackend, 
  StateBackend, 
  FilesystemBackend, 
  StoreBackend 
} from "deepagents";
import { InMemoryStore } from "@langchain/langgraph";
import * as path from "path";

const store = new InMemoryStore();
const workspaceRoot = path.join(process.cwd(), "data", "workspace");

// 配置多路径路由
const backend = new CompositeBackend(
  new StateBackend(), // 默认后端：所有未匹配的路径
  {
    // /workspace/路径映射到本地文件系统
    "/workspace/": new FilesystemBackend({ 
      rootDir: workspaceRoot,
      virtualMode: true, // 启用虚拟路径映射
    }),
    // /memories/路径映射到StoreBackend
    "/memories/": new StoreBackend({ store }),
  }
);

const agent = createDeepAgent({
  model,
  backend,
  // 配置文件系统权限（白名单模式）
  permissions: [
    { operations: ["read"], paths: ["/"], mode: "allow" },
    { operations: ["read", "write"], paths: ["/workspace/**"], mode: "allow" },
    { operations: ["read", "write"], paths: ["/memories/**"], mode: "allow" },
    { operations: ["read", "write"], paths: ["/**"], mode: "deny" }, // 最后拒绝所有
  ],
});
```


#### 权限系统详解

DeepAgents的权限系统采用**白名单优先**原则：

1. 先匹配最具体的路径规则
2. 没有匹配到的路径，使用默认规则
3. 建议最后添加一条`deny /**`规则，确保安全

权限操作类型：

- `read`：读取文件和目录
- `write`：创建、修改、删除文件
- `execute`：执行文件（仅沙箱Backend支持）

#### 最佳实践

1. **临时文件用StateBackend**：不需要持久化的中间结果，用完就丢
2. **任务产物用FilesystemBackend**：生成的报告、代码、文档等，需要保存到本地
3. **长期记忆用StoreBackend**：用户偏好、历史经验等，需要跨会话共享
4. **始终配置权限**：不要使用默认的全权限配置，遵循最小权限原则
5. **启用virtualMode**：防止路径穿越攻击，确保Agent只能访问指定目录


### 子代理委派


当主代理执行多个复杂任务时，大量的中间结果会污染主代理的上下文，让它无法专注于高层协调。


比如，主代理需要先做研究，再写代码，再做测试。如果所有这些步骤都在主代理的上下文中执行，那么研究过程中的多次搜索结果、代码编写过程中的调试信息，都会留在上下文中，很快就会导致上下文溢出。


#### DeepAgents的解决方案：子代理上下文隔离

DeepAgents内置了`task`工具，让主代理可以动态创建子代理来执行具体任务。


**核心思想**：

- 主代理：负责**目标规划、任务分配、结果整合**
- 子代理：负责**具体专业任务**，拥有独立的上下文、系统提示词和工具集
- 主代理只接收子代理的最终结果，不关心中间过程

这种设计不仅解决了上下文污染问题，还实现了**专业分工**：不同的子代理可以有不同的角色、技能和工具。


#### 子代理配置

```TypeScript
import type { SubAgent } from "deepagents";

// 定义研究子代理
const researcher: SubAgent = {
  name: "researcher",
  description: "检索并归纳指定主题的信息，输出3-5条高信号结论，必须指出信息来源。",
  systemPrompt: `
    你是专业的研究助理。
    你的任务是收集和归纳信息，不要做最终决策。
    输出格式：
    - 结论1（来源：xxx）
    - 结论2（来源：xxx）
    保持回答简洁，不超过300字。
  `,
  tools: [searchKnowledgeBase], // 子代理只拥有自己需要的工具
  // 可以为子代理指定不同的模型
  model: "anthropic:claude-3-5-sonnet-20240620",
};

// 定义代码审查子代理
const codeReviewer: SubAgent = {
  name: "code-reviewer",
  description: "审查代码质量，指出bug、安全问题和改进建议。",
  systemPrompt: "你是资深代码审查专家。输出bug、安全问题、改进建议三部分。",
  tools: [readFile, runLint],
};

// 创建主代理
const agent = createDeepAgent({
  model,
  subagents: [researcher, codeReviewer],
  systemPrompt: `
    你是项目负责人。
    1. 遇到需要资料收集的任务，委派给researcher子代理
    2. 遇到需要代码审查的任务，委派给code-reviewer子代理
    3. 你只负责协调和整合结果，不亲自做研究或审查
  `,
});
```


#### 执行流程

```Plain Text
用户请求：为DeepAgents项目编写代码审查报告
→ 主代理识别需要代码审查
→ 调用task工具启动code-reviewer子代理
→ code-reviewer在独立上下文中执行：
   1. 读取项目代码文件
   2. 运行lint工具
   3. 分析代码质量
   4. 生成审查报告
→ code-reviewer返回最终报告给主代理
→ 主代理整合报告并输出给用户
```


主代理的上下文中，只会保留"调用了code-reviewer子代理，返回了xxx报告"这一条信息，不会包含子代理执行过程中的任何中间结果。


#### 最佳实践

1. **子代理职责要单一**：每个子代理只做一件事，不要创建万能子代理
2. **子代理工具集要最小化**：只给子代理完成任务所需的最小工具集，提升安全性和专注度
3. **明确输出格式**：在子代理的系统提示词中明确规定输出格式，让主代理能够稳定地解析结果
4. **不要过度委派**：简单的任务不要委派给子代理，会增加不必要的开销
5. **错误处理**：主代理应该能够处理子代理执行失败的情况，比如重试或调整任务


### 技能系统


随着Agent能力的增加，系统提示词会越来越长，包含大量的技能说明和操作指南。这不仅会占用大量的上下文空间，还会导致模型注意力分散，降低执行准确率。


#### DeepAgents的解决方案：渐进式披露的技能系统

技能是DeepAgents的**可复用能力包**，它采用**渐进式披露**的设计思想：

1. Agent启动时，只加载所有技能的**元信息**（名称和描述）
2. 只有当任务匹配某个技能时，才加载该技能的**完整内容**
3. 技能可以包含说明文档、辅助脚本和其他资源

这种设计大幅减少了上下文占用，同时让系统能力可以无限扩展。


#### 标准技能结构

```Plain Text
skills/
└── brief-writer/           # 技能目录，名称与技能名一致
    ├── SKILL.md            # 技能元信息和使用说明（必须）
    └── scripts/            # 辅助脚本目录（可选）
        └── index.ts        # 辅助函数
```


#### SKILL.md格式

```Markdown
---
name: brief-writer
description: 用于生成课程讲义、教学笔记和模块摘要，强制使用工程化结构。
module: scripts/index.ts  # 辅助脚本路径（可选）
---

当用户要求生成课程讲义、模块大纲、讲师提示词或课堂总结时，使用本技能。

## 输出结构
1. 模块目标（3-5条）
2. 核心概念（2-3个）
3. Demo指向（明确运行哪个命令）
4. 课堂练习（1个）
5. 风险点（2-3个）

## 辅助函数
导入scripts/index.ts中的buildBriefSkeleton函数生成标准骨架。
```


#### 辅助脚本示例

`skills/brief-writer/scripts/index.ts`：

1. Agent启动时，扫描`/skills/`目录下的所有子目录

6. Agent按照技能说明执行任务


#### 最佳实践

1. **每个技能只做一件事**：遵循单一职责原则，不要创建大而全的技能
2. **技能描述要具体**：明确说明技能的使用场景和能力，让Agent能够准确匹配
3. **把确定性计算放进脚本**：凡是可以用代码实现的逻辑，都不要让模型去推理
4. **技能版本管理**：为技能添加版本号，方便迭代和回滚
5. **不要在技能中包含敏感信息**：技能内容会被模型读取，不要存放API密钥等敏感信息

### 沙箱执行环境


Agent生成并执行代码是一个极其危险的操作。如果没有隔离机制，Agent可能会：

- 删除你的系统文件
- 窃取你的API密钥和敏感信息
- 执行恶意代码攻击你的系统


#### DeepAgents的解决方案：可插拔的沙箱后端

Sandbox是一种特殊的Backend，它不仅支持文件操作，还提供`execute`工具用于运行任意shell命令。更重要的是，它提供了**安全隔离边界**，防止Agent访问宿主系统的资源。


#### 沙箱架构

```Plain Text
宿主系统
    ↑
沙箱API
    ↑
隔离沙箱（Docker/VM/容器）
    ↑
Agent执行的代码和命令
```


所有Agent执行的代码和命令都运行在隔离的沙箱中，与宿主系统完全隔离。即使Agent被攻破，也只能访问沙箱内部的资源。


#### 支持的沙箱提供商

| 提供商 | 特点 | 适用场景 |
|-|-|-|
| **LocalShellBackend** | 本地shell，无隔离 | 仅用于本地开发演示 |
| **Deno Sandbox** | 基于Deno的轻量级沙箱 | 简单代码执行 |
| **Daytona** | 全功能开发环境沙箱 | 复杂项目开发 |
| **Modal** | 云端无服务器沙箱 | 生产环境大规模部署 |
| **LangSmith Sandbox** | LangChain官方沙箱 | 与LangSmith生态深度集成 |


#### 生产环境用法

```TypeScript
import { DaytonaSandbox } from "@langchain/daytona";

// 创建远程隔离沙箱（生产环境推荐）
const sandbox = await DaytonaSandbox.create({
  memoryMb: 1024,          // 内存限制
  lifetime: "10m",         // 沙箱生命周期
  autoDeleteInterval: 3600, // 自动删除时间（秒）
  blockNetwork: false,     // 是否阻止网络访问
});

const agent = createDeepAgent({
  model,
  backend: sandbox,
  // 所有代码执行前必须人工审批
  interruptOn: {
    execute: { allowedDecisions: ["approve", "reject"] },
    write_file: { allowedDecisions: ["approve", "reject"] },
  },
});
```


### 人工审批（HITL）


Agent的自主执行可能导致不可控的副作用，比如：

- 发送错误的邮件给客户
- 删除重要的生产数据
- 执行昂贵的API调用


#### 基于中断的人工审批机制

Human-in-the-loop（HITL）允许你在Agent执行敏感操作前暂停执行，等待人类审批、修改或拒绝。只有审批通过后，Agent才会继续执行。


#### 核心概念

- **中断点**：配置需要审批的工具调用
- **决策类型**：approve（批准）、edit（修改参数后批准）、reject（拒绝）
- **状态恢复**：审批通过后，从断点继续执行，不需要从头开始

#### 关键用法

```TypeScript
import { MemorySaver } from "@langchain/langgraph";
import { Command } from "@langchain/langgraph";

// 1. HITL必须配置checkpointer来保存状态
const checkpointer = new MemorySaver();

// 2. 配置需要审批的工具
const agent = createDeepAgent({
  model,
  tools: [writeReleaseTicket, sendEmail],
  checkpointer,
  interruptOn: {
    // 发布工单：只能批准或拒绝
    write_release_ticket: { allowedDecisions: ["approve", "reject"] },
    // 发送邮件：可以批准、修改或拒绝
    send_email: { allowedDecisions: ["approve", "edit", "reject"] },
  },
});

// 3. 执行流程
async function runWithApproval() {
  const config = {
    configurable: { thread_id: "thread-123" }, // 必须指定thread_id
  };

  // 第一次调用：执行到第一个中断点
  let result = await agent.invoke(
    { messages: [{ role: "user", content: "发布v1.0版本并发送通知邮件" }] },
    config,
  );

  // 检查是否被中断
  if (result.__interrupt__) {
    const interrupt = result.__interrupt__[0].value;
    const actionRequests = interrupt.actionRequests;

    console.log("待审批动作：", actionRequests);

    // 收集用户决策（这里简化为直接批准）
    const decisions = [
      { type: "approve" }, // 批准发布工单
      { type: "edit", editedAction: { 
        name: "send_email", 
        args: { to: "team@example.com", subject: "v1.0版本发布通知" } 
      }}, // 修改邮件收件人后批准
    ];

    // 恢复执行
    result = await agent.invoke(
      new Command({ resume: { decisions } }),
      config, // 必须使用同一个config
    );
  }

  console.log("最终结果：", result.messages.at(-1)?.content);
}
```


#### 审批类型详解

1. **approve**：直接批准执行，使用Agent生成的原始参数
2. **edit**：修改参数后执行，常用于修正Agent生成的错误参数
3. **reject**：拒绝执行，Agent会收到拒绝通知，并可以调整策略


#### 最佳实践

1. **所有有副作用的操作都必须审批**：包括写入文件、执行命令、发送邮件、调用外部API等
2. **根据风险等级配置不同的审批策略**：高风险操作只能批准或拒绝，中等风险可以修改参数
3. **保留完整的审批日志**：记录谁在什么时候审批了什么操作，用于审计和追溯
4. **支持批量审批**：对于多个工具调用，可以一次性审批所有操作
5. **实现自动审批规则**：对于低风险操作，可以配置自动审批规则，提高效率


### 长期记忆


传统Agent是无状态的，每次对话都是全新的开始。它们无法记住用户的偏好、过去的经验和学到的知识。


#### DeepAgents的解决方案：文件系统式长期记忆

DeepAgents使用**文件系统式记忆**，记忆以文件的形式存储在StoreBackend中。Agent可以通过标准的文件工具（`read_file`、`write_file`、`edit_file`）来读写记忆。


这种设计的优势是：

- 简单直观：Agent已经熟悉文件操作，不需要学习新的API
- 结构化：记忆可以组织成目录和文件，便于管理
- 可扩展：支持任意大小和格式的记忆内容

#### 记忆隔离

通过`namespace`参数实现记忆隔离：

```TypeScript
// 用户级隔离：每个用户有独立的记忆
const userBackend = new StoreBackend({
  store,
  namespace: (rt) => [rt.serverInfo.user.identity],
});

// 代理级隔离：每个代理有独立的记忆
const agentBackend = new StoreBackend({
  store,
  namespace: (rt) => [rt.serverInfo.assistantId],
});

// 组织级隔离：整个组织共享记忆
const orgBackend = new StoreBackend({
  store,
  namespace: (rt) => [rt.context.orgId],
});
```


#### 完整用法

```TypeScript
const userId = "user-123";
const store = new InMemoryStore();
const memoryPath = "/memories/preferences.md";

// 预加载初始记忆
await store.put(
  [userId],
  memoryPath,
  createTextFileData(`
    ## 用户偏好
    - 喜欢简洁的回答，使用bullet points
    - 示例代码优先使用TypeScript
    - 对安全问题特别敏感
  `),
);

const agent = createDeepAgent({
  model,
  backend: new StoreBackend({ store, namespace: [userId] }),
  store,
  checkpointer: new MemorySaver(),
  memory: [memoryPath], // 启动时自动加载的记忆文件
  systemPrompt: `
    你是个人助理。
    回答前必须严格遵循/memories/preferences.md中的用户偏好。
    当用户明确要求记住新的偏好时，使用edit_file工具更新记忆文件。
  `,
});
```


#### 记忆类型

1. **用户偏好**：用户的习惯、风格、要求
2. **领域知识**：行业规则、最佳实践、内部文档
3. **历史经验**：过去的成功案例、失败教训、解决方案
4. **情景记忆**：过去的对话历史和交互记录

#### 最佳实践

1. **记忆文件要结构化**：使用Markdown格式，便于Agent解析和修改
2. **定期清理过时记忆**：删除不再需要的记忆，避免记忆膨胀
3. **敏感记忆要加密**：包含个人信息或商业机密的记忆要加密存储
4. **支持记忆检索**：对于大量记忆，实现基于向量的检索机制
5. **记忆合并**：定期合并相关的记忆，保持记忆的简洁性


### 事件流与可观测性【新特性了解】


Agent的执行过程是一个黑盒，你不知道它在做什么、为什么这么做、哪里出了问题。当Agent执行失败时，你很难排查原因。


#### DeepAgents的解决方案：结构化事件流

DeepAgents基于LangGraph的`streamEvents`API提供了v3版本的结构化事件流，它将复杂的执行过程拆分为多个分层投影，让你能够清晰地观察到Agent的每一个动作。


#### 核心投影

v3事件流提供三个核心投影：

1. **`stream.messages`**：所有消息流，包括主代理和子代理的消息
2. **`stream.toolCalls`**：所有工具调用流，包括开始、结束和错误
3. **`stream.subagents`**：所有子代理流，包括子代理的启动、执行和完成

每个子代理流又包含自己的消息、工具调用和嵌套子代理流，支持无限递归。


#### 完整用法

```TypeScript
const stream = await agent.streamEvents(
  { messages: [{ role: "user", content: "解释DeepAgents的事件流机制" }] },
  { version: "v3" }, // 必须指定v3版本
);

// 并发消费不同类型的事件
await Promise.all([
  // 消费主代理消息
  (async () => {
    for await (const message of stream.messages) {
      console.log("[主代理]", await message.text());
    }
  })(),

  // 消费主代理工具调用
  (async () => {
    for await (const toolCall of stream.toolCalls) {
      console.log(`[工具调用] ${toolCall.name} 开始`);
      const status = await toolCall.status;
      if (status === "finished") {
        console.log(`[工具调用] ${toolCall.name} 完成`);
      } else if (status === "error") {
        console.error(`[工具调用] ${toolCall.name} 失败: ${await toolCall.error}`);
      }
    }
  })(),

  // 消费子代理流
  (async () => {
    for await (const subagent of stream.subagents) {
      console.log(`[子代理] ${subagent.name} 启动`);
      
      // 消费子代理的消息
      for await (const message of subagent.messages) {
        console.log(`[${subagent.name}]`, await message.text());
      }
      
      // 消费子代理的工具调用
      for await (const toolCall of subagent.toolCalls) {
        console.log(`[${subagent.name} 工具] ${toolCall.name}`);
      }
      
      console.log(`[子代理] ${subagent.name} 完成`);
    }
  })(),
]);
```


#### UI映射规则

事件流可以很方便地映射到Web UI：

| 事件类型 | UI组件 |
|-|-|
| 主代理消息 | 对话气泡 |
| 工具调用开始 | 工具执行中卡片 |
| 工具调用完成 | 工具执行结果卡片 |
| 子代理启动 | 子任务面板展开 |
| 子代理消息 | 子任务详情 |
| 子代理完成 | 子任务面板收起 |


#### 最佳实践

1. **生产环境必须集成可观测性系统**：将事件流发送到日志系统或APM工具
2. **记录完整的执行轨迹**：保存所有事件，用于后续调试和审计
3. **支持执行轨迹回放**：让用户能够回放Agent的整个执行过程
4. **设置关键指标告警**：监控工具调用失败率、平均执行时间等指标
5. **错误追踪**：自动捕获和上报执行过程中的错误

#### 人工审批循环

```TypeScript
const approvals: ApprovalSummary[] = [];
let reviewRound = 0;
while (hasInterrupt(result)) {
  reviewRound += 1;
  const bundle = getInterruptBundle(result);
  
  // 收集用户审批决策
  const decisions = await collectReviewDecisions(result);
  approvals.push(
    ...decisions.map((decision, index) => ({
      round: reviewRound,
      action: bundle?.actionRequests?.[index]?.name ?? `action-${index + 1}`,
      decision: decision.type,
    })),
  );

  // 恢复执行
  result = await agent.invoke(new Command({ resume: { decisions } }), config);
}
```


**执行逻辑**：

- 循环检测是否有中断
- 收集用户的审批决策
- 记录审批历史
- 使用`Command({ resume: { decisions } })`恢复执行
- 直到没有更多中断，任务完成

   - [ ] 使用order-analysis技能分析订单指标

4. 子代理返回3-5条高信号结论
5. 主代理加载brief-writer技能，生成课程大纲和讲义
6. 主代理加载order-analysis技能，分析课程订单指标
7. 将大纲写入`/workspace/course-outline.md`
8. 将讲义和指标分析写入`/workspace/teaching-brief.md`
9. 启动course-qa-reviewer子代理进行质量审查
10. 子代理返回缺口、风险和改进建议
11. 将审查报告写入`/workspace/qa-review.md`
12. 生成运营复盘并写入`/memories/course-ops-retrospective.md`

#### 阶段3：人工审批

1. 主代理准备创建发布工单，触发人工审批

5. 主代理准备发送通知邮件，再次触发人工审批
6. 用户输入`approve`或`reject`
7. 主代理根据决策执行或跳过邮件发送

#### 阶段4：结果输出

1. 主代理汇总所有执行结果
2. 打印最终回答，包含产物路径、QA结论和审批执行情况

## 类 Codex 设计思路【拓展了解】


DeepAgents 定位是 agent harness，内置 planning、文件系统、subagents、memory、HITL、streaming 等能力；其 backend 文档明确支持 `read_file`、`write_file`、`grep`、`glob`、`execute`、权限和 CompositeBackend 路由。OpenAI Codex 文档也把 Codex 类产品能力拆成 tools、shell、file search、streaming、sandboxing、subagents、skills、permissions、AGENTS.md 等控制面。


- **Agent Core**

  - 使用 `createDeepAgent` 作为主智能体入口。
  - 主代理职责：理解用户目标、调用 `write_todos` 规划、选择工具、调度子代理、汇总结果。
  - 系统提示词固定为：先读上下文，再制定计划，再执行最小必要修改，最后验证和总结。
- **Workspace / Filesystem**

  - 用 `CompositeBackend` 分层：
  
    - `/workspace/`：项目文件，走 `FilesystemBackend`。
    - `/memories/`：长期记忆，走 `StoreBackend`。
    - `/skills/`：技能说明和 helper，走 `FilesystemBackend`。
    - 默认：`StateBackend` 存临时 scratchpad。
  - 所有读写必须经过权限 allow-list，最后 deny `/**`。
  - 文件修改前必须形成“读文件 → 变更意图 → 修改范围 → 验证方式”的计划记录。
- **Tools**

  - 自动搜索：
  
    - 本地搜索：`rg` / `glob` / `grep` / `read_file`。
    - 外部搜索：接入 web search 或 MCP search tool。
  - 文件操作：
  
    - `read_file`、`write_file`、`edit_file`。
    - 对代码修改优先使用 patch/edit，不允许无计划批量覆盖。
  - 命令执行：
  
    - 本地开发可用 `LocalShellBackend`。
    - 生产或云端必须换成 sandbox backend。
    - `npm test`、`npm run build`、`rg` 等低风险命令可直接执行；删除、提交、部署、联网敏感操作走 HITL。
- **Planning**

  - 规划结构固定为：
  
    - `understand`: 需求复述和约束。
    - `inspect`: 需要读取/搜索的文件。
    - `plan`: 修改步骤。
    - `execute`: 实际工具调用。
    - `verify`: 测试、构建、静态检查。
    - `summary`: 修改摘要和风险。
  - 每次计划变化都更新 `write_todos`。
  - 大任务委派给子代理，小任务由主代理直接完成。
- **Subagents**

  - `repo-researcher`：负责代码库搜索、架构归纳、依赖关系分析。
  - `implementation-planner`：负责输出文件级修改计划。
  - `code-reviewer`：负责找 bug、边界条件、测试缺口。
  - `doc-writer`：负责 README、课程文档、变更说明。
  - 子代理只拿最小工具集，默认不继承写权限。
- **Skills**

  - 用 `SKILL.md + scripts/index.ts` 管理可复用能力。
  - 建议内置 skills：
  
    - `repo-map`：生成项目结构和入口说明。
    - `patch-writer`：规范文件修改计划。
    - `test-runner`：选择验证命令。
    - `pr-reviewer`：按 code review 格式输出风险。
  - helper 脚本只做确定性转换，不承载业务决策。
- **Human-in-the-loop**

  - 必须审批：
  
    - 删除文件、移动目录、批量修改。
    - `git commit`、`git push`、`git reset`。
    - 执行 shell、联网调用、生产 API。
    - 写入 `.env`、密钥、系统配置。
  - 使用 `interruptOn + MemorySaver + Command({ resume })`。
  - 审批结果记录进过程日志。
- **Streaming / Logs**

  - 使用 `streamEvents(..., { version: "v3" })`。
  - UI/CLI 展示：
  
    - 主代理消息。
    - tool call start/input/status/output。
    - subagent started/completed。
    - 文件读写摘要。
    - 命令执行输出。
    - HITL 审批记录。
  - 最终输出固定包含：做了什么、改了哪些文件、验证结果、剩余风险。
