## 需求背景介绍


在内容创作爆发的今天，视频已经成为互联网最重要的信息载体之一，短视频、知识付费、企业营销、个人记录等场景的视频需求量持续高速增长。然而，传统的专业视频剪辑工具（如 Premiere Pro、Final Cut Pro）学习曲线陡峭，操作复杂度高，对于非专业剪辑师来说门槛极高；即使是专业创作者，大量重复性的剪辑工作也会消耗大量时间，真正用于创意构思的精力反而被挤占。

**miaoma-magicut（妙码智能剪辑）** 正是针对这一行业痛点打造的 **AI 驱动桌面端智能剪辑平台**，是一款**垂类专业化的音视频剪辑 Agent**。它的核心定位是：让大模型能力深度适配剪辑行业 workflow，从创意输入到成片输出全链路智能化，通过多节点智能体编排自动完成大部分重复性工作，只把创意决策留给人类。


### 核心目标用户分层

1. **内容创作者**：短视频博主、知识付费讲师、自媒体从业者。他们的核心痛点是产量要求高、重复性剪辑工作多，希望通过 AI 提升产出效率，把精力集中在内容创意本身。
2. **企业营销人员**：市场、运营、培训岗位员工，需要制作产品宣传片、培训视频、活动记录视频。他们的核心痛点是不专业、剪辑能力弱，希望降低制作门槛，快速产出可用的视频。
3. **普通个人用户**：用于旅行记录、家庭相册、生活分享。他们的核心痛点是完全不会专业剪辑，希望通过简单操作就能生成有质感的视频。


### 垂类智能体的业务与技术价值

传统 AI 剪辑工具大多只是在某个单点（比如字幕生成、模板套用）做 AI 增强，没有从全链路重构创作流程。本项目作为**完整的音视频剪辑 Agent**，核心价值体现在：


#### 业务价值

- **端到端自动化**：用户只需要输入自然语言创意，Agent 自动完成从创意简报 → 分镜规划 → 素材匹配 → 语音合成 → 时间线组装全流程，把创作周期从「小时级」压缩到「分钟级」
- **人机协同最优分工**：Agent 承担 80% 重复性劳动（分镜拆解、素材匹配、语音合成、时间线对齐），人类只负责最后的 20% 创意调整和质量确认，真正做到「AI 提效 + 人类创意」
- **本地隐私保护**：所有素材和创作过程都在用户本地完成，不需要上传敏感内容到云端，满足隐私合规要求
- **可编辑可调整**：AI 生成不是终点，而是起点，用户随时可以在可视化编辑器中做精细化调整，兼顾自动化效率和创作灵活性


#### 技术价值

- 验证了 **LangGraph 垂类业务落地**：在真实的音视频创作场景中，实践多步骤、有状态、需要人机交互的复杂智能体设计
- 沉淀了 **混合云 AI 架构最佳实践**：在线大模型保证效果，本地模型满足隐私和离线需求，通过适配器模式做到无缝切换和故障降级
- 完整工程化链路：覆盖从需求、架构、编码、联调、测试到打包签名分发全流程，是学习 AI 桌面应用开发的绝佳实战项目


### 产品核心价值主张

- **降门槛**：不用学习复杂的剪辑软件，用自然语言就能生成视频
- **提效率**：重复性剪辑工作 AI 自动完成，制作周期从小时级缩短到分钟级
- **保质量**：内置专业剪辑规范与最佳实践，AI 生成的结果达到基础专业水准

## 技术选型


### 整体架构分层设计

本项目采用经典的**四层分层架构**，每层职责清晰，依赖方向明确，符合单一职责原则：

| **分层** | **职责范围** | **核心技术选型** | **设计思想** |
|-|-|-|-|
| **界面层** | 用户交互、可视化编辑、状态展示 | React 19 + TailwindCSS 4.0 + Shadcn/ui + XYFlow | 组件化开发，单向数据流，分离交互与业务逻辑 |
| **智能体层** | AI 工作流编排、状态管理、人机协作 | LangGraph.js + LangChain.js + Zod | 图状编排，有状态执行，原生支持中断恢复 |
| **音视频层** | 媒体处理、元数据提取、导出合成 | FFmpeg/ffprobe + Index-TTS 2 + 火山 TTS | 模块化抽象，混合云架构，统一 Provider 接口 |
| **桌面底层** | 系统能力封装、安全边界、打包分发 | Electron + Electron Forge + pnpm | 遵循 Electron 安全最佳实践，最小权限原则 |


### 详细技术选型说明

#### 工程与包管理

- **包管理器**: `pnpm` + workspace

  - 优势：硬链接共享依赖，节省磁盘空间，安装速度快，Monorepo 原生支持良好
  - 适用场景：多包项目，清晰划分模块依赖
- **Monorepo 架构**: pnpm workspace

  - 为什么选 Monorepo：核心引擎和应用放在同一个仓库，版本对齐方便，跨模块修改一次性提交，文档代码同步
  - 分层原则：`packages` 放可复用核心库，`apps` 放应用入口，依赖从下往上，不循环依赖


#### 桌面端框架

- **应用框架**: `Electron`

  - 对比选型：
  
    - **vs Tauri**：Electron 生态更成熟，开发资料多，打包稳定，对 Node.js 原生模块支持更好；Tauri 体积更小但对原生 Node 模块集成不如 Electron 友好，本项目依赖 FFmpeg 二进制，不需要极致体积，所以选 Electron
    - **vs 原生开发**：Electron 复用前端技术栈，一人全栈可以搞定，开发效率高，满足当前项目阶段需求
  - 安全模型：主进程拥有系统权限，渲染进程沙箱隔离，预加载脚本桥接受控 API，遵循最小权限原则
- **构建工具**: `Vite` (渲染进程) + `Electron Forge` (打包分发)

  - Vite 热更新快，开发体验好
  - Electron Forge 一站式处理打包、签名、公证、发布，生态完善，减少配置工作量


#### 前端与 UI

- **前端框架**: `React 19` + `TypeScript`

  - React 19 带来最新的并发特性、`useOptimistic` 等 Hooks，适合局部重生成乐观更新场景
  - TypeScript 提供静态类型检查，配合 Zod 做运行时校验，双重保障类型安全
- **样式体系**: `TailwindCSS 4.0` + `Shadcn/ui`

  - Tailwind 4 采用 CSS-first 配置，编译更快，体积更小，原子类 CSS 开发效率高
  - Shadcn/ui 提供高质量 unstyled 基础组件，灵活定制，符合项目设计风格
- **可视化编辑**: 专业剪辑使用经典五区布局，核心交互不依赖额外可视化库；如果需要工作流可视化编排，可集成 `XYFlow (React Flow)`


#### AI 与智能体

- **智能体编排**: `LangGraph.js`

  - 核心优势：原生支持有状态图执行、Checkpoint 持久化、人机中断，完美匹配本项目「分镜审批需要用户确认后继续」场景
  - 对比手写状态机：LangGraph 已经处理了状态合并、持久化、中断恢复这些通用问题，我们只需要关注业务节点，开发效率更高
- **AI 基础层**: `LangChain.js`

  - 提供模型抽象、Prompt 模板、工具调用等基础能力，和 LangGraph 无缝集成
- **大模型服务**: 字节火山方舟

  - 兼容 OpenAI 接口协议，中文模型效果优秀，接入简单，国内访问速度快
- **数据校验与结构化**: `Zod`

  - **一处定义，多处复用**：Schema 定义一次，同时满足 TypeScript 类型推导、运行时校验、AI 结构化输出约束，完美匹配 AI 项目需求
- **结构化输出方案**: `Function Calling` + `Zod` + `自动重试`

  - 为什么选这个方案：相比纯 Prompt 约束，Function Calling 格式稳定性高很多；Zod 做最后一层兜底校验，失败自动重试，生产级可靠性有保障

## 面试问题


### **架构设计类**


#### **1. 为什么选择 Electron 开发桌面端 AI 剪辑应用，而不是用 Tauri？对比两者的优劣？**


**参考解答**：

- 核心选型思路：匹配项目当前阶段和团队技术栈，不需要追求极致体积，更看重生态成熟度和开发效率
- Electron 优势：生态更成熟，社区资料丰富，对 Node.js 原生模块支持更好，调试打包问题更容易定位，一人全栈开发可以快速推进；Tauri 优势是体积更小、更安全，但对原生 Node 模块集成不如 Electron 友好，本项目依赖 FFmpeg 二进制，不需要极致体积，所以选 Electron
- 如果是面向大众用户的成熟产品、对安装包体积敏感，Tauri 会是更好的选择

#### **2. 本项目中为什么选择 LangGraph.js 做智能体编排，而不是自己手写状态机？LangGraph 的核心优势是什么？**


**参考解答**：

- 本项目的智能体需要：多节点有序执行、状态持久化、人机中断（分镜需要用户审批）、断点续跑，这些如果手写状态机需要做很多工作：状态合并、Checkpoint 存储、中断恢复、异常回溯，LangGraph 已经原生支持这些核心能力
- 核心优势：

  1. **原生有状态执行**：自动管理全局状态，节点只需要返回增量更新，LangGraph 自动合并

  2. **Checkpoint 持久化**：每个节点执行完自动保存快照，支持中断后恢复，也支持时间旅行回溯

  3. **原生支持人机交互**：\`interrupt\` 机制天然适配「需要用户审批」场景，暂停后恢复非常方便

  4. **灵活的图编排**：支持顺序、分支、循环任意流程，节点可插拔，后续新增步骤不需要大面积重构

- 简单线性流程、不需要中断，手写状态机也够用；复杂需要人机协作的智能体，LangGraph 节省大量重复工程工作

#### **3. 什么是 Checkpoint 机制，LangGraph 如何利用 Checkpoint 实现断点续跑和中断恢复？**


**参考解答**：

\- Checkpoint 本质就是**每执行完一个节点，把当前完整状态快照保存下来**，用 \`thread_id\` 标识一次执行会话

- 实现逻辑：

  1. 执行节点前保存当前状态到 Checkpoint 存储（内存/SQLite/Redis）
  2. 遇到 `interrupt` 时停止执行，返回中断信息给调用方
  3. 用户恢复执行时，根据 `thread_id` 从 Checkpoint 恢复完整状态，从中断节点继续向下执行
- 在本项目中的应用：分镜生成后中断，等待用户审批，用户通过/反馈修改后再继续执行，不需要从头重新跑一遍，节省时间和 token 成本

#### **4. 本项目为什么采用混合云 TTS 架构？在线 TTS 和离线 TTS 各自的优劣是什么？**


**参考解答**：

- 混合云架构结合了两者优势，兼顾效果、成本和隐私：

  \- **在线 TTS（火山）优势**：中文音质顶尖、音色丰富、情感细腻、不需要本地算力、不需要用户自己部署模型，适合默认场景；劣势：按调用量收费、需要联网、文本要上传云端、隐私敏感场景不合适

  \- **离线 TTS（Index-TTS 2）优势**：完全本地运行、数据不出网、保护隐私、支持用户自定义音色克隆、没有调用成本；劣势：需要用户本地有一定算力、模型需要下载、音色数量和音质不如在线

- 本项目设计：默认用在线保证效果，自定义音色用本地保护隐私，抽象统一接口，自动路由，上层业务无感知，还支持故障降级——在线不可用自动切本地

#### **5. Electron 主进程、渲染进程、预加载脚本各自的职责是什么？为什么不能直接给渲染进程开放文件系统权限？**


**参考解答**：

- 职责划分：

  \- **主进程**：运行在完整 Node.js 环境，拥有系统权限，负责窗口管理、应用生命周期、访问本地文件系统、调用 FFmpeg 等原生能力、IPC 通信调度

  \- **渲染进程**：运行在 Chromium 沙箱，负责页面渲染、用户交互、前端业务逻辑，默认不能访问 Node.js API

  \- **预加载脚本**：运行在渲染进程隔离上下文，是主进程和渲染进程之间的安全桥梁，通过 \`contextBridge\` 只暴露业务必需的有限 API 给渲染进程

\- 安全原因：渲染进程运行网页内容，如果开放完整文件系统权限，万一加载了恶意内容，恶意代码就可以随意读写用户磁盘，造成安全问题；所以必须遵循**最小权限原则**，只有绝对必要的 API 才能暴露


### **音视频处理类**


#### **1. 什么是\`filter_complex\` 滤镜图，本项目中如何把多轨道时间线转换为 FFmpeg 滤镜图？**


**参考解答**：

- `filter_complex` 是 FFmpeg 支持复杂滤镜图的参数，可以构建包含多个输入输出、多个滤镜节点的复杂处理流，适合非线性剪辑多轨道拼接场景；简单的 `-vf` 只能处理单输入单输出，满足不了多轨道剪辑需求
- 本项目转换步骤：

  1. 收集所有输入素材（视频、音频、背景音乐），每个素材对应一个输入索引
  2. 对每个视频片段做裁剪、变速、缩放预处理，输出到对应标签
  3. 所有预处理后的视频片段通过 `concat` 滤镜拼接成完整视频流，空隙用黑场填充
  4. 对每个音频片段做变速、音量调整，拼接后和背景音乐混音
  5. 如果开启硬字幕，把字幕滤镜作用在拼接好的视频流上
  6. 最终输出完整的视频流和音频流，再做编码封装

#### **2. H.264 编码中 CRF 和 preset 参数分别是什么含义，如何平衡画质、文件体积和导出速度？**


**参考解答**：

\- **CRF**：恒定质量因子（Constant Rate Factor），范围 0-51，**越低画质越好，体积越大**；默认 23，一般 18-28 是常用范围：18 接近 visually lossless（视觉无损），28 体积更小画质依然可接受

\- **preset**：编码速度预设，从 \`ultrafast\` 到 \`veryslow\`，**越快压缩速度越快，最终体积越大**；越慢压缩效率越高，同等画质下体积更小，但导出速度更慢

- 实践平衡：一般导出选 `medium` preset + CRF 23，平衡画质、体积和速度；如果对体积敏感，可以降 CRF 到 24-26，preset 不变；如果追求最高画质且不关心时间，可以用 `slow` preset + CRF 20

#### **3. FFmpeg 中 atempo 滤镜变速范围是多少？如果要实现 4 倍速该如何处理？**


**参考解答**：

\- atempo 滤镜单个实例**只支持 0.5-2.0 倍速**范围，超出范围无法正常工作

\- 实现 4 倍速需要**串联多个 atempo 滤镜**：\`atempo=2,atempo=2\`，每个都在合法范围内，最终乘积是 4 倍速；同理 0.25 倍速需要 \`atempo=0.5,atempo=0.5\`

- 本项目在命令构建阶段自动处理这个逻辑，根据目标速度自动计算需要多少个 atempo 串联，对用户透明

#### **4. 为什么会出现字幕显示为方块的问题？本项目中是如何处理跨平台字体兼容的？**


**参考解答**：

\- 原因：FFmpeg 烧录字幕时**找不到对应字体文件**，或者字体不支持当前文字（比如中文字体），所以只能渲染成占位方块

- 跨平台处理方案：

  1. 不同系统选择不同默认字体：Windows 用微软雅黑，macOS 用苹方，Linux 用思源黑体
  2. 字幕样式指定字体名称时，使用 Fontconfig 样式匹配，确保能匹配到系统已有字体
  3. 如果用户有自定义字体，可以配置字体路径，烧录时优先使用自定义字体
  4. 极端情况找不到字体，fallback 到通用免费字体，保证至少能显示，不会全方块


### **安全与工程类**


#### **1. Electron 中为什么不建议使用\`file://\` 协议加载本地媒体，自定义协议解决了什么问题？**


**参考解答**：

- `file://` 协议问题：

  1. **跨域问题**：HTML 中本地媒体资源如果用 \`file://\`，会触发浏览器跨域安全限制，无法播放

  2. **权限问题**：\`file://\` 可以直接访问任意本地路径，容易被恶意利用，不符合最小权限原则

  3. **不支持 Range 请求**：视频播放器无法拖动进度条到未加载部分，只能从头播放

- 自定义协议解决：

  1. 注册自定义协议（比如 `miaoma://`），自己处理资源请求
  2. 做路径安全校验，确保只能访问项目目录内的资源，防止路径遍历攻击
  3. 完整支持 Range 请求，播放器可以正常拖动进度
  4. 解决跨域问题，因为自定义协议我们自己控制响应头

#### **2. 什么是路径遍历攻击，本项目中是如何防护的？**


**参考解答**：

- 路径遍历攻击：攻击者构造特殊文件名（比如 `../../etc/passwd`），如果应用直接拼接路径没有校验，攻击者可以访问项目目录外的敏感文件

\- 本项目**双层防护**：

1. 文件名做字符过滤：只保留安全字符，特殊字符替换掉

  2. 解析后做包含校验：最终解析得到的绝对路径**必须以项目目录为前缀**，否则拒绝访问

  双层防护彻底杜绝路径遍历风险


#### **3. 本项目中为什么用 Zod 做数据校验，AI 项目中为什么尤其需要结构化校验？**


**参考解答**：

\- Zod 价值：**定义一次 Schema，同时得到 TypeScript 类型和运行时校验**，不需要重复定义

\- AI 项目为什么尤其需要：大模型输出格式不稳定，偶尔会缺字段、类型不对，如果没有校验，错误格式会导致后续流程崩溃；Zod 校验可以在数据进入业务逻辑之前就发现错误，方便重试或者降级，**提升系统稳定性**

\- 本项目应用：从 LLM 输出、项目文件读取到 IPC 通信，都用 Zod 做校验，**全链路**保证数据格式正确


### **AI 与智能体类**


#### **1. Vibe Coding 和 Spec Driven Development 各自适用什么场景，本项目中是如何结合使用的？**


**参考解答**：

\- **Vibe Coding**：特点是快速迭代，先做出来再慢慢调整，适合**需求不明确的探索阶段**，比如原型验证、新技术预研、创意方向探索；优势是快，劣势是容易失控，适合小范围探索

\- **Spec Driven**：先写清楚规格说明书，再拆解任务开发，规格作为团队协作的**统一语言和唯一真相来源**，适合**需求明确的稳定开发阶段**；优势是质量可控，适合生产级功能开发

- 本项目结合：探索阶段（比如尝试 LangGraph 不同编排方式）用 Vibe Coding 快速验证方向；方向确定后，核心功能（比如数据模型、智能体节点、导出模块）切换到 Spec Driven，先定义 Schema 和接口再开发，保证质量，平衡效率和可控性

#### **2. AI 输出格式不稳定有哪些常见解决方法，本项目中完整的稳定化链路是什么？**


**参考解答**：

- 常见方法：Prompt 约束、JSON Mode、Function Calling、Grammar 约束、运行时校验、失败重试

\- 本项目**生产级完整链路**：

  1. **Schema 定义**：用 Zod 定义输出结构，同时得到类型和校验

  2. **模型约束**：转换为 Function Calling 定义，让模型严格按照格式输出

  3. **运行时兜底**：模型输出后用 Zod 做强校验

  4. **失败自动重试**：校验失败，把错误信息返回给模型，让它修正，最多重试 2 次

  5. **最终降级**：还是失败就抛出错误，让用户重试，不会导致整个流程崩溃

- 通过这五层，把 AI 输出格式错误率降到非常低，满足生产环境可用性要求

#### **3. 本项目中分镜审批为什么要设计中断机制，不中断直接跑完有什么问题？**


**参考解答**：

\- 如果不中断，AI 全程跑完，用户不满意分镜结果，**需要从头重新生成**，浪费时间和 token；而且用户无法在流程中给出反馈调整

\- 中断机制价值：生成分镜后暂停，让用户评审，可以直接通过，也可以给出反馈修改，修改后**继续从断点往下走**，不需要从头重新跑，节省时间和成本，提升人机协作体验，这也是 LangGraph Checkpoint 机制在本项目的核心应用
