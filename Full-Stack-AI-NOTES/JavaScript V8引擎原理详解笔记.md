# JavaScript V8引擎原理详解笔记

## 什么是 JavaScript V8 引擎

JavaScript 拥有众多引擎，其中V8引擎是最广为人知、应用最广泛的一款，以下是主流JS引擎的详细介绍：

• V8 (Google)：用C++编写，开放源代码，由Google丹麦团队开发，是Google Chrome浏览器的核心组件之一，同时也被Node.js采用，是前端和后端JS运行的核心依赖。

• JavaScriptCore (Apple)：开放源代码，主要用于WebKit内核的浏览器（如Safari），2008年通过实现编译器和字节码解释器，升级为SquirrelFish；苹果内部代号为“Nitro”的JavaScript引擎，其底层也是基于JavaScriptCore开发的。

• Rhino：由Mozilla基金会管理，开放源代码，完全以Java编写，主要用于HTMLUnit等工具，在Java环境中执行JavaScript代码。

• SpiderMonkey (Mozilla)：第一款JavaScript引擎，早期用于Netscape Navigator浏览器，目前主要应用于Mozilla Firefox浏览器，是JS引擎发展的基础。

**V8引擎执行JavaScript代码的核心流程（从代码获取到执行完成）：**

1. 始于从网络中获取JavaScript代码（如前端页面加载的JS文件、Node.js读取的本地JS文件）；

2. V8引擎解析源代码，将其转化为抽象语法树（AST，abstract syntax tree），AST是对代码结构的抽象表示，不包含具体执行细节，仅保留语法结构；

3. 基于生成的AST，Ignition基线解释器开始工作，将AST转化为字节码（字节码是介于源代码和机器码之间的中间代码，可被引擎快速解释执行）；

4. 此时引擎开始执行字节码，并在执行过程中收集类型反馈（如变量的类型、函数的调用方式等），为后续优化提供数据支撑；

5. 为了提升执行速度，字节码会与收集到的类型反馈数据一起，发送到TurboFan优化编译器；优化编译器基于这些数据做出合理假设（如变量类型固定），进而生成高度优化的机器码；

6. 若执行过程中，优化编译器的某个假设被证明是错误的（如变量类型发生变化），则会触发“去优化”操作，放弃优化后的机器码，重新回到Ignition解释器执行字节码。

## 什么是JS的垃圾回收机制

垃圾回收（Garbage Collection，简称GC）的核心目标是：自动识别不再被程序使用的内存，并释放它，避免内存浪费和内存溢出。

JavaScript是一门自动内存管理语言，开发者无需像C/C++那样手动通过`free`函数释放内存，但这并不意味着JS不会出现内存问题——自动管理不代表“无懈可击”，不当的代码编写仍会导致内存泄漏。

核心关键：只要某个对象“仍然可达”（即存在从根集合到该对象的引用链），垃圾回收器就不会回收它。因此，JS内存问题的本质不是“没法回收”，而是“本该无用的对象仍被引用，导致GC判断其存活，进而引发内存泄漏”。

### JS内存的基本生命周期

JS中内存的生命周期分为3个核心步骤，贯穿对象从创建到销毁的全过程，每个步骤都与垃圾回收密切相关：

##### 分配内存

当创建变量、对象、数组、函数等时，JS引擎会自动为其分配内存空间，存储对应的数据。不同类型的数据，分配的内存区域不同（如基本类型存在栈内存，引用类型存在堆内存）。

```javascript
// 基本类型变量分配内存（栈内存）
let num = 1;
// 对象分配内存（堆内存，栈内存存储对象引用地址）
let obj = { name: "Tom" };
// 数组分配内存（堆内存）
let arr = [1, 2, 3];
// 函数分配内存（堆内存，存储函数定义）
function foo() {};
```

##### 使用内存

对已分配的内存进行操作，包括读取、修改、传参、闭包引用等，都属于内存的使用。本质是通过引用（栈内存中的地址）访问堆内存中的数据，或直接操作栈内存中的基本类型数据。

```javascript
// 读取内存（访问对象属性，通过栈引用访问堆内存数据）
console.log(obj.name);
// 修改内存（修改数组元素，操作堆内存中的数据）
arr.push(4);
// 传参使用内存（函数调用时，将栈内存中的num值传递给函数参数）
foo(num);
```

##### 回收内存

当某块内存对应的对象不再可访问（即从根集合出发，无法找到该对象的引用链）时，GC会在合适的时机（如内存占用达到阈值、JS执行空闲时）自动回收该内存，释放空间供后续使用。回收后，该内存区域可被重新分配给新的对象。

### 垃圾回收的核心判断标准：可达性

现代JS垃圾回收的核心思想是：从一组根对象（根集合，Root Set）出发，能通过引用链访问到的对象就是“可达”的；不可达的对象（无法从根集合访问到），说明不再被程序使用，才会被GC回收。

注意：GC并非从单一“根对象”出发，而是从一组“根集合”（天然被认为仍在使用的引用）开始遍历，这一表述更严谨——根集合是GC判断对象存活的“起点”。

常见根集合（根对象）包括：

• 全局对象：浏览器环境中是`window`，Node.js环境中是`global`，全局对象及其属性始终可达；

• 当前执行栈中的局部变量：正在执行的函数内部的局部变量，必然是可达的（因为函数正在执行，需要使用这些变量）；

• 函数调用链中的变量：调用栈中未执行完的函数相关变量（如父函数的变量、参数），也是可达的；

• DOM引用链：文档树中存在的DOM节点，或被JS变量引用的DOM节点（只要DOM节点在文档树中，或被JS引用，就是可达的）；

• 系统保留的内部引用：浏览器宿主环境保留的引用（如事件监听器、定时器回调、WebSocket连接等），这些引用对应的对象会被认为是可达的。

示例：可达性判断

```javascript
// 分配对象，obj变量（栈内存）引用该对象（堆内存），对象可达
let obj = { name: "Alice" };
// 取消obj对该对象的引用，若无其他引用，对象变为不可达
obj = null;
```

说明：obj赋值为`null`后，原来的对象若没有其他引用（如没有其他变量指向它、没有闭包持有它），则无法从根集合（如window）访问到，后续GC执行时会将其标记为垃圾并回收。

补充示例：循环引用的可达性

```javascript
// 两个对象互相引用（循环引用）
let a = {};
let b = {};
a.b = b;
b.a = a;

// 取消根集合对a、b的引用
a = null;
b = null;
```

说明：虽然a和b互相引用（形成循环引用），但两者均已脱离根集合（没有全局变量、执行栈变量指向它们），整体不可达，现代JS引擎（如V8）可正常回收这两个对象，不会造成内存泄漏——这也是现代GC算法的核心优势。

### 常见垃圾回收算法

JS垃圾回收算法经过多代迭代，目前主流引擎（如V8）采用多种算法结合的方式，兼顾回收效率和性能，以下是核心算法的详细解析：

#### 引用计数（了解即可）

###### 核心思想

通过记录一个对象被引用的次数，判断其是否可回收：引用次数>0，说明对象仍被使用，不可回收；引用次数=0，说明对象不再被使用，可回收。

###### 核心问题

无法处理循环引用，这是其被现代JS引擎淘汰的主要原因。当两个对象互相引用时，即使外界已无任何引用指向它们，它们的引用次数仍然都是1，引用计数算法会认为它们仍在使用，无法回收，从而造成内存浪费。

```javascript
function test() {
  let a = {};
  let b = {};
  // 循环引用：a引用b，b引用a
  a.b = b;
  b.a = a;
}
```

说明：函数test执行结束后，a和b作为函数内部的局部变量，本应被释放，但由于两者互相引用，引用次数均为1，引用计数算法无法回收它们，导致内存浪费。

###### 结论

引用计数不是现代JS引擎的主流方案，仅作为了解即可，现代引擎均采用基于“可达性”的算法。

#### 标记清除（Mark-and-Sweep）——核心算法

现代浏览器和JS引擎的核心垃圾回收算法，基于“可达性”判断，可完美解决循环引用问题，是GC的核心逻辑。

###### 核心流程

标记清除算法的执行过程分为“标记”和“清除”两个核心阶段，具体流程如下：

1. 标记阶段：垃圾收集器在运行时，会给内存中的所有对象都加上一个初始标记（假设内存中所有对象都是垃圾，默认标记为0）；

2. 遍历阶段：从根集合出发，遍历所有可达的对象，将这些“非垃圾”对象的标记修改为1（标记为存活）；

3. 清除阶段：清理所有标记为0的垃圾对象，销毁这些对象，并回收它们所占用的内存空间；

4. 重置阶段：将内存中所有存活对象的标记修改为0，等待下一轮垃圾回收（为下一次标记做准备）。

###### 核心优点

实现简单，标记逻辑清晰——仅需用一个二进制位（0和1）即可完成标记，无需复杂的引用计数计算；同时能完美处理循环引用，只要对象不可达，无论是否存在循环引用，都会被回收。

###### 关键疑问解析

1. 根对象参与的循环引用，能回收吗？

不能。若循环引用的对象仍被根集合引用（即可达），GC标记时会从根集合出发找到这些对象，标记为存活，因此不会被回收。

示例：

```javascript
let a = {};
let b = {};
a.b = b;
b.a = a;
```

说明：a是全局变量（根集合中的引用），可直接访问；b可通过a.b访问，两者都会被标记为存活，因此不会被回收。

2. 循环引用脱离根集合后，能回收吗？

能。当循环引用的对象不再被根集合引用（不可达）时，GC从根集合出发无法找到它们，不会被标记为存活，最终会被回收。

示例：

```javascript
let a = {};
let b = {};
a.b = b;
b.a = a;
a = null;
b = null;
```

说明：a和b被赋值为`null`后，没有全局变量、执行栈变量指向它们，也没有其他根链路能访问到它们，因此不会被标记，最终会被回收。

3. 为什么标记清除能处理循环引用？

因为标记清除的核心判断依据是“对象是否可达”（能否从根集合走到该对象），不关心对象之间互相引用的次数；而引用计数的核心是“引用次数”，无法区分“循环引用”和“有效引用”。

引用计数的问题：即使外部已无引用，循环引用的对象彼此计数仍不为0，无法回收；标记清除的优势：只要根集合无法到达，无论对象内部如何循环引用，都会被视为垃圾。

4. 如何理解“根对象循环引用”？

该说法易混淆，可拆分为两种情况：

情况一：根引用还在——对象自引用，但根引用未断开，无法回收。

```javascript
let root = {};
root.self = root; // 对象自引用
```

说明：root是全局变量（根引用），即使对象自引用，root仍指向该对象，对象可达，因此无法回收。

情况二：根引用断开——对象自引用，但根引用已断开，可回收。

```javascript
let root = {};
root.self = root;
root = null; // 断开根引用
```

说明：root被赋值为`null`后，原来的对象虽然自引用，但已从根集合不可达，因此可以被回收。

###### 缺点

标记清除算法的核心缺点是：清除垃圾后，剩余的存活对象内存位置不变，会导致空闲内存空间不连续，出现“内存碎片”。由于剩余空闲内存是零散的小块，后续分配大块内存时，可能因没有足够大的连续空闲内存，导致无法分配（即使总空闲内存足够），影响内存分配效率。

#### 标记整理/压缩（Mark-Compact）

标记整理/压缩是标记清除的补充优化算法，核心目的是解决标记清除导致的内存碎片问题，提升后续内存分配效率。

核心流程：

1. 标记阶段：与标记清除算法一致，从根集合出发，标记所有存活对象；

2. 整理阶段：将所有存活对象移动到一起，紧凑排列在内存的一端，消除内存碎片；

3. 压缩阶段：更新所有存活对象的引用地址（因为对象位置移动，原来的引用地址失效），确保程序能正确访问对象；同时释放内存末尾的空闲内存块（连续的大块空间），供后续分配使用。

作用：提升后续内存分配效率，避免因内存碎片过多导致无法分配大块内存（如创建大数组、大对象时）。

#### 分代回收（Generational GC）——重要优化思想

分代回收是基于“大部分对象生得快、死得也快，只有少数对象长期存活”的核心假设（分代假说）设计的优化算法，通过将内存分为不同代，采用不同的回收策略，大幅提升GC效率，减少GC对JS执行的影响。

###### 内存分代

现代JS引擎（如V8）将内存分为两代，分别对应不同生命周期的对象：

• 新生代（Young Generation）：存放新创建的对象，内存空间较小（通常几MB），对象生命周期短（如函数临时变量、请求中间结果，大多执行完后就会被回收）；

• 老生代（Old Generation）：存放经过多次GC仍然存活的对象，内存空间较大（通常几十MB到几百MB），对象生命周期长（如全局变量、长期缓存、DOM节点等）。

###### 回收特点

• 新生代GC（Minor GC）：回收频率高、速度快，适合短生命周期对象。由于新生代对象大多很快会被回收，回收成本低，通常采用高效的复制算法；

• 老生代GC（Major GC）：回收频率低、速度慢（回收成本高），适合长期存活对象。老生代对象存活比例高，若采用复制算法，会消耗大量资源，因此通常采用标记清除+标记整理结合的方式。

###### 设计原因

大多数临时对象会快速失效（如函数执行完后，内部局部变量就无用了），针对不同生命周期的对象采用不同回收策略，可避免“一刀切”的回收方式——无需对所有对象都进行复杂、耗时的回收操作，从而大幅提升垃圾回收的整体效率，减少GC停顿对JS执行的影响。

#### V8引擎中常见的垃圾回收思路

浏览器（如Chrome）和Node.js均常用V8引擎，面试中掌握V8的回收思路即可满足要求。V8引擎基于分代回收思想，对新生代和老生代采用完全不同的回收策略，兼顾效率和性能。

##### 新生代回收

###### 1. 什么时候触发

新生代空间较小（V8中通常为1-8MB），新创建的对象会优先分配到新生代，因此很快就会把新生代空间填满，触发Minor GC（新生代回收）。V8的设计正是基于“多数对象死得很快”这个分代假说，因此Minor GC的触发频率很高。

###### 2. 新生代的核心思路

新生代主要使用Scavenger（复制/疏散）思想，V8的新生代采用semi-space（半空间）设计：将新生代内存分为两块大小相等的空间，一块作为当前分配区（From-Space），另一块预留为空（To-Space）；回收时，仅复制存活对象到To-Space，从而顺便完成压缩整理，避免内存碎片。

###### 3. 新生代回收的完整流程

第一步：找到根。Minor GC不会扫描整个老生代（避免消耗过多资源），而是从以下根开始，寻找新生代中的存活对象：

• 调用栈中的引用（当前执行函数的局部变量）；

• 全局引用（window/global上的变量）；

• 老生代指向新生代的引用（通过write barrier和remembered set记录，避免每次扫描整个老生代）。

第二步：标记/发现年轻代中的存活对象。GC从上述根出发，遍历From-Space，找到所有仍可达的存活对象，并标记这些对象。

第三步：复制存活对象。存活对象不会留在From-Space，而是被复制/疏散到To-Space，复制时会根据对象的“年龄”（经历GC的次数）判断是否晋升：

• 还比较“年轻”的对象（经历GC次数少），复制到To-Space的对应区域；

• 已经经历过一次或多次GC、达到晋升条件的对象，会被提升到老生代（认为这类对象生命周期较长，适合放在老生代，减少新生代GC的频率）。

V8文档明确提到：对象先在nursery（新生代的初始分配区），存活一次后进入intermediate（新生代的过渡区），再存活一次后进入old generation（老生代）。

第四步：更新引用。对象被复制到To-Space后，原来的地址失效，因此所有指向这些对象的指针（如其他对象的属性、变量引用）都要更新到新的地址，确保程序能正确访问对象。

第五步：整体切换空间。复制完成后，From-Space中未被复制的对象（垃圾）会被整体丢弃，释放From-Space的内存；随后，To-Space变成新的From-Space，原来的From-Space变成新的To-Space，等待下一次Minor GC。由于存活对象都被重新紧凑排列，新生代回收后天然没有内存碎片。

###### 4. 新生代流程记忆口诀

找根 → 找活对象 → 复制存活对象 → 晋升部分对象到老生代 → 更新指针 → 丢弃旧空间

##### 老生代回收

###### 1. 什么时候触发

当老生代中存活对象的大小增长到某个启发式阈值以上时，会触发Major GC（老生代回收）。老生代对象数量多、生命周期长、占用内存大，因此Major GC的触发频率低，但回收过程更重（耗时更长）。

###### 2. 老生代的核心思路

老生代主要依赖标记-清除（Mark-Sweep）算法，回收未标记的垃圾对象；并在内存碎片严重时，配合标记-整理/压缩（Mark-Compact）算法，减少内存碎片。此外，V8还引入了增量标记、并发标记、并发清扫等机制，目的是缩短主线程停顿时间（避免GC导致页面卡顿）。

###### 3. 老生代回收的完整流程

第一步：从根集合开始标记。GC从根集合（全局对象、执行栈变量、DOM引用等）出发，遍历整个老生代的对象图，把所有仍可达的对象标记为存活。V8官方将这个过程描述为一张图遍历：根对象是起点，沿着指针不断找到更多对象，直至遍历完所有可达对象。

第二步：增量/并发地推进标记。为了避免一次性长时间Stop-The-World（暂停主线程，导致页面卡顿），V8会把标记过程拆成很多小步骤，穿插在JS执行过程中（增量标记）；同时，会利用专门的工作线程做并发标记（主线程执行JS，工作线程进行标记），减少主线程的停顿时间。

第三步：清除未标记对象。标记结束后，未被标记的对象就是不可达的垃圾对象，它们占用的内存空间会被回收（清扫）。V8文档提到，清扫过程可以由专门的sweeper线程并发执行，不占用主线程资源，进一步减少卡顿。

第四步：必要时做压缩整理。老生代不像新生代那样每次都通过复制自然变紧凑，因此多次回收后可能留下很多内存碎片。如果碎片问题明显（如无法分配大块内存），V8会执行压缩整理操作，把存活对象搬到更紧凑的位置，并更新相关指针。V8明确说明：并不是每次Major GC都会压缩，而是“只压缩一部分碎片严重的页”，因为复制长期存活的大对象本身也会消耗大量资源，需权衡效率。

###### 4. 老生代流程记忆口诀

从根开始标记 → 增量/并发推进 → 清除未标记对象 → 需要时压缩整理碎片

##### 为什么新生代和老生代回收流程不同

新生代：大多数对象都“刚创建不久就死掉”，存活对象比例低，因此最划算的做法不是在原地细抠垃圾，而是快速找出少量活对象，把它们复制到新空间，剩下的整片空间直接废弃——这样回收成本主要跟“活下来的对象数”相关，而非“分配过多少对象”，效率极高。

老生代：老生代里活对象比例高，而且对象通常更大、活得更久。如果像新生代那样每次全量复制，需要消耗大量的内存和CPU资源，成本极高，因此更适合先标记谁活着，再清除死对象，只有在碎片严重时才进行压缩整理，平衡效率和内存利用率。

##### GC影响性能的原因

垃圾回收过程中，JS引擎会暂停当前JS执行（即“GC停顿”，Stop-The-World），执行以下操作：

• 扫描所有对象，确定存活状态；

• 标记存活对象，区分垃圾对象；

• 清理垃圾对象，释放内存；

• （可选）整理内存碎片，更新对象引用。

若某次GC操作过重（如Major GC），停顿时间过长（超过16ms，人眼可感知卡顿），会导致：页面卡顿、JS执行停顿、渲染不流畅（如动画卡顿、点击无响应）。V8引入的增量标记、并发标记等机制，都是为了缩短GC停顿时间，减少对性能的影响。

## 什么是内存泄漏

内存泄漏不是指“内存不会释放”，而是指：本来已经不需要使用的内存（对应的对象已无实际用途），因为仍然被引用（可达），导致无法被垃圾回收，长期占用内存的现象。

内存泄漏的长期影响（随着页面运行时间增长，影响会越来越明显）：

• 页面越来越卡，响应速度变慢（内存占用过高，JS执行和渲染资源被占用）；

• 内存占用持续增长，即使执行GC后也无法回落；

• 浏览器标签页崩溃、移动端页面白屏或闪退（内存占用超过浏览器/设备上限）；

• Node.js服务内存飙升，导致服务崩溃（后端JS内存泄漏的严重后果）。

### 常见内存泄漏场景（前端高频考点）

以下是前端开发中最常见、面试最常考的内存泄漏场景，每个场景附示例、问题分析和解决方案，覆盖高频考点：

#### 1. 意外的全局变量

###### 场景

变量未使用`let / const / var`声明，会自动挂到全局对象（window）上，成为全局变量，生命周期与页面一致。

```javascript
function foo() {
  // 未声明变量，非严格模式下挂到window上
  name = "Tom";
}
foo();
```

###### 问题

全局变量的生命周期与页面一致，只要页面不关闭，变量就会一直存在，占用内存；若变量引用大对象（如大数组、DOM节点），会造成严重的内存泄漏。

###### 解决方案

• 变量声明必须使用`let / const`（优先，块级作用域，避免全局污染）或`var`（函数级作用域）；

• 开启严格模式（`'use strict'`），禁止未声明变量的使用（未声明变量会报错，提前发现问题）；

• 使用ESLint工具，检查未声明变量，提前规避问题。

#### 2. 闭包使用不当

核心说明：闭包本身不是内存泄漏，是JS正常的语言特性（让内部函数可以访问外部函数的变量，延长外部变量的生命周期）；只有闭包长期存在，且持有外部无用的大对象时，才会导致内存泄漏。

###### 场景

```javascript
function outer() {
  // 大对象，本应使用后释放
  const hugeData = new Array(1000000).fill("data");
  // 闭包持有hugeData引用
  return function inner() {
    console.log(hugeData.length);
  };
}
// fn长期存在（挂到全局），导致hugeData无法回收
const fn = outer();
```

###### 问题

`fn`长期存在（如挂载到全局），闭包`inner`会一直持有`hugeData`的引用，即使`hugeData`已无实际用途（如无需再访问其长度），也无法被GC回收，导致大对象长期占用内存。

###### 解决方案

• 避免在闭包中无意义持有大对象、DOM节点等占用内存大的资源；

• 闭包使用完毕后，将引用置空（如`fn = null`），断开闭包的引用链；

• 缩小闭包持有的数据范围，仅保留必要的引用（如无需持有整个大对象，仅持有需要的属性）。

#### 3. 定时器未清除

###### 场景

```javascript
// 定时器持续执行，未手动清除
const timer = setInterval(() => {
  console.log("running");
}, 1000);
```

###### 问题

若页面组件销毁（如React/Vue组件卸载），但定时器未清除，定时器会持续执行，回调函数会一直存在，回调中引用的变量（如组件实例、DOM节点）也会一直存活，无法被回收，导致内存泄漏。

###### 解决方案

• 使用`clearInterval(timer)`清除定时器，`clearTimeout(timer)`清除延时器，确保定时器在不需要时被销毁；

• 组件卸载时（React的useEffect清理函数、Vue的onUnmounted钩子），必须清理对应的定时器，避免组件销毁后定时器仍在运行。

#### 4. 事件监听未移除

###### 场景

```javascript
// 给window绑定事件监听，未移除
function handleResize() {
  console.log("resize");
}
window.addEventListener("resize", handleResize);
```

###### 问题

绑定在`window`、`document`或DOM节点上的事件监听，若未移除，回调函数会一直存在，回调引用的上下文（如组件实例、DOM节点）也无法释放；即使DOM节点被删除，若事件监听未移除，相关引用仍会存在，导致内存泄漏。

###### 解决方案

• 使用`removeEventListener`移除对应事件监听，确保回调函数引用一致（不能使用匿名函数，否则无法移除）；

• 组件卸载、DOM节点删除时，必须清理对应的事件监听，断开引用链。

#### 5. DOM被移除，但JS仍持有引用

###### 场景

```javascript
// 获取DOM节点并引用
let btn = document.getElementById("btn");
// 从页面中删除DOM节点，但JS引用未清除
document.body.removeChild(btn);
```

###### 问题

DOM节点虽然从文档树中删除（页面上看不到），但JS变量（`btn`）仍持有该节点的引用，导致DOM节点无法被GC回收，形成“游离DOM”（Detached DOM tree），长期占用内存。

###### 解决方案

DOM节点删除后，将对应的JS引用置空：`btn = null`，断开JS对DOM节点的引用，让GC能正常回收该节点。

#### 6. 缓存使用不当

###### 场景

将大量数据长期存入数组、对象、Map、Set等容器中，只增不减，形成“无限缓存”，数据不断累积，占用内存越来越大。

```javascript
// 缓存容器，只存不删
const cache = {};
// 持续存储数据，无淘汰机制
function store(key, value) {
  cache[key] = value;
}
```

###### 问题

缓存数据不断累积，没有淘汰机制，内存占用会持续增长，最终导致内存泄漏；尤其是缓存大对象、大量数据时，泄漏问题会更严重。

###### 解决方案

• 设置缓存上限，达到上限后淘汰旧数据（如保留最新的100条数据）；

• 使用LRU（最近最少使用）策略，淘汰长期未使用的缓存数据（常用的缓存优化策略）；

• 为缓存设置过期时间，定期清理过期数据（如使用定时器定期清理）；

• 无需强引用时，使用`WeakMap`/`WeakSet`存储缓存，让GC自动回收无引用的缓存数据。

#### 7. Map / Set 强引用导致对象不能释放

###### 场景

```javascript
const map = new Map();
let obj = { id: 1 };
// Map强引用obj作为key
map.set(obj, "data");
// 取消obj的引用，但Map仍持有引用
obj = null;
```

###### 问题

`Map`/`Set`对其key/value是强引用——即使外部取消了对对象的引用（如`obj = null`），`Map`/`Set`仍持有该对象的引用，导致对象无法被GC回收，形成内存泄漏。

###### 解决方案

若key/value是对象，且希望对象无其他引用时自动释放，使用`WeakMap`/`WeakSet`（对key是弱引用，不影响GC回收）：

```javascript
// WeakMap对key是弱引用，不影响对象回收
const weakMap = new WeakMap();
let obj = { id: 1 };
weakMap.set(obj, "data");
obj = null; // 对象无其他强引用，可被GC回收
```

#### 8. 控制台或调试工具保留引用

###### 场景

```javascript
// 调试时打印大对象
console.log(largeObject);
```

###### 问题

某些情况下，浏览器DevTools会保留`console.log`打印的对象引用，导致对象无法被回收，误以为出现内存泄漏（属于调试干扰，非真正的内存泄漏）。

###### 说明

该场景不属于真正的内存泄漏，但面试中提及，可体现知识点的全面性；调试时可避免打印大对象，或调试完成后清除控制台记录。

#### 9. 未取消的异步任务

###### 场景

未取消的Promise链、未中止的fetch请求、未关闭的WebSocket、未断开的Observer等异步任务，会一直持有相关引用。

```javascript
// MutationObserver未断开
const observer = new MutationObserver(() => {});
observer.observe(document.body, { childList: true, subtree: true });
```

###### 问题

这些异步任务或观察者会一直存活，持有相关引用（如回调函数、监听目标），导致内存无法释放；即使组件销毁，若未取消这些任务，仍会造成内存泄漏。

###### 解决方案

• Observer类：使用`observer.disconnect()`断开监听；

• fetch请求：使用`AbortController`取消请求（通过`signal`参数控制）；

• WebSocket：使用`websocket.close()`关闭连接；

• Promise链：使用`Promise.race()`结合`AbortSignal`取消，避免Promise链一直执行。

#### 10. React / Vue 组件卸载后仍保留引用

###### React常见场景

• useEffect中注册事件、定时器，未在清理函数中移除；

• 异步请求返回后，更新已卸载的组件状态（如setState）；

• 大对象挂在ref上，长期不释放。

```javascript
// React组件中正确清理定时器示例
useEffect(() => {
  const timer = setInterval(() => {
    console.log("tick");
  }, 1000);
  // 清理函数：组件卸载时清除定时器
  return () => clearInterval(timer);
}, []);
```

###### Vue常见场景

• onMounted中添加事件监听，onUnmounted中未解绑；

• keep-alive缓存组件时，未清理组件内部的状态和引用（如定时器、事件监听）。

## 垃圾回收与内存泄漏总结

### 高频面试问题解析

#### 闭包是不是内存泄漏（高频面试题）

核心答案：闭包本身不是内存泄漏。

详细解析：

• 闭包是JS的正常语言特性，其核心作用是让内部函数可以访问外部函数的变量，延长外部变量的生命周期（这是闭包的设计初衷，并非缺陷）；

• 只有在以下场景下，闭包才会引发内存问题：闭包长期存在（如挂载到全局）、闭包持有外部大对象、这些对象实际上已经不需要了（无实际用途，但仍被闭包引用）；

• 更准确的表述：闭包不是泄漏的原因，滥用闭包、长期持有无用引用才是导致内存泄漏的根本原因。

#### 为什么“循环引用”在现代JS里通常不是大问题

核心原因：现代JS垃圾回收的判断标准是“对象是否可达”，而非“引用次数”，这也是标记清除算法的优势。

示例解析：

```JavaScript

let a = {};
let b = {};
// 循环引用
a.b = b;
b.a = a;

// 取消根集合对a、b的引用
a = null;
b = null;
```

说明：虽然a和b互相引用，但两者均已脱离根集合，整体不可达，GC会将其标记为垃圾并回收，因此不会造成内存泄漏。

补充：只有循环引用的对象同时被根集合引用（即可达）时，才会无法回收，但这种情况并非循环引用本身导致，而是对象可达导致。

#### 如何判断页面是否发生内存泄漏

内存泄漏的常见表现，可通过以下现象初步判断：

- 页面长期运行后，响应速度越来越慢、越来越卡（如后台管理系统开久了变慢）。

- 切换路由后，内存占用不下降（正常情况下，离开页面后相关资源应被释放）。

- 重复打开/关闭弹窗、组件后，内存持续增长，无回落趋势。

- Chrome DevTools的Performance/Memory面板中，堆内存（Heap）持续上升，GC后仍不回落。

#### 前端如何排查内存泄漏

主要借助Chrome DevTools和手动复现，核心排查方法如下：

##### 1. Chrome DevTools的Memory面板（核心工具）

- Heap snapshot（堆内存快照）：拍摄堆内存快照，查看对象数量、大小，定位异常增多的对象（如Detached DOM tree）。

- Allocation instrumentation on timeline（时间线内存分配）：观察内存随时间的变化，定位内存增长的时间段和对应的操作。

- Retainers（引用链）：查看某个对象的引用链，分析其为什么还活着（被哪个根对象或其他对象引用）。

##### 2. Perforance面板

录制页面运行过程，查看是否存在频繁GC（多次GC标记），以及GC时是否出现明显的页面卡顿（JS执行停顿）。

##### 3. 手动复现法

通过重复操作，观察内存变化，定位泄漏场景：

- 进入可疑页面，执行目标操作（如打开弹窗、切换组件）10次以上。

- 返回初始页面，观察内存是否持续上涨且不回落。

- 若内存持续上涨，则该操作对应的场景可能存在内存泄漏。

##### 4. 重点关注的对象

排查时，重点关注以下对象的数量变化，若持续增多，大概率存在泄漏：

- Detached DOM tree（游离DOM节点）

- Listener（未移除的事件监听器）

- Closure（闭包引用）

- Array / Object / Map（缓存对象）

#### 如何避免内存泄漏

从工程实践角度，可通过以下方法规避内存泄漏，养成良好的开发习惯：

- 减少全局变量：能使用局部变量的，尽量不使用全局变量，避免变量长期挂在window上。

- 及时清理副作用：定时器、事件监听、订阅、WebSocket、Observer、动画帧（requestAnimationFrame）等，使用完毕后必须清理。

- 避免闭包长期持有大对象：闭包中仅保留必要的引用，无用引用及时置空。

- 缓存要有淘汰策略：缓存不能只存不删，需设置上限、过期时间或LRU策略。

- 组件销毁时做清理：React用useEffect清理函数，Vue用onUnmounted钩子，清理定时器、事件监听等。

- 对象作为key时考虑WeakMap/WeakSet：无需强引用的场景，使用弱引用，避免无意义的引用持有。

#### WeakMap / WeakSet 为什么能帮助避免泄漏

核心原因：WeakMap/WeakSet对其key/value是“弱引用”，不会影响GC对对象的回收，当对象无其他强引用时，可被正常回收。

##### WeakMap 核心特点

- key只能是对象，不能是基本类型（如字符串、数字）。

- 对key是弱引用，不干扰GC对key对象的回收。

- 当外部没有其他强引用指向key对象时，GC会回收该对象，同时自动移除WeakMap中对应的键值对。

##### 示例

```JavaScript

const wm = new WeakMap();
let obj = {};
// 弱引用obj作为key
wm.set(obj, "data");

// 取消obj的强引用，obj可被GC回收
obj = null;
```

##### 适用场景

WeakMap/WeakSet适合用于：DOM节点关联数据、私有元数据、临时缓存等无需强引用的场景。

#### 模板1：回答“JS垃圾回收机制”
JavaScript采用自动垃圾回收机制，核心是根据对象的可达性来判断是否需要回收。GC会从根集合出发，遍历所有能够访问到的对象，并做存活标记；未被标记到的对象说明已经不可达，会在后续被回收。

现代引擎主要基于标记清除算法，可解决循环引用问题；为了提升性能，像V8引擎还引入了分代回收机制，把对象分为新生代和老生代：新生代对象生命周期短，回收频繁、速度快；老生代对象存活时间长，回收成本更高，采用标记清除、标记整理和增量标记结合的方式。

虽然开发者不用手动释放内存，但如果存在无用引用，比如未清理的定时器、事件监听、闭包持有大对象、全局变量或缓存不释放，仍然会导致内存泄漏。

#### 模板2：回答“什么情况下会内存泄漏”
内存泄漏的本质是本来应该释放的对象，因为仍然可达而无法被GC回收。前端常见场景包括：

1. 意外的全局变量，未声明的变量挂到window上；
2. 闭包长期持有无用的大对象；
3. 定时器、事件监听未清理；
4. DOM节点移除后仍被JS引用；
5. 缓存无限增长，没有淘汰策略；
6. Map/Set强引用对象，导致对象无法回收；
7. 未取消的异步任务、订阅和Observer；
8. React/Vue组件卸载后，副作用未清理。

#### 模板3：面试前快速背诵精简版
JavaScript的垃圾回收机制是自动的，核心依据是对象是否可达。现代引擎通常使用标记清除，并结合分代回收来提升效率：新生代对象生命周期短，回收频繁；老生代对象存活时间长，回收成本更高。
内存泄漏的本质是无用对象仍然被引用，导致GC无法回收。常见场景包括全局变量、闭包持有大对象、未清理的定时器和事件监听、DOM引用残留、缓存无限增长，以及组件卸载后副作用未清理。

### 高频易错点（面试避坑）

- GC不是“立刻回收”：对象不可达后，不会马上被释放，而是等待GC的下一次执行（合适的时机）。
- `obj = null`不一定立刻释放：只是取消了一个引用，对象是否回收，取决于是否还有其他强引用。
- 闭包不是洪水猛兽：闭包本身是正常特性，只有滥用闭包、长期持有无用引用时，才会引发内存问题。
- 循环引用不等于一定泄漏：现代JS引擎基于可达性判断，单纯的循环引用，若整体不可达，可正常回收。
- console.log可能干扰调试：某些情况下，DevTools会保留console.log打印的对象引用，导致误判内存泄漏。

### 核心总结
- JS垃圾回收的核心是“分代式垃圾回收”，根集合是可达性判断的起点，标记清除是现代引擎的核心算法。
- 分代回收是V8引擎的重要优化，区分新生代和老生代，提升GC效率，减少性能影响。
- 内存泄漏的本质是“无用对象仍被引用”，核心规避方法是“及时清理无用引用、避免强引用滥用”。
