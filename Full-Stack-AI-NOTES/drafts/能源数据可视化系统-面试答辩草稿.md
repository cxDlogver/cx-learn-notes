## 1. 项目介绍与个人工作重点

### 【提问】

**请简单介绍一下全球清洁能源开发潜力评估系统。你在项目中主要承担了什么工作，重点解决了哪些技术问题？**

### 【回答要点】

这道问题先回答“项目是什么、面向谁、我的工作是什么、主要技术挑战在哪里”，不急于展开瓦片加载、LOD、缓存与渲染的所有实现细节。

- **业务背景**：面向科研机构的全球清洁能源开发潜力评估系统，通过地图与图表展示全球不同区域、不同时间尺度下的能源数据，辅助研究人员理解能源资源的空间分布与开发潜力。
- **个人工作**：参与前端地图可视化开发，重点负责大规模能源数据在地图上的加载、展示与性能优化。
- **核心挑战**：全球尺度数据覆盖范围广、栅格数据规模大，地图在初始加载、平移和缩放时容易产生网络请求量大、重复加载以及浏览器绘制压力增高的问题，进而影响地图加载速度和交互流畅性。
- **主要设计方向**：围绕**资源缓存、请求优化与分层渲染**组织性能优化，而不是把性能问题仅归结为某个地图组件的绘制效率；在必要时再延伸到瓦片化、按缩放级别选择数据精度（LOD）、无效请求控制与栅格/矢量图层职责等具体实现。
- **目标与价值**：降低不必要的数据传输、重复请求和渲染开销，提高大规模数据场景下地图加载及缩放、拖动交互的稳定性。

### 【标准回答】

我参与的项目是一个**全球清洁能源开发潜力评估系统**，主要面向科研机构，通过地图和图表展示不同地区、不同时间尺度的清洁能源数据，帮助研究人员直观分析全球能源资源的空间分布和开发潜力。

在这个项目中，我重点参与的是**大规模地理数据的地图展示与性能优化**。

由于系统需要展示全球范围的数据，在地图加载、缩放和拖动过程中，容易面临数据请求量大、资源加载慢，以及大量数据同时渲染导致页面卡顿等问题。

因此，我主要围绕**资源缓存、请求优化和分层渲染**三个方向展开优化，减少不必要的数据传输和地图绘制开销，提升地图加载速度与交互流畅性。

## 2. 全球能源地图性能开销的主要来源

### 【提问】

**全球清洁能源开发潜力评估系统为什么需要进行地图性能优化？造成性能开销的主要原因是什么？既然使用了 OpenLayers 和瓦片化，为什么仍可能出现加载缓慢、缩放和拖动卡顿？**

### 【回答要点】

#### 【核心结论：数据规模决定潜在成本，视图变化让成本反复产生】

这个项目的性能压力不是单纯因为“地图需要绘制很多数据”，而是**全球尺度的数据覆盖广、空间精度要求高，地图又必须随着用户查看不同区域和缩放级别持续重新选择、获取、处理和绘制数据**。

与加载后就不再变化的静态图片不同，地图至少有两类性能目标：

- **加载体验**：当前视图所需的数据、图片资源什么时候能够返回，并经过解码和绘制后显示出来。这里主要受资源体积、网络请求、缓存和图像处理成本影响。
- **交互流畅度**：已经显示的地图在拖动、缩放、点击时是否能及时响应。这里主要受绘制工作量、几何计算、主线程负担、DOM 更新和帧时间影响。

二者并不等价：网络很快不意味着绘制一定流畅；绘制很轻也不意味着瓦片一定能迅速下载完成。

#### 【从实际操作建立完整的开销链路】

以用户打开全球太阳能分布地图、逐步放大到中国和某个省份为例：

~~~text
用户打开全球地图
      ↓
初始化 Map / View，加载底图、注记与能源业务图层
      ↓
根据可见地理范围、投影、缩放级别计算需要的瓦片
      ↓
优先复用已有瓦片 → 获取当前视图仍缺失的瓦片
      ↓
瓦片服务生成或读取数据 → 网络传输至浏览器
      ↓
浏览器接收、解码图片、分配资源并绘制图层
      ↓
用户不断拖动、放大或缩小地图
      ├─ 视图改变后，部分区域需要新的瓦片
      ├─ 已加载的瓦片在符合条件时可以复用
      ├─ 先前请求可能仍在途或已经不再有业务价值
      └─ 标记点、矢量交互与弹窗可能需要重新定位
      ↓
以上操作按需重复，产生新的网络、计算和绘制开销
~~~

这条流程说明的是**可能反复发生的局部工作**。OpenLayers 不会在每次平移时都必然重新下载全部瓦片：同一网格中可复用的瓦片可以继续显示，真正需要新增的资源由当前视图与缓存状态决定。

#### 【第一类成本：全球栅格数据范围广、精度高】

全球太阳能、风能等资源的空间分布常使用栅格数据表示，可以理解为把地理区域划分成连续的空间网格，各网格承载相应能源数值或可视化结果。全球覆盖范围越广、精度越高，原始数据规模越大。

假设用户只想在全球范围查看能源分布的大致趋势，却在前端一次性加载完整高精度栅格：

1. **不必要的网络传输**：大量细节并不处于当前屏幕的可视范围，或者在当前缩放级别根本分辨不出来。
2. **图片解码与内存压力**：图片传输格式经过压缩，不代表浏览器解码后的像素资源也很小；图片数量和尺寸仍会占用内存和图像处理资源。
3. **难以按观察尺度复用**：用户查看全球与查看局部地区需要不同精度；整图处理难以针对可见范围分配传输和绘制成本。

当前资料中的 OpenLayers TileWMS 将原本庞大的图像加载转化为**按当前视图获取瓦片**；TileGrid 通过 resolutions 指定不同缩放层级的空间分辨率，构成 LOD（Level of Detail，细节层级）设计的基础。

例如，项目记录的关键配置如下：

~~~javascript
const customTileGrid = new TileGrid({
  tileSize: 1024,
  origin: [-180, 90],
  resolutions: [
    0.703125,
    0.3515625,
    0.17578125,
  ],
});

const qgjMapSource = new TileWMS({
  url: baseURL + "/map/getmap",
  tileGrid: customTileGrid,
  // 实际代码还需配置 WMS 参数和瓦片加载鉴权
});
~~~

它说明不同缩放级别如何映射到瓦片分辨率、能源图层如何从瓦片服务获取图像；并不直接证明浏览器节省了多少流量，也不能单凭此配置认定服务端对所有缩放级别都已完成特定精度的数据预处理。

还要注意，**瓦片化只改变加载单位和范围，不会让图像解码、内存或绘制成本归零**。1024×1024 的瓦片也不是天然最优：瓦片越大，请求数可能更少，但单张下载与解码可能更重；瓦片越小则可能增加请求数量。需要真实测试权衡。

#### 【第二类成本：视图变化带来重复、并发和过期请求】

地图是一个持续交互系统。用户从全球视图连续放大至中国，再缩放到浙江，系统会根据视图生成新的瓦片请求；如果还伴随点击查询能源数据，可能同时存在多项业务接口请求。

这里应区分三种不同的浪费：

**1. 已经获取过的内容重复请求。** 用户返回此前区域或再次点击相同位置，如果没有有效缓存，可能重复消耗网络和服务端资源。瓦片可以使用 OpenLayers 自身的瓦片缓存并结合浏览器 HTTP 缓存；业务查询可单独设计请求缓存。

**2. 同一请求尚未完成，就再次发送。** 此时结果缓存尚未可用，可在业务接口层以请求键跟踪正在进行的 Promise，后续相同请求复用已有在途请求，避免并发重复。

**3. 用户已改变目标，旧请求却随后返回。** 例如先点击 A 区域、紧接着点击 B 区域，A 的请求如果最后返回并直接写入弹窗，就会覆盖当前 B 的结果。业务查询可以通过 AbortController 尽可能取消已无意义的旧请求，并辅以请求 ID 或控制器身份校验，禁止过期响应提交。

这几个机制各有作用，不应混淆：**缓存复用已完成结果，去重复用尚在途的相同请求，取消或版本校验处理不再需要的旧请求**。

项目资料中的这些示例主要针对地图点击获取能源数据等**业务接口**；OpenLayers TileWMS 内部的瓦片加载、缓存与生命周期机制是另一条链路，不能直接说所有瓦片请求都使用同一个业务请求缓存管理器。请求取消也不保证服务端已经停止计算。

#### 【第三类成本：图层叠加、图像处理与要素绘制】

地图不是一张普通图片，而是由不同职责的显示层共同构成：

| 内容 | 项目中的主要用途 | 可能产生的成本 |
| --- | --- | --- |
| 基础地图、注记和边界 | 帮助用户辨识地理位置 | 瓦片加载、图片解码和地图绘制 |
| 能源栅格图层（TileWMS） | 显示大范围能源热力分布 | 瓦片图像资源、叠加绘制与内存占用 |
| 矢量图层（VectorLayer） | 承载标记点、区域边界及少量需要交互的要素 | 几何处理、样式计算、绘制更新 |
| DOM 信息弹窗 | 展示点击位置的能源信息 | 坐标换算、位置更新、DOM 及浏览器布局绘制 |

如果把大量能源栅格值全部转化为前端矢量对象，再逐个管理、计算样式和绘制，浏览器需要处理的要素规模可能大幅增加。项目因此将**大范围能源热力图交给栅格图层显示，少量需要交互的点、线、区域交给矢量图层**，降低单一交互绘制链路的负担。

但“图层越多越好”并不成立。多个透明图层叠加、过量矢量要素、反复重建图层、不必要的样式更新和长时间保留大量瓦片，也可能带来额外的绘制与内存压力。

这个阶段真正要控制的是：**每次视图变化需要管理多少图像资源、多少几何对象，以及重新绘制多少内容**。

#### 【第四类成本：连续交互引起坐标计算和页面状态更新】

除地图本身的图层绘制之外，用户点击能源区域时，还需要执行交互链路：

~~~text
用户点击地图
    ↓
获取地图坐标并发起能源数据查询
    ↓
更新标记点、数据展示与弹窗
    ↓
地图坐标换算为容器像素 / 页面显示位置
    ↓
用户继续拖动与缩放
    ↓
判断标记点可见性、重新选择世界副本并校正弹窗位置
    ↓
提交必要的 DOM 或组件状态更新
~~~

在全球地图中，同一经纬度可能因水平方向的世界平铺而存在多个可见的世界副本。项目还需要对经度、视图范围、地图坐标到屏幕位置的关系进行处理，避免标记点与弹窗漂移或瞬移。

如果这些计算、DOM 测量和更新被绑定到频繁视图变化的回调里，就可能反复占用主线程，影响交互流畅性。

要特别注意事件机制：**OpenLayers 的 moveend 通常代表一次视图移动结束，并非每一帧都触发。** 在拖动过程中持续变化的视图事件、绘制回调，才更容易形成高频工作。因此不能笼统声称 moveend 每秒执行数十次，也不能不分场景对所有回调统一防抖。需要实时跟随的弹窗可能要持续进行轻量定位，而较重的数据查询或统计可以延后到移动结束。

#### 【四类成本如何对应性能优化】

| 性能开销来源 | 典型表现 | 关键排查点 | 对应优化方向 |
| --- | --- | --- | --- |
| 栅格范围广、精度高 | 首次加载慢、内存大 | 当前视图所需数据体积、瓦片级别与尺寸、解码和缓存 | 瓦片化、LOD、资源缓存 |
| 视图变化引起重复请求 | 请求堆积、结果过期 | 缓存命中、同请求并发、旧响应是否覆盖新状态 | 请求缓存、在途去重、取消或版本检查 |
| 多图层绘制与资源维护 | 拖动掉帧、重绘成本高 | 栅格和矢量职责、绘制量、对象与资源管理 | 分层渲染、减少无效绘制 |
| 坐标换算与 UI 更新 | 弹窗卡顿、定位抖动 | 事件频率、坐标转换、DOM 读写和组件更新 | 控制更新频率、分离轻重任务 |

从这里可以收束为两个最终目标：

- **让当前需要的数据尽快到达并显示**：减少没有必要的传输、重复请求、等待和解码负担。
- **让每次交互需要完成的工作足够少**：减少多余的图层绘制、坐标计算与 DOM 更新，保证帧时间稳定。

**事实边界**：上面四类是根据已有项目资料及地图运行机制分析出的主要潜在开销来源，并不是已经通过 Network、Memory、Performance Trace 测得的耗时占比排名。哪一类在特定页面上最重，还需要具体测量；不能凭数据量大就断言性能瓶颈一定在浏览器绘制阶段。

#### 【需要重点掌握的概念区别】

**全球数据规模大 ≠ 浏览器必须一次性加载并渲染全部原始数据。** TileWMS 和 LOD 正是通过当前视图范围与缩放级别减少浏览器需要接收的数据。但即便已经瓦片化，仍可能存在请求不合理、图片解码开销、图层叠加成本和频繁交互计算。

因此，这个项目的“地图渲染性能优化”不能狭义理解为只优化绘制 API，而应沿着**资源获取 → 数据处理 → 图层绘制 → 交互更新**的完整链路分析。

### 【标准回答】

这个项目的核心性能挑战主要来自**全球尺度的地理数据量大，以及地图视图变化时持续产生的数据加载和渲染开销**。

首先，能源分布主要通过大规模栅格数据展示，数据覆盖范围广、分辨率要求高。如果直接加载大量高精度数据，会给网络传输、图像解码和浏览器内存带来比较大的压力。

其次，地图属于持续交互场景。用户缩放、平移时，系统要根据当前视图重新确定需要哪些瓦片，并加载缺失资源。在这个过程中可能出现重复请求、在途请求堆积，以及已经不需要的业务数据请求，增加网络和数据处理成本。

另外，页面不仅显示能源热力数据，还需要叠加基础地图、矢量交互要素和信息弹窗。图层绘制、资源处理以及坐标换算和弹窗位置更新，也会在交互过程中造成额外的浏览器开销，影响流畅性。

所以，我把这个项目的性能问题主要归纳为**资源加载、请求处理和图层渲染**三个方向：使用瓦片化、LOD 和缓存控制数据规模与加载成本；通过请求缓存、去重和必要的取消机制减少无效请求；通过栅格与矢量分层及减少重复的绘制和交互计算，控制浏览器的工作量。目标就是让全球范围内的能源数据能够按需加载，并保证地图缩放、拖动时依然具有良好的交互体验。

## 3. 地图资源按需加载、缓存复用与网络请求管理

### 【提问】

**在全球清洁能源开发潜力评估系统中，你是如何优化地图资源加载和网络请求的？请结合 TileWMS、TileGrid、瓦片缓存、业务查询缓存、请求去重和 AbortController，说明各项机制的具体代码逻辑与适用边界。**

### 【回答要点】

本题不是笼统罗列“瓦片、LOD、缓存、去重和防抖”，而是先区分**地图图片获取链路**与**用户点位查询链路**，分别分析加载资源的范围、重复资源的复用、请求的发起时机以及过时结果的处理。

| 优化主线 | 当前实现与机制 | 解决的问题 | 代码边界 |
| --- | --- | --- | --- |
| 地图图片按需加载 | OpenLayers \`TileWMS\` + \`TileGrid\`，配置瓦片尺寸、原点和三个分辨率 | 按视图地理范围获取瓦片，而非一次加载全球整图 | 前端多级瓦片请求不等于服务端已构建 GeoTIFF Overview |
| 地图图片资源复用 | OpenLayers 内置瓦片管理；基础 \`/tiles\` 接口设置 HTTP 缓存头 | 减少已加载瓦片的重复获取与符合规则的 HTTP 传输 | 不能把基础图缓存策略扩展为私有能源 \`/map/getmap\` 的缓存策略 |
| 已完成业务查询复用 | \`requestCache\`：五分钟 TTL、最多 200 条、命中时调整顺序 | 短时间内重复点击相同点位时减少查询 | 缓存的是数据结果，不是 HTTP Cache 的完整响应副本 |
| 相同在途查询复用 | \`pendingRequests\` 保存同一 \`cacheKey\` 的 Promise | 上一次相同查询尚未完成时避免再次发送 | 它不是待执行任务队列，也不是所有 WMS 图片请求的去重器 |
| 过时请求处理 | \`AbortController\`、Axios \`signal\`、点击序号和 Controller 身份检查 | 连续点击不同位置时尝试中止旧请求，避免过时交互提交 | 取消客户端请求不保证服务端计算立即停止；当前保护仍有竞态边界 |
| 地图视图变化后的业务处理 | \`moveend\` + 100ms \`debounce\` | 合并短时间内连续发生的标记点、弹窗和坐标同步处理 | 不等同于对 OpenLayers 底层瓦片网络请求施加防抖 |

按照一次真实操作串联，两条主线如下：

~~~text
用户打开、缩放或拖动能源地图
    ↓
OpenLayers 计算当前视图与缺失瓦片
    ↓
TileGrid 决定瓦片网格、地理范围和请求分辨率
    ↓
TileWMS 构造 GetMap → 复用已有瓦片 / 请求服务端图片
    ↓
显示底图、能源热力图等图层
    ↓
用户点击能源点位，进入另一条业务查询链路
    ↓
构造包含地图、图层、坐标、语言的查询 Key
    ↓
已完成结果缓存命中？→ 是：直接返回结果
    ↓ 否
相同在途 Promise 存在？→ 是：复用 Promise
    ↓ 否
按需取消不同位置的旧请求 → Axios 携带 signal 发出新请求
    ↓
结果到达 → 核对取消状态、交互是否仍有效
    ↓
更新当前数据 / 弹窗联动；完成后安全清理请求状态
~~~

需要将**“地图瓦片的图片请求”**与**“点击坐标查询一个能源数值”**始终区分：前者依赖地图数据源的瓦片管理，后者才使用当前业务代码中的 \`requestCache\`、\`pendingRequests\` 和 \`abortControllers\`。

### 【TileWMS 和 TileGrid 决定瓦片加载范围与分辨率】

\`TileWMS\` 是 OpenLayers 的瓦片式 WMS（Web Map Service，网络地图服务）数据源，用来将不同地理区域的地图图片作为独立瓦片请求；\`TileGrid\` 则规定瓦片像素尺寸、网格起点和可用空间分辨率。项目的核心配置来自 [Map2D.vue](../../qhfg-energy-platform/apps/web/src/components/dataService/Map2D.vue)：

~~~javascript
const customTileGrid = new TileGrid({
  tileSize: 1024,
  origin: [-180, 90],
  resolutions: [0.703125, 0.3515625, 0.17578125],
});

const qgjMapSource = new TileWMS({
  url: \`\${baseURL}/map/getmap\`,
  params: {
    SERVICE: "WMS",
    VERSION: "1.1.0",
    REQUEST: "GetMap",
    Map: props.qgsMapPath,
    LAYERS: props.tifMapPath,
    FORMAT: "image/png",
    CRS: "EPSG:4326",
    language: locale.value,
  },
  tileGrid: customTileGrid,
  serverType: "geoserver",
  tileLoadFunction: function (imageTile, src) {
    // 实际项目通过 fetch(src, { headers: { Token: token } }) 加载图片。
  },
});
~~~

这段配置的输入是当前地图视图、图层标识和坐标系；OpenLayers 根据视图范围与分辨率查找或创建相应瓦片，并把需要的地理区域转化成 WMS 请求参数。对服务端来说，关键参数是：

- \`MAP\`、\`LAYERS\`：定位请求的是哪一个能源数据图层；
- \`BBOX\`：请求的矩形地理范围；
- \`WIDTH\`、\`HEIGHT\`：返回的图片像素大小；
- \`SRS\`：WMS 1.1.0 中表示坐标参考系统的参数；项目原始配置同时写了 \`CRS\`，最终请求以 OpenLayers 生成的参数为准。

例如在 \`0.17578125\` 度/像素的瓦片网格级别，宽度 \`1024\` 像素的一张瓦片理论上覆盖 \`1024 × 0.17578125 = 180°\` 的经度范围。在这个网格的示例瓦片 \`z=2,x=0,y=0\` 上，WMS 可以构造类似 \`BBOX=-180,-90,0,90&WIDTH=1024&HEIGHT=1024\` 的请求。这里的 \`z\` 是自定义瓦片网格级别，不可与 OpenLayers \`View.getZoom()\` 无条件视为同一个值；实际请求参数还可能受投影、像素比等因素影响。

后端 \`/map/getmap\` 接收请求并交给相应 Provider 生成图片：

~~~typescript
app.get("/map/getmap", async (req, reply) =>
  reply.type("image/png").send(await provider.image(req.query as Params)),
);
~~~

因此，当前可由源码证明的是**前端按视图范围和配置分辨率取得瓦片 PNG**。它控制地图资源的请求范围与输出像素精度，但瓦片化不等于对图片进行了额外压缩，也不等于服务端一定保存了三份不同精度的栅格文件。服务端是否使用预生成栅格金字塔（Overview）仍需检查真实数据与 QGIS 配置。

瓦片大小存在权衡：1024×1024 可能减少单屏请求数量，但单张图片的生成、下载、解码与内存压力也会增大；不能未经实测声称它必然优于 256 或 512 瓦片。

当前 \`tileLoadFunction\` 的实际加载链路还包括：\`fetch(src)\` 携带 Token 请求头 → 检查响应状态与图片内容类型 → \`response.blob()\` → \`URL.createObjectURL(blob)\` → 为 OpenLayers 图片对象设置 \`img.src\`。代码用 \`objectURLs: Set\` 记录创建的 Blob URL，并在替换或组件卸载时调用 \`URL.revokeObjectURL()\` 清理。这是**浏览器临时图片 URL 的生命周期管理**，不能把它误称为自建的持久化瓦片缓存；这段加载函数本身也没有把后面业务查询的 \`AbortController\` 管理器接入全部瓦片请求。

### 【OpenLayers 瓦片复用与 HTTP 响应缓存作用于不同层】

OpenLayers 数据源管理已经获取的瓦片对象与加载状态。地图回到历史区域时，如果相应瓦片仍在缓存中且适用于当前数据源状态，便可以直接复用；否则重新加载。这里属于**框架内置能力**，当前业务代码并没有独立实现 \`Map<tileKey, PNG>\` 的瓦片缓存管理器，更不能保证所有历史瓦片永久留存。

HTTP 缓存是另一层机制：服务端用 HTTP 响应头声明资源是否可以在浏览器或共享缓存中复用。当前 [app.ts](../../qhfg-energy-platform/apps/server/src/app.ts) 对基础瓦片接口显式配置：

~~~typescript
app.get("/tiles", async (req, reply) =>
  reply
    .type("image/png")
    .header("Cache-Control", "public,max-age=3600")
    .send(await provider.tile(req.query as Params)),
);
~~~

\`max-age=3600\` 表示适用缓存的一小时新鲜度寿命，\`public\` 表示该响应在符合其它协议条件时允许由共享缓存保存。第一次请求成功取得响应后，浏览器可按 HTTP 缓存规则存储；相同请求在缓存仍新鲜且匹配时可以不再访问服务器。

但能源业务图片走的是 \`/map/getmap\`，其路由没有显式设置同样的 \`Cache-Control\`。不能据此宣称私有能源瓦片已经配置了一小时的 HTTP 缓存，也不能仅因 Node.js 返回 \`Cache-Control\` 就宣称 Nginx \`proxy_cache\` 已开启。带 Token 的私有图层需要额外考虑共享缓存的权限隔离。对应通用机制见 [HTTP 缓存机制知识体系](../H-HTTP缓存机制知识体系.md)。

### 【requestCache 复用已完成的能源点位查询】

瓦片图片加载与点位数值查询不同。用户点击地图后，\`handleMapClick\` 取得经纬度，再通过 \`identifyNum()\` 调用 \`/map/getpoint\` 查询当前能源数值。为避免同一位置短时间内重复查询，项目使用进程内的 JavaScript \`Map\` 保存已完成结果：

~~~javascript
const requestCache = new globalThis.Map();
const pendingRequests = new globalThis.Map();
const abortControllers = new globalThis.Map();

const CACHE_EXPIRE_TIME = 5 * 60 * 1000;
const MAX_CACHE_ENTRIES = 200;
~~~

这里的 \`globalThis.Map\` 是原生键值映射，目的是避免与文件已导入的 \`OpenLayers Map\` 类混淆。缓存键保留图层及查询结果的关键输入：

~~~javascript
const cacheKey =
  "getPointData_" +
  props.qgsMapPath + "_" +
  props.tifMapPath + "_" +
  longitude.toFixed(3) + "_" +
  latitude.toFixed(3) + "_" +
  locale.value;
~~~

\`MAP\`、\`LAYERS\` 不同，数据值可能不同；语言不同，响应中的区域描述也可能不同，所以不能仅凭经纬度共享查询结果。坐标保留三位小数会增加相近点位的缓存复用率，但也存在不同原始坐标共用同一键的精度取舍。

\`cachedRequest(cacheKey, requestFn)\` 先清理 TTL 已过期的记录，再判断是否有可直接返回的结果：

~~~javascript
for (const [key, value] of requestCache) {
  if (Date.now() - value.timestamp >= CACHE_EXPIRE_TIME)
    requestCache.delete(key);
}
const cached = requestCache.get(cacheKey);
if (cached && Date.now() - cached.timestamp < CACHE_EXPIRE_TIME) {
  requestCache.delete(cacheKey);
  requestCache.set(cacheKey, cached);
  return cached.data;
}
~~~

- **命中**：直接返回 \`cached.data\`，避免再次进入网络请求；先删后设使刚访问过的记录排到 \`Map\` 顺序的末尾。
- **未命中**：继续检查是否存在在途 Promise；真正请求成功后才将返回数据和时间戳写入 \`requestCache\`。
- **容量控制**：写入前若达到 \`MAX_CACHE_ENTRIES=200\`，删除最早顺序的一项；结合命中时的顺序调整，形成基于 \`Map\` 的近似 LRU（最近最少使用）淘汰。

这套缓存保存的是**业务查询结果对象和时间戳**，不是浏览器管理的 HTTP 缓存副本；五分钟 TTL 也不是说五分钟后会自动定时发请求刷新数据。

### 【pendingRequests 复用尚未完成的同一查询】

结果缓存有一个空窗：第一次请求尚未返回时，\`requestCache\` 里还没有值。假设 A 点在 0ms 和 20ms 连续触发两次相同查询，而网络响应在 200ms 才返回，如果只检查已完成结果缓存，就可能重复发送两次 HTTP 请求。

因此项目另设 \`pendingRequests\`，以相同 \`cacheKey\` 存储正在执行的 Promise：

~~~javascript
if (pendingRequests.has(cacheKey)) {
  return pendingRequests.get(cacheKey);
}

const requestPromise = Promise.resolve()
  .then(() => requestFn())
  .then((data) => {
    if (requestCache.size >= MAX_CACHE_ENTRIES)
      requestCache.delete(requestCache.keys().next().value);
    requestCache.set(cacheKey, { data, timestamp: Date.now() });
    return data;
  })
  .finally(() => {
    pendingRequests.delete(cacheKey);
  });

pendingRequests.set(cacheKey, requestPromise);
return requestPromise;
~~~

一次完整过程是：

~~~text
第一次查询 A：结果缓存 MISS
    ↓
在途缓存 MISS → 创建 Promise P → 发送一次 HTTP 请求
    ↓
pendingRequests[A] = P

第二次查询 A：结果缓存仍然 MISS
    ↓
pendingRequests 命中 A → 直接返回同一个 Promise P
    ↓
不发送第二次 HTTP 请求

Promise P 成功完成
    ↓
将结果写入 requestCache[A]
    ↓
finally 删除 pendingRequests[A]
    ↓
之后的 A 查询优先命中已完成结果缓存
~~~

\`pendingRequests\` 不是按 FIFO 等待调度的“缓存队列”，而是**相同请求键对应的 Promise 注册表**：它实现的是 in-flight deduplication（在途请求去重）。失败和取消的 Promise 不会因成功分支而写入结果缓存，\`finally\` 会负责清理在途记录。

### 【AbortController 将过时查询的取消意图传递至 Axios】

\`AbortController\`（取消控制器）由浏览器提供，负责调用 \`abort()\` 发出取消信号；\`AbortSignal\` 则把这个信号传给支持取消的异步操作。当前项目的具体消费方是 Axios 请求，不是浏览器提供了一条自定义 HTTP“取消报文”。

连续点击 A 点、B 点时，若 A 尚未返回，A 的结果可能在 B 之后才到达。因此 \`identifyNum\` 为“当前点位查询”维护一个控制器槽位：

~~~javascript
const abortKey = "identifyNum";
const previousController = abortControllers.get(abortKey);

if (previousController && lastPointKey !== cacheKey) {
  previousController.abort();
}

const abortController =
  lastPointKey === cacheKey &&
  previousController &&
  !previousController.signal.aborted
    ? previousController
    : new AbortController();

lastPointKey = cacheKey;
abortControllers.set(abortKey, abortController);
~~~

代码执行逻辑：

1. 如果新查询与当前查询属于不同 \`cacheKey\`，先对旧 Controller 调用 \`abort()\`；
2. 如果是同一个 Key 且旧 Controller 尚未取消，就复用旧 Controller，以便配合在途 Promise 去重；
3. 否则创建新 Controller，登记为当前查询的控制器；
4. 调用 \`cachedRequest\`，在需要实际发起请求时把 \`abortController.signal\` 传给 \`getPointData\`。

\`Map2D.vue\` 中的实际调用：

~~~javascript
const result = await cachedRequest(cacheKey, () =>
  getPointData(
    props.qgsMapPath,
    props.tifMapPath,
    longitude,
    latitude,
    locale.value,
    abortController.signal,
  ),
);
~~~

这里仅将 \`requestFn\` 交给缓存管理器；**真正执行 Axios 请求**发生在 \`requestCache\` 和 \`pendingRequests\` 均未命中时。[request/index.js](../../qhfg-energy-platform/apps/web/src/request/index.js) 接收并传递 Signal：

~~~javascript
const response = await request.get(
  \`/map/getpoint?MAP=\${mapPath}&LAYERS=\${layers}&LONGITUDE=\${longitude}&LATITUDE=\${latitude}&language=\${language}\`,
  { signal },
);
return response.data ?? null;
~~~

从这个调用关系可以逐层确认：\`abort()\` → \`signal.aborted\` 变化 → Axios 感知取消 → 关联请求被尝试中止 → Promise 进入取消分支。API 封装会继续抛出名为 \`CanceledError\` 或 \`AbortError\` 的取消错误，\`identifyNum\` 的 \`catch\` 不将主动取消当作普通网络失败显示：

~~~javascript
} catch (error) {
  if (error.name !== "CanceledError" && error.name !== "AbortError") {
    console.error("数值获取失败:", error);
    identifyNumResult.value = t("message.dataException");
  }
}
~~~

**取消的能力边界**：它针对的是客户端关联的异步请求，不保证 Node.js、QGIS 或数据库中已经执行的操作立刻停止，也不保证请求刚好完成时不会出现其它异步逻辑；因此仍需要结果时效判断。

### 【点击序号与 Controller 所有权检查保护异步状态】

请求取消之后，还需处理两类独立的状态问题：**旧点击继续执行业务联动**以及**旧请求结束时清理掉新请求的状态**。

第一类由 \`pointSequence\` 处理：

~~~javascript
const handleMapClick = async (event) => {
  if (!props.active) return;
  const clickId = ++pointSequence;

  // 先设置标记，再查询当前点击位置的能源数值
  await identifyNum(normalizedCoordinate[0], normalizedCoordinate[1]);

  if (!props.active || clickId !== pointSequence) return;

  // 只有仍为当前点击，才继续处理弹窗位置与 mapPointSelected 联动
};
~~~

例如 A 点击得到序号 1，紧接着 B 点击得到序号 2；即使 A 的异步函数稍后恢复执行，它在 \`await\` 后发现 \`clickId=1\`、\`pointSequence=2\`，就不会继续执行 A 的后续弹窗及图表联动。

第二类由 Controller 对象身份检查处理：

~~~javascript
} finally {
  if (abortControllers.get(abortKey) === abortController)
    isLoading.value = false;
  if (abortControllers.get(abortKey) === abortController)
    abortControllers.delete(abortKey);
}
~~~

例如 A 使用 \`ControllerA\`，B 发起后 \`abortControllers["identifyNum"]\` 已切换成 \`ControllerB\`。如果 A 的 \`finally\` 无条件删除同一 Key，就可能清掉 B 的 Controller 并错误结束 B 的加载状态。身份检查使**只有当前持有该状态管理权的请求才能清理状态**。

此外，\`identifyNum()\` 在正常结果写入前检查：

~~~javascript
if (abortController.signal.aborted || !props.active) return;
identifyNumResult.value = result || "null";
~~~

地图非活动状态与组件卸载时，也会调用已登记 Controller 的 \`abort()\`，并清理相应记录，避免非活动页面继续维护不必要的业务请求。

**实现边界必须保留**：\`pointSequence\` 的检查发生在 \`await identifyNum()\` **之后**，因此主要保护 \`handleMapClick\` 中后续弹窗/图表联动；\`identifyNumResult.value\` 的赋值发生在 \`identifyNum()\` 内部，尚未由同一个序号统一守护所有成功、失败和加载状态写入。取消标志能够阻挡大部分被取消请求的正常成功提交，但不能把当前代码表述为已经彻底消除所有竞态。

特别是极短时间内出现 **A → B → A**：第一次 A 的 Promise 已被取消，但它仍可能短暂保留在 \`pendingRequests[A]\` 中；第三次 A 命中同一在途 Key 时，可能复用已经取消的 Promise。因此更稳妥的改进方向是将 Promise、Controller 和取消状态绑定到同一请求记录中，复用前检查状态，并用最新请求序号统一保护所有界面写入。**这是代码审查提出的改进方向，不是现有代码已经实现的能力。**

### 【moveend 与 debounce 控制视图变化后的业务回调】

[Map2D.vue](../../qhfg-energy-platform/apps/web/src/components/dataService/Map2D.vue) 为 \`moveend\` 绑定业务回调，并通过 Lodash 的 \`debounce\` 合并短时间内连续触发的回调：

~~~javascript
const handleViewChange = _.debounce(() => {
  const view = map.value.getView();
  const mapSize = map.value.getSize();
  const extent = view.calculateExtent(mapSize);
  const resolution = view.getResolution();

  // 判断标记点是否仍然可见、更新弹窗位置与坐标广播
}, 100);

map.value.on("moveend", handleViewChange);
~~~

\`moveend\` 表示地图移动结束后的事件，不是每一帧都触发的绘制事件。这里的 100ms 防抖约束的是**标记点可见性检查、弹窗重新定位及坐标状态广播**等业务处理，不是所有 \`TileWMS\` 底层 HTTP 请求。因此“拖拽缩放时对瓦片网络请求加了 100ms 防抖”不符合源码。

### 【服务端图片缓存需要区分运行模式】

当前后端根据 \`DATA_PROVIDER\` 选择数据提供方式：\`fixture\` 用于隔离测试，\`source\` 用 Node.js 读取本地真实原始数据，\`real\` 将 WMS 请求转交给 QGIS 等实际服务。不同模式不应混同。

\`SourceProvider\` 在 [source.ts](../../qhfg-energy-platform/apps/server/src/source.ts) 中定义：

~~~typescript
private cache = new Map<string, Promise<Raster>>();
private images = new Map<string, Buffer>();
~~~

- 原始 Raster 缓存最多保留 **2 份**读取解析结果，减少重复读取 GeoTIFF 和完整栅格数组；
- 已生成 PNG 缓存最多保留 **24 张**，缓存键关联图层、\`BBOX\`、\`WIDTH/HEIGHT\` 和坐标系，减少完全相同参数下的重复逐像素计算与 PNG 编码；
- 两种缓存都处于 **Node.js 进程内存**，服务重启后失效，不是磁盘或 Redis 持久化缓存。

\`RealProvider\` 则把对应 WMS 请求转发给 QGIS Server，现有代码不能证明外部 QGIS 已配置 GeoTIFF Overview、瓦片结果缓存或与 \`SourceProvider\` 相同的内存缓存。仓库默认 \`fixture\`，新增 \`source\` 曾用于本地真实 GeoTIFF 恢复与验证；不能将“存在 \`real\` 适配器”直接等同于完整生产数据服务已经部署验收。项目事实可继续核验 [README](../../qhfg-energy-platform/README.md) 和 [恢复验证记录](../../qhfg-energy-platform/docs/validation/restoration.md)。

### 【标准回答】

对于全球清洁能源开发潜力评估系统，我主要从**地图资源按需加载、缓存复用和业务网络请求管理**三个方面进行优化。

首先是地图资源按需加载。全球能源数据覆盖范围广、原始栅格规模大，因此前端采用 OpenLayers 的 TileWMS，通过瓦片化方式按当前可视范围请求地图图片，而不是一次获取完整的全球能源分布图。结合 TileGrid 配置瓦片尺寸、网格原点与分辨率级别，让 OpenLayers 根据当前视图确定需要的瓦片，并通过 BBOX、WIDTH、HEIGHT 等 WMS 参数请求指定范围和输出尺寸的 PNG 图片。这能够控制单次加载的地理范围与输出分辨率。对于服务端是否进一步建立多精度栅格金字塔，仍需根据实际 QGIS 服务和 GeoTIFF 文件配置确认。

其次是资源缓存复用。一方面，利用 OpenLayers 内置的瓦片管理能力，复用仍然有效的已加载瓦片，减少重复获取资源的开销；另一方面，项目为基础地图的 /tiles 接口设置了一小时的 HTTP 缓存新鲜期，让符合缓存条件的瓦片响应可被浏览器等缓存节点复用。需要区分的是，私有能源热力图的 /map/getmap 接口并没有发现同样的显式 HTTP 缓存配置，因此不能把基础地图的缓存策略直接推广到全部能源瓦片。

最后是业务网络请求管理，重点针对用户点击地图后的 /map/getpoint 能源数值查询。对于已经完成的查询，使用 requestCache 缓存结果，缓存键包含地图、图层、经纬度和语言，设置五分钟有效期与 200 条容量上限；对于尚在途的相同请求，使用 pendingRequests 保存 Promise，让后续相同查询复用同一次异步操作，避免重复发送请求。

当用户连续点击不同位置时，通过 AbortController 取消旧点位请求，将 signal 传给 Axios，同时结合取消状态、点击序号和 Controller 身份检查，控制过时结果的后续联动及旧请求对新请求状态的清理。地图视图变化相关的弹窗定位和坐标同步，则使用 moveend 事件与防抖处理，减少重复业务回调，而不影响 OpenLayers 自身的瓦片加载机制。

整体来说，**TileWMS 和 TileGrid 控制加载范围及输出精度，瓦片缓存和 HTTP 缓存复用已有资源，业务结果缓存和在途 Promise 去重减少重复查询，AbortController 与请求身份检查处理过时异步任务**。这些机制分别作用于不同环节，共同降低不必要的网络传输、重复计算和界面状态更新成本。当前效果需要结合瓦片请求量、缓存命中情况、点位查询重复率及实际加载/交互指标验证，不能仅凭机制存在就给出未经测量的性能提升数字。

### 【实现边界与可追问方向】

本题已核验的是仓库当前源码中可定位的**配置、数据结构和调用链**，并不代表每个优化项已通过生产环境 A/B 性能对比。需要特别保留如下边界：

1. **前端瓦片分辨率 ≠ 服务端栅格金字塔**：\`TileGrid\` 有三个分辨率级别，但不等于后端预先生成三个 Overview；是否使用多级 GeoTIFF 需要另外确认。
2. **瓦片复用 ≠ HTTP 缓存 ≠ 业务结果缓存**：OpenLayers 管理瓦片对象；HTTP 缓存存储符合规则的 HTTP 响应；\`requestCache\` 保存业务返回的数据对象；\`SourceProvider\` 的两个 Map 则是服务端进程内缓存。
3. **请求去重 ≠ 请求取消 ≠ 防抖**：\`pendingRequests\` 合并相同 Key 的在途查询；\`AbortController\` 尝试取消不同 Key 的过时请求；\`debounce\` 合并短时间内重复触发的业务回调。
4. **客户端取消 ≠ 服务端任务必然停止**：网络请求的取消不自动取消已经运行的 QGIS、数据库或服务端计算。
5. **当前竞态保护不是完备的统一请求状态机**：\`pointSequence\` 保护的是后续点击联动；仍需单独验证 A→B→A、错误分支以及所有界面写入是否由最新请求独占。
6. **配置并不等于效果已得到验证**：可对比地图请求次数与字节数、重复点位请求次数、取消请求占比、服务端 PNG 生成耗时及帧时间；1024 瓦片更优、网络节省比例或 QGIS 缓存命中率均不能无证据断言。

从这题自然延伸的两类追问：**（1）TileGrid 到 WMS BBOX 再到栅格数据读取的分辨率匹配链路；（2）在 Promise 去重与取消同时存在时，如何设计一个避免 A→B→A 竞态的统一请求状态管理器。** 通用缓存机制见 [HTTP 缓存机制知识体系](../H-HTTP缓存机制知识体系.md)，事件回调与异步执行机制可继续查阅 [前端事件机制](../Q-前端事件机制（event）.md) 和 [前端异步编程](../Q-前端异步编程.md)。
