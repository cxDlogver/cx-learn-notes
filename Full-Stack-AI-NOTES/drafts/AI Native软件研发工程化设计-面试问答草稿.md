# 第一项工作重点：AI Native 研发工程化设计与官网实践

## 1. 工程化设计思想与建设动机

### 1.1 【AI Native 下如何重新设计软件研发工程化体系？】

#### 【提问】

**在 AI Native 生态下，应该如何重新设计软件研发的工程化规范？相较于传统软件研发，人的职责和 Agent 的职责发生了什么变化？为什么要强调规范驱动、验证前置、可追溯与风险控制，这些原则如何贯穿研发的完整生命周期？**

本题并不只是问 AI 如何帮助写代码，而是问：当 Agent 能够承担从需求分析、技术规划到代码实现、测试验收的更多执行工作时，软件工程怎样重新组织人的决策、Agent 的执行、可检查的标准与交付责任。

#### 【回答要点】

##### 【AI Native 扩展了传统软件工程的人机协作关系，而不是取消 SDLC】

我理解软件研发工程化，首先要从传统软件开发生命周期（SDLC）出发。

一项软件需求并不是直接从需求描述跳到编写代码，而是需要经过需求分析、技术设计与任务规划、代码开发、测试验收，再到交付上线。每个阶段有自己的目标、产物和参与角色，前一阶段的结果是后一阶段的重要依据。传统工程化要解决的是：**怎样让产品、设计、研发和测试等多个角色在共同的规则下，稳定地把一个可能模糊的业务诉求转换成正确、可维护、可交付的软件**。

进入 AI Native 环境以后，这条生命周期主线依然存在，但任务的主要执行方式开始发生改变。

过去 AI 更多作为 Coding Assistant，帮助研发人员补全函数、编写局部代码或解决单个问题；而在 Agent 能够连续调用工具和处理多阶段任务的情况下，它可以进一步参与需求梳理、技术方案分析、任务拆解、编码、测试、代码审查与问题修复。研发人员的工作重点因此逐渐从大量重复执行，转向**业务目标定义、规范与验收标准确认、关键架构判断、风险审查以及最终质量负责**。

这里不是说人只需要检查 Agent 的最后一次输出，也不是所有软件都应该完全由 Agent 自动研发。需求歧义、架构取舍、业务规则、生产风险仍然需要人的判断；对于规则明确、边界清楚、风险可控的工作，才可以更充分地委托 Agent 执行。

因此，AI Native 下的工程化设计可以理解为：

> 将传统软件工程中“规范团队多人协作”的体系，进一步扩展为“规范人和 Agent 在同一套事实、规则、产物和质量门禁下协作”，在提高自主执行比例的同时，保证目标一致、结果可验证、过程可追溯以及风险可控制。

这与 AWS 所讨论的 AI-DLC（AI-Driven Development Life Cycle）中“AI 执行与人工监督”的协作方向一致。[[1]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

##### 【四项横向原则保障 Agent 能够长期、可靠地执行研发任务】

这四项原则不是按照先后顺序运行的四个阶段，而是同时作用于需求、设计、实现、验证和发布等全过程的**横向工程约束**。

###### <u>1. 规范驱动——先明确任务意图与规则，再让 Agent 执行</u>

第一项原则是规范驱动（Spec-Driven Development，SDD）。

Agent 开始执行前，应当先理解真正的业务意图，识别尚不明确的需求、边界条件与约束，并将已经确认的信息沉淀为结构化、可读取、可持续引用的工程产物。

这里要处理的不是“Prompt 写得够不够长”，而是**任务依据是否稳定**。如果原始 PRD 有歧义，或者关键接口、权限、异常流程没有说明清楚，Agent 很可能基于自己的猜测先写出一套看似完整的实现。随着任务跨多个步骤和多个 Session 推进，这种理解偏差还可能被后续计划、代码与测试不断放大。

因此，工程中需要逐步形成：

~~~text
业务问题与目标
      ↓
需求规范：做什么、不做什么、遵守什么约束
      ↓
验收标准：达到什么结果才算完成
      ↓
技术方案：现有系统中怎样实现、修改边界在哪里
      ↓
实现计划：有哪些依赖关系与执行顺序
      ↓
Task：每个独立任务的目标、输入、输出和完成条件
      ↓
代码实现
~~~

GitHub Spec Kit 的规范驱动思路强调先形成 Spec，再进入 Plan、Tasks 与 Implement；其意义在于把不同阶段所需的上下文变成可复用的依据，而不是让 Agent 每次从一条自然语言指令重新猜测。[[2]](https://github.com/github/spec-kit/blob/main/docs/index.md)

规范的深度还应该与任务的复杂度、风险和现有信息完整性相匹配。简单低风险修改不必机械生成大量文档；复杂跨系统需求则不能省略关键约束、接口合同和变更范围。

**规范驱动解决的是：Agent 应该做什么、为什么做、能够改哪里，以及执行时应遵循哪些事实与限制。**

###### <u>2. 验证前置——在代码实现之前确定什么算正确</u>

第二项原则是验证前置，与 ATDD（验收测试驱动开发）的思想相近。

当 AI 开始承担主要代码实现工作时，测试如果完全在代码生成之后，依据代码当前的行为反向设计，就可能出现一个很危险的闭环：

~~~text
Agent 错误理解需求
       ↓
按照错误理解生成代码
       ↓
按照当前错误代码反向生成测试
       ↓
测试全部通过
       ↓
实际需求仍然没有被正确满足
~~~

因此，我们不能只要求 Agent “写完以后跑测试”，而应当**在实施之前形成来自需求本身的验收标准**。

具体来说，需求分析阶段就应当尽量明确正常流程、异常场景、权限与安全边界、禁止行为，以及需求成功的判断条件。之后在技术分析阶段把 Acceptance Criteria 进一步转化为 Test Case Matrix（测试用例矩阵），明确每项测试的前置条件、输入或操作、预期结果，以及必要的证据类型。

在相对规范的团队研发中，需求评审和技术评审就是两个重要的确认机会：

- 需求评审：产品、研发、测试等相关角色确认业务规则、需求范围和验收目标。
- 技术评审：确认技术方案、接口及影响范围，并检查 Test Case 是否覆盖关键需求与边界条件。

ATDD 强调业务、开发和测试等不同视角在功能实施前共同明确验收测试。[[3]](https://agilealliance.org/glossary/atdd/)

这样做还有一层价值：Test Case 不仅服务于后续自动化验收，也能**反向发现需求与技术规划中的模糊点**。如果一个业务场景无法明确预期结果，或者不同角色对某项断言的理解不一致，说明需求还没有真正澄清，不应因为 Agent 已经能够编码就直接开始实现。

在执行阶段，Agent 可以选择适当的测试工具、生成测试脚本，甚至通过浏览器 Agent 自主操作页面，但**不能擅自把验收标准改成刚好能让自己的实现通过的条件**。

验收应形成：

~~~text
Requirement（需求）
      ↓
Acceptance Criteria（验收标准）
      ↓
Test Case（测试用例）
      ↓
Actual Result（实际行为）
      ↓
Evidence（截图、请求、状态、日志等独立证据）
      ↓
PASS / FAIL / 需要人工确认
~~~

**验证前置解决的是：不依赖 Agent 对自己工作的主观判断，怎样独立证明软件实现满足真实需求。**

###### <u>3. 可追溯——保留跨阶段、跨 Session 的状态与工程证据</u>

第三项原则是可追溯。

一个完整业务需求通常不是单次模型调用能够结束的短任务，而可能跨越多个 Agent、多个阶段及多个 Session。Agent 会遭遇上下文窗口限制、工具失败、运行环境异常和需求变化，因此不能只保留最终代码或者聊天对话。

更可靠的做法是持续维护真实的任务状态和可审查产物，使它们能够关联：

~~~text
Requirement（需求）
       ↓
Scenario（场景）
       ↓
Test Case（验收用例）
       ↓
Technical Plan（技术方案）
       ↓
Task（独立任务）
       ↓
Code Change（代码变更）
       ↓
Test Result / Evidence（测试结果与证据）
       ↓
Release（发布版本）
~~~

这种关联至少有两种工程价值。

第一是**可恢复**。执行中断以后，新的 Agent Session 可以读取任务计划、任务完成状态、Checkpoint、代码提交和现有测试结果，识别哪些工作已经通过验证、哪些仍未完成，从稳定状态继续执行，而不必重复整个需求。

第二是**可审查**。人工需要判断“当前 Agent 做到哪里、为什么做了这项修改、有没有偏离需求”时，可以追溯产物之间的关系。例如通过 Requirement 与 Test Case Matrix 检查需求理解，通过 Task 与 Git Diff 检查修改范围，通过 Test Case、Actual Result 和 Evidence 检查验收结论。

这里应区分：**Artifact 是持久化工程产物；State 记录当前任务状态；Checkpoint 用于恢复运行；Trace 记录实际执行过程；Evidence 证明具体断言是否成立。** 它们可以关联，但不能互相替代。尤其不能因为 Agent 的执行轨迹完整，就认定最终业务结果必然正确。

**可追溯解决的是：长任务能否持续推进、中断后能否恢复、人工能否看清执行依据、需求变化时能否准确定位影响范围。**

###### <u>4. 风险控制——按风险决定自动执行、独立门禁与人工审查的边界</u>

第四项原则更适合称为风险控制，而不只是安全性。

AI Native 并不意味着把从需求澄清到生产发布的所有动作无条件授权给 Agent。自动化深度应综合考虑任务的确定性、潜在影响、操作是否可逆、权限敏感程度，以及结果能否被独立验证。

对于规则明确、风险较低、容易测试的工作，例如局部组件实现、重复代码调整或已定义好范围的重构，可以让 Agent 承担较多实现、自测和修复工作，并通过自动化检查放行。

但对于需求歧义、敏感权限、数据迁移、核心交易链路、公共组件、跨系统架构变更以及生产发布等高风险操作，应限制工具权限并在关键节点引入 Human-in-the-Loop（人工确认）、独立质量门禁或人工最终放行。

因此，风险控制不仅有“人工 Review”一种手段，还包括：

- 执行前：明确允许修改的 Scope、工具权限、敏感操作与必须确认的决策。
- 执行中：通过沙箱、检查规则、测试、代码审查和状态门禁阻止越权或错误继续传播。
- 执行后：根据影响范围进行人工风险审查，在发布阶段支持灰度、停止和回滚。

人的职责并不是重新手工完成 Agent 已经完成的所有工作，而是重点负责**目标、架构、风险与最终交付责任**。

**风险控制解决的是：在增加 Agent 自主性的同时，如何避免错误或未经授权的动作被不断放大到不可接受的业务影响。**

#### 【标准回答】

整体来看，我理解 AI Native 下的软件工程化，不是让 Agent 无条件代替传统 SDLC，而是在保留“需求分析 → 技术分析 → 代码开发 → 测试验收 → 交付上线”这条生命周期的同时，重新分配人和 Agent 的职责：

- Agent 在清晰的目标与约束下承担越来越多分析、实现、测试与修复任务。
- 人负责业务意图、规范与验收标准确认、关键架构判断、风险审查和最终质量负责。
- 自动化系统通过测试、证据、任务状态、执行权限和质量门禁把每一次自主执行放在可验证、可恢复、可控制的框架内。

因此，**工程化设计的核心不是单纯追求更快地生成代码，而是在提高 Agent 自主执行比例的同时，让目标不跑偏、结果有证据、过程能追溯、风险有边界，最终稳定完成复杂软件交付。**

从职责上说，人要确认真实业务目标、设计边界、质量标准与高风险决策，Agent 在充分明确的约束下承担更多执行工作。设计应围绕共同事实、可执行规范、独立验收和可恢复证据展开；这是一套贯穿生命周期的协作机制，不意味着每项需求都必须运行完整自动化 Agent 工作流。

### 1.2 【为什么要建立可复用的软件研发工程规范？】

#### 【提问】

**在参与官网 2.0 前端开发时，为什么不只关注页面实现和项目上线，而是希望借助这个项目探索、沉淀一套后续软件开发也能够复用的工程规范？为什么认为这件事重要？**

回答应当从真实工程问题出发，不要一上来罗列 Nuxt、ESLint、Prettier、Design Tokens 等技术名词，也不要把官网项目描述成已经实现了全自动 Agent 研发流水线。

#### 【回答要点】

> **记录范围**：本节先回答“为什么将工程化规范建设作为官网 2.0 的一项工作重点，以及这项工作希望解决什么问题”。工程规范的具体落地过程（架构设计、Task 拆分、代码规范、AI 协作、质量验收）留待后续讨论继续完善。本节与前文的 AI Native 通用理论形成“通用思想 → 官网项目动机”的关系。

##### 【业务项目提供真实约束，规范沉淀是超越单次交付的目标】

官网 2.0 的直接目标是完成企业官网的内容和体验升级，包括首页、产品、解决方案、资讯、招聘和联系等多个业务模块。它不是只需一次性完成的孤立页面，而是要持续增加内容、调整视觉、接入功能并进行后续维护的前端应用。

在这个过程中，除了完成当前版本的功能，还存在另一类值得主动解决的问题：如果每开发一个页面或增加一个功能，都要重新讨论代码放在哪里、公共逻辑是否要复用、设计值采用什么标准、怎样提交以及怎样判断可以交付，那么随着模块和参与者增加，重复决策、沟通、返工与维护成本就会不断上升。

因此，选择官网项目作为工程规范实践场景，不是把“研究规范”变成脱离业务的独立任务，而是希望**在真实的需求迭代中识别反复出现的工程问题，形成统一的研发方式，并验证这些方式是否能够帮助项目稳定推进**。

这项工作的价值应区分两个层次：

- **当前项目的直接价值**：让官网不同模块在相同架构、设计规则和质量要求下开发，降低重复实现与代码整合成本，支持持续维护和交付。
- **面向未来的长期价值**：把有效的工作流程、架构判断、公共规范和验收方法沉淀为可以迁移、可以继续调整的工程基础，减少后续项目从零制定规则的成本。

需要注意，**“可迁移”不等于“所有项目都可以完全照搬”**。官网适用的组件粒度、渲染策略和视觉规范，迁移到后台管理系统或复杂全栈服务时仍要依据业务特点重新判断；能够复用的是工程设计方法、职责约束和验证思路。

##### 【第一个原因：多人、跨阶段、长期迭代的软件开发需要共同上下文与统一规则】

传统软件工程的一个基础事实是：**软件开发通常涉及产品、设计、研发和测试等不同角色，也不止于一次交付。**

如果每个人只依赖口头沟通、个人记忆和各自的开发习惯，那么参与者就可能对同一需求的边界、当前进度、技术方案和完成标准产生不同理解。即使每个人的局部任务都已经完成，整个项目仍可能遇到信息无法交接、模块难以整合以及问题难以追溯的情况。

因此，工程规范首先要建立**过程层面的共同上下文**：

1. **需求与设计依据**：记录业务目标、需求范围、页面职责、已经确认的设计与技术决策，避免任务在不同人员之间传递时丢失原始意图。
2. **任务与进度状态**：明确任务拆分、负责人或执行主体、当前状态、已完成工作、依赖关系与遗留问题，使新的参与者能够判断项目推进到哪一步。
3. **阶段产物与验收依据**：保留实施方案、代码变更、测试结果、评审结论等关键产物，让后续接手的人能够依据事实继续工作，而不是从头推断。

仅有文档还不够。不同开发人员需要在同一个代码库中持续提交与维护，因此还必须建立**技术实现层面的统一规则**，包括：

- **架构与模块规则**：页面、组件、公共逻辑、业务数据与服务端接口各自负责什么；在什么情况下应该抽象复用，避免不同模块重复实现。
- **视觉与设计规则**：统一品牌色、排版、间距、响应式与动效等基础约束，减少不同页面各自定义样式而产生的差异。
- **代码与提交规则**：统一 TypeScript、代码组织、格式化、静态检查和提交说明，让代码质量不依赖每个人的个人习惯。
- **交付与验收规则**：明确每一阶段什么条件下可以进入下一步，让功能完成、可维护性和可上线性之间有清晰的判断依据。

所以，传统协作场景中强调工程规范，并不是单纯为了“让代码格式看起来一样”，而是要让**不同参与者能够理解共同目标、共享真实进度、按照一致结构继续开发，并在需求变化时保持长期可维护性**。

##### 【第二个原因：AI Native 将协作对象扩展到 Agent，要求规范更加显式且结果可以检查】

AI Native 带来的是协作结构的变化：AI 不再只能进行局部补全，而是逐渐可以参与需求分析、技术规划、代码生成、测试和问题修复等多个阶段。研发人员可以将更多规则明确、边界清楚的任务委托给 AI，同时把精力集中到业务判断、技术取舍、风险与质量审查。

但**AI 执行速度提高，不等于交付效率必然提高**。当缺少明确约束时，AI 可能在不同任务中采用不同组件划分、重复生成已有的公共能力、改变未要求修改的逻辑，或者凭自身假设补充需求。结果可能是代码生成得更快，但人工后续纠正、整合和验证的成本反而更高。

因此，面向团队成员建立的工程规则，需要进一步变成**AI 也能理解、引用并据此执行的显式规范**：

- 在任务执行前，提供需求意图、已确认事实、模块职责、修改范围、设计规范和具体完成条件，减少自由猜测与越界修改。
- 在执行过程中，让 AI 参考现有架构和公共能力，按独立任务、小批量变更推进，并保留必要的实施记录与检查结果。
- 在每项任务结束后，依据独立的功能、视觉、SEO、性能和工程质量标准审查结果，而不是仅凭 AI 自报“已完成”直接放行。
- 对关键业务规则、复杂架构决定以及高风险操作，保留研发人员的判断和必要的人工确认。

这里还要把实践与发展方向区分开：**在官网项目中，实际强调的是“人主导工程设计，AI 辅助需求整理、方案探索、代码实现及初步检查”**；对于 Agent 全流程自主执行、完整 Checkpoint 体系和自动化门禁，则属于更进一步的 AI Native 工程演进，不能直接作为官网项目已实现的事实陈述。

因此，在 AI Native 环境中建立工程规范，实际上是要避免把 AI 仅作为“更快的代码生成器”，而是要**通过统一的上下文、执行边界与验收依据，减少人工反复纠偏，使 AI 的执行能力能够真正转化为可持续的研发效率**。

##### 【两个原因归于同一个目标：让人和 AI 按共同规则持续协作与交付】

这两个原因不是彼此独立的工作目标，而是同一个协作问题在不同开发环境下的体现：

~~~text
传统研发：多人、多角色、跨阶段协作
          │
          ├─ 需要共同目标、任务状态和阶段产物
          └─ 需要统一架构、编码规则与验收标准
          │
          ▼
形成可共享、可执行、可检查的研发工程规范
          │
          ▼
AI Native：协作成员进一步包含 AI / Agent
          │
          ├─ 将隐式经验转换成明确的任务输入和执行边界
          ├─ 让 AI 参照既有结构和公共能力开发
          └─ 用独立测试与人工审查控制结果质量
          │
          ▼
让人和 AI 基于同一套规范持续推进需求
          │
          ▼
降低协作、重复开发、人工纠偏及质量验证成本
支撑当前项目交付，并沉淀后续可复用的工程基础
~~~

从设计对象看，可以把这套工程规范归纳成三个相互关联的层次，而不是把所有规范都等同于代码规范：

| 规范层次 | 要解决的核心问题 | 典型产物或机制 |
| --- | --- | --- |
| **研发过程规范** | 需求怎样澄清、任务怎样交接、阶段怎样衔接 | 需求文档、技术方案、任务计划、状态记录、阶段产物 |
| **技术实现规范** | 多人和 AI 生成的代码怎样形成统一、可维护的系统 | 架构分层、组件边界、Design Tokens、Composables、类型规范、格式与提交规范 |
| **质量验证规范** | 怎样独立判断任务完成，控制错误流入后续阶段 | Acceptance Criteria、测试清单、静态检查、代码评审、页面与性能/SEO 验收 |

三层缺一不可：只有过程文档而没有技术约束，代码仍可能各自为政；只有统一的代码风格而没有阶段产物，任务仍然难以交接；只有快速实现而没有独立验收，交付质量就无法稳定保证。

#### 【标准回答】

在参与官网 2.0 前端开发的过程中，我希望不仅完成当前项目的页面与业务功能，还能够借助这个实际开发场景，探索并沉淀一套以后能够在软件研发中继续复用的工程规范。

之所以将工程化设计作为一个重点，主要有两个原因。

**第一，是团队协作和长期维护的需要。**

一个完整的软件项目通常不是由一个人一次性交付的，而是需要产品、设计、研发和测试等多个角色共同参与，而且随着业务需求不断迭代。

如果缺少统一的流程与规范，不同人员就可能按照自己的理解推进任务，导致需求信息丢失、代码结构不一致、公共能力重复实现，后续交接和维护成本也会不断上升。

所以我认为，工程化首先应该建立一套能够被团队共同遵循的研发规则。一方面通过需求文档、技术方案、任务计划和阶段产物持续保存工程上下文，让参与者能够快速理解当前目标、任务进度和遗留问题；另一方面通过统一的架构分层、组件设计、代码格式与提交规范，让不同开发任务可以按照一致的技术约束推进。

**第二，是 AI Native 环境下人机协作对工程规范提出了更高的要求。**

随着 AI 从局部代码辅助逐渐能够承担需求分析、方案规划、代码实现和测试等更多工作，工程协作的对象开始从传统团队成员进一步扩展到 AI。

但 AI 生成代码更快，并不意味着整体交付效率就一定更高。如果缺少明确的需求依据、架构约束和验收标准，不同任务很容易出现理解偏差、重复实现和代码风格不一致，反而需要研发人员花费大量时间纠正、整合和重新验收。

因此，我认为 AI 提效的关键，不只是让 AI 更快地完成某项开发工作，而是让**人和 AI 能在同一套研发规范下理解需求、执行任务和验证结果**，使生成能力能够真正转化为稳定的项目交付能力。

基于这两个原因，我希望以官网项目为实践场景，逐步形成覆盖需求分析、任务规划、技术架构、代码开发与测试验收的规范，让开发过程中的关键信息能够保留、不同任务能够依据共同标准推进、最终结果能够被独立验证。

**最终目标，一方面是通过规范化与 AI 辅助提升当前官网项目的协作效率和交付质量；另一方面是将实践中有效的架构原则、开发约束和质量检查方法沉淀下来，为后续项目提供能够复用并持续完善的工程基础。**

### 1.3 【工程化设计如何对应官网完整的研发流程？】

#### 【提问】

如何把需求、动态任务、技术方案与代码实现、测试以及上线复测连接成一条可追溯的过程？官网阶段的人与 AI 各承担什么工作？

#### 【回答要点】

##### 【五阶段生命周期把四项原则落实为具体的工作与产物】

四项原则是横向约束；它们需要落到传统 SDLC 的阶段中，才能形成可以真正运行的研发工作流。

###### <u>1. 需求分析——统一业务目标、行为与验收边界</u>

首先明确问题与业务目标，整理需求规则、适用范围、非目标、异常情况和安全要求。涉及前端页面时，还应通过 UI/UX 设计明确页面结构、交互路径、组件状态和设计变量，避免让 Agent 根据截图或一句话自由猜测。

这一阶段以需求规范、设计依据、Acceptance Criteria 和评审结论作为关键产物。产品、研发、测试等角色需要确认“最终做什么，以及什么算完成”。

这里优先应用**规范驱动与验证前置**，风险较高的业务规则还需要提前人工确认。

###### <u>2. 技术分析——建立工程边界、技术方案、Task 和 Test Case Matrix</u>

对于既有项目，应先读取真实代码仓库，理解模块结构、接口协议、数据流、公共能力和存量限制，明确 Change Scope：哪些内容必须改、哪些不能随意改。

之后形成技术方案与实施计划，将完整需求拆分为多个可以独立执行和验证的 Task，并为每个 Task 明确 Goal、Scope、Input、Output 和 Acceptance Criteria。

同时，根据需求规则制定 Test Case Matrix，进行技术方案和测试项的评审。**不能因为 Agent 能生成计划和测试，就跳过人对核心技术选择和验收预期的确认。**

这一步是**规范驱动、验证前置、可追溯**的交汇点，也决定后续 Agent 是否具备可靠执行依据。

###### <u>3. 代码开发——按照 Task 小批量实现、检查和修复</u>

Agent 依据确认后的 Task 小批量开发，而不是一次性生成整个需求的全部代码。每完成一个 Task，就执行相应的 Build、Type Check、Lint、Unit Test 或 Integration Test，形成短反馈循环。

随后可以由 AI 对 Git Diff 做第一轮 Code Review，检查是否超出 Scope、是否引入重复逻辑、破坏既有行为或带来安全与性能风险。能明确修复的问题由 Agent 修改并重新测试；高风险变更再交给人工 Review 和必要的合并门禁。

典型循环为：

~~~text
Task
  ↓
Implement（小批量实现）
  ↓
Test（针对性自动检查）
  ↓
AI Review（范围与质量审查）
  ↓
Fix / Re-test（必要时修复与重验）
  ↓
确认本任务完成并保存状态
  ↓
下一个 Task
~~~

这一阶段既强调**执行范围受规范约束**，也强调**过程产生可恢复、可审查的产物**。

###### <u>4. 测试验收——按照预先确认的 Case 和独立证据判断结果</u>

完整功能验收仍然需要回到技术分析阶段已经确认的 Test Case，而不能只依赖开发时的静态检查和单元测试。

对于需要操作页面的场景，Agent 可以通过浏览器工具选择操作顺序，但必须逐项产生 Actual Result 与 Evidence，如截图、DOM 状态、接口请求、日志及断言结果。特别是负向要求（例如无权限时不能获取真实数据、禁止提交时不得触发写请求），必须提供能够证明禁止行为确实未发生的证据。

这里应分别检查需求覆盖、代码覆盖、证据充分性、验收结论一致性，并让独立门禁决定 PASS、FAIL 或 Review，而不是只接受 Agent 的一句“全部通过”。

这一阶段体现了**验证前置的真正价值**：它为后续自主执行提供了不依赖实现本身的判定标准。

###### <u>5. 交付上线——保持发布可追溯、风险可控制和结果可观察</u>

代码测试通过以后，还需要经过合并与 CI/CD 门禁、构建正式 Release Artifact、目标环境验证以及适当的渐进式发布。

发布时需要知道版本对应的 Commit、依赖和构建结果；高风险变更要具备停止、回退和人工批准条件。上线以后持续观察错误率、接口异常、用户体验和必要业务指标，判断新版本是否稳定，以及最初的业务问题是否确实解决。

**Delivery Success（正确交付）与 Business Success（业务目标达成）应当区分。** 代码部署成功只说明版本已经上线，不足以证明需求带来了预期业务价值。

##### 【本节与后续讨论的衔接】

以上先明确**为什么要建立规范，以及规范需要共同解决什么问题**。接下来需要逐步回答“规范具体应该怎样设计、每项约束如何进入官网开发流程、有什么实际产物能够证明已落地”。

后续从 **需求分析与目标验收 → 技术与任务规划 → 工程架构与公共规范 → AI 辅助的模块化开发 → 持续检查和交付验收** 依次讨论，而不是直接罗列工具名称。下一章开始记录需求分析阶段。

官网项目的实践依据可对照：

- [官网开发记录](../G-官网开发.md)：Nuxt 目录分层、Design Tokens、组件与 Composables、AI 辅助框架搭建、代码和提交规范。
- [项目工程化设计](../X-项目工程化设计.md)：传统 SDLC 到 AI Native 的设计原则，以及五阶段的软件研发主线。
- [官网项目源码与复盘](https://github.com/cxDlogver/official-network/blob/main/docs/history/project-introduction.md)：官网需求、工程底座、协作与质量验证的实践分析。该记录中的建议性设计需要与实际配置区分，不能把规划中的 Hook、commitlint 或 CI Required Check 表述为全部已落地。

##### 【SDLC、AI-DLC、SDD 与 ATDD 处于不同层次】

| 概念 | 主要关注的层次 | 在这道题中的作用 |
| --- | --- | --- |
| SDLC | 软件研发的生命周期 | 提供需求、设计、编码、测试和交付的阶段性主线 |
| AI-DLC | AI 参与的开发生命周期与协作方式 | 让 Agent 承担更多执行任务，保留人工监督与阶段协作 |
| SDD | 规范驱动实现的方法 | 把目标、技术方案与任务逐步形成可以执行的规范 |
| ATDD | 验收标准前置的方法 | 以业务预期和测试场景建立独立的正确性标准 |

它们不是四种互相排斥的开发流程。不能说“用了 SDD 就不需要 SDLC”，也不能说“做了 AI Review 就完成了 ATDD”。

##### 【规范驱动与验证前置的区别】

规范驱动首先回答“应该做什么、修改什么、怎样组织任务”；验证前置进一步回答“必须观察到什么行为，才能证明做对了”。

两者的产物相互关联，但不应混为一份无法区分需求意图和测试预期的模糊提示词。

##### 【可追溯不等于只有执行日志】

Trace 是过程记录，Checkpoint 用于恢复，工程 Artifact 说明任务依据与阶段结果，Evidence 支撑具体测试断言。完成一次录屏或保存聊天记录不能自动代替这四种能力。

##### 【人工从主要执行转向决策、监督与负责，不是变成只看结果的审查员】

人仍然需要确认问题是否值得解决、要求是否正确、架构方案是否合适、哪些动作有风险，以及最终交付结果能否承担责任。AI 的自动化深度要根据任务明确性和可验证性逐步增加，而不是一开始就把所有动作授权出去。

##### 【四项原则不是对所有任务强制生成同一套长文档】

OpenSpec、Spec Kit、Superpowers 等方案可以体现阶段化、规范化和自动检查思想，但并不采用完全相同的运行方式，也不意味着每个微小修改都要生成完整 PRD、技术方案和测试矩阵。工程化强调的是**必要事实可见、约束明确、结果可独立判断**，形式应与任务风险相称。

#### 【标准回答】

我会先以需求分析确定问题、目标与验收依据，再在已有确定性约束下推进技术方案和按模块动态形成的任务；编码阶段通过代码组织、复用及静态检查统一输出，AI 参与辅助方案和实现，人工负责关键选择与整合。实现和测试证据关联到任务和版本，部署后再对照目标复测。这样不仅完成一次网站交付，也使过程可以回溯和交接。但要区分通用 AI Native 规范与官网当时实际采用的 AI 辅助研发，不能将设想中的端到端自动执行当作已落地事实。

## 2. 需求分析与目标验收

### 2.1 【如何从旧版官网问题推导业务目标和建设方向？】

#### 【提问】

**在官网 2.0 项目中，你是如何开展需求分析的？为什么强调先确定业务问题与目标，再制定可以量化的验收指标？Lighthouse 能够验证哪些目标，又有哪些目标不能只靠 Lighthouse 证明？**

这一问题既考察需求分析的实际过程，也考察候选人能否将“项目为什么值得做”与“后续技术方案应该如何设计”建立明确因果关系。

#### 【回答要点】

> **记录范围**：本节承接上一章“为什么建立可复用的工程规范”，开始逐步梳理官网项目中如何沿研发生命周期设计工程规范。当前先讨论**需求分析阶段的工作方法与项目事实**，后续技术选型、工程架构、开发与验收仍作为独立阶段继续讨论。实践背景参见 [官网项目介绍与复盘](https://github.com/cxDlogver/official-network/blob/main/docs/history/project-introduction.md)。
>
> **本阶段的核心观点**：技术方案不应先于问题定义；应先明确真实业务问题和目标，再将目标拆解为建设方向，并在进入技术规划前确定可检查、可度量的验收依据。

##### 【需求分析的起点是确定业务问题，而不是先决定框架与页面样式】

我认为，一项研发工作开始时，最重要的不是立即选择技术栈、设计组件或者让 AI 生成代码，而是先回答三个问题：**现状有什么问题？为什么需要解决？解决以后希望出现怎样的结果？**

官网 1.0 并不是因为“采用静态页面”这种技术形式就天然存在问题。真正需要改善的是：页面更接近若干静态内容区块的简单组合，企业业务信息展示不够充分；公司定位、产品能力、解决方案、资讯和招聘等内容之间缺乏清晰组织；视觉层次和交互反馈偏单一，难以引导访问者持续了解业务。

所以，官网 2.0 的业务目标不应只表述为“做一套更好看的界面”，而应进一步明确为：

> **重新组织企业业务信息与用户浏览路径，让访问者更快理解企业定位、产品和解决方案，通过清晰的页面内容与适当的互动提升继续浏览、深入了解或联系企业的意愿。**

用户浏览兴趣、停留时间或业务咨询是业务层期望改善的结果；在讨论具体实现以前，需要先把它们与可操作的工程建设任务分开。

##### 【业务目标向下拆解为四类建设目标，再分别设计验证方式】

业务目标不能直接变成一份代码任务。需要先转化为产品和工程可以共同理解的建设方向。

~~~text
现状问题：内容组织不足、企业业务表达不充分、页面交互单一
                         ↓
业务目标：让用户更快理解业务，并愿意继续浏览或建立联系
                         ↓
四类建设方向
├── 信息完整性：公司、产品、方案、资讯、招聘等内容表达清晰
├── 首屏与页面性能：重要内容尽快出现，加载与切换体验稳定
├── SEO 与搜索迁移：重要 URL 可以被发现、访问和正确理解
└── 交互与视觉体验：在可用性和性能约束下丰富页面表现
                         ↓
为各方向制定验收要求、测试口径和数据回收方法
                         ↓
评审确认后进入技术规划与任务拆解
~~~

其中，需要区分**目标、方案和指标**：

- **业务目标**回答“为什么投入这次重构”：希望访问者更好地认识企业并产生后续浏览、咨询等行为。
- **建设目标**回答“产品和工程必须改善哪些能力”：信息组织、首屏体验、SEO、视觉与交互。
- **实现方案**回答“具体采用什么技术”：例如 Nuxt 渲染方式、内容数据组织、图像处理和 SEO 组件化等，属于下一阶段的设计结果，并不是需求分析开始时预先确定的答案。
- **验收标准**回答“怎样证明建设目标得到满足”：包括明确的功能行为、可以自动审计的技术条件、性能指标和上线后的真实业务表现。

这也是为什么不能一上来就说“为了 SEO 所以选择 Nuxt”“为了性能所以做预渲染”。更准确的因果顺序是**先明确性能与 SEO 目标，再比较方案是否适合达成这些目标**。

#### 【标准回答】

官网旧版的主要问题不在于它使用某一种页面技术，而在于业务信息呈现不完整、产品与解决方案组织不清晰、交互形式偏简单。重构首先是帮助访问者更快理解公司业务，并愿意继续浏览、了解产品或联系企业。由这个业务目标拆出信息完整性、加载与首屏性能、SEO 与搜索衔接、交互与视觉体验四类建设方向。只有确定方向后，才进入 Nuxt 技术选型和具体实现方案，不应先有技术名词再反推需求。

### 2.2 【如何在需求分析时建立可验证的验收标准？】

#### 【提问】

为什么要把目标、方案和指标区分开？Lighthouse 可以验证哪些技术要求，不能代替哪些业务结果？基线尚不完整时如何处理？

#### 【回答要点】

##### 【验收指标需要分层，Lighthouse 不能替代全部业务结果】

官网项目采用 Lighthouse 作为开发与验收阶段的统一技术检查工具，这是把“页面快不快、SEO 技术基础是否合格”从主观印象转为可重复检查的重要一步。但验收不能只有一个笼统的 Lighthouse 分数。

| 建设目标 | 主要验证问题 | 可采用的验收依据 | 验证边界 |
| --- | --- | --- | --- |
| 信息完整性 | 公司、产品、方案等信息是否准确且易于查找 | 页面内容清单、关键信息核对、页面路径与导航检查 | 内容“存在”不等于用户已经充分理解 |
| 首屏与加载体验 | 主要内容是否较快出现，页面加载是否稳定 | Lighthouse Performance、FCP、LCP、CLS、TBT 等实验室指标 | 单次实验室评分不等于所有真实设备上的用户体验 |
| SEO 技术能力 | 页面是否可访问、可发现、可理解，元信息是否完整 | Lighthouse SEO 的部分基础检查；HTML/Head、Canonical、Sitemap、Robots 和结构化数据检查 | Lighthouse SEO 不能证明页面已经被收录，也不能保证排名 |
| 搜索结果新旧衔接 | 搜索结果中是否仍存在过时的旧版 URL 或内容 | URL 变化时的新旧映射与重定向检查、Search Console 索引和展示数据 | 搜索引擎重新抓取和更新有时间差，不能通过 Lighthouse 强制完成 |
| 交互与视觉体验 | 浏览路径、动画、响应式和操作反馈是否符合预期 | 桌面端/移动端页面验收、交互测试、布局与动效检查 | 动效丰富不必然提高用户兴趣，不能以动画数量衡量体验 |
| 真实业务效果 | 用户是否继续了解业务或进入后续行为 | 页面停留、关键内容访问、咨询点击、转化等行为数据 | 需要定义真实统计口径、基线与观察周期后才能判断是否改善 |

**关于 Lighthouse 的具体口径**：Performance 类别可以基于 FCP、LCP、TBT、CLS、Speed Index 等实验室测量形成评分；LCP 和 FCP 是指标，不应与“Lighthouse 分数”混为一项。INP 关注真实交互响应，更适合通过真实用户数据或专项交互测试观察，不能简单把一次页面加载的 Lighthouse 分数当作 INP 验收结果。

项目简历记录了使用 Lighthouse 进行技术验收且评分稳定在 **90+** 的成果表述；但“已有 90+ 结果”与“需求评审时明确写下 90+ 验收阈值”不是同一个事实。面试中应根据实际保存的测试报告与需求记录说明页面范围、测试类别、测试环境和评分口径，不为缺失的基线和目标阈值编造数字。

**关于旧版官网搜索结果**：如果新版沿用同一个 URL，应关注更新后的内容是否能重新被发现、抓取和索引；如果发生 URL 迁移，则需要明确旧 URL 到新 URL 的映射，按场景设置永久重定向、规范链接并更新站点地图。SEO 能提供正确的技术信号，但不能保证搜索平台立即清除或替换旧索引。

因此，需求验收不能全部压缩为一个技术评分。更合理的是区分：

1. **业务成功标准**：用户是否愿意深入了解产品、解决方案或产生后续联系，最终需要线上行为数据检验。
2. **产品与功能验收**：页面内容、路径、功能、视觉与响应式是否满足确认的要求。
3. **技术质量验收**：性能、SEO 基础条件、代码检查与构建是否满足事先确定的标准。

##### 【验收前置不等于所有指标在第一天就具备完整基线】

需求分析应当尽早明确**什么要被验证、通过什么方式验证、什么条件下可以判定完成**，但不意味着在尚未调研现状时就必须给每项指标编造精确数值。

例如：

- 对内容完整性，可以先确定必要页面及字段清单，进一步在评审中确认内容正确性。
- 对首页性能，可以先确定 Lighthouse 测试页面和实验环境，测量旧版或当前版本的基线，再设定可实现且有价值的性能目标。
- 对 SEO，可以先确定“重要 URL 可发现、可抓取、主体内容可获得、元信息一致”等技术验收项，再用 Search Console 验证实际收录表现。
- 对用户停留和转化，可先定义行为事件与统计口径，等数据采集和观察窗口充分后，再判断是否真正产生改善。

这样既遵循**验证前置**，又避免把当前尚未验证的假设包装成已经完成的量化成果。

##### 【需求评审让目标成为产品、研发、测试和 AI 共同遵循的事实依据】

工程规范中的需求分析不是单人写一段需求描述，而应当使不同参与角色对“问题、范围、预期结果、风险和验收方式”达成共同理解。

在官网项目中，AI 可以辅助整理旧版问题、页面模块、信息缺口和初步验收项，但最终业务目标的取舍、需求范围、优先级及通过标准仍需要依据真实业务材料进行人工确认。

这一阶段适合沉淀以下产物：

- **问题与背景说明**：旧版官网的具体不足，哪些属于有事实支撑的现状，哪些仍是待验证的判断。
- **业务目标与页面范围**：首页、产品、方案、资讯、招聘、联系各自承担的业务作用，明确本期范围和非目标。
- **建设目标与验收清单**：信息、性能、SEO、交互分别需要达到什么状态，以及采用什么方式检查。
- **度量基线与采集计划**：已经取得哪些 Lighthouse 或真实用户数据，哪些指标上线后才能收集。
- **评审记录与待澄清项**：记录参与者已确认的规则、尚有争议的问题及下一阶段必须处理的约束。

这里沉淀的规范不仅服务于当前开发者，还让后续接手的团队成员或 Agent 能够读取同一份需求事实，而不是重新猜测“官网重构究竟希望解决什么问题”。

##### 【业务目标是启动与后续决策的依据，不是唯一的启动条件】

我认为，你提出“目标是一项工作能否启动的基础”是重要的工程判断，但可以再补充一层边界：

> **明确业务目标是判断一项研发工作是否值得投入的前提；是否真正启动，还要综合预期收益、技术可行性、团队资源、执行成本和风险。**

这个判断也可以迁移到 AI Native 环境下的业务 Agent 化。例如，决定是否为一套传统业务流程接入 Agent，首先应当明确现有流程的效率瓶颈、错误率或人工成本；再评估 Agent 是否能够在可接受成本和风险下改善任务完成质量。之后才能根据任务完成率、人工干预率、返工率、执行成本等证据判断接入是否有实际价值。

不能因为“技术上可以接入 AI”就自动等同于“这个工作值得做”。

##### 【阶段产物与下一阶段技术分析的衔接】

需求分析的输出不应该只有一句“重构官网”。更完整的阶段产物是：

~~~text
旧版问题与业务事实
      ↓
业务目标与需求范围
      ↓
页面职责、内容及关键业务行为
      ↓
四类建设目标及对应验收要求
      ↓
已有基线、待测指标与评审结论
      ↓
进入技术分析：按目标评估技术方案、架构和工程初始化
~~~

下一阶段应继续回答：**为了达成首屏、SEO、信息组织和交互目标，为什么选择 Nuxt 4，如何按页面数据特征确定渲染策略，怎样设计模块职责与工程规范？** 技术方案应当是需求目标推导出来的，而不是事先选择框架以后再反向为选型寻找理由。官网项目初期的页面设计尚不完全明确，因此不额外设立独立的长期任务规划阶段。

#### 【标准回答】

第一阶段是需求分析。我认为它最重要的不是立即确定技术实现方式，而是**明确当前的业务问题与目标，并把目标转化为后续能够验证的标准**。

以官网 2.0 项目为例，旧版官网虽然能够完成基础的信息展示，但页面整体较简单，企业业务内容呈现不够完整，产品、解决方案等内容缺乏清晰的组织，交互形式也比较单一。这意味着用户进入官网以后，很难在短时间内建立对公司和产品能力的完整认识。

因此，我们希望通过重构重新组织官网的信息架构，丰富产品、解决方案等业务信息，再通过更清晰的视觉层次与适当的交互反馈，提升用户的阅读体验，使用户愿意进一步浏览和了解企业业务。

明确这一业务目标后，我把它拆成四个主要建设方向。

首先是**信息完整性**，要让公司定位、产品价值、解决方案及相关内容得到清晰、完整的表达。第二是**首屏体验**，官网作为用户了解企业的重要入口，必须让关键内容尽快出现，避免因为页面加载缓慢影响阅读。第三是**SEO 能力**，保证重要页面具备被搜索引擎发现、访问和理解的技术条件，同时关注新版与旧版 URL、内容和搜索索引之间的衔接。第四是**交互与视觉体验**，在保证性能与可用性的基础上，通过更好的内容层次、响应式布局和交互表现提高浏览体验。

有了建设方向，还必须继续把它们转换成验收标准。

例如在性能方面，我们引入 Lighthouse 建立统一的实验室测试与评分口径，关注 LCP、FCP、CLS 等指标，避免只用主观感受判断“页面够不够快”。在 SEO 方面，除了 Lighthouse 的基础技术检查，还要关注页面元信息、Canonical、Sitemap、结构化数据和实际索引情况。而用户是否愿意持续浏览，则需要结合真实页面停留、产品访问或其他关键行为数据进行后续判断。

这里我特别重视一个原则：**不能等到代码全部完成以后，才开始讨论怎样证明需求做对了。** 在需求分析时至少要先定义验收方向，在后续技术分析与评审中进一步细化测试环境、指标阈值、边界场景和 Test Case。

所以我理解需求分析阶段最重要的工程价值是：不仅确定“做什么”，还要明确“为什么做”和“怎样证明达到了目标”。只有这些要求得到基本确认，后续技术选型、任务规划、代码实现和验收才有共同依据。

这一方法也适用于后续的 AI 研发工作。比如判断是否需要把某个业务流程 Agent 化，应该先明确业务痛点和预期收益，再确认能否用完成率、人工投入、质量和成本等指标验证效果，而不是因为 AI 能实现，就认为这个项目一定值得启动。

## 3. 任务规划与动态管理

### 3.1 【需求不完整时如何逐步规划官网开发任务？】

#### 【提问】

**官网项目早期没有完整固定的需求与页面设计，进入实际开发后，你如何组织模块开发并保持进度可见？AI 如何辅助维护任务清单、整理代码与页面产物？怎样通过任务、路由、代码、截图和验证结果之间的关联，建立可回溯的项目执行记录？**

这道题的重点不是 AI 是否能一次性完成整个项目，而是当业务需求持续变化、开发者与 AI 都参与局部实现时，如何使项目进展**可理解、可交接、可定位、可验证**。

#### 【回答要点】

> **讨论范围**：本节延续第二阶段已形成的技术底座与工程规范，记录官网在实际页面开发过程中如何**按业务模块动态拆分工作、辅助维护任务清单、关联实现产物与验证记录**。强调“边开发边调整”，不把完整任务计划提前到项目启动阶段，也不把官网时期的 AI 说成端到端研发 Agent。
>
> **事实与设计边界**：以下动态清单、执行记录和页面截图的做法，来自本次项目经历的口述复盘；目前可从仓库验证页面路由和源码结构，但尚未找到能直接对应全部任务状态、截图及其版本关联的原始集中记录。文中的统一字段、任务 ID、状态机和证据链结构是对工作方法的**规范化梳理和建议模板**，并非声称当时已自动运行一套完整的 Agent 任务管理或自主验收系统。

##### 【项目启动时不冻结全部任务，开发过程中逐步形成动态清单】

官网 2.0 在开发初期没有完全确定所有页面设计和详细功能，因此不适合假设早期就存在一份覆盖整个项目、长期不变的任务计划。初期先明确业务目标、技术架构和基本工程规则；当具体页面需求逐步清晰后，再将实现工作按照业务模块拆分并持续维护。

当前官网主体可围绕以下业务模块组织开发工作：

| 业务模块 | 主要开发内容 | 对应实际路由举例 |
| --- | --- | --- |
| 首页 | 品牌首屏、产品矩阵、合作伙伴展示与引导 | `/` |
| 产品介绍 | 产品详情、核心能力、场景与页面区块复用 | `/product/[slug]` |
| 招聘 | 招聘介绍、岗位列表、岗位详情与流程 | `/join`、`/jobs`、`/jobs/[slug]` |
| 资讯中心 | 新闻列表、分类筛选、内容详情 | `/news`、`/news/[id]` |
| 联系 | 联系表单、提交反馈与关联接口 | `/contact` |
| 横向公共能力 | 导航、布局、SEO、响应式与公共设计规范 | 涉及多个页面与公共代码 |

“模块”是帮助团队管理工作范围的业务划分，不一定与单个路由一一对应：同一个模块可能有多个路由，也可能共用导航、SEO、组件、接口等能力。

实际拆解时，先按当前已经明确的页面或功能建立一组任务，再根据页面实现、设计反馈和新需求持续添加、修改、合并或拆分任务。不应要求每个页面一开始就确定全部细节。

##### 【任务清单既记录完成进度，也要明确任务的实现边界】

开发清单不能只有“做首页”“做招聘”这样缺少判断依据的标题。为了便于研发人员与 AI 接续工作，每项任务最好包含：任务目标、所属模块、前置条件、关联代码与路由、当前状态、完成要求以及遗留问题。

任务状态可保持简洁，例如：

~~~text
待明确 → 待开发 → 开发中 → 待验证 → 已确认
                        │         │
                        └──返工◄──┘
~~~

这里状态表达的是团队对工作的**当前认定**，并不代表 AI 输出一句“已完成”就能直接变成已验收；缺少必要检查时，应当保留为待验证。

例如“产品详情页实现”的任务，可以先明确路由、数据读取、页面区块、响应式和 SEO 等具体要求。后续页面设计如果变更，再调整该任务范围或新增子任务，不需要推翻整个官网的工程计划。

该清单的核心作用是让协作者无需浏览大量聊天和代码，也能快速知道：**本次要做什么、做到哪里、哪些内容还需要检查、下一步从哪里接续**。

##### 【AI 辅助执行与维护记录，不代替开发者决定项目状态】

在当前官网项目中，AI 更多是开发辅助者。它可以根据开发人员已明确的模块需求生成候选代码、分析改动范围、整理本次开发产物，并辅助补充任务清单和执行记录；但核心架构、业务判断、人工整合与最终检查仍由开发人员负责。

可以将这一过程理解为：

~~~text
研发人员明确当前页面或功能需求
              ↓
根据业务模块确定当前可开发的任务
              ↓
AI 辅助生成或修改局部代码
              ↓
研发人员审查并整合到现有架构
              ↓
执行构建、代码检查及必要的功能/页面验证
              ↓
整理任务记录：改动文件、页面路由、截图、结果与遗留问题
              ↓
研发人员确认状态，决定继续开发、调整或返工
~~~

这与后续 Agent 以任务调度器为核心、自动推进多阶段研发、跨 Session 恢复和执行全部门禁的工作流并不相同。**不能把“AI 帮助更新记录”描述成“Agent 自主管理整个研发流程”。**

#### 【标准回答】

项目初期页面需求和视觉设计没有完全确定，因此我不会预先冻结所有任务，而是先明确已有业务模块和本期能确认的目标，在开发中动态拆分并调整任务。每项任务说明实现范围、依赖、负责人或执行主体、相关文件和完成条件。AI 可以辅助整理任务、归纳修改和生成初稿，但任务状态、优先级与最终验收仍由研发人员判断。动态规划的目的不是不做计划，而是在不断出现新事实时仍然保持执行清楚、变更可管理。

### 3.2 【如何建立任务与代码、截图、测试结果的可追溯关系？】

#### 【提问】

开发过程中的任务、路由、提交、代码文件和页面截图应该如何关联？需求发生变化后如何重建证据链？

#### 【回答要点】

##### 【工程产物关联让任务状态不再是孤立的完成标记】

仅保留任务名称和“已完成”状态，无法让后续参与者判断具体实现在哪里，也无法审查任务是否真的符合原始目标。因此，应当将任务与可以定位的工程实体建立关联。

可以采用如下关系：

~~~text
需求与预期行为
      ↓
页面/功能 Task（所属模块、当前状态）
      ├─ 对应路由：在哪里访问
      ├─ 源码文件：在哪里实现
      ├─ Git Commit / PR：哪个版本引入了实现
      ├─ 截图或录屏：页面呈现了什么
      ├─ 测试结果：哪些行为和异常路径得到检查
      └─ 验收结论：谁依据什么标准确认
      ↓
下一个开发者或 AI 能够定位、审查并继续迭代
~~~

这里的**产物记录（Artifact）**和**验证证据（Evidence）**要区分：代码、路由和提交记录说明做了什么；截图提供特定页面和视口的视觉结果；测试或交互检查说明验证了哪些行为；最终“是否符合要求”还需要依据验收标准判断。

一个可以参考的任务记录示例：

| 字段 | 示例内容 |
| --- | --- |
| 任务 ID | GW-PRODUCT-01（示意编号，并非仓库已有 ID） |
| 业务模块 | 产品介绍 |
| 目标 | 使用统一数据结构展示某个产品的详情与主要区块 |
| 对应路由 | `/product/[slug]` |
| 关联代码 | `app/pages/product/`、`app/components/product/`、`app/composables/useProduct.ts` |
| 改动版本 | 当前任务对应的 Commit 或 PR，正式使用时填写真实标识 |
| 视觉证据 | 桌面端和移动端页面截图，注明路由与版本 |
| 功能验证 | 产品数据映射、路由参数、链接、异常输入和 SEO 检查 |
| 当前状态 | 待验证或已确认，以实际检查结果为准 |
| 遗留问题 | 未完成内容、需继续处理的设计与性能问题 |

示例的价值是展示任务记录应具备哪些关联维度，而不是为了形式上生成大量字段。较小任务可以只保留最必要的信息，复杂或高风险变更再增加相应的检查内容。

##### 【截图是页面实现证据，但不等于任务已经通过完整验收】

官网是强视觉与信息展示型项目，页面截图对协作很有帮助。它可以在不运行开发环境的情况下，帮助后续开发者快速理解特定版本的页面结构、内容摆放、组件状态和响应式效果。

但截图具有明确边界：

- 可以佐证某个时间、路由、视口下的可见页面结果。
- 不能单独证明交互逻辑、API 错误处理、路由参数与内容匹配或服务端 HTML 的 SEO 正确性。
- 不能单独证明 Lighthouse 分数、真实用户体验或实际搜索收录效果。
- 未标注版本与测试环境的旧截图，不能自动证明最新代码仍满足需求。

因此，本项目更合理的做法是按任务需要组合**截图、页面检查、自动测试结果、构建或 Lint 结果、代码版本信息**。特别是对于资讯筛选、招聘详情或联系表单等功能，必须结合实际交互和数据行为验证，而不是只看页面已呈现就宣布功能完成。

##### 【需求变化时要同步维护任务、产物和验证结果】

动态任务清单并不是“完成一次后永久不变”。官网持续新增页面区块、修改视觉方案、完善 SEO 或交互时，已经完成的任务也可能受到影响。

变化发生后应尽量执行以下更新动作：

1. **变更范围**：确认是新增功能、修改已有行为，还是替换原方案；更新任务描述或建立新记录。
2. **影响定位**：通过所属模块、路由和关联代码确认哪些页面、组件或公共逻辑受到影响。
3. **实现与版本更新**：将新代码变更关联到对应 Git 记录，避免把多个版本混为一谈。
4. **重新验证**：当原验收条件可能失效时，将状态退回待验证，重新取得必要的截图或测试结果。
5. **保留变更依据**：记录此次调整的原因和遗留问题，便于下一位开发人员理解。

特别需要注意的是：**可追溯性不是把所有文件和截图堆到一个目录里，而是让变更的原因、实现范围、证据和结论能够相互定位。**

工程记录还应避免不必要的冗余。一个足够稳定的任务编号、清晰的代码位置、具体的验证结果和可回看的提交记录，通常比大量重复的自然语言总结更有价值。

##### 【这项设计同时解决协作交接与 AI 上下文延续问题】

对于多人协作，结构化任务与产物记录使团队能够快速了解已经完成的内容、当前风险与下一步工作，不必依赖原开发人员反复解释。

对于 AI 辅助开发，这类记录也能帮助新的对话或新一次代码辅助更快获得当前任务背景：已有实现在哪里、哪些模块不应重复创建、上一次改动是否通过检查、还存在哪些问题。

但这种“通过记录补齐上下文”的工程方法，不等于项目已经搭建了自动持久化 State、Checkpoint 和 Agent Runtime。官网时期更合理的表述是：**通过文件、代码历史和必要的任务记录支持人工与 AI 的连续协作；自动化执行和自动恢复属于未来可以强化的方向。**

##### 【阶段总结与后续衔接】

本阶段最重要的收获，是将“开发一个功能”进一步理解为一项有状态、可定位、可检查的工程活动。与前两个阶段可以连接为：

~~~text
需求分析：解决什么问题、期待什么结果、怎样验收
                         ↓
技术设计：选什么框架、代码怎样分层、遵循什么规范
                         ↓
开发执行：在需求逐渐明确时动态维护模块与任务
                         ↓
实现记录：关联代码、路由、提交、页面截图和检查结果
                         ↓
持续改动：定位影响范围、更新记录、重新验证
                         ↓
后续测试验收：依据确认的标准审查行为与质量
~~~

后续讨论可以继续深入**具体页面的模块化开发、AI 辅助实现与持续测试验收**。本章记录的是开发组织与追溯方法，不应替代后续对功能正确性、视觉一致性、SEO 与性能的专项验收。

#### 【标准回答】

在完成技术选型和工程初始化之后，就进入具体的代码开发阶段。

**我在这个阶段重点考虑的，是如何让开发过程保持可持续管理与可追溯，而不是每实现一个页面就只留下孤立的代码提交。**

由于官网项目一开始并没有把所有页面设计和需求细节确定下来，所以我没有采用一次性冻结全部任务计划的方式，而是随着开发逐步明确需求，再按业务模块动态建立和维护任务清单。

整个官网主要包含首页、产品介绍、招聘、资讯中心和联系页面等模块。每个模块下又可以继续拆分页面结构、内容展示、接口接入、交互与响应式等具体工作。这样一方面方便不同研发人员了解项目当前进度，另一方面也方便针对新需求持续调整任务内容。

AI 在这里主要起辅助作用。它可以帮助我实现部分页面代码、整理某次开发涉及的文件和功能，以及辅助更新当前任务的完成情况与遗留问题。它不是独立决策和推进所有研发阶段的 Agent，关键实现判断与最终确认仍由我负责。

**更重要的是，我希望任务清单不仅记录“完成了没有”，还要能对应到真实产物。**

例如完成一个产品详情页面的功能后，除了记录任务状态，还可以关联该功能对应的页面路由、组件代码、提交记录和页面截图。截图帮助确认当时页面的视觉结果，功能与代码检查则进一步证明具体交互和实现是否符合预期。

这样后续开发人员看到一个任务，就能快速找到对应代码和页面结果，不需要重新翻阅大量聊天记录或逐个搜索文件。后续如果增加新功能，或者修改已经实现的页面，也可以沿着这些关联定位影响范围，再更新任务状态与验证证据。

所以这一阶段我希望形成的工程方法是：**在需求持续变化的情况下，通过动态任务清单和工程产物关联，将开发进度、代码实现和验证依据连接起来，使项目可以被持续推进、回顾和交接。**

这既服务于传统的多人协作，也为 AI 辅助编码提供了更加明确的项目上下文。它的意义不是把官网变成一套全自动 Agent 研发系统，而是以较轻量的方式提高过程透明度、减少重复理解，并为后续规范化研发沉淀可以复用的方法。

## 4. 技术设计与代码实现

### 4.1 【为什么官网选择 Nuxt 4？如何由目标推导技术选型？】

#### 【提问】

**官网重构在需求分析阶段明确首屏性能、SEO、信息展示与交互体验目标之后，为什么选择 Nuxt 4？如何在项目初始化时建立架构分层、代码质量、设计复用与 AI 辅助开发规范？这项工作怎样体现工程设计思想，而不是简单搭建一个前端项目？**

回答应先解释目标如何推导技术方案，再展示从零初始化的工程约束，最后说明人和 AI 如何在同一套规则下开展实际开发。不应只罗列框架、插件和脚手架命令。

#### 【回答要点】

> **记录范围**：承接需求分析阶段形成的首屏体验、SEO、信息展示和交互目标，记录官网 2.0 如何开展技术选型、工程初始化、架构与模块设计、代码及设计规范、AI 辅助开发约束。
>
> **实践边界**：官网开发初期的页面设计与业务细节并未完全明确，因此不单独加入“任务规划”阶段，也不把一开始便形成完整 Task 清单当成已发生的事实。本项目中的 AI 主要辅助方案分析、页面探索、代码开发和第一轮检查；研发人员主导技术判断、实现整合和交付质量。这不同于后续由 Agent 承担主要执行任务的端到端 AI Coding 工作流。

##### 【技术方案必须从业务目标推导，而不是先选框架再寻找理由】

上一阶段已经将官网重构拆为四类建设方向：信息完整性、首屏性能、SEO 和视觉交互。进入技术设计时，我首先要判断的是：**什么技术体系能够以合理的实现、部署和维护成本，支持这些目标？**

旧版官网信息承载不足，不代表“使用静态页面”本身是错误。新版官网仍然有许多稳定、公开、适合静态交付的页面。真正需要变化的是页面内容组织方式，以及不同类型内容在首屏、SEO 和更新时效方面所需的交付能力。

基于企业官网的业务特点，我选择 **Nuxt 4 + Vue 3 + TypeScript** 作为主技术栈，原因主要有两个。

**第一，Nuxt 的混合渲染能力适合官网不同页面的更新特点。**

相较于主要由浏览器下载并执行 JavaScript 后生成内容的普通 CSR 单页应用，Nuxt 能够通过服务端渲染、预渲染和缓存策略，让需要被用户与搜索引擎读取的 HTML 在更合适的时机生成。这提供了优化首屏和搜索抓取基础的手段，但并不自动保证 LCP 达到某个分数。

项目实际通过 [nuxt.config.ts](https://github.com/cxDlogver/official-network/blob/main/nuxt.config.ts) 中的 Route Rules，对页面采取不同策略：

| 页面类型 | 当前配置 | 采用该策略的原因 |
| --- | --- | --- |
| 首页、产品、解决方案、招聘、联系等内容相对稳定的页面 | Prerender | 构建时生成公开 HTML，访问时避免重复计算页面主体 |
| 新闻列表与详情 | SWR 86400 秒 | 新闻依赖会更新的内容源，复用缓存结果，同时保留内容更新途径 |
| 新闻、联系、订阅等 API | Nitro Server API | 由站点服务端统一代理、整形与处理接口，减少页面直接依赖外部系统 |

所以，这里的设计思想不是“全站都用 SSR 才有 SEO”，而是**根据页面是否公开、内容是否稳定、更新频率与加载要求分配渲染策略**。后续还需要通过实际的 LCP、FCP、CLS、接口耗时和资源加载结果验证性能，并关注预渲染内容的更新与重新构建。

**第二，Nuxt 的 SEO 相关生态适合形成统一工程能力。**

官网需要在首页、产品、新闻和招聘等页面分别管理标题、描述、Canonical、分享信息与结构化数据，并提供 Sitemap 等抓取入口。Nuxt 可通过页面 Head 能力和相关模块在一个项目里组织这些能力；项目配置已经包含 @nuxtjs/seo、@nuxt/image 等模块。

这降低了把 SEO 能力做成统一规则的实现成本，但不能把“安装 SEO 模块”视为“网站已经被搜索引擎收录”。真正的搜索结果仍然需要通过页面 HTML、URL、抓取条件和线上搜索数据进一步验证。

因此，**选型结论由需求和约束推出，后续验收再反向验证选型是否有效**，而不是为了使用某个框架而编造业务理由。

#### 【标准回答】

第二阶段是技术方案设计和工程初始化。我认为这一阶段最重要的，是**根据需求目标选择合适的技术体系，并在大规模开发之前建立统一的架构和工程规范**。

首先是技术选型。在需求分析阶段，我们已经明确官网需要重点优化首屏体验和 SEO，所以我主要围绕渲染方式、SEO 支持和内容维护成本比较方案，最终选择 Nuxt 4。

Nuxt 的优势在于支持混合渲染。比如首页、产品和解决方案等内容稳定的页面，可以在构建时预渲染；新闻这种需要持续更新的页面则可以使用 SWR 策略，在复用页面缓存的同时保留更新能力。同时，它的 SEO 相关生态也方便我们后续将页面元信息、结构化数据和抓取入口统一管理。这些能力都能和前面确定的需求目标对应起来。

第二是项目架构设计。因为官网是从零建设的，我希望尽早确定代码应该怎样组织。我们利用 Nuxt 约定式目录统一页面路由、组件、Composables 和服务端接口，同时结合官网以内容区块为主的特点，将组件分成布局级、页面 Section 和局部复用三个层次。

页面主要负责路由和装配，Composable 负责公共逻辑，数据与内容独立管理，Server API 负责对外部系统的适配。这不仅让目录清晰，更重要的是让不同代码职责明确，后续新增页面或调整业务时能够复用现有能力，减少重复实现。

第三是工程规范设计。项目通过 TypeScript、ESLint、Prettier 和统一的开发、测试、构建脚本，对类型、编码规则、格式和基础检查进行约束。同时，结合 Tailwind 和 Design Tokens，把品牌色、排版、间距与动效等基础视觉规则统一起来，减少不同页面之间的样式差异。提交说明也尽量按照统一的类型约定记录，未来还可以通过提交钩子和自动化门禁进一步强化。

第四是 AI 辅助开发的约束。这个项目中 AI 并不是主要的端到端执行者，而是帮助我们分析技术方案、探索视觉设计和生成部分代码。我负责关键架构判断、代码整合和质量审查。因为 AI 生成代码也容易与已有结构不一致，所以我希望它优先参考现有目录、公共组件和设计规范，而不是每次重新创建一套实现。后续还可以将这些规范整理成 Agent 可读取的项目说明。

另外，项目一开始并没有完全确定所有页面设计和详细任务，所以我没有把制定完整任务计划作为独立的固定阶段。我的做法是先建立稳定的工程底座，再随业务与页面设计逐步明确，不断收敛公共能力和开发规范。

**因此，这个阶段最有价值的工作不是把 Nuxt 项目搭起来，而是通过目标驱动选型、职责清晰的架构设计以及统一的技术与设计规范，让当前官网能够持续演进，也为后续团队和 AI 辅助研发形成可复用的工程基础。**

### 4.2 【如何设计官网的模块职责与组件复用边界？】

#### 【提问】

页面、布局、组件、公共逻辑、业务数据和服务端接口分别负责什么？什么时候应抽取 Section 或公共组件？

#### 【回答要点】

##### 【工程初始化不仅是生成脚手架，更要先建立统一职责边界】

既然已经明确技术体系，接下来就需要在大量页面开始开发之前，先确定整个项目应该遵循什么结构与开发规则。

Nuxt 的一个特点是约定式目录。只要遵循框架约定并满足相应扫描条件，页面路由、组件、Composables、插件和部分服务端接口就能按对应目录接入，不需要为每一个常规文件重复编写注册配置。

但是，**约定优于配置只解决“框架如何识别文件”，不能代替项目的业务架构设计**。我们仍然需要明确哪些内容放在页面、组件、公共逻辑、数据或服务端适配层，防止多人或 AI 各自设计一套组织方式。

官网项目实际形成的目录职责可以概括为：

~~~text
项目工程
  ├─ app/pages        页面路由、页面级数据装配与 SEO 接入
  ├─ app/layouts      全站布局与设备形态的整体组织
  ├─ app/components   页面区块与局部展示组件
  ├─ app/composables  可复用的数据查询、状态和 SEO 逻辑
  ├─ app/data         产品、解决方案等结构化展示数据
  ├─ app/types        产品、资讯等类型和接口约束
  ├─ content          招聘岗位等 Markdown 内容
  ├─ app/assets       样式、主题变量、动画等视觉资产
  ├─ server/api       WordPress 新闻、联系、订阅等服务端适配
  └─ nuxt.config.ts   模块、渲染、运行时与构建配置
~~~

这样划分并非追求目录数量，而是让不同层承担相对稳定的职责。

例如，产品详情页面根据路由参数取得对应产品数据，再装配产品介绍、价值、功能、场景等业务 Section；产品数据由结构化配置管理，公共查询逻辑则通过 Composable 复用。新增一个产品时，不应复制整套页面和查询逻辑。

明确职责边界后，团队成员能够知道需要到哪一层修改代码；AI 在生成新页面时，也能通过读取现有目录和实现，优先延续项目已经形成的结构。

##### 【模块化设计要服务于官网特点，避免为了抽象而抽象】

官网的主要复杂度集中在品牌表达、信息区块组织、内容复用和视觉交互，而不是典型后台系统中大量复杂表单状态。因此，组件设计采用更适合当前业务的分层方式：

1. **布局级组件**：导航栏、菜单、页脚、订阅区等全站共同使用的页面框架。
2. **页面 Section 组件**：首页 Hero、产品矩阵、解决方案痛点与实施过程、招聘展示等相对独立的内容区块。
3. **局部复用组件**：重复出现的卡片、信息单元等，在确有复用价值时抽取。

这里有两个重要判断。

第一，组件化不是让所有内容都抽成极小的原子组件。对于只属于某个业务页面的独立区块，让它保持合理的完整性，反而更方便修改和验收。

第二，**界面复用、逻辑复用和数据复用属于不同层次**。Component 处理如何展示，Composable 处理通用业务逻辑或状态，Data/Content 管理内容，Server API 对外部内容源进行适配。这样在调整某类内容或行为时，不需要同时修改大量无关页面。

模块化设计对 AI 辅助开发也有直接价值：它使一次局部需求有更明确的修改边界，避免 AI 为了实现一个页面区块重复生成其他页面已经具备的公共能力。

#### 【标准回答】

Nuxt 的约定目录提供框架入口，但业务模块仍需要有明确职责。我将页面路由与内容装配放在 pages，共享页面结构放在 layouts，展示区块放在 components，通用逻辑放在 composables，结构化数据与类型放在 data/types，外部数据适配放在 server/api。复用时区分布局级组件、页面 Section 与局部公共组件，只在存在稳定共同机制时抽取，避免过度原子化，让不同页面和 AI 辅助修改都遵循同一结构。

### 4.3 【如何通过代码质量工具建立统一的研发与提交检查？】

#### 【提问】

TypeScript、ESLint、Prettier、commitlint、Husky、lint-staged 之间如何分工？项目现状与建议质量门禁如何区分？

#### 【回答要点】

##### 【工程规范应同时统一代码结构、格式、提交方式与测试入口】

多人协作不应该依赖每个人记住同样的代码习惯。AI 加入之后，代码产生速度更快，风格不一致和重复实现的问题也可能更快积累，所以需要尽早把稳定规则固定下来。

项目的主要工程规范及实际状态如下：

| 规范或工具 | 解决的问题 | 官网仓库的实际状态 |
| --- | --- | --- |
| TypeScript | 统一数据模型和类型约束，提前发现部分接口与调用错误 | 已使用 |
| ESLint | 检查代码组织和约定规则，例如 import/export 排序、Vue SFC 结构 | 已配置 |
| Prettier | 统一引号、尾逗号、行宽和 Tailwind CSS 类名排序 | 已配置 |
| pnpm 与脚本 | 统一依赖和开发、格式化、检查、测试、构建入口 | 已配置 |
| Vitest | 为可自动验证的逻辑提供测试能力 | 有测试入口及部分测试文件 |
| Commit 类型约定 | 在历史记录中说明功能、修复、构建变更的性质 | 存在接近 Conventional Commits 的提交习惯 |
| Husky、lint-staged、commitlint | 把部分检查变成提交阶段自动执行的门禁 | 当前没有找到完整对应配置，不作为已落地成果 |

从作用上讲，这些机制是分层的：

- **类型与代码规范**：通过 TypeScript、ESLint 等约束容易静态判断的问题。
- **格式规范**：由 Prettier 统一排版，避免代码审查集中在无意义的风格差异。
- **提交规范**：使 Git 历史尽量能表达每次变更的类型和目的。
- **检查与验证**：通过项目统一脚本执行代码检查、测试和构建，逐步减少低级问题进入后续开发的机会。

例如，官网的 ESLint 配置明确要求 import/export 排序、Vue 单文件组件采用 script、template、style 的顺序；Prettier 统一单引号、不使用分号、100 字符行宽、保留尾逗号，并通过插件排序 Tailwind 类名。这些具体设置都可以在 [eslint.config.mjs](https://github.com/cxDlogver/official-network/blob/main/eslint.config.mjs) 和 [.prettierrc.json](https://github.com/cxDlogver/official-network/blob/main/.prettierrc.json) 中核对。

这里必须区分：**已经配置 Lint、Prettier 和测试脚本，不等于已经建立每次提交都自动运行且失败即阻断的完整质量门禁**。Husky、commitlint、lint-staged 和 CI Required Checks 是可以进一步强化的方向，不能在没有配置证据时描述成官网项目已完成的成果。

这一部分专门说明官网工程规范涉及的四类工具如何配置和配合，核心目的不是背工具名，而是解释**谁定义规则、谁执行规则、谁负责在 Git 生命周期触发规则**。

| 工具 | 主要职责 | 被检查的对象 | 与其他工具的边界 |
| --- | --- | --- | --- |
| ESLint | 静态代码规则检查及部分自动修复 | JS/TS/Vue 等源码 | 能发现符合规则定义的问题，但不能替代完整类型检查与测试 |
| Prettier | 按统一配置格式化代码 | 源码、CSS、JSON、Markdown 等 | 负责排版和部分约定排序，不判断业务逻辑是否正确 |
| commitlint | 按约定验证 Commit Message | Git 提交说明 | 不检查提交的具体代码 |
| Husky | 管理项目的 Git Hook 脚本 | `pre-commit`、`commit-msg` 等执行节点 | 只负责触发所配置命令，本身不定义编码或提交信息规则 |
| lint-staged（可选） | 将检查限定在本次暂存的匹配文件 | Git 暂存区中的文件 | 与 Husky 配合减少每次扫描全仓库的开销 |

**规则与触发需要分开设计**：安装 ESLint、Prettier 或 commitlint 后，相关检查通常仍需要命令触发；安装 Husky 也不会自动知道项目需要检查哪些内容。

##### 1. ESLint：用静态规则限制代码写法

ESLint 可以检查未遵守约定的写法、部分可疑代码和结构问题，并通过 `--fix` 自动修复支持自动修复的规则。最常见的命令为：

~~~bash
pnpm add -D eslint

# 检查当前项目
pnpm exec eslint .

# 只检查一个文件
pnpm exec eslint app/pages/index.vue

# 自动修复可修复的问题
pnpm exec eslint . --fix
~~~

现代 ESLint 通常在 `eslint.config.mjs` 等 Flat Config 中配置规则。一个简化示例如下：

~~~js
export default [
  {
    files: ['**/*.{js,ts}'],
    rules: {
      'no-debugger': 'error',
      'no-console': 'warn',
    },
  },
]
~~~

| 规则级别 | 效果 |
| --- | --- |
| `off` | 关闭规则 |
| `warn` | 产生警告，默认不直接导致命令失败 |
| `error` | 产生错误，令检查命令失败 |

**官网实际配置**见 [eslint.config.mjs](https://github.com/cxDlogver/official-network/blob/main/eslint.config.mjs)：基于 Nuxt 生成的 ESLint 配置，新增 `simple-import-sort/imports`、`simple-import-sort/exports` 检查导入与导出顺序，使用 `vue/block-order` 约束 Vue 单文件组件的结构顺序为 `script → template → style`，最后通过 `eslint-config-prettier` 关闭与格式化规则冲突的 ESLint 规则。

~~~vue
<script setup lang="ts">
const title = '官网首页'
</script>

<template>
  <h1>{{ title }}</h1>
</template>

<style scoped>
h1 { font-weight: bold; }
</style>
~~~

需要强调，**ESLint 的检查通过不意味着 TypeScript 全量类型检查通过，也不意味着功能测试已通过**。尤其是 Nuxt/Vue 项目，类型验证、构建和行为测试应各自提供检查依据。

##### 2. Prettier：将格式从个人习惯转化为确定性结果

Prettier 专注格式统一，通常使用以下命令：

~~~bash
pnpm add -D prettier

# 自动格式化并修改文件
pnpm exec prettier . --write

# 只检查格式，不修改文件
pnpm exec prettier . --check
~~~

`--write` 会修改文件；`--check` 检测是否已符合格式要求，更适合作为只读检查或 CI 条件。二者不能混为一谈。

**官网实际配置**见 [.prettierrc.json](https://github.com/cxDlogver/official-network/blob/main/.prettierrc.json)：

~~~json
{
  "semi": false,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all",
  "plugins": ["prettier-plugin-tailwindcss"]
}
~~~

这表示使用单引号、一般不加语句结尾分号、以 100 字符作为期望行宽、保留适用位置的尾随逗号，并通过插件统一 Tailwind 类名排序。

例如：

~~~js
// 格式化前
const product = {name: "A", count: 1};

// 格式化后
const product = { name: 'A', count: 1 }
~~~

ESLint 和 Prettier 建议分工明确：**ESLint 查规则，Prettier 管排版**。`eslint-config-prettier` 只负责关闭有冲突的 ESLint 规则，不会替你自动执行格式化。

##### 3. commitlint：让一次 Git 提交的目的可以快速理解

提交信息不应该长期停留在“修改代码”“调一下”这类无法追溯的描述。常见的 Conventional Commits 风格为：

~~~text
<type>(<scope>): <subject>

feat(home): add product showcase
fix(news): correct pagination behavior
refactor(product): extract common sections
docs(readme): update setup instructions
~~~

其中 `type` 表示变更类型、`scope` 表示受影响模块（通常可选）、`subject` 描述本次改变。常见的类型如下：

| 类型 | 含义 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档修改 |
| `refactor` | 不改变预期功能的代码重构 |
| `test` | 测试相关变更 |
| `build` | 构建或依赖相关修改 |
| `ci` | CI 配置变更 |
| `chore` | 其他工程维护任务 |

如果要用 commitlint 实施校验，可以安装：

~~~bash
pnpm add -D @commitlint/cli @commitlint/config-conventional
~~~

创建 `commitlint.config.mjs`：

~~~js
export default {
  extends: ['@commitlint/config-conventional'],
}
~~~

手动检查一个提交说明：

~~~bash
echo "feat(home): add hero" | pnpm exec commitlint
~~~

**commitlint 只检查提交说明，不会检查本次提交的源码；命令是否自动执行取决于后续是否绑定 Git Hook。**

##### 4. Husky：通过 Git Hook 在提交生命周期触发检查

Husky 用于管理仓库的 Git Hooks。最常见的钩子：

| Hook | 时机 | 适合的检查 |
| --- | --- | --- |
| `pre-commit` | 生成提交前 | ESLint、Prettier 等文件检查 |
| `commit-msg` | 检查提交信息阶段 | commitlint |
| `pre-push` | 执行推送前 | 按项目成本选择测试或其他检查 |

安装并初始化：

~~~bash
pnpm add -D husky
pnpm exec husky init
~~~

对于简单仓库，可以在 `.husky/pre-commit` 中配置：

~~~sh
pnpm run lint
pnpm exec prettier . --check
~~~

这会扫描相应范围的项目文件，但仓库较大时提交等待时间可能变长。若需要验证提交信息，可另建 `.husky/commit-msg`：

~~~sh
pnpm exec commitlint --edit "$1"
~~~

此处 `"$1"` 是 Git 提交消息文件的路径，`commitlint --edit` 通过这个文件读取本次提交说明。**提交消息校验应放在 `commit-msg`，不能把它错误理解为 `pre-commit` 中的普通代码规则检查。**

Husky 只负责在恰当时机触发命令；若某个 Hook 没有配置运行 ESLint、Prettier 或 commitlint，便不能说这个 Hook 已经完成对应检查。

##### 5. lint-staged：降低提交检查成本

如果每次提交都对整个仓库运行 ESLint 和 Prettier，成本会随项目规模增加。可以将 `lint-staged` 与 Husky 配合，让前者只处理本次暂存区中符合规则的文件。

~~~bash
pnpm add -D lint-staged
~~~

在现有 `package.json` 中**合并**下面的 `lint-staged` 配置，而不是直接替换原有 `scripts` 和依赖：

~~~json
{
  "lint-staged": {
    "*.{js,ts,vue}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{json,css,md}": "prettier --write"
  }
}
~~~

然后将 `.husky/pre-commit` 改为：

~~~sh
pnpm exec lint-staged
~~~

在默认配置和正常执行情况下，lint-staged 会将匹配的暂存文件传给对应命令，并管理成功修复后的暂存结果。相比运行 `prettier . --write`，它不会无差别格式化整个仓库。

如果想保留一个仅检查、不修改代码的命令，还可以增加：

~~~json
{
  "scripts": {
    "format:check": "prettier . --check"
  }
}
~~~

它应合并到现有脚本配置中；真正的全项目检查、类型检查、测试和构建，可以另由开发人员手动运行或在 CI 中统一执行。

##### 6. 四个工具如何串起一次 Git 提交

~~~text
git add：修改进入暂存区
        ↓
git commit：Git 开始提交
        ↓
Husky / pre-commit
        ↓
lint-staged 按暂存文件范围调用
        ├─ ESLint：代码规则检查、支持的自动修复
        └─ Prettier：格式统一
        ↓
Husky / commit-msg
        ↓
commitlint：验证 feat/fix 等提交信息结构
        ↓
所有必须通过的检查成功
        ↓
创建 Commit
~~~

实际开发操作例如：

~~~bash
git add app/pages/index.vue
git commit -m "feat(home): add product section"
~~~

其中还存在两个重要边界：

- **Git Hook 不等于不可绕过的质量门禁**。本地 Hook 可能被跳过，例如 `git commit --no-verify`；若团队要求合并前强制通过某些检查，应进一步在 CI 与仓库分支保护中配置检查。
- **提交检查不等于完整质量验收**。即使格式和提交说明通过，仍需要功能测试、类型检查、构建检查以及项目中的性能与 SEO 等专项验证。

##### 7. 项目真实状态与面试表达边界

官网仓库目前可以直接验证：

- 已有 [ESLint 配置](https://github.com/cxDlogver/official-network/blob/main/eslint.config.mjs)，包括导入排序与 Vue 文件块顺序。
- 已有 [Prettier 配置](https://github.com/cxDlogver/official-network/blob/main/.prettierrc.json)，包括 Tailwind CSS 类名格式化。
- [package.json](https://github.com/cxDlogver/official-network/blob/main/package.json) 已提供 `lint`、`lint:fix`、`format`、`test`、`build` 等统一入口。

当前仓库**未找到完整的 Husky、lint-staged、commitlint 配置**。因此面试时应该说：**项目已经用 ESLint 和 Prettier 建立了基础代码规则；对于提交规范，可以进一步通过 Conventional Commits、commitlint、Husky 和 lint-staged 将约定升级为提交时自动检查**。不能把这些建议直接讲成当前项目全部已实现的自动门禁。

**可用于口头回答的概括**：

在工程初始化阶段，我先将可以形成确定性规则的内容沉淀下来。ESLint 负责约束代码结构和潜在问题，Prettier 负责统一格式，两者已在官网项目中配置。对于提交规范，我希望通过统一的 Commit 类型让变更历史更加容易理解，并可以进一步通过 commitlint 校验提交信息，借助 Husky 在 Git Hook 中触发检查，再结合 lint-staged 只处理本次暂存文件。这样能够减少多人和 AI 辅助开发引入的无意义代码差异，让人工审查集中于业务逻辑、架构设计和最终交付质量。

#### 【标准回答】

我把规范分为类型与静态规则、格式一致性、提交说明和执行门禁四个方面。TypeScript、ESLint 对类型或规范问题做检查，Prettier 统一格式，commitlint 检查提交信息，Husky 在 Git Hook 时机触发约定命令，lint-staged 可以只对暂存文件运行检查。当前官网有 ESLint、Prettier 及项目脚本依据，但不能声称 Husky、commitlint 和 CI Required Check 都已完整部署。实现上必须区分“工具安装”“命令可运行”和“每次提交或合并时强制执行”三个层次。

### 4.4 【如何用 Design Tokens 保证官网视觉设计的一致性？】

#### 【提问】

主题色、排版、间距、响应式规则和动画规范如何在不同页面复用，并服务后续 AI 辅助开发？

#### 【回答要点】

##### 【Design Tokens 将统一视觉要求变成可复用的工程约束】

官网的主要任务是展示企业信息，页面之间的视觉一致性非常重要。如果每个开发人员或 AI 分别定义颜色、文字等级、间距、卡片圆角和动效参数，页面很容易出现风格漂移，后续统一修改的成本也会变大。

所以我在工程底座中使用 Tailwind CSS v4 和全局主题变量，统一管理品牌色、语义色、排版、空间节奏和部分动效参数，也就是 Design Tokens 的工程化思路。

它的意义不只是集中声明 CSS 变量，而是**把需要长期一致的设计决策沉淀成全站可复用的公共约束**。例如组件尽量依赖主色、弱文字、表面背景等语义角色，而不是随意写入多个接近但不一致的硬编码颜色。

对于一个初期没有完整设计稿、视觉方案需要逐步探索的官网，这样的设计尤为重要：可以先允许 AI 辅助探索视觉与交互，再逐步把确认过的设计方案收敛到公共样式和组件规范中，而不是每开发一个新页面就重新设计整套风格。

#### 【标准回答】

官网希望统一品牌表达，又存在不同产品和内容页面，因此需要用 Design Tokens、主题变量和公共视觉约定，把颜色、排版、间距、断点和基本动效沉淀成可复用约束。页面首先复用已有规范，确有差异再增补。它既能减少视觉不一致，也让团队和 AI 在生成新页面时能够沿用确定的设计边界，而不是每次重新选择样式。

### 4.5 【AI 如何辅助代码实现，并在需求变化中持续遵守规范？】

#### 【提问】

AI 在页面设计探索、方案分析、编码和初步检查中如何使用？如何处理技术底座稳定但局部业务方案仍在变化的情况？

#### 【回答要点】

##### 【AI 是辅助开发工具，项目规范为它提供清晰的上下文与约束】

这一阶段需要明确当时真实的人机协作关系。

在官网 2.0 开发中，AI 主要帮助我进行技术方案比较、页面设计探索、候选代码生成、重复逻辑调整建议和初步检查。架构选型、需求确认、已有代码整合、核心技术判断和最后的质量负责，仍由研发人员完成。

因此，官网的实际模式更接近：

~~~text
人确认业务目标与技术边界
              ↓
AI 辅助比较方案、探索页面与生成候选代码
              ↓
人根据真实项目结构与公共规范进行修改、整合
              ↓
使用项目现有代码检查、必要测试与页面验收验证
              ↓
保留代码提交、必要设计判断和问题记录
~~~

这与“Agent 拿到需求后独立运行到测试、部署和上线”有本质区别。

为了让 AI 在这样的协作过程中更稳定地发挥作用，可以进一步将原本分散在仓库和开发经验中的规则整理成 Agent 可读取的项目级说明，例如 AGENTS.md，约定技术栈、目录职责、公共组件、视觉规则、SEO 约束、可修改范围和检查命令。

但**AGENTS.md 是规则与指导的载体，而不是自动化执行引擎**。只有运行的 AI 工具实际读取并遵守这些规则，才会产生约束效果。独立的开发记录可以保存修改内容、验证结果和遗留问题，但它也不会仅凭文件存在就自动更新。

目前官网仓库未找到根目录 AGENTS.md，也没有证据证明存在由 Agent 自动维护的跨 Session Progress 或 Checkpoint。因而上述说明属于可以继续沉淀的工程设计，而不是这次官网实习已完整落地的端到端 Agent 能力。

##### 【需求与页面设计尚未完全稳定，因此先约束确定的部分，再持续收敛】

这段实践还有一个应当主动说明的事实：官网项目起初并没有完全确定的页面设计稿和长期任务计划，视觉方案和部分内容组织方式都需要随开发持续探索。

所以技术分析不能僵化地理解为“先生成完整 Task 清单，等所有任务冻结之后才能开发”。对于当前项目，更合理的做法是：

- **先确定相对稳定的部分**：Nuxt 技术栈、基础目录、代码格式、数据与展示职责、质量检查入口。
- **允许不确定的部分逐步收敛**：不同页面的视觉方案、局部交互、内容呈现方式随需求和反馈迭代。
- **发现可复用方案后及时沉淀**：从一次页面实现中提炼 Section、Composables、Design Tokens 和公共 SEO 逻辑，避免后续继续复制。
- **用现有规范持续检查增量修改**：无论是人编写还是 AI 辅助生成，都要符合现有代码结构和项目质量要求。

这体现的是一种**稳定底座与渐进式演进结合**的工程设计思路。工程化不是预先规定全部细节，而是在允许业务变化的情况下，让基础能力和代码质量保持一致。

##### 【阶段产物与后续设计开发的衔接】

本阶段的交付重点是稳定的工程基础，而不是一份假设早已确定的长期 Agent 执行计划：

~~~text
需求阶段：业务问题、建设目标、验收方向
                     ↓
技术选型：Nuxt、混合渲染、SEO 生态
                     ↓
工程初始化：目录约定、依赖、配置、统一脚本
                     ↓
架构设计：页面 / 展示组件 / 公共逻辑 / 数据 / 服务端适配
                     ↓
工程规范：类型、Lint、格式、提交约定、Design Tokens
                     ↓
AI 辅助规则：参考已有约束，由研发人员把关
                     ↓
后续开发：随着设计与需求逐步明确，开展页面实现与持续验证
~~~

下一阶段适合继续讨论**页面设计与代码开发**：如何从不完整的设计输入逐步形成页面 Section，如何将 SEO 与数据访问变成可复用能力，AI 具体在哪些编码任务中提效，以及怎样通过实际检查避免生成代码偏离项目架构。

#### 【标准回答】

我先统一 Nuxt 技术栈、目录职责、静态检查和基础视觉规则，这些确定的部分不会因为每次生成页面而改变；尚不明确的视觉和交互则在小批量实现、实际检查与反馈中持续收敛。AI 可以读取现有模块并辅助写代码或检查，但不应自主扩大改动范围或把未经验证的产物视为完成。发现多个页面确实共有的模式，再沉淀公共组件或方法，最终由人整合实现并负责质量。

## 5. 持续测试与质量验证

### 5.1 【如何建立贯穿官网开发过程的持续测试？】

#### 【提问】

**官网重构在需求分析阶段已经确定首屏性能与 SEO 目标，你如何在开发过程中持续测试，并在部署后验证这些目标？为什么需要同时检查页面实际体验与 Lighthouse 指标？开发环境和生产环境的分数为什么可能不同？最终取得了哪些结果，又如何看待 Lighthouse 的局限？**

这道题重点考察：有没有把“需求阶段定义目标”转化为可重复的验证活动；是否理解指标、评分、运行环境与最终业务效果之间的边界。

#### 【回答要点】

> **记录范围**：本节承接前文“需求分析 → 技术设计与工程初始化 → 动态模块开发与记录”，继续梳理官网如何在开发中反复验证、在生产构建与静态资源/CDN 部署后复测，并将结果回收到最初的首屏性能与 SEO 目标，形成项目研发闭环。
>
> **实践核验边界**：项目已有文档记录开发阶段使用 Lighthouse 进行 Performance 与 SEO 实验室审计；本次口述进一步补充“本地通过脚本调用 Lighthouse API”“上线后 FCP 约 0.9 秒、LCP 约 1.2～1.3 秒、SEO 100 分”等经历。当前 GitHub 仓库尚未发现对应的 Lighthouse CLI/CI 依赖配置、完整本地执行脚本或可复现的原始报告，因此应将它们标注为**个人复盘提供的测试方式与结果，待原始脚本和报告复核**，不能据此声称已建立 CI 自动发布门禁。旧版学习记录中另有 FCP 0.8 秒、LCP 0.9 秒的不同数据，不能混成同一次测试。

##### 【测试不是最后补做的一次评分，而是贯穿实现与交付的持续反馈】

在官网工程实践中，需求分析已经明确了重要的质量方向：用户进入页面时能够尽快看到主要内容、页面展示稳定、交互与跳转体验正常、搜索引擎能正确获取重要页面的信息。

因此，测试阶段不是等全部页面完成之后再打开 Lighthouse 检查一次，而是随着首页、产品、新闻、招聘和联系等模块的实现，持续执行必要的功能与性能检查。发现问题后回到实现阶段修复，再对相同页面与条件做回归。

可以把流程梳理为：

~~~text
需求阶段：确认首屏、SEO、功能与交互验收方向
                    ↓
开发阶段：模块实现和局部检查
                    ↓
Lighthouse：量化性能与部分 SEO 基础条件
                    ↓
出现问题：定位资源、渲染、交互、页面配置等原因
                    ↓
修改实现并重复回归
                    ↓
生产构建与部署：静态预渲染、服务器、CDN 等实际配置生效
                    ↓
目标环境复测：指标、交互、路由、资源和抓取条件
                    ↓
对照原目标确认结果，留下测试记录
                    ↓
线上数据继续反馈新问题
~~~

这条链路既体现**验收前置**，也体现测试对开发活动的反馈作用：验收标准来自需求，但验证活动发生在开发全过程，必要时会反向调整实现方案。

##### 【第一层是实际页面检查，不能用单次 Lighthouse 分数代替功能与体验测试】

对于企业官网，页面看起来是否完整、用户能不能完成浏览和跳转、不同屏幕下布局是否正确，是最直接的功能体验要求。开发过程中需要关注：

- **首屏呈现**：打开页面是否长时间空白，主要内容是否有明显延迟。
- **页面跳转**：从首页进入产品、资讯或招聘页面时，是否出现不必要的白屏、闪烁、跳转异常或内容未加载。
- **视觉稳定性**：图片、异步内容或字体到达后是否推动已有布局发生意外偏移；对动效造成的视觉变化应结合实际行为判断。
- **响应式与交互**：桌面与移动端的菜单、卡片、列表、筛选、表单、动画是否符合预期。
- **内容与 SEO 基础**：页面主体内容、标题、描述、Canonical、重要链接是否在实际输出中正确出现。

特别要区分：Lighthouse 对一个 URL 的初始页面加载审计，**不能替代对 Nuxt SPA 内部路由跳转、页面状态、异步数据错误或具体动画流畅度的检查**。例如路由切换出现短暂白屏，首页初始加载的 Lighthouse 高分不一定能发现。

AI 在当前项目中可以辅助执行约定的检查、整理结果和提出定位建议，但人需要核对真实页面与测试证据，决定是否接受修复结果。它不是独立控制完整测试、发布和回滚的 Agent。

#### 【标准回答】

测试不是最后跑一次评分。开发每个页面区块时，要结合真实页面检查首屏是否空白、路由跳转是否稳定、图片是否引起布局位移、菜单和按钮操作是否正确、桌面与移动端交互是否可用，同时检查关键页面输出的 HTML 与 SEO 信息。发现问题后回到代码及时调整，并保存截图、测试步骤、代码版本和结果证据，让验证成为持续反馈。

### 5.2 【如何使用 Lighthouse 建立性能和 SEO 的技术验收？】

#### 【提问】

如何固定测试条件、对比指标及执行脚本？为什么一次分数不能证明所有真实性能和搜索效果？

#### 【回答要点】

##### 【第二层通过 Lighthouse 形成可以比较的性能与 SEO 实验室指标】

为了避免性能验收只靠“感觉网页很快”，项目开发阶段使用 Lighthouse 统一进行实验室审计，关注 Performance 和 SEO 等类别。根据本次实践口述，还曾在本地编写脚本调用 Lighthouse API 对页面进行测试；由于脚本未在当前仓库检索到，记录为个人实践描述，后续如能找到原始文件，再补充调用参数、运行命令与报告路径。

Lighthouse 报告需要区别**指标数值**和**综合评分**：

| 指标/评分 | 实际衡量的问题 | 单位与边界 |
| --- | --- | --- |
| FCP（First Contentful Paint） | 浏览器首次绘制正文、图像等实际内容是什么时间 | 时间，秒；不是 0～100 的“FCP 分数” |
| LCP（Largest Contentful Paint） | 当前视口中最大内容元素完成渲染是什么时间 | 时间，秒；反映关键内容出现速度 |
| CLS（Cumulative Layout Shift） | 页面在加载与使用期间出现多少意外布局位移 | 无单位；数值越低通常越好 |
| TBT（Total Blocking Time） | Lighthouse 实验室加载区间内的主线程阻塞程度 | 时间，毫秒；不是 INP 的直接替代品 |
| Lighthouse Performance | 以多项性能指标的结果按当前 Lighthouse 评分模型计算 | 0～100 分；不能只看总分判断具体瓶颈 |
| Lighthouse SEO | 自动检查当前版本所覆盖的部分 SEO 基础技术要求 | 0～100 分；不能直接反映收录率或搜索排名 |

例如，FCP 0.9 秒意味着首次内容绘制出现在大约 0.9 秒时，而不是“FCP 得到 0.9 分”；LCP 1.2 秒意味着最大内容在这一测试条件下完成绘制的时间约 1.2 秒。

Lighthouse 对页面进行一次实验室访问并生成指标和审计结果，能够支持定位和回归。其性能评分依据当前 Lighthouse 版本的指标权重与评分模型计算；不同 Lighthouse 版本、设备模式、网络条件下的分数不能无条件直接比较。

另外，SEO 100 分只代表**该页面通过当次 Lighthouse 版本所覆盖的相关检查**。它不能保证 Google 已经收录页面、一定使用站点声明的 Canonical、搜索结果已替换旧版链接，也不能证明官网流量与实际转化提高。

##### 【本地脚本让检测更容易复用，但自动运行不等于自动验收或 CI 门禁】

口述中的“通过本地脚本直接调用 Lighthouse API”，可以体现将重复检查封装为固定操作的工程思想。要使测试真正可比较，脚本除触发 Lighthouse 以外，还应尽量保存或明确：

- 测试页面 URL、代码版本、测试时间和页面类型。
- Lighthouse/Chrome 版本、设备模式、网络和 CPU 模拟条件。
- Performance、SEO 分数，以及 FCP、LCP、CLS、TBT 与失败诊断项。
- 测试结果和对应问题记录，便于修复后在相同条件下复测。

需要分清三个层次：

~~~text
本地手动打开 Lighthouse
→ 能获取单次审计结果

编写本地脚本调用 Lighthouse
→ 可复用运行参数、批量检查或保存报告

接入 CI 并设置 Required Checks
→ 才可能形成自动执行且阻断不达标代码合并/发布的门禁
~~~

本项目可确认有 Lighthouse 作为实验室测试依据；根据本人经历补充本地脚本方式，但当前源码缺少原始脚本与 Lighthouse CI 完整配置的证据，**不应越过证据边界宣称已经把它集成成每次提交自动运行的强制 CI 门禁**。

本地脚本属于工具调用层面的自动化；它同样不代表 AI Agent 可以独立决定什么页面满足业务需求，AI 在这里仍主要是辅助编码、运行已有检查与总结发现的问题。

#### 【标准回答】

我会选取首页、产品和动态内容等代表页面，在可比较的环境中反复运行 Lighthouse，分别分析 FCP、LCP、CLS、TBT 等性能指标及 SEO 技术审计，并保留报告及源码版本。Lighthouse 的结果是实验室技术信号，不等于真实用户 INP 分布、搜索收录或业务转化。项目已具备一些本地测试入口，但不能仅凭脚本存在就说已经建立强制阻断的 CI 门禁。

## 6. 部署上线与线上复测

### 6.1 【为什么生产部署后仍然必须重新检查官网？】

#### 【提问】

正式构建、Prerender、静态资源/CDN、缓存策略与本地开发有什么区别？怎样保证测试结果可比？

#### 【回答要点】

##### 【第三层是部署后复测：开发环境分数不等于正式交付效果】

我认为本次官网项目性能验收中很有价值的认识，是主动区分**开发时的实验室结果**与**生产部署后的结果**。

页面性能受设备、网络、缓存、页面资源、浏览器版本、服务器距离、第三方脚本等因素影响。开发环境通常还有热更新、调试和未优化的开发构建资源；生产环境则会经过正式构建，并应用实际服务器与资源分发策略。两者产生差异是正常的，但不能先验地判断生产环境一定比开发环境快。

官网在交付时还有两个具体影响页面加载的技术条件：

**第一，稳定页面静态预渲染。** 通过 Nuxt Route Rules，让首页、产品、解决方案、招聘等内容相对稳定的页面在构建阶段生成 HTML。这样访问时可以直接交付预先生成的内容，减少重复页面生成；但仍需要确保部署的 HTML、页面资源及更新机制正确。

**第二，静态资源通过 CDN 分发。** 将图片等资源上传或映射到 CDN，再通过合理的缓存策略减少重复从源站获取的开销。CDN 在合适的网络与缓存条件下可能改善资源下载和首屏体验，但 CDN 命中、缓存预热、资源体积、LCP 图片发现与加载优先级仍会影响实际效果，不应声称只要用了 CDN，FCP/LCP 必然下降。

因此，更合理的验收顺序是：

~~~text
开发阶段：局部功能检查与 Lighthouse 回归
                  ↓
生产构建：确认输出与路由预渲染结果
                  ↓
部署：服务器、缓存、CDN、环境配置生效
                  ↓
目标环境复测：重新获取 Performance、SEO 和关键行为结果
                  ↓
分析环境差异，确认是否满足原定目标
~~~

生产部署以后也应注意测试缓存状态和条件：冷缓存访问与已命中 CDN 缓存的访问并不完全相同，不能把不同条件下的分数直接当作同一组可比样本。

##### 【最终指标应记录测试场景和证据来源，避免把不同批次结果混成一个成果】

根据本次讨论的个人复盘口述，官网上线部署、静态资源与 CDN 配置完成后，有过以下测试结果：

| 项目 | 本次口述的结果 | 应怎样表述 |
| --- | --- | --- |
| FCP | 约 **0.9 秒** | 在相应 Lighthouse 测试条件下，首次内容较快显示 |
| LCP | 约 **1.2～1.3 秒** | 在相应测试条件下，最大内容完成渲染较快 |
| Lighthouse SEO | **100 分** | 当次被测试的公开页面通过 Lighthouse 覆盖的基础 SEO 检查 |

**证据状态**：上述数值来自项目参与者本次复盘口述，当前未找到与之完整对应的原始 Lighthouse 报告，因此不能写成“已经从仓库报告独立复核”的事实。原有 [官网开发笔记](https://github.com/cxDlogver/official-network/blob/main/docs/history/官网开发.md) 的另一组记录是 FCP 0.8 秒、LCP 0.9 秒、TBT 0 毫秒、CLS 0.002、Speed Index 0.8 秒；它可能来自其他时间、环境、设备或页面，不能与本次 0.9/1.2～1.3 秒的结果混写为一次测试。

如果后续补齐原始报告，最好同时记录测试 URL、移动端或桌面端模式、Lighthouse 版本、时间与运行环境。这样可以使用可复核的证据在面试中给出具体数字，而不是只说“分数一直很高”。

关于质量结果，还需要保留两个边界：

1. **Lighthouse 的实验室指标不等于真实用户数据**：真实设备、网络和交互路径存在分布差异；线上 Web Vitals 和用户行为分析更适合观察实际体验。
2. **SEO 技术评分不等于搜索业务结果**：抓取、索引、展示、排名以及新旧网站搜索结果衔接，还需要线上页面状态、抓取日志、Search Console 等证据。

因此，项目可以说明“在所测条件下取得了较好的首屏和 SEO 基础审计结果”，但不能将实验室高分直接推导成搜索自然流量增长或所有真实用户性能达标。

#### 【标准回答】

开发环境与生产环境的 HTML 生成、构建产物、CDN、资源缓存、域名和真实网络条件并不相同。即使本地页面体验良好，也要在正式部署后核对真实响应 HTML、资源请求、缓存头、可索引性和页面交互，再按相同环境与测试场景复测关键指标。特别是 Prerender 与 CDN 可以改变内容交付路径，但不会自动保证所有图片请求和页面体验都已优化。结果需要注明版本、场景、环境和报告，避免不同测试条件的分数直接比较。

### 6.2 【如何将上线验收结果回收到最初的项目目标？】

#### 【提问】

如何将需求验收标准、实现版本、Lighthouse 结果与线上测试证据关联？如何准确表述 90+ 的结果？

#### 【回答要点】

##### 【测试与验收需要回收阶段产物，保证结论能够对应具体代码版本】

前一个阶段已经讨论通过任务清单关联页面路由、代码文件与截图；当前测试阶段则应将这些记录进一步关联**测试条件、指标、失败项、修复版本和复测结论**。

例如开发产品详情页时，最基本的复核记录可以形成：

~~~text
功能任务：产品详情展示
       │
       ├─ 页面路由 /product/[slug]
       ├─ 实现代码与 Git 版本
       ├─ 功能与移动端页面检查
       ├─ Lighthouse 性能和 SEO 审计
       ├─ 测试条件：设备 / 网络 / 构建环境
       ├─ 发现的问题与代码修复
       └─ 复测结论与遗留问题
                  ↓
       状态：待验收 / 已验收 / 需返工
~~~

这里应把“截图证明页面出现过”“Lighthouse 产生过分数”“任务实际通过验收”严格区分。只有当相关功能和质量要求都得到必要验证时，才能作出完整的验收判断。对于后续代码变更，原有测试结果可能不再有效，应按影响范围重新执行回归。

这种设计把**阶段产物追溯**和**验收前置**连接起来，使开发过程不仅能追踪“改了哪些代码”，还能追踪“为什么确认这些修改满足最初需求”。

##### 【阶段总结：从最初的业务目标到部署后的验证结果形成闭环】

完整过程可以归纳为：

~~~text
需求分析
→ 明确官网信息展示、首屏与 SEO 的业务和技术目标
           ↓
技术设计与工程初始化
→ Nuxt 混合渲染、组件分层、代码与设计规范
           ↓
开发执行
→ 模块化实现、AI 辅助开发、动态任务及产物记录
           ↓
持续验证
→ 页面体验检查 + Lighthouse 实验室指标 + 发现问题再修复
           ↓
部署和复测
→ 生产构建、静态预渲染、服务器与 CDN 配置生效后再检查
           ↓
目标验收
→ 将功能、性能、SEO 基础审计结果与最初要求对应
           ↓
后续反馈
→ 真实用户监控、搜索数据与版本回归支持持续优化
~~~

这体现的是**面向目标的研发闭环**：最初的技术目标决定设计重点，最终测试结论回到同一套目标检查是否达到预期；无法由 Lighthouse 证明的真实用户体验和搜索业务结果，则通过上线后的持续观察进一步验证。

#### 【标准回答】

第四阶段是持续测试与最终验收。

我认为这一阶段最重要的是，根据需求分析时确定的质量目标，持续验证开发结果，而不是等所有页面完成之后才一次性测试。

在官网项目中，我们最早就确定了首屏性能和 SEO 两个重要技术目标，因此我在开发过程中主要围绕这两方面建立统一的评价标准。

首先是**开发过程中的持续检查**。每完成一部分页面和功能，我会结合实际访问检查首屏内容、路由切换、响应式布局和交互表现，比如是否出现页面白屏、明显抖动，或者动画、跳转不流畅等问题。

同时，我们使用 Lighthouse 对关键页面进行实验室审计。我在本地通过脚本调用 Lighthouse 进行测试，重点关注 FCP、LCP、CLS 等指标及 Performance、SEO 的审计结果，把“页面快不快、稳定不稳定”转换成可以比较的指标。发现问题后，再结合页面加载过程和资源请求定位原因、修改代码并重新测试。AI 在这里主要辅助执行检查、分析问题和修改部分代码，最后仍由我确认结果。

其次，我会**区分开发阶段和实际部署环境的测试结果**。因为 Lighthouse 的结果与设备、网络、缓存、资源加载方式等条件有关，开发环境中的分数不一定代表线上真实效果。特别是我们的官网会在生产构建时对一些稳定页面进行预渲染，并通过 CDN 分发图片等静态资源，所以需要等应用部署到服务器、生产构建和资源配置真正生效之后，再对实际部署页面进行复测。

根据当时的测试记录回忆，官网的 FCP 约为 0.9 秒，LCP 约为 1.2 到 1.3 秒，Lighthouse SEO 基础审计达到 100 分。这里 FCP、LCP 是时间指标，SEO 100 是审计得分；这些数字都应该结合对应的测试页面、设备模式和报告判断。我不会把 SEO 100 分直接解释为搜索引擎收录和排名达到 100 分，也不会认为单次实验室性能结果能代表所有真实用户。

**最后，这一阶段真正要完成的是回到原始目标进行验收。** 我们在需求阶段提出首屏和 SEO 的目标，在技术分析时据此选择 Nuxt 与合适的渲染策略，在开发过程中持续回归优化，部署后又在实际资源和缓存条件下重新验证。

所以我认为这套方法最有价值的地方，不是最终取得了一个较高的 Lighthouse 分数，而是**把目标定义、技术选型、代码开发、持续测试和交付验收串成了一条有依据、可反馈的研发链路**，这也是我希望从官网项目沉淀到后续软件开发中的工程规范。

# 第二项工作重点：SEO 与 Web 性能工程化

## 7. SEO 工程化体系与具体实现

### 7.1 【官网 SEO 工程化体系如何从目标到运行链路构建？】

#### 【提问】

SEO 工程化如何围绕搜索引擎的发现、抓取、索引和理解页面建立分层设计？Lighthouse 在其中承担什么职责？

#### 【回答要点】

> **定位**：本专题属于官网第二项工作重点，说明如何在需求阶段确定 SEO 技术验收目标，再依据搜索引擎发现、抓取、索引和理解页面的过程建立工程体系，最后落地为 Nuxt 4 的站点级配置、页面级 SEO 公共方法、Sitemap 数据源和 JSON-LD 结构化表达。
>
> **事实边界**：以下已实现部分依据 [Nuxt 配置](https://github.com/cxDlogver/official-network/blob/main/nuxt.config.ts)、[SEO 公共方法](https://github.com/cxDlogver/official-network/blob/main/app/composables/useSIteSeo.ts)、[JSON-LD 生成器](https://github.com/cxDlogver/official-network/blob/main/app/composables/useSeoStructuredData.ts)、[动态 Sitemap](https://github.com/cxDlogver/official-network/blob/main/server/api/__sitemap__/urls.ts) 核对。针对索引规则、链接结构和数据完整性的补充建议，不应倒写成已全部完成的优化成果。

##### 1. 先从业务目标建立量化验收方向，不能将 Lighthouse 当成全部 SEO 标准

企业官网建设 SEO 的业务意义，是让搜索用户有机会找到企业、产品、资讯和招聘等真实内容。工程侧需要将其转换为**重要 URL 可发现、页面可访问、内容可索引、语义可理解**等基础目标，再选择技术方案和验证方法，而不是先安装 Nuxt SEO 模块后寻找理由。

~~~text
业务目标：用户能够通过搜索了解企业与产品
                   ↓
SEO 工程目标：URL 发现、抓取、索引、内容理解
                   ↓
技术方案：Nuxt 混合渲染 + URL/抓取规则 + Meta + JSON-LD
                   ↓
技术验收：Lighthouse 基础审计 + HTML/HTTP/URL 检查
                   ↓
线上反馈：Search Console 抓取、索引、曝光、点击等数据
~~~

Lighthouse 的 SEO Category 主要通过可自动检查的部分技术项目计算分数，**不等于 Google 排名评分**。在仓库通用 [SEO 工程知识文档](https://github.com/cxDlogver/cx-learn-notes/blob/main/Full-Stack-AI-NOTES/S-SEO工程体系.md) 已核对的 **Lighthouse v13.5.0** 运行配置下，全部计分项适用时约为：

| SEO Audit | 检查含义 | 约占分数 |
| --- | --- | ---: |
| `is-crawlable` | 页面没有被索引指令禁止索引 | **31%** |
| `document-title`、`meta-description` | Title、Description 的基础有效性 | 各 7.67% |
| `http-status-code` | 主文档状态码是否符合要求 | 7.67% |
| `link-text`、`crawlable-anchors` | 链接文案、链接能否被爬虫发现 | 各 7.67% |
| `robots-txt` | Robots 规则文件的基础有效性 | 7.67% |
| `image-alt` | 图片 Alt 的基础要求 | 7.67% |
| `hreflang`、`canonical` | 语言关系、规范 URL 的有效性 | 各 7.67% |
| `structured-data` | 结构化数据另需专项验证 | 不计分 |

**口径边界**：权重来自 [Lighthouse v13.5.0 的实际运行配置](https://github.com/GoogleChrome/lighthouse/blob/v13.5.0/core/config/default-config.js)；不适用项会影响最后归一化计算，版本更新也可能改变评分。不能说每个 Audit 永远固定扣 8 分。`SEO=100` 仅说明所测页面通过当时适用的 Lighthouse 基础审计，不能证明全站已被收录、Canonical 已被 Google 采用、JSON-LD 一定获得富结果或搜索排名优秀。主动 `noindex` 的页面不应被机械要求 SEO 100。

##### 2. 搜索引擎生命周期决定 SEO 的三层工程建设重点

理解 SEO 首先要区分几个不同环节：

~~~text
Discovery：发现 URL
→ 通过 Sitemap、站内/外部链接等知道页面存在
                   ↓
Crawling：抓取 URL
→ 根据 Robots、服务响应等决定是否能够获取内容
                   ↓
Rendering / Indexing：渲染与索引
→ 获取主体信息、读取 noindex、评估规范 URL
                   ↓
Understanding：理解内容
→ 解析 Title、正文、链接语义和实体数据
                   ↓
Search Appearance：搜索展示
→ 根据相关性、内容质量、体验等选择呈现结果
                   ↓
Feedback：反馈
→ 验证实际抓取、收录、展示和点击表现
~~~

在官网实现时，可以按照建设重点简化为三层，但不能认为它们完全独立：

| 层次 | 解决的问题 | 核心能力 |
| --- | --- | --- |
| **第一层：发现、抓取、索引基础** | 页面是否容易找到、能请求、具备索引资格 | Sitemap、标准链接、HTTP Status、Robots、noindex、Canonical、SSR/Prerender/SWR |
| **第二层：页面内容与语义准确性** | 当前 URL 讲什么，不同业务页面是否有独立主题 | Title、Description、Heading、正文内容、图片 Alt、链接文字、Open Graph |
| **第三层：业务实体结构化表达** | 页面描述哪些真实业务对象、属性和关系 | JSON-LD、Organization、Product、NewsArticle、JobPosting、BreadcrumbList |

渲染性能、页面内容质量、移动端体验及验收回归是**贯穿三个层次的横向约束**，而不是只归属某一层。

#### 【标准回答】

官网重构的第二项工作重点是以首屏性能和 SEO 为目标，建设可复用的性能与搜索优化体系。我认为这里最重要的是先明确目标和验收方式，再以目标反推具体工程设计。

对于 SEO，我们在开发阶段使用 Lighthouse 检查部分基础技术条件，包括 Title、Description、页面可索引性、规范链接和可抓取链接等。但它并不能代表 Google 的实际索引或排名，所以不能把 SEO 工程简单理解为逐项补齐 Lighthouse Audit。

我首先从搜索引擎处理页面的过程入手，将 SEO 的建设重点划分为三个层次。

**第一层是页面发现、抓取和索引基础。** 通过 Sitemap 和标准站内链接帮助搜索引擎发现企业的产品、资讯和招聘页面；根据页面内容更新特点选择 Nuxt 预渲染或 SWR；并通过 HTTP 状态、Robots、noindex 和 Canonical 明确哪些页面能够访问、是否应该被索引，以及重复 URL 应如何规范化。这里要区分 Robots 的抓取控制和 noindex 的索引控制，不能因为同时配置两者就认为更安全。

**第二层是内容和语义准确性。** 不同业务页面应当根据真实数据生成独立的 Title、Description 和其他 Meta 信息，同时让页面正文标题、图片和链接语义保持一致。我不希望每个页面分别维护一套 SEO 规则，因此将首页、产品、资讯和招聘的元信息抽象为统一的配置生成方法。

**第三层是业务实体的结构化表达。** 在真实业务内容基础上，通过 JSON-LD 表达 Organization、Product、NewsArticle、JobPosting 等实体信息和属性关系，使搜索系统能够更明确地识别页面描述的对象。

在 Nuxt 的具体实现上，我把站点级和页面级职责分开。站点级通过 `nuxt.config.ts` 配置 SEO 模块、Robots、Sitemap 和不同路由的渲染策略；Sitemap 通过服务端接口从产品、岗位、新闻数据动态生成 URL。页面级则通过 `seoConfig` 根据业务数据生成 SEO Meta，通过 JSON-LD Builder 生成结构化对象，再统一交给 `usePageSeo()`，由其调用 `useSeoMeta()` 和 `useHead()` 注入 Title、Description、OG、Canonical、页面级 robots 和 JSON-LD。

这样，新增一个产品或新闻页面时，页面只需要提供对应的真实业务信息和规范路径，就能复用公共 SEO 能力，避免各自维护重复逻辑。

最后，在测试阶段使用 Lighthouse 验证基础 SEO 配置，在部署后再核对真实 HTML、HTTP 状态、Sitemap 和索引表现。**这项工作的价值不仅是提高单次 SEO 评分，更在于把 SEO 从分散的页面配置转化为依据业务目标设计、统一表达、可复用并且可持续验证的工程体系。**

### 7.2 【Sitemap、Robots、HTTP 状态与站内链接怎样配合？】

#### 【提问】

怎样让重要页面可发现、可请求、可抓取并符合索引条件？Robots、noindex、HTTP 状态和链接语义分别控制什么？

#### 【回答要点】

##### 3. 第一层需要分别处理 URL 发现、抓取控制、HTTP 状态和索引控制

**URL 发现**主要通过页面内的标准链接与 Sitemap 实现。例如 Nuxt 页面可用 `<NuxtLink to="/news/123">`，最终输出带 `href` 的 `<a>`，既表达站内页面关系，也保留 SPA 导航体验。纯粹的 `@click="navigateTo(...)"` 只描述点击行为，不能等同于当前页面输出了一个标准可抓取链接。Sitemap 能补充 URL 发现，但搜索爬虫不保证完整遍历首页能到达的所有页面，也不保证抓取 Sitemap 中的全部 URL。

**Robots** 主要管理爬虫是否允许抓取 URL。官网 `nuxt.config.ts` 当前配置：

~~~ts
robots: {
  disallow: ['/develop'],
}
~~~

这个规则主要对应 Robots 文件中的 `Disallow: /develop`。没有需要限制抓取的公开页面时，无须为了 SEO 故意添加复杂禁止规则。Robots 不能代替实际访问权限和身份认证。

**HTTP 状态** 帮助搜索引擎判断 URL 当前是不是有效资源：

| 状态码 | 含义 | SEO 工程注意 |
| --- | --- | --- |
| 200 | 当前页面请求成功 | 主体内容应真实有效；200 不保证被收录 |
| 301 / 308 | 长期迁移 | 旧 URL 应明确映射到对应的新 URL |
| 302 / 307 | 临时重定向 | 不应误用为永久迁移 |
| 404 / 410 | 页面不存在或已删除 | 无效动态详情应真实返回不存在状态 |
| 5xx | 服务端异常 | 长期错误会影响抓取和页面索引 |

例如产品详情不存在却只在 Vue 中显示“产品不存在”、服务端仍返回 HTTP 200，可能形成 Soft 404。必须同时验证页面输出和响应状态。

**noindex** 作用于索引阶段，例如：

~~~html
<meta name="robots" content="noindex">
~~~

它要求支持该指令的搜索引擎不要索引此页面，但前提是爬虫能获取这个指令。因此当前官网 `/develop` 存在值得复核的配置：

~~~text
robots.txt：Disallow /develop
                  ↓
Googlebot 可能不访问该页面
                  ↓
页面中的 meta robots=noindex 可能无法读取
~~~

项目实际在 `app/pages/develop/index.vue` 中通过 `usePageSeo(..., { noindex: true, nofollow: true })` 生成页面索引指令。对于“公开可访问但不进入索引”的页面，更合理的方向是**允许抓取并提供 noindex**；对于敏感页面，则应使用服务端授权，不能靠 Robots 或 noindex 保密。

**Canonical** 用来声明相同或高度相似内容中网站偏好的**规范 URL**，不是“给每个页面模块配置主链接”。例如新闻筛选页：

~~~text
/news
/news?category=AI
/news?year=2026
             ↓
如果属于不需要单独索引的相似表示
Canonical 指向 /news
~~~

不同产品 `/product/a` 和 `/product/b` 则通常各自具有独立规范 URL。Canonical 是搜索引擎参考的强信号，不是强制命令。站内链接、Sitemap、重定向与 Canonical 最好都使用一致的主 URL。

#### 【标准回答】

首先要让重要页面 URL 具备搜索系统能够发现的入口。Sitemap、标准 href 链接负责提供地址，HTTP 状态描述服务器实际返回情况，robots.txt 约束抓取行为，而 noindex 是索引控制信号。它们并不互相替代。Nuxt 的客户端 navigateTo 可以让用户跳转，但不能在所有情况下代替搜索系统可以静态发现的标准链接。

### 7.3 【Canonical 如何处理重复 URL，与 Robots 和 noindex 有何不同？】

#### 【提问】

多个 URL 对应重复或相似内容时应该怎样选择主要版本？为什么不能用 Robots 或 noindex 简单取代 Canonical？

#### 【回答要点】

##### URL 规范化与抓取、索引是三个不同判断

Canonical 通过 link[rel=canonical] 等信号向搜索系统表明一组重复或高度相似 URL 的首选版本，它不是强制禁止访问，也不是 robots.txt 式的抓取控制。robots.txt 决定某些抓取路径是否允许，noindex 则要求搜索系统不将指定页面编入索引；如果抓取先被 robots 阻止，搜索系统可能看不到页面上的 noindex 或 Canonical。官网应结合服务端响应、URL 参数、站内链接、重定向与 Sitemap 核对规范地址是否一致。

原草稿关于 Canonical、robots 与 noindex 的详细冲突分析已完整迁移至上一题“第一层需要分别处理 URL 发现、抓取控制、HTTP 状态和索引控制”，本题聚焦这些机制的职责比较，避免整段重复维护。

#### 【标准回答】

我先区分“可否抓取”“是否允许索引”和“多个地址优先哪个版本”。Robots 主要是抓取规则，noindex 用于索引控制，Canonical 则是告诉搜索系统重复内容的首选 URL；后者是规范化信号，不能替代访问或索引规则。实际配置还需保证页面中的 Canonical 与重定向、Sitemap、站内链接保持一致，避免一边禁止抓取，一边期望爬虫能够读取页面上的规范化指令。

### 7.4 【SSR、Prerender 和 SWR 怎样影响搜索系统获取页面内容？】

#### 【提问】

官网为什么需要根据内容更新特点选择渲染方式？直接请求得到的 HTML 与客户端最终 DOM 在 SEO 上有什么差异？

#### 【回答要点】

##### 页面生成与搜索抓取的关系

CSR 可能使首次 HTML 缺少主要业务正文，搜索系统需要额外执行 JavaScript 才能观察到这部分内容；SSR 在请求时生成 HTML，Prerender 在构建阶段生成稳定页面，SWR 依赖缓存与重新生成策略复用页面结果。官网首页、产品页等采用 Prerender，新闻使用 SWR；真实配置与运作链路在性能题 8.4 中完整保留。渲染策略能够提升主要内容在 HTTP 响应中直接可见的机会，但并不自动解决站内链接、Canonical、结构化数据或者 SEO 内容准确性。

答辩核验时应直接请求代表性页面，检查服务端输出的 HTML、SEO Meta、HTTP Status 与可访问正文，而不只检查客户端页面最终变更后的 DOM。深入源码：[Nuxt 混合渲染项目分析](https://github.com/cxDlogver/official-network/blob/main/docs/页面渲染策略与Hybrid%20Rendering源码分析.md)。

#### 【标准回答】

我会按页面内容的更新频率和可读取要求选择渲染方式。首页与产品等稳定内容适合在构建时生成 HTML，新闻类页面可使用 SWR 复用缓存并按策略更新。这样不仅可以减少部分页面生成成本，也让搜索系统在直接请求 HTML 时更有机会获得主体内容。但它不意味着搜索引擎一定会收录，所以仍要核验状态、Meta、链接、正文和实际搜索反馈。

### 7.5 【如何在 Nuxt 中统一生成页面 Title、Description 和 SEO Meta？】

#### 【提问】

如何根据真实业务数据生成站点级与页面级元信息，处理 OG、Canonical 及其公共逻辑？

#### 【回答要点】

##### 4. 第二层要求页面语义从真实业务数据生成，并和正文一致

首页、产品、资讯、招聘分别承担不同信息表达任务，不能共用一份固定 Title 和 Description。项目将页面业务数据映射为 `SeoMeta`，并由公共方法统一注入。

| 字段或语义能力 | 主要作用 | 重要边界 |
| --- | --- | --- |
| Title | 说明页面主题，并可能用于搜索标题 | 应准确、独立，与正文一致 |
| Description | 描述页面内容，可作为搜索摘要候选 | 搜索引擎可能自行生成摘要 |
| Keywords | 历史 TDK 中的 K | Google 搜索不使用 Meta Keywords 进行排名 |
| Heading / 正文 | 实际表达页面内容和层次 | H1/H2 与 Title 应在主题上相互支持 |
| Image Alt | 表达图片内容，兼顾可访问性 | 不能堆砌无关关键词 |
| 链接文本 | 表达页面之间的语义关系 | 使用标准链接更明确 |
| OG / Twitter Card | 社交分享预览信息 | 与 Google 自然搜索排名不是同一个评价维度 |

官网 `seoConfig.product()` 从产品名称、卖点、描述和图片生成 Title、Description、OG 等元信息；`seoConfig.newsDetail()` 从文章标题、摘要、日期、栏目生成新闻配置；`seoConfig.jobDetail()` 从职位描述生成对应字段。这样避免每个页面重复维护 SEO 模板，并尽量保证 SEO 内容与具体业务对象关联。

##### 6. Nuxt 工程实现分为站点级和页面级，公共方法不负责全部 SEO

官网采用 **Nuxt 4 + `@nuxtjs/seo` + 自定义 SEO Composables**。关键职责分布如下：

| 工程位置 | 核心职责 | 实际实现 |
| --- | --- | --- |
| `nuxt.config.ts` | 全站域名、SEO 模块、Robots、Sitemap、渲染策略 | `site`、`robots`、`sitemap.sources`、`routeRules` |
| `server/api/__sitemap__/urls.ts` | 动态补充产品、招聘、新闻详情 URL | `ProductId`、Nuxt Content Jobs、WordPress API |
| `app/composables/useSIteSeo.ts` | 全站默认值和页面元信息规范化 | `useSiteSeo()`、`seoConfig`、`usePageSeo()` |
| `app/composables/useSeoStructuredData.ts` | JSON-LD 业务实体构建与序列化 | `createXxxJsonLd()`、`useJsonLd()` |
| `app/types/seoType.ts` | 定义统一的数据输入结构 | `SeoMeta`、`PageSeoConfig`、`StructuredDataNode` |

**站点级配置**包括：

~~~ts
export default defineNuxtConfig({
  modules: ['@nuxtjs/seo'],
  site: {
    url: 'https://www.lawgenesis.cn',
    name: '缔零科技',
  },
  robots: {
    disallow: ['/develop'],
  },
  sitemap: {
    sources: ['/api/__sitemap__/urls'],
  },
})
~~~

这是提炼主要 SEO 配置的示例，不是完整的 `nuxt.config.ts`。在非开发环境中，实际的 `routeRules` 还将首页、产品和招聘等稳定页面设置 Prerender，新闻列表和详情设置 `swr: 86400`，使重要内容以适合其更新频率的方式交付。

**动态 Sitemap** 的 URL 源通过 `defineSitemapEventHandler` 返回业务 URL。源码主要从三类业务数据建立：

~~~text
ProductId → /product/{id}
Nuxt Content Jobs → /jobs/{slug} + updatedAt
WordPress Posts → /news/{id} + date
             ↓
/api/__sitemap__/urls
             ↓
Nuxt Sitemap 模块生成最终站点地图
~~~

其中 Google 忽略 Sitemap 的 `priority` 和 `changefreq`；应重点关注 URL 完整性和准确 `lastmod`。目前 WordPress 仅拉取最多 100 篇新闻、使用发布时间 `date` 作为 `lastmod`，API 失败时会跳过新闻 URL，属于需要注意的实际边界。

**页面级公共方法**进一步拆成：

- `useSiteSeo()`：获取站点域名、默认描述、OG 图片、语言、Title 模板，并生成基础 Organization、WebSite 结构化信息。
- `seoConfig.home() / product() / newsDetail() / jobDetail()`：根据不同页面业务数据生成 `SeoMeta`。
- `createXxxJsonLd()`：把产品、新闻、岗位等业务对象转成 Schema.org 结构化数据。
- `usePageSeo(config, pageConfig)`：组合上述结果，使用 Nuxt `useSeoMeta()` 与 `useHead()` 统一注入 Title、Description、OG、Canonical、页面 robots meta、JSON-LD。

因此，**`usePageSeo()` 统一的是当前页面的 SEO 表达，不负责生成 `robots.txt` 或聚合 Sitemap URL**；站点级配置和页面级配置共同组成 SEO 工程体系。

#### 【标准回答】

我会把站点公共配置和页面真实业务信息分开处理。站点层负责默认信息、SEO 模块及全局规则；首页、新闻、产品和招聘页面按各自数据生成独立 Title、Description、Canonical 与 OG 等字段。再借助 seoConfig、usePageSeo 等公共方法统一输出，而不是让每个页面重复拼写 Meta。最终需要确认服务端 HTML 与页面正文一致，不能仅在客户端看到 Meta 更新就认为 SEO 已符合要求。

### 7.6 【如何用 JSON-LD 描述官网业务实体并抽象公共生成器？】

#### 【提问】

Organization、Product、NewsArticle 和 JobPosting 如何从真实数据构造？Builder 与 useHead 分别负责什么？

#### 【回答要点】

##### 5. 第三层将真实业务对象转换为 Schema.org 的 JSON-LD 表达

第二层说明“这页主要讲什么”，第三层进一步说明“具体讲的是哪个实体、有什么属性、与其他实体存在什么关系”。

~~~json
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "示例产品",
  "description": "页面真实存在的产品介绍",
  "brand": {
    "@type": "Brand",
    "name": "示例企业"
  }
}
~~~

这不是通过 JSON-LD 凭空补充业务信息。数据必须来自真实的页面内容。官网 [useSeoStructuredData.ts](https://github.com/cxDlogver/official-network/blob/main/app/composables/useSeoStructuredData.ts) 已有 `createOrganizationJsonLd`、`createWebsiteJsonLd`、`createProductJsonLd`、`createArticleJsonLd`、`createJobPostingJsonLd` 和 `createBreadcrumbJsonLd` 等函数。

`useJsonLd()` 负责把结构化对象序列化为最终 Script：

~~~ts
useHead({
  script: nodes.map((node, index) => ({
    key: createJsonLdKey(node, index),
    type: 'application/ld+json',
    textContent: JSON.stringify(node),
  })),
})
~~~

最终形成 HTML 中的 `<script type="application/ld+json">`。JSON-LD 不替代真实 HTML 正文，也不保证 Google 一定展示富结果；重要结构化类型需要额外用 Rich Results Test 和实际内容核验。

##### 7. 产品详情页体现“业务数据 → 规范化 SEO 表达”的完整链路

[产品详情页源码](https://github.com/cxDlogver/official-network/blob/main/app/pages/product/%5Bslug%5D.vue) 会根据当前产品对象生成 SEO 元信息，并传入 JSON-LD。调用关系可简化为：

~~~ts
const description = product.positioning.summary

usePageSeo(
  seoConfig.product(
    product.name,
    product.sellingPoints,
    description,
    product.image,
  ),
  {
    path: '/product/' + product.id,
    structuredData: [
      createProductJsonLd({
        name: product.name,
        description,
        path: '/product/' + product.id,
        image: product.image,
      }),
      createBreadcrumbJsonLd([
        { name: '首页', path: '/' },
        { name: product.name, path: '/product/' + product.id },
      ]),
    ],
  },
)
~~~

这是为说明职责而整理的**简化示例**；项目实际使用 `product.value`、`productionId.value`，对描述有多个后备字段，并包含更多的 Breadcrumb 信息。

其生成过程是：

~~~text
页面数据：产品名称 / 描述 / 图片 / ID / 分类
                  ↓
seoConfig.product()：Title / Description / OG
                  +
createProductJsonLd() / createBreadcrumbJsonLd()
                  ↓
usePageSeo(SeoMeta, PageSeoConfig)
  ├─ useSiteSeo()：补齐网站默认值
  ├─ useSeoMeta()：Title / Description / OG 等
  ├─ useHead()：Canonical、noindex/nofollow
  └─ useJsonLd() → useHead()：JSON-LD Script
                  ↓
Nuxt SSR / 预渲染 → 最终 HTML Head
                  ↓
Lighthouse、实际 HTTP/HTML 和索引数据分层验收
~~~

例如可以生成：

~~~html
<title>示例产品 - 智能内容安全解决方案 - 缔零科技</title>
<meta name="description" content="产品真实的业务介绍">
<meta property="og:title" content="示例产品 | 缔零科技">
<link rel="canonical" href="https://www.lawgenesis.cn/product/a">
<script type="application/ld+json">
  { "@context": "https://schema.org", "@type": "Product", "name": "示例产品" }
</script>
~~~

核心工程思想：**页面负责提供真实业务数据与规范路径，公共方法负责把这些输入转换为统一的页面 SEO 表达**。增加产品或新闻不需要复制一整套 Meta/Head/JSON-LD 实现。

#### 【标准回答】

结构化数据的核心不是增加更多标签，而是将网页真实描述的公司、产品、新闻或职位表达成机器容易理解的实体及属性。根据业务类型选择 Schema.org 的类型，再由公共 Builder 将实际字段映射为 JSON-LD，在页面层注入。实现时应验证字段合法性、真实内容一致性与链接正确性；即使 JSON-LD 有效，也不能保证搜索结果一定展示富媒体样式。

### 7.7 【如何验证 SEO 工程真正发挥作用？】

#### 【提问】

为什么 Lighthouse 的 SEO 技术审计高分不能代表搜索结果已经更新？还需要怎样的 HTTP、抓取、索引和结构化数据证据？

#### 【回答要点】

##### 8. 完整 SEO 验收必须覆盖 Lighthouse 之外的实际抓取与内容问题

| 需要验证的目标 | 实现能力 | 正确的验证途径 |
| --- | --- | --- |
| URL 能被发现 | Sitemap、标准站内链接 | 核对 URL 覆盖及抓取记录 |
| 页面可请求、状态准确 | SSR/Prerender/SWR、HTTP Status | 真实 HTTP 响应、HTML 主体与动态 404 |
| 索引与主版本明确 | Robots、noindex、Canonical | Lighthouse 部分 Audit、URL Inspection |
| 页面语义准确 | Title、Description、Heading、正文、图片 | Lighthouse 技术审计 + 内容一致性检查 |
| 业务实体结构化 | JSON-LD、Schema.org | Rich Results Test + 真实业务字段核对 |
| 搜索最终效果 | 抓取、索引、曝光和点击 | Search Console 等线上数据 |

对当前官网仍需特别说明：

- `/develop` 的 Robots Disallow 与 noindex 可能产生前述互相妨碍问题。
- News/Jobs 部分入口仍采用按钮或元素 `@click` 导航，应该区分“用户可以点击”与“HTML 存在 `<a href>` 标准链接”；可考虑逐步替换为 `NuxtLink`。
- Sitemap 新闻来源存在最多 100 条与 `lastmod` 取值等局限，不能声称全量无遗漏。
- `site` 配置、`useSiteSeo()` 与 JSON-LD 生成器都包含部分企业默认信息，后续可进一步统一配置来源。
- 资讯详情页面的 SEO 数据更新与异步数据有关，需要实际检查 SSR/SWR 响应 HTML 是否已经包含关键内容，而不能只观察客户端更新后的 DOM。
- 当前仓库记录过使用 Lighthouse 做开发期审计，但未核实完整自动化 Lighthouse CI 门禁配置，不应声称每次构建都已自动强制 SEO 分数达标。

##### 10. 通用知识与项目实践的阅读衔接

通用机制详见 [《SEO 工程体系》](https://github.com/cxDlogver/cx-learn-notes/blob/main/Full-Stack-AI-NOTES/S-SEO工程体系.md)；实际实现与更多边界详见 [《official-network SEO 工程体系源码分析》](https://github.com/cxDlogver/official-network/blob/main/docs/SEO工程体系源码分析.md)。通用知识以搜索生命周期为主线，不应被当前 Nuxt 实现限制。

#### 【标准回答】

SEO 验收应区分技术基础和搜索业务表现。Lighthouse 负责一部分技术检查，真实响应 HTML、HTTP 状态、Canonical、Sitemap、结构化数据测试检查当前网站输出是否准确；Search Console 等线上反馈才可能说明重要 URL 是否被发现、索引、展示及点击。对于新旧官网的 URL 和内容变化，还要确认迁移策略。不能把一个 Lighthouse 分数写成“搜索引擎已收录或排名提升”的结论。

## 8. 性能优化体系与具体实现

### 8.1 【官网性能优化怎样围绕三个体验目标设计整体方案？】

#### 【提问】

**官网包含大量图片、首屏 Hero、页面过渡和持续视觉动画，你如何从减少白屏、减少视觉抖动、保证交互和滚动流畅三个目标设计性能方案？每项优化在代码中如何实现，为什么能降低对应的浏览器成本，又如何判断是否真正有效？**

#### 【回答要点】

**官网包含大量图片、首屏 Hero、页面过渡和持续视觉动画，你如何从减少白屏、减少视觉抖动、保证交互和滚动流畅三个目标设计性能方案？每项优化在代码中如何实现，为什么能降低对应的浏览器成本，又如何判断是否真正有效？**

##### 1. 三个体验目标先决定关注的现象和验证指标

| 官网实际体验问题 | 首先回答的问题 | 主要指标与观测方法 | 优先选择的工程手段 |
| --- | --- | --- | --- |
| 首次访问或页面切换时长时间看不到内容 | 文档、首屏关键资源和页面内容在哪一步等待 | 首次导航 FCP（First Contentful Paint，首次内容绘制）、LCP（Largest Contentful Paint，最大内容绘制）；客户端路由切换另测新页面主体可见时间 | Nuxt 页面生成与缓存、CDN 与图片变体、关键资源加载优先级、非关键内容延后 |
| 图片和交互效果造成页面“跳动”或尺寸变化 | 是否有非预期布局位移，是否频繁触发布局计算 | CLS（Cumulative Layout Shift，累计布局偏移）；Layout / Recalculate Style Trace 辅助定位 | 容器尺寸预留、稳定文档流、避免通过 width / left 等布局属性反复执行动画 |
| 滚动、轮播、粒子和卡片动画出现卡顿 | 每帧 JavaScript、布局、绘制和合成工作是否过重 | FPS、Frame Time P95、LoAF（Long Animation Frames，长动画帧）；涉及点击反馈时额外分析 INP | transform / opacity、rAF、减少重复几何测量与框架更新、不可见时停做 |

**FCP 优先的合理边界**：官网的直接需求是让用户尽快摆脱初始白屏，因此可以把 FCP 作为首要观察点；但 FCP 只表示首次出现符合统计条件的内容，并不证明首屏主要信息已经出现。LCP 受 Hero 客户端渲染影响，恰恰可能暴露“页面不白了但主体仍迟迟不见”的问题，不能因为存在 ClientOnly 就忽略 LCP。客户端 SPA 路由跳转一般不会天然重新产生一个传统文档导航的 FCP，应借助路由开始时间、页面主体可见标记和 Filmstrip 单独评价切换白屏。

这里还需要严格区分“视觉抖动”与“帧卡顿”：CLS 衡量符合规则的非预期布局位移，重排、重绘、CSS 动画本身不自动等于 CLS；即使 CLS 为零，大量 Paint、Canvas 或 JavaScript 工作依然可能造成掉帧。

#### 【标准回答】

官网的性能优化并不是全面套用一份技术清单，而是从用户浏览官网时最直接的三个体验问题出发：**首次访问和页面切换是否有明显白屏，图片或交互效果是否导致布局跳动，以及滚动和持续动画是否流畅。**

第一部分是**加载体验**。因为官网以内容和图片展示为主，我首先关注 FCP，也就是用户多久能看到第一批内容，同时结合 LCP 判断主要内容是否真正出现。资源层通过 Nuxt Image 配合 WebP、图片质量、响应式尺寸和懒加载来减少不必要的图片字节与首屏资源竞争；关键首屏资源则需要尽早被发现，必要时才使用预加载或高优先级。网络和页面交付层，一方面使用 CDN 分发静态图片并按缓存规则复用资源，另一方面用 Nuxt 的混合渲染能力，将首页、产品等内容相对稳定的页面 Prerender，在构建阶段生成 HTML；新闻页面使用 SWR 兼顾更新与缓存复用。两者解决的是不同环节的等待，不是把预渲染等同于浏览器已经预加载资源。

第二部分是**视觉稳定**。官网有图片、轮播和动态内容，需要预留容器宽高或比例，减少资源加载完成后重新占位导致的非预期布局偏移；在动画设计上，优先使用 transform 和 opacity 做视觉移动和渐变，而不是持续修改 width、left 等布局属性。这里以 CLS 关注布局偏移，但并不把所有重排重绘都视为 CLS。

第三部分是**交互与持续流畅度**。复杂 Hero、粒子、卡片过渡等效果会持续占用浏览器主线程。对于 JavaScript 动画，项目采用 rAF 在重绘前调度更新，CSS 动画尽量走合成友好的属性；同时需要控制每帧计算量、避免 DOM 读写交错造成的强制同步布局，减少不必要的响应式计算与 Canvas 绘制，并逐步完善离屏停做的生命周期。rAF 只是调度机会，并不会自动消除掉帧。

最后我通过 Lighthouse、Network 和 Performance 对加载、布局与主线程进行分析，用相同环境的 A/B 实验验证改动，后续再用真实用户数据评估体验。**这套方案的价值是从具体用户问题出发，找到对应成本、选择恰当机制并且验证结果，而不是为了使用某项性能技术就直接认定优化已经成功。**

### 8.2 【如何优化官网图片资源的体积、格式和响应式尺寸？】

#### 【提问】

Nuxt Image 的 format、quality、sizes、width/height 怎样配合？如何检验 CDN 图片实际传输体积？

#### 【回答要点】

##### 2. 资源优化一：Nuxt Image 处理图片格式、质量与响应式尺寸

**已实现。** 官网在 nuxt.config.ts 注册 @nuxt/image，配置默认 WebP 格式和响应式断点：

~~~ts
modules: ['@nuxt/image'],
image: {
  format: ['webp'],
  screens: {
    sm: 320,
    md: 640,
    lg: 960,
    xl: 1280,
  },
},
~~~

页面中 [HubBrick.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/join/HubBrick.vue) 使用的代表性片段为：

~~~vue
<NuxtImg
  :src="image"
  :alt="name"
  width="1000"
  height="1000"
  sizes="md:200px 100px"
  format="webp"
  quality="80"
  decoding="async"
  loading="eager"
/>
~~~

**设计模板**：先确定图片的 CSS 实际显示尺寸和设备断点，再输出相应的 srcset/sizes 候选、合适格式与质量；最后在浏览器 Network 核验最终 URL、Content-Type、真实传输字节和渲染尺寸，不直接根据 Git 中源图的大小推断用户下载量。WebP 是仓库已配置的格式，不能把 AVIF 说成当前已开启；SVG 适合图标、Logo 和适当的矢量图，不是对照片和复杂动画统一转换 SVG 的理由。

~~~text
原图与展示需求
    ↓ 确认展示尺寸和设备范围
图片处理服务提供尺寸、格式和质量变体
    ↓ 通过 srcset / sizes 暴露候选
浏览器选择并请求实际需要的图片
    ↓
解码与呈现；以 Network 和 LCP 分解验证效果
~~~

项目同时通过 Vite 插件改写图片 CDN 地址。必须区分“组件写了 NuxtImg”和“CDN 远程图像服务确实生成对应变体”，后者要通过实际请求验证。源码：[nuxt.config.ts](https://github.com/cxDlogver/official-network/blob/main/nuxt.config.ts)、[Nuxt Image 官方使用说明](https://image.nuxt.com/usage/nuxt-img)。

#### 【标准回答】

官网有大量展示型图片，我先根据图片真实展示尺寸与设备断点配置 NuxtImg 的尺寸、响应式候选、WebP 编码格式和适当 quality，再用 Network 检查请求 URL、Content-Type 和 Transfer Size。配置 Image 组件本身不能证明远程 CDN 已提供正确的图片变体；需要实际请求验证。图片还要预留宽高防止布局偏移，SVG 只适用于适当的矢量图形场景。

### 8.3 【懒加载、预加载与加载优先级应如何选择？】

#### 【提问】

首屏 LCP 图片、非首屏图片及未来可能访问的资源分别应该怎样处理？

#### 【回答要点】

##### 3. 资源优化二：按首屏重要程度区分懒加载与预加载

**懒加载已实现。** [Values.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/join/Values.vue) 对图片显式使用：

~~~vue
<NuxtImg
  :src="value.imageUrl"
  :alt="value.title"
  width="1600"
  height="800"
  sizes="lg:35vw xl:420px"
  format="webp"
  quality="80"
  loading="lazy"
/>
~~~

**设计原理**：原生 loading=lazy 允许浏览器在非关键图片尚未接近视口时推迟加载，减少初始请求竞争；具体起始距离由浏览器决定，不是严格等到图片真正进入屏幕后才请求。轮播中即使不透明度为零的图片，依旧可能因共享位置和浏览器策略被一起加载，因此需要用 Network 验证。

**关键图片预加载属于参考模板，不是已经核验的项目实现。** 确认某张图属于首页重要 LCP 候选时，可以让资源在 HTML 中尽早暴露，必要时提供预加载提示：

~~~vue
<script setup lang="ts">
// 仅在图片地址固定且确实是首屏关键资源时考虑。
useHead({
  link: [
    {
      rel: 'preload',
      as: 'image',
      href: '/images/hero.webp',
      fetchpriority: 'high',
    },
  ],
})
</script>
~~~

或者让真实使用该图片的组件明确采取非延迟、高优先级加载：

~~~vue
<NuxtImg
  src="/images/hero.webp"
  width="1600"
  height="900"
  sizes="100vw"
  loading="eager"
  fetchpriority="high"
  alt="首屏主要展示"
/>
~~~

这里是**通用模板**，不是项目实际 Hero 的资源声明。使用响应式图像时，要确保 preload 与真实 srcset/sizes 选择一致，避免请求重复或错误尺寸。preload 主要提前获取当前页面关键资源；prefetch 则偏向未来可能用到的资源；不要把所有 JS、图片都设置为预加载或 high priority，否则可能阻碍真正的首屏关键资源。

#### 【标准回答】

我首先识别首屏真正关键的图片，尤其是 LCP 候选；这类资源通常应尽早被发现和请求，而不应随意设为 lazy。对于非首屏图片采用 loading=lazy，减少初始网络竞争；确实存在资源发现延迟时才考虑准确的 preload 或 fetchpriority。preload 主要面向当前页面重要资源，prefetch 面向未来可能需要的资源。项目的懒加载与 eager 设置有源码依据，但不能将关键图片预加载模板冒充现有成果。

### 8.4 【CDN、HTTP 缓存、Prerender 和 SWR 如何改善加载体验？】

#### 【提问】

缓存复用与提前生成 HTML 分别优化了哪一段链路？它们如何配置，又有哪些失效条件？

#### 【回答要点】

##### 4. 网络与页面交付一：CDN 分发和 HTTP 缓存复用解决不同阶段的成本

**已实现的是 CDN 路径转换。** 当前 [cdnImagesPlugin.ts](https://github.com/cxDlogver/official-network/blob/main/build/vite-plugin/cdnImagesPlugin.ts) 从配置的 CDN_URL 与 /images 前缀组合生成远程地址，并在适用的应用源文件中替换静态路径，接入方式为：

~~~ts
const CDN_URL = 'https://cdn.lawgenesis.cn/new/ui'

vite: {
  plugins: [
    cdnImagesPlugin({ cdnURL: CDN_URL }),
  ],
},
~~~

路径变化的含义：

~~~text
源代码中引用：/images/example.jpg
        ↓ 构建期按插件匹配规则改写
浏览器获取：https://cdn.lawgenesis.cn/new/ui/images/example.jpg
~~~

**设计模板**：先确认资源是否可公开共享、URL 版本策略及缓存一致性，再分别决定浏览器缓存与 CDN 缓存策略。对带内容哈希且 URL 变更代表内容更新的公开静态产物，可以考虑：

~~~http
Cache-Control: public, max-age=31536000, immutable
~~~

这是缓存策略**示例**，不是项目当前 CDN 已采用该响应头的证据。实际表现要检查 Cache-Control、Age、ETag、实际 CDN 配置和浏览器 Network。浏览器本地缓存命中可以省去这次网络获取；CDN 命中通常减少回源，但浏览器到 CDN 之间仍然发生请求。路径改写、图片编码和缓存命中是不同能力，不宜混称为“提前缓存”。

##### 5. 网络与页面交付二：Prerender / SWR 根据内容更新特点选择生成与复用时机

**已实现。** Nuxt 生产环境的部分真实 routeRules 为：

~~~ts
const routeRules =
  process.env.NODE_ENV === 'development'
    ? {}
    : {
        '/': { prerender: true },
        '/contact': { prerender: true },
        '/jobs': { prerender: true },
        '/jobs/**': { prerender: true },
        '/news': { swr: 86400 },
        '/news/**': { swr: 86400 },
        '/product/**': { prerender: true },
      }
~~~

该代码是从当前完整配置中**摘取的部分路由**，不表示真实配置只包含这些路径。

~~~text
稳定公开内容：首页、产品、招聘等
构建阶段预渲染 HTML → 部署静态结果 → 请求时直接交付
                                                ↓
更新依赖重新构建 / 部署

允许短时旧内容：新闻等
请求阶段生成或复用页面 → 缓存 → 过期后按 SWR 规则重新生成
~~~

核心是将 HTML 生成工作按页面特点提前或复用，从而降低请求时重复生成成本；Prerender 不代表全部静态资源都预先下载到用户浏览器，SWR 也不意味着每过 86400 秒就主动完成一次定时发布。实际新鲜度、过期重验证和部署缓存行为仍应核对。参考：[Nuxt Rendering](https://nuxt.com/docs/4.x/guide/concepts/rendering)。

#### 【标准回答】

浏览器缓存减少满足条件时的重复网络获取，CDN 缓存减少资源回源与网络距离，Prerender 提前生成相对稳定页面的 HTML，SWR 对动态内容按策略复用缓存和重新生成。官网通过自定义 Vite 插件改写静态图片的 CDN 路径，并在 Nuxt routeRules 中为不同页面选择 Prerender 或 SWR。但 CDN 路径改写不等于缓存命中，预渲染也不等于用户已经下载资源，必须结合缓存响应头、HTTP 和真实 Network 验证。

### 8.5 【为什么使用 ClientOnly？它对首屏显示有什么影响？】

#### 【提问】

当前 Hero 为何只能在客户端启动部分逻辑？静态 HTML 输出、动画启动与 LCP 之间有哪些取舍？

#### 【回答要点】

##### 6. 页面执行边界：ClientOnly 保护浏览器专用逻辑，但可能推迟首屏主体

**当前已实现的是整体 ClientOnly Hero。** 首页 [app/pages/index.vue](https://github.com/cxDlogver/official-network/blob/main/app/pages/index.vue)：

~~~vue
<div class="relative h-75 w-full md:h-145">
  <ClientOnly>
    <IndexHero />
  </ClientOnly>
</div>
~~~

它为 Hero 预留固定高度，且让 window、Canvas、rAF 等依赖浏览器的逻辑只在客户端运行；但 Hero 实际内容也需要等客户端 JS 运行和挂载才能出现。因此“减少服务端渲染工作”不必然等于“页面更早看到主要内容”，需要看实际 LCP Element 及客户端 Render Delay。

**待验证的设计模板**是只把交互与 Canvas 层后移，静态标题、首屏主要信息和占位层仍可由服务端输出：

~~~vue
<template>
  <section class="hero">
    <!-- 静态主体由 SSR / Prerender 输出 -->
    <h1>智能内容安全</h1>
    <p>一站式多模态内容审查平台</p>

    <!-- 只有依赖浏览器的动画层放在客户端 -->
    <ClientOnly>
      <HeroAnimation />
    </ClientOnly>
  </section>
</template>
<style scoped>
.hero { position: relative; min-height: 500px; }
</style>
~~~

这只是可对比的改造方案，不能写成当前首页已经实现“静态层与动画层拆分”。应比较当前 ClientOnly 整体 Hero 与拆分版本的首次内容可见时间、LCP 四阶段、JS 执行和主线程任务。

#### 【标准回答】

官网 Hero 包含 window、Canvas 和 rAF 等浏览器环境能力，因此当前使用 ClientOnly 隔离服务端不支持的部分，并为其预留高度。但这也使真正的 Hero 内容需要等待客户端脚本执行与挂载；如果它是首屏最大内容，就可能推迟 LCP。更合理的可选方向是将静态主体和文本提前放入可预渲染 HTML，仅将浏览器动画层放在客户端，不过这仍是需要实验验证的优化方案，不能描述成已落地收益。

### 8.6 【如何通过稳定布局减少图片和交互导致的视觉抖动？】

#### 【提问】

CLS 衡量什么？宽高、aspect-ratio、固定容器和正常文档流如何影响页面位移？

#### 【回答要点】

##### 7. 视觉稳定：图片比例和固定容器先解决内容加载后的布局变化

**已实现。** [新闻页](https://github.com/cxDlogver/official-network/blob/main/app/pages/news/index.vue) 的轮播区域使用固定比例与宽度，代表性片段：

~~~vue
<div class="relative aspect-21/8 w-full overflow-hidden md:h-145">
  <!-- 新闻轮播图片和文案 -->
</div>
~~~

**通用模板**：显示内容未下载时，也让浏览器预先知道占位尺寸：

~~~html
<div class="hero-image">
  <img src="/images/banner.webp" width="1600" height="900" alt="官网展示">
</div>
~~~
~~~css
.hero-image { width: 100%; aspect-ratio: 16 / 9; overflow: hidden; }
.hero-image img { width: 100%; height: 100%; object-fit: cover; }
~~~

这样可以降低图片加载后推开相邻文本和区块的风险。不过“有重排/重绘”不等于“产生 CLS”；需要确认是否真的发生符合 CLS 规则的非预期位置变化，特别是动画和紧邻交互发生的位移，不能混为一谈。

#### 【标准回答】

图片加载时如果没有预留尺寸，就可能把下面的文字和其他元素推开。官网通过尺寸、比例和轮播区域容器提前提供布局空间，降低这类位移风险。还要让交互动画尽量不频繁改变宽高和文档流中的位置。注意 CLS 衡量的是符合规则的非预期布局位移，不是浏览器所有的 Layout 或 Paint；验证时应直接检查 Layout Shift 记录及受影响元素。

### 8.7 【transform、opacity 为什么更适合持续动画？】

#### 【提问】

Style、Layout、Paint、Composite 分别可能产生什么成本？合成层和 will-change 的边界是什么？

#### 【回答要点】

##### 8. 合成友好动画：transform 与 opacity 减少布局属性变更

**已实现。** [app/assets/css/animate.css](https://github.com/cxDlogver/official-network/blob/main/app/assets/css/animate.css) 的页面过渡使用：

~~~css
.page-slide-enter-from {
  opacity: 0;
  transform: translateX(var(--page-shift));
}
.page-slide-enter-to {
  opacity: 1;
  transform: translateX(0);
}
.page-slide-enter-active {
  will-change: opacity, transform;
  transition:
    opacity var(--page-enter-dur) var(--page-ease),
    transform var(--page-enter-dur) var(--page-ease);
}
~~~

**通用对比模板**：

~~~js
// 修改 left / width 等布局属性可能反复引发布局成本。
element.style.left = x + 'px'

// 单纯做视觉位移时优先考虑 transform。
element.style.transform = 'translate3d(' + x + 'px, 0, 0)'
~~~

关键机制不是“用了 -webkit 就一定上 GPU”，也不是“transform 永远没有 Paint”：修改 width、height、left、top 等属性可能导致布局变化，继而影响绘制；transform / opacity 通常更可能沿合成路径更新视觉结果。浏览器仍决定是否创建合成层和是否需要重新栅格化。will-change 只是优化提示，不能给所有节点长期添加，否则图层和 GPU 内存成本可能反而增加。

页面过渡还应评估感知完成时间：当前项目 enter 动画变量设为 1000ms，合成路径较高效不代表用户会认为过渡已经结束。应区分 INP 所关注的下一次绘制延迟与“新页面主体完全稳定可读”的感知时间。

#### 【标准回答】

高频动画如果反复修改 left、top、width、height 等属性，可能使浏览器频繁重新布局和绘制；transform 和 opacity 更有机会沿合成路径更新视觉结果。官网页面过渡就使用这两个属性和 will-change。但这些并不保证动画每帧都只走 Composite，更不意味着将所有元素提升合成层一定更快。还需要关注实际图层、栅格化、GPU 内存以及页面过渡本身对用户感知完成时间的影响。

### 8.8 【rAF 如何工作？为什么使用 rAF 仍可能掉帧？】

#### 【提问】

如何理解 rAF 时间戳、刷新率、单帧预算以及 Vue 响应式更新与 Canvas 绘制的关系？

#### 【回答要点】

##### 9. rAF 只安排下一次绘制前的执行时机，不会自动减少每帧工作

**已实现持续 rAF。** [app/components/index/hero/index.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/index/hero/index.vue)：

~~~ts
const scrollX = ref(0)
const rafId = ref<number | null>(null)

function tick() {
  scrollX.value += 1.5
  rafId.value = requestAnimationFrame(tick)
}

onMounted(() => {
  rafId.value = requestAnimationFrame(tick)
})

onBeforeUnmount(() => {
  if (rafId.value != null) cancelAnimationFrame(rafId.value)
})
~~~

实际含义是浏览器在后续绘制前调用 tick，更新响应式位置，再触发相关组件更新。它不能保证 60 FPS，也不自动避免强制同步布局。每帧固定增加 1.5px 还会让移动速度随刷新率变化。

**参考改进模板**使用 rAF 时间戳控制速度，并控制单帧异常时间跨度：

~~~ts
const position = ref(0)
let rafId = 0
let lastTime = 0
const speedPxPerSecond = 90

function tick(now: number) {
  if (lastTime === 0) lastTime = now
  const delta = Math.min(now - lastTime, 50)
  lastTime = now

  position.value += speedPxPerSecond * delta / 1000
  rafId = requestAnimationFrame(tick)
}

onMounted(() => {
  rafId = requestAnimationFrame(tick)
})
onBeforeUnmount(() => {
  cancelAnimationFrame(rafId)
})
~~~

这个改进只解决基于刷新率的移动速度问题，不自动降低 Vue 响应式写入成本。对于纯视觉连续动画，还可研究 CSS Animation 或局部非响应式数据；必须用 Performance Trace 判断是否值得调整。

#### 【标准回答】

rAF 只把回调安排到浏览器下一次重绘前，不自动减少 JavaScript、Layout 和 Paint 的工作。官网 Hero 每帧增加 scrollX 响应式状态，可能让依赖它的组件重新计算；固定每帧增加 1.5px 还会因刷新率不同出现速度差异。可以采用时间戳驱动位移，并进一步减少不必要的框架级更新与单帧计算。是否有效要通过 Performance 的 Frame 和主线程数据验证。

### 8.9 【如何避免 DOM 读写交错导致强制同步布局？】

#### 【提问】

getBoundingClientRect 何时可能造成强制同步计算？如何批量读取、集中写入、利用 ResizeObserver 缓存稳定尺寸？

#### 【回答要点】

##### 10. 减少读写交错引起的强制同步布局，并控制持续计算量

**当前源码已存在逐帧测量，不等于已经完成这项优化。** [CelestialAuditCard.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/index/CelestialAuditCard.vue) 会在循环中读取：

~~~ts
function anyCardPassing(cards: HTMLElement[], zone: DOMRect) {
  for (const el of cards) {
    const r = el.getBoundingClientRect()
    if (centerInRect(r, zone)) return true
  }
  return false
}
~~~

getBoundingClientRect() 本身并非每次都会强制重排，风险来自脚本此前写入使布局失效，而后续立刻读取布局信息，迫使浏览器提前计算。

**参考模板：批量读取后统一写入。**

~~~js
// 不理想：每次循环交错读取尺寸与修改布局。
for (const el of elements) {
  const width = el.getBoundingClientRect().width
  el.style.width = (width + 10) + 'px'
}

// 可改为分组读取，完成计算后再集中写入。
const widths = elements.map(el => el.getBoundingClientRect().width)
elements.forEach((el, index) => {
  el.style.width = (widths[index] + 10) + 'px'
})
~~~

对于长期不变的几何量，优先在 resize、ResizeObserver 或内容实际变化时更新缓存；对于持续移动的元素，若位置能由时间、初始值和速度算出，可以研究计算交叉关系而不是逐帧遍历所有 DOMRect。注意：ResizeObserver 适合尺寸变化，不能直接替代所有移动位置检测。

另一个真实风险是 [ParticleEngine.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/index/hero/ParticleEngine.vue) 每帧遍历约 300 个粒子并 clearRect 全量重画 Canvas；rAF 无法消除这些绘制工作。可在实验后评估减少粒子数、控制 DPR、减少不必要的响应式对象、离屏停止与按实际数据变化更新。

#### 【标准回答】

问题并非 getBoundingClientRect 每次调用都强制布局，而是之前的写操作让布局失效后又立即读取尺寸，浏览器可能被迫同步结算。官网部分持续卡片动画逐帧测量几何矩形，这是需要通过 Trace 检查的潜在成本。设计时可先批量读取、完成计算后集中写入；对稳定尺寸使用缓存和 ResizeObserver 维护。移动对象若可通过时间与速度计算位置，也可以降低不断查询 DOMRect 的成本。

### 8.10 【如何降低离屏动画和 Canvas 粒子的持续渲染成本？】

#### 【提问】

IntersectionObserver、reduced-motion、组件启停、粒子规模和清屏重绘应该如何控制？

#### 【回答要点】

##### 11. 动画生命周期优化：进入视口启动，不需要展示时可以停止

**部分已实现。** [HeroAuditFlow.vue](https://github.com/cxDlogver/official-network/blob/main/app/components/index/HeroAuditFlow.vue) 已经考虑减少动画偏好和 IntersectionObserver：

~~~ts
const reduce = window.matchMedia?.('(prefers-reduced-motion: reduce)')?.matches
if (reduce) {
  active.value = true
  return
}

io = new IntersectionObserver(([entry]) => {
  if (entry?.isIntersecting) active.value = true
}, { threshold: 0.35 })
~~~

这里实现的是进入可见区域后**激活一次**，不是离开后自动暂停持续动画。可以按以下独立的参考模板为持续 rAF 增加启停管理：

~~~ts
const root = ref<HTMLElement | null>(null)
let observer: IntersectionObserver | null = null
let rafId = 0

function frame() {
  // 这里执行一次必要的动画计算和更新。
  rafId = requestAnimationFrame(frame)
}

function start() {
  if (rafId !== 0) return
  rafId = requestAnimationFrame(frame)
}

function stop() {
  if (rafId) cancelAnimationFrame(rafId)
  rafId = 0
}

onMounted(() => {
  if (!root.value) return
  observer = new IntersectionObserver(([entry]) => {
    if (entry?.isIntersecting) start()
    else stop()
  })
  observer.observe(root.value)
})

onBeforeUnmount(() => {
  observer?.disconnect()
  stop()
})
~~~

组件模板中需要在对应容器上写 ref="root"。生产使用时还应处理暂停后恢复的时间戳重置、页面 visibilitychange、用户 reduced-motion 设置，并确保逻辑不会因多次开始而产生重复循环。这个“可见则执行、不可见则停做”的模板**尚非整个官网动画系统的统一现状**。

#### 【标准回答】

官网已经有通过 IntersectionObserver 在进入可视区域后激活动画的代码，但还不能说整个动画系统都做到了离屏暂停。持续性 rAF 可以在组件离开视口、页面隐藏或用户希望减少动画时停止，在恢复时重新初始化时间差；组件销毁时取消回调。对于粒子 Canvas，还要根据实际性能分析每帧遍历的对象数、响应式对象开销、DPR 和全量重绘成本，在不同设备上控制计算与绘制规模。

怎样围绕白屏、布局位移和持续流畅度设置指标与 A/B 实验？不同页面如何关联数据与版本？

##### 12. 性能验证将目标、浏览器时序与优化动作一一对应

如果需要解释最小接入机制，可以给出以下**参考客户端插件模板**，并说明尚需把指标传给监控系统：

~~~ts
// app/plugins/performance.client.ts（参考模板）
import { onFCP, onLCP, onCLS } from 'web-vitals'

export default defineNuxtPlugin(() => {
~~~

这类 Web Vitals 回调主要对应文档导航生命周期，不应将 Nuxt 每次客户端切换都当成重新产生 FCP。实际页面切换应另外定义“开始导航 → 新页面内容可见”的业务时序，并使用 Performance Mark / Filmstrip、DOM 和交互测试确认可见时间。

| 场景 | 实验记录 | 修改所针对的证据 | 验收要点 |
| --- | --- | --- | --- |
| 首页首次加载 | FCP / LCP、HTML 响应、资源 Waterfall、Filmstrip | LCP 四阶段：TTFB、Load Delay、Load Duration、Render Delay | 同环境多次比较，确认内容是否真的更早出现 |

| Hero / Canvas 持续运行 | Frames、Long Animation Frames、主线程、Layout、Paint、CPU | 持续 rAF、响应式更新、DOM 测量、Canvas 重画 | 关闭某一类工作做 A/B，观察同条件掉帧变化 |

## 9. 性能监控平台与用户行为分析

### 9.1 【为什么通过 Lighthouse 验收后还需要上线监控？】

#### 【提问】

**既然官网已经通过 Lighthouse 完成了阶段性性能与 SEO 验收，为什么上线后还要建设监控平台？你希望采集哪些真实性能指标和用户行为，具体如何设计页面停留时间、产品访问及关键按钮点击的埋点？这些数据怎样反馈到最初的官网重构目标？**

这道题首先考察的是目标闭环：**技术验收只回答页面是否达到了给定的技术要求，真实用户监控才能进一步观察交付后的长期运行质量和用户行为**。因此不能把“上线”理解成全部业务目标都已经被证明实现。

#### 【回答要点】

> **记录范围**：承接前文“Lighthouse 开发测试与部署后复测”，讨论为什么官网还要在上线以后建设线上监控平台、采集真实性能与用户行为数据，以及如何把这些数据用于验证最初提出的“用户愿意继续浏览、深入了解企业业务”的业务目标。
>
> **事实与设计边界**：官网源码已能验证监控 SDK 接入、站点/一级路由可见停留时长埋点及其测试，相关平台文档记录了数据接收、聚合与查询设计；但目前没有找到官网中“产品按钮点击”的具体业务事件上报代码，也没有发现公开官网的用户登录业务。因此产品点击、咨询行为属于本次访谈提出的埋点设计方向，不应直接说成全部已上线运行；“登录事件”应依据公开官网实际业务更准确地称为“用户进站/访问事件”。当前插件源码上报地址仍为 localhost，需核对部署配置与线上数据链路后才能证明生产数据已经成功入库。

##### 【上线后的业务问题不同于开发阶段的技术验收】

在项目开始时，旧官网的问题不仅是首屏或 SEO 不完善，更重要的是企业业务信息展示不足，用户进入官网后不容易了解产品能力，也缺少吸引用户继续浏览的内容组织与交互反馈。

对应的工程目标是让首屏呈现更快、重要页面更容易被搜索引擎理解、内容更完整、交互更丰富。开发阶段借助 Lighthouse 可以衡量 FCP、LCP、CLS 等实验室指标，并检查一部分 SEO 基础技术条件。

但 Lighthouse 不能回答以下问题：

- 真实用户在不同设备、网络环境下进入官网时，页面性能是否仍然稳定？
- 用户访问了哪些业务模块？从首页进入产品、资讯或联系页面的情况如何？
- 用户在具体页面或业务板块停留了多长时间？页面切到后台后的时长是否应计入？
- 用户是否点击了产品介绍、了解更多、联系咨询等关键按钮？
- 不同页面的访问、停留与点击数据能否为下一轮内容和交互优化提供参考？

因此，项目上线后需要把观察对象从“受控条件下的一次页面测试”扩展为“真实用户在实际访问中的持续表现”，既关注**运行质量**，也关注**用户浏览行为和业务兴趣信号**。

##### 【监控体系分为运行质量和用户行为两个相关维度】

这项工作可以从两个互补层次理解：

| 维度 | 核心问题 | 主要观察内容 | 对后续优化的价值 |
| --- | --- | --- | --- |
| 运行质量监控 | 真实用户是否能够稳定、流畅地浏览官网 | LCP、INP、CLS、页面资源和接口耗时、异常、设备与路由 | 定位哪些页面、设备或版本出现体验退化 |
| 用户行为分析 | 用户实际关注哪些内容，是否继续了解企业业务 | 进站与页面访问、有效停留时长、产品访问、按钮点击、联系意向 | 判断内容组织与交互入口是否值得调整 |

两个维度不应互相替代。假如产品页面停留很短，可能是信息表达不够吸引人，也可能是资源加载慢、交互失败、用户迅速找到目标信息或跳转到其他页面。**停留时长本身只是行为信号，不能直接判定用户满意度**，应结合路径、点击和真实性能数据理解。

项目已有的 [监控 SDK 接入](https://github.com/cxDlogver/official-network/blob/main/app/plugins/monitor.client.ts) 使用浏览器侧 Client Plugin 创建 Monitor 实例；SDK 负责采集、标准化与上报性能和自定义信号，监控服务端负责接收、处理和统计，前端平台通过报表呈现不同路由与时间范围的数据。更完整的端到端服务链路可参见 [官网性能监控服务端聚合与可视化全链路](https://github.com/cxDlogver/official-network/blob/main/docs/history/官网性能监控服务端聚合与可视化全链路.md)。

##### 【监控平台将浏览器信号转换成可以持续查询的分析数据】

从工程架构上理解，线上监控不是在页面写几行埋点代码就结束，而是需要将浏览器采集事实通过可靠的数据链路传递到后续分析系统：

~~~text
官网真实访问
    │
    ├─ 自动性能采集：Web Vitals、资源与运行异常
    ├─ 访问生命周期：View / Session
    ├─ 业务停留信号：site.visit / site.route.stay
    └─ 可扩展业务点击：产品、联系等关键事件
    │
    ▼
浏览器监控 SDK：标准化、过滤、批处理、上报
    │
    ▼
监控服务端：接收、校验、去重、存储与异步处理
    │
    ▼
统计与查询：按路由、时间、版本、事件等维度聚合
    │
    ▼
监控与分析页面：真实性能趋势、页面排名、停留/业务行为
    │
    ▼
业务复盘和官网下一轮优化
~~~

当前项目的服务端监控文档说明了接收、可靠交接、Worker 投影、聚合和可视化等职责。这里的重点是说明数据怎么变成可用的信息，面试中无需把与本项工作重点无关的数据库表、队列实现细节全部展开。

同时，要注意**具备 SDK 代码与平台能力，不等于线上已经稳定采集到真实生产数据**。在当前 [monitor.client.ts](https://github.com/cxDlogver/official-network/blob/main/app/plugins/monitor.client.ts) 中，上报 DSN 仍指向本机地址；浏览器若从公开网站向本机地址发送数据，通常不能到达实际生产监控服务。应核对部署时是否替换配置、是否通过代理正确路由，以及服务端实际接收记录，再确定可声称的上线结果。文档不记录实际写入密钥。

#### 【标准回答】

Lighthouse 是可控场景下的单次实验室结果，无法覆盖真实用户的设备、网络、页面路径和持续运行差异。官网上线后还需要监控 SDK 和服务端平台采集、存储和聚合 LCP、INP、CLS、资源以及运行上下文等指标，按路由、版本和设备观察趋势。同时还需要单独收集真实浏览行为数据；运行质量与业务反馈是相关但不同的观察方向。

### 9.2 【如何设计页面停留、访问路径和关键行为埋点？】

#### 【提问】

官网的进站、一级路由浏览、有效停留和按钮点击应怎样定义事件？哪些已实现，哪些仍属后续扩展？

#### 【回答要点】

##### 【用户行为埋点按“进站—浏览—交互”逐步深入】

为了对应官网希望用户继续阅读和了解产品的业务目标，用户行为观察可以建立三个层次：

**第一层：用户进入官网。**

记录一次用户进站或访问会话的开始与结束，并结合入口路由、时间、设备等必要信息观察网站的基础访问情况。官网是公开展示型网站，当前代码没有可核验的用户登录功能，不能把每一次访问都叫作“登录”，也不能默认存在真实身份标识。

**第二层：用户浏览不同业务页面。**

当用户在首页、产品、招聘、资讯、联系等模块之间切换时，统计相关页面或业务板块的访问和**有效可见停留时长**。这一维度直接对应“用户是否愿意继续了解官网内容”，但分析时要区分访问次数、页面 View、会话数和停留时间，避免把几种统计口径混成一个数。

**第三层：用户触发关键业务行为。**

可以围绕产品详情访问、产品介绍按钮点击、了解更多、联系咨询、邮件订阅等环节设计自定义业务事件；具体选择哪些事件，应以实际业务目标和页面交互为依据，不应为了“埋点丰富”记录大量没有分析用途的普通点击。

示例事件可包含：事件名称、所在路由、产品标识或按钮类型、时间、匿名访问标识、应用版本和必要的会话上下文。此处是建议性字段设计，并非声称官网当前已经为每个按钮完成了事件上报。

由此可以观察：

~~~text
用户进入官网
      ↓
访问首页 / 其他入口页面
      ↓
浏览产品、资讯、招聘等业务模块
      ↓
进入具体产品详情或点击关键介绍入口
      ↓
可能进入联系或其他后续行为
      ↓
结合访问路径、停留时间、性能和事件数据分析
~~~

这是一种用于理解行为的分析框架，不代表现有监控数据已经能够无遗漏还原每个用户的完整路径，也不能将按钮点击直接等同于咨询转化。

##### 【页面停留时长已在官网中按进站与一级路由两层实现】

官网的 [停留时长编排代码](https://github.com/cxDlogver/official-network/blob/main/app/utils/monitor/stay-tracking.ts) 已包含明确的业务信号：

| 信号或指标 | 类型 | 统计含义 |
| --- | --- | --- |
| `site.visit` | Trace | 一次进入官网对应的站点访问生命周期 |
| `site.route.stay` | Span | 某个一级路由业务板块的一段停留 |
| `visibleMs` | 自定义指标 | 页面在前台可见的累计毫秒数 |

这套实现的重点不是简单记录进入页面和离开页面的墙钟时间，而是区分**用户实际可见的时间**与**标签页切换到后台后继续流逝的时间**。

项目通过 [可见时长计时器](https://github.com/cxDlogver/official-network/blob/main/app/utils/monitor/visible-stopwatch.ts) 在页面隐藏时暂停计时，重新可见时恢复；在路由切换、`pagehide` 等场景中结算相应的 Span/Trace，并在 BFCache 恢复等生命周期中重新处理访问记录。

实现中还存在一个需要主动说明的边界：为了让监控平台按业务板块聚合，[route-section.ts](https://github.com/cxDlogver/official-network/blob/main/app/utils/monitor/route-section.ts) 将具体路径归并到一级路由。例如：

~~~text
/product/a  ─┐
/product/b  ─┴→ /product

/news/123   ─┐
/news/456   ─┴→ /news
~~~

这样统计“产品模块整体停留时长”比较方便，也能减少大量动态路径造成的高基数问题。但代价是**不能只凭 `route_name=/product` 区分不同产品详情的兴趣差异**。

如果下一轮分析需要比较不同产品、不同页面 CTA 的表现，就应增加经过规范化的产品 ID、页面标识或事件属性，并遵守事件维度、隐私及聚合成本约束，而不是随意将完整带参数 URL 当作统计维度。

##### 【点击行为埋点应该与明确的业务问题对应，不能把监控能力等同于已经有事件】

用户希望后续判断“哪些产品介绍吸引用户、哪些按钮更容易被点击”，因此可以围绕几个核心业务事件设计明确的采集口径：

| 业务问题 | 建议观察的事件 | 需要注意的分析边界 |
| --- | --- | --- |
| 哪些产品更受到关注 | 产品详情访问、产品入口点击 | 需要区分具体产品，避免全部归并为 `/product` |
| 用户是否愿意进一步了解内容 | 产品介绍/了解更多按钮点击 | 点击是兴趣信号，不代表读完内容或完成转化 |
| 用户是否产生进一步联系意向 | 联系入口点击、咨询提交成功 | 点击联系按钮不等于成功提交表单 |
| 用户是否持续浏览 | 页面 View、路由停留、访问路径 | 需要区分页面隐藏、短访问与多次浏览 |

监控平台已有自定义事件接收、统计和可视化的设计能力；但在当前官网源码中尚未定位到上述产品按钮的具体业务埋点调用。因此应准确表述为：**官网已经实现性能监控和一级路由有效停留采集；产品按钮点击等业务事件，是围绕后续业务分析提出的进一步采集方向，其实际落地需要补充对应代码和数据证据**。

如果后续实现，业务侧可以在明确的按钮处理逻辑中调用监控 SDK 提供的自定义事件接口，并对事件命名、属性白名单、去重和来源版本形成统一约束。此处不编造具体的 SDK 方法签名。

#### 【标准回答】

我会沿进站、浏览、交互三个层次组织埋点：先记录访问和会话，再观察一级路由的页面访问与有效停留，最后按业务目标补充产品详情、联系入口等关键操作。停留统计要处理路由变化、页面隐藏与离开，不能简单认为时间差就是真实阅读。官网已能找到进站和一级路由停留的实现依据；产品按钮点击等具体埋点需要继续验证对应业务调用，不应把监控平台具有事件能力当作官网已经全面埋点。

### 9.3 【如何通过真实用户数据判断官网重构是否达到目标？】

#### 【提问】

如何从页面访问、有效停留、产品访问、曝光/点击和性能变化分析效果，同时避免相关性误判？

#### 【回答要点】

##### 【数据分析要回到原始目标，但不能过度解释停留和点击指标】

将数据回收到业务目标时，可以围绕几个具体问题逐步分析：

1. **首页是否有效引导深入浏览**：观察首页访问与后续产品/方案页面访问之间的关系，结合导航入口点击辅助判断信息路径是否顺畅。
2. **哪些内容值得继续优化**：比较不同板块的访问与有效停留分布；需要产品级分析时，补充具体产品维度，而不能仅使用一级路由汇总。
3. **交互入口是否有价值**：观察重要 CTA 的曝光、点击和下一步行为。如果只记录点击次数而没有曝光或访问分母，不能直接计算可比的点击率。
4. **是否存在性能导致的体验风险**：将页面性能与用户行为分开观察并尝试关联，但不要凭相关性直接推断某个性能问题必然导致用户离开。
5. **优化后是否真的改善**：明确改版日期、版本、观察窗口和统计口径，必要时结合对照实验；避免把流量季节变化或来源变化误判为页面改动的功劳。

隐私和安全方面，页面行为埋点应遵循数据最小化原则，避免上传表单内容、手机号、邮箱、完整敏感 URL、访问凭据等信息；如需非必要分析类追踪，还应依据适用地区的法律与产品告知、同意设置决定采集和启用方式。

因此，“监控数据驱动优化”更准确的含义是：**建立可持续观察与提出改进假设的基础，而不是证明上线的第一天已经实现了全部业务目标**。

##### 【整项工作重点的最终闭环与后续答辩衔接】

官网项目的实际工程化过程可归纳为：

~~~text
业务问题：旧官网信息不足、浏览路径与交互体验较弱
                 ↓
需求目标：更清晰的信息展示、更快的首屏、更好的 SEO 与浏览体验
                 ↓
技术方案：Nuxt、混合渲染、页面与数据架构
                 ↓
工程初始化：TypeScript、Lint、格式、设计规范与职责边界
                 ↓
开发执行：按模块渐进实现，AI 辅助开发与任务产物记录
                 ↓
持续测试：Lighthouse、实际页面与交互检查、修复回归
                 ↓
生产交付：正式构建、预渲染、CDN、目标环境复测
                 ↓
上线后观测：真实 Web Vitals、页面可见停留及可扩展业务行为
                 ↓
业务数据分析：评估页面兴趣信号、访问路径和体验问题
                 ↓
下一轮需求与优化：以新的数据再次驱动工程设计
~~~

这套主线的价值不是“官网采用了多少工具”，而是**在真实项目中把目标、工程约束、开发过程、验收证据和后续数据反馈连接起来，使一次交付能够沉淀成持续改进的软件研发方法**。

仍要明确 AI 的参与边界：官网时期是 AI 辅助分析、页面探索、编码和检查，不是后来具备完整自主任务执行与自动验收能力的 Agent 研发工作流。两者可以有工程思想上的延续，但不能将后续系统已经具备的自动化能力倒写到当前官网项目中。

#### 【标准回答】

最后一个阶段是官网上线后的数据采集与持续优化。

我认为官网完成部署并通过 Lighthouse 验收以后，并不意味着整个研发工作就结束了。因为我们在最初的需求分析中希望解决的不只是首屏性能和 SEO 问题，更重要的是让用户能够更充分地了解公司的产品和业务，并愿意继续浏览。

Lighthouse 能够反映受控测试条件下的性能和部分 SEO 基础技术质量，但无法说明真实用户究竟访问了哪些页面、停留了多久、对哪些产品更感兴趣，也不能完全代表线上不同设备和网络环境下的体验。

所以我们后续进一步建设了线上监控平台，通过浏览器监控 SDK 采集真实访问中的性能与行为数据。

**一方面是运行质量监控。** 我们采集 LCP、INP、CLS 等 Web Vitals 和部分资源、运行信息，目的是观察真实用户访问时网站的长期表现，帮助定位哪些页面或者环境中的体验需要继续改善。

**另一方面是用户行为数据采集。** 我希望围绕官网重构的业务目标，重点关注用户进入官网、不同业务模块的访问和有效停留时长，以及产品详情访问、产品介绍按钮和联系入口等关键行为。这些数据可以帮助我们观察用户是否会从首页继续浏览产品内容，哪些业务模块更容易吸引访问者，以及页面交互是否需要继续调整。

其中，官网已经实现了对整站访问和一级路由停留时长的采集。我们通过路由切换、页面可见性变化和离开页面等事件，累计用户实际在前台浏览的时间，避免用户把标签页切到后台以后仍持续计算停留时长。数据通过监控 SDK 上报，再由平台进行存储、聚合和展示。

而像具体产品介绍按钮点击等更细粒度的业务埋点，可以进一步加入产品标识和事件属性，形成从页面访问、内容浏览到关键操作的观察链路。这里我会把已实现的有效停留采集和后续规划的按钮行为采集区分开，不把监控平台支持自定义事件等同于每个业务按钮都已经完成上报。

通过这些数据，后续就可以把用户行为与页面真实性能结合起来，观察哪些页面值得继续优化，并根据实际结果调整内容组织、交互入口和页面性能。

**所以这一阶段的核心价值，是让官网项目从一次性的开发、测试和上线交付，进一步延伸为能够持续观察和迭代的业务系统。**

回到整个工程流程，我们首先从旧官网的业务问题出发确定重构目标，再据此选择 Nuxt 和混合渲染方案，在统一工程规范下完成 AI 辅助开发，通过 Lighthouse 和实际部署复测验证技术效果，最后利用线上监控持续观察真实运行质量和用户浏览行为。

这就形成了一套**从目标定义、技术方案、工程实现、质量验收到上线数据反馈的完整研发闭环**。对我来说，这也是通过官网项目探索可复用研发工程规范的核心意义。

## 附录 A. 原稿中仍需深入讨论的追问

### A.1 【同一 Agent 生成规范与测试时如何保证标准可信？】

#### 【提问】

> 如果需求分析文档、技术方案和 Test Case 都由同一个 Agent 生成，那么即使采用规范驱动、验证前置与完整的可追溯机制，是否仍然可能出现“整个工作流都按照错误需求正确执行”的问题？怎样设计机制，保证最终验收标准本身可信？

#### 【回答要点】

##### 【当规范和 Test Case 由同一个 Agent 生成时，如何保证标准本身可信】

当前先记录追问，不把尚未讨论的详细方案写成既定结论：

> 如果需求分析文档、技术方案和 Test Case 都由同一个 Agent 生成，那么即使采用规范驱动、验证前置与完整的可追溯机制，是否仍然可能出现“整个工作流都按照错误需求正确执行”的问题？怎样设计机制，保证最终验收标准本身可信？

该追问后续可围绕**原始事实的权威性、产品/研发/测试的独立审查、需求与用例映射、变更控制、负向断言和证据独立性**展开，避免简单回答“再找一个 Agent Review 一次”。

#### 【标准回答】

现阶段可明确：验收标准应回到权威原始 PRD、业务规则与实际用户需求，而不是由同一 Agent 依据自己生成的实现反向决定。需求与测试用例之间需要追溯映射，关键业务断言要经产品、研发、测试等独立视角核验，并结合负向用例、变更审批和独立证据。该题在原稿中属于待继续深入的问题，不能声称官网已经落地一套完全自动的独立评测系统。
