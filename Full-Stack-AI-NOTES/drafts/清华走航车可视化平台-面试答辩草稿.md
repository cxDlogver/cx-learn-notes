## 1. 请介绍清华走航车实时数据可视化平台，以及你主要负责的工作和技术重点

### 【提问】

**请简单介绍清华走航车实时数据可视化平台的项目背景、数据处理链路、你个人负责的工作，以及主要解决了哪些技术问题。**

### 【回答要点】

这一题首先建立业务场景，再解释为什么**实时通信可靠性**和**实时渲染流畅性**是两项主要工程挑战。开场回答要能够直接使用 WebSocket、JWT、心跳、状态管理、断线重连、数据补偿、生产者—消费者、requestAnimationFrame、帧耗时、LoAF、增量更新、自适应控制等术语，但每一项术语都必须对应一个明确问题和作用阶段，不应堆叠名词。

**一、项目背景与数据链路。**

- **项目定位**：面向科研机构的走航车实时气体监测数据可视化平台，支持实时监测与历史数据查询、回看。
- **数据来源**：车辆行驶时持续采集多种气体浓度、地理位置和时间戳等监测信息，并发送给服务端；服务端管理实时数据及持久化数据。
- **数据传输**：服务端向前端提供 WebSocket 长连接推送实时监测数据，历史时段数据通过 HTTP 按需查询。WebSocket 更适合持续推送，HTTP 更适合按范围检索。
- **前端展示**：基于 OpenLayers 显示车辆位置、行驶轨迹、气体浓度空间分布；基于 ECharts 展示不同监测指标随时间变化的趋势。
- **业务特点**：数据不是一次请求后静态展示，而是持续产生、不断到达和不断进入可视化组件；网络中断、历史补发或数据量累积都可能影响实时性和流畅性。

**二、个人工作方向一：实时通信的安全性、可靠性与可恢复性。**

- **目标**：连接状态可识别，网络异常能够在允许条件下恢复，鉴权状态正确，断线期间可补偿的数据能够继续接收。
- **连接生命周期**：连接建立与鉴权 → 心跳存活检测 → 异常分类与状态切换 → Token 刷新/重新鉴权或网络重连 → 恢复数据消费。
- **核心机制**：WebSocket + JWT；应用层心跳与超时检测；区分网络异常、凭证失效和权限撤销；指数退避重连；在合适的身份状态下恢复业务连接。
- **数据连续性**：连接恢复本身不代表消息完整恢复。需要以序号或时间游标记录接收进度，对重复或跨连接晚到数据做识别，发现缺口后在服务端保留范围内执行区间补偿。
- **异常分流**：短暂网络故障允许受控重连；短期 Access Token 过期可在 Refresh Token 仍有效时尝试刷新后重新鉴权；权限被撤销、刷新凭证失效时应终止无意义的自动重试。
- **价值**：从“有一个 WebSocket”提升为**连接生命周期管理 + 身份状态管理 + 数据恢复**的完整可靠通信设计。

**三、个人工作方向二：实时渲染性能治理。**

- **目标**：在数据持续进入、可能突发补发以及轨迹越来越长的情况下，保持最新数据展示及时，并控制主线程计算与地图/图表的绘制成本。
- **性能监测**：以 FPS、Frame Time P95 等反映流畅度的指标观察结果，结合 LoAF、主线程任务、单批次提交耗时、队列长度与等待时间定位瓶颈。FPS 不足以单独解释掉帧，LoAF 是长动画帧诊断线索，不是网络传输指标。
- **核心模型**：生产者—消费者模型，把**数据接收**和**渲染执行**分开；监测数据先进行规范化、去重与有界缓存，再由渲染调度器按适当节奏消费。
- **调度与处理**：requestAnimationFrame（rAF）提供绘制前的调度机会；批量更新避免一条数据调用一次绘制；ECharts 限频与局部更新减少重复图表计算；地图按需增量追加轨迹或更新单个车辆 Feature。
- **动态反馈**：结合帧耗时、FPS、队列积压和单次批量处理耗时，调整服务端推送速率或客户端每帧处理的 batch，实现自适应限流/动态批量，而非固定地追求最大吞吐量。
- **问题边界**：如果历史轨迹对象不断增长，仅靠降低输入频率不足以根治每次绘制都遍历历史对象的成本，还需要考虑轨迹分段、可见范围裁剪、聚合、降采样或增量绘制能力。
- **价值**：不是一次性“加一个 rAF”，而是**监测 → 定位 → 调度 → 控制 → 验证**的实时渲染性能优化闭环。

**四、整体收束。**

两项工作分别保证两类目标：**数据能可靠、连续地进入浏览器**，以及**进入浏览器以后能够以可控成本持续展示**。前者关注连接可恢复、权限有效和数据连续；后者关注展示实时性、帧开销、队列积压及交互流畅。

### 【重点回答】

这个项目是一个**面向科研机构的走航车实时气体监测数据可视化平台**，主要用于对走航车行驶过程中采集的气体浓度、地理位置及时间序列数据进行实时监测和可视化分析。

在整个数据链路中，走航车持续采集监测数据并上传至服务端，由服务端完成数据接入与持久化，通过 **WebSocket 实时推送**向前端传输最新监测数据，同时通过 HTTP 提供历史数据查询能力。前端基于 **OpenLayers 和 ECharts**，将实时数据展示为车辆行驶轨迹、气体浓度空间分布以及时间序列趋势图。

我主要负责**前端实时通信可靠性建设和实时渲染性能优化**，重点解决两个问题。

**第一个是实时通信的安全性、可靠性与可恢复性。**

由于走航车在实际运行过程中可能出现网络波动、连接假活以及身份凭证过期等问题，我围绕 WebSocket 连接生命周期，构建包含 **JWT 鉴权、心跳存活检测、异常分类、Token 刷新与重新鉴权、指数退避重连**的连接管理机制。

同时，为了解决网络断开期间的数据缺失问题，结合数据序号或时间游标、有序缓冲与缺口补偿机制，在连接恢复后同步可恢复范围内的缺失数据，保障实时数据展示的连续性。

**第二个是实时渲染过程中的页面流畅性。**

由于监测数据持续进入前端，地图需要不断更新车辆位置、行驶轨迹和气体浓度点，图表也需要持续刷新。随着历史数据不断累积，频繁的数据处理和绘制操作容易增加主线程负载，造成页面持续掉帧和交互卡顿。

针对这个问题，我构建了以 **FPS、Frame Time P95 为核心流畅度指标，结合 LoAF、主线程执行耗时和队列积压情况进行瓶颈诊断**的实时渲染性能优化体系。

在具体实现上，采用**生产者—消费者模型**，通过缓冲队列将实时数据接收与前端渲染解耦，再结合 **requestAnimationFrame 分帧调度、批量更新、增量渲染以及基于运行状态反馈的自适应限流机制**，控制每帧的数据处理量和绘制开销，避免高频数据更新持续阻塞浏览器主线程。

**整体而言，这个项目主要围绕实时数据的可靠传输与高效渲染两个方向展开：一方面通过连接生命周期管理和断线恢复机制保障数据链路的稳定性与连续性；另一方面通过渲染性能监测、批量调度和自适应控制，降低持续数据更新带来的渲染成本，保障地图和图表的实时性及交互流畅性。**

### 【项目背景与数据处理链路】

~~~text
走航车持续采样
    ↓
气体浓度 / 地理经纬度 / 采样时间
    ↓
上传到服务端 → 接入处理与持久化
    │
    ├─ WebSocket 实时推送 → 前端实时数据链路
    │                              ↓
    │                    数据解析、规范化与缓冲
    │                              ↓
    │                     受控批量消费与渲染
    │                              ↓
    │                    OpenLayers + ECharts
    │                      │             │
    │                      ↓             ↓
    │                车辆位置/轨迹   气体浓度趋势
    │
    └─ HTTP 历史查询 → 历史回看、统计及断线缺口补偿（需服务端支持）
~~~

这个框架重点区分**业务采样数据的持久化**、**实时通信的连接生命周期**和**前端渲染的调度生命周期**。数据已经在服务端保存，不等于正在显示的浏览器一定已收到；浏览器已经收到，也不等于当前屏幕完成绘制。后续追问应沿这三个阶段分别验证。

### 【工作重点一：可靠通信与可恢复数据链路】

~~~text
WebSocket 连接管理
    ↓
建立连接 / JWT 鉴权
    ↓
OPEN 后进行应用层心跳 / 超时判活
    ↓
状态变化 / 连接异常
    ├─ 网络中断或服务暂不可用
    │     → 指数退避重连（有次数、时间与停止条件）
    ├─ Access Token 失效
    │     → 在可刷新条件下更新凭证，再建立业务连接
    └─ 权限已撤销 / Refresh Token 失效
          → 停止自动恢复并提示重新授权
    ↓
连接重新可用
    ↓
对齐已确认的数据接收进度
    ↓
查询/接收可恢复范围内的缺失监测记录
    ↓
去重与顺序消费，切回实时监测
~~~

这里需要区分两条状态线：

1. **Connection Lifecycle（连接生命周期）**：连接、鉴权、心跳、异常、刷新凭证、重连、关闭，负责让通信通道重新可用。
2. **Data Progress（数据接收进度）**：序号、连续消费位置、去重、缺口与补偿，负责使通信恢复之后的数据链路尽可能连续。

**重要边界**：WebSocket 建立在 TCP 上，同一连接内的数据顺序是有保障的；实际重复、跨连接晚到或恢复缺口属于应用层消费进度与断线续传问题。“指数退避重连”也不是“网络消息超时重传”；是否真的实现了按 ACK 驱动的重发，必须由服务端协议与源码证明，不能以客户端再次执行 connect() 代替。

### 【工作重点二：实时渲染性能监测与反馈控制】

~~~text
WebSocket 持续推送 / 恢复后的集中补发
    ↓
数据校验、规范化、去重、时间顺序处理
    ↓
待渲染缓冲队列
    │        ↑
    │   监测输入速率 / 队列积压 / 最老待处理时间
    ↓
requestAnimationFrame 分帧调度
    ↓
一次消费适当数量的点（batch）
    ├─ 地图：浓度点、分段轨迹、车辆位置与方向
    └─ 图表：按时间窗口合并、限频、更新 series.data
    ↓
采集 FPS / Frame Time P95 / LoAF / 提交耗时
    ↓
反馈控制器根据负载调整 batch 与可控的输入 rate
    ↓
观察队列是否消退、延迟是否可接受、帧耗时是否改善
~~~

**为什么要分离数据接收与渲染？** 因为两者速率不同：走航车或服务端持续产生数据，网络恢复后还可能短时间集中补发；但浏览器必须在有限的单帧时间内同时处理 JavaScript、样式、布局、绘制与合成。如果每条数据到达就直接调用地图/图表更新，会出现重复工作与长任务，造成掉帧。

**为什么需要反馈控制，而不仅是固定限频？** 因为地图历史轨迹规模、同时展示的气体指标数量、设备性能和浏览器负载会变化。固定每帧处理很多点可能造成长帧；固定每帧只处理少量点则可能导致队列不断积压。应把吞吐量、队列等待时间与帧耗时一起作为反馈信号，在实时性和流畅性之间动态调整。

**哪些指标分别用于判断什么？**

| 观测指标 | 所在层次 | 主要用于回答 |
| --- | --- | --- |
| FPS | 展示流畅度的辅助结果指标 | 是否出现持续的画面更新频率下降，需结合实际帧观测 |
| Frame Time P95 | 流畅度结果指标 | 大部分帧之外的高耗时帧是否拖累用户体验 |
| LoAF（Long Animation Frame） | 长帧诊断指标 | 是否出现长动画帧，以及 JS/渲染阶段有哪些相关线索 |
| JS 任务/提交耗时 | 主线程诊断指标 | 是不是某次批量更新、ECharts setOption 或地图对象处理过重 |
| 队列长度与积压时间 | 调度和消费能力指标 | 是否出现消费跟不上输入、屏幕数据明显滞后 |
| 数据到视图提交延迟 | 实时性指标 | 收到点之后到应用状态提交展示经历了多久；不直接等于实际屏幕像素完成呈现 |

特别注意：**LoAF 不是网络指标**；\`requestAnimationFrame\` 调度时机不等于实际已完成一帧的 GPU 绘制；“调用 ECharts setOption 只更新 series.data”属于局部配置更新，不自动保证底层完全不重算/重绘。具体收益必须由实验验证。

### 【术语校准与标准表达】

| 容易混淆的表述 | 本项目答辩建议表达 | 必须说明的机制边界 |
| --- | --- | --- |
| WebSocket 断线后超时重传 | 心跳超时检测、指数退避重连、断线缺口补偿 | 重建连接与重发缺失消息是不同动作 |
| Token 失效一直重连 | Token 刷新与重新鉴权、按异常类别分流 | 权限撤销或刷新失效应终止无意义重连 |
| 重新连接就恢复全部数据 | 接收进度管理、有序消费与可恢复范围内缺口补偿 | 补偿依赖服务端保存并可查询缺失数据 |
| LOF 或 LOF 网络开销 | LoAF（Long Animation Frame），长动画帧诊断 | 用于定位浏览器长帧，不是网络传输开销 |
| FPS 越高就一定没问题 | FPS 与 Frame Time P95、LoAF、交互延迟联合判断 | 仅看帧率不足以解释突发长帧或输入滞后 |
| 数据到达就实时渲染 | 数据接收与渲染解耦、分帧批量消费 | 最新数据不应无限积压，也不能牺牲全部画面及时性 |
| 通过缓冲队列实现异步就不卡 | 生产者—消费者、rAF 调度、帧预算和背压策略 | 队列本身不会消除处理成本，需控制每批开销 |
| 自信限流、固定降频 | 基于反馈控制的自适应限流与动态批量 | 需要明确输入 rate、消费 batch 和控制指标的关系 |
| 已经使用增量渲染就不会有历史数据开销 | 地图轨迹增量更新 + 历史对象规模控制 | 需要确认 OpenLayers 的实际重绘方式和历史轨迹处理代价 |

### 【后续面试提问方向】

面试问题应该沿完整链路递进，而不是直接把技术名词拆成彼此独立的孤立问答：

1. **一次走航车采样数据如何从车辆经服务端到达地图和图表？** 区分实时流、历史查询和业务数据的存储、传输与消费。
2. **WebSocket 与 JWT 鉴权如何组成完整连接生命周期？** 解释握手、身份状态、心跳存活检测、异常分类和重连条件。
3. **为什么断线重连后仍可能有数据缺口？** 解释序号、接收确认进度、有序缓冲、去重和数据补偿，以及服务端保留范围的约束。
4. **为什么正常每秒接收少量采样点也可能导致严重掉帧？** 分析历史轨迹、图表更新、Canvas/矢量绘制及集中补发造成的单帧成本。
5. **如何建立实时渲染的性能定位体系？** 以 FPS/Frame Time P95 识别问题，再结合 LoAF、主线程、队列和更新调用诊断原因。
6. **如何将 WebSocket 数据接收与地图/图表渲染解耦？** 展开缓冲队列、rAF、批量处理和 ECharts 更新节奏。
7. **自适应渲染控制器如何调节 rate 和 batch？** 分析吞吐、队列积压、提交耗时与帧预算的反馈关系。
8. **随着历史轨迹不断增长，为什么 FPS 仍会下降？** 讨论增量数据更新与底层重绘成本的区别，以及裁剪、聚合、降采样和轨迹分段方案。
9. **如何验证可靠传输和渲染优化真的有效？** 明确不同测试场景、正确性断言、性能指标、前后对照和失败回退。

本节是项目整体介绍与第一题的回答；后续第 2～12 题继续展开渲染性能的定位、实测、控制与图形管线。所有未核验的算法设计都应与已有代码、测试事实明确区分。

## 2. 实时渲染性能优化的完整问题模型：究竟优化什么

### 【提问】

走航车持续接收监测点后，为什么会出现队列积压、画面卡顿与长动画帧？如何建立从实验归因到优化方案的完整体系？

### 【知识与分析】

走航车连续采样形成实时流。页面既要保存和展示浓度、位置和时间序列，又要更新 ECharts 曲线、二维 OpenLayers 或三维 Cesium 场景。所谓“数据已经消费”，仅表示已从待处理队列交付给页面或组件；**不等于浏览器已完成绘图、更不等于屏幕已展示新画面**。

~~~text
走航车采集（原始数据准确性由业务确定）
  ↓
服务端存储、实时可视化数据选择
  ↓
WebSocket 数据到达 → 待渲染队列 Q
  ↓                         ↑
requestAnimationFrame 调度   │ 观测输入速率、消费速率、队首等待时间
  ↓                         │
每次取 batch 个点            │
  ↓
页面状态与图表/地图对象更新
  ↓
Canvas 2D / WebGL 绘制准备与执行
  ↓
浏览器合成、提交显示
  ↑
测量帧间隔、长动画帧、更新耗时、可视延迟
  ↓
反馈调节 Batch、可视化 Rate，以及单次更新与历史场景复杂度
~~~

把问题拆成五个可以独立验证的变量：

| 变量 | 表示什么 | 主要优化手段 | 注意事项 |
| --- | --- | --- | --- |
| N：可视化输入规模 | 单位时间真正进入前端展示链路的新增点数 | 具有业务保真约束的降采样、可视化 Rate | 与走航车原始采集频率分离 |
| K：更新次数 | 单位时间向地图或图表提交更新的次数 | rAF 队列、Batch、图表更新合并 | 更新次数下降不意味着每次更新更轻 |
| C：单次更新成本 | 数据处理、对象管理、几何计算、绘制调用的时间 | 增量更新、对象复用、减少全量重建 | 需测量真实下游成本，而非仅测取点 |
| H：历史规模 | 已保留的数据、Feature、Entity、轨迹几何等 | 时间窗口、轨迹分段、裁剪、聚合、分层 | 逻辑数据历史和场景可视对象是不同规模 |
| B：帧预算 | 当前刷新率、设备性能及其他任务为更新留下多少执行空间 | 反馈控制、任务拆分、降载、诊断 | 60Hz 的 16.67ms 不是业务 JS 可独占的预算 |

可以用一个**说明方向而非精确预测**的成本模型：

~~~text
一次提交成本 ≈ 固定提交开销 F + 每点新增处理开销 c×batch + 历史/场景相关开销 G(batch, H)
单位时间负载 ≈ K × 一次提交成本
~~~

当增大 Batch 时，K 可能下降，固定开销被摊薄；但 G(batch, H) 可能上升，单帧仍然很重。因此不能只用消费吞吐来判断流畅度。

评价体系应同时覆盖四组结果：

- **流畅度**：rAF 帧间隔与 P95、LoAF 数量/持续时间/P95、交互响应；rAF 回调频率只是主线程调度代理指标，不严格等于 GPU 呈现帧率。
- **吞吐量**：Arrival Rate（进入渲染队列的点/秒）、Consume Rate（真正从队列交付的点/秒）。
- **实时性**：Pending、Queue Slope、Oldest Pending Age、数据时间戳与实际显示之间的滞后；队列清空不自动代表实时展示已完成。
- **归因指标**：主线程火焰图、JS 任务耗时、地图/图表更新与 LoAF 的阶段信息、对象数量、可视历史规模、GC。

### 【核心结论】

优化顺序不应是“发现掉帧就加 Batch”。应先根据对照实验识别 K、N、C、H 中哪个变量导致瓶颈，再选择对应措施；优化后必须共同验证吞吐、流畅度和监测数据的保真度。

## 3. 对照实验如何证明 Batch 能解决吞吐，却未必解决掉帧

### 【提问】

为什么提高每次消费的数据点数量，队列可以清空，但三维地图仍然掉帧？实验能证明什么，不能证明什么？

### 【回答要点】

第一轮 Batch Sweep：服务端固定约 20 点/秒、全部接收，历史从 0 开始、Chrome Headless 运行约 60 秒，分别调整 batch=1/2/5/10/20；二维、三维独立测量。

| 项目 | batch=1 | batch=20 | 能说明什么 |
| --- | --- | --- | --- |
| 二维：接收/消费 | 1180 / 414 | 1180 / 1180 | Batch 提升后能追平输入 |
| 二维：待处理点 | 766 | 0 | 队列积压得到缓解 |
| 二维：rAF 次数/秒（实验口径） | 10.49 | 54.94 | 二维在该场景下流畅度也改善 |
| 三维：接收/消费 | 1160 / 342 | 1140 / 1140 | 三维吞吐同样改善 |
| 三维：待处理点 | 818 | 0 | 三维队列清空 |
| 三维：rAF 次数/秒 | 9.07 | 7.47 | 三维的调度反而略慢 |
| 三维：LoAF P95 | 249.5ms | 739.2ms | 三维长帧显著恶化 |

数据来源：[Batch Sweep 原始分析](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/reports/realtime-rendering/batch-sweep-analysis.md)。这是每组单次约 60 秒测试，不能把单次数字直接推广为所有设备、所有运行时长的稳定阈值。

第二轮 Rate Sweep：生成端仍为 20 点/秒，服务端向该客户端展示的点数限制在 1/2/5/10/20 点/秒；测试中 **rate 和 batch 设为相同值**。三维从 rate=batch=20 到 rate=batch=1，rAF 次数/秒约由 7.47 上升到 44.08，LoAF P95 由 739.2ms 降到 93.2ms。

这一轮说明减少可视化输入量是有效方向，但由于 **N 与 K 同时变化**，不能把改善的全部原因归给 N。应结合固定 batch 的交叉对照，进一步单变量验证。[Rate Sweep 分析](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/reports/realtime-rendering/rate-sweep-analysis.md)。

第三轮历史规模与队列对照：相同 pending=10000、batch=1，历史点数 200 → 1000 → 6000 时，rAF 次数/秒约 19.95 → 8.02 → 3.69，LoAF P95 约 124.33ms → 291.33ms → 697.40ms。说明 **H 会放大实际绘制链路成本**。冻结下游的实验也证明：点位在视野外时图表是主要长帧来源；全部 6000 个点可见时图表和地图都贡献长帧。不能简单说“队列长导致绘制慢”或“一定是 Cesium 慢”。

实验源：[2026-10-08 队列与可视历史对照](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/reports/queue-backlog-2026-10-08/实验记录.md)。

### 【结论】

**消费能力 ≥ 输入速率，只解决是否积压；帧耗时可控，才解决是否流畅。** 当增大 Batch 已经无法同时满足两者，必须减少可视化输入 N，或者降低每次更新 C 与历史规模 H 带来的成本。

## 4. 第一阶段：通过 Batch 降低更新次数 K，但为什么不能无限增大

### 【提问】

Batch Size 为什么能够提高吞吐？判断是否继续增加 Batch 的依据是什么？Batch=1 时还掉帧怎么办？

### 【机制】

把 WebSocket 接收和浏览器绘制解耦：

~~~text
WebSocket → 待渲染队列
               ↓
        rAF 取最多 batch 个点
               ↓
        一次提交地图/图表更新
               ↓
        下一帧重新判断
~~~

如果 20 条数据每条都单独触发一次 Vue、地图或图表提交，就会重复支付固定成本 F；合并为一次提交可摊薄 F。理想模型为 N/batch 次更新，但实际受队列、帧预算、引擎内部异步调度和可用 rAF 频率限制。

**rAF 是绘制前的执行时机，不会把耗时 JS 自动分割成小任务。** 必须注意项目队列内的 budgetMs=5ms 主要约束“取出一批数据”的循环，不覆盖下游页面提交、Vue 更新、ECharts 定时器或 ZRender、地图真正绘制的全部时间，不能误称“每帧绘制只耗 5ms”。

判断是否加 Batch，分两步：

1. **必要性**：Arrival Rate 持续高于 Consume Rate，Pending 持续增长，或队首等待时间超标。
2. **安全性**：单次更新 P95、整体 Frame Time P95、rAF 间隔及 LoAF 表明仍有可用预算。需区分框架的同步提交耗时与图形库延迟绘制耗时。

队列近似变化：

~~~text
Q(t + Δt) ≈ max(0, Q(t) + (ArrivalRate − ConsumeRate) × Δt)
~~~

可估算追上输入所需 Batch：

~~~text
requiredBatch ≈ ceil((ArrivalRate + Pending / catchUpSeconds) / availableRafPerSecond)
~~~

但 **requiredBatch 是吞吐要求，不是安全配置**：增大 Batch 会改变可用 rAF 次数/秒，因此必须小步试探并重新观测。

决策原则：

| 情况 | 动作 | 原因 |
| --- | --- | --- |
| 无积压、帧稳定 | 维持或缓慢减小 Batch | 不必为了吞吐追求更大值 |
| 队列增长、渲染仍有预算 | 小步试探增大 Batch | 优先减少重复固定开销 |
| 增大后长帧增加或耗时超预算 | 停止试探并回退到安全 Batch | 防止吞吐与流畅度背离 |
| 队列仍增长、Batch 已无安全余量 | 请求降低可视化 Rate，或优化 C/H | 单靠批量无法解决 |
| Batch=1 时一次更新仍超预算 | 保持批量下限并切换瓶颈治理方向 | 不可能把 batch 再减到 0 来正常消费 |

例如，在 60Hz 显示器上完整帧周期约 16.67ms，但主线程业务更新不能独占这段时间。8ms 等更新预算可作为待实测的工程示例，而非浏览器硬性标准。

**Batch=1 仍然产生 20ms 以上更新耗时**时，Rate 调低可以减少高成本更新出现的次数，却未必减少这一次更新的耗时。如果一个新增点会触发全量历史曲线或历史轨迹重建，必须继续改进增量更新、历史规模或图形渲染策略。

## 5. 第二阶段：降低可视化输入 N，而不是降低科研采集频率

### 【提问】

如果把前端数据从 20 点/秒降到 1～2 点/秒后明显更流畅，应该直接降低走航车传感器的采样频率吗？怎样保证浓度峰值与轨迹关键点不丢失？

### 【设计原则】

**不能让低性能浏览器反过来决定科研仪器的原始采样频率。** 需要把完整原始数据与实时可视化数据分成两条不同的数据链路：

~~~text
走航车每秒采集 20 条（示例）
        ├── 原始数据链路：20 条完整校验、持久化、供科研分析与回放
        └── 可视化链路：按空间/浓度/时间等特征选择代表记录
                         ↓
                     WebSocket
                         ↓
                前端只展示必要点
~~~

内容感知降采样设计应判断以下条件：

- **空间相似性**：相邻位置足够接近、轨迹方向变化很小，可以考虑合并稳定片段。
- **浓度相似性**：同一气体或多种气体处于相应的噪声与业务误差阈值内；稳定区间可取浓度平均值或统计摘要。
- **异常保护**：浓度峰值、突变、极值、明显轨迹转折、开始/结束点和具有意义的业务事件，优先单独保留。
- **时间连续性**：约束最大无更新时长，防止车辆长时间静止显示；保留代表数据对应的采样时间与覆盖区间。
- **可追溯性**：代表记录明确标明采样还是聚合值、合并点数、时间范围和算法版本，可回查完整原始记录。

例如一秒 20 个点中有 19 个位置、浓度近似而 1 个是明显浓度尖峰：可合并稳定片段，**保留异常峰值**，而不是将异常点“剔除后丢掉”。使用平均浓度时，应该说明它是聚合代表值；代表位置尽量使用实际轨迹上的采样点，避免未经处理地平均经纬度后形成偏离实际道路的位置。

重要边界：

1. **1～2 点/秒只可作为目标预算，不是任意场景都必须满足的无条件硬上限**；同一秒多个异常事件都很重要时，需要允许关键事件通道、临时超额、延迟加载或可查询详情。否则在任意流量下无法同时承诺零关键点丢失与始终流畅。
2. 需要同时验收压缩率、轨迹最大偏离、浓度峰值召回、异常保留率、时间新鲜度、前端 Frame Time P95 等，不能只报告丢掉 90% 的点。
3. 当前项目中的实际服务端采样器属于基于稳定哈希和点数档位的确定性抽样；**“空间距离＋浓度相似性＋异常保留”是本轮讨论的升级算法设计，不可声称已经实现或经过上述实验验证**。既有 Rate Sweep 主要证明减少可视化点数有助于性能，不等于已经验证内容感知算法的科研保真度。

## 6. 第三阶段：Batch 与 Rate 如何组成自适应反馈控制闭环

### 【提问】

如何同时保证队列不积压、页面流畅与关键数据保真？控制器根据哪些指标决定提高 Batch、降低 Rate 或恢复 Rate？

### 【运行机制】

~~~text
性能采样（约每秒一个窗口）
  ├── Arrival Rate、Consume Rate、Pending、Queue Slope、Oldest Pending Age
  ├── rAF 观测频率、Frame Time P95、LoAF
  └── 完整更新耗时 P95、当前有效 Rate / Batch
                ↓
自适应控制器：先判断“有没有必要”，再判断“是否安全”
                ↓
    ┌───────────┴────────────┐
    ↓                        ↓
本地 Batch 控制          服务端可视化 Rate 目标
    ↓                        ↓
减少重复提交成本         减少实际新增展示点
    └───────────┬────────────┘
                ↓
          观察新窗口的效果
                ↓
  维持 / 小步继续 / 回退 / 逐级恢复
~~~

**两个控制维度不能混为一个：**

- Batch：每次前端向视图提交多少点，主要控制更新次数 K 与单次成本。
- Rate：服务端向特定可视化订阅下发多少代表点，主要控制 N；不得改变原始采集和数据库持久化要求。

### 【典型状态决策】

| 性能状态 | Batch 决策 | Rate 决策 |
| --- | --- | --- |
| 队列稳定、帧耗时可控 | 保持或缓降 | 保持；持续稳定后逐级试探恢复 |
| 队列增长、帧耗时仍有余量 | 每轮小幅增加，验证新 Batch | 暂时保持 |
| 增加 Batch 后帧耗时恶化 | 回退到已验证安全值 | 视持续过载情况降一档 |
| Batch 已达最大安全值或即使 Batch=1 仍过载 | 不继续冒进 | 在保真约束下尝试减少可视化输入；同时定位 C/H |
| 场景长期流畅、无积压、低延迟 | 不必追求最大 Batch | 冷却结束、稳定窗口足够后逐级恢复数据量 |

反馈算法需要持续窗口判断、滞回、冷却与试探回退，防止 FPS 略微反弹就立即升降 Rate 的控制振荡。

当前 AdaptiveRenderController 的实现可作为**已有控制思路的证据**，不是普适阈值：样本包含 actualFps、baselineFps、arrivalRate、consumeRate、pending、oldestPendingMs、renderP95Ms、frameIntervalMs、effectivePointLimit；以帧间隔约一半作为其内部预算参考；根据积压趋势与队首等待时间判断过载；安全时小步探测 Batch；持续过载且不能安全增加时申请降 Rate；稳定一段时间后慢速恢复。当前代码中的 renderP95Ms 是页面提交相关指标，不可以直接称作“GPU 完整绘制 P95”；如果 ECharts 延迟绘制，必须结合 LoAF、Chrome Trace 与真正帧间隔验证。

参考实现：[AdaptiveRenderController.ts](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/QHZHC_Web/src/views/DataVisualization/services/AdaptiveRenderController.ts)；[FrameTelemetryQueue.ts](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/QHZHC_Web/src/views/DataVisualization/services/FrameTelemetryQueue.ts)。

### 【控制边界】

自适应控制器不能从逻辑上保证“任意场景同时零信息损失、零排队且满帧”。当 Batch 到达安全边界、Rate 因保真约束无法进一步下降、历史绘制仍很重时，需要进入第四阶段——降低 C 和 H，而不是让控制器无限尝试调参。

## 7. LoAF 三阶段如何与 Canvas、WebGL 和浏览器渲染管线对应

### 【提问】

当 LoAF 发现 renderStart 到 styleAndLayoutStart 占了大量时间，ECharts、OpenLayers、Cesium 到底在做什么？Canvas 的图形生成与浏览器最后合成页面分别属于哪一步？

### 【LoAF 是时间边界，而非技术模块边界】

| 区间 | 表示什么 | 典型活动 |
| --- | --- | --- |
| startTime → renderStart | 浏览器渲染周期开始前 | 普通任务、Timer、WebSocket 回调、部分数据/状态处理 |
| renderStart → styleAndLayoutStart | 渲染周期开始后、常规样式布局之前 | rAF 回调、图形库 JS 场景处理、Canvas API 同步调用、WebGL 命令准备与提交 |
| styleAndLayoutStart → LoAF 结束 | 进入浏览器样式布局及后续主线程工作 | 如有需要的 Style/Layout 等工作；不是完整 GPU/合成耗时的同义词 |

LoAF 的划分依据是**工作发生的时间**。同样的 ECharts 数据处理，如果发生在 Timer 中，可能位于第一阶段；如果在 ZRender 的 rAF 中执行，可能位于第二阶段。不能说“Canvas 都是第二阶段、GPU 都是第三阶段”。LoAF 也不覆盖完整的 GPU 渲染与屏幕呈现时间。

**Canvas 2D 路径（ECharts/ZRender、常规 OpenLayers 矢量画布）：**

~~~text
新增监测点
  ↓
JS 组织时间轴/浓度坐标、Feature/Shape、样式和路径
  ↓
图形库调用 moveTo / lineTo / stroke / fill 等 Canvas 2D API
  ↓
浏览器底层图形引擎处理绘图操作
  ↓
生成或更新 Canvas 的图像内容
  ↓
与其他 DOM 图层进入浏览器合成与显示流程
~~~

JavaScript 不是逐像素自己画像素，而是组织图形并调用浏览器的 Canvas API；底层可以由原生 CPU 图形代码或 GPU 加速实现。部分绘图操作的同步耗时可处于第二阶段，后续图形处理/光栅化未必全部计入该阶段。

**WebGL 路径（Cesium）：**

~~~text
新增监测点
  ↓
JS 更新 Entity / Primitive / Geometry / Material / Scene
  ↓
CPU 侧准备 GPU Buffer 和 Draw Command，调用 WebGL API
  ↓
GPU 顶点处理 → 图元/光栅化 → 片元着色 → 写入图像缓冲区
  ↓
浏览器合成器把 Canvas 与 DOM 内容合成为页面帧
  ↓
提交显示
~~~

WebGL API 返回不代表 GPU 工作已经结束；GPU 执行也不能直接用 renderStart → styleAndLayoutStart 的 JS 主线程时间代替。

**为什么 Canvas 内部无需对每个点再做 CSS Layout？** 浏览器布局的是 canvas 元素本身的位置和尺寸，内部每个曲线点、浓度圈和三维柱体并不是独立 DOM 节点。它们的坐标与几何由图形引擎处理，最后画布的图像与普通页面内容一起参与 Composite。Canvas 元素尺寸或周围 DOM 若发生变化，仍可能触发正常 Style/Layout。

**LoAF 第二阶段很长时，应优先排查什么？**

- ECharts：历史窗口数据处理、Option/model 更新、坐标转换、图形元素处理、ZRender Canvas 绘制。特别注意 lazyUpdate 只推迟执行，不消除更新；notMerge=true 可能带来图表模型重新建立。
- OpenLayers：Feature/Geometry、图层变化、样式与可见矢量处理、Canvas 路径绘制。
- Cesium：Entity/Primitive 属性求值、轨迹几何、场景遍历、命令准备及 WebGL API 调用；若怀疑 GPU 侧，还需 Trace/GPU 分析。

**归因原则**：LoAF 确认时间集中在某个阶段；Performance 火焰图定位函数；冻结图表或地图、同历史规模同视野对照，进一步确认因果，不能直接宣称“第二阶段耗时全部是 GPU 绘制”或“全部是 CSS Layout”。

参考：[MDN Long animation frame timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongAnimationFrameTiming)、[Chrome Rendering Performance](https://developer.chrome.com/docs/devtools/performance/)、[当前项目 LoAF 实现](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/QHZHC_Web/src/views/DataVisualization/services/LongFrameDiagnostics.ts)。

## 8. 第四阶段的前提：数据增量更新 ≠ 历史图形不再绘制

### 【提问】

如果新增一个点时只操作这个点，那么历史点还会带来哪些开销？增量更新能否彻底消除历史成本？

### 【分清三个动作】

1. **数据增量**：只处理新批次，不重新遍历完整历史数组；减少 Vue 响应式深度观测、数据转换、图表数据准备等全量工作。
2. **几何/场景增量**：已完成的历史 Feature、Polyline、Entity 或 GPU 资源保留；只修改当前活动轨迹、车辆位置和新增浓度点。
3. **实际画面生成**：Canvas 矢量图层发生变化时仍可能再次绘制大量可见历史要素；Cesium 即使复用历史 GPU Buffer，生成新帧时也可能再次执行可见历史几何的绘制命令。

~~~text
新增 1 点
  ↓
仅更新最新数据与活动轨迹几何        ← 增量更新解决
  ↓
地图场景状态发生变化
  ↓
图形引擎处理当前可视范围的场景
  ↓
历史可见点/线仍可能参与 Canvas 或 WebGL 绘制  ← 仍需治理
~~~

历史开销至少有四类：对象管理（Feature/Entity/Primitive）、增量几何与场景更新、当前帧真实绘制、内存与 GC。它们分别受新增批次 b、历史累计数据 H 和视野内可视对象 V 影响。

**容易忽略的区别**：

- “不再重建历史轨迹数据”不等于“GPU/Canvas 永远不再绘制历史轨迹”。
- “已经绘制过的像素”不保证能够永久复用：视角变化、覆盖顺序、透明度、图层失效或场景变化可能要求重新绘制。
- 原始数据库历史、前端逻辑历史数组、渲染引擎中可视对象规模是三个独立边界；限制其中一个不自动限制另两个。
- 若每个新增点触发全历史轨迹重建，单次更新可能随 H 增长；即使成功消除该全量重建，绘制成本仍可能随 V 增长。

## 9. 二维 OpenLayers 优化方案：从 Feature 更新到图层绘制治理

### 【提问】

二维地图新增监测点时哪些工作会重复？已经实现了什么？进一步降低历史 Canvas 绘制成本应考虑什么？

### 【已实现、可结合源码验证】

二维场景分为车辆图标层、轨迹层、浓度点层，数据变化不必重新创建整个 Map。

1. **只处理新增批次**：监听 realtimeBatchId，drawRealtimeBatch 只遍历本次新增区间，不按全历史点再来一轮。
2. **车辆 Feature 复用**：更新已有车辆点的 Geometry、方向，而不是每帧新建整车图层。
3. **轨迹分段**：ROUTE_CHUNK_MAX_POINTS=256；当前段未满、轨迹连续时 appendCoordinate；满段或断点才新建 LineString Feature。
4. **点位与可视窗口**：只为新增浓度点创建新 Feature；超过用户设定时间窗口的浓度 Feature 可以移除，限制持续可视点规模。
5. **样式缓存与分层**：轨迹样式与浓度点样式复用；车辆、轨迹、浓度点相对独立管理。

源码：[PlanimetricMap.vue](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)。

### 【为什么仍然可能慢】

即使新增 1 个 Feature、只改一段 LineString，VectorSource/Geometry 的变化也可能使相关 VectorLayer 需要重新准备或绘制可见要素。历史 Feature 没有重建，但当前可视范围里的浓度点、线段可能仍然参与 Canvas 绘图。不能把 JavaScript 对象增量操作说成像素级局部重绘保证。

### 【进一步可评估的方案】

- **控制 V（可视历史）**：按时间窗口与可视范围淘汰/加载，低缩放时空间聚合，避免大量密集历史点全量进入当前可视层。
- **静态/动态分层**：将已完成的历史轨迹、历史点与车辆、最新轨迹分离；针对低频变化历史层评估缓存与 VectorImageLayer 等策略。缓存失效或视角变化仍可能重绘。
- **更适合海量点的渲染方式**：评估 OpenLayers WebGL 点图层或预聚合渲染；对比真实 CPU/GPU 成本、交互拾取与数据更新代价。
- **继续治理历史轨迹**：当前时间窗口主要淘汰浓度点；长期不截断的轨迹 Chunk 仍可能增长，可引入按区域、时间、缩放级别的历史线路简化与窗口管理。

方案应按“可视 Feature 数、图层准备耗时、Canvas 绘图成本、用户地图交互”逐项验证，不应为了使用新技术而迁移整个图层。

## 10. 三维 Cesium 优化方案：Entity、Polyline、Scene 与 GPU 负载

### 【提问】

为什么三维场景比二维更容易在增大 Batch 后恶化？如何降低历史 Entity、轨迹几何和实际 WebGL 绘制负担？

### 【已实现、可结合源码验证】

1. **避免历史轨迹每批全量重建**：旧路径曾将完整 mapList 交给 updateRealtimeRoute，清空已有轨迹再按历史重建，单次工作随 H 增加；当前实时路径改为 appendRealtimeRoute(batch)，仅追加新增位置。
2. **256 点轨迹活动段**：完成的 Polyline 不再随新点反复改写，活动段最多约 256 点，达到上限新开一段。当前活动段赋值 positions.slice() 仍可能触发该段几何重新处理，但更新范围不随完整历史无限增长。
3. **静态柱体使用静态属性**：已确定的 position、dimensions、material 不必每一帧都使用 CallbackProperty 重算。新增柱体按需创建或更新。
4. **按需渲染**：Viewer 使用 requestRenderMode=true、shouldAnimate=false，并在发生真实变更时 requestRender。减少无变化期间的无效新帧。
5. **可视浓度柱体窗口**：按时间移除超窗柱体 Entity；完整逻辑历史和地图可视对象数分别控制。

源码：[StereoscopicMap.vue](https://github.com/cxDlogver/qhzhc-realtime-platform/blob/main/QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)。

### 【为什么仍然可能慢】

- Entity 数量多时，Cesium CPU 侧需要维护场景属性、几何与绘制命令。
- 即使静态历史几何缓存在 GPU 内，新的三维画面仍可能需要重新绘制当前可见的历史几何。按需渲染减少“什么时候画”，不保证“每次画多少”。
- 大量独立几何可能增加 Draw Call、状态切换与片元处理；三维还涉及相机、可见性与材质。不同设备可能是 JS 侧或 GPU 侧瓶颈，需通过 Trace/对照实验辨别。

### 【进一步可评估的方案】

- 高频最新车辆/活动轨迹继续实时更新；历史静态柱体和路线采用更适合批处理的 Primitive / GeometryInstance 等形式，权衡静态批处理收益与重新构建成本。
- 根据视野、缩放/屏幕误差与时间层级进行裁剪、简化、LOD 和聚合；不要把历史几十万个样本无差别变成同时可见的几十万个独立 Entity。
- 控制三维复杂度：合理复用材质、几何、绘制资源；避免每点高开销动态属性或不必要的场景重建。
- 结合 CPU 主线程 Trace、GPU 负载与实际 LoAF 测量，而不是仅从 Frame Time 推断 WebGL 哪个阶段耗时。

以上 Primitive 批处理、LOD 等属于进一步可选的优化方向，不可写成当前版本已经上线的结果。

## 11. Chunk 分段究竟优化什么，为什么不是越小越好

### 【提问】

将轨迹分为 256 点一段，所谓“避免整体重建”具体指什么？已绘制历史段是不是以后都不绘制？Chunk 越小是否一定越好？

### 【工作机制】

不分段的全历史轨迹若每次被重建，新来一个点也要处理 H 个历史坐标。分段后：

~~~text
历史完成段 1～M：保留已有 LineString / Polyline，不重新创建其几何
当前活动段：最多容纳 L 个点，仅在这一段追加新点
活动段满或轨迹断开：封存旧段、新建下一段
新的页面帧：可见的历史段仍可能被 Canvas / WebGL 绘制
~~~

**已完成的历史段不再反复“构建/修改” ≠ 已绘制的历史段绝对不会再“绘制”。**

二维 OpenLayers：只改活动段，但受影响的 VectorLayer 可能重画历史可见线段。三维 Cesium：历史几何和 GPU 资源可复用，但新一帧仍可能执行可见历史线段的绘制命令。

Chunk 大小 L 带来两个方向相反的成本：

- L 越大：活动段位置数组、几何更新成本可能越高；单次更新容易形成长帧。
- L 越小：历史段数约 H/L，Feature/Entity/Polyline 对象变多，管理、图层准备、绘制命令的开销可能上升。

例如固定历史 10,000 点：

| L（每段最大轨迹点） | 段数约为 | 单次需更新的活动段最大规模 |
| ---: | ---: | ---: |
| 32 | 313 | 32 点 |
| 128 | 79 | 128 点 |
| 256 | 40 | 256 点 |
| 1024 | 10 | 1024 点 |

公式只描述趋势：

~~~text
总成本 ≈ 活动几何更新成本 f(L)
       + 场景对象管理成本 g(H/L)
       + 实际绘制成本 h(可见段、坐标数、引擎缓存、设备)
~~~

实际不是各项都严格线性，也不应把 256 看成适用于所有设备的最佳值。实验应在相同历史 H、可视历史 V、输入 Rate、Batch、设备、地图视角下比较 L=32/64/128/256/512，记录几何更新 P95、LoAF P95、rAF、对象数量、Draw Call / 内存。选择能满足业务精度与帧预算的折中值。

**更进一步的边界**：想减少历史图形真正参与新帧，需要历史可视规模控制、二维缓存/静态动态分层、三维批处理/裁剪/LOD；Chunk 本身不是“历史画一次，以后永不重画”的开关。

## 12. 性能体系的验证方法与完整面试回答

### 【如何验证优化有效】

**先固定场景再一次只改变关键变量**。至少区分：二维/三维、冷启动/已有历史、点位视野内/视野外、不同历史点规模、正常 20 点/秒/断线补发、同 Batch 下不同 Rate、同 Rate 下不同 Batch、Chunk L 的独立对照。

验证顺序：

1. **确认正确性**：轨迹不断线、坐标与时间顺序正确、浓度峰值与报警事件不被采样算法吞掉，聚合点可追查完整原始数据。
2. **确认消费能力**：Arrival 与 Consume 长期可匹配，Queue Slope 不持续为正，Oldest Pending Age 与最新画面的数据滞后受控。
3. **确认主线程流畅度**：Frame Time P95、LoAF P95/Max、长帧发生频率和交互响应改善；rAF 次数/秒仅作辅助观测。
4. **确认实际成本归因**：性能火焰图及 ECharts、OpenLayers、Cesium 各自独立冻结实验；必要时采集 Canvas/GPU 渲染证据，避免把同步 flush 时间误当整帧耗时。
5. **确认持续运行**：历史 H 从小到大、地图可见对象 V 改变时仍不持续退化；记录内存/GC、图形对象数、可视时窗。
6. **确认控制稳定性**：Batch/Rate 调整不会高频振荡，过载时可回退，恢复后能逐档提高信息展示量。

### 【面试标准回答】

> 走航车的渲染性能优化，我主要按“监测定位—分离变量—逐层降低成本—反馈验证”的方式推进。首先把实时数据链路抽象成生产者与消费者，观测 FPS、帧时间、LoAF、数据到达速率、消费速率、队列长度和数据等待时间，区分页面是否流畅、数据是否积压和最新位置是否滞后。
>
> 第一阶段使用待渲染队列与 rAF 批量更新，将多条数据合并到一次地图/图表更新，减少固定提交次数。实验显示二维在增大 Batch 后，吞吐与流畅度都可能改善，但三维存在队列已经清空、LoAF 却更严重的情况，说明吞吐达标不等于渲染成本受控。
>
> 第二阶段考虑降低真正进入可视化的数据规模，而不是降低走航车原始采样频率：科研数据完整持久化，实时推送侧通过内容感知的代表性采样减少稳定、重复的点，并优先保留浓度峰值、轨迹转折和重要监测事件。这里代表性采样是进一步算法设计，不应与现有简单点数限制混为一谈。
>
> 第三阶段用运行时反馈协调 Batch 与可视化 Rate：队列积压而帧预算充足时，逐步提高 Batch；批量到达安全边界而仍过载时，谨慎降低 Rate；加入持续窗口、冷却和恢复策略，避免控制振荡，同时监测数据保真。
>
> 如果 Batch 已经降到 1，单次完整更新仍然过重，就不能继续依靠调参，需要进一步降低每次更新成本与历史规模影响。通过 LoAF 阶段分析和冻结组件实验，定位 ECharts 的数据模型/Canvas 更新、OpenLayers 的 Feature/Geometry 与可见图层重绘，以及 Cesium 的 Entity/Primitive、轨迹几何、WebGL 场景更新等开销。
>
> 地图的具体优化采用增量批次、对象复用、固定大小的轨迹分段和历史可视对象窗口，避免新增一个点就重建全部历史几何。但是还要区分：不重建历史对象，不代表新一帧不再绘制历史可见内容。二维可以进一步评估缓存、静态动态分层、可视范围裁剪和空间聚合；三维可以进一步考虑按需渲染、几何批处理和 LOD。Chunk 太小会增加历史对象数量，太大又会增加活动段几何更新成本，应通过受控测试确定折中值。
>
> 最终目标不是单独最大化 FPS 或吞吐，而是在业务数据准确、关键异常保留的前提下，让数据消费持续跟得上输入、页面不会形成严重长帧，并避免渲染成本随着历史数据无限增长。

### 【容易说错的结论与准确表述】

| 容易说错 | 准确表述 |
| --- | --- |
| 增大 Batch 就能解决掉帧 | 减少重复提交有利于吞吐；若单批过重，掉帧可能恶化 |
| 每帧队列取点预算 5ms，所以页面绘制 5ms 内完成 | 队列取点预算不覆盖 Vue、地图/图表与延迟图形绘制 |
| 服务端从 20 降到 1 就证明内容感知采样算法保真 | 性能实验证明降低 N 可改善负载，峰值/轨迹保真必须独立评估 |
| Rate 从 20 降到 1，FPS 变好就完全证明是 N 的作用 | 某轮 Rate Sweep 同时调整 Batch，N/K 因果还需交叉实验 |
| LoAF 第二阶段就是 GPU 画图，第三阶段就是整个浏览器合成 | LoAF 按主线程时间划分；GPU、Raster、Composite 不与其一一对应 |
| 增量更新后历史轨迹不再重新绘制 | 不再重建历史几何，但当前可见历史仍可能参与下一帧绘制 |
| Chunk 越小越好 | 小段降低单段几何更新规模，但增加历史对象数量；应实测折中 |
| Batch=1 还卡就只能降低数据量 | 降 Rate 可降低更新频次，还需定位单次 C 与历史 H 的成本 |
| rAF FPS 就是真正的屏幕呈现 FPS | rAF 反映回调调度能力，必须结合帧间隔、LoAF 和浏览器图形 Trace |
| 设计方案、代码已有和实验已证实是一回事 | 每个结论注明“已实现/已测得/待设计验证”，并给出相应证据 |
