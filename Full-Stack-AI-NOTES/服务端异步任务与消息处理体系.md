# 服务端异步任务与消息处理体系建立从请求解耦到失败恢复的完整认知

服务端异步处理解决的不是“怎样写 async/await”，而是：**一项业务工作是否必须跟随当前 Request 生命周期完成，以及当工作被交给后台系统后，怎样可靠地保存、领取、执行、重试和观察。**

~~~text
Request
    ↓
Business Logic
   /          \
  /            \
Sync Work     Async Work
  ↓             ↓
Response      Task / Event
                ↓
          Queue / Job Store
                ↓
              Worker
                ↓
        Success / Retry / Failure
~~~

本文建立系统级 Asynchronous Processing 的通用框架。具体 Queue / Broker 产品只用于说明不同实现；仓库项目代码放在最后作为实践映射。

## 1. 异步处理把业务工作从当前请求生命周期中解耦

### 【Async I/O 与 Background Job 解决不同层级的问题】

~~~text
Runtime-level Asynchrony
│
├── Event Loop
└── Async I/O
    ↓
解决当前 Process 等待 I/O 时怎样继续推进其他工作

System-level Asynchronous Processing
│
├── Background Task
├── Queue
└── Worker
    ↓
解决业务工作是否需要与当前 Request 生命周期解耦
~~~

例如 Request → await database query → Response 虽然包含异步 I/O，但业务仍属于当前 Request；Request → Create Export Job → Response，随后由 Worker → Generate Export，才把业务工作的完成时间从 Request 中拆开。

因此 Async I/O ≠ Background Job。Node.js Event Loop、异步 I/O 与线程/进程运行边界继续参考 [NodeJS 核心总结](./NodeJS核心总结.md) 与 [服务端完整框架体系](./服务端完整框架体系.md)。

### 【异步处理适合把不需要阻塞当前响应的工作移出请求链】

典型场景包括发送通知、生成报表、导出文件、媒体处理、批处理和定时任务。是否异步不能只由“执行时间长”决定，还要判断调用方是否必须立即得到最终结果、失败如何反馈、任务是否允许重试以及业务是否允许最终一致。

### 【Worker Process 与 Worker Thread 属于不同抽象层】

~~~text
Worker Thread
    ↓
同一 Process 内的并行执行单元
    ↓
常用于 CPU-intensive JavaScript

Worker Process / Worker Service
    ↓
独立运行的后台任务消费者
    ↓
从 Queue / Job Store 获取业务任务
~~~

Worker Service 内部仍然可以使用 Worker Thread。前者属于系统级任务执行角色，后者属于 Runtime 内的并行机制。

## 2. Task、Message 与 Event 描述不同业务语义

### 【Task 或 Command 表达需要执行的工作】

GenerateReport、SendEmail、ResizeImage、ExportUserData 等 Task / Command 共同表达“请执行某项工作”，核心问题是：谁执行、什么时候执行、失败是否重试、最终是否完成。

### 【Event 表达已经发生的业务事实】

OrderCreated、UserRegistered、PaymentSucceeded 更接近“某件事情已经发生”。多个独立 Consumer 可以根据自己的职责对同一个 Event 作出反应。

### 【业务语义与消息传递拓扑需要分层理解】

~~~text
Business Semantics
│
├── Task / Command
└── Event
        ↓
Delivery Model
│
├── Task Queue
├── Message Queue / Broker
├── Pub/Sub
└── Durable Job Store
~~~

Task、Message、Event、Queue 并不是同义词。一个 Task 可以存进数据库 Job Table，也可以通过专用 Task Service 或 Message Broker 交付。

Google Cloud 对 Cloud Tasks 与 Pub/Sub 的比较体现了这一差异：Cloud Tasks 更关注显式调用和任务执行控制，而 Pub/Sub 更关注把消息发布给解耦 Subscriber。[[1]](https://cloud.google.com/tasks/docs/comp-pub-sub)

### 【Scheduled Job 与 Queue Job 的区别首先在触发方式】

~~~text
Scheduled Job
    ↓
由 Time / Schedule 触发

Queue Job
    ↓
由 Enqueue / Message Arrival 触发
~~~

Scheduled Job 被触发以后仍然可以创建 Queue Job，因此 Schedule 与 Queue 是不同阶段的职责。

## 3. Queue 与 Worker 共同形成后台任务执行链

### 【可靠异步执行不止 Queue → Worker 两步】

~~~text
Create
↓
Enqueue / Persist
↓
Ready
↓
Claim / Deliver
↓
Running
↓
Business Side Effect
↓
Acknowledge / Commit State
↓
Succeeded
~~~

其中最关键的边界是 Delivered / Claimed ≠ Processing Succeeded ≠ Acknowledged。

RabbitMQ Work Queue 官方教程说明，Consumer 可以在任务完成后发送 Acknowledgement；如果 Consumer 在未确认前退出，未确认消息可以被重新投递。[[2]](https://www.rabbitmq.com/tutorials/tutorial-two-javascript)

### 【ACK 与 Lease 都是在回答任务所有权什么时候结束】

不同系统可能分别使用 ACK / NACK、Visibility Timeout / Lease、数据库 Lock / locked_until / Status Transition。实现不同，但共同问题是：Worker 获得任务以后，系统怎样判断它仍在处理、已经成功，还是已经失联并允许其他 Worker 再次处理。

### 【多个 Worker 需要协调同一批待处理任务】

~~~text
Ready Jobs
   ↓
Claim Coordination
   ↓
Worker A / Worker B / Worker C
~~~

协调目标包括避免所有 Worker 阻塞在同一任务、控制并发量，以及让失联任务最终重新可领取。具体方案可能由 Broker、Lease、数据库行锁或其他协调机制实现。

## 4. 任务状态机描述一次异步工作的完整生命周期

### 【正常路径和失败路径共同组成任务生命周期】

~~~text
Queued
  ↓
Running
  ↓
Succeeded

Running
  ↓
Failed
  ↓
Retryable?
├── Yes → Backoff → Ready
└── No / Retry Exhausted → Terminal Failure
~~~

任务状态机让系统明确知道任务当前处于什么阶段，而不是只保存一条“有个任务”的记录。

### 【Worker Crash 需要由超时、Lease 或 Redelivery 恢复】

~~~text
Worker Claim
↓
Running
↓
Worker Crash
↓
没有成功确认
↓
Lease Timeout / Redelivery / Recovery Scan
↓
Task 再次可处理
~~~

如果系统没有这条恢复路径，Running 状态可能永久卡住。

### 【Dead Letter 或 Terminal Failure 是自动处理链的出口】

~~~text
Task
↓
Retry
↓
Retry Limit Reached
↓
Dead Letter / Terminal Failed State
↓
Inspect / Repair / Replay / Discard
~~~

Dead Letter 不只是“另一个 Retry Queue”，而是正常自动处理已经无法继续后的失败事实保存与恢复入口。至少需要能够关联 Task ID、Failure Reason、Attempt Count、Timestamp 和 Trace / Correlation Context。

## 5. Retry、Backoff 与 Idempotency 共同保证失败恢复

### 【失败首先需要判断是否具有重试价值】

~~~text
Failure
│
├── Transient
│   ├── Network Timeout
│   ├── Temporary Unavailable
│   └── Rate Limit
└── Permanent / Business Failure
    ├── Invalid Input
    ├── Permission Denied
    └── Permanent Conflict
~~~

Transient Failure 通常才适合进入 Retry；Permanent Failure 应进入明确的 Failed / Conflict / Manual Handling 状态。真实分类必须结合业务和远端协议。

### 【Retry 是 Policy 而不是简单循环】

Retry Policy 至少需要回答 When to Retry、How Many Attempts、How Long to Retry、Backoff、Maximum Delay、Server Retry Hint。Google Cloud Tasks 的 RetryConfig 将 maxAttempts、maxRetryDuration、minBackoff、maxBackoff、maxDoublings 等作为独立配置。[[3]](https://cloud.google.com/tasks/docs/reference/rest/v2/RetryConfig)

### 【Backoff 防止失败任务持续冲击故障系统】

Exponential Backoff 常用于逐渐拉大尝试间隔；Jitter 可以避免大量 Client 在相同时间点同时重试。服务端返回 Retry-After 等信息时，也可以作为下一次尝试时间的输入。

### 【可重试系统必须考虑重复执行】

~~~text
Worker
↓
Remote Side Effect 已成功
↓
Worker 在记录 Success 前崩溃
↓
Task 被再次投递
↓
同一业务操作再次执行
~~~

因此 Retry / Redelivery → Duplicate Execution Risk → Idempotency。

幂等（Idempotency）关注同一个逻辑操作被重复提交时，系统能否避免产生不应重复的业务副作用。幂等键、唯一约束、已处理记录和业务状态检查都是可能的实现手段。

### 【Delivery Guarantee 不能直接等价为业务副作用只发生一次】

消息系统对 Delivery 的保证与业务 Side Effect 的实际执行语义不是同一层。入门阶段更稳妥的工程模型是“任务可能重新交付 → 业务处理考虑重复 → Idempotent Consumer / Operation”，而不是把 Exactly Once 简化成整个分布式业务绝对不会重复执行。

## 6. Transactional Outbox 连接数据库事务与异步任务

### 【Database Write 与 Message Publish 会产生 Dual Write Problem】

~~~text
BEGIN
↓
INSERT order
↓
COMMIT
↓
Publish OrderCreated
~~~

如果 Database Commit 成功后 Process Crash，就会出现 Order 已存在但 Message 未发布；反过来先 Publish、后 Commit，也可能出现 Message 已被下游看到而 Database 最终 Rollback。

真正的问题是 Database Write + Message / Task Creation 属于两个独立系统时，怎样维持业务一致性。

### 【Transactional Outbox 先把业务数据和待发布事实放入同一本地事务】

~~~text
Database Transaction
│
├── Business Data
└── Outbox Record
        ↓
      COMMIT

Outbox Processor
        ↓
Publish / Execute
        ↓
Mark Processed
~~~

AWS 对 Transactional Outbox Pattern 的说明也是：业务对象与 Event / Message 放在同一 Transaction 中保存，再由独立组件把消息发送出去，从而避免业务更新与消息发送之间的 Dual Write 不一致。[[4]](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

Outbox Processor 本身仍可能在“发送成功、标记完成前”失败，因此 Consumer / Operation 仍需考虑重复与 Idempotency。数据库 Transaction 的通用知识见 [数据库完整框架体系](./数据库完整框架体系.md)。

### 【Outbox 是一致性模式，不等于某一种 Queue 产品】

Outbox Record 可以由 Polling Worker、CDC 或其他机制继续处理。Transactional Outbox 解决的是“业务状态变化与待发送事实怎样可靠地一起落地”，并不规定后续必须使用哪一种 Broker。

## 7. 异步处理进入生产环境后还需要并发控制与可观测性

### 【并发度需要同时考虑吞吐和下游承载能力】

~~~text
More Workers
↓
Potential Higher Throughput
↓
More DB / API / CPU Pressure
~~~

Worker Concurrency 需要结合任务耗时、数据库连接、远端 Rate Limit、CPU / Memory 和队列增长速度调整。当 Producer 持续快于 Consumer 时，Queue Depth 与等待时间会增长，需要通过 Concurrency Control、Rate Limit、Backpressure 或容量扩展恢复平衡。

### 【异步系统需要观察任务结果而不只是进程是否存活】

| 维度 | 典型信号 |
| --- | --- |
| Backlog | Queue Depth、Oldest Job Age |
| Latency | Queue Wait、Processing Duration、End-to-end Latency |
| Reliability | Success Rate、Failure Rate、Retry Count、Dead Letter Count |
| Worker | Active Workers、Concurrency、Lease Timeout |
| Traceability | Task ID、Correlation ID、Trace / Span、Failure Reason |

### 【项目实践一：PostgreSQL-backed Job Queue】

仓库 ios-plan-checkin/apps/worker/src/planReminders.ts 是 Database-backed Job Queue 的真实实现案例：

~~~text
worker_jobs
↓
dedupe_key + ON CONFLICT DO NOTHING
↓
run_after <= now()
↓
FOR UPDATE SKIP LOCKED
↓
status = running
↓
attempts + 1
↓
locked_until
↓
Execute
↓
succeeded / failed
↓
run_after = next retry time
~~~

PostgreSQL 官方说明，SKIP LOCKED 会跳过无法立即获得锁的 Row，它不适合一般一致性查询，但可用于多个 Consumer 访问 queue-like table 时减少 Lock Contention。[[5]](https://www.postgresql.org/docs/18/sql-select.html)

这说明通用 Job Lifecycle 可以使用 PostgreSQL Row Lock + Status + Lease 实现，而不是“Queue 必须使用 PostgreSQL”。

### 【项目实践二：移动端 Durable Outbox 与失败分类】

仓库 ios-plan-checkin/apps/mobile/src/data/outboxRunner.ts 提供另一个真实映射：

~~~text
Durable Local Outbox
↓
claimNextOperation
↓
send
↓
acknowledgeOperation
~~~

失败时区分 Network / 429 / 5xx → Retry，409 CHECKIN_CONFLICT → Conflict State，其他 Client Error → Failed；Retry Delay 使用 Exponential Backoff + Jitter，并把 Retry-After 作为下限。

这些状态和 HTTP 分类属于该项目的工程设计，不应直接泛化成所有系统的固定规则。
