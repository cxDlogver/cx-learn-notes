# Git分支操作、发布流程及CI/CD相关面试笔记（完整版）

## 基于main分支代码改进的操作流程

### 一句话结论

先拉取并同步当前main分支的最新代码，然后基于main分支新建一个开发分支，在该分支上完成改动，最后通过合并请求将改动合并回main分支。

**对应问题**：想在当前main分支的版本代码基础上进行改进，正确的操作流程是什么？

### 标准面试回答

若要基于当前main分支的代码做改进，需遵循规范的分支协作流程，避免直接操作main分支，具体步骤如下：

1. 切换到main分支：确保当前操作的是main主干分支，命令为`git checkout main`（新版本Git可使用`git switch main`）。

2. 拉取远程最新代码：同步远程main分支的最新变更，确保本地main分支与远程保持一致，避免基于落后版本开发，命令为`git pull origin main`。这一步是核心，能有效减少后续合并冲突。

3. 基于main分支新建开发分支：从最新的main分支切出独立的功能分支，用于隔离开发改动，分支命名需规范（如feature/功能名称、optimize/优化内容），命令为`git checkout -b feature/xxx`（新版本可使用`git switch -c feature/xxx`）。

4. 在新分支上开发改进：在新建的功能分支上完成代码编写、调试等操作，所有改动均在该分支上进行，不影响main分支的稳定性。

5. 提交本地改动：开发完成后，提交本地代码到功能分支，命令依次为`git add .`（添加所有改动文件）、`git commit -m "feat: xxx"`（提交说明需规范，明确改动内容）。

6. 推送远程功能分支：将本地功能分支推送到远程仓库，供团队评审和协作，命令为`git push origin feature/xxx`。

7. 发起合并请求：在Git平台（GitHub/GitLab）上发起合并请求（PR/MR），申请将功能分支的代码合并到main分支，经过代码评审通过后，完成最终合并。

### 常见命令流程（可直接背诵）

```bash
# 1. 切换到main分支
git checkout main
# 2. 拉取远程最新代码
git pull origin main
# 3. 新建并切换到功能分支
git checkout -b feature/optimize-homepage
# 4. 开发完成后，提交代码
git add .
git commit -m "feat: optimize homepage performance"
# 5. 推送远程功能分支
git push origin feature/optimize-homepage
# 6. 后续在Git平台发起PR/MR，合并到main
```

### 高频追问点：为什么不建议直接在main分支上修改？

这是面试官重点关注的问题，核心原因的是保障main分支的稳定性和团队协作安全，具体如下：

- main分支是主干分支，通常代表可发布、稳定的版本，是团队协作的基线，直接修改会增加版本不稳定的风险。

- 不利于代码隔离：新功能开发、bug修复、实验性修改需隔离在独立分支，避免不同改动互相影响，降低开发风险。

- 不方便协作和审核：直接修改main分支，团队成员无法清晰查看改动范围，难以开展Code Review，出问题后回滚也不够灵活。

- 容易污染主干历史：多人协作时，main分支需保持整洁、稳定，直接修改会导致提交历史混乱，不利于版本追溯。

**对应问题**：为什么不建议直接在main分支上进行代码改进？核心原因有哪些？

### 面试加分点

若开发周期较长，需定期将main分支的最新变更同步到功能分支，减少后续合并冲突，具体命令流程如下：

```bash
# 1. 切换到main分支，拉取最新代码
git checkout main
git pull origin main
# 2. 切换回功能分支，合并main分支的变更
git checkout feature/optimize-homepage
git merge main
# 或使用rebase（根据团队规范选择）
git rebase main
```

**对应问题**：若开发周期较长，如何避免功能分支与main分支产生大量合并冲突？

## 分支修改完成后的发布流程

### 一句话结论

分支开发完成后，先提交代码并推送远程分支，再发起合并请求（PR/MR），经评审、测试和CI校验后合入主干，最后通过CI/CD流程部署上线。

**对应问题**：在分支上修改完最新版本代码后，如何发布上线？

### 标准面试回答

分支开发完成后，不建议直接从开发分支发布线上，需遵循“代码合并→校验→部署”的规范流程，确保上线版本稳定，具体步骤如下：

1. 提交本地代码：确认开发完成后，将本地改动提交到功能分支，命令为`git add .`、`git commit -m "feat: xxx"`，确保提交说明清晰，便于后续版本追溯。

2. 推送远程分支：将本地功能分支推送到远程仓库，让团队成员可查看改动、参与评审，命令为`git push origin feature/xxx`。

3. 发起PR/MR：在Git平台（GitHub/GitLab）上发起合并请求，指定目标分支（通常是main、develop或release分支，具体看团队分支管理策略），提交评审申请。

4. 代码评审与自动化校验：这是核心环节，需完成两部分验证：一是团队成员进行Code Review，检查代码质量、逻辑合理性；二是触发CI流程，自动执行lint检查、单元测试、构建验证，确保代码可正常运行、无语法错误。若有问题，需在功能分支上修改后重新提交推送。

5. 合并到目标分支：评审通过、CI校验通过后，将功能分支合并到目标分支（如main），完成代码集成。

6. CI/CD流水线部署：合并到目标分支后，通常会自动触发CD流程，完成构建产物生成、部署到测试/预发/生产环境，最终实现上线。

### 常见命令流程（可直接背诵）

```bash
# 1. 提交本地改动
git add .
git commit -m "feat: optimize login logic"
# 2. 推送远程功能分支
git push origin feature/optimize-login
# 3. 后续在Git平台发起PR/MR，合并到目标分支
# 4. 合并后由CI/CD流水线完成部署，无需手动执行发布命令
```

### 高频追问点

#### 追问1：能不能直接从功能分支发布上线？

可以，但不推荐，核心原因如下：

- 功能分支通常未经过完整测试和评审，稳定性无法保证，直接发布易引发线上故障。

- 不利于团队统一管理发布版本，发布记录和回滚管理不够清晰，后续排查问题难度大。

- 规范做法：功能分支开发→合并到主干/发布分支→统一经过测试、校验后发布。

#### 追问2：发布一定是合到main分支吗？

不一定，取决于团队的分支管理策略，常见两种情况：

- 小团队/简单项目：功能分支直接合并到main分支，然后从main分支发布上线，流程简单高效。

- 规范团队/复杂项目：通常有多类分支分工，功能分支先合并到develop（日常集成分支），再从release（发布准备分支）合并到main，最终从main分支发布，确保上线版本经过充分集成和测试。

#### 追问3：发版前main分支有新变更，该如何处理？

需先同步main分支的最新变更到功能分支，减少合并冲突，具体操作如下：

```bash
# 1. 切换到main分支，拉取最新代码
git checkout main
git pull origin main
# 2. 切换回功能分支，合并main分支变更
git checkout feature/xxx
git merge main
# 或使用rebase（推荐，保持提交历史整洁）
git rebase main
# 3. 解决冲突、测试通过后，重新推送分支并发起PR/MR
```

#### 追问4：发布和Git分支操作的关系是什么？

Git负责版本管理和代码合并，解决“代码如何集成”的问题；发布负责构建、部署，解决“代码如何上线”的问题，二者是两个独立但关联的环节：Git合并是发布的前提，发布是Git合并后代码落地到线上的后续流程，实际项目中发布通常依赖CI/CD流水线自动完成，而非手动操作。

**对应问题**：发布和Git分支操作的核心关系是什么？为什么不推荐直接从功能分支发布？

### 面试精简版回答

我会先在功能分支提交并推送代码，然后发起PR/MR，经过代码评审、CI校验后合并到主干或发布分支，最后由CI/CD流水线完成测试、预发和生产环境部署。规范流程下，不建议直接从个人开发分支发布，避免版本不稳定。

## 发布后发现问题的回滚方法

### 一句话结论

发布后有问题，优先通过部署平台回滚线上稳定版本止损；Git层面，对已合入远程主干的提交，优先用`git revert`撤销改动，避免使用`git reset`改写公共历史。

**对应问题**：发布后发现线上有问题，该如何回滚？Git层面有哪些常用方法？

### 标准面试回答

发布后发现问题，需先判断问题严重程度，优先保障业务稳定，再处理代码层面的回滚，具体分为“发布层面回滚”和“Git层面回滚”两类方式：

#### 一、发布层面的回滚（优先选择）

这是实际项目中最常见的回滚方式，核心是“快速恢复线上稳定版本”，无需修改Git历史，具体操作：

通过CI/CD部署平台，直接回滚到上一个稳定的构建版本、Docker镜像或发布包，重新部署上线。例如：回滚前端静态资源到上一版本、回滚后端服务镜像到上一稳定版。

优点：恢复速度快、风险小，能快速止损，适合线上严重故障（如核心功能不可用、大量用户受影响）；缺点：仅解决线上版本问题，未处理Git仓库中的问题代码。

#### 二、Git层面的回滚（处理代码仓库问题）

若需从代码仓库中撤销问题提交，根据提交是否已共享（推送到远程、被他人拉取），选择不同方法，核心原则：不破坏公共分支的提交历史。

##### 方法1：git revert（推荐，适合公共分支）

核心作用：新增一个“反向提交”，抵消原有问题提交的改动，不删除原有提交历史，对团队协作无影响。

常用命令：

```bash
# 撤销指定提交（最常用）
git revert <commit_id>
# 撤销最近一次提交
git revert HEAD
# 撤销多个连续提交（区间回滚）
git revert old_commit^..new_commit
# 撤销merge提交（需指定主线，-m 1表示以第一个父提交为主线）
git revert -m 1 <merge_commit_id>
```

优点：不改写提交历史，安全可靠，适合已推送到远程、被他人拉取的公共分支（如main）；缺点：会新增提交记录，若需撤销多个连续提交，操作相对繁琐。

##### 方法2：git reset（不推荐用于公共分支）

核心作用：直接移动分支指针，回退到某个旧提交，本质是“删除”后续的提交记录，会改写提交历史。

常用命令：

```bash
# 硬回滚到指定提交（彻底删除后续提交，本地使用）
git reset --hard <commit_id>
# 若已推送到远程，需强推（风险极高，谨慎使用）
git push -f origin main
```

优点：回退直接、操作简单，适合本地分支或未共享的远程分支；缺点：改写提交历史，强推可能覆盖他人提交，风险极高，严禁用于main等公共主干分支。

### 实际项目常见处理流程

1. 判断问题严重程度：若为严重线上故障（如核心功能异常、数据错误），优先执行发布层面回滚，快速恢复业务。

2. 定位问题提交：找到导致线上故障的具体提交记录（通过Git日志、监控日志）。

3. 处理Git代码：若问题提交已合入main分支，用`git revert`撤销改动；若仅在本地或未共享分支，可使用`git reset`回退。

4. 修复与重新发布：在功能分支修复问题，测试通过后，重新走PR/MR合并流程，再次发布上线。

### 高频追问点

#### 追问1：git revert和git reset的本质区别是什么？

- `git revert`：新增反向提交，不改写历史，适合公共分支，安全无风险，会保留问题提交记录，便于追溯。

- `git reset`：移动分支指针，改写历史，可能丢失提交记录，适合本地或未共享分支，风险高，不适合公共分支。

#### 追问2：一次发布包含多个提交，如何回滚？

有两种方式，优先选择更安全的方案：

- 方案1：逐个revert，依次撤销每个问题提交，命令为`git revert <commit1>`、`git revert <commit2>`，适合提交数量少、改动独立的场景。

- 方案2：区间revert，用`git revert old_commit^..new_commit`撤销一段连续提交，适合提交数量多、属于同一功能的场景。

- 实际项目中，若影响范围大，更倾向于直接回滚部署版本，比逐个处理Git提交更快。

#### 追问3：线上紧急问题，除了回滚还有其他处理方式吗？

可以采用“回滚+修复并行”的方式：一边通过部署平台回滚到上一稳定版本，保障业务正常；一边拉取hotfix（紧急修复）分支，定位并修复问题，测试通过后紧急发布，再将修复代码同步回main分支。

**对应问题**：git revert和git reset的核心区别是什么？一次发布包含多个提交时，如何实现Git回滚？

### 面试精简版回答

发布后有问题，先判断影响范围：严重故障优先回滚线上部署版本，快速止损；Git层面，已合入远程主干的提交用`git revert`撤销，避免改写历史，适合团队协作；`git reset`仅用于本地或未共享分支。修复问题后，重新走发布流程上线。

## PR、MR、CI、CD的概念及区别

### 一句话结论

PR/MR解决代码评审与分支合并问题，属于代码协作流程；CI/CD解决代码提交后的自动化验证、构建、部署问题，属于工程自动化流程，二者协同完成“开发→合并→上线”的全链路。

**对应问题**：PR、MR、CI、CD的概念是什么？它们之间的区别和联系是什么？

### 核心概念详解

#### 1. PR（Pull Request）

PR即拉取请求，是GitHub平台的常用叫法，核心作用是：开发者在自己的分支开发完成后，请求将分支代码合并到目标分支（如main、develop）。

核心特点：既是代码合并申请，也是代码评审入口，包含改动差异（diff）、评论讨论、评审意见等，只有评审通过后，才能完成合并，确保代码质量。

示例：从`feature/login`分支发起PR，请求合并到main分支，团队成员查看改动、提出评审意见，修改通过后合并。

#### 2. MR（Merge Request）

MR即合并请求，是GitLab平台的常用叫法，本质上与PR功能完全一致，核心作用也是请求将某个分支的代码合并到目标分支。

核心区别：仅命名不同，源于不同Git平台的习惯，GitHub常用PR，GitLab常用MR，实际使用中可互换理解。

#### 3. CI（Continuous Integration，持续集成）

CI即持续集成，核心是“频繁提交代码，自动完成集成校验”，开发者每次提交代码（或发起PR/MR）后，系统自动执行一系列校验操作，尽早发现问题。

CI常见操作：自动安装依赖、执行lint检查（代码规范校验）、运行单元测试、静态代码分析、构建项目，确保代码可正常运行、无语法错误、符合团队规范。

示例：前端项目CI流程，自动执行`pnpm install`、`pnpm lint`、`pnpm test`、`pnpm build`，若任意一步失败，PR/MR无法合并。

核心目的：避免代码合入主干后才发现问题，减少集成风险，提升开发效率。

#### 4. CD（Continuous Delivery / Continuous Deployment，持续交付/持续部署）

CD 在面试中需要区分 Continuous Delivery 与 Continuous Deployment。Continuous Delivery 的核心是通过可重复的 Build、Test、Environment Verification 与 Release Process，让变化持续保持可安全发布状态；生产 Release 可以保留显式人工或业务 Gate。Continuous Deployment 则把通过既定 Gate 的变化继续自动推进到 Production。完整定义、Artifact / Release / Deployment 边界与 Pipeline 模型统一见 [软件交付与 CI/CD 工程体系](./R-软件交付与CI-CD工程体系.md)。

### 核心区别与联系

#### 区别

- PR/MR：聚焦“代码协作与合并”，解决“谁来合并、怎么合并、合并前如何审核”的问题，属于Git分支管理流程。

- CI/CD：聚焦“自动化验证与部署”，解决“代码是否合格、如何自动构建、如何自动上线”的问题，属于工程自动化流程。

#### 联系

二者协同构成完整的开发上线链路，流程如下：

1. 开发者在功能分支开发，提交代码并推送远程。

2. 发起PR/MR，请求合并到目标分支。

3. PR/MR 同时进入 Human Review 与 Automated CI Checks；两者都可以成为 Merge Gate 的组成条件，具体强制规则和先后关系由团队策略决定。

4. Review 与 Required Checks 满足仓库规则后，合并到目标分支。

5. 后续 Pipeline 继续使用经过验证的 Artifact 进入 Release / Deployment / Production Verification；具体是否自动进入生产取决于 Continuous Delivery / Continuous Deployment 策略。

### 高频追问点

#### 追问1：PR和MR有本质区别吗？

没有本质区别，核心功能完全一致，均为“代码合并请求+评审入口”，仅命名不同，源于不同Git平台：GitHub常用PR，GitLab常用MR。

#### 追问2：CI和CD的核心区别是什么？

CI的重点是“集成验证”，关注代码提交后是否合格（能否构建、测试是否通过）；CD的重点是“交付部署”，关注合格的代码如何自动落地到线上环境，核心区别是CI解决“代码能不能用”，CD解决“代码怎么上线”。

#### 追问3：持续交付和持续部署的区别是什么？

核心区别在于“上线是否需要人工确认”：持续交付需人工确认后才能上线，持续部署无需人工干预，自动上线，二者均基于CI通过后的可部署产物。

#### 追问4：前端项目中，CI/CD具体会做哪些操作？

前端CI流程：安装依赖（`pnpm install`）、代码规范校验（`pnpm lint`）、单元测试（`pnpm test`）、构建项目（`pnpm build`）、生成静态资源产物。

前端CD流程：将构建后的dist目录上传到CDN/OSS、部署到Nginx服务器、更新Docker镜像、推送至生产环境，完成静态资源上线。

**对应问题**：持续交付和持续部署的核心区别是什么？前端项目中CI/CD具体会执行哪些操作？

### 面试精简版回答

PR和MR本质都是代码合并请求，用于分支协作和Code Review，仅平台命名不同（GitHub叫PR，GitLab叫MR）。CI是持续集成，代码提交后自动执行lint、测试、构建，确保代码合格；CD是持续交付/持续部署，CI通过后自动完成交付或部署，区别在于是否需要人工确认。PR/MR管代码合并，CI/CD管自动验证和发布，协同完成开发上线全流程。

## 代码合并后到部署上线的完整流程

### 一句话结论

代码合并后，依次经过CI校验、构建产物、部署测试/预发环境、验证通过、发布审批、部署生产环境，最后完成发布后监控与异常回滚，形成完整的上线闭环。

**对应问题**：代码合并到主干后，到最终部署上线需要经过哪些流程？

### 标准面试回答

代码合并到主干分支（如main）后，并不意味着直接上线。典型交付链会继续经过“自动化校验 → Build Artifact → 环境验证 → Release Gate → Deployment → Production Verification / Recovery”。下面保留的是面试场景下的一种常见实现，不应理解为所有团队唯一的固定顺序；完整通用模型见 [软件交付与 CI/CD 工程体系](./R-软件交付与CI-CD工程体系.md)。

#### 1. 触发CI流程（自动校验）

代码合并到主干后，自动触发CI流水线，核心目的是验证代码质量和可运行性，常见操作如下：

- 拉取主干最新代码，自动安装项目依赖（如前端`pnpm install`、后端`maven install`）。

- 执行代码规范校验（lint检查），确保代码符合团队规范，无语法错误。

- 运行单元测试、集成测试，验证代码逻辑正确性，避免功能异常。

- 执行项目构建，生成可部署产物（前端dist目录、后端jar包、Docker镜像）。

若CI流程失败（如测试不通过、构建失败），需修复问题后重新提交合并，再触发CI校验。

#### 2. 生成可部署产物

CI校验通过后，系统自动生成可部署的产物，不同项目类型产物不同：

- 前端项目：dist目录（包含HTML、CSS、JS、图片等静态资源）、Docker镜像。

- 后端项目：jar包、war包、Docker镜像。

产物会被存储到指定仓库（如Docker仓库、静态资源仓库），供后续部署使用。

#### 3. 部署到测试环境

构建产物生成后，首先部署到测试环境，核心目的是验证功能完整性和兼容性，常见操作：

- 前端：将dist目录部署到测试环境Nginx，或上传到测试环境CDN，配置测试环境接口地址。

- 后端：部署jar包或Docker镜像，连接测试环境数据库、缓存等中间件。

测试环境验证内容：页面能否正常访问、路由是否正常、接口联调是否顺畅、功能是否符合需求、是否有白屏、资源404等问题。

#### 4. 测试与验收验证

部署到测试环境后，进入验证环节，确保代码“能用、好用”，常见验证流程：

- 开发自测：开发人员验证自己的改动是否符合预期，修复测试环境中发现的小问题。

- QA测试：测试人员进行全面回归测试，验证功能完整性、边界场景、兼容性（如浏览器、设备）、性能、安全等。

- 产品验收：产品人员验证功能是否符合需求文档，确认交互、UI等符合设计要求。

若验证发现问题，需回到功能分支修复，重新提交合并，再次触发后续流程。

#### 5. 部署到预发环境（可选，规范团队必备）

预发环境与生产环境配置完全一致（如数据库、CDN、网关、域名），核心目的是模拟线上真实场景，验证上线流程和配置正确性，常见验证内容：

- 环境配置验证：CDN缓存、网关路由、接口权限、跨域配置等是否正常。

- 发布流程验证：部署流程是否顺畅，产物是否能正常运行，无环境适配问题。

- 关键链路验证：核心业务流程（如登录、支付）是否正常，避免因环境差异导致线上故障。

#### 6. 发布审批（可选，规范团队必备）

预发环境验证通过后，进入发布审批环节，确保上线动作可控，常见审批内容：

- 确认发布时间窗口（避开业务高峰，如电商平台避开下单高峰）。

- 确认改动影响范围、回滚方案，确保出现问题能快速止损。

- 确认相关人员（开发、测试、运维）在场，应对上线过程中的突发情况。

- 提交发布单/变更单，经负责人审批通过后，进入正式部署环节。

#### 7. 部署到生产环境

审批通过后，正式部署到生产环境，不同项目部署方式不同，核心是“替换线上旧版本，确保服务不中断”：

- 前端：将构建产物上传到生产环境CDN/OSS，更新Nginx配置，清理缓存，确保用户能访问到新版本。

- 后端：采用滚动部署、蓝绿部署或灰度部署，避免服务中断，部署完成后验证服务可用性。

#### 8. 发布后验证与监控

部署完成后，并非结束，需进行发布后监控，确保线上版本稳定，常见操作：

- 人工冒烟测试：验证核心功能（如登录、首页访问）是否正常，无明显故障。

- 监控平台告警：关注系统报错率、接口响应时间、页面加载速度、服务器资源占用等指标，若出现异常及时告警。

- 日志检查：查看线上日志，排查是否有隐藏错误或异常信息。

- 用户反馈：关注用户反馈渠道，及时响应线上问题。

#### 9. 异常回滚

若发布后发现严重线上问题（如核心功能不可用、大量用户受影响），立即执行回滚操作，快速恢复到上一个稳定版本，再排查问题、修复后重新发布。

### 前端项目上线常见问题（面试加分点）

结合前端项目特点，上线过程中最容易出现的问题及原因：

- 环境变量错误：测试环境与生产环境的接口地址、CDN地址、鉴权配置不一致，导致接口请求失败、资源加载异常。

- 静态资源路径问题：构建后静态资源路径配置错误，导致JS/CSS/图片404，页面白屏。

- 缓存问题：旧版本HTML引用新版本资源，或新版本代码与浏览器缓存不匹配，导致用户无法看到新版本。

- 接口联调问题：测试环境接口正常，但生产环境接口权限、域名、跨域配置不一致，导致接口调用失败。

- 构建异常：CI构建通过，但生产环境运行失败（如SSR项目使用浏览器专属API，导致线上报错）。
