# HTTP 缓存、浏览器缓存与 CDN 共享缓存

HTTP 缓存通过复用已取得的响应，减少重复传输和源站计算。浏览器 HTTP 缓存通常服务于当前客户端；CDN 与启用缓存功能的反向代理属于共享缓存，可以为多个请求者复用响应。**缓存能否复用不仅取决于位置，还取决于是否允许存储、缓存键是否匹配、响应是否新鲜，以及过期后能否验证。** [[1]](https://www.rfc-editor.org/rfc/rfc9111)

> 页面导航会重新发现页面引用的资源，但不代表每次都重新下载。导航和渲染的完整链路见 [Web 渲染架构](./W-Web渲染架构.md)。

## 1. HTTP 缓存通过不同位置的响应副本减少重复请求

本文深入 HTTP 缓存行为和版本管理。其工程优化归属为 [Web 性能优化工程体系的① 网络传输优化](./W-Web性能优化工程体系.md#2-网络传输优化降低连接往返和重复传输成本)：缓存减少重复网络工作，但不会自动消除首次访问的服务端计算或 JS 执行成本。

### 【缓存位置决定复用范围】

浏览器 HTTP 缓存保存浏览器请求得到的 HTTP 响应，通常只供对应客户端的请求复用。CDN（内容分发网络）边缘缓存位于网络侧，按其缓存键与访问策略为多个请求者提供共享响应。反向代理可以只转发请求，也可以按配置承担共享缓存职责；源站负责生成或提供原始响应。

```text
浏览器发起资源请求
  ↓ 浏览器 HTTP 缓存：检查本地响应能否直接复用
若不能复用，发起网络请求
  ↓ 可选 CDN 边缘缓存：检查共享副本
  ↓ 可选反向代理缓存：检查源站前的共享副本
  ↓ 源站：生成或读取响应
响应沿请求路径返回，符合存储规则的缓存可以保存副本
```

图中的 CDN 与反向代理并非所有部署都存在，也不是必然启用缓存。请求首先受浏览器控制，浏览器无法直接复用时才需要网络响应；网络侧是否命中决定是否继续回源。缓存是否真正保存响应，仍由协议规则和部署配置决定。[[1]](https://www.rfc-editor.org/rfc/rfc9111)

### 【浏览器 HTTP 缓存与 CDN 缓存的差异】

| 维度 | 浏览器 HTTP 缓存 | CDN 共享缓存 |
| --- | --- | --- |
| 位置 | 用户浏览器管理的本地响应副本 | 网络边缘节点管理的响应副本 |
| 复用范围 | 通常为当前客户端 | 可为多个请求者复用符合共享条件的响应 |
| 管理主体 | 浏览器实现与 HTTP 响应指令共同决定 | HTTP 规则、CDN 配置及服务商实现共同决定 |
| 主要收益 | 避免重复网络传输 | 降低地域延迟与源站压力 |
| 清除方式 | 浏览器可清除本地数据 | 通常由 CDN 控制台/API 或过期机制处理 |

浏览器清除缓存不会清除 CDN 缓存；CDN 清除缓存也不会自动删除所有浏览器本地副本。缓存位置说明了复用范围，但尚不能决定响应是否允许保存，因此下一步需要判断缓存资格。

## 2. 缓存资格与新鲜度控制决定响应是否可以直接复用

### 【存储资格与共享范围】

HTTP 缓存并非对所有响应都无条件存储。请求方法、状态码、授权信息和缓存指令都会影响存储资格；共享缓存尤其需要避免跨用户复用私人内容。[[1]](https://www.rfc-editor.org/rfc/rfc9111)

- `Cache-Control: no-store`：要求缓存不存储该请求或响应的相关内容；它不是清除历史副本的命令。
- `Cache-Control: no-cache`：可以存储，但未经成功验证不得直接用存储响应满足后续请求；并非“完全不缓存”。
- `Cache-Control: private`：限制共享缓存存储响应，私有缓存仍可在其他条件满足时存储。
- `Cache-Control: public`：显式允许共享缓存存储符合规则的响应，但不覆盖所有其他安全与协议限制。
- 带有 `Authorization` 的请求，默认受到共享缓存复用限制；只有满足规范规定的显式条件才可由共享缓存复用。

涉及身份、个人信息和权限差异的响应，不能仅因为 URL 相同就视为可共享。实际工程还要检查 Cookie、鉴权、缓存键与 CDN 配置。

### 【新鲜度与过期时间】

缓存已存储响应后，需要判断它是否仍然新鲜。`Cache-Control: max-age=N` 定义响应的新鲜度生命周期（秒），`Expires` 则使用绝对时间；存在适用的 `max-age` 时，它优先于 `Expires`。缓存会结合响应时间、`Date`、`Age` 等计算当前年龄，不能简单把每次命中都当作重新获得完整有效期。[[1]](https://www.rfc-editor.org/rfc/rfc9111)

`s-maxage` 为共享缓存指定新鲜度期限，并在共享缓存中优先于 `max-age` 或 `Expires`；浏览器私有缓存不按它覆盖自己的 `max-age`。

```http
Cache-Control: public, max-age=600, s-maxage=3600
```

这个响应在其他条件允许时，浏览器可以使用 600 秒的新鲜度期限，共享缓存可以使用 3600 秒。示例只说明不同缓存的有效期，并不保证响应一定被存储或命中。

### 【强缓存与过期响应】

前端常说的“强缓存”，通常指已有副本仍新鲜时直接复用，无须为该次复用发送验证请求。过期响应一般不能无条件复用，但在明确允许的条件下可以使用过期副本，例如 `stale-while-revalidate` 允许在指定窗口内提供过期响应并异步重新验证。[[1]](https://www.rfc-editor.org/rfc/rfc9111) [[3]](https://www.rfc-editor.org/rfc/rfc5861)

`immutable` 表示新鲜期内响应内容不会变化，支持该扩展的客户端可以避免不必要的重新验证；它不保证任何刷新操作都绝不会联网。[[4]](https://www.rfc-editor.org/rfc/rfc8246)

新鲜度解决“能否直接使用”的问题；一旦需要确认资源是否变化，就进入条件请求。

## 3. 条件请求通过验证器避免重复传输完整响应

### 【ETag 与 Last-Modified】

`ETag` 是服务端为选定表示提供的实体标签，不必理解为全局唯一文件 Hash；`Last-Modified` 表示服务端声明的最后修改时间。客户端可以在后续请求中分别使用 `If-None-Match`、`If-Modified-Since` 发起条件请求。[[2]](https://www.rfc-editor.org/rfc/rfc9110)

```http
GET /app.js HTTP/1.1
If-None-Match: "v2"
If-Modified-Since: Wed, 07 Oct 2026 10:00:00 GMT
```

对于同时存在这两个条件的请求，接收方必须忽略 `If-Modified-Since`，以 `If-None-Match` 的规则判断；它们不是必须同时满足的两个独立条件。[[2]](https://www.rfc-editor.org/rfc/rfc9110)

### 【304 与 200 的处理链路】

```text
已有响应需要重新验证
  ↓ 发送条件请求
验证结果仍匹配 → 304 Not Modified：不重传完整表示，更新可用缓存元数据
验证结果不匹配 → 200 OK：传回新表示，按缓存规则更新副本
```

这里的“协商缓存”是对条件请求和缓存验证的常见工程称呼，不代表它与新鲜度缓存是两套互斥存储系统。条件请求也可能由共享缓存转发或处理。若没有可用的旧响应，客户端通常需要取得完整表示。

## 4. CDN 与多级共享缓存减少回源，但不保证每次请求命中

### 【命中、未命中与回源】

以 `https://cdn.example.com/app.js` 为例：浏览器先判断是否有可直接复用的本地响应；需要联网时，CDN 按缓存键和策略查找副本。命中且允许复用则返回，未命中或需要回源验证则向上游请求；上游可能是另一层代理，也可能是源站。

CDN 缓存命中可以减少源站压力与跨地域延迟，但并不意味着所有用户一定连接到物理距离最近的节点，也不保证每次请求都更快。反向代理只在启用相应缓存配置后才是缓存层。代理与公开入口的完整职责见 [反向代理与 Web 入口体系](./F-反向代理与Web入口体系.md)。

### 【缓存键与响应变体】

缓存键通常至少涉及目标资源标识，但 CDN 还可能按查询参数、请求头等配置划分副本。HTTP 的 `Vary` 响应头要求缓存复用时考虑指定请求头是否匹配，例如内容编码差异；它并不意味着所有 CDN 会自动把任意业务身份字段纳入安全的缓存键。[[1]](https://www.rfc-editor.org/rfc/rfc9111)

```http
Vary: Accept-Encoding
```

若同一 URL 会因登录用户或权限返回不同内容，应优先采用明确的私有/禁止存储策略或经过审查的隔离方案，而不是假设共享缓存天然识别用户身份。

### 【源站故障与过期副本】

CDN 节点可能在源站故障时继续提供已有副本，但必须具备可用副本、相应过期复用规则或服务商故障回退策略。使用 CDN 本身不构成高可用保证。可靠性与故障域的进一步判断见 [服务端可靠性体系](./F-服务端可靠性体系.md)。

## 5. 浏览器 HTTP 缓存与可编程存储属于不同机制

浏览器 HTTP Cache 由 HTTP 语义与浏览器实现管理；`localStorage` 属于 Web Storage API，由应用显式读写，不会自动根据 `Cache-Control` 存储 HTTP 响应。Cache Storage 则通过 Cache API 显式保存 Request/Response 对，常与 Service Worker 配合使用。[[5]](https://developer.mozilla.org/en-US/docs/Web/API/Cache) [[6]](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)

Service Worker 可以拦截其控制范围内的请求并自行选择缓存或网络策略，因此“浏览器 HTTP 缓存 → CDN → 源站”只是常见简化路径，不是覆盖所有浏览器应用的固定执行顺序。

存储 API、容量和生命周期见 [浏览器存储方式](./L-浏览器存储方式.md)；SSR、ISR 与 SWR 等页面数据/生成策略见 [Web 渲染架构](./W-Web渲染架构.md)。这些机制可能配合 HTTP 缓存，但不等同于 HTTP 缓存。

## 6. 资源版本与发布顺序决定用户何时发现更新

### 【内容指纹与长期缓存】

构建工具常将内容 Hash 写入资源名，例如 `app.8f3a2.js`。内容变化后资源 URL 变化，可以让新旧资源并存，并为不可变资源配置较长新鲜度：

```http
Cache-Control: public, max-age=31536000, immutable
```

其中 31536000 秒约为一年；长期缓存适用于 URL 随内容变化且旧版本仍可取得的资源。此配置不能保证所有 CDN 自动缓存，也不能保证浏览器刷新时绝不验证。[[1]](https://www.rfc-editor.org/rfc/rfc9111) [[4]](https://www.rfc-editor.org/rfc/rfc8246)

### 【HTML 负责发现新资源版本】

资源 Hash 改变并不会自动通知已经持有旧 HTML 的浏览器。完整更新链路是：

```text
构建新资源并生成新 URL
  ↓ 先确保新资源已发布且可访问
发布引用新 URL 的 HTML
  ↓ 浏览器取得更新后的 HTML
发现新 URL → 请求新资源 → 按规则缓存
```

新资源先可用、旧资源适当保留，可降低部署期间旧页面引用失效资源的风险。未带 Hash 的 HTML 可选择 `Cache-Control: no-cache` 配合验证器，或按敏感性和更新要求选择 `no-store`；不存在“所有 HTML 必须采用同一缓存头”的规则。

缓存失效可以依赖过期、验证、版本化 URL，也可以使用 CDN 提供的主动清除功能。但 CDN 清除不等于浏览器缓存清除。资源优化与构建产物的进一步机制见 [Web 性能优化完整知识体系](./W-Web性能优化完整知识体系.md)。

## 7. 缓存安全、观测与验证约束整个请求及发布过程

安全约束作用于存储资格、共享复用和缓存键，重点防止用户特定响应被其他请求者取得；观测作用于浏览器复用、CDN 命中、回源验证和版本发布，重点验证策略是否真实生效；可靠性约束作用于源站不可用、过期副本与发布回滚。它们是贯穿多个阶段的能力，而非请求中额外固定的一层。

实际验证时应分别观察浏览器 Network 面板中的本地缓存、条件请求及 304，响应中的 `Cache-Control`、`Age`、`Vary`，以及 CDN 提供的命中或回源诊断字段。服务商自定义的 HIT/MISS 等字段并非 HTTP 统一强制字段，不能仅凭一个响应头推断全部链路。

策略选择需要同时回答：资源是否含个人信息、URL 是否随内容变化、浏览器如何发现更新、CDN 是否允许共享、过期时能否验证、源站故障时是否允许提供旧内容。不能单纯追求最长缓存时间或最高命中率。
