## 1. 从传统软件工程到 AI Native 工程化

理解 AI Native 下的工程化设计，首先需要回到传统软件工程中的 **SDLC（Software Development Life Cycle，软件开发生命周期）**。

### 【SDLC -- 软件开发生命周期】

IBM 将 SDLC 定义为一种结构化、迭代式的软件开发方法，它把软件开发拆分成多个**独立、可重复并且相互依赖的阶段**。每个阶段都有自己的目标和交付物，并为后续阶段提供输入。IBM 给出的典型阶段包括 Planning（规划）、Analysis（分析）、Design（设计）、Coding（编码）、Testing（测试）、Deployment（部署）和 Maintenance（维护）。同时，SDLC 还用于协调不同 Stakeholder（利益相关者）的需求、资源和职责，提高开发过程的透明度，并帮助团队提前发现风险。[[1]](https://www.ibm.com/think/topics/sdlc)

因此，从工程角度可以把 SDLC 理解为：

**<u>软件开发不是一次“需求 → 编码”的活动，而是通过一系列相互衔接、能够被管理和验证的工程步骤，把一个业务需求逐步转换成可以交付的软件</u>。**

传统软件工程之所以需要这样的生命周期设计，一个重要原因就是：**软件开发本质上是多人协作完成复杂任务的过程。**

一个需求通常会经过产品、设计、前端、后端、测试、安全、运维等多个角色。如果缺少统一的流程、规范和交付物，每个人就可能按照自己的理解工作。IBM 将 **<u>Improved Project Transparency（提高项目透明度）和 Greater Collaboration（增强协作）明确列为 SDLC 的价值</u>**：通过标准化文档、明确职责和阶段状态，不同参与者能够理解前面的工作、知道自己需要完成什么，并围绕共同目标进行协作。[[1]](https://www.ibm.com/think/topics/sdlc)

因此，传统软件工程化解决的核心问题可以概括为：

> 如何让多个角色按照一套稳定的流程和共同标准协作完成复杂的软件任务，使目标能够持续传递、工作能够明确分工、结果能够被验证、过程能够被追踪、风险能够被控制。

更完整地说，工程化设计是在回答：

> 如何把一个最初可能比较模糊的业务问题，逐步转换最终可以安全上线的版本。

---

### 【AI-DLC -- AI Native 下的工程化设计】

到了 **AI Native（AI 原生）**环境以后，传统的软件生命周期并没有消失。真正发生变化的是：

> **AI/Agent 开始从一个局部的编码辅助工具，逐渐成为整个软件研发过程中的执行者。**

Amazon 在 2026 年对 **AI-native software development（AI 原生软件开发）**的总结非常直接：

> “AI-native software development treats AI as the foundation of how software is built.”

也就是把 AI 看作**软件如何被构建的基础**，并由越来越强的 Agent 在人的专业指导下执行工作，而不只是用 AI 更快地写几段代码。Amazon 对大量团队实践进行总结后还提出了一个非常重要的结论：

> “The workflow matters, not just the tool.”
>
> **即：真正影响结果的并不只是用了什么 AI 工具，而是团队是否围绕 AI 重新设计了整个工作方式。[[2]](https://aws.amazon.com/blogs/machine-learning/how-frontier-teams-are-reinventing-ai-native-development/)**

OpenAI 在《Building an AI-native engineering team》中也指出，当 Coding Agent 可以可靠执行越来越长的多步骤任务以后，工程师的工作开始从大量机械性的实现工作，转向产品行为澄清、架构判断、业务逻辑、性能、安全、工程规范以及最终质量。Agent 则可以承担需求明确情况下的代码实现、重构、测试以及更完整的端到端 Build Task（构建任务）。[[3]](https://cdn.openai.com/business-guides-and-resources/building-an-ai-native-engineering-team.pdf)

于是传统模式：

**<u>人理解需求 → 人设计 → 人编码 → 人测试 → 自动化工具辅助交付</u>**

开始逐渐变成：

**<u>人定义目标和关键约束 → AI/Agent 承担大量分析和执行 → 自动化体系持续验证 → 人处理关键判断、风险和最终放行。</u>**

AWS 把这种新的研发方式进一步概括成 **AI-DLC（AI-Driven Development Life Cycle，AI 驱动开发生命周期）**。

AI-DLC 的一个核心原则就是：

> “AI Powered Execution with Human Oversight”--AI 执行，人工监督。

AI 可以生成计划、主动寻找需求中的不确定问题、请求澄清并执行方案，但是重要的业务和技术决策仍然交给人。与此同时，AI 不再只存在于 Coding 阶段，而是贯穿需求形成、系统构建以及运行交付的全过程。[[4]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

所以，AI Native 并没有让传统工程化失去价值。

**<u>当 AI 把代码生成和任务执行的速度大幅提高以后，工程问题逐渐从“能不能把代码写出来”，转向“AI 有没有理解正确、执行是否符合目标、结果能不能被证明，以及出现错误以后能不能快速发现和控制”。</u>**

DORA 2025 的研究把 AI 的作用概括为 **Amplifier（放大器）**：AI 会同时放大一个组织已经存在的优势和问题。成熟的工程体系、平台能力和工作流程可以被 AI 放大；原本存在的流程混乱和工程问题同样可能被放大。[[5]](https://dora.dev/research/2025/dora-report/)

因此，在 AI Native 环境中，工程化设计进一步变成：

> **如何让人和 AI/Agent 在同一套工程规则下协同完成复杂的软件任务，并且在 AI 高速执行的情况下，仍然保持目标一致、团队协作、结果可验证、过程可追溯和风险可控制。**

---

### 【AI Native 开发生命周期的核心主线】

围绕这个目标，可以进一步抽象出四条贯穿整个 AI Native 软件开发生命周期的核心主线：

> **规范、验证、可追溯、风险控制。**

#### <u>1. 规范先行--先确定“应该做什么”</u>

传统研发依靠人完成大量上下文补充。

一份 PRD 即使没有写完整，产品、研发和测试仍然可以通过会议、聊天、历史经验来补充信息。

但是，当任务越来越多地交给 Agent 执行时，很多过去存在于人脑中的隐式信息必须被转换成 Agent 可以理解的显式规范。

因此 AI Native 工程首先强调：

> **Intent（意图）和 Specification（规范）必须先于代码实现。**

GitHub 的 Spec Kit 就把 **SDD（Spec-Driven Development，规范驱动开发）**的默认过程设计成：

> **Spec → Plan → Tasks → Implement**
>
> 即：
>
> **需求规范 → 技术计划 → 可执行任务 → 实现。**

明确提出，要先 **“Define what to build before building it”**，并要求 Specification 首先描述 **what and why（做什么、为什么做）**，之后再确定技术方案和任务。每一个阶段形成结构化产物，并作为下一阶段的输入，而不是让 Coding Agent 每一次都依赖临时 Prompt 重新理解任务。[[6]](https://github.com/github/spec-kit/blob/main/docs/index.md)

Amazon 在 AI Native 团队实践中也得到了类似结论。其总结的关键实践之一就是：

> **“Make intent explicit before code gets written.”**

也就是在写代码之前先让意图明确，通过详细需求、结构化 Specification 和清晰的 Task Decomposition（任务拆解），让 Agent 知道“完成”到底意味着什么。[[2]](https://aws.amazon.com/blogs/machine-learning/how-frontier-teams-are-reinventing-ai-native-development/)

因此，AI Native 工程中的第一条主线就是：

> **规范先行：先建立稳定的事实来源，再让 AI 执行。**

整个信息链路应该逐渐形成：

> 业务目标 → Requirement Spec（需求规范） → Acceptance Criteria（验收标准） → Technical Plan（技术方案） → Task（任务） → Code（代码）

规范的目的并不是增加文档，而是：

> **明确需求和规范，减少 AI 和不同角色在多阶段协作中的重复理解和自由猜测，让后续所有工作尽量建立在同一个目标上。**

#### <u>2. 验证前置--提前确定“什么算正确”</u>

仅仅告诉 AI “做什么”还不够。

第二个问题是：

> **怎么证明 AI 做出来的东西是正确的？**

如果等代码生成完成以后，再根据代码生成测试，就容易出现一个问题：

需求理解错误 → 代码按照错误理解实现 → 测试又根据错误实现生成 → 所有测试仍然可能通过。

所以：

> **Test Pass（测试通过）并不天然等于 Requirement Correct（符合需求）。**

这也是为什么验证标准需要尽量独立于具体实现，并前置到代码生成之前。

这与 **ATDD（Acceptance Test-Driven Development，验收测试驱动开发）**的思想非常接近。

Agile Alliance 对 ATDD 的定义是：

> 客户/业务、研发和测试等具有不同视角的角色，在实现对应功能之前，共同定义 Acceptance Test（验收测试）。

这些测试一方面描述系统应该表现出的行为，另一方面用于以后证明系统是否按照预期工作。[[7]](https://agilealliance.org/glossary/atdd/) **<u>测试矩阵不仅是后续 AI 实现自动化验收的标准，也是反映 AI 在做前面需求分析和任务规划的时候，是否存在需求理解偏差。</u>**

因此：**Specification 解决：**

> 应该做什么？

而：**Acceptance Test 解决：**

> 什么情况下能够证明它已经做对？

Amazon 对 AI-native 团队的研究同样强调 **Shift Testing Left（测试左移）**：让 Agent 能够在代码进入正式 Pipeline（流水线）之前运行集成测试、组件测试、性能检查以及自动化 Guardrail（防护检查），尽可能提前发现问题。[[2]](https://aws.amazon.com/blogs/machine-learning/how-frontier-teams-are-reinventing-ai-native-development/)

因此第二条主线可以概括成：

> **验证前置：不是代码完成以后才考虑如何测试，而是在开发开始之前就确定“什么算正确”，并让测试和验证标准贯穿整个实现过程。**

最终形成：

> **Requirement → Acceptance Criteria → Test Case → Actual Result → Evidence → Pass / Fail**
>
> 也就是：
>
> **规范告诉 AI 要完成什么，验证负责独立证明它有没有完成。**

#### <u>3. 可追溯--知道每一步为什么产生</u>

AWS 的 AI-DLC 强调保存 Requirements（需求）、Plans（计划）和 Design Artifacts（设计产物），使 AI 在不同阶段和不同 Session（会话）之间能够继续使用之前形成的上下文。[[4]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

因此，在 AI Native 工程中，可以进一步把追溯关系设计成：

Requirement → Scenario → Test Case → Technical Plan → Task → Code Change → Test Result → Release

可追溯的价值不是“留下更多文档”。

它真正解决的是：

> **任何一个结果出现问题时，都能够沿着工程链路向前寻找原因；任何一项代码变化，也能够向后找到它到底服务于什么需求。**

对于 Agent 来说，这一点尤其重要。这时候如果没有稳定的工程产物和关联关系，开发过程会很快失去上下文。

Anthropic 对 Long-running Agent（长任务 Agent）的实验也得到了类似结论。它发现，让 Agent 尝试一次完成整个应用，很容易因为 Context Window（上下文窗口）耗尽而留下“做到一半”的功能，使下一次执行不得不重新猜测之前发生了什么。更稳定的方法是：**每次只推进一个明确的 Feature，并持续保存 Feature List（功能清单）、Progress File（进度文件）和 Git History（代码历史）等结构化产物。** 新的 Agent Session 开始时，先读取这些产物，就可以重新理解当前状态并继续执行，而不需要从头开始。

它有两个核心价值。

第一是 **恢复执行**。

当 Agent 因为上下文限制、异常、工具失败或者 Session 中断而停止时，不需要重新执行整个需求，而是可以根据 Spec、Plan、Task 状态、测试结果和 Git 历史恢复到最近的稳定状态，再从未完成的任务继续执行。Anthropic 的实践中特别强调通过 progress file 和 Git commit 保存状态，使后续 Agent 能快速了解“之前做了什么、现在做到哪里、下一步是什么”，同时可以利用 Git 回退错误修改。

第二是 **审查和持续改进**。

这些产物不仅服务于 Agent，也服务于人。当后续需要 Review、修改需求或者定位问题时，可以沿着：

> **需求 → 方案 → Task → Code → Test**

找到对应关系。因此，可追溯的目的并不是单纯“多留下几份文档”，而是：

> 把长任务执行过程中的关键状态实体化保存下来，使软件研发能够跨阶段、跨 Session 持续推进；任务中断时可以恢复，结果产生后可以审查，需求变化后可以继续演进。

这也是 AI Native 环境下可追溯比传统开发更重要的原因：

**<u>当执行者从一个持续拥有上下文的人，变成可能跨多个 Agent、多个 Session 执行的系统以后，工程产物本身就承担了保存任务上下文和当前真实状态的作用。</u>** 

#### <u>4. 风险控制--AI 执行，但关键决策不能失控</u>

AI Native 并不意味着：

> **AI 从需求开始一直自动执行到生产发布，人完全退出。**

AWS 在 AI-DLC 中明确提出：

> **AI Powered Execution with Human Oversight。**

AI 负责生成计划、请求澄清和执行工作，但 Critical Decisions（关键决策）仍然交给人。[[4]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

OpenAI 在 AI-native engineering 中采用了一套非常清晰的职责划分：

- **Delegate（委托）**：定义明确、风险较低的工作交给 Agent 执行。
- **Review（审查）**：Agent 完成以后，人重点检查设计、性能、安全、迁移风险和业务逻辑。
- **Own（负责）**：新的核心抽象、跨系统架构变化、存在歧义的产品需求以及长期可维护性等高判断任务，仍然由工程师承担责任。[[3]](https://cdn.openai.com/business-guides-and-resources/building-an-ai-native-engineering-team.pdf)

这实际上形成了一种很重要的 AI Native 工程原则：

**<u>自动化程度不应该只由“AI 能不能做”决定，而应该同时由任务的风险、确定性以及结果是否容易验证决定。</u>**

规则明确、错误容易发现、失败容易恢复的工作，可以更多交给 AI。

而需求歧义、权限、安全、核心交易链路、架构变化、不可逆操作以及最终生产发布等错误代价较高的工作，则应该保留 Human-in-the-Loop（人在回路）。

所谓 **Human-in-the-Loop**，可以简单理解为：

> **AI 可以执行过程，但人在关键节点拥有判断、确认或者否决的权力。**

所以，人并不是重新手工执行 Agent 已经完成的所有工作。

这也是风险控制真正解决的问题：

> 不是阻止 AI 自动化，而是在自动化链路中明确哪些节点可以自动通过，哪些节点必须经过人工或者独立质量门禁。

---

在这四条主线之上，就可以形成一套 **AI-Native Software Delivery Lifecycle（AI 原生软件交付生命周期）** 的工程思想：

> 从业务意图开始，通过规范把目标逐渐明确，通过计划和任务把复杂工作转化成 AI 可以执行的工作单元，通过测试和证据持续证明执行结果，通过可追溯的工程产物连接整个生命周期，并在高风险和高不确定性的关键节点保留人工判断和放行，最终把经过验证的软件安全交付到生产环境。

所以，AI Native 下工程化设计的本质可以最终收敛成一句话：

> 软件工程化原本解决的是“如何让多人按照共同规则协作完成复杂软件”；
>
> AI Native 以后，这套协作体系进一步扩展为“如何让人和 Agent 按照同一套规范共同完成复杂软件”，并确保在 AI 高速执行的情况下，整个研发过程仍然保持目标一致、结果可验证、过程可追溯和风险可控制。

这也可以作为后续展开 **需求分析 → 技术分析 → 代码开发 → 测试验收 → 交付上线** 五个阶段的总纲。

## 2. 第一阶段：需求分析

需求分析是软件交付的起点。它的目的不是立即讨论“代码怎么写”，而是在进入技术设计之前，把**为什么做、需要做什么、最终应该呈现成什么样，以及什么情况下算完成**先明确下来。

ISO/IEC/IEEE 29148 对 Requirement（需求）的定义是：

> “statement which translates or expresses a need and its associated constraints and conditions”

即需求是对某种**需要，以及与之相关的约束和条件的表达**。该标准进一步把 Requirements Engineering（需求工程）描述为围绕需求进行发现、获取、开发、分析、验证、确认、沟通、记录和管理的一系列活动。[[8]](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso-iec-ieee%3A29148%3Aed-2%3Av1%3Aen)

因此，需求分析不能只理解成“产品写一份 PRD”。它**<u>实际上是在把一个最初可能比较模糊的业务诉求，逐步整理成产品、设计、研发、测试以及后续 AI Agent 都能够共同理解和执行的需求规范</u>**。

`项目工程化设计.md` 第一阶段可以进一步分为三个部分：

> **需求设计 → UI / UX 设计 → 需求评审**

---

### 【需求设计--明确为什么做、做什么以及什么算完成】

需求设计首先解决的不是技术方案，而是：

> **当前真正需要解决的问题是什么，为谁解决，最终需要实现什么，以及怎样判断这个需求已经完成。**

ISO/IEC/IEEE 29148 对 Requirements Elicitation（需求获取）的定义强调，要通过系统化的方法主动识别并记录 Customer（客户）和 End User（最终用户）的需要；而 Requirements Engineering（需求工程）不仅包括记录需求，还包括分析、验证、确认、沟通和持续管理需求。[[8]](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso-iec-ieee%3A29148%3Aed-2%3Av1%3Aen)

因此，一份完整的需求设计至少应该把以下几类信息逐步明确。

**<u>第一，先定义问题和业务目标。</u>** 需求不能只描述一个表面的解决方案，而应该先说明当前存在什么问题、哪些用户受到影响、为什么值得解决，以及期望达到什么状态。

例如：

**“给字段增加权限控制”**

只是一个功能方案。真正的问题应该进一步明确为：

> 当前部分敏感数据可能被没有授权的用户获取，因此需要建立访问控制，确保只有满足权限要求的用户能够获得真实数据。

这里的重点是先明确 **Problem（问题）**，再决定 Solution（方案）。否则很容易出现“功能完成了，但真正的问题没有解决”的情况。同时还要明确需求的 **<u>Business Goal（业务目标）</u>**，例如降低安全风险、提升运营效率、减少人工成本或者改善用户体验。

**<u>第二，把问题转换成明确的需求规则。</u>** 当目标确定以后，需要进一步描述系统最终应该具备哪些能力，包括正常流程、业务规则、异常情况和必要的非功能要求。

例如权限需求除了“无权限不展示数据”，还应该继续明确：

> 哪些用户有权限、权限由哪个系统判断、无权限时页面如何处理、权限查询失败怎么办、历史数据如何处理，以及是否存在性能、安全、兼容性等额外约束。

这一点在涉及安全和隐私的需求中尤其重要。Microsoft SDL（Security Development Lifecycle，安全开发生命周期）明确强调，安全和隐私需要在项目早期就作为基础要求考虑，因为规划阶段是识别并集成这些要求、同时减少后续改动影响的重要时机。[[9]](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/cc307412%28v%3Dmsdn.10%29)

因此：

> **安全、权限、性能等重要约束，本身就是需求的一部分，而不是等代码完成以后再补充的检查项。**

**<u>第三，在需求设计阶段提前定义验收标准。</u>** 需求不仅需要说明“做什么”，还应该同步明确：

> **什么情况下可以认为这个需求已经完成。**

这就是 Acceptance Criteria（验收标准）。

Agile Alliance 对 ATDD（Acceptance Test-Driven Development，验收测试驱动开发）的定义强调，业务、研发和测试等具有不同视角的角色，应该**在对应功能实现之前共同编写 Acceptance Test（验收测试）**。这些测试既从用户角度描述系统应该如何工作，也用于后续验证系统是否按照预期运行。[[7]](https://agilealliance.org/glossary/atdd/)

这时就形成了：

> **Requirement → Scenario → Acceptance Criteria**

后续技术分析阶段可以继续把这些验收标准展开成完整的 Test Case（测试用例）。这样做的一个重要价值是：

> **测试标准来自需求，而不是代码开发完成以后再根据已有实现反推“什么算正确”。**

**<u>第四，定义需求成功的判断指标。</u>** 对于有明确业务目标的需求，还需要考虑上线以后如何判断需求有没有真正解决原来的问题。

这里可以区分两个层次：

**Delivery Success（交付成功）**关注功能有没有按照要求正确实现；**Business Success（业务成功）**关注上线以后业务问题有没有真正得到改善。

例如运营类产品可以关注使用率、任务完成率、转化率；安全类需求则可以关注未授权访问风险是否消除以及异常访问情况。因此，需求设计最终应该形成一份比较完整的 **Requirement Specification（需求规范）**，至少能够回答：

> **为什么做 → 解决什么问题 → 为谁解决 → 做哪些内容 → 不做哪些内容 → 遵守什么规则 → 什么算完成 → 上线以后如何判断是否有效。**

---

### 【UI / UX 设计--把需求转换成明确的视觉和交互】

当需求涉及页面和用户操作时，仅仅有文字需求还不够，还需要进一步通过 UI / UX Design（用户界面与用户体验设计）明确：

> **用户最终会看到什么，以及用户如何完成整个操作过程。**

UI / UX 设计不只是确定颜色、间距或者按钮位置，而是在进一步表达需求中的状态和行为。例如：

正常状态如何展示、无数据状态如何展示、无权限状态如何展示、加载过程中如何反馈、操作失败以后如何提示、不同状态之间如何切换。

因此，UI / UX 设计实际上是在把：

> **文字需求 → 页面结构 + 交互行为 + 状态变化**

进一步具体化。

典型的设计产物就是 Figma 设计稿。

在传统研发中，Figma 主要用于产品、设计和研发之间对齐视觉与交互；而在 AI Coding 环境下，它还可以成为 Coding Agent 的结构化输入。

Figma 官方对 MCP Server 的描述是：

> “giving AI agents access to the structured design context needed to generate accurate, design-informed code.”

也就是向 AI Agent 提供生成更准确、基于真实设计信息的代码所需要的 **Structured Design Context（结构化设计上下文）**。[[10]](https://help.figma.com/hc/en-us/articles/39216419318551-Get-started-with-the-Figma-MCP-server)

通过 Figma MCP Server，Agent 可以直接读取 Component（组件）、Variable（设计变量）、Layout（布局）、Token（设计令牌）等设计信息，而不只是根据一张截图推测页面结构。[[11]](https://developers.figma.com/docs/figma-mcp-server/)

例如传统方式更接近：

> **截图 → AI 视觉理解 → 推测布局和样式 → Code**

而结构化设计输入可以变成：

> **Figma → MCP → Component / Variable / Layout → Code**

Figma 同时明确说明，MCP Server **并不是一键把设计转换成完美代码的工具**。它负责向 AI 提供结构化设计输入，最终代码仍然由 AI Assistant 根据设计上下文、代码库、组件体系和 Prompt 生成；结果质量也取决于上下文质量和模型行为。[[12]](https://developers.figma.com/docs/figma-mcp-server/mcp-vs-agent/)

因此，在 AI Native 开发中，UI / UX 设计承担了两层作用：

> **一方面，它是产品、设计和研发对页面与交互形成共同理解的设计依据；另一方面，它逐渐成为 AI Coding 和后续视觉验收的重要结构化输入。**

设计稿越规范，例如合理使用 Component、Variable、Auto Layout 和具有语义的组件名称，AI 越容易正确理解设计意图并复用已有组件。Figma 官方也把这些做法列为获得更稳定代码结果的重要实践。[[13]](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/)

---

### 【需求评审--让需求从“产品方案”变成团队共同认可的规范】

需求设计和 UI / UX 设计完成以后，需要进入 Requirement Review（需求评审）。

需求评审的目的不是简单地把 PRD 再讲一遍，而是让产品、研发、测试、设计以及必要的安全、风控或业务角色，对需求形成共同理解，并确认这份需求已经具备进入技术分析阶段的条件。

Agile Alliance 在 ATDD 中强调 Customer、Development 和 Testing 三种不同视角共同定义验收标准，其中分别回答：

- 业务：我们真正想解决什么问题？  
- 研发：我们可能怎样解决这个问题？  
- 测试：还有哪些情况需要考虑？ [[7]](https://agilealliance.org/glossary/atdd/)

因此，需求评审主要应该确认三个问题。

**第一，需求设计是否真正解决了原来的业务问题。** 不能只判断页面或者功能是不是按照方案设计出来，还需要重新检查“方案和问题是否对应”。

例如敏感数据治理，如果需求只规定前端隐藏字段，但无权限用户仍然能够通过接口获得真实数据，那么页面设计虽然完成了，最初的数据安全问题实际上没有解决。

所以评审首先要确认：

> **我们设计的是不是正确的事情。**

**第二，需求是否完整并且具备落地条件。** 研发和测试需要共同检查功能范围、业务规则、异常状态、依赖关系和影响范围，同时判断在当前时间和资源条件下是否可实现。

如果需求过大，可以继续进行优先级或者阶段拆分，例如：P0 / P1，或者一期 / 二期。

如果 PRD、设计稿、安全要求之间存在冲突，也应该在这一阶段完成澄清，而不是让后续开发人员或者 Agent 自己选择一种理解。

ISO/IEC/IEEE 29148 把 Requirements Engineering 定义为一个跨领域协作过程，并明确包含 Requirements Verification（需求验证）、Requirements Validation（需求确认）、Communication（沟通）和 Management（管理）。[[8]](https://www.iso.org/obp/ui?_escaped_fragment_=iso%3Astd%3Aiso-iec-ieee%3A29148%3Aed-2%3Av1%3Aen) 这说明需求形成以后，本身仍然需要检查它是否完整、准确并能够代表真实需要。

**第三，相关角色是否对“验收标准”形成一致理解。** 产品、研发和测试最终应该能够共同确认：

为什么做这个需求；最终实现什么；哪些场景必须覆盖；每个场景的预期结果是什么。

Agile Alliance 对 Acceptance Test 的定义强调，它是对软件预期行为的正式描述，通常通过具体 Example（示例）或 Usage Scenario（使用场景）表达，并最终得到 Pass / Fail（通过 / 失败）的判断。[[14]](https://agilealliance.org/glossary/acceptance-testing/)

因此，需求评审通过的标准应该是：

> 产品、研发、测试以及必要的相关角色，已经对需求目标、功能范围、业务规则、UI / UX 和验收标准形成共同理解，所有影响后续实现的关键歧义已经解决。

---

需求分析阶段最终可以形成一条比较完整的需求链路：

Business Goal（业务目标） → Problem（问题） → Requirement Specification（需求规范） → Acceptance Criteria（验收标准） → UI / UX Design（界面与交互设计） → Requirement Review（需求评审）

最终的核心产物包括 **需求规范、UI / UX 设计、验收标准、成功指标以及需求评审结论**。

所以，第一阶段“需求分析”的核心目的可以收敛成一句话：

> **在任何技术设计和代码实现开始之前，把业务问题逐步转换成一套产品、设计、研发、测试以及 AI Agent 都能够共同理解的明确需求规范，并提前确定“为什么做、最终做什么以及什么情况下算完成”。**

达到这个状态以后，需求才具备进入下一阶段**技术分析**的条件。

---

## 3. 第二阶段：技术分析

需求分析主要解决的是：

> **What--为什么做、做什么、什么情况下算完成。**

技术分析进一步解决的是：

> **How--需求最终怎么落到系统里，以及后续怎么证明实现是正确的。**

AWS 在 AI-DLC（AI-Driven Development Life Cycle，AI 驱动开发生命周期）的 Construction（构建）阶段中，把 Logical Architecture（逻辑架构）、Domain Model（领域模型）、Code Solution（代码方案）和 Tests（测试）放在同一个构建阶段中，并强调团队需要共同确认关键技术决策和架构选择。[[4]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

结合 AI Coding 的实际研发过程，技术分析可以整理成三个部分：

> **项目初始化与规范设计 → 技术设计 → 技术评审**

---

### 【项目初始化与规范设计--先建立统一的开发环境和工程规则】

如果当前是在一个已经存在的项目中进行需求改造，一般不需要重新初始化项目，而是先理解并遵循项目已经存在的工程规范。

但如果是一个从零开始的项目，就需要在正式开发业务功能之前完成 **<u>Project Initialization（项目初始化）</u>**，建立项目结构和基本工程规则。

这一阶段首先需要确定项目采用什么技术框架、目录如何组织、公共能力放在哪里、测试代码放在哪里，以及不同类型的文件应该按照什么规则管理。

与此同时，还需要把代码质量要求尽量转换成自动执行的规则。前端项目中常见的工具包括：

- **ESLint**：进行静态代码检查，发现不符合代码规则的问题；
- **Prettier**：统一代码格式；
- **Git Hooks（Git 钩子）**：在 Commit、Push 等代码操作前自动执行检查；
- **commitlint**：检查 Commit Message（代码提交信息）是否符合约定；

**<u>这些规范最好不要只写在一份文档里，而应该尽可能通过工具自动执行。</u>**例如 GitHub 的 Status Checks（状态检查）可以把 Build、Test、Code Scanning 等检查作为 Pull Request 合并条件；如果设置为 Required Check（必需检查），检查没有通过就不能进入受保护分支。[[15]](https://docs.github.com/en/pull-requests/reference/status-checks)

因此，项目初始化与规范设计的目的不是单纯“把项目跑起来”，而是：

> **在业务代码开始生成之前，先建立统一的项目结构、开发规则和自动化质量基线，让后续所有人和 Agent 都在同一套工程约束下开发。**

这一阶段最终形成的主要产物包括项目基础结构、目录与代码规范、Git 提交规范、自动化检查规则以及 CI 配置。

---

### 【技术设计--把需求转换成可执行的实现计划和测试标准】

项目环境和工程规范确定以后，开始进入真正的技术设计。

技术设计的核心任务是：

> **把需求阶段确定的“要实现什么”，转换成系统层面的“具体怎么实现”。**

对于已有项目，第一步通常不是直接提出新的架构，而是先进行现状和代码分析。

需要理解当前功能所在模块、数据从哪里产生、涉及哪些接口和公共组件、状态如何管理、哪些页面会受到影响，以及系统中是否已经存在可以复用的能力。

这一阶段尤其要明确 **<u>Change Scope（修改范围）</u>**：哪些地方需要修改，哪些地方明确不需要修改。

对于 AI Coding 来说，这一点非常重要。如果 Agent 没有充分理解存量系统，就容易为了实现一个局部需求重新设计已有能力，产生重复代码或者不必要的大范围修改。

完成现状分析以后，再进行技术方案设计，通常需要明确系统结构、数据流、接口协议、组件复用、状态管理以及性能、安全、兼容性等约束。

例如一个权限需求需要回答：

权限判断放在哪里；权限数据从哪里获得；前后端接口字段如何约定；多个页面是否需要复用统一能力；权限失败时如何降级；哪些存量逻辑可能受到影响。

因此，技术设计本质上是在建立：

> **Requirement → System Design**

也就是把需求映射到真实的软件系统结构中。技术方案确定以后，还需要形成 Implementation Plan（实现计划），把完整需求继续拆成可以独立执行的 Task（任务）。

其 Tasks 机制还要求任务按照 User Story（用户故事）组织，并明确依赖关系、执行顺序和 Independent Test Criteria（独立测试标准），使一个较大的 Feature 可以被拆成能够独立实现和验证的小任务。[[16]](https://github.com/github/spec-kit/blob/main/templates/commands/tasks.md)

因此，一个 Task 最好能够明确：

> 目标是什么、修改范围是什么、依赖什么、需要产出什么，以及什么情况下认为任务完成。

---

技术设计阶段还有一个非常重要的产物：

> **Test Case（测试用例）。**

Test Case 不是代码开发完成以后才产生，而应该根据前面的 Requirement Specification（需求规范）和 Acceptance Criteria（验收标准）进一步设计。

Agile Alliance 对 ATDD（Acceptance Test-Driven Development，验收测试驱动开发）的定义明确提出，业务、研发和测试等不同角色应该：

> **“collaborating to write acceptance tests in advance of implementing the corresponding functionality”**

也就是在对应功能实现之前共同定义验收测试。[[7]](https://agilealliance.org/glossary/atdd/)

一个 Test Case 至少应该明确：

> **Precondition（前置条件） → Action（操作） → Expected Result（预期结果）**

例如：

前置条件：用户没有敏感数据权限；操作：进入达人详情页面；预期结果：真实敏感数据不可见，并展示权限申请入口。

。AWS 当前 AI-DLC 的 Build and Test 阶段同样明确区分 Unit Test（单元测试）、Integration Test（集成测试）、Performance Test（性能测试），以及根据需要增加 Security、Contract 和 E2E 等测试。[[17]](https://aws.amazon.com/blogs/devops/building-with-ai-dlc-using-amazon-q-developer/)

因此可以根据不同风险，把 Test Case 分配到适合的测试层级：

> 局部函数和规则通过单元测试验证，模块之间的协作通过集成测试验证，关键用户流程再通过 E2E 验证。

在本文这套 AI Coding 工作流中，**Test Case 应该被看作技术分析阶段最关键的质量产物之一。**

它有两层作用。

第一，它是后续测试验收的直接标准：

> **代码最终是否完成，不由 Agent 自己判断，而要回到 Test Case 逐项验证。**

第二，它同时可以反过来检查前面的需求理解是否正确。

如果在设计 Test Case 时发现：

某个场景不知道预期结果是什么；某个需求无法转换成可验证场景；不同人对同一个 Case 的预期结果不一致；某些边界情况没有被覆盖；

那么问题往往不只是“测试没写好”，而是说明前面的需求分析或者技术方案仍然存在歧义和遗漏。

因此：

> **Test Case 不只是测试阶段的输入，也是检查需求分析和技术设计是否真正形成共同理解的重要依据。**

技术设计完成以后，主要应该形成：

> **技术方案 + 接口协议 + 影响范围 + 实现计划 + Task 列表 + Test Case / Test Matrix（测试矩阵）。**

---

### 【技术评审--统一实现方案和最终验证标准】

技术设计完成以后，需要进行 Technical Review（技术评审）。

> 如果说需求评审解决的是： “我们到底要做什么？”
>
> 那么技术评审主要解决的是： “我们准备怎么实现，以及这套实现和测试方案是否足以支撑需求交付？”

技术评审首先要完成**研发之间的技术对齐**。

对于前后端协作需求，需要确认接口协议、字段含义、状态定义、错误处理、数据权限和联调方式；如果涉及基础架构、安全、测试或者上下游系统，也需要相关角色共同确认方案。

AWS 在 AI-DLC 的 Construction 阶段把这种协作称为 **<u>Mob Construction（团队共同构建）</u>**：AI 可以提出架构、领域模型、代码方案和测试，但团队需要实时澄清关键技术决策和架构选择。[[4]](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)

技术评审的第二个重点也是 AI Coding 场景中特别重要的评审对象，是 **Test Case 的完整性和准确性**。

这里需要让产品、研发和测试共同确认：

每一个主要需求是否都有对应测试；正常场景、异常场景和关键边界是否已经覆盖；每一个 Case 的前置条件和预期结果是否明确；Test Case 是否真正验证需求，而不是验证某一种具体代码实现。

ATDD 本身就强调 Customer、Development、Testing 三种不同视角共同建立 Acceptance Test，因为这些测试既是对系统行为的描述，也是后续判断系统是否按照预期工作的依据。[[7]](https://agilealliance.org/glossary/atdd/)

因此，在 AI Coding 工作流中，可以把 Test Case Review（测试用例评审）理解成一个非常重要的 **Quality Gate（质量门禁）**：

> 只有当需求能够完整转换成一套大家共同认可的 Test Case，才能说明产品、研发和测试对“最终要做什么以及什么算正确”已经基本达成一致。

如果 Test Case 中出现遗漏或者预期结果错误，就应该继续回到需求或技术设计中澄清，而不是直接让 Agent 开始编码。

所以技术评审最终需要完成两个层面的统一：

- 第一，统一“怎么实现”--前端、后端及相关技术角色对技术方案达成一致；
- 第二，统一“怎么证明实现正确”--产品、研发和测试对 Test Case 的完整性和准确性达成一致。

只有这两个条件同时满足，技术分析阶段才真正完成，需求才能进入下一阶段的代码开发。

---

因此，第二阶段“技术分析”可以最终收敛成： 项目初始化与规范设计 → 技术设计 → 技术评审

三部分之间的关系是：

> 先建立统一的工程环境和规则，再把需求转换成技术方案、实现计划和 Test Case，最后通过技术评审统一实现方案和验收标准。

其中，在 AI Coding 场景下需要特别强调：

> Test Case 是连接“需求理解”和“最终验收”的关键产物。一方面，它决定后续 Agent 根据什么标准判断功能是否完成；另一方面，它也能够反向检查前面的需求分析和技术规划是否存在遗漏或理解偏差。因此，在代码生成之前先把 Test Case 做完整、做准确，是保证后续 AI 自动开发和自动验收可信的重要前提。

## 4. 第三阶段：代码开发

经过前面的需求分析和技术分析以后，需求目标、技术方案、Task（任务）和 Test Case（测试用例）都已经基本明确，这时才真正进入代码开发阶段。

代码开发阶段解决的问题是：

> 如何按照已经确认的需求规范、技术方案和任务计划，把设计稳定地转换成代码，并在实现过程中持续证明每一个任务是正确的。

在 AI Coding 环境下，代码本身越来越可以由 Coding Agent 执行，但这并不意味着可以把整个需求一次性交给 Agent 完成。相反，DORA 当前特别强调 **<u>Working in Small Batches（小批量工作）</u>**：将大功能拆成能够在较短时间内独立完成的工作单元，可以更快获得反馈、更快验证假设，并在方向错误时及时调整。DORA 进一步指出，在生成式 AI 时代这一能力反而更加重要，因为 AI 很容易快速生成大规模代码变更，而大的变更通常更难 Review、测试和安全集成。[[18]](https://dora.dev/capabilities/working-in-small-batches/)

因此，代码开发阶段可以分成四个部分：

> 按 Task 小批量实现 → 开发过程持续验证 → AI 自检与自动 Review → 人工 Code Review 与合并门禁

---

### 【按 Task 小批量实现--一次完成一个可以独立验证的任务】

代码开发不应该重新从整个需求开始规划，而应该直接执行技术分析阶段已经拆好的 Task。

例如一个权限需求已经拆成：

Task 1：实现权限解析能力；Task 2：改造达人详情页面；Task 3：接入权限申请入口；Task 4：改造其他受影响页面；Task 5：补充相关自动化测试。

Coding Agent 应该按照 Task 逐个推进：

> **Task → Implement（实现）→ Verify（验证）→ 完成 → 下一个 Task**

而不是一次执行：

> “完成整个权限需求。”

DORA 对 Small Batch（小批量）的建议就是把 Feature（功能）拆成能够**独立完成、独立检查并快速获得反馈**的工作单元。DORA 还特别针对 AI Coding 指出，虽然 AI 擅长快速生成大量代码，但大型 Change（代码变更）会显著增加 Review、Test 和 Integration（集成）的难度，因此应该避免生成巨大的 Pull Request。[[18]](https://dora.dev/capabilities/working-in-small-batches/)

对于 AI Coding 来说，每一个 Task 最好继续受到技术分析阶段已经定义好的几个条件约束：

> Goal（目标） + Scope（修改范围） + Input（输入） + Output（产物） + Acceptance Criteria（完成标准）

其中 Scope 尤其重要。这样可以减少 Agent 为了解决局部问题而顺带修改其他模块、重构无关代码或者扩大实现范围。

所以小批量开发的核心目的不是单纯“任务拆得小”，而是：

> 让每一次代码变化都有明确目标和边界，并且能够在进入下一个任务之前独立证明这一小步已经完成。

---

### 【开发过程持续验证--不是全部写完以后才开始测试】

每完成一个 Task，都应该立即执行和这个任务相关的自动化检查，而不是整个需求全部开发结束以后再统一验证。

典型检查包括：

> Build（构建检查）、Type Check（类型检查）、Lint（静态代码检查）、Unit Test（单元测试）、Integration Test（集成测试）。

例如实现一个权限解析函数以后，可以立即执行对应 Unit Test；完成页面与权限接口集成以后，再执行相关 Integration Test。

```text
Task 1 → Code → Test → Pass
Task 2 → Code → Test → Pass
Task 3 → Code → Test → Pass
```

这种方式的价值在于，一旦测试失败，可以比较容易知道：

> **问题来自刚刚完成的哪个 Task。**

而不是在大量代码全部生成以后，再从一个很大的变更集中寻找错误来源。

GitHub 的 Status Checks（状态检查）就是这种工程机制的典型实现。Build、Test、Code Scanning（代码扫描）等检查可以自动关联到 Commit 或 Pull Request；对于受保护分支，还可以设置为 Required Status Checks（必需状态检查），只有检查通过以后代码才能合并。[[15]](https://docs.github.com/en/pull-requests/reference/status-checks)

因此：

> **测试不是代码开发结束以后的独立动作，而应该成为代码开发过程中的持续反馈机制。**

这一阶段执行的 Unit Test 和 Integration Test，主要解决代码实现层面的快速反馈；前面已经定义的完整 Test Case，则会在后续“测试验收”阶段进一步执行完整的功能验收。

---

### 【AI 自检与自动 Review--代码完成后先进行第一轮质量检查】

Coding Agent 完成一个 Task 以后，不应该立即把代码视为最终结果。

在提交人工 Review 之前，可以先让 AI 完成第一轮 Code Review（代码审查）。

OpenAI 在《Building an AI-native engineering team》中明确提出，在 Review 阶段可以先 **Delegate（委托）**第一轮代码审查给 Agent，而且这一过程可能执行多轮；之后代码才进入团队成员的正式 Review。[[3]](https://cdn.openai.com/business-guides-and-resources/building-an-ai-native-engineering-team.pdf)

AI 自检可以重点检查以下内容：

**第一，修改范围是否正确。**

通过 Git Diff（代码差异）检查：

是否只修改了当前 Task 要求的代码；是否出现需求范围之外的修改；是否意外删除或者重构了存量逻辑。

**第二，实现是否符合需求和技术方案。**

检查：代码有没有实现当前 Task 的目标；是否遵循已经确定的接口协议和业务规则；是否存在明显逻辑遗漏。

**第三，代码质量是否合理。**

是否出现重复代码；是否产生没有必要的抽象；是否引入无用依赖；是否出现明显的过度设计；是否符合项目已有的代码和目录规范。

**第四，是否产生新的风险。**

权限判断是否被绕过；是否影响全局状态；是否产生性能问题；是否修改公共能力而影响其他页面。

完成 Review 后，如果发现有效问题，可以让 Agent 根据 Review Comment（审查意见）继续修改，然后重新执行相关测试。

于是形成： **Implement → Test → AI Review → Fix → Test** 的内部循环。

这里需要注意，AI Review 的目的主要是：

> **在代码进入人工审查之前，先过滤掉大量能够被自动发现和修复的问题。**

它并不意味着 AI 对自己代码的判断就可以作为最终质量结论。

---

### 【人工 Code Review 与合并门禁--重点审查高风险和高判断问题】

AI Coding 并没有消除人工 Code Review，只是人工 Review 的重点开始发生变化。

OpenAI 对 AI-native engineering 的职责划分非常清楚：

- **Delegate**：第一轮代码审查可以交给 Agent；  
- **Review**：工程师仍然需要审查 Pull Request，重点关注架构是否合理、是否采用正确的工程模式、功能是否满足需求；  
- **Own**：最终进入生产环境的代码仍然由工程师负责。[[3]](https://cdn.openai.com/business-guides-and-resources/building-an-ai-native-engineering-team.pdf)

所以人工 Review 不应该只是把 AI 生成的每一行代码重新人工实现一遍。

更合理的是采用 **Risk-based Review（风险导向审查）**：

> **修改风险越高、影响范围越大、错误后果越严重，人工投入越多。**

例如以下变化应该重点人工审查：

- 权限和安全逻辑；
- 敏感数据处理；
- 全局状态；
- 公共基础组件和公共方法；
- 大范围重构；
- 第三方依赖变化；
- 不可逆的数据操作。

而一些风险较低、结果容易验证的修改，例如简单样式调整、局部新增组件或者规则非常明确的重复性实现，可以更多依赖自动化检查、AI Review 和后续功能验收。

OpenAI 在 Agent 工程指南中也提出类似的风险控制思想：应根据 Tool 或 Action（动作）的敏感程度、是否可逆、所需权限和潜在影响进行风险分级；对于 **high-risk actions（高风险动作）**以及 Agent 超过失败阈值的情况，应触发 Human Intervention（人工介入）。[[19]](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-agents/)

因此，在 AI Coding 环境下，更合理的质量链路是：

> **AI 实现 → 自动测试 → AI Review → 自动检查 → 人工风险 Review → Merge**

---

第三阶段“代码开发”最终可以收敛成：

> **按 Task 小批量实现 → 开发过程持续验证 → AI 自检与自动 Review → 人工 Code Review 与合并门禁**

它的核心思想是：

> 代码开发不是让 Agent 一次生成整个需求，而是按照已经确认的 Task 小批量推进，每完成一步就验证一步；AI 负责大量实现、自检和低风险问题修复，人工则重点处理高风险、高影响和需要工程判断的问题。

当这些代码级检查和 Review 完成以后，只能说明：

> **代码已经具备进入完整功能验收的条件。**

它还不能直接证明整个需求已经正确交付。下一阶段仍然需要回到技术分析阶段提前定义的 Test Case，对真实功能场景逐项进行**测试验收**。

## 5. 第四阶段：测试验收

代码开发完成以后，进入测试验收阶段。

这一阶段解决的核心问题是：

> “是否存在独立、完整并且可以审查的证据，证明当前实现满足前面已经确定的需求和 Test Case？”

这一点在 AI Coding 环境下尤其重要。传统自动化测试的执行步骤和断言通常由人提前写死，而 AI Browser Agent（浏览器智能体）可以根据目标、页面状态和 Test Case 自主决定下一步操作。因此，测试的执行能力变强了，但同时也产生了一个新的问题：

> Agent 的执行过程具有一定不确定性，因此最终的 PASS / FAIL 结论本身不能直接作为质量证明，还需要验证这个结论是怎么得到的。

测试验收阶段可以整理成三个部分：

> 功能验收 → 覆盖率检查 → 质量门禁

其中最核心的问题始终是：

> 如何证明验收结论可信。

---

### 【功能验收--按照 Test Case 逐项证明功能满足需求】

功能验收的基础，是技术分析阶段已经提前确定的 Test Case（测试用例）。

因此测试阶段应该把前面已经确定的：

> **Precondition（前置条件） + Action（操作） + Expected Result（预期结果）**

作为验收标准。

传统自动化测试通常会把具体执行过程提前写成固定脚本：

> 打开页面 → 点击 A → 输入 B → 点击 C → Assert（断言）结果。

而 AI Browser Agent 可以采用更加动态的执行方式：

> 给定 Test Case 和验收目标 → Agent 读取当前页面 → 自主选择下一步操作 → 不断观察页面状态 → 直到完成验收。

Anthropic 在介绍 Agent Eval 时也提到，已经有团队使用 Browser Agent 对应用进行实际操作测试，再通过不同 Grader（评分器）检查最终结果。[[20]](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

每一个 Test Case 不能只留下： PASS。

还应该尽可能保存与结论对应的 Evidence（验收证据），例如截图、页面状态、接口请求与响应、操作轨迹、Console Log（控制台日志）、Mock 命中记录和 Assertion Result（断言结果）。

最终形成：

Test Case → Expected Result → Actual Result → Evidence → PASS / FAIL

这样功能验收的结果才具有可审查性。

这里需要区分两个评测对象：**功能验收是在证明软件产物是否满足 Requirement；Agent Eval 是在证明 Agent / Harness 是否能够稳定完成 Task。** AI Coding 场景可以复用 Acceptance Criteria、Test Case 和 Evidence 作为 Eval Task 的成功标准，但还需要额外观察多次 Trial、Tool 使用、执行轨迹、成本和稳定性。完整关系见 [《Agent Eval 与 Benchmark》](./Agent-Eval与Benchmark.md)。

**第一，完整性。** 已定义的 Test Case 是否全部被执行，是否存在 Skip（跳过）、失败后未继续或者遗漏的场景。

**第二，正确性。** Actual Result（实际结果）是否真正满足前面定义的 Expected Result，而不是 Agent 自己重新解释了验收标准。

**第三，证据充分性。** 每一个 PASS / FAIL 是否有对应的截图、日志、接口记录、页面状态或者其他可以独立检查的 Evidence。

**第四，一致性。** Agent 的操作轨迹、观察结果、最终系统状态和 PASS / FAIL 结论之间是否一致，避免出现“执行过程实际上失败，但最终仍然输出通过”的情况。

---

### 【覆盖率测试--确认重要代码路径是否被实际验证】

Code Coverage（代码覆盖率）主要用于观察：

> **在测试执行过程中，哪些代码、函数和条件分支真正被执行到了。**

常见指标包括：

- Line Coverage（行覆盖率）：哪些代码行被执行过；
- Function Coverage（函数覆盖率）：哪些函数被调用过；
- Branch Coverage（分支覆盖率）：if / else、switch 等条件分支是否都被执行过。

代码覆盖率主要解决两个问题。

**<u>第一，判断测试覆盖是否充分</u>**。比如一个权限逻辑存在“有权限、无权限、接口异常”三个重要分支，但测试只执行过“有权限”路径，那么即使当前 Test Case 全部通过，也不能说明这个模块已经得到充分验证。Coverage 可以帮助发现这种遗漏，并推动补充对应的 Unit Test（单元测试）、Integration Test（集成测试）或者 E2E（端到端测试）。

**<u>第二，帮助发现可疑的未执行代码</u>**。如果某些代码分支在正常业务场景、异常场景以及测试场景中始终无法进入，就需要进一步判断：

> 这是测试遗漏，还是这段逻辑本身已经不可达、过期或者没有实际用途？

如果确认不存在合理的进入条件，就可能属于 Dead Code（死代码）或者冗余逻辑，可以进一步考虑删除，从而减少代码复杂度和后续维护成本。

但需要注意：

> Coverage 低，可以说明测试可能存在遗漏；Coverage 高，并不能直接证明代码质量高。

所以在测试验收阶段，代码覆盖率更准确的作用可以概括成：

> 通过观察测试是否执行到重要代码路径，判断测试覆盖是否充分；同时识别长期无法进入的可疑分支，进一步判断是测试缺失还是代码冗余，从而辅助提升测试完整性和代码质量。

---

### 【质量门禁--基于工程规范进行 AI Review】

在 AI Coding 场景下，可以让 AI 基于团队沉淀的 **Coding Standards（编码规范）**、安全规范、架构规范以及历史最佳实践，对本次代码变更进行自动 Review（代码审查）。

这里检查的重点不是“功能能不能跑起来”，而是进一步判断：

> 这份代码虽然实现了需求，但它是不是一份可以长期维护和安全交付的高质量代码。

AI Review 通常可以从几个方面进行判断：

- **Correctness（正确性）**：实现是否符合需求和技术方案，是否存在明显逻辑错误；
- **Security（安全性）**：是否存在权限绕过、敏感数据泄露、不安全输入处理等风险；
- **Maintainability（可维护性）**：代码结构是否清晰，是否存在大量重复逻辑、过高复杂度或者难以理解的实现；
- **Extensibility（可扩展性）**：后续需求变化时是否容易扩展，是否把本应该复用的能力写死在局部页面；
- **Compatibility（兼容性）**：是否会破坏已有逻辑、公共组件或者上下游调用；
- **Engineering Risk（工程风险）**：是否引入新的依赖、修改全局状态、改变公共接口或者产生其他高影响变更。

 AI Review 就不是完全依赖模型自身的通用知识，而是：

> 通用模型能力 + 项目规范 + 团队工程知识

共同判断当前代码是否符合团队质量要求。

如果 AI Review 发现问题，可以生成 Review Comment（审查意见），例如：当前权限判断只发生在 UI 层，存在数据已经下发到前端的风险；

对于这类明确的问题，AI 可以继续自动修改代码，然后重新执行 Test、Coverage 和 Review。

因此可以形成：

> Code → AI Review → Review Comments → AI Fix → Test → Re-review

也就是说，**AI 不仅可以发现问题，也可以完成大量低风险、规则明确的问题修复。**但是这里必须保留最后一个边界：

AI 可以完成 Review 和自动修复，但不能因为“AI 自己认为已经修好了”，就自动通过最终质量门禁。

**<u>最终进入 Merge 或 Release 之前，仍然需要根据风险进行人工确认。</u>**这一部分可以最终概括为：

> 代码质量检查负责判断“代码是否不仅能工作，而且具备足够的安全性、可维护性和可扩展性”。AI 可以基于项目规范和工程知识自动完成质量 Review，并自动修复明确的问题；但最终质量门禁仍然需要根据风险进行人工确认，特别是涉及安全、权限、核心业务链路和大范围架构变化的代码，不能仅依赖 AI 自身的 Review 结果直接放行。

## 6. 第五阶段：交付上线

测试验收通过以后，需求还没有真正结束，最后还需要进入交付上线阶段。

这一阶段解决的核心问题是：

> 如何把已经通过验证的软件，以可控、可回退、可观察的方式安全发布到生产环境，并在上线后确认它既没有引入新的系统问题，也真正达到了最初的业务目标。

---

### 【构建发布产物--形成唯一、可追溯的发布版本】

通过发布门禁以后，需要把源代码构建成真正能够部署到目标环境的 Release Artifact（发布产物）。

根据不同系统，它可能是：

> Bundle（前端构建包）、Package（软件包）、Container Image（容器镜像）或者其他可以直接部署的产物。

Google SRE 在发布工程原则中明确强调 **Reproducible Builds（可重复构建）**：相同的构建输入应该能够稳定产生相同的构建结果；代码提交以后，构建系统应该自动产生并保存对应的 Artifact。[[21]](https://sre.google/workbook/canarying-releases/)

因此，发布产物不能只是一份无法确认来源的文件，而应该能够关联：

Release Version（版本号） → Commit → Source Code → Dependencies（依赖） → Build Result（构建结果）

NIST SSDF（Secure Software Development Framework，安全软件开发框架）也明确增加了对 Software Release Provenance（软件发布来源信息）的要求，包括收集并共享软件 Release 中各组成部分的 Provenance Data（来源数据）。[[22]](https://csrc.nist.gov/projects/ssdf)

它的价值在于：

> 当线上版本出现安全问题、依赖漏洞或者功能异常时，可以准确知道当前运行的是哪一份代码、包含哪些依赖以及经过了什么构建过程。

因此，这一步解决的是：

> **把“当前代码”转换成一个固定、可重复部署并且可以追溯来源的正式发布版本。**

---

### 【发布前验证--确认真正要上线的版本在目标环境中仍然正常】

测试环境中的功能通过，并不意味着最终发布包一定能够在生产环境正常运行。

原因可能包括：环境配置不同、依赖版本不同、真实数据规模不同、权限配置不同，或者构建和部署过程本身引入了问题。

因此，在真正进入生产环境之前，通常还会执行一轮针对 Release Candidate（候选发布版本）的验证，例如：

Staging（预发布环境）  
Pre-production（接近生产的环境）  
Smoke Test（冒烟测试）  
Regression Test（回归测试）。

Smoke Test 主要快速确认最核心功能是否能够正常工作；Regression Test 则检查本次变更有没有破坏原来已经正常工作的功能。

Google SRE 的发布实践也强调：

> 自动构建完成以后，需要先通过测试，构建产物才能进入系统测试以及后续 Canary Deployment（金丝雀发布）。[[23]](https://sre.google/sre-book/release-engineering/)

所以发布前验证真正检查的是：

> **之前通过测试的代码，在经过真实构建和部署流程以后，最终要上线的那个 Release Artifact 是否仍然可以正常工作。**

---

### 【渐进式发布--不要一次把风险扩大到全部用户】

即使发布前已经进行了完整测试，也不能保证生产环境中绝对不会出现问题。

Google SRE 明确指出：

> 测试环境不可能与生产环境完全一致，测试也不可能覆盖所有真实场景，因此部分问题只有在真实流量进入以后才会出现。[[21]](https://sre.google/workbook/canarying-releases/)

因此，对于影响范围较大或者风险较高的变更，更安全的方式不是一次把新版本发布给 100% 用户，而是采用 **Canary Release（金丝雀发布）**或者其他 Gradual Rollout（渐进式发布）方式。

Google SRE 对 Canarying 的定义是：

> “a partial and time-limited deployment of a change in a service and its evaluation.”
>
> 也就是：
>
> **先把一个变更在服务的一小部分范围内、有限时间内进行部署和评估，再根据结果决定是否继续扩大发布。** [[21]](https://sre.google/workbook/canarying-releases/)

典型过程可以是：**5% → 验证 → 20% → 验证 → 50% → 验证 → 100%**

这里具体百分比并不是固定标准，关键思想是：

> **逐步扩大影响范围，并且在每一个阶段都观察结果。**

Google 的可靠发布实践同样强调，大多数服务更新都会逐渐推进，并在不同阶段之间插入 Verification（验证）；如果发现异常，可以停止 Rollout（发布扩展）甚至 Rollback（回滚）。[[24]](https://sre.google/sre-book/reliable-product-launches/)

所以渐进式发布解决的是：

> 即使已经通过测试，也不要一次把未知风险扩大到所有用户，而是通过真实生产流量逐步建立对新版本的信心。

---

### 【上线监控与数据回收--发布成功不等于需求成功】

代码成功发布到 100% 用户，并不意味着需求已经真正完成。

上线以后至少还需要回答两个问题：

**<u>系统运行是否稳定？</u>**

以及：

**<u>最开始定义的业务问题有没有真正得到解决？</u>**

因此，需要持续观察 Monitoring（监控）数据。

技术层通常关注：

> Error Rate（错误率）、Latency（延迟）、Availability（可用性）、Crash（崩溃）、API Failure（接口失败）以及资源使用情况。

DORA 把 Monitoring 定义为收集、分析并使用系统和基础设施信息来支持决策的过程，并强调监控能够形成快速反馈，使团队更早发现并修复问题；生产环境中获得的信息还应该继续反馈给开发和产品团队。[[25]](https://dora.dev/capabilities/monitoring-systems/)

另一方面，还需要重新回到需求分析阶段提前确定的 Business Success（业务成功指标）。

例如：

转化率是否提升；功能使用率是否达到预期；作者活跃度是否改善；任务领取率是否提高；安全风险是否真正被消除。

这意味着：

> **Delivery Success（成功上线）和 Business Success（解决业务问题）不是同一个概念。**

软件成功上线只能证明：**<u>这个版本已经安全地交付给用户。</u>**

而需求真正成功，还需要证明：**<u>最开始希望解决的问题确实得到了改善。</u>**

因此整个工程流程最后应该形成一个反馈闭环：

> **业务问题 → 需求 → 设计 → 实现 → 测试 → 发布 → 监控与数据回收 → 判断问题是否解决 → 下一轮需求**

因此：

> **软件开发生命周期不是一条在“上线”处结束的直线，而是通过生产数据和用户反馈重新回到需求分析的持续循环。**

---

第五阶段“交付上线”最终可以收敛成：

发布门禁 → 构建发布产物 → 发布前验证 → 渐进式发布 → 上线监控与数据回收

其中每一步分别解决：

- 发布产物：到底发布哪一个确定、可追溯的版本；  
- 发布前验证：真正的部署包在目标环境中是否正常；  
- 渐进式发布：如何控制生产环境中的未知风险；  
- 上线监控与数据回收：系统是否稳定，以及最初的业务问题是否真正得到解决。

所以整个交付上线阶段的核心思想可以总结成一句话：

> 测试通过只能证明软件具备发布条件，真正可靠的软件交付还需要保证发布版本可追溯、上线过程可控制、异常能够快速发现和回退，并在上线后通过技术指标和业务指标持续验证这次需求是否真正成功。

## 7. AI Native 下的软件工程化设计

如果让我理解当前的软件工程化设计，我会认为它的核心目的，是**<u>把一个最开始比较模糊的业务需求，通过一套稳定的工程流程，逐步转换成明确的需求、技术方案、可执行任务、经过验证的软件实现，最后能够安全、完整地交付到生产环境</u>**。

传统软件工程中的 SDLC（Software Development Life Cycle，软件开发生命周期）体现的就是这种思想。软件开发并不是一次简单的“需求到编码”的活动，而是由多个相互衔接的阶段共同完成。每一个阶段都有自己的目标和交付物，同时又为下一个阶段提供输入。

这样做的价值，是让产品、研发、测试等不同角色能够围绕同一个目标、同一套规范和同一套阶段产物协作完成复杂任务，而不是依赖个人理解和临时沟通。

到了 AI Native 环境以后，这套工程体系并没有消失，反而变得更加重要。

现在 AI 已经逐渐从 Coding Assistant（编码辅助工具）变成整个研发流程中的执行者，可以参与需求分析、技术规划、代码实现、测试、Review 和交付。因此，工程化设计需要解决的问题，也从单纯的“人和人如何协作”，进一步变成：

> **如何让人和 AI / Agent 在同一套工程规则下共同完成复杂任务，并且在 AI 高速执行的情况下，仍然保证需求不跑偏、任务可追踪、结果可验证、风险可控制。**

AWS 在 AI-DLC（AI-Driven Development Life Cycle，AI 驱动开发生命周期）中把这种关系概括成“AI 执行、人工监督”。也就是说，大量分析和执行工作可以交给 AI，但是关键判断、高风险节点和最终放行仍然由人负责。

基于这个目标，我认为 AI Native 下的软件工程化可以通过四条主线来贯穿整个研发流程：规范、验证、可追溯和风险控制。

### 【第一，规范驱动】

第一条原则是规范先行。

AI 要稳定执行任务，前提是我们要先把过去依赖产品、研发个人理解的隐式信息，转换成明确的工程规范。

这和 SDD（Spec-Driven Development，规范驱动开发）的思想是一致的：在真正开始编码之前，先形成明确的 Spec（规范），然后再形成 Plan（计划）、Tasks（任务），最后进入 Implementation（实现）。

因此，在需求分析和技术分析阶段，需要提前沉淀需求规范、技术方案、接口协议、Test Case、代码规范和实现计划等结构化产物。

这些产物不只是留档，它们本身就是后续 AI 执行任务的依据。

也就是说，要尽量形成：

> **业务目标 → 需求规范 → 验收标准 → 技术方案 → 实现计划 → Task → Code**

这样可以减少 AI 在每一个阶段重新理解需求、自由猜测或者扩大修改范围的问题。

---

### 【第二，验证前置】

第二条原则是验证前置。

不能等代码已经生成以后，才重新讨论“这个需求应该怎么测试”。

因为如果测试项根据已经生成的代码反向设计，就可能出现一种风险：AI 一开始对需求理解错了，按照错误理解写了代码，又根据错误代码生成测试，最后测试仍然全部通过。

所以测试标准应该来源于需求规范，而不是来源于代码实现。

这和 ATDD（Acceptance Test-Driven Development，验收测试驱动开发）的思想一致：在功能实现之前，产品、研发、测试就应该共同明确什么情况下可以认为需求已经完成。

在我们的工程体系中，可以进一步采用“规范驱动测试”的思路，把 Requirement（需求）逐渐转换成 Scenario（场景）和 Test Case（测试用例），建立需求与测试项之间的映射关系，并覆盖正常场景、异常场景和重要边界条件。

因此，在技术评审阶段需要形成一套完整的 Test Case Matrix（测试用例矩阵），并由产品、研发和测试共同确认。

在整个 AI Coding 工作流中，我认为 Test Case 是最重要的质量产物之一。

一方面，它是后续 AI 自动验收的标准，它的完整性和准确性直接决定最终验收质量；另一方面，它也是检查前面需求分析和技术规划是否存在理解偏差的重要手段。

如果一个 Test Case 的预期结果说不清楚，或者不同角色对同一个 Case 的预期存在分歧，就说明前面的需求本身还没有真正对齐。

---

### 【第三，可追溯】

第三条原则是可追溯。

一个完整需求实际上可以看成一个 Long-running Task（长任务），它会跨多个阶段，也可能跨多个 Agent 和多个 Session 执行。

因此不能只保存最后的代码，而需要持续沉淀结构化工程产物，把整个过程连接起来。

例如建立：

> **Requirement → Scenario → Test Case → Technical Plan → Task → Code Change → Test Result → Release**

这样的关系。

它首先解决的是人工审查问题。人工不可能重新执行 Agent 完成的所有工作，而是需要根据需求、技术方案、代码 Diff、测试结果和验收证据判断当前结论是否可信。

**同时，它也是 Agent 执行长任务的重要基础。**

一个大需求应该提前拆成多个相对独立、具有明确目标和完成标准的任务。每个任务执行完成以后，都应该留下任务状态、代码修改、测试结果等结构化产物。

这样即使 Agent 因为上下文限制、工具异常或者环境问题中断，也能够根据已有产物快速恢复到之前的稳定状态，从未完成的位置继续执行，而不是重新执行整个需求。

因此，可追溯真正解决的是：

> **任务能够持续推进，中断以后能够恢复，结果能够审查，需求变化以后能够继续演进。**

---

### 【第四，风险控制】

第四条原则是风险控制。

AI Native 并不意味着所有研发节点都应该完全自动化。

AI 本身仍然具有不确定性，因此自动化程度不能只看“AI 能不能做”，还要看当前任务的风险、确定性和结果是否容易验证。

规则明确、风险较低、结果容易判断的任务，可以更多交给 AI 自动执行。

但对于需求歧义、安全权限、全局状态、公共能力、核心业务链路、大范围架构变化以及最终生产发布等高风险节点，需要引入 Human-in-the-Loop（人在回路），也就是由人工进行判断、确认或者放行。

所以在 AI Native 的工程体系中，人的角色会逐渐从大量执行工作，转变成规范制定、关键判断、风险审查和最终质量负责。

---

### 【第一阶段：需求分析】

需求分析主要解决三个问题：

> **为什么做、做什么、什么算完成。**

首先需要根据当前的业务目标和业务问题来设计需求。

要先判断当前真正存在的问题是什么、这个问题影响谁、为什么值得解决，以及解决以后能够带来什么业务价值。

然后再把问题拆解成具体需求点，明确系统需要支持哪些能力、有哪些业务规则、哪些边界场景需要考虑，以及本次需求的范围和非范围。

如果需求涉及页面，还需要进一步完成 UI / UX 设计。

在当前 AI Coding 环境下，设计稿已经不只是给人看的交互参考，也逐渐成为 AI 的结构化输入。像 Figma 这样的设计工具可以让 Agent 直接读取布局、组件、设计变量等结构化信息，相比单纯依赖截图和自然语言，更容易保持页面结构和设计意图的一致性。

因此，对于前端需求来说，结构化设计稿是后续代码实现和视觉验收的重要依据。

完成需求设计以后，还需要进行需求评审。

需求评审主要解决三个问题：第一，当前需求方案是否真的能够解决最开始定义的问题；第二，根据现有系统、代码、接口和资源条件，这个需求是否能够落地，如果范围过大是否需要划分优先级或者一期、二期；第三，当前需求是否已经能够转换成明确的验收标准和测试场景。

需求分析最终不是简单产生一份 PRD，而是要让产品、研发、测试以及必要的安全、风控角色对：

> **为什么做、最终做什么、什么情况下算完成**

形成共同理解。

---

### 【第二阶段：技术分析】

如果需求分析解决的是“做什么”，那么技术分析解决的是：

> **怎么做，以及后续怎么证明实现正确。**

如果是一个从零开始的新项目，首先需要进行项目初始化和规范设计。

包括技术框架和工具链选型、项目目录结构，以及 ESLint、Prettier、Git Hooks、commitlint、Type Check、CI 等工程规则。

这些规范的作用，是让后面无论代码由人还是 AI 生成，都必须遵循同一套工程质量要求。

之后进入技术设计。

对于已有项目，需要先分析存量系统，明确当前模块在哪里、数据从哪里来、涉及哪些接口、公共组件和页面，哪些能力能够复用，以及本次需求真正需要修改哪些代码。

在此基础上形成技术方案，包括接口协议、数据流、状态管理、公共能力设计以及安全、性能和兼容性等约束。

技术设计完成以后，需要进一步形成两个非常关键的产物。

第一个是 Implementation Plan（实现计划）。

把整个需求拆成多个可以独立执行和验证的 Task，并为每个 Task 明确目标、修改范围、输入、输出和完成标准。后续 AI Coding 就按照这个计划逐项执行，而不是一次性完成整个需求。

第二个是 Test Case。

Test Case 是后续测试验收的直接标准，同时也用来反向验证前面的需求分析和技术设计是否正确。

因此，在技术评审阶段，一方面需要前后端和相关研发角色对技术方案、接口和影响范围形成共识；另一方面需要产品、研发、测试共同检查 Test Case 的完整性和准确性。

只有当大家既统一“怎么实现”，又统一“怎么证明实现正确”，才能进入代码开发阶段。

---

### 【第三阶段：代码开发】

进入代码开发以后，主要执行者可以逐渐变成 AI。

这里不建议让 AI 一次完成整个需求，而是按照前面已经拆好的 Task 小批量推进：

> **Task → Implement → Test → Review → 下一个 Task**

每完成一个 Task，就应该立即执行对应的静态检查、类型检查、Unit Test（单元测试）和 Integration Test（集成测试），而不是整个需求全部完成以后才统一测试。

同时 AI 需要主动执行第一轮 Code Review。

首先通过 Git Diff 判断代码修改是否都有需求依据，是否出现需求范围之外的改动，避免为了实现局部功能破坏存量逻辑。

然后进一步检查是否存在重复代码、无用参数、无用函数、不必要的依赖、过度设计，以及安全、性能和公共能力方面的潜在风险。

对于明确的问题，AI 可以自动修改并重新测试。

人工在代码阶段主要关注高风险变更，例如全局状态、核心业务逻辑、权限、安全、公共组件、公共方法以及大范围重构，因为这些修改可能影响多个页面或者已有功能。

所以这一阶段的核心不是“AI 能不能把代码写出来”，而是：

> **AI 是否能够按照已经确定的规范和 Task 小批量实现，并持续证明每一步修改都是必要、正确和可控的。**

---

### 【第四阶段：测试验收】

测试验收阶段解决的核心问题是：

> **如何证明当前代码真的满足前面已经确定的需求。**

首先是功能验收。

按照技术分析阶段已经确定的 Test Case，基于前置条件和预期结果逐项验证功能。

传统自动化测试通常提前写死测试步骤和输入；现在也可以通过 Browser Agent（浏览器智能体），只提供 Test Case 的前置条件和预期结果，由 AI 根据页面当前状态自主判断下一步如何操作。

也就是说：

> **AI 可以自主决定“怎么验”，但是不能自己决定“什么算正确”。**

验收标准仍然必须来自前面已经确定的 Test Case。

第二部分是覆盖率检查。

一方面检查 Requirement Coverage（需求覆盖率），确认所有重要需求场景和边界条件都有对应 Test Case。

另一方面检查 Code Coverage（代码覆盖率），判断重要的代码行、函数和分支是否真正被执行过。

如果某些代码分支在正常、异常和测试场景中始终无法进入，就需要进一步判断到底是测试遗漏，还是代码本身已经不可达或者属于冗余逻辑。

第三部分是代码质量检查。

AI 可以基于团队沉淀的代码规范、安全规范、架构规范和知识库，对当前代码从安全性、可维护性、可扩展性、兼容性等角度进行 Review，并自动修复明确的问题。

最后是 Quality Gate（质量门禁）。

AI 自动化验收最关键的问题，不是 AI 能不能把页面操作完，而是：

> **怎么证明 AI 给出的验收结论可信。**

所以每一个 Test Case 都不能只留下 PASS，而应该建立：

> **Test Case → Expected Result → Actual Result → Evidence → Pass / Fail**

Evidence 可以包括截图、接口请求、日志、DOM 状态、Mock 命中记录以及操作轨迹。

最终需要检查 Test Case 是否全部执行、实际结果是否符合预期、证据是否充分、执行过程和最终结论是否一致。

对于高风险需求，最终质量门禁仍然需要人工审查和放行。

所以整个测试验收阶段最关键的一句话是：

> **AI 可以负责执行验收，但验收是否可信，必须由预先确定的 Test Case、完整证据链和独立质量门禁共同证明。**

---

### 【第五阶段：交付上线】

测试验收通过以后，最后进入交付上线阶段。

首先通过 CI/CD 的自动化门禁执行 Build、Test、安全检查、Review 等流程，保证只有满足要求的代码才能进入正式发布。

之后形成明确的 Release（发布版本），再经过回归测试、发布前验证以及必要的小流量或灰度验证。

对于高风险需求，可以先发布给少量用户，观察错误率、接口异常、核心业务指标等情况，再逐步扩大流量；出现异常时及时停止或者回滚。

最终上线以后，还要回到需求分析阶段最开始定义的业务目标和成功指标。

因为：

> **代码成功上线，只能证明 Delivery Success（交付成功），并不能证明 Business Success（业务成功）。**

最终还要通过线上数据判断：

> 最开始定义的问题是不是真的被解决了。

因此整个研发过程最终形成一个闭环：

> **业务问题 → 需求分析 → 技术分析 → 代码开发 → 测试验收 → 交付上线 → 数据反馈 → 下一轮需求。**

---

整体来看，我理解的 AI Native 软件工程化，不是简单地把原来的研发流程全部交给 AI，而是：

> 通过规范、验证、可追溯和风险控制四条主线，重新设计人和 Agent 的协作方式。AI 承担越来越多分析、开发、测试和修复工作，人则重点负责目标定义、规范确认、风险判断和最终质量放行，再通过需求分析、技术分析、代码开发、测试验收和交付上线五个阶段，把一个业务问题稳定地转换成可以安全交付的软件。
