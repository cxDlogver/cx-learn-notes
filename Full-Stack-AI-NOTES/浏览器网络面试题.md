## 跨域问题

### 面试题 1：什么是跨域？为什么会有跨域问题？

**回答模板：**
 跨域本质是**浏览器的同源策略限制**。
 同源指的是：**协议、域名、端口**三者完全一致。
 只要三者中任意一个不同，浏览器就会认为是跨域，从而**限制前端脚本读取响应内容**，以防止恶意网站窃取用户数据。
 需要注意的是：**跨域是浏览器层面的安全限制，服务器本身并不受影响**。

### 面试题 2：同源策略限制了哪些行为？

**回答模板：**
 同源策略主要限制的是：

- JS 读取跨域响应内容（`response / responseText`）
- 跨域 Cookie 的自动携带与读取
- 跨域 DOM、Storage 的访问

但**不会限制请求是否发出**，例如：
 `img / script / link / form` 都可以发起跨域请求，并且能够绕过跨域问题

### 面试题 3：前端常见的跨域解决方案有哪些？

第一种：CORS（跨域资源共享，最标准）

CORS 是 **浏览器制定的一套跨域访问规范**。
 浏览器会根据这套规范，**通过请求头和响应头来判断是否允许跨域访问**。

核心思想是：

> **是否允许跨域，不由前端决定，而是由服务器通过响应头声明。**

服务器可以通过设置诸如：

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`
- `Access-Control-Allow-Credentials`

来精细化控制哪些源、哪些方法、哪些请求头可以跨域访问。

CORS 支持：

- 所有 HTTP 方法
- 复杂请求
- Cookie / 认证信息

因此它是**生产环境中最规范、最安全、最常用的跨域方案**。

------

第二种：反向代理（工程中非常常见）

反向代理的核心原理是：

> **Same-Origin Policy（同源策略）是浏览器安全机制；服务端到服务端的转发不受浏览器同源策略约束。**

具体做法是：

- 在前端同源的服务器上设置一台代理服务器（如 Nginx、开发服务器）
- 浏览器请求代理服务器（同源请求）
- 代理服务器再向真实后端服务器转发请求
- 后端返回数据给代理服务器
- 代理服务器再将数据转发给浏览器

从浏览器视角来看：

- 请求始终是**同源请求**
- 因此**不会触发跨域问题**

这种方式：

- **开发环境非常常见**
- 生产环境也常用于 API 网关、统一入口

反向代理的完整网络位置、Upstream、Forwarded Header、静态 Web、Docker Runtime 与 Caddy / Nginx 实现统一参考 [反向代理与 Web 入口体系](./反向代理与Web入口体系.md)。本节只保留“它为什么能让浏览器保持同源”的面试视角。

------

第三种：JSONP（已过时）

JSONP 是一种**早期的跨域解决方案**，原理是：

- 利用 `<script>` 标签**不受同源策略限制**
- 通过 URL 参数传递一个回调函数名
- 服务器返回一段**调用该回调函数的 JS 代码**
- 浏览器执行这段 JS，从而获取数据

这种方式的缺点非常明显：

- **只支持 GET 请求**
- 存在安全风险
- 不符合现代前后端分离架构

因此 **现在基本已经被淘汰，不推荐使用**。

- 有安全风险，基本不再推荐

### 面试题 4：为什么有的请求会触发 CORS 预检（OPTIONS）？

> 浏览器根据 CORS 规范将跨域请求分为简单请求和非简单请求。
>  当请求不满足简单请求条件，比如使用 `application/json` 或自定义请求头时，会先发送一次 `OPTIONS` 预检请求，用于确认服务器是否允许跨域访问。
>  预检结果可以通过 `Access-Control-Max-Age` 缓存，避免每次都触发。

标准回答模板

有些请求会触发 CORS 预检，是因为**浏览器根据 CORS 规范，将跨域请求分为「简单请求」和「非简单请求」两类**。

当浏览器判定当前请求是**非简单请求**时，会在真正的业务请求之前，**先自动发送一次 `OPTIONS` 预检请求**，用来确认服务器是否允许该跨域请求。

------

一、什么情况下会触发预检请求？

只要请求**不满足简单请求的条件**，浏览器就会触发 `OPTIONS` 预检。

------

二、什么是简单请求？

简单请求必须**同时满足以下三个条件**：

#### 1️⃣ 请求方法只能是三种之一

- `GET`
- `POST`
- `HEAD`

------

#### 2️⃣ 请求头只能是 CORS 规范允许的“安全请求头”

通常情况下：

> **只要不手动添加自定义请求头（如 `Authorization`），就满足这一条件**

------

#### 3️⃣ Content-Type 只能是以下三种之一

- `text/plain`
- `multipart/form-data`
- `application/x-www-form-urlencoded`

⚠️ **重点：**

> `application/json` **不属于简单请求的 Content-Type**

因此：

- 只要使用 `application/json` 发送请求
- 浏览器就会将其判定为 **非简单请求**
- 从而触发 `OPTIONS` 预检

------

三、什么是 OPTIONS 预检请求？

`OPTIONS` 预检请求的作用是：

> **在真正发送跨域请求之前，先询问服务器是否允许本次跨域访问**

服务器会在预检响应中返回：

- 是否允许该源访问
- 是否允许该请求方法
- 是否允许这些请求头
- 是否允许携带 Cookie

如果预检通过：

- 浏览器才会发送真正的业务请求（GET / POST 等）

如果预检失败：

- **浏览器直接拦截**
- 业务请求根本不会发出

------

四、为什么不是每次都发送 OPTIONS？

CORS 允许服务器通过响应头：

```
Access-Control-Max-Age
```

指定：

> **预检结果的缓存时间**

在该时间内：

- 浏览器不会重复发送 OPTIONS
- 可以直接复用上一次的预检结果
- 这是 CORS 的重要性能优化机制

### 面试题 5: 一次非简单请求的完整校验是怎样的？

### 标准回答模板（紧凑版）

一次**非简单跨域请求**的完整校验流程，严格按照 **CORS 规范**分为以下几个步骤：

------

**1️⃣ 浏览器判定请求类型**
 浏览器在发起请求前，会先根据 CORS 规则判断是否为非简单请求：

- 使用了非简单方法
- 使用了自定义请求头（如 `Authorization`）
- `Content-Type` 为 `application/json`
   只要满足任意一条，就会进入预检流程。

------

**2️⃣ 发送 OPTIONS 预检请求**
 浏览器自动向目标服务器发送 `OPTIONS` 请求，用于“探测”是否允许跨域。
 预检请求中会携带：

- `Origin`
- `Access-Control-Request-Method`
- `Access-Control-Request-Headers`

------

**3️⃣ 服务器返回预检响应**
 服务器根据自身 CORS 配置返回响应头：

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`
- （可选）`Access-Control-Allow-Credentials`
- （可选）`Access-Control-Max-Age`

------

**4️⃣ 浏览器校验预检结果**
 浏览器会对响应头进行校验：

- 源是否被允许
- 方法是否被允许
- 请求头是否被允许

若任意一项不通过，流程直接终止，**业务请求不会发送**。

------

**5️⃣ 发送真正的业务请求**
 预检通过后，浏览器才会发送真正的跨域请求（GET / POST / PUT 等），并携带 Cookie（如已开启 credentials）。

------

**6️⃣ 浏览器校验业务响应**
 浏览器再次检查业务响应中的 CORS 头：

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Credentials`
   校验通过后，JS 才能正常读取响应数据。

------

**7️⃣ 预检结果缓存（性能优化）**
 如果服务器返回了 `Access-Control-Max-Age`，
 在有效期内，相同请求将**不再重复发送 OPTIONS 预检**。

------

### 面试题 6：跨域请求为什么 Cookie 传不过去？

**回答模板：**
 跨域 Cookie 需要**前后端同时满足条件**：

- 前端：
  - `xhr.withCredentials = true`
- 后端：
  - `Access-Control-Allow-Credentials: true`
  - `Access-Control-Allow-Origin` 不能为 `*`

缺一不可，否则浏览器会直接拦截 Cookie。

------

### 面试题 7：OPTIONS 请求失败会发生什么？

**回答模板：**
 如果 OPTIONS 预检失败：

- 浏览器**不会发送真正的业务请求**
- 控制台会直接报 CORS 错误
- 后端日志中通常只看到 OPTIONS，没有 GET/POST

这是前端“看似请求没发出去”的常见原因。

### 面试题 8：开发环境是怎么解决跨域的？

**回答模板：**
 开发环境通常使用**本地代理**：

- Vite / Webpack Dev Server
- 将 `/api` 请求代理到真实后端
- 浏览器认为请求仍然是同源

这种方式**只解决开发阶段问题**，生产环境仍需 CORS 或网关代理。

------

### 面试题 9：为什么 Postman 没有跨域问题？

**回答模板：**
 因为跨域是**浏览器的安全策略**。
 Postman、curl、后端服务之间的请求：

- 不受同源策略限制
- 可以自由访问任何接口

这也是“Postman 能通，前端不通”的根本原因。

### 面试题10： Nginx 的特点是什么？常见的三大作用？

> Nginx 是一个高性能的 Web 服务器和反向代理服务器，采用事件驱动模型，支持高并发、低内存占用。
>  常见三大作用是：作为静态资源服务器、反向代理服务器以及负载均衡器，在前后端分离和高并发架构中非常常见。

一、Nginx 的核心特点（先说优势）

**标准回答模板：**
 Nginx 是一个**高性能的 Web 服务器和反向代理服务器**，核心特点是：

- **事件驱动、异步非阻塞 I/O**（单进程可支撑大量并发）
- **高并发、低内存占用**（C10K 问题的经典解决方案）
- **配置简单、模块化清晰**
- **稳定性强，适合长期运行**

一句话概括：

> Nginx 用更少的资源，支撑更多的并发连接。

------

二、Nginx 的三大常见作用（必考重点）

------

1️⃣ Web 服务器（静态资源服务器）

**作用说明：**

- 直接对外提供 HTTP 服务
- 高效处理：
  - HTML
  - CSS / JS
  - 图片 / 视频等静态资源

**优势：**

- 静态资源处理能力极强
- 比后端应用服务器（如 Node / Java）更省资源
- 常用于**前后端分离架构中的静态资源托管**

------

2️⃣ 反向代理服务器（最常用）

**作用说明：**

- 浏览器 → Nginx → 后端服务
- 客户端只感知 Nginx，不直接访问后端

**典型用途：**

- **解决跨域问题**
- 隐藏真实后端地址
- 统一入口（API Gateway）
- 请求转发、权限隔离

**核心原理一句话：**

> 浏览器与 Nginx 同源，服务器与服务器之间不存在跨域问题。

------

3️⃣ 负载均衡器（高并发架构核心）

**作用说明：**

- 将请求分发到多台后端服务器
- 避免单点瓶颈

**常见策略：**

- 轮询（默认）
- 权重轮询
- IP Hash
- 最少连接数

**典型场景：**

- 高并发 Web 服务
- 微服务架构
- 集群部署

### 面试题11：Web 服务器和应用服务器的区别是什么？

标准回答模板

Web 服务器和应用服务器的核心区别在于：
 **Web 服务器主要负责处理 HTTP 请求和静态资源，而应用服务器负责执行业务逻辑并生成动态内容。**

------

**Web 服务器：**

- 主要职责是接收 HTTP 请求、返回静态资源（HTML、CSS、JS、图片等）
- 也常作为反向代理，将请求转发给后端应用
- 特点是高并发、低资源消耗
- 常见的有：Nginx、Apache

**应用服务器：**

- 主要职责是执行业务逻辑，处理动态请求
- 通常需要访问数据库、缓存等后端资源
- 返回的是动态生成的数据或页面（如 JSON、HTML）
- 常见的有：Node.js、Tomcat、Spring Boot、Django 等

------

**实际项目中通常是两者配合使用：**

- Web 服务器作为统一入口，处理静态资源和请求转发
- 应用服务器专注于业务逻辑处理

------

一句话总结（面试加分）

> Web 服务器负责“接收和转发请求、提供静态资源”，
>  应用服务器负责“执行业务逻辑、生成动态数据”，
>  两者分工协作是现代 Web 架构的常见模式。

------

30 秒极简版

> Web 服务器主要处理 HTTP 和静态资源，比如 Nginx；
>  应用服务器主要处理业务逻辑和动态请求，比如 Node 或 Java 服务；
>  实际项目中通常由 Web 服务器作为入口，再将请求交给应用服务器处理。

### 面试题12： 手写Nginx和Vue配置代理服务器的代码？

`nginx`

> 放到 `nginx.conf` 的 `http {}` 里或单独的 `conf.d/app.conf`

```js
server {
  listen 80;
  server_name localhost;

  # 反向代理：/api -> 后端
  location /api/ {
    proxy_pass http://127.0.0.1:8080/;  # 注意结尾的 /
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

> 如果你希望把 `/api` 前缀去掉再转发（上面已经是“去掉”的效果），关键就是 `location /api/` + `proxy_pass .../` **都带尾部 `/`**。

`vite.config.ts`

```js
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://127.0.0.1:8080",
        changeOrigin: true,
        // 如果后端不需要 /api 前缀就打开下面这行
        // rewrite: (path) => path.replace(/^\/api/, ""),
      },
    },
  },
});
```

## HTTP请求

### 面试题1：一次完整的 URL 请求通常会经历哪些步骤？

> 一次完整的 URL 请求通常会经历：**URL 解析 → DNS 解析 → 建立连接（TCP/UDP + TLS）→ 发送 HTTP 请求 → 服务端处理并返回 → 浏览器接收与缓存处理 → 解析渲染页面（HTML/CSS/JS）→ 资源加载与执行 → 首屏呈现与后续交互**。

**1）输入 URL 与浏览器预处理**

- **解析 URL**：协议（http/https）、域名、端口、路径、query、hash
- **HSTS/升级**：可能把 http 自动升级为 https
- **查缓存/预连接**：浏览器可能命中 **DNS 缓存 / 连接池 / HTTP 缓存**，命中则跳过部分步骤

**2）DNS 解析（把域名变成 IP）**

- 查询顺序通常是：**浏览器 DNS 缓存 → 系统缓存 → hosts → 本地 DNS → 递归解析（根/顶级/权威）**
- 结果会有 **TTL**，决定缓存时长
- 性能优化：`dns-prefetch`、减少跨域域名数量

**3）建立连接（传输层 + 安全层）**

**3.1 TCP（三次握手）**（HTTP/1.1、HTTP/2 通常跑在 TCP 上）

- SYN → SYN/ACK → ACK
- 建立后进入连接复用（Keep-Alive）

**3.2 TLS 握手（HTTPS 才有）**

- 证书校验、协商加密套件、生成会话密钥
- 优化点：TLS1.3、会话复用、OCSP Stapling

> 补充：HTTP/3 基于 **QUIC(UDP)**，把“传输层握手 + TLS”合并加速，减少延迟（面试可加分一句）。

**4）发送 HTTP 请求（应用层）**

- 组成：**请求行（method/path）+ headers + body**
- 常见行为：
  - 携带 Cookie / Authorization
  - `Accept-Encoding` 触发 gzip/br 压缩
  - 跨域且“非简单请求”会先发 **OPTIONS 预检**

**5）服务端处理与返回响应**

- 典型链路：**CDN/反向代理(Nginx) → 应用服务器 → DB/缓存/微服务**
- 返回：**状态码、响应头（缓存/类型/长度）、响应体**
- 性能指标：TTFB（Time To First Byte）

**6）浏览器接收响应：缓存与连接管理**

- 根据响应头决定缓存策略：
  - 强缓存：`Cache-Control: max-age` / `Expires`
  - 协商缓存：`ETag/If-None-Match`、`Last-Modified/If-Modified-Since`
- `304 Not Modified` 走协商缓存，减少下载

**7）解析与渲染（浏览器渲染流水线）**

- **解析 HTML → DOM**
- **解析 CSS → CSSOM**
- DOM + CSSOM → **Render Tree**
- **Layout（回流）→ Paint（绘制）→ Composite（合成）**
- JS 可能阻塞解析（尤其是同步脚本），并触发重排/重绘

**8）资源加载与执行（并行/优先级）**

- 遇到 `link/script/img` 会发起更多请求
- HTTP/2 多路复用提升并发效率；浏览器也有优先级调度
- `defer/async`、`preload/prefetch` 会影响加载顺序与首屏

**9）页面可用：首屏、交互、后续请求**

- 首屏渲染完成后进入交互期
- SPA 场景下：后续路由切换多为 **JS 驱动渲染**，但接口请求仍走同样的网络链路

### 面试题2：DNS解析的步骤是什么？

**步骤：**

1. **浏览器缓存**：检查是否有未过期的 DNS 记录（TTL）
2. **操作系统缓存 / hosts**：本地 DNS Cache 与 hosts 文件
3. **本地 DNS 服务器（递归解析器）**：通常由运营商或企业提供
4. **根域名服务器（.）**：返回对应的顶级域服务器地址
5. **顶级域服务器（TLD，如 .com）**：返回目标域名的权威 DNS 服务器
6. **权威 DNS 服务器**：返回最终解析结果（A / AAAA / CNAME）
7. **结果缓存并返回**：递归服务器、OS、浏览器按 TTL 缓存，浏览器使用 IP 建立连接

> 客户端**递归**地把解析任务交给本地 DNS，本地 DNS 再**迭代**地向各级域名服务器查询，最终拿到 IP 并返回。

### 面试3：**TCP 连接是怎么建立的？**

**口述模板：**

TCP 通过**三次握手**建立连接，核心目的有三个：
 **确认双方收发能力、同步初始序列号、防止历史连接误建立。**

第一次，**客户端发送 SYN**，表示我要建立连接，并告诉服务端我的初始序列号；

第二次，**服务端返回 SYN + ACK**，表示我收到了你的请求，同时告诉客户端我的初始序列号；

第三次，**客户端再回一个 ACK**，表示我确认收到了你的确认，至此双方状态一致，连接建立完成。

#### 面试题：**三次握手过程中如果报文丢失，会发生什么？**

TCP 在三次握手过程中，对任意一次报文丢失都设计了**超时重传和状态回退机制**。

------

第一种情况：第一次 SYN 丢失

客户端发送 SYN 后进入 **SYN-SENT 状态**。
 如果服务器没有收到该 SYN，就不会返回任何响应。
 客户端在超时后会**重传 SYN**，多次失败后连接建立失败。

------

第二种情况：第二次 SYN+ACK 丢失

服务器收到 SYN 后，会返回 **SYN+ACK**，并进入 **SYN-RECEIVED（半连接）状态**。
 如果这个 SYN+ACK 丢失：

- 客户端仍处于 SYN-SENT，会**重传 SYN**
- 服务器在半连接状态下，会**重传 SYN+ACK**

双方不断重试，直到成功完成握手或超时清理半连接。

------

第三种情况：第三次 ACK 丢失

客户端收到 SYN+ACK 后，会立即发送 ACK，并认为连接已建立。
 如果这个 ACK 丢失：

- 服务器仍停留在 **SYN-RECEIVED 状态**
- 会再次发送 SYN+ACK
- 客户端每次收到重复的 SYN+ACK，都会**重新发送 ACK**

最终服务器收到 ACK，连接建立；否则超时释放半连接。

------

总结收尾（一定要说）

> 三次握手的设计可以确保通信双方都具备收发能力，
>  并同步初始序列号，同时防止服务器因异常或丢包长期处于半连接状态。

#### **什么不能两次握手？**

**口述模板：**

如果只有两次握手，服务端无法确认客户端是否真的收到了确认包，
 一旦出现**延迟的旧 SYN 报文**，服务端可能会错误地建立连接，造成资源浪费。
 第三次握手的作用，就是**确认客户端的接收能力并清理历史请求**。

### 面试题：**为什么 TCP 不能只用两次握手？**

口述回答模板（清晰版）

TCP 不能只用两次握手，**核心原因是无法避免服务器长期处于半连接状态，从而占用服务器资源**。

------

第一层原因：**无法确认客户端的接收能力**

如果只有两次握手：
 客户端发送 **SYN**，服务器返回 **SYN + ACK** 后就认为连接建立。

但如果这个 **SYN + ACK 丢失**：

- 服务器已经进入 **半连接状态（SYN-RECEIVED）**
- 客户端由于收不到响应，会判断连接失败
- 服务器却无法确认客户端是否存在，**只能等待超时**

第三次握手的 ACK，作用就是**明确告诉服务器：客户端确实收到了你的响应**。

------

第二层原因：**无法防止历史延迟的 SYN 造成错误连接**

如果网络中存在**延迟的旧 SYN 报文**：

- 客户端早已放弃该连接
- 延迟的 SYN 在之后到达服务器

在两次握手模型下：

- 服务器会误认为这是一次新的连接请求
- 从而建立一个**无效的半连接**

第三次 ACK 可以明确区分：

- 这是一次真实的当前连接
- 还是一条历史失效请求

------

第三层原因（安全层面）：**容易被 SYN Flood 攻击**

如果只有两次握手：
 攻击者可以持续向服务器发送大量 **SYN 请求**，
 但**从不发送最后的确认**。

服务器就会：

- 维持大量半连接
- 占用 TCP 控制块和内存资源
- 导致正常用户无法建立连接

这类攻击称为 **SYN Flood（半连接攻击）**。

------

总结收尾（一定要说）

> 第三次握手的存在，不仅是为了完成连接确认，
>  更重要的是**防止服务器因异常、延迟或攻击长期处于半连接状态**，
>  从而保证 TCP 连接的可靠性和安全性。

### 面试题：**TCP 连接是怎么断开的？**

**口述模板：**

TCP 通过**四次挥手**断开连接，
 这是因为 TCP 是**全双工协议**，双方的发送方向必须**分别关闭**。

------

第一次挥手：客户端 → 服务器（FIN）

客户端向服务器发送 **FIN 报文**，
 表示：**客户端已经没有数据要发送了**，
 此时客户端进入 **FIN-WAIT-1 状态**。

------

第二次挥手：服务器 → 客户端（ACK）

服务器收到 FIN 后，返回 **ACK 报文**，
 表示：**已确认客户端的关闭请求**。

此时：

- 客户端不再发送数据
- 但服务器仍然可以向客户端发送数据
- 连接尚未完全关闭

------

第三次挥手：服务器 → 客户端（FIN）

当服务器把**剩余数据全部发送完毕后**，
 会向客户端发送 **FIN 报文**，
 表示：**服务器也准备关闭发送方向**。

------

第四次挥手：客户端 → 服务器（ACK）

客户端收到服务器的 FIN 后，
 返回 **ACK 报文**，
 至此，服务器连接关闭，客户端进入 **TIME_WAIT 状态**。

------

#### **为什么断开是四次，而建立是三次？**

**口述模板：**

建立连接时，服务端可以把 **SYN 和 ACK 合并发送**，是因为**服务器在确认客户端关闭请求时，可能还有数据没有发送完**。

- 第二次的 **ACK**：只是确认客户端“我知道你要关了”
- 第三次的 **FIN**：是服务器真正关闭自己发送方向的请求

这两个动作**在时间上不一定同时发生**，
 因此一般不能合并发送。

#### TIME_WAIT 状态的作用

**口述模板：**

客户端在发送最后一个 ACK 后，并不会立刻关闭连接，
 而是进入 **TIME_WAIT 状态**，通常持续 **2MSL**。

TIME_WAIT 的作用有两点：

1. **确保服务器能够收到最后一个 ACK**
2. **防止旧连接的延迟报文影响新连接**

因此，TIME_WAIT 状态**经常出现在客户端**，
 因为**主动关闭连接的一方会进入 TIME_WAIT**。

### 面试题：**TCP 是怎么保证可靠传输的？**

**口述模板：**

TCP 通过五个核心机制保证可靠性：
 **序列号保证顺序、ACK 确认接收、超时重传防止丢包、滑动窗口保证连续传输、
 流量控制和拥塞控制防止压垮接收方和网络。**

------

### 面试题：**流量控制和拥塞控制有什么区别？**

**口述模板：**

**流量控制**关注的是**接收方是否接得住**，
 TCP 通过**接收窗口 rwnd**实现，
 接收方在 ACK 中告诉发送方还能接收多少数据，
 发送方发送的数据量不能超过 rwnd，
 本身**没有复杂算法**，是一个动态窗口调节机制。

**拥塞控制**关注的是**网络是否扛得住**，
 TCP 通过**拥塞窗口 cwnd**控制发送速率，
 实际发送窗口大小是 **min(rwnd, cwnd)**，
 拥塞控制包含一套完整算法体系。

经典的拥塞控制算法包括：
 **慢启动**：cwnd 从小开始指数增长；
 **拥塞避免**：达到阈值后线性增长；
 **快重传**：收到 3 个重复 ACK 立即重传；
 **快恢复**：重传后不回慢启动，直接进入拥塞避免。

#### TCP 拥塞控制完整流程

1️⃣ 慢启动（Slow Start）

- 连接建立后，**cwnd 从 1 MSS 开始**
- **每收到一个 ACK，cwnd 翻倍增长**
- 目的：**快速探测网络的承载能力**
- 当 **cwnd ≥ ssthresh（慢启动阈值）** → 进入拥塞避免

------

2️⃣ 拥塞避免（Congestion Avoidance）

- cwnd **不再指数增长**
- 改为：**每个 RTT 线性增长 1 MSS**
- 目的：**避免过快增长引发网络拥塞**
- 如果此阶段**发生丢包** → 触发重传机制

------

3️⃣ 快重传（Fast Retransmit）

- 如果发送方收到 **3 个重复 ACK**
- 判断：**某个数据包丢失**
- **不等待超时，立即重传丢失报文**
- 同时调整阈值：
  - `ssthresh = 当前 cwnd / 2`

------

4️⃣ 快恢复（Fast Recovery）

- 重传完成后：
  - **cwnd 直接降到 ssthresh**
  - **不回到慢启动**
- 直接进入 **拥塞避免阶段**
- 目的：**快速恢复吞吐量，避免从头开始**

------

一句话流程总结（强背）

> TCP 先慢启动指数增长，
>  到阈值后拥塞避免线性增长，
>  出现丢包触发快重传，
>  再通过快恢复直接回到拥塞避免。

### 面试题：TCP 和 UDP 有什么区别？

口述模板（紧凑版）

TCP 和 UDP 的核心区别是：
 **TCP 面向连接、可靠、有序；UDP 无连接、不可靠、无序，但实时性更好。**

**连接方式**：

- TCP 需要三次握手、四次挥手
- UDP 直接发送，不建立连接

**可靠性**：

- TCP 通过序列号、ACK、重传、流量控制和拥塞控制保证可靠
- UDP 不确认、不重传、不保证顺序

**数据形式**：

- TCP 面向字节流，可能粘包
- UDP 面向报文，保留消息边界

**性能特点**：

- TCP 延迟较高但稳定
- UDP 延迟低、开销小

**典型场景**：

- TCP：HTTP/HTTPS、文件传输
- UDP：音视频、实时通信、DNS

### 面试题：**WebSocket 可以代替 UDP 的适用场景吗？**

口述模板（先给结论）

**WebSocket 不能完全代替 UDP 的适用场景，只能覆盖其中一部分。**
 因为两者的“实时性”来源于**不同的层次**。

------

一、WebSocket 的实时性是什么？

**口述模板：**

WebSocket 的实时性体现在**应用层**，
 它相对于 HTTP 的优势在于：

- 连接是**长连接**
- **服务器可以主动向客户端推送数据**

但 WebSocket **本质仍然是基于 TCP 的**，
 数据依然以 **TCP 报文**传输，
 必须满足 TCP 的可靠性机制，包括：

- 流量控制
- 拥塞控制
- 超时重传
- 有序传输

因此，WebSocket 的实时性是
 **“可靠前提下的实时”**。

------

二、UDP 的实时性是什么？

**口述模板：**

UDP 的实时性体现在**传输层**，
 它通过**主动牺牲可靠性**来换取极低延迟。

UDP 的特点是：

- 无连接
- 不确认
- 不重传
- 无流量控制、无拥塞控制

数据一发即走，
 **延迟最低，但可能丢包、乱序**。

------

三、为什么 WebSocket 不能代替 UDP？

**口述模板：**

由于 WebSocket 运行在 TCP 之上，
 必须遵守 TCP 的可靠性和控制机制，
 在网络拥塞或丢包时：

- 会等待确认
- 会触发重传
- 会降低发送速率

这些机制虽然保证了可靠性，
 但也决定了 **WebSocket 无法达到 UDP 的超低延迟**。

------

四、各自适用场景（面试官很爱听）

**WebSocket 适用场景：**

- 即时聊天（IM）
- 实时通知 / 推送
- 在线协作
- 实时监控面板
   👉 **要求实时，但不能丢消息**

**UDP 适用场景：**

- 音视频通话 / 直播
- 实时游戏状态同步
- 高速传感器数据
   👉 **允许丢数据，但不能卡**

### 面试题：**浏览器缓存有哪些？强缓存和协商缓存有什么区别？**

口述模板（先给结论）

浏览器缓存主要分为**强缓存**和**协商缓存**。
 **强缓存优先级最高，其次才是协商缓存。**

------

一、强缓存（Strong Cache）

**口述模板：**

强缓存是指**浏览器直接从本地读取资源**，
 **不再向服务器发送 HTTP 请求**。

强缓存通过响应头来控制：

- **`Expires`**：设置一个绝对过期时间（HTTP/1.0）
- **`Cache-Control: max-age`**：设置相对过期时间（HTTP/1.1，优先级更高）

只要资源在有效期内：

- 浏览器直接使用缓存
- 状态码通常显示为 **200（from cache）**

------

二、协商缓存（Conditional Cache）

**口述模板：**

当强缓存**失效或未命中**时，
 浏览器会向服务器发送请求，
 **询问资源是否发生变化**，这就是协商缓存。

协商缓存依赖的字段主要有：

- **`Last-Modified / If-Modified-Since`**
- **`ETag / If-None-Match`**

如果资源**没有发生变化**：

- 服务器返回 **304 Not Modified**
- 浏览器继续使用本地缓存

如果资源**发生变化**：

- 服务器返回 **200 + 最新资源**
- 浏览器更新本地缓存

#### 浏览器缓存本质是什么？

**口述模板：**

浏览器缓存本质上是 **HTTP 缓存机制**，
 用于**减少网络请求、提升加载性能**。

它的特点是：

- 缓存的是 **HTTP 请求返回的资源**
- 是否缓存、缓存多久 **由服务器响应头控制**
- **浏览器自动管理**，前端不可精细干预
- 参与 **强缓存 / 协商缓存 / 304** 流程

所以它是**网络通信过程的一部分**。

#### 点击刷新按钮或者按 F5、按 Ctrl+F5 （强制刷新）、地址栏回车有什么区别？

- **点击刷新按钮或者按 F5：**浏览器直接对本地的缓存文件过期，但是会带上If-Modifed-Since，If-None-Match，这就意味着服务器会对文件检查新鲜度，返回结果可能是 304，也有可能是 200。
- **用户按 Ctrl+F5（强制刷新）：**浏览器不仅会对本地文件过期，而且不会带上 If-Modifed-Since，If-None-Match，相当于之前从来没有请求过，返回结果是 200。
- 地址栏回车： 浏览器发起请求，按照正常流程，本地检查是否过期，然后服务器检查新鲜度，最后返回内容。

### 面试题：浏览器的存储方式有哪些？

从工程视角看，浏览器存储主要分为四类：协议级存储 Cookie、页面级状态存储 Web Storage、本地数据层 IndexedDB，以及网络缓存层 Cache API。

Cookie 是 HTTP 协议级存储机制，主要用于会话保持和身份识别，最大特点是会在满足条件时自动随请求发送给服务器，并支持 HttpOnly、Secure、SameSite 等安全属性，因此非常适合存放 Session ID 等高安全信息，但不适合存储业务数据。

localStorage 和 sessionStorage 属于 Web Storage，用于在前端持久化保存少量状态数据，不参与 HTTP 请求。二者区别在于生命周期：localStorage 是持久化的、同源多标签共享；sessionStorage 只在当前标签页有效。它们都是同步 API，适合存储用户偏好或页面中间态，但不适合高频、大数据或安全敏感信息。

IndexedDB 是浏览器内置的本地数据库，支持异步 API、对象存储、索引和事务，能够存储大规模结构化数据。所有读写操作必须在事务中完成，通过原子提交和自动回滚保证数据一致性，因此 IndexedDB 通常作为前端的数据层，用于离线应用、大数据缓存或实时系统的数据缓冲。

Cache API 是用于缓存 HTTP 请求与响应的存储机制，通常与 Service Worker 配合使用，主要解决静态资源缓存、接口响应缓存、离线访问和首屏性能优化等问题。它缓存的是 Request-Response，而不是业务对象，与 IndexedDB 的职责是明确区分的。

总体来说，浏览器存储并不是相互替代关系，而是协议层、状态层、数据层和网络层各司其职，在实际工程中往往需要组合使用。

### 面试题：HTTP 不同版本协议的区别？

口述模板（按时间线）

**HTTP/1.0**

- 短连接，请求完成即断开
- 每个请求都要重新建 TCP 连接，效率低

**HTTP/1.1**

- 支持长连接（Keep-Alive）
- 支持 Host 头，完善缓存控制
- 仍然是**串行请求**，存在队头阻塞

**HTTP/2**

- 基于 TCP
- **多路复用**：一个连接并发多个请求
- 二进制分帧、头部压缩、服务端推送
- 解决应用层队头阻塞，但仍受 TCP 丢包影响

**HTTP/3**

- 基于 **QUIC（UDP）**，不再使用 TCP
- 每个流独立，**彻底解决队头阻塞**
- 建连更快（0-RTT），支持连接迁移

### 面试题：**HTTPS 是什么？它是如何保证安全性的？**

> [9.浏览器安全协议 - 相](https://cxdlogver.github.io/2025/12/28/前端面试/9-浏览器安全协议/)

HTTPS（HyperText Transfer Protocol Secure）是 **HTTP + TLS/SSL** 的组合。
 它的本质是：**在 HTTP 的基础上，通过 TLS 协议为通信提供安全保障**，确保浏览器与服务器之间的数据传输是安全的。

HTTPS 主要解决三个问题：

- **数据是否被窃听**
- **数据是否被篡改**
- **服务器身份是否可信**

> HTTPS 通过非对称加密完成身份认证和密钥协商，再使用对称加密进行高效的数据传输，并结合完整性校验，保证通信过程不被窃听和篡改。

HTTPS 本质上是 **HTTP + TLS 协议**，它的核心作用是 **在不安全的网络环境中，保证浏览器与服务器之间通信的安全性**，主要解决三类问题：**数据是否被窃听、是否被篡改、以及服务器身份是否可信**。

首先，HTTP 本身是明文传输的，如果只做数据完整性校验，比如使用哈希函数，中间人依然可以截获请求、修改内容、重新计算摘要，再转发给服务器，这样完整性校验仍然可以通过，所以 **单纯依赖哈希并不能保证安全**。

因此 HTTPS 的第二层是 **对数据进行加密传输**。在实际通信过程中，HTTPS 使用的是 **对称加密算法**。对称加密的特点是通信双方使用同一把密钥进行加解密，性能高、速度快，适合 HTTP 这种高频、持续的数据传输场景。

但对称加密存在一个核心问题：**通信双方必须先安全地协商出这把对称密钥**，而密钥协商本身又需要通过网络进行，这时网络仍然是不安全的。

为了解决这个问题，HTTPS 引入了 **非对称加密机制**。非对称加密有一对密钥：公钥和私钥。公钥是公开的，私钥只由服务器持有。客户端可以使用服务器的公钥加密数据，只有持有私钥的服务器才能解密，这样可以保证密钥协商过程不被中间人破解。

在这个过程中，服务器会通过 **数字证书** 将自己的公钥发送给客户端。客户端会对证书进行校验，以确认服务器身份的真实性，从而防止中间人伪造服务器。

**整个流程包括：**

**客户端发起请求**

- 发送支持的加密算法
- 发送一个随机数

**服务器响应**

- 返回服务器随机数
- 返回服务器公钥
- 返回服务器证书

**客户端校验证书**

- 确认服务器身份可信

**生成会话密钥**

- 双方基于随机数 + 协商结果
- 得到同一把对称密钥

**最终确认**

- 双方发送加密校验消息
- 确认握手未被篡改

**正式通信**

- 使用对称加密 + 完整性校验
- 保证安全传输

#### 一、为什么不用非对称加密直接加密所有数据？

**结论一句话：**
 因为**非对称加密性能开销太大，不适合用于大量、持续的数据传输**。

**展开说明：**

1. 非对称加密（如 RSA）计算复杂
   - 涉及大整数运算
   - 加解密速度远慢于对称加密
2. HTTP 通信是高频、连续的数据流
   - 一个页面可能包含大量请求和响应
   - 如果全部用非对称加密，会严重影响性能和延迟

------

#### 二、证书为什么能够解决身份认证问题？

**结论一句话：**
 因为**数字证书通过可信第三方（CA）对服务器公钥进行背书，防止公钥被伪造**。

**展开说明：**

1. 服务器自己声明“这是我的公钥”是不可信的
   - 中间人也可以伪造一对公私钥
   - 客户端无法判断公钥属于谁
2. 数字证书由 CA 机构签发
   - CA 会校验服务器身份
   - 再用 CA 的私钥对服务器公钥进行签名
3. 客户端内置了可信 CA 的公钥
   - 可以验证证书签名是否合法
   - 从而确认：
     - 公钥未被篡改
     - 公钥确实属于目标服务器

**结论强化：**
 证书解决的是 **“这个公钥到底是不是这个服务器的”** 问题。

------

#### 三、TLS 握手中的随机数是干什么的？

**结论一句话：**
 随机数用于 **保证每一次 HTTPS 会话生成的密钥都是唯一的，防止重放和密钥复用攻击**。

**展开说明：**

1. TLS 握手过程中
   - 客户端和服务器都会各自生成随机数
   - 这些随机数参与会话密钥的生成
2. 即使使用相同的证书和算法
   - 不同随机数会生成不同的会话密钥
   - 保证每次连接的独立性
3. 安全意义在于：
   - 防止攻击者复用历史密钥
   - 防止重放旧的加密通信内容

### 面试题：常见网络攻击类型有哪些？

1️⃣ 中间人攻击（Man-in-the-Middle, MITM）

**核心特征：**
 攻击者同时与客户端和服务器通信，双方都以为在“直连”。

**常见形式：**

- HTTP 明文劫持
- 伪造 HTTPS 证书
- Wi-Fi 钓鱼热点

**危害：**

- 窃听数据
- 篡改请求和响应
- 注入恶意内容

**HTTPS 主要就是为了解决这一类问题。**

------

2️⃣ 重放攻击（Replay Attack）

**攻击方式：**

- 攻击者截获一段合法请求
- 在之后的时间重复发送该请求

**典型场景：**

- 重复提交转账请求
- 重复使用已认证的数据包

**防御方式：**

- 使用随机数（nonce）
- 使用时间戳
- 会话级密钥

------

3️⃣ 窃听攻击（Eavesdropping）

**攻击方式：**

- 被动监听网络流量
- 不修改数据，只读取内容

**常见于：**

- HTTP 明文通信
- 公共 Wi-Fi

**防御方式：**

- 加密通信（HTTPS、TLS）

------

4️⃣ 数据篡改攻击（Tampering）

**攻击方式：**

- 修改请求参数
- 修改响应内容
- 注入恶意脚本或错误数据

**特点：**

- 如果没有完整性校验，很难发现

**防御方式：**

- MAC / HMAC
- TLS 完整性校验

------

5️⃣ 身份冒充攻击（Spoofing）

**常见类型：**

- IP 欺骗
- DNS 欺骗
- ARP 欺骗
- 服务器冒充

**典型例子：**

- DNS 被污染，访问到假网站
- 返回伪造服务器证书

**防御方式：**

- 数字证书
- CA 验证
- DNSSEC（部分场景）

------

6️⃣ 会话劫持（Session Hijacking）

**攻击方式：**

- 窃取 Cookie / Session ID
- 冒充合法用户继续访问

**常见原因：**

- Cookie 明文传输
- XSS 注入
- Session 固定攻击

**防御方式：**

- HTTPS
- HttpOnly / Secure Cookie
- Session 失效机制

------

7️⃣ 拒绝服务攻击（DoS / DDoS）

**攻击目标：**

- 让服务器无法正常提供服务

**常见形式：**

- SYN Flood
- HTTP Flood
- 分布式流量攻击（DDoS）

**防御方式：**

- 流量清洗
- 限流
- CDN

## 浏览器渲染

### 面试题：浏览器是如何渲染页面的？（完整流程题）

**口述模板：**

浏览器渲染页面可以拆成五个阶段：
 解析 HTML 构建 DOM 树，解析 CSS 构建 CSSOM 树，将 DOM 和 CSSOM 合并生成 Render Tree，然后进行 Layout 计算元素的几何信息，最后通过 Paint 将像素绘制到屏幕。

在这个过程中，HTML 解析、CSS 下载是并行的，但 Render Tree 的生成必须等待 DOM 和 CSSOM 都准备完成，这也是 CSS 会影响首屏渲染速度的根本原因。

------

### 面试题：HTML、CSS、JS 在渲染过程中是如何相互影响的？

**口述模板：**

HTML 负责结构，CSS 负责样式，JS 负责行为。
 HTML 解析过程中可以并行下载 CSS，但 CSS 未解析完成之前，浏览器无法确定元素最终样式，因此会阻塞渲染。

而 JavaScript 因为可能读取或修改 DOM 和 CSSOM，一旦执行就必须保证它看到的是一致的结构和样式，因此默认情况下 JS 会阻塞 HTML 解析和渲染。

------

### 面试题：async 和 defer 在浏览器层面的本质区别是什么？

**口述模板：**

**defer 和 async属性都是去异步加载外部的JS脚本文件，它们都不会阻塞页面的解析**，其区别如下：

- 执行顺序：多个带async属性的标签，不能保证加载的顺序；多个带defer属性的标签，按照加载顺序执行；
- 脚本是否并行执行：async属性，表示后续文档的加载和执行与js脚本的加载和执行是并行进行的，即异步执行；defer属性，加载后续文档的过程和js脚本的加载(此时仅加载不执行)是并行进行的(异步)，js脚本需要等到文档所有元素解析完成之后才执行，DOMContentLoaded事件触发执行之前。

------

### 面试题：CSS 为什么会阻塞 JS 执行？（高级追问）

**口述模板：**

如果 JavaScript 中访问了样式相关的 API，比如 `getComputedStyle`，而 CSSOM 尚未构建完成，浏览器就无法返回正确结果。因此在某些场景下，浏览器会等 CSS 加载和解析完成后再执行 JS，从而保证样式计算的准确性。

这也是为什么把 CSS 放在 head，把 JS 放在 body 底部有利于性能。

------

### 面试题：DOMContentLoaded 和 load 在渲染流程中的真实含义？

**口述模板：**

DOMContentLoaded 表示 HTML 解析完成、DOM 树构建完成，此时可以安全操作 DOM，但不保证图片、字体等资源加载完成。

load 事件则表示页面依赖的所有资源全部加载完成，包括图片、样式、脚本和 iframe，此时页面进入完全可交互状态。

从用户体验角度看，DOMContentLoaded 更接近“页面可用”，而 load 更接近“页面完全加载完成”。

------

### 面试题：回流（Layout）和重绘（Paint）在渲染中的角色？

**口述模板：**

Layout 负责计算元素的几何信息，比如位置和大小；Paint 负责将这些信息转化为像素绘制到屏幕。

修改元素的尺寸、位置、字体大小等会触发回流，而只修改颜色、背景等不影响布局的属性通常只会触发重绘。回流的性能开销远大于重绘，因此在实际开发中需要尽量减少回流次数。

------

### 面试题：为什么说“减少 DOM 操作可以提升性能”？

**口述模板：**

DOM 的任何修改都有可能触发样式重新计算、回流和重绘，尤其是在频繁操作 DOM 时，会导致渲染流水线被反复打断。

因此常见的优化手段包括：
 批量修改 DOM、使用文档片段、避免在循环中频繁读取布局信息，以及通过 CSS 动画代替 JS 驱动的动画。

### 面试题：什么是进程和线程？

进程是操作系统进行**资源分配的最小单位**，每个进程都有独立的地址空间、内存、文件描述符等资源。
 线程是操作系统进行**CPU 调度的最小单位**，线程必须依附于进程存在，一个进程可以包含多个线程。
 同一进程内的线程**共享进程资源**，但各自拥有独立的执行栈和程序计数器，因此线程切换成本比进程更低。

**进程和线程的区别可以从三个层面理解：**

第一，**本质不同**。
 进程是一个正在运行的程序实例，是资源的拥有者；
 线程是进程中的执行单元，负责具体的代码执行。

第二，**资源隔离程度不同**。
 进程之间资源相互隔离，通信需要通过 IPC；
 同一进程内的线程共享内存、全局变量、文件句柄，因此通信成本低，但安全性更弱。

第三，**调度与性能不同**。
 线程是 CPU 调度的基本单位，线程切换只涉及寄存器和栈，开销小；
 进程切换需要切换地址空间，开销更大，但稳定性和安全性更好。

一句话总结：
 **进程负责“隔离和资源”，线程负责“并发和执行”。**

---

### 面试题：浏览器的进程有哪些？

- 1 个浏览器主进程
- 1 个 GPU 进程
- 1 个网络进程
- 多个渲染进程
- 多个插件进程

这些进程的功能：

- **浏览器进程**：主要负责界面显示、用户交互、子进程管理，同时提供存储等功能。
- **渲染进程**：核心任务是将 HTML、CSS 和 JavaScript 转换为用户可以与之交互的网页，排版引擎 Blink 和 JavaScript 引擎 V8 都是运行在该进程中，默认情况下，Chrome 会为每个 Tab 标签创建一个渲染进程。出于安全考虑，渲染进程都是运行在沙箱模式下。
- **GPU 进程**：其实， GPU 的使用初衷是为了实现 3D CSS 的效果，只是随后网页、Chrome 的 UI 界面都选择采用 GPU 来绘制，这使得 GPU 成为浏览器普遍的需求。最后，Chrome 在其多进程架构上也引入了 GPU 进程。
- **网络进程**：主要负责页面的网络资源加载，之前是作为一个模块运行在浏览器进程里面的，直至最近才独立出来，成为一个单独的进程。
- **插件进程**：主要是负责插件的运行，因插件易崩溃，所以需要通过插件进程来隔离，以保证插件进程崩溃不会对浏览器和页面造成影响。

所以，**打开一个网页，最少需要四个进程**：1 个网络进程、1 个浏览器进程、1 个 GPU 进程以及 1 个渲染进程。如果打开的页面有运行插件的话，还需要再加上 1 个插件进程。

虽然多进程模型提升了浏览器的稳定性、流畅性和安全性，但同样不可避免地带来了一些问题：

- **更高的资源占用**：因为每个进程都会包含公共基础结构的副本（如 JavaScript 运行环境），这就意味着浏览器会消耗更多的内存资源。
- **更复杂的体系架构**：浏览器各模块之间耦合性高、扩展性差等问题，会导致现在的架构已经很难适应新的需求了。

### 面试题：**浏览器为什么要多进程**

浏览器采用多进程架构，主要是为了解决 **稳定性、安全性和性能** 三个问题。
 单进程模型下，一个页面崩溃会导致整个浏览器崩溃，而且 JS 阻塞会卡死 UI。
 多进程通过把不同页面和功能拆分到独立进程中，实现 **页面隔离、崩溃隔离和安全沙箱**，同时提升多核 CPU 的利用率。

浏览器之所以使用多进程，核心原因有三点：

第一，**稳定性**。
 一个渲染进程崩溃，只会影响当前标签页，不会导致整个浏览器退出。

第二，**安全性**。
 不同页面运行在不同进程中，配合沙箱机制，可以防止恶意脚本跨站点窃取数据。

第三，**性能与并行能力**。
 多进程可以充分利用多核 CPU，让多个页面同时渲染、执行 JS 和发起网络请求。

一句话总结：
 **多进程是浏览器在复杂网页场景下，实现高并发、高安全、高稳定的基础架构选择。**

------

### 面试题：**渲染进程里有哪些线程**

渲染进程内部是多线程结构，主要包括：

1. **GUI 渲染线程**：负责 DOM、CSSOM、布局和绘制
2. **JS 引擎线程**：负责执行 JavaScript
3. **事件触发线程**：管理事件循环
4. **定时器线程**：处理 setTimeout、setInterval
5. **异步网络线程**：处理 fetch、XHR 回调

其中 **GUI 渲染线程和 JS 引擎线程互斥执行**。

渲染进程内部最核心的是两条线程：

第一，**GUI 渲染线程**
 负责解析 HTML 和 CSS，生成 DOM 树、CSSOM，完成布局和绘制。

第二，**JS 引擎线程**
 负责执行 JavaScript 代码，比如事件回调、同步脚本逻辑。

为了保证页面状态一致性，这两个线程 **不能同时执行**，
 所以当 JS 执行时间过长时，会阻塞页面渲染，导致卡顿。

除此之外，还有：

- 事件触发线程：维护事件队列
- 定时器线程：管理时间到期的回调
- 网络线程：处理异步请求结果

一句话总结：
 **渲染进程是“多线程协作”，但 JS 与渲染是互斥的。**

### 面试题：**一次页面打开涉及哪些进程**

一次页面打开，主要涉及：

1. **浏览器主进程**：处理地址栏输入，创建渲染进程
2. **网络进程**：发起 HTTP 请求，下载 HTML 和资源
3. **渲染进程**：解析 HTML/CSS，执行 JS，渲染页面
4. **GPU 进程**：负责页面合成和图形加速（如果需要）

完整流程可以分为四步：

第一步，用户输入 URL，**浏览器主进程** 进行导航决策，判断是否新建渲染进程。

第二步，**网络进程** 发起请求，获取 HTML 文档和相关资源。

第三步，HTML 返回后，**渲染进程** 开始解析 HTML、CSS，构建 DOM 树，执行 JS，并进行页面布局和绘制。

第四步，如果涉及动画、3D、Canvas 等，**GPU 进程** 参与页面合成，提高渲染性能。

一句话总结：
 **主进程负责调度，网络进程负责请求，渲染进程负责页面，GPU 进程负责加速。**

### 面试题：进程之间的通信有哪些？

**进程之间通信，本质是解决两个问题：**

第一，**如何把数据从一个进程传给另一个进程**；
 第二，**如何在相互隔离的地址空间中保证数据安全和同步**。

因此操作系统提供了多种 IPC 机制，比如 **管道、消息队列、共享内存、信号、Socket**。
 其中共享内存效率最高，但需要自己做同步；
 Socket 最通用，既能进程通信，也能跨机器通信。

进程之间之所以需要通信，是因为 **进程拥有独立的地址空间，不能直接读写彼此内存**。
 IPC 的核心思想可以总结为三类：

第一类，**基于内核中转的通信**
 比如管道、消息队列。
 数据需要先从进程 A 拷贝到内核，再拷贝到进程 B，安全但性能一般。

第二类，**基于共享内存的通信**
 多个进程映射同一块物理内存，读写效率最高。
 但操作系统只负责“共享”，**不负责同步**，需要配合信号量或互斥锁。

第三类，**基于网络抽象的通信**
 比如 Socket，把本地进程通信抽象成网络通信模型，通用性最强。

一句话总结：
 **IPC 的本质是在“隔离”和“共享”之间做权衡。**

**常见 IPC 方式速记版**

1. 管道（Pipe）

- 半双工
- 主要用于父子进程
- 简单，但不适合大量数据

2. 消息队列

- 按消息发送
- 解耦发送方和接收方
- 有格式，但性能一般

3. 共享内存

- 速度最快
- 多进程直接访问同一块内存
- **必须自己处理并发安全**

4. 信号 / 信号量

- 信号：通知事件发生
- 信号量：控制并发访问
- 常用于同步，而不是大量数据传输

5. Socket

- 最通用
- 可本地、可远程
- Web 服务、浏览器进程通信常用

**浏览器多进程之间如何通信？**

浏览器通常采用 **基于消息的 IPC**：

- 主进程 ↔ 渲染进程
- 通过序列化消息进行通信
- 避免直接共享内存，提升安全性

把请求和数据序列化成消息，由主进程、网络进程等统一处理，从而保证安全性和稳定性。

例如：
 用户点击页面 → 渲染进程发送事件消息 → 主进程处理 → 返回结果。

网页里写了：

```
fetch('/api/data')
```

你以为是 JS 在发请求？不是。

真实流程是：

```
JS（渲染进程）
 → 发消息：我要请求这个 URL
 → 网络进程真的去请求
 → 再把结果“传纸条”回来
```

### 面试题：产生死锁的原因和预防方法？

**产生死锁的原因：**

**（1）竞争资源**

- 产生死锁中的竞争资源之一指的是**竞争不可剥夺资源**（例如：系统中只有一台打印机，可供进程P1使用，假定P1已占用了打印机，若P2继续要求打印机打印将阻塞）
- 产生死锁中的竞争资源另外一种资源指的是**竞争临时资源**（临时资源包括硬件中断、信号、消息、缓冲区内的消息等），通常消息通信顺序进行不当，则会产生死锁

**（2）进程间推进顺序非法**

若P1保持了资源R1，P2保持了资源R2，系统处于不安全状态，因为这两个进程再向前推进，便可能发生死锁。例如，当P1运行到P1：Request（R2）时，将因R2已被P2占用而阻塞；当P2运行到P2：Request（R1）时，也将因R1已被P1占用而阻塞，于是发生进程死锁



**产生死锁的必要条件：**

- 互斥条件：进程要求对所分配的资源进行排它性控制，即在一段时间内某资源仅为一进程所占用。
- 请求和保持条件：当进程因请求资源而阻塞时，对已获得的资源保持不放。
- 不剥夺条件：进程已获得的资源在未使用完之前，不能剥夺，只能在使用完时由自己释放。
- 环路等待条件：在发生死锁时，必然存在一个进程——资源的环形链。



**预防死锁的方法：**

- 资源一次性分配：一次性分配所有资源，这样就不会再有请求了（破坏请求条件）
- 只要有一个资源得不到分配，也不给这个进程分配其他的资源（破坏请保持条件）
- 可剥夺资源：即当某进程获得了部分资源，但得不到其它资源，则释放已占有的资源（破坏不可剥夺条件）
- 资源有序分配法：系统给每类资源赋予一个编号，每一个进程按编号递增的顺序请求资源，释放则相反（破坏环路等待条件）

## 性能优化

### 面试题：CDN 和 Service worker是什么？

一、CDN 的介绍（面试模板）

**CDN（内容分发网络）** 是通过在全球各地部署边缘节点，把静态资源缓存到离用户最近的节点，从而减少网络延迟、减轻源站压力、提升访问速度。
 用户请求资源时，优先从就近节点命中缓存，只有未命中时才回源站。

---

CDN 的核心思想是 **“空间换时间”**。

当用户访问资源时：

1. 请求首先到达 CDN 节点
2. 如果节点有缓存，直接返回（命中）
3. 如果没有缓存，向源站请求资源并缓存下来（回源）

CDN 主要解决三类问题：

- **访问速度慢**（就近访问）
- **源站压力大**（请求被分流）
- **高并发不稳定**（节点分担流量）

一句话总结：
 **CDN 是网络层面的缓存和加速方案。**

**CDN 通常缓存什么？**

- JS / CSS / 图片 / 视频
- 部分可缓存的接口响应（配合缓存策略）

**CDN 是否一定比源站快？**

**CDN的工作原理：**

（1）用户未使用CDN缓存资源的过程：

1. 浏览器通过DNS对域名进行解析（就是上面的DNS解析过程），依次得到此域名对应的IP地址
2. 浏览器根据得到的IP地址，向域名的服务主机发送数据请求
3. 服务器向浏览器返回响应数据



（2）用户使用CDN缓存资源的过程：

1. 对于点击的数据的URL，经过本地DNS系统的解析，发现该URL对应的是一个CDN专用的DNS服务器，DNS系统就会将域名解析权交给CNAME指向的CDN专用的DNS服务器。
2. CND专用DNS服务器将CND的全局负载均衡设备IP地址返回给用户
3. 用户向CDN的全局负载均衡设备发起数据请求
4. CDN的全局负载均衡设备根据用户的IP地址，以及用户请求的内容URL，选择一台用户所属区域的区域负载均衡设备，告诉用户向这台设备发起请求
5. 区域负载均衡设备选择一台合适的缓存服务器来提供服务，将该缓存服务器的IP地址返回给全局负载均衡设备
6. 全局负载均衡设备把服务器的IP地址返回给用户
7. 用户向该缓存服务器发起请求，缓存服务器响应用户的请求，将用户所需内容发送至用户终端。



如果缓存服务器没有用户想要的内容，那么缓存服务器就会向它的上一级缓存服务器请求内容，以此类推，直到获取到需要的资源。最后如果还是没有，就会回到自己的服务器去获取资源。

 不一定，首次请求或缓存未命中时仍需回源。

------

二、Service Worker 的介绍（面试模板）

**Service Worker 是运行在浏览器中的独立脚本线程**，位于页面和网络之间，可以拦截网络请求，实现资源缓存、离线访问和请求控制，是 PWA 的核心能力之一。

Service Worker 的本质是一个 **浏览器侧的网络代理**。

它的特点包括：

- 不运行在主线程，不阻塞页面渲染
- 可以拦截 `fetch` 请求
- 可以把请求结果缓存到 Cache Storage
- 在离线或弱网环境下返回缓存内容

典型工作流程是：

1. 页面注册 Service Worker
2. Service Worker 安装并激活
3. 拦截请求，决定 **走网络 / 走缓存 / 组合返回**

一句话总结：
 **Service Worker 是客户端层面的缓存和请求控制机制。**

**Service Worker 能缓存接口请求吗？**
 可以，只要是 `fetch` 请求，都可以被拦截并缓存。

**Service Worker 和 HTTP 缓存的关系？**
 Service Worker 的优先级更高，可以完全绕过 HTTP 缓存规则。

------

CDN 和 Service Worker 都能提升访问速度，但**层级不同、职责不同**：

- CDN 工作在 **网络侧 / 服务器侧**
- Service Worker 工作在 **浏览器侧 / 客户端**

CDN 解决的是 **“资源怎么更快送到用户”**，
 Service Worker 解决的是 **“浏览器怎么更聪明地用资源”**。

| 对比维度       | CDN          | Service Worker |
| -------------- | ------------ | -------------- |
| 工作位置       | 网络边缘节点 | 浏览器内部     |
| 是否依赖浏览器 | 否           | 是             |
| 是否支持离线   | 否           | 是             |
| 控制粒度       | 粗（文件级） | 细（请求级）   |
| 典型用途       | 静态资源加速 | 离线、缓存策略 |

> 实际项目中，通常 **CDN + Service Worker 结合使用**：
>  CDN 负责首次访问和大规模分发，
>  Service Worker 负责二次访问、离线体验和弱网优化。

### 面试题：懒加载和预加载

#### 面试题一：什么是懒加载？它解决了什么问题？

**口述回答模板：**

本质：**代码分割（Code Splitting）+ 按需加载（On-Demand Loading）**。

懒加载指的是：资源并不是在页面一开始就全部加载，而是等到真正需要使用的时候才去加载。
 这里的资源可以是图片、组件、路由模块，甚至是数据请求。

引入懒加载的根本原因在于性能优化。现代前端页面资源体积越来越大，如果在首屏阶段一次性加载所有内容，会显著拉长首屏渲染时间，影响用户体验。懒加载通过“延后非关键资源”的加载时机，把带宽和计算资源优先留给首屏和核心功能。

从工程角度看，懒加载的本质不是少加载，而是**把加载时机推迟到最合适的时间点**，从而在性能和功能之间取得平衡。

------

#### 面试题二：什么是预加载？和懒加载的出发点有什么不同？

**口述回答模板：**

预加载的思路和懒加载恰好相反。
 预加载是指：在当前阶段还没用到某些资源时，**提前把它们加载到浏览器中**，以便在真正需要时能够立刻使用。

预加载的出发点不是减少请求数量，而是减少“等待时间”。
 比如用户接下来很可能会跳转到下一个页面，如果等到真正跳转时才开始加载资源，就会产生明显的延迟。预加载则是利用浏览器空闲时间，提前准备好未来可能用到的资源。

因此，预加载关注的是**未来体验的平滑性**，而懒加载关注的是**当前性能的优化**。

------

#### 面试题三：懒加载和预加载的核心区别是什么？

**口述回答模板：**

懒加载和预加载的核心区别在于加载时机和目标不同。

懒加载强调“**非必要不加载**”，优先保证当前页面和首屏体验，把非关键资源推迟到真正需要时再加载；
 预加载强调“**即将需要先准备**”，在不影响当前性能的前提下，提前加载未来高概率会用到的资源。

可以理解为：懒加载是减法，减少首屏负担；预加载是加法，减少未来等待。
 在实际工程中，两者并不是对立关系，而是常常配合使用。

------

#### 面试题四：前端常见的懒加载和预加载应用场景有哪些？

**口述回答模板：**

懒加载最常见的场景包括：图片懒加载、路由级代码拆分、组件级异步加载以及滚动加载列表数据。这些场景的共同点是：资源在首屏并不一定会用到，但体积或数量较大。

预加载常见于：路由切换、用户行为可预测的页面跳转、关键交互所需的脚本或样式提前准备等。
 比如用户 hover 到某个菜单项时，提前加载对应页面的代码，就是一种典型的预加载策略。

在复杂应用中，是否使用懒加载或预加载，取决于资源是否关键、使用时机是否可预测以及当前网络和设备性能。

------

#### 面试题五：懒加载和预加载在构建和运行阶段是如何实现的？

**口述回答模板：**

从构建角度看，懒加载通常依赖代码拆分，把大资源拆成多个独立块，在运行时按需加载。
 而预加载更多是通过构建工具或浏览器机制，提前告诉浏览器“某些资源很快会用到”，从而在合适的时机加载。

从运行时角度看，懒加载往往和用户行为相关，比如滚动、点击、路由切换；
 预加载则更多依赖浏览器调度和开发者对用户路径的预判。

本质上，两者都是在**控制浏览器加载资源的优先级和时机**。

#### 面试题：什么是 preload 和 prefetch？它们有什么区别？

**口述回答模板：**

preload 和 prefetch 都是浏览器提供的**资源预加载机制**，本质目的都是：提前获取资源，减少用户等待时间。但它们解决的问题不同，加载优先级和使用时机也完全不同。

preload 的含义是：**当前页面“马上就要用到”的关键资源，要求浏览器尽早加载**。
 它的特点是优先级高，浏览器会把 preload 的资源当作当前页面渲染路径上的一部分来对待。
 典型场景是：关键脚本、关键样式、首屏字体等，如果这些资源不及时加载，就会直接影响当前页面的渲染或交互。

prefetch 的含义是：**当前页面暂时用不到，但未来很可能会用到的资源，提前在空闲时加载**。
 它的特点是优先级低，浏览器只会在网络和主线程空闲时才去加载，不会影响当前页面的关键资源。
 典型场景是：用户可能即将跳转到的下一个页面所需的脚本或数据。

从时间维度上看，preload 面向的是“现在”，prefetch 面向的是“将来”；

从优先级上看，preload 是高优先级，prefetch 是低优先级

从使用目的上看，preload 是为了解决当前页面性能瓶颈，prefetch 是为了提升未来页面切换的流畅度。

### 面试题：对节流与防抖的理解

**口述回答模板：**

节流和防抖都是用来控制高频事件触发频率的手段，解决的问题是：像 scroll、resize、mousemove、input 这种事件触发太密集，会导致频繁执行回调，带来性能问题或者重复请求。

防抖的思路是“只要触发就重新计时”，也就是事件持续触发时不执行，等到停止触发一段时间后才执行一次。它适合“只关心最终结果”的场景，比如搜索框输入联想、窗口大小调整完成后的重新计算、表单校验等。

节流的思路是“固定时间窗口最多执行一次”，不管事件多频繁，回调都按节奏执行。它适合“需要过程反馈”的场景，比如滚动监听上报、拖拽过程位置更新、页面滚动加载、mousemove 跟随效果等。

工程上常见的区别点是：防抖更像把多次触发合并成最后一次；节流更像把触发频率压到一个可控范围。两者都可以做“立即执行”或“尾部再补一次”的变种，具体选哪种取决于业务要的是开始响应、过程响应还是结束响

#### 防抖

```javascript
function debounce(fn, wait) {
  var timer = null;

  return function() {
    var context = this,
      args = [...arguments];

    // 如果此时存在定时器的话，则取消之前的定时器重新记时
    if (timer) {
      clearTimeout(timer);
      timer = null;
    }

    // 设置定时器，使事件间隔指定事件后执行
    timer = setTimeout(() => {
      fn.apply(context, args);
    }, wait);
  };
}

function handleResize() {
  console.log('resize');
}

const debouncedResize = debounce(handleResize, 300);

// 之后只用这个函数
window.addEventListener('resize', debouncedResize);

```



#### 节流

```javascript
// 时间戳版
function throttle(fn, delay) {
  var preTime = Date.now();

  return function() {
    var context = this,
      args = [...arguments],
      nowTime = Date.now();

    // 如果两次时间间隔超过了指定时间，则执行函数。
    if (nowTime - preTime >= delay) {
      preTime = Date.now();
      return fn.apply(context, args);
    }
  };
}

// 定时器版
function throttle (fun, wait){
  let timeout = null
  return function(){
    let context = this
    let args = [...arguments]
    if(!timeout){
      timeout = setTimeout(() => {
        fun.apply(context, args)
        timeout = null 
      }, wait)
    }
  }
}
```

### 面试题：HTTP 状态码概念

HTTP 状态码用于表示服务器对请求的处理结果，按首位数字分为五类。

------

状态码分类

-  **1xx**：信息（处理中）
-  **2xx**：成功
-  **3xx**：重定向
-  **4xx**：客户端错误
-  **5xx**：服务器错误

------

高频状态码（必背）

**2xx**

- **200 OK**：请求成功
- **201 Created**：资源创建成功
- **204 No Content**：成功但无返回体

**3xx**

- **301 Moved Permanently**：永久重定向（可缓存）
- **302 Found**：临时重定向
- **304 Not Modified**：资源未修改，使用缓存

**4xx**

- **400 Bad Request**：请求参数或格式错误
- **401 Unauthorized**：未认证（未登录 / token 失效）
- **403 Forbidden**：已认证但无权限
- **404 Not Found**：资源不存在

**5xx**

- **500 Internal Server Error**：服务器内部错误
- **502 Bad Gateway**：网关收到无效上游响应
- **503 Service Unavailable**：服务不可用（过载 / 维护）
- **504 Gateway Timeout**：网关请求上游超时

------

面试一句话总结

> **2xx 成功，3xx 跳转，4xx 客户端错，5xx 服务端错；401 是没身份，403 是没权限，304 是用缓存。**

### 面试题：为什么工程项目中通常会有两个token

两个 token 的设计，本质是把 **“频繁访问接口”** 和 **“长期保持登录态”** 这两件事分开处理。

- Access Token：负责访问业务接口，生命周期短
- Refresh Token：负责在 Access Token 过期时，换取新的 Access Token，生命周期长

------

#### 完整流程（从登录到刷新）

##### 1. 用户登录

1. 用户在前端输入账号和密码
2. 前端向后端发送登录请求
3. 后端校验成功后，返回两个 token：
   - Access Token（短期有效）
   - Refresh Token（长期有效）

------

##### 2. 正常访问业务接口

1. 前端在每一次业务请求中，都会在请求头中携带 Access Token
2. 后端只校验 Access Token 的合法性
3. 校验通过，返回业务数据

在这个阶段，Refresh Token 不参与任何业务请求。

------

##### 3. Access Token 过期

1. 当 Access Token 过期时，后端返回 401 状态码
2. 前端拦截到 401，但不会立刻让用户重新登录

------

##### 4. 使用 Refresh Token 刷新 Access Token

1. 前端自动发送刷新请求，并携带 Refresh Token
2. 后端校验 Refresh Token 是否有效、是否过期、是否被吊销
3. 校验通过后，返回一个新的 Access Token

------

##### 5. 重试刚才失败的请求

1. 前端用新的 Access Token
2. 重新发送刚才因为过期而失败的业务请求
3. 请求成功，页面继续正常使用

整个过程对用户是无感知的。

------

##### 6. 刷新失败的情况

如果 Refresh Token 校验失败，通常有以下原因：

- Refresh Token 过期
- 用户主动退出登录
- 服务端主动吊销 Refresh Token

此时前端需要：

1. 清空本地 token
2. 跳转登录页面
3. 要求用户重新登录

------

#### 为什么要这样设计

##### 1. 安全性

- Access Token 生命周期短，即使泄露，风险时间窗口有限
- Refresh Token 使用频率低，可以单独管理和吊销

##### 2. 用户体验

- 用户不需要频繁重新登录
- token 刷新过程对用户无感

##### 3. 工程可控性

- 可以统一处理 token 过期和刷新逻辑
- 刷新失败时，能够明确地回退到登录流程

------

#### 前端实现时必须注意的几点

1. 防止多个请求同时触发刷新，需要加锁或请求队列
2. Refresh Token 只用于刷新接口，不能参与业务请求
3. 刷新失败时，必须统一清理状态并跳转登录页
