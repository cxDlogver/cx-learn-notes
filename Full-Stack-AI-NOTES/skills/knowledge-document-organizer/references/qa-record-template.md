# QA 记录模板以“提问方式—回答框架—完整回答—继续展开”组织知识

只有用户明确要求记录时，才据此更新 `QA.md` 并在 `QA/` 新建单题文档。QA 的目标不是保存一次聊天的过程，而是把一个知识主题整理成可以反复用于复习、面试和继续追问的“问题视图”。

因此，QA 成稿中不得保留“原问题”“原始资料”“中间分析”“用户当时怎么说”等过程性字段。原始资料只作为整理时的输入和证据来源，最终只保留经过整理后的知识结构和必要的正式引用。

## 1. 一个 QA 记录代表一套回答知识框架，而不是一句历史提问

同一个知识点可能有多种提问方式。例如：

```text
Harness、Runtime、Loop 有什么区别？
Agent Runtime 和 Agent Loop 是什么关系？
一次 Agent Run 到底是谁在驱动？
Harness 为什么不能直接等同于 Runtime？
```

这些问题如果最终依赖同一套知识结构回答，就应归入同一个 QA，而不是因为问法不同重复创建多个记录。

`QA.md` 中每条记录采用：

```markdown
## <连续编号>. <知识主题>

### 【提问】

- <这个知识点常见的一种提问方式>
- <另一种从关系、机制或边界切入的提问方式>
- <确实属于同一回答框架时，可继续列出其他问法>

### 【回答框架】

<先用一段话说明回答这类问题时的核心判断和主线。>

```text
<用层级、流程或因果关系表示回答路径>
```

- **<框架节点 1>**：说明这一部分要回答什么、核心结论和关键边界。
- **<框架节点 2>**：说明为什么需要继续展开这一层，以及它和上一层的关系。
- **<框架节点 3>**：继续补足机制、对比、工程边界或判断方法。

### 【完整回答】

[查看完整回答](<./QA/<与知识主题一致的文件名>.md>)

### 【继续展开】

- **追问：** <只有从当前回答自然产生的下一层问题才记录>
  - 关联知识：<只有确实有帮助时才链接对应知识正文或已有 QA>
```

“回答框架”不是把完整回答缩短成一句摘要，而是保存**如何分析和组织答案**。只看这一节，也应该能够复原答案的主要知识结构。

## 2. 【提问】保存可能的问法，不保存聊天痕迹

提问用于表示：

> 当前这一套知识框架，在实际学习、面试或答辩中可能以哪些方式被问到。

规则：

1. 可以保留用户问题的知识含义，但要去掉聊天上下文、临时措辞和过程性描述。
2. 一个 QA 可以有多个提问，只要它们确实共享同一套核心回答框架。
3. 如果两个问题需要不同的核心机制、判断链或知识结构才能回答，应拆成两个 QA，不能为了减少文件数量强行合并。
4. 提问优先覆盖不同切入角度，例如定义、关系、运行机制、工程边界、方案选择和常见误区；不要只做同义句改写。
5. QA 成稿中不出现“用户原话”“原问题”“根据某次对话”“原始资料”等字段。

## 3. 【回答框架】必须形成连续的答题推导，而不是知识点目录

回答框架承担 QA 索引最重要的复习职责。它要解决的不是“这道题涉及哪些知识”，而是“**面对这个问题，应该怎样一步一步把答案讲成立**”。

默认参考类似 PAEP / PREP 的思路，但只使用其推导逻辑，不在成稿中机械标记 P、A、E、P：

```text
先给核心判断
回答“这道题最重要的结论是什么”
        ↓
解释判断依据
回答“为什么要这样理解，问题的矛盾或区分维度是什么”
        ↓
沿机制 / 流程展开
把前面的判断放进真实运行过程、因果链或工程场景中证明
        ↓
补充边界与对比
说明什么不能混淆、什么条件下结论会变化
        ↓
收束回答
重新用一段可复述的话回答最初的问题
```

这五步必须前后相接：后一步是在回答前一步自然产生的问题，而不是把定义、流程、优缺点等知识点并排罗列。

例如概念关系题，不应写成：

```text
Loop 定义
  ↓
Runtime 定义
  ↓
Harness 定义
```

因为三者并不存在这种先后流程。应先找到它们为什么会同时出现，再用同一个运行场景建立关系：

```text
核心判断
三者描述的是同一个 Agent 执行系统的不同抽象层次，不能只按三个独立定义记忆
        ↓
为什么
Agent 不只是“模型调用一次”，而是需要持续决策、真正执行，并获得完整工程支撑
        ↓
因此产生三个问题
任务怎样反复推进？ → Loop
谁把每一轮真正跑起来？ → Runtime
完整运行还依赖什么能力？ → Harness
        ↓
放进一次 Agent Run 验证
Runtime 构建 Context → 调 Model → 得到 Tool Call
→ 执行 Tool → 更新 State → 形成 Observation
→ Loop 决定继续或结束
整个过程依赖 Harness 提供 Tool、Memory、权限、Checkpoint、Trace 等支撑
        ↓
边界
Loop 是循环机制，Runtime 是执行载体，Harness 是工程支撑抽象；
它们有职责关系，但不同框架不一定采用固定的代码包含层级
        ↓
收束
因此回答三者关系时，应从“一次 Agent 如何持续运行”切入，
再分别说明循环机制、执行主体和工程支撑，而不是背三个孤立定义
```

不同题型可以改变中间展开方式，但都要保持“结论 → 依据 → 展开验证 → 边界 → 收束”的连续推导：

- **概念关系题**：先给关系判断 → 找共同问题 → 分出各自职责 → 放入同一流程验证 → 补边界 → 收束关系。
- **系统架构题**：先给系统整体判断 → 解释为什么需要分层 → 沿主请求流 / 数据流展开各层协作 → 补横切能力与边界 → 收束整体架构。
- **机制原理题**：先给机制结论 → 解释触发原因 → 沿时间或因果过程展开 → 分析结果和异常分支 → 收束原理。
- **方案设计题**：先给选择结论或判断原则 → 明确目标与约束 → 按关键维度比较方案 → 用场景验证选择 → 补代价和适用边界 → 收束决策。
- **故障分析题**：先给定位原则 → 解释为什么不能直接下结论 → 沿现象到根因建立排查链 → 用证据逐层排除 → 给修复和验证 → 收束根因。

回答框架最终至少满足：

1. **第一段能直接回答问题。** 不能先铺大量背景才出现结论。
2. **每一步都有“为什么进入下一步”。** 删除箭头后如果只是几个并列知识点，说明框架仍未建立联系。
3. **展开过程用于证明前面的判断。** 流程图、案例、对比不是额外知识，而是回答逻辑中的证据。
4. **边界用于防止过度推导。** 明确哪些是职责抽象、哪些是实现关系、哪些结论只在特定条件下成立。
5. **最后必须回到原问题。** 用一段能够直接复述的总结把前面的分析重新收束，而不是停在知识点罗列。

## 4. 单题文档只保留整理后的知识，不保留中间分析残留

单题文档的职责是提供完整标准回答。正文根据知识本身建立层级，不要求机械出现“问题解析”“原始资料”“分析过程”等章节。

具体规则：

1. 正文必须是整理后的标准知识回答，不记录“先查了什么”“最开始怎么分析”“用户原来怎么问”等过程。
2. 原始资料、本地文档和项目材料可以作为整理输入，但不设置“原始资料”章节。真正支撑结论的标准、官方文档、论文或必要知识正文应在对应论述附近正常引用。
3. 完整回答仍遵循“结论—机制—证据—边界”的知识文档原则；流程图后必须解释，表格不能代替机制。
4. 单题正文可以比 QA.md 的回答框架更完整，但两者的主线和结论必须一致。

## 5. 【继续展开】只记录自然产生的追问和知识关系

不再要求每条 QA 固定给出若干“关联问题”，也不为了建立知识图谱而机械链接文档。

只有当前回答自然暴露出下一层问题时，才增加 `### 【继续展开】`。

判断一个追问是否值得记录，可以检查：

```text
当前回答中的某个概念 / 边界 / 机制
        ↓
继续理解它是否需要一个新的问题？
        ↓
是 → 记录追问
        ↓
是否存在真正能帮助回答这个追问的知识正文或已有 QA？
        ├─ 是 → 附关联知识
        └─ 否 → 只保留追问，不强行链接
```

可以记录的关系包括：

- 当前概念继续深入后的机制问题；
- 当前回答中的易混概念对比；
- 当前方案进入生产环境后的治理问题；
- 当前机制失败时产生的异常、恢复或安全问题；
- 当前知识的前置缺口确实会阻碍理解。

不要因为两个文档都属于 Agent、服务端、前端等同一大类，就建立关联。

## 6. QA.md 与单题文档承担不同粒度

`QA.md` 是问题索引和回答地图，重点保存：

```text
知识主题
  ├─ 可能怎样提问
  ├─ 应该怎样分析和回答
  ├─ 完整回答入口
  └─ 值得继续追问什么
```

`QA/<题目>.md` 是完整知识回答，重点保存：

```text
完整定义
  ↓
知识框架
  ↓
运行机制 / 因果链
  ↓
工程判断
  ↓
边界与误区
  ↓
证据与参考资料
```

因此，QA.md 不能退化成一句摘要列表；单题文档也不能退化成聊天记录归档。

## 7. 记录完成后检查

- 是否统一使用“【提问】”，且没有“原问题”“原始资料”等过程字段；
- 多个提问是否真的共享同一回答框架，而不是为了合并而合并；
- “回答框架”是否能够独立说明分析路径、知识层级、关键结论和边界；
- 是否避免把回答框架写成一长句或几个孤立关键词；
- 完整回答是否删除中间分析痕迹，只保留整理后的知识；
- “继续展开”是否来自当前回答本身，而不是为了关联而关联；
- 关联文档是否确实能帮助回答对应追问；没有合适文档时是否保持不链接；
- QA.md 与单题完整回答的主线、结论和边界是否一致。
