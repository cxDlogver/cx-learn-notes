# 知识文档样式规范

这份规范提炼自紧凑型中文学习教程。它约束结构和表达，但不能覆盖用户对某一文档提出的更窄修改范围。

## 标题层级

- 文档已有一级标题时保留；没有一级标题时，不为形式完整强行新增。
- 二级标题必须连续编号：`## 1. 标题`、`## 2. 标题`。参考文献也占一个二级标题编号，例如 `## 3. 参考文献`。
- 三级标题使用中文方头括号：`### 【标题】`。不要写成英文方括号，也不要同时堆叠多套编号。
- 四级标题使用下划线并带局部编号：`#### <u>1. 标题</u>`。同一组内的编号连续，编号与标题之间留一个空格。
- 不跳级，不用加粗正文模拟标题。

## 段落与叙述节奏

一个自然的知识章节通常按以下节奏推进：

1. 先界定正在讨论的概念，说明它与相近概念的差异。
2. 解释为什么这个区别重要，以及它解决什么实际问题。
3. 给出研发、业务或真实使用场景，不只给抽象定义。
4. 提供可以执行的判断问题、流程或指标。
5. 用官方定义、标准、论文、数据、反例或结果收束结论。

短判断句与解释性段落交替使用。允许使用“不是……而是……”“到底改善了什么”“有没有可验证结果”一类自然判断句，但不要重复同一结论。少用“首先、其次、再次、综上所述”等机械串联词，除非它们确实表达顺序。

## 重点内容

强调方式分成两类，不要把所有重点都写成引用块：

- 引用块用于权威原话、包含完整边界的关键定义、章节核心结论，以及决定章节逻辑且值得读者停下来回答的问题。
- 粗体加下划线 `**<u>内容</u>**` 用于局部细节、限制条件、风险提醒、实现差异和注意点。

只有概念名称、分类标签或一句局部提示时，不算完整的关键概念定义，优先使用粗体加下划线。

```markdown
> **不是步骤多就需要 Agent；只有执行路径需要动态判断时，Agent 才可能有必要。** [[1]](https://example.org/source)

**<u>注意：这里的结论只适用于执行路径由模型动态决定的场景。</u>**
```

直接引语必须紧邻来源。引用块不是装饰，不要把每段总结、概念名称或注意事项都放进去。普通强调优先使用少量加粗；只有确实需要与正文拉开层级的细节或注意点才同时使用粗体和下划线。

## 列表、表格与代码块

- 每一项包含完整解释、条件或例子时，使用项目符号或编号列表。
- 只有多个词组、指标或短标签时，写在同一行并用中文分号隔开，例如：准确率；错误率；人工接管率；重试率。
- 不创建只有一个项目的列表。能用一两个紧凑段落讲清楚时，不拆成稀疏列表。
- 只有多个对象需要按相同字段精确对比时才使用表格。
- 流程图或结构示意可以使用代码块；有明确语言的程序代码应标注语言，无语言的 ASCII 图使用 `text`。
- 纯单链流程能在一行清楚表达时，统一改为横向箭头，例如 `输入 → 校验 → 调用 API → 保存结果`，不要为每个节点占两行。
- 存在分支、并行、汇合、回流、循环、层级树、上下文边界，或横向一行会明显过长时，保留多行结构。
- 真实程序代码、伪代码和数据结构示例不因压缩流程图而改写。

### 代码块重排的判断顺序

重排代码块的目标不是减少围栏数量，而是让信息关系在 Markdown 预览中更容易识别。逐块按以下顺序判断：

1. **先判断它是否真的需要代码块。** 只有标签、术语、文件名或短指标的块不是流程图，应改为正文并用中文分号连接。真实代码、伪代码、分支图、回流图、层级树和状态边界继续使用代码块。
2. **再识别节点之间的关系。** 区分单链、分支、并行、汇合、回流、循环、层级、阶段交接和状态边界。不能只看当前排版是横向还是纵向，因为原始排版本身可能没有准确表达关系。
3. **列出必须保留的信息。** 修改前确认所有节点、条件、角色、状态、产物、文件名、失败路径和输出。只改箭头、空格、缩进、换行及不影响含义的连接符，不借排版删除或改写内容。
4. **选择关系最清楚的布局。** 单链优先横向；一对多使用树形；失败后返回前序节点使用回流图；多个阶段采用阶段行；不同状态空间或上下文边界采用分层框图。
5. **真正重排保留下来的多行块。** “决定保留 `text` 围栏”不等于保持原样。仍要检查箭头是否对齐、同级缩进是否一致、父子连接是否完整、回流方向是否可见，以及一行是否会在常用 Markdown 预览宽度内折行。

重排时保持一个主要阅读方向。普通流程优先从左到右或从上到下；只有表达重试、恢复或循环时才使用返回箭头。不要在同一个图里无理由地频繁切换方向。

### 常用布局模式

纯单链且长度适中，直接移出围栏：

```markdown
输入 → 校验 → 调用 API → 保存结果
```

存在一对多选择时，使用树形结构，让条件和结果保持同级：

```text
判断节点如何执行
├─ 执行路径明确
│  └─→ Code / API / Script
└─ 需要模型动态判断
   └─→ Agent
```

发生失败后需要回到先前阶段时，必须画出返回方向，不能继续伪装成单向长链：

```text
Task 2 ──发生异常──→ Restore Checkpoint
  ↑                        ↓
  └──────继续 Task 2 ← 重新读取 Artifact
```

多个阶段采用相同的“阶段 → 产物 → 检查点”关系时，使用阶段行，避免每个节点各占两行：

```text
Planning       → plan.md                           → Checkpoint
Implementation → code + implementation-result.json → Checkpoint
Testing        → test-report.json                  → Checkpoint
Review         → review-result.json
```

父子职责较多时，使用统一的树干和缩进。相同层级使用相同缩进，`├─` 表示后面还有同级节点，`└─` 表示同组最后一个节点；不要混用没有含义的空格、竖线和箭头。

状态、产物和会话属于不同边界时，可以使用多个纵向框或分区。每个框只回答一个问题，例如“任务执行到哪里”“阶段确认了什么”“当前 Agent 如何执行”；删除框内只为撑高而存在的空行，但保留边界名称和关键字段。

如果一条单链过长，不强行压成一行。优先按业务阶段分组，或把“执行者 → 产物”放在同一行，再用纵向箭头连接下一阶段。是否过长以常用 Markdown 预览中能否稳定阅读为准，不使用固定字符数机械判断。

### 程序代码与伪代码

程序代码和伪代码的重排边界比 ASCII 图更严格：

- 保留正确的语言标记，例如 TypeScript 使用 ```ts`；不要把程序代码误标为 `text`。
- 仅排版或补注释时，不改函数签名、变量、Schema、条件、返回值、调用顺序和异常分支。
- 先在代码块开头用简短注释说明示例目标、状态层次和关键步骤总览，再在对应代码之前放置步骤注释。
- 步骤较多时使用“阶段步骤 1/6”“Runtime 步骤 1/4”一类编号，使顶部总览能够与代码位置一一对应。
- 注释解释该步骤为什么存在、读取什么、改变什么状态、生成什么产物、怎样验收或恢复；不要逐行复述代码字面含义。
- Gate、Artifact、Checkpoint、重试和终止属于状态变化点，应在操作发生之前说明。异常分支必须明确由哪一层决定重试、恢复或终止。
- 若完整代码已迁移到外部源文件，正文可以保留关键伪代码和源文件链接，但只有在用户明确允许简化正文代码时才能这样处理。

修改后可把代码块中的空行和注释行暂时忽略，对比其余程序语句；如果非注释语句发生变化，就不再是单纯的代码块排版。

### 代码块重排检查

- 所有围栏成对闭合，程序代码有正确语言标记，ASCII 图使用 `text`。
- 每个代码块都完成关系判断；保留多行的块也检查过内部布局，而不是默认原样保留。
- 原有节点、条件、角色、状态、文件名、产物、失败路径和输出仍然存在。
- 单链没有无意义地纵向拉长；分支、并行、汇合和回流能够从连接线直接看出。
- 同级缩进一致，箭头方向稳定，连接线不会让读者误判父子关系或执行顺序。
- 常用 Markdown 预览宽度下没有因强行横排而难以阅读的超长行。
- 程序或伪代码的非注释语句与控制流程保持不变；步骤注释与实际代码位置和执行顺序一致。

## 引用与参考文献

### 正文引用

正文统一使用可见方括号且编号可点击的格式：

```markdown
这一结论来自官方工程指南。[[1]](https://example.org/source)
```

编号按正文首次引用的顺序排列；同一来源始终复用同一个编号。引用放在它支持的句子或段落末尾，不把一组编号悬空放在章节标题上。

### 参考文献

文末设置带编号的二级标题，并让每条文献独占一段，不使用项目符号：

```markdown
## 4. 参考文献

[1] AUTHOR OR ORGANIZATION. [Title](https://example.org/source)[EB/OL]. 2026-01-15[2026-08-29].

[2] ORGANIZATION. [Report title](https://example.org/report.pdf)[R/OL]. [2026-08-29].
```

常用文献类型：在线文档或网页 `[EB/OL]`；在线报告 `[R/OL]`；在线期刊论文 `[J/OL]`。只写已核验的元数据：机构或作者；准确题名；文献类型；官方明确提供的发布日期或更新时间；访问日期；规范 URL。

若页面只给出更新时间，可以直接写该日期，但不要称为首发日期。若没有可核验日期，省略日期并保留访问日期。英文机构责任者可使用大写形式，整篇保持一致。

## 受限编辑模式

当用户限定“只修改引用和参考文献”时，只允许：

- 新增、删除或重排正文引用标记；
- 修正与正文不匹配的引用链接；
- 去除追踪参数，统一编号与链接形式；
- 新增或整理文末参考文献章节；
- 为准确覆盖原有表述增加必要的一手来源。

不要调整任何标题、分隔线、列表、代码块、空格习惯或正文措辞，即使发现样式不一致；将这些问题留到用户另行授权后处理。
