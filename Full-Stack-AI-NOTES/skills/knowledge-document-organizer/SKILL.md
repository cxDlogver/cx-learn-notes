# 知识问答与文档维护

本 Skill 服务于 `Full-Stack-AI-NOTES`。它同时负责 **知识读取、知识问答、知识文档维护、资源归档和 QA 记录**。目标不是把仓库当成普通文件夹搜索，而是让每一次回答或修改都沿着既有知识体系进行，并保持文档、代码、图片和附件之间的边界清晰。

## 1. 先读取知识体系，再读取具体文件

处理任何与 `Full-Stack-AI-NOTES` 有关的知识任务时，默认读取顺序为：

```text
README.md
   ↓
知识体系索引.md
   ↓
QA.md
   ↓
与当前问题直接相关的 Markdown 正文
   ↓
source/ / resource/ / assets/（按任务需要）
   ↓
外部官方文档、标准、论文或官方工程资料
```

规则：

1. [知识体系索引](../../知识体系索引.md) 是本目录的主知识地图。先通过它确认主题、前置知识、主文档和延伸文档，再读取正文。
2. 索引只用于定位，**不得仅根据索引摘要回答知识问题**。正式回答必须继续读取相关 Markdown 的实际内容。
3. [QA.md](../../QA.md) 用于判断当前问题是否已有记录、是否存在相关问题以及当前学习链路。普通问答只读 QA，不自动写入。
4. 一个主题存在多个历史文档时，优先选择知识体系索引中的主入口，再读取与当前问题实质相关的补充文档；不要按文件名随机拼接内容。
5. 如果本地资料互相冲突，明确指出冲突文件和差异，并使用更可靠的事实源进行核验，不静默选择一个版本。
6. 对版本、标准、框架行为、产品能力等可能变化的事实，必须结合最新官方资料核验。

## 2. 每次问答都同时使用本地知识和权威资料

1. 从知识体系索引和 QA 找到相关主题，再检索并阅读所有与本题实质相关的本地段落和交叉引用。
2. 同时查阅可访问的权威在线资料。优先级通常为：标准 / 规范 → 官方文档 → 原始论文 → 官方工程文章 → 高质量二手资料。
3. 区分三类结论：
   - **资料事实**：本地原文、标准、官方资料或论文直接支持；
   - **分析**：基于多个事实作出的解释，需要写清依据；
   - **工程推论**：经验性判断、设计建议或本地抽象，不冒充官方定义。
4. 回答时先建立完整知识框架：前置概念、主流程或因果链、分支和边界、工程场景、常见误区、与已有知识的关系。
5. 在回答中就近引用本地知识与外部来源。发现本地资料明显过时、错误、冲突或缺失时，指出具体文档和建议修正方式。

## 3. 知识文档的文件类型必须进入固定目录

`Full-Stack-AI-NOTES` 使用以下稳定目录边界：

| 类型 | 固定位置 | 规则 |
| --- | --- | --- |
| 知识正文 | `Full-Stack-AI-NOTES/*.md` | 独立知识体系、专题笔记、项目与工程文档优先放根目录 |
| 文档图片 | `Full-Stack-AI-NOTES/assets/` | PNG、JPG、JPEG、GIF、WebP、SVG 等文档图片必须放这里 |
| 代码资源 | `Full-Stack-AI-NOTES/source/` | 独立 Demo、脚本、HTML、TS/JS/Python、可运行项目和测试代码必须放这里 |
| 其他附件 | `Full-Stack-AI-NOTES/resource/` | PDF、导出文档、Prompt、简历和其他非代码附件统一放这里 |
| Skill | `Full-Stack-AI-NOTES/skills/` | 保存稳定的 AI 执行规则、模板和参考规范 |
| QA | `QA.md` 与按需创建的 `QA/` | 只有明确要求记录的问题才进入 QA |

### 【图片资源必须进入 assets】

- 新增到知识文档中的本地图片必须保存到 `assets/`，不要把图片散落到根目录或与 Markdown 同级。
- 推荐按主题建立子目录，例如 `assets/browser/`、`assets/agent/`、`assets/performance/`。
- Markdown 使用相对路径引用，并在移动文件后检查链接是否仍有效。
- 图片本身只承担视觉证据或说明作用；关键结论仍应在 Markdown 正文中用文字表达。

### 【完整代码资源必须进入 source】

- Markdown 可以包含用于解释的最小代码片段。
- 当代码需要独立运行、测试、复用或超过“解释片段”的范围时，将完整文件放入 `source/`。
- HTML Demo、脚本、最小 Agent、测试项目等都属于 `source/`，不要放在知识根目录。
- 知识正文需要说明该源码验证了什么，并链接到对应文件；不要只留下源码而没有知识解释。

### 【PDF 等非代码附件必须进入 resource】

- PDF、简历、导出报告、历史 Prompt 等统一进入 `resource/`。
- 附件可以作为补充证据或原始材料，但不能成为长期知识的唯一入口。
- 如果 PDF 中存在需要长期复用的知识，优先提炼为 Markdown 知识正文，再从正文链接附件。
- 新增、移动或删除附件后，检查引用这些附件的 Markdown 和知识体系索引。

## 4. 完善知识文档时保持知识关系

- 发现经过核验、与现有主题相关的知识缺口时，优先补充或修正已有文档，不在末尾机械堆砌“补充内容”。
- 只有新主题具有独立概念边界、明确前置知识并且后续会持续扩展时，才在根目录新建独立 Markdown。
- 新写和实质整理的正文遵循 [文档规范](references/style-guide.md)。局部补充应尽量匹配原文风格，不破坏已有阅读路径。
- 完整工程过程必须保留问题、假设、方案、证据、失败结果、决策原因和最终结论，不能为了“整理”删除真实探索过程。
- 权威资料和引用必须真实可追溯。资料不足时缩小结论或显式标记不确定性。

## 5. 每次实质更新都同步维护知识体系索引

新增、重命名、移动或实质修改知识文档后，必须检查 [知识体系索引](../../知识体系索引.md)。

索引至少维护四种关系：

1. **主题入口**：新内容属于哪一条知识主线，主入口是什么。
2. **前置依赖**：理解该知识前应该先读什么。
3. **延伸关系**：学完后可以继续读什么。
4. **资源关系**：是否存在 `source/` 实现、`resource/` 附件或 `assets/` 图片。

索引只保存导航和关系，不复制整篇正文。移动资源时同步修正索引中的旧路径。

## 6. 只有明确要求时才记录 QA

普通提问、AI 主动提问、知识回答和知识文档完善都不自动产生 QA 文件。

只有用户明确说“记录问题”“保存这题”“写入 QA”等，才执行：

1. 先读取 [QA.md](../../QA.md)，检查是否已有相同或高度相关问题；
2. 如果需要新记录，在 `QA/` 下创建单题 Markdown；
3. 单题文件包含问题、可复述回答要点、完整标准回答、本地知识链接和外部证据；
4. 同步更新 `QA.md` 的问题索引、回答要点和相关问题；
5. 如果该问题暴露出知识正文缺口，优先完善对应知识文档，并同步知识体系索引；
6. QA 中涉及图片、代码或 PDF 时，同样遵守 `assets/`、`source/`、`resource/` 的目录规则。

用户明确要求记录时，按 [QA 记录模板](references/qa-record-template.md) 填写；模板只规定必需信息，不替代针对具体问题的知识结构。

## 7. 完成前进行仓库级检查

提交或写回前确认：

- 已先读取知识体系索引和相关正文，而不是只根据文件名或索引摘要处理；
- QA 是否只在用户明确要求时写入；
- 新增图片是否全部位于 `assets/`；
- 完整代码、Demo、脚本是否位于 `source/`；
- PDF 与其他非代码附件是否位于 `resource/`；
- 移动文件后的 Markdown 相对链接是否有效；
- 新增或实质修改的知识是否已经接入知识体系索引；
- 本地资料与外部资料的事实边界清楚；
- 关键结论有可靠证据，工程推论没有被写成官方定义。
