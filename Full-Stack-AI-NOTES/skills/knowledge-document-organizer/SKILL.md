# 知识问答与文档维护

本 Skill 服务于 `Full-Stack-AI-NOTES`。它同时负责 **知识读取、知识问答、知识文档维护、资源归档和 QA 记录**。目标不是把仓库当成普通文件夹搜索，而是让每一次回答或修改都沿着既有知识体系进行，并保持文档、代码、图片和附件之间的边界清晰。

## 1. 先读取知识体系，再读取具体文件

处理任何与 `Full-Stack-AI-NOTES` 有关的知识任务时，默认读取顺序为：

```text
README.md
   ↓
知识体系索引.md
   ↓
QA.md
   ↓
与当前问题直接相关的 Markdown 正文
   ↓
source/ / resource/ / assets/（按任务需要）
   ↓
外部官方文档、标准、论文或官方工程资料
```

规则：

1. [知识体系索引](../../知识体系索引.md) 是本目录的主知识地图。先通过它确认主题、前置知识、主文档和延伸文档，再读取正文。
2. 索引只用于定位，**不得仅根据索引摘要回答知识问题**。正式回答必须继续读取相关 Markdown 的实际内容。
3. [QA.md](../../QA.md) 用于判断当前问题是否已有记录、是否存在相关问题以及当前学习链路。普通问答只读 QA，不自动写入。
4. 一个主题存在多个历史文档时，优先选择知识体系索引中的主入口，再读取与当前问题实质相关的补充文档；不要按文件名随机拼接内容。
5. 如果本地资料互相冲突，明确指出冲突文件和差异，并使用更可靠的事实源进行核验，不静默选择一个版本。
6. 对版本、标准、框架行为、产品能力等可能变化的事实，必须结合最新官方资料核验。

## 2. 每次问答都同时使用本地知识和权威资料

1. 从知识体系索引和 QA 找到相关主题，再检索并阅读所有与本题实质相关的本地段落和交叉引用。
2. 同时查阅可访问的权威在线资料。优先级通常为：标准 / 规范 → 官方文档 → 原始论文 → 官方工程文章 → 高质量二手资料。
3. 区分三类结论：
   - **资料事实**：本地原文、标准、官方资料或论文直接支持；
   - **分析**：基于多个事实作出的解释，需要写清依据；
   - **工程推论**：经验性判断、设计建议或本地抽象，不冒充官方定义。
4. 回答时先建立完整知识框架：前置概念、主流程或因果链、分支和边界、工程场景、常见误区、与已有知识的关系。
5. 在回答中就近引用本地知识与外部来源。发现本地资料明显过时、错误、冲突或缺失时，指出具体文档和建议修正方式。

## 3. 知识梳理优先保证准确、清楚和可理解

知识梳理的目标不是展示术语数量，而是让读者能够沿着清晰的结构理解一个概念。表达准确和容易理解同等重要；不能为了显得专业而增加不必要的专业词，也不能为了简化表达而改变原始定义。

### 【优先使用直接、具体的中文表达】

1. 能用普通中文讲清楚的内容，不优先使用抽象术语、缩写或行业黑话。
2. 先说明“它是什么、解决什么问题、和前后知识是什么关系”，再解释内部机制和实现细节。
3. 一句话只承担一个主要意思。避免连续堆叠多个概念，让读者必须反向拆句才能理解。
4. 对概念之间的关系，优先使用因果链、执行流程、输入输出或对比表述，例如“请求进入服务端 → 校验身份 → 执行业务逻辑 → 访问数据库 → 返回结果”，而不是只罗列名词。
5. 如果一种表述虽然专业但不直观，应补充一层通俗解释；通俗解释用于帮助理解，不替代严格定义。

### 【专业术语首次出现时必须解释】

专业术语只有在确实能够提高准确性时才使用。术语第一次出现时，不能只给出名称而不说明含义。

推荐格式：

```text
中文名称（English Term / Abbreviation）：用一句直接的中文解释它表示什么，以及它在当前问题中起什么作用。
```

例如：

```text
幂等（Idempotency）：同一个操作重复执行多次，不应该因为重复执行而产生额外的业务结果。

反向代理（Reverse Proxy）：位于客户端和实际应用服务之间，先接收外部请求，再把请求转发给后端服务。

事件循环（Event Loop）：运行时持续检查哪些异步任务已经可以继续执行，并安排对应回调进入 JavaScript 执行流程。
```

具体规则：

1. 中文已有稳定译名时，优先写“中文名称（英文原词）”，例如“依赖注入（Dependency Injection）”。
2. 常见英文缩写第一次出现时，同时给出英文全称和中文解释，例如“TTL（Time To Live，生存时间）：表示一条数据还能保留多久”。
3. 没有稳定中文译名时，可以保留英文，但必须紧跟中文解释，不能默认读者已经理解。
4. 同一术语完成第一次解释后，后文可以直接使用中文名称或常见缩写，不需要重复解释。
5. 不要在同一句中连续引入多个没有解释的新术语。必须使用多个术语时，拆开说明它们各自的职责和关系。

### 【概念性问题先建立可理解的框架，再进入细节】

对于“某个系统是什么、完整体系如何组成、某个机制如何工作”这类概念性问题，默认按照下面的顺序组织：

```text
主题范围
   ↓
一句话核心定义
   ↓
整体框架 / 主要组成
   ↓
各部分分别解决什么问题
   ↓
主要流程或因果关系
   ↓
关键专业术语及解释
   ↓
适用边界、常见误区
   ↓
案例 / 工程映射
```

不要一开始就进入某个框架 API、配置项或底层实现，也不要把大量专业词平铺成“完整体系”。先让读者知道知识位于哪里，再逐步深入。

### 【流程图与框架图必须具备中文可读性】

流程图、框架图、知识树和时序图遵循以下规则：

1. 英文术语或缩写必须附简短中文含义或职责，不能只堆叠术语。
2. 节点优先表达“阶段 / 对象 + 职责”；关键箭头在关系不明显时补充“进入、触发、产生、验证”等关系词。
3. 总图只表达上位阶段和关系，API、配置、类名等实现细节下沉到局部图或正文。
4. 图必须通过“只看图”测试：不读正文也能看懂起点、各节点职责、前后关系和最终结果。

### 【知识文档必须先建立上位框架，禁止把完整性误写成同级知识清单】

知识点很多不等于知识体系完整。整理一个较大主题时，必须先回答：**这些知识为什么会同时出现在这里，它们之间是什么依赖、因果、数据流或阶段关系。** 如果只是把定义、协议、API、状态、性能、安全、部署、测试等连续写成大量同级标题，读者得到的是目录清单，而不是可迁移的知识框架。

默认先建立三层结构：

```text
总主线
主题从起点到目标怎样逐步演进
        ↓
核心分支
每个阶段分别解决哪一类问题
        ↓
叶子知识点
具体机制、API、数据结构、方案和边界
```

具体规则：

1. **先确定主线，再决定目录。** 新建或重构长文前，先用一句话或一张简图说明主题的起点、终点以及中间为什么会出现这些阶段。目录必须从这条主线推导，而不是从搜到的术语反向拼装。

2. **章节顺序优先体现“上一层暴露问题 → 下一层解决问题”。** 推荐使用以下关系组织：
   - 前置 → 后续；
   - 原因 → 结果；
   - 问题 → 机制；
   - 输入 → 处理 → 输出；
   - 数据流 / 请求流；
   - 生命周期 / 状态迁移；
   - 单机 → 分布式；
   - 功能实现 → 生产治理 → 验证。

3. **大量同级标题是需要重新归组的信号。** 如果连续出现很多 H2，并且这些标题只是“协议、API、鉴权、缓存、性能、安全、测试”等名词并列，应先寻找更高一级的共同问题，把它们收进少量核心阶段。H2 应表达上位阶段或一级知识分支，具体机制继续下沉到 H3 / H4。

4. **主线、支线和横切能力必须区分。** 有些知识属于流程中的某一步；有些能力会同时作用于多个阶段。不要把横切能力强行塞进生命周期中的某一个节点。常见横切维度包括：
   - Security（安全）；
   - Performance / Capacity（性能与容量）；
   - Observability（可观测性）；
   - Reliability（可靠性）；
   - Testing / Verification（测试与验证）。
     如果它们贯穿多个阶段，应明确标记为横切约束，并说明分别作用在哪些层。

5. **复杂系统优先寻找 1～2 条贯穿全文的长期主线。** 例如可以是 Request Lifecycle（请求生命周期）、Data Flow（数据流）、State Lifecycle（状态生命周期）、Control Flow（控制流）或 Resource Lifecycle（资源生命周期）。不同知识点要能够挂回这些主线，而不是各自孤立。

6. **总框架图只负责建立方向，不代替正文。** 总图之后仍需逐层解释：这一层从上游接收什么、解决什么问题、产生什么结果、为什么会继续进入下一层。

7. **已有长文重构时优先调整层级，不盲目重写内容。** 如果原有机制说明已经准确，应先把同级章节重新归入上位框架，再修正过渡关系和重复内容。结构问题不等于内容必须推倒重写。

8. **判断框架是否成立，可以做“只看目录”测试。** 隐藏正文后，读者应该仍能从标题看出：
   - 主题从哪里开始；
   - 分成哪几个核心阶段；
   - 每一阶段为什么接着上一阶段；
   - 哪些是主流程，哪些是横切约束；
   - 最终怎样进入工程实践、治理或验证。

推荐的抽象结构不是固定模板，但可以作为起点：

```text
问题背景 / 系统目标
        ↓
基础机制 / 核心模型
        ↓
业务或运行生命周期
        ↓
可靠性 / 状态 / 数据连续性
        ↓
规模化 / 部署 / 安全治理
        ↓
可观测性 / 测试 / 验证
```

不同主题应根据自身机制调整层级，**不得机械套用这组名称**。规范要求的是“先有上位逻辑，再有叶子知识”，不是要求所有文档拥有相同章节。

### 【知识点必须形成“结论—机制—证据”的完整解释链】

知识文档不能停留在“给出概念、列出优缺点、画一张箭头图”的层面。一个知识点只有在读者能够理解**为什么成立、怎样运行、如何验证**时，才算真正梳理完整。

默认优先建立下面这条解释链：

```text
先给核心结论
    ↓
说明它解决什么问题
    ↓
解释内部机制 / 因果关系
    ↓
用 API、协议、最小代码、流程图或状态机辅助理解
    ↓
用官方规范、测试、源码或可运行示例提供证据
    ↓
说明适用边界、方案取舍和常见误区
    ↓
必要时再收束为面试 / 答辩可复述结论
```

这是一种**内容完整性模型，不是固定排版模板**。PREP、结论先行、问题—原因—方案等结构都可以作为组织思路，但不得机械地在正文中强制使用 `P / R / E / P` 标签，也不得为了匹配模板把自然连续的知识拆碎。

具体规则：

1. **结论后必须继续解释。**
   “A 比 B 更安全”“WebSocket OPEN 不等于业务可用”“Monorepo 便于协作”这类句子都只是结论，后文必须继续回答“为什么”“通过什么机制”“代价是什么”。

2. **流程图后必须逐步解释。**
   图和箭头只负责展示关系，不能替代正文。每个关键节点都要说明输入、处理、输出，以及为什么需要这一层；同时图内节点本身也必须遵守“中文职责 + 必要术语”的可读性要求，不能依赖图后解释来补救术语堆叠。

3. **对比表不能代替机制说明。**
   表格适合压缩同一维度的差异，但“优点 / 缺点”之后仍应解释这些差异是怎样产生的。
   例如只写“Upgrade 前鉴权更安全、Upgrade 后更灵活”是不完整的，还要继续说明浏览器 API 限制、凭证承载方式、未认证连接窗口、认证超时和状态约束。

4. **抽象概念优先补一种可执行或可验证的辅助材料。**
   根据主题选择最合适的证据，不要求每个知识点同时拥有所有形式：
   - API 签名或官方最小用法；
   - 协议报文；
   - 伪代码或最小代码；
   - 状态机；
   - 时序图 / 数据流；
   - 数据结构 / Schema；
   - SQL / 配置片段；
   - 单元测试 / 集成测试；
   - 官方规范中的关键行为；
   - 项目源码中的真实实现证据。

5. **代码必须解释“验证了什么”。**
   不直接堆大段源码。优先截取能够证明当前结论的最小片段，并在代码前后说明：
   - 这段代码对应知识链中的哪一步；
   - 它证明了什么行为；
   - 它没有证明什么；
   - 当前实现还有什么边界。

6. **没有真实项目证据时使用通用示例，不编造实现。**
   可写“主流方案”“最小示例”“理想方案”；如果需要项目事实但未核验，明确写“需查仓库确认”。

7. **证据强度要和结论强度匹配。**
   - 标准定义 → 标准 / RFC / W3C / 官方文档；
   - API 行为 → 官方 API 文档或框架源码；
   - 项目实现 → 当前活动源码 + 测试；
   - 性能结果 → 可复现实验和指标；
   - 工程建议 → 明确标记为分析或方案，不冒充规范。

可以把一节完整知识理解成：

```text
“知道这个名词”
        ↓
“知道它解决什么问题”
        ↓
“知道内部为什么这样工作”
        ↓
“看到一个最小实现后能对应机制”
        ↓
“能从源码 / 测试 / 标准中验证结论”
        ↓
“知道什么时候不应该这样用”
        ↓
“能够迁移到新的工程场景”
```

知识梳理的目标是到达最后一层，而不是停在第一层。

### 【项目材料只能作为实践证据，不能承担通用正文的叙事上下文】

通用知识正文必须在脱离项目名、仓库和业务背景后仍然成立。项目的作用是**验证和连接知识**，不是替代知识本身；当某个机制存在对应的项目实践时，可在该知识点附近加入简短的实践映射，链接到项目分析文档的对应章节。

正确关系：

```text
通用问题
    ↓
定义 / 原理 / 机制
    ↓
API / 协议 / 最小示例
    ↓
工程判断方法
    ↓
项目源码作为实现证据
```

不推荐：

```text
项目先做了 A
    ↓
项目又做了 B
    ↓
因此顺便解释 A / B 是什么
```

如果文档位于项目仓库中，可以在对应知识点附近引用真实源码、测试、配置和运行结果，但仍应先把通用机制讲清楚，再说明“当前实现如何落地这一机制”。不要把项目变量、文件名或业务流程升级成知识目录本身。

项目源码证据推荐按下面方式使用：

```text
通用结论
    ↓
机制解释
    ↓
最小示例
    ↓
源码证据：真实工程中的实现片段
    ↓
当前实现边界 / 与主流方案差异
```

这样项目事实提供说服力，同时不会让正文退化成项目总结。


### 【项目分析文档必须能够脱离仓库独立阅读】

项目文档虽然以真实仓库为证据，但正文不能把“打开源码链接以后自己看”当成解释的一部分。读者即使暂时无法访问仓库，也应该能够仅凭文档理解关键实现、关键数据流和关键取舍。

具体规则：

1. **关键实现必须直接出现在正文中。** 对支撑核心结论的实现，必须截取真实源码中的最小必要片段并放在对应机制附近，不能只写文件路径、行号或 GitHub 链接。
2. **源码链接是核验入口，不是正文替代物。** 链接用于继续查看完整上下文；正文必须已经解释完当前机制。删除链接后，文档的主逻辑仍应成立。
3. **每个主链关键节点至少满足“机制 + 代码 + 解释”三件事。** 例如数据接收、队列调度、状态提交、缓存、鉴权、恢复、渲染、限流等核心节点，不能只画箭头或只给结论。
4. **代码片段优先保留真实变量、判断和调用关系。** 不为了简短而改写成与源码不一致的伪代码；如果确实使用伪代码，必须明确标记“伪代码 / 结构化简化”。
5. **不要把整个文件复制进正文。** 每段只保留能够证明当前结论的部分，并在代码后明确说明：输入是什么、做了什么判断或状态变化、输出到下一层是什么、它解决了前面哪个问题、还有什么没有解决。
6. **涉及优化过程时要同时给出优化前后的关键差异。** 如果旧实现已经删除，可以根据当前保留的实验报告、提交证据或历史资料提炼“原逻辑”，但必须明确这是经过证据还原的历史实现，不得伪装成当前源码。
7. **实验结论附近要给出对应实现。** 例如实验得出“批量能够降低更新次数”，正文后续必须展示实际 batch 是在哪里进入队列、怎样热更新、怎样影响消费；不能让实验和代码各自成为孤岛。
8. **项目正式文档不得依赖待删除的历史文档才能理解。** 历史文档可作为迁移输入，但迁移后的正式正文必须重新写完整；长期保留的证据应优先落到当前源码、当前测试、当前实验结果和稳定的官方资料。

推荐结构：

```text
项目现象 / 问题
        ↓
为什么怀疑这一层
        ↓
实验或运行证据
        ↓
当前真实关键代码
        ↓
逐行解释关键状态变化
        ↓
优化解决了什么
        ↓
仍然没有解决什么
```

项目分析文档的目标不是“告诉读者代码在哪”，而是“让读者通过文档本身理解这套代码为什么这样设计”。

### 【权威定义和原始结论不能被通俗解释替代】

如果概念涉及标准、规范、官方文档、论文、权威报告或正式技术定义，需要同时保留“严格定义”和“通俗解释”两层内容。

处理规则：

1. **权威定义优先保持原意。** 对正式定义、结论、限制条件、适用范围和关键数字，不为了语言更顺而自行改变含义。
2. **必要时保留关键原文或严谨翻译。** 原文较短且本身就是核心定义时，可以保留原始表述；原文较长时只保留支持当前结论的关键部分，并给出来源。
3. **通俗解释必须与权威定义分开。** 推荐先写“官方 / 标准定义”，再写“直观理解”，避免读者把工程类比误认为正式定义。
4. **不能用项目经验替代标准结论。** 项目做法只能作为实现案例；如果项目实现与标准存在差异，需要明确说明。
5. **多个权威来源存在口径差异时，不自行合并成一个不存在的统一定义。** 分别说明来源、时间或版本以及差异。
6. 对可能随版本变化的框架能力、平台规则和指标标准，仍按前文规则查阅最新官方资料核验。

推荐表达：

```text
严格定义：
    保留标准、官方文档或论文真正表达的结论。

直观理解：
    用更简单的中文解释这一定义解决什么问题、可以怎样理解。

工程场景：
    再说明它在实际系统中通常怎样使用。
```

这三层承担不同职责，不能互相替代。

## 4. 知识文档的文件类型必须进入固定目录

`Full-Stack-AI-NOTES` 使用以下稳定目录边界：

| 类型     | 固定位置                        | 规则                                                                                       |
| -------- | ------------------------------- | ------------------------------------------------------------------------------------------ |
| 知识正文 | `Full-Stack-AI-NOTES/*.md`      | 独立知识体系、专题笔记和工程知识文档优先放根目录；知识点正文必须脱离具体项目上下文独立成立 |
| 文档图片 | `Full-Stack-AI-NOTES/assets/`   | PNG、JPG、JPEG、GIF、WebP、SVG 等文档图片必须放这里                                        |
| 代码资源 | `Full-Stack-AI-NOTES/source/`   | 独立 Demo、脚本、HTML、TS/JS/Python、可运行项目和测试代码必须放这里                        |
| 其他附件 | `Full-Stack-AI-NOTES/resource/` | PDF、导出文档、Prompt、简历和其他非代码附件统一放这里                                      |
| Skill    | `Full-Stack-AI-NOTES/skills/`   | 保存稳定的 AI 执行规则、模板和参考规范                                                     |
| QA       | `QA.md` 与按需创建的 `QA/`      | 只有明确要求记录的问题才进入 QA                                                            |

### 【根目录知识正文统一使用“首字母-原名”前缀】

根目录知识正文统一采用 `字母-原名.md` 的命名形式：去掉原有的排序数字前缀，再按文件名的首字符取一个 A～Z 的字母前缀，让首字母相同的文档在目录中自然聚拢、按字母表顺序排列。

```text
A-Agent学习教程.md
Q-前端模块化规范.md
X-项目工程化设计.md
```

规则：

1. **按首字符确定字母。**
   - 首字符是英文字母取该字母的大写，首字符是中文取该字的拼音首字母。
2. **前缀只表示分组和排序，不表示知识重要性或学习顺序。** 知识之间的前置、延伸和依赖关系仍由 [知识体系索引](../../知识体系索引.md) 维护，不能靠前缀表达。
3. **索引类入口文件不加前缀。** `README.md`、`知识体系索引.md`、`QA.md` 保持原名，作为稳定入口。
4. **重命名后必须同步修正引用。** 至少检查：本目录正文之间的相对链接、`知识体系索引.md`、`README.md`、Skill 内部链接，以及仓库其他目录中以相对路径、GitHub URL 或百分号编码 URL 形式引用本目录文档的位置。链接目标含空格时，要同时处理空格与 `%20` 两种写法。

### 【图片资源必须进入 assets】

- 新增到知识文档中的本地图片必须保存到 `assets/`，不要把图片散落到根目录或与 Markdown 同级。
- 推荐按主题建立子目录，例如 `assets/browser/`、`assets/agent/`、`assets/performance/`。
- Markdown 使用相对路径引用，并在移动文件后检查链接是否仍有效。
- 图片本身只承担视觉证据或说明作用；关键结论仍应在 Markdown 正文中用文字表达。

### 【完整代码资源必须进入 source】

- Markdown 可以包含用于解释的最小代码片段。
- 当代码需要独立运行、测试、复用或超过“解释片段”的范围时，将完整文件放入 `source/`。
- HTML Demo、脚本、最小 Agent、测试项目等都属于 `source/`，不要放在知识根目录。
- 知识正文需要说明该源码验证了什么，并链接到对应文件；不要只留下源码而没有知识解释。

### 【PDF 等非代码附件必须进入 resource】

- PDF、简历、导出报告、历史 Prompt 等统一进入 `resource/`。
- 附件可以作为补充证据或原始材料，但不能成为长期知识的唯一入口。
- 如果 PDF 中存在需要长期复用的知识，优先提炼为 Markdown 知识正文，再从正文链接附件。
- 新增、移动或删除附件后，检查引用这些附件的 Markdown 和知识体系索引。

## 5. 完善知识文档时保持知识关系

### 【通用知识与项目实践分层维护，并在正文就近建立映射】

`Full-Stack-AI-NOTES` 负责通用知识，项目仓库负责真实实现、实验和取舍。两层内容分开维护，但不应彼此割裂。

规则：

1. **通用知识必须能够脱离具体项目独立成立。** 定义、原理、机制、流程、边界和判断方法不能依赖某个项目的业务背景或实现细节。
2. **当某个知识点在项目中存在可验证的具体实践时，应在对应知识点附近就近衔接项目分析。** 链接尽量指向项目文档中与当前机制对应的章节，而不是统一堆到文末。
3. 正文中的项目衔接只承担“从通用知识进入真实工程”的导航作用，可以简短说明该项目章节验证了什么；真实源码、配置、数据流、实验结果、取舍和项目结论仍写在项目分析文档中。
4. **项目实例不能反向主导通用知识结构。** 先按通用机制组织正文，再把项目实践挂到对应节点；不能按项目开发顺序重写知识体系，也不能把单个项目做法写成行业通则。
5. 项目分析文档应反向引用对应的通用知识入口，并明确区分当前实现、主流方案与建议方案。
6. 文末可以保留项目实践导航或汇总入口，但它只是补充索引，**不能替代正文中的就近映射**。
7. 如果只有项目分析、还没有对应通用知识入口，应先补齐可独立成立的通用正文，再建立双向引用；同一个知识点仍只维护一个主要通用入口。

推荐关系：

```text
知识体系索引
    ↓
通用知识正文
    ├─ 知识点 A ──→ 对应项目实践 A
    ├─ 知识点 B ──→ 对应项目实践 B
    └─ 知识点 C ──→ 对应项目实践 C
```

**知识体系索引仍只连接 `Full-Stack-AI-NOTES` 内部内容，跨项目连接由通用正文承担。**

- 发现经过核验、与现有主题相关的知识缺口时，优先补充或修正已有文档，不在末尾机械堆砌“补充内容”。
- 只有新主题具有独立概念边界、明确前置知识并且后续会持续扩展时，才在根目录新建独立 Markdown。
- 新写和实质整理的正文遵循 [文档规范](references/style-guide.md)。局部补充应尽量匹配原文风格，不破坏已有阅读路径。
- 完整工程过程必须保留问题、假设、方案、证据、失败结果、决策原因和最终结论，不能为了“整理”删除真实探索过程。
- 权威资料和引用必须真实可追溯。资料不足时缩小结论或显式标记不确定性。

## 6. 每次实质更新都同步维护知识体系索引

新增、重命名、移动或实质修改知识文档后，必须检查 [知识体系索引](../../知识体系索引.md)。

索引至少维护四种关系：

1. **主题入口**：新内容属于哪一条知识主线，主入口是什么。
2. **前置依赖**：理解该知识前应该先读什么。
3. **延伸关系**：学完后可以继续读什么。
4. **资源关系**：是否存在 `source/` 实现、`resource/` 附件或 `assets/` 图片。

索引只保存导航和关系，不复制整篇正文。移动资源时同步修正索引中的旧路径。

索引的直接链接范围必须限制在 `Full-Stack-AI-NOTES` 目录内部，包括根目录知识正文、`source/`、`resource/`、`assets/`、`skills/` 和 QA。其他项目目录中的实现文档不得直接成为知识体系索引节点；需要关联时，先进入本目录中的通用知识正文，再由正文在相关知识点附近建立项目实践映射。

## 7. 只有明确要求时才记录 QA

普通提问、AI 主动提问、知识回答和知识文档完善都不自动产生 QA 文件。

只有用户明确说“记录问题”“保存这题”“写入 QA”等，才执行：

1. 先读取 [QA.md](../../QA.md)，检查当前知识点是否已经存在同一套回答框架；不要只按提问文字判断是否重复。
2. 如果需要新记录，在 `QA/` 下创建单题 Markdown；一个 QA 表示一套稳定的回答知识框架，同一框架可以对应多个常见提问方式。
3. `QA.md` 每条记录默认按“【提问】→【回答框架】→【完整回答】→【继续展开】”组织。其中“回答框架”必须说明回答路径、知识层级、关键结论和边界，不能压缩成一句回答摘要。
4. QA 成稿不得保留“原问题”“原始资料”、聊天过程、中间分析或检索过程等整理痕迹。原始资料只作为输入；真正支撑结论的资料按正文引用规则正常使用。
5. “【提问】”描述当前知识点在学习、面试或答辩中可能出现的问法。多个问法只有在共享同一核心回答框架时才合并，否则拆成独立 QA。
6. “【继续展开】”只记录从当前回答自然产生的下一层追问。只有存在真正有助于回答该追问的知识正文或已有 QA 时才附链接；不得为了建立关联而机械指定若干文档。
7. 单题文件保存整理后的完整标准回答，正文按知识自身的概念依赖、流程、因果和边界组织，不保留中间分析残留。
8. 如果问题暴露出知识正文缺口，优先完善对应知识文档，并同步知识体系索引。
9. QA 中涉及图片、代码或 PDF 时，同样遵守 `assets/`、`source/`、`resource/` 的目录规则。

用户明确要求记录时，按 [QA 记录模板](references/qa-record-template.md) 填写；模板定义 QA 的知识组织原则，不要求机械套用固定章节。

## 8. 完成前进行仓库级检查

提交或写回前确认：

- 已先读取知识体系索引和相关正文，而不是只根据文件名或索引摘要处理；
- QA 是否只在用户明确要求时写入；
- 新增图片是否全部位于 `assets/`；
- 完整代码、Demo、脚本是否位于 `source/`；
- PDF 与其他非代码附件是否位于 `resource/`；
- 移动文件后的 Markdown 相对链接是否有效；
- 新增或重命名根目录知识正文时，文件名是否符合“首字母-原名”前缀规范，且引用是否已同步修正；
- 新增或实质修改的知识是否已经接入知识体系索引；
- 长文是否已经先建立总主线和上位框架，避免大量同级标题平铺；
- 是否区分主流程、分支知识和横切能力，并说明章节之间的前后依赖或因果关系；
- 知识正文是否能够脱离具体项目上下文独立阅读；
- 知识体系索引是否只直接链接 `Full-Stack-AI-NOTES` 内部路径；
- 如果关联其他项目实现，是否在相关知识点附近建立了对应实践映射，而不是只在文末集中挂链接或由索引直接跨目录链接；
- 是否避免在通用知识正文中复制已有项目文档的目录、配置和实现细节；
- 本地资料与外部资料的事实边界清楚；
- 关键结论有可靠证据，工程推论没有被写成官方定义。
