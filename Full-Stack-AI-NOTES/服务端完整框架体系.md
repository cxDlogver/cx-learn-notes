# 第一章 服务端完整框架体系建立从请求到运行环境的全景认知

学习服务端时，最容易产生的误区，是把“服务端”直接等同于 Node.js、NestJS、数据库，或者某一个 HTTP 接口。更准确的理解应该从 **Client / Server（客户端 / 服务端）之间的通信关系**开始，再逐步扩展到一个真实系统为了长期对外提供能力所需要的其他部分。

## 1. 服务端从 Client / Server 通信关系扩展为完整工程系统

### 【HTTP 首先定义客户端与服务端之间的通信关系】

从 HTTP 最基本的通信模型看：

```text
Client（客户端）
      │
      │ Request（请求）
      ↓
Server（服务端）
      │
      │ Response（响应）
      ↓
Client（客户端）
```

HTTP 语义标准 RFC 9110 将 HTTP 描述为一种 Client / Server（客户端 / 服务端）协议。Client 是主动建立连接并发送 HTTP Request（HTTP 请求）的程序；Server 是接受连接、处理 HTTP Request，并返回 HTTP Response（HTTP 响应）的程序。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html)

这里的 Client 和 Server 表示的是**一次通信中的角色**，而不是某种固定的软件类型。

例如，一个后端 API 面对浏览器时是 Server：

```text
Browser
   │ Request
   ↓
API Server
```

但这个 API 去访问数据库时，它又会成为数据库的 Client：

```text
API Server
   │ Database Request
   ↓
Database Server
```

PostgreSQL 官方文档同样使用 Client / Server 模型描述数据库系统：数据库 Server 持续管理数据库并接受来自 Client 应用的连接，而 Web Server 也可以作为数据库 Client。[[2]](https://www.postgresql.org/docs/current/tutorial-arch.html)

因此首先需要建立一个重要认识：

> **Client / Server 描述的是通信关系，而不是一套固定的软件身份。**

同一个程序面对不同对象时，可以处于不同角色。

### 【工程中的服务端范围大于一次 HTTP 请求】

如果只从 HTTP 通信看，服务端可以简单表示为：

```text
Request
   ↓
Server
   ↓
Response
```

但真实工程中的 Server 通常不是一个单独函数，也不是某一个框架。

一个请求进入系统后，可能还要经过：

```text
网络入口
   ↓
HTTP 请求接收
   ↓
参数和身份检查
   ↓
业务逻辑处理
   ↓
数据库 / 缓存访问
   ↓
异步任务
   ↓
外部服务
   ↓
Response
```

这些程序又必须真正运行在操作系统、服务器或容器中，并且需要配置、安全、日志、指标和健康检查等能力保证它们能够长期运行。

因此，从工程学习的角度，可以先把服务端理解为：

> **服务端系统是一组持续对外提供业务能力的程序和运行环境。它负责接收请求或任务，执行必要的业务规则，读取和修改数据，并通过安全、配置、部署和监控等能力保证这些功能能够稳定运行。**

这里需要区分两层含义：

```text
HTTP 中的 Server
    ↓
描述一次通信中的“服务端角色”

工程中的服务端系统
    ↓
描述为了长期提供业务能力而形成的一整套程序、数据和运行环境
```

后者是一种为了学习和分析真实工程而建立的**工程模型**，并不是 RFC 或其他标准规定的“服务端官方架构”。

### 【完整服务端可以拆成五个主要体系】

从工程角度，可以先把服务端整理为五个主要体系：

```text
                                Client
                    Browser / SDK / App / Web
                                  │
                                  │ HTTP / HTTPS
                                  ↓
┌─────────────────────────────────────────────────────────────┐
│                    一、请求处理体系                          │
│                                                             │
│  网络接入 → HTTP Server → Framework → Controller → Service │
└─────────────────────────────┬───────────────────────────────┘
                              │
                 ┌────────────┴────────────┐
                 ↓                         ↓
┌────────────────────────┐      ┌─────────────────────────┐
│   二、状态与数据体系    │      │   三、异步处理体系      │
│                        │      │                         │
│ Database               │      │ Task / Queue / Outbox │
│ Cache                  │      │ Worker                 │
│ Storage                │      │ Retry / Dead Letter   │
└────────────┬───────────┘      └────────────┬────────────┘
             │                               │
             └──────────────┬────────────────┘
                            ↓
                    External Services

───────────────────────────────────────────────────────────────

                 四、运行与部署体系

Source → Build → Process → Service → Container → Host

───────────────────────────────────────────────────────────────

                 五、横向系统能力

Security / Config / Log / Metric / Trace / Health
```

这五个部分分别回答五类问题：

| 体系 | 主要解决的问题 |
| --- | --- |
| 请求处理体系 | 一个外部请求进入服务端以后，怎样被接收并转换成具体业务操作 |
| 状态与数据体系 | 用户、订单、配置等数据怎样被保存，并在请求结束后继续存在 |
| 异步处理体系 | 不需要在当前请求中立即完成的任务怎样交给后台继续执行 |
| 运行与部署体系 | 写好的代码怎样真正变成持续运行的程序 |
| 横向系统能力 | 系统怎样保证安全、可配置、可观察，并在异常时能够被发现和定位 |

这五个部分**不是某个标准规定的“服务端五层架构”**，而是一套用于学习服务端的工程心智模型。

它的作用是让后续学习到的具体技术都能够找到位置：

```text
Node.js
    → 程序运行环境

HTTP / NestJS
    → 请求处理

PostgreSQL / Redis
    → 数据和状态

Worker / Queue
    → 异步任务

Docker
    → 运行与部署

Log / Metric / Trace
    → 横跨整个系统的可观测能力
```

因此，服务端学习的第一步并不是先记住大量框架和工具，而是先建立下面这张基础认知：

```text
                    服务端系统
                        │
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
   请求怎么处理      数据怎么保存      后台任务怎么执行
       │                │                │
       └────────────────┼────────────────┘
                        ↓
                  程序怎么运行
                        │
                        ↓
             系统怎么稳定、安全地运行
```

后续学习到任何具体技术时，都可以重新问两个问题：

> **它位于服务端体系的哪个位置？**

> **它到底解决了什么问题？**

这就是建立服务端完整知识框架的第一步。
