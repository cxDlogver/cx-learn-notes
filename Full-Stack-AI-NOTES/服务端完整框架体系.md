# 服务端完整框架体系建立从请求到运行环境的全景认知

## 1. 服务端从 Client / Server 通信关系扩展为完整工程系统

### 【HTTP 首先定义客户端与服务端之间的通信关系】

从 HTTP 最基本的通信模型看：

```text
Client（客户端）
      │
      │ Request（请求）
      ↓
Server（服务端）
      │
      │ Response（响应）
      ↓
Client（客户端）
```

HTTP 语义标准 RFC 9110 对这一关系有明确说明：HTTP 是一种 **Client / Server（客户端 / 服务端）协议**。Client 是主动建立连接并发送 HTTP Request（HTTP 请求）的程序；Server 是接受连接、处理 HTTP Request，并返回 HTTP Response（HTTP 响应）的程序。这里的 Client 和 Server 表示的是**一次通信中的角色**，而不是某种固定的软件类型；同一个程序在一种关系中可以是 Server，在另一种关系中又可以成为 Client。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html)

例如，一个后端 API 面对浏览器时是 Server：

```text
Browser
   │ Request
   ↓
API Server
```

但这个 API 去查询 PostgreSQL 时，它又变成数据库的 Client：

```text
API Server
   │ SQL / Database Request
   ↓
PostgreSQL Server
```

PostgreSQL 官方文档本身也采用 Client / Server 模型：应用程序作为数据库 Client，与持续运行的 PostgreSQL Server 建立连接并执行数据库操作。[[2]](https://www.postgresql.org/docs/current/tutorial-arch.html)

因此：

> **Client / Server 首先描述的是通信关系，而不是一套固定的系统架构。**

### 【工程中的服务端范围比一次 HTTP 请求更大】

但如果从工程角度讨论“服务端系统”，范围会比 HTTP 中的 Server 更大。

可以先建立这样一个定义：

> **服务端系统是一组持续对外提供业务能力的程序和运行环境。它负责接收请求或任务，执行必要的业务规则，读取和修改数据，并通过安全、配置、部署和监控等能力保证这些功能可以稳定运行。**

这里需要特别注意：这是一种为了理解工程系统而建立的**工程定义**，不是 RFC 或某个标准规定的“服务端官方定义”。

一个最简单的服务端可能只有：

```text
Request
   ↓
HTTP Server
   ↓
Business Logic
   ↓
Response
```

例如 Node.js 官方展示的最小 HTTP Server，就是通过 `createServer()` 接收请求并返回响应。Node.js 官方将 Node.js 定义为 **asynchronous event-driven JavaScript runtime（异步、事件驱动的 JavaScript 运行时）**，可以用于构建网络应用。这里的 Runtime（运行时）可以简单理解为：**真正负责执行 JavaScript 程序的运行环境**。[[3]](https://nodejs.org/en/about)

但是随着业务复杂度增加，一个请求通常不会只经过一个函数。

例如，一个“创建订单”的请求可能经历：

```text
用户发送请求
    ↓
确认请求应该进入哪个服务
    ↓
解析 HTTP 请求
    ↓
检查用户身份和请求参数
    ↓
执行创建订单的业务规则
    ↓
读取商品和库存数据
    ↓
写入订单数据库
    ↓
创建后续异步任务
    ↓
返回创建结果
```

因此，真实的服务端逐渐形成多个相互协作的部分。

### 【完整服务端可以拆成五个主要体系】

可以把它整理成下面五个主要体系：

```text
                               Client
                    Browser / App / SDK / Other Service
                                  │
                                  │ HTTP / HTTPS
                                  ↓
┌──────────────────────────────────────────────────────────────┐
│                     一、请求处理体系                         │
│                                                              │
│ 网络入口 → HTTP Server → Application → Business Logic       │
│                                                              │
│ 把一次外部请求转换成具体的业务操作                           │
└──────────────────────────────┬───────────────────────────────┘
                               │
                 ┌─────────────┴──────────────┐
                 ↓                            ↓
┌─────────────────────────┐       ┌───────────────────────────┐
│   二、状态与数据体系     │       │    三、异步处理体系      │
│                         │       │                           │
│ Database（数据库）      │       │ Task（任务）             │
│ Cache（缓存）           │       │ Queue（任务队列）        │
│ Storage（文件存储）     │       │ Worker（后台执行程序）  │
│                         │       │ Retry（失败重试）        │
│ 保存和读取系统状态      │       │ 处理不必立即完成的工作  │
└────────────┬────────────┘       └────────────┬──────────────┘
             │                                 │
             └──────────────┬──────────────────┘
                            ↓
              External Service（外部服务）

──────────────────────────────────────────────────────────────

                     四、运行与部署体系

Source Code（源码）
        ↓
Build（构建）
        ↓
Runtime（运行环境）
        ↓
Process（运行中的程序）
        ↓
Container / Host（容器 / 主机）

让代码真正成为可以持续运行的程序

──────────────────────────────────────────────────────────────

                     五、横向系统能力

Security        安全
Configuration   配置
Logging         日志
Metrics         指标
Tracing         请求链路
Health Check    健康检查

这些能力贯穿前面的所有部分
```

这五个部分**不是某个标准规定的“服务端五层架构”**，而是一套用来学习和分析服务端系统的工程框架。它的价值在于：以后学习 Node.js、NestJS、PostgreSQL、Redis、消息队列、Docker 等技术时，可以知道每一种技术究竟在解决什么问题，而不是把它们当成一串互不相关的名词。

### 【请求处理体系负责把外部请求转换成业务操作】

其中第一部分是**请求处理体系**，回答的是：

```text
一个请求进入服务端以后，
是谁接收它，
怎样找到对应代码，
最终怎样完成业务操作？
```

例如在 NestJS 中，Controller（控制器）负责接收进入应用的请求，并把更复杂的处理交给 Service 等 Provider（提供业务能力的对象）。NestJS 官方明确说明，Controller 的职责是处理进入应用的请求并向客户端返回响应。[[4]](https://docs.nestjs.com/controllers)

因此可以把它简化理解成：

```text
HTTP Request
      ↓
Controller
      ↓
Service
      ↓
Business Logic
      ↓
Database / Other Service
```

但 **Controller / Service 并不是 HTTP 标准要求的结构**，而是 NestJS 等应用框架常用的代码组织方式。

### 【状态与数据体系让请求结束以后数据仍然存在】

第二部分是**状态与数据体系**。

请求本身通常很短：

```text
Request
   ↓
处理
   ↓
Response
   ↓
结束
```

但用户、订单、权限、配置、监控数据等信息不能随着请求结束而消失，所以系统需要 Database（数据库）、Cache（缓存）或者 Storage（存储）来保存状态。

### 【异步处理体系负责执行不必阻塞当前请求的工作】

第三部分是**异步处理体系**。

有些工作不需要在当前请求中立即完成，例如：

```text
发送邮件
生成报告
处理图片
数据聚合
大量计算
```

如果全部放在一次 HTTP 请求里执行：

```text
Request
   ↓
任务 A
   ↓
任务 B
   ↓
任务 C
   ↓
Response
```

客户端就必须一直等待。

因此可以把任务拆出去：

```text
Request
   ↓
API
   ↓
创建 Task
   ↓
Queue
   ↓
快速返回 Response

        Queue
          ↓
        Worker
          ↓
       后台执行任务
```

Queue（队列）可以理解为**暂时保存待处理任务的地方**；Worker（工作进程 / 后台执行程序）则负责从队列中取出任务并执行。RabbitMQ 官方对 Work Queue（工作队列）的解释就是：避免立即执行耗时任务并等待其完成，而是先把任务放入队列，由后台 Worker 稍后处理。[[5]](https://www.rabbitmq.com/tutorials/tutorial-two-javascript)

### 【运行与部署体系让源码真正变成在线程序】

第四部分是**运行与部署体系**。

写出代码并不意味着系统已经存在：

```text
main.ts
```

只是源码。

必须经过：

```text
Source Code
    ↓
Build
    ↓
Runtime
    ↓
Process
```

程序真正开始执行以后，操作系统中才出现 Process（进程，也就是**一个正在运行的程序实例**）。

这个进程可以直接运行在服务器上，也可以放在 Container（容器）中：

```text
Application Process
        ↓
Container
        ↓
Host
```

因此 Container 并不是服务端业务逻辑的一部分，它解决的是**程序以什么环境运行和部署**的问题。Container 也不是所有服务端系统都必须使用的，所以这里更准确的关系是：

```text
Process
   ↓
可以运行于
   ├── Host
   │
   └── Container → Host
```

多个应用、数据库和缓存还可以组成一个完整运行环境。例如 Docker Compose 官方将自己定义为用于 **定义和运行多容器应用（multi-container applications）** 的工具，一个配置文件可以描述多个 Service、Network 和 Volume。[[6]](https://docs.docker.com/compose/)

### 【横向系统能力贯穿服务端的所有部分】

最后是**横向系统能力**。

这些能力不是请求处理完成以后额外添加的“第五步”，而是贯穿整个系统：

```text
                 Request
                    │
                    ↓
Security ─────── Application ─────── Logging
                    │
                    ↓
                 Database
                    │
                    ↓
                  Worker

Configuration / Metrics / Trace / Health
同样贯穿这些运行单元
```

例如 Observability（可观测性）指的是：**通过系统主动产生的信息理解一个正在运行的系统发生了什么**。OpenTelemetry 官方将 Logs（日志）、Metrics（指标）和 Traces（链路追踪）作为重要的 Telemetry（遥测数据，即系统运行时产生的观察数据）。[[7]](https://opentelemetry.io/docs/concepts/observability-primer/)

### 【服务端学习首先建立问题框架而不是技术名词表】

最终可以把服务端的整体概念压缩成一句话：

> **服务端不是某一种技术，而是一套持续对外提供业务能力的系统。它接收请求或任务，执行业务规则，管理系统数据；同时还需要异步处理、运行部署、安全、配置和可观测性等能力，才能成为一个可以稳定运行的完整工程系统。**

因此，学习服务端时真正需要建立的不是：

```text
Node.js
NestJS
Redis
PostgreSQL
Docker
...
```

这样一张技术名词表，而应该先建立：

```text
                    服务端系统
                        │
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
   请求怎么处理      数据怎么保存      后台任务怎么执行
       │                │                │
       └────────────────┼────────────────┘
                        ↓
                  程序怎么运行
                        │
                        ↓
             系统怎么稳定、安全地运行
```

后续学习到任何具体技术，都可以重新问一句：

> **它位于服务端体系的哪个位置，它到底解决了什么问题？**

## 2. 请求处理体系建立从网络入口到业务响应的完整链路

在第一部分中，我们已经把服务端拆成了五个主要体系：

```text
服务端系统
   │
   ├── 请求处理体系
   ├── 状态与数据体系
   ├── 异步处理体系
   ├── 运行与部署体系
   └── 横向系统能力
```

现在先单独进入第一条主线：**请求处理体系**。

这里最重要的不是先记住 Middleware、Guard、Controller、Service 这些名称，而是先回答一个完整问题：

> **客户端发出的一个请求，从进入服务端开始，到最终得到响应，中间究竟发生了什么？**

从完整工程角度看，可以先建立下面这条主链：

```text
Client
  │
  │ HTTP Request
  ↓
网络入口
  ↓
Reverse Proxy / Gateway
  ↓
HTTP Server
  ↓
Application Framework
  ↓
通用前置处理
  ↓
路由与访问控制
  ↓
参数解析与校验
  ↓
Controller
  ↓
Service
  ↓
Database / Cache / External Service
  ↓
业务结果
  ↓
响应转换 / 异常处理
  ↓
HTTP Response
  ↓
Client
```

这就是后续所有请求知识的“父级框架”。

### 【请求体系的边界大于 Controller 到 Service】

如果只从 NestJS 代码看，一个请求可能很像：

```text
Controller
    ↓
Service
    ↓
Database
```

但这只是请求进入应用以后的中间一段。

完整链路实际上包含三个明显阶段：

```text
第一阶段：请求到达应用
Client
  ↓
Network
  ↓
Proxy
  ↓
HTTP Server


第二阶段：应用理解并处理请求
HTTP Server
  ↓
Framework
  ↓
Middleware / Guard / Pipe
  ↓
Controller
  ↓
Service


第三阶段：产生并返回结果
Service
  ↓
Database / External Service
  ↓
Result
  ↓
Interceptor / Exception Handling
  ↓
HTTP Response
  ↓
Client
```

因此可以把请求处理体系定义为：

> **请求处理体系负责接收外部请求，理解请求表达的意图，判断请求是否允许执行，把请求映射到具体业务逻辑，并最终生成符合通信协议的响应。**

这里实际上存在三种不同层次的问题：

| 层次       | 主要问题                               |
| ---------- | -------------------------------------- |
| 网络与协议 | 请求怎样真正到达程序                   |
| 应用框架   | 请求应该交给哪段代码、怎样进行统一处理 |
| 业务处理   | 这个请求真正要完成什么业务             |

理解这三个层次以后，就不会把 HTTP、NestJS 和业务代码混为一谈。

### 【网络入口负责把请求送到正确的服务程序】

客户端发送：

```text
POST https://api.example.com/orders
```

以后，请求并不是直接“跳进 Controller”。

在进入应用之前，首先要找到目标服务器并建立通信。

可以先建立一个粗粒度链路：

```text
URL
 ↓
DNS
 ↓
IP
 ↓
建立网络连接
 ↓
HTTPS 时建立 TLS 安全连接
 ↓
发送 HTTP Request
 ↓
服务端网络入口
```

DNS（Domain Name System，域名系统）负责把类似：

```text
api.example.com
```

转换成服务器能够访问的网络地址。

TCP（Transmission Control Protocol，传输控制协议）等传输机制负责建立数据传输通道。

TLS（Transport Layer Security，传输层安全协议）则用于 HTTPS 场景，对通信进行加密和身份验证。

这些知识本身属于网络体系，因此在请求章节中暂时不深入内部原理。现在只需要理解：

> **HTTP Request 必须先经过网络传输，才能进入真正的服务端程序。**

生产环境通常不会让客户端直接访问某一个 Node.js 进程。

更常见的是：

```text
Internet
    ↓
Reverse Proxy
    ↓
Application Server
```

Reverse Proxy（反向代理）可以简单理解为：

> **先替后端应用接收外部请求，再决定把请求转发给哪一个真正处理业务的服务。**

例如：

```text
Client
  ↓
api.example.com
  ↓
Nginx
  ↓
10.0.0.12:3000
  ↓
Node.js API
```

NGINX 官方对反向代理的基本流程描述就是：代理接收请求，把请求发送到指定的后端服务，获取后端响应，再把响应返回给客户端。[[8]](https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/)

所以：

```text
Reverse Proxy
        ≠
Application
```

反向代理主要解决：

```text
请求应该进入哪个服务
HTTPS 在哪里终止
多个服务之间怎样分流
是否需要负载均衡
```

应用服务解决：

```text
这个请求究竟要完成什么业务
```

这是两个完全不同的职责。

### 【HTTP Server 把网络中的 HTTP 消息转换成程序能够处理的请求对象】

请求进入服务器后，首先需要一个真正监听网络端口的程序。

这就是 HTTP Server（HTTP 服务器）。

例如 Node.js：

```ts
import http from "node:http";

const server = http.createServer((req, res) => {
  res.end("hello");
});

server.listen(3000);
```

这里真正发生的是：

```text
操作系统收到网络数据
        ↓
Node.js HTTP Server
        ↓
解析 HTTP Message
        ↓
req
res
        ↓
JavaScript 代码
```

Node.js 官方文档中，`http.createServer()` 创建 HTTP Server；当请求到来时，会产生请求对象和响应对象。IncomingMessage（进入的消息对象）用于表示已经被 HTTP Parser（HTTP 解析器）处理后的请求头和请求数据。[[9]](https://nodejs.org/api/http.html)

因此 HTTP Server 的核心职责可以理解为：

```text
网络字节
    ↓
HTTP 协议解析
    ↓
程序中的 Request 对象
```

### 【HTTP Request 包含方法、目标、头部和内容】

这一层是整个请求体系非常重要的基础。

RFC 9110 对 HTTP Request 的抽象不是简单的：

```text
URL + JSON
```

而是：

```text
Request
│
├── Method
├── Target
├── Header Fields
└── Content
```

HTTP 标准明确说明，请求消息包含 Request Method（请求方法）和 Request Target（请求目标），还可以包含 Header Fields（请求头字段）和 Content（请求内容）。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html)

例如：

```http
POST /orders HTTP/1.1
Host: api.example.com
Authorization: Bearer xxx
Content-Type: application/json

{
  "productId": 1001,
  "count": 2
}
```

可以拆成：

| 内容              | 表达的意思               |
| ----------------- | ------------------------ |
| `POST`          | 我准备执行什么类型的操作 |
| `/orders`       | 我要操作哪个资源         |
| `Authorization` | 当前请求携带的身份凭据   |
| `Content-Type`  | 请求内容采用什么数据格式 |
| JSON Body         | 请求真正提交的数据       |

Method（请求方法）不是单纯的路由分类标签。

RFC 9110 明确指出，Request Method 是 Request Semantics（请求语义）的主要来源，也就是它表达客户端为什么发送这个请求。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html)

例如：

```text
GET
    获取资源

POST
    提交信息并让目标资源处理

PUT
    用新的表示替换目标资源

DELETE
    请求删除资源
```

因此：

```text
GET /users/1
```

和：

```text
DELETE /users/1
```

虽然 Target 相同，但是**请求意图不同**。

### 【应用框架在 HTTP Server 之上建立统一的请求处理管线】

如果直接使用 Node.js：

```ts
http.createServer((req, res) => {
  if (req.url === '/users' && req.method === 'GET') {
    ...
  }

  if (req.url === '/orders' && req.method === 'POST') {
    ...
  }
});
```

业务越来越复杂以后，就会出现大量重复问题：

```text
这个 URL 对应哪个函数？

用户有没有登录？

用户有没有权限？

Body 是否合法？

如何统一处理异常？

如何记录请求日志？

如何统一转换返回值？
```

Framework（应用框架）就是在 HTTP Server 之上建立一套统一处理机制。

例如：

```text
Node.js HTTP Server
        ↓
Express / Fastify
        ↓
NestJS
        ↓
Application Code
```

这里需要区分：

```text
Node.js
    → 提供运行时和底层 HTTP Server

Fastify / Express
    → 提供 HTTP 路由、中间件等 Web Server 能力

NestJS
    → 在这些能力之上进一步组织应用结构
```

所以 NestJS 不是 HTTP 协议，也不是 Node.js 本身。

它主要解决的是：

> **请求进入应用以后，代码应该怎样组织和执行。**

### 【请求进入应用后形成固定的处理管线】

NestJS 官方把这一过程称为 Request Lifecycle（请求生命周期）。

官方给出的总体顺序是：

```text
Incoming Request
      ↓
Middleware
      ↓
Guards
      ↓
Interceptors
      ↓
Pipes
      ↓
Controller
      ↓
Service
      ↓
Interceptors
      ↓
Response
```

如果出现没有被业务代码自行处理的异常，则进入 Exception Filter（异常过滤器）。NestJS 官方当前文档给出的完整请求生命周期也是这一顺序。[[10]](https://docs.nestjs.com/faq/request-lifecycle)

不过这里最重要的不是死记顺序，而是理解为什么需要这么多层：

```text
请求来了
 │
 ├── 有没有一些所有请求都要执行的逻辑？
 │       → Middleware
 │
 ├── 当前用户能不能进入这个接口？
 │       → Guard
 │
 ├── 输入的数据是否合法？
 │       → Pipe
 │
 ├── 哪段代码真正接收这个请求？
 │       → Controller
 │
 ├── 真正的业务规则在哪里？
 │       → Service
 │
 ├── 前后是否需要统一记录、转换？
 │       → Interceptor
 │
 └── 出错以后怎样统一返回？
         → Exception Filter
```

这才是理解 NestJS 请求生命周期的关键。

### 【Middleware 处理与具体业务无关的通用前置逻辑】

Middleware（中间件）可以理解为：

> **请求进入具体业务处理之前，统一执行的一层通用处理函数。**

例如：

```text
Request
  ↓
记录访问日志
  ↓
读取 Cookie
  ↓
建立 Request Context
  ↓
继续处理请求
```

NestJS 官方定义中，Middleware 会在 Route Handler（路由处理函数）之前执行，并且可以访问 Request、Response 和 `next()`；如果没有结束请求，就需要继续把控制权交给后面的处理流程。[[11]](https://docs.nestjs.com/middleware)

常见用途包括：

```text
请求日志
Request ID
解析 Cookie
通用 Header
基础身份信息解析
```

Middleware 最大的特点是：

```text
它通常关注：
“所有类似请求都要做什么”

而不是：
“这个具体业务接口允许谁访问”
```

后者更加适合 Guard。

#### <u>1. Middleware 的实现逻辑是 next() 驱动的函数链</u>

Middleware 最底层可以抽象成：

```ts
function middleware(req, res, next) {
  // 前置逻辑
  next();
}
```

它拿到三个核心对象：

```text
req
    当前请求

res
    当前响应

next
    把控制权交给下一个处理函数
```

多个 Middleware 会形成线性的函数链：

```text
Request
   ↓
Middleware A
   ↓ next()
Middleware B
   ↓ next()
Middleware C
   ↓ next()
Controller
```

框架内部可以近似理解为：

```ts
const middlewares = [A, B, C];

let index = 0;

function next() {
  const middleware = middlewares[index++];

  if (middleware) {
    middleware(req, res, next);
  } else {
    controller(req, res);
  }
}

next();
```

这就是 Middleware 最本质的实现思想：

> **每一个 Middleware 决定“我处理完以后，要不要继续交给下一个函数”。**

因为 Middleware 直接持有 Request 和 Response，所以它既可以调用 `next()` 继续执行，也可以直接通过 Response 结束当前请求。

### 【Guard 负责判断当前请求是否允许继续执行】

Guard（守卫）最直接的理解是：

> **决定当前请求有没有资格进入目标业务接口。**

例如：

```text
Request
   ↓
用户是谁？
   ↓
有没有 admin 权限？
   ↓
      ┌── 没有 → 拒绝
      │
      └── 有 → Controller
```

这里需要区分两个经常混淆的概念。

Authentication（身份认证）：

```text
你是谁？
```

Authorization（权限控制）：

```text
你能做什么？
```

例如：

```text
Access Token
    ↓
验证成功
    ↓
userId = 123

这一步主要解决身份认证
```

然后：

```text
userId = 123
roles = ["user"]

DELETE /users/10
    ↓
是否拥有 admin 权限？
```

这一步解决权限控制。

NestJS 官方指出 Guard 能够访问 Execution Context（执行上下文，即当前准备执行哪个 Controller / Handler 的信息），因此很适合根据具体路由的权限要求决定请求是否继续。[[12]](https://docs.nestjs.com/guards)

### 【Pipe 负责把外部输入转换成业务可以信任的数据】

客户端传来的任何内容，本质上都属于 External Input（外部输入），不能直接认为它一定正确。

例如：

```json
{
  "age": "-abc",
  "email": 123,
  "count": -100
}
```

因此在真正进入业务逻辑之前通常需要：

```text
Input
  ↓
解析
  ↓
转换
  ↓
校验
  ↓
可信的业务参数
```

Pipe（管道）在 NestJS 中主要承担两类职责：

```text
Transformation
数据转换

Validation
数据校验
```

NestJS 官方同样把 Transformation（转换）和 Validation（校验）作为 Pipe 的两个主要使用场景。[[13]](https://docs.nestjs.com/pipes)

例如：

```text
"id": "123"
     ↓
ParseIntPipe
     ↓
123
```

或者：

```text
CreateUserDto
       ↓
ValidationPipe
       ↓
email 合法？
age 合法？
字段是否允许？
       ↓
Controller
```

因此：

> **Pipe 的意义不是为了框架结构更复杂，而是建立外部数据与可信业务输入之间的边界。**

### 【Controller 负责把 HTTP 请求映射到应用行为】

经过前面的统一处理以后，请求才真正进入 Controller（控制器）。

NestJS 官方对 Controller 的定义非常直接：

> Controller 负责处理进入应用的请求，并把响应返回给客户端。[[4]](https://docs.nestjs.com/controllers)

例如：

```ts
@Post('/orders')
createOrder(@Body() dto: CreateOrderDto) {
  return this.orderService.create(dto);
}
```

Controller 主要解决：

```text
什么 Method？
什么 Path？
输入从哪里拿？
调用哪个业务能力？
HTTP 返回什么？
```

因此：

```text
POST /orders
      ↓
OrderController.createOrder()
```

Controller 可以理解为：

> **HTTP 世界和业务世界之间的入口。**

所以 Controller 通常不应该承担大量业务计算。

### 【Service 负责真正的业务规则】

假设 Controller 收到：

```text
POST /orders
```

真正的问题其实不是：

```text
怎样读取 @Body？
```

而是：

```text
这个商品存在吗？

库存够吗？

用户允许购买吗？

优惠规则是什么？

订单价格怎样计算？

订单应该以什么状态创建？
```

这些才是业务逻辑。

因此常见结构变成：

```text
Controller
    ↓
Service
    ↓
Business Logic
```

NestJS 官方也建议 Controller 处理 HTTP 请求，把更复杂的任务委托给 Provider（提供能力的对象）；Service 是最常见的 Provider 类型之一。[[14]](https://docs.nestjs.com/providers)

例如：

```ts
class OrderService {
  async createOrder(userId, dto) {
    const product = await productRepository.find(dto.productId);

    checkStock(product, dto.count);

    const total = calculatePrice(product, dto.count);

    return orderRepository.create({
      userId,
      total,
    });
  }
}
```

所以：

```text
Controller
    → 处理通信问题

Service
    → 处理业务问题
```

这是非常重要的一条分界。

### 【API 分层把通信、业务和数据访问职责拆开】

API 分层本质上不是“为了多写几层代码”，而是把一次接口调用中不同类型的职责拆开。

最常见的结构是：

```text
Client
  ↓
Controller / API Layer
  ↓
Service / Business Layer
  ↓
Repository / Data Access Layer
  ↓
Database
```

每一层解决的问题不同：

| 层                      | 主要职责                                               | 不应该主要负责     |
| ----------------------- | ------------------------------------------------------ | ------------------ |
| Controller / API 层     | 接收 HTTP 请求、读取参数、调用业务能力、返回 HTTP 响应 | 大量业务规则       |
| Service / 业务层        | 执行业务规则、组织一次完整业务操作                     | 关心具体 HTTP 细节 |
| Repository / 数据访问层 | 查询和保存数据                                         | 决定业务规则       |
| Database                | 真正持久化数据                                         | 应用业务流程       |

例如“创建订单”。

如果不做职责分层，Controller 可能同时完成：

```text
接收请求
+
参数处理
+
查询数据库
+
检查库存
+
计算价格
+
创建订单
+
组织 Response
```

代码可能变成：

```ts
@Post('/orders')
async createOrder(@Body() body) {
  const product = await db.query(...);

  if (product.stock < body.count) {
    throw new Error('库存不足');
  }

  const total = product.price * body.count;

  const order = await db.query(...);

  return {
    code: 0,
    data: order,
  };
}
```

这类写法的问题不是“Controller 代码行数太多”，而是**通信、业务规则和数据访问职责混在了一起**。

分层之后，Controller 只负责把 HTTP 请求转换成应用调用：

```ts
@Post('/orders')
createOrder(@Body() dto: CreateOrderDto) {
  return this.orderService.create(dto);
}
```

它主要处理：

```text
什么 Method？
什么 Path？
参数从哪里来？
应该调用哪个业务能力？
返回什么 HTTP 状态和结果？
```

Service 负责业务规则：

```ts
async create(dto: CreateOrderDto) {
  const product = await this.productRepository.findById(dto.productId);

  if (product.stock < dto.count) {
    throw new InsufficientStockError();
  }

  const total = product.price * dto.count;

  return this.orderRepository.create({
    productId: dto.productId,
    count: dto.count,
    total,
  });
}
```

它主要解决：

```text
商品是否存在？
库存是否足够？
价格怎样计算？
订单以什么状态创建？
```

Repository（仓储 / 数据访问层）负责具体的数据访问：

```ts
findById(id) {
  return this.db.product.findUnique({
    where: { id },
  });
}
```

它解决的是：

```text
业务需要什么数据
        ↓
具体怎样从数据库中读取或写入
```

因此可以把三层关系压缩成：

```text
Controller
    → 处理通信问题

Service
    → 处理业务问题

Repository
    → 处理数据访问问题
```

这就是请求体系中最常见的 API 职责分层。

这样的分层还有一个重要价值：业务规则不会过度依赖某一种通信方式。

例如同一个创建订单能力，未来可能来自：

```text
HTTP Controller ─┐
GraphQL Resolver ├──→ OrderService
Message Consumer ┘
```

HTTP、GraphQL 或消息队列只是不同的入口，真正的创建订单规则仍然可以复用 OrderService。

因此：

> **API 分层的核心，是把“怎么接收请求”“业务应该怎么做”“数据怎么存取”拆开。**

这里还需要区分另一个经常也被称为“API 分层”的概念。

有时工程中说 API 分层，指的是 API 对外边界或路径组织，例如：

```text
/api/v1/users
/api/v1/orders
/api/admin/users
/api/internal/tasks
```

或者：

```text
Public API
Internal API
Admin API
Partner API
```

以及：

```text
/api/v1
/api/v2
```

这些属于**接口边界、用途或版本的划分**，和：

```text
Controller
   ↓
Service
   ↓
Repository
```

这种**代码职责分层**不是同一个概念。

在当前“服务端请求处理体系”的上下文中，API 分层主要指后者：

```text
HTTP 世界
    ↓
Controller / API Layer
    ↓
业务世界
    ↓
Service
    ↓
数据访问
    ↓
Repository
    ↓
Database
```

理解这一层以后，就能更清楚地判断请求体系中的每一段代码应该放在哪里，而不是单纯按照文件夹名称组织代码。

### 【Service 继续访问数据系统和外部服务】

业务逻辑通常无法凭空完成。

它可能需要：

```text
Database
Cache
Object Storage
Payment Service
User Service
AI Service
Third-party API
```

因此请求继续向系统内部传播：

```text
Controller
    ↓
Service
    ↓
Repository / Data Access
    ↓
Database
```

或者：

```text
Service
   ↓
HTTP Client
   ↓
External Service
```

Repository（仓储 / 数据访问层）可以简单理解为：

> **把“业务需要什么数据”和“具体如何访问数据库”分开。**

例如：

```ts
orderRepository.findById(id);
```

业务 Service 不一定需要知道内部执行的是：

```sql
SELECT ...
FROM orders ...
```

需要注意，Repository 并不是 HTTP 或 NestJS 强制规定的层，它是一种常见工程组织方式。

至此，请求体系已经开始与第二个体系发生交叉：

```text
请求处理体系
      ↓
Service
      ↓
状态与数据体系
```

所以几个体系并不是完全隔离的，而是在真实执行链路中互相连接。

### 【异步任务也可能从一次请求中产生】

有些请求处理到一半会发现：

```text
核心业务已经完成
但是还有后续工作
```

例如创建订单：

```text
创建订单
   ↓
数据库写入成功
   ↓
订单创建已经可以返回
```

但是还需要：

```text
发送邮件
发送通知
数据统计
生成报表
```

这时请求可能变成：

```text
Service
   │
   ├── Database
   │
   └── Create Task
           ↓
         Queue

随后

HTTP Response
```

后台：

```text
Queue
  ↓
Worker
  ↓
继续处理
```

于是请求体系又和异步处理体系发生连接：

```text
请求处理体系
      ↓
Task
      ↓
异步处理体系
```

但两者需要区分：

> **请求体系负责决定当前请求什么时候可以完成；异步体系负责当前请求结束以后剩余工作怎样继续执行。**

### 【Interceptor 包裹业务执行的前后过程】

Interceptor（拦截器）和 Middleware 很容易混淆。

一个最直观的区别是：

```text
Middleware

Request
  ↓
执行
  ↓
继续向后
```

而 Interceptor 更像：

```text
          Interceptor
          ↓         ↑
Request → Controller → Result
          ↓         ↑
          Service
```

也就是说它可以同时观察调用之前和调用之后。

NestJS 官方说明 Interceptor 可以在函数执行前后增加逻辑、转换函数返回结果、转换异常、扩展函数行为，并在某些场景下完全替代函数执行结果。[[15]](https://docs.nestjs.com/interceptors)

因此它常用于：

```text
统一日志
请求耗时
响应结构转换
缓存
Trace
```

#### <u>1. Interceptor 的实现逻辑是对后续执行进行包裹</u>

Interceptor 的典型结构是：

```ts
intercept(context: ExecutionContext, next: CallHandler) {
  console.log('before');

  return next.handle().pipe(
    tap(() => {
      console.log('after');
    }),
  );
}
```

核心在于：

```ts
next.handle();
```

它表示继续执行后续 Interceptor，最终进入 Controller，并返回一条结果流。

因此 Interceptor 更像：

```text
Interceptor
      │
      │ before
      ↓
Controller / Service
      │
      │ result
      ↑
Interceptor
      │
      │ after
      ↑
Response
```

多个 Interceptor 会形成 Onion Model（洋葱模型），也就是外层先进入、返回时内层先退出：

```text
A before
  ↓
B before
  ↓
C before
  ↓
Controller
  ↓
C after
  ↓
B after
  ↓
A after
```

NestJS 官方 Request Lifecycle 也明确指出，Interceptor 入站时按 global → controller → route 执行，而返回时按 route → controller → global 反向解析。[[10]](https://docs.nestjs.com/faq/request-lifecycle)

框架内部可以近似理解为递归构造包装链：

```ts
async function nextFn(i = 0) {
  if (i >= interceptors.length) {
    return controller();
  }

  const handler = {
    handle: () => nextFn(i + 1),
  };

  return interceptors[i].intercept(context, handler);
}
```

真实 NestJS 实现会进一步借助 RxJS Observable（可观察数据流）统一处理同步值、Promise 和 Observable，但核心思想就是：**当前 Interceptor 包住后续整个执行过程。**

因此 Middleware 和 Interceptor 的根本差异可以收敛为：

> **Middleware 是基于 `next()` 的请求处理函数链，重点是“把请求继续交给谁”；Interceptor 是基于 `next.handle()` 的执行包装链，重点是“包住后续业务执行，并观察或改变它的结果”。**

### 【Exception Filter 把程序异常重新转换成 HTTP 响应】

请求执行过程中任何地方都有可能失败：

```text
参数错误
权限错误
数据库错误
外部接口错误
业务规则错误
程序异常
```

如果没有统一处理，很容易出现：

```text
不同接口
返回不同错误格式
```

因此需要统一异常处理：

```text
Exception
    ↓
Exception Filter
    ↓
HTTP Status
+
Error Response
```

Exception Filter（异常过滤器）可以理解为：

> **把应用内部出现的异常转换成客户端能够理解的 HTTP 错误响应。**

NestJS 自带异常处理层；没有被应用代码处理的异常会进入异常处理机制。如果无法识别异常，默认会生成 HTTP 500 响应。[[16]](https://docs.nestjs.com/exception-filters)

例如：

```text
throw UserNotFound
      ↓
Exception Mapping
      ↓
404 Not Found

{
  "code": "USER_NOT_FOUND",
  "message": "User does not exist"
}
```

因此要区分：

```text
Exception
    → 程序内部发生了什么

HTTP Status
    → 对客户端表达处理结果
```

### 【Response 把业务结果重新转换成 HTTP 消息】

最终：

```ts
return order;
```

并不意味着网络中直接传输一个 JavaScript Object。

它还需要经历：

```text
JavaScript Object
      ↓
Serialization
      ↓
JSON
      ↓
Response Headers
      ↓
HTTP Status
      ↓
HTTP Response
```

Serialization（序列化）可以简单理解为：

> **把程序内部的数据结构转换成可以通过网络发送的数据格式。**

最终可能形成：

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 1001,
  "status": "created"
}
```

RFC 9110 定义 Response（响应）至少包含 Status Code（状态码），并且还可以携带 Header Fields 和 Content。[[1]](https://www.rfc-editor.org/rfc/rfc9110.html)

于是完整链路终于闭合：

```text
HTTP Request
    ↓
Application
    ↓
Business Logic
    ↓
Result
    ↓
HTTP Response
```

### 【CORS 属于请求入口的浏览器安全控制分支】

前端开发中经常遇到：

```text
Browser
    ↓
跨域 Request
    ↓
Server
```

CORS（Cross-Origin Resource Sharing，跨源资源共享）不是 Controller 或 Service 的业务规则。

它解决的是：

> **浏览器是否允许网页读取来自另一个 Origin（源）的响应。**

MDN 对 CORS 的定义是：一种基于 HTTP Header 的机制，服务器通过响应头告诉浏览器哪些其他来源可以访问资源。对于部分跨源请求，浏览器还会自动先发送 Preflight Request（预检请求）。[[17]](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

例如：

```text
Browser

先发送：

OPTIONS /orders
        ↓
CORS Check
        ↓
Server允许？

        ↓ Yes

再发送：

POST /orders
```

所以某些情况下真实链路不是：

```text
POST
 ↓
Controller
```

而是：

```text
OPTIONS
   ↓
CORS
   ↓
Response

然后

POST
   ↓
正常请求体系
```

这就是为什么 CORS 也属于理解完整请求链路时必须知道的一个分支。

### 【安全、稳定性和可观测性横穿整条请求链路】

到目前为止，我们画的是纵向链路：

```text
Request
  ↓
Middleware
  ↓
Guard
  ↓
Pipe
  ↓
Controller
  ↓
Service
  ↓
Database
  ↓
Response
```

但实际系统还存在大量横向能力。

例如：

```text
               Request
                  │
                  ↓
┌──────────────────────────────────┐
│ Authentication / Authorization  │
│ Validation                       │
│ Rate Limit                       │
│ Timeout                          │
│ Request ID                       │
│ Logging                          │
│ Trace                            │
└──────────────────────────────────┘
                  │
                  ↓
              Response
```

Context（上下文）可以理解为：

> **处理当前这一次请求时，各层都需要知道的公共信息。**

例如：

```text
requestId
userId
traceId
locale
clientIp
startTime
```

于是：

```text
Request
   ↓
requestId = abc123
   ↓
Controller
   ↓
Service
   ↓
Database
   ↓
Log

所有记录都带 abc123
```

就可以把一次请求产生的日志关联起来。

Trace（链路追踪）用于描述：

```text
一次请求
经过了哪些服务
每一步耗时多久
哪里发生错误
```

OpenTelemetry 的 HTTP Semantic Conventions（HTTP 语义约定）把一个进入服务端的 HTTP 请求表示为 HTTP Server Span，并记录 Method、Route、Server、Client 等信息。[[18]](https://opentelemetry.io/docs/specs/semconv/http/http-spans/)

例如：

```text
POST /orders              120ms
│
├── Auth                  5ms
│
├── OrderService         90ms
│    │
│    ├── PostgreSQL      40ms
│    │
│    └── Payment API     35ms
│
└── Serialize             3ms
```

所以可观测性不是请求结束以后再做的事情，而是贯穿 Request → Response 整个生命周期。

### 【请求体系还存在多种特殊分支】

到这里建立的是最常见的 API 请求：

```text
Request
  ↓
Business Logic
  ↓
Response
```

真实系统还会出现一些特殊路径：

```text
普通 API
    Request → Controller → Service → JSON Response

静态文件
    Request → Static File → Response

重定向
    Request → 3xx Response → Client访问新地址

CORS Preflight
    OPTIONS → CORS Check → Response

文件上传
    Request Stream → File Storage / Business Logic

流式响应
    Request → Server持续写 Response Stream

WebSocket
    HTTP Upgrade → WebSocket Connection
```

这些并不是另一套完全独立的系统。

它们都是：

> **请求进入服务端后，根据不同通信需求产生的分支。**

第一阶段不需要深入这些分支，只需要知道它们在请求体系中的位置。

### 【NestJS 只是完整请求体系中的应用处理阶段】

现在重新看最开始经常看到的：

```text
Middleware
    ↓
Guard
    ↓
Interceptor
    ↓
Pipe
    ↓
Controller
    ↓
Service
```

它的位置其实是：

```text
Client
  ↓
Network
  ↓
Reverse Proxy
  ↓
HTTP Server
  ↓
┌───────────────────────────────────────┐
│           Application Framework       │
│                                       │
│ Middleware                            │
│    ↓                                  │
│ Guard                                 │
│    ↓                                  │
│ Interceptor                           │
│    ↓                                  │
│ Pipe                                  │
│    ↓                                  │
│ Controller                            │
│    ↓                                  │
│ Service                               │
└───────────────────┬───────────────────┘
                    ↓
          Database / Cache
          External Services
                    ↓
                  Result
                    ↑
┌───────────────────┴───────────────────┐
│ Interceptor / Exception / Serialize  │
└───────────────────┬───────────────────┘
                    ↑
              HTTP Response
                    ↑
             Reverse Proxy
                    ↑
                  Client
```

所以以后不要把 NestJS Request Lifecycle 直接等同于完整服务端请求生命周期。

更准确的关系是：

```text
完整请求体系
│
├── 网络接入
├── HTTP Server
│
├── Application Request Lifecycle
│      ├── Middleware
│      ├── Guard
│      ├── Interceptor
│      ├── Pipe
│      ├── Controller
│      └── Service
│
├── 数据 / 外部依赖
│
├── 响应与异常处理
│
└── 日志 / Trace / 安全 / 超时等横向能力
```

### 【请求体系最终收敛为六个核心问题】

第一阶段不需要把 NestJS 每一个装饰器、HTTP/2 Frame、TLS 握手、反向代理配置全部学完。

真正需要先建立的是下面这张知识地图：

```text
                    Request System
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
  ① 请求怎么到达应用  ② 请求表达什么    ③ 谁负责统一处理
        │                 │                 │
 Network / Proxy       HTTP Message      Framework Pipeline
                                            │
                                            ↓
                            Middleware / Guard / Pipe
                                            │
                                            ↓
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
  ④ 谁执行业务逻辑   ⑤ 数据从哪里来    ⑥ 结果怎样返回
        │                 │                 │
 Controller/Service  DB/Cache/External   Response/Error
```

因此，请求体系真正需要回答六个问题：

1. **请求怎样到达这个程序？**
2. **HTTP Request 到底携带了什么？**
3. **应用怎样判断这个请求应该交给谁？**
4. **身份、权限、输入校验和通用逻辑在哪里完成？**
5. **真正的业务规则和数据访问在哪里完成？**
6. **结果或异常最后怎样重新变成 HTTP Response？**

只要这六个问题能够连起来，就已经建立了完整的**请求处理体系框架**。

下一步再深入时，不应该直接进入 NestJS API，而应该从其中最底层的一层继续：

```text
Request
   ↓
HTTP Server
```

也就是先把“HTTP Request 到达 Node.js 后，Node.js 到底怎样接收、解析并产生 req / res”这一层讲透，然后再向上进入 Framework 和 NestJS Request Lifecycle。这样后面的 Middleware、Guard、Pipe、Controller 才不会只是需要背诵的框架名词。



## 3. Web Server、Fastify 与 NestJS 将 HTTP 通信逐层组织成可维护的应用请求体系

第二部分已经从完整链路说明了一个请求如何经过网络入口、HTTP Server、Application Framework，再进入 Controller、Service 和数据系统。第三部分继续把其中最核心的应用处理阶段展开：

```text
Client
  ↓
Reverse Proxy
  ↓
Node.js HTTP Server
  ↓
Fastify
  ↓
NestJS
  ↓
Controller
  ↓
Service
  ↓
Database / Cache / External Service
```

这里需要先建立三个层次：

| 层次 | 主要职责 | 典型技术 |
|---|---|---|
| HTTP Server | 监听端口、接收 HTTP Request、构造 HTTP Response | `node:http` |
| Web Framework | 路由、请求解析、生命周期、校验、序列化 | Fastify / Express |
| Application Framework | 模块、Controller、Service、依赖注入、权限与应用级生命周期 | NestJS |

因此三者不是三个并列的后端框架：

> **HTTP Server 负责“接住 HTTP 请求”，Fastify 负责“把 HTTP 请求处理过程组织起来”，NestJS 继续负责“把复杂应用中的模块、业务对象和请求处理职责组织起来”。**

### 【Node.js HTTP Server 提供最基础的 HTTP 通信能力】

Node.js 的 `node:http` 模块已经可以创建一个完整可运行的 HTTP Server。Node.js 官方提供 `http.createServer()` 创建 HTTP Server，并在收到请求时触发 `request` 事件。[[19]](https://nodejs.org/api/http.html)

最小示例：

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'application/json');

  res.end(
    JSON.stringify({
      message: 'hello',
    }),
  );
});

server.listen(3000);
```

对应链路是：

```text
创建 Node Process
    ↓
http.createServer()
    ↓
创建 HTTP Server
    ↓
server.listen(3000)
    ↓
监听 3000 端口
    ↓
Request 到达
    ↓
触发 request 事件
    ↓
requestListener(req, res)
    ↓
res.end()
    ↓
HTTP Response
```

#### <u>1. createServer 的两个参数分别表示 Server 配置和请求处理函数</u>

`createServer` 的基础签名可以理解为：

```js
http.createServer(options?, requestListener?)
```

其中：

```text
options
    ↓
HTTP Server 本身的配置

requestListener
    ↓
每次收到 HTTP Request 时执行的处理函数
```

最常见的是只传请求处理函数：

```js
const server = http.createServer((req, res) => {
  res.end('hello');
});
```

这里的函数会被注册为 Server 的 `request` 事件监听器，因此下面两种写法在基础语义上可以这样理解：

```js
const server = http.createServer(handler);
```

约等于：

```js
const server = http.createServer();

server.on('request', handler);
```

如果写：

```js
const server = http.createServer();
```

并不是“创建失败”或者“Server 为空”，而只是**创建 Server 时暂时没有注册 requestListener**。后续仍然可以：

```js
server.on('request', (req, res) => {
  res.end('hello');
});
```

因此：

```text
createServer()
    创建 HTTP Server

createServer(handler)
    创建 HTTP Server
    +
    同时注册 request handler
```

#### <u>2. requestListener 是事件回调，但默认不是 async 函数</u>

例如：

```js
http.createServer((req, res) => {
  res.end('hello');
});
```

这里的：

```js
(req, res) => {}
```

仍然是普通 JavaScript 函数。

需要区分两个概念：

```text
网络请求在未来某个时间到达
    ↓
这是异步事件

requestListener 被事件触发执行
    ↓
这个函数本身可以是普通函数
也可以显式声明为 async
```

也就是说：

```text
“异步触发”
≠
“async function”
```

如果确实需要等待异步操作，可以写：

```js
http.createServer(async (req, res) => {
  const user = await getUser();

  res.end(JSON.stringify(user));
});
```

但 `node:http` 不会把函数的 `return` 值自动转换成 HTTP Response。例如：

```js
http.createServer(async () => {
  return {
    name: 'Tom',
  };
});
```

这里返回的是 Promise，但客户端不会自动收到 JSON。原生 HTTP Server 的响应仍然需要通过：

```js
res.write();
res.end();
```

明确写入 Response。

#### <u>3. req 表示进入服务器的 HTTP Request，res 表示当前 HTTP Response</u>

请求回调：

```js
(req, res) => {}
```

中的两个对象分别是：

```text
req
 ↓
http.IncomingMessage
 ↓
读取进入服务器的请求信息

res
 ↓
http.ServerResponse
 ↓
构造服务器准备返回的响应
```

常见读取方式：

```js
req.method;
req.url;
req.headers;
```

例如：

```http
GET /users?page=1 HTTP/1.1
Host: localhost:3000
```

程序中可以得到：

```js
req.method;
// GET

req.url;
// /users?page=1
```

Response 常见 API：

```js
res.statusCode = 200;

res.setHeader(
  'Content-Type',
  'application/json',
);

res.write('...');
res.end('...');
```

其中 `res.end()` 表示当前 Response 已经完成。

#### <u>4. listen 监听的是网络端口，不是业务路由</u>

```js
server.listen(3000);
```

表示：

```text
HTTP Server
    ↓
绑定网络端口 3000
    ↓
等待进入该端口的连接和 Request
```

因此：

```text
GET /users
POST /users
DELETE /users/1
```

都可以进入同一个 HTTP Server。

`listen()` 解决的是：

```text
“从哪里接收网络请求？”
```

而路由解决的是：

```text
“这个请求应该交给哪一段处理代码？”
```

二者不是同一个概念。

#### <u>5. node:http 没有完整 Router，需要自己根据 Method 和 URL 判断</u>

例如：

```js
const server = http.createServer((req, res) => {
  if (
    req.method === 'GET' &&
    req.url === '/users'
  ) {
    res.end('user list');
    return;
  }

  if (
    req.method === 'POST' &&
    req.url === '/users'
  ) {
    res.end('create user');
    return;
  }

  res.statusCode = 404;
  res.end('Not Found');
});
```

这已经构成最基础的 Routing：

```text
Request
   ↓
Method + URL
   ↓
条件匹配
   ↓
对应 Handler
```

如果 URL 包含 Query String：

```http
GET /users?page=1
```

此时：

```js
req.url === '/users'
// false
```

可以先通过 WHATWG URL API 解析：

```js
const url = new URL(
  req.url,
  `http://\${req.headers.host}`,
);

url.pathname;
// /users

url.searchParams.get('page');
// 1
```

#### <u>6. Request Body 在原生 HTTP 中是数据流，需要自己读取</u>

原生 `node:http` 不会自动产生：

```js
req.body
```

因为 Body 是通过 Stream（流，即连续到达的数据）读取的：

```js
let body = '';

req.on('data', chunk => {
  body += chunk;
});

req.on('end', () => {
  const data = JSON.parse(body);

  res.end(
    JSON.stringify(data),
  );
});
```

所以原生 HTTP Server 的基本开发模型最终是：

```text
http.createServer()
        ↓
server.listen()
        ↓
request event
        ↓
req.method + req.url
        ↓
自己进行 Route Matching
        ↓
自己解析 Query / Body
        ↓
执行业务逻辑
        ↓
自己设置 Status / Header
        ↓
res.end()
```

随着路由、Body、参数校验、异常处理、日志和生命周期逻辑不断增加，直接使用 `node:http` 的工程成本会快速上升，因此通常会继续使用 Web Framework。

### 【Fastify 在 HTTP Server 之上建立完整的 Web Request Processing】

Fastify 官方将自己定位为面向 Node.js 的低开销 Web Framework。它并没有替代 Node.js HTTP Server，而是在 HTTP Server 之上建立 Route、Request / Reply、Lifecycle、Hook、Schema、Plugin 等能力。[[20]](https://fastify.dev/docs/latest/)

整体结构可以先理解为：

```text
Node.js Runtime
      ↓
Node.js HTTP Server
      ↓
Fastify
      │
      ├── Route
      ├── Request / Reply
      ├── Lifecycle
      ├── Hook
      ├── Schema
      ├── Validation
      ├── Serialization
      └── Plugin / Encapsulation
      ↓
Route Handler
```

#### <u>1. Fastify() 是 Factory Function，用来创建 Fastify Instance</u>

基础写法：

```js
import Fastify from 'fastify';

const fastify = Fastify();
```

Fastify 官方把这个入口称为 Factory Function（工厂函数），也就是通过函数创建一个新的 Fastify Server Instance，而不是要求使用：

```js
new Fastify();
```

[[21]](https://fastify.dev/docs/latest/Reference/Server/)

可以把：

```js
Fastify(options)
```

理解成：

```text
读取 Options
    ↓
创建 Fastify Instance
    ↓
准备底层 HTTP Server
    ↓
准备 Router
    ↓
准备 Lifecycle / Hook
    ↓
准备 Schema Compiler
    ↓
准备 Plugin System
    ↓
返回 Fastify Instance
```

空参数：

```js
const fastify = Fastify();
```

表示使用默认配置创建实例。

传入参数：

```js
const fastify = Fastify({
  logger: true,
  bodyLimit: 1024 * 1024,
  requestTimeout: 30_000,
});
```

表示在创建实例时设置 Server 的全局行为。

创建完成以后，实例提供：

```js
fastify.get();
fastify.post();
fastify.route();

fastify.addHook();

fastify.register();

fastify.addSchema();

fastify.setErrorHandler();

fastify.listen();
fastify.close();
```

等能力。

#### <u>2. Fastify Route 根据 Method + Path 匹配请求</u>

```js
fastify.get('/users', handler);
```

只表示注册：

```text
Method = GET
Path   = /users
Handler = handler
```

并不表示所有 Fastify Request 都是 GET。

Fastify提供：

```js
fastify.get();
fastify.post();
fastify.put();
fastify.patch();
fastify.delete();
fastify.head();
fastify.options();
```

也可以使用统一形式：

```js
fastify.route({
  method: 'POST',
  url: '/users',
  handler: async (request, reply) => {
    // ...
  },
});
```

因此：

```js
fastify.get('/users', handler);
```

可以理解为：

```js
fastify.route({
  method: 'GET',
  url: '/users',
  handler,
});
```

Fastify 的 Router 实际匹配：

```text
HTTP Method
     +
Request Path
     ↓
Route Matching
     ↓
Route Handler
```

例如：

```js
fastify.get('/users', getUsers);
fastify.post('/users', createUser);
```

那么：

```text
GET /users
   ↓
getUsers

POST /users
   ↓
createUser
```

Route 官方参考说明 Fastify Route 以 Method、URL 和 Handler 为核心定义。[[22]](https://fastify.dev/docs/latest/Reference/Routes/)

#### <u>3. Fastify Request / Reply 对 node:http 的 req / res 进一步封装</u>

Handler：

```js
async function handler(request, reply) {
  // ...
}
```

拿到的是：

```text
request
    Fastify Request

reply
    Fastify Reply
```

常见 Request 数据：

```js
request.method;
request.url;

request.params;
request.query;
request.body;
request.headers;

request.ip;
request.log;
```

例如：

```http
POST /users/100?page=2

{
  "name": "Tom"
}
```

Route：

```js
fastify.post(
  '/users/:id',
  async request => {
    console.log(request.params.id);
    // 100

    console.log(request.query.page);
    // 2

    console.log(request.body.name);
    // Tom
  },
);
```

相比原生 `node:http`：

```text
node:http

req.url
+
自己解析 path
+
自己解析 query
+
自己读取 body stream
```

Fastify提供：

```text
request.params
request.query
request.body
```

这就是 Web Framework 对 HTTP Request 的进一步抽象。[[23]](https://fastify.dev/docs/latest/Reference/Request/)

#### <u>4. Fastify Handler 可以是同步函数，也可以是 async / Promise Handler</u>

Fastify并不是要求所有 Handler 都写 `async`。

同步形式：

```js
fastify.get('/hello', (request, reply) => {
  reply.send({
    hello: 'world',
  });
});
```

异步形式：

```js
fastify.get('/users', async request => {
  const users = await getUsers();

  return users;
});
```

区别在于 Fastify 能理解 Handler 返回的 Promise。

```text
async Handler
    ↓
返回 Promise
    ↓
Fastify 等待 Promise
    ↓
Promise resolve
    ↓
得到返回值
    ↓
进入 Reply / Serialization
```

所以这里存在三个不同层次：

```text
① Request 在未来到达
   → Node Event Loop / 网络事件层

② async / await
   → JavaScript Promise 层

③ Fastify 等待 Promise 并处理返回值
   → Framework 层
```

原生 `node:http` 即使 Handler 写成 `async`，仍然不会自动把 `return` 的对象转换成 Response；Fastify则把 Promise 的完成状态和返回值纳入自己的请求生命周期。

#### <u>5. Request Lifecycle 把一次请求拆成固定处理阶段</u>

Fastify 的核心不只是 Router，还包括完整 Request Lifecycle（请求生命周期）。官方生命周期主要包含 Routing、Parsing、Validation、Handler、Serialization 以及多个 Hook。[[24]](https://fastify.dev/docs/latest/Reference/Lifecycle/)

入门阶段可以整理成：

```text
Incoming Request
       ↓
Route Matching
       ↓
onRequest
       ↓
preParsing
       ↓
Body Parsing
       ↓
preValidation
       ↓
Validation
       ↓
preHandler
       ↓
Handler
       ↓
preSerialization
       ↓
Serialization
       ↓
onSend
       ↓
HTTP Response
       ↓
onResponse
```

进一步压缩就是：

```text
收到请求
  ↓
找到 Route
  ↓
解析 Request
  ↓
校验输入
  ↓
执行前置逻辑
  ↓
Handler
  ↓
整理输出
  ↓
发送 Response
```

因此 Fastify 本质上建立的是一条**可扩展、可插入逻辑的 HTTP 请求处理管线**。

#### <u>6. Hook 是 Request Lifecycle 中的固定扩展点</u>

Hook（钩子）指：

> **在 Request / Reply Lifecycle 的某个固定阶段插入自己的处理逻辑。**

例如记录请求：

```js
fastify.addHook(
  'onRequest',
  async request => {
    request.log.info({
      method: request.method,
      url: request.url,
    });
  },
);
```

身份判断：

```js
fastify.addHook(
  'preHandler',
  async (request, reply) => {
    if (!request.headers.authorization) {
      return reply
        .code(401)
        .send({
          message: 'Unauthorized',
        });
    }
  },
);
```

可以理解为：

```text
Request
  ↓
onRequest
  ↓
Parsing
  ↓
preValidation
  ↓
Validation
  ↓
preHandler
  ↓
Handler
  ↓
preSerialization
  ↓
Serialization
  ↓
onSend
```

不同 Hook 能访问的数据不同。例如 `onRequest` 执行得很早，此时 Body 还没有完成 Parsing，因此需要根据生命周期位置选择 Hook。

Fastify Hooks 还受到 Plugin Encapsulation（插件封装作用域）影响，因此既可以定义全局 Hook，也可以只作用于某个 Plugin 内部的 Routes。[[25]](https://fastify.dev/docs/latest/Reference/Hooks/)

#### <u>7. Hook 与 Express Middleware 相似，但不是同一个机制</u>

Express 的核心模型可以概括为：

```text
Request
  ↓
Middleware 1
  ↓ next()
Middleware 2
  ↓ next()
Route Handler
```

而 Fastify 的原生模型是：

```text
Request Lifecycle
      │
      ├── onRequest
      ├── preParsing
      ├── preValidation
      ├── preHandler
      ├── Handler
      ├── preSerialization
      └── onSend
```

因此：

```text
Express
    Middleware Chain

Fastify
    Lifecycle + Hook
```

Hook 能完成大量传统 Middleware 的工作，例如：

```text
日志
认证
请求上下文
耗时记录
Response 修改
```

但 Hook 不是通过 `next()` 串起任意函数链，而是挂载到 Fastify 预定义的生命周期位置。

如果确实需要 Express / Connect 风格 Middleware，Fastify可以通过 `@fastify/middie` 或 `@fastify/express` 等方式接入。Fastify官方因此把 Middleware 与 Hooks 分开说明。[[26]](https://fastify.dev/docs/latest/Reference/Middleware/)

#### <u>8. Schema 同时描述 Request 输入和 Response 输出</u>

Fastify 推荐使用 JSON Schema 描述 Route Contract（接口契约）。[[27]](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

例如：

```js
fastify.post('/users/:id', {
  schema: {
    params: {
      type: 'object',
      required: ['id'],
      properties: {
        id: {
          type: 'integer',
        },
      },
    },

    body: {
      type: 'object',
      required: ['name'],
      properties: {
        name: {
          type: 'string',
        },
        age: {
          type: 'integer',
        },
      },
    },

    response: {
      200: {
        type: 'object',
        properties: {
          id: {
            type: 'integer',
          },
          name: {
            type: 'string',
          },
        },
      },
    },
  },
}, handler);
```

这里的 Schema 分成两个方向：

```text
Request Schema
      ↓
Validation

Response Schema
      ↓
Serialization
```

因此 Schema 不只是“参数校验配置”，而是在说明：

```text
这个 Route 接受什么输入
+
这个 Route 输出什么结构
```

#### <u>9. Validation 在 Handler 之前校验 Request，并可能执行数据转换</u>

Fastify默认使用 Ajv 完成 Request Validation。

可以校验：

```text
params
querystring
headers
body
```

例如：

```js
body: {
  type: 'object',

  required: ['name'],

  properties: {
    name: {
      type: 'string',
    },

    age: {
      type: 'integer',
    },
  },
}
```

如果请求：

```json
{
  "age": 20
}
```

因为缺少 `name`：

```text
Request
   ↓
Parsing
   ↓
Validation
   ↓
Failed
   ↓
不会进入 Handler
   ↓
400 Bad Request
```

因此 Validation Failure 发生在业务 Handler 之前。

Fastify默认 Ajv 配置还允许一定的数据处理，例如：

```text
Type Coercion
    根据 Schema 尝试转换类型

Default Value
    根据 Schema 补默认值

Remove Additional
    在相应 Schema 设置下处理额外字段
```

例如 Query：

```text
?page=1
```

网络输入通常首先表现为字符串：

```js
"1"
```

如果 Schema 声明：

```js
{
  type: 'integer',
}
```

Ajv 可以根据配置转换为：

```js
1
```

因此 Fastify 的 Validation 不能简单理解为：

```text
只判断 true / false
```

更准确的链路是：

```text
Raw Input
   ↓
Parsing
   ↓
Schema
   ↓
Ajv
   │
   ├── 必要的数据转换
   ├── 默认值处理
   ├── 额外字段处理
   └── Validation
   ↓
Validated Request
```

这些行为都可以通过 Ajv 配置调整。

#### <u>10. Serialization 根据 Response Schema 把返回对象转换成网络输出</u>

Response Schema 不等同于“再做一次 Request Validation”。

Fastify可以根据 Response Schema 创建 Serializer（序列化函数），把程序中的 JavaScript Object 转换成 HTTP Response Body。

例如：

```js
response: {
  200: {
    type: 'object',

    properties: {
      id: {
        type: 'integer',
      },

      name: {
        type: 'string',
      },
    },
  },
}
```

Handler：

```js
return {
  id: 1,
  name: 'Tom',
  internalToken: 'secret',
};
```

最终输出会按 Response Schema 处理：

```json
{
  "id": 1,
  "name": "Tom"
}
```

因此：

```text
Validation
    Request → 是否满足输入规则

Serialization
    Result → 怎样按照输出规则生成 Response
```

完整 Schema 链路是：

```text
HTTP Request
      ↓
Parsing
      ↓
Request Schema
      ↓
Ajv Validation
      ↓
是否合法？
   ↙       ↘
 否         是
 ↓          ↓
400      Handler
            ↓
       Return Value
            ↓
      Response Schema
            ↓
       Serialization
            ↓
       HTTP Response
```

#### <u>11. Plugin + Encapsulation 负责组织大型 Fastify 应用</u>

Fastify 的另一个核心能力是 Plugin。

例如：

```js
async function userPlugin(fastify) {
  fastify.get('/users', async () => {
    return [];
  });

  fastify.post('/users', async () => {
    return {};
  });
}

fastify.register(
  userPlugin,
  {
    prefix: '/api',
  },
);
```

于是：

```text
User Plugin

GET  /api/users
POST /api/users
```

Plugin 不只是“拆文件”。

Fastify的 `register()` 会建立 Encapsulation Context（封装上下文）：

```text
Root Fastify
     │
     ├── User Plugin
     │      ├── Route
     │      ├── Hook
     │      └── Decorator
     │
     └── Order Plugin
            ├── Route
            ├── Hook
            └── Decorator
```

可以先理解为：

```text
父作用域
   ↓
子作用域可以继承

子作用域内部能力
   ↓
默认不会随意污染兄弟作用域和父作用域
```

因此 Fastify 的模块化模型最终可以理解为：

```text
Fastify
  │
  ├── Plugin
  │     ├── Routes
  │     ├── Hooks
  │     └── Shared Capability
  │
  └── Encapsulation
        控制这些能力影响哪些 Routes
```

[[28]](https://fastify.dev/docs/latest/Reference/Plugins/) [[29]](https://fastify.dev/docs/latest/Reference/Encapsulation/)

### 【Fastify 与 Express 的主要差异在于请求处理模型和工程约束】

Express 和 Fastify都位于：

```text
Node.js HTTP Server
        ↓
Web Framework
```

这一层，但设计中心不同。

Express官方把框架定位为 Minimal（精简）、Flexible（灵活）的 Web Framework，其核心使用方式围绕 Routing 和 Middleware。[[30]](https://expressjs.com/en/guide/using-middleware.html)

可以整理成：

| 维度 | Express | Fastify |
|---|---|---|
| 核心请求模型 | Routing + Middleware Chain | Route + Lifecycle + Hook |
| 通用处理 | `app.use()` + `next()` | `addHook()` 挂载生命周期 |
| Request Validation | 常配合其他库实现 | Schema + Ajv 属于核心体系 |
| Response Serialization | 一般由应用直接返回 / JSON 序列化 | 可通过 Response Schema 编译序列化 |
| 模块组织 | Router / Middleware，自由度较高 | Plugin + Encapsulation |
| 框架约束 | 较少 | 请求契约和生命周期更明确 |
| 生态特点 | 历史更久、Middleware 生态广 | 更强调低开销和 Schema 驱动 |

因此选型不应该简单理解为：

```text
Fastify 快
Express 慢
```

更适合从工程模型判断：

```text
如果项目更加依赖：

成熟 Express Middleware
现有 Express 代码和团队经验
较自由的框架组织方式

→ Express
```

而：

```text
如果项目更加重视：

明确的 Request / Response Schema
统一 Validation / Serialization
完整 Request Lifecycle
Plugin 模块隔离
较强的 API 工程约束

→ Fastify
```

Fastify官方提供的 Benchmark 可以说明其低开销设计目标，但性能数字会受到 Node 版本、硬件、插件和真实业务逻辑影响，因此 Benchmark 不应该成为唯一选型依据。[[31]](https://fastify.dev/benchmarks/)

### 【NestJS 在 Web Framework 之上进一步建立应用组织体系】

Fastify已经能够独立构建完整 HTTP API：

```text
HTTP Server
   ↓
Route
   ↓
Validation
   ↓
Handler
   ↓
Response
```

但随着系统增长，还会出现：

```text
几十到几百个 Route
多个业务模块
Service 相互依赖
认证和权限
配置
异常
数据访问
测试
生命周期管理
```

这时问题开始从：

```text
“这个 HTTP Request 怎样处理？”
```

转变为：

```text
“整个服务端应用怎样组织？”
```

NestJS主要解决的是后一层问题。

NestJS官方将自己定位为构建高效、可扩展 Node.js 服务端应用的框架，并通过 Platform Adapter 运行在 Express 或 Fastify 之上。[[32]](https://docs.nestjs.com/first-steps)

#### <u>1. FastifyAdapter 把 NestJS 应用模型连接到 Fastify</u>

如果选择 Fastify：

```bash
npm install @nestjs/platform-fastify
```

启动：

```ts
import { NestFactory } from '@nestjs/core';
import {
  FastifyAdapter,
  NestFastifyApplication,
} from '@nestjs/platform-fastify';

import { AppModule } from './app.module';

async function bootstrap() {
  const app =
    await NestFactory.create<NestFastifyApplication>(
      AppModule,
      new FastifyAdapter(),
    );

  await app.listen(3000);
}

bootstrap();
```

可以理解为：

```text
NestJS Application Model
          ↓
FastifyAdapter
          ↓
Fastify
          ↓
Node.js HTTP Server
```

Adapter（适配器）的作用是：

> **把 NestJS 的通用应用模型连接到具体的 HTTP Framework。**

[[33]](https://docs.nestjs.com/techniques/performance)

#### <u>2. Controller 负责 HTTP 边界，Service / Provider 负责应用能力</u>

Controller：

```ts
import {
  Controller,
  Get,
} from '@nestjs/common';

@Controller('users')
export class UserController {
  @Get()
  findAll() {
    return [];
  }
}
```

表示：

```text
GET /users
    ↓
UserController.findAll()
```

NestJS官方定义中，Controller负责处理进入应用的请求并向客户端返回响应。[[4]](https://docs.nestjs.com/controllers)

业务逻辑则通常进入 Service：

```ts
import { Injectable } from '@nestjs/common';

@Injectable()
export class UserService {
  findAll() {
    return [
      {
        id: 1,
        name: 'Tom',
      },
    ];
  }
}
```

Controller：

```ts
@Controller('users')
export class UserController {
  constructor(
    private readonly userService: UserService,
  ) {}

  @Get()
  findAll() {
    return this.userService.findAll();
  }
}
```

形成：

```text
HTTP Request
    ↓
Controller
    ↓
Service
    ↓
Business Logic
```

#### <u>3. Module 把相关 Controller 和 Provider 组织成应用模块</u>

```ts
@Module({
  controllers: [
    UserController,
  ],

  providers: [
    UserService,
  ],
})
export class UserModule {}
```

可以理解为：

```text
UserModule
   │
   ├── UserController
   └── UserService
```

进一步形成：

```text
AppModule
   │
   ├── UserModule
   ├── AuthModule
   ├── OrderModule
   └── AnalyticsModule
```

因此 Module 解决的是：

```text
整个应用有哪些能力模块
每个模块包含哪些 Controller
每个模块包含哪些 Provider
模块之间怎样建立边界和依赖
```

#### <u>4. Dependency Injection 统一管理对象创建和依赖关系</u>

如果 `UserController` 需要 `UserService`，手动方式可能是：

```ts
const service = new UserService();

const controller =
  new UserController(service);
```

NestJS则允许只声明依赖：

```ts
constructor(
  private readonly userService: UserService,
) {}
```

然后由框架完成：

```text
发现 UserController
      ↓
发现其依赖 UserService
      ↓
查找对应 Provider
      ↓
创建 / 获取 UserService
      ↓
注入 UserController
```

这就是 Dependency Injection（依赖注入）：对象声明自己依赖什么，框架负责管理依赖对象的创建和连接。NestJS Provider 文档把可注入 Provider 作为框架核心机制之一。[[14]](https://docs.nestjs.com/providers)

#### <u>5. NestJS 在 Web Framework 之上增加应用级 Request Lifecycle</u>

NestJS Request Lifecycle 包含：

```text
Middleware
   ↓
Guard
   ↓
Interceptor
   ↓
Pipe
   ↓
Controller
   ↓
Service
   ↓
Interceptor
   ↓
Response
```

不同能力主要解决：

| 能力 | 主要职责 |
|---|---|
| Middleware（中间件） | 请求进入 Nest 应用后的通用前置处理 |
| Guard（守卫） | 判断当前请求是否允许继续执行 |
| Pipe（管道） | 校验或转换 Controller 参数 |
| Interceptor（拦截器） | 包裹 Controller 执行前后过程 |
| Controller（控制器） | 把 HTTP 请求映射到应用入口 |
| Service / Provider | 承载业务能力 |
| Exception Filter（异常过滤器） | 把异常转换成统一 Response |

Nest官方 Request Lifecycle 对这些组件的总体顺序有明确说明。[[10]](https://docs.nestjs.com/faq/request-lifecycle)

### 【Fastify 与 NestJS 的两层生命周期属于不同抽象层】

当系统使用：

```text
NestJS + Fastify
```

时，会同时存在两套生命周期能力。

可以用分层模型理解：

```text
HTTP Request
      ↓
Node.js HTTP Server
      ↓
──────── Fastify ────────
      ↓
Route Matching
      ↓
Parsing
      ↓
Fastify Hook
      ↓
Validation
      ↓
──────── NestJS ─────────
      ↓
Middleware
      ↓
Guard
      ↓
Interceptor
      ↓
Pipe
      ↓
Controller
      ↓
Service
      ↓
──────── 返回阶段 ───────
      ↓
Nest Interceptor / Filter
      ↓
Fastify Serialization
      ↓
HTTP Response
```

这张图是理解层级的工程模型，不应该当作所有内部函数逐行调用顺序。

真正需要区分的是：

```text
Fastify
    更关注 HTTP Request Processing

NestJS
    更关注 Application Processing
```

Fastify回答：

```text
这个 Method + URL 匹配哪个 Route？
Body 怎样解析？
输入怎样校验？
请求生命周期怎样扩展？
返回对象怎样序列化？
```

NestJS回答：

```text
这个 Route 对应哪个 Controller？
请求是否有权限执行？
参数怎样进入 Controller？
业务由哪个 Service 承担？
Service 依赖怎样管理？
整个应用怎样拆成 Module？
```

### 【完整请求最终从 HTTP 通信进入业务应用再返回网络响应】

把 Web Server、Fastify 和 NestJS 放在一起，一次请求可以整理成：

```text
Client
   │
   │ HTTP / HTTPS
   ↓
Reverse Proxy
   ↓
Node.js Process
   ↓
Node.js HTTP Server
   │
   │ 接收 Request
   ↓
Fastify
   │
   ├── Route Matching
   ├── Request Parsing
   ├── Fastify Hooks
   ├── Schema Validation
   └── Request / Reply
   ↓
NestJS
   │
   ├── Middleware
   ├── Guard
   ├── Interceptor
   ├── Pipe
   └── Controller
   ↓
Service
   ↓
Business Logic
   ↓
Database / Cache / External Service
   ↓
Result
   ↑
NestJS Interceptor / Exception Filter
   ↑
Fastify Serialization
   ↑
Node.js HTTP Response
   ↑
Reverse Proxy
   ↑
Client
```

最终可以把三层职责收敛成：

```text
Node.js HTTP Server
    让程序具备 HTTP 通信能力

Fastify
    把 HTTP 通信组织成完整 Web 请求处理体系

NestJS
    把 Web 请求进一步映射到可维护的应用结构和业务能力
```

因此从原生 Node.js 逐步演进到 Fastify、NestJS，本质上不是不断“增加一层没有必要的封装”，而是在不同复杂度下持续解决新的工程问题：

```text
node:http
    ↓
解决“能不能接收 HTTP 请求”

Fastify
    ↓
解决“怎样统一处理大量 HTTP 请求”

NestJS
    ↓
解决“怎样组织一个持续增长的服务端应用”
```

当前阶段只需要掌握每一层的职责边界和基础使用，不需要深入 Node HTTP Parser、Fastify Router 内部数据结构、Ajv Compiler 或 NestJS DI Container 的内部实现。


## 4. Node.js 服务端运行体系建立从代码到服务实例的运行认知

前面的服务端体系已经回答了“服务端由哪些系统组成”。继续向下，需要回答一个更基础的问题：

> **一份 JavaScript / TypeScript 服务端代码，如何变成一个长期运行、能够持续接收和处理请求的服务？**

这一部分先建立完整运行链路：

```text
Source Code
     ↓
Node.js Runtime
     ↓
Operating System 创建 Process
     ↓
Main Thread 执行 JavaScript
     ↓
Event Loop + Node APIs + I/O
     ↓
HTTP Server
     ↓
listen(port)
     ↓
持续接收 Request
     ↓
Application Handler / Service
     ↓
Database / Redis / External API
     ↓
Response
```

当前阶段重点建立 **Runtime → Process → Thread → Event Loop → I/O → Server → Request** 的关系，暂不深入 V8 编译器、libuv 内部结构和操作系统调度算法。

### 【Runtime、Process 和 Server 描述程序运行的不同层级】

#### <u>1. Runtime 是代码能够运行所依赖的执行环境</u>

JavaScript 首先是一门语言。源代码本身不能直接完成服务端网络监听、文件访问和进程管理，需要运行环境提供执行和系统能力。

```text
JavaScript / TypeScript
        ↓
   Node.js Runtime
        ↓
 Operating System
        ↓
CPU / Memory / Network / File
```

Node.js 官方将 Node.js 定义为 JavaScript Runtime Environment，并使用 V8 JavaScript Engine 执行 JavaScript。[[34]](https://nodejs.org/en/about)

入门阶段可以把 Node.js Runtime 简化为：

```text
                 Node.js Runtime
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
         V8        Node APIs      libuv 等
          │            │            │
      执行 JS      fs/http/net   Event Loop / I/O
```

因此需要区分：

```text
JavaScript
= 编程语言

Node.js
= JavaScript 服务端运行环境
```

Runtime 回答的是：

> **这份代码依靠什么环境获得执行能力和系统能力？**

#### <u>2. Process 是程序真正运行起来后的操作系统实例</u>

电脑安装 Node.js，只说明机器中存在 Node Runtime。执行：

```bash
node server.js
```

以后才真正发生：

```text
server.js
    ↓
node server.js
    ↓
Operating System
创建 Node Process
    ↓
Process 中初始化 Node Runtime
    ↓
加载 server.js
    ↓
执行 JavaScript
```

因此：

```text
Runtime
= 程序依赖什么环境运行

Process
= 程序当前作为哪个运行实例存在
```

同一种 Node Runtime 可以启动多个独立 Process：

```bash
node api.js
node worker.js
node scheduler.js
```

对应：

```text
Operating System
│
├── Node Process A
│     └── api.js
│
├── Node Process B
│     └── worker.js
│
└── Node Process C
      └── scheduler.js
```

因此同一个 Repository 中的 `apps/api`、`apps/worker` 可以使用相同 Node.js 技术栈，却在运行时形成不同 Process。

#### <u>3. Server 是 Process 内建立起来的持续服务能力</u>

普通脚本：

```js
console.log('hello');
```

运行后可以形成 Process，但代码执行结束且没有剩余活动工作时，Process 会退出。

所以：

```text
Runtime  ✓
Process  ✓
HTTP Server  ×
```

而：

```js
import http from 'node:http';

const server = http.createServer((req, res) => {
  res.end('Hello');
});

server.listen(3000);
```

会建立：

```text
Node Process
     ↓
Node Runtime
     ↓
执行 server.js
     ↓
HTTP Server
     ↓
listen(3000)
     ↓
Listening Socket
     ↓
持续等待 Request
```

Node.js 的 `node:http` 模块提供 HTTP Client 和 HTTP Server 能力。[[35]](https://nodejs.org/api/http.html)

因此三个概念最终可以压缩为：

```text
Runtime
= 程序“靠什么运行”

Process
= 程序“作为什么运行实例存在”

Server
= 这个运行实例“持续提供什么服务”
```

层级关系可以先理解为：

```text
Operating System
└── Node Process
      └── Node Runtime
            └── Application Code
                  └── HTTP Server
                        └── Request Handler
```

Process 与 Server 不能画等号。一个 Process 可以不是 HTTP Server，例如 Worker；一个 Process 也可以创建多个 Server。实际 API 工程通常主要运行一个 HTTP Server，所以二者容易被误认为同一概念。

### 【Main Thread、Event Loop 和异步 I/O 共同形成 Node.js 的请求执行基础】

#### <u>1. Node.js 默认由主 JavaScript 线程执行应用代码</u>

一个 Node Process 可以先简化为：

```text
Node Process
│
├── Node Runtime
├── Main JavaScript Thread
├── Event Loop
└── I/O Runtime
```

应用 JavaScript 主要运行在 Main Thread。同一个主 JavaScript 执行线程在某一时刻通常只执行一段 JavaScript。

因此常说：

```text
JavaScript 主执行路径
        ↓
      单线程
```

但这并不意味着整个 Node.js Runtime 只有一个操作系统线程。Node Runtime 内部还可能使用其他线程，应用也可以通过 `worker_threads` 创建额外 JavaScript 执行线程。

更准确的说法是：

> **Node.js 默认的主 JavaScript 执行路径是单线程，而不是“整个 Node.js 只有一个线程”。**

#### <u>2. Event Loop 让主线程在 I/O 等待期间继续推进其他工作</u>

服务端请求大量时间并不是执行 CPU 计算，而是在等待 Database、Redis、HTTP、File、Network 等 I/O。

例如：

```js
async function getUser(id) {
  const user = await database.findUser(id);
  return user;
}
```

如果同步阻塞等待数据库：

```text
Main Thread

执行 JS
████
等待 DB
░░░░░░░░░░
DB 返回
████
继续执行
```

等待期间线程无法处理其他 JavaScript 工作。

Node.js 的典型非阻塞模型则是：

```text
Request A
    ↓
发起 DB I/O
    ↓
等待 DB
    │
    ├──→ Request B
    ├──→ Request C
    └──→ Request D

DB 返回
    ↓
继续 Request A
```

Node.js 官方说明其通过异步、非阻塞 I/O，使 JavaScript 线程不必在网络、数据库、文件系统等 I/O 等待期间持续阻塞。[[34]](https://nodejs.org/en/about)

Event Loop 的价值不是：

```text
一个 JS Thread
同时执行多个 JS 函数
```

而是：

```text
任务 A 等待 I/O
       ↓
Main Thread 暂时执行其他可执行工作
       ↓
I/O 完成
       ↓
任务 A 后续逻辑重新获得执行机会
```

#### <u>3. Event Loop 和 I/O 需要分开理解</u>

不能简单认为 Event Loop 自己执行所有网络、文件和数据库 I/O。

当前阶段先建立：

```text
JavaScript
    ↓
调用 Node API
    ↓
Node Runtime
    ↓
发起 I/O
    ↓
OS / Runtime 等待 I/O 完成
    ↓
I/O Completion
    ↓
Event Loop
    ↓
对应 JavaScript 后续逻辑获得执行机会
```

因此 Event Loop 更接近：

> **协调什么时候执行哪些 JavaScript 工作的运行机制。**

真正的 I/O 可能由操作系统异步机制、Runtime 底层能力或者线程池等不同机制完成。这部分在后续 Event Loop / libuv 专题再深入。

### 【HTTP Server 将 Node Process 变成长时间运行的服务程序】

执行：

```js
server.listen(3000);
```

以后建立网络监听：

```text
Node Process
    ↓
HTTP Server
    ↓
listen(3000)
    ↓
Listening Socket
    ↓
等待网络事件
    ↓
Event Loop 仍存在活动工作
    ↓
Process 持续运行
```

因此服务端所谓“长期运行”不是通过：

```js
while (true) {}
```

持续占用 CPU 实现，而是 Process 中存在 Server、Socket、Timer 等活动资源，Event Loop 可以在没有事件时等待，在事件到来时继续执行对应工作。

一次 HTTP 请求最终形成：

```text
Browser
   ↓
TCP / HTTP
   ↓
Operating System
   ↓
Node Process
   ↓
HTTP Server
   ↓
Request Event
   ↓
Main JavaScript Thread
   ↓
Request Handler
   ↓
发起 Database / Redis / HTTP I/O
   ↓
等待期间处理其他工作
   ↓
I/O 完成
   ↓
Event Loop 调度后续执行
   ↓
JavaScript 继续运行
   ↓
res.end()
   ↓
HTTP Response
```

因此 HTTP Server 不是独立于 Node Runtime 的另一个系统，而是运行在 Node Process 中、利用 Runtime 的网络和异步 I/O 能力建立起来的服务能力。

### 【Node.js 的并发能力来自 I/O 并发、线程并行和进程扩展三个层级】

首先区分：

```text
Concurrency（并发）
= 多个任务在同一时间段内持续推进

Parallelism（并行）
= 多个任务在同一时刻真正执行
```

Node.js 服务端会在不同层级使用不同机制。

#### <u>1. Event Loop + Async I/O 主要解决大量 I/O 等待型并发</u>

普通 Web API：

```text
Request
   ↓
Database
   ↓
Redis
   ↓
External API
   ↓
Response
```

大量时间属于 I/O Wait，因此不必把每个请求直接映射成一个 JavaScript Thread：

```text
                 Main Thread
                      │
                  Event Loop
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
    Request A     Request B     Request C
        │             │             │
       DB           Redis          HTTP
        │             │             │
      Waiting       Waiting       Waiting
```

这正是 Node.js 默认请求模型擅长的场景。

#### <u>2. Worker Threads 主要解决 Process 内 CPU 密集 JavaScript 工作</u>

如果请求中出现图片处理、数据压缩、复杂算法、加密计算、大量数据转换等持续占用 CPU 的工作：

```text
Main Thread

Request A
   ↓
████████ CPU Calculate ████████
   ↓
Response

Request B
   ↓
等待 Main Thread
```

Event Loop 无法通过“利用 I/O 等待”解决，因为 Main Thread 本身正在执行 CPU 工作。

可以使用 Worker Threads：

```text
Node Process
│
├── Main Thread
│      └── HTTP / Event Loop
│
├── Worker Thread 1
│      └── CPU Task
│
├── Worker Thread 2
│      └── CPU Task
│
└── Worker Thread 3
       └── CPU Task
```

Node.js 官方说明 `worker_threads` 可以并行执行 JavaScript，适合 CPU-intensive JavaScript 操作，而对 I/O-intensive 工作通常帮助不大，因为 Node.js 自身的异步 I/O 更适合后者。[[36]](https://nodejs.org/api/worker_threads.html)

Worker Thread 不是让同一个 JavaScript 执行环境直接变成多线程，而是为不同 Worker 建立独立 JavaScript 执行环境。普通 JavaScript 对象默认不作为同一个对象直接共享；Worker 可以通过 Message、Transferable 对象或 `SharedArrayBuffer` 等机制交换或共享数据。[[36]](https://nodejs.org/api/worker_threads.html)

#### <u>3. Thread 数量不等于 CPU Core 数量</u>

4 个 CPU Core 并不意味着只能创建 4 个 Thread：

```text
100 Threads
     ↓
OS Scheduler
     ↓
┌──────┬──────┬──────┬──────┐
│Core 1│Core 2│Core 3│Core 4│
└──────┴──────┴──────┴──────┘
```

线程数量可以远大于 CPU Core 数量，但 CPU-bound 工作能够获得的真实并行能力受到 CPU 执行资源限制。

因此 CPU Worker 不是越多越好。过多 CPU-bound Thread 还会增加调度、Context Switch 和内存开销。

#### <u>4. Multiple Processes 用于复制完整运行实例并建立更强隔离</u>

另一种扩展方式是启动多个独立 Node Process：

```text
Operating System
│
├── Node Process A
│     └── Main Thread
│
├── Node Process B
│     └── Main Thread
│
└── Node Process C
      └── Main Thread
```

例如：

```text
                   Requests
                      ↓
                 Load Balancer
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
   API Process 1 API Process 2 API Process 3
```

Node.js Cluster 可以创建多个 Node.js Process 并在它们之间分配连接；官方文档同时区分了需要进程隔离的多进程方案和单进程中的 Worker Threads。[[37]](https://nodejs.org/api/cluster.html)

多进程的价值不仅是利用多个 CPU Core，还包括：

```text
独立生命周期
独立内存空间
故障隔离
独立重启
独立扩容
资源隔离
```

#### <u>5. 多线程与多进程解决不同层级的问题</u>

| 场景 | 主要机制 | 解决的问题 |
|---|---|---|
| 大量 DB / Redis / HTTP 等待 | Event Loop + Async I/O | I/O 并发 |
| Process 内 CPU 密集计算 | Worker Threads | CPU 并行 |
| 整个 API 实例容量不足 | Multiple Processes / Instances | 服务扩容 |
| 后台任务形成独立运行职责 | Worker Process | 生命周期与职责隔离 |
| 需要更强故障隔离 | Multiple Processes | 进程隔离 |

真实系统可以同时存在：

```text
                    Service
                       │
            Multiple Processes
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
 API Process 1    API Process 2    API Process 3
       │
       ├── Main Thread
       │      ↓
       │  Event Loop
       │      ↓
       │  Async I/O
       │
       └── Worker Threads
              ↓
          CPU Parallelism
```

所以三层能力可以分别记成：

```text
Event Loop + Async I/O
    ↓
解决 I/O 并发

Worker Threads
    ↓
解决单个 Process 内 CPU 并行

Multiple Processes
    ↓
解决完整运行实例扩展与隔离
```

### 【Node.js 服务端运行体系最终收敛为代码运行链、请求链和扩展链】

#### <u>1. 代码运行链解释 server.js 如何成为长期运行程序</u>

执行：

```bash
node server.js
```

应该展开理解为：

```text
server.js
Source Code
    ↓
Node.js Runtime
    ↓
Operating System 创建 Process
    ↓
Node Process
    ↓
Main Thread 执行 JavaScript
    ↓
Event Loop + Node APIs + I/O
    ↓
http.createServer()
    ↓
HTTP Server
    ↓
listen(port)
    ↓
Listening Socket
    ↓
持续等待 Request
```

#### <u>2. 请求链解释一个 Request 如何借助 Runtime 完成</u>

```text
Client
   ↓
HTTP Request
   ↓
Network
   ↓
Node HTTP Server
   ↓
Request Event
   ↓
Main Thread
   ↓
Application Handler
   ↓
Service
   ↓
Database / Redis / External API
   ↓
Async I/O Wait
   ↓
Event Loop
   ↓
继续执行 JavaScript
   ↓
HTTP Response
```

如果使用 NestJS，它位于 Node.js 基础运行体系之上：

```text
Client
   ↓
Node HTTP Server
   ↓
Express / Fastify
   ↓
NestJS
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

NestJS 不会替代 Runtime、Process、Thread、Event Loop 和 Network，而是在这些能力之上组织应用代码。

#### <u>3. 扩展链要求先判断瓶颈属于哪个运行层级</u>

```text
Node API 性能不足
       │
       ↓
   瓶颈在哪里？
       │
       ├── I/O Wait
       │      ↓
       │   Async I/O / Cache / DB / Network 优化
       │
       ├── CPU-intensive Task
       │      ↓
       │   Worker Threads
       │
       ├── 单个 API Instance 容量不足
       │      ↓
       │   Multiple Processes / Containers
       │
       └── Database / Redis / 下游服务饱和
              ↓
          优化对应系统
```

因此服务端扩展不能简单理解成“请求多就增加 Thread”或者“性能差就增加 Process”，而是先找到瓶颈，再判断它属于哪个运行层级。

### 【当前阶段先建立运行边界，底层机制留到后续专题】

这一部分最终需要稳定掌握：

```text
JavaScript
= 编程语言

Node.js
= JavaScript Runtime

Process
= 操作系统中的程序运行实例

Thread
= Process 内部的执行单元

Event Loop
= 协调异步事件与 JavaScript 执行的运行机制

I/O
= 程序与网络、文件、数据库等外部资源交互

HTTP Server
= Process 内建立的 HTTP 服务能力

Worker Thread
= Process 内额外的 JavaScript 执行线程

Multiple Processes
= 多个相互隔离的完整程序运行实例
```

最终主链：

```text
Source
  ↓
Runtime
  ↓
Process
  ↓
Main Thread
  ↓
Event Loop
  ↓
HTTP Server
  ↓
Request
  ↓
Application
  ↓
Async I/O
  ↓
Response
```

当前暂不深入：

```text
V8 Parser / Ignition / TurboFan
libuv uv_loop_t
Event Loop 具体 Phase
epoll / kqueue / IOCP
libuv Thread Pool 调度细节
OS Thread Scheduling
Context Switch 底层实现
```

这些内容在完整运行体系建立以后，再进入 Event Loop、异步 I/O 和 libuv 专题逐层展开。

## 5. 服务端数据与状态体系建立从运行时状态到持久化数据的整体边界

请求处理体系解决“请求怎样进入业务逻辑”，但业务系统还必须回答另一个问题：

~~~text
一次请求产生的状态
        ↓
请求结束以后
        ↓
哪些需要消失？
哪些需要继续存在？
哪些需要被其他请求、进程或服务共享？
~~~

### 【状态存储首先由生命周期和访问方式决定】

~~~text
Server State
│
├── Process Memory
│   └── 当前进程内部的短生命周期状态
├── Cache
│   └── 可重建、强调快速访问的状态
├── Database
│   └── 需要长期保存、查询、约束和并发维护的结构化业务状态
└── Object / File Storage
    └── 文件、图片、视频、归档对象等大对象
~~~

这些系统不是简单的“速度不同”，而是承担不同生命周期、数据模型、一致性和访问模式。具体选择仍要结合数据规模、一致性要求、访问模式和可靠性目标。

### 【Database 负责长期结构化状态，但数据库内部仍是一套独立体系】

从服务端看：

~~~text
Controller
    ↓
Service
    ↓
Data Access
    ↓
Database
~~~

继续向下会进入：

~~~text
Data Model
    ↓
Schema
    ↓
Driver / Connection / Pool
    ↓
SQL
    ↓
Constraint
    ↓
Transaction / Concurrency
    ↓
Index / Query Planner
    ↓
Migration / Operations
~~~

因此本篇只负责确定 Database 在完整 Server Architecture 中的位置；数据库内部知识由 [数据库完整框架体系](./数据库完整框架体系.md) 继续展开。

### 【Cache 与 Database 的职责不能用“快”和“慢”简单替代】

常见错误模型是 Database = 慢、Cache = 快。更准确的判断需要同时考虑：

~~~text
Source of Truth
Data Lifetime
Consistency
Query Model
Recoverability
Latency
Capacity
~~~

某些系统会把 Database 作为主要持久化事实来源，再使用 Cache 保存可重新生成的热点数据；其他架构可能采用不同语义。Cache 是否适合作为某类状态的主要存储，需要根据具体系统判断。

### 【服务端数据体系继续连接异步任务和运行环境】

~~~text
Request
    ↓
Service
    ↓
Database Transaction
    ↓
Commit
    ↓
Async Task / Event
    ↓
Worker
~~~

同时 API Process、Worker Process、Scheduled Job 可能共享 Database、Cache 或 Storage。因此数据体系会继续与后续的异步处理、部署、可靠性和可观测性发生连接。

当前阶段先建立 Memory、Cache、Database、Object Storage 的职责边界；数据库内部继续阅读 [数据库完整框架体系](./数据库完整框架体系.md)，Redis、消息系统、对象存储和分布式一致性再进入各自专题。
