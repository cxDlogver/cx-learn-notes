# 作用域与JavaScript执行过程

## 0.目标

### 作用域类型与边界

- **全局作用域**：script vs module 的区别（顶层 `this`、是否挂全局对象）
- **函数作用域**：`function` 创建作用域；`var` 以函数为边界
- **块级作用域**：`{}` / `if` / `for` / `catch` 的块级环境；`let/const/class`
- **局部作用域（口语）**：泛指非全局（函数/块）

### 变量声明语义

- **var/let/const 的作用域差异**
- **提升与初始化差异**
  - `var`：创建阶段初始化 `undefined`
  - `let/const`：创建阶段登记但未初始化 → TDZ
- **重复声明规则**
  - `var` 可重复；`let/const` 同一作用域不可重复
  - `var` 与 `let/const` 在同一作用域的冲突（会报语法错误）
- **const 的“不可变”边界**
  - 绑定不可变 vs 引用对象内部可变

### 闭包基本概念与识别

- 闭包定义：函数携带其定义时的外层环境引用（自由变量）
- 如何识别：函数体内使用外层变量 + 函数在外层返回/异步执行
- “闭包不是一定返回函数”：回调、事件处理器同样形成闭包

### 闭包的常见应用

- **计数器/状态保持**（counter）
- **函数工厂**（makeAdder）
- **防抖/节流**（timer 状态）
- **循环 + var 的经典问题**与两种解法：IIFE 闭包 / `let`

### 基本调试能力

- DevTools Scope 面板：Local / Block / Closure / Global 的含义
- 能解释一次调用中“块只创建词法环境，不创建执行上下文”

### 作用域链工作原理

- **词法作用域**：外层是谁由“定义位置”决定，不由“调用位置”决定
- **环境链（outer 链）**：从当前环境记录向外查找
- **Environment Record / HasBinding 的抽象**
- **LexicalEnvironment vs VariableEnvironment**
  - 两个入口指针
  - 块切换的是 LexicalEnvironment 指针
  - `var` 的绑定落在函数/全局层（变量区），但外层关系仍在同一 outer 体系

### 闭包的实现机制（能对齐执行上下文生命周期）

- 函数对象的内部槽位：`[[Environment]]` 指向定义时词法环境
- 调用函数时：新执行上下文的本地环境 `outer` 连接到 `[[Environment]]`
- 外层函数返回后：**执行上下文出栈**，但**环境记录因引用可达而存活**
- 闭包保留的是环境记录/绑定，不是“上下文一直不销毁”

### 变量生命周期与内存管理影响

- 为什么闭包可能导致内存占用上升（捕获大对象/DOM/缓存）
- 何时可回收：引用断开（闭包函数不可达）→ 环境记录可 GC
- 实战规避：
  - 避免无意捕获大对象
  - 不再使用时解除引用（置 `null`）
  - 事件监听器泄漏与闭包的关系

### 模块化编程中的闭包（封装与私有化）

- IIFE 模块模式：私有变量 + 暴露 API
- 工厂函数模块：配置注入、依赖注入（DI）
- 与现代模块（ESM）的关系：
  - ESM 自带模块作用域与封装
  - 闭包更偏“运行期私有状态/实例化模块”的封装

### 高级陷阱与边界行为

- `this` 与闭包：箭头函数 `this` 词法捕获 vs 普通函数动态绑定
- `for (let i...)` 每次迭代环境（per-iteration binding）机制
- `eval/with` 对作用域链的影响（了解即可，强调不推荐）

## 1.什么是作用域

- 作用域的概念？
- 作用域的解析规则？
- 作用域的类别？

作用域指在某段代码位置上，一个名字（变量/函数/类等标识符）到底指向哪一个声明，以及它在什么范围内可见。

作用域的本质是名字解析（Identifier Resolution）。当代码中出现标识符`x`（读/写操作均算），JS引擎需要解决的是：这个`x`指向哪一个“绑定”（binding）。

这里的“绑定”来源包括：

- 变量声明：`var`/`let`/`const`

- 函数声明/参数：`function f(){}`、`function(a){}`、`(...args)=>{}`

- 类声明：`class A {}`

- import引入：`import x from '...'`

- catch (e) 的异常变量、`for (let i...)` 的迭代变量

### 作用域解析规则

1. 从当前执行位置所在的作用域开始查找

2. 找不到就沿着外层作用域向外找（作用域链/词法环境链）

3. 直到全局作用域；若仍找不到，会抛出`ReferenceError`（严格模式下限制更严格）

关键点：查找方向永远是“由内到外”，且“外层作用域是谁”由代码结构决定，与运行时无关。

### 作用域相关术语区分

#### 作用域类型

由语法结构产生的真实作用域，对应规范层面的词法环境/环境记录：

- 全局作用域：脚本顶层（`<script>`传统脚本）或模块顶层（ESM），是最外层的词法环境（脚本与模块的全局行为存在差异）。

- 函数作用域：由`function`（声明/表达式）与函数参数产生，`var`的作用域边界通常为函数或全局。

- 块级作用域：由`{ ... }`及特定结构（`if`/`for`/`while`/`switch`/`catch`等）创建，`let`/`const`/`class`的绑定仅在块内有效。

总结：全局、函数、块级是三类最常用的“作用域产生器”。

#### 非规范但常用的描述方式

此类表述并非独立的作用域类型，更多是对作用域的概括：

- 局部作用域：口语化表述，泛指“非全局”的作用域，通常覆盖函数作用域、块级作用域及模块内部等。

- 变量作用域：并非作用域类型，而是描述“某个绑定的可见范围”。例如`var`是函数级作用域，`let`/`const`是块级作用域。

### 词法作用域

词法作用域是统领作用域形成与查找的总规则，核心是：作用域的嵌套关系在编写代码时就由语法结构确定，而非运行时由调用位置决定。

> “外层作用域是谁”，只看代码定义时的嵌套结构，与代码如何被调用无关。

全局、函数、块级这三类作用域，均由代码语法结构创建，而语法结构天然具有嵌套特性，词法作用域正是规范了这种嵌套关系下的查找规则，因此能统领三类作用域。

- 在`{}`内声明`let`，其外层作用域就是包裹该`{}`的词法结构；

- 在一个函数内定义另一个函数，内部函数的外层作用域就是定义它的外部函数环境；

- 在顶层编写代码，其外层作用域就是全局环境。

注意：词法作用域并非“第四种作用域”，而是作用域形成与查找的总原则。

### 注意点

全局作用域 ≠ 全局对象（`window`），两者的差异需结合运行环境区分：

- 浏览器脚本（非module）中：`var x = 1`会使`x`成为`window.x`；`let x = 1`/`const x = 1`不会挂载到`window`，但仍处于全局词法环境中，可在同一脚本后续代码中被解析到。

- ES Module（`<script type="module">`）中：顶层声明位于模块作用域，不会挂到`window`，模块有自身的顶层词法环境，更强调隔离性。

面试表达建议：全局作用域是名字解析的最外层环境；全局对象只是某些环境下可用的对象载体，二者不能等价。

### 作用域核心总结

- 作用域：解决“代码中的名字指向哪一个绑定”的问题。

- 词法作用域：外层作用域由定义时的代码嵌套决定，与调用位置无关。

- 全局/函数/块级：语法结构产生的三类主要作用域节点。

- 局部作用域：口语化表述，泛指非全局作用域。

- 变量作用域：描述绑定的可见范围，`var`为函数级，`let`/`const`/`class`为块级。

- 全局作用域≠`window`：`var`可能挂载`window`，`let`/`const`不会；模块环境更隔离。

## 2.什么是执行上下文

- 执行上下文的概念？
- 执行上下文包含的内容有哪些？
- 执行上下文的生命周期和执行机制是什么？
- 执行上下文和作用域的区别？

执行上下文是JS引擎在运行一段可执行代码时创建的一份“运行时记录（runtime record）”，用于保存本次执行所需的所有环境信息，包括变量/函数绑定、`this`指向、作用域链入口等。

执行上下文解决的核心问题：这段代码“此刻如何运行”、变量从哪里获取、`this`的值是什么、声明如何登记。

【类型包括】

- 全局执行上下文：脚本开始执行时创建一次，贯穿脚本运行全程。

- 函数执行上下文：每次调用函数（包括构造函数调用）都会创建一个新的实例，函数执行结束后会被销毁（除非形成闭包）。

- 模块执行上下文：ESM模块执行时创建，其顶层行为与传统`<script>`脚本存在差异。

### 执行上下文包含的内容

核心包含三大组成部分，结合两个阶段的行为差异，是理解执行上下文的关键：

**【三大组成部分】**

- 词法环境（Lexical Environment）：管理`let`/`const`/`class`等绑定，包含`outer`引用指向外层环境（支撑作用域链的向外查找），是暂时性死区（TDZ）的基础——声明被登记但未初始化。

- 变量环境（Variable Environment）：管理`var`和函数声明等绑定，`var`在创建阶段会被初始化为`undefined`，形成“var提升”的视觉效果。

- this绑定（this binding）：存储当前上下文里`this`的值。普通函数的`this`由调用方式决定；箭头函数没有自己的`this`，继承外层上下文的`this`。

**补充：**执行上下文是JS引擎内部维护的运行时记录，可抽象为包含上述字段的数据结构，可以将可执行上下文看作一个对象，但并非能直接打印的普通JS对象。

### 执行上下文栈（Call Stack）示意

JS引擎维护一个调用栈，用于管理执行上下文的入栈与出栈，示意流程如下：

1. push Global EC（全局执行上下文入栈，脚本开始执行）；

2. push f EC（调用函数f，f的执行上下文入栈）；

3. push g EC（函数f内部调用函数g，g的执行上下文入栈）；

4. pop g EC（函数g执行结束，出栈）；

5. pop f EC（函数f执行结束，出栈）；

6. pop Global EC（页面关闭或脚本执行结束，全局执行上下文出栈）。

执行上下文的生命周期分为三个阶段：创建（Creation）→ 执行（Execution）→ 退出（Exit），全程配合调用栈（Call Stack）运作：进入上下文时入栈，执行结束后出栈。

### 执行上下文生命周期

执行上下文的生命周期分为三个阶段：创建（Creation）→ 执行（Execution）→ 退出（Exit），全程配合调用栈（Call Stack）运作：进入上下文时入栈，执行结束后出栈。

#### 创建阶段

进入某个执行上下文时，先完成准备工作，核心是建立环境、处理声明、确定`this`，也是“提升”现象产生的根源：

- 建立环境：创建词法环境和变量环境，通过`outer`指针连接到外层环境，形成作用域链。

- 处理声明：将当前作用域内的声明登记到环境记录中，不同声明的行为不同：
  
    - 函数声明（`function foo(){}`）：创建阶段完成绑定，因此可在声明前调用。
    
    - `var`声明：创建阶段登记并初始化为`undefined`，因此声明前访问会得到`undefined`。
    
    - `let`/`const`/`class`：创建阶段登记但不初始化，进入暂时性死区（TDZ），声明前访问会抛出`ReferenceError`。
    
- 确定`this`：`this`的绑定发生在“进入上下文时”，具体值由上下文类型决定：
  
  - 全局上下文：传统脚本中通常是`window`，严格模式和模块环境中有差异。
    
  - 函数上下文：由调用方式决定（`new`调用、`call`/`apply`调用、对象方法调用、默认绑定）。
    
  - 箭头函数：无自身`this`，继承外层上下文的`this`。

#### 执行阶段

逐行执行代码，包括变量赋值、表达式计算、函数调用（调用函数会创建新的函数执行上下文并入栈）。

> 易错点：进入`{}`/`for`/`catch`等块级结构时，会创建块级词法环境层，但通常不会创建新的执行上下文；新执行上下文的创建主要来自“函数调用、全局脚本执行、模块执行”（后面解释）。

#### 退出阶段

当出现以下情况之一时，执行上下文进入退出阶段：

- 函数执行到末尾或遇到`return`语句；

- 抛出异常且未在当前上下文内被捕获。

退出阶段的核心操作：当前执行上下文从调用栈中出栈，引擎不再维护该上下文的运行信息。

> 关键补充：出栈后变量不一定会被销毁——若有函数引用了外层环境的记录，会形成闭包，导致该外层环境记录仍可访问，无法被垃圾回收机制回收（后面解释）。

### 完整生命周期演示

以下代码可直观体现执行上下文的创建、执行、退出三个阶段，以及闭包的形成：

```javascript
function f() {
  console.log(a); // undefined（创建阶段var a被初始化为undefined）
  // console.log(b); // ReferenceError（创建阶段let b进入TDZ，未初始化）

  var a = 1;
  let b = 2;

  function g() {
    console.log(this, a, b);
  }

  g(); // 调用g：创建g的执行上下文并入栈
  return g; // 返回g：形成闭包（g引用了外层a、b的环境）
}

const h = f(); // f的执行上下文出栈，但环境记录因闭包保留
h(); // 再次调用h（即g），创建新的g执行上下文
```

流程解析：

- 调用`f()`：创建f的执行上下文（登记`var a`、`let b`、函数`g`，确定`this`）→ 执行f内部代码 → 执行`return g` → f的执行上下文出栈。

- `g()`每次被调用（无论是在f内部还是外部通过h调用），都会创建一个新的g执行上下文。

- `return g`使g引用了f的词法环境，形成闭包，因此f的环境记录在f的执行上下文出栈后仍可被访问。

### 执行上下文核心总结

- 生命周期：创建阶段（登记声明、确定`this`）→ 执行阶段（逐行执行、函数调用入栈）→ 退出阶段（出栈）。

- 块级结构仅修改词法环境指针，不创建新的执行上下文。

- 闭包保留的是词法环境记录，并非让执行上下文一直不出栈。

### 执行上下文与作用域的区别

**【本质差异（静态vs动态）】**

- 作用域：静态规则，由代码的嵌套结构决定“名字向外查找的路径”（即词法作用域链结构），在编写代码时就已确定，与运行时无关。

- 执行上下文：动态实例，每次运行到某段可执行代码时创建，保存“这一次执行”的运行信息（`this`、环境记录当前状态等），运行结束后会被销毁（除非闭包）。

**【两者的协作关系】**

1. 作用域（静态）决定外层环境是谁（由代码定义位置决定）；

2. 执行上下文（动态）在创建阶段，会将自身环境的`outer`指针指向外层环境；

3. 运行时变量查找时，就会沿着`outer`指针形成的链（作用域链）向外查找，实现作用域的查找规则。

**【闭包常见误区校正】**

误区：闭包是让执行上下文一直不销毁、不出栈。

正解：执行上下文会正常出栈（函数返回即结束），闭包的核心是“外层词法环境记录仍可被访问”，即环境记录的生命周期被延长，而非执行上下文不销毁。

## 3.词法环境和变量环境

- 什么是词法环境和变量环境？
- 什么是会创建新的执行上下文？
- 什么时候会创建新的词法环境而不创建执行上下文？
- 一个执行上下文是如何管理多层词法环境的？

### 什么是词法环境和变量环境

#### 词法环境（Lexical Environment）

用于管理`let`/`const`/`class`、块级绑定、函数表达式等，是实现块级作用域、暂时性死区（TDZ）和作用域链查找的核心。其核心结构包含两部分：

- 环境记录（Environment Record）：存储当前作用域内的所有绑定（变量、函数等），例如块级声明的`let x`、`const y`均存储于此。

- outer引用：指向外层词法环境，形成作用域链，是标识符向外查找的关键。

特点：每进入一个块级结构（`if`/`{}`/`for`/`catch`等），就会创建一层新的词法环境，且不会创建新的执行上下文；离开块级结构时，当前词法环境指针会回退到其outer指向的外层环境。

#### 变量环境（Variable Environment）

用于管理`var`声明和函数声明（函数声明提升），其结构与词法环境一致（包含环境记录和outer引用），但功能和行为有明确区别。

特点：`var`声明在执行上下文创建阶段会被初始化为`undefined`，形成“var提升”；函数声明在创建阶段会完成绑定，可在声明前调用；其作用域边界为函数或全局，不支持块级作用域，**一个执行上下文只可能有一个变量环境**。

#### 两者关系

在ES6及以后，词法环境和变量环境是两个独立的环境，但共享同一个outer引用，共同构成执行上下文的环境体系：

- 词法环境负责块级绑定和`let`/`const`等，变量环境负责`var`和函数声明。

- 两者的outer引用指向一致，因此无论是从词法环境还是变量环境向外查找，都会遵循相同的作用域链，最终都指向同一个外层环境（比如同一个全局环境/同一个上层函数环境）。

- 标识符查找时，优先从当前词法环境开始，找不到再沿outer向外，若仍找不到则查找变量环境，最终仍找不到则抛出`ReferenceError`。

### 多层词法环境的运作机制

执行上下文是“运行一段可执行代码”的实例。典型创建时机只有几类：

1. **首次运行脚本/页面**：创建 **全局执行上下文（Global EC）**
2. **执行 ES Module**：创建 **模块执行上下文（Module EC）**
3. **每次调用普通函数**：创建新的 **函数执行上下文（Function EC）**
   - 递归/多次调用 ⇒ 多个函数 EC 实例

> 关键边界：**“进入块”不会创建新的执行上下文；“调用函数/进入模块/进入全局”才会。**

典型场景：进入会产生块级绑定的结构时，**创建/切换词法环境层**，但不新建 EC：

- `{ ... }` 普通块
- `if / else` 语句块
- `for / for...in / for...of`（尤其 `for (let i=...)` 会引入块级绑定）
- `while / do...while`（带块体时）
- `switch`（每个 `case` 的细节较绕，但可理解为在 switch 结构内存在块级环境管理）
- `try { } catch (e) { }`：**`catch (e)` 会引入一个新的块级绑定 e**
- （以及某些带块语义的结构）

> 一句话：**块级结构只“加一层词法环境”，不“加一个执行上下文”。**

通过以下代码示例，可完整理解多层词法环境的形成、切换、查找、遮蔽，以及词法环境与执行上下文的关系：

```javascript
let x = 'G';

function demo(p) {
  let x = 'F';          // 函数层词法环境里的 x（遮蔽全局 x）
  if (p) {
    let x = 'B';        // if 块词法环境里的 x（再遮蔽函数层 x）
    const y = 'Y';
    console.log('1', x, y);  // B, Y
  }

  console.log('2', x);       // F

  {
    const z = 'Z';
    console.log('3', x, z);  // F, Z
  }

  console.log('4', x);       // F
}

demo(true);
console.log('5', x);         // G
```

#### 1. 环境链（outer链）的形成

代码运行过程中，会形成多层词法环境，通过outer引用串联成环境链，从外到内依次为：

- E0：全局词法环境，存储`let x='G'`、函数`demo`等绑定，outer为`null`（最外层环境）。
- E1：函数词法环境，调用`demo(true)`时创建，存储参数`p=true`、`let x='F'`等绑定，outer引用指向E0（外层为全局环境）。
- E2：if块词法环境，进入`if (p)`块时创建，存储`let x='B'`、`const y='Y'`等绑定，outer引用指向E1（外层为函数环境）。
- E3：普通块词法环境，进入第二个`{}`块时创建，存储`const z='Z'`等绑定，outer引用指向E1（外层为函数环境）。

环境链示意：

E2 (if块) → outer → E1 (函数) → outer → E0 (全局)

E3 (普通块) → outer → E1 (函数) → outer → E0 (全局)

#### 2. 词法环境切换与执行上下文的关系

关键点：块级结构仅切换词法环境指针，不创建新的执行上下文；只有函数调用、模块执行、全局脚本执行才会创建新的执行上下文。

- 调用`demo(true)`时，创建一个函数执行上下文（EC_demo），该上下文内部包含词法环境和变量环境，初始时词法环境指针指向E1。
- 进入`if (p)`块时，不创建新的执行上下文，仅将EC_demo内部的词法环境指针切换到E2。
- 离开`if`块时，词法环境指针回退到E1（E2的outer指向）。
- 进入第二个普通块时，词法环境指针切换到E3；离开该块时，指针再次回退到E1。
- `demo`函数执行结束后，EC_demo出栈销毁，其关联的词法环境（E1、E2、E3）若无引用，会被垃圾回收机制回收。

通俗理解：执行上下文（EC）是一栋楼（仅函数调用等场景新建），词法环境层是楼里的楼层（进块上下楼，不新建楼），词法环境指针就是当前所在的楼层。

#### 3. 标识符查找与遮蔽（shadowing）

标识符解析遵循“当前环境优先，沿outer向外查找”的规则，内层同名绑定会遮蔽外层绑定，结合示例中`console.log`的执行过程可清晰理解：

- 打印1（`console.log('1', x, y)`）：当前词法环境为E2，查找`x`时，E2有`x='B'`，直接命中；查找`y`时，E2有`y='Y'`，直接命中，输出“1 B Y”。
- 打印2（`console.log('2', x)`）：离开if块，词法环境指针回退到E1，查找`x`时，E1有`x='F'`，命中，输出“2 F”（E2的`x`被遮蔽，且已不处于当前环境）。
- 打印3（`console.log('3', x, z)`）：当前词法环境为E3，查找`x`时，E3无`x`，沿outer指向E1，找到`x='F'`；查找`z`时，E3有`z='Z'`，命中，输出“3 F Z”。
- 打印4（`console.log('4', x)`）：离开普通块，词法环境指针回退到E1，`x`仍为`F`，输出“4 F”。
- 打印5（`console.log('5', x)`）：`demo`执行结束，函数EC出栈，回到全局执行上下文，当前词法环境为E0，`x='G'`，输出“5 G”。

#### 4. 核心机制总结（必记）

- 每进入一个块级结构，就可能创建一层新的词法环境（环境记录+outer引用），用于存储块内绑定。
- 块级结构不创建新的执行上下文，仅切换当前执行上下文内部的词法环境指针；新执行上下文仅由函数调用、模块、全局脚本创建。
- 标识符解析从当前词法环境开始，找不到则沿outer向外查找，内层同名绑定会遮蔽外层绑定，直至全局环境；仍找不到则抛出`ReferenceError`。
- 离开块级结构时，词法环境指针回退到其outer指向的外层环境；若该层词法环境无任何引用（如E2、E3），执行结束后会被垃圾回收。
- 词法环境管理`let`/`const`等块级绑定，变量环境管理`var`和函数声明，二者共享outer引用，协同支撑作用域查找。

### 同一层outer体系

关键结论：**outer（Outer Environment Reference，外部环境引用）是 Lexical Environment（词法环境）的专属属性**，并非变量环境的属性。

执行上下文（EC）包含两个核心字段，二者均引用某一个 Lexical Environment（规范层面的词法环境对象），且共享同一套 outer 引用规则：

- `LexicalEnvironment`：当前词法环境入口，负责块级绑定（let/const/class等），进入块级结构时会切换指向（如从函数环境切换到块环境）。

- `VariableEnvironment`：函数级 var/函数声明绑定的入口，通常固定指向函数的词法环境（不会随块级结构切换），仅用于定位 var 类绑定的初始位置。

重点澄清：VariableEnvironment 只是 var/函数声明的“绑定入口”，并非独立的“环境体系”，它不会引入一套新的 outer 引用结构——其指向的 Lexical Environment，仍会通过自身的 outer 属性，接入全局的词法环境链。

#### 核心概念：`[[Environment]]` 内部槽位

`[[Environment]]` 是 JS 规范中，**函数对象（及部分可执行对象）的内部槽位**（引擎内部维护，JS 代码拿不到），核心作用是：记录函数被创建（定义）时所处的词法环境，决定函数未来执行时，自由变量查找（闭包捕获）的起始外层环境。

- **存储位置**：存放在函数对象内部，属于函数的“固有属性”，随函数对象创建而存在，随函数对象销毁而消失。
- **设置时机**：函数对象被创建时（执行到函数声明、函数表达式、箭头函数定义时），立即设置，固定不变。

指向一个完整的 Lexical Environment（词法环境）实体，该实体包含两部分：

- Environment Record（环境记录）：存储该词法环境内的所有绑定（变量、函数等）。

- Outer Environment Reference（outer 指针）：指向外层词法环境，形成环境链。

直观理解：函数一“出生”，就会记住自己“诞生”在哪个词法环境里，未来执行时，无论在哪里被调用，查找外层变量都会从这个“诞生环境”开始，这也是词法作用域“定义时确定外层，与调用位置无关”的底层原因。

**【`[[Environment]]`在函数调用时的作用】**

当调用一个函数时，JS 引擎会创建该函数的执行上下文（EC_func），此时`[[Environment]]`会参与环境链的建立，步骤如下：

1. 创建函数执行上下文 EC_func，同时创建该函数的本地词法环境（存储函数参数、局部变量等绑定）。

2. 将“本地词法环境的 outer 指针”，设置为「函数对象的`[[Environment]]`所指向的词法环境」。

3. 形成完整的环境链：本地词法环境 →（outer）→`[[Environment]]`指向的外层环境 →（outer）→ ... → 全局词法环境。

核心意义：函数调用时的外层环境，由`[[Environment]]`固定（定义时确定），与调用位置无关，彻底印证了词法作用域的核心规则。

#### var 声明在块内的查找过程

标识符解析（查找变量/函数）的核心逻辑是：**沿词法环境链（outer 链）逐层查找环境节点，在每个节点上调用 HasBinding 抽象操作，判断该节点是否存在目标绑定，找到则返回，未找到则继续向外，直至全局环境（仍未找到则抛出 ReferenceError）**。

> HasBinding 是定义在 Environment Record（环境记录）上的抽象操作，作用是“判断当前环境记录中，是否存在目标标识符的绑定”，不同类型的环境记录，HasBinding 的实现逻辑不同（无需深入引擎细节，掌握核心规则即可）。

**【代码示例】**（重点理解 var 不具备块级作用域，及 HasBinding 的判断逻辑）：

```javascript
function f() {
  var a = 1;
  {
    var a = 2;
    console.log(a); // 最终输出：2
  }
}
f();
```

执行 `console.log(a)` 时（块内），完整查找步骤：

1. 从当前环境节点（块环境 E_block）开始查找

- 当前词法环境入口指向块环境 E_block（进块时切换），E_block 的环境记录（Environment Record）仅存储 let/const/class 等块级绑定。

- 调用 E_block.record.HasBinding("a")：块内声明的是 var a，var 不属于块级绑定，不会存储在 E_block 的环境记录中，因此返回「false」（未找到 a）。

2. 沿 outer 指针，查找外层环境节点（函数环境 E_f）

- 沿 E_block.outer 指针，指向外层环境节点——函数环境 E_f（函数 f 的词法环境）。

- 调用 E_f.record.HasBinding("a")：var a 是函数级绑定，会存储在 E_f 的环境记录中，因此返回「true」（找到 a）。

- 读取 E_f 环境记录中 a 的当前值（此时块内的 var a = 2 已覆盖函数外层的 var a = 1，值为 2），返回结果，查找结束。

**关键总结**

块环境节点（E_block）不存储 var 绑定，因此 HasBinding 会返回 false；var 绑定属于函数级，存储在函数环境节点（E_f），因此会在函数节点命中，这也是 var 不具备块级作用域的底层原因。

**【代码示例】**（重点理解 let 块级绑定的遮蔽效果，及 HasBinding 的优先级）：

```javascript
function f() {
  var a = 1;
  {
    let a = 2;
    console.log(a); // 最终输出：2
  }
  console.log(a);   // 最终输出：1
}
```

块内 console.log(a) 的查找步骤

- 当前环境节点为 E_block（块环境），调用 E_block.record.HasBinding("a")：块内声明的是 let a，属于块级绑定，存储在 E_block 的环境记录中，返回「true」。

- 直接读取 E_block 中 a 的值（2），查找结束，不会继续向外查找（体现块级绑定的遮蔽效果）。

块外 console.log(a) 的查找步骤

- 当前环境节点为 E_f（函数环境），调用 E_f.record.HasBinding("a")：var a 存储在 E_f 的环境记录中，返回「true」。

- 读取 E_f 中 a 的值（1），查找结束。

关键总结

let 块级绑定会存储在块环境节点的环境记录中，使得 HasBinding 直接返回 true，优先命中块内绑定，遮蔽外层的 var 绑定，这是 let 具备块级作用域的底层原因。

### 词法环境 vs 变量环境

结合前文所有知识点，用“近似口径”（便于理解，贴合引擎实现逻辑）总结二者的关系：

1. 函数执行上下文包含两个入口指针：

   - EC.LexicalEnvironment：当前词法环境入口，进块会切换到块环境节点（E_block），出块会回退到函数环境节点（E_f）。

   - EC.VariableEnvironment：函数级 var/function 绑定的入口，通常固定指向函数环境节点（E_f），不随块级结构切换。

2. 标识符解析的核心逻辑：引擎沿「EC.LexicalEnvironment 的 outer 链」向外查找环境节点，每到一个节点，调用该节点的 HasBinding 操作，覆盖该节点能管理的所有绑定（函数节点可管理 var/function 绑定，块节点可管理 let/const 绑定）。

3. 近似理解：每个环境节点（函数/块）内部，可看作有两个“绑定分区”——块级分区（let/const/class）和 var 分区（var/function）；查找时，先检查当前节点的所有分区，找到则返回，未找到则沿 outer 向外。

**测试：**

```javascript
function outer() {
  var v = 'V_outer(var)';
  let l = 'L_outer(let)';

  function inner() {
    console.log('1)', v); // 读到外层 var v
    console.log('2)', l); // 读到外层 let l

    {
      // 进入块：创建一个新的块级词法环境 E_block（但不会创建新的 EC）
      let v = 'V_block(let)'; // 在块级词法环境里声明 v，遮蔽外层 v
      console.log('3)', v);   // 读到块级 let v
      console.log('4)', l);   // 仍然能读到外层 let l（沿 outer 链向外）
    }

    console.log('5)', v); // 块结束，回到读外层 var v
  }

  inner();
}

outer();
```

输出结果（必记，对应后续逐行解析）：

```text
1) V_outer(var)
2) L_outer(let)
3) V_block(let)
4) L_outer(let)
5) V_outer(var)
```



## 4.对象与作用域/执行上下文的关系

核心结论：对象不会创建新的作用域或执行上下文（除非创建对象时调用了函数），对象带来的是属性/原型链，而非作用域链。

**【对象不会创建新的执行上下文】**

执行上下文仅在以下场景创建：`script`/`module`开始执行、函数调用（包括构造函数调用）。

- 示例1：`const o = { a: 1 };` 仅为表达式求值，不会创建新的执行上下文，也不会入栈。

- 示例2：`new Foo()` 会创建新的执行上下文，因为其本质是一次函数（构造函数）调用。

代码示例：

```javascript
function Foo() {
  // 此处处于Foo的函数执行上下文内
  this.x = 1;
}

const a = {}; // 不创建新执行上下文
const b = new Foo(); // 创建Foo的函数执行上下文
```

**【对象不会创建新的词法作用域】**

词法作用域由`function`、`{ ... }`（配合`let`/`const`/`class`）、模块创建，而对象字面量的`{ ... }`是对象表达式，并非块语句，不会产生块级作用域。

对比示例：

对象字面量（不产生块级作用域）

```javascript
let x = 1;

const obj = {
  x: 2,
  f() {
    let y = 3; // y的作用域在f的函数体块内，不在对象上
    return y;
  }
};

// console.log(y); // ReferenceError：y未定义，说明对象未创建作用域
```

代码块（产生块级作用域）

```javascript
let x = 1;

{
  let x = 2;
  console.log(x); // 2（块级作用域内的x）
}

console.log(x); // 1（外层作用域的x）
```

### 对象属性访问与作用域查找的区别

两者是两套独立的查找系统，极易混淆，需明确区分：

- 作用域链：用于查找标识符（如`x`），遵循“由内到外”的规则，对应词法环境链。

- 原型链：用于查找对象属性（如`obj.x`），遵循“自身→原型→原型链顶端”的规则，与作用域无关。

- 对象不会创建新的执行上下文（除非创建对象时调用了函数，如`new Foo()`）。

- 对象不会创建新的词法作用域（对象字面量的`{}`不是块级作用域）。

- 对象的核心是属性和原型链，与作用域链、执行上下文无直接关联。



## 5.this 与 执行上下文的关系

- this 的指向问题？
- this 的绑定方式？

#### 核心疑问解答

- **this 的指向问题**：this 指向不固定（普通函数），取决于函数的「调用方式」，而非函数的定义位置；箭头函数的 this 特殊，取决于定义时的外层执行上下文 this，与调用方式无关。

- **this 的绑定方式**：分为普通函数的4种绑定规则（按优先级排序）和箭头函数的词法绑定，绑定时机均与执行上下文的创建相关。

- **this 属于执行上下文的一部分吗**：是！this 是执行上下文（EC）的核心属性之一（规范中称为 ThisBinding），与 LexicalEnvironment、VariableEnvironment 并列，是执行上下文的重要组成部分。

- **this 指向外部环境吗**：不指向！this 指向的是函数调用时关联的对象（普通函数）或定义时的外层 this（箭头函数），与作用域链的「外部词法环境」完全是两个独立概念，不可混淆。

#### this 与作用域链的差异

同一个函数体中，作用域链与 this 的行为完全不同，核心差异源于「决定因素不同」，具体对比如下：

- 作用域链（外层变量解析路径）：由函数「定义位置」决定，一旦函数定义完成，作用域链就固定不变，用于自由变量的查找。

- this：普通函数中，this 由函数「调用方式」决定，每次调用函数都会创建新的执行上下文，this 会在此时重新绑定，可能每次调用都不同；箭头函数的 this 由定义时的外层执行上下文决定，定义后固定不变。

#### 普通函数 this 的核心绑定规则

普通函数的 this 绑定，优先级决定了调用时 this 的最终指向，记住以下4条规则即可覆盖所有常用场景（按优先级从高到低）：

#### new 绑定

调用方式：`new F()`（使用 new 关键字调用构造函数）。

this 指向：新创建的对象（即 new 操作符返回的实例对象），与函数本身、外层环境无关。

```javascript
function F() {
  console.log(this); // 指向 new 创建的新对象
}
const obj = new F();
console.log(obj === this); // 函数内部 this 就是 obj 实例
```

#### 显式绑定

调用方式：使用 `call()`、`apply()`、`bind()` 方法主动指定 this。

this 指向：方法中传入的第一个参数（指定的对象）；若传入 null/undefined，非严格模式下会指向全局对象，严格模式下仍为 null/undefined。

```javascript
function f() {
  console.log(this.x);
}
const obj = { x: 10 };

f.call(obj); // 10（this 指向 obj）
f.apply(obj); // 10（与 call 效果一致，参数传递方式不同）
const fBind = f.bind(obj);
fBind(); // 10（bind 绑定后，后续调用均指向 obj）
```

#### 隐式绑定

调用方式：`obj.F()`（函数作为对象的属性被调用）。

this 指向：调用函数的那个对象（即 obj）；需注意「this 丢失」问题——当函数被单独提取赋值后，调用时会失去隐式绑定，触发默认绑定。

示例：隐式绑定与 this 丢失

```javascript
const obj = {
  x: 1,
  f() { console.log(this.x); }
};

obj.f(); // 1（隐式绑定，this 指向 obj）
const g = obj.f; // 提取函数，失去隐式绑定
g(); // undefined（非严格模式，this 指向全局对象，全局无 x）
// 严格模式下，g() 中 this 为 undefined，会报错 Cannot read property 'x' of undefined
```

#### 默认绑定

调用方式：`F()`（函数单独调用，无任何绑定标识）。

this 指向：取决于代码是否为严格模式，与执行上下文的全局环境相关：

- 非严格模式：this 指向全局对象（浏览器中为 `window`，Node.js 中为 `global`）。

- 严格模式：this 为 `undefined`（规范设计，避免全局变量污染）。

```javascript
// 非严格模式
function f1() {
  console.log(this); // window（浏览器环境）
}
f1();

// 严格模式
function f2() {
  'use strict';
  console.log(this); // undefined
}
f2();
```

### 箭头函数：this 走“词法”，非调用时绑定

箭头函数与普通函数的 this 绑定机制完全不同，核心特点：箭头函数没有自己的 this，不绑定执行上下文的 ThisBinding，其 this 来源于「定义时所在的外层执行上下文的 this」，本质是沿作用域链查找外层 this，与调用方式无关。

#### 核心细节

- 箭头函数的 this 定义时固定，后续无论如何调用（call、apply、bind 均无效），都不会改变其指向。

- 箭头函数的 this 查找规则：自身无 this → 沿作用域链向外查找 → 找到外层执行上下文的 this，作为自身的 this。

- 常用场景：解决普通函数的 this 丢失问题（如回调函数、定时器中）。

#### 箭头函数修复 this 丢失

```javascript
const obj = {
  x: 1,
  f() {
    // 箭头函数定义在 f 函数内部，外层执行上下文是 f 的执行上下文
    const arrow = () => console.log(this.x);
    arrow(); // this 继承自 f 调用时的 this（即 obj）
  }
};
obj.f(); // 1（箭头函数 this 指向 obj，修复了 this 丢失）

// 对比普通函数回调（this 丢失）
const obj2 = {
  x: 2,
  f() {
    const normal = function() { console.log(this.x); };
    normal(); // undefined（普通函数，触发默认绑定）
  }
};
obj2.f();
```

### 核心总结

- this 是执行上下文的固有属性（ThisBinding），与 LexicalEnvironment、VariableEnvironment 共同构成执行上下文，每次创建执行上下文时，会同步完成 this 的绑定。

- 普通函数 this 由调用方式决定，每次调用创建新执行上下文，this 重新绑定，遵循「new 绑定 > 显式绑定 > 隐式绑定 > 默认绑定」的优先级。

- 箭头函数无自身 this，其 this 继承自定义时的外层执行上下文 this，与调用方式无关，本质是沿作用域链查找外层 this，常用于解决 this 丢失问题。

- this 与作用域链（outer 链）无关：作用域链用于查找自由变量，由定义位置决定；this 用于确定函数执行时的关联对象，普通函数由调用方式决定，箭头函数由定义时外层 this 决定。

## 6.`var / let / const`

- 什么是变量提升？
- 什么是暂时性死区？

### 变量提升与执行上下文的生命周期

#### 变量提升的过程

执行上下文的生命周期分为三个阶段，变量（var/let/const）的声明、初始化、赋值行为，均对应生命周期的不同阶段，这是三者差异的核心底层原因。

**【创建阶段（Creation Phase）】**

执行上下文创建时，JS 引擎会解析当前作用域内所有变量和函数声明，完成初步初始化，但不同声明方式的初始化行为不同：

- var 声明：会被提升到当前作用域顶部，同时初始化为 `undefined`，存储在当前执行上下文的 VariableEnvironment（变量环境）中。

- let 和 const 声明：会被提升到当前作用域顶部，但**不会进行初始化**，进入「暂时性死区（TDZ）」，存储在当前执行上下文的 LexicalEnvironment（词法环境）中。

**【执行阶段（Execution Phase）】**

执行上下文进入执行阶段后，JS 引擎会按代码顺序执行，完成变量的赋值操作：

- var 变量：此时会将创建阶段初始化的 `undefined` 替换为代码中指定的实际值。

- let 和 const 变量：此时会完成初始化，将声明时指定的值赋值给变量，同时退出暂时性死区，允许被访问。

**【退出阶段（Exit Phase）】**

当函数执行完毕、返回值被处理，或代码抛出异常时，当前执行上下文会从调用栈中移除，其内部声明的变量（var/let/const）会随执行上下文销毁（闭包场景除外）。

#### 示例讲解

```javascript
function outer() {
  var a = 10; // 函数级变量，提升到函数顶部，初始化为 undefined

  {
    var b = 20;   // 块级内的 var 变量，提升到函数顶部
    let c = 30;   // 块级内的 let 变量，只在块内有效
    const d = 40; // 块级内的 const 变量，只在块内有效

    console.log('Inside block: ', a, b, c, d); // 10, 20, 30, 40
  }

  console.log('Outside block: ', a, b); // 10, 20
  // console.log(c); // ReferenceError: c is not defined
  // console.log(d); // ReferenceError: d is not defined
}

outer();
```

**1. 创建阶段（Creation Phase）：变量提升与初步初始化**

当执行到`outer()` 时，JS 引擎会创建 outer 函数的执行上下文（EC_outer），进入创建阶段；后续进入块级作用域时，词法环境会切换，变量的提升和初始化行为也会随之变化，具体拆解如下：

（1）outer 函数执行上下文创建时（未进入块级作用域）

此时执行上下文的两个核心入口（LexicalEnvironment、VariableEnvironment）均指向 outer 函数的词法环境（LE_outer），变量提升行为如下：

- `var a = 10;`：var 变量会被提升到 outer 函数作用域的顶部，同时初始化为 `undefined`，存储在 VariableEnvironment（变量环境）关联的环境记录中（属于函数级绑定）。
- 块级作用域内的 `var b = 20;`：由于 var 不具备块级作用域，仅支持函数级作用域，因此 b 会和 a 一样，被提升到 outer 函数作用域的顶部，同样初始化为 `undefined`，存储在 VariableEnvironment 中。
- 块级作用域内的 `let c = 30;`、`const d = 40;`：此时尚未进入块级作用域，let/const 变量暂未被提升，仅在进入块级作用域后才会触发提升。

（2）进入块级作用域时（切换词法环境）

当执行流进入 `{}` 块级结构时，词法环境会发生切换：执行上下文的 LexicalEnvironment（词法环境入口）会从 LE_outer（函数环境）切换到块级词法环境（LE_block），此时 let/const 变量的提升行为触发：

- var 变量（b）：无新变化，依然是之前提升到 outer 函数顶部、初始化为 `undefined` 的状态——因为 var 不识别块级作用域，块级结构不会改变其提升范围和存储位置。
- let 变量（c）：会被提升到块级作用域（LE_block）的顶部，但**不会进行初始化**，直接进入「暂时性死区（TDZ）」，存储在 LexicalEnvironment（切换后的块级词法环境）关联的环境记录中。
- const 变量（d）：与 let 行为一致，会被提升到块级作用域顶部，不初始化，进入暂时性死区，存储在 LexicalEnvironment 关联的环境记录中。

**2. 执行阶段（Execution Phase）：变量赋值与可访问性**

创建阶段结束后，执行流进入执行阶段，按代码顺序执行赋值操作，变量的可访问性也会在此时确定，结合代码中的打印语句，具体分析如下：

（1）块级作用域内部执行（打印 Inside block）

- `var a = 10;`：执行到该语句时，将创建阶段初始化的 `undefined` 替换为 10，此时 a 的值为 10（函数级作用域，块内可正常访问）。
- `var b = 20;`：执行到该语句时，将创建阶段初始化的 `undefined` 替换为 20，此时 b 的值为 20（虽在块内赋值，但属于函数级作用域，outer 函数内均可访问）。
- `let c = 30;`：执行到该语句时，完成 c 的初始化，将 30 赋值给 c，同时 c 退出暂时性死区，可正常访问。
- `const d = 40;`：执行到该语句时，完成 d 的初始化，将 40 赋值给 d，d 退出暂时性死区，可正常访问。
- 打印结果：`Inside block: 10, 20, 30, 40`——此时四个变量均已完成赋值，且处于可访问状态。

（2）块级作用域结束后执行（打印 Outside block）

当执行流走出块级作用域时，词法环境会从 LE_block（块环境）回退到 LE_outer（函数环境），变量的可访问性随之变化：

- var 变量（a、b）：均为函数级作用域，存储在 VariableEnvironment 中，不受块级结构结束的影响，因此 outer 函数内依然可访问，打印结果为 `Outside block: 10, 20`。
- let 变量（c）、const 变量（d）：均为块级作用域，存储在 LE_block（块级词法环境）的环境记录中；块级作用域结束后，LE_block 会被标记为可回收，c 和 d 随之不可访问，若强行打印会抛出 `ReferenceError`（代码中注释部分可验证）。

### 变量提升的差异

变量提升是指“变量声明被提升到作用域顶部”，但 var、let、const 的提升行为存在明显差异，核心区别在于「是否初始化」和「是否存在暂时性死区」。

#### var 的提升

var 的提升包含「声明提升」和「初始化提升」，是三种声明方式中唯一会自动初始化的类型。

- 声明提升：var 声明的变量，会被提升到当前作用域（函数级或全局）的顶部，无论实际声明位置在代码何处。

- 初始化提升：创建阶段会自动初始化为 `undefined`，因此在声明语句之前访问 var 变量，不会报错，只会得到 `undefined`。

代码示例：

```javascript
function test() {
  console.log(x);  // undefined（var 提升并初始化为 undefined）
  var x = 10;      // 执行阶段赋值
  console.log(x);  // 10（赋值后的值）
}
test();
```

解析：执行上下文创建阶段，`var x` 被提升到 test 函数作用域顶部，初始化为 `undefined`；执行阶段，执行到 `var x = 10` 时，将 x 的值从 `undefined` 替换为 10，因此两次打印结果不同。

#### let 和 const 的提升（暂时性死区）

let 和 const 也会发生声明提升，但**没有初始化提升**，提升后会进入暂时性死区，这是二者与 var 的核心差异之一。

- 声明提升：let/const 声明的变量，同样会被提升到当前作用域（块级）顶部。

- 暂时性死区（TDZ）：从作用域顶部到变量实际声明语句之间的区域，称为暂时性死区；在此区域内访问该变量，会直接抛出 `ReferenceError`，直到执行到声明语句，完成初始化后，才会退出死区。

代码示例：

```javascript
function test() {
  console.log(x);  // undefined（var 提升并初始化）
  // console.log(y);  // ReferenceError: Cannot access 'y' before initialization（处于暂时性死区）
  var x = 10;      // var 执行阶段赋值
  let y = 20;      // let 执行阶段初始化，退出暂时性死区
  console.log(y);  // 20（初始化后可正常访问）
}
test();
```

解析：`let y` 被提升到 test 函数作用域顶部，但未初始化，进入暂时性死区；执行到 `let y = 20` 时，完成初始化，退出死区，因此之前访问 y 会报错，之后访问正常。

#### const 的特别行为

const 与 let 的提升行为完全一致（均有提升、均存在暂时性死区），核心差异在于「可变性」和「初始化要求」：

- 必须初始化：const 声明变量时，必须在声明语句中直接赋值，不能后续赋值（否则抛出 `SyntaxError`）。

- 不可修改：const 声明的变量，一旦赋值，其值不能被修改（基本类型）；若为引用类型（对象、数组），则不能修改引用地址，但可修改内部属性。

代码示例：

```javascript
function test() {
  const z = 30;
  console.log(z);  // 30（初始化后正常访问）
  // z = 40;  // TypeError: Assignment to constant variable.（修改常量报错）

  // 引用类型特例
  const obj = { name: 'test' };
  obj.name = 'newTest'; // 允许修改内部属性
  // obj = {}; // 报错，修改引用地址不允许
}
test();
```

#### let 和 const 的作用域

let 和 const 均支持「块级作用域」，其作用域范围仅限于当前块级结构（`{}`包裹的区域），包括 if、for、while 块及独立块，同时遵循以下规则：

- 块内声明：变量作用域仅限于当前块内，块外无法访问。

- 不可重复声明：在同一作用域内，let 和 const 不允许重复声明同一变量（包括与 var 重复声明），否则抛出 `SyntaxError`。

代码示例：

```javascript
function test() {
  if (true) {
    let y = 20;  // let 声明在 if 块内，作用域为当前 if 块
    const z = 30; // const 同理，作用域为当前 if 块
    console.log(y);  // 20（块内可正常访问）
    console.log(z);  // 30（块内可正常访问）
  }
  // console.log(y);  // ReferenceError: y is not defined（块外无法访问）
  // console.log(z);  // ReferenceError: z is not defined（块外无法访问）
}
test();
```

### let、var 和 const 的重复声明行为

三种声明方式在重复声明的规则上差异明显，核心取决于作用域类型和声明机制。

#### var 允许重复声明

var 允许在同一作用域内重复声明同一变量，后续声明会覆盖前面的声明（包括赋值），不会报错。

代码示例：

```javascript
function test() {
  var x = 10;
  var x = 20;  // 允许重复声明，后面的声明覆盖前面的
  console.log(x);  // 20（输出覆盖后的值）
}
test();
```

#### let 和 const 不允许重复声明

在同一作用域内，let 和 const 不允许重复声明同一变量，无论之前是用 var、let 还是 const 声明，重复声明都会抛出 `SyntaxError`。

代码示例：

```javascript
function test() {
  let x = 10;
  // let x = 20;  // SyntaxError: Identifier 'x' has already been declared（重复声明报错）
  // var x = 30;  // 同样报错，与 var 重复声明也不允许
}
test();
```

### var、let、const 核心差异总结

结合前文解析，从执行上下文、作用域、变量提升、可变性四个核心维度，总结三者差异（无需表格，用文字清晰区分）：

- **作用域**：var 是函数级作用域，作用域覆盖整个函数或全局；let 和 const 是块级作用域，作用域仅限于当前块级结构内。

- **变量提升**：var 提升且自动初始化为 `undefined`，无暂时性死区；let 和 const 提升但不初始化，存在暂时性死区，访问前会报错。

- **重复声明**：var 允许同一作用域内重复声明，后续覆盖前文；let 和 const 不允许同一作用域内重复声明，否则报错。

- **可变性**：var 和 let 声明的变量可修改值；const 声明的基本类型变量不可修改，引用类型变量不可修改引用地址，但可修改内部属性。

- **初始化要求**：var 可先声明后赋值（创建阶段已初始化为 `undefined`）；let 可先声明后赋值（但赋值前处于暂时性死区）；const 必须在声明时同时赋值，否则报错。

## 7.闭包（Closure）

- 什么是闭包？
- 闭包的实现机理？
- 闭包的作用？

闭包是 JavaScript 中核心且高频考点，与前文讲解的执行上下文、词法环境、[[Environment]] 内部槽位、作用域链密切相关，其本质是作用域链与函数 [[Environment]] 共同作用的结果。理解闭包，需先掌握执行上下文生命周期、作用域链维护及内存管理机制，以下从概念、作用、实现原理、代码示例到常见陷阱，逐步梳理。

### 闭包的概念

闭包的核心定义：一个函数（内函数）可以访问并操作其外部函数（外函数）作用域中的变量，**即使外部函数已经执行完毕并返回**。

简单理解：闭包让内函数“记住”了它创建时所处的外函数作用域，即便外函数的执行已经结束，内函数依然能访问外函数中声明的变量、参数，不会因为外函数执行上下文销毁而丢失对这些变量的引用。

关键补充：闭包并非“某个函数”，而是一种**机制**——内函数通过 [[Environment]] 捕获外函数的词法环境，从而实现对於外函数变量的持久访问，这种“捕获-访问”的机制，称为闭包。

### 闭包的作用

闭包的价值源于其“持久化访问外函数变量”的特性，主要应用于三个核心场景，均依赖闭包对於外函数状态的保存能力：

**【数据封装与隐式数据保护】**

闭包可创建“私有变量”：外函数中声明的变量，无法被外函数外部直接访问，但可通过外函数返回的内函数（闭包），暴露对这些私有变量的操作接口（读取、修改），实现数据的隐藏与保护，避免全局变量污染。

典型应用：JS 中模拟私有方法、模块模式，通过闭包将核心逻辑与数据封装在函数内部，仅暴露必要的操作方法。

**【实现函数的工厂模式】**

通过闭包，外函数可接收参数，内函数绑定这些参数并返回，从而生成具有固定行为的函数实例，实现类似工厂模式的效果。

核心逻辑：外函数接收不同参数，内函数通过闭包捕获这些参数，后续调用内函数时，始终基于捕获的参数执行，无需重复传递，实现函数行为的“定制化”。

**【保持外部函数的状态】**

在需要跨多次函数调用保存状态的场景中，闭包尤为实用。内函数通过闭包捕获外函数的变量，每次调用内函数时，操作的都是同一个外函数变量（不会被重置），从而实现状态的持久化。

典型应用：计数器、定时器回调、事件监听器等，需要记住上一次执行的状态，避免使用全局变量保存状态导致的污染问题。

#### 柯里化（curry）

目的：把“多参数函数”拆成“分批传参”，并在多次调用间保存已传参数【函数编程思想】。

```js
function curry(fn, len = fn.length) {
  return _curry(fn, len);
}


function _curry(fn, len, ...arg) {
  return function (...params) {
    const _arg = [...arg, ...params];
    if (_arg.length >= len) {
      return fn.apply(this, _arg);
    } else {
      return _curry.call(this, fn, len, ..._arg);
    }
  };
}


const fn = curry(function (a, b, c, d, e) {
  console.log(a + b + c + d + e);
});


fn(1, 2, 3, 4, 5);      // 15
fn(1, 2)(3, 4, 5);      // 15
fn(1, 2)(3)(4)(5);      // 15
fn(1)(2)(3)(4)(5);      // 15
```

闭包点：`_curry` 返回的函数持有 `arg`（已累积参数）的引用。

#### 节流（throttle）

目的：限制高频触发的执行频率。闭包保存 `timer` 状态。

```js
function throttle(fn, timeout) {
  let timer = null;
  return function (...arg) {
    if (timer) return;
    timer = setTimeout(() => {
      fn.apply(this, arg);
      timer = null;
    }, timeout);
  };
}
```

闭包点：返回函数长期持有 `timer`，跨调用共享同一状态。

#### 防抖（debounce）

目的：事件停止一段时间后再执行。闭包保存 `timer`，每次重置。

```js
function debounce(fn, timeout) {
  let timer = null;
  return function (...arg) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, arg);
    }, timeout);
  };
}
```

闭包点：`timer` 只存在于函数内部，但跨多次触发保持可读写。

#### 函数作为参数（回调）

回调经常“引用外部变量”，自然形成闭包（异步/事件尤其常见）。

```js
function test(fn) {
  fn('done');
}


test(function (msg) {
  console.log(msg);
});
```

如果回调里引用外层变量（例如配置、状态），就会捕获形成闭包。

#### 闭包的注意事项（工程必会）

1. **内存占用**：闭包保留外层环境记录，引用越多保留越多
2. **循环捕获陷阱**：`var` 循环 + 异步常见坑（优先用 `let` 或 IIFE）
3. **释放引用**：不再使用的闭包可置 `null`，帮助 GC（尤其大对象/DOM 引用）
4. **调试识别**：DevTools 的 Scope 面板会出现 `Closure` 区域

### 闭包的工作原理

闭包的实现完全依赖前文讲解的执行上下文、词法环境、[[Environment]] 内部槽位及作用域链，三者协同工作，构成闭包的底层逻辑，核心是“内函数捕获外函数词法环境，实现变量持久访问”。

#### 执行上下文与作用域链的关系

闭包的产生，本质是“函数 [[Environment]] 对於外函数词法环境的捕获”，结合执行上下文的生命周期，可拆解为两个核心前提：

每当调用一个函数，JS 引擎会创建该函数的执行上下文（EC），执行上下文包含词法环境（LexicalEnvironment），用于存储当前函数的变量、参数绑定。当函数执行完毕（return 或执行到末尾），其执行上下文会被从调用栈中移除，正常情况下，执行上下文关联的词法环境也会被垃圾回收，里面的变量无法再被访问。

闭包的特殊之处：若外函数执行完毕后，其内部声明的内函数被返回（或被其他引用），则内函数会通过 [[Environment]] 捕获外函数的词法环境，导致外函数的词法环境无法被垃圾回收——即便外函数执行上下文已销毁，其词法环境依然存在，供内函数访问。

**【作用域链与 [[Environment]] 的核心作用】**

前文已明确：函数对象的 [[Environment]] 内部槽位，会在函数创建时（定义时），记录其所处的词法环境。对于内函数而言，它创建时所处的词法环境，就是外函数的词法环境（外函数的 LexicalEnvironment），因此内函数的 [[Environment]] 会指向外函数的词法环境。

当内函数被调用时，会创建内函数的执行上下文，其本地词法环境的 outer 指针，会指向 [[Environment]] 所记录的外函数词法环境，形成完整的作用域链：内函数本地词法环境 →（outer）→ 外函数词法环境 →（outer）→ 全局词法环境。这就是内函数能访问外函数变量的底层原因。

#### 闭包的工作原理（分步拆解）

结合内存管理、[[Environment]] 捕获、作用域链，闭包的工作过程可拆解为4个关键步骤，清晰体现其核心机制：

1. 外函数被调用：创建外函数的执行上下文（EC_outer），同时创建外函数的词法环境（LE_outer），存储外函数的变量、参数（如 outerVar），LE_outer 的 outer 指针指向全局词法环境。
2. 内函数被定义：在外函数作用域内定义内函数（inner），此时内函数的 [[Environment]] 内部槽位被设置，指向当前所处的词法环境——即外函数的 LE_outer（捕获外函数词法环境）。
3. 外函数执行完毕并返回：外函数执行 return inner，将内函数返回并赋值给外部变量（如 closure）；此时外函数的 EC_outer 从调用栈中销毁，但由于内函数的 [[Environment]] 仍引用 LE_outer（外函数词法环境），LE_outer 不会被垃圾回收，里面的变量（outerVar）依然存活。
4. 内函数被调用：调用 closure()（即内函数 inner），创建内函数的执行上下文（EC_inner），其本地词法环境（LE_inner）的 outer 指针，指向 [[Environment]] 所指向的 LE_outer；内函数访问 outerVar 时，沿作用域链（LE_inner → LE_outer）查找，找到 LE_outer 中的 outerVar 并访问、操作，实现闭包的效果。

#### 闭包的内存模型

闭包的核心内存特征：内函数持有对外函数词法环境的引用，导致外函数的词法环境无法被垃圾回收，外函数中的变量、参数会一直存在于内存中，供内函数后续访问。

关键细节：

- 闭包访问的是外函数变量的「引用」，而非变量的副本——内函数对於外函数变量的修改，会直接改变外函数词法环境中变量的值，后续再次调用内函数，会访问到修改后的值。
- 垃圾回收时机：只有当「所有引用外函数词法环境的内函数」都被销毁（如赋值为 null，无任何引用），外函数的词法环境才会被垃圾回收，里面的变量才会释放内存。
- 闭包并非“内存泄漏”：合理使用闭包是正常的编程技巧，只有不当使用（如长期持有不必要的闭包引用），导致内存无法释放，才会造成内存泄漏。
- 调用 outer() 时，创建 EC_outer 和 LE_outer，LE_outer 中存储 outerVar: 'I am outer'。
- 定义 inner 时，inner 的 [[Environment]] 指向 LE_outer（捕获外函数词法环境）。
- outer() 执行完毕，返回 inner 并赋值给 closure，EC_outer 销毁，但 LE_outer 被 inner 的 [[Environment]] 引用，不会被回收。
- 调用 closure()（即 inner），创建 EC_inner，LE_inner 的 outer 指向 LE_outer，查找 outerVar 时，在 LE_outer 中找到，输出对应值。

**示例2：闭包作为回调函数（状态保持）**

闭包最常用的场景之一，通过闭包保持外函数变量的状态，实现跨多次调用的数据持久化（如计数器）：

```javascript
function createCounter() {
  let count = 0; // 外函数变量（计数器状态）
  return function() { // 返回内函数（闭包）
    count++; // 内函数修改外函数变量
    console.log(count); // 访问修改后的变量
  };
}

const counter = createCounter(); // 接收闭包
counter(); // 输出 1
counter(); // 输出 2
counter(); // 输出 3
```
