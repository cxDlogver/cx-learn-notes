# 清华走航车可视化平台：项目介绍与工作重点

## 1. 项目整体介绍与工作重点

### 【项目背景与我的职责】

车辆在行驶过程中持续采集空气中的多种气体浓度和位置信息，平台通过地图和图表展示行驶轨迹以及气体浓度的变化，并支持历史数据查询与回看。

我主要负责前端实时可视化模块，核心目标是：**在数据持续进入、网络可能波动的情况下，保证实时数据展示的稳定性，同时保持页面交互流畅。**

---

### 【三个核心问题与设计思路】

#### <u>1. 实时连接的稳定性：状态管理、异常检测与分类恢复</u>

第一个问题是，网络异常、连接假活或凭证失效时，页面需要及时感知当前状态，并采取合适的恢复方式。

核心思想是把连接看成一个**WebSocket完整生命周期的状态机**，具体设计包括 WebSocket 握手连接、鉴权、心跳机制及响应超时检测，以及指数退避重连。鉴权采用短期 Access Token 与长期 Refresh Token 配合：访问凭证过期时尝试刷新，刷新成功后重新建立可用的业务连接；权限被撤销或刷新凭证失效时结束自动恢复并提示重新登录。

#### <u>2. 实时数据的可靠性：有序缓冲、确认进度与缺口补偿</u>

第二个问题是，断线恢复、历史补发和实时推送交错时，可能出现业务数据重复、晚到或缺失，导致曲线重复、轨迹回退，或者恢复连接后仍缺少中间一段数据。核心思想是借鉴可靠传输中的序号、确认和补偿思路，在应用层建立可追踪的数据接收进度。

围绕这一思想，可以为数据设置序号或时间游标，利用有界缓冲区去重、暂存尚未连续的数据，按顺序推进消费进度；发现缺口后请求对应区间的数据，断线恢复时从已确认的连续位置继续接收。补偿依赖服务端保留可恢复的数据；超出保留范围时，需要明确标记缺失并重新同步，不能把缺口当作已经完整恢复。

**<u>协议边界：</u>**WebSocket 建立在 TCP 之上，同一连接中的传输顺序不能简单描述成“网络乱序直接传到了页面”。这里需要处理的是应用层的数据顺序、重复和跨连接恢复。[[1]](https://www.rfc-editor.org/rfc/rfc6455.html) 当前重构版可以确认序号缓冲、ACK 和区间补发；“ACK 驱动发送窗口推进”和“ACK 超时后自动重传”尚缺少完整实现证据，因此本段先采用“有序缓冲与确认补偿”的表述。最近几分钟的图表展示窗口也与传输协议的滑动窗口不同。

#### <u>3. 页面渲染的流畅性：生产者与消费者解耦、分帧批量更新</u>

第三个问题是，数据到达具有持续性和突发性，而浏览器处理数据、更新图表和绘制地图都需要消耗时间。网络恢复后的集中补发尤其容易堆积主线程任务，影响地图拖拽、页面交互和绘制节奏。

核心思想是采用生产者—消费者模型，把数据接收与页面渲染解耦：消息先经过规范化、去重和排序进入队列，再通过 `requestAnimationFrame` 按帧分批消费；同时对图表更新限频、合并多次更新，并限制图表时间窗口和地图对象数量，使每次更新的工作量可控。`requestAnimationFrame` 提供重绘前的调度时机，单帧预算还需要覆盖数据处理、状态更新与实际绘制开销。[[2]](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

普通 WebSocket API 不会自动处理接收端背压，因此还需要观察队列长度和积压时间。[[3]](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) 展示层可以合并重复刷新、限制可视范围；需要保留的业务记录仍应由可靠的数据链路保存。图表局部更新等优化应结合实际实现和测量结果说明，不能仅凭采用了分帧队列就认定渲染问题已经解决。

---

### 【如何衡量设计效果】

衡量方式与三个目标一一对应。测试时固定设备、浏览器、数据输入速率、图表数量和展示窗口，分别观察正常持续输入、突发补发、短暂断网、凭证过期及长时间运行等场景。下面是建议采用的指标口径，具体结果需由相同条件下的测试记录支撑。

| 目标 | 核心指标 | 衡量口径与用途 |
| --- | --- | --- |
| 连接恢复 | 异常恢复成功率 | 在网络恢复、权限仍有效的可恢复故障中，规定观察时间内恢复鉴权与业务数据流的次数，占可恢复故障总次数的比例；权限撤销单独验证停止重连行为。 |
| 连接恢复 | 异常检测耗时、恢复耗时 | 分别记录故障发生到识别异常，以及网络恢复到重新收到有效业务数据的时间，关注 P50、P95，定位检测和重连阶段的等待。 |
| 数据可靠性 | 补偿成功率、最终缺失率 | 以服务端已保存且位于可恢复范围内的唯一数据为基准，比较前端最终连续接收的序号；补偿成功率看发现的缺失记录补回了多少，最终缺失率看核对截止时仍缺多少。 |
| 数据可靠性 | 输入重复率、输入乱序率；输出重复与逆序次数 | 对重复数据与首次到达的数据分别统计；首次到达但序号低于此前最大到达序号的记录可计为输入乱序。输入指标描述异常负载，输出指标验证去重与排序效果，不能仅凭输入乱序率下降判断优化有效。 |
| 渲染流畅性 | FPS、帧耗时与长帧情况 | 在前台页面持续更新和地图交互时测量，结合帧耗时分布判断卡顿；rAF 回调频率仅作辅助观察，不能直接等同于实际完成绘制的帧率。 |
| 数据处理能力 | 有效消费吞吐量、队列长度与积压时间 | 统计每秒按序消费的唯一数据条数，并观察队列是否持续增长、最早待处理数据等待了多久，判断消费能力能否跟上输入。 |
| 实时性与资源 | 数据到视图提交延迟、CPU 与内存趋势 | 记录消息到达至页面状态提交的耗时，并结合绘制记录观察可见更新；长期运行时检查 CPU 峰值、内存及地图对象数量。状态提交时间不等于屏幕完成绘制时间。 |
