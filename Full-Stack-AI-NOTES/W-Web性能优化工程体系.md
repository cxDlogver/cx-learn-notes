# Web 性能优化工程体系：内容交付、应用执行与视觉呈现的六大优化领域

Web 性能优化工程体系回答的是**“页面为了交付内容、执行交互和产生画面，需要支付哪些成本，以及可以在哪些环节减少这些成本”**。它不是以 LCP、INP、CLS 或 Smoothness 分章节的指标诊断体系，也不是性能监控、CI 性能预算等质量治理机制。指标与证据帮助判断瓶颈是否存在，但本篇的知识主干是**优化对象及其运行机制**。

Web 页面经历内容交付、应用执行和视觉呈现，三部分形成相互关联的执行链；按具体工程职责进一步分为六个优化领域：

~~~text
                        Web 性能优化方案的工程主线

【第一部分：内容交付优化】——让必要内容更早、更少成本地到达浏览器
  ① 网络传输优化           → 连接建立、请求往返、传输与网络缓存
           ↓
  ② 服务端与数据交付优化   → 页面/接口计算、数据访问与响应生成
           ↓
  ③ 资源加载优化           → 资源发现、体积、优先级与下载/解码
           │
           ▼
【第二部分：应用执行优化】——让浏览器减少无效计算并合理安排工作
  ④ JavaScript 与状态优化 → 解析执行、计算、框架更新、对象分配与 GC
           ↓
  ⑤ 任务调度与更新优化     → 执行时机、优先级、分片、合批与更新控制
           │
           ▼
【第三部分：视觉呈现优化】——让画面变化减少布局、绘制与图形成本
  ⑥ 浏览器渲染优化         → Style、Layout、Paint、Raster、Composite、GPU

【整体约束】
  只有用户需要的结果更早出现、交互更及时、连续画面更稳定，
  并且没有引入不可接受的功能或其他性能代价，才算优化有效。
~~~

这幅图是按**工程职责和主要介入位置**组织的逻辑链，不能理解为浏览器总是严格按 ①→⑥ 各执行一次。HTML 交付和资源请求会交叠，脚本执行与渲染反复交替；运行中还会重新发起网络和数据请求。将网络与服务端分开，是为了区分**传输链路成本**和**业务内容生产成本**，而不是说网络必定在服务端执行之前才发生。[[1]](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work)

## 1. 性能优化方案按照执行职责划分为六个领域

### 【六个领域分别承担不同的优化对象和成本】

| 部分 | 核心优化领域 | 优化对象 | 主要改变的成本 |
| --- | --- | --- | --- |
| 内容交付 | ① 网络传输 | 客户端到服务器或边缘节点之间的通信 | 连接与往返等待、重复传输、传输链路效率 |
| 内容交付 | ② 服务端与数据交付 | HTML、API、SSR 等内容的计算、查询和响应 | 生成时间、数据依赖等待、回源与重复计算 |
| 内容交付 | ③ 资源加载 | JS/CSS/图片/字体等浏览器资源的组织、发现、传输和准备 | 不必要字节、关键资源发现延迟、下载与解码 |
| 应用执行 | ④ JavaScript 与状态 | JS 解析、编译和执行、状态与组件计算、对象管理 | CPU 工作量、重复计算、GC 与内存占用 |
| 应用执行 | ⑤ 任务调度与更新 | 主线程任务及视觉更新的执行顺序、频率和单次规模 | 等待、长时间阻塞、单次峰值和重复更新 |
| 视觉呈现 | ⑥ 浏览器渲染 | DOM/样式、布局、绘制、合成及图形资源 | Layout/Paint/Raster/GPU 成本及视觉更新延迟 |

分类原则是**按当前操作直接改变的对象确定主要归属**。例如 HTTP 缓存用于避免重复网络请求，属于网络层；服务端查询缓存用于复用计算结果，属于服务端层；计算结果缓存属于 JavaScript 层；图形纹理复用属于渲染层。不要因为都叫“缓存”就再建立第七个“缓存优化领域”。

同理，内存管理贯穿页面运行，却不单独占一个一级领域：JavaScript 对象分配与 GC 放在 ④，任务与订阅清理放在 ⑤，DOM 和 GPU 资源的复用、销毁放在 ⑥，网络和服务端缓存分别放在 ①、②。

### 【各领域共享五种成本优化原理，而不共享一套固定技术清单】

从机制上看，大部分优化方案都可以解释为以下几种成本变化：

| 通用原理 | 解释 | 不同领域的表现 |
| --- | --- | --- |
| 减少必要工作总量 | 完成同样结果所需的字节、计算、对象或绘制工作减少 | 压缩传输、减少查询、删除无用 JS、减少布局节点 |
| 缩短关键依赖路径 | 关键内容无需等待非关键操作，必要工作可以更早开始 | 避免请求串行、提前提供 HTML、尽早发现首屏资源 |
| 复用已经完成的工作 | 不重复获取、计算或绘制未变化的结果 | HTTP 缓存、服务端缓存、Memoization、图层缓存 |
| 控制执行时机和峰值 | 非紧急工作不占用关键展示或交互时刻 | 资源优先级、任务让步、分段更新、按需执行 |
| 控制资源占用及生命周期 | 避免缓存、对象、监听与图形资源无界积累 | TTL/淘汰、组件卸载清理、释放 Buffer 与纹理 |

这些原理不是七、八个新技术分组，而是解释**“为什么优化有效”**的稳定依据。某项方案可能同时应用多个原理，例如代码分割同时减少初始下载与执行工作，并改变加载时机；缓存通常以空间换时间，并需要失效和版本控制。

### 【六大领域与用户体验指标之间是多对多关系】

LCP、INP、CLS 和持续流畅度描述用户体验的结果；它们不是本工程体系的一级优化领域。同一种优化可能影响多个结果，而同一指标恶化也可能来自多个领域。

例如减少阻塞脚本的主线程工作，既可能改善 LCP 元素的呈现等待，也可能减少交互输入等待；避免图片加载后改变布局，有助于 CLS；缩小组件提交和 Paint 范围，有助于下一帧反馈与连续动画。

因此使用本体系时，应从已经得到证据支持的成本出发选择六大领域之一或跨领域组合方案。无需在本文重新叙述四类指标的全部采集、阶段归因和治理流程。

## 2. 网络传输优化降低连接、往返和重复传输成本

### 【网络层管理请求如何在浏览器、网络与边缘/源站之间到达】

一次请求的总体时间可能涉及 DNS 查询、连接建立、TLS 握手、请求发送、网络往返与响应字节传输。浏览器对连接复用、缓存命中、协议协商与网络调度具有自己的规则。网络优化首先改变的是**这些链路成本**，而不是替服务端减少业务计算量。

~~~text
浏览器准备发出请求
      ↓
是否能够从适用的缓存复用响应？
  ├─ 可以 → 避免或减少必要网络往返
  └─ 不可以 → 选择可用连接或建立连接
                      ↓
               DNS / TCP / TLS（依情况而定）
                      ↓
               发送请求与网络往返
                      ↓
               接收响应字节并交给浏览器
~~~

缓存、连接与协议行为受当前浏览器、HTTP 版本、跨域策略和响应头控制；并非每次请求都必然发生 DNS、TCP、TLS 全过程。更详细的 HTTP 缓存机制见 [CDN 缓存与浏览器缓存笔记](./C-CDN缓存与浏览器缓存笔记.md)。

### 【减少往返和连接建立开销要先确认时间花在哪里】

常见工程方向：

- **减少不必要的串行网络依赖**：若后续请求并不依赖前一请求的结果，应减少人为串行等待；但需要控制并发竞争，不是越多并发越快。
- **正确利用连接复用与协议能力**：HTTP/2 和 HTTP/3 支持复用多个请求流，但不能保证消除所有排队、拥塞或服务端处理瓶颈；网络版本选择应结合实际平台与客户端支持。
- **边缘与就近交付**：使用 CDN 缩短静态资源从源站到用户的地理路径，减少回源及传输延迟；若源站响应慢或缓存不命中，仍要回到服务端分析。
- **预连接提示（preconnect）**：当关键跨域源确定会被较早使用，而且连接建立延迟明显时，可以提前安排连接；若滥用预连接，反而消耗带宽、电量或连接资源。[[2]](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preconnect)

下面示意只对确实承载关键资源的域名提出连接提示：

~~~html
<!-- 仅当该第三方域名确实承载关键资源时使用 -->
<link rel="preconnect" href="https://static.example.org" crossorigin>
~~~

它有助于**可能发生的连接准备**，不会让图片、脚本本身更小，也不代表服务器执行时间缩短。应观察连接阶段及最终关键资源获取时刻，而不是单独把它当作 LCP 改善的保证。

### 【网络缓存的职责是避免重复传输，而不是替代内容计算】

HTTP 缓存的核心是利用已经取得的响应。需要区分浏览器私有缓存、CDN 等共享缓存、未过期响应复用及过期后的条件验证：

| 方案 | 减少的成本 | 重要约束 |
| --- | --- | --- |
| 可缓存静态响应 | 重复请求和传输 | 内容需要正确版本化并允许复用 |
| 内容哈希文件名 + 较长新鲜期 | 版本固定资源的重复传输和重新验证 | HTML 必须更新引用，新旧资源发布衔接要稳定 |
| ETag / Last-Modified 验证 | 过期时重复传输完整响应正文 | 仍可能需要一次往返，不是完全无请求 |
| CDN 缓存 | 用户到源站的请求与跨区域传输 | Cache Key、Vary、鉴权、个性化响应、安全范围 |
| stale-while-revalidate | 允许在特定条件下先使用陈旧响应并异步验证 | 用户可接受的陈旧时长、实现与缓存策略 |

示意：

~~~http
Cache-Control: public, max-age=31536000, immutable
~~~

这种长期新鲜度设置只适用于**URL 对应内容不会被原地修改**的版本化资源；不应套用到会动态变化、包含个性化敏感数据的 HTML/API。MDN 对 Cache-Control、条件验证与 immutable 的行为有独立说明。[[3]](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

### 【网络优化的边界是传输能力而非全部页面性能】

网络请求快不代表浏览器有足够时间解析 JS、更新 DOM 或绘制画面。资源加载优先级、图片体积属于 ③ 的主职责；服务端生成响应慢属于 ②。诊断时可利用 Network Waterfall、DNS/Connect/SSL、Waiting、Download、传输字节和缓存命中判断该领域是否值得优化。

本领域还可进一步进入 [CDN 缓存与浏览器缓存笔记](./C-CDN缓存与浏览器缓存笔记.md) 和 [静态资源预加载方法](./J-静态资源预加载方法及实践笔记（完整版）.md)；前者解决缓存与版本规则，后者涉及资源提示，其中真正的 preload/fetchpriority 选择归入 ③。

## 3. 服务端与数据交付优化缩短内容生成和必要数据依赖

### 【服务端优化的对象是响应内容的生产与组织方式】

客户端网络再快，如果服务器仍须串行读取多个数据源、执行耗时计算、同步组装完整页面才能返回首字节，关键内容仍会推迟出现。

~~~text
浏览器发起页面 / API 请求
         ↓
服务端路由匹配与请求上下文
         ↓
获取页面需要的数据（数据库、缓存、下游服务）
         ↓
执行必要业务逻辑与页面/数据序列化
         ↓
输出 HTML、Payload 或 API 响应
         ↓
浏览器继续解析和执行
~~~

这是一条**逻辑职责链**；真实系统中的缓存、并发查询、流式响应可以改变执行顺序。判断成本时要区分“服务端响应首字节何时到达”与“整份内容何时结束生成与传输”，不能把 TTFB 当作全部 Server Time。

### 【页面生成策略通过改变计算时机重新分配成本】

CSR、SSR、SSG、Hybrid Rendering 不是简单的“越后出现越先进”，而是让相同页面内容在不同阶段生成：[[4]](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path)

| 策略 | 页面内容的主要生成位置 | 能减少的某类成本 | 新增或转移的成本 |
| --- | --- | --- | --- |
| CSR（客户端渲染） | 浏览器获得 JS 后组装页面 | 服务端页面 HTML 生成相对简单 | 首屏可能需要等待更多 JS 和数据 |
| SSR（服务端渲染） | 每次请求时先在服务端输出 HTML | 可更早交付可见首屏结构 | 服务端计算与数据依赖、客户端 Hydration |
| SSG / Prerender（预生成） | 构建时提前生成页面结果 | 可减少请求时页面生成工作 | 构建、内容更新和部署失效管理 |
| Hybrid（按路由选择） | 不同页面使用不同生成策略 | 按页面内容新鲜度分配成本 | 配置、缓存和运行边界复杂 |

**SSR 不保证 LCP 必然更好，SSG 不保证数据永远准确，CSR 也并非一定性能差。** 是否值得采用取决于首屏内容是否可提前确定、数据是否可安全复用、个性化程度和需要支付的客户端工作。

完整渲染策略关系参见 [Web 渲染架构](./W-Web渲染架构.md)，SSR 数据依赖与 HTML/Payload/Hydration 的具体分工参见 [服务端渲染完整链路](./F-服务端渲染完整链路.md)。

### 【数据访问优化首先减少关键查询依赖和重复计算】

服务端优化不限于页面 SSR，还包括普通 API、BFF（面向前端的后端聚合服务）及数据交付：

- **缩短请求关键路径**：避免同步等待非必要的数据或串行执行相互独立的查询；首屏必要数据与非关键数据可按业务可见性分开。
- **降低数据访问成本**：对有证据的慢查询优化索引、执行计划、连接池、数据量和查询次数；不能把“加索引”当成所有慢接口的固定答案。
- **避免重复请求与 N+1 查询**：适用时批量取数、聚合接口或复用同一请求期间已经取得的结果；但巨型聚合接口可能放大单次响应和耦合。
- **控制传输模型**：响应只包含需要的字段与当前场景必要数据，减少重复 JSON 序列化和冗余 Payload；不能为了少传字段破坏业务数据正确性。
- **复用可共享结果**：服务端数据/页面缓存可以避免重复计算，却必须考虑身份隔离、失效条件、版本一致性和可容忍陈旧时间。

这里的“服务端缓存”主要减少**生成结果的计算或查询**，虽然也可能进一步配合 HTTP 缓存影响网络层，但责任边界依实际缓存位置划分，不应混淆它们的更新语义。

### 【流式和分阶段响应优化关键可见内容的到达顺序】

当必须在服务端完成全部工作才能返回 HTML 时，慢数据源可能使所有内容被迫等待。支持流式响应的技术可以在适用条件下先交付已经准备好的内容，随后交付剩余部分，缩短重要内容的等待。

但流式输出**并不会自动降低总服务器计算成本**，也不保证最终 LCP 更好：如果 LCP 元素依赖的部分仍然晚到，或者客户端渲染、Hydration 和 CSS 尚未就绪，就可能只是移动了等待位置。

决策应该围绕三件事：最初能否输出可用内容、后续数据是否会影响布局稳定性、客户端是否需要承担额外 Hydration/JavaScript 工作。

### 【服务端交付效果必须与客户端成本一起衡量】

本领域直接关注 Server Timing、关键查询耗时、请求间依赖、HTML 生成与输出时刻；对最终用户仍要检查 LCP、接口可用性、Hydration 与缓存新鲜度。把 ② 优化到极致可能把过多工作挪到 ④，因此这两处需要协同设计，而不是两边分别宣称“处理更少”。

## 4. 资源加载优化改变资源体积、发现顺序和必要下载范围

### 【资源层的核心不是“下载尽可能少”，而是“及时获取必要资源”】

HTML、CSS、JavaScript、图片和字体在浏览器中各自承担不同工作。资源的性能成本至少包括：

~~~text
某项资源的实际使用成本
   = 是否进入关键路径
   + 何时被浏览器发现
   + 请求优先级与传输字节
   + 解压、解析、解码或编译成本
   + 使用它之前的依赖等待
~~~

网络层主要解决怎样传；资源层重点决定**哪些资源需要传、何时被发现、必须传多少、拿到后如何准备**。对首屏关键资源与非关键资源采用相同的懒加载策略，可能使用户最关心的内容反而更晚出现。

### 【提前发现关键资源与延迟非关键资源必须同时成立】

| 优化方法 | 主要减少的成本 | 正确选择与限制 |
| --- | --- | --- |
| 初始 HTML 中可发现关键图片 | 避免等待客户端 JS 才开始请求 | 必须确定它确实是当前首屏的重要资源 |
| preload（预加载） | 对隐藏在 CSS/JS 中、但必须较早使用的资源提前发起获取 | 过多会抢占带宽；as、type、crossorigin 等需匹配 |
| fetchpriority（请求优先级提示） | 让确实重要的资源获得更合适的调度优先级 | 它是提示而不是完全强制调度，也不改变字节大小 |
| preconnect（预连接） | 提前准备后续要用的跨域连接 | 属于网络连接准备，正文归 ①；资源层仅说明使用时机 |
| async / defer / module | 避免或调整脚本对 HTML 解析与执行的阻塞 | 不等于脚本永远不耗 CPU；需要理解相应执行顺序 |
| 动态 import 与按需加载 | 首次访问不必下载/执行非关键功能 | 不要把马上要交互的必要功能延迟得太晚 |
| below-the-fold 图片 lazy loading | 避免屏幕外图片占用首屏带宽 | **不要给关键 LCP 图片套不必要的 lazy loading** |

HTML 示例：

~~~html
<!-- 关键首屏图片：允许浏览器尽早发现 -->
<img src="/hero.webp" width="1200" height="640"
     fetchpriority="high" alt="页面主视觉">

<!-- 非关键的屏幕外图片：按需加载 -->
<img src="/below.webp" width="800" height="600"
     loading="lazy" alt="后续内容">
~~~

宽高或稳定的长宽比同时能帮助浏览器预留布局空间，但这属于与 ⑥ 的交叉影响，不代表图片提前加载等于自动解决 CLS。Chrome/web.dev 明确将 LCP 资源的发现时机和优先级视为 Resource Load Delay 的重要影响因素。[[5]](https://web.dev/articles/optimize-lcp) [[6]](https://web.dev/articles/fetch-priority)

资源提示的机制、缓存键和适用条件可继续阅读 [静态资源预加载方法及实践笔记](./J-静态资源预加载方法及实践笔记（完整版）.md)。

### 【图片、字体和媒体优化需要同时考虑字节与最终显示】

图片优化不能只看源文件大小：

- 响应式尺寸和 srcset/sizes 使实际设备得到与显示需求匹配的图片，而非统一下载过大的源图。
- 编码格式、压缩质量、裁剪和合理分辨率影响网络字节，也要注意解码 CPU、透明度、动画、兼容性及视觉质量。
- 图片宽高或 aspect-ratio 应尽早确定，避免完成加载后重新分配布局空间。
- 字体子集化、按需字体文件和 font-display 策略可以减少字体等待，但不适当的字体替换也可能改变文本宽度与布局。
- 视频、动画资源需要区分预览内容、封面图、自动播放、解码与实际观看需求，避免抢占首屏关键资源。

这些策略既改变 Resource Load Duration，也可能改变浏览器解码、布局和绘制成本；需要看整体结果，不要把“图片格式更先进”当成默认最优答案。

原有 [资源优化实战](./Z-资源优化实战.md) 包含资源压缩、请求优化、资源缓存、浏览器存储和字体处理材料。本篇给出分类与机制；该文档保留实施细节，而不是复制所有配置项。

### 【JavaScript 与 CSS 构建优化要减少实际下载和执行的必要代码】

构建工具通过 Tree Shaking（移除可证明未使用的模块代码）、Code Splitting（按入口或动态边界拆包）、Minification（缩减源码表达）和压缩输出等方式改变资源体积、加载边界及浏览器后续执行工作。

- Tree Shaking 是否有效取决于模块结构、副作用声明和构建工具行为，不能只看源码是否使用了 ESM。
- 代码分割减少初始必须下载和执行的功能，但若把关键功能拆成等待链，也可能增加额外请求与关键路径等待。
- JS Bundle 体积下降并不保证解析/编译/执行时间等比例下降；仍要区分字节、模块数量、运行时初始化和任务耗时。
- CSS 同样需要减少无效样式、控制首屏阻塞与复杂度；盲目内联全部 CSS 会增加 HTML 体积和缓存重复成本。

例如动态 import 将一个非关键功能延后加载：

~~~js
async function openOptionalEditor() {
  // 用户确实需要编辑时才加载模块。
  const { mountEditor } = await import('./optional-editor.js');
  return mountEditor();
}
~~~

这段代码表明“把可延后的功能从启动路径移开”，并不保证编译器一定生成理想分包，也不适用于用户进入页面时马上需要编辑的场景。实际 Chunk 边界和大小需以构建产物为准。Vue 官方将代码分割及组件更新范围优化分别列为加载与更新性能策略。[[7]](https://vuejs.org/guide/best-practices/performance)

更完整的构建策略见 [编译构建与打包全面优化](./B-编译构建与打包全面优化.md)，其中构建速度与**线上运行性能**需要区分：提高本地 HMR 或构建时间不等于用户页面更快。

## 5. JavaScript 与状态优化降低实际执行与对象管理成本

### 【应用执行的成本来自启动、业务计算和状态更新三类工作】

浏览器获得 JS 文件后还需要解析、编译、执行模块，应用运行后还要处理业务数据、响应式状态以及组件计算。**资源的字节数是 ③ 的直接优化对象，实际运行的 CPU 工作属于 ④**；减小 Bundle 可能改善执行，但二者不保证等比例变化。

~~~text
浏览器取得 JS 资源
     ↓
解析 / 编译 / 模块初始化
     ↓
应用和 Hydration 启动
     ↓
用户操作 / 网络数据 / 定时逻辑触发状态变化
     ↓
业务计算与状态依赖求值
     ↓
框架计算哪些组件需要更新
     ↓
向 DOM 或绘图系统提交必要变化
~~~

在这条链上，④ 的目标是**减少必须执行的代码量、重复计算与无效状态变化**。何时执行这些工作、是否让出主线程属于 ⑤；浏览器如何做 Layout/Paint 属于 ⑥。

### 【减少启动执行要区分“初始必须运行”和“可在使用时激活”】

启动优化不仅是 Tree Shaking 和代码分割。即使网络资源已下载，脚本仍可能在启动期同步初始化大量状态、构造缓存、绑定监听器、执行第三方插件、完成 Hydration。

- 首屏必须的核心交互逻辑应尽早准备，但非关键编辑器、分析模块或功能插件可以按需初始化。
- 删除重复初始化、重复解析和构造未使用模块的工作，比仅改变它们的执行顺序更直接。
- SSR/SSG 可让 HTML 更早出现，但客户端仍可能承担 Hydration；不能把服务端输出成功当作交互完全就绪。
- 第三方脚本也占执行预算，需要判断是否必须位于关键路径，是否可以延后或有更轻的替代方案。

具体的页面生成/Hydration 边界见 [Web 渲染架构](./W-Web渲染架构.md) 和 [服务端渲染完整链路](./F-服务端渲染完整链路.md)。Vue 官方也把加载阶段的代码分割与运行阶段的状态更新性能分别讨论。[[7]](https://vuejs.org/guide/best-practices/performance)

### 【计算优化从复杂度、变化范围和复用已计算结果入手】

假设某个状态每次改变一个元素，却让程序重新遍历全部数据：

~~~text
全量更新方式：
  N 个对象 → 一个对象发生变化 → 对 N 个对象重新计算

增量计算方式：
  N 个对象 → 识别变化集合 Δ → 只处理 Δ 及受其影响的依赖
~~~

能够减少工作量的方案包括：

1. **减少复杂度**：采用更适合查询模式的索引、Map/Set、预计算与合适的数据结构，不在每次关键路径上做重复排序和搜索。
2. **缓存稳定结果**：对相同输入复用计算结果，但缓存依赖和失效规则必须正确；缓存命中率低时可能白白增加对象驻留。
3. **增量计算**：根据变化集合更新衍生数据，而非重新处理所有记录；维护增量状态有自己的同步和一致性成本。
4. **减少中间转换**：避免同一数据在不同组件反复过滤、序列化、映射；统一必要的规范化输入。
5. **调整业务工作集**：只计算当前确实需要呈现或处理的内容；完整数据保存与活动计算范围不必相同。

算法优化的效果应在相同输入规模下比较 CPU 耗时和正确性。如果每次输入都全量变化，增量维护未必更划算。

### 【响应式和组件性能的核心是缩小受影响的更新集合】

组件或状态更新次数过多，往往不只是函数执行慢，而是**原本不变的消费者也被安排重新计算**：

- 缩小状态依赖范围，不让高频变化的全局状态不必要地通知整个页面。
- 使用稳定的 Props 和状态语义，避免父组件的无关变化导致大量子组件更新。
- 在有明确计算成本时使用 Memoization 或框架提供的稳定化能力；缓存同样要管理失效和内存。
- 大列表先减少应用层的无效计算，浏览器层再通过虚拟化减少实际参与 DOM/Layout 的节点。
- 避免无意义的重复状态提交；何时合并和让出执行机会交给 ⑤ 处理。

Vue 的 Props Stability、v-once、v-memo 等是框架特例，背后的通用机制是**减少不必要的组件更新**；不要直接把某个 API 当作所有框架通用的性能规则。[[7]](https://vuejs.org/guide/best-practices/performance)

深入入口：[Vue 应用级性能分析及优化](./V-Vue应用级性能分析及优化.md)、[动态高虚拟列表报告](./D-动态高虚拟列表_报告.md)。

### 【内存分配、GC、对象缓存与存活引用属于 JavaScript 执行优化】

这里**不再建立独立的内存与生命周期优化层**。应用层内存管理本质上关系到分配 CPU 成本、垃圾回收以及长期状态规模带来的计算开销。

| 成本类型 | 为什么影响性能 | 解决方式及边界 |
| --- | --- | --- |
| 高频临时分配（Allocation Rate） | 创建对象耗 CPU，可能更频繁触发年轻代 GC | 减少无意义复制和中间数组，不以“零分配”为目标 |
| 长期存活对象过多（Live Set） | GC 可能需要处理更多对象；保留数据本身也可能扩大每次计算 | 明确缓存容量、失效和引用生命周期 |
| 已失效对象仍被引用 | 组件已卸载但闭包、监听器、缓存继续保留对象 | 释放多余引用与订阅，检查 Retainers |
| 数据规模增长导致重复工作 | 即使 GC 不明显，每次业务计算也可能越来越重 | 增量计算、索引、限制活动工作集 |
| 盲目使用对象池 | 降低部分创建成本，却可能增加长期存活规模 | 只有在 Profile 证明收益时使用 |

V8 使用分代、增量和并发 GC，因此 Heap 较大不意味着一定会卡顿；要区分 Allocation Rate、GC 暂停与业务数据增长导致的 CPU 工作。[[8]](https://v8.dev/blog/trash-talk)

JS 对象/订阅的引用清理属于本领域；**持续定时任务何时停止执行**还涉及 ⑤，**Canvas/GPU 资源的创建与释放**则放在 ⑥。这些内容按照对象所处的执行职责分布，不再另设“资源生命周期优化”一级章节。可继续阅读 [V8 引擎原理笔记](./J-JavaScript V8引擎原理详解笔记.md) 和 [Smoothness / GC 专项](./drafts/Smoothness-持续渲染流畅度指标与性能诊断体系-草稿.md)。

### 【减少工作量与让出执行权的差别必须保持清晰】

假设一个计算原来用 100ms，通过更好的算法和复用降到 30ms，是**降低计算成本**；若还是总共计算 100ms，但拆分成多段允许主线程处理交互，则主要属于**改变执行时机**，并不保证总体 CPU 更少。

这两种方案都可能让用户感觉更流畅，但机理不同。减少对象分配不能破坏框架不可变状态语义；多做 Memo 也可能增加内存与失效维护成本。④ 的优化应围绕工作总量和对象正确性证明有效。

## 6. 任务调度与更新优化控制执行顺序、更新频率和单次峰值

### 【任务调度关注的是“什么时候执行”和“是否占用关键时刻”】

浏览器主线程需要处理 JavaScript Task、Microtask、用户交互及部分渲染工作。即使每个计算本身都必要，如果连续执行时间过长，也可能推迟下一次输入或绘制机会。因此调度优化主要改变**任务执行时机、优先级、让步机会、触发频率和单次工作规模**，而不是让算法凭空变快。

~~~text
待执行工作：
   用户输入 / 关键视图更新 / 计算任务 / 后台统计
                          ↓
按照业务语义判断优先级和截止时间
           ┌──────────────┼──────────────┐
           ▼              ▼              ▼
     必须及时处理      必须处理但可让步      可以延后
           ↓              ↓              ↓
       优先执行       分片 / Yield      适时或空闲运行
           └──────────────┼──────────────┘
                          ▼
               重要输入和视觉更新及时获得机会
~~~

⑤ 与 ④ 的关键差别是：④ 减少计算和组件更新**实际要做的工作**，⑤ 决定这些工作**怎样安排而不阻塞更紧急的任务**。因此优先减少无意义工作，再考虑切分或调度有必要的工作。[[9]](https://web.dev/articles/optimize-long-tasks/)

### 【先缩短长任务，再对可分片工作让出执行权】

最常见的错误是把 Promise、async/await 当成自动防止主线程阻塞的工具。一个同步函数即便写在 async 内部，在遇到真正的让步点之前仍可能占用主线程。

- **删除**：避免过期任务、无效轮询和重复计算。
- **缩短**：降低任务中不可中断部分的计算量。
- **Yield（主动让出）**：在非紧急且可中断的阶段划分工作，让更高优先级输入或绘制有机会执行。
- **转移**：CPU 密集、无需直接 DOM 操作的工作可以考虑 Worker，代价是线程资源和数据通信。
- **取消**：页面已经切换或结果过期时，不再继续消耗资源计算已经没有意义的工作。

概念代码：

~~~js
// 可逐块处理的任务；批次大小应由真实单次 CPU 成本决定。
async function processChunks(items, processOne) {
  for (let start = 0; start < items.length; start += 40) {
    const end = Math.min(start + 40, items.length);
    for (let i = start; i < end; i++) processOne(items[i]);

    // 在支持的浏览器中主动让出；需要按兼容性提供降级。
    if (globalThis.scheduler?.yield) {
      await globalThis.scheduler.yield();
    } else {
      await new Promise(resolve => setTimeout(resolve, 0));
    }
  }
}
~~~

它只说明“允许浏览器在任务之间执行其他工作”，并不意味着 40 是最佳分片，也不保证执行总耗时下降。真正业务处理可能需要保序、取消、事务原子性或错误恢复，必须保留这些约束。

### 【不同调度 API 的职责不能混用】

| 调度能力 | 适合的工作 | 风险与边界 |
| --- | --- | --- |
| requestAnimationFrame（rAF） | 下一次绘制前准备相关的动画/视觉状态 | rAF 仅提供调度机会，不会自动拆短同步计算 |
| Task / setTimeout | 一般延迟、分片后继续执行 | 不具备精确帧语义，计时器可能受后台限频 |
| scheduler.postTask / scheduler.yield（可用时） | 按优先级安排或主动让步的任务 | 依赖目标浏览器支持，必须考虑降级 |
| requestIdleCallback | 非紧急、可等待的后台工作 | 触发时机不确定，不能承诺关键交互截止时间 |
| Web Worker | 不需要直接访问 DOM 的 CPU 密集工作 | 消息传输、序列化、内存以及最终 UI 提交仍有成本 |
| Microtask / Promise 回调 | 当前 Task 完成之后的短续接工作 | 无界 Microtask 链可能妨碍浏览器获得渲染机会 |

rAF 是刷新前的回调，不表示画面最终已经被 GPU 呈现；把耗时循环从 click 回调移动到 rAF 并不能令它消失。[[10]](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

这一层的正式深入文档为 [浏览器主线程、Event Loop 与任务调度完整知识体系](./B-浏览器主线程Event Loop与任务调度完整知识体系.md)，不在本篇重复整个事件循环模型。

### 【批量、节流、增量和背压分别改变不同的工作成本】

当状态变化密集出现时，需要同时考虑**单位时间工作总量**和**一次连续执行的峰值**：

| 策略 | 主要减少或控制什么 | 不适用时的风险 |
| --- | --- | --- |
| Batch（合批） | 减少多次提交的固定成本 | 批次过大，单次处理反而超过帧预算 |
| Throttle（节流） | 限制持续事件触发处理的频率 | 忽略了需要逐条处理的事件 |
| Debounce（防抖） | 将一串连续输入收敛为一轮最终处理 | 持续输入时结果可能长期不更新 |
| Incremental（增量） | 减少对未变化数据与视图的重复计算 | 需要正确识别变化范围和失效条件 |
| Backpressure（背压） | 防止工作输入长期超过处理容量 | 不能随意丢失重要业务数据 |
| Cancellation（取消） | 避免过期任务和订阅继续执行 | 必须维护完成状态、清理和副作用安全 |

例如更新合批可能降低每秒视图提交次数，但如果单次 Batch 使某次 rAF 回调执行 70ms，画面仍可能明显卡顿。正确的批次设计不只是降低次数，还需要使关键单次工作量留在预算内。

增量计算本身的计算成本属于 ④，最终图形增量更新属于 ⑥，而**何时取出变化并安排提交**是 ⑤ 的核心。对于高频数据，还要检查处理队列是否持续积压；表面 FPS 正常不代表最新内容已经及时显示。

### 【自适应更新属于反馈控制手段，不是通用的首次优化】

负载和设备能力变化时，可以用任务耗时、帧压力、积压长度和数据新鲜度作为反馈信号，小幅调整工作频率或批量。但这种策略有明确边界：

- 需要滞回、冷却与渐进恢复，避免档位反复振荡；
- 必须保持交互响应和重要数据时效，而不是为了 FPS 数字无限降级；
- 如果单次工作的实际成本随数据规模上升，长期只降低输入频率不能替代增量计算和渲染优化。

更深入的测量与更新控制案例见 [页面流畅度与连续渲染性能完整知识体系](./Y-页面流畅度与连续渲染性能完整知识体系.md)。其工作负载参数与案例不应上升为所有 Web 页面都需要的通用控制模型。
