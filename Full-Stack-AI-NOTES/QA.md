# QA 索引连接提问方式、回答框架与继续学习路径

QA 是 `Full-Stack-AI-NOTES` 的“问题视图”，不是聊天记录，也不是第二套知识库。每条 QA 对应一套可以复用的回答知识框架：同一个知识点可以有不同提问方式，但只要核心分析路径一致，就归入同一条记录。

正式回答问题时仍遵循：

```text
知识体系索引.md
   ↓ 定位主题和前置知识
QA.md
   ↓ 找到已有回答框架与可继续追问方向
相关知识 Markdown
   ↓ 阅读完整正文
source/ / resource/
   ↓ 按需读取实现和附件
外部权威资料
   ↓ 核验变化事实和关键结论
```

QA.md 重点回答四件事：

```text
这个知识点可能怎样被问？
        ↓
应该沿什么框架分析和回答？
        ↓
完整标准回答在哪里？
        ↓
当前回答继续展开后会产生什么问题？
```

“继续展开”不是固定关联文档列表。只有从当前回答自然产生新的问题时才记录；只有某个知识正文或已有 QA 确实有助于回答该追问时才附链接。

## 1. Harness、Runtime 与 Loop 的职责和关系

### 【提问】

- Agent Harness、Agent Runtime 和 Agent Loop 分别是什么，它们有什么区别？
- 一次 Agent Run 到底是谁在驱动，Loop 和 Runtime 是什么关系？
- Harness 是否包含 Runtime，Runtime 是否等于 Agent Loop？

### 【回答框架】

核心判断：Loop、Runtime、Harness 不是三个互相独立的名词，而是从“Agent 怎样持续完成任务”这个共同问题中拆出的不同职责。

一次模型调用只能完成一次输入到输出。Agent 要根据执行结果继续工作，就会依次出现三个工程问题：

1. **任务怎样持续推进**：模型需要根据行动结果再次判断，形成“判断 → 行动 → 观察 → 再判断”的循环，这一机制就是 Loop。
2. **这套循环由谁真正执行**：循环不能自己运行，需要有执行层负责构建 Context、调用 Model、解析 Tool Call、执行 Tool、更新 State，并判断继续还是结束，这就是 Runtime。
3. **Runtime 怎样可靠运行**：真正进入工程环境后，还需要 Tool 管理、Memory、权限、Checkpoint、Trace 等公共能力，这些运行支撑共同构成 Harness 这一更宽的工程抽象。

把三者放回一次 Agent Run，可以验证这个关系：

```text
用户目标
  ↓
Runtime 构建 Context 并调用 Model
  ↓
Model 给出 Final Answer 或 Tool Call
  ↓
需要行动时，Runtime 执行 Tool 并更新 State
  ↓
Tool Result 成为新的 Observation
  ↓
Loop 使系统基于新信息进入下一轮判断
  ↓
直到满足停止条件

整个过程中：
Harness 持续提供 Tool、Memory、权限、Checkpoint、Trace 等运行支撑
```

因此这里真正的联系是：**Loop 描述持续推进的机制，Runtime 负责把这个机制实际跑起来，Harness 再为 Runtime 和整个 Agent 执行提供完整工程支撑。**

最后要补充边界：这是职责层面的工程抽象，不代表所有框架都存在固定的 `Loop < Runtime < Harness` 代码包含关系。回答时应先从“一次模型调用为什么不足以构成 Agent”推出持续执行问题，再推出 Loop、Runtime、Harness，最后用一次 Agent Run 验证三者关系。

## 2. Agent 研发从 Prompt 扩展到 Context、Harness 与可靠运行

### 【提问】

- 为什么现在做 Agent 不能只关注 Prompt Engineering？
- Prompt、Context、Harness 分别解决什么问题？
- Agent 工程化相比单次 LLM 调用增加了哪些核心问题？

### 【回答框架】

核心判断：Prompt、Context、Runtime / Harness、Workflow 不是 Agent 工程里并列堆叠的几个名词，而是随着系统从“让模型回答”走向“让系统可靠完成任务”，逐步暴露出的不同工程问题。

单次模型调用首先需要 Prompt 表达目标和约束，但很快会发现：**写清楚任务不等于模型拥有完成任务所需的信息**，因此需要 Context 选择这一轮真正进入模型的信息。模型拥有信息后，如果还要查询外部数据、执行动作并根据结果继续工作，就从一次生成进入 Agent Loop，此时 Runtime / Harness 开始承担工具执行、状态、权限、恢复和观测。

把能力继续推到真实业务中，问题又从“Agent 能不能执行”变成“系统能不能长期可靠执行”：

```text
模型需要正确理解任务
→ Prompt

仅有任务描述不够，还要获得当前有效信息
→ Context

仅有信息不够，还要行动并根据结果继续判断
→ Agent Loop + Tool

动态执行不能只靠模型自身维持
→ Runtime / Harness 管理 State、Tool、权限、恢复和 Trace

真实业务还存在确定阶段、外部副作用和长期任务
→ Workflow + 幂等 + 对账 + 验收 + 持久化
```

因此 Agent 工程并不是“Prompt Engineering 被 Harness 取代”，而是问题边界不断扩大：**Prompt 解决任务表达，Context 解决模型当轮可见信息，Runtime / Harness 解决动态执行的工程承载，Workflow 与可靠性机制解决真实业务中的长期运行和副作用控制。**

边界上，这些能力也不是严格的技术代际：简单任务仍可能只需要 Prompt + Model；只有任务复杂度、动态性和可靠性要求提高时，才逐步引入后面的工程层。回答这类问题最终要落到“系统需要解决的问题如何扩大”，而不是背一组 Agent 热词。

## 3. Agent Eval 与 Benchmark 的任务质量评测框架

### 【提问】

- 一个 Agent 到底应该怎么评测，不能只看最终回答吗？
- Agent Eval 中 Task、Trial、Trace、Outcome 和 Grader 是什么关系？
- AI 在 Verify 阶段怎样证明 PASS，而不是“自己执行、自己宣布通过”？
- pass@k、pass^k 和普通成功率分别说明什么？

### 【回答框架】

核心判断：Agent Eval 的本质不是“给模型输出打一个分”，而是建立一条**从任务成功标准到可验证证据，再到评分和版本比较**的闭环。之所以不能只看最终回答，是因为 Agent 可以声称完成任务，但真实环境可能根本没有发生预期变化。

因此回答首先要从“怎样证明成功”出发。成功标准必须在执行前由 Task 定义；Agent 真正运行一次形成 Trial；Trial 之后不能直接相信自然语言答案，而要收集 Output、外部 Outcome、Trace / Trajectory 和 Cost 等证据。只有有了证据，Grader 才能按任务性质判断是否成功。

```text
先定义什么叫成功
→ Task / Success Criteria

让 Agent 在明确条件下真实执行
→ Trial

执行结束后收集可验证事实
→ Output + Outcome + Trace / Trajectory + Cost

根据证据类型选择判断方式
→ Code Grader / Rubric Model / Human Review

把单次判断聚合成系统能力
→ Success Rate / pass@k / pass^k / Cost / Stability

固定任务集、预算、版本和评分口径
→ Eval Suite / Benchmark

持续比较新旧版本
→ Regression
```

这条链也解释了几个常见概念的关系：Trace 是“发生了什么”的过程证据，不等于 Eval；Grader 是判定机制，不等于 Benchmark；单次 Trial 的成功也不能代表系统稳定性，所以才需要成功率、pass@k、pass^k 等聚合指标。

边界上，指标必须服务于任务目标：确定性任务优先使用可验证的代码或环境结果，开放质量问题才更多依赖 Rubric / Model Grader，并在高风险或争议场景加入人工复核。最终应收束为：**先定义成功，再运行任务，再取得证据，再评分，最后通过固定评测集和指标做版本回归。**

## 4. Agent 工具执行的身份、授权、审批与隔离

### 【提问】

- Agent 调用 Tool 时，权限到底应该在哪里控制？
- Prompt、Skill、Tool 权限和业务后端授权有什么区别？
- Human-in-the-loop、Guardrail 和 Sandbox 分别解决什么安全问题？

### 【回答框架】

核心判断：Agent 安全不能建立在“模型会不会听话”上，而要建立在**模型只能提出动作，可信执行系统决定动作是否允许以及怎样执行**这一边界上。因此 Prompt、Tool 过滤、授权、审批、Sandbox 和 Audit 不是同一种“权限控制”，而是动作从意图变成真实副作用过程中不同位置的控制点。

从一次 Tool 调用反推：系统首先要知道是谁在发起任务，因此需要认证；有了身份以后，也不意味着 Agent 应看到所有能力，因此需要 Tool 暴露与过滤；模型选中某个 Tool 后，还必须判断该身份能否对具体资源执行具体动作，因此进入业务授权。对于高风险动作，仅有权限仍可能不够，还需要人工审批；真正执行代码或访问资源时，又需要 Sandbox / Resource Boundary 限制执行范围。

```text
模型产生“我想执行某动作”
        ↓
这个请求来自谁？
→ Authentication

这个 Agent 当前应该看到哪些能力？
→ Tool Exposure / Filtering

这个身份能否对这个资源执行这个动作？
→ Authorization

即使有权限，这次高风险动作是否需要再次确认？
→ Human Approval

动作实际执行时能访问哪些环境和资源？
→ Sandbox / Resource Boundary

真实业务系统最终是否允许副作用发生？
→ Backend Revalidation + Execution

事后如何证明发生过什么？
→ Trace / Audit
```

这条链说明 Prompt / Skill 最多提供行为指导，不能替代可信后端的授权；Tool 可见也不代表 Tool 可执行；人工批准也不能绕过最终业务校验。恢复旧任务时还要重新检查可能已经变化的身份、资源和策略，而不能把旧 Checkpoint 当成永久授权。

最终应收束为：**模型负责提出动作，可信系统通过身份、能力暴露、资源授权、人工审批、执行隔离和后端复核逐层收窄动作，Audit 再保存治理证据。**

## 5. Agent 可观测性通过 Trace、Span、Metric 与 Audit 解释执行过程

### 【提问】

- Agent 系统为什么需要 Trace，仅有日志够不够？
- Trace、Span、Log、Metric 和 Audit 分别解决什么问题？
- 如何观察一次 Agent 从模型判断到 Tool 执行的完整链路？

### 【回答框架】

核心判断：Agent 可观测性的目标不是“多记一些日志”，而是能够回答一次 Agent Run **发生了什么、各步骤如何关联、系统整体表现怎样，以及敏感动作由谁触发**。不同问题需要不同观测数据，因此 Trace、Span、Log、Metric、Audit 必须按职责组合，而不是互相替代。

先从排障问题出发：如果只看到一条 Tool 报错日志，只知道某个局部事件失败，却不知道它属于哪次任务、由哪个模型判断触发、前后发生了什么。因此需要 Trace 把整次 Run 串起来，并用 Span 表示模型调用、Tool 调用、Agent 节点或业务阶段。Span 中仍可能需要 Log 补充异常细节。

但逐条 Trace 只能解释单次执行，无法回答“最近成功率是否下降、Token 是否上涨、哪个 Tool 最慢”，因此还需要 Metric 做跨 Run 聚合。涉及审批、身份和敏感副作用时，又需要 Audit 保存治理证据。

```text
想解释一次任务整体发生了什么
→ Trace

想知道任务内部哪些步骤耗时或失败
→ Span

想查看某一步的具体事件与错误细节
→ Log

想判断大量任务的趋势和健康度
→ Metric

想证明谁在何时批准或执行了敏感动作
→ Audit

统一关联并送入查询分析系统
→ Exporter / Observability Backend
```

采集时，Runtime 可以自动覆盖模型、Tool 和 Agent 调用，业务 Hooks / 自定义 Span 补充框架不知道的业务阶段；分析时还要把模型可见输入、Tool Call、参数、结果和时间关系关联起来，才能解释“为什么发生”。

边界上，可观测性解决的是**执行事实与解释能力**：Trace 不是任务成功判定，因此不能替代 Eval；Trace 也不是可恢复状态，因此不能替代 Checkpoint。最终应收束为：**用 Trace/Span 还原链路，用 Log 解释事件，用 Metric 看趋势，用 Audit 保留治理证据。**

## 6. Agent 长任务的任务分解、状态持久化、验收与恢复

### 【提问】

- Agent 怎样执行几个小时甚至几天的长任务？
- Context、Memory、State、Checkpoint 和 Artifact 在长任务中分别负责什么？
- Agent 中断后如何继续，而不是重新从头执行？

### 【回答框架】

核心判断：长任务不是把一次 Agent Run “挂得更久”，而是把一个长期目标改造成**可以分段推进、阶段验收、持久保存并从可信边界恢复**的任务系统。只增加 Context Window 或 Memory 都不能解决这个问题。

原因在于任务时间越长，中断、进程重启、外部系统变化和错误累积的概率越高。如果任务没有可独立完成和验收的阶段，就无法判断已经完成到哪里；如果只有内存中的 State，中断后就无法恢复；如果恢复时只加载旧状态而不检查外部世界，又可能重复产生副作用。

因此长任务要沿着“拆分 → 执行 → 验收 → 持久化 → 恢复”建立闭环：

```text
长期目标
→ 拆成可独立推进、可验收的工作单元

执行某个工作单元
→ State 记录当前计划、阶段、结果和待办

阶段产生结果
→ Verification 判断结果能否成为后续可信前置

通过验收
→ Checkpoint 保存恢复状态
→ Artifact 保存任务产物
→ Memory 保存未来可复用信息

发生中断或失败
→ 读取持久状态
→ Reconcile 外部副作用和真实业务状态
→ 从可信边界 Resume
```

这条链同时区分了容易混淆的概念：Context 是当前一轮给模型看的信息；State 是当前运行事实；Checkpoint 是 State 的持久快照；Artifact 是交付物；Memory 是未来运行可能重新取用的信息。它们共同参与长任务，但不能互相替代。

边界上，Agent 内部 Checkpoint 只能恢复 Agent 自身状态，涉及真实业务副作用时仍需要外层任务状态、幂等、对账和权限复核。最终应收束为：**长任务能力来自可分解、可验证、可持久化和可恢复，而不是来自更长的一次模型调用。**

## 7. Agent 故障恢复通过失败分类、幂等、对账与补偿保证一致性

### 【提问】

- Agent Tool 调用失败以后是不是直接 Retry 就可以？
- Agent 如何避免重试造成重复扣款、重复发消息或重复写数据？
- Checkpoint、Retry、Idempotency、Reconciliation 和 Compensation 分别解决什么问题？

### 【回答框架】

核心判断：Agent 故障恢复不能从“失败了就 Retry”开始，因为**调用失败不等于业务动作没有发生**。真正要先判断的是失败类型，以及上一次动作是否已经产生外部副作用；只有确认可以安全重放后，Retry 才成立。

例如请求超时时，可能是服务端根本没收到，也可能已经完成扣款但响应丢失。如果不区分这两种状态直接重试，就可能重复执行。因此第一步要分类：临时异常可能适合有限重试；参数或确定性错误需要修正输入；业务拒绝必须尊重业务规则；结果未知则必须先查询真实状态。

```text
观察到执行失败
        ↓
先判断失败属于什么类型
临时异常 / 确定错误 / 业务拒绝 / 结果未知
        ↓
这次动作能否确认安全重放？
├─ 能
│   → 有限 Retry + Backoff
│
└─ 不能 / 结果未知
    → Reconciliation 查询真实业务状态
       ├─ 实际未执行 → 安全重放
       └─ 实际已执行 → 复用已有结果
                         或按业务语义执行 Compensation
        ↓
更新可信 State / Checkpoint
        ↓
继续后续任务
```

这里各机制解决不同问题：Retry 处理可恢复执行失败；Idempotency 让重复请求不产生重复副作用；Reconciliation 在结果未知时确认外部真实状态；Compensation 处理已经发生且需要业务逆向处理的副作用；Checkpoint 只保存 Agent 的恢复位置。

因此 Checkpoint 不能提供 Exactly-once，权限拒绝也不能通过 Retry 或 Fallback 绕过。最终应收束为：**先分类失败，再判断副作用和可重放性；能安全重放才 Retry，不确定就先对账，已经执行则复用结果或按业务规则补偿。**

## 8. Agent 编排通过执行结构和决策权分配组织复杂任务

### 【提问】

- Workflow、Supervisor、Manager、Handoff、多 Agent 到底是什么关系？

- 多 Agent 是否一定意味着模型拥有更大的流程控制权？

### 【回答框架】

核心判断：Agent 编排真正要设计的不是“选 Workflow、Supervisor 还是 Multi-Agent 这个名词”，而是两个相互独立的问题：**任务采用什么执行结构，以及每个关键节点的下一步决策权交给代码还是模型。** 先回答决策权，再选择拓扑，才能避免为了使用 Agent 而把整个流程动态化。

复杂任务中通常同时存在两类步骤：一类规则稳定、顺序明确、风险高，可以预先编码；另一类需要根据运行时信息搜索、规划、选择工具或拆分任务，难以提前穷举。因此首先应划出确定性业务骨架，再判断哪些局部节点值得把 Decision Authority 交给模型。

```text
复杂业务目标
        ↓
哪些阶段可以提前确定？
→ 固定顺序 / 规则 / 高风险 Gate
→ Code 控制

哪些局部步骤必须根据运行时信息决定？
→ Planning / Replanning / Tool Selection / Agent Selection
→ Model 控制

决策权边界明确以后
        ↓
任务之间需要怎样协作？
→ 单 Agent
→ Manager + Specialists
→ Handoff
→ Parallel / Graph

最后约束动态执行范围
→ Goal / Permission / Budget / Verification / Human Gate
```

这样可以进一步解释常见概念：Manager 是中心 Agent 调用专业 Agent 后继续持有总体控制权；Handoff 是把后续处理权转交给目标 Agent；Parallel 只描述并发结构；Multi-Agent 只说明存在多个 Agent。它们都不能直接推出“模型拥有整个业务流程控制权”。

边界上，确定性 Workflow 与 Agent 动态决策不是二选一。真实系统通常让代码控制稳定业务骨架和高风险节点，让模型只在不确定、需要语义判断的局部获得自主权。最终应收束为：**先划业务骨架和决策权，再选择执行拓扑，最后用权限、预算、验收和人工 Gate 约束自主范围。**
