# QA 索引连接提问方式、回答框架与继续学习路径

QA 是 `Full-Stack-AI-NOTES` 的“问题视图”，不是聊天记录，也不是第二套知识库。每条 QA 对应一套可以复用的回答知识框架：同一个知识点可以有不同提问方式，但只要核心分析路径一致，就归入同一条记录。

正式回答问题时仍遵循：

```text
知识体系索引.md
   ↓ 定位主题和前置知识
QA.md
   ↓ 找到已有回答框架与可继续追问方向
相关知识 Markdown
   ↓ 阅读完整正文
source/ / resource/
   ↓ 按需读取实现和附件
外部权威资料
   ↓ 核验变化事实和关键结论
```

QA.md 重点回答四件事：

```text
这个知识点可能怎样被问？
        ↓
应该沿什么框架分析和回答？
        ↓
完整标准回答在哪里？
        ↓
当前回答继续展开后会产生什么问题？
```

“继续展开”不是固定关联文档列表。只有从当前回答自然产生新的问题时才记录；只有某个知识正文或已有 QA 确实有助于回答该追问时才附链接。

## 1. Harness、Runtime 与 Loop 的职责和关系

### 【提问】

- Agent Harness、Agent Runtime 和 Agent Loop 分别是什么，它们有什么区别？
- 一次 Agent Run 到底是谁在驱动，Loop 和 Runtime 是什么关系？
- Harness 是否包含 Runtime，Runtime 是否等于 Agent Loop？

### 【回答框架】

这类问题不能只背三个定义，应该从“**机制—运行—支撑体系**”三个层次回答，再把三者放回一次 Agent 执行过程验证关系。

```text
Agent 要持续完成任务
        ↓
Loop：描述“判断 → 行动 → 观察 → 再判断”的循环机制
        ↓
Runtime：真正驱动模型调用、Tool 执行、State 更新和停止条件
        ↓
Harness：把 Runtime 与 Context、Tool、Memory、权限、Trace 等能力装配起来
        ↓
回到一次 Agent Run
验证三者如何协作
        ↓
补充边界：这是职责抽象，不是行业统一固定嵌套关系
```

- **先区分问题层次**：Loop 回答“任务怎样反复推进”，Runtime 回答“谁负责把这套过程运行起来”，Harness 回答“完整 Agent 运行还需要哪些工程支撑”。
- **再解释协作过程**：Runtime 构建上下文并调用 Model；模型产生 Tool Call 后 Runtime 执行工具、写入 State，再进入下一轮 Loop；Harness 提供这一过程中需要的 Context、Tool、Memory、权限、Checkpoint、Trace 等能力。
- **最后说明边界**：不同框架对 Runtime 和 Harness 的模块划分不同，因此不能把 `Loop < Runtime < Harness` 当成行业统一标准；Agent Loop 也不等于预定义业务 Workflow。

## 2. Agent 研发从 Prompt 扩展到 Context、Harness 与可靠运行

### 【提问】

- 为什么现在做 Agent 不能只关注 Prompt Engineering？
- Prompt、Context、Harness 分别解决什么问题？
- Agent 工程化相比单次 LLM 调用增加了哪些核心问题？

### 【回答框架】

回答这类问题要沿着“**模型能回答 → Agent 能执行 → 系统能长期可靠执行**”的能力扩展来解释，而不是把 Prompt、Context、Harness 当成几个并列名词。

```text
Prompt
明确当前任务目标与约束
        ↓
Context
决定模型这一轮实际能看到什么
        ↓
Agent Loop / Tool
让模型根据结果继续行动
        ↓
Harness / Runtime
管理状态、权限、执行、恢复和观测
        ↓
业务 Workflow
管理更大的任务阶段与确定性边界
        ↓
可靠性问题
重试 / 幂等 / 中断 / 恢复 / 验收
```

- **Prompt 层**解决“怎样表达任务”，但不能独立解决信息选择、工具执行、跨轮状态和失败恢复。
- **Context 层**解决“当前这一轮模型应该看到哪些信息”；运行时拥有的信息不等于全部都应该进入模型上下文。
- **Harness / Runtime 层**解决“怎样让模型能够安全、可恢复地执行”，包括 Tool、State、权限、Checkpoint、Trace 等。
- **Workflow 层**继续约束更大的业务阶段。Agent 的动态决策与确定性业务流程可以同时存在，并不是技术代际上的互相替代。
- **可靠运行是最终判断标准**：涉及真实副作用时，还必须考虑幂等、对账、重试、中断恢复和验收，不能只评价模型回答质量。

## 3. Agent Eval 与 Benchmark 的任务质量评测框架

### 【提问】

- 一个 Agent 到底应该怎么评测，不能只看最终回答吗？
- Agent Eval 中 Task、Trial、Trace、Outcome 和 Grader 是什么关系？
- pass@k、pass^k 和普通成功率分别说明什么？

### 【回答框架】

Agent 评测应从“**先定义成功，再收集执行证据，最后由合适的评分器判断**”展开，而不是先选指标或先让模型自评。

```text
Task
先定义任务和成功标准
        ↓
Trial
让 Agent 在受控条件下真实执行
        ↓
Evidence
收集 Output + Outcome + Trace / Trajectory + Cost
        ↓
Grader
代码规则 / Rubric 模型 / 人工复核
        ↓
Metrics
成功率 / pass@k / pass^k / 成本 / 稳定性
        ↓
Suite / Benchmark
固定样本、预算、版本和聚合口径
        ↓
Regression
持续比较版本变化
```

- **第一步永远是成功标准**：模型声称“完成”不能作为任务成功证据。
- **第二步收集真实结果和过程证据**：最终输出、外部系统结果、执行轨迹和资源消耗承担不同证据职责。
- **第三步选择评分方式**：确定条件优先代码评分；开放质量使用明确 Rubric 的模型评分；复杂或争议场景引入人工复核。
- **第四步正确理解聚合指标**：成功率看总体完成情况，pass@k 更关注多次尝试中至少成功一次的能力，pass^k 更强调连续多次都成功的稳定性。
- **第五步形成可回归体系**：评测集、预算、评分器和版本必须可追踪，否则不同版本结果不能可靠比较。

## 4. Agent 工具执行的身份、授权、审批与隔离

### 【提问】

- Agent 调用 Tool 时，权限到底应该在哪里控制？
- Prompt、Skill、Tool 权限和业务后端授权有什么区别？
- Human-in-the-loop、Guardrail 和 Sandbox 分别解决什么安全问题？

### 【回答框架】

回答 Agent 安全治理不能只说“增加权限控制”，而要沿着一次动作真正落地的链路区分多个控制点。

```text
谁在发起任务？
身份认证
        ↓
Agent 能看到哪些能力？
Tool 暴露 / 过滤
        ↓
这个身份能否对这个资源执行这个动作？
业务授权
        ↓
当前动作是否需要额外批准？
Human Approval
        ↓
动作允许在哪个环境执行？
Sandbox / Resource Boundary
        ↓
真实业务后端再次校验并执行
        ↓
Trace / Audit 保存治理证据
```

- **身份和授权是基础边界**：可信身份由认证系统建立，对真实业务资源的最终授权必须由可信服务端执行。
- **Prompt / Skill 是行为指导，不是安全边界**：它们可以告诉模型“不要做什么”，但不能代替后端权限校验。
- **Tool 可见性、动作授权、人工审批和执行隔离是不同控制点**，不能混成一个“权限”概念。
- **恢复时仍要重新检查关键条件**：审批前后的身份、资源状态和策略可能变化，不能因为存在旧 Checkpoint 就默认继续执行仍然安全。
- **治理需要证据**：Trace / Audit 应能解释谁发起、系统做了什么判断、最终执行了什么动作。

## 5. Agent 可观测性通过 Trace、Span、Metric 与 Audit 解释执行过程

### 【提问】

- Agent 系统为什么需要 Trace，仅有日志够不够？
- Trace、Span、Log、Metric 和 Audit 分别解决什么问题？
- 如何观察一次 Agent 从模型判断到 Tool 执行的完整链路？

### 【回答框架】

先回答“**要解释一次 Agent Run，需要哪些不同粒度的运行事实**”，再沿采集、关联、导出和分析链路展开。

```text
一次 Agent Run
        ↓
Trace：关联整次任务
        ↓
Span：拆出模型、Tool、Agent、业务阶段
        ↓
Log：补充离散事件和错误细节
        ↓
Metric：聚合延迟、Token、成功率、错误率等趋势
        ↓
Audit：保存身份、审批和敏感动作等治理证据
        ↓
Exporter / Backend
形成查询、定位和分析能力
```

- **先区分数据职责**：Trace/Span 还原调用关系，Log 解释具体事件，Metric 看聚合趋势，Audit 服务治理和审计。
- **再解释如何采集**：Runtime 可以自动记录模型、工具和 Agent 调用；业务 Hooks / 自定义 Span 补充框架不知道的业务阶段。
- **再解释如何关联**：只知道 Span 父子关系还不够，分析模型为什么执行某动作还需要关联模型可见输入、Tool Call、参数、时间和结果。
- **最后说明边界**：Observability 告诉我们“发生了什么”，但 Trace 本身不是任务成功证明，也不是用于恢复执行的 Checkpoint。

## 6. Agent 长任务的任务分解、状态持久化、验收与恢复

### 【提问】

- Agent 怎样执行几个小时甚至几天的长任务？
- Context、Memory、State、Checkpoint 和 Artifact 在长任务中分别负责什么？
- Agent 中断后如何继续，而不是重新从头执行？

### 【回答框架】

长任务的核心不是“让一个模型调用运行更久”，而是把工作变成**可分解、可验收、可持久化、可恢复**的执行过程。

```text
Long-running Goal
        ↓
Task Decomposition
拆成可独立推进和验收的工作单元
        ↓
State
记录当前阶段、计划、结果和待处理事项
        ↓
Execution + Verification
每个阶段产生可验证结果
        ↓
Persistence
Checkpoint 保存恢复状态
Artifact 保存交付产物
Memory 保存未来可复用信息
        ↓
Interruption / Failure
        ↓
Reconcile
核对已完成动作和外部副作用
        ↓
Resume
从可信边界继续
```

- **任务首先要可切分**：长任务如果没有阶段边界，就无法可靠判断完成度、保存进度或局部重试。
- **几个状态概念职责不同**：State 是当前运行数据；Checkpoint 是 State 的持久快照；Artifact 是任务产物；Memory 是未来任务可重新取用的信息；Context 是当前一轮真正提供给模型的输入。
- **阶段结果必须经过验收后再成为可靠前置**，否则错误结果会被后续步骤持续放大。
- **恢复不是简单加载 Checkpoint**：还要核对外部副作用、待审批动作和已提交结果，确认从哪里继续才安全。
- **Agent 内部恢复与业务级持久编排是两个层次**：长业务任务通常还需要外层任务状态和幂等保护。

## 7. Agent 故障恢复通过失败分类、幂等、对账与补偿保证一致性

### 【提问】

- Agent Tool 调用失败以后是不是直接 Retry 就可以？
- Agent 如何避免重试造成重复扣款、重复发消息或重复写数据？
- Checkpoint、Retry、Idempotency、Reconciliation 和 Compensation 分别解决什么问题？

### 【回答框架】

故障恢复的第一步不是 Retry，而是先判断“**到底失败了什么，以及上一次动作是否已经产生副作用**”。

```text
Execution Failure
        ↓
Failure Classification
临时异常 / 确定错误 / 业务拒绝 / 结果未知
        ↓
Can Replay Safely?
        ├─ 可以 → 有限 Retry + Backoff
        └─ 不确定
              ↓
          Reconciliation
          查询真实业务状态
              ↓
      ┌───────┴────────┐
      ↓                ↓
   未执行            已执行
      ↓                ↓
安全重放          复用结果 / 补偿
        ↓
从可信 State / Checkpoint 继续
```

- **先分类失败**：网络超时、参数错误、业务拒绝和“请求可能成功但响应丢失”不能使用同一种恢复策略。
- **Retry 只适合可安全重放的动作**，并且要有次数、退避和总体执行预算。
- **幂等必须由真正产生副作用的服务端或下游接口保证**；Checkpoint 只保存 Agent 状态，不能保证外部动作恰好执行一次。
- **结果未知优先对账**：先确认真实系统是否已经执行，再决定复用结果还是重新执行。
- **补偿是新的业务动作**：它用于处理已经产生的副作用，不等于数据库意义上的自动回滚，也不能保证抹掉所有外部影响。
- **权限拒绝不能通过 Fallback 或 Retry 绕过**。

## 8. Agent 编排通过执行结构和决策权分配组织复杂任务

### 【提问】

- Workflow、Supervisor、Manager、Handoff、多 Agent 到底是什么关系？
- 什么步骤应该由代码控制，什么步骤可以交给模型动态决定？
- 多 Agent 是否一定意味着模型拥有更大的流程控制权？

### 【回答框架】

编排问题不能只按框架名分类，应该先拆成两个核心维度：**执行结构是什么，以及下一步的决策权掌握在谁手里。**

```text
复杂任务
        ↓
先划分确定性业务阶段
        ↓
判断每个阶段的 Decision Authority
        ├─ Code
        │   固定 Workflow / Rule
        │
        └─ Model
            Planning / Replanning
            Tool Selection
            Agent Selection
        ↓
再决定 Execution Topology
单 Agent / Manager + Specialists / Handoff / Parallel
        ↓
最后定义 Control Boundary
目标、权限、预算、验收和人工 Gate
```

- **先确定业务骨架**：能够预先定义且高风险的阶段优先由代码控制，不应因为用了 Agent 就把整个流程交给模型。
- **再分配局部决策权**：无法预先确定的搜索、规划、工具选择或任务拆分可以交给模型动态决定。
- **Manager 和 Handoff 是不同控制方式**：Manager 调用专业 Agent 后收回结果；Handoff 则把后续处理控制权交给目标 Agent。
- **多 Agent、并行、Graph、模型动态控制属于不同维度**：用了多 Agent 不代表一定使用 Handoff，也不代表整体流程一定由模型控制。
- **最终方案通常是混合编排**：确定性的业务骨架约束动态 Agent 能力，并通过目标、权限、预算、验收和人工 Gate 控制自主范围。
