# AI Coding 工作流如何完成真实前端需求交付

## 1. 【提问】

你简历中写到参与端到端 AI 研发工作流建设，融合 SDD、ATDD 与 AI-DLC 规范，驱动 Agent 完成前端开发、视觉对齐和验收交付。

请结合一个真实需求说明：

- 为什么团队需要单独建设这套 AI Coding 工作流？
- 它如何完成从需求分析到代码交付的端到端流程？
- 你本人主要参与了哪些部分？
- 它和直接使用 Codex、Claude Code 等 Coding Agent 写代码有什么本质区别？
- 如何证明它是一套研发工作流，而不是 Prompt、Skill 和工具的简单串联？

---

## 2. 【回答思路】

回答时不要先展开 SDD、ATDD 等概念定义，而应从真实研发问题切入，再解释工作流设计。

```text
真实前端研发 SOP
需求分析 → 任务规划 → 代码开发 → 测试验收 → 交付
        ↓
通用 Coding Agent 只能覆盖其中一部分
        ↓
目标：AI 成为主要执行者，人负责关键判断与放行
        ↓
四条原则
规范驱动 → 验收前置 → 可追溯 → 风险控制
        ↓
工程实现
阶段状态 + 标准产物 + Gate + Tool/MCP + Agent + Evidence
        ↓
真实需求验证
内容活动激励管控线上化
        ↓
结果与边界
交付效率、质量、人工参与 + 未闭合证据不强制放行
```

回答时需要持续区分三类职责：

- **团队已有能力**：内部 CI、BAM、Figma、MCP、Agent、业务代码仓库等基础设施。
- **本人参与工作**：将这些能力组织进真实前端交付流程，重点完善需求澄清、Task/Test Case、Mock/真实环境边界、验收 Gate 和运行证据。
- **Agent 自动执行内容**：资料读取、结构化拆解、代码修改、自动检查、浏览器取证和阶段产物生成等受控执行工作。

---

## 3. 【完整回答】

我们做这套 AI Coding 工作流，核心目标是针对电商前端真实研发需求，构建一套能够让 AI 从需求分析一直执行到验收交付的端到端研发流程。

传统研发本身已经有比较稳定的 SOP：

```text
需求分析
   ↓
任务规划
   ↓
代码开发
   ↓
测试验收
   ↓
交付
```

我们并不是重新设计一套软件研发流程，而是希望把 AI 放进这条既有流程中，让 AI 从单纯的 Coding Assistant 变成主要执行者。

基本的人机分工是：

- AI 负责需求资料读取、任务拆解、代码实现、自动检查、运行验证和证据整理等规模化执行工作；
- 人从大量重复执行中退出，把精力集中到需求判断、风险判断、关键产物审查和最终放行。

因此，这套工作流真正想解决的是：**在减少人工参与、缩短交付周期的同时，仍然保证需求理解和代码质量可控。**

### 3.1 通用 Coding Agent 还不能直接覆盖真实需求交付

我们调研和实际使用通用 Coding Agent 后发现，在团队内部真实电商前端需求中存在几个明显缺口。

第一，通用 Agent 很难天然理解团队已有的研发基础设施。

例如团队已经存在 CI、BAM 接口生成、Figma、MCP、内部调试环境等能力。问题并不是 Agent 完全不能调用工具，而是它并不知道：

- 什么阶段应该调用什么工具；
- 工具输出如何成为下一阶段的输入；
- 哪些结果只能作为辅助信息；
- 哪些结果能够真正作为阶段放行证据。

所以工具本身不能直接构成完整工作流。

第二，很多 AI Coding 方案重点解决的是代码生成，而真实研发的完成标准并不是“代码已经生成”。

真实需求还包含：

```text
需求是否理解正确
        ↓
接口和实现范围是否正确
        ↓
代码是否满足需求
        ↓
异常和负向场景是否覆盖
        ↓
UI 是否和设计一致
        ↓
真实环境是否成立
        ↓
是否具备最终交付条件
```

如果没有后续验证和质量 Gate，Agent 很容易把“代码完成”误认为“需求完成”。

第三，前后端经常并行开发。

部分需求进入前端开发阶段时，后端接口或者特殊测试数据还没有准备完成。前端不能完全等待后端，因此需要一套自动化 Mock 能力，让 Agent 可以继续验证前端请求、状态管理和交互分支。

但这里必须有明确边界：

> **Mock 通过只能证明前端是否按照接口合同发起请求并正确消费数据，不能证明真实接口、权限、事务和数据口径已经正确。**

所以 Mock 之后仍然需要真实环境验证，不能把 Mock PASS 直接升级为最终交付 PASS。

### 3.2 规范驱动让 Agent 基于稳定合同执行

第一个原则是规范驱动。

Agent 在每一个阶段执行之前，都需要有明确的输入和阶段产物，而不是依赖一次性的自然语言 Prompt。

整体关系可以表示为：

```text
Requirement
    ↓
Plan
    ↓
Task
    ↓
Test Case
    ↓
Code
    ↓
Verification
```

需求分析阶段形成已经确认的需求事实；任务规划阶段形成技术计划和可执行任务；代码阶段按照已经确认的 Task 执行；验收阶段再根据预先定义的 Test Case 判断结果。

这样做的核心价值不是“多写几份文档”，而是给 Agent 建立一个稳定的执行合同。

当任务跨越较长时间或者多个 Session 时，Agent 不需要完全依赖聊天历史重新理解任务，而可以通过这些正式产物恢复上下文。

### 3.3 验收前置避免实现和测试一起偏离需求

第二个原则是验收前置。

这部分融合了 ATDD（Acceptance Test-Driven Development，验收测试驱动开发）的思想。

我们不会等 AI 把代码实现完成以后，再让它根据已有实现生成测试项。

原因是这样很容易产生同源偏差：

```text
Agent 先生成代码
      ↓
Agent 再根据已有代码生成测试
      ↓
测试逐渐贴近“当前实现”
      ↓
实现和测试可能一起偏离真实需求
```

因此 Test Case 必须在 Code 之前形成，并且主要从 PRD、产品确认、设计稿和接口合同出发。

Test Case 会尽量采用 BDD（Behavior-Driven Development，行为驱动开发）常见的 Given-When-Then 结构描述单个业务场景：

```text
Given：当前存在命中不激励规则的问题作品
When：用户点击提交
Then：
  - 页面提示问题作品仍未处理
  - Drawer 不关闭
  - 二次确认弹窗不出现
  - 发奖请求不发送
```

Given-When-Then 解决的是单个行为场景如何被清楚、标准化地表达。

测试是否完整，则不能只依靠这个格式，而需要继续检查：

```text
原子需求 → Scenario → Test Case
```

之间是否存在完整覆盖关系。

所以这里真正强调的是：

> **测试标准来自需求，而不是从已经写好的代码反推。**

### 3.4 可追溯让工作流能够恢复、审查和定位失败原因

第三个原则是可追溯。

整个工作流按照研发 SOP 划分成多个阶段，每个阶段都有：

- 固定输入；
- 阶段产物；
- Gate；
- 当前执行状态；
- 失败后的恢复位置。

当前工作流主链为：

```text
/delivery:init
    ↓
/delivery:prd
    ↓
/delivery:bam
    ↓
/delivery:plan
    ↓
/delivery:task
    ↓
/delivery:code
    ↓
/delivery:verify
    ↓
/delivery:design
    ↓
/delivery:accept
```

阶段执行过程中持续沉淀需求分析、技术方案、Task、Test Case Matrix、代码实现记录、Verify 结果以及 Design Evidence。

这些产物有两个重要作用。

第一是跨阶段、跨 Session 恢复。

Agent 可以重新读取正式产物判断当前任务是什么、已经完成到哪里、有哪些未决问题以及下一步应该继续什么，而不需要重新猜测聊天上下文。

第二是失败以后可以回溯。

如果最终需求不符合预期，可以沿着：

```text
Requirement
   ↓
Plan
   ↓
Task
   ↓
Test Case
   ↓
Code
   ↓
Runtime Evidence
```

去定位最早出现偏差的位置。

这样能够判断到底是：

- 需求没有澄清；
- Plan 或 Test Case 本身理解错了；
- Agent 没有按照已经明确的任务实现；
- 还是 Verify 阶段证据不足却错误放行。

因此，可追溯的重点不是保存更多文档，而是**让每个阶段的关键状态实体化，使任务能够恢复、结果能够审查、失败能够定位。**

### 3.5 风险控制让 AI 执行，但不让关键决策失控

第四个原则是风险控制。

AI 可以成为主要执行者，但不能同时拥有所有关键决策权。

我们的判断标准主要是：

> 如果一个阶段判断错误会被后续流程不断放大，或者操作本身具有较高风险，就需要人工参与。

需求澄清就是一个典型的关键 Gate。

AI 在读取 PRD、评论、技术文档和 Figma 后，如果发现业务规则存在歧义，不允许自己猜，而是把问题整理出来，由产品和研发确认。

只有关键需求事实明确以后，才能进入 Plan、Task 和 Code。

最终交付也是人工 Gate。

Agent 可以准备代码、测试结果、运行证据和风险清单，但是是否真正具备发布条件，需要人基于这些证据进行最终判断。

所以人并不是重新执行一遍 Agent 已经完成的工作，而是集中承担高风险、高不确定性节点的判断责任。

## 4. 【真实需求案例：内容活动激励管控线上化】

这套工作流实际用于验证过“内容活动激励管控线上化”需求。

业务目标是在运营发放 DOU+ 币、DOU+ 券等奖励之前，识别命中“不激励”规则的作品或账号，支持问题提示、剔除、原因展示、导出和提交保护，降低错误发奖风险。

该需求最终拆解出 17 条原子需求，并形成 30 多个 Test Case。

以“问题作品未处理时禁止提交”为例，验收不只检查页面有没有弹出提示，还需要验证：

- 正常作品没有被错误移除；
- Drawer 没有错误关闭；
- 二次确认弹窗没有出现；
- Network 中没有发送真实发奖请求。

这里的重点是：**验收不仅证明应该发生的行为，还要证明高风险副作用没有发生。**

项目中还出现过一次典型 UAT 问题：一键移除问题作品以后，整个汇总操作区被错误隐藏。

继续回溯以后发现，这并不只是一个代码 Bug，而是 Plan 和 Test Case 对这个产品状态本身就存在共同误读。

因此修复没有停留在代码层，而是从最早出现偏差的位置重新修正：

```text
Plan
 ↓
Task
 ↓
Test Case
 ↓
Code
 ↓
Verify
 ↓
Design
```

修复后，问题作品数量更新为 0，正常作品继续保留；“一键移除”仍然保留但进入禁用状态；已经剔除的记录仍然可以导出。

这个案例能够比较直接地体现可追溯机制的价值：**如果上游合同本身就是错的，仅修改代码并不能真正解决问题。**

## 5. 【个人贡献边界】

这套体系不是我一个人从零创造的。

团队本身已经具备内部 Agent、MCP、BAM、Figma、CI 和前端工程基础设施。

我参与的重点主要是把这些能力组织进真实前端交付过程，并在真实需求中持续验证和优化，主要包括：

1. 参与梳理端到端研发阶段以及各阶段输入、产物和 Gate。
2. 在需求分析阶段强化不确定性识别和需求澄清，避免 Agent 自行补全业务规则。
3. 在 Task 阶段重点参与 Test Case Matrix 和需求覆盖关系设计，将验收标准前置到 Code 之前。
4. 完善 Mock 与真实环境的边界，让后端未就绪时前端仍能推进，但不把 Mock 结果包装成真实环境验收。
5. 在 Verify / Design 阶段通过 UI、DOM、Network、Console、Screenshot 等运行证据判断 Case 是否真正成立。
6. 审查 Agent 和 AI Code Review 的输出，接受有事实依据的建议，拒绝与真实接口合同或业务事实冲突的建议。
7. 将真实需求中出现的偏差反向沉淀到 Plan、Task、Test Case 和工作流规范中，而不是只修一次业务代码。

因此我的角色更接近“业务研发 + 工作流设计与验证 + 质量门禁”，而不是单纯使用 AI 生成代码。

## 6. 【和直接使用 Coding Agent 的本质区别】

如果只是直接使用 Codex、Claude Code 等 Coding Agent，一个典型过程可能是：

```text
PRD
 ↓
Prompt
 ↓
Agent 写代码
 ↓
Agent 写测试
 ↓
Agent 判断完成
```

它最大的问题是：需求理解、实现和验收可能都来自同一个执行主体。

如果 Agent 在最开始就理解错了，那么代码和测试完全可能一起偏离真实需求。

这套工作流更强调：

```text
Requirement
    ↓
Acceptance Criteria
    ↓
Test Case
    ↓
Task
    ↓
Code
    ↓
Runtime Evidence
    ↓
Gate
```

所以代码只是整个交付链路中的一个中间产物。

最终是否完成，不由 Agent 的自然语言声明决定，而由已确认需求、Test Case、实际运行证据、阶段 Gate 和必要的人工审查共同决定。

因此它和普通 AI Coding 最大的区别不是使用了更多 Skill 或 Agent，而是：

> **把 AI 放进一套有规范、有状态、有验收合同、有运行证据、有人工 Gate 的软件交付体系中。**

最终目标不是“让 AI 写更多代码”，而是：

> **让 AI 成为研发流程的主要执行者，同时让人继续掌握需求判断、风险判断和最终质量放行权。**

## 7. 【结果与指标口径】

这套工作流最终希望同时优化三个指标：

```text
交付周期
+
缺陷与返工
+
人工参与率
```

在当前答辩材料中，整体研发提效采用的阶段性口径为约 3 PD → 2 PD，对应约 33% 的周期缩短。

该数字必须结合当前样本和 baseline 解释，不能脱离统计范围表述为稳定的团队整体收益。仓库历史材料还存在 4 PD → 2 PD 等其他阶段口径，因此正式面试时应统一当前使用的基线。

同时，工作流不会为了体现自动化效果强制所有 Gate 通过。

对于真实环境样本、外部埋点平台证据或高风险写操作仍未闭合的场景，应继续保留 BLOCKED 或待补证状态。

这也是工作流质量控制的一部分：

> **没有证据证明完成，就不把“AI 已执行”包装成“需求已交付”。**

## 8. 【继续展开】

### 8.1 Test Case 也是 Agent 生成的，怎么避免 AI 自己出题、自己写代码、自己判卷？

需要继续区分需求事实、Test Case 合同、执行 Agent 和 Gate Review，并通过人工审查关键 Case、负向断言和独立运行证据降低同源偏差。

### 8.2 为什么一定要 Test Case 前置？

因为代码完成后再生成测试，很容易受到当前实现影响。前置测试的核心价值是让“什么叫正确”先于“代码怎么实现”。

### 8.3 Mock 自动化具体怎么做？Mock 结果为什么可信？

重点回答 Mock Rule 如何从接口合同和 Test Case 产生、如何确认规则命中，以及 Mock 能证明什么、不能证明什么。

### 8.4 33% 的效率提升是怎么算出来的？

必须说明 baseline、统计范围、样本数量和包含哪些研发阶段。若无法提供稳定统计口径，应主动说明这是当前需求验证中的阶段性数据。

### 8.5 为什么还需要人工 Gate？

因为需求歧义、关键业务规则、生产发布和高风险副作用都具有较高错误成本。AI 适合规模化执行，但最终责任不能完全委托给模型。

### 8.6 什么样的工作值得沉淀成 Skill？

重点回答：重复和高价值只是前提，还要判断方法是否已经稳定，以及执行时是否仍然需要 Agent 根据上下文做语义判断。完全确定的计算、转换和校验应优先下沉成 Script / Tool；可复用且仍需组合知识、工具和动态判断的方法才更适合 Skill。

完整项目面试回答见：[Skill 如何判断是否值得沉淀以及如何设计高质量 Skill](./Skill如何判断是否值得沉淀以及如何设计高质量Skill.md)。

通用知识框架见：[Agent Skill 适合沉淀重复且仍需语义判断的稳定任务方法](../../Full-Stack-AI-NOTES/QA/Agent%20Skill%20适合沉淀重复且仍需语义判断的稳定任务方法.md)。
