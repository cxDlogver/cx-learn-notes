# Skill 如何判断是否值得沉淀以及如何设计高质量 Skill

## 【提问】

你简历中提到参与多类 Skill 的设计与建设，也做过“如何让 Agent 可靠执行 Skill”的专项调研。

如果让你判断一个工作是否值得沉淀成 Skill，你会怎么判断？Skill 和 Prompt、SOP、Script、Tool 有什么区别？一个高质量 Skill 应该具备哪些特征？

---

## 【回答框架】

这道题首先回答的是 **Skill 的适用边界和设计方法**，不是介绍某一个具体 Skill。

回答应该沿着同一条判断链展开：

~~~text
先判断一个工作是否值得沉淀
        ↓
是否重复出现并具有复用价值
        ↓
是否已经形成相对稳定的方法
        ↓
执行时是否仍然需要 Agent 根据上下文判断
        ↓
如果适合 Skill，再设计触发、主流程、资源和完成条件
        ↓
把确定性的部分继续下沉到 Script / Tool / Verifier
        ↓
通过真实任务持续验证和迭代
~~~

项目中的 Mock Skill、前端增量覆盖率 Skill 和可靠 Skill 调研只用于证明这些判断为什么成立，不作为回答主线本身。

---

## 【标准回答】

我不会把 Skill 理解成一个更长的 Prompt，也不会把所有重复工作都直接沉淀成 Skill。

我更倾向把 Skill 理解成：**把一类重复任务中已经验证过的稳定方法，沉淀成 Agent 可以按需发现、复用和持续演进的执行能力。**

因此，判断一个工作是否值得做成 Skill，我首先会看三个条件，而且这三个条件是有顺序的。

第一，要先判断这个工作是不是会重复出现，并且重复的价值是否足够高。Skill 本身也需要维护触发条件、执行流程、参考资料、脚本、模板和验证方式。如果只是一次性的临时任务，直接通过 Prompt、现有 Tool 或临时 Script 解决通常更合适。只有当同类问题会持续出现，并且重复处理的成本已经明显高于维护 Skill 的成本时，才有长期沉淀的价值。

第二，在“重复出现”之外，还要判断这个问题是不是已经形成了相对稳定的方法。重复并不等于可以抽象。如果每一次任务的输入、判断过程、执行路径和完成标准都完全不同，说明我们还处在探索阶段，这时过早抽象往往只会把大量例外和临时规则堆进 Skill。真正适合沉淀的情况是：具体参数和业务上下文会变化，但是识别问题的方法、主要处理步骤、关键分支和完成标准已经比较稳定。

第三，还要继续判断这套方法执行时是否仍然需要 Agent 根据上下文做语义判断。这是 Skill 和 Script、Tool 之间最重要的边界。如果一个过程已经能够表示成：

~~~text
确定输入
→ 确定执行
→ 确定输出
~~~

例如检查文件是否存在、验证 JSON Schema、执行固定测试命令、计算覆盖率是否超过阈值，这些事情没有必要每次都让模型重新理解，更适合直接下沉成 Script 或 Tool。

而如果任务中仍然存在这样的判断：

~~~text
当前未覆盖代码对应哪个业务场景？
应该操作页面上的哪个状态才能触发这段代码？
多个候选方案中哪个更适合当前上下文？
当前证据是否真正支持某个业务结论？
~~~

这些问题需要理解源码、页面、业务语义或者运行环境，无法提前把所有分支穷举出来，就更适合由 Agent 负责。

所以我判断 Skill 的核心不是“这个事情是否重复”，而是：

> **它是否是一类重复、高价值、已经形成稳定方法，但执行过程中仍然需要模型理解上下文并做动态判断的任务。**

这个判断也能把 Skill 和 Prompt、SOP、Script、Tool 的职责区分开。

Prompt 或 Context 更多解决的是当前一次任务的目标和上下文；SOP 或 Reference 主要保存固定流程、规则和知识，供人或 Agent 阅读；Script 负责确定性的计算、转换和校验；Tool 或 MCP 给 Agent 提供真实的外部动作，例如查询接口、操作浏览器、运行命令或者读取覆盖率；Skill 则站在这些能力之上，描述面对某一类任务时，应该怎样组织知识、判断和 Tool 完成目标。

因此它们不是互斥关系。一个成熟的 Skill 往往正是由这些能力组合出来的：

~~~text
SKILL.md
→ 保存稳定的任务方法、步骤和判断条件

references/
→ 保存详细领域知识、接口说明、Schema 和案例

assets/
→ 保存可以直接复用的模板或固定产物骨架

scripts/
→ 执行重复且结果确定的计算、转换和检查

Tool / MCP
→ 操作真实外部系统
~~~

在我实际参与的 Skill 场景里，这个区别比较明显。比如前端增量覆盖率场景中，“获取哪些文件没有覆盖”“某一行是否被覆盖”“当前覆盖率是否超过阈值”都属于确定性数据，可以由覆盖率平台和固定规则直接得到；但是“这一段未覆盖代码对应页面上的什么业务行为，应该怎样操作真实页面才能触发”仍然需要理解源码和页面状态，这部分才适合交给 Agent。这里 Tool 提供查询覆盖率和操作浏览器的能力，Skill 则负责把这些能力组织成一套持续定位并补齐覆盖缺口的方法。

当确认一个问题适合 Skill 以后，下一步才是设计 Skill 本身。

我认为高质量 Skill 首先要解决的是 **什么时候应该被使用**。因为 Skill 如果没有被正确发现，后面的流程写得再完整也没有意义。通常模型会先看到 Skill 的名称和 description，再根据当前任务决定是否加载完整内容，所以 description 不能只写“这是一个 coverage helper”，而应该说明它解决什么问题、在哪些场景下应该使用，以及必要时哪些场景不适用。

Skill 被触发以后，主文件应该保存真正影响执行的稳定主线，而不是把所有背景资料都塞进去。也就是要让 Agent 能够从主文件里直接知道：

~~~text
当前任务目标是什么
输入是什么
第一步做什么
不同情况怎样分支
需要使用哪些 Tool 或资源
产生什么输出
遇到什么情况应该停止
什么条件下才算完成
~~~

详细的 API 定义、字段说明、大量示例和业务资料可以按需放进 Reference；固定产物使用 Template 或 Asset；确定的计算和校验放进 Script。这样做不是单纯为了减少 Token，而是为了让 Agent 在真正做决策时看到的是稳定的主流程，而不是被大量背景信息稀释。

这里还需要继续处理一个重要问题：**Skill 中并不是所有规则都应该保留为自然语言。**

一条规则应该以什么形式落地，取决于它到底需要多少模型自由度。

如果规则依赖业务语义和现场上下文，例如“根据当前代码判断需要触发什么业务路径”，就应该保留给 Agent；如果输入输出结构已经固定，可以使用 Schema 或 Template；如果执行过程和结果已经完全确定，就应该使用 Script；如果需要操作外部真实系统，则通过 Tool 或 MCP；如果某个完成条件绝对不能被绕过，就不能只依赖 Skill 里的自然语言说明，而应该进一步下沉到 Verifier、Gate、Hook 或 Runtime Policy。

例如在 Skill 里写：

> 代码修改以后必须运行测试。

这仍然是一条需要模型读取、记住并主动执行的自然语言规则。即使 Agent 能复述这条要求，在长任务中仍然可能用自己的判断替代规定动作，或者在没有真正执行测试时提前宣布完成。

所以更可靠的方式是把结果变成系统可以检查的事实，例如：

~~~text
test_executed = true
test_result = PASS
~~~

然后让确定性的检查决定是否允许任务继续。

因此，高质量 Skill 的设计不能停留在“Prompt 写得够不够详细”，而应该继续回答：

> **哪些步骤必须依赖 Agent 的智能判断，哪些规则其实已经能够被结构化、程序化和确定性验证？**

这也是我后续做“如何让 Agent 可靠执行 Skill”专项调研时得到的一个重要结论。真实执行中发现，单纯把“必须”“禁止”“完成前检查”写得更强，并不能消除模型执行的不确定性。更有效的做法是把固定字段、模板、脚本校验、结构化状态和不能绕过的 Gate 结合起来，让模型只保留真正需要语义推理的自由度。

这个原则也可以用我做过的 Mock Skill 来验证。头达敏感数据权限需求涉及多个接口和多种权限状态，人工调试时需要反复寻找接口响应、修改字段、切换状态和刷新页面。这个问题具有明显重复性，而且“根据目标权限状态统一修改对应响应”已经形成稳定方法，因此适合沉淀。但不同接口、字段和当前调试目标又会变化，仍然需要 Agent 根据当前任务选择规则和修改位置，所以它没有被简单收敛成一个完全固定的 Script。这个实践真正支持的是前面的判断：**Skill 适合封装稳定方法，而不是把所有执行步骤都强行模型化或者全部脚本化。**

最后，我认为 Skill 也不是设计完成以后就固定不变。它本身应该通过真实任务持续演进。

一个比较合理的过程是：

~~~text
真实重复任务
        ↓
发现其中稳定的方法
        ↓
形成 Skill V1
        ↓
放回真实 Case 执行
        ↓
观察失败发生在哪里
        ↓
判断是触发不准确、流程不清、知识缺失、
Tool 使用错误、状态丢失还是完成条件不可信
        ↓
调整 description / instructions / references /
scripts / verifier
        ↓
重新用代表性 Case 做验证
~~~

所以我评价一个 Skill 的质量，不会只看它的 Markdown 写得是否详细，而会看它能不能在代表性的真实任务中被正确触发、按照预期的方法推进，并稳定地产生满足完成标准的结果。

最终我会把这道题收束成一句话：

> **一个工作值得沉淀成 Skill，不是因为它“重复”或者“复杂”，而是因为它已经形成了可复用的稳定方法，同时执行中仍然存在需要 Agent 理解上下文和动态判断的部分。Skill 应该负责组织这套方法，而能够确定执行和验证的部分继续交给 Script、Tool、Schema 或 Gate。这样 Skill 才不是一段越来越长的 Prompt，而是真正可复用、可验证、可迭代的 Agent 工程能力。**

## 【项目证据】

上面的判断可以由当前实习材料中的三类实践支撑，但这些实践用于证明方法，不替代回答本身。

### 【Mock Skill 证明“稳定方法 + 动态判断”适合 Skill】

头达敏感数据权限需求涉及多个接口以及多种权限状态。人工调试需要反复定位接口响应、修改字段、切换权限状态和重新验证。

当前答辩材料记录的 Mock Skill 将接口规则和权限状态映射集中维护，由 Agent 根据当前目标状态批量修改 Chrome Local Overrides 关联的响应文件，再通过真实页面请求验证页面状态。

这个案例能够证明：工作本身具有高重复性和稳定方法，但不同接口和字段仍需要结合当前任务判断，因此适合由 Skill 组织，而不是只依赖一次性 Prompt 或完全固定 Script。

### 【前端增量覆盖率 Skill 证明 Skill 可以组合确定性能力与 Agent 判断】

该 Skill 通过华佗 `branch/files` 获取变更文件覆盖率，通过 `branch/code` 定位未覆盖代码；覆盖率平台负责提供确定性数据，Agent 负责理解未覆盖代码对应的业务路径，再调用 Chrome DevTools MCP 操作真实页面触发对应分支。

当前答辩材料保留了多轮覆盖率提升记录：

~~~text
44.25% → 74.62% → 82.18% → 85.15%
85.15% → 88.60% → 89.56%
89.56% → 91.28%
~~~

这个案例支持的不是“Skill 一定可以提高覆盖率”，而是说明一个 Skill 可以把确定性数据查询、Agent 语义判断和外部 Tool 操作组织成一套稳定方法。

### 【可靠 Skill 调研证明自然语言规则仍需要工程约束】

后续 AI Coding 工作流实践中又暴露出：即使 Skill 已明确规定某些步骤必须执行，Agent 仍可能遗漏步骤、替代规定动作或提前宣布完成。

因此进一步形成了 [《如何编写让 Agent 可靠执行的 Skill》](../如何让Agent可靠执行Skill-汇报分享.md)，重点分析自然语言软约束、结构化合同、脚本校验、状态记录和 Gate 回溯等机制。

这部分实践支撑的是回答后半段：**高质量 Skill 不仅要告诉 Agent 怎么做，还要识别哪些规则应该继续下沉成确定性工程机制。**

## 【个人贡献边界】

当前仓库能够确认的个人实践包括：

- 在真实前端需求中参与沉淀 Mock Skill；
- 使用和完善前端增量覆盖率 Skill，将覆盖率查询、未覆盖代码定位与真实页面操作组织起来；
- 针对 Agent 执行 Skill 时可能遗漏步骤、绕过检查和提前结束的问题，完成可靠 Skill 设计调研并形成分享材料。

这些材料可以支持：

> **参与 Skill 的实际设计、使用、问题发现和方法沉淀。**

但不能扩大成：

> 独立建设了团队统一 Skill Platform、Skill Runtime 或完整 Skill Registry 基础设施。
