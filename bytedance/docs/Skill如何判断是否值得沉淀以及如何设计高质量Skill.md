# Skill 如何判断是否值得沉淀以及如何设计高质量 Skill

## 【提问】

你简历中提到参与多类 Skill 的设计与建设，也做过“如何让 Agent 可靠执行 Skill”的专项调研。

如果让你判断一个工作是否值得沉淀成 Skill，你会怎么判断？Skill 和 Prompt、SOP、Script、Tool 有什么区别？一个高质量 Skill 应该具备哪些特征？

---

## 【回答框架】

回答时先讲通用判断标准，再落到项目实践，不要一开始只介绍某个具体 Skill。

~~~text
先判断任务性质
        ↓
是否重复且有复用价值？
        ↓
是否已经形成稳定方法？
        ↓
执行时是否仍需要 Agent 结合上下文判断？
        ↓

一次性说明
→ Prompt / Context

稳定流程说明
→ SOP / Reference

确定输入 → 确定执行 → 确定输出
→ Script / Tool

重复任务 + 稳定方法 + 仍需语义判断
→ Skill
~~~

然后继续说明高质量 Skill 的组成：

~~~text
触发条件
→ description

稳定主流程
→ SKILL.md

详细知识
→ references/

固定模板
→ assets/

确定性动作 / 校验
→ scripts/

真实外部操作
→ Tool / MCP

不能绕过的完成条件
→ Verifier / Gate / Hook
~~~

最后再结合项目中的 Mock Skill、前端增量覆盖率 Skill 和可靠 Skill 调研说明。

---

## 【标准回答】

我不会把 Skill 理解成一个更长的 Prompt，而是把它理解成：

> **把一类重复任务中已经验证过的稳定方法，沉淀成 Agent 可以按需发现、复用和持续演进的执行能力。**

所以我判断一个工作是否值得沉淀成 Skill，主要看三个条件。

第一，这个工作是不是会重复出现，而且具有足够高的复用价值。如果只是一次性的临时任务，直接通过 Prompt、现有 Tool 或临时 Script 处理通常更合适；Skill 本身也需要维护触发条件、流程、资源和验证方式，因此只有持续重复的问题才值得长期沉淀。

第二，这个问题是不是已经形成相对稳定的方法。Skill 不是把所有经验都提前抽象。如果每次任务的输入、判断过程和完成标准都完全不同，说明方法还没有稳定，这时应该先通过真实任务继续探索。更适合 Skill 的情况是：具体参数和上下文会变化，但问题识别方式、主要步骤、分支逻辑和完成标准已经比较稳定。

第三，执行这个方法时是不是仍然需要 Agent 根据上下文做判断。这是 Skill 和 Script 最重要的边界。如果一个过程已经能够表示为“确定输入 → 确定执行 → 确定输出”，例如检查文件是否存在、执行固定测试、验证 Schema、计算覆盖率阈值，我会优先下沉成 Script 或 Tool，而不是让模型每次重新解释。只有当任务仍然需要理解代码、页面、业务语义，动态选择 Tool 或决定下一步时，才适合保留在 Skill 中。

所以我一般会这样区分：

~~~text
Prompt / Context
→ 当前一次任务的目标和上下文

SOP / Reference
→ 固定流程和知识说明

Tool
→ Agent 可以执行什么动作

Script
→ 确定性的计算、转换或检查

Skill
→ 面对一类任务，应该怎样组织知识、判断和 Tool 完成目标
~~~

这些能力并不是互斥的。一个 Skill 往往会组合自然语言 Instructions、Reference、Template、Script 和 Tool。

高质量 Skill 首先要解决触发问题，也就是 description 要明确说明“它做什么”和“什么时候应该使用”。Skill 如果根本没有被正确发现，后面的流程写得再完整也没有意义。

Skill 被触发以后，主文件应该保留稳定的执行主线，包括输入、主要步骤、关键分支、使用哪些能力、输出以及完成条件。详细的 API、案例和领域资料可以放到 Reference，固定产物可以使用 Template，重复且能够确定执行的部分下沉成 Script，外部真实操作再调用 Tool 或 MCP。

这里我还会进一步根据规则的确定程度分配执行自由度：

~~~text
需要业务理解和语义判断
→ Agent + 自然语言规则

输入输出结构固定
→ Schema / Template

重复且结果确定
→ Script

外部真实操作
→ Tool / MCP

绝对不能绕过的完成条件
→ Verifier / Gate / Hook
~~~

因为把一句“必须执行测试”写进 Skill，并不能保证 Agent 每次一定执行。Skill 的自然语言仍然属于模型需要理解和遵守的软约束。如果某个条件是交付前绝对不能跳过的，就应该进一步把测试结果、证据状态等变成结构化事实，再通过程序检查和 Gate 控制是否允许完成。

所以一个可靠 Skill 的设计原则不是“把规则写得更强硬”，而是：

> **让 Agent 负责真正需要智能判断的部分，让确定性的工程机制负责已经能够客观执行和验证的部分。**

最后，Skill 也不是一次写完。它应该通过真实任务持续演进：

~~~text
真实重复任务
→ 抽取稳定方法
→ Skill V1
→ 执行真实 Case
→ 观察 Failure
→ 判断是触发、流程、Tool、状态还是完成判断的问题
→ 修改 Skill / Reference / Script / Verifier
→ 再做代表性回归
~~~

因此我评价一个 Skill 的质量，不会只看 Markdown 写得是否详细，而会看它是否能够在真实任务中被正确触发、稳定执行，并产出满足验收标准的结果。

## 【项目实践一：Mock Skill】

在头达敏感数据权限项目中，需求涉及多个接口以及多种权限状态。

人工调试时需要反复：

~~~text
找到接口
→ 修改响应
→ 切换权限状态
→ 刷新页面
→ 再验证
~~~

这类工作重复度很高，并且已经形成稳定方法，所以我们把它沉淀成 Mock Skill。

它的核心不是简单“改 JSON”，而是根据当前调试目标统一处理接口响应：

~~~text
指定目标权限状态
→ 读取接口和字段改写规则
→ 批量修改 Local Overrides 响应
→ 页面重新发起真实请求
→ Chrome 使用本地响应替换接口结果
→ 验证对应页面状态
~~~

这里之所以适合 Skill，而不是只做一个固定 Script，是因为不同接口、字段和权限场景仍然需要 Agent 根据当前任务选择对应规则和修改位置；而具体的文件修改、模板和固定规则则可以继续结构化或脚本化。

项目答辩材料能够确认已经沉淀权限 Mock Skill，用于批量切换权限状态进行页面调试。

## 【项目实践二：前端增量覆盖率 Skill】

第二个例子是前端增量覆盖率 Skill。

原来的人工过程是：

~~~text
查看覆盖率报告
→ 找未覆盖文件
→ 找未覆盖代码行
→ 回到页面判断怎样触发
→ 手动操作页面
→ 再重新查看覆盖率
~~~

这里同时包含确定性步骤和不确定判断。

确定性部分包括：

~~~text
获取覆盖率
定位未覆盖文件
定位未覆盖代码行
判断是否达到阈值
~~~

这些步骤可以通过覆盖率平台和固定规则执行。

但是：

> **某一段未覆盖代码应该通过页面上的什么业务行为才能真正触发？**

仍然需要结合代码、页面状态和业务交互进行判断。

因此这个问题很适合 Skill：

~~~text
华佗 branch/files
→ 获取增量覆盖率

华佗 branch/code
→ 定位未覆盖代码

Agent
→ 理解未覆盖代码对应的业务路径

Chrome DevTools MCP
→ 操作真实页面触发代码

重新获取覆盖率
→ 判断是否继续
~~~

项目答辩材料记录了这套 Skill 在真实权限需求中的使用过程，并保存了多轮覆盖率提升结果。

这个案例能够体现：

> **Tool 提供“查询覆盖率”和“操作浏览器”的能力，Skill 负责把这些能力组织成一套持续补齐覆盖率的方法。**

## 【项目实践三：可靠 Skill 设计调研】

在后续 AI Coding 工作流实践里又发现一个问题：

> 即使 Skill 已经明确写了某些步骤必须执行，Agent 仍然可能遗漏、替代规定动作或者提前判断任务完成。

因此我进一步调研了“如何编写让 Agent 可靠执行的 Skill”。

这部分得到的核心结论不是继续增加自然语言规则，而是按照可检查程度拆分：

~~~text
需要上下文判断
→ 保留自然语言

固定字段和状态
→ Template / Schema

重复、确定、可验证
→ Script

不能遗漏的完成条件
→ Gate / Hook

执行过程
→ 持续保存结构化状态和证据
~~~

仓库中的 [《如何编写让 Agent 可靠执行的 Skill》](../如何让Agent可靠执行Skill-汇报分享.md) 对这部分调研做了完整沉淀。

它和前面的 Skill 选型问题是两个层次：

~~~text
什么工作值得做成 Skill？
→ Skill 的适用边界

Skill 建好以后怎么稳定执行？
→ Skill 的可靠性工程
~~~

## 【个人贡献边界】

这里需要区分项目事实和通用能力。

仓库能够确认的个人实践包括：

- 在真实前端需求中沉淀 Mock Skill；
- 使用前端增量覆盖率 Skill 自动获取覆盖率、定位未覆盖代码并驱动页面验证；
- 针对 Agent 执行 Skill 时可能遗漏步骤、绕过检查和提前结束的问题，完成可靠 Skill 设计调研，并形成分享材料。

这些经历可以证明：

> **参与了 Skill 的实际设计、使用和方法总结。**

但不能扩大表述为：

> 独立建设了团队统一 Skill Platform、Skill Runtime 或完整的 Skill Registry 基础设施。

## 【一句话收束】

> **我判断一个工作是否应该沉淀成 Skill，主要看它是不是重复、高价值、已经形成稳定方法，同时执行过程中仍然需要 Agent 根据上下文做判断；完全确定的部分应该继续下沉成 Script、Tool 或 Verifier，而不是全部留在 Skill 的自然语言里。一个高质量 Skill 的价值，是把已经验证过的任务方法变成 Agent 可以正确发现、复用并持续演进的工程能力。**
