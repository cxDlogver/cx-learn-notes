# AI Coding 如何定位测试通过但需求验收错误

这篇回答对应 AI Coding 研发交付中的质量问题：**为什么自动化测试已经通过，最终 UAT 仍可能发现业务不符合预期，以及怎样从最早偏差阶段修复。** 回答坚持先解释通用机制、再用低业务门槛的示例论证；真实项目只作为可核验的事实依据，不以内部细节取代回答。

## 【核心判断】

AI Coding 中的“测试通过但业务不对”，不能直接归因于 Agent 没有认真测试。自动化测试检查的是**实际行为是否满足既定断言**；如果断言来自错误的需求理解，代码与测试可以一起偏离真实目标。解决问题的主线是：**先从 UAT 差异寻找最早偏差，再修复受影响的上游合同和下游产物；在下一轮交付中，通过需求澄清、验收前置和覆盖审查减少重复发生。**

整篇答案参考 PREP 的结论、原因、例证与回扣逻辑，但保持完整因果推导，不以固定四段结构截断机制。本题侧重**验收标准为什么会错以及如何纠偏**；“已有 Test Case 正确，但执行证据不足造成误判”是相邻但独立的问题，参见[AI Coding 如何保证 Agent 验收结论可信](./AI-Coding如何保证Agent验收结论可信.md)。

## 【提问】

- AI Coding 工作流中，为什么自动化测试全部通过，最终 UAT 仍可能不符合真实需求？
- 如果 Plan 与 Test Case 共同误读业务规则，应该如何定位最早偏差并修复？
- 验收前置为什么不能彻底避免边界条件遗漏？工作流如何形成持续纠偏的闭环？

## 【回答思路】

先给出判断：**成功执行测试不等于测试标准正确**。然后沿“需求事实 → 技术方案 → 任务与测试 → 实现 → 验收”解释错误向下游传播的路径。定位时从 UAT 的现象倒查“Code 是否满足 Case → Case 是否对应 Requirement → Plan 是否已经误读 → 需求是否仍需产品确认”，寻找最早出现偏差的阶段。用一个简单的列表清空按钮场景说明边界遗漏，再回到通用方法：需求澄清与场景覆盖负责前置预防，Repair 从错误源头回流并重验下游，证据门禁和人工审查负责限制错误放行。

~~~text
真实业务预期
  ↓ 定义验收依据
需求澄清与场景覆盖
  ↓
Plan / Task / Test Case → Code → Verify → UAT
                                    ↓ 发现偏差
                        反向寻找最早错误或遗漏
                                    ↓
                   修正上游规则与受影响的下游产物
                                    ↓
                            重新验证与回归
~~~

注意区分“资料没有明确规定”与“Agent 理解错了”：前者需要补充产品决策，不能把尚未确认的边界直接改写为已有需求。

## 【完整标准回答】

### 【一、用验收前置、阶段控制与问题回溯保障真实交付】

我认为，面对 AI Coding 工作流中自动化测试通过、最终验收却发现功能不符合预期的问题，不能只让 Agent 重新写代码或多跑几次测试，而需要建立一套**验收前置、阶段质量控制、跨产物追溯与问题回流修复**的机制。

真实研发通常沿需求分析、技术规划、任务拆解、代码实现和测试验收推进。每个阶段都消费上一个阶段提供的判断和产物。如果起初的需求规则不完整，后续 Plan、Task、Test Case 即使彼此一致，也可能把同一个错误持续传下去。因此质量保障首先要确定：**现在的测试究竟是在检验真实需求，还是只是在检验前面已经做出的某种实现假设。**

GitHub 的 Spec Kit 将 Specify、Clarify、Plan、Tasks、Implement、Converge 组织为可审查的阶段；其中 Clarify 用来在规划前消除规范中的歧义，Checklist 与 Analyze 用来检查需求质量和产物之间的冲突、缺口。这支持了“先确认意图，再根据规范实施和回查”的工程方法，但并不表示采用 Spec Kit 就能自动保证需求绝对正确。见 [GitHub Spec Kit 官方快速入门](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)。

### 【二、为什么测试通过仍可能与真实需求不符】

测试通过仍不符合真实需求，至少存在三种不同原因。

第一种是**需求分析发生偏差**。PRD 或设计稿可能没有完整写出状态恢复、连续操作、异常分支等约束，Agent 也可能把未经确认的假设当作既定规则。一旦被写入需求分析产物，下游就会按错误前提推进。

第二种是**技术规划和测试标准共同发生偏差**。需求本来已经明确，但 Plan 转化规则时遗漏了一个条件，而 Test Case 又完全根据 Plan 生成。此时代码可以满足 Case，Case 也可以满足 Plan，却没有真正覆盖 Requirement。这里的核心问题是测试合同的来源错误，而不是测试执行次数不够。GitHub Spec Kit 的跨产物分析强调检查规范、计划和任务之间的缺口与冲突，属于降低此类风险的一种机制。[GitHub Spec Kit 官方文档](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)。

第三种是**正确的 Test Case 没有得到正确执行**。例如预期要求按钮操作后不得发出删除请求，但 Agent 只观察到了页面更新，就自行判为 PASS。这时才应重点检查实际观察值、证据来源、断言覆盖与 Gate 条件。它和前两种属于不同问题：前两种要纠正“什么算对”，第三种要纠正“是否真的证明它对”。详细证据机制参见[Agent 验收结论可信性](./AI-Coding如何保证Agent验收结论可信.md)。

因此，出现 UAT 问题时应从实际症状出发，确定是需求—验收合同的偏差，还是实现／执行偏差，而不能直接让 Agent 依据原有测试重新修复。

### 【三、从 UAT 的差异反向定位最早错误阶段】

我会先固定 UAT 的复现步骤、操作前置状态、预期行为和实际表现，确认真正与产品要求冲突的是什么。随后沿依赖链反向追踪，而不是盲目重复整个交付过程。

先比较 Code 与 Test Case：如果验收断言明确、正确，而实际实现不符，就从代码阶段修复并回归。如果代码确实满足当前 Case，则继续比较 Case 与已确认的 Requirement，判断是否有缺失的边界场景或者错误的预期。如果 Case 有问题，还要比较 Task 和 Plan：若 Plan 已经遗漏对应业务状态，就必须从 Plan 开始修复，而非只改断言。如果连原始资料也没有对该场景给出结论，就需要向产品或业务负责人确认规则，补充正式需求事实，再修改下游。

这个过程要寻找的是**最早出错或最早缺少必要约束的阶段**。不能把“缺少产品决策”强行写成“Agent 已误读”，也不能为了让测试变绿而把实际产品预期改成当前实现。

仓库中的真实交付记录提供了这条追踪方法的对应实践：在“内容活动激励管控线上化”的 **REPAIR-005** 中，验收发现一键移除后整个汇总操作区消失。回溯发现 Plan 只提出保留导出入口，没有完整描述汇总文案和移除按钮的保留规则，Task 与 Test Case 继续沿用了这一口径；修正从 Plan 开始，更新 Task 与 Test Case，并经过代码修复、Verify 和 Design 复验，结果记录为 `PASS_WITH_NOTES`。该结果只代表本次返修记录中的状态，并不等于整个需求所有真实环境条件都已经验收。[项目交付记录：3.11 Repair 阶段](../AI交付记录-运营平台内容活动激励管控线上化交付过程记录.md)、[项目面试问答](./AI-Coding工作流面试问答.md)。

### 【四、清空按钮场景说明连续操作边界如何遗漏】

为了让不熟悉业务背景的面试官快速理解，可以采用一个**为解释机制而简化的假设场景（不是原项目故障原样复现）**，不把演绎细节冒充已核验的项目故障。

假设产品希望实现一个列表的“清空”按钮：按钮始终显示，列表可以重新加载数据，用户应该能够反复清空。若需求分析只写了“点击清空后数据变为空”，没有进一步明确按钮在空状态、重新加载状态下的行为，AI 就可能把按钮可见性错误地与某个列表状态绑定：第一次清空后按钮消失，重新加载以后仍未恢复，于是清空变成只能操作一次。

如果 Test Case 只检查“清空后列表为空”，这条 Case 可以通过，却没有验证连续操作的完整行为。问题根源就可能是**对状态迁移和连续操作场景的覆盖不足**。修正时应先确认按钮是否始终显示的产品规则，再补充“加载 → 清空 → 空状态仍可见 → 重新加载 → 再次清空”的验收场景，最后修正代码并重新验证。这是说明机制的通用简化案例；原始真实项目的可核验范围仍以 REPAIR-005 记录为准。

Cucumber 的 Gherkin 参考将 Given、When、Then 分别用于表达前置条件、操作和预期结果；但这一格式只能让**已想到的场景**更清楚，不能自动发现所有遗漏。[Cucumber Gherkin 官方参考](https://cucumber.io/docs/gherkin/reference/)。因此，此例的重要结论不是多写一条“空列表”测试，而是说明前置的场景发现与后续的真实反馈必须一起工作。

### 【五、通过需求澄清与验收前置减少共同误读】

从这个问题可以反推出两项关键改进。

第一项是需求澄清：Agent 应从 PRD、设计稿、评论和产品确认记录中提取可核对的业务事实，按触发条件、操作结果、状态切换、禁止行为和重要异常边界识别歧义。遇到会改变交付范围或测试结论的问题，先请求产品与研发确认，不让模型自行补充成“既定需求”。Cucumber 的 [Example Mapping](https://cucumber.io/docs/bdd/example-mapping/) 官方文档强调在开发之前通过具体实例讨论验收规则、未决问题和范围，促进共同理解；它是可借鉴的方法，而非已证明本仓库采用该工具的事实。

第二项是验收前置：Test Case 应从已确认的需求、业务场景和可观察行为形成，而不能只从 Plan 或已经生成的代码反推。先确立“什么才算正确”，再让技术方案回答“怎样实现”。建立 `Requirement → Scenario → Test Case` 的映射，既查有没有需求缺少测试，也查有没有测试断言找不到业务依据。

这两项不是要求第一轮就穷尽全部状态。真正的目标是让关键假设可见，让高风险规则在实现前得到确认，把可以预见的覆盖缺口尽可能提前处理。**需求已确认也不意味着后续不得修订；新发现的事实应进入变更与回流机制。**

### 【六、通过 Repair 将修复同步回流到上游规范】

当 UAT 报告新的遗漏时，我会首先确定它究竟是在补充产品未说明的规则，还是纠正既有规则被错误转换的情况；然后定位最早需要调整的产物，并同步更新其下游依赖。

例如 Plan 遗漏了按钮清空后的状态要求，就不应该只在 Code 中加一个条件判断，也不应该仅把新断言塞进 Test Case。应把明确的业务规则先写回 Plan 或更上游的需求事实，再同步修正 Task、Test Case 和实现，最后重新执行原问题复现、相关正反向场景以及必要的回归验证。

这与 GitHub Spec Kit 的两种官方方法相呼应：其 [Living Spec](https://github.github.io/spec-kit/guides/evolving-specs.html) 指出，当预期行为改变时先更新规范，再使 Plan 和 Task 与之对齐；其 [Bug Fixing](https://github.github.com/spec-kit/guides/bugfix.html) 则强调先记录症状和根因、限定修复范围，再重跑原始复现与有关测试。两者是通用方法依据，仓库中实际执行的 Repair 阶段与之具有相近目标，但并非宣称团队直接运行了 Spec Kit。

验证需要同时确认三件事：修正后的需求和 Case 表达真实业务预期；代码达到了这些 Case；相关旧行为没有因为本次更改而退化。如果仍缺真实环境、关键数据或业务确认，应如实记录待补证状态，不能把模拟环境的 PASS 提升为正式交付结论。

### 【七、用证据门禁与人工复核阻止错误放行】

即使 Requirement 与 Test Case 的来源已经明确，Agent 仍可能在执行时采集不充分的证据。因此，完成每条 Case 时还要把预期断言、实际观察值和证据对应起来，借助程序化校验处理可判定的结构条件，对复杂业务语义和最终交付保留必要的人工判断。这能降低“测试没做完就自报 PASS”的问题。

但不能反过来推断“证据完整，需求一定正确”。形式检查、截图和日志只能证明它们实际覆盖的行为，无法替产品决定没有确认的业务规则。当前工作流也明确区分 Mock 验证、真实环境验证与最终交付状态，不能由一项阶段性通过推断整体需求已完成。[项目交付记录：交付结果与证据边界](../AI交付记录-运营平台内容活动激励管控线上化交付过程记录.md)。

因此，**验收标准正确性**与**验收执行可信性**是两道连续但不同的质量关：前者约束“应该验证什么”，后者约束“如何证明已满足”。两者都成立，才有资格结合实际覆盖范围判断是否交付。

### 【八、总结：降低偏差传播，让真实反馈持续修正研发合同】

所以，我认为 AI Coding 的质量保障不是要求 Agent 第一次就生成完美无缺的需求和用例，而是建立一套**前期尽量减少错误、过程中限制错误传播、后期能够回溯修正**的交付体系。

需求澄清与验收前置解决“正确的目标如何进入流程”；需求到 Case 的覆盖关系解决“关键状态有没有被遗漏”；Repair 与回归验证解决“新发现的偏差怎样反向修复整个依赖链”；执行证据和人工 Gate 则防止尚未验证的结论被提前放行。

这样即使在 UAT 阶段发现边界遗漏，系统也不必退回到随意试错，而是能确定问题的依据、修改的范围与下一次验收应怎样证明正确。这才是端到端 AI Coding 工作流相比单纯自动写代码更有价值的工程能力。
