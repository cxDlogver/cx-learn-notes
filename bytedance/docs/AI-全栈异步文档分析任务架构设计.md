# AI 全栈开发中的异步文档分析任务架构设计

> 本文为面试题完整存档，保留**原始题目、原始回答要点和完整标准回答**。其中 AI 文档分析平台是用于系统设计答辩的假设业务场景，不代表字节项目中已经实际实现该平台。参考资料在相关论述处就近引用。

## 【原始面试题目】

**第 2 题｜AI 全栈开发中的异步任务架构设计**

**考察方向：** 全栈系统设计 · 服务端架构 · 任务状态管理与可靠性

假设你需要开发一个 AI 文档分析平台。

用户在前端上传一份文档，点击“开始分析”后，服务端会调用 Agent 对文档进行处理，并最终生成一份分析报告。

这个过程通常需要 **1～3 分钟**，同时需要满足以下要求：

- 用户提交任务后，前端能够查看分析进度和最终结果。
- 用户即使刷新页面或者暂时关闭浏览器，后台任务也能够继续执行。
- 用户重复点击提交按钮，不应该导致同一个任务被重复执行。
- 如果分析过程中出现异常，系统能够正确记录失败状态，并支持后续重试。

**问题：如果让你从零设计这个功能，你会如何构建前端、服务端与 Agent 执行系统之间的完整架构，并说明一次分析任务从创建到最终完成的执行过程？**

## 【原始回答要点】

1. **整体架构**：前端、API 服务、Agent 执行模块和数据存储各自承担什么职责？为什么这样划分？
2. **请求链路**：用户点击开始分析后，前端请求如何进入服务端？服务端应该在什么时候向前端返回响应？
3. **任务生命周期**：任务创建、执行、完成或失败时，状态如何管理？前端如何获知任务进度？
4. **可靠性设计**：如何处理重复提交、执行异常和页面刷新，避免任务丢失或重复执行？

**回答要求：** 先建立完整的系统架构，再沿着一次真实任务的执行过程逐步说明各模块如何协作，最后补充异常处理与设计取舍。

---

## 【完整标准回答】

### 一、核心观点：通过异步任务机制，将用户请求与 Agent 执行过程解耦

我认为，这类 AI 文档分析平台的核心设计思想是：**将用户提交请求和后台 Agent 执行过程分离，通过持久化任务状态、异步执行队列以及任务状态查询机制，保证长时间运行的任务不会依赖浏览器连接，同时能够处理重复提交、执行失败和任务恢复。**

因为一次文档分析可能需要 1～3 分钟，如果直接在 HTTP 请求中等待 Agent 执行完成，就会产生几个问题。

首先，用户必须持续等待请求返回。虽然异步 HTTP 处理并不意味着整个服务线程一直被阻塞，但长时间保持请求仍然会占用连接等系统资源，也可能受到客户端、网关和服务端超时限制。

其次，如果浏览器刷新、网络中断或者服务端实例重启，直接依赖这次请求维护的执行过程就很难保证任务状态和执行结果得到可靠恢复。

最后，随着同时分析的文档数量增加，Agent 对外部模型的调用、文档解析以及结果生成都可能消耗较多时间和资源。如果没有独立的任务调度与并发控制机制，就容易影响普通 API 请求的响应能力。

因此，我会将系统设计成两条相互协作的链路：

**第一条是同步请求链路**，负责接收用户操作、完成身份与参数校验、创建任务，并尽快返回任务标识。

**第二条是异步任务链路**，负责从任务队列获取任务、执行文档分析、更新任务状态，并持久化最终结果。

这样的设计将“创建任务成功”和“分析任务完成”明确区分。HTTP `202 Accepted` 适合表达请求已被接受、但后续处理尚未完成的语义。需要强调，**HTTP 202 本身不保证任务最终会执行成功；可靠接收与恢复能力需要系统自行实现**。[参考：MDN，202 Accepted](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/202)。

### 二、整体架构：将系统划分为交互、任务管理、异步执行和数据持久化四个部分

我会先建立下面这套架构：

~~~text
前端 Web 应用
  └─ 上传文档、提交分析、显示进度、查询报告
         │ HTTP
         ▼
API 服务
  ├─ 身份校验、权限检查、文件登记
  ├─ 创建任务、查询任务、返回结果
  │      │
  │      ├─ 数据库：保存任务状态、归属、进度、结果引用
  │      ├─ 对象存储：保存原始文档和分析报告
  │      └─ 任务队列：分发待执行任务、控制消费
  │                            │
  └────────────────────────────┤
                               ▼
                         Worker 后台任务执行服务
                           ├─ 领取任务
                           ├─ 校验执行资格
                           ├─ 调用 Agent
                           └─ 更新进度和结果
                                     │
                                     ▼
                            Agent / 文档处理能力
                             ├─ 解析文档
                             ├─ 调用模型
                             └─ 生成分析报告
~~~

这个架构中的几个模块各自解决不同的问题。

**前端负责用户交互，而不负责维持后台任务生命周期。** 它保存当前正在查看的任务标识，根据服务端返回的状态渲染页面。前端可以关闭，后台任务仍由服务端继续管理。

**API 服务负责请求入口与任务管理。** 它负责用户身份和资源权限校验、文档上传登记、任务创建、状态查询等轻量操作，不在创建任务的 HTTP 请求中等待完整分析执行。

**任务队列负责异步调度。** 它把待执行任务从 API 服务传递给 Worker，并为任务积压、并发执行和失败重试提供基础机制。例如 Node.js 生态可以使用 BullMQ + Redis；云环境也可以使用托管任务队列。BullMQ 官方将 Worker 定义为实际消费并处理队列任务的执行实例。[参考：BullMQ Workers](https://docs.bullmq.io/guide/workers)。

**Worker 负责执行长时间任务。** 它接收任务标识，获取文档数据，调用 Agent，并把执行结果回写到数据库。

**数据库与对象存储负责持久化。** 关系数据库保存任务状态、归属、进度、执行次数和报告引用；对象存储保存原始文件和体积较大的报告。队列主要承担调度，不应该成为唯一的业务状态来源。

这里还有一个重要的架构边界：**Worker 与 Agent 不一定是两个独立部署的微服务。**

对于早期系统，Worker 可以直接调用同一代码仓库中的 Agent 模块。只有当模型执行需要独立扩容、资源隔离或复杂的运行环境时，才有必要进一步拆分独立的 Agent 服务。

### 三、任务创建：先可靠地保存任务，再向前端返回任务标识

一次真实任务从用户上传文档开始。

对于较小的文件，前端可以通过 API 直接上传，由服务端校验后保存到对象存储。

如果需要处理较大的文件，我会优先考虑预签名 URL 上传：API 在认证后签发一个有范围和有效期限制的上传地址，前端直接将文件上传到对象存储，再通过 API 确认上传完成。

这样可以避免大文件传输长期占用应用 API 的带宽。AWS S3 官方支持预签名 URL 上传，但仍需要控制上传权限、文件完整性、对象归属和有效期。[参考：AWS S3 使用预签名 URL 上传对象](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html)。

文档保存完成后，用户点击“开始分析”，前端发送创建任务请求：

~~~http
POST /api/analysis-tasks
Idempotency-Key: req-abc123
Content-Type: application/json

{
  "documentId": "doc-1001",
  "analysisType": "summary"
}
~~~

API 服务会依次完成：

1. 确认用户身份，以及是否有权访问该文档。
2. 校验文档是否已上传成功、是否允许分析，并检查任务参数。
3. 判断同一提交请求是否已经创建过任务。
4. 将任务记录持久化，初始状态设为 `PENDING`。
5. 可靠地安排任务进入后台队列。
6. 返回 `taskId` 和状态查询地址。

正常的新任务创建成功以后，可以返回：

~~~http
HTTP/1.1 202 Accepted
Location: /api/analysis-tasks/task-1001
Content-Type: application/json

{
  "taskId": "task-1001",
  "status": "PENDING",
  "statusUrl": "/api/analysis-tasks/task-1001"
}
~~~

此时服务端表达的是**已接受并记录任务，但分析尚未完成**，而不是直接返回分析报告。`202` 只是 HTTP 响应语义，是否能从崩溃中恢复仍取决于持久化与调度设计。

前端拿到 `taskId` 以后，就可以立即进入任务详情页或者分析进度页面。

这里要特别注意：**数据库创建任务成功与消息进入队列，不天然是同一个原子操作。**

如果先写数据库，再发送队列消息，数据库写入成功后服务突然崩溃，就可能留下一个永远没有被执行的待处理任务。

因此，要求较高的系统可以使用事务性 Outbox：在同一个数据库事务中写入任务记录和待投递事件，再由独立投递程序将事件发送到队列，并根据投递结果更新事件状态。这样即使服务中途崩溃，也可以继续投递未完成事件。

AWS Transactional Outbox 官方设计指南专门讨论了数据库写入与消息发布之间的双写一致性问题，同时指出事件可能重复发送，消费者仍须具备幂等处理能力。[参考：AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

### 四、异步执行：通过任务状态机管理完整生命周期

当任务被可靠地投递到队列以后，后台 Worker 就可以独立执行分析过程。

我会先为每一个任务建立明确的状态机，而不是仅仅使用一个 `isLoading` 布尔值表示是否正在执行。

~~~text
                  创建任务
                     │
                     ▼
               PENDING 待处理
                     │ Worker 领取任务
                     ▼
               RUNNING 执行中
                 /         \
           执行成功       执行失败
              │               │
              ▼               ▼
       SUCCEEDED 完成     FAILED 失败
                              │
                  符合重试条件且有剩余额度
                              │
                              ▼
                  RETRY_WAITING / PENDING
                              │
                              └─ 再次进入 RUNNING
~~~

对于临时错误，可以进入等待重试；取消是可选的独立终态，这里为突出主流程未绘出。

各个状态有明确含义：

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| `PENDING` | 任务已经创建，等待执行 | 等待 Worker 领取 |
| `RUNNING` | Worker 正在执行文档分析 | 更新阶段与进度 |
| `SUCCEEDED` | 分析完成，报告已保存 | 提供报告查询 |
| `FAILED` | 达到失败条件，当前任务无法继续 | 保存错误原因，决定是否允许重试 |

在实际工程中，还可以增加 `RETRY_WAITING`、`CANCELLED` 等状态，并区分一次执行尝试与整个任务的生命周期。

为了使状态能够跨进程和页面恢复，我会在数据库中保存类似这样的任务记录：

~~~text
task_id           任务唯一标识
user_id           所属用户
document_id       原始文档标识
status            任务状态
stage             当前分析阶段
progress          可选的进度信息
attempt_count     已执行次数
result_ref        最终分析报告的存储引用
error_code        失败类型
created_at        创建时间
started_at        开始时间
finished_at       结束时间
updated_at        最后更新时间
~~~

Worker 领取任务后，先原子地确认自己是否有权执行该任务，并将状态从 `PENDING` 更新为 `RUNNING`。

然后开始实际分析，例如：

~~~text
领取任务
   ↓
读取原始文档
   ↓
提取文档内容
   ↓
调用 Agent 分析
   ↓
生成分析报告
   ↓
保存报告
   ↓
将任务标记为 SUCCEEDED
~~~

这里的 Agent 内部可以存在自己的推理、工具调用和规划循环，但外层 Worker 仍然负责执行任务的生命周期管理，包括超时、异常处理和结果持久化。

分析成功以后，必须先确认最终报告已经成功保存，再将任务标记为 `SUCCEEDED`。否则就可能出现前端显示成功，但实际查询不到报告的情况。

此外，任务状态更新必须有合法的状态迁移约束，例如通过数据库条件更新或版本号检查，避免两个 Worker 同时更新同一任务，或者较旧的执行结果覆盖新的任务状态。

BullMQ 等任务系统也提供 Worker 处理、进度事件和失败处理等基础能力，但业务任务状态是否正确，仍需要应用层保证。[参考：BullMQ Workers](https://docs.bullmq.io/guide/workers)、[参考：BullMQ Events](https://docs.bullmq.io/guide/events)。

### 五、前端状态同步：以服务端持久化状态为准，支持刷新和断线恢复

当服务端开始异步执行以后，前端就不能再通过最初的创建请求获取最终结果，而应该根据 `taskId` 单独查询任务状态。

例如：

~~~http
GET /api/analysis-tasks/task-1001
~~~

返回：

~~~json
{
  "taskId": "task-1001",
  "status": "RUNNING",
  "stage": "analyzing",
  "progress": {
    "message": "正在分析文档内容"
  },
  "resultRef": null
}
~~~

这里需要区分两种数据：

**服务端的任务状态是持久化的业务事实；前端展示的进度是根据这些事实构建的 UI 状态。**

因此，我会优先使用服务端状态来恢复页面，而不是依赖前端内存中的 `loading` 标志。

用户刷新页面时，只要 URL 或任务列表中能够找到 `taskId`，前端就可以重新查询任务状态：

~~~text
打开任务详情页
       ↓
读取 taskId
       ↓
请求服务端任务状态
       ↓
PENDING   → 显示等待执行
RUNNING   → 显示分析进度
SUCCEEDED → 展示报告
FAILED    → 展示失败原因和重试入口
~~~

即使浏览器关闭，只要后台任务独立运行且状态已经持久化，任务就不依赖页面继续存在。

#### 【如何选择轮询、SSE 和 WebSocket】

前端获取进度主要有三种方案：

| 方案 | 机制 | 适用场景 |
| --- | --- | --- |
| 轮询 | 前端定期请求任务状态 | 任务数量少、进度变化不频繁 |
| SSE | 服务端单向推送状态事件 | 主要需要服务端向前端推送进度 |
| WebSocket | 双向长连接通信 | 需要频繁双向交互或实时控制 |

对于 1～3 分钟的文档分析任务，**我会先选择轮询，复杂度最低；如果需要更实时的阶段反馈，再考虑 SSE。**

SSE 比较适合这个场景，因为分析进度通常主要从服务端发往浏览器，不需要持续的双向消息交换。浏览器 `EventSource` 支持断线重连，配合事件 ID 和服务端事件保留能力，可以实现按事件位置恢复。[参考：MDN，Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

但无论选择哪种通信方式，都必须注意：

**SSE 或 WebSocket 只是状态通知通道，不应该成为任务状态唯一的存储位置。**

如果推送连接发生中断，前端仍然应该能够通过 `GET /tasks/{taskId}` 查询最新状态。重新建立推送连接时，也应以服务端状态为准进行同步。

此外，Agent 的推理进度往往无法准确量化成百分比，所以实际产品中可以优先展示“文档解析中、内容分析中、报告生成中”等阶段，而不是编造一个准确性无法保证的百分比。

### 六、可靠性设计：分别解决重复提交、重复执行和任务丢失

这类系统最容易被面试官继续追问的，其实不是怎么调用 Agent，而是系统遇到异常以后能否维持正确的业务状态。

我会从三个不同层次处理。

#### 【第一，重复提交通过服务端幂等控制】

前端可以在用户点击提交以后禁用按钮，减少重复操作，但这只是体验优化，不能作为最终的重复提交保障。

因为用户可能刷新页面、网络重试、重复发送请求，甚至同时在多个页面提交。

真正的幂等应该由服务端完成。

我会让前端为一次用户提交意图生成 `Idempotency-Key`。服务端结合用户身份、任务类型等作用域，在数据库建立唯一约束，并将该键绑定到请求参数摘要和任务标识。

如果同一个请求重复到达，就返回已经创建的 `taskId`，而不是重新创建任务。

如果相同的幂等键对应不同请求参数，则应该拒绝冲突请求，而不是把不同业务操作合并。

这里也要区分两个概念：

- **同一次提交请求重复发送**：应该返回同一个任务。
- **用户主动再次发起相同内容的分析**：是否复用旧结果，需要由业务决定，不能一概禁止。

因此，幂等键解决的是请求重试造成的重复创建，不等于业务上永远不允许分析相同文档。

#### 【第二，队列的重复投递需要 Worker 幂等】

即使前端没有重复提交，队列本身也可能把同一任务再次交给 Worker。

例如，Worker 已经完成分析，但在确认消费成功之前崩溃，队列可能重新投递任务。

AWS SQS 标准队列采用至少一次投递语义，因此消费者必须能够正确处理重复消息；BullMQ 也建议将 Job 设计为幂等且尽可能简洁。[参考：AWS SQS standard queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues.html)、[参考：BullMQ Idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs)。

因此，我不会假设“一个消息只会被执行一次”。

Worker 应该使用数据库状态和条件更新来控制执行资格：如果任务已经 `SUCCEEDED`，直接结束本次重复消费；如果任务处于有效的其他 Worker 执行期，则不允许第二个 Worker 同时提交结果。

对于长时间运行的任务，还需要使用租约或心跳机制判断执行者是否仍然有效，并使用版本号或执行令牌防止已经失效的 Worker 回写过期结果。

但要注意，这些机制主要保证**最终业务状态的幂等性**。如果重复执行涉及外部模型调用，仍然可能产生额外成本；需要尽可能复用已成功完成的阶段产物，或利用外部服务实际提供的幂等能力，不能假设本地状态控制就能阻止所有重复外部调用。

#### 【第三，任务丢失需要持久化与恢复机制】

队列和数据库属于不同的存储系统，因此需要处理任务创建、投递以及 Worker 执行过程中的失败。

前面提到的 Outbox 可以解决“任务已创建但消息未成功发送”的问题。

Worker 运行过程中，还可能发生进程崩溃、服务器重启或者执行超时。此时可以依靠任务租约过期、队列重投递以及恢复扫描机制重新安排执行。

但不能直接将所有 `RUNNING` 状态任务重新启动，而应该先确认原执行者是否仍然有效，并检查是否已有持久化的阶段结果，避免并发执行和重复副作用。

因此，整个可靠性设计可以概括为：

~~~text
重复请求
→ 幂等键 + 数据库唯一约束

重复队列消息
→ Worker 执行资格检查 + 幂等处理

数据库成功但投递失败
→ Outbox / 待投递任务恢复

Worker 崩溃或失联
→ 租约 / 心跳 + 恢复调度

外部执行结果未知
→ 查询或核对实际结果，再决定是否重试
~~~

这比简单地说“使用 Redis 队列，就不会丢任务”更准确。

### 七、执行失败：区分可重试错误与业务失败，避免盲目重试

当 Worker 调用 Agent 或其他外部服务时，可能遇到网络超时、限流、模型服务异常、文档损坏或者请求参数错误。

这些异常不能统一执行自动重试。

对于网络短暂故障、限流等临时错误，可以在限定次数内重试，并采用指数退避，避免短时间连续请求继续加重故障。

对于文档损坏、格式不支持、参数非法等确定性错误，则应该直接记录失败原因，由用户修改输入后再提交。

对于执行超时但外部结果未知的情况，应优先核对外部执行状态，判断上一次操作是否已经成功，再决定是否重新执行。

BullMQ 官方支持按执行次数和退避策略进行失败重试，也提供识别停滞任务的机制。[参考：BullMQ Retrying failing jobs](https://docs.bullmq.io/guide/retrying-failing-jobs)、[参考：BullMQ Stalled](https://docs.bullmq.io/guide/jobs/stalled)。

此外，我会为任务设置最大重试次数和总执行期限。达到限制后，将任务标记为 `FAILED`，保留错误代码、已完成阶段和执行记录，并根据业务需要提供人工重试入口。

对于涉及用户取消的场景，也可以补充 `CANCELLED` 状态，但取消并不等于浏览器关闭，更不代表已经发出的外部模型请求一定能够立即停止。系统需要明确取消所能控制的执行边界。

### 八、生产环境：进一步关注安全、成本和可观测性

前面的设计已经满足了题目要求。但真正部署到生产环境时，我还会考虑三个横切问题。

首先是**权限与数据安全**。文档和分析报告可能包含敏感信息，因此所有任务查询和报告下载都必须检查用户或租户权限；对象存储不能直接暴露无约束的永久公开地址。上传文件也需要进行大小、类型和内容安全检查。Agent 读取文档时，应把文档内容视为不可信输入，防止其中的指令影响系统工具权限。

其次是**并发与成本控制**。模型调用通常存在速率和预算限制，可以利用队列控制同时执行的任务数量，并按用户或租户设置配额。Worker 的并发数应结合模型请求限额、处理时长和资源占用调整，而不是无限增加实例。

最后是**可观测性**。我会围绕 `taskId` 关联一次任务的 API 创建请求、队列等待、Worker 执行、Agent 调用和报告保存过程，采集排队时长、执行时长、成功率、失败率、重试次数以及模型 Token 和成本等指标。

这样出现任务长时间停留在 `PENDING`、Worker 频繁超时或者模型成本异常时，才能快速判断问题发生在哪里。

这里不需要一开始就把系统拆成大量微服务，也不需要直接引入复杂的多 Agent 架构。更合理的路线是：**先用一个 API 服务、一个持久化数据库、一个可靠任务调度机制和独立 Worker 完成闭环，再根据吞吐量、故障隔离和扩容需要逐步演进。**

### 九、总结：将完整任务从一次请求转化为可持久化、可调度、可恢复的业务过程

所以，如果让我设计这个 AI 文档分析平台，我会以任务生命周期作为整个系统的主线。

用户上传文档后，API 服务完成校验并创建持久化任务，通过异步队列交给 Worker 执行；Worker 负责调用 Agent、记录阶段状态、保存分析报告，并在失败时根据异常类型进行处理。

前端只需要根据 `taskId` 查询或订阅任务状态，无论页面刷新还是重新打开，都能够从服务端恢复任务的真实进度。

与此同时，使用服务端幂等控制重复提交，使用 Worker 执行资格检查和状态约束控制重复消费，再通过可靠投递、失败重试和恢复机制处理异常情况。

**这套架构的核心价值，不是简单地把一个耗时接口改成异步调用，而是将一次可能中断的长时间操作，转化为一个能够独立执行、持久保存状态、可靠恢复并最终交付结果的任务系统。**

## 【这道题背后的完整技术知识框架】

从 AI 全栈面试的角度，这道题实际上连接了几个重要的服务端知识领域：

| 知识方向 | 核心问题 | 本题对应的设计 |
| --- | --- | --- |
| HTTP 与 API 设计 | 请求如何接收、何时返回 | `POST` 创建任务、`202 Accepted` |
| 异步任务架构 | 长任务如何脱离请求执行 | Queue + Worker |
| 数据持久化 | 任务状态和结果保存在哪里 | 数据库 + 对象存储 |
| 状态机 | 任务怎样合法推进 | PENDING → RUNNING → 终态 |
| 实时通信 | 前端怎样获取服务端变化 | Polling / SSE / WebSocket |
| 分布式一致性 | 多系统写入如何避免丢失 | Outbox、任务恢复 |
| 并发与幂等 | 重复提交和重复消费怎么办 | Idempotency Key、条件更新 |
| 可靠性与治理 | 失败后怎样重试、恢复和限制资源 | Retry、Backoff、Lease、限流 |
| Agent 工程 | Agent 怎样融入业务流程 | 外层任务生命周期 + 内层 Agent Runtime |

这些知识不是彼此独立的技术名词，而是沿着同一条任务链路逐步出现的：

**用户发起操作 → 服务端接收请求 → 创建持久化任务 → 后台执行 → 更新状态 → 前端恢复展示 → 处理失败与重复执行。**

掌握这条链路以后，就可以把同样的架构迁移到 AI 报告生成、批量数据处理、视频转码、文件导入和长时间 Agent Workflow 等业务场景中。
