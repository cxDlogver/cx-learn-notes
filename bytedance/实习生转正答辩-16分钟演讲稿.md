## 三、重点工作的介绍

接下来对我的重点工作进行介绍。

### 第一个重点工作

第一个重点工作是头达数据分级管控。这个需求的背景是，头部达人的交易数据存在被非必要查看和对外传播的风险，而原有数据管控不够完整，因此需要对敏感数据进行分级授权。  

业务目标最终将数据访问分为四种状态。  非协作人员，无数据权限，确认查看和展示真实数据，并且分成了字段和模块两种维度。运营人员进入页面后，按照页面数据“是否属于管控范围 —> 是否为 L4+ 数据 —> 是否为作者协作人 —> 是否拥有数据权限 —> 近七天是否确认查看”的顺序完成访问。

#### 技术方案

技术方案主要从四个方面考虑。  

第一是安全边界。真实数据必须在后端完成权限校验，未通过校验时，真实值不能下发到浏览器。

第二是权限复杂度。这次权限管控包含字段级和模块级两种管控力度，四种权限状态，同时还涉及作者、商品等多类数据维度权限。   后端在经过权限校验以后，如何设计返回的协议，能够让前端拿到返回字段以后进行权限判断？

针对字段级权限，  可以直接使用原业务接口。后端在返回前，将字段处理为真实值或者脱敏值。脱敏值采用固定前缀加字段标识的形式，作为一个完整的 value 返回。这里没有额外增加权限字段，是为了避免数据经过多层组件传递时可能导致权限字段丢失。  模块级权限没有一个单独的业务字段可以承载权限信息，因此使用独立的权限查询接口。前端在加载真实的业务数据之前先通过接口判断权限是否存在。

第三是配置维护。页面使用稳定的字段标识，字段标识和平台权限 code 之间的关系由 TCC 配置维护。以后平台 code 发生调整时，只需要修改 TCC 配置，不需要重新修改代码。  

第四是权限操作。对于L4+等级的数据，依次完成协作人申请、数据权限申请和点击确认查看以后再展示真实数据。

#### 前端页面实现

整个需求中我独立负责前端页面的实现，那么主要提炼出了四个要点

**要点一：将各页面重复的权限处理提取成公共能力**

由于这个需求多个页面，同时包含字段和模块两种管控方式。因此，需要考虑**如何实现页面不同位置的权限统一管控**。

整体设计分为页面层和公共层。页面层提供业务信息，公共层保留字段和模块两条链路。字段通过公共解析方法，从原始值中识别权限状态；模块先查询独立的权限接口，再通过公共方法将接口结果转换成权限状态。状态确定以后，分别交给对应的公共组件，由组件完成页面展示和后续操作处理。

**要点二：用公共组件统一权限展示和操作**

这里要解决的核心问题是，同一个字段或者模块可能出现多种状态，而每种状态对应的展示内容和后续操作都不同。避免权限逻辑分散在各个页面中， 需要用一个组件去统一管理所有的权限状态。

解决思路是，字段级和模块级分别提供一个公共组件，组件根据公共层返回的状态进行分支判断，选择对应的脱敏展示、提示内容和权限申请入口。

那么页面需要管控字段或模块时，只需将公共组件替换掉原来的字段和业务模块。页面不需要修改已有内容的渲染逻辑。

**要点三：在存量代码基础上接入权限操作**

这里的难点是，三类操作依赖的能力不同，因此，接入前需要先梳理存量代码逻辑。

数据权限申请依赖宿主平台弹窗，  这个弹窗可以通过接口调用，因此可以通过全局方法实现统一调用。协作人申请弹窗已经分别实现在作者列表和作者详情页中，因此保留页面原有的渲染逻辑，  不能和申请数据权限一样，直接通过全局接口调用平台的弹窗，只把打开弹窗的方法传给公共组件。

确认查看。  要求记录操作以后能够刷新当前页面，作者列表调用 `getList` 可以重新请求当前列表；作者详情页可以通过更新当前 Tab 的版本，让 Tab 重新加载并再次请求数据。基于这两种实现，公共组件提供统一的确认查看入口。先调用接口查看记录写入后端， 再执行全局刷新方法，该方法由每个页面单独注册自己的刷新方法。

**要点四：将两项重复的交付工作沉淀成 Skill**

这两个 Skill 的核心作用，都是将重复的人工工作整理成 Skill，让 AI 能够自动执行。

例如，在设计 Mock Skill 时，我通过工具调研发现，Chrome Local Overrides 可以使用本地文件替换接口响应。因此，我将这项能力整理成 Skill，让 AI 直接批量修改 Overrides 目录中的响应文件。浏览器刷新后，就可以一次性切换所有页面的权限状态。

增量覆盖率 Skill 则是通过调研 Chrome DevTools MCP 自动化工具，并结合华佗 API，让 AI 自动获取和定位未覆盖的代码行，再通过 MCP 操作真实页面，配合网络层 Mock 触发对应分支，  实现自动提高增量覆盖率。

#### 项目结果

最终，上线运行以来，没有出现权限判断错误问题。

在覆盖结果上，覆盖了全部 L4 和 L4+ 敏感数据项。

 上线结果是截止到8月5日，确认查看链路累计生成了 4486 条访问记录；权限申请也在线上产生了实际审批记录，说明整套权限链路已经在真实业务中运行。

此外，项目沉淀了两项skill，后续也继续应用到了 AI Coding 工作中。

### AI Coding 工作流搭建与业务实践

第二个重点工作是 AI Coding 工作流的搭建和业务实践。它的技术目标，是构建一套面向前端业务需求的端到端 AI Coding 工作流。工作流以 Meego 需求链接作为入口，读取关联的 PRD、Figma 设计和仓库代码，依次完成需求分析、任务规划、代码实现、浏览器验收和任务交付。

在设计初期，团队调研并使用过 Spec Kit、OpenSpec 和 Superpowers的一些通用方法。它们提供了规范驱动开发和分阶段执行的思路，但直接应用于电商前端需求时仍存在一些不足。

例如，它们无法直接使用 Lark CLI、Meego、Figma MCP 等内部工具；在后端接口尚未完成时，也缺少一套完整的数据 Mock 流程；同时缺少浏览器主动验收能力。因此，实际应用效果并不理想。

因此，团队保留了这些通用方案，同时结合电商前端需求的实际交付经验，并接入内部工具，形成一套更适合业务需求的AI Coding 工作流。

工作流的建设效果主要从缩短交付时间，提高交付质量，减少人工参与三个方面衡量：

#### 工作流整体结构

整体结构可以概括为一条主流程和两个辅助环节。

主流程由 AI 完成开发和交付过程。人工主要在三个位置进行审查：  审查验收项：审查最后的证据对齐，并进行测试联调。

 人工审查未通过的时候，能够让 AI 自动回到相应的阶段进行修复。全部结果通过后，由 BITS 辅助交付环节。



#### 工作重点一：按 Test Case 构建 Mock 规则

第一个工作重点，是按 Test Case 构建 Mock 规则。

它的目标是，在后端未实现情况下，让 AI 仍然能够继续完成前端开发和页面验收。

这里的问题是，AI在验收的时候，同一个接口在不同测试场景下，可能需要返回不同的数据，  所以，mock规则必须要和当前的测试项进行对应。

因此，在生成 Test Case 时，会为每个依赖接口数据的 Case 配置对应的 Rule ID，从而建立 Mock 规则与 Test Case 的对应关系，让每条规则都有明确的测试来源和验收场景。这样，Agent 就可以按照 Test Case 自动准备 Mock 数据并完成页面验收。  

最后每一条规则要构建出test case和rule id以及请求字段和mock响应之间的映射关系

#### 工作重点二：将 Verify 证据与 Test Case 对齐

第二个工作重点，是将 Verify 证据与 Test Case 对齐。

它的目标是**让浏览器验收结果可信**。所以skill要求一个 Test Case 只要存在断言未执行或者证据缺失，当前 Case 就不能通过。

这里的问题是，Skill 本质上仍然是软约束，Agent 在长任务中可能遗漏要求或者提前判断完成。因此，设计重点是如何让 Agent 稳定执行 Skill。

为此，我调研了任务型 Skill 和长任务 Agent 的设计，总结出三个结论：

第一，Gate 是任务型 Skill 的关键环节。即使 Agent 在执行过程中遗漏了某些规范，只要 Gate 没有被绕过，它仍然会重新检查当前规范，并根据失败原因定位到对应规则进行修复。

第二，按照可检查程度拆分 Skill 规范。也就是使用脚本和结构化字段替代部分自然语言，让 Agent 能够更加稳定地执行。

第三，执行产物要随着任务进度及时更新。不要等任务完成后，再让 Agent 根据上下文统一生成产物，否则上下文经过压缩后一定会丢失部分信息。

根据这些调研结果，我将其应用到了 Verify Skill 的规范中，具体流程如下：

1. 初始化结构化的验收记录，再逐条执行验收并增量记录。
2. 完成断言与证据的对齐。
3. 最后执行 Gate，检查并定位失败项。

它的完成标准是：

1. 每条断言都有验收标准。
2. 每条断言都被拆分成具体的验收项。
3. 每个验收项都有对应的证据。
4. 最终形成明确的验收结论。

#### 工作重点三：建立 Repair 返修流程

第三个工作重点，是建立 Repair 返修流程。

不能期望 Agent 通过一轮执行完成全部交付，测试联调发现问题后，需要支持二次修正和重新验证。

这里的问题是，修复不能只修改代码，而是将产物进行同步更新，否则产物就无法代表当前代码的最新状态。

因此，Repair 会接收问题并保存当前工作区，定位受影响的阶段和产物，同步更新相关产物和代码，再复验对应的 Test Case。验收通过后，把修改结果和验收结果写回原问题。

#### 工作重点四：通过 BITS 完成交付前检查

第四个工作重点，是通过 BITS 完成交付前检查。

它的目标是把自动化范围扩展到评审评论的处理，减少人工成本。

整个流程会先拉取评审评论，由 AI 逐条完成必要的代码修复和验证，并回复处理结果。随后，人工统一审查原评论和回复内容。确认没有问题后，再提交代码并关闭评论。

最终，评审评论的具体处理由 AI 完成，人工只负责提交前的最终审查。

#### 业务实践结果

通过内容激励需求进行了第一次完整实践，完成完整交付，验证这套工作流可以真正用于业务交付。将整个交付时间从原有预计的 3 PD 缩短到了 2 PD。证明并达到提效的目的。
