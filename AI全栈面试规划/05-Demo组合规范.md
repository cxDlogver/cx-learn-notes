# AI 全栈面试 Demo 组合规范

## 1. 组合策略

Demo 同时保留两种形态：一个持续演进的个人知识库 Agent，以及由复习缺口触发的独立微型 Demo。

主 Demo 证明端到端整合和工程取舍；微型 Demo 隔离一个难点，用最少依赖证明机制。微型 Demo 通过验证后，只有在能增强主链路且不会制造无关复杂度时才合并。

## 2. 主 Demo：个人知识库 Agent

### 【用户价值】

用户可以选择当前仓库中允许的知识文档，完成上传/导入、读取、检索、分析、维护和受控修改。回答需要展示引用来源；修改需要展示 diff、请求人工批准、保留版本并支持恢复。

### 【技术边界】

| 层 | 第一阶段选型 | 主要职责 |
| --- | --- | --- |
| 前端 | React + TypeScript | 文档、会话、Run、事件流、引用、diff、审批和恢复界面 |
| API | NestJS | 身份、授权、输入校验、业务服务、错误契约、SSE/HTTP |
| Agent Runtime | LangGraph.js | Graph State、Checkpoint、Interrupt/Resume、工具编排和流式事件 |
| 主存储 | PostgreSQL | 用户、文档、版本、Run、Checkpoint、审批、幂等与审计 |
| 向量检索 | pgvector | Chunk Embedding、相似度检索和来源关联 |
| 异步任务 | Redis + BullMQ | 文档解析、索引、重试和失败任务留存 |
| 观测 | OpenTelemetry + 结构化日志 | 关联 HTTP、Run、检索、模型、工具、队列和数据库操作 |
| 本地环境 | Docker Compose | API、Worker、PostgreSQL/pgvector、Redis 等依赖的一键启动 |

### 【受控文件能力】

读取流程：用户选择允许目录 → 服务端规范化路径 → 授权检查 → 读取固定文件类型 → 记录来源与版本 → 解析和索引。

修改流程：Agent 形成修改提案 → 服务端验证路径与版本 → 生成 diff → LangGraph 中断 → 用户批准/编辑/拒绝 → 幂等写入 → 保存版本和审计 → 更新索引。

Agent 不能直接获得任意 Shell 或仓库写权限。第一阶段仅允许 Markdown 等明确白名单文件；所有路径必须相对于配置的知识根目录解析，并验证最终真实路径没有越界。Git 提交是知识版本证据之一，但不能代替数据库中的审批、幂等和运行审计。

## 3. 主 Demo 能力切片

### 【M0：最小垂直链路】

React 发起请求，NestJS 创建 Run，LangGraph 执行最小节点，前端看到最终状态；PostgreSQL 和 Redis 可连接；存在基础测试与启动说明。

### 【M1：知识导入与检索】

选择允许的仓库文档；异步解析、分块和索引；检索时返回文档路径、版本和 Chunk；回答引用可追溯；重复导入不会产生失控重复数据。

### 【M2：受控维护与中断恢复】

读取、分析和提出修改；展示 diff；敏感写入触发 Interrupt；进程退出后仍能查到待审批 Run；批准后使用同一线程恢复；拒绝时没有文件副作用。

### 【M3：可靠性与安全】

幂等写入、版本冲突、重试分类、任务失败留存、权限校验、路径越界阻断、恶意知识内容隔离、审计查询和可回滚版本。

### 【M4：观测、评测与演示】

端到端 Trace；关键延迟和错误 Metric；结构化日志；至少一组检索质量、引用正确性、工具权限、恢复和幂等回归用例；固定演示脚本覆盖成功、失败和安全拒绝路径。

## 4. 微型 Demo 规则

微型 Demo 必须对应一次真实复习失败或主 Demo 阻塞，并在自己的 README 中记录：要证明的问题；最小环境；运行命令；预期状态变化；至少一个失败断言；学到的边界；是否合并主 Demo。

候选主题包括：

- LangGraph 数据库 Checkpoint 与进程重启恢复。
- 相同幂等键下的重复副作用抑制。
- PostgreSQL 并发更新和隔离异常。
- BullMQ 指数退避、重试与失败任务留存。
- SSE 断线重连、事件序号和补偿读取。
- Markdown 分块、向量检索、来源引用和索引更新。
- 路径穿越、资源授权和恶意 Prompt 文档拒绝。
- HTTP → Agent Run → Tool → Queue → DB 的 Trace 关联。

不设固定数量。只写代码但没有运行证据的微型 Demo 不计入 S3；无法说明如何服务主目标的 Demo 不进入任务池。

## 5. 面试演示验收

最终演示应能在 12～15 分钟内完成：说明业务问题和架构；导入一份知识文档；发起带引用的分析；提出文档修改；展示待审批状态和 diff；模拟服务重启；批准并恢复；证明重复恢复没有重复写入；展示审计与 Trace；用恶意文档或越权用户触发一次安全拒绝。

演示结束后要能回答：为什么 State 不等于数据库业务数据；为什么 Checkpoint 不等于知识库；为什么必须幂等；为什么写操作不能只靠 Prompt 约束；为什么使用队列；PostgreSQL 与 Redis 各自保存什么；当前方案在多实例和大规模文档下还缺什么。
