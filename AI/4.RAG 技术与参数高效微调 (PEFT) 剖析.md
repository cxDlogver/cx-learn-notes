## 相关面试真题

### 请说明 RAG 与 PEFT 的核心区别，并结合业务场景说明如何在两者之间做技术选型。

**参考答案要点**：
RAG 与 PEFT 是大模型应用中解决两类正交问题的核心技术，定位和适用场景存在本质差异。RAG 是**外部知识注入技术**，相当于让大模型"开卷考试"，专门解决静态知识截止和私有领域知识获取问题；PEFT 是**模型行为定制技术**，相当于训练大模型的"答题习惯"，用于解决输出格式不稳定、领域风格不匹配的问题。

两者核心维度对比如下：

| 维度 | RAG | PEFT |
| --- | --- | --- |
| 知识更新 | 成本极低，秒级生效 | 成本高，需重新训练 |
| 可追溯性 | 回答可精确溯源到原始文档 | 无法追溯知识来源 |
| 推理开销 | 增加检索延迟，模型成本不变 | 合并后无额外推理开销 |
| 通用能力 | 完全不影响模型原有能力 | 几乎不影响模型原有能力 |

技术选型遵循以下核心原则：
- ✅ 频繁变化、需要审计、需要精确引用的**事实性信息**，优先用 RAG
- ✅ 稳定的输出格式、行为模式、领域表达风格，考虑用 PEFT
- ✅ 生产环境主流采用"RAG 提供实时事实 + PEFT 规范输出行为"的组合架构
- ❌ 绝对不要用 PEFT 注入事实知识，这是最常见的架构反模式

### 请对比 2-Step RAG、Agentic RAG、Hybrid RAG 三种架构的优缺点，并说明各自的适用场景。

**参考答案要点**：
三种 RAG 架构代表了从简单到复杂的演进路径，在可控性、灵活性和延迟之间做出了不同权衡，没有绝对的优劣，只有是否适合业务需求。

2-Step RAG 是最基础也最可靠的生产基线，遵循固定的"先检索后生成"流程。它的优势是行为完全可预测、延迟稳定、成本最低、最容易建立自动化测试体系；缺点是灵活性有限，无法处理多步推理问题。**最适合 FAQ、内部文档助手、政策查询等需要强可控性的标准化场景**。

Agentic RAG 将检索封装为标准工具，由 Agent 自主决定调用时机。它的优势是灵活性极高，能处理开放式研究、多工具协作等复杂任务；缺点是行为不可预测、调试难度大、成本波动明显。**更适合研究助手、数据分析等对灵活性要求高于可控性的场景**。

Hybrid RAG 介于两者之间，结合了多种检索策略和中间验证步骤。通过向量检索与关键词检索的互补提升召回鲁棒性，同时引入检索验证和回答校验环节保障质量。虽然系统复杂度更高，但能满足对召回率和准确性有较高要求的场景，**特别是包含专有名词、编号、代码片段等精确匹配需求的查询**。

架构选型核心原则：
1. 永远从最简单的 2-Step RAG 开始，建立基线
2. 只有当 2-Step 明确无法满足需求时，再逐步增加复杂度
3. 避免过早引入 Agentic RAG，大多数业务场景 2-Step 或 Hybrid 足够
4. 复杂度的增加必须带来可量化的业务价值提升

### 生产环境中 RAG 系统最常见的问题是幻觉，请问你会从哪些方面系统性地解决这个问题？

**参考答案要点**：
幻觉不是单一环节的缺陷，而是 RAG 全链路多个因素共同作用的结果，必须采用分层治理的系统性方案，不能只靠优化提示词解决。

**数据层（基础）**：
- 确保数据源本身的准确性和完整性，建立定期清洗和更新机制
- 优化文档切分策略，保证每个 chunk 的语义独立性，避免关键信息被拆分
- 完善元数据管理，为每个文档块添加来源、版本、可信度等信息

**检索层（核心）**：
- 采用混合检索策略，结合向量检索的语义匹配和关键词检索的精确匹配
- 合理调整 top-k 和相似度阈值，在召回率和噪声之间取得平衡
- 高要求场景引入重排序（Reranker）模型，对初筛结果进行二次排序

**生成层（关键）**：
- 严格的提示词约束，明确要求"只基于上下文回答，不知道就说不知道"
- 强制模型引用来源，要求回答中的每个事实标注对应的文档 ID
- 使用低 temperature（0-0.3），减少生成过程中的随机性

**验证层（兜底）**：
- 实现回答自一致性检查，让模型自己验证是否与上下文一致
- 引入 LLM-as-judge 进行自动化事实一致性评估
- 高风险场景建立人工审核兜底机制

整体解决原则：
1. 预防优先：从数据和检索环节减少幻觉产生的可能
2. 分层治理：每个环节都要有对应的质量控制措施
3. 闭环迭代：建立用户反馈机制，收集错误案例持续优化
4. 合理预期：接受幻觉无法 100% 消除，重点是将其控制在可接受范围内

## 大模型应用的核心架构约束

所有大模型应用架构设计都必须围绕以下两个不可突破的约束展开：
1. **有限上下文窗口**：模型只能处理固定长度的输入序列，无法一次性摄入完整知识库
2. **静态知识截止**：模型知识固化于训练完成时刻，无法获取实时信息与私有领域知识

这两个约束决定了：**试图通过增大模型规模或延长上下文窗口来解决所有问题的方案，在工程上是不可行的**。

### 两种主流解决方案

针对上述约束，业界演化出两条正交的技术路线：

| 技术路线 | 核心思想 | 解决问题 | 技术本质 |
| --- | --- | --- | --- |
| **RAG（检索增强生成）** | 运行时动态注入外部知识 | 静态知识与实时信息获取 | 外部记忆系统与大模型的解耦集成 |
| **PEFT（参数高效微调）** | 训练少量可插拔适配器 | 模型行为与输出风格适配 | 大模型能力的定向增强与定制 |

### 核心架构边界：事实与行为分离

- 所有频繁变化、需要可追溯、需要审计的**事实性信息**，必须通过 RAG 系统注入
- 所有稳定的、可复用的、与领域风格相关的**行为模式**，可以通过 PEFT 固化

### 验证案例：学生信息查询系统

我们将以学生信息查询系统贯穿整个课程，对比两种技术路线的优劣：
- **RAG 方案**：将学生数据存储在 CSV 文件中，运行时检索并注入上下文
- **PEFT 方案**：训练模型学会"根据给定上下文回答问题，信息不足时拒答"的行为模式
- **最优架构**：RAG 提供实时学生数据，PEFT 确保输出格式与行为一致性

## RAG 模块化检索流水线

Retrieval-Augmented Generation（检索增强生成）
### RAG 的核心设计哲学

RAG 的本质是**将知识从模型参数中解耦出来，构建独立的外部记忆系统**。这种解耦带来了三个关键的架构优势：
1. **知识可独立更新**：无需重新训练模型即可更新知识库
2. **来源可追溯**：所有回答都可以追溯到原始文档
3. **系统可水平扩展**：检索系统与生成系统可以独立扩容

### 两条独立流水线

一个生产级 RAG 系统由两条完全解耦的流水线组成：

#### 离线索引流水线（Indexing Pipeline）

```plaintext
数据源 → 文档加载器 → 标准化Document → 文档切分器 → 嵌入模型 → 向量数据库
```

**架构特性**：
- 批量执行，对延迟不敏感
- 计算密集型，适合离线调度
- 幂等操作，支持增量更新

#### 在线服务流水线（Serving Pipeline）

```plaintext
用户查询 → 查询嵌入 → 向量检索 → 上下文聚合 → 提示词模板 → 大模型 → 回答
```

**架构特性**：
- 实时执行，对延迟敏感
- IO 密集型，需要高并发支持
- 无状态设计，支持水平扩展

### 七大核心组件的职责边界

LangChain 官方将 RAG 系统抽象为七个标准组件，每个组件都有明确的职责与替换接口：

| 组件 | 核心职责 | 替换原则 | 官方实现示例 |
| --- | --- | --- | --- |
| **Document Loader** | 将异构数据源转换为统一 Document 对象 | 支持任意数据源接入 | CSVLoader、PDFLoader、WebLoader |
| **Text Splitter** | 将长文档切分为适合嵌入的语义块 | 根据文档类型调整切分策略 | RecursiveCharacterTextSplitter |
| **Embedding Model** | 将文本映射到高维向量空间 | 语义相似度匹配效果优先 | OpenAIEmbeddings、OllamaEmbeddings |
| **Vector Store** | 向量存储与近似最近邻搜索 | 根据规模与性能需求选择 | MemoryVectorStore、Chroma、Pinecone |
| **Retriever** | 面向应用的查询接口 | 实现不同的检索策略 | SimilarityRetriever、MMRRetriever |
| **Prompt Template** | 上下文与查询的标准化格式化 | 可插拔的提示词策略 | ChatPromptTemplate |
| **LLM** | 基于上下文生成最终回答 | 效果与成本的权衡 | ChatOpenAI、ChatAnthropic |

**架构原则**：所有组件都应该面向接口编程，替换任何一个组件都不应该影响其他组件的逻辑。

### 最小 RAG 系统实现

```typescript
// src/shared/knowledge-base.ts
import { CSVLoader } from "@langchain/community/document_loaders/fs/csv";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { OpenAIEmbeddings } from "@langchain/openai";
import { MemoryVectorStore } from "langchain/vectorstores/memory";

/**
 * 构建学生知识库向量存储
 * 实现了离线索引流水线的完整逻辑
 */
export async function createStudentVectorStore() {
  // 1. 数据加载：异构数据源标准化
  const loader = new CSVLoader("data/students.csv");
  const documents = await loader.load();

  // 2. 文档切分：语义块划分
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: 200,
    chunkOverlap: 50,
    separators: ["\n\n", "\n", " ", ""],
  });
  const splits = await splitter.splitDocuments(documents);

  // 3. 向量索引：语义空间映射
  const embeddings = new OpenAIEmbeddings({
    model: process.env.RAG_EMBEDDING_MODEL || "doubao-embedding-vision",
  });

  // 返回标准Retriever接口
  return MemoryVectorStore.fromDocuments(splits, embeddings);
}
```

**架构解读**：
这段代码不是一个简单的示例，而是生产级 RAG 系统的核心骨架。它完美体现了 RAG 的模块化设计思想：
- 替换`CSVLoader`可以接入任何数据源
- 调整`TextSplitter`参数可以适配不同文档类型
- 替换 OpenAIEmbeddings 可以使用任何嵌入模型
- 替换`MemoryVectorStore`可以使用任何向量数据库

## 知识库构建——离线索引流水线设计

### Document 对象标准化

LangChain 定义了标准的`Document`接口，这是整个 RAG 系统的数据契约：
```typescript
interface Document {
  pageContent: string;  // 文档的纯文本内容
  metadata: Record<string, any>;  // 文档元数据
}
```

**架构重点**：`metadata`是 RAG 系统可观测性与可追溯性的基础。生产环境中必须至少包含以下字段：
- `source`：文档来源标识
- `last_updated`：最后更新时间
- `document_id`：唯一文档 ID
- `chunk_id`：块在文档中的序号

### 文档切分策略设计

文档切分是 RAG 系统中最影响检索效果的环节，也是最容易被忽视的环节。

#### 切分粒度的权衡

- **过粗**：单个块包含过多无关信息，增加模型噪声
- **过细**：语义完整性被破坏，单个块无法独立表达完整含义

#### 通用切分参数指南

| 文档类型 | 推荐 chunkSize | 推荐 chunkOverlap |
| --- | --- | --- |
| 结构化数据（CSV/JSON） | 100-300 | 20-50 |
| 纯文本（Markdown/TXT） | 300-1000 | 50-200 |
| 代码文件 | 100-500 | 20-100 |
| PDF 文档 | 500-1500 | 100-300 |

#### RecursiveCharacterTextSplitter 工作原理

这是 LangChain 官方推荐的通用文本切分器，它按照以下优先级递归切分文档：
1. 按段落分隔符（`\n\n`）切分
2. 按行分隔符（`\n`）切分
3. 按空格切分
4. 按字符切分

这种切分策略能够最大程度地保持语义单元的完整性。

### 生产级切分实现

```typescript
// src/shared/text-splitter.ts
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import type { Document } from "@langchain/core/documents";

/**
 * 生产级文档切分器
 * 保留完整元数据，支持不同文档类型的参数配置
 */
export async function splitDocuments(
  documents: Document[],
  options: {
    chunkSize?: number;
    chunkOverlap?: number;
    separators?: string[];
  } = {}
): Promise<Document[]> {
  const {
    chunkSize = 200,
    chunkOverlap = 50,
    separators = ["\n\n", "\n", " ", ""],
  } = options;

  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize,
    chunkOverlap,
    separators,
    keepSeparator: false,
    stripWhitespace: true,
  });

  const splits = await splitter.splitDocuments(documents);

  // 为每个块添加唯一chunk_id
  return splits.map((doc, index) => ({
    ...doc,
    metadata: {
      ...doc.metadata,
      chunk_id: `${doc.metadata.source || "unknown"}_chunk_${index}`,
    },
  }));
}
```

### 索引更新策略

生产环境中，知识库不可能是静态的。常见的索引更新策略有三种：
1. **全量重建**：简单可靠，但更新延迟高，适合小规模知识库
2. **增量更新**：只更新变化的文档，需要维护文档版本号
3. **实时更新**：文档变化时立即触发索引更新，适合高频变化场景

**架构建议**：从全量重建开始，随着数据规模增长逐步演进到增量更新。

## RAG 范式对比：三种核心架构的权衡

LangChain 官方明确区分了三种主流的 RAG 架构，每种架构都有明确的适用场景与权衡。

### 官方架构对比矩阵

| 架构 | 核心描述 | 控制度 | 灵活性 | 延迟特性 | 典型用例 |
| --- | --- | --- | --- | --- | --- |
| **2-Step RAG** | 检索总是在生成之前执行 | ✅ 高 | ❌ 低 | ⚡ 可预测 | FAQ、文档助手、政策查询 |
| **Agentic RAG** | Agent 自主决定何时及如何检索 | ❌ 低 | ✅ 高 | ⏳ 可变 | 研究助手、多工具协作、复杂推理 |
| **Hybrid RAG** | 结合固定流程与 Agentic 验证 | ⚖️ 中 | ⚖️ 中 | ⏳ 可变 | 领域 QA、质量敏感型应用 |

**架构原则**：永远从最简单的 2-Step RAG 开始，只有当它无法满足需求时，再考虑更复杂的架构。

### 2-Step RAG：生产级基线架构

#### 架构定义

2-Step RAG 是最简单也最可靠的 RAG 架构，它遵循严格的执行顺序：
```plaintext
用户查询 → 检索 → 上下文格式化 → 生成 → 回答
```

#### 核心特性

- **确定性执行**：每次查询的执行路径完全相同
- **单次 LLM 调用**：延迟稳定，成本可控
- **易于评估**：可以建立完整的自动化测试体系
- **故障点清晰**：问题可以明确归因到检索或生成环节

#### 生产级实现

```typescript
// src/2.rag-patterns/1.two-step-rag.ts
import "dotenv/config";
import { ChatOpenAI } from "@langchain/openai";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";
import { createStudentVectorStore } from "../shared/knowledge-base";

async function main(question: string) {
  // 初始化依赖（生产环境应使用依赖注入）
  const model = new ChatOpenAI({ temperature: 0 });
  const vectorStore = await createStudentVectorStore();
  const retriever = vectorStore.asRetriever({ k: 3 });

  // 标准化提示词模板
  const prompt = ChatPromptTemplate.fromMessages([
    [
      "system",
      `你是一个严谨的学生信息助手。
      请严格基于以下<context>中的内容回答问题。
      如果上下文中没有相关信息，请明确回答"上下文中没有足够信息"。
      禁止编造任何信息。

      <context>
      {context}
      </context>`,
    ],
    ["human", "{question}"],
  ]);

  // 构建RAG链
  const ragChain = prompt.pipe(model).pipe(new StringOutputParser());

  // 执行流程
  const docs = await retriever.invoke(question);
  const context = docs.map((doc) => doc.pageContent).join("\n\n");
  const answer = await ragChain.invoke({ context, question });

  // 生产环境应记录完整的执行日志
  console.log(JSON.stringify({
    question,
    retrieved_docs: docs.map((d) => d.metadata),
    answer,
  }, null, 2));

  return answer;
}

main(process.argv[2] || "heyi的成绩是多少？");
```

#### 适用场景

- 所有需要强可控性的业务场景
- 问题类型固定且可枚举的场景
- 对延迟和成本敏感的场景
- 需要严格合规与审计的场景

### Agentic RAG：工具化检索架构

#### 架构定义

Agentic RAG 将检索能力封装为一个工具，由 LLM 驱动的 Agent 自主决定是否调用工具：
```plaintext
用户查询 → Agent推理 → 工具调用决策 → 检索 → 上下文 → 生成 → 回答
```

#### 核心特性

- **自主决策**：Agent 可以根据问题复杂度决定是否需要检索
- **多步推理**：支持多次工具调用和复杂推理链
- **可组合性**：可以轻松集成其他工具（数据库、API 等）
- **不确定性**：执行路径不可预测，调试难度大

#### 官方标准实现

```typescript
// src/2.rag-patterns/2.agentic-rag.ts
import "dotenv/config";
import { tool } from "@langchain/core/tools";
import { createAgent } from "langchain";
import { ChatOpenAI } from "@langchain/openai";
import { z } from "zod";
import { createStudentVectorStore } from "../shared/knowledge-base";

async function main(question: string) {
  const model = new ChatOpenAI({ temperature: 0 });
  const vectorStore = await createStudentVectorStore();
  const retriever = vectorStore.asRetriever({ k: 3 });

  // 将检索器封装为标准LangChain工具
  const retrieveStudentKnowledge = tool(
    async ({ query }) => {
      const docs = await retriever.invoke(query);
      return docs.map((doc) => 
        `[来源: ${doc.metadata.source}] ${doc.pageContent}`
      ).join("\n\n");
    },
    {
      name: "retrieve_student_knowledge",
      description: "检索学生知识库，用于回答学生姓名、学号、成绩相关问题",
      schema: z.object({
        query: z.string().describe("用于检索的自然语言查询"),
      }),
    }
  );

  // 创建Agent
  const agent = createAgent({
    model,
    tools: [retrieveStudentKnowledge],
    systemPrompt: `
      你是学生信息助手。
      所有关于学生信息的问题，必须先调用retrieve_student_knowledge工具。
      只能使用工具返回的信息回答问题。
      如果工具返回的信息不足以回答问题，请明确说明。
    `,
  });

  // 执行Agent
  const result = await agent.invoke({
    messages: [{ role: "user", content: question }],
  });

  return result.messages.at(-1)?.content;
}

main(process.argv[2] || "heyi和lihua谁的数学成绩更高？");
```

#### 架构要点

- 工具的`description`和`schema`是 Agent 正确调用工具的关键
- 系统提示词必须明确约束工具的使用规则
- 生产环境必须记录所有工具调用的输入和输出
- Agentic RAG 不是"更智能"的 2-Step RAG，而是解决不同问题的架构

### Hybrid RAG：验证增强型架构

#### 架构定义

Hybrid RAG 结合了 2-Step RAG 的可控性和 Agentic RAG 的灵活性，引入了中间验证步骤：
```plaintext
用户查询 → 查询增强 → 多源检索 → 检索验证 → 上下文聚合 → 生成 → 回答验证 → 回答
```

#### 核心特性

- **多策略检索**：同时使用向量检索、关键词检索等多种策略
- **检索验证**：评估检索结果的相关性与充分性
- **回答验证**：检查生成回答与上下文的一致性
- **迭代优化**：支持多轮检索与生成循环

#### 实现

```typescript
// src/2.rag-patterns/3.hybrid-rag.ts
import "dotenv/config";
import { ChatOpenAI } from "@langchain/openai";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";
import { createStudentVectorStore } from "../shared/knowledge-base";
import { mergeHybridResults } from "../shared/rag-utils";

async function main(question: string) {
  const model = new ChatOpenAI({ temperature: 0 });
  const vectorStore = await createStudentVectorStore();

  // 1. 查询增强：生成多个语义相似的查询
  const rewritePrompt = ChatPromptTemplate.fromTemplate(`
    将以下用户查询改写为3个不同的搜索查询，用于从学生知识库中检索信息。
    只输出查询，每行一个。

    原始查询：{question}
  `);

  const rewriteChain = rewritePrompt.pipe(model).pipe(new StringOutputParser());
  const rewrittenQueries = (await rewriteChain.invoke({ question }))
    .split("\n")
    .filter((q) => q.trim());

  // 2. 多策略并行检索
  const vectorResults = await Promise.all(
    rewrittenQueries.map((q) => vectorStore.similaritySearch(q, 2))
  );
  const keywordResults = await vectorStore.similaritySearch(question, 2);

  // 3. 结果合并与去重
  const mergedResults = mergeHybridResults(
    [...vectorResults.flat(), ...keywordResults],
    4
  );

  // 4. 生成回答
  const prompt = ChatPromptTemplate.fromTemplate(`
    基于以下上下文回答问题。
    上下文：{context}
    问题：{question}
  `);

  const ragChain = prompt.pipe(model).pipe(new StringOutputParser());
  const context = mergedResults.map((doc) => doc.pageContent).join("\n\n");
  const answer = await ragChain.invoke({ context, question });

  return answer;
}

main(process.argv[2] || "heyi 数学 分数");
```

## RAG 系统优化：调参与评估体系【了解】

### 分层评估模型

生产级 RAG 系统必须建立分层评估体系，不能只看最终回答的质量：

| 评估层次 | 评估指标 | 评估方法 |
| --- | --- | --- |
| **数据层** | 覆盖率、准确率、新鲜度 | 自动化数据校验 |
| **索引层** | 切分准确率、嵌入质量 | 人工抽样评估 |
| **召回层** | 召回率、精确率、MRR、NDCG | 基于标注数据集的自动化评估 |
| **上下文层** | 相关性、冗余度、噪声水平 | 自动化评分 + 人工审核 |
| **生成层** | 事实一致性、相关性、有用性 | LLM-as-judge + 人工评估 |

### 核心调参策略

#### 检索调参

- **k 值**：控制返回的文档数量，通常 3-5 是比较均衡的选择
- **检索策略**：
 - Similarity：纯相似度搜索，速度最快
 - MMR：最大边际相关性，兼顾相关性与多样性
 - ScoreThreshold：过滤相似度低于阈值的文档

#### 提示词调参

- 明确约束模型只能基于上下文回答
- 加入明确的拒答指令
- 要求模型引用来源信息
- 使用结构化输出格式

### RAG 系统优化：调参与评估体系的生产级落地

RAG 系统的质量不是靠感觉判断的，而是靠**量化指标**和**系统化实验**来提升的。本节将提供一套完整的、可直接落地的调参方法论和评估体系实现。

#### 调参实验设计：科学的参数优化流程

调参每次只改变一个参数，保持其他参数不变，观察指标的变化。

##### 标准调参实验流程

1. **建立基线**：使用默认参数运行，记录所有评估指标
2. **单变量实验**：每次只调整一个参数，运行完整的评估流程
3. **结果对比**：对比调整前后的指标变化，确定最优值
4. **迭代优化**：重复步骤 2-3，直到所有关键参数都优化完毕

##### 核心参数调优顺序与实验设计

| 参数 | 默认值 | 实验范围 | 评估指标 | 最优值判断标准 |
| --- | --- | --- | --- | --- |
| **chunkSize** | 200 | 100, 200, 300, 500 | 召回率、精确率 | 召回率最高的最小值 |
| **chunkOverlap** | 50 | 0, 25, 50, 100 | 召回率 | 召回率不再提升的最小值 |
| **k 值** | 3 | 1, 2, 3, 5, 10 | 召回率、上下文长度 | 召回率最高且上下文长度不超过模型窗口的 20% |
| **检索策略** | Similarity | Similarity, MMR | 精确率、多样性 | 精确率最高的策略 |
| **嵌入模型** | nomic-embed-text | nomic-embed-text, text-embedding-3-small | 召回率 | 召回率最高的模型 |

#### 召回层评估：RAG 质量的基础

召回层是 RAG 系统的基础，如果召回不到正确的文档，再好的模型也无法生成正确的回答。召回层的评估可以完全自动化，不需要人工参与。

##### 标注数据集格式

首先需要创建一个标注数据集，包含查询和对应的正确文档 ID：
```json
// data/test-queries.json
[
  {
    "query": "heyi的成绩是多少？",
    "relevant_doc_ids": ["student.csv_chunk_0"]
  },
  {
    "query": "liuyi的学号是多少？",
    "relevant_doc_ids": ["student.csv_chunk_1"]
  },
  {
    "query": "谁的数学成绩最高？",
    "relevant_doc_ids": ["student.csv_chunk_0", "student.csv_chunk_1", "student.csv_chunk_2"]
  }
]
```

##### 召回层评估实现

```typescript
// src/evaluation/retriever-evaluator.ts
import type { Retriever } from "@langchain/core/retrievers";
import type { Document } from "@langchain/core/documents";

type TestQuery = {
  query: string;
  relevant_doc_ids: string[];
};

type RetrieverMetrics = {
  recall: number;  // 召回率：正确召回的文档数 / 总相关文档数
  precision: number; // 精确率：正确召回的文档数 / 总召回文档数
  f1: number; // F1分数：召回率和精确率的调和平均
  mrr: number; // 平均倒数排名：第一个相关文档的排名倒数的平均值
};

export async function evaluateRetriever(
  retriever: Retriever,
  testQueriesPath: string
): Promise<RetrieverMetrics> {
  const testQueries: TestQuery[] = await import(testQueriesPath);
  
  let totalRecall = 0;
  let totalPrecision = 0;
  let totalMrr = 0;

  for (const testQuery of testQueries) {
    const docs = await retriever.invoke(testQuery.query);
    const retrievedDocIds = docs.map((doc) => doc.metadata.chunk_id);
    const relevantDocIds = testQuery.relevant_doc_ids;
    
    // 计算真阳性：既在召回结果中又在相关文档中的数量
    const truePositives = retrievedDocIds.filter((id) => 
      relevantDocIds.includes(id)
    ).length;
    
    // 计算召回率和精确率
    const recall = truePositives / relevantDocIds.length;
    const precision = truePositives / retrievedDocIds.length;
    
    // 计算MRR
    let mrr = 0;
    for (let i = 0; i < retrievedDocIds.length; i++) {
      if (relevantDocIds.includes(retrievedDocIds[i])) {
        mrr = 1 / (i + 1);
        break;
      }
    }
    
    totalRecall += recall;
    totalPrecision += precision;
    totalMrr += mrr;
  }
  
  return {
    recall: totalRecall / testQueries.length,
    precision: totalPrecision / testQueries.length,
    f1: 2 * (totalPrecision * totalRecall) / (totalPrecision + totalRecall),
    mrr: totalMrr / testQueries.length,
  };
}
```

#### 生成层评估：事实一致性与相关性

生成层的评估比召回层复杂，需要判断回答的事实一致性、相关性和有用性。常用的方法是**LLM-as-judge**，即使用另一个大模型来评估生成的回答。

##### 生成层评估实现

```typescript
// src/evaluation/generation-evaluator.ts
import { ChatOpenAI } from "@langchain/openai";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";

type GenerationTest = {
  query: string;
  context: string;
  expected_answer: string;
};

type GenerationMetrics = {
  factuality: number; // 事实一致性：0-1分
  relevance: number; // 相关性：0-1分
  helpfulness: number; // 有用性：0-1分
  overall: number; // 综合得分：0-1分
};

export async function evaluateGeneration(
  testCases: GenerationTest[],
  modelName: string = "doubao-seed-2.0-mini"
): Promise<GenerationMetrics> {
  const model = new ChatOpenAI({ model: modelName, temperature: 0 });
  
  const prompt = ChatPromptTemplate.fromTemplate(`
    你是一个专业的RAG系统评估员。请根据以下上下文和预期答案，评估模型生成的回答质量。
    
    上下文：{context}
    问题：{query}
    预期答案：{expected_answer}
    模型回答：{generated_answer}
    
    请从以下三个维度进行评分，每个维度0-1分：
    1. 事实一致性：回答是否与上下文一致，没有编造信息
    2. 相关性：回答是否与问题相关，没有答非所问
    3. 有用性：回答是否清晰、准确、有用
    
    只输出三个分数，用逗号分隔，不要其他内容。
    例如：0.8,0.9,0.7
  `);
  
  const chain = prompt.pipe(model).pipe(new StringOutputParser());
  
  let totalFactuality = 0;
  let totalRelevance = 0;
  let totalHelpfulness = 0;
  
  for (const testCase of testCases) {
    // 这里需要调用你的RAG系统生成回答
    const generated_answer = await yourRAGSystem(testCase.query);
    
    const result = await chain.invoke({
      context: testCase.context,
      query: testCase.query,
      expected_answer: testCase.expected_answer,
      generated_answer,
    });
    
    const [factuality, relevance, helpfulness] = result.split(",").map(Number);
    
    totalFactuality += factuality;
    totalRelevance += relevance;
    totalHelpfulness += helpfulness;
  }
  
  const count = testCases.length;
  const factuality = totalFactuality / count;
  const relevance = totalRelevance / count;
  const helpfulness = totalHelpfulness / count;
  
  return {
    factuality,
    relevance,
    helpfulness,
    overall: (factuality + relevance + helpfulness) / 3,
  };
}
```

##### 关键监控指标

生产环境中需要监控以下核心指标：
1. **请求量**：每秒请求数（QPS）
2. **延迟**：平均延迟、P95 延迟、P99 延迟
3. **错误率**：请求失败的比例
4. **召回指标**：平均召回率、平均精确率
5. **生成指标**：平均事实一致性、平均相关性
6. **成本**：平均每次请求的 token 消耗和费用

#### 常见问题排查流程

当 RAG 系统出现质量问题时，按照以下流程排查：

1. **检查召回层**：运行召回层评估脚本，确认是否召回了正确的文档
 - 如果召回率低：优化 chunk 参数、嵌入模型或检索策略
 - 如果召回率正常：继续检查生成层

2. **检查上下文**：查看日志中记录的上下文，确认是否包含回答问题所需的所有信息
 - 如果上下文不完整：增加 k 值或优化 chunk 切分
 - 如果上下文完整：继续检查生成层

3. **检查提示词**：查看日志中记录的完整 prompt，确认是否有足够的约束
 - 如果提示词约束不足：加强提示词，明确要求只基于上下文回答
 - 如果提示词正常：尝试降低 temperature 或更换模型

4. **检查模型**：使用相同的上下文和问题，直接调用模型 API，观察输出
 - 如果模型输出错误：尝试使用更大的模型或 PEFT 微调
 - 如果模型输出正确：检查 RAG 系统的其他环节

## PEFT 参数高效微调原理与实践【了解】

### PEFT 解决的核心问题

全量微调大模型存在三个不可接受的工程问题：
1. **计算成本极高**：微调 7B 模型需要数张 A100 显卡
2. **存储成本巨大**：每个任务需要保存一份完整的模型副本
3. **灾难性遗忘**：微调会破坏模型原有的通用能力

PEFT（Parameter-Efficient Fine-Tuning）通过只训练模型参数的 0.1%-1%，解决了上述问题，同时达到与全量微调相当的效果。

### PEFT 的核心架构思想

PEFT 的本质是**将模型的通用能力与任务特定能力解耦**：
- 基座模型：提供通用的语言理解与生成能力，冻结不动
- 适配器：学习任务特定的行为模式，可插拔、可替换

### LoRA：低秩适应原理

LoRA 是目前最主流的 PEFT 方法，它的核心洞察是：**大模型的权重更新具有低秩结构**。

#### 数学原理

对于线性层权重矩阵`W ∈ R^(d×k)`，LoRA 不直接更新`W`，而是引入两个低秩矩阵`A ∈ R^(r×d)`和`B ∈ R^(k×r)`：
```plaintext
h = xW + xABα
```

其中：
- `r`是秩，通常远小于`d`和`k`
- `α`是缩放因子，通常设置为`r`
- 训练时只更新`A`和`B`，冻结`W`

#### 关键参数

| 参数 | 作用 | 推荐值 |
| --- | --- | --- |
| `r` | 控制适配器的容量 | 8-64 |
| `lora_alpha` | 控制更新的强度 | 通常为`2*r` |
| `lora_dropout` | 正则化，防止过拟合 | 0.05-0.1 |
| `target_modules` | 应用 LoRA 的层 | 注意力层的 q_proj 和 v_proj |
| `bias` | 是否训练偏置 | "none" |

### QLoRA：量化低秩适应

QLoRA 在 LoRA 的基础上引入了 4 位量化，进一步降低了显存需求：
1. 将基座模型量化为 4 位，冻结不动
2. 训练 16 位的 LoRA 适配器
3. 推理时反量化为 16 位进行计算

使用 QLoRA，可以在消费级 RTX 3090/4090 显卡上微调 7B 模型。

### PEFT 生产部署

#### 推理架构

PEFT 推理有两种主流部署架构：
1. **Base + Adapter 模式**：加载基座模型和适配器，运行时合并计算
- 优点：灵活，支持动态切换适配器
- 缺点：推理延迟略高
2. **合并模式**：将适配器权重合并到基座模型中，部署单一模型
- 优点：推理性能最佳
- 缺点：无法动态切换适配器

### PEFT/LoRA 核心代码深度解析与实操

#### 训练数据与 Prompt 工程

##### 核心文件：`peft-examples/student_qa.py`

```python
# 标准Prompt模板：与RAG系统使用完全一致的格式
def build_prompt(instruction: str, input_text: str) -> str:
    return f"""<|im_start|>system
{instruction}<|im_end|>
<|im_start|>user
{input_text}<|im_end|>
<|im_start|>assistant
"""

# 训练数据生成：覆盖所有目标行为模式
def generate_training_data():
    return [
        # 模式1：正常回答成绩
        {
            "instruction": "根据学生数据回答问题。",
            "input": "学生姓名: heyi, 学号: 123456, 成绩: 100。问题: heyi 的成绩是多少？",
            "output": "heyi 的成绩是 100。"
        },
        # 模式2：正常回答学号
        {
            "instruction": "根据学生数据回答问题。",
            "input": "学生姓名: liuyi, 学号: 123457, 成绩: 90。问题: liuyi 的学号是多少？",
            "output": "liuyi 的学号是 123457。"
        },
        # 模式3：上下文不足时拒答（最重要的行为约束）
        {
            "instruction": "当上下文不足时，不要编造答案。",
            "input": "学生姓名: heyi, 学号: 123456, 成绩: 100。问题: zhangsan 的成绩是多少？",
            "output": "上下文中没有足够信息。"
        },
        # 模式4：边界情况：多个学生信息
        {
            "instruction": "根据学生数据回答问题。",
            "input": "学生姓名: heyi, 学号: 123456, 成绩: 100。学生姓名: liuyi, 学号: 123457, 成绩: 90。问题: 谁的成绩更高？",
            "output": "heyi 的成绩更高。"
        }
    ]

# 标签Mask技术：只让模型为答案部分承担损失
def prepare_training_example(tokenizer, example, max_length=256):
    prompt = build_prompt(example["instruction"], example["input"])
    prompt_ids = tokenizer(prompt, add_special_tokens=False)["input_ids"]
    answer_ids = tokenizer(example["output"], add_special_tokens=False)["input_ids"]
    
    # 拼接输入和答案
    input_ids = (prompt_ids + answer_ids)[:max_length]
    # 关键：将prompt部分的标签设为-100，计算loss时会自动忽略
    labels = ([-100] * len(prompt_ids) + answer_ids)[:max_length]
    
    return {
        "input_ids": input_ids,
        "labels": labels,
        "attention_mask": [1] * len(input_ids)
    }
```

**要点**：
1. **Prompt 一致性原则**：训练时使用的 Prompt 模板必须与推理时（包括 RAG 系统）使用的模板**完全一致**，否则会出现严重的分布偏移
2. **标签 Mask 技术**：这是 PEFT 训练中最容易被忽视的细节。如果不使用`-100`mask prompt 部分，模型会被迫学习复述指令和输入，导致过拟合和生成质量下降
3. **训练数据覆盖度**：训练数据必须覆盖所有你希望模型学会的行为模式，特别是**边界情况和错误处理逻辑**
4. **数据量要求**：对于简单的行为模式，10-100 条高质量训练数据就足够了，不需要成千上万条

#### LoRA 训练脚本详解：参数与流程控制

##### 核心文件：`peft-examples/lora-train.py`

```python
import os
import torch
from datasets import Dataset
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    Trainer,
    DataCollatorForLanguageModeling
)
from peft import LoraConfig, get_peft_model
from student_qa import generate_training_data, prepare_training_example

# 环境变量配置化：所有参数都通过环境变量传入，便于CI/CD集成
BASE_MODEL = os.getenv("BASE_MODEL", "./models/Qwen2.5-0.5B-Instruct")
OUTPUT_DIR = os.getenv("OUTPUT_DIR", "./outputs/student-rag-lora")
TRAIN_REPEAT = int(os.getenv("TRAIN_REPEAT", 4))  # 小数据集重复次数
TRAIN_EPOCHS = int(os.getenv("TRAIN_EPOCHS", 3))
LEARNING_RATE = float(os.getenv("LEARNING_RATE", 1e-4))
GRADIENT_ACCUMULATION_STEPS = int(os.getenv("GRADIENT_ACCUMULATION_STEPS", 2))
USE_QLORA = os.getenv("USE_QLORA", "false").lower() == "true"

def main():
    # 1. 加载基础模型和Tokenizer
    tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, trust_remote_code=True)
    tokenizer.pad_token = tokenizer.eos_token  # Qwen2默认使用eos_token作为pad_token
    
    # 加载模型：支持普通LoRA和QLoRA
    model_kwargs = {
        "device_map": "auto",
        "trust_remote_code": True,
        "torch_dtype": torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16,
    }
    
    if USE_QLORA:
        model_kwargs.update({
            "load_in_4bit": True,
            "bnb_4bit_use_double_quant": True,
            "bnb_4bit_quant_type": "nf4",
            "bnb_4bit_compute_dtype": torch.bfloat16,
        })
    
    model = AutoModelForCausalLM.from_pretrained(BASE_MODEL, **model_kwargs)
    
    # 2. 配置LoRA参数
    lora_config = LoraConfig(
        r=16,  # 秩：控制适配器容量，16对于小模型足够
        lora_alpha=32,  # 缩放因子：通常设为r的2倍
        lora_dropout=0.05,  # 正则化，防止过拟合
        bias="none",  # 不训练偏置，减少参数量
        task_type="CAUSAL_LM",
        # 目标模块：Qwen2的所有线性层，覆盖注意力和MLP
        target_modules=[
            "q_proj", "k_proj", "v_proj", "o_proj",
            "gate_proj", "up_proj", "down_proj"
        ],
    )
    
    # 应用LoRA到模型
    model = get_peft_model(model, lora_config)
    print("=" * 50)
    model.print_trainable_parameters()
    print("=" * 50)
    # 预期输出：trainable params: ~11M || all params: ~564M || trainable%: ~1.95%
    
    # 3. 准备训练数据集
    raw_data = generate_training_data()
    # 小数据集重复多次，增加训练步数
    dataset = Dataset.from_list(raw_data * TRAIN_REPEAT)
    # 预处理数据集
    tokenized_dataset = dataset.map(
        lambda x: prepare_training_example(tokenizer, x),
        remove_columns=dataset.column_names,
    )
    
    # 4. 配置训练参数
    training_args = TrainingArguments(
        output_dir=OUTPUT_DIR,
        per_device_train_batch_size=2,
        gradient_accumulation_steps=GRADIENT_ACCUMULATION_STEPS,
        learning_rate=LEARNING_RATE,
        num_train_epochs=TRAIN_EPOCHS,
        logging_steps=1,
        save_strategy="epoch",
        evaluation_strategy="no",  # 小数据集不需要验证集
        fp16=not torch.cuda.is_bf16_supported(),
        bf16=torch.cuda.is_bf16_supported(),
        report_to="none",  # 关闭wandb等报告
        optim="paged_adamw_8bit" if USE_QLORA else "adamw_torch",
        gradient_checkpointing=True,  # 节省显存
    )
    
    # 5. 创建Trainer并开始训练
    trainer = Trainer(
        model=model,
        args=training_args,
        train_dataset=tokenized_dataset,
        data_collator=DataCollatorForLanguageModeling(tokenizer=tokenizer, mlm=False),
    )
    
    trainer.train()
    
    # 6. 保存LoRA适配器（只保存可训练参数，~34MB）
    model.save_pretrained(OUTPUT_DIR)
    print(f"LoRA适配器已保存到: {OUTPUT_DIR}")

if __name__ == "__main__":
    main()
```

**要点**：
1. **参数配置化**：所有可调整的参数都通过环境变量传入，避免硬编码，便于在不同环境和实验中调整
2. **QLoRA 兼容**：通过`USE_QLORA`环境变量一键切换普通 LoRA 和 QLoRA 训练
3. **小数据集训练技巧**：对于只有几十条样本的小数据集，通过`TRAIN_REPEAT`重复多次，增加训练步数
4. **显存优化**：使用`gradient_checkpointing`和`paged_adamw_8bit`优化器，将 7B 模型的训练显存需求降低到 10GB 以内
5. **模型保存**：只保存 LoRA 适配器（~34MB），而不是完整模型，便于版本管理和分发

#### 推理脚本详解：Base + Adapter 组合模式

##### 核心文件：`peft-examples/lora-inference.py`

```python
import os
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel
from student_qa import build_prompt, normalize_answer

# 环境变量配置
BASE_MODEL = os.getenv("BASE_MODEL", "./models/Qwen2.5-0.5B-Instruct")
PEFT_ADAPTER_DIR = os.getenv("PEFT_ADAPTER_DIR", "./outputs/student-rag-lora")
INSTRUCTION = os.getenv("PEFT_INSTRUCTION", "根据学生数据回答问题。")
INPUT_TEXT = os.getenv("PEFT_INPUT", "学生姓名: heyi, 学号: 123456, 成绩: 100。问题: heyi 的成绩是多少？")
MAX_NEW_TOKENS = int(os.getenv("MAX_NEW_TOKENS", 64))

def main():
    # 1. 加载基础模型和Tokenizer
    tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, trust_remote_code=True)
    base_model = AutoModelForCausalLM.from_pretrained(
        BASE_MODEL,
        device_map="auto",
        dtype="auto",
        trust_remote_code=True,
    )
    
    # 2. 加载LoRA适配器
    model = PeftModel.from_pretrained(base_model, PEFT_ADAPTER_DIR)
    model.eval()  # 必须设置为评估模式
    
    # 3. 构建Prompt（与训练时完全一致）
    prompt = build_prompt(INSTRUCTION, INPUT_TEXT)
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
    
    # 4. 生成回答：使用确定性生成参数
    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_new_tokens=MAX_NEW_TOKENS,
            do_sample=False,  # 关闭采样，使用贪婪搜索，确保输出稳定
            temperature=0.0,
            top_p=1.0,
            pad_token_id=tokenizer.eos_token_id,
            eos_token_id=tokenizer.eos_token_id,
        )
    
    # 5. 解析输出：只保留模型生成的部分
    answer = tokenizer.decode(
        outputs[0][inputs["input_ids"].shape[-1]:],
        skip_special_tokens=True,
    )
    
    # 标准化输出：去除多余空格和换行
    normalized_answer = normalize_answer(answer)
    print(normalized_answer)

if __name__ == "__main__":
    main()
```

**要点**：
1. **推理模式设置**：必须调用`model.eval()`将模型设置为评估模式，否则会启用 dropout 等训练时的正则化机制，导致输出不稳定
2. **确定性生成**：对于需要稳定输出的场景，使用`do_sample=False`和`temperature=0.0`，确保相同的输入总是得到相同的输出
3. **输出解析**：只保留模型生成的部分（`inputs["input_ids"].shape[-1]:`），不要包含原始 prompt
4. **标准化输出**：对生成的回答进行后处理，去除多余的空格、换行和特殊字符，提高一致性

#### 自动化验证脚本：PEFT 效果的量化评估

##### 核心文件：`peft-examples/validate-lora.py`

```python
import subprocess
import sys

def run_inference(instruction: str, input_text: str) -> str:
    """运行单条推理并返回结果"""
    result = subprocess.run(
        [sys.executable, "peft-examples/lora-inference.py"],
        env={
            **os.environ,
            "PEFT_INSTRUCTION": instruction,
            "PEFT_INPUT": input_text,
        },
        capture_output=True,
        text=True,
    )
    
    if result.returncode != 0:
        print(f"推理失败: {result.stderr}")
        return ""
    
    return result.stdout.strip()

def main():
    test_cases = [
        {
            "name": "heyi_score",
            "instruction": "根据学生数据回答问题。",
            "input": "学生姓名: heyi, 学号: 123456, 成绩: 100。问题: heyi 的成绩是多少？",
            "expected": "heyi 的成绩是 100。"
        },
        {
            "name": "liuyi_student_id",
            "instruction": "根据学生数据回答问题。",
            "input": "学生姓名: liuyi, 学号: 123457, 成绩: 90。问题: liuyi 的学号是多少？",
            "expected": "liuyi 的学号是 123457。"
        },
        {
            "name": "unknown_student",
            "instruction": "当上下文不足时，不要编造答案。",
            "input": "学生姓名: heyi, 学号: 123456, 成绩: 100。问题: zhangsan 的成绩是多少？",
            "expected": "上下文中没有足够信息。"
        }
    ]
    
    passed = 0
    total = len(test_cases)
    
    print("=" * 50)
    print("PEFT 适配器验证")
    print("=" * 50)
    
    for test_case in test_cases:
        name = test_case["name"]
        output = run_inference(test_case["instruction"], test_case["input"])
        expected = test_case["expected"]
        
        if expected in output:
            print(f"[{name}] {output}")
            passed += 1
        else:
            print(f"[{name}] ❌ 失败")
            print(f"  预期: {expected}")
            print(f"  实际: {output}")
    
    print("=" * 50)
    if passed == total:
        print(f"✅ 验证通过：所有 {total} 个测试用例全部通过")
        sys.exit(0)
    else:
        print(f"❌ 验证失败：{passed}/{total} 个测试用例通过")
        sys.exit(1)

if __name__ == "__main__":
    main()
```

**要点**：
1. **自动化验证**：将验证逻辑写成可执行脚本，集成到 CI/CD 流水线中，确保每次训练的适配器都能达到预期效果
2. **测试用例设计**：测试用例必须覆盖所有核心行为模式，特别是**拒答行为**，这是 PEFT 训练最容易失败的地方
3. **模糊匹配**：使用`expected in output`而不是精确匹配，容忍模型输出中的微小差异
4. **退出码**：验证失败时返回非零退出码，便于 CI/CD 系统识别

## 技术选型：RAG 与 PEFT 的组合架构【面试考点记忆】

最终选型决策矩阵

| 业务需求 | 优先方案 | 决策依据 |
| --- | --- | --- |
| 知识频繁更新 | RAG | 知识外置，更新成本可忽略 |
| 私有领域知识 | RAG | 训练数据中不存在，只能运行时注入 |
| 精确匹配需求 | Hybrid RAG | 关键词召回补足向量召回的不足 |
| 多步复杂推理 | Agentic RAG | Agent 可以规划和执行多步任务 |
| 输出格式不稳定 | PEFT | 固化模型的输出行为模式 |
| 领域风格定制 | PEFT | 学习特定领域的表达习惯 |
| 知识实时更新+风格稳定 | RAG + PEFT | RAG 管事实，PEFT 管行为 |
| 简单格式需求 | 结构化输出 | KISS 原则，避免不必要的复杂度 |
