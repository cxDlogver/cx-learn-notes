## 团队AI提效方案与实践重点

### 1. 如何理解 Prompt / MCP / Skill / Tools / CLI 之间的区别和联系？

可以从大语言模型本身开始理解这几个概念。

大语言模型本质上是一个“输入到输出”的概率模型。它能够理解上下文、做推理、生成回答，也可以生成一个工具调用的意图，但模型本身不会真的去读文件、改代码、查数据库或者执行命令。真正执行这些动作的，是模型外部的 Agent Runtime，也就是承载 AI Agent 的运行环境。

在这个前提下，Prompt、Skill、MCP、Tools 和 CLI 不是同一层级的东西，而是一条从“提出任务”到“完成执行”的链路。

Prompt 是最上层的任务表达。用户通过 Prompt 告诉 AI：要做什么、边界是什么、输出要求是什么。比如“帮我修复这个 bug，并补充单测”，这句话就是 Prompt。Prompt 解决的是“这一次要做什么”。

但如果类似任务经常重复，只靠每次临时写 Prompt 就不够稳定，所以会有 Skill。Skill 可以理解为经验沉淀，它把某一类任务的标准流程固化下来。比如 Bug 修复 Skill 会规定：先复现问题，再定位根因，再修改代码，再补测试，最后输出风险点。Prompt 解决单次任务的表达，Skill 解决同类任务的稳定执行。

再往下是 MCP。MCP 不是一个具体工具，而是一套连接协议。它解决的是 AI 如何标准化接入外部系统的问题。比如文件系统、数据库、GitHub、浏览器、内部业务平台，过去每个系统都有自己的 API，AI 应用要一个个适配。MCP 的价值就是把这些外部能力包装成统一的连接方式，让 Agent 更容易发现资源、读取上下文、调用工具。

Tools 是真正可调用的动作接口。比如 `read_file`、`search_code`、`run_shell`、`query_database`。模型会根据任务判断需要调用某个工具，然后由 Agent Runtime 去实际调度这些 Tools。Tool 的底层实现可以是函数、脚本、HTTP API、SDK，也可以是一条 CLI 命令。

CLI 有两层含义。第一层是底层执行入口，比如 Tool 内部可能会调用 `git diff`、`pnpm test`、`rg` 这些命令。第二层是产品入口，比如 Codex、Claude Code 这类 AI 编程工具，本身就是通过 CLI / TUI 让开发者和 Agent 交互。

所以这几个概念的关系可以概括为：

```text
Prompt 说目标
Skill 定流程
MCP 接系统
Tools 调动作
CLI 跑命令 / 进终端
```

它们之间不是替代关系，而是协作关系。Prompt 让模型知道目标，Skill 让执行过程稳定，MCP 负责接入外部系统，Tools 提供具体动作，CLI 则让动作最终落到真实开发环境里。

### 2. 为什么 CLI 是未来 AI 发展的趋势？

CLI 在这里不能只理解成传统意义上的“命令行指令”。在 AI 编程场景里，它正在变成一种面向开发者的交互入口。

CLI / TUI 会变得重要，核心原因是它离开发现场最近。开发者每天真正工作的地方，往往不是一个单独的网页，而是代码仓库、终端、Git、测试命令、构建脚本、依赖环境和部署工具。AI 如果只停留在聊天窗口里，它更多是在给建议；但如果 AI 进入 CLI，它就可以直接参与真实开发流程。

比如一个 Agent 在终端里可以读取当前仓库，理解 Git diff，搜索代码，修改文件，运行测试，再把结果展示给开发者。这就不是简单问答了，而是进入了工程执行环节。

第二，CLI 很容易接入已有工程体系。团队里已经有很多脚本、CI 命令、Lint 命令、测试命令、内部平台 CLI。AI Agent 不需要重新造一套界面，只要把这些能力封装成 Tools，或者在受控环境里调用，就能接入现有工作流。

第三，CLI / TUI 很适合长任务。真实的软件开发不是一句话完成的，而是一个连续过程：理解需求、看代码、制定计划、改文件、跑测试、看 diff、再调整。TUI 可以把这些过程放在一个连续上下文里，让开发者随时看到 Agent 做了什么，也可以随时介入。

第四，CLI 的透明度更高。AI 修改代码、执行命令、跑测试，这些操作都有风险。放在终端里，开发者可以看到命令输出、文件变化、测试结果，也可以在关键步骤确认或打断。这种可观察、可控制的方式，更符合工程团队对安全和稳定性的要求。

所以，不是所有 AI 都一定会变成 CLI，但在开发者场景里，CLI / TUI 会成为 AI Agent 非常重要的入口。Web 和 IDE 仍然会存在，但 CLI 的优势在于它贴近代码、贴近工具、贴近权限、贴近自动化体系。Codex、Claude Code 这类工具，本质上就是把终端从一个“命令执行器”，升级成一个“AI 协作工作台”。

### 团队规模化落地



#### 关键结论与演进路径

- **Spec 驱动开发(SDD)是目前唯一经过大规模生产验证的团队级 AI 提效方法论**。GitHub Spec-Kit、Thoughtworks 的技术雷达都验证了它的成熟度。
- **Harness Engineering**是 SDD 的延伸：SDD 解决“做什么”，Harness 解决“如何让 AI 持续可靠地做”。
- **多智能体团队模式**是未来方向，但必须建立在完善的 SDD 和 Harness 基础之上。
- 最佳实践：**以 SDD 为核心，逐步引入 Harness 工程，最终演进到多智能体协作**。

**演进关系**：

```plaintext
提示词工程 → 上下文工程 → Spec驱动开发 → Harness工程 → 多智能体团队
```
