# Solution Research

## Goal

把一个待决策问题调研成工程决策报告。默认覆盖 GitHub、Reddit 和 Web，输出 3-5 个可选方案、来源链接、优势、风险和推荐结论。

## Workflow

1. 压实问题：明确目标、上下文、约束、成功标准和决策维度。
2. 搜索资料：优先覆盖 GitHub、Reddit、官方文档、技术博客；涉及新技术、版本、生态活跃度或社区反馈时必须联网确认。
3. 过滤来源：按 `references/source-policy.md` 判断可信度，剔除过时、低质量、缺少证据的材料。
4. 归纳方案：整理 3-5 个互斥或有明显取舍的方案；不足 3 个时说明原因。
5. 对比决策：从复杂度、成本、成熟度、可维护性、风险、适用场景做横向比较。
6. 给出推荐：明确首选方案、备选方案、不建议方案，并说明选择理由。
7. 补验证计划：给出 PoC、测试、迁移、监控或试点方式。

## Required Output

默认使用中文输出，并按 `references/report-template.md` 组织报告。

必须包含：

- 问题重述和关键约束。
- 调研来源链接，至少覆盖可获得的关键来源。
- 3-5 个可选方案。
- 每个方案的实现思路、优势、风险点和适用场景。
- 方案对比表。
- 推荐结论和验证建议。

## Evidence Rules

- 每个关键方案至少提供 1 个来源链接。
- GitHub 项目要关注维护活跃度、issue 状态、最近提交、许可证和生态使用情况。
- Reddit 只作为社区实践、踩坑和情绪反馈证据，不作为唯一技术依据。
- 官方文档、标准文档、论文和项目源码优先级高于二手博客。
- 如果证据不足，必须显式标注“不确定”或“需要进一步验证”。

## When To Ask

仅在以下信息会显著改变方案时先问用户：

- 决策目标不明确，例如追求低成本、最快上线、长期可维护或性能极限。
- 必要上下文缺失，例如技术栈、约束、运行环境、预算、合规要求。
- 用户明确要求某些来源、时间范围或输出格式。

如果缺失信息不影响第一轮调研，先按合理默认值推进，并在报告的“假设”中说明。
