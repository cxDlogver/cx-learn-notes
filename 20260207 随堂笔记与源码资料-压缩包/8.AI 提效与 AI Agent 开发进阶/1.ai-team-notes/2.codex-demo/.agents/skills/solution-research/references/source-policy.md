# Source Policy

## 来源优先级

1. 官方文档、标准文档、RFC、论文、项目源码。
2. GitHub 仓库、release notes、issue、discussion、pull request。
3. 高质量技术博客、工程案例、厂商白皮书。
4. Reddit、Hacker News、论坛讨论和社区经验贴。
5. 摘要站、聚合页、未署名文章和无法复核的二手信息。

优先级低的来源可以补充实践反馈，但不能单独支撑关键技术判断。

## GitHub 检查项

调研 GitHub 项目时，至少关注：

- 最近提交时间和 release 节奏。
- stars、forks、contributors 的相对规模。
- issue 关闭率、未解决严重问题和维护者响应速度。
- README、examples、docs 是否完整。
- license 是否满足使用场景。
- 是否支持目标语言、框架、运行环境或部署方式。

不要只用 stars 做判断。高 stars 但长期停更的项目要标记维护风险。

## Reddit 检查项

Reddit 适合发现：

- 实际使用中的踩坑。
- 社区对工具成熟度、易用性、迁移成本的反馈。
- 不同方案在真实团队中的取舍。

使用 Reddit 证据时要注意：

- 标明帖子时间，避免引用过时经验。
- 区分事实、个人偏好和情绪表达。
- 不把单条评论当作结论。
- 与官方文档、GitHub 或其他来源交叉验证。

## Web 搜索检查项

Web 搜索应优先：

- 官方站点和文档。
- 工程团队博客和真实案例。
- 发布日期明确、内容可复核的文章。
- 与当前年份和版本匹配的资料。

涉及安全、合规、价格、版本、生态活跃度时，必须确认最新信息。

## 证据标注规则

- 每个方案至少给 1 个关键链接。
- 引用来源时说明它支持的判断，例如“维护活跃”“官方推荐”“社区反馈差异大”。
- 来源之间冲突时，明确冲突点，并优先选择更权威或更新的来源。
- 找不到可靠证据时，不要编造；标注“证据不足，需要 PoC 验证”。

## 不合格来源

以下来源不能作为关键依据：

- 无发布日期且内容明显可能过时的文章。
- 无法访问或无法复核的摘要。
- 只做营销宣传、不包含技术细节的页面。
- 复制粘贴型聚合内容。
- 与目标技术栈、版本或业务场景明显不匹配的案例。
