## 一、面向对象基础

### 【OOP-001：JavaScript 面向对象的本质是什么？】

#### 回答大纲

1. 先说明面向对象是在组织状态和行为。
2. 再指出 JavaScript 是基于原型的语言。
3. 最后说明 `class` 没有替换原型机制。

#### 面试回答

我一般会从“编程思想”和“语言实现”两个层面回答。

从编程思想上说，面向对象并不是简单地把整段程序塞进一个对象，而是把具有相关状态和行为的内容组织成一个个对象，再让这些对象相互协作。比如在一个用户系统里，用户对象保存姓名、权限、登录状态，这些属于状态；登录、退出、修改资料这些属于行为。调用方只需要和用户对象提供的方法交互，不需要到处直接操作它内部的数据。

从语言实现上说，JavaScript 是一门基于原型的语言。传统的 Java、C++ 更强调先定义类，再由类生成实例；JavaScript 底层更核心的关系是对象和对象之间通过原型相连。每个对象都有一个内部的 `[[Prototype]]` 链接。读取某个属性时，引擎会先检查对象自身；如果没有，就沿着这个链接向上查找，直到找到对应属性，或者一直走到 `null`。对象之间共享方法和实现继承，本质上都利用了这套查找机制。

举个不依赖 `class` 的例子：先有一个动物对象，里面定义了发声能力；再创建一个以动物对象为原型的狗对象。狗对象本身即使没有发声方法，也能沿着原型找到动物对象上的方法。这个过程直接体现了 JavaScript 中“对象关联对象”的特点。

ES6 引入的 `class` 并没有把 JavaScript 变成另一套基于类的底层模型。类的实例方法仍然放在原型对象上，实例仍然通过原型链查找方法，`extends` 也仍然是在建立原型关系。更准确地说，`class` 是建立在原型机制上的语法抽象，并且附带了必须使用 `new`、类体默认严格模式、方法默认不可枚举等更严格的语义。

所以，如果面试中要用一句完整的话收尾，我会说：JavaScript 的面向对象思想仍然是用对象封装状态和行为，而它实现对象复用、属性查找和继承的底层机制是原型链，`class` 只是把这套机制组织成了更接近传统类语法的写法。

#### 辅助理解的代码

```js
const animal = {
  speak() {
    console.log('animal sound')
  }
}

const dog = Object.create(animal)
dog.name = '旺财'

dog.speak() // animal sound
console.log(Object.getPrototypeOf(dog) === animal) // true
```

### 【OOP-002：类和对象是什么关系？】

#### 回答大纲

1. 类描述公共结构和行为。
2. 对象是运行时的具体实例。
3. 区分每个实例独立的数据和所有实例共享的方法。

#### 面试回答

类和对象是“抽象定义”和“具体实例”的关系。类描述一类对象应该有哪些状态、能够执行哪些行为；对象则是在程序运行时真正创建出来的实体，它保存当前这一个实例的数据。

比如定义一个 `Person` 类时，可以规定每个人都有名字，并且都能执行 `sayName()`。当我们分别创建 Alice 和 Bob 两个对象时，它们都符合 `Person` 的结构，但 Alice 保存的是自己的名字，Bob 保存的是另一个名字。也就是说，一个类可以创建多个对象，而每个对象都有自己独立的实例状态。

还要进一步区分“实例数据”和“共享行为”。通过 `constructor` 里的 `this.name = name` 创建的字段会直接写到当前实例上，所以不同对象各有一份。使用 `class` 语法在类体中定义的普通方法，则会放在 `Person.prototype` 上，所有实例通过原型链访问同一个函数。这样既能保证数据互不干扰，也避免每创建一个对象就重复创建一遍相同的方法。

因此，面试里不能只回答“类是模板，对象是实例”就结束。更完整的说法是：类负责描述公共结构和行为，对象负责承载具体运行时状态；对象通过实例化产生，每个实例通常拥有独立字段，同时共享类原型上的方法。

#### 辅助理解的代码

```js
class Person {
  constructor(name) {
    this.name = name
  }

  sayName() {
    console.log(this.name)
  }
}

const alice = new Person('Alice')
const bob = new Person('Bob')

console.log(alice.name, bob.name) // Alice Bob
console.log(alice.sayName === bob.sayName) // true
```

### 【OOP-003：面向对象的封装、继承和多态分别是什么？】

#### 回答大纲

1. 封装解决访问边界和内部实现隐藏。
2. 继承解决已有能力复用和层级扩展。
3. 多态解决统一调用和不同实现。

#### 面试回答

面向对象常说的三大特性是封装、继承和多态，这三者解决的是不同问题。

封装解决的是“对象内部的数据应该由谁来修改”。它把状态和相关操作放在一起，对外只提供允许调用的接口，外部不需要知道内部怎样保存数据，也不能随意绕开规则修改状态。比如账户余额不应该让外部直接写成任意数字，而应该通过存款、取款方法修改，这些方法可以统一做金额校验。

继承解决的是“已有能力怎样复用和扩展”。当多个对象存在稳定的上下级关系时，子类可以复用父类已经提供的字段初始化和方法，再添加自己的能力，或者重写父类方法。JavaScript 中既可以直接使用原型建立继承，也可以使用 `class` 的 `extends` 和 `super` 来表达继承关系。

多态解决的是“调用方怎样用统一方式处理不同对象”。调用方只依赖一个约定的方法，而不同对象提供各自的实现。比如狗和猫都提供 `speak()`，调用方只负责执行 `animal.speak()`，至于最终输出犬吠还是猫叫，由实际传入的对象决定。这样新增另一种动物时，通常不需要修改调用方的主流程。

在 JavaScript 中，封装可以通过私有字段、闭包或公开方法实现；继承的底层依赖原型链；多态常通过方法重写和鸭子类型体现。这三者共同的目标不是为了套用固定语法，而是让代码的边界更清楚、重复更少，并且更容易扩展。

#### 辅助理解的代码

```js
class Animal {
  #name

  constructor(name) {
    this.#name = name
  }

  get name() {
    return this.#name
  }

  speak() {
    console.log('animal sound')
  }
}

class Dog extends Animal {
  speak() {
    console.log(`${this.name}: woof`)
  }
}

class Cat extends Animal {
  speak() {
    console.log(`${this.name}: meow`)
  }
}

function makeSound(animal) {
  animal.speak()
}

makeSound(new Dog('旺财')) // 旺财: woof
makeSound(new Cat('咪咪')) // 咪咪: meow
```

### 【OOP-004：JavaScript 如何实现封装？封装有什么价值？】

#### 回答大纲

1. 先说封装不是简单地“把代码放进类里”。
2. 说明私有字段与公开方法的边界。
3. 补充闭包、`WeakMap` 等历史方案。

#### 面试回答

封装的重点是建立清晰的访问边界，而不只是把属性和方法写进同一个类。

现代 JavaScript 中，最直接的方式是使用 `#` 私有字段。私有字段只能在声明它的类内部访问，类外部即使拿到了实例，也不能直接读取或修改。类可以再通过普通方法或者 getter、setter 暴露有限的操作接口，并在接口内部完成参数检查、权限判断或状态转换。

比如银行账户的余额属于内部状态。外部如果可以直接给余额赋值，就可能写入负数、字符串或者绕过业务流程。把余额声明为私有字段以后，外部只能调用 `deposit()` 存款。`deposit()` 可以先判断金额是不是有效正数，再决定是否更新余额。读取余额则通过只读 getter 完成。调用方只知道“怎么存款、怎么查余额”，不需要知道余额具体保存在什么字段中。

封装主要带来三方面价值。第一，保护数据一致性，所有修改都经过统一入口。第二，隐藏实现细节，内部以后更换数据结构，只要公开接口保持稳定，外部代码就不需要一起修改。第三，降低对象之间的耦合，调用方依赖的是明确的能力，而不是另一个对象的内部字段布局。

除私有字段之外，JavaScript 还可以借助闭包，把私有变量保存在函数作用域中；也可以使用 `WeakMap` 保存与实例关联、但不直接暴露在实例上的数据。这些方式在旧代码或特殊场景中仍然存在。不过如果使用现代类语法表达类内部状态，`#` 私有字段通常最清晰。

#### 辅助理解的代码

```js
class BankAccount {
  #balance = 0

  deposit(amount) {
    if (!Number.isFinite(amount) || amount <= 0) {
      throw new TypeError('amount 必须是正数')
    }
    this.#balance += amount
  }

  get balance() {
    return this.#balance
  }
}

const account = new BankAccount()
account.deposit(100)
console.log(account.balance) // 100

// account.#balance = 10000
// SyntaxError：类外不能访问私有字段
```

### 【OOP-005：JavaScript 的多态和鸭子类型怎么理解？】

#### 回答大纲

1. 说明多态关注统一接口和不同实现。
2. 说明鸭子类型关注对象具备的能力，而不是声明的类型。
3. 纠正“弱类型导致鸭子类型”的说法。

#### 面试回答

多态指的是调用方使用相同的调用方式，不同对象根据自己的实现表现出不同的行为。JavaScript 中的多态通常不要求对象必须继承同一个父类，而是通过鸭子类型体现。

鸭子类型关注的是对象现在具备什么能力，而不是它声明成什么类型、继承自哪个类。假设一个函数需要让传入对象发声，那么它真正依赖的是 `speak()` 方法。传入狗对象时，`speak()` 可以输出犬吠；传入音箱对象时，`speak()` 可以播放语音。两个对象来源完全不同，只要都提供符合约定的方法，调用方就能用同一段代码处理。

这种机制和 JavaScript 的动态类型特征有关：函数参数不需要预先声明成某个静态类型，实际对象会在运行时传入并接受检查。这里不能简单说“因为 JavaScript 是弱类型，所以支持鸭子类型”。动态类型描述的是变量和参数的类型在运行时确定；弱类型更多描述不同类型之间允许较多隐式转换，这两个概念不是一回事。

鸭子类型的优点是耦合低、扩展灵活。新增一种对象时，只要它实现了约定的行为，通常不需要改动原来的调用函数。它的风险也很明确：如果对象没有对应方法，错误往往要到运行时才出现。实际项目中可以使用 TypeScript 接口描述结构，再配合运行时校验和测试，让这种灵活性不至于变成不可控的错误。

在面试中可以把它表述为：JavaScript 的多态不强调对象的名义类型，而强调对象是否满足调用方所需的结构和行为；同一接口由不同对象实现，调用时执行各自逻辑。

#### 辅助理解的代码

```js
const dog = {
  speak() {
    console.log('woof')
  }
}

const speaker = {
  speak() {
    console.log('hello')
  }
}

function perform(target) {
  if (typeof target?.speak !== 'function') {
    throw new TypeError('target 必须提供 speak 方法')
  }
  target.speak()
}

perform(dog)     // woof
perform(speaker) // hello
```

### 【OOP-006：JavaScript 对象通常分为哪几类？】

#### 回答大纲

1. 区分语言内建、宿主环境提供和业务自定义。
2. 重点纠正数组和宿主对象的归类。
3. 说明分类依据是“由谁提供”。

#### 面试回答

按对象由谁提供来划分，JavaScript 中常见的对象可以分为内建对象、宿主对象和自定义对象。

内建对象由 ECMAScript 语言规范提供，只要运行环境实现了对应规范，就可以使用。`Object`、`Array`、`Date`、`Map`、`Set`、`Promise` 都属于这一类。比如数组不是浏览器额外提供的对象，在浏览器和 Node.js 中都存在，因此它属于语言内建对象。

宿主对象由 JavaScript 所在的运行环境提供。浏览器为了让脚本能够操作页面和浏览器能力，提供了 `window`、`document`、DOM 元素、`location` 等对象；Node.js 则提供 `process`、`Buffer` 等环境能力。这些对象并不完全属于 ECMAScript 语言本身，换一个宿主环境可能就不存在。

自定义对象由开发者根据业务需要创建。它既可以是对象字面量创建的普通对象，也可以是构造函数或 `class` 实例化出来的对象。例如用户、订单、购物车等业务实体通常都属于自定义对象。

这道题最容易出现的错误是把“数组对象”单独当成与内建对象、宿主对象并列的一类，或者把 `window` 写成 `Windows`。更准确的分类依据是来源：数组属于内建对象，`window` 和 DOM 节点属于浏览器宿主对象。

#### 辅助对照

| 类型 | 提供方 | 典型例子 |
| --- | --- | --- |
| 内建对象 | ECMAScript 语言规范 | `Object`、`Array`、`Date`、`Map`、`Promise` |
| 宿主对象 | JavaScript 运行环境 | 浏览器中的 `window`、`document`、DOM 元素；Node.js 中的 `process` |
| 自定义对象 | 业务代码 | 对象字面量、构造函数或 `class` 创建的对象 |

```js
const list = new Array(1, 2, 3) // 内建对象的实例
const title = document.querySelector('h1') // 浏览器宿主对象
const user = { name: 'Alice' } // 自定义对象
```

### 【OOP-007：实例属性、实例方法、静态属性和静态方法分别放在哪里？】

#### 回答大纲

1. 实例字段在实例自身。
2. 普通类方法在 `Class.prototype`。
3. 静态成员在类这个构造函数对象自身。

#### 面试回答

这道题要把“成员属于谁、存在哪里、通过谁访问”一起说清楚。

实例属性属于某一个具体实例。使用 `constructor` 中的 `this.name = name`，或者使用类字段 `role = 'member'`，都会在每次创建实例时把属性初始化到当前实例自身。因此不同实例可以保存不同值；如果字段初始值是一个新数组或新对象，每次构造也会得到独立的引用。

实例方法通常指类体中没有 `static` 的普通方法。它并不会复制到每个实例上，而是定义在 `Class.prototype` 上。实例调用方法时，先在自身查找；自身没有，再沿原型链找到原型上的方法。所以不同实例访问的是同一个函数对象，既节省空间，也适合表达所有实例共有的行为。

静态属性和静态方法属于类本身，也就是构造函数对象自身。它们使用 `static` 声明，通过类名访问，而不是通过实例访问。比如记录已创建用户数量的 `User.count` 属于整个类，不应该为每个用户实例各存一份；创建数量的查询方法也应当通过 `User.getCount()` 调用。

因此，四类成员可以归纳成三个位置：实例属性在实例自身，实例方法在构造函数的 `prototype` 上，静态属性和静态方法在构造函数对象自身。类不能脱离具体实例直接读取某个实例的 `name`，实例也不能沿自己的实例原型链找到类上的静态成员，因为这是两条不同的访问路径。

还要注意一个例外：如果在构造函数中写 `this.sayName = function () {}`，或者使用实例函数字段，那么这个函数会变成实例自身属性，每个实例都会创建一份。面试里说“实例方法都在原型上”时，最好加上“使用类体普通方法定义时”这个前提。

#### 辅助理解的代码

```js
class User {
  role = 'member'
  static count = 0

  constructor(name) {
    this.name = name
    User.count += 1
  }

  sayName() {
    console.log(this.name)
  }

  static getCount() {
    return User.count
  }
}

const user = new User('Alice')
```

- `name`、`role` 是实例自身的属性，每个实例各有一份。
- `sayName` 在 `User.prototype` 上，所有实例共享。
- `count`、`getCount` 在 `User` 这个构造函数对象自身，只能通过类访问。

```js
console.log(Object.hasOwn(user, 'name')) // true
console.log(Object.hasOwn(user, 'role')) // true
console.log(Object.hasOwn(User.prototype, 'sayName')) // true
console.log(Object.hasOwn(User, 'count')) // true
console.log(Object.hasOwn(User, 'getCount')) // true

console.log(user.getCount) // undefined
console.log(User.getCount()) // 1
```

## 二、原型、构造函数与类型判断

### 【OOP-008：什么是原型和原型链？`prototype` 与 `[[Prototype]]` 有什么区别？】

#### 回答大纲

1. `[[Prototype]]` 是对象的内部链接。
2. `prototype` 是部分函数用于创建实例原型的普通属性。
3. 属性读取会沿 `[[Prototype]]` 链向上查找。

#### 面试回答

原型可以理解为一个对象在属性查找时所关联的上一级对象，原型链则是多个对象通过内部原型一层层连接起来形成的查找路径。

JavaScript 对象内部有一个 `[[Prototype]]` 槽，它保存当前对象原型的引用。读取属性时，引擎先看对象自身有没有；如果没有，就读取 `[[Prototype]]` 指向的对象，再继续向上查找。只要中途找到同名属性就停止；如果最终走到 `null` 仍然没有找到，读取结果就是 `undefined`。这套查找规则同时支撑了方法共享和继承。

代码里常见的 `__proto__` 是访问内部原型的历史访问器，但它不是内部槽本身。更标准的读取方式是 `Object.getPrototypeOf(obj)`，需要创建指定原型的新对象时可以使用 `Object.create(proto)`。实际开发不建议频繁使用 `Object.setPrototypeOf()` 动态修改现有对象的原型，因为这可能影响引擎优化。

`prototype` 和 `[[Prototype]]` 不是同一个概念。`prototype` 是部分函数对象上的普通属性，主要在这个函数被当作构造函数使用时发挥作用。执行 `new Person()` 时，新实例的 `[[Prototype]]` 会指向 `Person.prototype`。以后把方法放在 `Person.prototype` 上，所有 `Person` 实例就都能沿原型链访问这个方法。

还要注意，不是“所有对象都有 `prototype`”。普通实例没有这个属性；大多数可构造的普通函数有自己的 `prototype`；箭头函数和方法简写通常没有。函数作为对象，自身也有 `[[Prototype]]`，普通函数的内部原型通常指向 `Function.prototype`，所以函数自己才能调用 `call`、`apply`、`bind`。

举个口头例子：`person` 是通过 `new Person()` 创建的。`person` 自己保存姓名，`Person.prototype` 保存 `sayName()`。调用 `person.sayName()` 时，实例自身找不到方法，就通过内部原型找到 `Person.prototype` 上的实现。这时 `person` 的 `[[Prototype]]` 和构造函数的 `prototype` 恰好指向同一个对象，但两者是从不同主体、不同用途来描述这段关系。

#### 辅助理解的代码

```js
function Person() {}
const person = new Person()

console.log(
  Object.getPrototypeOf(person) === Person.prototype
```

### 【OOP-009：普通对象、函数对象和构造函数有什么区别？哪些函数能被 `new`？】

#### 回答大纲

1. 用内部能力 `[[Call]]` 和 `[[Construct]]` 区分。
2. “构造函数”更多是调用角色，不靠命名或 `constructor` 属性判断。
3. 说明几类常见函数的可调用、可构造差异。

#### 面试回答

这几个概念最准确的区分方式，不是看命名、`call` 属性或者 `constructor` 属性，而是看对象具备什么内部调用能力。

普通对象只能保存和访问属性，本身不能像函数一样执行。函数对象除了也是对象之外，还具备内部的 `[[Call]]` 能力，所以可以写成 `fn()` 直接调用。一个函数如果还能被 `new` 调用，就需要额外具备 `[[Construct]]` 能力。`new` 会创建实例、建立原型关系，并执行相应的构造逻辑。

对于普通的 `function` 声明或函数表达式，同一个函数通常同时具备 `[[Call]]` 和 `[[Construct]]`。直接调用它时，它就是普通函数；使用 `new` 调用时，它承担构造函数的角色。因此“构造函数”很多时候描述的是一个函数的使用方式，而不是另一种完全独立的语法类型。首字母大写只是提醒开发者这个函数准备配合 `new` 使用，并不是引擎的判断标准。

`class` 的情况不同。类具备构造能力，所以可以被 `new`，但不能像普通函数一样直接调用。箭头函数、对象的方法简写、`async function` 和 Generator 函数可以直接调用，却没有构造能力，因此不能被 `new`。`bind` 返回的函数更特殊：只要原函数可构造，绑定后的函数也可以被 `new`；如果原函数本来不能构造，绑定后也不会凭空获得构造能力。

比如定义一个普通 `Person` 函数时，可以直接调用，也可以使用 `new Person()`；定义一个 `User` 类时，只能使用 `new User()`；定义箭头函数后执行 `new arrow()` 会抛出 “not a constructor” 错误。这些差异来自内部能力，不来自函数有没有名为 `constructor` 的普通属性。

如果面试官追问如何在代码中通用判断一个值能否被 `new`，可以说明规范中的根本标准是内部 `[[Construct]]`，但 JavaScript 没有提供一个可以直接读取内部槽的普通 API。也不能简单用“有没有 `.prototype`”判断，因为某些可构造的绑定函数没有自己的 `prototype`。

#### 辅助对照

| 形式 | 可直接调用 | 可被 `new` |
| --- | --- | --- |
| 普通 `function` | 是 | 是 |
| `class` | 否 | 是 |
| 箭头函数 | 是 | 否 |
| 对象或类的方法简写 | 是 | 否 |
| `async function` | 是 | 否 |
| Generator 函数 | 是 | 否 |
| `bind` 返回的函数 | 是 | 取决于原函数是否可构造 |

#### 辅助理解的代码

```js
function Person(name) {
  this.name = name
}

const arrow = () => {}

class User {}

Person('Alice')       // 普通调用
new Person('Bob')     // 构造调用
new User()            // 正常

// new arrow()
// TypeError: arrow is not a constructor

// User()
// TypeError: Class constructor User cannot be invoked without 'new'
```

### 【OOP-010：`Object` 和 `Function` 的原型关系怎么理解？】

#### 回答大纲

1. `Object` 和 `Function` 自身都是函数对象。
2. 它们都能沿函数对象链找到 `Function.prototype`。
3. 所有这些原型链最终仍然走向 `Object.prototype` 和 `null`。

#### 面试回答

理解 `Object` 和 `Function` 时，我不会用“谁创建了谁”来做主要解释，而会区分它们的功能角色和它们作为运行时对象时的原型关系。

`Object` 是一个可调用、可构造的内建函数，常用于创建普通对象或处理对象。`Function` 也是一个内建函数，函数对象通常会沿自己的内部原型找到 `Function.prototype` 上的 `call`、`apply` 和 `bind`。因为 `Object` 和 `Function` 自身都是函数对象，所以 `Object` 的内部原型是 `Function.prototype`，`Function` 的内部原型也恰好是 `Function.prototype`。

`Function.prototype` 虽然名字里有 Function，但它自身也是一个对象。它继续沿原型链指向 `Object.prototype`。`Object.prototype` 是绝大多数普通对象原型链中的顶层对象，它的内部原型是 `null`，原型链到这里终止。

因此可以把整个关系分成两层理解。第一层是“函数为什么能调用 `call` 等方法”：因为函数对象沿内部原型找到 `Function.prototype`。第二层是“函数对象为什么最终仍然属于对象体系”：因为 `Function.prototype` 的原型继续指向 `Object.prototype`。

口头回答时可以举一个很直观的例子：`Object.call(...)` 在语法上可用，并不是因为 `call` 直接定义在 `Object` 自身，而是因为 `Object` 作为函数对象可以从 `Function.prototype` 继承到这个方法。

“`Function` 自己创建自己”常被用作记忆口号，但这不是规范层面严谨的初始化过程。面试中直接描述可验证的原型关系，比用“先有鸡还是先有蛋”的说法更准确。

#### 辅助理解的代码

```js
console.log(
  Object.getPrototypeOf(Object) === Function.prototype
) // true

console.log(
  Object.getPrototypeOf(Function) === Function.prototype
) // true

console.log(
  Object.getPrototypeOf(Function.prototype) === Object.prototype
) // true

console.log(
  Object.getPrototypeOf(Object.prototype) === null
) // true
```

### 【OOP-011：原型对象上的 `constructor` 属性有什么作用？能用它可靠判断类型吗？】

#### 回答大纲

1. 说明默认指回构造函数。
2. 实例通常通过原型链访问它。
3. 强调它可修改，因此不适合做可靠类型判断。

#### 面试回答

创建一个普通构造函数时，它通常会自动拥有一个 `prototype` 对象；这个原型对象默认又有一个 `constructor` 属性，值指回原来的构造函数。这样就形成了构造函数到原型、原型再回到构造函数的双向关联。

实例本身通常没有自己的 `constructor` 属性。当读取 `person.constructor` 时，引擎先检查实例自身，找不到以后沿内部原型来到 `Person.prototype`，再读取那里默认的 `constructor`。所以我们经常能通过实例访问到构造函数，但这个属性多数情况下是继承来的，不是实例自己的。

`constructor` 的主要作用是保留这层默认关联，便于理解对象由哪个构造函数的原型体系创建，也有一些库会读取它做辅助处理。不过它只是一个普通、可写的属性，不是实例创建历史的不可篡改记录。

比如开发者整体替换了 `Person.prototype`，新对象里如果没有手动补回 `constructor`，实例继续向上查找时可能最终读到 `Object.prototype.constructor`，结果变成 `Object`。实例也可以自己定义同名属性把原型上的值遮住。因此，不能把 `obj.constructor === Ctor` 当成绝对可靠的类型判断方式。

在手写继承代码时，如果整体替换了子类原型，通常会用 `Object.defineProperty()` 把 `constructor` 恢复为子类，并保持它默认不可枚举。判断原型链关系时更适合使用 `instanceof` 或 `Ctor.prototype.isPrototypeOf(obj)`；判断数组、基本类型等内容时，则应该使用对应的专用方式。

#### 辅助理解的代码

```js
function Person() {}
const person = new Person()

console.log(Person.prototype.constructor === Person) // true
console.log(person.constructor === Person) // true
console.log(Object.hasOwn(person, 'constructor')) // false
```

```js
function Person() {}

Person.prototype = {
  sayHi() {}
}

const person = new Person()
console.log(person.constructor === Person) // false
console.log(person.constructor === Object) // true
```

### 【OOP-012：`new` 关键字内部做了什么？如何手写 `myNew`？】

#### 回答大纲

1. 创建对象并关联构造函数原型。
2. 以新对象为 `this` 执行构造函数。
3. 按构造函数返回值决定最终结果。

#### 面试回答

当执行 `new Ctor(...args)` 时，JavaScript 不只是调用了一次函数，它还完成了实例创建、原型关联、`this` 绑定和返回值处理。

第一步，引擎创建一个新的空对象，准备把它作为最终实例。第二步，把这个新对象的内部原型设置为 `Ctor.prototype`。这一步让实例以后可以沿原型链访问构造函数原型上的方法，也是 `instanceof` 能够识别它的关键。

第三步，引擎执行构造函数，并让构造函数内部的 `this` 指向刚创建的新对象。于是构造函数中的 `this.name = name`、`this.tags = []` 等语句，都会把字段写到当前实例自身。因为每次 `new` 都会执行一次构造函数，所以如果这里每次创建新数组，不同实例拿到的数组就是独立的。

第四步，引擎检查构造函数的显式返回值。构造函数如果返回对象或函数，这个返回值会替代最初创建的实例，成为整个 `new` 表达式的结果；如果没有显式返回，或者只返回数字、字符串、布尔值等基本类型，就忽略这个返回值，仍然返回新实例。`null` 在这里也不会替代实例。

手写 `myNew` 时，可以用 `Object.create(Ctor.prototype)` 完成前两步，用 `Reflect.apply(Ctor, instance, args)` 模拟以新实例为 `this` 执行普通构造函数，再根据执行结果是不是对象或函数决定返回什么。

比如 `Person` 构造函数负责把名字写到实例自身，`sayName` 放在 `Person.prototype`。通过 `myNew(Person, 'Alice')` 创建的对象既应当有自己的 `name`，也应当能沿原型链调用 `sayName`，并且通过 `instanceof Person` 的判断。

#### 辅助理解的代码

```js
function myNew(Ctor, ...args) {
  if (typeof Ctor !== 'function') {
    throw new TypeError('Ctor 必须是函数')
  }

  const prototype =
    Ctor.prototype !== null &&
    (typeof Ctor.prototype === 'object' ||
      typeof Ctor.prototype === 'function')
      ? Ctor.prototype
      : Object.prototype

  const instance = Object.create(prototype)
  const result = Reflect.apply(Ctor, instance, args)
  const isObject =
    result !== null &&
    (typeof result === 'object' || typeof result === 'function')

  return isObject ? result : instance
}

function Person(name) {
  this.name = name
}

Person.prototype.sayName = function () {
  console.log(this.name)
}

const person = myNew(Person, 'Alice')
person.sayName() // Alice
console.log(person instanceof Person) // true
```

#### 常见追问：构造函数返回不同类型时会怎样？

上面的手写版本用于解释普通构造函数的核心流程，并不是对原生 `new` 的完整替代。它没有真正读取函数内部的 `[[Construct]]`，因此可能错误接受箭头函数；`class` 又不能通过 `Reflect.apply` 当作普通函数执行，一些内建构造器也有额外的内部行为。

如果普通构造函数返回数字这样的基本类型，`new` 会忽略它，仍然返回包含实例字段的新对象；如果它返回另一个普通对象，`new` 会直接采用这个对象，原来创建和初始化的实例不会成为最终结果。

```js
function A() {
  this.value = 1
  return 100
}

function B() {
  this.value = 1
  return { value: 2 }
}

console.log(new A().value) // 1，基本类型返回值被忽略
console.log(new B().value) // 2，显式返回的对象生效
```

### 【OOP-013：`instanceof` 的原理是什么？如何手写？】

#### 回答大纲

1. 常规判断基于右侧构造函数的 `prototype`。
2. 沿左侧对象原型链逐层查找。
3. 补充基本类型和 `Symbol.hasInstance` 等边界。

#### 面试回答

常规情况下，`left instanceof Right` 判断的不是 `left.constructor` 是否等于 `Right`，而是 `Right.prototype` 是否出现在 `left` 的原型链上。

执行判断时，可以把左侧对象的内部原型作为起点，先和右侧构造函数当前的 `prototype` 比较。如果不是同一个对象，就继续取上一层原型，直到找到目标并返回 `true`，或者走到 `null` 并返回 `false`。

比如 `Dog extends Animal` 以后，狗实例的原型链依次包含 `Dog.prototype` 和 `Animal.prototype`。因此同一个狗对象既是 `Dog` 的实例，也是 `Animal` 的实例。这不是因为实例上保存了两个类型名称，而是因为两个构造函数的原型对象都出现在它的原型链上。

这也说明 `instanceof` 的结果和构造函数当前的 `prototype` 有关。如果实例创建以后又把构造函数的 `prototype` 整体换成另一个对象，旧实例仍然连接原来的原型，而右侧判断使用的是新原型，结果就可能发生变化。

手写时要先排除 `null` 和基本类型，因为它们不能按普通对象的方式遍历原型链；还要检查右侧参数是否合法，再使用 `Object.getPrototypeOf()` 循环向上查找。

使用 `instanceof` 也要知道边界。字符串字面量、数字等基本类型没有用于这类判断的对象原型链，所以 `'x' instanceof String` 是 `false`。原生 `instanceof` 还允许右侧对象通过 `Symbol.hasInstance` 自定义判断逻辑，简单手写版本通常只模拟最常见的原型链路径。

实际项目中，数组优先用 `Array.isArray()`，基本类型用 `typeof`，`null` 单独判断；`instanceof` 更适合判断自定义类实例或具有明确构造关系的对象。

#### 辅助理解的代码

```js
function myInstanceof(value, Ctor) {
  if (value === null ||
      (typeof value !== 'object' && typeof value !== 'function')) {
    return false
  }

  if (typeof Ctor !== 'function') {
    throw new TypeError('右侧必须是可用于类型判断的函数')
  }

  const target = Ctor.prototype
  if (target === null ||
      (typeof target !== 'object' && typeof target !== 'function')) {
    throw new TypeError('构造函数 prototype 必须是对象')
  }

  let current = Object.getPrototypeOf(value)

  while (current !== null) {
    if (current === target) return true
    current = Object.getPrototypeOf(current)
  }

  return false
}

class Animal {}
class Dog extends Animal {}

const dog = new Dog()

console.log(myInstanceof(dog, Dog)) // true
console.log(myInstanceof(dog, Animal)) // true
console.log(myInstanceof(dog, Array)) // false
```

### 【OOP-014：JavaScript 有哪些常见的对象创建方式和创建模式？】

#### 回答大纲

2. 再列为解决复用问题形成的设计模式。
3. 说明现代业务代码通常如何选择。

#### 面试回答

如果只问 JavaScript 怎样创建对象，可以先从语言提供的方式回答，再补充经典的对象创建模式。

最直接的是对象字面量，适合创建结构简单、数量不多的对象。`Object.create(proto)` 可以创建一个新对象，并明确指定它的原型，适合需要直接控制对象关联关系的场景。构造函数配合 `new` 可以批量创建同一类型的实例，并通过构造函数的 `prototype` 共享方法。ES6 以后还可以使用 `class` 配合 `new`，写法更集中，但底层仍然使用实例、构造函数和原型之间的关系。

如果讨论经典创建模式，通常会提到工厂模式、构造函数模式、原型模式、组合模式和动态原型模式。它们不是五套互不相关的语法，而是在逐步解决对象创建中的实际问题。

工厂模式把创建过程放进普通函数，调用方便，但返回的通常只是普通对象，不容易表达具体业务类型。构造函数模式通过 `new` 建立实例和构造函数原型的关系，可以使用 `instanceof` 判断类型，但如果把方法也写成 `this.fn = function () {}`，每个实例都会重复创建函数。原型模式把方法放到 `prototype` 上实现共享，却不适合把每个实例都应该独立的可变数据放在原型上。组合模式因此把实例数据放在构造函数中，把共享方法放在原型上。动态原型模式只是在这个基础上，把一次性的原型初始化也封装进构造函数。

在现代业务代码中，单个配置对象通常直接使用对象字面量，需要一组同类实例时通常使用 `class`。学习这些经典模式的价值，主要是理解为什么实例字段应该独立初始化、为什么普通方法适合放在原型上，以及 `class` 帮我们自动完成了哪些工作。

#### 辅助理解的代码

```js
const a = { name: 'A' }
const b = Object.create(a)

function Person(name) {
  this.name = name
}
const c = new Person('C')

class User {
  constructor(name) {
    this.name = name
  }
}
const d = new User('D')
```

### 【OOP-015：工厂模式如何创建对象？优缺点是什么？】

#### 回答大纲

1. 普通函数封装对象创建。
2. 优点是隐藏创建细节。
3. 缺点是业务类型不明确，内联方法通常重复创建。

#### 面试回答

工厂模式使用一个普通函数封装对象的创建和初始化过程，调用方传入需要的数据，函数在内部创建对象、添加属性和方法，最后把对象返回。

比如业务需要反复创建用户对象，可以提供 `createPerson(name)`。调用方只传姓名，不需要知道内部使用对象字面量还是其他方式创建，也不需要重复编写属性和方法。这是工厂模式最明显的优点：创建逻辑集中，调用简单，内部实现可以独立调整。

它的第一个典型缺点是类型信息不够明确。如果工厂直接返回 `{}` 创建的普通对象，这些对象的内部原型通常都是 `Object.prototype`。`createPerson` 只是负责生产对象的普通函数，并不是这些对象原型链上的构造函数，因此 `person instanceof createPerson` 不成立。不同工厂如果都返回相似的普通对象，仅靠原型链也不容易区分它们属于哪一种业务类型。

第二个缺点取决于方法如何定义。如果每次调用工厂时，都在返回对象中重新写一个 `sayName()` 函数，那么每个对象会持有不同的函数实例。对象数量很多时，这会带来不必要的重复。可以把共享函数提前定义到外部，再让返回对象引用它，但这需要开发者自己组织，工厂模式不会自动提供像构造函数原型那样的共享机制。

所以面试里可以说：工厂模式适合封装创建细节，尤其适合不强调类和实例关系的对象生产；它的不足是缺少天然的业务类型标识，并且如果方法在工厂内部重复创建，就无法自动实现方法共享。

#### 辅助理解的代码

```js
function createPerson(name) {
  return {
    name,
    sayName() {
      console.log(this.name)
    }
  }
}

const alice = createPerson('Alice')
const bob = createPerson('Bob')

console.log(alice.sayName === bob.sayName) // false
console.log(alice instanceof createPerson) // false
console.log(Object.getPrototypeOf(alice) === Object.prototype) // true
```

### 【OOP-016：构造函数模式和原型模式各解决了什么问题？】

#### 回答大纲

1. 构造函数模式保留类型信息和独立实例属性。
2. 构造函数内定义方法会重复创建。
3. 原型模式共享方法，但共享可变数据容易出问题。

#### 面试回答

构造函数模式主要解决了工厂模式中对象类型关系不明确的问题。使用 `new Person()` 时，新实例的内部原型会指向 `Person.prototype`，因此可以通过 `instanceof Person` 判断它属于这个原型体系。构造函数还能通过 `this` 给当前实例初始化字段，每次构造都执行一次，所以姓名、数组等实例状态可以彼此独立。

但如果把方法也写在构造函数中，比如每次执行都做 `this.sayName = function () {}`，这个函数也会成为实例自己的属性。创建 Alice 和 Bob 两个对象时，会生成两个内容相同但引用不同的函数。行为完全一致，却不能共享，实例数量多时会产生不必要的重复。

原型模式就是为了解决方法共享问题。把 `sayName` 定义在 `Person.prototype` 上以后，所有 `Person` 实例都可以通过原型链访问同一个函数。这样方法只定义一次，同时执行时的 `this` 仍然由具体调用它的实例决定，因此同一个方法可以读取不同实例的姓名。

原型模式也有边界。如果把数组或普通对象这样的可变数据放到原型上，所有实例读取到的会是同一个引用。Alice 对原型数组执行 `push()` 后，Bob 再读取时也会看到变化。因此原型适合存放真正需要共享的行为或常量，不适合存放每个实例应该独立维护的可变状态。

完整的面试回答可以落在这个取舍上：构造函数适合初始化实例自身状态，原型适合共享方法；只使用其中一种都会有局限，把两者结合起来才是更常见的组织方式。

#### 辅助理解的代码

```js
function Person(name) {
  this.name = name
  this.sayName = function () {
    console.log(this.name)
  }
}

const alice = new Person('Alice')
const bob = new Person('Bob')

console.log(alice instanceof Person) // true
console.log(alice.sayName === bob.sayName) // false
```

```js
function Person(name) {
  this.name = name
}

Person.prototype.sayName = function () {
  console.log(this.name)
}

const alice = new Person('Alice')
const bob = new Person('Bob')

console.log(alice.sayName === bob.sayName) // true
```

```js
Person.prototype.tags = []

alice.tags.push('admin')
console.log(bob.tags) // ['admin']
```

### 【OOP-017：组合模式和动态原型模式是什么？】

#### 回答大纲

1. 组合模式：实例数据放构造函数，方法放原型。
2. 动态原型模式：在构造函数内部完成一次性原型初始化。
3. 提醒不要反复整体替换原型。

#### 面试回答

组合模式把构造函数模式和原型模式各自适合的部分放在一起：每个实例都应独立拥有的数据，在构造函数中通过 `this` 初始化；所有实例都可以复用的行为，定义在构造函数的 `prototype` 上。

比如每个人的姓名和标签列表都应该独立，因此构造 `Person` 时为当前实例写入 `name`，并新建一个 `tags` 数组。`sayName()` 的实现对所有人都相同，就只放在 `Person.prototype` 上。这样修改 Alice 的标签不会影响 Bob，而 Alice 和 Bob 调用的又是同一个 `sayName` 函数。

组合模式同时解决了类型识别、实例状态独立和方法共享三个问题，是理解传统 JavaScript 对象创建方式时最重要的模式。现代 `class` 中，实例字段在构造时初始化，类体普通方法放在原型上，本质上也体现了类似的职责分配。

动态原型模式并没有改变这个分配原则。它只是希望把构造逻辑和原型初始化逻辑都写在同一个函数附近，所以会在构造函数第一次执行时检查原型方法是否已经存在；如果不存在才添加，后续创建实例就不再重复定义。

这种写法有一个重要限制：应该在原来的 `Person.prototype` 对象上增加方法，而不是每次执行构造函数都把整个 `Person.prototype` 替换成新对象。整体替换后，已经创建的旧实例仍然连接旧原型，新实例连接新原型，会出现实例行为不一致；默认的 `constructor` 关联也可能丢失。

#### 辅助理解的代码

```js
function Person(name) {
  this.name = name
  this.tags = []
}

Person.prototype.sayName = function () {
  console.log(this.name)
}
```

```js
function Person(name) {
  this.name = name

  if (typeof Person.prototype.sayName !== 'function') {
    Person.prototype.sayName = function () {
      console.log(this.name)
    }
  }
}

const alice = new Person('Alice')
const bob = new Person('Bob')

console.log(alice.sayName === bob.sayName) // true
```

## 四、继承模式与数据共享

### 【OOP-018：JavaScript 常见的继承方式有哪些？】

#### 回答大纲

1. 列出经典的六种原型继承方案。
2. 说明它们是在逐步解决属性独立和方法复用问题。
3. 把现代 `class extends` 单独说明。

#### 面试回答

JavaScript 经典的继承方式通常包括原型链继承、借用构造函数继承、组合继承、原型式继承、寄生式继承和寄生组合式继承。现代代码还会使用 `class extends` 来表达继承。

这些名称看起来很多，但它们主要在解决两个问题：父类构造时创建的实例字段怎样让每个子类实例独立，以及父类原型上的方法怎样让所有子类实例复用。

原型链继承让子类原型指向父类实例，子类实例因此能沿原型链访问父类方法；问题是父类实例上的数组、对象等可变数据也会落在共享原型上。借用构造函数继承在子类构造函数中执行 `Parent.call(this)`，可以为每个子类实例单独初始化字段，却没有建立子类原型到父类原型的关系，因此复用不到父类原型方法。

组合继承同时使用这两种方式：调用父类构造函数初始化独立字段，再连接原型复用方法。经典组合继承使用 `new Parent()` 创建子类原型，导致父类构造函数执行两次。寄生组合式继承改用 `Object.create(Parent.prototype)`，直接连接原型，不再为了建立原型关系额外执行父类构造函数。

原型式继承不强调构造函数，而是使用 `Object.create(existingObject)` 创建以现有对象为原型的新对象。寄生式继承则在这个基础上，用工厂函数为新对象增加额外能力。不过，如果增强方法每次都在工厂内部创建，仍然会有函数不能共享的问题。

现代 `class extends` 仍然建立在原型机制上，但它自动连接实例方法链和静态成员链，并通过 `super()` 规定父类实例字段怎样初始化。它并不是某一段 ES5 寄生组合继承代码在所有语义上的完全替换，因为类还有必须通过 `new` 调用、方法默认不可枚举、类体默认严格模式等额外规则。

面试中不需要只背六个名称。更有价值的回答方式是沿着“共享方法”和“独立字段”这条主线，说明后一种方案具体修复了前一种方案的什么缺点。

#### 辅助理解的脉络

```text
父类实例字段怎样让每个子类实例独立？
父类原型方法怎样让所有子类实例复用？
```

### 【OOP-019：原型链继承的原理和缺点是什么？】

#### 回答大纲

1. 子类原型指向父类实例。
2. 子类实例借助原型链访问父类能力。
3. 分析共享引用属性和传参限制。

#### 面试回答

原型链继承的经典做法是把子类的 `prototype` 设置成父类实例。这样创建子类实例以后，它的原型链会先到子类原型，而这个子类原型本身就是一个父类实例；再向上还能到父类的 `prototype`。因此，子类实例既能读取父类构造函数写入那个父类实例的字段，也能继续访问父类原型上的方法。

例如父类构造函数创建一个 `tags` 数组，父类原型提供 `sayHi()`。执行 `Child.prototype = new Parent()` 后，`tags` 会存在于这个唯一的父类实例，也就是新的 `Child.prototype` 上；`sayHi()` 则继续位于 `Parent.prototype` 上。所有子类实例都沿同一条原型链访问它们。

这也带来原型链继承最典型的问题：共享的引用类型属性。如果子类实例自身没有 `tags`，多个实例读到的是原型上的同一个数组。一个实例对数组执行 `push()` 是原地修改这个共享数组，其他实例随后也会看到新增内容。这里不是继承时给每个实例复制了数组，而是所有实例都查找到同一个引用。

第二个问题是父类参数无法按子类实例灵活传入。父类构造函数是在建立 `Child.prototype` 时执行的，只执行一次；以后创建每个 `Child` 时不会自动再次以当前参数调用父类。第三个问题是建立原型关系本身就执行了父类构造逻辑。如果后续为了初始化每个实例又在 `Child` 里调用 `Parent.call(this)`，父类构造函数总共会在不同阶段执行两次。

另外，整体替换 `Child.prototype` 后，新的原型对象默认继承自 `Parent` 实例，它的 `constructor` 不再自然指回 `Child`。如果代码依赖这层关联，需要把 `constructor` 恢复为 `Child`，并尽量保持它不可枚举。

所以这套方式优点是实现直观、能复用父类原型方法；缺点是共享父类实例中的可变数据、不能针对每个子类实例灵活传参，并且容易引出父类构造函数重复执行的问题。

#### 辅助理解的代码

```js
function Parent() {
  this.tags = ['base']
}

Parent.prototype.sayHi = function () {
  console.log('hi')
}

function Child() {}

Child.prototype = new Parent()
Object.defineProperty(Child.prototype, 'constructor', {
  value: Child,
  writable: true,
  configurable: true
})

const a = new Child()
const b = new Child()

a.sayHi() // hi
a.tags.push('a')
console.log(b.tags) // ['base', 'a']
```

### 【OOP-020：借用构造函数继承的原理和缺点是什么？】

#### 回答大纲

1. 用 `Parent.call(this)` 初始化父类实例字段。
2. 每个子类实例得到独立数据。
3. 没有连接父子原型，无法继承父类原型方法。

#### 面试回答

借用构造函数继承也叫经典继承。它不先处理父子原型之间的关系，而是在子类构造函数中通过 `Parent.call(this, ...)` 或 `Parent.apply(this, args)` 执行父类构造函数，并把当前子类实例作为父类构造过程中的 `this`。

这样一来，父类构造函数原本要写到父类实例上的字段，会直接写到当前子类实例上。每创建一个子类实例，父类构造函数都会重新执行一次。如果父类内部做 `this.tags = []`，每次执行都会创建新数组，所以不同子类实例的数组互不影响。父类需要姓名等初始化参数时，子类也可以在 `call` 中把当前参数传过去。

它解决了原型链继承中“父类实例字段被放到共享原型上”的问题，但没有建立 `Child.prototype` 到 `Parent.prototype` 的连接。因此，父类原型上的 `sayName()` 不会出现在子类实例的查找链上，子类实例也不会通过 `instanceof Parent`。这说明借用构造函数主要完成的是父类实例初始化逻辑的复用，而不是完整的原型继承。

如果为了让子类拿到方法，把方法也定义在父类构造函数中，那么每次调用 `Parent.call(this)` 都会为当前实例重新创建函数。虽然能够调用，但无法共享，失去了原型复用方法的优势。

所以它的优点是实例字段独立、可以向父类传参；缺点是不能继承父类原型方法，也不能建立完整的父子实例关系。实际使用时，通常会把它和原型链连接结合成组合继承。

#### 辅助理解的代码

```js
function Parent(name) {
  this.name = name
  this.tags = []
}

Parent.prototype.sayName = function () {
  console.log(this.name)
}

function Child(name, age) {
  Parent.call(this, name)
  this.age = age
}

const a = new Child('Alice', 18)
const b = new Child('Bob', 20)

a.tags.push('admin')
console.log(b.tags) // []
console.log(a.sayName) // undefined
console.log(a instanceof Parent) // false
```

### 【OOP-021：组合继承与寄生组合式继承有什么区别？】

#### 回答大纲

1. 组合继承同时使用构造函数初始化和原型链。
2. 经典写法会执行两次父类构造函数。
3. 寄生组合式继承用 `Object.create()` 直接连接原型。

#### 面试回答

组合继承把借用构造函数和原型链继承放在一起使用。创建每个子类实例时，通过 `Parent.call(this, ...)` 执行父类构造函数，让姓名、数组等父类实例字段直接初始化到当前子类实例上；在构造函数之外，再把 `Child.prototype` 连接到父类原型体系，让子类实例能够共享 `Parent.prototype` 上的方法。

它的优点比较完整：父类构造函数能接收每个子类实例自己的参数；数组、对象等实例字段彼此独立；父类原型方法只保留一份；`child instanceof Parent` 也能成立。

经典组合继承的问题出在连接原型的写法。它使用 `Child.prototype = new Parent()`，为了得到一个能连接 `Parent.prototype` 的对象，额外执行了一次父类构造函数。以后真正执行 `new Child()` 时，`Child` 内部又会调用一次 `Parent.call(this)`。因此父类构造逻辑在建立继承关系和创建实例两个阶段被执行了两次，`Child.prototype` 上还会留下没有实际用途的父类实例字段。

寄生组合式继承保留“构造函数初始化独立字段”这部分，但不再通过 `new Parent()` 建立原型关系。它使用 `Object.create(Parent.prototype)` 创建一个以父类原型为原型的新对象，再把它赋给 `Child.prototype`，并恢复正确的 `constructor`。这样只建立对象之间的链接，不会执行父类构造函数。

如果还希望 ES5 风格的子类构造函数能够继承父类的静态成员，可以额外执行 `Object.setPrototypeOf(Child, Parent)`，建立构造函数对象之间的原型链。这对应现代 `extends` 自动建立的第二条链。

因此两者的核心区别不在于是否都能实现属性独立和方法共享，而在于建立子类原型时是否多执行了一次父类构造函数。寄生组合式继承避免了这次无意义的构造，是更完善的传统实现。

#### 辅助理解的代码：经典组合继承

```js
function Parent(name) {
  this.name = name
  this.tags = []
}

Parent.prototype.sayName = function () {
  console.log(this.name)
}

function Child(name, age) {
  Parent.call(this, name) // 第二次调用 Parent
  this.age = age
}

Child.prototype = new Parent() // 第一次调用 Parent
Child.prototype.constructor = Child
```

#### 辅助理解的代码：寄生组合式继承

```js
function Parent(name) {
  this.name = name
  this.tags = []
}

Parent.prototype.sayName = function () {
  console.log(this.name)
}

function Child(name, age) {
  Parent.call(this, name)
  this.age = age
}

Child.prototype = Object.create(
  Parent.prototype,
  {
    constructor: {
      value: Child,
      writable: true,
      configurable: true
    }
  }
)

// 如果还要继承静态成员，再连接构造函数链
Object.setPrototypeOf(Child, Parent)

const child = new Child('Alice', 18)
child.sayName() // Alice
console.log(child instanceof Parent) // true
console.log(child instanceof Child) // true
```

### 【OOP-022：给实例属性赋值会修改原型吗？引用类型什么时候会被实例共享？】

#### 回答大纲

1. 区分属性读取和属性写入。
2. 说明属性遮蔽。
3. 共享与否取决于引用值创建和存放的位置。

#### 面试回答

这道题需要把“读取属性”“给属性重新赋值”和“修改引用对象内部内容”分开。

读取属性时，如果实例自身没有，引擎会沿原型链向上查找。对于常见的可写数据属性，如果随后执行 `child.level = 2`，引擎不会继续沿原型链找到 `parent.level` 并把它改成 2，而是会在 `child` 自身创建一个同名属性。之后再读取 `child.level` 时，自身属性会先被找到，原型上的值被遮住，这叫属性遮蔽。

基本类型的场景比较直观。原型上的 `level` 是 1，实例给自己的 `level` 赋值 2 后，父对象仍然是 1。只有直接拿到原型对象并执行 `parent.level = 3`，才是在修改原型本身，所有没有自有 `level`、仍然依赖原型值的实例才会看到变化。

引用类型要继续区分“属性赋值”和“原地修改”。如果数组放在原型上，多个实例读取到的是同一个数组引用。一个实例执行 `tags.push('x')` 时，并没有给实例的 `tags` 属性重新赋值，而是在修改那个共享数组的内部内容，所以其他实例也会看到变化。如果执行 `instance.tags = ['x']`，则是在实例自身创建新属性，后续这个实例使用自己的数组，不再读取原型数组。

在构造函数中写 `this.tags = []` 时，每次执行构造函数都会求值一次数组字面量，产生新的数组，再写到当前实例自身，因此不同实例通常互不影响。但不能笼统地说“构造函数会自动深拷贝引用类型”。如果构造函数把同一个外部数组赋给所有实例，或者调用方每次都传入同一个对象，实例仍然会共享这个引用。

因此，共享与否的决定因素不是“这个字段是不是引用类型”这一点，而是多个实例最终得到的是否是同一个引用。面试中把创建位置、赋值行为和原地修改这三件事说清楚，答案会比“引用类型都会共享”准确得多。

还可以补充一个边界：如果原型链上是 setter，给实例赋值可能会触发这个 setter；如果继承的是不可写数据属性，严格模式下赋值还可能报错。所以“赋值一定在实例上创建同名属性”是针对常见可写数据属性的简化说法。

#### 辅助理解的代码：属性遮蔽

```js
const parent = { level: 1 }
const child = Object.create(parent)

child.level = 2

console.log(child.level) // 2
console.log(parent.level) // 1
console.log(Object.hasOwn(child, 'level')) // true
```

#### 辅助理解的代码：原型上的数组

```js
function A() {}
A.prototype.tags = []

const a1 = new A()
const a2 = new A()

a1.tags.push('x')
console.log(a2.tags) // ['x']
```

#### 辅助理解的代码：构造时创建新数组

```js
function B() {
  this.tags = []
}

const b1 = new B()
const b2 = new B()

b1.tags.push('x')
console.log(b2.tags) // []
```

#### 辅助理解的代码：显式共享外部数组

```js
const shared = []

function C() {
  this.tags = shared
}

const c1 = new C()
const c2 = new C()

c1.tags.push('x')
console.log(c2.tags) // ['x']
```

## 五、`class` 语法与继承

### 【OOP-023：`class` 的本质是什么？各类成员在底层如何组织？】

#### 回答大纲

1. `class` 建立在构造函数和原型机制上。
2. 实例方法、实例字段、静态成员位置不同。
3. 补充 `class` 不只是换一个写法，还有更严格语义。

#### 面试回答

`class` 可以理解为 JavaScript 对构造函数、原型对象和继承关系的一层结构化语法。它让开发者可以在一个类体中集中声明构造逻辑、实例方法、静态成员、私有字段和继承关系，但实例方法共享、属性查找和方法继承仍然依赖原型机制。

定义一个类以后，类名对应的是一个可构造的函数对象，因此 `typeof Person` 的结果仍然是 `"function"`。这个类对象会有自己的 `prototype`，通过 `new Person()` 创建的实例，其内部原型会指向 `Person.prototype`。

类中的 `constructor` 用于初始化实例。执行 `new` 时，`constructor` 中的 `this.name = name` 会把 `name` 写到当前实例自身。直接写在类体中的实例字段，例如 `kind = 'human'`，也会在每次实例化时初始化到当前实例上，而不是放到原型上。因此如果实例字段的初始值是一个新数组，每个实例都会得到不同数组。

没有 `static` 的普通方法会被定义在 `Person.prototype` 上，所有实例通过原型链访问同一个函数。getter 和 setter 访问器也会定义在原型对象上。使用 `static` 声明的字段和方法则直接定义在 `Person` 这个类对象自身，只能通过类名访问，普通实例不会沿自己的原型链找到它们。

举例来说，人的姓名属于每一个具体对象，应该在构造时写到实例自身；`sayName()` 的实现对所有人相同，适合放在原型上共享；已经创建了多少个人属于整个类的统计信息，适合放成静态字段。

`class` 虽然经常被称为“语法糖”，但不能因此认为它和随便写一个构造函数在所有细节上完全一样。类必须通过 `new` 调用，直接执行 `Person()` 会报错；类体默认运行在严格模式；类方法默认不可枚举；类声明在完成初始化前也不能访问。这些是 `class` 自己提供的更严格语义。

所以比较完整的回答是：`class` 没有替换 JavaScript 的原型模型，而是自动完成了构造函数创建、原型方法定义、静态成员定义和继承链搭建，并用更明确、更严格的语法约束这些操作。

#### 辅助理解的代码

```js
class Person {
  kind = 'human'
  static count = 0

  constructor(name) {
    this.name = name
    Person.count += 1
  }

  sayName() {
    console.log(this.name)
  }

  static getCount() {
    return Person.count
  }
}
```

```js
function PersonLike(name) {
  this.kind = 'human'
  this.name = name
  PersonLike.count += 1
}

Object.defineProperty(PersonLike.prototype, 'sayName', {
  value: function () {
    console.log(this.name)
  },
  writable: true,
  configurable: true,
  enumerable: false
})

PersonLike.count = 0
PersonLike.getCount = function () {
  return PersonLike.count
}
```

### 【OOP-024：没有显式写 `constructor` 时，`class` 会生成什么默认构造器？】

#### 回答大纲

1. 普通类得到空的默认构造器。
2. 派生类得到转发全部参数的默认构造器。
3. 说明 `...args` 就是 `new` 时传入的全部实参。

#### 面试回答

没有显式声明 `constructor` 时，JavaScript 会为类提供默认构造器，但普通基类和派生类的默认行为不同。

一个没有继承其他类的普通类，可以近似理解为自动得到 `constructor() {}`。实例仍然可以通过 `new` 创建，只是默认构造器没有执行额外的实例字段初始化逻辑。类体中直接声明的实例字段仍会按自己的规则初始化，不依赖开发者必须手写一个空 `constructor`。

一个通过 `extends` 继承父类的派生类，如果没有显式构造器，可以近似理解为自动得到 `constructor(...args) { super(...args) }`。这里的 `...args` 就是执行 `new Child(...)` 时传给子类的全部实参，默认构造器会原样把它们转发给父类。父类构造函数因此可以继续使用这些参数初始化姓名、年龄等实例字段。

比如 `Student extends Person`，但 `Student` 没有写自己的构造器。执行 `new Student('Alice', 18)` 时，默认派生构造器会把 `'Alice'` 和 `18` 都交给 `Person` 的构造器，最终得到带有姓名和年龄的学生实例。

如果派生类显式声明了构造器，情况就由开发者自己负责。派生构造器在读取或修改当前实例的 `this` 之前，必须先执行 `super(...)`，因为这个 `this` 需要由父类构造过程完成初始化。通常会先用 `super` 初始化父类负责的字段，再添加子类自己的字段。

严格来说，派生构造器也可以在不调用 `super()` 的情况下直接返回另一个对象，但日常类继承并不依赖这种特殊写法。面试回答聚焦“派生类使用 `this` 前必须先调用 `super()`”即可。

#### 辅助理解的代码：默认构造器

```js
class Base {
  // 等价理解：constructor() {}
}
```

派生类没有显式 `constructor` 时，会自动把收到的全部参数转交给父类：

```js
class Child extends Base {
  // 等价理解：
  // constructor(...args) {
  //   super(...args)
  // }
}
```

#### 辅助理解的代码：参数转发

```js
class Person {
  constructor(name, age) {
    this.name = name
    this.age = age
  }
}

class Student extends Person {}

const student = new Student('Alice', 18)
console.log(student.name, student.age) // Alice 18
```

### 【OOP-025：`extends`、`super` 和两条继承链分别做什么？】

#### 回答大纲

1. 实例方法链：`Child.prototype → Parent.prototype`。
2. 静态成员链：`Child → Parent`。
3. `super()` 初始化父类实例字段，`super.method()` 调用父级方法。

#### 面试回答

`class Child extends Parent` 不只连接了一条实例原型链，它会同时建立实例成员继承链和静态成员继承链；`super` 则负责在不同位置访问父级构造逻辑或父级方法。

第一条链是实例方法继承链。`Child.prototype` 的内部原型指向 `Parent.prototype`。创建 `child` 实例后，属性查找会先经过 `Child.prototype`，再到 `Parent.prototype`。因此，子类实例不仅能调用子类自己的原型方法，还能访问父类原型上的实例方法。如果子类定义了同名方法，查找会先命中子类版本，这就是方法重写。

举例来说，父类定义 `sayName()`，子类没有重写时，学生实例会沿原型链直接调用父类方法；子类重写以后，调用会先进入子类方法。子类方法内部如果还想复用父类实现，可以使用 `super.sayName()`，它会从父类原型开始查找，而不是再次调用当前子类方法。

第二条链是类或构造函数对象之间的继承链。`Child` 自身的内部原型指向 `Parent`。父类的静态字段和静态方法直接定义在 `Parent` 上，不在 `Parent.prototype` 上；当读取 `Child.category` 时，如果子类自身没有这个静态字段，引擎会沿构造函数链到 `Parent` 上查找。因此子类可以继承父类静态成员，普通实例却访问不到这些成员。

在派生类构造器里，`super(name)` 会调用父类构造逻辑，并完成当前实例 `this` 的初始化。父类构造函数中对 `this.name` 的赋值，最终写到正在创建的子类实例上。执行完 `super()` 后，子类再继续初始化自己的 `age`。所以类继承不只是原型方法查找，还包含父类构造逻辑对当前子类实例的初始化。

`super` 在不同位置含义也不同。派生构造器中的 `super(...)` 调用父类构造器；实例方法中的 `super.method()` 从父类原型开始找方法；静态方法中的 `super.method()` 则从父类构造函数对象开始找静态方法。

还要说明静态属性的遮蔽行为。父类静态字段直接在 `Parent` 自身，`Child` 最初只是通过构造函数链读到它。如果后来给 `Child.category` 赋一个新值，通常会在 `Child` 自身创建同名静态属性，之后读取子类值时先命中子类，父类原来的值不变。

因此，`extends` 的完整作用可以概括为：建立 `Child.prototype → Parent.prototype` 的实例方法链，建立 `Child → Parent` 的静态成员链；`super()` 再负责让父类构造逻辑初始化当前子类实例。

#### 辅助理解的原型链

```text
child
  → Child.prototype
  → Parent.prototype
  → Object.prototype
  → null
```

```text
Child
  → Parent
  → Function.prototype
  → Object.prototype
  → null
```

#### 辅助理解的代码

```js
class Parent {
  constructor(name) {
    this.name = name
  }

  sayName() {
    console.log(this.name)
  }

  static category = 'person'

  static describe() {
    console.log(this.category)
  }
}

class Child extends Parent {
  constructor(name, age) {
    super(name)
    this.age = age
  }

  sayName() {
    super.sayName()
    console.log(`age: ${this.age}`)
  }
}

console.log(
  Object.getPrototypeOf(Child.prototype) === Parent.prototype
) // true

console.log(
  Object.getPrototypeOf(Child) === Parent
) // true

console.log(Child.category) // person
Child.describe() // person
```

## 六、`this` 绑定方法

### 【OOP-026：`call`、`apply`、`bind` 的区别和底层思路是什么？】

#### 回答大纲

1. 三者都改变函数调用时的 `this`。
2. `call`、`apply` 立即执行，参数形式不同。
3. `bind` 返回新函数，还要考虑预置参数和构造调用。

#### 面试回答

`call`、`apply` 和 `bind` 都定义在 `Function.prototype` 上，因此普通函数可以通过原型链访问它们。三者都可以指定函数运行时的 `this`，但执行时机和参数传递方式不同。

`call` 会立即执行原函数。第一个参数是希望绑定的 `this`，后面的实参逐个列出。`apply` 也会立即执行，区别是待传给原函数的参数以数组或类数组形式整体提供。比如一个介绍函数需要问候语和标点，使用 `call(user, 'Hi', '!')` 时参数逐个传，使用 `apply(user, ['Hi', '!'])` 时参数放在一个数组中，最终执行效果相同。

`bind` 不会立即执行原函数，而是返回一个新的绑定函数。以后调用这个新函数时，它通常会使用绑定时提供的 `this`。`bind` 还能预先保存一部分参数，真正调用新函数时再补充剩余参数，因此常用于事件回调、方法传递和参数预置。

理解 `call` 和 `apply` 的经典教学原理时，可以利用一条普通调用规则：以 `obj.fn()` 形式调用函数时，函数内部的 `this` 会指向点号前面的 `obj`。手写时，可以把原函数临时保存为目标对象的一个唯一属性，再通过目标对象调用它；函数执行结束后删除这个临时属性，并返回执行结果。使用 `Symbol` 作为属性名可以降低覆盖对象原有属性的风险，使用 `try...finally` 可以保证函数抛错时也尽量清理临时属性。

不过，这只是帮助理解 `this` 绑定的教学模型，不等于原生方法的完整规范实现。目标对象如果不可扩展，临时挂载属性就可能失败；原生方法对严格模式函数、`null`、基本类型上下文的处理也有更细致的规则。实际业务代码应直接使用原生方法。

手写 `bind` 要多考虑两件事。第一，要把绑定阶段预置的参数和以后调用时传入的参数合并。第二，绑定函数仍可能被 `new` 调用。如果原目标函数本身可构造，`new bound()` 时绑定的普通上下文应该被忽略，因为这时 `this` 应指向新创建的实例；同时还要保持实例能够通过原目标函数进行原型关系判断。

因此，面试中可以先给出清晰结论：`call` 和 `apply` 都立即执行，区别是参数形式；`bind` 返回延迟执行的新函数，并支持参数预置。被追问底层时，再说明临时挂载方法的教学思路，以及手写 `bind` 必须额外处理构造调用。

#### 辅助对照

| 方法 | 是否立即执行 | 参数形式 | 返回值 |
| --- | --- | --- | --- |
| `call` | 是 | 逐个传参 | 原函数执行结果 |
| `apply` | 是 | 数组或类数组 | 原函数执行结果 |
| `bind` | 否 | 可预置部分参数 | 绑定后的新函数 |

#### 辅助理解的代码：基本用法

```js
function introduce(greeting, punctuation) {
  return `${greeting}, ${this.name}${punctuation}`
}

const user = { name: 'Alice' }

console.log(introduce.call(user, 'Hi', '!'))
console.log(introduce.apply(user, ['Hi', '!']))

const bound = introduce.bind(user, 'Hi')
console.log(bound('!'))
```

#### 辅助理解的代码：简化版 `call` 和 `apply`

```js
Function.prototype.myCall = function (context, ...args) {
  const receiver =
    context === null || context === undefined
      ? globalThis
      : Object(context)

  const key = Symbol('temporaryFunction')

  try {
    receiver[key] = this
    return receiver[key](...args)
  } finally {
    delete receiver[key]
  }
}

Function.prototype.myApply = function (context, args = []) {
  return this.myCall(context, ...args)
}
```

```text
把原函数保存为目标对象的临时属性
  → 通过目标对象调用它，使 this 指向目标对象
  → 删除临时属性并返回结果
```

#### 辅助理解的代码：简化版 `bind`

```js
Function.prototype.myBind = function (context, ...presetArgs) {
  const target = this

  function bound(...laterArgs) {
    const args = [...presetArgs, ...laterArgs]

    if (new.target) {
      return Reflect.construct(target, args, new.target)
    }

    return Reflect.apply(target, context, args)
  }

  if (target.prototype &&
      (typeof target.prototype === 'object' ||
        typeof target.prototype === 'function')) {
    bound.prototype = Object.create(
      target.prototype,
      {
        constructor: {
          value: bound,
          writable: true,
          configurable: true
        }
      }
    )
  }

  return bound
}
```
