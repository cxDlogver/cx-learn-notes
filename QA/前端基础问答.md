# 前端基础问答

## FE-001：触发重排一定会触发重绘吗？

### 问题

触发重排一定会触发重绘吗？

### 回答大纲

本题考察的是浏览器渲染流水线中 `Layout/Reflow` 和 `Paint/Repaint` 的关系，而不是只背“重排比重绘更贵”这句话。

核心判断是：如果一次布局变化最终要提交成新的视觉帧，通常会连带影响绘制和合成；但“发生了布局计算”并不等于“一定发生重绘”。例如强制同步布局、布局结果没有造成可见像素变化、或变化未进入本帧视觉提交时，都可能只发生布局计算而不发生实际重绘。

回答思路是：先区分“重排”的两种语境，再说明典型情况、例外情况、工程判断方式，最后给出面试中更严谨的表达。

### 正式回答

不一定。更严谨的说法是：触发重排后，如果布局变化导致页面上可见像素需要更新，通常会继续触发重绘和合成；但如果只是浏览器为了计算几何信息而执行布局，或者布局结果没有造成可见区域变化，就不一定发生实际重绘。

先把概念边界说清楚。重排，也就是 `Layout/Reflow`，本质是浏览器重新计算元素的几何信息，包括尺寸、位置、相互影响关系。MDN 对关键渲染路径的描述是：浏览器构建 DOM 和 CSSOM 后生成渲染树，布局阶段决定元素的位置和大小，布局完成后才把像素绘制到屏幕上 `https://developer.mozilla.org/en-US/docs/Web/Performance/Critical_rendering_path`。本地资料 `基于 Chrome 浏览器渲染原理.md` 也把流程描述为“渲染树 → 布局计算 → 绘制 → 分层与合成”。

但这里容易混淆两个层次：

| 语境 | 含义 | 是否一定重绘 |
| --- | --- | --- |
| 布局计算发生了 | 浏览器为了得到元素几何信息，重新计算布局 | 不一定 |
| 布局变化要提交到屏幕 | 元素大小、位置变化，并影响可见像素 | 通常会 |
| 只改变绘制属性 | 不影响几何信息，只改变颜色、阴影等 | 不触发布局，但会重绘 |
| 只改变合成属性 | 如合适条件下的 `transform`、`opacity` | 可跳过布局和绘制，直接合成 |

为什么说“通常会”？因为只要元素的位置、尺寸发生变化，页面上原来的像素就可能不再正确。比如一个元素高度变大，把下面的元素挤下去，那么浏览器不仅要重新计算布局，还要重新绘制受影响区域，最后再合成到屏幕。web.dev 的渲染性能文章也把像素流水线拆成 `JavaScript → Style → Layout → Paint → Composite`，并说明当改变 `width`、`height`、`left`、`top` 等布局属性时，浏览器需要重新布局，受影响区域需要重新绘制，最终再合成 `https://web.dev/articles/rendering-performance`。

例如：

```js
box.style.width = '300px'
```

如果 `box` 是可见元素，并且宽度变化影响了自身或兄弟元素的位置，那么这类操作通常会走：

```text
Style → Layout → Paint → Composite
```

这也是为什么很多资料会概括说“重排一定会引起重绘”。这句话在“可见布局变化提交到屏幕”的场景下基本成立，但它不是绝对规则。

第一个例外是：强制同步布局可能只发生布局计算，不一定立刻发生重绘。比如：

```js
box.style.width = '300px'
const width = box.offsetWidth
```

读取 `offsetWidth` 时，浏览器为了返回准确值，可能会被迫先刷新样式和布局，也就是常说的 forced reflow 或 forced layout。但如果后续还没有进入下一帧绘制，或者这个变化被后续代码覆盖，浏览器可能还没有真正把这一中间状态绘制到屏幕。

例如：

```js
box.style.width = '300px'
const width = box.offsetWidth
box.style.width = '200px'
```

中间的 `300px` 可能触发过布局计算，用于回答 `offsetWidth`，但它未必作为一个可见帧被绘制出来。浏览器实际绘制时可能只绘制最终状态。

第二个例外是：布局计算结果没有造成可见像素变化。比如你修改了某个布局相关属性，但最终计算出来的位置和尺寸没有实际变化，或者元素不可见、不在当前可绘制区域、被裁剪、被其他元素完全遮挡，那么浏览器可能没有必要重绘实际像素。MDN 也提到，渲染树只包含可见内容，`display: none` 的元素不会进入渲染树 `https://developer.mozilla.org/en-US/docs/Web/Performance/Critical_rendering_path`。所以对不可渲染元素的某些变更，不应简单套用“重排后一定重绘”。

第三个例外是现代浏览器有脏区域、分层、合成等优化。浏览器不会总是重绘整个页面，而是尽量只重绘受影响区域。MDN 在 Paint 部分也说明，初次加载通常绘制整个屏幕，之后浏览器会优化为只重绘受影响的最小区域 `https://developer.mozilla.org/en-US/docs/Web/Performance/Critical_rendering_path`。因此即使重排引发了重绘，也通常不是“整个页面全部重绘”，而是“受影响区域重绘”。

可以用一个更准确的关系来记：

```text
布局属性变化
  ↓
样式计算
  ↓
布局失效或布局计算
  ↓
如果可见几何结果改变：通常需要绘制受影响区域
  ↓
最终合成到屏幕
```

而不是简单记成：

```text
重排 = 必然全页面重绘
```

这句话太粗糙。

面试或专业表达中，推荐这样回答：

“触发重排不一定绝对触发实际重绘，要看这次布局计算是否导致可见像素变化并提交到屏幕。但在常见的可见 DOM 或盒模型变化中，重排通常会连带重绘和合成，因为元素几何位置变了，原来的像素区域需要更新。浏览器会尽量只重绘受影响区域，并可能通过分层和合成减少成本。”

从工程优化角度，重点不是纠结“百分之百是否触发”，而是避免高频触发布局。尤其要避免读写布局交错：

```js
// 不推荐：每次循环都可能读布局 + 写布局
for (const item of items) {
  item.style.width = container.offsetWidth + 'px'
}
```

更好的方式是先读后写：

```js
const width = container.offsetWidth

for (const item of items) {
  item.style.width = width + 'px'
}
```

这样可以减少浏览器被迫反复刷新布局的次数。对于动画，也优先使用 `transform`、`opacity` 这类在合适条件下可以跳过布局和绘制、直接进入合成阶段的属性。web.dev 明确指出，如果改变的属性不需要布局和绘制，浏览器可以直接跳到合成阶段，这是像素流水线中成本最低的路径之一 `https://web.dev/articles/rendering-performance`。

### 本地资料修正或完善建议

`基于 Chrome 浏览器渲染原理.md` 中“合成层是浏览器处理完重排和重绘后，将页面分割成多个层次，然后由合成器合成最终视觉输出的过程”这句话建议稍微修正。因为现代渲染流水线中，有些变化可以跳过布局和绘制，直接进入合成，例如合适条件下的 `transform`、`opacity`。更准确的写法是：“合成是浏览器将已绘制或可复用的多个图层按顺序组合成最终画面的过程；某些合成友好的属性变化可以跳过布局和绘制，但图层提升本身也有内存和合成成本。”

### 专业回答总结：

触发重排不一定绝对触发实际重绘。重排表示浏览器重新计算布局几何信息；重绘表示浏览器重新填充可见像素。只有当布局结果导致可见区域的像素需要更新，并且该变化要提交为新的视觉帧时，重排才通常会继续引发重绘和合成。

在日常前端开发中，修改可见元素的尺寸、位置、DOM 结构等布局相关内容，通常可以认为会走 `Style → Layout → Paint → Composite`，所以性能成本较高。但如果只是强制同步布局读取、布局结果没有可见变化、中间状态没有进入绘制帧，或者浏览器通过分层和脏区域优化减少了绘制范围，就不能说“一定发生实际重绘”。

因此，专业表述应是：重排通常会导致受影响区域重绘，但不是绝对必然，更不是必然全页面重绘。工程上应关注如何减少布局触发次数、避免读写布局交错、批量更新 DOM，并在动画中优先选择合成友好的属性。

## FE-002：为什么读写布局交错会导致强制同步布局和布局抖动？

### 问题

为什么读写布局交错会导致强制同步布局和布局抖动？

### 回答大纲

本题考察的是上一题“重排/重绘”之后更工程化的一层：浏览器本来会按自己的节奏批量执行样式计算和布局，但某些 JavaScript 读写顺序会打断这个节奏，迫使浏览器提前布局。

核心判断是：先写 DOM 或样式，再立刻读取几何信息，会让浏览器为了返回准确值被迫同步刷新样式和布局；如果这种模式在循环中反复出现，就会形成布局抖动。

回答思路是：先说明浏览器一帧中的正常渲染顺序，再解释什么是强制同步布局，接着分析布局抖动的形成原因，最后给出正确的读写分离写法。

### 正式回答

强制同步布局的本质是：浏览器原本想把样式计算和布局延后到合适的渲染时机统一处理，但 JavaScript 在样式变更之后立刻读取布局信息，浏览器为了返回准确的几何值，不得不马上执行样式计算和布局。Chrome 性能文档明确说明，当 DOM 状态变化导致样式失效后，如果 JavaScript 查询 `offsetWidth` 这类几何属性，就会触发强制自动重排，迫使浏览器立即布局并中断脚本执行 `https://developer.chrome.com/docs/performance/insights/forced-reflow`。

浏览器一帧中的理想顺序通常可以理解为：

```text
JavaScript
  ↓
Style 计算
  ↓
Layout 布局
  ↓
Paint 绘制
  ↓
Composite 合成
```

web.dev 的渲染性能资料也把像素流水线拆成 `JavaScript → Style → Layout → Paint → Composite`，并指出布局阶段负责计算元素在页面中的大小和位置 `https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing`。正常情况下，浏览器会尽量批量处理这些工作，而不是你每改一次样式就立刻重新布局一次。

问题出在“写后立刻读”。例如：

```js
box.classList.add('big')
console.log(box.offsetWidth)
```

第一行修改了元素样式，浏览器知道布局可能已经失效，但它本可以等 JavaScript 执行完之后再统一计算。第二行读取 `offsetWidth`，而 `offsetWidth` 返回的是元素的布局宽度，包含 CSS 宽度、padding、border 和垂直滚动条等信息 `https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/offsetWidth`。为了给你一个准确值，浏览器只能立即把前面的样式变更应用掉，并同步执行布局。

这就是强制同步布局，也常被叫作 `forced reflow` 或 `forced layout`。它的问题不只是“触发了布局”，而是“在 JavaScript 执行过程中强行插入了一次本来可以延后的布局”。这会打断浏览器的批处理节奏，让主线程在脚本执行期间额外承担样式计算和布局工作。

布局抖动是强制同步布局的更糟糕版本：不是触发一次，而是在短时间内反复触发很多次。典型代码如下：

```js
for (const item of items) {
  item.style.width = container.offsetWidth + 'px'
}
```

这段代码看起来只是把多个元素宽度设置成容器宽度，但它在循环中形成了“读 → 写 → 读 → 写”的交错模式。每次读取 `container.offsetWidth`，浏览器都可能需要确认前一次写入是否影响布局；每次写入 `item.style.width`，又会让后续布局状态变脏。web.dev 将这种快速连续执行大量强制布局的模式称为布局抖动，并建议先读取样式值，再进行样式更改 `https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing`。

可以把它理解成下面的流程：

```text
第 1 次循环：
读 offsetWidth → 写 item.style.width → 布局可能失效

第 2 次循环：
再次读 offsetWidth → 浏览器被迫刷新布局 → 再写 style → 布局再次失效

第 3 次循环：
再次读 offsetWidth → 浏览器又被迫刷新布局 → 再写 style
```

如果 `items` 有 100 个元素，就可能把一次本可批量完成的布局工作，变成多次同步布局。DOM 越大、布局关系越复杂，这种开销越明显。web.dev 也指出，布局开销与需要布局的元素数量和布局复杂度有关，DOM 越大，布局成本通常越高 `https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing`。

正确的方式是读写分离：先统一读取布局信息，再统一写入 DOM 或样式。

```js
const width = container.offsetWidth

for (const item of items) {
  item.style.width = width + 'px'
}
```

这个版本只读取一次 `offsetWidth`。浏览器即使需要刷新布局，也只需要为这一次读取付出成本；后面的多次写入可以被浏览器合并到之后的渲染流程中处理。

更通用的优化原则是：

| 写法 | 问题 | 推荐方式 |
| --- | --- | --- |
| 写样式后立刻读布局 | 可能强制同步布局 | 尽量先读后写 |
| 循环中读写交错 | 容易形成布局抖动 | 批量读，再批量写 |
| 高频修改 `width`、`height`、`top`、`left` | 容易触发布局 | 动画优先考虑 `transform`、`opacity` |
| 凭感觉判断性能 | 容易误判瓶颈 | 用 DevTools Performance 验证 |

比如下面这种写法也容易出问题：

```js
element.style.height = '200px'
const rect = element.getBoundingClientRect()
element.style.width = rect.width + 10 + 'px'
```

因为 `getBoundingClientRect()` 也需要返回元素的几何信息，所以如果前面已经写入了影响布局的样式，它同样可能迫使浏览器刷新布局。这里不是说不能使用这些 API，而是要避免在同一段同步代码里频繁交错“改布局”和“读布局”。

在真实项目里，常见的风险场景包括：

| 场景 | 容易出问题的原因 |
| --- | --- |
| 列表批量计算宽高 | 循环中反复读写布局 |
| 拖拽、缩放、滚动监听 | 高频事件里触发布局 |
| 动画中修改 `top/left/width/height` | 每帧都可能重新布局 |
| 复杂表格或瀑布流布局 | DOM 多，布局依赖复杂 |
| 读取 `offsetWidth`、`clientHeight`、`scrollTop` 后马上写样式 | 容易破坏浏览器批处理 |

工程上可以这样判断：如果你的代码会读取元素几何信息，例如 `offsetWidth`、`offsetHeight`、`clientWidth`、`scrollHeight`、`getBoundingClientRect()`，同时又在附近修改 DOM 结构或布局相关样式，就要警惕强制同步布局。如果这种读写模式出现在循环、滚动、拖拽、动画回调里，就要进一步警惕布局抖动。

优化时不要只背“少操作 DOM”。更准确的目标是：减少会让布局失效的写操作，避免写后马上读几何信息，把多次布局读取合并，把多次样式写入合并，并用 Performance 面板验证是否真的减少了 Layout 时间。Chrome DevTools 现在也提供强制重排相关分析，用于发现耗时较高的 forced reflow 场景 `https://developer.chrome.com/docs/performance/insights/forced-reflow`。

### 本地资料修正或完善建议

本地 `基于 Chrome 浏览器渲染原理.md` 已经覆盖了 DOM、CSSOM、Layout、Paint、Composite、重排和重绘，但对“强制同步布局”和“布局抖动”的工程触发方式展开不足。建议在“浏览器的重排与重绘怎么理解”后补充一个小节：说明 `offsetWidth`、`offsetHeight`、`getBoundingClientRect()` 等几何读取 API 在样式失效后可能触发 forced layout，并用“读写交错”和“批量读写分离”的代码对比作为示例。

### 专业回答总结：

读写布局交错会导致强制同步布局，是因为 JavaScript 修改 DOM 或布局相关样式后，浏览器的布局状态可能已经失效；如果此时立刻读取 `offsetWidth`、`getBoundingClientRect()` 等几何信息，浏览器为了返回准确值，只能提前执行样式计算和布局。这打断了浏览器原本可以批量处理渲染工作的节奏。

布局抖动则是强制同步布局在循环或高频事件中的放大版本。它通常表现为反复执行“读布局 → 写样式 → 再读布局 → 再写样式”，导致浏览器在短时间内多次同步布局。DOM 越大、布局关系越复杂，性能损耗越明显，最终可能造成卡顿、掉帧和交互延迟升高。

工程上应优先做到读写分离：先批量读取布局值，再批量写入 DOM 或样式；避免在循环、滚动、拖拽、动画中频繁读取和修改布局；动画尽量使用 `transform`、`opacity` 等合成友好属性；最终用 DevTools Performance 验证 Layout 是否确实减少。

## FE-003：为什么使用 `transform` 和 `opacity` 做动画，通常比使用 `top`、`left`、`width`、`height` 性能更好？

### 问题

为什么使用 `transform` 和 `opacity` 做动画，通常比使用 `top`、`left`、`width`、`height` 性能更好？

### 回答大纲

本题考察浏览器像素流水线中不同 CSS 属性对 `Layout`、`Paint` 和 `Composite` 阶段的影响。

核心判断是：`top`、`left`、`width`、`height` 通常会改变元素的几何信息，容易触发布局；`transform` 和 `opacity` 通常不改变文档布局，更容易让浏览器复用已经绘制的内容，直接在合成阶段完成视觉变化。但这不是绝对规则，也不等于“使用它们就一定由 GPU 加速”。

回答思路是：先对比不同属性影响的渲染阶段，再解释合成动画的工作方式，最后讨论图层、`will-change` 和实际性能验证。

### 正式回答

浏览器更新页面视觉效果时，通常要经过下面这条像素流水线：

```text
JavaScript / CSS
  ↓
Style：重新计算样式
  ↓
Layout：重新计算元素大小和位置
  ↓
Paint：重新绘制文本、颜色、图片、阴影等
  ↓
Composite：合成多个图层
```

不同 CSS 属性会影响流水线中的不同阶段。web.dev 将动画属性大致分成三类：会触发布局的属性、会触发绘制的属性，以及可以直接进入合成阶段的属性 `https://web.dev/articles/animations-guide`。

#### `top` 和 `left` 为什么容易触发布局

`top`、`left`、`width`、`height` 等属性会直接影响元素的几何信息。

例如：

```css
.box {
  position: absolute;
  animation: move 2s infinite;
}

@keyframes move {
  to {
    left: 500px;
  }
}
```

当 `left` 每一帧发生变化时，浏览器需要重新确认元素的位置。由于元素可能影响其他元素、溢出区域、滚动区域或父子布局关系，因此通常会进入：

```text
Style → Layout → Paint → Composite
```

如果这是一个持续 60 帧/秒的动画，就意味着浏览器可能需要在每一帧重新执行布局和绘制。布局越复杂、DOM 越大，越容易超过当前帧预算，造成掉帧或卡顿。

web.dev 的动画指南给出了类似对比：使用 `top` 和 `left` 移动元素时，DevTools 中可能看到渲染工作；而使用 `transform` 移动元素时，可以减少甚至避免这部分渲染工作 `https://web.dev/articles/animations-guide`。

#### `transform` 为什么通常更适合移动和缩放

`transform` 改变的是元素的视觉变换结果，例如：

- 平移：`translate`
- 缩放：`scale`
- 旋转：`rotate`
- 倾斜：`skew`

它通常不会改变元素在正常文档流中的布局位置。比如：

```css
.box {
  animation: move 2s infinite;
}

@keyframes move {
  to {
    transform: translateX(500px);
  }
}
```

这里元素的布局位置仍然是原来的位置，只是最终显示时被视觉变换到了其他位置。因此浏览器通常可以复用已经完成的布局和绘制结果，只更新图层在屏幕上的变换矩阵：

```text
Style → Composite
```

这条路径比：

```text
Style → Layout → Paint → Composite
```

需要做的工作更少，特别适合拖拽、滑动、旋转、缩放等高频动画。

可以这样理解：

```text
top/left：
重新计算“元素应该在哪里”
  ↓
可能影响其他元素
  ↓
重新布局和绘制

transform：
布局位置基本不变
  ↓
只改变“已经画好的图层如何显示”
  ↓
重新合成
```

#### `opacity` 为什么通常也适合动画

`opacity` 改变的是元素整体透明度，通常不影响元素的尺寸、位置和文档流关系。

```css
.fade {
  animation: fade 1s infinite alternate;
}

@keyframes fade {
  from {
    opacity: 0;
  }

  to {
    opacity: 1;
  }
}
```

如果元素已经被绘制到合适的图层中，浏览器可以在合成阶段改变这个图层的透明度，而不需要重新绘制图层中的文字、背景和图片。因此常见路径是：

```text
Style → Composite
```

这也是淡入淡出动画通常性能较好的原因。

不过，`opacity` 并不意味着完全没有绘制成本。如果元素没有合适的独立图层，或者透明度变化会影响与其他内容的混合关系，浏览器仍可能需要进行额外的绘制或合成工作。是否真的只走合成路径，要以 DevTools 的实际记录为准。

#### “只触发合成”不等于“必然 GPU 加速”

这里有一个常见误区：

> `transform` 和 `opacity` 一定使用 GPU，所以一定性能好。

这个说法不严谨。

更准确的说法是：

1. `transform` 和 `opacity` 通常不会改变布局；
2. 它们更容易复用已经绘制的内容；
3. 在满足条件时，可以主要通过合成器更新画面；
4. 合成器可能使用 GPU 或其他图形处理路径，但具体实现由浏览器决定；
5. 合成也需要内存、图层管理和栅格化成本。

因此，不能简单把“合成”直接等同于“GPU 加速”。性能优化的重点是减少每帧必须执行的工作，而不是机械地给元素加上 `translateZ(0)`。

#### 为什么图层会影响合成动画

如果一个元素需要频繁独立变化，浏览器可能会把它放到单独的合成层中。这样动画发生时，只需要移动或调整这个图层，而不必重新绘制整个页面的其他部分。

例如一个固定侧边栏正在通过 `transform` 滑入：

```css
.sidebar {
  transform: translateX(-100%);
  transition: transform 300ms ease;
}

.sidebar.open {
  transform: translateX(0);
}
```

理想情况下，侧边栏可以作为独立图层处理，动画时只改变它的合成位置，页面其他区域不需要重复绘制。

但图层不是越多越好。每个图层都可能带来：

- 额外显存或内存占用；
- 图层创建和管理成本；
- 更高的栅格化成本；
- 图层合成和混合成本；
- 透明图层重叠导致的额外计算。

所以，优化目标不是“让所有元素都成为图层”，而是只为确实需要高频独立变化的元素使用合适的合成策略。

#### `will-change` 应该如何使用

`will-change` 可以提前告诉浏览器某个元素即将发生变化：

```css
.panel {
  will-change: transform;
}
```

浏览器可能因此提前进行相关优化，例如准备独立图层。但它不应该被大范围、长期、无条件地使用。

不推荐：

```css
* {
  will-change: transform, opacity;
}
```

原因是这会让大量元素提前占用资源，可能导致内存压力和合成成本增加，反而降低性能。

更合理的方式是：

- 只给确实会持续动画的元素使用；
- 在动画即将开始时添加；
- 动画结束后移除；
- 先测量，再决定是否需要；
- 不把 `will-change` 当成默认性能开关。

web.dev 的动画指南也建议谨慎使用 `will-change`，只在确实需要时应用，并在变化结束后移除 `https://web.dev/articles/animations-guide`。

#### 一个常见对比

使用布局属性：

```css
.box {
  position: absolute;
  top: 10px;
  left: 10px;
  animation: move 3s ease infinite;
}

@keyframes move {
  50% {
    top: 300px;
    left: 500px;
  }
}
```

更推荐使用 `transform`：

```css
.box {
  position: absolute;
  top: 10px;
  left: 10px;
  animation: move 3s ease infinite;
}

@keyframes move {
  50% {
    transform: translate(490px, 290px);
  }
}
```

两者视觉上都可以移动元素，但渲染成本可能不同：

| 动画属性 | 通常影响 | 典型风险 |
| --- | --- | --- |
| `top`、`left` | Layout、Paint、Composite | 每帧重新布局，可能影响其他元素 |
| `width`、`height` | Layout、Paint、Composite | 改变几何尺寸，容易引发连锁布局 |
| `background-color` | Paint、Composite | 不布局，但每帧可能重绘 |
| `box-shadow` | Paint、Composite | 阴影绘制可能较重 |
| `transform` | 通常主要是 Composite | 图层过多或栅格化成本 |
| `opacity` | 通常主要是 Composite | 透明混合和图层重叠成本 |

#### 如何验证动画是否真的走了合成路径

不要只根据 CSS 属性名称推断性能，应该使用 Chrome DevTools 验证：

1. 打开 Performance 面板；
2. 录制动画运行过程；
3. 查看是否频繁出现 `Layout`、`Recalculate Style`、`Paint`；
4. 观察每帧耗时和是否存在掉帧；
5. 使用 Rendering 面板中的 Paint flashing 查看哪些区域反复绘制；
6. 必要时查看图层和合成相关信息。

web.dev 建议通过 DevTools 检查动画是否触发布局、是否产生绘制，以及是否出现丢帧；如果使用 `transform` 的动画仍然有明显渲染成本，就需要继续分析图层、绘制内容和其他同时运行的 JavaScript `https://web.dev/articles/animations-guide`。

### 本地资料修正提醒

本地 `基于 Chrome 浏览器渲染原理.md` 中有两处表述需要更精确：

- “`transform3d` 优化，减少 Reflow，GPU”容易让人误以为使用 `transform3d` 就一定 GPU 加速。建议改为“`transform`、`opacity` 在合适条件下可以避免布局和绘制，主要通过合成阶段更新；是否建立图层以及具体使用何种硬件路径由浏览器决定”。
- “`transform` 和 `opacity` 动画只触发合成，跳过布局和绘制”过于绝对。建议增加“通常”“在满足条件时”等限定，并强调图层过多、透明混合、滤镜和复杂绘制仍可能产生额外成本。

### 专业回答总结：

使用 `transform` 和 `opacity` 做动画通常更高效，是因为它们一般不会改变元素在文档中的几何布局。浏览器可以复用已经完成布局和绘制的内容，在合适条件下只更新图层的变换或透明度，减少每帧执行 `Layout` 和 `Paint` 的工作。

相比之下，`top`、`left`、`width`、`height` 会改变元素的尺寸或位置，容易触发布局，并可能连带影响其他元素和绘制区域。需要注意的是，`transform`、`opacity` 并不保证一定只走合成，也不等同于必然 GPU 加速；图层创建、透明混合和栅格化同样有成本，最终应通过 Chrome DevTools Performance 验证实际效果。

## FE-004：页面出现卡顿，一定是重排或重绘导致的吗？如何使用 Chrome DevTools Performance 定位真正的性能瓶颈？

### 问题

页面出现卡顿，一定是重排或重绘导致的吗？如何使用 Chrome DevTools Performance 定位真正的性能瓶颈？

### 回答大纲

本题考察的是从“现象”定位“原因”的性能分析能力。

核心判断是：卡顿不一定由重排或重绘造成。JavaScript 长任务、垃圾回收、布局抖动、绘制成本过高、合成压力、网络等待、图片解码、第三方脚本等，都可能造成用户感知到的卡顿。

回答思路是：先区分卡顿的表现和根因，再按照 Performance 面板中的时间线、主线程、帧、网络、GPU 和布局信息逐层定位，最后建立“录制、定位、验证”的排查流程。

### 正式回答

页面卡顿不一定是重排或重绘导致的。

重排和重绘只是浏览器渲染流水线中的一部分。一个页面从响应用户操作到下一帧显示，可能涉及：

```text
事件处理
  ↓
JavaScript 执行
  ↓
样式计算
  ↓
Layout
  ↓
Paint
  ↓
Composite
  ↓
下一帧显示
```

任何一个阶段耗时过长，都可能导致卡顿。除此之外，垃圾回收、图片解码、网络处理、第三方脚本和主线程排队，也可能延迟下一帧。

web.dev 将浏览器任务定义为浏览器执行的一段离散工作，包括 JavaScript、渲染、HTML/CSS 解析等。任何超过 50ms 的任务都属于长任务，长任务会阻塞主线程，使用户交互和视觉更新无法及时执行 `https://web.dev/articles/optimize-long-tasks`。

#### 常见卡顿来源

| 卡顿来源 | 典型表现 | 主要检查对象 |
| --- | --- | --- |
| JavaScript 长任务 | 点击后很久没有响应，主线程出现大段黄色区域 | `Function Call`、脚本执行时间 |
| 强制同步布局 | JS 执行中频繁出现 Layout | `offsetWidth`、`getBoundingClientRect()` 等读取 |
| 布局抖动 | 循环中反复出现读写布局 | `Layout` 次数和调用栈 |
| 绘制成本高 | 阴影、滤镜、大面积背景变化导致卡顿 | `Paint`、Paint Profiler |
| 合成压力 | 图层过多、透明层重叠、巨大图层 | `Composite Layers`、GPU、图层信息 |
| 垃圾回收 | 卡顿与内存分配或回收同步出现 | `Minor GC`、`Major GC` |
| 图片解码 | 大图加载后瞬间卡顿 | 图片请求、解码、绘制事件 |
| 第三方脚本 | 广告、埋点或外部 SDK 占用主线程 | 第三方脚本调用栈 |
| 网络或资源阻塞 | 首屏迟迟不显示 | Network、Render-blocking 请求 |

因此，只看到“页面卡了”，不能直接得出“发生了重排”这个结论。需要通过性能记录确认具体是哪个阶段占用了时间。

#### 第一步：录制正确场景

打开 Chrome DevTools 的 **Performance** 面板，然后根据问题类型选择录制方式：

- 页面加载慢：使用 `Record and reload`；
- 点击、滚动、拖拽卡顿：开始录制后执行对应操作；
- 动画卡顿：录制动画运行过程；
- 偶发卡顿：延长录制时间，尽量复现问题。

Chrome DevTools Performance 面板支持记录加载性能和运行时性能，也能显示主线程活动、网络请求、帧、布局偏移、动画、GPU、绘制和合成等信息 `https://developer.chrome.com/docs/devtools/performance/reference`。

录制时最好保持测试场景稳定：

- 使用固定浏览器窗口尺寸；
- 关闭不必要的标签页和扩展；
- 使用 CPU 节流模拟低性能设备；
- 如果问题与网络有关，使用网络节流；
- 至少复现一次完整的卡顿过程；
- 不要只看录制结束后的总时间，要定位具体卡顿时间段。

#### 第二步：先看帧和时间线

录制完成后，先不要马上查看某个函数，而是先观察顶部的时间概览和 Frames 区域。

常见判断方式：

```text
红色帧 / 丢帧
  ↓
定位对应时间段
  ↓
查看 Main、Network、GPU、Frames
  ↓
确认是谁阻塞了这一帧
```

Chrome DevTools 会把帧分成不同状态：

- 空闲帧；
- 正常按时完成的帧；
- 部分呈现的帧；
- 丢帧。

如果某一帧是红色丢帧，应向下检查这一时刻对应的主线程和渲染活动。Chrome 文档说明，Frames 区域可以展示单帧耗时，并区分正常帧、部分呈现帧和丢帧 `https://developer.chrome.com/docs/devtools/performance/reference`。

这里要注意：低 FPS 只是结果，不是根因。它只能说明浏览器没有及时生成帧，不能直接说明是布局、绘制还是 JavaScript 导致的。

#### 第三步：看 Main 轨道

Main 轨道是定位页面卡顿最重要的区域之一。

在火焰图中，横轴表示时间，纵向层级表示调用关系。上层事件通常会触发下层事件。Chrome DevTools 会把 JavaScript 活动显示为黄色，把渲染相关活动显示为紫色，并对超过 50ms 的长任务进行标记 `https://developer.chrome.com/docs/devtools/performance/reference`。

可以先按颜色粗略判断：

| Main 轨道表现 | 可能原因 |
| --- | --- |
| 黄色区域很长 | JavaScript 执行时间过长 |
| 紫色 `Layout` 很长 | 布局计算成本高 |
| 紫色 `Recalculate Style` 很多 | 样式失效频繁或选择器匹配成本高 |
| 紫色 `Paint` 很长 | 绘制区域大或视觉效果复杂 |
| `Composite Layers` 较长 | 图层合成压力较大 |
| `Minor GC`、`Major GC` 集中出现 | 内存分配或垃圾回收造成停顿 |

例如，如果火焰图显示：

```text
click
  └── Function Call 120ms
       └── processLargeList 110ms
```

那么问题主要是 JavaScript 长任务，而不是重排或重绘。

如果显示：

```text
click
  └── Function Call
       └── Layout 80ms
```

则需要进一步检查这个事件处理函数是否修改了大量 DOM，或者是否存在写样式后立刻读取几何信息的情况。

#### 第四步：判断是不是强制同步布局

如果主线程中出现 Layout，并且它嵌套在 JavaScript 函数内部，就要警惕强制同步布局。

典型代码是：

```js
for (const item of items) {
  item.style.width = container.offsetWidth + 'px'
}
```

它形成了：

```text
写样式
  ↓
读取 offsetWidth
  ↓
强制 Layout
  ↓
再次写样式
  ↓
再次读取布局
```

这就是布局抖动。Chrome 的强制重排分析会帮助定位：哪些函数在样式失效后读取几何属性，并因此迫使浏览器立即布局 `https://developer.chrome.com/docs/performance/insights/forced-reflow`。

如果定位到这类问题，可以采用读写分离：

```js
const width = container.offsetWidth

for (const item of items) {
  item.style.width = `${width}px`
}
```

如果是高频动画，则优先考虑：

```css
.box {
  transform: translateX(100px);
  opacity: 0.8;
}
```

而不是频繁修改：

```css
.box {
  left: 100px;
  width: 300px;
}
```

#### 第五步：判断是不是绘制问题

如果 `Paint` 事件时间较长，不一定说明 DOM 结构有问题，也可能是绘制内容本身太复杂。

常见绘制成本较高的效果包括：

- 大范围 `box-shadow`；
- `filter: blur()`；
- 大面积渐变；
- 频繁变化的背景图；
- 大量文本；
- 大尺寸 Canvas；
- 多个半透明图层重叠；
- 大面积区域不断重绘。

可以使用 Rendering 面板的 **Paint flashing** 来观察页面哪些区域在重绘。如果用户只是移动一个小按钮，但整个页面都在闪烁，说明重绘范围可能过大。Chrome DevTools Performance 文档提供了 Paint flashing、Layer borders、FPS 等渲染分析能力 `https://developer.chrome.com/docs/devtools/performance/reference`。

还可以在 Performance 面板中选中 `Paint` 事件，并查看 Paint Profiler，分析具体绘制操作消耗的时间。

#### 第六步：判断是不是合成问题

如果 Layout 和 Paint 都不明显，但页面仍然掉帧，可以继续检查合成和图层。

合成阶段的常见问题包括：

- 页面创建了过多独立图层；
- 单个图层尺寸非常大；
- 多个透明图层发生重叠；
- 使用了复杂滤镜；
- 过度使用 `will-change`；
- 大量元素同时使用动画；
- GPU 栅格化或图层上传成本过高。

Chrome DevTools 可以查看帧的图层信息、GPU 活动和栅格化活动。动画轨道还会标记非合成动画，并提供合成失败原因 `https://developer.chrome.com/docs/devtools/performance/reference`。

所以，即使动画使用了 `transform`，仍然可能卡顿。`transform` 只能减少布局和绘制的可能性，不能消除 JavaScript 长任务、图层内存、纹理上传或透明混合成本。

#### 第七步：区分 JavaScript 卡顿和渲染卡顿

可以用下面的判断表快速区分：

| 现象 | Main 轨道 | 更可能的根因 |
| --- | --- | --- |
| 点击后很久没有视觉反馈 | 大段黄色任务 | JavaScript 长任务 |
| 滚动时页面跳动且紫色 Layout 明显 | Layout 事件较多 | 布局计算或布局抖动 |
| 鼠标移动时整个页面持续闪烁 | Paint 区域很大 | 重绘范围过大 |
| 使用 `transform` 仍然掉帧 | Composite 或 GPU 明显 | 图层、纹理或合成压力 |
| 页面偶发停顿，伴随 GC | GC 事件明显 | 内存分配和垃圾回收 |
| 首次打开页面很慢 | Network 和加载任务明显 | 资源、脚本或渲染阻塞 |
| 交互后下一帧迟迟不出现 | 事件到下一帧之间工作很多 | INP 相关交互延迟 |

Interaction to Next Paint，简称 INP，关注用户交互后页面何时完成下一次视觉更新。Chrome DevTools 的互动轨道可以展示输入延迟、处理时间和呈现延迟，帮助判断是事件排队、JavaScript 处理，还是渲染过程耗时 `https://developer.chrome.com/docs/devtools/performance/reference`。

#### 一套实用排查流程

可以把实际排查过程固定成以下步骤：

```text
复现卡顿
  ↓
录制 Performance
  ↓
定位掉帧时间段
  ↓
查看 Main 主线程
  ↓
判断 JS / Layout / Paint / Composite / GC
  ↓
查看调用栈和触发源
  ↓
修改代码
  ↓
重新录制对比
```

不要只做一次录制。优化是否有效，应至少比较优化前后的：

- 卡顿区间；
- 长任务数量；
- 最长任务耗时；
- Layout 总耗时；
- Paint 总耗时；
- Composite 总耗时；
- 丢帧数量；
- 交互延迟；
- 页面实际体验。

#### 常见误区

**误区一：看到紫色区域就认为是重排。**

紫色区域可能包含样式计算、布局、绘制等多个渲染活动，需要选中具体事件确认。

**误区二：FPS 低就一定是渲染流水线慢。**

JavaScript 长任务会阻塞浏览器，即使 CSS 使用了合成友好的属性，也可能无法及时生成下一帧。

**误区三：使用 `transform` 就不会卡顿。**

`transform` 通常可以避免布局，但 JavaScript、图层数量、GPU 合成和绘制内容仍可能成为瓶颈。

**误区四：只优化最显眼的函数。**

应先看总时间和自用时间。Chrome DevTools 提供 Call Tree、Bottom-up 和 Event Log 三种视图，分别适合查看根活动、直接耗时和事件发生顺序 `https://developer.chrome.com/docs/devtools/performance/reference`。

**误区五：只看本地高性能电脑。**

桌面设备上不明显的问题，可能在低端移动设备上严重暴露。可以使用 CPU 和网络节流进行更接近真实用户环境的测试。

### 本地资料修正提醒

本地 `基于 Chrome 浏览器渲染原理.md` 已经提到 Performance、FPS、图层和性能分析，但当前内容容易让学习者把“卡顿”主要等同于重排、重绘或 GPU 问题。建议补充以下定位框架：

```text
卡顿
├── JavaScript 长任务
├── Style / Layout
├── Paint
├── Composite / GPU
├── GC
├── 网络与资源
└── 第三方脚本
```

另外，本地资料中“为了确保平滑滚动和动画效果，所有主线程操作必须在 16.67ms 内完成”的说法应加上设备和刷新率语境。`16.67ms` 对应约 60Hz 屏幕的一帧时间，但现代设备可能是 90Hz、120Hz 或其他刷新率；同时浏览器和系统本身也需要占用一部分时间，因此不能把 16.67ms 当作所有场景的绝对阈值。

### 专业回答总结：

页面卡顿不一定由重排或重绘造成，也可能来自 JavaScript 长任务、强制同步布局、绘制成本过高、合成和 GPU 压力、垃圾回收、图片解码、网络阻塞或第三方脚本。FPS 低只是结果，不能直接证明某个具体阶段存在问题。

使用 Chrome DevTools Performance 定位时，应先录制真实卡顿场景，再从 Frames 和时间线找到掉帧区间，接着查看 Main 轨道中的 JavaScript、Layout、Paint、Composite、GC 等事件，并结合调用栈确认触发源。修复后要重新录制，对比长任务、布局耗时、绘制耗时、丢帧和交互延迟，不能只凭代码形式判断优化是否成功。

## FE-005：`requestAnimationFrame` 的回调在事件循环中的什么时机执行？它与每一帧的渲染、`Promise` 微任务和 `setTimeout` 任务分别是什么关系？

### 问题

`requestAnimationFrame` 它的回调函数执行时机是什么时候？每一帧动画的渲染时间是在事件循环的哪一个地方？

### 回答大纲

- 本题考察浏览器事件循环与渲染更新流程如何衔接。
- 核心判断是：rAF 不是普通宏任务或微任务；浏览器在存在渲染机会时，于下一次视觉提交前的更新渲染阶段调用它。
- 回答思路是先区分任务调度与渲染更新，再定位 rAF 回调，最后说明其与实际渲染流水线的关系。

### 正式回答

`requestAnimationFrame` 的核心语义是：请求浏览器在下一次重绘之前调用回调，让 JavaScript 有机会更新这一帧要展示的状态。它通常随显示器刷新率调度，例如 60Hz、120Hz 或 144Hz，但不是保证固定间隔的定时器。

它不应简单归入宏任务或微任务。更准确地说，rAF 由浏览器在事件循环的“更新渲染”环节调度。一个实用的高层模型是：

```text
执行一个 task
  ↓
清空微任务队列
  ↓
若浏览器存在渲染机会，运行 rAF 回调
  ↓
执行必要的 Style、Layout、Paint、Composite
  ↓
提交画面
```

rAF 回调是“渲染前更新 JavaScript 状态的窗口”，不是渲染本身。回调里修改 DOM 或 CSS 后，浏览器才会根据实际变化做必要的样式计算、布局、绘制、合成和显示；浏览器内部线程细节并不由 HTML 标准承诺为固定顺序。

`Promise.then` 属于微任务：当前 task 结束后会先清空。`setTimeout(fn, 0)` 的回调属于后续 task，延迟到期只表示它具备调度资格。rAF 是否运行则取决于浏览器是否决定更新画面，因此不应死记“rAF 与 setTimeout 谁一定先执行”。浏览器通常会在后台标签页或隐藏 iframe 中暂停或显著降低 rAF 调度频率。

```ts
function animate(timestamp: number): void {
  const progress = (timestamp % 1000) / 1000;
  box.style.transform = `translateX(${progress * 300}px)`;
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

rAF 是一次性请求，继续动画必须重新注册下一帧；应使用 `timestamp` 计算进度，不能固定假设每帧都是 16.67ms。若回调内有大计算、频繁读写布局，仍会超过帧预算而掉帧。视觉动画宜优先更新 `transform`、`opacity`，并采用先读后写的批处理方式。

### 专业回答总结：

rAF 不是普通 task 或微任务，而是浏览器在合适的渲染机会中、下一次视觉提交之前执行的回调。高层顺序可理解为：task 完成、微任务清空、更新渲染并运行 rAF、再进行必要的 Style/Layout/Paint/Composite。它不是固定 60fps 定时器，也不保证每轮事件循环执行。

## FE-006：浏览器的“渲染时机”到底是什么时候？如果一个大型项目的 JavaScript 执行很久，调用栈会不会阻塞渲染和用户交互？

### 问题

浏览器在存在渲染机会时，于“更新渲染”阶段、下一次视觉提交之前执行的回调。渲染时机是什么时候？当一个大的项目 JS 执行时，调用栈中是否会存在时间过长的问题？

### 回答大纲

- 本题考察事件循环、渲染机会与主线程长任务的关系。
- 核心判断是：当前 task 和微任务完成后，浏览器才可能进入更新渲染；同步 JS 长时间占用调用栈会阻塞这一过程。
- 回答思路是解释渲染机会不是固定定时器，再说明长任务如何造成白屏、掉帧和交互延迟。

### 正式回答

渲染机会不是“每轮事件循环必然发生一次”，也不是每 16.67ms 强制中断 JavaScript。浏览器在当前 task 执行结束、调用栈清空并完成微任务检查点后，会在页面需要更新且可进行视觉刷新时进入更新渲染阶段：

```text
task 中的同步 JavaScript
  ↓
调用栈清空
  ↓
清空微任务
  ↓
存在渲染机会时：rAF → Style → Layout → Paint → Composite → 提交
```

普通同步 JavaScript 具有 run-to-completion 特性：一段 task 开始执行后，浏览器不会在任意函数中间打断它去渲染。因此大型项目的首屏解析、编译、执行、框架挂载、大列表创建、复杂状态更新、大 JSON 转换或第三方脚本，都可能让调用栈长时间不清空。超过 50ms 的连续主线程工作通常被称为长任务。

```ts
box.textContent = "加载中...";
heavyWork(); // 同步执行两秒
box.textContent = "加载完成";
```

用户可能完全看不到“加载中...”，因为第一次写入后浏览器还没有渲染机会，就被 `heavyWork()` 继续占用；最终只提交“加载完成”。长任务会导致 rAF 延迟、输入事件排队、动画掉帧、INP 变差。优化方向包括减少首屏 JS、代码分割、拆分任务、避免微任务饥饿，以及把重计算移至 Web Worker。

### 专业回答总结：

渲染发生在主线程交还控制权后的可用渲染机会中，而不是固定频率强制插入同步 JS。大型项目完全会出现调用栈过长；只要同步 JS 不结束，浏览器就无法及时处理输入、rAF 或下一帧提交，进而导致白屏、卡顿和掉帧。

## FE-007：代码分割为什么能降低主线程阻塞？如果在 JS 文件开头写静态 `import`，浏览器会不会把所有 JS 文件都加载下来？

### 问题

代码分割如何降低主线程阻塞，import 写在 js 开头，会导致浏览器加载所有 js 文件吗？

### 回答大纲

- 本题考察代码分割、静态 `import` 与动态 `import()` 的加载边界。
- 核心判断是：代码分割减少首屏必须下载、解析、编译和执行的 JS；静态导入加载入口可达的静态依赖图，而不是项目全部文件。
- 回答思路是区分静态依赖和动态依赖，再说明路由、组件和重型库的按需加载。

### 正式回答

代码分割并不让单个函数自动执行得更快，而是把非首屏代码从初始 bundle 中移出，减少启动阶段的下载、解析、编译、执行和框架初始化工作，从而降低主线程长任务风险。

```text
未分割：main.js = 首页 + 图表 + 编辑器 + 管理页 + 所有重型库
分割后：main.js + 当前路由 chunk；其他功能在访问时加载
```

静态导入：

```ts
import ChartPage from "./pages/ChartPage";
```

会让 `ChartPage` 进入当前入口的静态依赖图。它不会因为写在文件开头就加载项目中所有 JS 文件，但会沿着当前模块可静态追踪的依赖继续加载；未被该依赖图引用的文件不会自动加载。

动态导入：

```ts
const ChartPage = () => import("./pages/ChartPage");
```

只有代码实际执行到该表达式时才加载模块。Webpack、Vite 等构建工具通常会据此生成异步 chunk，适合路由懒加载、重型组件、低频弹窗和 ECharts、Monaco、地图 SDK 等大型依赖。

```ts
export const routes = [
  { path: "/", component: () => import("./pages/HomePage") },
  { path: "/chart", component: () => import("./pages/ChartPage") },
];
```

代码分割并非越碎越好：过多 chunk 会带来额外请求、依赖调度和切换 loading 成本。优先按路由、重型组件、低频功能和大型第三方库拆分；首屏关键代码保留直接加载，首屏后高概率使用的资源可预加载。

### 专业回答总结：

代码分割通过延后非必要 JS 的下载、解析、编译和执行，降低首屏主线程阻塞。静态 `import` 不会加载整个项目，但会把入口可达的静态依赖图纳入初始加载；真正按需加载应使用动态 `import()`，并结合路由和重型功能边界生成异步 chunk。

## FE-008：如果主线程阻塞导致 `requestAnimationFrame` 多个刷新周期没有执行，浏览器后续会不会把“错过的 rAF 回调”一次性补回来执行？

### 问题

rAF 如果由于阻塞导致多次回调没有执行，会在后续某一次渲染时一次性执行吗？

### 回答大纲

- 本题考察 rAF 的一次性语义、掉帧和时间补偿。
- 核心判断是：错过的刷新帧不会补执行；下一次渲染机会只执行已登记的 rAF 回调。
- 回答思路是区分“错过的帧”和“已注册的回调”，再说明动画应使用 `timestamp` 或 deltaTime。

### 正式回答

不会因为主线程阻塞错过多帧，就补偿式连续执行多次 rAF。rAF 是一次性请求，语义是“请在下一次重绘前调用我一次”；阻塞期间没有生成的帧已经丢失。

递归 rAF 不会积压，因为下一次 rAF 只有当前回调执行后才会注册：

```ts
function frame(timestamp: number): void {
  update(timestamp);
  requestAnimationFrame(frame);
}

requestAnimationFrame(frame);
```

如果主线程阻塞 300ms，期间可能错过多个刷新周期；阻塞结束后，浏览器只会在下一次渲染机会执行一次此前已登记的回调，而不会补跑约 18 次。

但是，如果阻塞前主动登记了多个回调：

```ts
requestAnimationFrame(() => console.log("A"));
requestAnimationFrame(() => console.log("B"));
requestAnimationFrame(() => console.log("C"));
```

它们可能在下一次渲染机会中同帧执行，并接收相同 `timestamp`。这只是执行已经登记的回调列表，不是补帧。

动画不应依赖“每帧固定移动多少”，而应按真实经过时间推进：

```ts
let lastTime: number | null = null;
let x = 0;
const speed = 120;

function animate(timestamp: number): void {
  if (lastTime === null) lastTime = timestamp;

  const delta = Math.min(timestamp - lastTime, 50);
  lastTime = timestamp;
  x += speed * (delta / 1000);

  box.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(animate);
}
```

限制最大 delta 可避免长时间卡顿恢复后动画突然跳得过远；是否完全追赶真实时间取决于 UI 动画、进度条、游戏物理或数据播放等具体业务。

### 专业回答总结：

rAF 不会补执行阻塞期间错过的刷新帧。后续渲染机会只会运行已经注册的回调；多个预先登记的回调可以同帧执行，但不是补帧。连续动画应以 `timestamp` 或 deltaTime 计算进度，而不是假设每次回调间隔固定。
