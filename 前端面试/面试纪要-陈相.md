### 题目：为什么在实时可视化项目里选择 WebSocket，而不是 HTTP 轮询或 SSE？

- 一句话结论：如果场景是高频实时数据、后续还可能需要客户端反向控制，WebSocket 通常比 HTTP 轮询和 SSE 更适合。
- 30秒回答：我选择 WebSocket，核心是它能建立持久连接并支持全双工通信，适合实时数据连续推送，也方便后续扩展客户端主动控制的需求。相比之下，HTTP 轮询请求开销更高，实时性也更差；SSE 更适合单向推送，但在需要双向交互和更强扩展性时不如 WebSocket。
- 1分钟展开：
  - HTTP 轮询本质上还是多次请求响应，连接建立和请求头开销重复，实时性和资源利用率都不理想。
  - SSE 基于 HTTP，服务端到客户端单向推送比较方便，但如果后续要根据地图缩放、筛选条件或区域切换反向通知服务端，就不如 WebSocket 灵活。
  - WebSocket 建立连接后可以长期保持，服务端推送和客户端回传都更自然，适合实时可视化这种持续流式场景。
  - 边界上，如果只是低频单向通知，SSE 其实也够用；但在这个项目里，我们更看重实时性、双向能力和后续扩展空间。
- 高频关键词：WebSocket、HTTP 轮询、SSE、持久连接、全双工、实时推送、扩展性
- 易追问：WebSocket 的心跳和重连怎么做；连接断开如何恢复；什么时候 SSE 更合适
- 回答雷区：只说“WebSocket 更快”但说不出为什么；把 SSE 说成双向通信；忽略场景边界

### 题目：实时数据量比较大时，前端如何兼顾 WebSocket 的实时性和渲染性能？

- 一句话结论：核心不是“来一条画一条”，而是把数据接收和视图渲染解耦，用缓冲队列、批量消费和时间窗口控制性能。
- 30秒回答：我的做法是先把 WebSocket 收到的数据放进缓冲队列，不直接触发渲染；渲染层再按固定节奏批量消费，比如结合 requestAnimationFrame 每帧绘制一批数据。再加上历史窗口长度限制和已渲染数据清理，就能在保证实时性的同时控制内存和掉帧风险。
- 1分钟展开：
  - 第一层是接收和渲染解耦，避免数据一到就立即重绘，导致高频更新把主线程打满。
  - 第二层是通过队列或缓冲区做削峰，网络抖动时先缓存，再按渲染节奏批量消费。
  - 第三层是用 requestAnimationFrame 把绘制和浏览器刷新节奏对齐，减少无效重绘。
  - 第四层是做时间窗口或最大长度限制，例如只保留最近 2 小时轨迹，已经消费的数据及时出队，防止内存持续增长。
  - 如果峰值再高，还可以继续加降采样、分层绘制或分级展示，保证用户看到的是“稳定实时”，不是“理论零延迟”。
- 高频关键词：缓冲队列、削峰填谷、requestAnimationFrame、批量消费、滑动窗口、内存控制、掉帧
- 易追问：队列长度怎么定；是否会引入延迟；峰值数据再高怎么办；如何监控内存和帧率
- 回答雷区：把实时性理解成每条消息都立刻渲染；没有队列和窗口控制；只讲前端不讲网络抖动

### 题目：requestAnimationFrame 和 setInterval 有什么区别？为什么前者更适合动画渲染？

- 一句话结论：requestAnimationFrame 是为渲染准备的同步节奏 API，setInterval 只是定时器；做动画或高频视觉更新时，前者通常更合适。
- 30秒回答：requestAnimationFrame 会在浏览器下一帧渲染前执行，能和屏幕刷新率同步，适合动画和逐帧绘制；setInterval 只是按时间把任务丢进任务队列，执行时机还会受主线程繁忙程度影响，所以更容易抖动。页面切到后台时，requestAnimationFrame 还会自动暂停或降频，更节省资源。
- 1分钟展开：
  - requestAnimationFrame 的回调时机贴近渲染前，天然适合提交样式更新、Canvas 绘制和可视化动画。
  - 它会跟随浏览器刷新率运行，减少“算了但没显示”这种无效更新。
  - setInterval 属于定时触发，不保证真正执行时机，也不关心浏览器是否正要渲染，所以容易和实际帧节奏脱节。
  - 当主线程繁忙时，setInterval 的回调会堆积，实际间隔往往不等于设定间隔；而 requestAnimationFrame 更符合视觉流畅性的目标。
  - 边界上，如果是非视觉类轮询任务，定时器依然有用；但动画、地图轨迹或图表逐帧更新更适合 requestAnimationFrame。
- 高频关键词：requestAnimationFrame、setInterval、刷新率同步、任务队列、后台暂停、动画渲染
- 易追问：setTimeout 和 setInterval 的区别；为什么 requestAnimationFrame 更省资源；后台标签页会发生什么
- 回答雷区：把 requestAnimationFrame 说成“更快的定时器”；忽略它和渲染同步的本质；不提适用场景边界

### 题目：setInterval 的 delay 设为 0 就会立刻执行吗？宏任务和微任务怎么理解？

- 一句话结论：不会立刻执行，0ms 只是“尽快入队”，真正何时运行还要等当前调用栈和微任务清空后再轮到对应宏任务。
- 30秒回答：setInterval 或 setTimeout 的 delay 设成 0，不代表 0 毫秒就执行，它只是满足最小延迟后进入宏任务队列。当前同步代码、已有微任务和前面的宏任务没处理完之前，它都不会立刻跑。微任务常见的是 Promise.then、queueMicrotask、MutationObserver；宏任务常见的是 script、setTimeout、setInterval、I/O 和 UI 事件回调。
- 1分钟展开：
  - JavaScript 先执行当前调用栈里的同步代码，同步代码不清空，后面的任务都轮不到。
  - 微任务优先级高于下一轮宏任务，所以本轮同步代码结束后，会先把微任务队列清空。
  - 定时器时间到了，也只是把回调放进宏任务队列，并不代表立刻执行。
  - 因为存在最小时间粒度、任务排队和主线程占用，所以 delay 为 0 只能理解为“尽快”，不能理解为“马上”。
  - 面试里最好把事件循环说成“同步代码 -> 微任务 -> 渲染机会 -> 下一轮宏任务”，而不是只背名词。
- 高频关键词：事件循环、setTimeout、setInterval、delay 0、宏任务、微任务、调用栈
- 易追问：Promise 为什么比定时器先执行；浏览器最小延迟限制是什么；渲染发生在事件循环的哪个阶段
- 回答雷区：说 delay 0 就是立即执行；把 Promise 归到宏任务；把 Node.js 的机制和浏览器机制混着讲

### 题目：为什么官网项目会选择 Nuxt.js 或服务端渲染方案？

- 一句话结论：官网类场景选择 SSR，核心通常不是“技术新”，而是首屏体验、SEO 能力和内容可索引性更重要。
- 30秒回答：官网项目选择 Next.js，主要是因为我们更看重首屏加载和 SEO。服务端可以直接返回可渲染的 HTML，用户首屏更快看到内容，搜索引擎也更容易抓取页面信息。对于官网这类对品牌展示和长期流量获取敏感的业务，SSR 的收益通常是明确的。
- 1分钟展开：
  - SSR 可以让服务端先把首屏 HTML 产出出来，减少纯客户端渲染“先空白再执行”的问题。
  - 对搜索引擎来说，可直接抓取到主要内容，比纯 CSR 的空壳页面更友好。
  - Next.js 本身在路由、数据获取、静态生成和部署链路上也更完整，适合官网这种内容型项目。
  - 但不是所有页面都必须 SSR，静态内容可以考虑 SSG 或 ISR，强交互区域仍然可以保留客户端渲染。
  - 真正的回答重点不是框架名字，而是你为什么为这个业务做了这个取舍。
- 高频关键词：Next.js、SSR、SEO、首屏加载、CSR、SSG、ISR、官网场景
- 易追问：SSR 的成本是什么；什么时候不建议用 SSR；SSR 如何处理数据获取和缓存
- 回答雷区：只说“Next.js 很流行”；把 SSR 说成万能优化方案；不提适用业务场景

### 题目：前端性能优化你通常会从哪些方面入手？

- 一句话结论：性能优化要按“资源、网络、渲染、运行时监控”分层处理，而不是只记几个零散技巧。
- 30秒回答：我一般会从四层看性能优化。第一层是资源体积，比如图片压缩、格式选择、代码拆包；第二层是网络请求，比如缓存、懒加载和预加载；第三层是渲染链路，比如减少重排重绘、优先用 transform 和 opacity；第四层是运行时监控，通过指标和报告持续定位问题。只有分层处理，优化才不会停留在口号上。
- 1分钟展开：
  - 资源层重点看图片格式、分辨率、JS/CSS 体积、第三方依赖和构建产物大小。
  - 网络层重点看缓存策略、CDN、预加载、懒加载、按需加载和代码拆分，减少无效请求。
  - 渲染层重点看 DOM 规模、布局抖动、长列表、动画属性选择和主线程压力，尽量减少重排重绘。
  - 交互层要关注事件监听、频繁状态更新和高频渲染，必要时做节流、批处理或虚拟化。
  - 最后一定要用数据闭环，不然“我感觉优化了”并不可靠。
- 高频关键词：图片压缩、代码拆分、缓存、懒加载、预加载、重排重绘、transform、虚拟列表
- 易追问：你做过最有效的一次优化是什么；如何判断瓶颈在网络还是渲染；如何优化长列表
- 回答雷区：只会背“懒加载、压缩、缓存”；说不出分层思路；优化没有前后对比指标

### 题目：你在项目里是怎么做前端性能检测和监控的？

- 一句话结论：性能优化要有检测闭环，先用开发工具定位，再用埋点或指标系统持续观察关键页面和关键交互。
- 30秒回答：开发阶段我会先用 Chrome DevTools、Lighthouse 和 Performance、Memory 面板定位问题；落地阶段再结合 Web Vitals 指标做监控，比如 FCP、LCP、CLS、INP 和资源加载情况。像页面访问、路由切换、关键交互这些时机，都可以触发采集，最后输出成报告或上报到平台，形成持续优化闭环。
- 1分钟展开：
  - 第一步是用开发工具看网络瀑布、主线程耗时、重排重绘和内存波动，先找到瓶颈在哪一层。
  - 第二步是明确线上要跟踪的指标，例如首屏、最大内容渲染、交互响应、布局稳定性和资源错误率。
  - 第三步是在页面进入、路由切换、关键组件加载完成后做统一采集，而不是只在首屏埋点。
  - 第四步是把数据沉淀成报表或告警，用于版本对比和回归验证。
  - 如果没有指标闭环，性能优化很容易只停留在开发阶段，无法支撑长期维护。
- 高频关键词：DevTools、Lighthouse、Performance、Memory、Web Vitals、FCP、LCP、CLS、INP
- 易追问：你如何定位首屏慢；线上和本地检测有什么区别；采集频率和上报成本怎么平衡
- 回答雷区：只说“我会用 Lighthouse”；只做本地测试不谈线上监控；只讲指标名不讲采集时机

### 题目：JWT 的工作流程是什么？为什么它适合前后端分离场景？

- 一句话结论：JWT 的核心是“服务端签发、客户端携带、服务端验签和验时效”，它适合无状态认证，但也要配合刷新和失效策略使用。
- 30秒回答：JWT 一般由 Header、Payload 和 Signature 三部分组成。用户登录成功后，服务端根据用户身份和过期时间签发 token，客户端后续请求把 token 带上，服务端再校验签名是否一致、是否过期、权限是否匹配。它适合前后端分离，因为服务端不一定需要保存完整会话状态，但如果涉及主动失效、续期和更高安全要求，通常还要配合 refresh token、黑名单或短期 token 策略。
- 1分钟展开：
  - Header 里放签名算法等元信息，Payload 放用户标识、权限和过期时间等声明，Signature 用来做完整性校验。
  - 登录后由服务端签发 token，客户端一般通过 Authorization 头携带，部分场景也会结合 Cookie 做存储。
  - 服务端收到请求后要重新计算签名并校验 exp、iat、权限等声明，不能只看 token 存不存在。
  - JWT 的优势是跨服务传递方便、服务端状态压力小、适合网关或多服务体系。
  - 但它不是万能的，注销、踢人下线和高安全场景仍然需要额外机制补足。
- 高频关键词：JWT、Header、Payload、Signature、Authorization、无状态认证、refresh token
- 易追问：JWT 和 Session 的区别；token 放 Cookie 还是 localStorage；如何做主动失效和续期
- 回答雷区：把 JWT 说成“天然绝对安全”；只会背三段结构；不提过期、续期和失效边界

### 题目：你在项目或日常开发里是怎么用 AI 提效的？

- 一句话结论：AI 提效不是把开发外包给模型，而是把它放进“需求分析、方案草拟、编码、评审、文档”这些高重复环节里提升效率。
- 30秒回答：我会把 AI 用在几个固定环节里，比如需求文档分析、页面或 UI 草稿、代码补全和重构建议、文档生成、提交说明和部分代码审查。这样能明显减少重复劳动，但对于核心架构、关键逻辑、权限安全和最终代码质量，我还是会自己做校验，不会完全依赖模型输出。
- 1分钟展开：

### 题目：Design Token 是什么？你在项目里是怎么用的？

### 题目：setTimeout(fn, 0) 和 setInterval(fn, 0) 的区别是什么？为什么 setInterval 更容易出问题？

- 一句话结论：两者都不是立即执行，但 `setTimeout` 是一次性调度，`setInterval` 是按固定周期不断尝试入队，所以后者更容易出现漂移、堆积和节奏失控。
- 30秒回答：`setTimeout(fn, 0)` 和 `setInterval(fn, 0)` 都要等当前同步任务结束后才能进入事件循环，不会立刻执行。区别是 `setTimeout` 只执行一次，而 `setInterval` 会持续按周期让回调获得入队机会，不关心主线程是否忙，所以当任务执行慢或主线程阻塞时，更容易出现执行不准和任务堆积。很多轮询场景会改用递归 `setTimeout`，因为它更可控。
- 1分钟展开：
  - 两者共同点是都属于定时器宏任务，`0ms` 表示尽快调度，不代表同步执行，也会受最小延迟限制。
  - `setTimeout` 的特点是一次性，执行完就结束，适合延迟执行、超时控制或手动递归调度。
  - `setInterval` 的特点是周期性派发任务，不会等待上一次任务完成，因此主线程繁忙时容易越积越多。
  - 如果业务要求“上一轮完成后再开启下一轮”，例如轮询、重试、异步请求，更推荐递归 `setTimeout`。
- 高频关键词：setTimeout、setInterval、宏任务、最小延迟、任务堆积、递归定时器
- 易追问：为什么 `setInterval` 会越跑越不准；轮询为什么常用递归 `setTimeout`；`delay=0` 为什么不等于立即执行
- 回答雷区：把 `0ms` 说成立刻执行；只说一个执行一次一个执行多次；忽略主线程阻塞和任务堆积问题

### 题目：setInterval 是固定间隔执行吗？如果发生堆叠，会不会短时间连续触发？

- 一句话结论：`setInterval` 是按固定周期尝试入队，不是按固定周期真正执行；主线程空闲后可能会短时间连续处理多个已到期回调，但不是并发执行。
- 30秒回答：`setInterval` 更准确地说是“固定周期给回调入队资格”，而不是固定周期立刻执行。如果主线程被同步任务卡住，多个 interval 回调可能已经到期但还没跑，等主线程空闲后，事件循环会连续把这些回调取出来执行，所以你会看到短时间内连续触发多次，但它们仍然是单线程串行执行，不是并发。
- 1分钟展开：
  - 定时器到点后，宿主环境只负责把回调放入宏任务队列，真正何时执行还要看调用栈和前面的任务是否清空。
  - 如果前一个回调很重，或者主线程被长任务阻塞，后面的 interval 仍会继续到期，导致多个回调等待执行。
  - 主线程恢复后，这些回调可能被连续处理，看起来像“扎堆触发”，但本质还是一个个执行。
  - 不同浏览器或运行时可能会做节流、合并或限制，因此面试里要强调风险和趋势，不要说成绝对补齐每一次。
- 高频关键词：固定周期入队、主线程阻塞、宏任务队列、回调堆叠、连续执行、非并发
- 易追问：浏览器会不会补齐所有过期任务；如何避免 interval 堆叠；为什么动画不适合用 interval
- 回答雷区：把“固定间隔执行”和“固定间隔入队”混为一谈；说多个回调会并发执行；忽略浏览器节流

### 题目：如果 setInterval 的回调里是 async，会发生什么问题？怎么解决？

- 一句话结论：`setInterval` 不会等待异步任务完成，回调里即使写了 `async/await`，也可能出现请求重叠、响应乱序和状态覆盖。
- 30秒回答：如果 `setInterval` 的回调是 `async`，定时器仍会按固定间隔继续触发，不会等上一次 Promise 完成。这样当异步任务耗时大于间隔时，就会出现多个请求并发重叠，可能导致返回顺序错乱、旧数据覆盖新数据、页面 loading 状态异常。更稳妥的做法是用递归 `setTimeout`，或者至少加运行锁避免重入。
- 1分钟展开：
  - `async/await` 只是让函数内部写法更像同步，不会改变 `setInterval` 的调度机制。
  - 当请求耗时 1.5 秒、间隔只有 1 秒时，第二次触发时第一次还没结束，任务就开始重叠。
  - 结果可能是请求并发、数据回写倒挂、资源浪费，严重时还会让 UI 状态不断被旧结果覆盖。
  - 最推荐的方案是“任务完成后再开启下一轮”，也就是递归 `setTimeout`；临时方案可以用布尔锁或 AbortController 控制重入和取消。
- 高频关键词：async interval、请求重叠、响应乱序、状态覆盖、递归 setTimeout、运行锁
- 易追问：为什么 `await` 也挡不住下一次 interval；轮询请求如何避免并发；AbortController 适合什么场景
- 回答雷区：以为 `async` 会自动串行；只说“会慢一点”；不提数据回写乱序和 UI 状态污染

### 题目：SSR 的完整渲染流程是什么？什么是 Hydration，什么叫客户端接管？

- 一句话结论：SSR 是服务端先根据路由和数据生成 HTML，浏览器先显示首屏；随后客户端下载 JS 做水合，复用已有 DOM、绑定事件并恢复状态，最后由客户端接管后续交互。
- 30秒回答：SSR 的核心流程是请求先到服务端，服务端匹配路由、预取数据并渲染出完整 HTML 返回给浏览器，用户先看到可读的首屏内容；接着客户端下载 JS，通过 Hydration 复用服务端生成的 DOM、绑定事件和恢复状态，让页面变成可交互应用；水合完成后，后续的状态更新和路由切换主要由客户端框架接管，运行方式就更接近 SPA。
- 1分钟展开：
  - 第一步是服务端收到请求，根据 URL 匹配页面组件并预取首屏所需数据。
  - 第二步是服务端把组件树渲染成 HTML，同时注入初始状态、CSS、JS 和 SEO 标签，一起返回给浏览器。
  - 第三步是浏览器直接解析 HTML 完成首屏展示，所以 SSR 对 SEO 和 FCP 更友好。
  - 第四步是客户端执行 Hydration，复用已有 DOM，建立虚拟 DOM 映射，绑定事件和状态，避免整页重渲染。
  - 第五步是客户端接管后，后续交互、局部更新和前端路由切换按 SPA 方式运行，但首次整页请求或刷新仍会回到服务端。
- 高频关键词：SSR、预取数据、HTML 渲染、水合、Hydration、客户端接管、FCP、SEO
- 易追问：为什么 SSR 之后还要 Hydration；Hydration mismatch 是什么；SSR 为什么不一定让 TTI 更快
- 回答雷区：把 SSR 说成返回后就已经可交互；把 Hydration 理解成重新渲染整页；只讲首屏快不讲客户端接管

### 题目：以 Vue 为例，服务端没有 DOM，为什么还能渲染 HTML？

- 一句话结论：Vue 服务端渲染不是操作真实 DOM，而是先执行组件生成 vnode，再由 SSR 渲染器把 vnode 序列化成 HTML 字符串。
- 30秒回答：Vue 在服务端不会调用 `document.createElement` 这类 DOM API，而是用 `createSSRApp` 创建应用，执行组件的 `setup` 和 `render` 逻辑先生成 vnode，再通过 `renderToString` 之类的 SSR 渲染器把 vnode 递归转成 HTML 字符串。也就是说，服务端渲染的本质是“字符串生成”，不是“DOM 操作”。
- 1分钟展开：
  - 模板最终会被编译成 render 函数，render 函数执行后先得到描述 UI 结构的 vnode。
  - 这些 vnode 不依赖浏览器 DOM，所以既能在浏览器里变成真实节点，也能在服务端被序列化成 HTML。
  - Vue SSR 里通常会用 `createSSRApp` 配合 `renderToString` 或流式渲染接口完成输出。
  - 真正依赖浏览器环境的逻辑，比如 `window`、`document`、元素尺寸读取，要放到 `onMounted` 或客户端判断里执行。
- 高频关键词：Vue SSR、createSSRApp、renderToString、vnode、字符串生成、onMounted
- 易追问：`createApp` 和 `createSSRApp` 的区别；什么代码不能在服务端跑；流式 SSR 有什么好处
- 回答雷区：说服务端也会直接创建 DOM；把 vnode 说成真实节点；忽略浏览器专属 API 的限制

### 题目：Nuxt 3 作为全栈框架，是如何启动和运行服务器的？Nitro 在里面负责什么？

- 一句话结论：Nuxt 负责页面、组件和约定式目录的组织编译，Nitro 负责真正的服务器运行、请求分发和跨平台部署能力。
- 30秒回答：Nuxt 3 的全栈能力本质上是建立在 Nitro 上的。开发阶段执行 `nuxt dev`，Nuxt 会扫描 `pages`、`server/api`、`server/middleware` 等目录，生成路由和服务端中间产物，再启动带 HMR 的 Nitro 开发服务器。生产阶段执行 `nuxt build`，会输出前端静态资源和 Nitro 服务器产物，最后由 Node、Serverless 或 Edge 运行环境启动 Nitro 来接收请求、处理 SSR 和 API。
- 1分钟展开：
  - 开发阶段的核心是扫描约定目录、生成路由映射和服务端注册信息，再启动带热更新的 Nitro 开发服务器。
  - Nuxt 负责把 Vue 页面、布局、插件和模块生态组织起来，Nitro 负责 HTTP 请求、API 路由、中间件和 SSR 渲染入口。
  - 生产构建后通常会产出 `.output` 目录，其中包含客户端资源和服务端入口文件。
  - 运行时 Nitro 会根据路由类型分发请求，命中页面时执行 SSR 或返回静态内容，命中 `/api` 时执行对应 handler。
  - Nitro 的一个重要价值是支持 Node、Serverless、Edge 等多种部署目标，减少代码层面的环境适配成本。
- 高频关键词：Nuxt 3、Nitro、nuxt dev、nuxt build、约定式目录、SSR、API 路由、HMR
- 易追问：`pages` 和 `server/api` 是怎么生效的；开发和生产启动流程有什么差异；Nitro 为什么适合多平台部署
- 回答雷区：把 Nuxt 和 Nitro 当成同一个概念；以为 Nuxt 自己就是服务器；说不清开发态和生产态差异

### 题目：Nuxt 本质上是前后端一体框架吗？客户端接管后，浏览器的 HTTP 请求还是谁来接收？

- 一句话结论：Nuxt 是工程和运行时一体化框架，对外通常是统一的 HTTP 入口；客户端接管的是页面运行权，不是服务器职责，浏览器的 HTTP 请求仍由 Nitro 接收处理。
- 30秒回答：Nuxt 可以理解为把前端页面层、SSR 层和 BFF/API 层放进同一个工程里，对外通过同一个域名和端口提供服务，所以它是前后端一体框架。但客户端接管后，接管的是前端路由和局部渲染，不是接管服务器。浏览器真正发出的 HTTP 请求，无论是首次整页访问、刷新，还是后续的数据请求，本质上仍然是由 Nitro 服务器接收并处理。
- 1分钟展开：
  - “一体化”说的是工程结构和运行时协同，不是前后端职责完全消失，页面渲染和数据处理仍有边界。
  - 对外看通常是一个统一入口，请求先进入 Nitro，再按页面、API、静态资源等链路分流。
  - 首次访问、刷新和直达链接时，服务器仍要负责返回整页 SSR/SSG 结果。
  - 客户端接管后，前端路由切换可以在本地完成，但只要需要数据，请求还是会打到 Nitro 或其代理的后端服务。
  - 服务器在接管后仍承担 API、鉴权、BFF 聚合、SSR 刷新渲染等职责，不会因为 Hydration 完成就消失。
- 高频关键词：前后端一体、统一 HTTP 入口、客户端接管、Nitro、BFF、路由分流
- 易追问：客户端接管后为什么还需要服务器；Nuxt 适不适合做 BFF；哪些请求是本地完成、哪些必须走服务器
- 回答雷区：把客户端接管理解成服务器没用了；说成只有一个逻辑入口没有分流；混淆路由切换和数据请求

### 题目：Nuxt/Nitro 配合独立 CMS 时，完整部署流程和容错思路是什么？

- 一句话结论：这类项目要按“两套系统协同”来设计，部署上要保证 CMS 接口先稳定、Nuxt 再发布接入，运行时靠配置解耦、缓存兜底和快速回滚保证可用性。
- 30秒回答：Nuxt + 独立 CMS 的部署不能只看前端一侧，而要看两套系统的协同。一般先保证 CMS 内容发布和接口稳定，再在 Nuxt 里用 `useAsyncData` 或 BFF 层接入数据，经过 CI 构建后部署 Nitro 服务，对外再挂 Nginx、负载均衡和缓存。容错上要重点做接口兼容、超时控制、缓存兜底、多实例部署和前后端双向回滚，不然其中一侧变更就可能把整站拖垮。
- 1分钟展开：
  - 第一步先保证 CMS 的内容模型、发布流程和对外 API 稳定，尤其要避免字段改动直接打挂旧前端。
  - 第二步在 Nuxt 侧完成页面、SEO、数据请求和必要的 BFF 聚合，把 CMS 地址和 token 通过运行时配置注入，而不是写死在代码里。
  - 第三步通过 CI 完成 lint、类型检查、测试和构建，产出 Nitro 服务端产物与前端资源，再部署到 Node/容器环境。
  - 运行时要有超时、重试、默认值、缓存和多实例策略，CMS 异常时能返回兜底页或命中旧缓存，不至于白屏。
  - 回滚时要能同时回退 Nuxt 版本、CMS 版本和相关缓存，确保接口结构、页面版本和 CDN/Nitro 缓存保持一致。
- 高频关键词：Nuxt、Nitro、CMS、BFF、运行时配置、接口兼容、缓存兜底、多实例、回滚
- 易追问：CMS 字段变更如何避免打挂页面；内容发布后怎么让前台快速生效；回滚为什么要同时清缓存
- 回答雷区：只讲“前端怎么发版”；忽略 CMS 接口兼容；没有缓存和回滚策略；把配置写死在代码里

### 题目：Nuxt 项目部署到服务器的步骤是什么？CDN 怎么接？CDN 失败会直接报错吗？请求失败会自动回源吗？

- 一句话结论：Nuxt 部署核心是“准备环境、构建产物、注入配置、启动 Nitro、Nginx 代理、CDN 分发”；CDN 只有缓存未命中时会正常回源，链路失败不会自动绕过 CDN。
- 30秒回答：Nuxt 项目部署到服务器通常先准备 Node、包管理器、PM2 和 Nginx，再构建出 `.output` 产物，注入环境变量后启动 Nitro 服务，最后通过 Nginx 做反向代理和 HTTPS。接 CDN 时，要先确定静态资源域名和源站，再按“静态资源长缓存、HTML/接口短缓存”配置策略，并在 Nuxt 中通过 `app.cdnURL` 这类配置切到 CDN 地址。CDN 失败不一定统一表现为报错，关键资源失败可能白屏，图片字体失败通常只是局部异常；只有缓存未命中时 CDN 才会回源，浏览器连不上 CDN 或 CDN 连不上源站都不会自动绕过。
- 1分钟展开：
  - 服务器部署步骤通常是：准备运行环境、拉代码或上传构建产物、注入环境变量、启动 Nitro、用 Nginx/负载均衡对外暴露服务。
  - CDN 接入要先准备独立域名，配置源站，然后按资源类型设计缓存策略，带 hash 的 JS/CSS 长缓存，HTML 和接口短缓存或不缓存。
  - Nuxt 侧可以通过 `app.cdnURL` 或公开运行时配置让静态资源自动走 CDN，避免改业务代码。
  - CDN 失败的表现取决于资源类型，主 JS/CSS 加载失败可能白屏，图片或字体失败通常只是局部退化。
  - “自动回源”只发生在 CDN 节点可达且缓存未命中时；如果请求压根没到 CDN，或者 CDN 到源站链路断了，默认不会自动改成直接请求源站。
- 高频关键词：Nitro 部署、PM2、Nginx、HTTPS、CDN、源站、缓存策略、app.cdnURL、回源
- 易追问：为什么 HTML 不能长缓存；如何做多 CDN 或主备域名；CDN 命中率怎么看；502 和回源失败有什么关系
- 回答雷区：把 CDN 说成一定会自动兜底；把所有资源都配成长缓存；不区分缓存未命中和链路失败

### 题目：进程和线程有什么区别？

- 一句话结论：进程是资源分配和隔离的基本单位，线程是进程内部的执行单位；进程隔离更强，线程协作更轻但也更容易出现共享状态问题。
- 30秒回答：进程可以理解成独立运行的程序实例，拥有自己的地址空间、文件句柄和系统资源；线程是进程内部的执行流，同一进程内的多个线程共享内存和大部分资源。进程之间隔离更强、稳定性更好，但通信成本高；线程切换和通信更轻量，适合并发执行，不过因为共享数据，也更容易出现竞争、死锁和同步问题。
- 1分钟展开：
  - 进程有独立地址空间，崩一个进程通常不会直接把其他进程的内存带崩，隔离性更强。
  - 线程共享进程内存和资源，因此创建和切换成本通常低于进程，但同步复杂度更高。
  - 进程间通信要靠 IPC、Socket、消息队列等方式，线程间可以直接读写共享内存。
  - 选型上，强调稳定隔离时偏多进程，强调资源共享和轻量并发时偏多线程，实际系统中常常混合使用。
- 高频关键词：进程、线程、地址空间、资源隔离、共享内存、上下文切换、同步
- 易追问：为什么线程切换更轻；死锁是什么；浏览器为什么会有多进程架构
- 回答雷区：说线程拥有独立资源和地址空间；把“并发”和“并行”混为一谈；只背概念不讲取舍

### 题目：TCP 和 UDP 有什么区别？分别适合什么场景？

- 一句话结论：TCP 面向连接、可靠、有序，适合对正确性要求高的传输；UDP 无连接、轻量、低时延，适合更看重实时性的场景。
- 30秒回答：TCP 和 UDP 的核心区别在于可靠性和连接方式。TCP 需要建立连接，保证数据有序到达、可重传、可做流量控制和拥塞控制，所以适合 HTTP、文件传输、数据库连接这类不能乱也不能丢的场景。UDP 不建立连接，协议头更小，不保证到达和顺序，但时延更低，适合音视频、实时通信、游戏这类更重视实时性的场景。
- 1分钟展开：
  - TCP 有三次握手、四次挥手，并通过确认应答、重传、滑动窗口、拥塞控制保证可靠传输。
  - UDP 不维护连接状态，也不保证顺序和重传，所以开销更小，适合快速发送小包。
  - 选择时要看业务目标，是“宁可慢一点也要准确”，还是“宁可丢一点也要低延迟”。
  - 需要注意的是 UDP 不是天然更先进，而是协议能力更少，很多可靠性要交给业务层自己补。
- 高频关键词：TCP、UDP、可靠传输、面向连接、无连接、重传、拥塞控制、低时延
- 易追问：三次握手为什么不是两次；TCP 为什么会有粘包；WebSocket 建立在什么协议之上
- 回答雷区：把 UDP 说成一定更快更好；把 TCP 的可靠性说成“完全不会丢包”；忽略应用场景差异

### 题目：常用的 HTTP 状态码有哪些？怎么按场景理解？

- 一句话结论：面试里不要只背数字，最好按“成功、重定向、客户端错误、服务端错误”分类，再结合高频场景说清楚。
- 30秒回答：常见的 2xx 我会记 `200`、`201`、`204`；3xx 会记 `301`、`302`、`304`；4xx 会记 `400`、`401`、`403`、`404`、`429`；5xx 会记 `500`、`502`、`503`、`504`。回答时重点不是把数字背全，而是能结合缓存、鉴权、网关、服务不可用这些真实场景说清楚差别，比如 `401` 是未认证，`403` 是已认证但无权限，`304` 是走协商缓存。
- 1分钟展开：
  - 2xx 代表成功，`200` 是通用成功，`201` 常用于创建成功，`204` 表示成功但没有响应体。
  - 3xx 代表重定向或缓存相关，`301` 是永久重定向，`302` 是临时重定向，`304` 表示资源未修改，可以复用本地缓存。
  - 4xx 代表客户端请求有问题，`400` 参数错误，`401` 未登录或 token 失效，`403` 无权限，`404` 资源不存在，`429` 请求过多。
  - 5xx 代表服务端异常，`500` 通用内部错误，`502` 常见于网关拿到上游错误响应，`503` 表示服务暂时不可用，`504` 是网关等待上游超时。
- 高频关键词：200、201、204、301、302、304、401、403、404、429、502、503、504
- 易追问：`401` 和 `403` 的区别；`304` 什么时候返回；`502` 和 `504` 有什么区别
- 回答雷区：只会背数字不讲场景；把 `401` 和 `403` 混掉；把 `304` 说成真正返回资源内容

### 题目：什么是跨域？常见解决方案有哪些？

- 一句话结论：跨域本质是浏览器同源策略带来的限制，核心解决方案是服务端正确配置 CORS，其他方案要结合具体场景使用。
- 30秒回答：跨域是指当前页面去请求协议、域名或端口任一项不同的资源时，会受到浏览器同源策略限制。最主流的方案是 CORS，由服务端通过响应头声明允许的来源、方法和头信息；开发环境常见反向代理；跨窗口通信可以用 `postMessage`；历史方案还有 JSONP，但它只适合 GET，而且现在主要是兼容老场景。
- 1分钟展开：
  - 同源策略的本意是隔离不同来源的脚本和数据，防止恶意站点随意读取其他站点资源。
  - 触发跨域时，简单请求和非简单请求处理不同，后者通常会先发预检请求 `OPTIONS`。
  - CORS 的关键是服务端返回 `Access-Control-Allow-Origin`、`Allow-Methods`、`Allow-Headers` 等响应头。
  - 工程上常见做法是本地开发用代理，线上通过网关或 BFF 统一收口，减少前端直连多个域名带来的复杂性。
- 高频关键词：同源策略、跨域、CORS、预检请求、OPTIONS、反向代理、postMessage、JSONP
- 易追问：什么请求会触发预检；为什么后端服务之间不存在“浏览器跨域”；带 cookie 的跨域要注意什么
- 回答雷区：把跨域说成后端不能访问别的域名；把 JSONP 当通用方案；只背响应头不说同源策略目的

### 题目：什么是闭包？它有什么价值和风险？

- 一句话结论：闭包就是函数和其词法作用域的绑定关系，它让函数在外部作用域已经结束后，依然能访问原来的变量。
- 30秒回答：闭包本质上不是“函数套函数”这么简单，而是内部函数在被返回或传递后，仍然能访问定义时所在作用域里的变量。它的价值在于做私有状态封装、函数柯里化、回调和缓存；风险在于变量被长期引用，可能带来内存占用、循环引用场景下的泄漏风险，或者出现常见的“闭包拿到旧值”的问题。
- 1分钟展开：
  - 闭包的核心来自词法作用域，函数访问变量看的是定义位置，不是调用位置。
  - 当内部函数被返回出去，外层函数虽然执行完了，但相关变量因为仍被引用，不会立刻释放。
  - 常见应用包括私有变量封装、计数器、工厂函数、事件处理器和函数式编程中的柯里化。
  - 常见问题包括循环里错误捕获同一个变量、React 等框架中的 stale closure，以及不必要的长期引用导致内存浪费。
- 高频关键词：闭包、词法作用域、私有状态、柯里化、回调、stale closure、内存占用
- 易追问：`var` 循环为什么会有闭包问题；`let` 为什么能解决；闭包一定会导致内存泄漏吗
- 回答雷区：把闭包定义成“函数里有函数”；一味说闭包会泄漏；说不清词法作用域

### 题目：一张 100px × 100px 的图片，在内存里的占用大概是多少？

- 一句话结论：如果问的是图片解码后的位图内存占用，常见估算是 `100 × 100 × 4 Byte = 40000 Byte`，约等于 39KB。
- 30秒回答：这道题一般考的是图片解码到内存后的大小，而不是文件压缩后的磁盘体积。按最常见的 RGBA 位图来估算，每个像素 4 个字节，所以 `100 × 100 × 4 = 40000 Byte`，大概是 39KB。面试里最好顺手补一句，这个是解码后的内存占用，不等于 jpg/png 文件本身大小。
- 1分钟展开：
  - 如果图片被浏览器解码成 RGBA 位图，1 个像素通常对应 R、G、B、A 四个通道，每个通道 1 Byte。
  - 所以 100×100 的实际像素点一共有 10000 个，乘以 4 Byte 就是 40000 Byte。
  - 换算成 KB 时大约是 39KB，这个是运行时位图占用，不是网络传输时的压缩大小。
  - 边界上，不同色深、通道数、浏览器实现或图片实际像素尺寸不同，结果也会变化，所以要先明确题目问的是哪种占用。
- 高频关键词：图片解码、位图、RGBA、像素、内存占用、压缩体积
- 易追问：为什么文件大小和内存占用不一样；如果没有 alpha 通道怎么算； Retina 场景为什么可能更大
- 回答雷区：把下载后的文件大小当成内存占用；忘记说明这是解码后的位图大小；只报数字不说计算方式

### 题目：什么是静态站点生成（SSG）和增量静态生成（ISR）？它们和 SSR 有什么区别？

- 一句话结论：SSG 是构建时预生成静态页面，ISR 是“静态页面 + 按需再生成”，SSR 是每次请求时动态生成 HTML，三者核心差异在于生成时机、更新方式和服务端成本。
- 30秒回答：SSG 会在构建阶段把页面提前生成好，用户访问时直接返回静态内容，首屏快、SEO 好，但内容更新要重新构建；ISR 是 SSG 的增强版，页面先以静态形式提供，当缓存过期或触发再生成时，后台重新产出新页面，适合中低频更新场景；SSR 则是每次请求都在服务端动态渲染 HTML，实时性最强，但服务端压力也最大。
- 1分钟展开：
  - SSG 适合官网、文档、博客这类内容稳定且追求极致性能和 SEO 的页面，但页面很多时构建成本会变大。
  - ISR 保留了静态页面的性能优势，又允许上线后按页更新，不需要每次内容变化都整站重构建。
  - SSR 的优势是数据最实时，适合强动态内容，但每次请求都要走服务端渲染链路，成本更高。
  - 在 Next.js 里，SSG 常见写法是 `getStaticProps`，ISR 则是在其基础上增加 `revalidate`，动态路径还可能配合 `fallback` 使用。
  - 真实项目里三者往往会混用，比如首页用 SSG，详情页用 ISR，强实时模块用 SSR。
- 高频关键词：SSG、ISR、SSR、构建时生成、按需再生成、revalidate、fallback、SEO
- 易追问：`revalidate` 的作用是什么； `fallback` 有哪些模式； ISR 和缓存有什么关系； Nuxt 里怎么做类似能力
- 回答雷区：把 ISR 说成纯 SSR 加缓存；以为 ISR 每次请求都会重新生成；只讲定义不讲适用场景和成本
