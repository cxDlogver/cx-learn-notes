### 1.1 已锁定的产品和技术边界

- 首版只交付 React Native iOS，业务层为以后 Android 复用留接口；服务端为 TypeScript + NestJS + PostgreSQL，Redis 用于短时状态与任务。
- 中国大陆 +86 手机号登录。计划时区创建后固定；一次性任务截止日仅今天及未来，且只支持“要做”。固定日期计划今天未提交时不提前计入完成率。
- 离线只允许记录提交、修改、补记和附件暂存；计划规则和好友授权必须联网。多设备记录冲突由用户选择，保留修订审计。
- 暂停或归档当天立即取消未提交义务。账号注销立即停用访问与分享，30 天内可撤销，期满永久清理。
- 以 1 万日活作为初期容量与压测设计基线；首版单区域部署。版本号和具体云供应商须经 FND-02、FND-05 的样板与环境核对后锁定，不在计划中猜定。

## 2. 任务定义、依赖与质量门槛

任务 ID 长期稳定。每项任务须提交：代码与配置变更、接口/迁移/页面映射更新、变更说明、静态检查记录；涉及可观察行为的任务另附必要的开发自测记录。§3.1 的优先级是 AI 领取任务的唯一排序依据；前置任务已集成到项目开发基线后，独立任务才可并行领取。可使用已冻结的 contracts、domain 接口和 mock repository 开发，最终以真实实现替换 mock。

**完成标准统一规则：**表中“完成标准”与对应静态门槛必须同时满足。静态门槛失败、未运行、被跳过，任务状态为未完成。配置和文档变更也必须通过其适用的静态检查。运行冒烟、单元测试和集成测试是开发自检，不能替代静态门槛，也不能标记 ATDD 用例为通过。

## 11. AI 执行、Git checkout 与任务签出

### 11.1 仓库基线与工作树

当前 Git 根目录是 F:/CX_notes/cx-learn-notes，项目目录 ios-plan-checkin 尚未被父仓库跟踪，父仓库还存在其他目录的未提交改动。**本文件只设计流程，不执行 checkout、提交或改动其他项目。**开始 FND-01 前先完成一次受控仓库准备：

1. 记录父仓库 HEAD、分支和完整工作区状态；只审查并暂存 ios-plan-checkin 目录的已确认文件，检查 staged 路径全部属于该目录。父仓库其他目录的修改、暂存项和未跟踪文件必须原样保留。
2. 形成仅包含该项目当前文档与设计资源的基线提交，记录 baseCommit 与文档 SHA-256；若路径范围无法保证，停在仓库准备，不使用全仓暂存或清理命令。
3. 从 baseCommit 建立项目开发分支 codex/ios-plan-checkin-build，并在独立工作树工作；优先使用宿主提供的托管 worktree 能力。不要在已有脏工作区直接切换分支或重置。将 integrationBranch、integrationCommit、worktreePath 写入任务台账。
4. 每个任务从**当前已集成**的 integrationCommit 创建专属 codex/ios-plan-checkin-任务ID 分支/工作树。领取时检查工作树干净、基线 SHA 正确、依赖都为 DONE。并行任务不能共用工作树、直接修改彼此分支或借用未合并代码作为前置。
5. 集成到项目开发分支时只纳入该任务约定的项目路径；先复核差异及文件归属，再在集成后的 commit 重跑受影响的 S0 与专门静态门槛。更新 integrationCommit 后才能把任务置为 DONE；正式上线分支与远端发布另待后续验收决定。

工作树/分支命名中的任务 ID 使用小写形式，例如 codex/ios-plan-checkin-fnd-01。若工作树创建或文件权限受阻，记录 BLOCKED 和具体原因，不改用会覆盖父仓库脏改动的 checkout/reset/clean。项目基线准备属于 FND-01 的启动前置，不额外计为已完成业务任务。

### 11.2 AI 领取与集成协议

每轮先读取本文件的 §3.1 优先级、§4–9 对应任务行和任务台账，再执行以下闭环：

1. **找 READY**：状态未开始，全部依赖已在 integrationCommit 中完成；接口、迁移、设计映射已冻结。按优先级从小到大领取。多个 READY 可并行且无固定上限，但共享核心文件、未冻结契约、迁移序号或同一设计 token 的任务须先协调归属，冲突不可独立解决时顺序执行。
2. **Git checkout**：在独立工作树检出任务分支，保存 baseCommit、branch、worktreePath 和任务目标；只修改本任务范围。发现已有未提交工作时先查明来源并保留，不执行破坏性清理。
3. **设计与编码**：先读任务 sourceRefs、对应 Pen screen.key/nodeId 与 contracts/domain 类型；必要时更新契约/迁移及调用端。mock 只服务当前未就绪的依赖，完成标准要求的真实集成不能由 mock 代替。
4. **本分支检查**：运行本任务 S0 与专门门槛，运行相关开发自测；记录命令、工具版本、退出码、日志与当前 commit。失败留在本任务修复，不标为 STATIC_PASS。
5. **任务 check-out**：对照本任务完成标准逐条核对，审查 changedPaths 与来源映射，完成代码评审、提交和风险记录。此时最多为 REVIEWED，不能因分支绿色就解锁下游。
6. **集成复检**：按 §3.1 优先级将已评审任务逐项集成，解决冲突；在新 integrationCommit 上重跑受影响静态门槛及必要开发自测。通过后记录集成提交、把任务置为 DONE，随后重新计算 READY 集合。

任务状态为 NOT_STARTED → READY → IN_PROGRESS → STATIC_PASS → REVIEWED → DONE；若静态门槛失败回到 IN_PROGRESS。依赖未完成、仓库前置未满足或设计/API 冲突未解决时为 BLOCKED，并记录阻断者、影响和解除条件。只有集成复检通过才可从 REVIEWED 变为 DONE。任务不以“页面看起来差不多”或“接口能返回 200”单独判完成。

[任务状态台账](./build-progress.json)保存 35 个 ID 的优先级、直接依赖、静态门槛和当前状态；初始均为 NOT_STARTED，READY 由依赖状态实时计算。只有集成者在项目开发分支上更新台账和 integrationCommit，并在同一次集成中提交；并行任务分支提交签出记录，不直接争写台账。台账与本计划冲突时先停止领取任务，修正计划和台账的一致性，再继续。无固定并行任务数量上限，但一个任务 ID 同时只能由一个工作树领取。

台账的 planSha256 对本文件 UTF-8 字节先统一 CRLF/CR 为 LF 再计算，避免 Windows 与 macOS/Linux checkout 换行符不同造成误报。integrationCommit 记录最近一次通过静态复检的**代码提交**；台账自身的后续状态提交不改变这个值。创建下一个任务分支时使用项目开发分支的实际 HEAD，并确认 integrationCommit 是其祖先。

### 11.4 任务分配与变更规则

同一数据实体由 CORE schema/契约任务维护单一来源，客户端只消费 contracts；设计 token 由 FND-03 维护单一来源。领域规则变更先改 domain、契约和版本迁移，再改 API/客户端。数据库、API 与客户端可由不同开发者并行，但合并前必须在相同 commit 上完成适用静态门槛。新增页面或业务规则先更新来源文档与映射，再新增任务或修改受影响任务；任务 ID 不复用。每个模块结束时复核其任务产物和依赖，未完成项不能被 OPS-06 悄悄吸收。

## 12. 候选版移交给后续 ATDD 阶段

OPS-06 移交：候选构建及 commit、服务端/Worker 镜像摘要、数据库迁移版本、OpenAPI 文件、32 页组件映射表、任务状态台账、Pen/PRD/技术/UIUX/验收文件摘要、测试环境及种子数据说明、静态检查总报告、开发自测清单、已知缺陷与限制。后续团队按 [ATDD/BDD 验收矩阵](./ATDD-BDD-计划打卡-iOS-v1-验收矩阵.md)执行场景、操作、功能/视觉/反向断言和证据包；只有该独立阶段才能给出正式通过、失败或阻断结论。未通过验收时回到对应任务修复，重跑该任务静态门槛与相关开发自测，再提交新候选版。
