> 平台：Web（桌面与手机浏览器）

> 文档范围：面向有限真实用户的 Web 首版完整需求  
> 核心场景：登录 → 创建计划 → 今日执行 → 打卡记录 → 日历回顾 → 好友监督

## 1. 产品背景与定位

### 1.1 产品背景

iOS 首版定义了计划创建、主动打卡、日历回顾和指定好友监督的完整链路。用户在电脑前管理计划、填写备注或查看较长时间跨度的记录时，也需要直接通过浏览器使用同一账号。手机用户在没有安装 iOS App 或使用其他手机系统时，同样需要通过网址完成核心操作。

Web 首版面向真实使用，不是仅供演示的管理后台。它承载与 iOS 相同的个人产品能力，使用同一份云端业务数据。Web 不引入独立的计划类型、统计口径或好友权限。

### 1.2 产品定位

“计划打卡 Web”是计划打卡的浏览器客户端。它帮助用户回答：

```text
今天需要关注什么？
今天实际做得怎么样？
过去一段时间坚持得怎么样？
指定好友能看到并鼓励哪些计划？
```

Web 与 iOS 的区别在于操作环境和页面布局，而不是用户拥有两套计划或两种打卡结果。

### 1.3 目标用户与使用环境

首版主要面向：

- 已经使用或准备使用计划打卡的个人用户；
- 需要在桌面浏览器集中管理计划和回顾历史的用户；
- 需要在手机浏览器直接使用产品的用户；
- 希望在 Web 与 iOS 之间查看同一份记录的用户。

桌面与手机同等优先。用户通过网址直接进入产品；添加到主屏幕或安装为网页应用属于可选使用方式。首版允许真实用户公开注册，通过有限推广控制初期规模，不设置邀请码或手机号白名单。

### 1.4 产品目标

| 目标 | 首版要求 |
| --- | --- |
| 完整业务闭环 | Web 覆盖 iOS PRD 中的账号、计划、打卡、统计、好友、提醒设置与个人数据管理 |
| 跨端一致 | 同一账号在 Web 与 iOS 看到相同的计划、记录、统计及授权结果 |
| 双端可用 | 桌面与手机浏览器均可独立完成所有业务流程 |
| 状态可信 | 未记录不被自动解释成成功或失败；同步、提交、冲突状态清晰 |
| 有限真实用户上线 | 开放注册、限制推广；使用真实登录、真实持久化数据和可执行的验收门槛 |

### 1.5 首版范围与例外

Web V1 包含：

- 手机号验证码登录、新用户资料、退出、换号；
- 三类计划创建、编辑、暂停、恢复、归档和删除；
- 分组、今日、计划列表、计划详情、全局日历、单计划日历和统计；
- 成功、失败、跳过打卡，备注、照片、每计划一个可选数值项、补记和修正；一次性任务的最终结果也可附加这些内容；
- 好友申请、逐计划分享、预览、撤销、屏蔽、Emoji 和鼓励留言；
- 计划提醒与社交通知的设置和站内呈现；
- 数据导出、账号删除。

与 iOS 首版相比，Web 有两个明确的渠道边界：

1. **断网不可使用。** Web 不承诺离线查看、离线打卡、离线附件暂存或断网后自动重试。断网时呈现不可用状态，用户不能误以为操作已经保存。
2. **关闭页面后的提醒不作为发布门槛。** Web 提供站内提醒与可选浏览器通知；浏览器、系统或用户权限可能限制后台送达。

首版不做公开动态、排行榜、群组共享、实时聊天和独立 Web 管理后台。Web 与 iOS 共用业务数据，但 Web 不要求复制 iOS 的原生相册、系统通知权限页或离线本地库交互。Web 可以在 iOS App 尚未正式发布时独立上线，前提是 Web 自身的服务端、浏览器、安全及业务验收通过。

### 1.6 来源与冲突处理

业务状态、计划类型、统计语义、好友权限和隐私边界以 [iOS PRD](./PRD-计划打卡-iOS-v1.md) 为共同产品规则。本文写明 Web 的页面、浏览器和发布要求；发生平台差异时，以本文明确列出的 Web 例外为准。实现方案中的接口和技术选型不能反向修改产品规则。

## 2. 计划设计与管理

### 2.1 计划类型与方向

Web 使用与 iOS 相同的三类时间规则：

| 类型 | 用户输入 | 生效和展示 |
| --- | --- | --- |
| 固定日期循环 | 每周选择至少一天；七天全选即每日 | 仅选中日产生应打卡事项 |
| 每周目标 N 天 | 设置每自然周 1～7 天 | 周一至周日累计成功天数，日期不预先指定 |
| 一次性任务 | 设置截止日期 | 截止前待完成，逾期后持续可见直至终态 |

循环计划可选择“要做”或“不要做”；一次性任务仅支持“要做”。“不要做”的成功必须由用户主动确认，文案明确表达“今天做到了，没有发生该行为”。

### 2.2 创建计划

| 字段 | 是否必填 | 规则 |
| --- | --- | --- |
| 名称、方向、时间规则 | 是 | 根据计划类型显示对应输入 |
| 开始日期 | 循环计划必填 | 包含在有效期内 |
| 固定星期 | 固定日期计划必填 | 至少一天 |
| 每周目标 N | 每周目标计划必填 | 整数 1～7 |
| 截止日期 | 一次性任务必填 | 按计划时区解释 |
| 结束日期、分组、说明、提醒、数值项 | 否 | 数值项最多一个，配置名称和单位；不阻断基本计划创建 |

创建表单在桌面和手机上使用相同字段与校验。切换计划类型时，先提示即将移除不适用字段；保存失败时保留用户已填写内容，明确指出具体字段与原因。

### 2.3 日期、周与时区

- 计划开始日期和结束日期均包含在有效期内。
- 自然周统一为周一至周日。
- 计划所属 IANA 时区在创建时确定，历史业务日期不随浏览器或设备时区变化而移动。
- 页面在浏览器当前时区与计划时区不同时，显示“按计划时区计算”提示。
- 未来日期不得预先打卡；历史日期只可在当时有效的计划规则允许范围内补记。

### 2.4 生命周期与规则变更

循环计划支持运行、暂停、恢复、归档和删除。暂停与归档不产生新的应打卡项，也不继续催促；历史记录保留。删除是不可恢复操作，确认界面列出打卡、照片、数值和分享权限将被删除，并提供归档入口。

名称、分组、说明、提醒修改不改变历史统计。时间规则变更次日生效，过去日期按照旧规则解释。每周目标计划在周中开始、结束、暂停、恢复或更改目标时，该周标记为“部分周”，保留已产生的记录，但不计入周达标率和连续达标周数。数值项的名称或单位允许修改，新配置从生效日起用于新记录；历史记录保留原名称、单位和原始数值，不自动换算。

## 3. 打卡与统计规则

### 3.1 记录模型与提交

每次打卡必须选择结果和业务日期，并记录实际提交时间。文字备注、照片和数值均为可选项。一次性任务的完成、失败或取消结果同样允许附加这些内容。数值仅供回顾，不自动判定成功或失败；一次基本打卡不应因未上传照片或未填写数值而无法提交。

同一计划在同一自然日最多有一条有效记录。再次提交进入修改流程，不能用重复记录增加每周成功天数。Web 提交后，界面在服务端确认前显示“提交中”；成功后显示最终结果；失败时保留输入并提供重试。未得到服务端确认时不得显示“已保存”。

### 3.2 状态语义

| 状态 | 产生方式 | Web 表达 |
| --- | --- | --- |
| 待处理 | 今天属于应执行日且尚未提交 | 显示可操作入口 |
| 成功 | 用户主动确认做到 | 状态文字、图标及可访问名称一致 |
| 失败 | 用户主动确认未做到 | 不与未记录共用文案 |
| 跳过 | 用户主动决定本次不参与 | 不作为失败 |
| 未记录 | 应执行日期结束仍无操作 | 系统派生未知状态，不能伪装成用户打卡 |

固定日期循环仅在选中日期出现这些状态；非选中日期没有打卡或补记入口。每周目标 N 天的空白日期不产生单日“未记录”。一次性任务采用待完成、逾期、按时完成、迟完成、失败、取消的独立状态，不计算每日未记录或连续打卡。

### 3.3 不同类型的结果判定

**固定日期循环**：仅生效、未暂停且星期命中的日期需要结果。今天未操作仍为待处理；日期结束后仍未操作才显示未记录。用户已打卡的卡片当天继续显示最终结果。

**每周目标 N 天**：成功天数按不同业务日期计数；用户可自愿记录失败或跳过，但不因此减少目标 N。达到 N 后仍可继续记录，进度可显示 4/3，周达标率上限为 100%。周末不足 N 才判定“本周未达标”。

**一次性任务**：截止日结束后仍未完成则逾期，并持续出现在待处理范围。逾期后完成显示“迟完成”及完成日期。失败和取消为终态；误操作通过原记录修正，不在同一任务上再次新建完成记录。

### 3.4 补记、修正与跨端冲突

- 补记同时保存业务日期和实际提交时间，显示“补记”。
- 修改保留“已修正”和最近修改时间；分享计划的授权好友也能看到修正标记。
- 对同一记录的 Web/iOS 并发修改必须提示冲突，展示本机提交意图与云端版本，让用户选择最终版本；不得静默覆盖。
- Web 正在编辑的表单在网络断开时停止提交，保留当前页面输入供用户联网后再次操作；不承诺关闭页面后保存草稿。

### 3.5 统计口径

今日、日历、计划详情、统计和好友视图使用同一服务端业务状态。固定日期计划的完成率以适用日期为基础，跳过不进入分母；今天未提交时不提前进入完成率分母。连续成功遇到失败、跳过或未记录时中断。每周目标按周一至周日的自然周计算；部分周只保留记录，不计入周达标率和连续达标周数。已完成日期补记或修正后，相应历史统计同步更新。一次性任务不展示每日完成率或连续打卡。

## 4. 页面与信息组织

### 4.1 信息架构

Web 保留“今日、日历、计划、朋友”四个主入口，并提供个人设置入口。所有视口统一使用移动端的四项底部主导航，内容采用最大 480 CSS px 的单列容器，水平居中并从顶部排布；消息与设置从页内入口进入，详情页面按移动端独立组织，所有关键操作不依赖悬停。路径在刷新、浏览器前进/后退后仍可回到正确页面；未经登录访问私人页面时引导登录，登录后回到原目标页面。

```text
登录 / 首次使用
  ├─ 今日
  │   ├─ 快速打卡 / 修改
  │   └─ 计划详情
  ├─ 日历
  │   ├─ 日期详情 / 补记
  │   └─ 计划详情
  ├─ 计划
  │   ├─ 创建 / 编辑 / 分组
  │   └─ 计划详情 / 单计划日历 / 统计
  ├─ 朋友
  │   ├─ 好友请求
  │   ├─ 逐计划分享 / 撤销
  │   └─ 鼓励互动
  └─ 设置
      ├─ 账号与通知
      ├─ 数据导出
      └─ 账号删除
```

### 4.2 登录与首次使用

沿用中国大陆手机号和一次性短信验证码登录。首版开放注册，新用户补充唯一用户名和昵称；推广节奏控制初期用户量，不以白名单阻止新用户。首次登录无计划时，今日页给出创建计划入口；不强制添加好友、照片或提醒。登录失败、验证码冷却、号码不合法、会话过期均有明确提示。

### 4.3 今日页

今日页为登录后默认入口：

- 固定日期计划仅在今天为选中执行日时显示；
- 每周目标计划显示本周成功天数、目标及可操作入口；
- 一次性任务显示截止日期，不能伪装成每天必须完成；
- 逾期一次性任务持续显示，直到产生终态；
- 完成打卡后卡片不突然消失，而是展示提交结果。

桌面、平板与手机使用相同移动端信息结构，按重要性纵向排列今日内容。宽度为 min(100%, 480px)，容器之外填充主题背景；字号和控件尺寸不随容器整体缩放。各视口的计划状态、数量和操作结果一致。

### 4.4 日历与计划详情

全局日历按日期显示成功、失败、跳过和未记录数量，并允许按分组筛选、查看日期详情和合法补记。状态必须同时用文字或图形说明，不能只靠颜色。每周目标计划仅在实际打卡日期显示日记录，并另展示周结果。

计划详情包括规则、当前进度、统计、单计划日历、历史记录和设置。固定日期计划重点展示完成率及连续记录；每周目标展示本周进度与历史达标周；一次性任务展示截止日期、逾期与最终完成日期。

### 4.5 分组、好友与设置

计划列表支持分组查看及未分组。删除分组只将计划移到未分组，不删除计划历史。朋友页区分好友请求、本人分享的计划、对方分享给自己的计划及鼓励互动。设置页提供账号资料、通知、数据导出、退出登录和账号删除。

### 4.6 响应式与页面状态

当前 [Pen 设计](./ui/plan-checkin.pen)及其结构化视觉树是本次样式对齐的权威，[Web 样式映射](./ui/web-style-map.json)记录来源节点、令牌、固定文案、页面结构和业务差异。有对应画板的页面对齐字体（Noto Sans SC）、字号、字重、颜色、间距、圆角、图标、固定文案和移动端结构。无画板页面保留现有内容与业务能力，继承同一居中容器和公共样式，不新增专用页面设计规格。真实日期、数量、用户名等由数据生成；Web 业务规则优先于画板示例。所有视口保持单列移动式布局、最大 480px；页面允许纵向滚动，禁止横向溢出和不可达控件。保留深色模式，结构、字体和间距与浅色相同，使用语义深色配色。

每个核心页面至少定义加载、空态、提交中、成功、失败、无网络、无权限和会话失效状态。重试操作不得导致重复打卡或重复留言。

## 5. 好友、提醒与数据

### 5.1 好友与逐计划分享

好友关系本身不开放计划。分享权限按“具体计划 × 具体好友”建立。分享前明确提示：对方将看到该计划已有的状态和文字备注，包括历史失败原因，并允许预览好友可见内容。

| 内容 | 授权好友可见 |
| --- | --- |
| 计划名称、时间规则、进度 | 是 |
| 历史状态、文字备注、补记与修正标记 | 是 |
| 照片、数值、其他计划和个人统计 | 否 |

好友可发送 Emoji 和简短鼓励留言，不能替用户打卡或修改记录。鼓励留言仅计划拥有者与发送者可见，不形成所有好友共享的评论区。撤销分享、删除好友或屏蔽后，相关计划的当前和历史访问立即失效。

### 5.2 提醒与通知

计划提醒规则与 iOS 相同：固定日期计划仅在选中日提醒；每周目标由用户选择提醒日且达标后停止催促；一次性任务按照用户设置的截止日前提醒规则处理。暂停、归档、当天已打卡或一次性任务终结后停止对应提醒。

计划提醒的时间与星期属于共享的计划规则，在 Web 或 iOS 修改后两端均看到新规则。是否接收计划提醒和社交通知按 Web、iOS 两个渠道独立设置；开启或关闭 Web 投递不改变 iOS 投递，反之亦然。同一用户主动开启两端时允许两端分别收到提醒。

Web 首版必须提供可回看的社交消息中心，包含好友申请、计划分享和鼓励留言；消息内容及已读状态按账号跨端共享。计划打卡的站内提醒只在网页打开时即时提示，待处理事项始终在今日页可见，不为每次计划提醒生成持久消息。

浏览器通知由用户主动开启。首版实现 Web Push 订阅和发送链路，并在可控支持场景验收；权限被拒绝、浏览器不支持或订阅失效时，设置页说明当前状态和可采取的操作。浏览器关闭后的实际送达受平台限制，不作为首版发布阻断项。通知外层仅显示“有计划需要关注”“收到新互动”等通用提示，不显示计划名、失败原因或留言；用户登录后在站内查看详情。

iPhone/iPad 的后台 Web 推送以用户将网页添加到主屏幕并授权为前提；普通网址模式仍可使用全部业务功能和站内提醒，产品不得声称普通浏览器标签页关闭后一定收到通知。该边界依据 [WebKit 的 Web Push 说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)。

### 5.3 在线使用与网络异常

Web 断网不可使用。访问产品或操作时检测到网络不可用，应明确显示“当前无法连接，请联网后重试”；不得在本机制造看似已提交的打卡结果。网络从可用变为不可用时，未确认的写操作保持未完成状态。恢复网络后由用户重试或重新加载权威数据。

浏览器可能清除站点存储，因而 Web 不把本地缓存当作业务记录的权威来源。首次加载、刷新以及切换设备时以云端结果为准。

### 5.4 账号、会话与个人数据

Web 与 iOS 使用同一账号及云端数据。沿用现有服务端会话口径：访问令牌有效 15 分钟，临近过期时在有效刷新会话下自动续期；刷新会话每次轮换后有效 30 天。刷新会话到期、被撤销或用户退出后，要求重新短信登录。普通退出仅结束当前 Web 会话，不自动退出 iOS；换号与账号注销按既有全会话撤销规则执行。会话失效时清除私人页面并引导登录。

用户可在 Web 导出包含计划、分组、打卡、照片、好友及分享关系的个人数据。账号删除前说明云端数据和分享访问如何处理；确认后立即停用登录和分享访问，并遵循既有 30 天可撤销与期满删除规则。

### 5.5 照片与权限

Web 允许用户通过浏览器文件选择上传打卡照片；在浏览器和设备支持时可使用相机入口。拒绝相机或文件访问不能阻断不带照片的打卡。照片始终仅本人可见，分享计划不会开放照片；数值记录同样保持私密。

## 6. 跨模块规则与质量要求

### 6.1 核心业务规则总表

| 编号 | 规则 |
| --- | --- |
| W01 | Web 与 iOS 共用账号、计划、打卡和权限数据 |
| W02 | 三类计划及“要做/不要做”方向与 iOS 共用业务语义 |
| W03 | 每日是固定日期七天全选，不是独立计划类型 |
| W04 | 未操作不自动判定成功或失败 |
| W05 | 每周 N 天的空白日不产生单日未记录 |
| W06 | 每计划每自然日最多一条有效打卡 |
| W07 | 计划时区与历史业务日期不随浏览器时区变化而重归属 |
| W08 | 一次性任务逾期后继续可见，完成区分按时与迟完成 |
| W09 | 分享按具体计划与具体好友授权，照片和数值不共享 |
| W10 | Web 断网时不得显示已保存或提供离线写入承诺 |
| W11 | Web 与 iOS 的提醒订阅和开关互不改变 |
| W12 | 桌面与手机浏览器均可完成全部核心流程 |
| W13 | 所有跨端视图使用同一权威结果，冲突不得静默覆盖 |
| W14 | 每周目标部分周只保留记录，不计入周达标率或连续达标周数 |
| W15 | 计划提醒时间规则共享，计划及社交通知投递开关按 Web/iOS 渠道独立 |
| W16 | 社交消息和已读状态按账号跨端共享，浏览器通知外层仅显示通用文案 |
| W17 | 所有计划最多配置一个可选数值项；历史数值保留当时名称和单位 |

### 6.2 交互与可访问性

- 成功、失败、跳过、未记录和待处理必须能通过文字及图形辨认，不仅依赖颜色。
- 键盘可完成导航、表单输入、日历选择、打卡和设置；可见焦点清晰。
- 表单字段具备标签、错误信息和辅助说明；动态提示能够被屏幕阅读器识别。
- 支持浏览器文字缩放和窄屏重排，不能因放大字体而遮挡提交按钮。
- 页面宽度不得超出可用视口；禁止横向溢出或屏幕外不可达操作。长表单和历史列表允许纵向滚动，固定导航与提交控件不得遮住内容。
- 触屏操作区域足够大；不能将悬停作为唯一入口。
- 深浅色模式按统一视觉系统设计并保证状态对比度。
- 当前 Pen 结构化设计用于有画板页面的样式与结构对齐；Web 浅色和深色均按最大 480px 单列居中布局、视觉令牌、状态、文案、可读性与无障碍验收，不设置逐像素差异阈值。

### 6.3 浏览器与发布环境

首版正式验收覆盖桌面 Chrome、Edge、Safari、Firefox，以及手机 Safari、Chrome 在上线时的当前稳定大版本和上一稳定大版本。桌面与手机同等优先测试。更旧版本提示升级；遇到缺少通知或相机能力时，仅降级该能力，不改变打卡结果或隐私权限。

真实用户环境须使用 HTTPS、可用的短信验证和持久化云端服务。Web 客户端上线前应验证现有 API 的浏览器接入、会话安全和跨域配置；当前仓库的本地检查通过不代表 Web 或服务端已完成生产验收。

### 6.4 数据一致性与可靠性

用户在 Web 将某天“失败”修正为“成功”后，今日/历史、日历、统计及获授权好友视图都应更新。iOS 后续查看仍应得到同一最终结果，这是共享产品要求；Web 发布验收仅核对 Web、共享 API 与同账号多浏览器，不以 iOS 客户端联测为门槛。重复点击、请求重试和多标签页提交不得生成重复有效记录。分享撤销应在再次读取时立即阻断历史数据，而不是只隐藏入口。

## 7. 衡量、验收与风险

### 7.1 产品指标

首版记录计划创建完成率、首周打卡率、应打卡日记录率、周计划达标率、日历回访率、计划分享率与鼓励互动率，并分桌面 Web、手机 Web 和 iOS 观察。上线前不预设缺乏真实基线的增长百分比。

### 7.2 核心验收场景

**响应式主流程**

```text
Given 用户分别在桌面和手机浏览器登录同一账号
When 创建“每周二、周四学英语”并在周二打卡
Then 两种屏幕均可独立完成操作
And 今日、日历、计划详情显示同一结果
And 同账号另一浏览器及共享 API 读取同一条记录
```

**计划规则与结果**

- 七天全选的固定日期计划每天产生一次应处理事项；前一日未操作显示“未记录”，不自动判失败。
- 每周二、周四的固定日期计划在周三不提供打卡或补记入口。
- 每周目标 3 天在周一、周三成功后显示 2/3；周一或周三重复提交不使成功天数增加；空白日不显示未记录。
- 每周目标在第四天成功时可显示 4/3，但达标率不超过 100%。
- 一次性任务截止后仍未完成时显示逾期；逾期后完成显示“迟完成”。
- “不要做”计划必须由用户主动选择成功，页面文案表达“今天做到了，没有发生该行为”。
- 周中开始、结束、暂停、恢复或改目标的部分周保留记录，但不计入周达标率和连续达标周数。

**补记、修正与多浏览器冲突**

```text
Given 用户在 9 月 22 日补记 9 月 20 日的成功
When Web 保存成功
Then 记录保留业务日期 9 月 20 日、实际提交时间 9 月 22 日和“补记”标记
And 同账号另一浏览器、日历与统计显示一致
```

同一记录在两个 Web 浏览器会话并发修正时，用户看见冲突及两个版本，选择后最终仅有一条有效记录。Web 与 iOS 的客户端联测另行执行，不阻断 Web 独立发布。

**好友与隐私**

```text
Given A 与 B 已是好友，但 A 未分享计划
Then B 看不到 A 的任何计划
When A 仅分享跑步计划给 B
Then B 可见跑步的规则、进度、历史状态和文字备注
And B 看不到照片、数值、其他计划或个人统计
When A 撤销分享
Then B 无法再读当前和历史数据，也不能继续留言
```

**网络、会话与提醒**

- 断网进入 Web 时显示不可用状态；断网提交不能显示成功或“已保存”；联网后用户可重试。
- 访问令牌过期而刷新会话有效时，用户继续使用且不丢失已确认数据；刷新会话失效后重新登录。
- Web 退出不自动退出 iOS；换号和注销使相关会话按既有规则失效。
- 修改共享提醒时间规则后 Web/iOS 均看到新规则；关闭 Web 的投递开关不修改 iOS 开关，反之亦然。
- 社交消息在 Web 标记已读后，同一账号在 iOS 也显示已读；计划提醒仅在打开网页时即时提示。
- Web Push 订阅和发送链路在支持场景可用，通知外层只显示通用文案；浏览器后台实际送达失败不阻断发布。
- 手机浏览器在未安装 Web 应用时仍可通过网址完成完整业务流程。

**数值与一次性任务附件**

- 所有计划可配置一个数值项；记录可选填数值，但结果始终由用户主动选择。
- 数值项改名或改单位后，旧记录仍按原名称和单位显示，不自动换算。
- 一次性任务完成、失败或取消时可附加文字、照片和数值；修正后仍保留修正标记。

**个人数据**

- 导出的文件包含该用户有权导出的计划、记录、照片与关系数据。
- 删除账号后立即停止登录及分享读取，数据清理遵循已确认的撤销窗口与最终删除规则。

### 7.3 发布门槛

详细用例、浏览器/视口变体、证据与判定规则见 [Web ATDD/BDD 验收矩阵](./ATDD-BDD-计划打卡-Web-v1-验收矩阵.md)。该矩阵是未来验收基线，当前尚无 Web 执行结果。

1. 桌面与手机正式支持浏览器中的全部主流程通过；主要页面无阻断性布局或键盘问题。
2. 三类计划、打卡、补记、修正、统计以及 Web/API/同账号多浏览器一致性的核心验收通过；iOS 客户端联测不属于 Web 发布门槛。
3. 好友授权、撤销、照片/数值隔离、导出和账号删除完成权限验收。
4. 断网和服务异常不造成假成功、重复记录或静默数据覆盖。
5. 真实短信、云端持久化、HTTPS 和会话失效流程在拟发布环境完成验证。

### 7.4 重点风险

**浏览器后台提醒差异。** 浏览器与操作系统可能限制推送、权限请求和后台执行。产品必须展示真实权限状态，不能承诺关闭页面后一定送达；手机端安装入口仅作为获取特定平台后台提醒的可选引导。

**网络中断与重复提交。** Web 不提供离线写入，网络异常可能使用户不确定是否成功。页面应通过查询权威结果和幂等操作恢复，而非让用户猜测或重复生成记录。

**共享设备上的私人数据。** 用户可能在公共电脑登录；退出和会话失效时应清除当前页面的私人展示，防止浏览器返回、前进或多标签页继续显示敏感内容。

**跨端统计漂移。** Web 与 iOS 共享同一计划规则、业务日期和权威数据。Web 发布前用共享 API 与同账号多浏览器验证规则修改、补记、周边界和时区变化；iOS 客户端联测在其独立验收中完成。

**分享历史备注。** 授权会开放既有文字备注，可能包含用户忘记的私人内容。分享前提示、预览及随时撤销是必需流程。

### 7.5 产品模型总结

```text
同一用户与云端计划
        ↓
Web / iOS 根据相同规则展示今日事项
        ↓
用户主动申报成功、失败或跳过
        ↓
服务端保存唯一有效记录
        ↓
今日、日历、统计及授权好友视图一致更新
```

Web V1 的核心判断是：**完整承载既有业务、适配桌面与手机、共用账号和数据；断网不可使用，浏览器关闭后的提醒不作为发布门槛。**
