# 计划打卡 iOS 产品需求文档

> 产品名称：计划打卡
> 平台：iOS
> 版本：V1.1
> 文档范围：首版完整需求
> 核心场景：计划创建 → 今日执行 → 打卡记录 → 日历回顾 → 好友监督

**阅读框架**：

1. 产品背景与定位：为什么做、为谁做、首版目标是什么。
2. 计划设计与管理：计划如何定义、何时生效、怎样调整。
3. 打卡与统计规则：用户如何记录，系统如何解释结果。
4. 页面与信息组织：用户在哪里执行、查看和回顾。
5. 好友、提醒与数据：监督、通知和同步如何工作。
6. 跨模块规则与质量要求：各页面如何保持一致。
7. 衡量、验收与风险：怎样判断首版完成。

## 1. 产品背景与定位

### 1.1 产品背景

用户想长期坚持一件事情时，通常会建立某种计划，但实际计划并不都是传统的“待办事项”。

常见情况包括：

| 场景             | 示例                     | 核心特点                       |
| ---------------- | ------------------------ | ------------------------------ |
| 固定日期执行     | 每天阅读、每周二四学英语 | 指定日期需要执行               |
| 每周达到一定频次 | 每周运动 3 天            | 日期不固定，只要求周内完成次数 |
| 一次性任务       | 9 月 30 日前提交报名材料 | 只需要完成一次，并存在截止日期 |
| 克制某种行为     | 每天不吸烟、不喝奶茶     | 成功代表某行为没有发生         |

传统 Todo List 很难同时处理这些场景。

例如：

```
每天阅读
→ 不应该每天重新创建一个 Todo

每周运动 3 天
→ 周二没运动不能直接判定失败
→ 只需要判断这一周最终是否达到 3 天

每天不吸烟
→ 用户没有打开 App ≠ 当天成功

截止日前提交材料
→ 截止日未完成后不能直接从列表消失
→ 应继续显示“逾期”
```

因此，本产品不是单纯记录“任务是否勾选”，而是：

```
定义计划
   ↓
确定执行规则
   ↓
产生应处理事项
   ↓
用户主动申报结果
   ↓
记录历史状态
   ↓
通过日历和统计回顾
```

### 1.2 产品定位

“计划打卡”是一款面向个人的计划执行与记录工具。

产品核心不是社交，也不是任务管理，而是帮助用户回答三个问题：

```
今天需要做什么？
        ↓
今天实际做得怎么样？
        ↓
过去一段时间坚持得怎么样？
```

其中：

- **今日**负责执行。
- **日历**负责按时间回顾。
- **计划详情**负责查看单个计划的长期情况。
- **朋友**负责有限范围内的监督和鼓励。

好友功能属于辅助能力，不改变计划本身的执行和判定逻辑。

### 1.3 目标用户

首版主要面向：

- 使用 iPhone 的个人用户；
- 希望建立习惯或维持某种行为频率；
- 需要管理有期限的个人事项；
- 希望减少某些行为；
- 希望获得朋友监督，但又希望保留私人记录。

### 1.4 产品目标

首版需要完成以下闭环：

```
创建计划
   ↓
每天查看待处理事项
   ↓
记录成功 / 失败 / 跳过
   ↓
查看历史与统计
   ↓
根据结果继续执行
```

具体目标：

| 目标             | 要求                                     |
| ---------------- | ---------------------------------------- |
| 多种计划统一管理 | 支持固定日期循环、每周 N 天和一次性任务  |
| 用户拥有解释权   | 系统不能把“没记录”自动判定为失败或成功   |
| 历史可回顾       | 可以知道某一天、某一周发生了什么         |
| 可有限分享       | 可以只分享指定计划，而不是整个账号       |
| 数据可靠         | 换设备、离线和重新同步后不能产生重复记录 |

### 1.5 首版范围

首版包括：

- 账号体系；
- 计划创建与管理；
- 打卡；
- 今日页；
- 全局日历；
- 单计划日历；
- 计划统计；
- 分组；
- 提醒；
- 补记与修改；
- 好友关系；
- 计划分享；
- 鼓励互动；
- 离线记录；
- 云端同步；
- 数据导出；
- 账号删除。

### 1.6 核心业务模型

产品中的核心对象及其关系如下：

```
用户 User
 │
 ├── 计划 Plan
 │      │
 │      ├── 执行规则 Schedule
 │      │
 │      └── 打卡记录 Check-in
 │
 └── 好友 Friend
        │
        └── 计划分享 Permission
```

其中最重要的是：

```
Plan
= 我要坚持什么

Schedule
= 哪些日期需要执行 / 怎样算达标

Check-in
= 某一次实际执行结果
```

计划规则只负责定义“什么时候应该执行”。

打卡记录负责回答“用户实际上做得怎么样”。

两者必须分开。

## 2. 计划设计与管理

### 2.1 时间规则与计划类型

#### 时间规则归类

首版保留三类时间规则：

| 一级类型      | 用户设置方式                     | 示例                   |
| ------------- | -------------------------------- | ---------------------- |
| 固定日期循环  | 选择周一～周日中的一个或多个日期 | 每天阅读、每周二四英语 |
| 每周目标 N 天 | 设置一周至少完成 N 天            | 每周运动 3 天          |
| 一次性任务    | 设置截止日期                     | 9 月 30 日前提交材料   |

#### 固定日期循环

用户选择：

```
执行日期

[一] [二] [三] [四] [五] [六] [日]
```

至少选择一天。

例如：

```
每周二、周四学英语

周一  -
周二  ✓
周三  -
周四  ✓
周五  -
周六  -
周日  -
```

只有周二、周四产生应打卡事项。

其他日期没有：

- 待打卡；
- 失败；
- 未记录；
- 跳过。

非选中日不开放该计划的打卡或补记入口，不能主动记录成功、失败或跳过。若希望自由选择执行日期，应使用“每周目标 N 天”。

如果选择：

```
固定日期循环
+
周一 ✓
周二 ✓
周三 ✓
周四 ✓
周五 ✓
周六 ✓
周日 ✓
```

则表示：

> 每日执行。

因此产品中可以提供“每日”的快捷选择，但底层业务规则与固定日期完全一致。因此后续所有规则可以统一描述为：

> 固定日期循环计划。

#### 每周目标 N 天

用户只指定：

```
每周完成 N 天
```

其中：

```
1 ≤ N ≤ 7
```

例如：

```
每周运动 3 天
```

用户可以选择：

```
周一 ✓
周三 ✓
周五 ✓
```

也可以：

```
周二 ✓
周六 ✓
周日 ✓
```

系统不要求用户提前决定具体日期。

因此：

```
周二没运动
≠
周二失败
```

只有当一周结束后：

```
成功天数 < N
```

才判断：

```
本周未达标
```

#### 一次性任务

一次性任务只执行一次。

例如：

```
9 月 30 日前提交报名材料
```

状态变化：

```
创建
 ↓
待完成
 ↓
截止日前完成 ──→ 按时完成

截止日期结束
 ↓
逾期
 ↓
之后完成 ─────→ 迟完成
```

也允许用户主动：

```
失败
取消
```

一次性任务只支持“要做”。

如果用户想表达：

```
9 月 30 日前每天不喝奶茶
```

应该建立：

```
固定日期循环
+
周一～周日全部选择
+
结束日期 = 9 月 30 日
+
计划方向 = 不要做
```

### 2.2 计划方向

时间规则回答：

> 什么时候执行？

计划方向回答：

> 什么情况代表成功？

计划方向分为两种：

| 方向   | 示例               | 成功含义               |
| ------ | ------------------ | ---------------------- |
| 要做   | 阅读、运动、背单词 | 用户完成了该行为       |
| 不要做 | 不吸烟、不熬夜     | 该考核日没有发生该行为 |

#### “要做”计划

例如：

```
计划：阅读
```

打卡：

```
✓ 今天完成了
✕ 今天没有完成
— 今天跳过
```

#### “不要做”计划

例如：

```
计划：不吸烟
```

打卡文案应变为：

```
✓ 今天做到了，没有吸烟
✕ 今天发生了吸烟
— 今天跳过
```

不能出现：

```
“已完成吸烟”
```

这种容易产生相反含义的表达。

#### 不允许自动判定成功

例如用户建立：

```
每天不吸烟
```

当天没有打开 App。

第二天：

```
昨天 = 未记录
```

而不是：

```
昨天 = 成功
```

用户必须主动确认：

```
今天没有吸烟
```

才能形成成功记录。

用户可以在当天尚未结束时主动确认成功。若之后发生了原本要克制的行为，用户须把当天记录修正为失败；系统保留“已修正”标记，已分享计划的好友也能看到该标记。

### 2.3 创建计划

#### 创建计划字段

| 字段       | 必填     | 适用范围  | 说明                          |
| ---------- | -------- | --------- | ----------------------------- |
| 计划名称   | 是       | 全部      | 如“阅读”“不吸烟”              |
| 计划方向   | 是       | 全部      | 要做 / 不要做                 |
| 时间规则   | 是       | 全部      | 固定日期 / 每周 N 天 / 一次性 |
| 开始日期   | 是       | 循环计划  | 计划从什么时候生效            |
| 固定星期   | 条件必填 | 固定日期  | 至少选择一天                  |
| 每周目标 N | 条件必填 | 每周 N 天 | 1～7                          |
| 截止日期   | 条件必填 | 一次性    | 任务最后期限                  |
| 结束日期   | 否       | 循环计划  | 不设置则持续执行              |
| 分组       | 否       | 全部      | 默认未分组                    |
| 说明       | 否       | 全部      | 对计划进行补充                |
| 提醒       | 否       | 全部      | 设置提醒规则                  |
| 数值字段   | 否       | 全部      | 如公里、页数、分钟；仅供回顾，不自动判定结果 |

#### 创建流程

```
填写计划名称
      ↓
选择“要做 / 不要做”
      ↓
选择执行方式
      │
      ├── 固定日期
      │      ↓
      │   选择星期
      │
      ├── 每周 N 天
      │      ↓
      │   设置 N
      │
      └── 一次性
             ↓
          设置截止日期
      ↓
设置开始 / 结束日期
      ↓
可选：分组 / 提醒 / 数值字段 / 说明
      ↓
保存计划
      ↓
按开始日期生效；一次性任务保存后进入待完成
```

创建计划不要求：

- 先创建分组；
- 添加好友；
- 设置照片；
- 设置数值；
- 分享计划。

### 2.4 日期与时间边界

#### 日期范围

开始日期和结束日期均包含在计划有效期中。

例如：

```
开始：9 月 1 日
结束：9 月 30 日
```

有效范围：

```
9 月 1 日 ～ 9 月 30 日
```

#### 周定义

统一采用：

```
周一 → 周日
```

作为一个自然周。

#### 时区

计划创建时需要确定计划所属时区。

一天按照：

```
计划所属时区的 00:00 ～ 23:59
```

划分。

用户旅行或切换设备时区后：

- 已产生的历史记录不重新归属日期；
- 历史统计不重新计算；
- 避免同一条历史记录因为时区变化移动到前一天或后一天。

### 2.5 计划生命周期

循环计划存在：

```
运行中
暂停
归档
删除
```

#### 运行中

正常产生新的应打卡日期。

#### 暂停

暂停后：

```
不产生新的应打卡项
不发送该计划提醒
保留历史记录
```

恢复之后继续按照计划规则运行。

#### 周中暂停

如果“每周运动 3 天”：

```
周一开始运行
周三暂停
```

当前周无法公平计算完整周目标。

因此该周标记：

```
部分周
```

处理规则：

- 已经产生的记录保留；
- 不计算该周达标率；
- 不参与连续达标周统计；
- 下一完整周重新考核。

周中恢复同理。若每周目标 N 天计划在周中开始或结束，该首周或末周也标为“部分周”：保留已有打卡，但不计入周达标率和连续达标周数。

#### 归档

归档代表：

```
计划结束执行
+
历史继续保留
```

归档之后：

- 不产生新任务；
- 不发送提醒；
- 可以继续查看计划详情；
- 可以查看历史记录。

#### 删除

删除属于不可恢复操作。

删除前必须提示：

```
删除计划将同时删除：

- 历史打卡
- 照片
- 数值记录
- 分享权限
```

同时向用户提供：

```
归档计划
```

作为保留历史的替代方案。

### 2.6 计划规则修改

#### 可以直接修改的内容

以下内容可以修改：

- 名称；
- 分组；
- 提醒；
- 说明。

这些修改不会改变历史统计。

#### 修改时间规则

例如：

```
原计划：
每周二、四运动

修改为：
每周二、四、六运动
```

新规则：

```
次日开始生效
```

历史数据：

```
继续按照当时的旧规则计算
```

不能因为今天修改计划，就重新判断过去的记录。

#### 周中修改每周目标

例如：

```
原目标：每周运动 3 天

周三修改：
每周运动 4 天
```

当前周：

```
标记为“部分周”
```

已经存在的记录保留，但：

```
不参与周达标率
```

下一完整周：

```
按照 4 天进行统计
```

## 3. 打卡与统计规则

### 3.1 打卡记录模型

#### 一次打卡包含的内容

每条打卡记录包括：

| 字段         | 是否必须 |
| ------------ | -------- |
| 结果         | 是       |
| 对应日期     | 是       |
| 实际提交时间 | 是       |
| 文字备注     | 否       |
| 照片         | 否       |
| 数值         | 否       |
| 是否补记     | 系统生成 |
| 是否修改     | 系统生成 |

其中最核心的是：

```
结果
```

结果必须由用户主动选择。

#### 打卡操作

```
进入计划
   ↓
选择结果
   │
   ├── 成功
   ├── 失败
   └── 跳过
   ↓
可选填写
   │
   ├── 文字
   ├── 照片
   └── 数值
   ↓
提交
```

用户不填写任何附加信息，也能完成打卡。

#### 同一天只能存在一条有效记录

对于同一计划：

```
一个自然日
=
最多一条有效打卡记录
```

例如今天已经打卡成功，再次进入：

```
不是新增第二条
```

而是进入：

```
修改当前记录
```

因此不能出现：

```
周一跑步三次
→ 本周成功天数 +3
```

而只能：

```
周一
→ 成功 1 天
```

### 3.2 打卡状态

循环类计划需要明确区分五种界面状态。

| 状态   | 产生条件                     | 是否用户主动产生 |
| ------ | ---------------------------- | ---------------- |
| 待处理 | 当前应执行日期尚未提交结果   | 否               |
| 成功   | 用户明确表示做到             | 是               |
| 失败   | 用户明确表示没有做到         | 是               |
| 跳过   | 用户主动决定本次不参与       | 是               |
| 未记录 | 应执行日期已经结束仍没有操作 | 否               |

其中最重要的是：

```
失败 ≠ 未记录
```

#### 成功

用户主动确认完成。

计入：

```
成功次数
```

#### 失败

用户明确确认没有完成。

例如：

```
今天没有运动
```

或者对于“不要做”计划：

```
今天吸烟了
```

这是明确结果。

#### 跳过

用户主动表示：

```
今天不参与考核
```

例如：

```
生病，今天跳过跑步
```

跳过不是失败，也不是忘记记录。

#### 未记录

如果：

```
今天本来应该打卡
+
自然日已经结束
+
用户没有提交任何结果
```

系统生成：

```
未记录
```

这是未知状态。

不能自动转换为：

```
失败
```

也不能转换为：

```
成功
```

#### 待处理

如果今天还没有结束：

```
今天应该打卡
+
尚未操作
```

显示：

```
待处理
```

不能提前显示：

```
未记录
```

### 3.3 不同计划的结果判定

#### 固定日期循环

例如：

```
每周二、四运动
```

则：

| 日期 | 是否需要记录 |
| ---- | ------------ |
| 周一 | 否           |
| 周二 | 是           |
| 周三 | 否           |
| 周四 | 是           |
| 周五 | 否           |
| 周六 | 否           |
| 周日 | 否           |

只有周二、周四才可能产生：

```
待处理
成功
失败
跳过
未记录
```

**每日（固定日期七天全选）的示例**

每日只是：

```
固定日期循环
+
七天全部选中
```

因此每天都属于应打卡日期。

例如：

```
周一没打开 App
```

周二查看：

```
周一 = 未记录
```

#### 每周目标 N 天

例如：

```
每周运动 3 天
```

单日只存在：

```
今天是否选择运动并记录
```

没有：

```
今天必须运动
```

因此：

```
周一空白
周二空白
周三成功
```

周一和周二不能被标记为：

```
未记录
```

用户可以主动把某一天记为失败或跳过，供自己回顾；这两种记录都不减少本周目标 N，也不会使其他空白日变成未记录。

只有本周整体：

```
成功 2 天 / 目标 3 天
```

最终在周结束后得到：

```
本周未达标
```

#### 每周提前达标

例如：

```
目标 = 3 天

周一成功
周二成功
周三成功
```

此时：

```
本周已经达标
```

系统：

- 停止本周催促；
- 保留计划进度展示；
- 用户仍然可以继续记录。

例如周五再次运动：

```
4 天 / 目标 3 天
```

可以展示实际数量。

但是：

```
周达标率最高 = 100%
```

#### 一次性任务

一次性任务拥有独立状态：

```
待完成
   ↓
按时完成

待完成
   ↓
逾期
   ↓
迟完成

待完成 / 逾期
   ↓
失败

待完成 / 逾期
   ↓
取消
```

标记失败后，一次性任务进入终态，不能继续在同一任务上提交完成。误操作可修正原记录；如果确实要重新尝试，应新建任务。

一次性任务：

- 不使用“每日完成率”；
- 不参与连续打卡；
- 不产生每天的未记录状态。

### 3.4 补记与修正

#### 补记

用户可以为：

```
过去
+
计划已经生效
```

的日期补充记录。

不能：

```
提前为未来日期打卡
```

系统需要同时保存：

```
记录日期：9 月 20 日
提交时间：9 月 22 日 10:30
```

并显示：

```
补记
```

#### 修改

已经存在的记录允许修改：

```
成功 → 失败
失败 → 成功
修改备注
修改照片
修改数值
```

修改后显示：

```
已修正
最近修改时间
```

历史标签不能因为修改而消失。

#### 分享后的修改

如果某计划已经分享给好友：

好友也需要看到：

```
补记
已修正
```

避免用户后来修改历史后，让好友误以为这些记录从一开始就是当前状态。

### 3.5 统计与连续记录

#### 固定日期循环完成率

包括每日计划。

公式：

```
完成率
=
成功次数
────────────
应打卡次数 - 跳过次数
```

其中：

| 状态   | 分子 | 分母 |
| ------ | ---- | ---- |
| 成功   | +1   | +1   |
| 失败   | 0    | +1   |
| 未记录 | 0    | +1   |
| 跳过   | 0    | 0    |

例如：

```
7 个应打卡日

成功 4
失败 1
未记录 1
跳过 1
```

完成率：

```
4 / (7 - 1)
=
4 / 6
```

#### 每周 N 天计划

不使用每日完成率。

核心展示：

```
本周成功天数 / 目标 N
```

例如：

```
2 / 3
```

周结束：

```
成功天数 ≥ N
→ 本周达标

成功天数 < N
→ 本周未达标
```

#### 连续记录

固定日期循环：

```
连续的“应打卡日期”成功
```

如果为每日：

```
就是连续自然日
```

如果为每周二、四：

```
周二成功
→ 周四成功
→ 下周二成功
=
连续成功 3 次
```

不应该显示：

```
连续 7 天
```

#### 每周 N 天连续记录

使用：

```
连续达标周数
```

例如：

```
第 1 周 达标
第 2 周 达标
第 3 周 达标
```

显示：

```
连续达标 3 周
```

## 4. 页面与信息组织

### 4.1 信息架构

底部导航包含四个一级入口：

```
今日
日历
计划
朋友
```

另外通过个人入口进入：

```
个人资料
通知设置
隐私设置
账号设置
数据导出
账号删除
```

四个主要页面职责必须明确：

| 页面     | 回答的问题               |
| -------- | ------------------------ |
| 今日     | 今天有什么需要处理？     |
| 日历     | 某一天整体发生了什么？   |
| 计划     | 我有哪些计划？           |
| 计划详情 | 这一项计划坚持得怎么样？ |
| 朋友     | 谁可以查看我的哪些计划？ |

### 4.2 今日页

#### 页面目标

今日页是 App 默认核心入口。

用户打开 App 后首先应该知道：

```
今天需要处理什么？
```

#### 不同计划的展示逻辑

| 计划类型     | 今日页展示                   |
| ------------ | ---------------------------- |
| 固定日期循环 | 今天属于选中日期时显示       |
| 每周 N 天    | 显示本周进度，并允许今天打卡 |
| 一次性       | 展示截止日期和当前状态       |
| 逾期一次性   | 持续展示，直到产生终态       |

#### 固定日期计划

例如：

```
每周二、四学英语
```

周一：

```
今日页不作为待处理事项出现
```

周二：

```
今天待处理
英语练习
```

#### 每周 N 天计划

例如：

```
每周跑步 3 天

当前：
2 / 3
```

今日页展示：

```
跑步

本周 2 / 3
还差 1 天
```

用户今天可以直接打卡。

达到目标后：

```
本周 3 / 3
已达标
```

仍可查看，但不再作为欠账催促。

#### 一次性计划

例如：

```
9 月 30 日前提交报名材料
```

9 月 20 日可以显示：

```
提交报名材料
截止 9 月 30 日
```

但不能表现成：

```
“今天必须完成”
```

因为它是截止日前完成一次，而不是每日任务。

截止后仍未完成：

```
已逾期 2 天
```

并持续保留。

#### 打卡后不能从今日页立即消失

例如用户点击：

```
阅读 → 成功
```

卡片继续存在，并显示：

```
✓ 今日成功
```

避免用户因为项目突然消失，而怀疑提交是否成功。

### 4.3 全局日历

#### 页面目标

全局日历回答：

> 某一天，我整体做得怎么样？

日期可以汇总：

```
成功 3
失败 1
跳过 1
未记录 2
```

不能只依赖颜色表达结果。

必须同时使用：

- 图形；
- 状态标识；
- VoiceOver 可读文本。

#### 日期详情

用户点击：

```
9 月 20 日
```

展示当天：

```
阅读        成功
不吸烟      失败
学英语      未记录
跑步        成功
```

用户可以进一步查看记录详情。

#### 每周 N 天特殊处理

例如：

```
每周跑步 3 天
```

周二没有跑步。

日历不能显示：

```
周二：未记录
```

因为周二本来就不是必须执行日期。

日历只显示：

```
有实际打卡的日期
+
整周最终达标结果
```

例如：

```
第 39 周

运动
2 / 3
本周未达标
```

#### 日历筛选

支持：

- 月份切换；
- 按分组筛选；
- 查看当天详情；
- 进入单计划详情；
- 对过去日期进行补记。

### 4.4 计划详情

计划详情负责回答：

> 这一项计划长期执行得怎么样？

页面建议划分为：

```
计划基本信息
      ↓
当前进度
      ↓
统计信息
      ↓
计划日历
      ↓
历史记录
      ↓
计划设置
```

基本信息包括：

- 计划名称；
- 要做 / 不要做；
- 时间规则；
- 开始日期；
- 结束日期；
- 当前运行状态。

#### 固定日期计划

重点展示：

```
本周期执行结果
完成率
连续成功次数
历史日历
```

#### 每周 N 天

重点展示：

```
本周 2 / 3
本周是否达标
历史达标周
连续达标周数
```

#### 一次性任务

重点展示：

```
截止日期
当前状态
是否逾期
最终完成日期
```

不展示：

```
连续打卡
每日完成率
```

### 4.5 分组

分组只用于整理计划。

例如：

```
健康
学习
生活
```

规则：

- 一个计划最多属于一个分组；
- 允许未分组；
- 可以创建分组；
- 可以重命名；
- 可以删除；
- 可以移动计划。

删除分组：

```
删除“学习”
      ↓
其中计划
      ↓
移动到“未分组”
```

不能连同计划历史一起删除。

## 5. 好友、提醒与数据

### 5.1 好友关系

#### 好友关系建立

每个用户拥有唯一用户名。

其他用户可以搜索：

```
用户名
```

搜索结果只展示：

- 用户名；
- 昵称；
- 可选头像。

流程：

```
A 搜索 B
   ↓
发送好友请求
   ↓
B 同意
   ↓
建立好友关系
```

好友关系本身：

```
不开放任何计划
```

### 5.2 计划分享

分享权限必须绑定到：

```
具体计划
+
具体好友
```

而不是：

```
好友 = 可以看到全部计划
```

例如：

```
A 有：

阅读
跑步
不吸烟

A 只把“跑步”分享给 B
```

则 B：

```
✓ 跑步
✕ 阅读
✕ 不吸烟
```

#### 分享前提示

由于分享包含历史记录，因此确认前必须明确告诉用户：

> 对方将能查看该计划已有的全部打卡状态和文字备注，包括历史失败原因。

同时应允许用户预览朋友将看到的内容。

#### 分享内容范围

| 内容         | 好友是否可见 |
| ------------ | ------------ |
| 计划名称     | 是           |
| 时间规则     | 是           |
| 当前进度     | 是           |
| 历史状态     | 是           |
| 文字备注     | 是           |
| 补记标记     | 是           |
| 修改标记     | 是           |
| 照片         | 否           |
| 数值记录     | 否           |
| 其他计划     | 否           |
| 用户个人统计 | 否           |
| 其他分组     | 否           |

### 5.3 好友互动

好友可以：

```
查看被分享计划
发送 Emoji 回应
发送简短鼓励留言
```

好友不能：

```
替用户打卡
修改用户记录
判断记录真假
查看私人照片
查看私人数字
```

#### 留言隐私

如果：

```
A 分享跑步计划给 B、C
```

B 给 A 留言：

```
“这周继续加油！”
```

则：

```
A 可以看
B 可以看
C 不可以看
```

因此它不是公开评论区。

### 5.4 撤销分享与屏蔽

计划拥有者可以随时：

```
撤销某项计划授权
```

撤销后：

```
好友立即失去：
- 当前数据访问
- 历史数据访问
- 留言权限
```

如果：

```
删除好友
或
屏蔽用户
```

同样立即取消相关计划访问权限。

已经收到的历史鼓励：

```
计划拥有者仍可查看
```

### 5.5 提醒系统

提醒与计划规则对应。

| 计划         | 提醒规则                     |
| ------------ | ---------------------------- |
| 固定日期循环（含每日） | 仅在选中的星期提醒；全选即每天提醒 |
| 每周 N 天    | 用户选择提醒星期；达标后停止 |
| 一次性       | 按截止日前提醒规则发送       |

#### 不应继续提醒的情况

以下情况下停止不适用提醒：

```
当天已经打卡
计划暂停
计划归档
每周目标已经达标
一次性任务已经结束
```

#### 系统通知权限

首次需要发送通知时：

```
请求 iOS 通知权限
```

如果用户关闭权限：

App 设置页应明确显示：

```
通知权限已关闭
```

并提供：

```
前往系统设置
```

入口。

#### 社交通知

以下通知独立控制：

- 好友申请；
- 计划分享；
- 鼓励留言。

不能和：

```
计划打卡提醒
```

共用一个总开关。

### 5.6 离线与云同步

#### 离线能力

没有网络时仍允许：

```
查看已经缓存的个人数据
提交打卡
修改记录
```

提交之后显示：

```
已保存到本机
```

#### 同步状态

记录需要存在明确状态：

```
已保存到本机
      ↓
同步中
      ↓
已同步
```

异常时：

```
同步失败
```

并提供重试。

#### 防止重复记录

例如：

```
离线提交一次
↓
恢复网络
↓
自动重试 3 次
```

最终仍只能产生：

```
1 条打卡记录
```

不能产生：

```
3 条重复记录
```

#### 多设备冲突

例如：

```
iPhone A：
阅读 → 成功

iPhone B：
阅读 → 失败
```

如果两个设备同时修改同一条记录：

系统不能静默覆盖。

需要：

```
识别冲突
↓
明确提示
↓
说明最终保留版本
```

### 5.7 账号与个人数据

用户可以：

- 登录；
- 退出；
- 更换设备恢复数据；
- 导出个人数据；
- 删除账号。

云端同步范围包括：

```
计划
分组
打卡
好友
分享关系
```

删除账号前需说明：

- 云端计划如何处理；
- 打卡历史如何处理；
- 分享给朋友的数据如何失效。

### 5.8 照片与权限

照片属于：

```
私人附加数据
```

即使计划已经分享：

```
照片仍只有本人可见
```

上传照片时按 iOS 权限机制单独申请相册或相机权限。

权限之间必须隔离：

```
同意好友请求
≠
开放照片

分享计划
≠
开放全部个人数据
```

## 6. 跨模块规则与质量要求

### 6.1 核心页面关系

整个产品的主要使用链路为：

```
                ┌──────────┐
                │ 创建计划 │
                └────┬─────┘
                     ↓
                ┌──────────┐
                │  今日页  │
                └────┬─────┘
                     ↓
                  用户打卡
                     ↓
          ┌──────────┴──────────┐
          ↓                     ↓
     全局日历               计划详情
   按日期看记录             按计划看记录
          │                     │
          └──────────┬──────────┘
                     ↓
                 历史回顾
                     │
                     ↓
               继续执行计划
```

社交链路独立存在：

```
建立好友
   ↓
选择具体计划
   ↓
授权好友
   ↓
好友查看进度
   ↓
鼓励 / 回应
```

好友不能介入：

```
打卡判定
统计计算
历史修改
```

### 6.2 核心业务规则总表

| 编号 | 规则                                  |
| ---- | ------------------------------------- |
| R01  | 每日属于固定日期循环的七天全选状态    |
| R02  | 固定日期循环至少选择一个星期          |
| R03  | 每周 N 天的 N 范围为 1～7             |
| R04  | 每周 N 天没有“某个空白日未记录”的概念 |
| R05  | 一次性任务仅支持“要做”                |
| R06  | 用户未操作不能自动判定成功            |
| R07  | 用户未操作不能自动判定失败            |
| R08  | 成功、失败、跳过、未记录必须严格区分  |
| R09  | 每个计划每天最多一条有效打卡          |
| R10  | 补记必须保存记录日期和实际提交时间    |
| R11  | 修改历史记录必须保留“已修正”标记      |
| R12  | 固定计划修改时间规则后不追溯修改历史  |
| R13  | 周中修改周目标，该周作为部分周        |
| R14  | 每周 N 天达到目标后允许继续记录       |
| R15  | 单周达标率最多 100%                   |
| R16  | 一次性任务逾期后继续显示              |
| R17  | 一次性任务完成后区分按时完成和迟完成  |
| R18  | 好友关系不等于计划授权                |
| R19  | 分享按“计划 × 好友”授权               |
| R20  | 分享计划时照片和数值始终保持私密      |
| R21  | 离线重试不能产生重复记录              |
| R22  | 历史日期不能因设备时区改变而重新归属  |

### 6.3 交互与可用性要求

#### 降低理解成本

创建计划时重点解释：

```
固定日期
vs
每周 N 天
```

例如：

```
固定日期：
“每周二、周四”

每周 N 天：
“一周完成任意 3 天”
```

这是用户最容易混淆的两个规则。

#### 降低打卡成本

最常用流程：

```
打开 App
↓
进入今日
↓
点击结果
↓
提交
```

不能强制用户填写：

- 照片；
- 备注；
- 数值。

#### 状态必须清晰

尤其需要视觉区分：

```
失败
vs
未记录
```

以及：

```
跳过
vs
未记录
```

不能只通过颜色表达。

#### iOS 可访问性

首版支持：

- Dynamic Type；
- VoiceOver；
- 深色模式；
- 足够大的点击区域；
- 日历状态提供非颜色信息。

### 6.4 可靠性要求

以下数据在：

```
今日页
日历
计划详情
朋友视图
统计
```

必须来自同一套业务状态。

例如用户把：

```
9 月 20 日 阅读
失败
```

修改为：

```
成功
```

则：

```
今日/历史状态
日历
完成率
连续记录
朋友视图
```

都必须同步变化。

不能出现某个页面成功、另一个页面仍然失败。

## 7. 衡量、验收与风险

### 7.1 产品指标

首版上线后重点统计：

| 指标           | 目的                   |
| -------------- | ---------------------- |
| 计划创建完成率 | 用户是否能顺利建立计划 |
| 首周打卡率     | 创建后是否真正开始使用 |
| 应打卡日记录率 | 用户是否持续记录       |
| 周计划达标率   | 每周 N 天计划使用效果  |
| 日历回访率     | 用户是否进行历史回顾   |
| 计划分享率     | 用户是否使用监督能力   |
| 鼓励互动率     | 分享后是否产生互动     |

首版不预设缺乏数据依据的增长目标。

上线取得真实基线之后，再制定：

```
提升 X%
达到 X%
```

等数值目标。

### 7.2 核心验收场景

#### 固定日期循环（含每日）

**场景 A：每天阅读**

```
Given
用户创建“阅读”
选择固定日期
周一～周日全部选中

When
保存计划

Then
每天今日页产生一次应处理事项
```

如果昨天未操作：

```
昨天 = 未记录
```

**场景 B：每周二、周四英语**

```
Given
用户选择：
周二 ✓
周四 ✓

When
周一打开 App

Then
英语不属于今日待处理
```

周二：

```
英语进入今日待处理
```

#### 每周 N 天

**场景：每周运动 3 天**

```
Given
目标 = 3 天

When
周一成功
周三成功
周三再次提交

Then
成功天数仍然 = 2
```

周日结束：

```
2 / 3
本周未达标
```

如果成功三天：

```
3 / 3
本周达标
停止本周催促
```

第四天仍允许继续记录：

```
4 / 3
```

但：

```
达标率 = 100%
```

#### 一次性计划

```
计划：
9 月 30 日前提交材料
```

9 月 30 日前：

```
待完成
```

9 月 30 日结束：

```
逾期
```

10 月 2 日提交：

```
迟完成
完成日期：10 月 2 日
```

不能显示：

```
按时完成
```

#### 不要做计划

```
计划：
每天不吸烟
```

当天未打开 App：

```
未记录
```

用户主动确认：

```
今天没有吸烟
→ 成功
```

用户主动确认：

```
今天吸烟了
→ 失败
```

#### 跳过

固定日期计划：

```
今天属于应打卡日
```

用户主动选择跳过：

```
状态 = 跳过
```

统计时：

```
不进入完成率分母
```

但：

```
连续成功中断
```

#### 补记

```
今天 = 9 月 22 日
```

用户进入 9 月 20 日：

```
补记成功
```

系统保存：

```
记录日期：9 月 20 日
提交时间：9 月 22 日
状态：补记
```

未来日期不能提前打卡。

#### 分享

```
A 添加 B 为好友
```

在 A 尚未分享计划时：

```
B 看不到 A 的任何计划
```

A 分享：

```
跑步
```

B 可以看到：

```
跑步计划
进度
历史状态
文字备注
```

看不到：

```
照片
数值
其他计划
其他个人统计
```

#### 撤销分享

```
A 撤销 B 对跑步计划的访问
```

结果：

```
B 立即无法查看当前数据
B 立即无法查看历史数据
B 无法继续留言
```

#### 离线同步

```
设备断网
↓
用户提交打卡
↓
本机保存
↓
恢复网络
↓
自动同步
```

最终服务器和另一台设备只能看到：

```
1 条记录
```

不能因为重试产生重复数据。

**边界验收补充**

- 固定周二、周四的计划在周三不能打卡或补记；七天全选的同类计划每天可以打卡。
- “不要做”计划当天先确认成功、稍后修正为失败时，最终结果与“已修正”标记在本人及获授权好友视图一致。
- 每周目标 3 天计划记录一天失败或跳过后，目标仍为 3 天；周中开始或结束的首末周标为部分周，不纳入达标统计。
- 一次性任务标记失败后不再接受新的完成打卡；误记可修正，数值记录可填写但不改变手动选择的结果。

### 7.3 重点风险

#### 用户自主申报

本产品记录的是：

```
用户申报结果
```

而不是：

```
平台验证结果
```

因此不能使用：

- 已认证；
- 已核实；
- 经验证完成；

等可能误导用户的表达。

#### 历史备注隐私

分享计划会暴露历史文字备注。

旧备注可能包含用户已经遗忘的私人内容。

因此：

```
分享前提示
+
分享内容预览
+
随时撤销
```

属于核心流程，而非辅助功能。

#### 周规则容易产生统计错误

以下情况组合时需要重点测试：

```
周中修改规则
+
暂停
+
恢复
+
补记
+
跨周
+
月底
+
时区变化
```

因此“部分周”必须作为独立统计状态处理。

#### 照片和同步不能影响基本打卡

基本打卡链路应该始终是：

```
选择结果
↓
提交
```

即使：

- 图片上传失败；
- 网络异常；
- 云同步延迟；

也不能阻断纯结果或文字记录。

### 7.4 产品模型总结

整个产品可以最终收敛为以下模型：

```
计划 Plan
│
├── 方向
│     ├── 要做
│     └── 不要做
│
├── 执行规则
│     │
│     ├── 固定日期循环
│     │      ├── 每周二、四
│     │      └── 每日 = 周一～周日全选
│     │
│     ├── 每周目标 N 天
│     │
│     └── 一次性任务
│
├── 生命周期
│     ├── 运行
│     ├── 暂停
│     ├── 归档
│     └── 删除
│
└── 打卡记录
      ├── 成功
      ├── 失败
      └── 跳过

```

“未记录”由应打卡日期结束后缺少打卡记录派生，不是一条用户提交的打卡记录。

```
建立计划
   ↓
系统根据规则判断今天是否需要关注
   ↓
今日页处理
   ↓
用户主动申报结果
   ↓
形成打卡历史
   ↓
日历 / 计划详情统计
   ↓
可选分享给指定好友
   ↓
持续执行和回顾
```

整个产品最重要的业务边界可以归纳为三句话：

> **时间规则决定“什么时候需要执行”，但不决定执行结果。**

> **执行结果始终由用户主动申报；没有记录就是未知，而不是成功或失败。**

> **每日不是独立计划类型，而是固定日期循环中周一至周日全部选中的特殊情况。**
