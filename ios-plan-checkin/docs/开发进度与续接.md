# 计划打卡 iOS V1：开发进度与续接

## 权威记录

- [构建计划](./构建计划-计划打卡-iOS-v1.md)定义 35 个稳定任务 ID、依赖、退出标准和静态门槛。
- [机器可读台账](./build-progress.json)逐项记录状态、前置、分支、基线提交、任务提交、集成提交和阻断原因。`integrationCommit` 指最后一次完成静态复检的**代码提交**，不随台账文档提交变化。
- 当前项目主检出为 `F:/CX_notes/cx-learn-notes/ios-plan-checkin`，父仓库分支为 `main`。任务项中的 `branch` 保留当时执行任务的历史分支；恢复开发时以台账顶层 `integrationBranch` 和此目录的 Git 状态为准。
- `currentWork` 是唯一当前检查点，记录正在执行的任务、已完成步骤、下一步和环境限制。每次任务切换、重要实现步骤、静态检查结果或中断前更新，并在同一工作树提交。不要仅依赖聊天记录或终端滚动输出。

## 状态含义

| 状态 | 含义 |
| --- | --- |
| `NOT_STARTED` | 尚未领取；依赖是否可用由构建计划和台账共同判断。 |
| `IN_PROGRESS` | 已领取，`currentWork` 指向该任务；代码或分析正在推进。 |
| `STATIC_PASS` | 当前代码提交的必过静态门槛已通过，待审查或集成。 |
| `DONE` | 完成标准已核对、代码已集成且静态复检通过。 |
| `BLOCKED` | 任务仍有未验证的必需条件；`staticPassed: true` 表示源代码检查已通过，`blocker` 写明剩余条件。 |

用户已指定“先完成静态代码，稍后验证”。因此已通过静态门槛、仅因 Docker/iOS 真机环境而标记 `BLOCKED` 的上游任务，可以作为后续**源代码实现**的接口基线；这不等于它们已完成真实环境验证，也不允许把发布候选版或 ATDD 标记通过。此阶段若接口发生改变，更新契约、调用端和对应任务记录，再重跑受影响的静态门槛。

## 每个任务的记录时点

1. **领取前**：读取台账和 `currentWork`，确认 Git `HEAD`、工作树状态、依赖及最高优先级可执行任务；记录任务 `baseCommit`、目标与下一步。
2. **开发中**：在重要边界（数据库/契约/服务端/客户端之一完成、规则决定、受阻）更新 `completedSteps`、`nextSteps` 和受影响文件。中断前必须留下可执行的下一条动作。
3. **静态检查后**：记录命令、退出码、对应提交或工作树状态；失败保持 `IN_PROGRESS`。开发自测和真实环境验证单独记录，不能代替静态门槛或后续 ATDD。
4. **提交后**：记录 `taskCommit`、集成复检对应的 `integratedCommit`、状态和残余阻断。清除旧 `currentWork` 后再领取下一任务。

## 中断后恢复

在项目工作树运行 `pnpm progress:show`，然后运行 `git status --short` 与 `git rev-parse HEAD`。若工作树有未提交改动，先对照 `currentWork.uncommittedChanges` 和 `git diff` 核查来源，保留并继续，不执行 `reset` 或 `clean`。若 `HEAD` 与台账不一致，先检查提交历史，不覆盖已有代码。有 `currentWork` 时读取其第一条下一步；当前源码冻结后 `currentWork` 为 `null`，按 `resumeWhenAvailable.priorityTaskIds` 和各 `blocker` 在环境就绪时逐项补验。完成后运行 `pnpm progress:check`、任务静态门槛和开发自测，再更新台账。

`pnpm progress:check` 校验 35 个任务 ID、唯一性、状态字段、当前任务指向和提交 SHA 格式；`pnpm progress:show` 输出已完成、已静态通过但待环境验证、进行中及未开始数量，并显示下一步。它们只读，不会自动宣称任务完成。

## 当前快照

当前代码集成基线、各任务状态与下一步以机器可读台账为准。若 `currentWork` 为 `null` 且 `nextTaskId` 存在，先核对该任务与依赖；若两者均为空，说明静态源码阶段已走完，读取 `resumeWhenAvailable` 和各任务的 `blocker`。重新补验或修复前建立新检查点。真实环境验证仍以各任务的 `blocker` 字段逐项追踪。
