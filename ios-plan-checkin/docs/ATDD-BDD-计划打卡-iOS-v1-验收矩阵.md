## 1. 验收模型与判定原则

每个用例按 `Given 场景 → When 操作 → Then 功能结果 / Visual 视觉结果 / But 反向结果` 编写。`Given` 必须固定账户、计划类型、计划时区、业务日期、规则版本、生命周期和网络/设备状态；`When` 只描述一个可观察的业务动作或事件；`Then` 与 `But` 必须能用证据判定。共享参数组合使用场景大纲，不把十几个动作塞进一个场景。该结构与 [Cucumber Gherkin 参考](https://cucumber.io/docs/gherkin/reference/) 的 Given/When/Then 语义一致。

**一项通过条件**：功能断言、视觉断言、反向断言全部成立，且必需证据齐全、时间戳/版本/设备元数据可追溯。某个断言“不适用”必须在用例中明确标为 `N/A`，不得以缺证据等同通过。用例可标 `PASS / FAIL / BLOCKED / NOT_RUN`；`BLOCKED` 需说明外部依赖和复测条件。任何越权、数据丢失、重复有效记录或错误统计均为阻断缺陷。

### 1.1 三类结果的含义

| 类型 | 必须回答的问题 | 证据准则 |
| --- | --- | --- |
| 功能断言 `F` | 用户或外部调用者实际得到什么？状态、数值、时间、导航、API 结果是否正确？ | UI 与 API 双侧可观察；关键数据一致性补数据库或同步事件证据 |
| 视觉断言 `V` | 对应设计页面/状态的层级、文案、布局、颜色、间距、控件状态是否一致且可读？ | 同尺寸截图 + iOS 无障碍树 + 设计节点关联 + 差异图；系统区域可受控遮罩 |
| 反向断言 `N` | 什么**不应**发生？如越权可见、重复数据、静默覆盖、错误提醒或错误统计 | 截止时间明确的缺席证据：API 拒绝、记录计数、事件日志、通知队列/本地待发清单；单张截图不足以证明“没有发生” |

### 1.2 iOS 结构证据与视觉阈值

React Native 的 iOS 页面没有浏览器 DOM。本文的 `H` 指 **XCUITest/Appium 可导出的 iOS 无障碍元素树**，其中包含 `testID`/accessibility identifier、label、value、enabled、frame 和可访问顺序；若测试涉及嵌入 WebView，才额外保存该 WebView 的 DOM。开发时为关键按钮、输入、状态标签、弹层和列表项设置稳定 `testID`，不把随机业务 ID 作为唯一定位器。XCTest 可附加截图和文件作为测试证据，参见 [Apple XCTest attachments](https://developer.apple.com/documentation/xctest/activities-and-attachments)。

页面映射画板尺寸为 **393 × 852 Pen 画布单位**，节点树也以画布 px 记录边界。先按实际截图缩放比例映射到 iOS 逻辑 pt，再比较位置与尺寸。在与画板比例匹配的基准设备/系统/字体档位上，视觉硬门槛为：设计文案和组件可见性一致；关键节点映射后的偏差不超过 4 pt；实体色 token、字号、字重与设计 token 一致；无裁切、重叠、溢出、键盘遮挡、异常滚动。截图差异在剔除**明确登记**的动态时间、头像、系统状态栏与键盘区域后，非动态内容面积差异默认不超过 3%；任一关键按钮或状态文案的差异即使总面积低于 3% 也判失败。真机、其他屏宽与动态字体以语义布局约束为硬门槛，不要求与单张画板逐像素相同。基准设备选择 393 × 852 逻辑点的档位并记录型号、iOS 版本与截图分辨率；不得事后为通过测试而随意扩大遮罩或阈值。

**视觉值优先使用已落地的 Pen 节点树及对应 PNG**，UI/UX 文档中的令牌是语义建议，不用它们覆盖设计稿实际值。例如 Pen 变量为背景 `#F8F9F6`、表面 `#FFFFFF`、主行动 `#236B4A`、主文字 `#17231C`、次文字 `#7E8880`；UI/UX 建议值的背景 `#F7F7F4`、主行动 `#236A49` 与之不同。AI 逐屏对图时取 Pen frame/node 的实际填充与字体，检查结果中同时记录差异来源。失败、跳过、未记录、逾期仍按 UI/UX 的**语义**区分，并以实际 Pen 节点值为截图基线。排版遵循 8 pt 基准，主要按钮高度建议 50–56 pt，所有可点击区域至少 44 × 44 pt。状态必须同时用文字、图形和色彩表达。系统辅助功能导致的必要对比度调整可登记为受控例外。

### 1.3 证据代码与文件契约

| 代码 | 文件/内容 | 使用条件 |
| --- | --- | --- |
| `S` | `screen-before.png`、`screen-after.png`、必要时 `sheet.png` | 所有 UI 场景；截图须含完整屏幕与设备元数据 |
| `H` | `hierarchy.json` / `.xml`：原生无障碍树；WebView 才另存 `dom.html` | 所有 UI/可访问性/视觉断言 |
| `V` | `visual-diff.png`、`visual-result.json`：设计页面 ID、Pen 节点 ID、遮罩、阈值、偏差 | 有设计页面或组件对照的 UI 场景 |
| `A` | `api.json`：脱敏请求/响应、HTTP 状态、requestId、时间、幂等键摘要 | 涉及 API、权限、错误码、统计的场景 |
| `D` | `db-assertions.json`：测试库只读查询与预期/实际计数，隐藏手机号/笔记正文 | 唯一性、修订、权限、删除、统计核对 |
| `L` | `client-log.jsonl`、`server-log.jsonl`：结构化事件、同步状态、job/requestId | 离线、重试、并发、通知、异步任务 |
| `N` | `notification-evidence.json`：本地待发 ID、APNs 发送回执、通知中心截图 | 提醒/社交通知；仅截图不证明“未发送” |
| `F` | `artifact-manifest.json`、ZIP 清单、哈希或对象存储清单 | 照片、导出、删除/注销 |
| `T` | `timeline.json`：冻结时钟、网络切换、设备 A/B、操作与服务端时间轴 | 跨日、时区、离线、多设备、30 天注销 |

推荐每次运行保存 `evidence/<runId>/<caseId>/<variant>/`，其中 `result.json` 至少含：`caseId`、`variant`、`sourceRefs`、`build`、`gitCommit`、`environment`、`device`、`osVersion`、`screenScale`、`fontScale`、`planTimezone`、`businessDate`、`fixtureId`、`startedAt`、`endedAt`、三类断言各自的 `expected/actual/status/evidencePaths`、`reviewer`。敏感数据在采集前脱敏，哈希摘要不得反推手机号。证据目录只接受相对路径，文件 SHA-256 写入清单；缺失文件或哈希不符判 `BLOCKED`。

### 1.4 测试前置与数据种子

- 账户：主人 A、好友 B、陌生人 C、被拉黑用户 D、第二设备上的同一账户 A2；每次运行用隔离命名空间重新种子化。
- 固定计划 F：周一/周三/周五；每日计划 FD：周一至周日；每周目标 W：目标 3/周；一次性计划 O：到期日可参数化。为结果/文本/私人照片/数值分别准备可辨识样本。
- 时间由测试时钟控制，明确 `serverNowUtc`、计划 IANA 时区、周一 00:00、日界线前后、DST 切换与真实手机系统时间；不得仅修改客户端显示时间来模拟服务端日期。
- 网络可切断设备 A/B 对 API 与对象存储的访问，记录切换时间；短信与 APNs 在模拟器使用可审计桩，在真机使用受控测试通道。
- 数据库检查仅用测试环境的只读凭证；生产数据、真实手机号和私人照片不得作为固定测试数据。

### 14.3 可执行 Gherkin 转换约定

矩阵中的每个 ID 对应一个 `Scenario` 或一个 `Scenario Outline` 的一组 `Examples`。场景标题必须保留 ID；参数组每个值独立运行并给 `variant`。`Given` 仅准备事实，`When` 是用户动作或受控时间/网络事件，`Then` 验证用户可见结果，`But` 验证禁止发生的结果；数据库断言是补强证据，不代替用户可观察结果。示例：

```gherkin
Feature: 固定日期计划完成率

  @STAT-01 @ios @api @visual
  Scenario: 今日尚未打卡时不提前降低完成率
    Given 计划 F 位于 Asia/Shanghai 且今天是选定应打卡日
    And 过去 4 个应打卡日有 2 次成功、1 次失败、1 次未记录
    When 用户打开固定日期计划详情
    Then 完成率显示 2/4 和 50% 且显示统计截止日期
    And 今日卡片显示待处理
    But 完成率不得按 2/5 计算
```

步骤实现必须绑定 `caseId` 与证据目录；不能仅输出 Cucumber 绿色状态而没有三类断言和证据。不同实现可用 XCTest/Appium/Detox 驱动 UI、HTTP 驱动 API，但同一用例的期望语义不随框架变化。

## 15. AI/人工判定流程与发布门槛

### 15.1 每项用例的执行闭环

1. **冻结来源**：记录 PRD、UI/UX、技术方案、页面映射、视觉树的 SHA-256 与应用构建 commit；若任一文件变化，重新评估受影响用例。
2. **准备 Given**：使用种子 ID、冻结服务端时间、计划时区、设备/网络状态；保存 `fixture.json`。两设备场景分别记录 A1/A2 时钟与网络。
3. **执行 When**：UI 动作由稳定 accessibility identifier 定位，API 动作保存脱敏请求与 requestId；记录起止时间。
4. **判定 Then/Visual/But**：先验证用户可见功能结果，再核对结构与截图，最后用 API/DB/事件日志证明反向断言。缺席断言必须写清观察窗口，例如“撤销提交后 30 秒内所有新读返回拒绝，队列中无新推送”。
5. **存档证据**：按 §1.3 写入统一证据目录、`result.json` 和 SHA-256 清单；格式须通过 [结果 JSON Schema](./atdd/acceptance-result.schema.json)。AI 判定附理由、证据路径与置信度；低置信度/视觉差异争议交人工复核。
6. **复测与回归**：修复后重跑失败项及同域依赖项，保留原证据，不能覆盖失败记录。需求变更必须更新用例、基线、追踪表和源文件版本。

### 15.2 发布门槛

- **范围门槛**：197 个稳定用例 ID 全部有执行记录；`UI-01` 对 32 页逐页展开，所以在额外参数组之前至少有 228 个执行实例。参数组的每个边界值单独判定，不可取平均结果。
- **阻断门槛**：所有权限、照片私有性、数据删除、幂等、冲突、统计口径、计划时区和核心打卡用例必须 `PASS`；任一数据丢失/越权/双记录为阻断。所有其他必测项也需 `PASS`，`BLOCKED/NOT_RUN` 不算通过。
- **视觉门槛**：32 页均有 `S+H+V`，关键状态变体有独立证据；动态字体、深色、VoiceOver、窄屏无阻断问题。截图差异通过但关键文案/按钮缺失仍判失败。
- **真机门槛**：短信自动填充与重发、APNs/本地提醒、相册/相机权限、断网杀进程恢复、系统权限拒绝至少各有受控真机通过记录。系统投递不确定性按 §9 的调度/受理证据判定。
- **证据门槛**：所有 `result.json` 通过 schema 校验，证据文件存在且 SHA-256 匹配，敏感信息脱敏；用例的 `F/V/N` 任一缺项不得通过。

### 15.3 评审者检查清单

开发者或 AI 在给出通过结论前，必须逐项问：

1. Given 是否足以唯一确定计划类型、方向、日期、时区、规则版本、用户关系与网络状态？
2. When 是否真的发生，有动作时间轴或 requestId，而不是只看测试脚本写了什么？
3. 功能 Then 是否既在 UI 可见，又与 API/权威记录一致？
4. 视觉 Then 是否使用正确的页面 key、参考 PNG、节点树和设备档位？遮罩是否事先登记？
5. 反向 But 是否有可证明“未发生”的观察窗口、计数或拒绝响应？
6. 证据是否能由另一个人从相同种子和构建复现？
7. 测试期望是否确实来自当前版本源文档，而不是从现有实现反推并降低标准？
