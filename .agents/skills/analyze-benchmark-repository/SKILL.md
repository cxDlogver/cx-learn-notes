# Benchmark 仓库调研

以仓库、数据文件、实现和一手文献为证据，还原 Benchmark 实际测量机制。重点解释“数据怎样变成任务、评测对象怎样行动、输出怎样被判分”，不要根据名称或排行榜印象下结论。

## 工作流

### 1. 确认范围与产物

1. 解析仓库路径、输出目录和用户要求。
2. 查找适用的 `AGENTS.md`，检查 Git 状态，保留用户已有修改。
3. 默认一个 Benchmark 家族生成一份报告；同一数据集的 split、难度子集和派生子集写入同一报告。只有任务定义、输入输出或评分协议相互独立时才拆成多份。
4. 使用稳定文件名：`<benchmark-name>-调研报告.md`。

### 2. 固定证据快照

记录：

- 仓库绝对路径、远端 URL、当前 Commit、Commit 日期和工作区状态；
- 数据与代码版本、许可证、访问限制、Canary 和禁止泄漏条款；
- 分析日期；
- 本地证据与外部证据的边界。

优先级：本地数据/源码 > 官方论文 > 官方数据卡与项目文档 > 官方模型卡 > 可信第三方。关键结论不得只依赖二手博客。

### 3. 生成结构盘点

运行：

```bash
python3 scripts/inventory_benchmark_repo.py <repo> --output <inventory.md>
```

盘点文件只作为分析证据，不直接当最终报告。检查：

- 数据文件、行列数、字段、缺失、split 和子集关系；
- Notebook 单元与已保存输出；
- Prompt、模型/工具调用、评分方式和结果文件；
- README、论文链接、许可证和归档文件；
- 已提交基线结果的结构。

默认不输出原始题目、答案或长文本样例。遇到 gated 数据或防泄漏声明时，只写结构和统计。

结构盘点用于定位证据，不要在最终报告中逐文件、逐函数介绍代码。只有实现细节会改变模型可见输入、行动空间、反馈、终止、Judge 或指标时，才把它提炼为评测协议的一部分。

### 4. 分析评测所需的数据

按 [classification-guide.md](references/classification-guide.md) 检查：

1. 哪些数据文件可以直接作为评测集合；
2. 每个文件有多少条任务，文件之间是互斥 split、嵌套子集还是不同任务；
3. 一条记录中哪些字段被任务构造器、Agent、环境、Judge 或聚合器实际读取；
4. 评测如何选择、过滤、采样或随机化记录；
5. 逐样本输出如何关联回输入任务并进入最终指标。

使用脚本或数据读取验证数量和关系。不要用 `wc -l` 统计允许多行字段的 CSV。

最终报告的“数据集设计”只允许三个三级标题：

1. `3.1 构建动机`：解释为什么采用这种任务形式、输入形式和标签形式，不讲人员、标注、审核或数据生产流水线；
2. `3.2 数据文件、规模和结构`：只写后续评测需要选择的文件、样本数、文件关系和实际读取字段；
3. `3.3 数据如何被后续评测消费`：从一条记录说明可见输入、隐藏参考、执行输出、Judge 和聚合。

不要介绍数据集的构建过程。不要枚举后续评测不读取的字段；即使仓库中存在解释、标注者反馈、质检记录或分析元数据，也只在内部分析时用于排除它们，不能在报告中展开。

建立评测字段消费链：

```text
评测文件中的一条记录
        │
        ├─ 可见字段 ─→ Prompt / Observation ─→ 模型或 Agent
        └─ 隐藏字段 ─→ 标准答案 / 测试 / 目标状态 ─→ Judge
模型或 Agent 输出 ─────────────────────────────→ Judge ─→ 单题结果 ─→ 聚合指标
```

至少回答：

- 一条原始记录如何变成一个或多个评测任务；
- 哪些被实际读取的字段对模型/Agent 可见，哪些只对环境或 Judge 可见；
- 哪些字段用于初始化环境、工具、隐藏测试或目标状态；
- split、过滤和采样如何决定最终评测集合；
- 逐样本输出如何关联回原始任务并聚合。

必须先用一句直白中文解释首次出现的专业术语，再使用英文名或缩写。例如：先解释“Prompt 是发送给模型的完整输入文本”，再使用 `Prompt`。为每个数据集提供一个不含真实受限样本的简化示例，并用 `text` 代码块展示“原始记录 → 可见输入/隐藏参考 → 输出 → Judge → 分数”。不要用 Mermaid 代替这个示例。

### 5. 还原评测任务与 Agent 流程

从评测语义而不是源码目录出发，追踪完整生命周期：

```text
选择 split → 读取一条样本 → 构造可见输入与隐藏参考
→ 初始化模型/Agent与环境 → 行动/工具/反馈循环 → 终止
→ 解析最终输出 → 单样本判分 → 失败分类 → 跨样本聚合
```

先列出仓库实际支持的评测协议。只有输入、推理次数、工具、状态循环、终止或回退策略完全相同时，才能合并讲解；只要其中一项不同，就要作为独立协议说明。

先提取所有协议真正共用的环节，例如：

- 相同的数据读取与选项随机化；
- 相同的答案解析、Judge 和失败计分；
- 相同的逐题记录与数据集级聚合。

共用环节只讲一次。每一种协议随后分别说明：

- 样本来源和进入评测的筛选条件；
- 模型/Agent 可见输入和评测器隐藏参考；
- 执行主体：裸模型、Agent Scaffold、工具、环境分别承担什么；
- Observation、Decision、Action、Tool Result、State/History 如何流动；
- 行动空间、工具 Schema、轮数/Token/时间/成本预算；
- 正常终止、预算终止、拒答、超时和基础设施错误；
- 最终输出格式、解析规则和单样本结果结构；
- Judge 是 Exact Match、程序测试、状态 Verifier、规则、人工、LLM Judge 还是混合；
- 失败、拒答、解析失败和基础设施错误如何进入分母；
- 跨样本如何按 split、子集、任务类型或重复运行聚合。

每种协议必须提供一个简化示例，优先复用第 3 章的同一条合成任务，以便读者直接比较流程差异。示例至少显示“输入增加了什么、执行了几次、是否调用工具、何时终止、怎样进入共用 Judge”。

第 4 章不要使用 Markdown 表格。按以下方式表达：

1. 线性流程或简单分支使用 `text` 代码块流程图；
2. 有多轮状态、回路和多个分支时才使用 Mermaid；
3. 流程图后使用编号步骤和分点解释，不让流程图独自承担全部信息；
4. 不用“协议对照表”代替逐协议讲解；
5. 专业术语先用直白中文解释，再给英文名或缩写。

不要把“调用了哪些文件和函数”当作评测流程；实现仅作为协议结论的证据。

可以执行无副作用的离线结构检查。不要未经授权调用付费模型、搜索 API、生产工具或外部写操作。

### 6. 判定评测层级

必须分别判定“数据集本体”和“仓库中的每种实验配置”：

- 静态模型能力评测；
- 工具增强模型评测；
- 受限 Agent 组件评测；
- 端到端 Agent 评测；
- Artifact/最终环境状态评测；
- 人类或元评估研究。

存在工具调用不等于端到端 Agent。只有当评测目标覆盖多步自主行动，并通过真实环境、应用状态或完整交付物验证结果时，才判为端到端 Agent。

### 7. 收集论文与官方资料

需要文献时使用互联网检索，并优先：

- 论文正式版本或 arXiv/OpenReview；
- 官方 GitHub；
- 官方数据卡；
- 官方评测框架或模型卡。

核对标题、作者、年份、版本和 URL。将“论文原始设计”“本地仓库实现”“当前常见使用方式”分开陈述。正文相关论断就近引用，文末只列实际使用的资料。

凡是判断“当前是否可用”或“是否有更优公开数据集”，必须查询分析日期附近的官方仓库、官方数据卡或正式论文，不能只依据本地旧仓库。替代基准按评测目标比较，不使用“全面更好”这种无条件结论。

### 8. 写报告

读取并遵循 [report-template.md](references/report-template.md)。报告至少回答：

- 数据是什么；
- 评测实际使用哪些数据文件、规模和字段；
- 每类字段如何被后续评测消费；
- 单条样本如何形成任务、执行、终止和判分；
- 测模型还是测 Agent；
- 测到哪些能力，没测到哪些能力；
- 分数意味着什么；
- 有哪些协议偏差、复现风险和使用边界；
- 对 Agent 评测和产品选型有什么意义；
- 当前数据、官方评测实现和排行榜是否仍可使用；
- 同方向是否存在更合适的公开基准。

最终报告不要设置“代码实验”章节，也不要逐文件介绍实现。所有关键统计写明证据来源；对实现推断使用“实现显示”或“据此推断”，不把推断写成论文事实。

将能力、方法、结果、局限和结论合并为“Agent Benchmark 整体总结”。按读者理解顺序写：

1. Agent Benchmark 的基本运行结构；
2. 判断评测是否可靠的核心标准；
3. Agent 范围、评测方式和评测能力的对应关系；
4. 可比较的标准实验结构；
5. 当前 Benchmark 在上述框架中的位置、可用性和替代项；
6. 当前 Agent Benchmark 的主要局限；
7. 有一手资料支持的发展趋势；
8. 继续使用、作为分项使用或替换的结论。

基本运行结构必须从任务进入评测开始，讲到 Agent 使用模型或工具、产生答案或改变环境、评分和结果汇总。使用一张简单流程图，不从代码模块或专业术语讲起。

用一张表说明“Agent 范围、评测方式、评测能力”的对应关系。至少区分：无工具的模型、受限工具 Agent、多步多工具 Agent、需要改变环境或交付产物的端到端 Agent。明确当前 Benchmark 属于哪一类。

标准实验结构说明基线组、Agent 实验组、控制条件、重复运行、评分和失败分析。这里讲实验怎样比较，不介绍代码文件。

写作时遵守以下规则：

- 先说结论，再解释原因；
- 能用“评分程序”“最终状态检查”“运行框架”说清楚时，不堆叠 Judge、Verifier、Harness 等英文词；
- 专业词只在确有必要时保留，首次出现立即用中文解释；
- 一段只回答一个问题，避免连续罗列近义术语；
- 第 4 章保留协议细节，整体总结只讲结构和结论；
- 表格用于表达对应关系，不把每个细节都拆成表格。

判断可用性时分开写：

- **数据可用性**：能否获取、是否 gated、许可证和防泄漏限制；
- **运行可用性**：官方 Harness、模型/API、工具服务和依赖是否仍可直接运行；
- **评测有效性**：污染、题量、任务覆盖和 Judge 是否仍支持目标结论。

推荐替代基准时比较任务目标、Agent 交互、Judge、公开程度、运行成本和不能替代的部分。

### 9. 验收

完成前检查：

1. 报告中的样本数、评测文件关系和被消费字段能由数据或实现复核；
2. 第 3 章只有“构建动机”“数据文件、规模和结构”“数据如何被后续评测消费”三节；
3. 没有数据构建过程，也没有枚举后续评测不消费的字段；
4. 每个专业术语首次出现前有直白解释，并包含合成简化示例和 `text` 结构图；
5. 数据本体、模型、Agent Scaffold、工具、环境和 Judge 没有混淆；
6. 单样本从构造到聚合的流程完整，Judge、主指标和失败计分定义清楚；
7. 第 4 章先提取公共环节，再为流程不同的每种协议提供独立示例；
8. 第 4 章没有 Markdown 表格，简单流程使用 `text` 图，复杂循环才使用 Mermaid；
9. 原能力、结果、意义、局限和结论已合并为单一“Benchmark 整体总结”；
10. 总结包含基本运行结构、核心标准、三者对应关系和标准实验结构；
11. 总结说明当前 Agent Benchmark 的局限和有证据的发展趋势；
12. 全文优先使用常用中文，删除不影响结论的生僻术语；
13. 当前状态、替代基准和发展趋势使用分析日期附近的一手资料；
14. 没有“代码实验”或逐文件实现介绍；
15. 没有泄漏受限样本；
16. 引用均为实际使用的一手来源；
17. 报告目录只包含最终产物，不留下临时盘点文件；
18. Skill 变更后运行 `quick_validate.py`。
